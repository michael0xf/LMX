# ТЗ для Fable: операнды, строки, аргументы и исполнение выражений

**Дата:** 18 ноября 2026 года.  
**Редакция:** 2 — исполнение по требованию и `string(identificator)`.  
**Статус:** требования к следующей редакции спецификаций и реализации LMX.  
**Основание:** последние решения автора в обсуждении; текущие документы редакций (6) и (2), перечисленные в §11.

## 1. Задача и обязательные изменения

Реализовать и согласованно описать шесть изменений:

1. Добавить ресивер **`operand:`**, который объявляет пользовательский операнд и связывает его с пользовательской Structure. Применение: `(foo 1 2 3 4)`.
2. Распространить действующий механизм передачи единственной Structure на единственный Array. **Анализ сигнатур, выбор прочтения, отсутствие предпочтений и диагностика неоднозначности должны быть точно теми же.**
3. Разделить самостоятельный именованный аргумент и присваивание, встроенное в выражение аргумента. Встроенное присваивание изменяет соответствующее `data` и возвращает значение в выражение; отдельного actual argument из него не возникает.
4. Привести приоритеты и ассоциативность поддерживаемых операций к Си. Для `**` сохранить указанное ниже правило Python.
5. Вычислять необходимые значения по требованию потребляющего их ресивера. Связанное с конкретным вхождением присваивание исполняется и при более низком приоритете, сохраняя свою правую часть и возвращая присвоенное значение.
6. Добавить `string(identificator)`: получение написания любого идентификатора из существующей служебной таблицы как обычной LMX-строки — массива символов переменной длины.

Последние решения автора имеют приоритет над противоречащими им фрагментами предыдущих редакций. Требуется обновить примеры и реализацию, а не дописать рядом ещё одну несовместимую норму.

Выражение остаётся Structure. Сохраняются один общий парсер, чистый граф и существующие механизмы разрешения имён, приёма аргументов и исполнения. Приоритеты относятся к анализу и исполнению выражения после P0. Изменения не дают P0 права удалять контейнеры, менять написанную вложенность или переустраивать `parent` и `length`.

## 2. Пользовательский операнд: ресивер `operand:`

### 2.1. Имя и форма объявления

Предлагаемое и используемое в этом ТЗ имя — **`operand`**, в соответствии с авторским термином «операнд».

```text
operand: foo Target
```

Здесь:

- `foo` — объявляемое имя пользовательского операнда;
- `Target` — ссылка на пользовательскую Structure, с которой связывается его действие.

После объявления:

```text
(foo 1 2 3 4)
```

применяет связанную Structure к указанной цепочке аргументов.

**Новый операнд явно выделяется из множества идентификаторов.** Указанное объявление сообщает, что `foo` в выражении имеет роль операнда. Само наличие обычной Structure с каким-либо именем в пространстве имён этой роли не создаёт. Лексически имя может оставаться идентификатором; его объявленная роль учитывается общим семантическим механизмом.

### 2.2. Контракт применения

Связывание аргументов, выбор допустимой сигнатуры, преобразования, admission и исполнение используют общие правила LMX. Для `foo` действуют и правила единственного контейнера из §3.

Аналогия с `(+ 1 2 3 4)` означает возможность такого применения в выражении. Она не делает любую целевую Structure автоматически принимающей произвольное число аргументов. Допустимые входы определяет её собственный контракт.

Целью является Structure. Не вводить дополнительное требование оборачивать всякую цель в `fn`. Одновременно регистрация не создаёт результат, которого у целевого исполнения нет: если окружающему выражению нужно значение, действуют обычные требования языка к получению результата.

Объявление, видимость имени и разрешение конфликтов подчиняются действующим правилам контекста. Не вводить специальную глобальную область видимости для пользовательских операндов.

### 2.3. Реализация

Объявление хранится обычным образом в чистом графе. Производный индекс зарегистрированных имён допустим как часть существующей обработки контекста; он не становится самостоятельным скрытым реестром программы.

Общий P0 сохраняет написанную структуру. Распознавание роли `foo` не требует второго парсера или обращения P0 к сигнатурам. Реализация должна использовать общий этап разрешения и потребления структур.

При известном связывании транслятор генерирует обычный вызов выбранной реализации. Наличие пользовательского операнда само по себе не требует вызова интерпретатора из каждого нативного метода.

Минимальная обязательная форма в рамках этой задачи — префиксное применение `(foo …)`. Объявление новых символических токенов, произвольных инфиксных приоритетов и макросистемы в задачу не входит.

## 3. Единственный Array и цепочка аргументов

### 3.1. Нормативное положение

> Передача единственного Array допускает то же прочтение в виде цепочки его непосредственных элементов, что передача единственной Structure — в виде цепочки её непосредственных полей. Для Array и Structure применяется один и тот же общий алгоритм анализа сигнатур и выбора прочтения. У Array нет собственного приоритета раскрытия, специального выбора по длине или исключения для одноаргументной сигнатуры.

В текущей модели LMX все Array имеют переменную длину; строки также являются Array. Это ТЗ не вводит отдельного вида фиксированных массивов.

Это тождество относится к передаче аргументов. Оно не утверждает, что Array и Structure имеют одинаковое физическое представление или удовлетворяют любому одному и тому же типизированному формалу.

Ссылка на контейнер обрабатывается по содержимому контейнера, на который она ссылается. Правило не ограничивается контейнерами, записанными непосредственно в месте вызова.

### 3.2. Общий алгоритм выбора

Опорная действующая норма — §11 текущей семантики, подразделы «The general algorithm» и «How the declaration is chosen». Расширить её с единственной Structure на единственный Array:

1. Собрать все объявления вызываемого имени, видимые в месте вызова.
2. Для единственного допускающего раскрытие контейнера рассмотреть оба прочтения: **контейнер как один аргумент** и **цепочка его непосредственных элементов/полей**.
3. Проверить оба прочтения против каждого объявления, включая объявление с одним формалом.
4. Для каждой пары «объявление — прочтение» применить общие правила соответствия позиций и имён, отсутствующих значений, defaults, `required`, преобразования и admission через действующий `implements`.
5. Ровно одна допустимая пара определяет вызов. Ни одной — отказ. Больше одной — неоднозначность.

**Порядка предпочтения между объявлениями или прочтениями нет.** Нельзя сначала принять целый контейнер и проверять раскрытие лишь при неудаче: такой порядок скроет допустимое второе прочтение и неоднозначность.

Само количество формалов не создаёт приоритета. Например, формы с одним входом и с двумя входами, второй из которых необязателен, могут пересекаться. Такое пересечение выявляется общим алгоритмом; `required` может устранить его за счёт допустимости вызовов, а не «более точной арности».

### 3.3. Границы раскрытия

- Раскрытие происходит **только при обработке вызова**, ровно на один уровень. Исходный контейнер и чистый граф сохраняются.
- Вложенный Array или Structure остаётся одним элементом полученной цепочки. Рекурсивного автоматического раскрытия нет.
- Единственный элемент контейнера также может стать единственным actual argument. Наличие одного формала не запрещает это прочтение.
- Пустой контейнер при раскрытом прочтении даёт пустую цепочку. Дальше действуют обычные defaults, отсутствие значения и `required`.
- Явная именованная передача `f(a := A)` передаёт `A` целиком в `a`. Аналогично `f(a := S)` для Structure. Эти формы не запускают раскрытие.
- Ресиверы, принимающие написанные аргументы как `data`, сохраняют свой действующий контракт без такого раскрытия.
- При раскрытии Structure поле-объявление сохраняет имя. Его соответствие формалу проверяется по существующим правилам именованной и позиционной передачи. Элемент Array не получает выдуманного имени.
- Для Array чисел передаются типизированные элементы соответствующего типа; для Array ссылок — элементы ссылочного типа. Плотный массив чисел нельзя переинтерпретировать как массив указателей.
- Если контейнер получен вычислением с эффектом, это вычисление выполняется один раз в предусмотренной точке исполнения. Перебор кандидатов не должен повторять его.
- Анализ кандидатов не запускает тело целевой Structure и не приводит к повторному исполнению присваиваний в её `data`.

### 3.4. Что именно означает «точно как Structure»

Для сравнения алгоритма тестовые Array и Structure должны иметь соответствующие последовательности элементов и **одинаковые условия совместимости** с проверяемыми формалами. Если один формал специально принимает Array, а другой — Structure, разные результаты допустимости объясняются контрактами типов.

| Условия | Результат для обоих видов контейнеров |
| --- | --- |
| Целый контейнер не подходит; подходят два элемента двум входам | Вызов с цепочкой этих двух элементов |
| Один формал принимает элемент, но не контейнер | Раскрытие и один actual argument |
| Один формал принимает контейнер, но не элемент | Передача контейнера целиком |
| Подходят целое и раскрытое прочтения | Ошибка неоднозначности |
| Не подходит ни одно прочтение | Отказ по общему механизму |
| Контейнер явно передан по имени | Передача контейнера целиком |

Нативный код получает уже подготовленные транслятором вызовы. Это ТЗ не добавляет в него обязательный повторный выбор сигнатуры и автоматический `implements` на каждом вызове. Сохраняется действующее разграничение трансляции, интерпретации и подготовленного нативного исполнения.

Реализация раскрытия не должна требовать временной Structure или отдельной упаковки каждого элемента только ради передачи аргументов. Допустимо использовать представление последовательности поверх существующего контейнера.

## 4. Именованный аргумент и встроенное присваивание

### 4.1. Два разных структурных случая

| Случай | Значение |
| --- | --- |
| `v := expression` занимает самостоятельную позицию аргумента | Именованный actual argument `v`, получающий результат правой части |
| `v := expression` находится внутри выражения аргумента | Запись в соответствующее `data`; присвоенное значение участвует в окружающем выражении |

Встроенное присваивание не создаёт дополнительный actual argument, не занимает дополнительную позицию и не сдвигает позиционный курсор. Результат всего выражения передаётся как один аргумент.

Различие определяется структурным положением записи после общего разбора. Если потребителю требуется результат встроенного присваивания, он получает его по правилу §5: связанное присваивание вычисляется и при более низком приоритете. Одного совпадения имени с формалом для такой связи недостаточно.

### 4.2. Основной пример без дополнительных скобок

```text
f(1 + v := 2 + 3)
```

Написанная цепочка:

```text
1 plus: v let: 2 plus: 3
```

Разбор исполнения:

1. Первому `plus` нужны `1` и результат конкретного встроенного присваивания, связанного с этим вхождением `v`.
2. `plus` требует этот результат. Меньший приоритет `let` не запрещает исполнить его для получения нужного значения.
3. В правой части присваивания `plus` имеет более высокий приоритет, чем `let`. Поэтому сначала вычисляется `2 + 3 = 5`.
4. В соответствующее **data вызываемой `f`** записывается `v := 5`. Значением этого присваивания является `5`.
5. Первый `plus` получает `1 + 5 = 6`.
6. `f` получает **один** позиционный actual argument `6`.

По результату и записи в `v` это соответствует:

```text
f(1 + (v := 2 + 3))
```

Скобки в последней записи лишь показывают получившееся вычисление. В исходный граф дополнительный контейнер не добавляется.

Запись не превращается в `f(v := 5; 6)`. Отдельное одноимённое место `v` вызывающего контекста не становится целью присваивания.

В проверочной функции первый формал должен называться, например, `x`, а `v` быть другим полем её `data`. Наблюдаемый результат: `x = 6`, `v = 5` и ровно один actual argument. Даже если `v` уже содержало `100`, результат именно этого выражения остаётся таким же.

Использовать существующее соответствующее `data` получателя. Это требование само по себе не вводит копию графа, новую модель кадра или специальный механизм обратной записи.

### 4.3. Явная группа задаёт другой эффект

```text
f(1 + (v := 2) + 3)
```

Здесь правая часть сгруппированного присваивания — только `2`:

1. В data `f` записывается `v := 2`.
2. Значение присваивания `2` участвует в окружающем выражении.
3. Вычисляется `1 + 2 + 3 = 6`.
4. Передаётся один позиционный actual argument `6`.

Эта запись также допустима. В ней `v = 2`, тогда как в §4.2 `v = 5`. Совпадение итогового аргумента `6` не означает совпадения эффектов.

### 4.4. Самостоятельный именованный аргумент

```text
f(v := 2 + 3; 6)
```

даёт:

```text
f(v := 5; 6)
```

Здесь два actual arguments: самостоятельный именованный `v := 5` и следующий позиционный `6`.

Для этого положительного примера формал `v` должен стоять первым. По действующему правилу именованный аргумент на своей позиции считается позиционным, и передача может продолжиться позиционно.

Если `v` находится на другой позиции, сохраняется общее ограничение: после именованного аргумента вне своей позиции следующие аргументы тоже должны быть именованными.

Исполнение по требованию внутри выражения не меняет структурную роль этой самостоятельной записи и не отменяет правил именованной передачи.

### 4.5. Сопоставление редакций и проверка эффектов

В прежней норме присваивание имело высокий приоритет. Текущая норма сочетает низкий приоритет присваивания с вычислением необходимого результата по требованию.

| Запись | Прежний высокий приоритет: `v` / аргумент `f` | Текущая норма: `v` / аргумент `f` |
| --- | --- | --- |
| `f(1 + v := 2 + 3)` | `2 / 6` | `5 / 6` |
| `f(10 * v := 2 + 3)` | `2 / 23` | `5 / 50` |
| `f(1 + v := 2 * 3)` | `2 / 7` | `6 / 7` |

В среднем примере новое исполнение: `2 + 3 → 5`, запись `v := 5`, затем `10 * 5 → 50`. Это отличает новую норму от ошибочного временного повышения приоритета `let`, которое сохранило бы `v = 2` и дало бы `23`.

Убрать из предыдущей редакции ТЗ тезис, что после понижения приоритета присваивания пример без скобок остаётся без определённого результата и обязательно требует скобок. Новое правило определяет и результат, и записанное значение.

При переводе примеров проверять оба наблюдаемых результата. Скобки добавлять только для выражения требуемой границы вычисления; механическое добавление скобок может изменить значение присваивания.

## 5. Исполнение по требованию и эффекты

### 5.1. Общее правило

> Перед исполнением ресивера вычисляются необходимые ему значения. Если необходимое значение является результатом другого ресивера, тот исполняется по требованию независимо от сравнительного приоритета этих двух ресиверов. Его аргументы и правая часть сохраняют границы, определяемые структурой и приоритетами.

Приоритет определяет обработку и принадлежность операций в выражении. Зависимость по значению определяет, что необходимо вычислить до завершения потребителя. Более высокий приоритет потребителя не запрещает ему сначала получить результат зависимой операции с меньшим приоритетом.

В примере §4.2 низкий приоритет `let` позволяет вычислить внутри его правой части `2 + 3`; зависимость левого `plus` от результата `let` требует завершить присваивание перед сложением с `1`.

**Исполнение по требованию не повышает приоритет присваивания.** Вызвать `let` раньше потребителя не означает взять только первый атом `2`, оставив `+ 3` снаружи. Правая часть вычисляется по действующим низким приоритетам присваивания.

Правило относится к общему механизму expression, включая зарегистрированные пользовательские операнды. Для каждого ресивера сохраняется его контракт потребления: например, логическая операция может не потребовать правый операнд.

Исполнение по требованию следует связям получения значения, установленным общим анализом выражения. Само соседство записей такой связи не создаёт. В `10 * 2 + 3` умножению требуется непосредственно число `2`; вычисляется `(10 * 2) + 3 = 23`. В `10 * v := 2 + 3` потребляемое вхождение связано с результатом конкретного присваивания `v`; его правая часть даёт `5`, поэтому результат равен `50`. Приоритеты обычных арифметических цепочек сохраняются.

### 5.2. Связь с конкретным вхождением

Связь между потребляемым вхождением и производящей его значение операцией устанавливает общий анализ выражения после P0.

В `1 + v := 2 + 3` нужен результат **этого** присваивания `v`. Наличие старого значения у места не отменяет требование получить результат. При прежнем `v = 100` новое значение равно `5`, а результат выражения — `6`.

Обычное чтение имени сохраняет свою роль. Оно не запускает поиск ещё не выполненных одноимённых присваиваний в окружающем коде. Обычное имя Structure также не превращается в неявный вызов.

В обычной записи кода:

```text
v := v + 1
```

правое `v` читает значение уже известного места до этой записи. При `v = 100` оно даёт `100`, сумма — `101`, присваивание записывает `101`. Правое `v` не требует повторно исполнить само это присваивание.

Таким образом, требование значения привязано к конкретной операции выражения, а обычное чтение переменной — к соответствующему месту по действующим правилам разрешения.

### 5.3. Однократность и результат операции

В одном динамическом вычислении конкретное вхождение операции исполняется один раз. Если оно уже исполнено по требованию, последующее достижение этого вхождения обходчиком использует результат и не повторяет эффект.

Например, при `read_once()`, возвращающем `4`:

```text
f(1 + v := read_once() + 3)
```

получаются одно чтение, `v = 7` и один аргумент `8`. Тело `f` запускается после получения аргумента.

Сохраняется результат операции — присвоенное ею значение. Его получение потребителем не подменяется повторным чтением изменяемого места после возможных других записей.

Однократность относится к конкретному исполнению выражения. Новый вызов, новая итерация или новая проверка условия выполняют его заново. Вычисленный однажды результат не становится постоянным кэшем в исходном графе.

При ошибке вычисления необходимого значения потребитель не получает выдуманного результата; применяются обычные правила отказа и обработки ошибок. Вычисление по требованию не оправдывает пробные исполнения при переборе сигнатур.

### 5.4. Скобки и короткое замыкание

Приоритет и группировка не разрешают заранее выполнить все вложенные группы и присваивания независимо от потребности в результате.

Для поддерживаемых `&&` и `||` сохраняется короткое замыкание:

```text
0 && (x := 1)
1 || (x := 1)
```

В обоих случаях правый операнд не требуется и `x` не изменяется. Аналогично не исполняется вызов с эффектом внутри пропущенной части выражения.

Сначала потребитель определяет, какие значения нужны на достигнутом пути, затем запрашивает их. Общего предварительного прохода по всем присваиваниям и скобкам нет. Пропущенная операция не должна позднее исполниться лишь потому, что обходчик дошёл до её записи.

Порядок вычисления действительных аргументов остаётся установленным правилами LMX. Перенос таблицы приоритетов Си не переносит автоматически все особенности или неопределённости порядка вычисления в Си.

### 5.5. Условие `while`

Автором подтверждена следующая пара:

```c
while ((c = getchar()) != EOF)
```

```text
while ((c := getchar()) != EOF)
```

У `while` используется то же `data`, что у окружающего callable. На каждой проверке условия:

1. Сравнению нужно значение сгруппированного присваивания.
2. `getchar()` исполняется один раз.
3. Результат записывается в `c` этого общего `data` и становится значением присваивания.
4. Это значение сравнивается с `EOF`.
5. `while` получает одно логическое значение условия.

Дополнительного именованного аргумента `c` нет. Присваивание не выносится в однократную подготовку перед циклом и не исполняется второй раз при той же проверке.

Проверка на источнике, последовательно возвращающем `A`, `B`, `EOF`: три чтения, два исполнения тела, после последней проверки `c` содержит `EOF`. Тип `c` должен допускать значения символов и `EOF`.

Не объявлять эквивалентной форму `while(c := getchar() != EOF)`. В присваивании с такой правой частью сначала вычисляется сравнение, поэтому присваиваемое значение — его логический результат; кроме того, самостоятельная именованная запись проверяется по контракту аргументов `while`. Исполнение по требованию не отрезает `!= EOF` от правой части.

## 6. Приоритеты и ассоциативность

### 6.1. Основная таблица

Привести к следующему относительному порядку все перечисленные операции, которые уже поддерживаются соответствующим профилем LMX. Сверху — сильнее. Отдельное правило `**` дано в §6.2.

| Уровень | Операции | Ассоциативность |
| --- | --- | --- |
| Постфиксный | Вызов, индекс, доступ к полю; постфиксные `++` и `--` | Слева направо |
| Унарный | Префиксные `+`, `-`, `!`, `~`, `++`, `--`; существующие адресные операции | Справа налево |
| Умножение | `*`, `/`, `%` | Слева направо |
| Сложение | `+`, `-` | Слева направо |
| Сдвиги | `<<`, `>>` | Слева направо |
| Отношения | `<`, `<=`, `>`, `>=` | Слева направо |
| Равенство | `=`, `!=` | Слева направо |
| Побитовое И | `&` | Слева направо |
| Побитовое исключающее ИЛИ | `^` | Слева направо |
| Побитовое ИЛИ | `\|` | Слева направо |
| Логическое И | `&&` | Слева направо |
| Логическое ИЛИ | `\|\|` | Слева направо |
| Присваивание | `:=` и существующие составные присваивания, включая `**=` | Справа налево |

В LMX `=` остаётся сравнением, соответствующим `==` в Си. Присваивание записывается `:=`. Написание существующих составных присваиваний этой задачей не меняется.

Существующие в машинном профиле преобразования типов и `sizeof` должны быть согласованы с соответствующими отношениями в грамматике Си. Отсутствующие `?:` и оператор запятой вводить не требуется. `,` и `;` сохраняют свои структурные функции LMX.

Таблица задаёт относительный порядок, а не конкретные числовые значения внутренних приоритетов. Получение необходимых значений происходит по §5; низкий приоритет источника значения не запрещает вычислить его до потребителя. Основание для сопоставления с Си — грамматика выражений N1256, §§6.5.2–6.5.16; ссылка в §11.

### 6.2. Исключение: степень `**`

Сохранить действующее Python-подобное связывание:

- вызов, индекс и доступ к полю связывают сильнее `**`;
- `**` связывает сильнее `*`, `/` и `%`;
- цепочка степеней группируется справа;
- слева `**` связывает сильнее унарных `+`, `-`, `~`;
- справа `**` допускает унарный операнд.

Обязательные примеры:

```text
-2 ** 2       → -(2 ** 2)       → -4
(-2) ** 2                       → 4
2 ** -2       → 2 ** (-2)
2 ** 3 ** 2   → 2 ** (3 ** 2)   → 512
2 * 3 ** 2    → 2 * (3 ** 2)    → 18
```

Для `2 ** -2` здесь фиксируется группировка. Числовой результат и допустимые типы определяет числовой контракт LMX; вся числовая семантика Python автоматически не переносится.

Это асимметричное правило нельзя заменить одной строкой «степень выше всех унарных операций». Для остальных унарных операций, не имеющих такого аналога в Python, не приписывать Python выдуманное поведение. Сохранить действующие отношения LMX и явно отразить их в полной таблице реализации.

### 6.3. Приоритеты Си и зависимость по значению

Запись:

```text
1 + v := 2 * 3
```

остаётся структурной цепочкой:

```text
1 plus: v let: 2 mult: 3
```

Ресивер присваивания связан с написанным `v`. Нельзя пересобрать его левую часть в `1 + v` и выдать ошибку «присваивание сумме», ссылаясь на грамматику Си.

Исполнение по текущей норме:

1. Левому `plus` нужен результат связанного с этим вхождением `let`.
2. Для получения результата `let` вычисляет свою правую часть: `2 * 3 = 6`.
3. `let` записывает `v := 6` и возвращает `6`.
4. `plus` вычисляет `1 + 6 = 7`.

Итог определён: **`7` и `v = 6`**, в том числе при другом ранее записанном значении `v`. Нельзя читать прежнее значение только потому, что `plus` имеет более высокий приоритет, чем `let`.

В этом примере явная запись:

```text
1 + (v := 2 * 3)
```

даёт тот же результат и тот же эффект. Это совпадение конкретных вычислений; исходная форма без скобок не получает новый анонимный контейнер в P0.

Для согласованного с Си подмножества проверить:

```text
c := (a := 10) + (b := 20) * 2
```

Сгруппированные присваивания возвращают `10` и `20`; умножение даёт `40`, сумма — `50`, затем записывается `c := 50`. Итог: `a = 10`, `b = 20`, `c = 50`.

Для правой ассоциативности:

```text
a := b := 10
```

внешнему присваиванию нужен результат внутреннего: сначала `b := 10`, затем `a := 10`.

Меняются приоритеты и правила получения значений, а базовая структурная грамматика сохраняется. Допустимость дополнительных форм LMX, запрещённых в Си, сама по себе не противоречит совпадению результатов на общем подмножестве.

Backend получает результат анализа LMX. Текстовая замена `:=` на `=` с передачей исходного выражения Си-компилятору не является реализацией этого требования.

### 6.4. Интерпретация и нативная генерация

Интерпретатор получает результат необходимой операции через общий механизм исполнения и не повторяет уже выполненное в текущем вычислении вхождение.

При статически известных связях транслятор может заранее выстроить последовательность вычислений. Например, для `f(10 * v := 2 + 3)` она состоит из сложения, записи в data `f`, умножения полученного значения на `10` и вызова `f` с одним аргументом.

Вычисление по требованию не требует динамически искать присваивание при каждом чтении переменной. Рабочие результаты исполнения и временные значения нативного кода не должны превращаться в новые постоянные поля чистого графа.

## 7. `string(identificator)`: имя как LMX-строка

### 7.1. Нормативный контракт

> `string(identificator)` принимает написанный идентификатор и возвращает его имя как обычную строку LMX — `Lmx` Array символьных элементов переменной длины. Написание получается из существующего представления канонического имени и служебной таблицы имён.

Пример:

```text
string(foo) → "foo"
```

Ресивер потребляет аргумент **как идентификатор**. Он не разрешает его как переменную, не читает связанное значение, не вычисляет инициализатор и не вызывает Structure или метод. Имя не обязано иметь объявление: «из любого идентификатора» включает любое корректное написание, уже распознанное общим парсером.

Если `foo` — переменная со значением `42`, результатом остаётся строка `"foo"`. Если `foo` — метод или зарегистрированный через `operand:` операнд, получение имени не запускает его исполнение. Для указателя `ptr` возвращается `"ptr"`, а не имя объекта, на который он указывает.

Эта форма принимает один идентификатор. Она не вводит универсального преобразования произвольных значений в текст. Несоответствующий аргумент обрабатывается по существующим правилам недопустимой формы.

### 7.2. Написание идентификатора

Возвращается значение имени после обычного разбора идентификатора. Оформление exact identifier снимается по действующему правилу: внешние обратные кавычки удаляются, удвоенная обратная кавычка внутри становится одной.

```text
string(foo)          → "foo"
string(`foo`)        → "foo"
string(`long name`)  → "long name"
string(`a``b`)       → "a`b"
string(``)           → ""
```

Прочие допустимые символы имени сохраняются. Пустой exact identifier даёт пустой массив символов. Новая кодировка, нормализация регистра или ограничение длины имени не вводятся.

Это получение написания идентификатора из существующего представления, а не сериализация значения переменной или повторный разбор исходного текста.

### 7.3. Представление и получение результата

В текущей норме одно написание представлено одной повторно используемой канонической строкой со стабильным адресом. Имя сущности получается через существующую служебную таблицу. Старую схему отдельных числовых кодов идентификаторов восстанавливать не требуется.

Реализация:

1. Получить каноническое имя написанного аргумента через существующее представление идентификатора и служебную таблицу.
2. Выдать его как обычную строку LMX, используя имеющееся строковое представление.
3. Сохранить обычные контракты владения и доступа к этому представлению.

Результат имеет общий дескриптор `Lmx` и обычный массив `char` переменной длины. Других видов массивов по фиксированности длины текущая модель не вводит. Для `foo` длина результата равна `3`; для пустого имени — `0`. Завершающий NUL не входит в строку LMX.

Использовать существующую строку и служебную таблицу. Новая таблица регистрации, повторное построение написания или обязательная аллокация и копирование на каждый вызов не требуются. Точная выдача ссылки или копии следует существующему контракту строк и служебных имён; это ТЗ не добавляет отдельной гарантии адресного тождества результатов.

Интерпретатор и подготовленный нативный код должны получать одинаковое содержимое и обычный Lmx-результат. Во время трансляции не требуется исполнять код обозначенной идентификатором сущности ради получения её имени.

Основания текущего представления: §4 семантики — канонические имена и служебная таблица; §5 грамматики — bare/exact identifiers; §5 L2 — строки как Array точной длины. Ссылки приведены в §11.

### 7.4. Связь с общими правилами

Контракт `string` потребляет написанный идентификатор. Общее исполнение не должно сначала вычислять этот аргумент как обычное значение или требовать результата зарегистрированного операнда с тем же именем.

Возвращённая строка является Array и участвует в общих правилах передачи:

```text
f(string(foo))
f(a := string(foo))
```

В первом случае выбор между целым массивом символов и цепочкой его элементов выполняется по §3, с обычной проверкой неоднозначности. Во втором случае массив передаётся целиком в именованный аргумент `a`. Особого исключения для строк нет.

## 8. Требования к выполнению работ

### 8.1. Общие точки реализации

Перед изменениями определить действующие места, отвечающие за:

- разрешение роли головы и идентификатора;
- обработку expression после P0 и связь конкретного вхождения с производящей его значение операцией;
- получение необходимых значений по требованию и однократное исполнение в рамках текущего вычисления;
- выбор объявления и прочтения единственного контейнера;
- последовательное связывание actual arguments с формалами;
- выбор соответствующего `data` для записи;
- генерацию нативного исполнения;
- получение канонического имени из служебной таблицы и выдачу его как Lmx-строки.

Обновить эти общие механизмы. В Array, пользовательском операнде и отдельном backend не должны появиться независимые версии алгоритма сигнатур или правил присваивания. `string` использует существующую обработку идентификаторов и таблицу имён.

Проверки и вычисления отделять по их контракту. Выбор кандидата не может служить поводом многократно выполнять пользовательские аргументы, писать в несколько кандидатных `data` или запускать тела. Проверки, возможные до выполнения аргументов, сохраняют действующее место.

### 8.2. Перевод старых примеров

Найти и исправить:

- «сначала все скобки, затем присваивания, затем остальные операции»;
- примеры, сохраняющие прежний высокий приоритет присваивания;
- утверждение, что меньший приоритет присваивания заставляет сначала прочитать прежнее или отсутствующее значение его цели;
- требование обязательно добавлять скобки в `f(1 + v := 2 + 3)` ради возможности исполнения;
- обходы, повторно исполняющие уже вычисленный по требованию ресивер или исполняющие пропущенную логическую ветвь;
- превращение встроенного присваивания в дополнительный именованный actual;
- безусловный запрет раскрытия при наличии одноаргументной сигнатуры;
- автоматическое предпочтение целого контейнера или совпадения арности;
- реализацию раскрытия через изменение P0 или исходного графа.

Если в документах сохранены исторические цитаты, явно отделить их от действующей нормы. При исправлении примеров проверять итоговое значение, записанные значения и число эффектов. Добавление скобок не должно незаметно подменять требуемый эффект.

Согласовать места, называющие expression «чистым»: они не должны случайно запрещать уже допускаемые присваивания и вызовы с эффектами. Действующие ограничения отдельных профилей описать отдельно, не переопределяя общий механизм.

### 8.3. Диагностика

В неоднозначном вызове показать конкурирующие объявления и прочтения: «контейнер целиком» и/или «цепочка элементов». Для недопустимого вызова использовать существующие сведения об именах, позициях, `required` и admission.

Для незарегистрированного `foo` не имитировать молчаливую регистрацию по факту разрешения обычного имени. Для ошибки присваивания указывать реальное место и правило LMX, а не выдуманную левую часть из Си. `string` не должен сообщать об отсутствии объявления у корректного идентификатора: получение написания не требует разрешения его значения.

## 9. Приёмочные проверки

Проверки ниже — требования к Fable, а не заявление, что реализация уже проверена. Выполнить их на интерпретаторе и применимых нативных путях. Различия, предусмотренные действующим контрактом admission для нативного кода, не устранять добавлением новых автоматических проверок.

### 9.1. Регистрация операнда

| ID | Проверка | Ожидаемый результат |
| --- | --- | --- |
| O01 | `operand: foo Target`; Target складывает четыре входа; `(foo 1 2 3 4)` | `10` |
| O02 | Обычное имя `bar` разрешается в Structure, но не объявлено операндом | Одного этого недостаточно для применения `(bar 1 2)` как нового операнда |
| O03 | Аргумент и Target увеличивают отдельные счётчики | Каждый необходимый эффект возникает один раз |
| O04 | Вызов через `foo` с единственным Array и с соответствующей Structure | Общий механизм из §3 |
| O05 | Сохранение и повторная загрузка графа с объявлением | Связь операнда восстанавливается из программы |
| O06 | Статически известное применение в нативном коде | Обычная генерация вызова без обязательного прохода интерпретатора |

### 9.2. Контейнеры

В A01–A08 выполнить парные случаи для Array и Structure с одинаковыми условиями совместимости.

| ID | Условие | Ожидаемый результат |
| --- | --- | --- |
| A01 | Два элемента подходят двум формалам; целый контейнер не подходит | Раскрытая цепочка |
| A02 | Один формал принимает элемент, но не контейнер | Раскрытие в один аргумент |
| A03 | Один формал принимает контейнер, но не элемент | Целый контейнер |
| A04 | Подходят оба прочтения | Неоднозначность |
| A05 | Ни одно прочтение не подходит | Отказ |
| A06 | Пустой контейнер; целое прочтение не подходит | Пустая цепочка с обычными defaults/`required` |
| A07 | Внутри контейнера находится другой контейнер | Только один уровень раскрытия |
| A08 | `f(a := C)` | `C` передаётся целиком |
| A09 | Пересекающиеся объявления с одним входом и двумя, второй optional | Неоднозначность, без предпочтения арности |
| A10 | Пересечение устранено требованием `required` | Выбор по допустимости |
| A11 | Контейнер возвращается эффектным вызовом | Этот вызов не повторяется при проверке кандидатов |
| A12 | P0 разбирает несколько вложенных контейнеров; затем обрабатывается вызов | Написанная вложенность сохраняется; семантическое раскрытие не изменяет исходный граф |

### 9.3. Аргументы, data и управление

| ID | Проверка | Ожидаемый результат |
| --- | --- | --- |
| D01 | `f(1 + (v := 2) + 3)`; первый формал `x`, отдельное поле `v` | Один actual; `x = 6`, `v = 2` |
| D02 | У вызывающего контекста тоже есть `v` | D01 и D09 пишут в data `f`; отдельное `v` вызывающего контекста не изменяется |
| D03 | `f(v := 2 + 3; 6)`; `v` — первый формал | Два actual; `v = 5`, второй формал получает `6` |
| D04 | Та же запись, `v` не на первой позиции | Сохраняется запрет positional после внепозиционного named actual |
| D05 | `while ((c := read()) != EOF)`; источник `A, B, EOF` | Три чтения, два исполнения тела, `c = EOF` |
| D06 | `0 && (x := 1)` | `x` не изменяется |
| D07 | `1 || (x := 1)` | `x` не изменяется |
| D08 | Неисполняемая правая ветвь содержит зарегистрированный операнд с эффектом | Target не запускается |
| D09 | `f(1 + v := 2 + 3)`; первый формал `x`, отдельное поле `v` | Один actual; `x = 6`, `v = 5` |
| D10 | D09 при прежнем `v = 100` и отдельно при объявленном месте без значения | В обоих случаях `x = 6`, `v = 5`; старое значение не подменяет результат присваивания |
| D11 | `f(1 + v := read_once() + 3)`; чтение возвращает `4` | Одно чтение; один actual `8`; `v = 7`; обход не повторяет присваивание |
| D12 | Два отдельных исполнения D11 | Два чтения всего; результат первого исполнения не кэшируется на второе |
| D13 | `f(0 && v := tick())` и `f(1 \|\| v := tick())` | `tick()` не вызывается; `v` не меняется; `f` получает один логический аргумент |
| D14 | В коде с объявленными местами: `v := 100; x := v; v := 5` | `x = 100`, `v = 5`; обычное чтение не запускает будущую запись |
| D15 | Несколько исполнений выражения с присваиванием по требованию | Сохраняются исходная вложенность, имена, `parent` и `length` чистого графа |

### 9.4. Приоритеты

| ID | Запись | Ожидаемый результат |
| --- | --- | --- |
| P01 | `2 + 3 * 4` | `14` |
| P02 | `(2 + 3) * 4` | `20` |
| P03 | `20 - 6 - 3` | `11` |
| P04 | `24 / 4 / 2` | `3` |
| P05 | `a := b := 10` | `a = 10`, `b = 10` |
| P06 | `c := (a := 10) + (b := 20) * 2` | `a = 10`, `b = 20`, `c = 50` |
| P07 | `-2 ** 2` и `(-2) ** 2` | `-4` и `4` |
| P08 | `2 ** -2` | Группировка `2 ** (-2)` |
| P09 | `2 ** 3 ** 2` | `512` |
| P10 | `2 * 3 ** 2` | `18` |
| P11 | `1 + (v := 2 * 3)` | `7`; `v = 6` |
| P12 | `1 + v := 2 * 3` | `7`; `v = 6`; сохраняется цепочка §6.3 |
| P13 | `v := v + 1` в обычном коде, прежде `v = 100` | `v = 101`; правое чтение не вызывает это же присваивание повторно |
| P14 | `10 * v := 2 + 3` | `50`; `v = 5`, включая случай с другим прежним значением |
| P15 | `c := (read() != EOF)` в обычном коде; `read()` возвращает `EOF` | Одно чтение; `c` получает логическую ложь, а не `EOF` |
| P16 | `10 * 2 + 3` | `23`; соседнее сложение не становится источником значения литерала `2` |
| P17 | `(+ 2 - 3)` | `-1`; сохраняется математическая запись общего expression |

Для поддерживаемых сдвигов, сравнений, побитовых и логических операций добавить минимальные проверки границ соседних уровней таблицы. Не ограничиваться арифметикой, оставляя остальные уровни по прежней схеме.

### 9.5. Идентификатор в строку

В примерах запись результата в кавычках обозначает символьное содержимое обычного Lmx Array.

| ID | Проверка | Ожидаемый результат |
| --- | --- | --- |
| S01 | `string(foo)` при необъявленном `foo` | `"foo"`, длина `3` |
| S02 | `string(foo)` при значении переменной `foo = 42` | `"foo"`; значение `42` не читается для преобразования |
| S03 | `string(foo)`, где `foo` — метод со счётчиком вызовов | `"foo"`; метод не вызывается |
| S04 | `string(x)`, где получение значения `x` потребовало бы инициализатора с эффектом | `"x"`; инициализатор не исполняется |
| S05 | `string(foo)` после `operand: foo Target` | `"foo"`; Target не исполняется |
| S06 | Первые два вызова из §7.2: один с bare identifier, другой с exact identifier | Одинаковое содержимое `"foo"` |
| S07 | Exact identifier с пробелами и пунктуацией | Содержимое имени сохраняется без внешних кавычек |
| S08 | Exact identifier с удвоенной обратной кавычкой | В результате одна буквальная обратная кавычка |
| S09 | Пустой exact identifier | Пустой массив символов, длина `0` |
| S10 | `string(ptr)`, где `ptr` указывает на `Target` | `"ptr"` |
| S11 | Получение имени в интерпретаторе и подготовленном native-коде | Одинаковое содержимое; обычный Lmx char Array переменной длины, без добавочного NUL |
| S12 | `f(string(foo))` и `f(a := string(foo))` | Общий выбор прочтения Array в первом случае; целый Array в именованной передаче |
