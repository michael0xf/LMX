## Callable: формирование аргументов до точной сигнатуры; return вложенного callable через merge

Источник: задача автора в чате fable 2026-09-24 («вот еще задача в next_core_tasks.md»), дословно:

````text
Нужно внести два связанных изменения в спецификацию и реализацию callable.

1. Требуется: применять обычные правила формирования аргументов и результата ДО проверки конечной callable-сигнатуры
Сейчас в §6 implements фактически требует буквального равенства исходных callable-сигнатур:

sig(aVar.p) = sig(bVar.p) = ExpectedSig(Consumer, p)
а §7.13 отдельно говорит, что converter table не влияет на exact callable signatures.

Это надо изменить.

Смысл должен быть таким:

При прямом вызове и вызове через переданный callable аргументы сначала формируются по общим правилам подстановки и присвоения, включая доступные преобразования и проверки их контрактов. Точное соответствие дескриптору реально выбранного вызываемого выражения требуется после формирования аргументов. Различие исходных типов само по себе не является основанием для отказа, если требуемые аргументы могут быть сформированы по обычным правилам языка.

Возвращённое значение принимается по тем же общим правилам, включая преобразование к типу, требуемому получателем результата.

То есть не надо создавать специальную систему covariance/contravariance или отдельный механизм adapter для callable. Это обычное формирование аргументов и обычное принятие результата, которое уже существует для значений.

Требование конечного точного соответствия можно сохранить. Меняется только точка, в которой оно проверяется:

actual source value
    ↓
ordinary assignment/substitution rules
    ↓
conversion if explicitly available
    ↓
formed argument
    ↓
exact match with selected callable argument descriptor
И аналогично для результата:

selected callable result
    ↓
ordinary receiving/assignment rules
    ↓
conversion if explicitly available
    ↓
value required by the result consumer
Изменение текста §6
Формулу надо изменить так, чтобы для invoked callable сравнивалась не буквальная исходная сигнатура кандидата с исходным exemplar descriptor, а проверялось, что каждый реально требуемый аргумент может быть сформирован для выбранного callable по общим правилам consumption/conversion, после чего сформированный вызов точно соответствует его дескриптору.

То есть концептуально вместо:

sig(aVar.p) = sig(bVar.p) = ExpectedSig(Consumer, p)
нужно что-то в духе:

invoked_callable(p) ⇒
    call_arguments_formable(
        ExpectedCall(Consumer, p),
        sig(aVar.p)
    )
    ∧ formed_call_matches_exactly(sig(aVar.p))
    ∧ result_consumable(
        result(sig(aVar.p)),
        ExpectedResult(Consumer, p)
    )
Названия предикатов здесь не обязательны; важно зафиксировать семантику.

§7.13 тоже надо изменить: broad converter table по-прежнему не создаёт неизвестные пути и не ищет скрытые conversion chains, но доступные явные conversions должны участвовать в обычном формировании аргументов callable и принятии его результата.

Проверочный пример
fn: s (string: x) int
return: x + "1"

fn: apply (op(fn: (int: x) int) int(value)) int
return: op(value)

print: apply(s 10)
Здесь:

apply получает value = int 10

op фактически указывает на s

для реального вызова s:
    int 10
        → обычное разрешённое преобразование
        → string "10"

формируется точный аргумент s:
    string: x "10"

s выполняет:
    "10" + "1"
        → "101"

s объявлена возвращающей int:
    "101"
        → обычное преобразование string → int
        → 101

apply принимает int и возвращает:
    101
Ожидаемый результат:

101
Если бы s была объявлена возвращающей string, это тоже не должно само по себе запрещать использование:

fn: s (string: x) string
return: x + "1"
Тогда s вернула бы "101", а преобразование string → int произошло бы при принятии результата там, где apply требует int.

Это близко по назначению к возможности написать в Haskell:

apply :: (a -> b) -> a -> b
apply f x = f x
но в LMX обобщение достигается не обязательными type variables a/b, а существующими правилами структурного admission, формирования аргументов и явных conversions.

2. Требуется: return вложенного callable должен материализовать новую callable-Structure через обычный merge
Пример:

fn: getXplusN (int: n) (fn: (int: x) int)
    fn: addN (int: x) int
        return: n + x

    return: addN
Текущее правило о nested functions надо сохранить:

Само вложенное определение не захватывает frame вызывающей функции. Вызов getXplusN не должен создавать hidden closure environment и не должен heapify весь activation frame.

Но надо дополнить семантику return: addN.

Если возвращаемый callable использует значения текущей активации, return должен сначала сформировать самостоятельное возвращаемое значение через обычный механизм merge.

В данном примере addN использует внешний n.

При:

getXplusN(5)
текущее значение аргумента представляет Structure примерно:

int: n 5
При вычислении:

return: addN
строится новый callable посредством обычного merge:

merge(
    addN,
    current-used-values
)
где из текущей активации реально требуется только:

int: n 5
Результат семантически эквивалентен новой Structure:

fn: addN (int: x) int
    int: n 5
    return: n + x
Для:

getXplusN(100)
создаётся другая Structure:

fn: addN (int: x) int
    int: n 100
    return: n + x
После этого n уже является собственным полем сформированного callable. Это не dynamic input и не сохранённый аргумент старого frame.

При последующем вызове передаётся только обычный явный аргумент:

add5(1)
а n = 5 читается из собственной Structure add5.

Текст для спецификации
Предлагаю добавить правило примерно в таком виде:

Returned nested callable construction

When evaluation of a returned expression yields a callable whose body uses values supplied by the current activation outside that callable's own formal arguments or existing own fields, the returned callable value is constructed through the ordinary merge mechanism before the return transfer occurs.

Only values actually required by the returned callable's used graph are included. The current activation frame itself is not retained, copied, heapified, or attached as a hidden closure environment.

Required current values are supplied to merge as ordinary typed structural data. After composition they become own fields of the newly constructed callable Structure. References in the returned callable resolve to those own fields under the ordinary lexical rules; the corresponding names no longer require dynamic input from a later caller.

The ordinary merge rules remain unchanged: it follows the complete used graph and necessary lexical ancestry, copies mutable used state, preserves shared method references under their contracts, rewrites references and parent links, and does not copy unused state merely because it exists in an enclosing activation or lexical ancestor.

return itself still performs no additional copy. Construction of the returned callable belongs to evaluation of the returned expression; after that construction, return transfers the resulting reference with its exact identity.

Важное следствие
Для этого:

fn: getXplusN (int: n) (fn: (int: x) int)
    fn: addN (int: x) int
        return: n + x

    return: addN
не должно получаться:

returned addN + hidden saved activation argument n
и не должно сохраняться:

whole getXplusN stack frame
Должно получаться:

new callable Structure
    own field:
        int: n 5

    method/body:
        fn: addN (int: x) int
        return: n + x
То есть closure здесь получается обычным LMX-способом: специализацией/композицией Structure через merge, а не особым типом runtime closure.

При этом merge должен идти по обычному used graph вплоть до необходимых lexical ancestors. Он не копирует всё подряд до parent = 0: в результирующую mutable Structure попадает только реально используемая часть графа и необходимые связи. В данном примере из текущего runtime frame нужен только n, поэтому runtime добавляет фактическое:

int: n 5
Проверочный пример — аналог Haskell makeAdder
Haskell:

makeAdder :: Int -> (Int -> Int)
makeAdder n = \x -> n + x

add5   = makeAdder 5
add100 = makeAdder 100

-- (add5 1, add100 1, add5 1)
-- => (6, 101, 6)
LMX:

fn: makeAdder (int: n) fn: (int: x) int
    fn: addN (int: x) int
        return: n + x

    return: addN

add5: makeAdder 5
add100: makeAdder 100

[add5: 1; add100: 1; add5: 1]
Ожидаемый результат:

[6 101 6]
После makeAdder 5 структура add5 логически содержит:

fn: addN (int: x) int
    int: n 5
    return: n + x
После makeAdder 100 структура add100 логически содержит:

fn: addN (int: x) int
    int: n 100
    return: n + x
Это две разные callable occurrences / Structures, но общая неизменяемая реализация метода при этом не обязана копироваться.

Что надо проверить в реализации
Убрать ранний отказ только из-за буквального несовпадения primitive types в исходных callable descriptors.

Формировать actual arguments обычным существующим механизмом assignment/conversion.

После формирования требовать точное соответствие реально выбранной callable-сигнатуре.

Результат callable пропускать через обычный механизм consumption/conversion получателем.

Изменить соответствующие правила §6 и §7.13.

Для return вложенного callable обнаруживать значения текущей активации, реально используемые возвращаемым callable.

Строить самостоятельную callable-Structure через обычный merge с этими текущими typed values.

Не сохранять activation frame и не вводить отдельный hidden closure object.

После merge захваченные значения должны быть обычными own fields новой Structure.

Проверить два теста выше: callable с преобразованием аргумента/результата и makeAdder с двумя независимо сохранёнными значениями n.
````
