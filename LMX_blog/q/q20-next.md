# q20-next: как работал бы вариант «child 0 = {method, base}, поля от base» — и что именно сегодня ломается у скопированного merge метода

Состояние: 2026-09-24, материал для размышления (автор: «надо нажать на стоп и подумать … методы таким образом мержить нельзя»). **Merge методов не делаем** — ниже нет цепочек методов; только (1) точный разбор сегодняшнего поведения с измерением и (2) развёрнутое описание базовой адресации полей как одного из способов сделать скопированный метод верным. Ничего из этого не реализуется до вашего решения.

## 1. Что сегодня запечено в нативный код метода (по сгенерированному C)

Для метода `M` транслятор эмитирует функцию `l2_mN (node, self)` и адресует поля **абсолютными индексами**, вычисленными на трансляции по лексической раскладке:

- **свои own-поля** — `lmx_arena_ref_cell(self, 1U + k)`: `self` = вхождение метода (child 0 — дескриптор, дальше own-поля по порядку). Эти индексы **не зависят от merge**: merge копирует вхождение метода как поддерево целиком, внутренняя раскладка вхождения не меняется.
- **поля лексического родителя** — `node\x` → `lmx_arena_ref_cell(node, j)`: `node` = родитель вхождения в графе, `j` = индекс `x` в раскладке того родителя, **у которого метод объявлен** (для метода уровня единицы — единица: child 0 = дескриптор E, own-поля с 1).
- **экземпляры именованных Structure и вхождения callable-полей** — `lmx_arena_ref_struct(self, ns_base + rank)` и, внутри результата merge, `lmx_arena_ref_struct(R, bat + aj)` — тоже статически.

Merge (`lmx_merge_owned.h.lm1` :12–:23): результат — плоское дерево из копий детей операндов по порядку; **родительские ссылки копий переписываются** на копию структурного родителя; METHOD-дескрипторы разделяются по адресу; «метод, пришедший копированием, вызывается через результат» (:18).

## 2. Измерение (транслятор `298ef1e`, драйвер)

```
B:
    size_t: y 42U
end: B

A:
    fn: M
    size_t: tag 7U
end: A

size_t: tag 3U

fn: M () size_t
    size_t: v
    v: node\tag
    return: v
end: M

size_t: t0
size_t: t1
size_t: t2
R: merge: A
t0: A\M()
Q: merge: B A
t1: R\M()
t2: Q\M()
if: t0 != 3U
    return: 80
if: t1 != 3U
    return: 81
if: t2 != 3U
    return: 82
return: 5
```

Сгенерировано: в `M` — `l2_pst: node` / `l2_pxp: lmx_arena_ref_cell(l2_pst, 1U)` (индекс 1 = `tag` в раскладке единицы: child 0 — дескриптор E, `tag` — первое own-поле); вызовы — `A\M()`: `l2_pst: ref_struct(self, 13U)` → `ref_struct(l2_pst, 0U)` → `l2_m0(l2_c0\parent, l2_c0)`; `R\M()`: `ref_struct(self, 10U)` → `ref_struct(·, 0U)`; `Q\M()`: `ref_struct(self, 11U)` → `ref_struct(·, 1U)` (транслятор верно посчитал, что во `Q = merge: B A` вхождение `M` — слот 1).

Результат прогона: **entry 81** — `t0 = 3` (верно), `t1 ≠ 3`. Разбор: у `A\M()` вхождение `M` в поле `A` — ссылка на вхождение уровня единицы, его `parent` — единица, `ref_cell(node, 1U)` = `tag 3U` ✓. У `R\M()` merge **скопировал** вхождение `M` и переписал его `parent` на `R`; `node` = `R`, `ref_cell(R, 1U)` = слот 1 результата = скопированный `tag 7U` из `A` — метод прочитал **7 вместо 3**. У `Q\M()` (`B` первым) `ref_cell(Q, 1U)` = слот 1 = само вхождение `M` (Structure, не ячейка) — чтение мусора/чужого адреса.

Итак, точная формулировка (вместо моей «верно лишь для первого операнда»): **скопированный merge метод адресует поля лексического родителя индексами, запечёнными для исходного родителя, а его `node` после merge указывает на результат с другой раскладкой.** Это «работает» только когда раскладка результата случайно совпадает с раскладкой исходного родителя (`R`: индекс 1 в обоих — но и тогда значение чужое: 7 вместо 3). Own-поля самого метода (`self`) не страдают. Callable-поле в первом операнде спасает не «первенство», а совпадение индексов.

Два прочтения нормы, из которых вытекают разные починки:

- **(I) `node` копии = результат merge** (как сегодня, по правилу «родительские ссылки переписываются»): тогда скопированный метод *должен* видеть поля результата (`R\tag` = 7), и ошибка — только в способе адресации (индекс единицы вместо индекса в `R`). Лечится базовой адресацией (раздел 3).
- **(II) `node` копии = исходный лексический родитель** (метод объявлен в единице — его `node\tag` всегда 3, независимо от того, чьим полем стало вхождение): тогда merge не должен переписывать `parent` у скопированного вхождения callable-поля (или транслятор должен передавать в `node` исходного родителя, а не `l2_cN\parent`). Никакой базы не нужно; merge остаётся плоским; «метод, пришедший копированием, вызывается через результат» означает только «через слот результата», а не «в контексте результата». Это проще и не трогает ABI; цена — скопированный метод не «специализируется» полями результата (что вы, видимо, и имеете в виду словами «методы так мержить нельзя»).

## 3. Как работала бы базовая адресация (прочтение I), развёрнуто — без merge методов

Цель: метод, вхождение которого скопировано в результат merge, читает поля своего лексического родителя **в результате** по верным адресам, хотя раскладка результата отличается.

1. **Дескриптор.** `LmxCallable {method, header}` (child 0 вхождения) получает поле `base` (`size_t`): смещение области, в которой лежат поля лексического родителя этого вхождения, внутри фактического `node`. Для вхождения уровня единицы `base = 0` (own-поля E идут с 1, индексы как сегодня). Для вхождения, скопированного merge из операнда `k`, `base` = сумма ширин операндов 0..k−1 (`lmx_merge_add_width`) — merge знает её при раскладке результата и пишет в дескриптор копии (дескриптор копии — своя запись, `LmxMethod` по-прежнему разделяется по адресу).
2. **ABI и эмиссия.** Сгенерированный метод читает `base` из child 0 своего `self` при входе (`lmx_callable_base(self)`; никакого третьего параметра — `(node, self)` остаётся) и адресует поля родителя как `lmx_arena_ref_cell(node, base + j)`. Все `ns`-индексы (`ns_base + rank`) и `bat + aj` для чтений *снаружи* остаются статическими — снаружи форма результата известна транслятору; база нужна только *внутри* тела, где раскладка родителя определяется во время исполнения тем, куда вхождение скопировали.
3. **Собственные поля и вложенные тела** — без изменений (`self`-относительно; тела `if`/`while` — hosted own-поля того же `self`).
4. **`merged\x` снаружи.** Транслятор знает формы операндов: если `x` есть в нескольких операндах, `merged\x` = последний по порядку операндов (правило «lastIndex», ваше следствие 1), явный `[N]` — лексический порядок. Никакого «переопределения в слоте»: у каждого операнда свои слоты.
5. **`implements` к модели.** Проверка по области модели: `base` модели-операнда + её форма; лишние слоты других операндов не мешают (структурное надмножество), сравнение — с child 1 области, child 0 — дескриптор.
6. **Что НЕ делается.** Никаких массивов методов в child 0 и никакого последовательного исполнения нескольких тел: у результата merge **нет собственного** дескриптора; каждое скопированное callable-поле остаётся отдельным вхождением со своим `{method, header, base}` и вызывается как сегодня — `R\M()`. Исполнение именованной Structure (Q20 = Д) — заморожено.
7. **Q19.2, checkpoint, dirty load** — не затрагиваются: публикация идёт в те же ячейки, только адрес считается от базы.
8. **Объём.** Ядро: поле `base` в `LmxCallable`, запись базы в merge при копировании вхождения callable-поля (`lmx_graph_copy_owned` при переписывании `parent`), `lmx_callable_base`. Транслятор: эмиссия `node\x` через базу (все места `lmx_arena_ref_cell(node, j)` / `ref_struct(node, j)` — единый помощник), self-build/пин не затрагиваются. Интерпретаторы: walker/L3 читают `base` там, где сегодня берут `node` (позиционный доступ, имён нет). Свидетель — программа из раздела 2: `t1 = 7` при прочтении I (или `3` при прочтении II), `t2` = то же, без мусора.

## 4. Что решить вам

- Прочтение **I** (копия метода живёт в контексте результата; нужна `base`) или **II** (копия сохраняет исходный лексический родитель; merge не переписывает `parent` у вхождения callable-поля; базы нет). Оба согласованы с «merge методов не делаем»; II проще и ничего не меняет в ABI, I даёт специализацию скопированного метода полями результата.
- Правило `merged\x` = последний операнд (следствие 1) — независимо от I/II.
- До решения: в `steps/defects.md` заведён D-29 — «скопированный merge метод читает поля родителя по индексам исходной раскладки» (минимальная программа выше, измерено entry 81), владелец назначается после ответа.
