# Связь с уже открытым чатом Grok

Common operational guide for Codex and Grok: [chat_config.md](../chat_config.md).

Проверена 2026-09-19 с активной сессией **grok** (Grok CLI в LMX, не Grok Bot). Это именно прежний терминальный чат пользователя, не новая ACP-беседа и не Claude. PID и внутренний UUID смотреть в реестре.

## Проверенный обмен

1. Codex присоединился к консоли работающего процесса через Windows `AttachConsole`, проверил пустую строку запроса и передал текст через `WriteConsoleInputW`.
2. В родной истории этой сессии Grok появился запрос и ответ `ACK ACTIVE-GROK-93281`. Grok спросил, какой ID сессии видит Codex.
3. Codex ответил напрямую с ID той же активной сессии, не повторяя тестовый код. Grok ответил `ACTIVE-CONSOLE-CONFIRMED`, затем `ACTIVE-GROK-93281`.
4. Ответы прочитаны из родного `updates.jsonl` Grok и завершены событиями `turn_completed` с `end_turn`. Пользователь независимо увидел первый ответ в своём окне. Человеческая пересылка для получения ответов не использовалась.

## Клиент

```powershell
C:\grok\grok.bat send "Сообщение Grok"
C:\grok\grok.bat send --timeout 180 "Сообщение Grok"
```

Лаунчер сам делает `cd /d C:\Nyasha_Planet\LMX`, затем `python claude_chat\grok_active.py --session grok …`. Тот же каталог, что у `grok --resume grok`. Не вызывать `grok_active.py` из произвольной папки.

`--session grok` совпадает с `grok --resume grok`: не UUID, а заголовок сессии (`generated_title` после `/rename`), без учёта регистра, только среди **запущенных** CLI в этом каталоге. Если несколько с тем же title — выигрывает единственная с `title_is_manual`; иначе ошибка со списком ID. Это не «любой Grok в LMX». UUID по-прежнему можно передать явно. Клиент не вызывает `--resume` и не стартует процесс. Без аргумента `send` bat открывает TUI.

Перед отправкой ставит сообщение в FIFO `claude_chat/profiles/grok/api_queue.jsonl`. Ждёт конца хода (`turn_completed`). «Непустой prompt» — только **набранный текст** на строке курсора. Отсутствие глифа `❯` и курсор в (0,0) на пустой строке **не** занятость (ложное срабатывание 2026-09-20: ход уже `turn_completed`, ввод никогда не набирали, клиент 75 с ждал `❯` и `cursor.X <= 8`). Затем inject по одному. После тайм-аута элемент остаётся в очереди; **не** повторять тот же текст слепо.

Многострочный текст в очереди перед единственной консольной отправкой переводится в одну строку: CR/LF/TAB заменяются пробелами. Остальные управляющие символы отклоняются, чтобы один элемент FIFO не мог превратиться в несколько команд или навсегда заблокировать очередь.

Ввод посылается прямо в консоль. Чтение `updates.jsonl` — чтение штатного журнала ответа, не файловая почта: в этот файл клиент ничего не записывает и постоянных вотчеров не создаёт.

## Ограничения

- Это Windows-консольный адаптер, а не штатный удалённый интерфейс Grok. Нужны живой CLI-процесс и доступная консоль. Занятый prompt больше не отказ: сообщение в очереди до пустой строки `❯`. Не печатать в ту же строку вместе с клиентом.
- Grok может преобразовать путь внутри введённого текста автодополнением. Такое преобразование наблюдалось во втором тесте; ответ модели при этом получен. В клиент добавлен уникальный префикс для сопоставления, а фактически доставленный текст и признак `input_transformed` возвращаются вызывающему агенту. Эта последняя доработка не прошла полный повторный цикл: следующая попытка корректно остановилась до отправки из-за непустого ввода.
- Проверка не подтверждает фоновую инициативную доставку от Grok в простаивающую задачу Codex. Codex получает ответ, читая журнал после собственного запроса.
- Адрес этой консоли — имя **grok**, не Grok Bot и не UUID другой беседы. После закрытия чата снова открывать через `C:\grok\grok.bat` и проверять `peers`.
- Агенты L1 и сессии Claude не используются этим каналом.

Отдельный ACP-клиент `grok.py` остаётся отдельной новой беседой; его нельзя выдавать за подключение к этому открытому чату.
