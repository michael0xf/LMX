# Каталог L3Thread до компиляции

<a id="thread-capture"></a>
## Основа снимка

Первое действие каталога — получить у владельца **конкретный чистый граф L3Thread до входа в транслятор**. Построенный Thread можно описать, даже если компилятор никогда не будет вызван, машинная генерация недоступна или исходный файл отсутствует. Для входного файла этот граф сначала создаёт `sys\fromLmx`. Инвентаризация готового объекта сразу начинает обход. Поиск по тексту LMX и список методов для native не покрывают безымянные узлы, DATA и участки, появившиеся во время исполнения. [Кодек Structure и Thread](../spec/LMX_semantics.ru.md#source-codec) · [API просмотра](API.md#runtime-operations).

1. На полосе владельца зафиксировать корень, разрешённую область, контекст и границу наблюдения. Удержать нужные объекты обычными средствами lifetime/GC. Операционный ключ узла выдавать при первом посещении, **до** обхода детей. Для каждого физического вхождения сохранить ordinal, имя при наличии и ребро либо пустой слот. Повторная встреча даёт ребро к тому же ключу. Затем связать действительные parent и таблицы именно этого Thread в пределах заявленного экспорта. Для внешнего или недоступного ребра указать границу покрытия, не раскрывая чужой объект. От вершины с `parent=0` обход начинается обычным образом.
2. До освобождения этой границы завершить фиксацию. При переходе через ход нельзя считать одной основой данные до и после изменения. Если прежняя основа больше не доказуема, отбросить незавершённую часть и снять новую. После обхода ключи относятся к снимку, временная карта адресов и удержания освобождаются. У отчёта нет обратной ссылки, которой можно было бы произвольно писать в живой объект.
3. Выдать подготовленный снимок запросившему агенту. На этом можно закончить. При явной компиляции зафиксировать именно её вход (`compile-input`) до проверки/трансляции. Переиспользовать подготовленный снимок, только если он относится к тому же удержанному входу и контексту. Совпадения имени, пути или текста недостаточно для тождества живого объекта.
4. Решения подготовки и трансляции дописывать из действительных проходов этой компиляции. После тестов при необходимости отдельно снять `post-tests-current`. Артефакт, native entry, успешный тест или факт исполнения получают собственную расписку. Тест может изменить граф. Сведения о первоначальном входе сохраняют прежнюю основу.

Промежуточный снимок до вызова компилятора доступен вызвавшему в подготовленной области. Активный опубликованный каталог компиляции продолжает отвечать с token последней успешной публикации. Ни preview, ни обычное редактирование не подменяют эту публикацию. Так можно ответить и на «что сейчас в Thread», и на «из чего собран этот модуль». [LMX-модель обхода и публикации](src/catalogue.lmx).

## Что попадает в каталог

| Семейство | Что фиксировать | Основание и граница |
| --- | --- | --- |
| Топология и значения | Порядок полей/элементов, дубли имён, пустой слот, uninitialized, typed null, тип, фактические ссылки, sharing, циклы, реальные parent, входящие в экспорт таблицы | `graph-observed`. Полный `payload_lmx` создаёт `sys\toLmx`. Сокращённое представление помечается как проекция. |
| Имена, определения, употребления | Написанное вхождение, scope, TYPE/DATA/CODE в контексте потребителя, полный TypeRef, описание измерений, defaults, required, входы, результат, declared throws | `written` или результат фактической подготовки. Вычисляемый размер, default и пользовательский `test` не запускаются ради индекса. Сохранённые TypeRef восстанавливаются по каноническому описанию. |
| Вызовы и зависимости | Написанный call site, известная цель и карта actual → formal, reads/writes, import/copy/merge, связи типов, возможный эффект, обратное использование | `resolved-for-this-compilation` содержит evidence, контекст и compile token. Неизвестная динамическая цель сохраняет место и причину с `dynamic-unresolved`. Ветвь, по которой не ходили, может оставаться `not-analysed`. |
| Тесты, документы и native | Связь с написанным тестом, отдельное наблюдение запуска, комментарии и примеры, имеющийся URI/hash/span исходника, модуль, entry, ABI, артефакт и статус установки | `runtime-observed` привязано к конкретному запуску. У созданного во время работы графа может отсутствовать дисковый источник. Машинные указатели после рестарта не используются как идентификаторы. |

Публикация заявляет область и полноту *по каждой* группе фактов. Полная топология совместима с частичным знанием вызовов и эффектов. Поиск по имени возвращает все совпадения. Запрос о влиянии изменений перечисляет доказанные зависимости и остаток неизвестного. Написанный `test` и его результат хранятся раздельно. Допуск, выполнение тестов, планировщик и выбор перегрузки продолжают работать на графе. [Тест и его потребитель](../spec/LMX_semantics.ru.md#edit-api-catalogue).

## SQLite и граница endturn

Каждому владельцу соответствует одна активная проекция. Доверенное отображение владельца на БД или таблицу задаёт провайдер. Имена и пути от клиента передаются параметрами запросов. Таблица хранит строки `snapshot/node/field/relation/attribute/text/coverage`. Для вхождения важна пара «узел, ordinal». Для перехода из результата поиска нужны область владельца, token публикации и локальный ключ. Проверка token и чтение выполняются в одной read-транзакции. Устаревший token или курсор возвращает `catalogue-stale`. Переход к живому PLACE требует нового разрешения владельцем. [DDL](schema/catalogue.sql) · [Проверка ключа](fixtures/catalogue/queries/14_admit_key.sql).

`finishPrepared` отдаёт проверенный частный кандидат. Успешный этап компиляции ставит его в очередь владельца. В соответствующей успешной границе владелец вызывает издателя **до** невозвращающего `endturn`. При ошибке компиляции либо теста прежняя публикация доступна. Издатель заменяет снимок в одной короткой транзакции `BEGIN IMMEDIATE`, проверяет ссылки, позиции, основу и coverage, затем делает `COMMIT`. Отказ проверки, `BUSY` по исчерпании заданного ожидания или ошибка записи дают отдельный результат. Читатели продолжают видеть целую предыдущую либо новую версию. Можно явно повторить только публикацию уже подготовленного кандидата при подтверждённой основе. Установка native и внешние эффекты не откатываются транзакцией SQLite. Если установка уже состоялась, а БД осталась на старой версии, обе расписки доступны раздельно. [Проверка публикации](fixtures/catalogue/queries/00_validate.sql) · [Изоляция SQLite](https://sqlite.org/isolation.html).

Запросы охватывают статус публикации, точные имя и тип, callers/callees, влияние, exports, связанные тесты и документы, поля по ordinal, сигнатуры, нерешённые употребления и циклы. Для многостраничной выдачи курсор связывает запрос, порядок, scope и публикацию. Поиск по полному тексту опционален. [Запросы SQL](fixtures/catalogue/queries) · [Синтетический набор и ожидания](fixtures/catalogue/query_cases.json).

<a id="catalogue-integration"></a>
## Точки подключения

`lm_graph_build_root` даёт корень из документа P0. `lm_graph_emit_node` назначает метку прежде рекурсии, `lm_graph_emit_parents` отдельно восстанавливает связи parent. При реализации выделить пригодный обход из существующего механизма и подключить наблюдение до lowering, включая Thread-таблицы и участки без native. Выводить L1 для обхода не требуется. `lm_graph_collect_methods` отбирает только вызываемые кандидаты. `lmx_native_descriptor` позволяет узнать о существующей ассоциации. Запись о типе, месте и выбранном вызове поступает там, где компилятор действительно разрешил их для указанного контекста. Полный связанный поставщик фактов и публикация от владельца остаются работой этапа 3. [Построитель](../../selfbuild/src/l2src/l2_graph_build.lm2) · [Обход графа](../../selfbuild/src/l2src/l2_graph_tool.lm2) · [Диспетчер вызовов](../../selfbuild/src/l2src/lmx_call.lm2).

На исходной базе `171668495` hosted frontend уже передаёт `source_node` и `L2StructCallPlan` в `lm_compiler_check_struct_call`. `lm_compiler_check_call_data` сохраняет известное место или пространство и оставляет неразрешённые координаты открытыми. Отсюда можно взять условный факт для конкретного прохода после его успешного решения. Фактический вызов в Graph виден в `lmx_graph_invoke_data_value` вместе с выбранными code, data и привязками. Это источник runtime-наблюдения. Данные живого кадра, адреса временных структур и внутренние номера этого frontend не переживают его запуск. Для постоянной ссылки нужен ключ вхождения в снимке, для координат — действительно сохранённый источник. [Проверка frontend](../../selfbuild/src/l2src/l2_frontend_core.lm2) · [Вызов в Graph](../../selfbuild/src/l2src/lmx_graph_run.lm2).
