# Ответы Fable по текущей документации

Редакция: **23 ноября 2026 года**. Этот файл входит в общий архив `spec` и содержит ответы на **все пункты А1–А11, Б1–Б9, Б2.1–Б2.9 и В1–В10** из полученной записки `found-for-docs-patch-20261123.md`. Исправления правил, исходников и описаний внесены также в соответствующие постоянные главы; этот документ объясняет решения и даёт переходы к ним.

Большинство записей Fable — уже принятые выводы или сообщения о состоянии конкретного ядра. Они не требуют заново выбирать синтаксис языка. Ниже отдельно указаны реальные несогласованности документации, установленное поведение и работа, которая остаётся в реализации. Результаты старых запусков относятся к названному Fable срезу; они не служат квитанцией исполнения обновлённого архива. **Изменённый LMX в этой среде не запускался.**

## Что существенно для продолжения работы

- Типизированные ссылки и массивы используют тип в голове: `Model@: p`, `int@: left`, `Model[]: arr`, `int[]: values [1 2 3]`. Все восемь согласованных форм собраны в [главе об объявлениях](TYPE_DECLARATION_FORMS.md).
- В примере А4 `C()` читает **5**: у него есть собственное исходное значение. Локальная запись в `Main` не переписывает исходный граф. Пустой вход и свободное имя продолжают использовать разрешённое динамическое связывание.
- Автоматический отказ допуска, обнаруженный интерпретатором при достигнутом вызове в корректно построенном графе, обрабатывается как **`interpreter`**. Название внутренней проверки `satisfies` не задаёт имя этого отказа.
- Всегда запускается корень как обычный L3 Thread без DATA и пользовательских аргументов. Локальные объявления и вызовы работают общим механизмом; если у заглушки-родителя есть аргументы, она может отправить корню обычное сообщение. Запуска через `Main` нет.
- В библиотечных исходниках устранены ссылки на необъявленный `sys\OPERANDS_TEMPLATE`: используется одна обычная DATA-заготовка и явно заданные готовые приоритеты.
- Исправлено противоречие о группе в голове перед `:`. Сама такая голова допустима грамматически; смысл определяет её потребитель.

**Вопрос А3 закрыт ответом автора (23 ноября 2026):** у R0 нет родителя, как у любой Structure с нулевым `parent` (например, у построенной под `independent`); тест R0 пишется для R0 без родителя, а сценарий, которому родитель нужен, запускается обычным вызовом из R0 дочерней Structure или метода, у которых он есть. `Main` не вход, `root()`, `data` и новый `self` для неподходящего старого теста не вводятся, дополнительного механизма нет. Подробности — [А3](#a3).

## А. Языковые правила

<a id="a1-a2"></a>
### А1 и А2. Где писать тип ссылки и массива

**Переформулировка:** нужно ли ещё разбирать старые неоднозначные порядки типа и имени? **Нет.** Действующая запись уже выбрана. Тип целиком стоит перед двоеточием, а элементы массива — в квадратной группе. Разрешены как именованные, так и безымянные инициализированные массивы. `@: p Model` сохраняет обычный смысл универсальной ссылки, инициализированной значением `Model`; скрытого аргумента типа в этой записи нет.

Ошибка занятого или недопустимого имени проверяется общим механизмом имён. Описанный в В8 пропуск этой проверки относится к ядру. См. [восемь положительных форм](TYPE_DECLARATION_FORMS.md#1-eight-author-approved-forms) и [договор объявления](LMX_semantics.en.md#receiver-args-only).

<a id="a3"></a>
### А3. Как коду корня обратиться к самому корню

**Переформулировка:** требуется ли специальное «я» для корневого исполняемого тела, чтобы обращаться к его полям по индексу, когда обычной ссылки на корень нет?

Здесь нужно различать два случая. Если доступна именованная Structure, которая действительно является непосредственным ребёнком нужного корня, существующий `parent(child)` возвращает этот корень. После получения ссылки работают обычные `root[i]`, `root\field` и индексированные вхождения имён. Это следует из общего договора `parent`, без нового ресивера или изменения `node`. Само наличие имени недостаточно: важна реальная связь `parent` выбранной Structure.

Если подходящей дочерней Structure или иной доступной ссылки нет, универсальная исходная запись самого R0 нынешней нормой не задана. `node` смотрит в лексическое пространство **над выбранным методом**, которого над R0 нет. `parent()` и `sys\descriptor()` без аргумента выбирают DATA, а DATA у R0 нет. `code` — обычный параметр `call`, а не зарезервированное имя корня. Локальный служебный указатель R0 в C не становится пользовательским входом автоматически.

Поэтому утверждение «корень нельзя назвать вообще» слишком широко; условный путь через `parent(child)` уже существует. Вопрос об **универсальном доступе без исходной ссылки** закрыт ответом автора (23 ноября 2026): такой записи не нужно, у R0 нет родителя, как у любой Structure с нулевым `parent`, а нужный родителю сценарий запускается обычным вызовом дочерней Structure или метода. `node` не переопределяется, специальный `data` не возвращается, тесты не получают выдуманный `root()`.

Основание: [parent и DATA](LMX_semantics.en.md#parent-receiver), [R0](LMX_semantics.en.md#root-entry), [явная граница доступа к корню](LMX_semantics.en.md#root-reference-boundary). Если тест проверяет обычный метод, у которого корень — лексическое окружение, `node` в этом методе уместен. Если он проверяет именно поведение R0, перенос тела в метод меняет проверяемый сценарий и не является исправлением этого теста: тест R0 пишется для R0 без родителя, а сценарий, которому родитель нужен, запускает R0 и обычным вызовом доходит до дочерней Structure или метода, у которых родитель есть.

<a id="a4"></a>
### А4. Почему `C()` видит 5 после `x := 9` в `Main`

**Ответ: по действующей норме итоговая запись в `seen` равна 5.** Сам фрагмент описывает обычные методы как DATA. Для этого наблюдения уже работающий корень или достигнутый обработчик выполняет обычный вызов `Main()`; это не точка старта программы и не полный корневой файл. Родитель обоих методов описывает `x` с собственным готовым значением 5. `Main` получает собственное место вызова и меняет его на 9. Новый вызов `C()` опять имеет собственное исходное значение 5, которое автозаполнение не заменяет.

Это не отменяет динамического связывания. Получаются три разных, уже определённых сценария:

| Изменение примера | Что видит C | Почему |
| --- | ---: | --- |
| Исходные `int: x 5`, `x := 9`, `C()` | 5 | Готовый собственный default C имеет приоритет перед автозаполнением. |
| Явный вызов `C(x := 9)` | 9 | Допущенный явный actual заполняет выбранный вход. |
| Исходное объявление изменено на `int: x`, Main записывает 9 | 9 | Пустой вход C допускает автозаполнение текущим инициализированным значением Main. |
| Main явно пишет `node\x := 9`, затем вызывает C | 9 | Изменён сам исходный граф; следующий новый вызов видит изменённое исходное значение. |

Fable правильно вывел 5. Сообщённый результат 9 для неизменённого первого сценария противоречит действующему правилу B22 и требует исправления исполнения. Полный пример и объяснение добавлены в [норму о собственном default](LMX_semantics.en.md#own-default-root-example); общая передача свободных имён и её ограничения остаются в [разделе о связывании](LMX_semantics.en.md#binding-places).

<a id="a5"></a>
### А5. Как называется автоматический отказ допуска

**Переформулировка:** какое имя ловить, когда интерпретатор дошёл до вызова и не смог допустить аргумент?

Для этой ситуации действует уже установленное имя **`interpreter`**, то есть обработчик `catch: interpreter ()`. Интерпретатор использует стандартную проверку `satisfies`, но имя использованной внутренней проверки не переименовывает общий отказ интерпретатора. Предположение Fable о `catch: satisfies ()` не следует из действующей нормы для автоматического допуска.

Границы ответа существенны. Известное несоответствие, обнаруженное при построении или трансляции графа, остаётся диагностикой стадии и не перехватывается выполняемой программой. Явно вызванный ресивер имеет свой договор. Явный отказ, выброшенный достигнутым тестом или конвертером, сохраняет своё имя и payload. В подготовленный машинный вызов не добавляется автоматический runtime `satisfies`.

Это следствие [стадий допуска](LMX_semantics.en.md#admission) и [общего отказа интерпретатора](LMX_semantics.en.md#exceptions) теперь прямо записано в [подразделе об имени отказа допуска](LMX_semantics.en.md#admission-failure-name).

<a id="a6"></a>
### А6. Нужны ли пробелы в `Name::A`

**Нет.** `Name::A`, `Name ::A`, `Name:: A` и `Name :: A` имеют одинаковые границы: `::` распознаётся целым токеном до одиночного двоеточия. Это не две вложенные colon-формы. Прямая фраза добавлена в [грамматику структуры](LMX_grammar.en.md#structure).

<a id="a7"></a>
### А7. Корень запускается всегда; Main не является входом

**Уточнение автора от 23 ноября 2026 года:** запуск всегда начинается с корня. Он поднимается как обычный **L3 Thread**, не имеет DATA и не принимает пользовательских аргументов запуска. У корня есть локальные переменные и возможность выполнять любые допустимые обычные вызовы. Если у заглушки-родителя имеются аргументы, она может передать их корню **обычным сообщением**.

Предыдущее объяснение через отдельный профиль «загрузить файл как DATA и начать исполнение с выбранного Main» неверно. Оно удалено. Имя `Main` может принадлежать обычному методу, но процесс от этого метода не стартует. Именованные вызовы в сравнительных проверках — последующие обычные действия уже работающего корня или обработчика.

Механизм должен быть общим: отсутствие DATA пропускает только описание/заполнение входов данной активации. Подготовка CODE-локальных мест, достигнутые объявления, разрешение голов, вызовы, управление потоком и обработка сообщений сохраняют обычные правила. Заглушка не подставляет DATA=CODE, не передаёт скрытый пользовательский actual и не превращается в отдельный интерпретатор. Её родительство в дереве Thread не является лексическим `node`.

В корневом CODE обычная голова `Pair:` вызывает разрешённую Pair, а ресивер объявления создаёт место по своему обычному договору. DATA-фрагмент с описаниями методов сохраняет собственную роль там, где его принимает соответствующий потребитель; он не становится другим способом запуска приложения. Полный пример запуска должен иметь корень с обычными операциями, которые получают нужные данные и достигают нужных вызовов. Само отсутствие такого полного runner в сравнительном фрагменте честно отмечается как граница интеграции, без выдуманного CLI или автоматического Main.

Способность получить Structure и затем исполнить её не требует DATA у корня: обычные конструкторы квадратных групп создают значения по [общему договору типов](CORE_SEQUENCES_REGEX.en.md#types), а `sys\fromLmx(text)` возвращает обычный граф, который допускает чтение, композицию и интерпретацию без отдельной компиляции ([source codec](LMX_semantics.en.md#source-codec)). Это существующие операции, доступные и корню. Произвольная круглая группа внутри `@` от этого не получает нового универсального режима цитирования. [Схема общей активации](kernel-implementation.en.md#root-activation) описывает условный DATA-pass и общий путь CODE-исполнения.

Прямая норма и наблюдения R001–R006 добавлены рядом с [R0](LMX_semantics.en.md#source-entry-profiles). Они проверяют запуск с начала корня, CODE-локальные места без DATA, обычный вызов и передачу аргументов сообщением от родителя. Ведущая анонимная CODE-группа исполняется по общему договору; неисполнение достигнутой группы не является разрешённой альтернативой.

### А8–А10. Объявления как аргументы и длина массива

| Пункт | Ответ текущей редакции |
| --- | --- |
| А8: внутреннее имя объявления совпало с именем формала | Совпадение ничего не выбирает и не заменяет. Объявление передаётся **целой DATA Structure на обычную позицию**. Только внешнее `formal := value` выбирает вход по имени. Требование формала проверяет переданную Structure; тип или initializer внутри неё не подставляется вместо целого аргумента. Передача сама не запускает initializer. |
| А9: как объявить массив длины N без элементов | Отдельной формы длины в объявлении нет. `int[]: values` оставляет место без значения; `int[]: values []` создаёт пустой массив; квадратная группа задаёт элементы. Длину уже существующего массива меняет `sys\resize`. Новым элементам не приписывается неоговорённое нулевое значение. |
| А10: объявлению-аргументу не осталось позиции | Лишний позиционный actual отклоняет кандидата до выполнения initializer и входа в тело. Это справедливо и для callable без входов. Внутреннее имя объявления не создаёт дополнительную позицию. |

Все три пункта закрыты. Прямые следствия и случаи приёмки A22/A23 находятся в [объявлениях-аргументах](LMX_semantics.en.md#declaration-arguments) и [наблюдениях](LMX_semantics.en.md#declaration-observations); массивы описаны в [главе об объявлениях](TYPE_DECLARATION_FORMS.md).

<a id="a11"></a>
### А11. Составная голова, многострочная группа и `T@x`

Все три вывода Fable подтверждены и записаны прямо. Многострочная ограниченная группа сохраняется в голове целиком. `(Model): p` имеет группу-основу и ноль постфиксов: парсер сохраняет эту голову, а её допустимость решает потребитель. Прижатый к левому операнду `@` в `T@x` относится к постфиксной голове `T@`, после которой идёт отдельное `x`.

Здесь была реальная ошибка документации: старая фраза запрещала непустую группу-голову перед двоеточием, хотя EBNF её разрешала. Фраза исправлена. Пояснение группового присваивания также сужено: colon-голова не приобретает семантику присваивания от одного наличия группы; само присваивание использует `:=`. См. [структуру](LMX_grammar.en.md#structure), [пути и составные головы](LMX_grammar.en.md#paths), [групповое присваивание](LMX_semantics.en.md#group-assign).

## В. Наблюдения о ядре: что именно требуется проверить

Следующие пункты не объявляются исправленными этим архивом. Он не содержит production-исполнитель Fable. При этом два наблюдения требуют особенно точной постановки проверки: невыполненный initializer в выводе графа сам по себе допустим, а диагностика проблемы должна относиться к реальной стадии и пути исполнения.

| Пункт | Понятная постановка и ожидаемое правило |
| --- | --- |
| В1 | Одиночное `@` в описании результата `return: @` должно читаться в роли описания результата. Нельзя без учёта роли требовать правый аргумент оператора взятия адреса. Проверять построение графа и разрешение результата отдельно от исполнения тела. |
| В2 | Для каждого конкретного значения нужно проверить допустимость указанного типа: typed reference, числовые требования и универсальная ссылка имеют разные условия. Нельзя отклонять все значения `u8`/`long` или все Structure под `@` из-за отсутствующего общего пути. При этом контракт диапазона и требования модели сохраняется. |
| В3 | `length` пустой Structure равна числу её собственных непосредственных полей — нулю. Транспортирующая ссылка сама не добавляет поле в выбранную пустую Model. Проверка должна действительно измерять Model, а не содержащую её группу/описание. |
| В4 | **Невычисленное объявление в сериализованном графе само по себе не ошибка.** Явный путь и `sys\toLmx` читают записанный initializer без его запуска. Если декларация достигнута как CODE либо её computed input востребован в вызове, выражение выполняется по договору и результат появляется в соответствующем месте активации; это не обязано переписывать исходный граф. Нужны отдельно наблюдение эффекта/значения вызова и наблюдение неизменённой записи графа. |
| В5 | Сообщение о медленной вставке в индекс арены требует профиля actual implementation. По действующей физической норме тип и размер графового значения берутся из кода соответствующей записи; плотный элемент использует описание Array, а native local — установленный тип своего машинного контекста; классификация адреса не является отдельным способом определения типа. Индекс владения/размещения не превращается в второй источник типа. Документация не подтверждает измеренную скорость. |
| В6 | После разрешённой записи в ранее uninit место автозаполнение использует его **текущее инициализированное состояние**. Передача прежнего uninit вопреки этой записи — дефект исполнения. Отсутствие исходного initializer не означает пожизненного отсутствия значения. |
| В7 | Достигнутый голый `return` завершает исполнение по договору выхода; голый `break` выходит из соответствующего цикла. Это специальные формы управления потоком. Исполнение следующей обычной инструкции при таком выходе противоречит норме; наличие working workaround `break()` её не заменяет. |
| В8 | Объявление с недопустимым или занятым именем получает обычную диагностику имени. Отсутствие такой диагностики не возвращает старое чтение typed-reference деклараций. |
| В9 | Нативная индексация L2 вычисляет машинное смещение по своему договору без добавленных проверок знака и длины. Отрицательный индекс не отклоняется только из-за знака, а подходящее целочисленное выражение не должно останавливаться из-за отсутствующего искусственного пути допуска. Обычное понижение арифметики смещения всё равно должно сохранять значение и машинный тип. Проверки L3 и интерпретируемого L2 не отменяются. |
| В10 | Индексирование после поля-ссылки должно проходить тот же общий путь доступа, что и после иной ссылки подходящего типа. Отсутствующая ветвь lowering требует реализации; отказ трансляции должен указывать реальную причину и позицию. Тихое прекращение или сообщение без места не является предусмотренной альтернативной семантикой. |
