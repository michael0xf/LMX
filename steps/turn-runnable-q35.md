# Ход по графу после Q35: замер и предложение (Opus, 2026-09-27)

Ответ автора — `LMX_blog/2026-09-27.md`, «Q35: ход по графу и «успех»» (вопрос — `LMX_blog/q/q35.md`, дефект D-90).
Записка — замер и предложение срезов для ревью; кода нет.

## 1. Норма — дословно

```text
Q35 -- куда возвращаемый статус и зачем? Что такое "учпех"? "success" выставляет пользовательский код -- то есть ядро само не выставляет его. Какая разница есть native или нет? Интерпретатор должен работать.По поводу хода по графу делайте пока просто -- если корень это стуктура без аргументов и возвращаемого значения, то он вызывается на каждый turn как будто это runnable такой. Во всех прочих случаях выполнение вызывает только входящий message из раздлеа про "post".
```

## 2. Замер

1. **Где значение становится статусом.** `lmx_thread_dispatch_native` (`dev/l2src_sandbox/lmx_thread.lm1`
   :557–:566): в режиме статуса (`lmx_call_walk_returns_status`, ставит только привязка L3 — `l3_thread_bind`,
   `dev/l3_interp/l3_thread.lm1` :348, :383) результат `lmx_call0` возвращается как статус хода; код 2
   (`LMX_CALL_NOT_CALLABLE`) — как `LMX_TURN_BODY_OK`. У графа без нативного слова `lmx_call0` отдаёт то, что вернул
   крюк обходчика L3, — вердикт интерпретатора `LMX_INTERP_*` (`l3_thread_dispatch`), а значение графа крюк кладёт
   отдельно (`l3_bound_result`). У графа с нативным словом `lmx_call0` отдаёт **значение** обработчика — оно и
   читается как статус (D-90): вернул 1 — ход провален.
2. **Ветка «2 → OK» мертва для обхода.** `LMX_WALK_NO_GRAPH` сегодня никто не производит (k.4: `lmx_walk_enter`
   проверяет только, что код — Structure; тело без шагов — ноль шагов, не отказ); `lmx_interp_map` лишь отображает
   его. Ветка ловит только нативное значение 2.
3. **Без привязки L3** значение хода не читается (модель 31); провал хода — только канал броска
   (`lmx_call_walk_fail_status`: бросок — число хода, ошибка обходчика — X1, D-37).
4. **«success» — пользовательский код.** L2: выход — письмо выхода корня или `success` R0 (`lmx_root_launch_tapped`
   :1138–:1150), оба ставит программа. L3: примитив `success` (`l3_prim_success` — `message\success: 1`). Ядро
   `success` само не ставит — так уже есть.
5. **Корень L2 — без аргументов и значения по построению.** Юнит — вхождение E: собственные поля и управляющие тела E идут
   с 0, частей заголовка у E нет (комментарий в `l2_layout_owns`) — ни аргументов, ни результата; `return` со значением в корне отказывается
   транслятором. R0 получает один ход на запуск (`lmx_root_launch_tapped` :1135: `lmx_manager_round(…, 1U, …)`).
6. **Корень L3 — с аргументом и значением.** `l3_thread_dispatch` применяет граф с одним аргументом (сам граф,
   `args = @ subject`, `nargs 1U`) и сохраняет int-результат как значение выхода хозяина — E1 (`l3_thread_result`;
   `l3_thread_bind_selftest`: «an entry returning 7 is an ordinary successful turn», «the entry's 7 is observed as the
   host's exit value»).
7. **Ядро не читает сигнатуру корня надёжно.** k.4: сигнатура — обычные поля Structure; `lmx_walk_arg_arity`
   считает частью аргументов простую Structure в child 0. У E child 0 — первое собственное поле, и оно бывает
   Structure (`Model: fresh`, строка `unit_named_struct_exec_instance`): «аргументы» по этому признаку были бы у
   корня без аргументов. Части результата ядро не знает вовсе (тип результата CALL — ребёнок 3, его пишет
   транслятор).

## 3. Предложение

**Срез A — D-90 (ответ прямой).** Значение графа не статус хода ни в каком режиме: в режиме статуса нативный путь
ведёт себя как без L3 (значение не читается; провал — канал броска), путь обходчика несёт вердикт
интерпретатора (сбой интерпретатора — провал хода, как сегодня). Ветка «2 → OK» снимается. Свидетель — селфтест
L3-хода с графом, чьё нативное слово возвращает 1 и 2: ход OK; мутант — сегодняшняя ветка (возврат 1 проваливает
ход).

**Срез B — корень-runnable.** L2 уже соответствует (п. 5). L3 расходится (п. 6): по ответу корень со значением —
не runnable, и E1 («значение входа — значение выхода хозяина») этому ответу противоречит («куда возвращаемый статус
и зачем?»). Предложение, «пока просто»: значение графа L3 не записывается и не становится значением выхода (E1
снимается, `l3_thread_result` и его строки — тоже); граф вызывается на каждом ходу, как сегодня. Отличать
«с аргументами/значением» ядро сейчас не может (п. 7) — это нужно вместе с `post` (§8a): там исполнение по
входящему message, и сигнатуре нужен физический признак, который ядро читает. До §8a корень, который не runnable,
транслятор не пишет (L2), а L3-графы строятся руками тестов.

## 5. Ответ автора на q40 (2026-09-27) — срез B уточнён

Дословно — `LMX_blog/2026-09-27.md`, «Q40». (1) E1 давно отменён: действует норма R0 от 2026-09-24 (`LMX_blog/2026-09-24.md` — письмо `exit(exit_code: <code>; stdout: ""; stderr: "")` родителю R0, без него — флаг `success` R0); значение графа хода L3 не сохраняется как код выхода — `l3_thread_result` и строки `l3_thread_bind_selftest`, которые его читают, снимаются. (2) Аргумента-субъекта нет: исполнение — execute(code data), у корня data = code, это принцип, не аргумент; `l3_thread_dispatch` зовёт граф как пару (граф, граф) без аргументов (`nargs` 0). Вопросы 2 и 3 раздела 4 закрыты; срез B — по этому ответу.
