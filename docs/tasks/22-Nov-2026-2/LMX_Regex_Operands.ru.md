# Словарь текстовых шаблонов LMX

Редакция имён: см. [выбор узнаваемых имён](1/NAMING_2026-11-22.md). Переименования применены к текущему тексту; договоры операций сохраняются.

**Проект v0.4 · 22 ноября 2026 года**

**Общий комплект:** `LMX-TZ-2026-11-22-postfix-1`.

**Изменения v0.4:** принята постфиксная запись типов `T[]`, `T@`, `T@@`, … по [общему договору типов массивов и ссылок](LMX_Array_Reference_Types_Core.ru.md#forms); обновлены именованный и безымянный примеры `Pattern[]` и проверки различия типа, значения и отсутствующего значения. Универсальный @ по-прежнему передаёт непосредственный указатель на {type value}; sequence/choice не требуют промежуточной упаковки источника. Основной regex-словарь, приоритеты, порядок сопоставления и текстовые профили сохранены. Связанное ТЗ: [Операции над последовательностями LMX](LMX_Sequence_Operations.ru.md#universal).

**Приоритет:** новый [core ТЗ](LMX_Array_Reference_Types_Core.ru.md) определяет смысл форм `[]`/`@` и имеет приоритет над прежними описаниями этих форм в каталоге `1/`. Его [порядок миграции](LMX_Array_Reference_Types_Core.ru.md#migration) применяется и к объявлениям, на которые ссылается этот документ. Regex использует общий договор, не вводя собственного синтаксиса типов или нового смысла `::`.

Этот документ предлагает аналог регулярных выражений средствами обычных LMX Expression и ресиверов. Основной набор — **`then`, `|`, `times`, `atLeast`, `atMost`, `optional`**. Пять словесных операндов явно задают работу с шаблонами; существующий `|` получает одно дополнительное применение — упорядоченную альтернативу Pattern. Более сложные операции имеют обычные именованные параметры.

Критерий выбора — меньше правил для чтения выражения. Поэтому арифметические `+`, `*` и операции `&`, `-`, `~` в этом словаре не получают новых шаблонных значений. Отдельные `or`, `and`, `xor` не вводятся: обязательного семейства таких слов здесь нет. У всех шаблонов, включая классы символов, одна семантика альтернативы.

Статус документа: конкретное предложение для обсуждения и реализации. Имена и контракты ниже ещё не являются утверждением о возможностях исполняемого ядра. Документация LMX изучена; приведённые программы на ядре LMX не запускались. Проверки в конце задают будущую приёмку.

Файл рассчитан на размещение рядом с каталогом **`1/`**, содержащим текущую документацию LMX. Относительные ссылки ведут в этот каталог.

## 1. Быстрый справочник

В таблицах `P` и `Q` — готовые значения шаблонов. Строка в параметре, явно принимающем шаблон, означает буквальную последовательность. Для шаблонного применения `|` хотя бы один аргумент данной операции должен быть готовым Pattern: `literal("cat") | "dog"`. `n`, `minimum`, `maximum` — целые неотрицательные числа. Записи с многоточием описывают семейство вызовов, а не новый синтаксис.

### Пять новых слов и существующий `|`

| Запись | Чтение | Результат |
| --- | --- | --- |
| `P then Q` | P, затем непосредственно Q | Шаблон последовательности |
| `P \| Q` | P или Q, в указанном порядке | Шаблон альтернативы с возвратом |
| `P times n` | P ровно n раз | Шаблон точного повторения |
| `P atLeast n` | P не менее n раз | Повторение без верхней границы |
| `P atMost n` | P от нуля до n раз | Повторение с верхней границей |
| `(P optional)` | P может присутствовать | От нуля до одного повторения |

Приоритеты от сильного к слабому: **повторение → `then` → `|`**. Скобки подчиняются существующим правилам LMX, включая единственное условное открытие правого контейнера. Для двух составных групп удобна префиксная форма:

```lmx
(then (literal("a") | "ab") (literal("c") | "d"))
```

Это два аргумента-шаблона для `then`. Обычный вызов `then(P Q)` не объявляется эквивалентным операторной записи: у операнда остаётся действующий ABI `left/right`.

### Ресиверы построения

| Ресивер | Назначение |
| --- | --- |
| `literal(text)` | Буквальный текст; символы `*`, `\|`, `(` и другие не получают regex-смысл |
| `oneOf(text)` / `noneOf(text)` | Один символ из заданного набора / вне набора |
| `charRange(first; last)` | Один символ включительного диапазона |
| `satisfy(predicate)` | Один символ, удовлетворяющий чистой проверке |
| `sequence(patterns := S)` | Последовательность шаблонов из готовой последовательности, переданной через `@` |
| `choice(patterns := S)` | Упорядоченная альтернатива из готовой последовательности, переданной через `@` |
| `repeated(pattern := P; minimum := m; maximum := n; order := stopFirst)` | Повторение с явными параметрами |
| `atomic(pattern := P)` | Зафиксировать первый локальный успех P |
| `capture(name; pattern)` | Сохранить именованный диапазон успешного пути |
| `sameAs(name)` | Повторить ранее захваченный текст; расширение регулярной основы |
| `ahead(pattern := P)` / `notAhead(pattern := P)` | Проверить наличие / отсутствие P впереди без продвижения |
| `behind(pattern := P)` / `notBehind(pattern := P)` | Проверить наличие / отсутствие P, заканчивающегося здесь |
| `boundaryOf(predicate := F)` | Граница принадлежности символов по явному предикату |

### Готовые значения

| Значения | Назначение |
| --- | --- |
| `emptyPattern`, `neverPattern` | Успех нулевой длины / отсутствие любого успеха |
| `anyChar`, `lineChar`, `lineBreak` | Любой символ / символ внутри строки / разделитель строки |
| `asciiDigit`, `asciiLetter`, `asciiWord`, `asciiSpace` | Точно определённые ASCII-классы |
| `textStart`, `textEnd`, `lineStart`, `lineEnd`, `wordBoundary` | Проверки позиции без потребления символа |
| `extendFirst`, `stopFirst`, `unbounded` | Обычные значения настроек повторения |

Готовое имя читается как значение. Оно не является неявным вызовом без аргументов. Имена `repeat`, `lazy`, `some`, `none`, `record`, `match`, `guard` сохраняют свои существующие значения в ядре.

### Применение и результаты

| Ресивер | Результат |
| --- | --- |
| `matchAt(source; pattern; position)` | `Maybe` одного совпадения с заданного начала |
| `wholeMatch(source; pattern)` | `Maybe` совпадения, занимающего весь вход |
| `find(source; pattern)` | `Maybe` первого найденного совпадения |
| `eachMatch(source; pattern)` | Итератор совпадений в порядке поиска |
| `contains(source; pattern)` | `int` 0/1: найдено ли совпадение |
| `hasPrefix(source; pattern)` | `int` 0/1: есть ли совпадение с начала входа; хвост разрешён |
| `hasSuffix(source; pattern)` | `int` 0/1: есть ли совпадение, заканчивающееся в конце входа |
| `matches(source; pattern)` | `int` 0/1: совпадает ли весь вход |
| `replaceFirst(source; pattern; replacement)` | Новый текст с первой заменой |
| `replace(source; pattern; replacement)` | Новый текст со всеми выбранными заменами |
| `split(source; pattern)` | Последовательность частей между совпадениями-разделителями |

Основной текстовый профиль — `utf8Text(text)`: одна позиция соответствует одной Unicode scalar value. Для обработки байтов применяется явный `byteText(bytes)`. В v0.4 ресиверы поиска получают такое представление явно; кодировку по содержимому не угадывают.

## 2. Практические примеры

Это выражения предлагаемого API. Они предполагают доступность описанных в словаре объявлений. Результаты справа поясняются текстом; это не дополнительные формы языка.

### 2.1. Код вида `AB-09`

```lmx
matches(
    utf8Text("AB-09");
    (then (charRange("A"; "Z") times 2) "-" (asciiDigit times 2))
)
```

Результат — 1. Для `AB-9`, `ab-09`, `XAB-09Y` результат 0. `matches` проверяет весь вход, поэтому отдельных якорей не требуется.

### 2.2. Имя с буквенным началом

```lmx
wholeMatch(
    utf8Text("river_12");
    capture("name"; (then asciiLetter (asciiWord atLeast 0)))
)
```

Возвращается присутствующий `Match`; захват `name` занимает весь текст. В этой версии имя начинается именно с ASCII-буквы. Другой алфавит задаётся другим явным классом, а не скрытой настройкой locale.

### 2.3. Пары `ключ=число`

```lmx
eachMatch(
    utf8Text("x=12 y=7");
    (then capture("key"; asciiLetter atLeast 1) "=" capture("value"; asciiDigit atLeast 1))
)
```

Итератор выдаёт `x=12` и `y=7`. У каждого результата собственные истории `key` и `value`. Эти имена не создают и не изменяют одноимённые локальные переменные вызывающего кода.

### 2.4. Ближайшая закрывающая скобка

```lmx
eachMatch(
    utf8Text("a<b><c>d");
    (then "<" repeated(pattern := anyChar; minimum := 0; order := stopFirst) ">")
)
```

Получаются `<b>` и `<c>`. В точке выбора повторение сначала пробует остановиться; если следующий `">"` не подходит, оно продолжает. Это правило порядка попыток, а не обещание глобально кратчайшего результата любого составного шаблона.

### 2.5. Повторить то же слово

```lmx
matches(
    utf8Text("echo echo");
    (then capture("word"; asciiLetter atLeast 1) " " sameAs("word"))
)
```

Результат — 1, а для `echo Echo` — 0. `sameAs` сравнивает конкретный ранее захваченный текст. Эта зависимость от прочитанного содержимого относится к расширениям регулярной основы.

### 2.6. Замена и разбиение

```lmx
replace(utf8Text("a12b3"); asciiDigit atLeast 1; "#")
split(utf8Text("a,b,"); ",")
```

Первая операция возвращает `a#b#`. Вторая — три части: `a`, `b`, пустую строку. Разделители не включаются, крайние пустые поля сохраняются. Вместо строки замены можно передать обычный callable с контрактом «`Match` → текст».

<a id="pattern-model"></a>
## 3. Что является шаблоном

`Pattern`, `TextView`, `Match`, `Span` и названия результатов в этом документе обозначают обычные структурные требования и значения LMX. Эти роли не регистрируют собственные regex-specific physical type codes, дополнительные поля `Lmx`, новую категорию указателей или новый язык инструкций. Используемые массивы и типизированные ссылки получают коды через [общий механизм ядра](LMX_Array_Reference_Types_Core.ru.md#type-codes).

Значение универсального ссылочного типа `@` указывает непосредственно на `{type value}`, где value может быть примитивом либо дескриптором, например массива. Массив типа `@[]` хранит эти указатели прямо. Универсальный вход не требует дополнительной упаковки ссылок или предварительного преобразования плотного массива в особый «формат записей»; способ чтения определяет существующий тип значения. Все виды Arrays уже имеют изменяемую длину в ядре; capacity хранится отдельно от Lmx-дескриптора. Эти правила не заменяют требования конкретной операции к тексту, Pattern или элементам последовательности. См. [универсальный доступ и представление](LMX_Sequence_Operations.ru.md#universal).

Шаблон — обычный callable Structure с настоящим DATA/parent. Его применение к входу, позиции и текущему состоянию захватов задаёт **упорядоченную последовательность возможных продолжений**. Продолжение содержит новую позицию и журнал захватов данного пути. Это описание наблюдаемого контракта: реализация может перечислять результаты через обычный iterator, хранить явные продолжения или использовать подготовленный native-код.

Основной API строит готовые значения шаблонов. Строители ничего не сопоставляют, не читают будущий вход и не вызывают тело переданного Pattern. Шаблон можно хранить, передавать, возвращать и собирать из runtime-значений. Общие требования к вызовам и приёму продолжают действовать; статически фиксированная арность всего шаблона не требуется.

Литерал-строка в позиции Pattern принимается контрактом как буквальная последовательность. Пустая строка эквивалентна `emptyPattern`. Это решение потребителя, а не преобразование P0 и не специальная regex-грамматика внутри строки. Число само по себе не означает символ, диапазон или количество повторений: его смысл задаёт конкретный параметр ресивера.

`Match` содержит как минимум `source`, `begin`, `end`, `captures`. Поле `source` удерживает исходный `TextView` вместе с профилем и правилом интерпретации позиций. Интервал полуоткрытый: `[begin,end)`. Уже выданные границы и журнал captures не переписываются последующими шагами итератора или backtracking; это самостоятельные обычные результаты, ссылающиеся на общий источник. Успех нулевой длины имеет `begin = end` и остаётся успехом. Отсутствие результата представляется стандартным `Maybe`, а не числом 0, нулевой ссылкой или пустой строкой. `contains`, `hasPrefix`, `hasSuffix` и `matches` специально возвращают Boolean в виде `int` 0/1.

### Типы и массивы шаблонов

`T[]` обозначает интернированный в арене код типа массива, представленный значением `int` в общей системе `typeof`; само это выражение не создаёт массив. `[]: parts` объявляет неинициализированное место для любого массива, а `Pattern[]: parts` — неинициализированное место массива с требованием `Pattern` к элементам. Ни одна из этих форм не означает готовый пустой `@[]` или пустую альтернативу.

В выражении типа `@[]` символ `@` принимается тем же нормализатором TYPE-роли как символьный атом типа. Результат — общий код типа Structure / void-array. Здесь не исполняется префиксное получение адреса и не создаётся массив: применяется [общий механизм кодов типов](LMX_Array_Reference_Types_Core.ru.md#type-codes).

Обе формы bare `[]` сохраняются и различаются по исходной форме первого аргумента **до вычисления значения**: в `[]: parts` написано имя объявления, а в `[]: [P Q]` — квадратная группа, создающая безымянную Structure / массив ссылок. Поэтому `choice(patterns := ([]: [P Q]))` принимает готовые P и Q без обязательного `Pattern[]`. Имя с группой в `[]: parts [P Q]` означает инициализацию переменной. Обнаруженное значение ранее известного имени не меняет его роль на группу и не перегруппировывает аргументы; применяется [общий разбор ядра](LMX_Array_Reference_Types_Core.ru.md#common-parsing), без отдельного regex-parser.

Обычная Structure и массив ссылок `@[]` взаимозаменяемы по [общему договору ядра](LMX_Array_Reference_Types_Core.ru.md#forms). В частности, `[]: parts [P Q]` и `@: parts [P Q]` могут инициализировать переменную ссылкой на безымянную Structure, где P и Q — уже готовые значения Pattern. Отдельное преобразование Structure в Array, дополнительный wrapper или копирование целей ссылок для этого не нужны.

В DATA формы `Parts(P Q)` и `Parts: P Q` объявляют обычную Structure, которая уже является той же последовательностью ссылок. Затем `[]: arrayParts Parts` и `@: referenceParts Parts` могут хранить ссылки на этот же объект; `sequence(patterns := Parts)` и `choice(patterns := Parts)` используют его непосредственно. Имя `Parts` у структурной декларации остаётся постоянным именем; `arrayParts` и `referenceParts` — переменные, хранящие ссылки. Общность представления не превращает структурное имя в присваиваемую переменную и сама по себе не делает тело Structure immutable.

Готовые части можно объявить и передать обычному потребителю:

```lmx
Pattern[]: alternatives [literal("cat") literal("dog")]
choice(patterns := alternatives)
```

Без отдельного имени используется тот же типизированный receiver:

```lmx
choice(patterns := (Pattern[]: [literal("cat") literal("dog")]))
```

Именованный actual `patterns :=` передаёт построенный массив целиком. `Pattern` здесь остаётся обычным структурным требованием; вид хранения `Pattern[]` определяется существующей информацией о типе, без особого regex-layout или дополнительной коробки вокруг каждого значения. Конструктор действует при обычном достигнутом исполнении: явно написанные `literal(...)` вычисляются по одному разу, а тела полученных Pattern не вызываются для сопоставления. Получение кода типа также не запускает эти построители. В чистом графе receiver и его аргументы сохраняются как написанные.

Форма `T[]: [copy(S)]` принимает поток существующей операции copy внутри явно написанного литерала и создаёт безымянный массив; copy сохраняет свой обычный договор копирования графа. Именованный вариант `T[]: name [copy(S)]` использует те же механизмы. Это применение [действующих форм ядра](LMX_Array_Reference_Types_Core.ru.md#forms), без нового spread, `toArray` или regex-конструктора коллекций.

При сравнении только типов действует правило `A[] satisfies B[] ⇔ A satisfies B`. Возможный кэш этого [отношения типов](LMX_Array_Reference_Types_Core.ru.md#admission) не подтверждает содержимое текста, результат Pattern или успех сопоставления с конкретным входом. Приём значений и само распознавание выполняют свои обычные проверки.

Различия между выражением типа, составным типизированным head и обычным compact-вызовом задаёт [общий разбор](LMX_Array_Reference_Types_Core.ru.md#common-parsing). В частности, bare `[](T)` означает `[]: T`, а не фабрику типа; bare `@(Struct)` означает `@: Struct`. В составных heads `(Struct)[]: tail` и `(Struct)@: ptr` сохраняется обычная группа `(Struct)` со своим действующим смыслом. Её нельзя автоматически удалить: равенство `(Struct)[]` с `Struct[]` или `(Struct)@` с `Struct@` в общем случае не утверждается. Прежние префиксные записи типизированных heads не являются алиасами постфиксных форм; возможные иные обычные прочтения исходников определяет общий разбор. Regex не вводит для этих форм отдельных правил пробелов или индексирования.

Постфиксные формы типов `T@`, `T@@`, `T@@@`, … для любой конечной глубины n используют [один расширяемый механизм ядра](LMX_Array_Reference_Types_Core.ru.md#common-parsing). `@[]` — массив элементов универсального ссылочного типа `@`, `int@[]` — массив указателей на int, а `int[]@` — указатель на массив int. Префиксное `@Struct` по-прежнему получает адрес значения Struct и не является записью типа `Struct@`. Regex не задаёт собственного предела глубины или отдельных правил для каждого количества `@`.

<a id="expression-contract"></a>
## 4. Операнды, скобки и приоритеты

### 4.1. Общий механизм LMX

Пять новых словесных операндов используют [существующий структурный заголовок](1/LMX_semantics.en.md#operand-receiver): `left`, `right`, готовые константы `PASS_ARGS_AS_IS` и `PRIORITY`, обычный результат метода. Они получают [подготовленные значения](1/LMX_semantics.en.md#prepared-operands), `PASS_ARGS_AS_IS = 0`.

По уточнению автора встроенный `|` уже принимает ссылки `@`; шаблонное применение добавляется в алгоритм того же операнда. Его прежние допустимые значения, готовый приоритет и правила подготовки сохраняются. Новый механизм перегруженных объявлений, реестр или особая грамматика не требуются.

Логический список аргументов метода составляется из **написанного левого аргумента, если он есть, затем элементов `right`**. Это внутреннее правило метода; ABI не меняется. `left` не переносится в `right` и не дублируется. Строка или Array остаётся одним аргументом.

| Форма | `left` | `right` | Логический список |
| --- | --- | --- | --- |
| `P then Q R` | P | Q, R | P, Q, R |
| `(then P Q R)` | отсутствует | P, Q, R | P, Q, R |
| `P times 3` | P | 3 | P, 3 |
| `(times P 3)` | отсутствует | P, 3 | P, 3 |
| `(P optional)` | P | present empty Array | P |
| `(optional P)` | отсутствует | P | P |

`then` и новое шаблонное применение `|` требуют минимум два логических аргумента. Для `|` хотя бы один из них — готовый Pattern; прочие могут быть Pattern или буквальным текстом. Префиксное `(| P Q R)` допускается тем же расширенным контрактом и перечисляет ветви в написанном порядке; это алгоритм операции, а не автоматическая свёртка любого `right` самим языком. Для пустой или одноэлементной последовательности служат `sequence` и `choice`.

`times`, `atLeast`, `atMost` требуют шаблон и количество, `optional` — один шаблон. Проверка арности происходит после общих правил группировки; тело операнда не использует её, чтобы «дочитать» соседние выражения. Например, `P optional Q` имеет лишний аргумент; последовательность записывается `(P optional) then Q`.

У новых словесных операндов получающие места `left` и `right` объявляются `private`. Отсутствующий `left` остаётся отсутствующим; для postfix-форм передаётся явный пустой `right`. Caller-locals с такими именами не дополняют новые формы через [autofill](1/LMX_semantics.en.md#binding-autofill); явная передача разрешена [контрактом private](1/LMX_semantics.en.md#private-binding). У встроенного `|` сохраняются его действующие modifiers, defaults и binding; расширение алгоритма не переписывает общий контракт связывания.

### 4.2. Существующее открытие правого контейнера

При подготовке аргументов сохраняется [действующее единственное правило](1/LMX_semantics.en.md#operand-right-only-opening): если левый аргумент — написанная безымянная Structure, справа ровно один аргумент и он тоже написанная безымянная Structure, справа открывается **один** внешний уровень. Левый контейнер остаётся целым.

По пояснению автора это правило согласует групповые присваивания, C-подобные и Lisp-подобные Expressions. Словарь следует ему наравне с остальными операндами.

```text
(x y) op (a b)     → left: целое (x y); right: a, b
(x y) op ((a b))   → left: целое (x y); right: одно (a b)
```

Поэтому намерение «две составные части» записывается явно:

```lmx
(then (literal("a") | "ab") (literal("c") | "d"))
```

У префиксной формы нет левого аргумента, а в `right` две группы. Особое открытие не применяется. Для уже готового набора используется `sequence(patterns := S)`: именованный actual передаёт S целиком, без обычной альтернативы W/E. Общее раскрытие Array, автоматическое снятие всех скобок и превращение результата функции в список аргументов не вводятся.

### 4.3. Приоритеты и обычные вызовы

На [общей шкале приоритетов](1/LMX_semantics.en.md#expression-priority) проект задаёт следующие отношения:

| Сильнее → слабее | Группа |
| --- | --- |
| 1 | Обычный вызов, индекс и доступ к полю |
| 2 | `times`, `atLeast`, `atMost`, `optional` |
| 3 | `then` |
| 4 | `\|` |

Внутри каждой группы обработка идёт слева направо. Новые повторения получают приоритет существующего умножения, `then` — сложения через обычный `sys\priority`. У `|` сохраняется его существующий готовый приоритет. Это не меняет смысл арифметических операций; сложное выражение количества группируется: `P times (n + 1)`.

Константы приоритета и режима должны быть доступны до вычисления эффектных аргументов. Для обычных receivers действуют их обычные сигнатуры; они не притворяются operand-entry. В частности, `atomic(pattern := P)` получает один Pattern, а не `left` и массив `right`. Ссылки на методы и Pattern сами по себе не вызываются.


### 4.4. Где расширение существующего операнда упрощает запись

Для `|` выбран один новый смысл: упорядоченная альтернатива шаблонов. `asciiLetter | asciiDigit` и `literal("cat") | "dog"` используют его одинаково. Классы символов здесь — обычные односимвольные Patterns: отдельная ветвь «объединить Class, удалить совпадающие пути и изменить правила ошибок» не вводится.

Граница применения явная. Если хотя бы один логический аргумент данного `|` — готовый Pattern, все остальные должны быть Pattern либо текстом, который принимается буквально. Произвольная Structure или число не становятся шаблоном. Если Pattern нет, сохраняется прежний контракт `|`; внешний `wholeMatch` не меняет задним числом смысл уже вычисленной операции. Для альтернативы только из текстов есть `literal("a") | "b"` либо `choice(patterns := ("a" "b"))`.

Это единственная дополнительная граница в основном словаре. Она оправдана знакомой записью альтернативы. Распространять её на каждую операцию не требуется: [арифметика Arrays](1/LMX_semantics.en.md#array-operations) уже поэлементная, а строка LMX — массив типа `char[]`. Поэтому `"a" then "b"` и `"a" times 3` сразу задают нужный смысл, не затрагивая `+` или `*` и не требуя начального Pattern-маркера.

`p |= q` следует [существующему правилу составного присваивания](1/LMX_semantics.en.md#compound-assign): результат `p | q` записывается в известное изменяемое место p после обычного приёма. Место вычисляется один раз; специального regex-присваивания нет.

Новые `and` и `xor` не нужны. Последовательность — это `then`; проверки вперёд и назад имеют свои явные ресиверы. Более сложное множество символов задаёт `satisfy` с обычным предикатом. Логические `&&`, `||`, `!` и побитовые `&`, `^`, `~` сохраняют свои значения и не становятся новыми способами композиции Pattern.

Критерий для будущих расширений: новый смысл существующего знака должен сокращать объяснение обычного случая. Уменьшение числа имён само по себе недостаточно. Пять словесных операндов уже используют общий механизм LMX, поэтому отказ от них не даёт отдельной экономии в парсере.

<a id="dictionary"></a>
## 5. Полные контракты словаря

### 5.1. Элементарные шаблоны

`literal(text)` явно строит Pattern буквального текста. Строители сохраняют текстовые значения по обычным правилам ссылок. Декодирование и проверки, зависящие от профиля, выполняются при подготовке к конкретному `TextView`; независимые проверки арности и числовых аргументов — при построении. Текст не проходит regex-разбор. Изменение регистра и Unicode-нормализация не выполняются.

`oneOf(text)` принимает множество отдельных единиц: порядок и дубликаты не создают альтернативных captures. `noneOf(text)` — дополнение этого множества в области единиц текущего профиля. Пустой набор даёт соответственно `neverPattern` и `anyChar`. Обе операции потребляют ровно одну единицу; строка `"ab"` как самостоятельный шаблон потребляет две.

`charRange(first; last)` требует по одной единице в каждой границе и сравнивает их числовые значения. Границы включены. Обратный диапазон — ошибка аргументов, а не автоматическая перестановка. `satisfy(predicate)` передаёт числовое значение единицы обычному чистому callable и принимает ненулевой `int` как истину. Callback обязан завершаться; его объявленный выход не превращается в несовпадение.

ASCII-классы фиксированы: `asciiDigit` — U+0030…U+0039; `asciiLetter` — A…Z и a…z; `asciiWord` добавляет цифры и `_`; `asciiSpace` содержит SPACE, TAB, LF, CR, FF, VT. Они одинаковы в обоих профилях и не зависят от locale.

`anyChar` потребляет одну единицу, включая разделитель строки. `lineChar` исключает CR и LF. `lineBreak` распознаёт CRLF, одиночный LF или одиночный CR. Одиночный CR допускается только без следующего LF, одиночный LF — только без предшествующего CR. Поэтому CRLF является одним логическим разделителем из двух текстовых единиц и не даёт отдельного совпадения со своего второго символа. Другие Unicode-разделители не добавляются неявно.

### 5.2. Списки частей и параметры повторения

`sequence(patterns := S)` и `choice(patterns := S)` принимают готовую последовательность S через универсальный `@`. Вид массива и доступ к его непосредственным элементам определяются по действительному значению и его существующему типу. Каждый полученный элемент принимается обычным контрактом как Pattern либо буквальный текст; произвольное число не превращается в символ или шаблон. Вложенный Pattern остаётся одной частью, рекурсивного раскрытия нет. Пустая `sequence` даёт `emptyPattern`, пустая `choice` — `neverPattern`; один элемент сохраняет его поведение.

Обычная Structure принимается здесь наравне с `@[]`: категория или способ объявления контейнера не служат причиной отказа. При передаче той же Structure через инициализированную переменную `[]` или `@` сохраняются идентичность контейнера, ссылки на части и их обычные parent-связи. Требования к самим частям проверяются по прежнему договору; `Pattern` и `TextView` остаются обычными структурными требованиями, без отдельного object kind.

`repeated` имеет параметры `pattern`, `minimum`, `maximum`, `order`. Значения по умолчанию: `minimum = 0`, `maximum = unbounded`, `order = extendFirst`. `unbounded` — обычное объявленное значение отсутствия верхней границы; не отрицательное число и не переполнение машинного счётчика. Конечные границы неотрицательны, `maximum >= minimum`.

Операнды являются удобными формами этого контракта: `times n` задаёт обе границы n; `atLeast n` — минимум n; `atMost n` — диапазон 0…n; `optional` — 0…1. Все они используют `extendFirst`.

`atomic(pattern := P)` сохраняет только первый локальный результат P при данном входном состоянии. Если позднее продолжение отвергает этот результат, внутрь P возврата нет. Внешняя альтернатива при этом остаётся возможной. Выражение `atomic(pattern := P atLeast 0)` задаёт повторение без отдачи уже выбранного текста последующей части.

### 5.3. Проверки позиции

`textStart` и `textEnd` проверяют точные границы всего входа. Последний перевод строки не является исключением для `textEnd`.

`lineStart` успешен в начале входа и сразу после полного `lineBreak`; `lineEnd` — в конце входа и перед началом полного `lineBreak`. Между CR и LF якоря строки не срабатывают. Пустая строка и позиция после завершающего разделителя имеют обычные обе границы.

`wordBoundary` успешен, когда принадлежность соседних единиц к `asciiWord` различается; за пределами входа считается «не слово». Это техническая ASCII-граница, а не определение слова естественного языка. Для другой границы служит `boundaryOf(predicate := F)`: чистая завершающаяся проверка одной единицы задаёт принадлежность. Ресивер сравнивает результаты по сторонам позиции; за пределами входа считает результат ложным и F не вызывает. Он не пытается доказать односимвольность произвольного Pattern анализом тела.

<a id="matching-order"></a>
## 6. Выбор совпадения и повторение

В одной начальной позиции каждый шаблон задаёт порядок кандидатов. `P | Q` рассматривает кандидаты P прежде кандидатов Q. `P then Q` для очередного кандидата P рассматривает подходящие продолжения Q; исчерпав их, возвращается за следующим кандидатом P. Такой порядок сохраняется при вложении.

Например, `(literal("a") | "ab")` имеет локально первый результат `a`. Но последовательность с последующей `"c"` на `abc` возвращается и выбирает `ab`, после чего `c` подходит. Нельзя реализовать `|` через обычный Boolean `||`: первый локальный успех не всегда решает судьбу всего выражения.

`extendFirst` в каждой разрешённой точке повторения сначала пробует ещё одну итерацию, затем остановку. `stopFirst` сначала пробует остановку, затем дополнительную итерацию. До достижения минимума остановка запрещена; на максимуме продолжение запрещено. Внутри тела сохраняется его собственный порядок альтернатив.

Это локальный порядок поиска, не глобальная сортировка по длине или количеству итераций. В частности, альтернативы `literal("aa") | "a"` могут дать одну итерацию `aa` раньше двух итераций `a`. Начальное положение и порядок уже написанных альтернатив не переставляются ради более длинного совпадения.

### Пустое повторение

После итерации без продвижения дальнейшее **необязательное** повторение той же операции на этом пути прекращается. Если обязательный конечный минимум ещё не достигнут, выполняются необходимые дополнительные итерации до него. После достижения минимума повторение останавливается, если последняя итерация не продвинула позицию.

Поэтому `emptyPattern times 3` успешен, а `emptyPattern atLeast 0` не создаёт бесконечную цепочку. При `extendFirst` последний пример выполняет одну пустую итерацию, при `stopFirst` сначала предлагает ноль итераций. Если тело содержит другие варианты, backtracking сохраняет возможность их попробовать. Захваты отражают именно выбранное число выполненных итераций.

Никакого отката внешнего графа отсюда не следует. Отменяются только собственные данные попытки: позиция и журнал захватов. Обычный LMX [`retry`](1/LMX_semantics.en.md#suspension) не переопределяется и не становится транзакцией.

<a id="captures"></a>
## 7. Захваты и проверки окружения

`capture(name; pattern)` сохраняет начальную позицию, выполняет pattern и добавляет его успешный диапазон к истории имени. Имя — обычная строка, сравниваемая по содержимому. Отдельного глобального реестра captures нет.

История хранит **все завершённые захваты успешного пути**, включая повторения. Отказ ветви восстанавливает прежнюю историю. Захват пустого текста присутствует с диапазоном `[i,i)`; отсутствие имени отличается от него. Несколько occurrences с одним явным именем намеренно добавляют элементы в общую историю. Порядок — порядок завершения; у вложенных одноимённых captures внутренний завершается раньше внешнего.

`sameAs(name)` потребляет текст последнего завершённого захвата этого имени в текущем пути. Сравнение буквальное, в единицах выбранного профиля. При отсутствии захвата получается обычное несовпадение. Будущий capture справа не считается уже полученным. Объявление capture и его результаты не пишут в caller-locals и не используют их как запасной источник.

`ahead(pattern := P)` проверяет существование результата P с текущего начала. `behind(pattern := P)` проверяет существование результата P, заканчивающегося точно в текущей позиции; возможные начала лежат между 0 и этой позицией. Отрицательные формы успешны при отсутствии соответствующего результата. Внешняя позиция не меняется.

В v0.4 все lookaround являются чистыми проверками: их внутренние captures **не публикуются наружу**. Ранее доступные captures можно читать через `sameAs`; локально созданные видны только внутри данной проверки. Ошибка внутри проверки остаётся ошибкой и не превращается в успех отрицательной формы. Такая семантика намеренно определена здесь; полной совместимости с capture-поведением Perl не заявляется.

Общая семантика `behind` не требует статически известной ширины. На конечном входе можно проверять допустимые начала с ограничением конца. Оптимизация фиксированных диапазонов разрешена, но не меняет язык и не отбрасывает динамически построенные Patterns.

### Доступ к результату

| Ресивер | Возвращаемое значение |
| --- | --- |
| `matchedSpan(result)` | Диапазон всего совпадения |
| `matchedText(result)` | Явно материализованная копия совпавшего текста |
| `captureSpans(result; name)` | Последовательность всех диапазонов имени; пустая при отсутствии |
| `lastCapture(result; name)` | `Maybe` последнего диапазона |
| `captureText(result; name)` | `Maybe` копии текста последнего захвата |
| `captureTexts(result; name)` | Последовательность копий текста всех захватов |

Самостоятельно возвращаемая `Span` содержит `source` — ссылку на тот же `TextView` — и позиции `begin`, `end`. Она сохраняет источник и профиль по обычным правилам ссылок, а не native pointer внутрь перемещаемого backing. Текстовые accessors выполняют явное копирование по своему контракту; сами `Match` и `captureSpans` не обещают снимок исходных данных.

<a id="text-operations"></a>
## 8. Поиск, замена и разбиение

`matchAt` проверяет целую последовательность Pattern с единственного начала `position` и возвращает первый её кандидат. `wholeMatch` рассматривает только кандидаты с началом 0 и концом в точной длине входа. Ограничение конца участвует в выборе: `wholeMatch(utf8Text("ab"); literal("a") | "ab")` должен выбрать `ab`, а не отвергнуть всё после первого короткого результата.

`find` перебирает начальные позиции от 0 до длины включительно, выбирая минимальное успешное начало, а внутри него — первый допустимый кандидат. `contains` — проверка присутствия результата `find`; `matches` — проверка присутствия `wholeMatch`. Они не материализуют текст захватов ради получения Boolean.

`hasPrefix(source; pattern)` возвращает int 1/0 по наличию результата `matchAt(source; pattern; 0)`. Совпадение должно начинаться в нуле, но не обязано занимать весь текст. Строковый pattern нормализуется как literal тем же путём, что другие операции.

`hasSuffix(source; pattern)` возвращает int 1/0, если допустимый кандидат Pattern заканчивается точно на длине входа. Начало может быть любой допустимой границей текста, включая последнюю. Проверка конца участвует в выборе кандидата: более ранняя короткая альтернатива не отменяет более позднюю, достигающую конца. Поэтому последний результат find/eachMatch не является реализацией hasSuffix: он может пропустить перекрывающееся совпадение. Явные atomic и обычный порядок Pattern сохраняются. Подготовка профиля выполняется один раз, сопоставление использует полный исходный TextView, без обрезания контекста для anchors/lookaround.

Оба предиката допускают успешное пустое совпадение. Невалидная кодировка, недопустимый pattern и объявленный отказ callback передаются обычным путём ошибок, а не превращаются в 0. `matches` по-прежнему проверяет весь вход, а `wholeMatch` возвращает Maybe Match.

```lmx
hasPrefix(utf8Text("prefix-tail"); "prefix")
hasSuffix(utf8Text("head-suffix"); "suffix")
hasSuffix(utf8Text("ababa"); "aba")
hasSuffix(utf8Text("ab"); literal("a") | "ab")
```

Все четыре вызова дают 1. Третий проверяет перекрывающийся суффикс, четвёртый — альтернативу, которая достигает конца после более короткого кандидата.

### `eachMatch` и пустые совпадения

После непустого результата `[s,e)` новый поиск начинается с e. После пустого `[s,s)` сначала ещё раз проверяется **тот же старт**, но исключаются все кандидаты нулевой длины. Если есть непустой кандидат, он выдаётся; иначе начало сдвигается на одну единицу. На конце входа после последней пустой выдачи поиск завершается.

Следовательно, `eachMatch` не теряет непустой вариант на том же старте, стоящий после пустой альтернативы. Повторно выдавать все нулевые варианты одного старта он не обязан. История захватов каждого выдаваемого совпадения начинается заново. Iterator использует обычные `yield` и завершение `throw: Stop`; другой объявленный выход остаётся ошибкой.

### Замена

`replacement` — текст либо обычный callable, получающий один `Match` и возвращающий текст в том же профиле. Callback выполняется ровно один раз на каждое выбранное совпадение и никогда на отвергнутые пробные пути. Порядок вызовов совпадает с порядком выдачи. Текст замены повторно не сканируется; интервалы относятся к исходному source.

`replaceFirst` использует первый результат `find`, `replace` — последовательность `eachMatch`. Они возвращают новый обычный текстовый Array и не изменяют исходник. Если совпадений нет, возвращается равный исходному текст по значению; тождество адреса не обещается. В случае ошибки callback операция не возвращает частичный текст, но уже совершённые callback внешние эффекты не откатываются.

Для `ab`, `emptyPattern` и замены `-` результат `replace` — **`-a-b-`**. Курсор копирования исходных фрагментов и позиция следующего поиска — разные обычные значения: продвижение поиска после пустого совпадения не должно терять символ между вставками.

### Разбиение

`split` использует тот же порядок неперекрывающихся разделителей. Он выдаёт тексты между их интервалами, исключает сами разделители и сохраняет пустые поля, в том числе крайние. Captures разделителя автоматически в результат не добавляются. Выходные части материализуются как новые обычные Arrays.

Если разделителей нет, результат содержит один элемент — весь вход; при пустом входе и отсутствии разделителя это один пустой элемент. Пустой вход с `emptyPattern` имеет один пустой разделитель и даёт два крайних пустых поля: `["", ""]`. Для `ab` и `emptyPattern` результат — **`["", "a", "b", ""]`**. Эта запись показывает математическую последовательность результата, а не новую форму литерала LMX.

В v0.4 нет неявных режимов «удалить крайние пустые поля», «вставить captures», «искать с перекрытием» и «ограничить число замен». Они могут быть обычными дополнительными параметрами следующей версии, но текущие результаты полностью определены без них.

<a id="text-and-lifetime"></a>
## 9. Текст, ошибки и время жизни

### Явные текстовые профили

`utf8Text(source)` создаёт обычное представление валидного UTF‑8. Единицы и все публичные позиции — Unicode scalar values; не UTF‑16 code units и не графемы. CRLF занимает две единицы. Source остаётся исходным массивом типа `char[]` точной длины; завершающий NUL не добавляется, а внутренний U+0000 является обычным символом.

`byteText(source)` читает каждый элемент как байт со значением 0…255, независимо от signedness C `char`. Для байтового профиля требуется восьмибитный байтовый substrate; иной машинный профиль не получает молча другую область значений. Позиции считаются в байтах. Текстовые литералы в шаблоне интерпретируются в том же выбранном профиле; ASCII-примеры одинаковы в обоих.

Невалидный UTF‑8, включая surrogate-кодировки и недопустимые последовательности, даёт ошибку `PatternEncoding`. Декодер не вставляет молча U+FFFD. Нормализация, locale, grapheme clustering и folding регистра не выполняются. Для будущих Unicode-свойств потребуется явно поставленная версия таблиц и описанный профиль; изменение этих таблиц не должно незаметно менять значение уже подготовленного шаблона.

### Source view и срок жизни

`TextView` хранит профиль и обычную ссылку на descriptor исходного Array. `Match` и публичные `Span` сохраняют это представление и позиции. Они не держат native pointer на backing Array. При необходимости сопоставления кодовых точек с исходными байтами используются явные обычные данные представления; это не второе представление исполняемой программы.

Источник должен оставаться живым и неизменным на время поиска, приостановленного `eachMatch` и чтения результатов, обращающихся к нему. Применяются [обычные правила reachability и lifetime](1/LMX_semantics.en.md#memory). Новая ссылка не воскрешает завершённую активацию и не превращает native local в долговечную строку. Не вводятся автоматический snapshot, copy-on-write или скрытое продление lifetime.

Построитель не удерживает временные служебные ссылки `left/right` на записи завершившейся активации. Числовые параметры сохраняются по значению, ссылки на Pattern, текст, имена захватов и последовательности частей — в собственных обычных DATA с допустимым lifetime. Ссылочные зависимости остаются живыми и неизменными до завершения применений Pattern и обращений к результатам, удерживающим эти зависимости; независимые копии вызывающий создаёт явно.

Если нужен результат, независимый от будущей мутации исходника, вызывающий явно запрашивает `matchedText`/`captureText` либо заранее подготавливает отдельную копию входа. Изменять вход через другой alias во время его потребления — нарушение API-контракта; нельзя продолжить поиск и назвать произвольный результат корректным старым совпадением.

### Ошибка и несовпадение

| Ситуация | Исход |
| --- | --- |
| Шаблон не подошёл, включая отсутствующий `sameAs` | Отсутствие результата/кандидата |
| Успешная пустая строка | Присутствующий результат с равными границами |
| Отрицательное число повторений, неверная арность, обратный диапазон | `PatternArgument` |
| Невалидная кодировка | `PatternEncoding` |
| Позиция вне 0…length | `PatternPosition` |
| Несовместимый callback, неверное значение вместо Pattern | Обычная ошибка приёма LMX |
| Объявленный выход callback | Обычное распространение по его контракту |
| Исчерпание применимого явного лимита ресурсов | Отдельная ошибка лимита, никогда «не найдено» |

Названия `PatternArgument`, `PatternEncoding`, `PatternPosition` — предлагаемые обычные declared failures. Нового канала исключений не требуется. Подавление ошибок внутри `notAhead`/`notBehind` запрещено.

<a id="execution"></a>
## 10. Исполнение и границы проекта

### Подготовленные значения и непосредственное исполнение

Основной интерфейс использует готовые Pattern-значения и `PASS_ARGS_AS_IS = 0`. Отдельный потребитель исходного Expression может использовать `PASS_ARGS_AS_IS = 1`, но это самостоятельный контракт с явно заданными моментом вычисления и захватом контекста. Он не подменяет режим `|` или словесных операндов. Данный словарь такого потребителя не требует.

Raw occurrence сохраняет исходный контекст лишь в пределах установленного языком срока жизни. [`sys\eval`](1/LMX_semantics.en.md#expression-eval) сам по себе не сопоставляет строку, не откатывает эффекты и при повторном вызове выполняет новую оценку. Для долговечного правила используются обычный callable с DATA и [существующие механизмы возвращаемых методов](1/LMX_semantics.en.md#factory-reference-result), а не сохранённый указатель на закончившийся frame.

Реализация может использовать обычные методы, явные данные состояния, итераторы и подготовленный native-код. Если строится автомат, его таблицы — явно созданный обычный результат или деталь lowering. Обязательные regex parser, bytecode VM, новые opcodes языка и скрытый второй рабочий граф не вводятся. [Единый граф LMX](1/LMX_semantics.en.md#program-representation) сохраняется.

### Эффекты

Основной recognizer-профиль чист относительно внешнего графа: он изменяет собственное состояние попытки. `satisfy` и другие проверки не используют внешние записи как часть управления backtracking. Эффектные действия выполняются после выбора результата — например, callback замены.

Строитель может получать вычисленные аргументы; их оценка следует обычным правилам LMX и не повторяется при каждом откате сопоставления. В `makeP() | makeQ()` оба написанных построителя выполняются при подготовке значения; порядок проб ветвей относится к последующему сопоставлению. Аналогично `makeP() times 0` вычисляет построитель один раз, хотя сопоставление P не выполняется. Оптимизация чистых распознавателей допустима при сохранении результатов и порядка. Никакой общей гарантии линейного времени для произвольных расширений не заявляется.

### Регулярная основа и расширения

Литералы, пустой/невозможный шаблон, классы символов, `then`, `|` и повторение образуют регулярную основу. Captures добавляют результаты распознавания. `sameAs` связывает дальнейшее распознавание с ранее прочитанным текстом и входит в отдельный расширенный профиль.

Рекурсивные правила, преобразование captures в произвольные значения во время backtracking, условие по capture и эффектные predicates не включены в v0.4. Они могут быть обычными callable/receiver-расширениями с точными контрактами; наличие общего `sys\eval` не делает эти контракты определёнными автоматически. Основное ядро этого документа завершено без них.

### Почему повторение не называется `lazy`

Текущий `lazy` — [обычный receiver ядра](1/LMX_semantics.en.md#functional-receivers), принимающий callable без объявленных входных параметров и создающий отложенную обёртку, сохраняющую первый успешный результат. После неудачи следующая попытка может повторить вычисление; повторный вход в незавершённое вычисление даёт `FxLazyCycle`. `lazy(operation := F)` передаёт F; `lazy(F())` уже вызывает F при подготовке аргумента и не откладывает этот вызов.

Это независимо от порядка повторения: здесь он называется `extendFirst`/`stopFirst`. Прямой `thunk()` возвращает исходный R; `force(thunk := thunk)` — ссылку на типизированную запись результата и сам по себе не создаёт кэш. Общий `force` сообщает объявленные отказы через `FxCallFailure`, сохраняя первоначальное имя и payload; это отличается от прямого вызова обёртки. Точный алгоритм приведён в [исходнике lazy/once/force](1/patterns/LMX_Fn_Receivers/src/generic_wrappers.lmx). Значения существующих `repeat`, `some`, `none`, `record`, `match` и `guard` также сохраняются.

## 11. Будущие приёмочные проверки

Это требования к реализации, **не отчёт о выполненных тестах**. Все текстовые входы ниже используют `utf8Text`, кроме явно указанного byte-профиля. Успехи проверяются вместе с границами, captures и нужными эффектами.

| № | Случай | Требуемое наблюдение |
| --- | --- | --- |
| 01 | `literal("a*b")` | Совпадает с буквальным `a*b`, без regex-разбора |
| 02 | `(then (literal("a") \| "ab") "c")` на `abc` | Успех после возврата от `a` к `ab` |
| 03 | `literal("a") \| "ab"` на `ab` | `matchAt` выбирает `a`; `wholeMatch` выбирает `ab` |
| 04 | `(then (literal("a") \| "ab") (literal("c") \| "d"))` | Два групповых аргумента; исходные контейнеры сохраняются |
| 05 | Специальное RHS-открытие и двойная группа | Открывается только один разрешённый правый уровень; слева ничего не открывается |
| 06 | Пустые и одноэлементные S | `sequence`/`choice` дают описанные identity/failure; Array не разворачивается сам |
| 07 | `charRange("z"; "a")`; отрицательное число повторений | `PatternArgument`, не ложное совпадение и не перестановка аргументов |
| 08 | `makeP() times 0`; `P atMost 0` | Пустой успех без сопоставления P; написанный построитель выполнен один раз |
| 09 | Поиск `<...>` с `extendFirst` и `stopFirst` на `<b><c>` | Первый вариант получает `<b><c>`, второй — `<b>` |
| 10 | `atomic(pattern := literal("a") \| "ab")` затем `"c"` на `abc` | Отказ без возврата внутрь atomic; внешняя альтернатива всё ещё допустима |
| 11 | `emptyPattern times 3`; `emptyPattern atLeast 0` | Конечное выполнение; минимум выполнен, лишний нулевой прогресс остановлен |
| 12 | `eachMatch` после пустого кандидата, за которым есть непустой на том же старте | Непустой кандидат не пропущен |
| 13 | `eachMatch` с `emptyPattern` на `ab` | Ровно три пустых результата в позициях 0, 1, 2 |
| 14 | `replace` с `emptyPattern`, `ab`, `-` | Ровно `-a-b-` |
| 15 | `split` с `emptyPattern` на `ab` | Ровно четыре поля: пустое, `a`, `b`, пустое |
| 16 | Повторение `capture("x"; oneOf("ab"))` на `ab` | История x содержит отдельно `a` и `b` |
| 17 | Неудачная ветвь создала x; успешная ветвь создала x вновь | В результате только capture успешной ветви |
| 18 | Отсутствующий capture, пустой capture и `sameAs` | Три состояния различаются; пустой capture может успешно повториться |
| 19 | Успешный lookaround с внутренним capture | Внешняя позиция и внешний журнал captures не меняются |
| 20 | `behind(pattern := "a")` перед `"b"` с позиции 1 на `ab` | Успех `[1,2)`; источник слева не включён в результат |
| 21 | Emoji вне BMP в UTF‑8 и byte-профиле | Одна scalar unit против четырёх байтов; позиции не смешиваются |
| 22 | Невалидный UTF‑8 внутри отрицательного lookaround | Ошибка кодировки, а не успех отрицания |
| 23 | Caller имеет locals `left`, `right`, `name`, `captures` | У новых слов private исключает случайный autofill; captures не становятся caller-locals |
| 24 | Замена callable при отвергнутых пробных путях | Callback вызван по одному разу на выбранное совпадение; вставленный текст не сканируется |

## 12. Основания в документации LMX

Проект опирается на следующие текущие правила. Для форм `[]`/`@` первым применяется core ТЗ комплекта `LMX-TZ-2026-11-22-postfix-1`; прежние варианты в ссылочных документах подлежат его миграции:

- [Формы массивов и ссылок](LMX_Array_Reference_Types_Core.ru.md#forms), [интернированные коды](LMX_Array_Reference_Types_Core.ru.md#type-codes), [общий разбор](LMX_Array_Reference_Types_Core.ru.md#common-parsing), [направленный приём типов](LMX_Array_Reference_Types_Core.ru.md#admission), [миграция](LMX_Array_Reference_Types_Core.ru.md#migration) и [приёмка ядра](LMX_Array_Reference_Types_Core.ru.md#acceptance).
- [Пользовательские операнды](1/LMX_semantics.en.md#operand-receiver), [подготовленные аргументы](1/LMX_semantics.en.md#prepared-operands), [единственное открытие справа](1/LMX_semantics.en.md#operand-right-only-opening), [приоритеты](1/LMX_semantics.en.md#expression-priority).
