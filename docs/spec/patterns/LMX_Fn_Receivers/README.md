## Унификация по смыслу

`Name :: DATA`, существующие `signatureTypes` и `record`, postfix-типы `T[]`/`T@` и новые Pattern-слова используют общий Expression-механизм. `then` обозначает последовательность, `times/atLeast/atMost/optional` — ограничения повторения. Существующий `|` получает упорядоченную Pattern-альтернативу и сохраняет прежний числовой/Array-путь. Нового `or`, regex-парсера или отдельного раскрытия аргументов нет.

`range`, `slice`, `concat`, `map`, `filter` и операции изменения остаются обычными прямыми receivers. Унифицируются их общий типизированный доступ и алгоритмы; похожие внутренние имена не скрывают разные договоры. Например, публичный slice использует begin/end, старый внутренний helper — start/count; append изменяет тот же target, а прежний append создаёт новый контейнер. Эти различия явно переводятся в делегатах.

Каждая Structure уже является `@[]`. Универсальный @ принимает и плотный T[], и Structure без пользовательского boxing всего массива. Actual storage читается через фактический type-code. Выбор результата сохраняет оговорённый профиль; copy/merge, parent, lifetime и ошибки остаются обычными.

## Единое ядро и статус исполнения

Все перечисленные операции входят в проект одного текущего ядра и доступны напрямую. Опциональных пользовательских версий, client import или второго runtime не вводится. Внутренняя группа fun/const содержит ссылки на методы с их фактическими DATA/parent; квалифицированный путь нужен только при настоящей коллизии имён.

Сборка и отдельные src-файлы представляют одни исходники: загружают либо сборку, либо её части. Определения в reference сохраняют прежние алгоритмы текущего upload для пояснения; они не подключаются одновременно с основными телами. Именованная сигнатура пишется `Name :: DATA`, type-token вариант — существующий signatureTypes; публичный fn не возвращается.

В архиве нет исполняемого ядра LMX. Здесь написаны LMX-алгоритмы и конкретные интерфейсы интеграции, **но ни runtime-приёмка, ни скорость не подтверждены исполнением**. Общие операции metadata/type interning, postfix-head resolution и вызова надо связать с реальным ядром. Алгоритмы последовательностей, backtracking/captures, адаптации и кеширования не заменены непрозрачными вызовами готового движка.

## Приёмка и воспроизводимость

`python3 tools/rebuild_acceptance.py` синхронизирует 181 нормативное наблюдение с тремя корневыми ТЗ; все режимы остаются NOT_RUN. `python3 tools/rebuild_catalog.py`, затем `python3 tools/assemble.py` и `python3 tools/check_static.py` пересобирают каталог/исходник и проверяют комплектность, литералы, скобки, cutters и зависимости. Это ограниченные source checks, не P0 и не LMX-компилятор.

Перед сборкой `python3 tools/sync_effects.py` разрешает повторно используемые
конечные списки `throws` и сохраняет их компактную запись через `copy`.
Внутренний банк `FxThrows` хранит общие списки; отчёт
`tests/effect_contracts.json` содержит разрешённые имена по методам.
Инструмент сохраняет заявленные консервативные контракты и не выдаётся за
полный вывод эффектов или проверку всех динамических вызовов и `catch`.
Обычная обязанность обработать объявленный исход либо передать его через
собственный `throws` остаётся в силе; [API](API.md#ошибки) объясняет границу.

После интеграции `FxAllExamples\run()` явно запускает семь групп подготовленных проверок: прежние пять, последовательности и адаптеры. Он не запускается при чтении файла. Regex fixtures загружаются и запускаются по одному согласно их manifest, поскольку у независимых случаев могут совпадать локальные имена и разные ожидаемые ошибки. Каждый случай должен пройти четыре сочетания interpreter/native. До реального запуска в журналах остаётся NOT_RUN.

## Правило честного подсчёта

В usage-примере LMX используется прямой helper ядра, а контрольный язык использует
реальную библиотеку либо оператор с сопоставимым действием. Самописный foreign
helper из соседнего документа не импортируется клиентом. При сравнении реализаций
считаются полные тела объявленного договора и оговорённые зависимости. Основной
вариант — самый короткий допустимый по этой границе. Полный второй листинг
сохраняется только для другого способа решения; малые изменения становятся
примечаниями. Сам статус «входит в ядро» не даёт исключения из подсчёта.

При этом архитектурно оптимальный LMX не переписывается ради совпадения алгоритма
контрольного языка. Собственные общие примитивы LMX — copy, merge, binding,
обычный вызов и работа с графом — законно остаются примитивами языка; их runtime
реализацию не разворачивают в каждом сравнительном листинге. Проверка границы
касается сокрытия специфической работы helper за коротким вызовом, когда другая
сторона показывает эту работу вручную, а не требования одинакового алгоритма.
