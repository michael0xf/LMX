# LMX и другие языки: краткость, типизация и модель исполнения

Обновлено **21 ноября 2026 года**.

**В этой подборке LMX обычно короче Python и одновременно предоставляет типизацию, акторную конкурентность, низкоуровневые операции и сочетание интерпретации с нативным исполнением.** После расширения до 23 шаблонов LMX короче Python в 19 случаях, а суммарный объём меньше на 15,92%. Однако исключения теперь бывают существенными: тезис «изредка длиннее лишь на несколько процентов» точно описывает первые 18 примеров, но уже не всю подборку.

Речь идёт о свойствах модели языка и о стоимости предусмотренных ею операций. Сопоставимая с оптимизированным исполнением на JVM производительность нативного пути — архитектурно обоснованная возможность: типизированные вычисления и известные вызовы могут понижаться в обычный C, а машинные оптимизации выполнять внешний компилятор.

## Что именно измерено

Основная метрика — число непробельных символов полного показанного исходника. В него входят необходимые импорты, объявления, оболочки и `demo`. Пробелы, отступы и переводы строк не учитываются. Для дополнительных метрик полного размера и строк текст нормализуется к LF, без пустых строк по краям и с одним LF в конце. Внешняя команда запуска, добавленный для запуска `main`, печать результата, проверочные тесты и реализация runtime не входят в подсчёт.

Это сравнение конкретных реализаций согласованных задач. Имена не нормализованы; иной выбор имён или архитектуры может изменить числа. Python приведён без необязательных аннотаций типов. Использованы естественные для соответствующего языка средства: функции, замыкания, записи, интерфейсы, структуры или варианты перечисления. Дополнительные возможности одного представления не объявляются обязательными для остальных, если их нет в общем контракте задачи.

Примеры LMX используют общие DATA, автопередачу и обычные ссылки на методы. Объявления `int`, `return` и записанные требования уже входят в измеренный объём. При этом общий `@` не выдаётся за полную статически проверенную сигнатуру каждого callable.

## Результат первых 18 примеров

Для исходных двух подборок прежний вывод подтверждается буквально:

- LMX короче Python в **16 из 18 случаев — 88,89%**; равенств нет.
- Суммы: **4319 символов LMX и 5243 Python**; сокращение относительно Python — **17,62%**.
- **Adapter:** 163 против 160; LMX длиннее на **1,88%**.
- **Proxy:** 191 против 181; LMX длиннее на **5,52%**.
- Значительные сокращения: **Observer — 48,24%, State — 39,20%, Builder — 29,06%, Template Method — 25,25%**.

LMX минимален среди всех восьми языков в 15 из 18 случаев. Python имеет наименьшую сумму среди остальных семи, но выигрывает среди них не в каждой строке: минимум приходится на него в 14 случаях. C++ короче Python в Factory, Builder, Prototype и Memento. В Factory C++ также короче LMX: 297 против 304 символов.

## Что изменили пять дополнительных шаблонов

Singleton, Abstract Factory, Flyweight, Mediator и Interpreter расширяют выборку. После правок Flyweight и Interpreter сумма этой пятёрки составляет **1457 символов LMX против 1627 Python**: LMX короче суммарно на **10,45%** и в трёх отдельных примерах.

Два исключения в этой группе:

- **Singleton:** 141 против 127 — LMX длиннее на **11,02%**.
- **Interpreter:** 232 против 185 — на **25,41%**.

В [Flyweight](21_flyweight_comparison.md) обе версии теперь используют именованное поле `width`: LMX — в `immutable`-структуре, Python — в `@dataclass(frozen=True)`. Два обращения к `thin` возвращают один объект, позиция остаётся внешним аргументом. LMX занимает **281** символ против **309** у Python, то есть на **9,06%** меньше. Вложенная группа `drawing` видит `get` лексически; отдельные импорты и копирование общих объектов не нужны. Это пример разделения состояния, а не измерение экономии памяти.

В [Interpreter](23_interpreter_comparison.md) общий сценарий — сохранить выражение `(x + 3) + x`, вычислить его при `x = 2` и `x = 5`, затем сложить результаты. Python сохраняет форму композицией замыканий, LMX — в графе тела `calculate`, где вход называется `n`. Короткий LMX-листинг демонстрирует повторное вычисление этого выражения; универсальный API построения произвольных деревьев во время выполнения в него не включён. Остальные представления могут предоставлять такую возможность дополнительно.

Метод `add` в LMX определяется структурным контрактом DATA и разрешается по обычному имени, без регистрации в `sys\operand`. В его описании явно присутствуют обязательные `PASS_ARGS_AS_IS 0` и `PRIORITY sys\priority("+")`. Общий исполнитель подготавливает значения, а `\left` и `\right[0]` читают их; `return: int` возвращает обычное число. Режим `PASS_ARGS_AS_IS 1` передаёт исходные аргументные вхождения с явным вычислением через `sys\eval`, но в этом примере не используется. Отдельные `number`, `variable` и копирование через `merge` для этой записи не требуются. Основание: [контракт операндов, §§2–3](reference/to_fable_operands_arguments_priorities.md).

По всем **23 примерам**:

- LMX короче Python в **19 случаях — 82,61%**.
- LMX имеет общий минимум среди восьми языков в **18 случаях**.
- Суммы LMX и Python: **5776 и 6870**; сокращение — **15,92%**.
- Остальные суммы: Java — **9809**, C++ — **7743**, C# — **9105**, TypeScript — **8843**, Go — **8241**, Rust — **8890**.

Python остаётся самым коротким суммарно среди остальных семи языков и минимален среди них в **17 из 23** строк. Общие исключения относительно Python — Adapter, Proxy, Singleton и Interpreter. Поэтому вывод о частой компактности LMX сохраняется, а частоту и величину исключений следует относить к определённой подборке и её текущим листингам.

## Типизация и структурные контракты

Модель LMX предусматривает физические типы значений, описания допустимых значений, контекст преобразований и проверку структурной совместимости через `implements`. Одинаковое физическое представление структур не отменяет требований к используемым полям и операциям. Контракты могут различаться даже при совпадении представления: значение имеет допустимый диапазон и способ использования, а не только размер ячейки.

Поэтому корректно говорить, что компактная запись совмещается с типизацией и проверяемыми контрактами. Это не утверждение, что каждое требование известно статически: часть данных и целей вызова выбирается динамически, и проверка относится к соответствующему случаю потребления. Основания: [описания значений](reference/LMX_semantics.en.md#descriptions), [контекст типов и преобразований](reference/LMX_semantics.en.md#conversion-context), [проверка используемого интерфейса](reference/LMX_semantics.en.md#admission) и [контракт связывания и сигнатур](reference/LMX_Fable_TZ_Binding_and_Callables_v2_2026-11-19.md).

## Акторы, низкий уровень и два способа исполнения

Сравнение с Erlang относится к организации конкурентности: самостоятельное состояние участника, обмен сообщениями и последовательное исполнение внутри одного участника при возможности параллельной работы разных участников. В LMX Message имеет собственное владение графом, работающий Thread — почту и не более одного активного turn. Логический Thread не требует отдельного потока ОС. Это следует из [модели Message и акторов](reference/LMX_semantics.en.md#messages) и [арен](reference/L2_spec_en.md#arena). Erlang также строит конкурентность на самостоятельных процессах и асинхронных сообщениях; поэтому «акторная модель, архитектурно близкая Erlang» точнее общего слова «многопоточность». См. [документацию Erlang](https://www.erlang.org/doc/system/ref_man_processes.html).

Низкоуровневые адресные операции, работа с памятью и машинные интерфейсы находятся в L2. Структурное представление высокоуровневой программы совместимо с наличием такого слоя. [Область языка и уровни](reference/LMX_semantics.en.md#scope) определяют также интерпретацию графа и нативное исполнение: способ выбирается для конкретного вызова по подходящему нативному варианту или телу в графе. Разные участки одной системы могут использовать оба способа с общим контрактом поведения.

## Почему простой транслятор может давать быстрый нативный код

Единый граф программы не обязывает нативный путь обходить граф при каждой арифметической операции. Типизированные нативные локальные переменные имеют обычное машинное представление; числовые массивы хранят элементы плотно. Когда реализация, типы и связывание известны, предусмотрен прямой C-вызов без упаковки аргументов в граф, поиска по таблице вызовов и универсального диспетчера. См. [представление значений](reference/L2_spec_en.md#value-record), [native и связывание](reference/L2_spec_en.md#binding-executors), [прямые вызовы](reference/L2_spec_en.md#explicit-compilation).

Например, при общем объявлении `int: value` и результате `int`:

```lmx
with_one:
    return: base() + 1
```

Автопередача `value` может выражаться обычным C-параметром:

```c
int with_one(int value) {
    return base(value) + 1;
}
```

Это схема передачи значения; служебные параметры ABI в неполном фрагменте опущены. Изменяемое место вызывающего передаётся адресом его ячейки, сохраняя в LMX тип самой переменной. [Семантика связывания исполнителей](reference/LMX_semantics.en.md#binding-executors) отделяет этот транспорт от пользовательского типа.

Далее внешний C-компилятор может выполнять встраивание функций, распространение констант, удаление лишних вычислений и оптимизацию циклов. Такие проходы входят в [обычные средства GCC](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html). Собственному транслятору LMX достаточно выразить операции и связывание так, чтобы необходимые сведения сохранялись в C. Формулировка «без сложного собственного оптимизатора» поэтому имеет конкретный технический смысл.

## Смысл сравнения производительности с JVM

Для нативного пути сопоставимая производительность — обоснованная архитектурная возможность. Типизированные операции, прямые вызовы и обычные обращения к памяти не требуют обязательного штрафа относительно другого машинного кода. Наличие интерпретатора не заставляет нативные участки исполняться через него; [компиляция и выбор нативного исполнения](reference/LMX_semantics.en.md#explicit-compilation) являются отдельными механизмами.

Динамический выбор реализации, проверка неизвестного типа, обход структуры и копирование при `merge` сохраняют цену фактически выполняемой работы. Оптимизатор может устранять избыточность там, где имеет необходимые сведения. HotSpot тоже устраняет часть затрат абстракций: встраивает вызовы, включая некоторые виртуальные, и использует анализ выхода объектов для устранения некоторых выделений. См. [архитектуру HotSpot](https://www.oracle.com/java/technologies/whitepaper.html) и [описание оптимизаций JVM](https://docs.oracle.com/en/java/javase/24/vm/java-hotspot-virtual-machine-performance-enhancements.html).

Итоговая характеристика модели: **LMX часто позволяет записать рассмотренные задачи компактнее Python, сохраняя типизацию, структурные контракты, акторную конкурентность и низкоуровневые возможности. Интерпретация сочетается с прямым нативным исполнением через C99, для которого архитектура допускает производительность, сопоставимую с оптимизированной JVM, при использовании возможностей внешнего C-компилятора. По расширенной выборке краткость не универсальна, а отдельные преимущества Python существенны.**
