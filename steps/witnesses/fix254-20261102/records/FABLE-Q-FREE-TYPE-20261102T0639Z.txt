Step B (S7, tp116: the activation chain, design 4.5) -- one scoping question, the dependent part is held, the independent parts go on (the book sentence and docs regeneration; the kernel activation chain: records pushed by the walker's activation and by the native trampoline lmx_call_prim_values around entry(), anchored in the program arena so one chain spans both executors; the walker's entry-time resolution of its own free inputs from the chain; the native prologue registering its bindings).

The fact. Today a method's hidden input gets its C type in two ways: (a) the callee's own lexical source declaration (l2_frontend_lower scan_ident: own_visible + dt_of_own -- the twins hidden_input_* and most programs: a unit field read by a method), or (b) the closure -- the type of a binding of some caller down the chain, propagated by dyn_step/dyk_close to the fixed point -- and dyn_typed refuses an input left untyped ("unresolved dynamic=<name>", located at the free use). The walker needs the same static type: the header's ARG witness (lmx_walk_witness_type; lmx_walk_values_arg_place refuses a present input of another type). With the closure removed (design 4.5: a method's inputs are its own free names, resolution at the callee's entry through the chain of activation records), case (b) has no static type at translation: dev/l2src_sandbox/tests/unit_dyn_chain65.lm2 (m0 declares `char: quote`, 64 forwarders, leaf reads `quote = 65`), unit_dyn_leaf/mid/early/predecl/cap/bool (quote typed only by outer's local), steps/free-names.md's measured forms (k free in peek, typed only by the caller's T: k). The width is no problem (own free names only); the TYPE of such a name is.

The options I see. (1) A free name with no lexical source is runtime-typed in native code as it is in the walker: its place is a LmxWalkValue (the resolved binding's type travels with the value), every use goes through the kernel's value functions (lmx_walk_value_number & co.), a type mismatch at use is the runtime type error (the author: types are checked at runtime, the translator does no more typing than C needs -- here C needs only the record type). Norm-true; a large emitter change (every expression form over such a name: arithmetic, comparison, assignment, actuals, return), i.e. a slice of its own on top of the chain. (2) Static type = the lexical source's type when there is one; a located translation refusal at the free use when there is none ("a free name without a declaration in scope" -- today's unresolved-dynamic refusal kept, now reached also by chain65-style programs, whose type came only from a caller's local): the chain semantics stay (first binding up the chain, lexical fallback, forwarders form nothing, hold at entry), only such programs stop translating -- the corpus rows of that kind become refusals by the norm, recorded as expectation changes as 4.6 does for os_implements_refused; a present binding of another type than the lexical source is the runtime type error. (3) Infer the type from the name's uses in the method's text -- rejected by me (m0's char against leaf's `= 65` literal: a wrong guess, and it is analysis).

My proposal for tp116: (2), with (1) named in the design as the target of a later slice if you want it at all; or do you rule (1) inside tp116? In either case the walker side of B is the same (runtime-typed already). No author question in this: it is the scope of this slice under norms you have already given (no analysis, types at runtime, three passes).
