# M14: исходное поле, namespace и взятие адреса

Закрыто ответами автора. Сверено с действующей документацией 2026-11-15.

Вопрос исполнителя:

> Осталась одна граница между кадром и исходной data. В data записано `@: fptr getFuncPtr()`. После входа, до первого чтения fptr, код выполняет `data\fptr := 0`, затем `fptr("hello world")`. Голое fptr сохраняет исходное вычисляемое объявление, выбранное для кадра, или уже видит 0 из изменённой data? Локального присваивания fptr здесь не было.

Дословный ответ автора:

> после входа голые переменные независимы и голое var не видит никаких изенений в data\var, такое же универсальное правило у нас кстати для лексического и динамического связывания -- поля не меняются

Источник — [журнал автора](../2026-11-15.md#m14-independent-bindings).
Следствие: выбранное место кадра не отслеживает последующую замену исходного поля;
явное обращение к исходному графу остаётся отдельным обращением.

## Взятие адреса вычисляемого входа

Вопрос исполнителя:

> Для вычисляемого входного поля `int: x next()` остаётся случай, когда code не читает `x`, а только берёт `@x`. Должно ли взятие адреса вызвать `next()` и дать адрес обычной локальной int-ячейки? Это позволило бы сохранить обычные указатели без специального поведения при разыменовании.

Дословный ответ автора:

> 1 -- да, но как это "не читает" если он его упоминает? А что делает @(data\x) ? Тоже не читает?

Вариант 1 означал «Да, `@x` получает значение и адрес ячейки».
Источник — [журнал автора](../2026-11-15.md#m14-address-evaluates).

Вывод исполнителя: формулировка «не читает, а только берёт адрес» была неверной.
`@x` получает значение вычисляемого входа и адрес его локальной ячейки.
По общему правилу `@(data\x)` также вычисляет операнд `data\x`;
унарный `@` не подавляет вычисление записанного RHS. Источник обращения различен:
место кадра для x и исходный граф для явного пути. Это не правило автоматического
переноса между ними и не отдельный механизм указателей с вычисляемым разыменованием.

Если явный путь выбирает готовую ячейку, адресуется она. Для вычисляемого
объявления адресуется результат его исполнения; запись через адрес результата
не заменяет исходное объявление. См. [действующий контракт](../../docs/LMX_semantics.ru.md#computed-field-address)
и [пояснение хранения](m14-namespace-reading-20261115.md#место-результата-вычисляемого-поля).

## Хранение результата уточнено

Последующее [уточнение автора](../2026-11-15.md#m14-result-storage) подтверждает,
что адресуется вычисленное значение. Для реализации выбран обычный механизм
типизированной ячейки результата на стороне потребителя, как при сохранении
результата C-вызова в переменную и взятии её адреса. Отдельное общее хранилище
return не требуется. Задание внесено в to_sol и основной M14; наличие задания
не означает, что вычисляемый путь уже реализован.

Окончательная [граница задачи](../2026-11-15.md#m14-address-scope): `@(data\field)`,
где в data записано `int: field getValue()`; в разобранном native-пути используется
адрес уже существующего `l2_tN`, без специального выделения. Исследование `@f()`
не является поручением отдельно реализовать эту форму или ввести запрет как в C.
