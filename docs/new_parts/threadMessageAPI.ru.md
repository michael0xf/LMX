# API Thread, сообщения и протокол `post`

**Задание Fable: изменить спецификацию и реализовать согласованную модель.**  
Парный документ: [английская версия](threadMessageAPI.en.md).

## 0. Область задания, приоритет решений и требуемый результат

Это задание сводит последние решения автора из обсуждения. Оно описывает требуемую реализацию, а не утверждает, что текущий runtime уже всё это поддерживает. Использовать приведённые здесь исправления, а не прежние, отменённые объяснения.

Цель — один механизм: пользовательский граф Thread образует его API; обычные по виду вызовы становятся почтовыми запросами; почта связывает результаты с исходными запросами и раскладывает их по указанным в `answer` местам. Вся совместимость проверяется обычным механизмом LMX `implements`.

Не вводить отдельную объектную модель RPC, подсистему promise/future, глобальный реестр слушателей или вторую почту. Существующие операции доступа к ящику оставить. Основа — обычные построение графа, композиция, владение, исполнение и надзор.

**Особенно важно: входящие описания аргументов вида `ms: int: time` ОБЯЗАТЕЛЬНО поддержать через обычный структурный `implements`. Это общее требование LMX, а не специальная возможность парсера тайм-аутов.** См. §8.

Детали реализации, которые обсуждение не определило окончательно, отдельно перечислены в §12. Использовать уже согласованный контракт, если он их разрешает; иначе сообщить о недостающем решении, а не молча выбрать новую семантику. Эти открытые детали не отменяют и не переоткрывают подтверждённые требования.

## 1. Требуется: считать пользовательский граф API самого Thread

### 1.1 Один источник содержимого API

Считать тело/пользовательский граф Thread его API. Источник для построения словаря поиска — уже существующее массивное представление этого графа. Словарь является представлением для поиска по этим элементам, а не вторым независимо поддерживаемым описанием возможностей Thread.

Массив содержит обычные Structures: исполняемые тела, явно описанные callable `sub`/`fn`, используемые ими данные и структуры обработчиков, добавляемые протоколом. Сохранять обычное различие между присутствием Structure как данных и её исполнением в роли, заданной получателем.

API заполняется двумя явными способами:

1. Structures и ссылки явно передаются при построении/композиции пользовательского графа Thread.
2. Подготовка `answer` добавляет соответствующие структуры слушателей/мест назначения ответа в API отправителя теми же обычными графовыми механизмами. Почта записывает, к каким исходным запросам они относятся.

Изменения структуры выполнять по существующим правилам построения/`merge`. Не добавлять обязательные `registerMethod`, `registerListener` или параллельный реестр callback, который должен обслуживать пользователь. Производный словарь должен отражать реальный граф и сохранять всех подходящих кандидатов; нельзя молча заменить множественный подбор первым совпадением или затереть кандидата только из-за совпадения ключа поиска.

Настройки и обработчики конкретного `post` относятся именно к этому обмену. Два экземпляра одного исходного блока не должны перезаписывать связи ответов или настройки друг друга через скрытый глобальный слот.

### 1.2 Роли объектов вместо двух специальных входов

Изменение возникло при обсуждении рисования: экран и отрисовщик конкретной фигуры — разные роли объектов. Объекты создаются и получают явные ссылки. Не возвращать прежний специальный протокол `registerFigure` и не превращать один объект в обязательную пару входов `main`/`paint`.

У Thread по-прежнему одна полоса исполнения. Сохраняются существующее пошаговое обслуживание без выделенного потока ОС и исполнение на потоке ОС. Это задание не вводит новую потоковую модель GUI или отдельный физический поток для каждого элемента API.

## 2. Требуется: исполнение API по ходам и сохранение прямого доступа к почте

На `endturn` просматривать входящую почту и выполнять соответствующую работу API на полосе исполнения владельца. Исполняемые структуры API без аргументов и без результата последовательно выполняются в порядке массива как описанная автором повторяющаяся работа. Обычные циклы Thread продолжаются до пользовательского `success: 1`, с сохранением существующих правил ошибок, остановки и надзора.

«Без результата» означает отсутствие возвращаемого значения, а не текстовый поиск отсутствия bare `return`. Bare `return` может просто завершать `sub` или исполняемое тело.

Роли обработчиков сохраняют значение. Тело, связанное с `answer`, `undelivered`, `unanswered` или `catch`, исполняется при соответствующем исходе; помещение в API не исполняет его немедленно и не превращает в безусловное повторяющееся действие. Настройки внутри описания `post` тоже не являются командами, которые надо слепо выполнять сверху вниз.

Отправитель не исполняет код непосредственно внутри изменяемого графа получателя. Входящую работу выполняет полоса получателя. Запрос остановки не доказывает завершение и не разрешает освобождать ещё исполняемое состояние.

Сохранить `sendMessage`, `receiveMessage` и доступ callable к собственной почте. Сохранить согласованный вариант получения итератора по адресу, вариант получения всех доступных элементов и `0` как конец итератора/null. Использовать реальное существующее написание вызовов; не придумывать другой смысл адресного отбора и не считать без проверки, что вариант всей почты обязательно записывается `receiveMessage(0)`.

Ручное потребление и обработка через API используют один ящик. Уже извлечённое письмо не должно независимо извлекаться вторым способом ещё раз. Это требование к владению/потреблению, а не обещание сетевой гарантии exactly-once.

Последнее пользовательское письмо, подготовленное перед `success: 1`, проходит обычную публикацию успешного конца хода. Не отбрасывать его только потому, что пользователь завершает этот ход.

## 3. Требуется: выводить входную фильтрацию из содержимого API

Использовать исправленную автором таблицу:

| Состав API | Входная фильтрация |
| --- | --- |
| Есть обычные исполняемые Structures без формальных аргументов и результата | Принимать входящую пользовательскую почту без отсечения по сигнатуре на входе в ящик: эти тела могут сами разбирать произвольную почту через `receiveMessage`. |
| Только явно описанные `sub` | Полный отбор по контрактам аргументов **и отсутствию возвращаемого значения**, через обычный `implements`. |
| Только явно описанные `fn` | Полный отбор по входному и возвращаемому контрактам, через обычный `implements`. |

Прежнее утверждение «только `sub` — частичная фильтрация по типу ответа» было ошибкой и отменено.

Явно объявленный `sub` с пустым списком аргументов остаётся явно описанным callable. Не относить его к открытым обработчикам произвольной почты только потому, что у него нулевая арность и нет результата.

Принятие всей входящей почты не разрешает переинтерпретировать произвольную память или обходить контракт последующего получателя. Оно означает, что фильтрация по сигнатуре не может исключить письмо до того, как его получит произвольный обрабатывающий код.

Для смешанного явно описанного API с `sub` и `fn`, но без открытого тела обработки произвольной почты, применять полный собственный контракт каждого кандидата. Само смешение не включает приём всего подряд. Это следствие того же правила проверки каждого кандидата.

### 3.1 Обычный входящий запрос с телом

Для запроса, который не является связанным ответом, находить **все** подходящие элементы API: их входные контракты и требуемый контракт результата/отсутствия результата должны допускать запрос. Использовать обычное формирование аргументов и `implements`; не выбирать только первое совпадение.

Поэтому один входящий запрос, подошедший нескольким callable, может вызвать несколько реальных исполнений методов и их соответствующие результаты. Этот подбор на стороне запроса отличается от почтового размножения одного уже вычисленного ответа из §6.

Запрос, отклонённый фильтром API, не запускает метод и не вызывает его `catch`. Если отказ произошёл при доставке, он относится к исходному `undelivered`. Статически установленная несовместимость остаётся обычной диагностикой до исполнения: ради неё не требуется специально отправлять заведомо неправильный запрос.

### 3.2 Письмо без тела: сохранить требование автора

Автор также задал правило: **в случае письма без тела отправителю приходят все `sub` из массива API**.

Сохранить это требование в спецификации и плане реализации. В обсуждении не было окончательно определено представление возвращаемых данных и не было установлено, описывает ли его уже существующий контракт получения/просмотра API. Не подменять это молча правилом «выполнить каждый `sub` без аргументов», в том числе методы с обязательными аргументами. Точный операционный смысл вынесен в §12.

Не смешивать такое письмо без тела с концом итератора `0`, явно пустой Structure или отсутствием возвращаемого значения у `sub`.

## 4. Требуется: `post` как единый обычный ресивер протокола

Окончательная форма — `post`, принимающий Structure со следующими ветвями:

| Ветвь | Роль |
| --- | --- |
| `ask` | Один или несколько исходных запросов, записанных как обычные вызовы. |
| `answer` | Одно или несколько мест назначения/слушателей соответствующих вычисленных ответов. |
| `timeout` | Явные типизированные данные предела ожидания этого обмена. Это не аргумент вызываемого метода. |
| `undelivered` | Принимающее описание и тело для исходного запроса, который не доставлен/не принят. |
| `unanswered` | Принимающее описание и тело для истечения ожидания ответа на исходный запрос. |
| `catch` | Обычная обработка явно объявленного в `throws` выхода вызываемого callable. |

Например, в `getPixel: x y` имя `getPixel` разрешается в явно предоставленную ссылку на получателя/метод, а `x y` образуют тело запроса. `getPixel`, `setRed`, `ms` и подобные имена не становятся новыми зашитыми в ядро операциями.

Связь `ask`/`answer` структурная, аналогично обсуждавшейся паре `if`/`else`. И `ask`, и `answer` множественные. Внешний `post` явно ограничивает область их настроек и исходов.

Простейший пример без результата по-прежнему выглядит как обычный вызов:

```text
post:
. ask:
. . print: "hello world"
```

Здесь `print` — явно предоставленный адрес Message, а не обязательно встроенный вывод в stdout. Его контракт `sub` принимает текст и не возвращает значения. Не создавать `answer` или почтовое подтверждение только ради завершения такой отправки.

До отправки потребить и подготовить всё описание протокола: разрешить получателей, проверить нужные контракты, подготовить формирование аргументов, связать ответы и обработчики исходов с исходными отправками. В частности, первое положение `ask` в исходнике не означает, что письмо должно уйти раньше, чем обработаны следующие `answer` и `timeout`.

Не вводить синхронное ожидание, join-барьер, позиционный zip, общую транзакцию или неявный повтор для всего блока. У каждого исходного запроса своя идентичность и свои исходы.

## 5. Требуется: использовать существующие `implements` и конверсии

### 5.1 Аргументы запроса

Аргументы формируются обычной подстановкой/присвоением LMX, включая явно доступные преобразования и их контракты значений/диапазонов. Точное соответствие выбранному callable требуется **после формирования аргументов**, а не как буквальное равенство исходной Си-сигнатуры кандидата первоначальным описаниям вызывающего.

Контекст типов и конверсий — обычные данные, явно предоставленные конкретному Message, в том числе из root. Это не глобальный реестр процесса; создание одним Message другого само по себе не наследует этот контекст.

### 5.2 Получатели результата проверяются на стороне отправителя

При подготовке `post` автоматически проверить, может ли каждый указанный получатель `answer` принять результат вызываемого callable. В примере проверяется отношение:

```text
результат getPixel -> вход, потребляемый setRed
результат getPixel -> вход, потребляемый setGreen
результат getPixel -> вход, потребляемый setYellow
```

`uint32: rgb` описывает получаемый результат, связанный с именем `rgb`. Это не вопрос о том, что возвращает сам `setRed`. Реализованный через `sub` получатель `setRed` может принять результат `getPixel`, ничего нового не возвращая.

После подготовки связей и конверсий почта доставляет по ним. Не добавлять отдельный повторный подбор/согласование получателей при приходе ответа. Это не отменяет реального выполнения преобразования или проверки конкретного значения на формат/диапазон, если они входят в уже выбранную обычную конверсию.

Сохранить тесты принимающего выражения как часть существующего единого допуска. Не заменять этот механизм классификацией диапазона физических адресов или поверхностной сверкой сигнатуры. Сам аналитический этап не исполняет конвертеры или прикладной код кандидата; исполнение обязательных тестов и выбранных конверсий сохраняет свой существующий смысл.

### 5.3 Объявленные ошибки

Явный `throws` у `getPixel` должен покрываться обычным соответствующим `catch` или уже предусмотренным контрактом распространения. Граница Message не отменяет эту обязанность. Сохранить имя выхода и объявленный payload: не переименовывать его в недоставку и не создавать вместо него обычное значение возвращаемого типа.

## 6. Требуется: корреляция и размножение ответа силами почты

Почта сохраняет адрес/идентичность исходного сообщения и сопоставляет с ним ответы. Пользовательский код не должен создавать request ID, поддерживать таблицу корреляции или вручную выбирать обработчик сравнением идентификаторов.

Необходимые ссылки и время жизни сохранять по существующим правилам почты и владения, чтобы поздний ответ не оказался связан с другой отправкой или повторно использованным адресом. Это требование не предписывает новую схему идентификации.

### 6.1 Один запрос, одно вычисление, один ответ, три размещения

```text
ask:
. getPixel: x y
answer:
. setRed: uint32: rgb
. setGreen: uint32: rgb
. setYellow: uint32: rgb
```

В этом примере выполняется один выбранный `getPixel` и получается один исходный ответ. **Почта размножает/распределяет готовый ответ на три места.** Это не три вычисления пикселя и не три исходных ответа.

```text
Q1 -> однократное исполнение getPixel -> R1
почта кладёт R1 в setRed, setGreen и setYellow
```

### 6.2 Три запроса, три исходных ответа, девять размещений

```text
ask:
. getPixel: x y
. getPixel: x + 1, y + 1
. getPixel: x + 2, y + 2
answer:
. setRed: uint32: rgb
. setGreen: uint32: rgb
. setYellow: uint32: rgb
```

```text
Q1 -> R1 -> setRed, setGreen, setYellow
Q2 -> R2 -> setRed, setGreen, setYellow
Q3 -> R3 -> setRed, setGreen, setYellow
```

**Три исходных запроса; три прикладных исполнения; три исходных ответа; девять почтовых размещений.** Получатели затем выполняют свою работу при потреблении доставленного. Не смешивать эту последующую работу с повторным исполнением запрошенного метода.

Каждый исходный ответ сохраняет связь со своим Q1/Q2/Q3. Строки получателей и запросов не сопоставляются по номеру. Не требуется накапливать результаты до завершения всех запросов.

Если входящий запрос подходит нескольким callable получателя, сначала учитываются реальные ответы этих методов; уже затем к каждому применяется подготовленное почтовое размножение по местам назначения. Само размножение никогда не увеличивает число исходных вычислений.

Эти числа относятся к прикладным запросам после подготовки, а не к отдельным вызовам из обязательных тестов допуска. Представление размноженных доставок в памяти определяется существующими правилами копирования/владения: не предполагать совместный доступ разных Messages к изменяемой памяти и не требовать копирования исполняемых тел.

## 7. Требуется: различать доставку, результат, `throw` и истечение ожидания

| Событие | Требуемый смысл |
| --- | --- |
| Исходный запрос не доставлен/не принят | Связанный `undelivered` выполняется у отправителя с исходным адресатом и сформированными аргументами запроса. |
| Вызываемый `fn` нормально вернул значение | Результат получается один раз; почта связывает и распределяет его через `answer`. |
| Вызываемый callable вышел через объявленный `throw` | Объявленный выход и payload направляются обычному связанному `catch`. |
| По настройке `timeout` истекло ожидание ответа | Для исходного запроса срабатывает `unanswered` по согласованной политике тайм-аута. |
| Получатель завис или перестал продвигаться | Ответственность остаётся у общего надзора за Thread, взаимных опросов и остановки. Тайм-аут запроса не доказывает смерть получателя. |

Почта **не** отправляет пользовательскому коду свои подтверждения успешной доставки. Если пользователю нужно состояние доставки, он смотрит существующие флаги через API собственной почты. `answer` предназначен для вычисленного пользовательского ответа, а не для созданного почтой ACK.

Корректный нормально завершающийся `fn` возвращает результат либо выходит через применимый объявленный механизм ошибки; «успешно закончил, но молча забыл результат» не является ещё одним нормальным исходом. Напротив, `sub` намеренно не возвращает значения и не требует синтетического результата для признания успешного исполнения.

Диагностика использует уже сформированные исходные аргументы. Не вычислять заново `x + 1` после того, как `x` отправителя изменился.

`timeout` находится в `post`, отдельно от `ask`. Размножение одного ответа на три места не создаёт трёх новых ожиданий исходного вычисления. Тайм-аут не отменяет и не повторяет вызываемый метод, не освобождает его живую арену и не устанавливает флаг завершения другого участника.

Начало отсчёта, граница получения своевременного ответа, поздние ответы и диагностический смысл параметра обработчика `time` автор окончательно не выбрал; см. §12. Не превращать прежнее предложение ассистента в молча принятое правило.

## 8. ОБЯЗАТЕЛЬНАЯ ОБЩАЯ ПОДДЕРЖКА: вложенные типизированные входящие аргументы

### 8.1 `int` — ресивер, а не переменная на пути данных

Окончательная настройка:

```text
timeout: ms: int: time 500
```

`int` потребляет объявление, создаёт и инициализирует типизированную привязку `time`. Путь в данных настройки:

```text
timeout
  ms
    time -> целое значение 500
```

Поэтому значение адресуется так:

```text
timeout\ms\time
```

Не через выдуманный дочерний элемент `int`. Исходный граф кода может представлять применение ресивера `int`; это нельзя смешивать с получившимся расположением данных. Не возвращаться к `ms: int: 500`: окончательная декларация явно содержит имя создаваемого значения `time`.

### 8.2 Описание формального аргумента использует тот же общий механизм

Формальная часть обработчика:

```text
(ms: int: time; getPixel: method; int: x; int: y)
```

**Реализовать `ms: int: time` как обычное вложенное структурное описание аргумента.** Контракт получателя включает ветку `ms` и её целочисленную привязку. Обычный `implements` проверяет необходимую структуру и допустимость потребления листа; обычное связывание аргументов делает принятое значение доступным в обработчике под локальным именем `time`.

Не сворачивать описание до голого `int` перед структурной проверкой. Не требовать для этой формы нового `Duration`, обязательного тега `unit`, привилегированного класса миллисекунд или внешней подсистемы единиц измерения.

У входящего формального описания нет инициализатора, потому что значение предоставляет реальное сообщение. `time` — формальная привязка, а не свободный поиск, который должен случайно прочитать настройку тайм-аута. Сопоставление/нормализация формальных имён следует обычным правилам LMX, а не отдельному правилу тайм-аута.

Поддержка должна распространяться на другие имена ветвей, ресиверы листьев и глубины вложенности. Посторонняя ветка с целым листом сама по себе не становится `ms`; переход между такими смысловыми ветвями допустим только тогда, когда его явно предоставляет существующий контекст конверсий Message. Одно примитивное числовое преобразование не переименовывает структурные роли.

### 8.3 Два разных обращения в окончательном журналировании

Внутри `unanswered`:

```text
time                  # значение, полученное этим обработчиком
timeout\ms\time       # настройка именно этого post
```

Они должны оставаться различными. Обработчик сохраняет доступ к настройкам своего обмена, а не к последнему `post`, выполненному где-либо в процессе.

В обсуждении предлагалось передавать обработчику фактически измеренное время ожидания, оставляя `500` настроенным пределом. Этот диагностический смысл надо связать с реальным контрактом времени; структурная поддержка и раздельные привязки обязательны независимо от такого выбора.

## 9. Обязательный опорный пример

Сохранить эту исходную форму. В английском документе переведён только поясняющий комментарий о `throws`; операции, структуры аргументов, пути и текст журналирования в обеих версиях одинаковы.

```text
post:
. ask:
. . getPixel: x y
. . getPixel: x + 1, y + 1
. . getPixel: x + 2, y + 2
. answer:
. . setRed: uint32: rgb
. . setGreen: uint32: rgb
. . setYellow: uint32: rgb
. timeout: ms: int: time 500
. undelivered: (getPixel: method; int: x; int: y)
. . log\error: "undelivered: " method "( x: " x " y: " y " )"
. unanswered: (ms: int: time; getPixel: method; int: x; int: y)
. . log\error:
. . . "unanswered after " time " ms "
. . . method "( x: " x " y: " y " ) timeout: " timeout\ms\time
. . end: error
. catch: axisOutOfBound (int: value; int: number) # требуется явным throws в getPixel
. . println: "axis: " number " value: " value
```

Ведущие точки выражают вложенность. `end: error` — явно указанное автором закрытие выражения журналирования. Сохранить вложенные ресиверы и обычную обработку явного закрытия; не создавать отдельный парсер под этот пример.

### 9.1 Подготовка

Окружающий Message явно предоставляет адресатов, `x`, `y`, logger/printer, описания типов/ресиверов и контекст конверсий. `post` получает настройку тайм-аута, три исходных вызова, три места назначения ответов и связанные обработчики.

Например, при текущих координатах `x = 10`, `y = 20` формирование аргументов даёт:

| Исходный запрос | Адресат | Сформированные аргументы |
| --- | --- | --- |
| Q1 | `getPixel` | `10, 20` |
| Q2 | `getPixel` | `11, 21` |
| Q3 | `getPixel` | `12, 22` |

Q1/Q2/Q3 — поясняющие обозначения, а не новый пользовательский синтаксис идентификаторов. Почта использует идентичность исходных сообщений. Настройки и связи слушателей должны быть готовы до отправки.

Проверить каждый запрос по выбранному контракту адресата и каждый маршрут результата — стандартным `implements` на стороне отправителя. В этом примере считаем, что объявленный результат `getPixel` допускает потребление как `uint32`, а показанный `axisOutOfBound` входит в его явные `throws`.

### 9.2 Все запросы успешны

Каждое вызванное исполнение возвращает один цвет. Почта раскладывает каждый цвет в `setRed`, `setGreen`, `setYellow`. Всего три исходных результата и девять размещений. Обработчики недоставки/истечения ожидания и показанный `catch` не выполняются.

### 9.3 Q2 не доставлен

`undelivered` получает исходного адресата `getPixel` в `method` и сформированные аргументы Q2: `x = 11`, `y = 21`. Он журналирует этот запрос без повторного вычисления аргументов. Если Q1 и Q3 успешны, они по-прежнему дают два исходных результата и шесть размещений. Отказ Q2 не превращает весь `post` в отменённую транзакцию.

### 9.4 Q2 превысил предел ожидания

`unanswered` получает исходного адресата и сформированные координаты Q2, а также вложенный аргумент `ms`, связанный с локальным `time`. Журналирование отдельно читает настройку обмена по `timeout\ms\time`, получая `500`.

Если принято толкование фактически прошедшего времени и почта передаёт `time = 512`, запись различает «unanswered after 512 ms» и «timeout: 500». Это числовая иллюстрация такого толкования, а не выбор начала отсчёта или политики поздних ответов за автора.

### 9.5 Q2 вызывает `axisOutOfBound`

Связанный `catch` получает `value` и `number` из объявленного payload исключительного выхода. Это не псевдонимы аргументов запроса `x` и `y`: их смысл задаёт контракт ошибки `getPixel`. У этого исполнения нет обычного цветового результата для размножения.

Отказ фильтра сигнатур до исполнения метода — другое событие; нельзя изображать его как выброшенный `axisOutOfBound`.

### 9.6 Несколько подходящих методов адресата

Вне теста с одним `getPixel` обычный входящий запрос, не являющийся ответом, может соответствовать нескольким элементам API. Каждый выбранный метод выполняется по своему контракту. Каждый реальный нормальный ответ сохраняет связь с исходным запросом и распределяется почтой по уже допущенным местам назначения. Не вводить выбор только первого совпадения и не превращать размножение ответа в причину повторного вызова исходного метода.

## 10. Работы по реализации и приёмочные тесты

### 10.1 Порядок работ

Сначала изучить живое дерево исходников и текущие тесты. Затем:

1. Поддержать/исправить общие вложенные формальные описания и структурное связывание в обычных `implements` и формировании аргументов, независимо от возможности тайм-аута.
2. Сделать пользовательский массив Thread источником API; строить/обновлять поиск без второго авторитетного реестра.
3. Реализовать исправленные случаи фильтрации, несколько подходящих адресатских методов, исполнение по ходам и сосуществование с явным потреблением почты.
4. Реализовать подготовку `post`, автоматическую совместимость результатов на стороне отправителя, добавление `answer` и связь с исходными запросами.
5. Реализовать почтовое размножение ответа, `undelivered` и сохранение объявленных `throw`/`catch`.
6. Подключить тайм-аут к согласованной существующей модели времени; до заявления о завершённости соответствующих случаев разрешить только действительно отсутствующие решения из §12.
7. Совместно обновить относящиеся к этому документы L3/L2/L1 и заметки ядра. При фиксации решений синхронизировать обе языковые версии задания.

### 10.2 Минимальные наблюдаемые тесты

| ID | Проверка | Требуемое наблюдение |
| --- | --- | --- |
| T01 | API построен из явно предоставленных Structures | Словарь представляет эти элементы; отдельная пользовательская регистрация не требуется. |
| T02 | Подготовка `answer` | Структуры слушателей/назначений и связи с исходными запросами существуют до отправки. |
| T03 | Два живых экземпляра одного `post` | Ответы и настройки не переходят между экземплярами. |
| T04 | API с открытым обычным исполняемым телом | Иначе несовместимое письмо может попасть в ящик для ручной обработки. |
| T05 | Только `sub`, включая безаргументный `sub` | Полная проверка аргументов/отсутствия результата; нет автоматического приёма всего и синтетического ответа. |
| T06 | Только `fn` | Полная фильтрация входа/результата; отвергнутый запрос не выполняет тело адресата. |

| T09 | Разрешённая конверсия и значение вне диапазона | Используется существующий конвертер; неверное значение не обходит правила диапазона/формата. |
| T10 | Один запрос и три назначения | Одно прикладное исполнение, один исходный ответ, три размещения. |
| T11 | Три запроса и три назначения | Три прикладных исполнения, три исходных ответа, девять размещений. |
| T12 | Ответы пришли в другом порядке | Каждый сохраняет исходный запрос и правильные назначения. |
| T13 | Второй запрос не доставлен, отправитель затем изменил `x/y` | Обработчик получает уже сформированные исходные аргументы второго запроса. |
| T14 | Объявленный `axisOutOfBound` | Правильный `catch` отправителя и payload; нет выдуманного успешного цветового ответа. |
| T15 | `timeout: ms: int: time 500` | Значение в данных находится по `timeout\ms\time`; `int` не является узлом пути данных. |

| T17 | Тот же вложенный механизм с другим именем ветви/типом листа | Общая поддержка без зашитых веток `ms`, `timeout` или `uint32`. |
| T18 | Отсутствующая/другая смысловая ветвь | Отказ, если существующий явный контекст не допускает требуемую структурную конверсию. |
| T19 | `time` обработчика отличается от настройки тайм-аута | Журналирование читает два разных значения из правильных источников. |
| T20 | Истечение, своевременный ответ, поздний ответ, гонка на границе | Поведение соответствует явно закреплённой политике таймера; нет случайного двойного срабатывания. |

| T25 | Письмо без тела | Соответствие авторскому «все sub» после определения точного контракта payload. |

Тесты пограничных тайм-аутов и ответа на письмо без тела явно остаются ожидающими до фиксации соответствующих контрактов. Сборка или разбор исходника сами по себе не доказывают поведение при исполнении.

## 11. Отменённые идеи и запрещённые подмены

- Не «`sub` проверяет только тип ответа»: проверяются аргументы и отсутствие возвращаемого значения.
- Не вставлять в `answer` пользовательский почтовый ACK.
- Не повторять `getPixel` ради нескольких мест доставки ответа.
- Не перекладывать корреляционные ID и циклы выбора callback на пользователя вместо почты.
- Не добавлять вторую подсистему совместимости при получении ответа после подготовки отправителем.
- Не добавлять аргумент `timeout` в `getPixel` и не прятать настройку в голове `ask`.
- Не вставлять переменную/поле `int` в путь `timeout\ms\time`.
- Не сворачивать `ms: int: time` до голого целочисленного контракта.
- Не вводить новый примитив единиц, обязательную номинальную обёртку или глобальную таблицу конверсий.
- Не обходить общие правила LMX специальным написанием, именем API или сравнением Си-сигнатур.
- Не повторять/отменять вызов, не освобождать его память и не создавать успешный результат автоматически по тайм-ауту.
- Не возвращать отдельную публичную регистрацию методов/слушателей или обязательный двухвходовый GUI-объект из прежнего наброска.

## 12. Решения, окончательно не закреплённые в обсуждении

Это точки завершения спецификации, а не приглашение переделать согласованный механизм.

**O1 — Письмо без тела.** Отправитель получает все `sub`. Уточнить точное представление и наличие уже принятого протокола получения/просмотра API, включая отличие от явно пустого тела аргументов.

**O2 — Время и диагностика.** Уточнить фазу начала отсчёта (подготовка, публикация, приём или другая уже определённая граница), момент удовлетворения ожидания ответом и смысл локального `time` обработчика. «От публикации» и «фактически прошедшее время» были предложениями ассистента, а не окончательными явными решениями автора. Определить применение одной настройки тайм-аута, когда один запрос выбирает несколько методов с результатом. Намеренно безрезультатный `sub` не должен становиться ошибкой только из-за отсутствия результата.

**O3 — Поздние исходы.** Определить обработку ответа/объявленного `throw` после `unanswered`, гонку ответа с истечением и освобождение связанных слушателей. Прежнее предложение отбрасывать поздние ответы не было окончательным решением автора. Отказ доставки уже вычисленного ответа одному из назначений `answer` не доказывает недоставку исходного `getPixel`; использовать применимую политику ошибок самой почты.

**O4 — Порядок хода и жизнь слушателей.** Согласовать точный порядок входящей обработки, обычных безаргументных безрезультатных тел, изменений API, публикации исходящих и завершения с текущим контрактом ядра. Указать, когда видны добавленные обработчики, какие ожидающие обработчики переживают какие ходы и как освобождаются ссылки на исходные сообщения. Не заменять это рекурсивным входом в чужой Thread.

## 13. Результат работы и карта источников

Предоставить согласованный патч живой реализации и соответствующих спецификаций, исполняемые положительные и отрицательные тесты, а также отчёт: точная ревизия/дерево, команды тестов, фактические результаты и оставшиеся несовпадения. Отдельно показывать число исполнений запросов, число исходных ответов и число размещений. Один успешный exit code не доказывает, что обработчик или вызываемый метод действительно исполнился.

- `CORE(1).md`, §§5–6: жизненный цикл Thread, публикация успешного хода, владение почтой и существующий надзор.
- `LMX_semantics.en.md`, §§5–6: явные описания, конверсии, структурный `implements` и обязательные тесты получателя.

В приложенных документах есть переходный и старый текст. В частности, старое буквальное равенство callable-сигнатур не должно отменять позднее согласованное правило формирования аргументов/конверсий; прежние леса наброска `main`/`paint` в задание не входят. Реализовать решения автора, а не реконструкцию знакомого внешнего RPC-фреймворка.
