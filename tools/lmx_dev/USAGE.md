# LMX: как пользоваться сервисами разработки

Эту инструкцию читают рабочие агенты проекта при старте. Почтальон `lmx_uds`
исключён: он доставляет сообщения, а не выполняет проверки. Ведущий проекта —
**codex (Sol)**; astra — его консультант. Роли и правила делегирования сохраняются.

## Поиск нормы

Для поиска действующего правила сначала используй MCP-сервер **`lmx-dev`**,
инструмент **`get_spec_rule`**. В Claude Code имя обычно имеет префикс
`mcp__lmx-dev__`; в Codex используй инструмент сервера, показанный клиентом.

Примеры аргументов:

```json
{"topic":"R0"}
{"topic":"int@:"}
{"topic":"динамическое связывание"}
{"topic":"then"}
```

Ответ — дословный фрагмент текущей `docs/spec`, его роль, источник, строки и хеш
рабочего дерева. `ambiguous` требует выбрать подходящий `ruleId`, а не угадать
значение. Для `sectionTooLarge` повтори запрос по `ruleId` с достаточным
`max_chars`, прочти весь раздел. Связанные правила читай по `related` и ссылкам
самой нормы. При `notFound` открой действующие документы обычным способом:
корпус сервиса перечислен в `catalogue.json`, он не охватывает все файлы.
Результат поиска не заменяет чтение условий, исключений и конкретного кода.
Не исправляй документацию под ограничения старого компилятора.

## Проверки и сборки

Сначала вызови **`service_status()`**. `configured=true` означает наличие
адаптера; возможность запуска определяется также permit, mutex и ресурсами.

- `check_file(file, phase="syntax")` — только P0-разбор, без выполнения программы.
- `check_file(file, phase="translate")` — перевод `.lm2` в L1 принятым FE;
  внутри есть его CHECK. Это не реализация нормативного `sys\translate`.
- `check_file(file, phase="static")` сейчас возвращает `unavailable/notRun`:
  отдельного нормативного CLI `sys\check` нет. Не выдавай перевод за этот этап.
- `bootstrap(profile="smoke")` запускает компонентный suite10 и исполняет его
  программы. Это не самосборка поколений.
- `bootstrap(profile="selfHost")` — **полная G1/G2**, full-suite и штатные
  сравнения. Выбирается только ведущим при основаниях из
  [to_fable2_fast_build.md](../../to_fable2_fast_build.md), не на каждом шаге.

Все compiler/test/docs действия координирует **codex**. Sonnet, Haiku и другие
исполнители не открывают permit, не снимают lock/markers и не запускают проверки
параллельно с ведущим. При закрытом окне передай запрос codex, продолжай независимую
работу. Исполнители не обходят закрытый сервис несогласованной прямой командой
компилятора. Это окно относится к закреплённому W3-адаптеру, а не ко всем работам
проекта: ведущий вправе выполнять уже разрешённые автором официальные producers
другого согласованного комплекта, в частности W4, под тем же `machine.lock.d`
и своим memory guard. Закрытый W3 permit такую работу координатора не запрещает.

Текущий адаптер закреплён на принятом комплекте **W3**. Smoke/selfHost используют
частную копию принятой стадии W3 и не проверяют автоматически будущий W4 или новые
правки ядра. Перед применением к новому срезу ведущий обновляет согласованные
producers, stage и pins. Нельзя смешивать W3 runtime с W4 headers основного S.

`passed` подтверждает только `achievedPhase`. `rejected` — отказ проверяемого
входа. `unavailable/notRun` означает, что запуска не было. Timeout, crash,
`protocolError`, `resourceLimit`, отмена и `stale=true` не являются успехом.
Полные argv, входы, журналы и артефакты лежат по `receipt`/`log`; в отчёте указывай
реальный исход, фазу и эту ссылку. Не запускай заново широкие проверки без причины.

## Если текущая сессия ещё не видит MCP

Конфигурация добавлена в Codex и целевые bat-файлы. Уже работающий процесс может
сохранить прежний набор MCP до переподключения/перезапуска. Не перезапускай чужие
сессии или занятый конвейер самостоятельно. До обновления используй **тот же CLI**:

```powershell
$lmxDevPython = 'C:/Nyasha_Planet/LMX/build2/lmx_dev/venv/Scripts/python.exe'
$lmxDevEntry = 'C:/Nyasha_Planet/LMX/tools/lmx_dev/entry.py'
& $lmxDevPython $lmxDevEntry spec R0
& $lmxDevPython $lmxDevEntry status
& $lmxDevPython $lmxDevEntry check path/to/file.lm2 --phase syntax
```

CLI применяет ту же блокировку, permit и адаптеры. Это не обход политики.
Не запускай bat другого агента ради подключения сервиса: так создаётся лишняя
модельная сессия. MCP-процесс Python запускает сам клиент.

## Проверка подключения и отчёт

Если поручена проверка подключения, достаточно **доступности инструмента, поиска
и status**, без нового compiler/build окна: `R0`, `int@:`, неоднозначный `then`
и `service_status`. Допустим CLI fallback, если инструмента ещё нет в текущей
сессии; явно различай эти результаты. Не открывай permit ради этой пробы и не
повторяй её автоматически при каждом обычном шаге.

После проверки отправь через `lmx_uds` **To: codex** содержательный отчёт:
использован MCP или CLI, запрос, статус, `ruleId`/источник, состояние окна и ошибки,
если они есть. Добавь: **«По просьбе astra и поручению автора используем lmx-dev
для поиска правил и согласованных проверок; инструкция — tools/lmx_dev/USAGE.md»**.
Отчёт адресуется ведущему codex, не astra. Транспортный ACK не заменяет результат.
