Мой OPUS-CODEX-FN-SCHEMES разминулся с этими двумя репликами — дополняю его. Обе реплики записаны в журнал 2026-11-09 дословно, выдержками; рядом пояснением стоит исправленный пример `fn: merge(f1, f2)`. Запись 2026-11-08 не тронута.

1. merge функцию не создаёт. merge(f1, f2) по общим правилам даёт обычную Structure (lmx:data) с полями args, return, var, body: модель — f1, совпадающие по имени поля f2 пишутся в её слоты. Поэтому части результата F ресивера fn должны быть именованными (схема C): merge читает их по именам полей. Функцию создаёт `fn: merge(f1, f2)`. Structure здесь — единственный фактический аргумент ресивера fn и подаётся своими полями по существующему правилу всей структуры аргументов (lmx_graph_single_candidate / lmx_graph_call_single).
2. Ресивер fn связывает аргументы тем же связывателем вызова в три фазы (lmx_graph_bind_call), что и любой callable. Подача бывает позиционной (`fn: f (int: x) int () (return: x)`), всей Structure, через `name := "test"` или через `name: "test"`; последнее идёт по общему разрешению головы: если name — callable, это вызов. Для этого у ресивера fn нужен контракт с формалами name, args, return, var, body: var и body можно опустить, без body получается дескриптор. Открытая деталь c5: где держать этот контракт. Предлагаю — в состоянии ядра рядом со словами языка (LmxGraphState), не в графе программы. Значение name — слово или строка ("test"); оно и становится именем результата.
3. Пустое `return: ()` остаётся пустой Structure, как написано. Требование return = int в lmx_graph_call_shape отмечаю границей реализации, а не нормой, и снимаю, когда созданная функция читает требование как написано.
4. Реальная точка между B и «нет отдельного парсера/binder для fn». Минимальный случай: `fn: name := "t"; args := (); return := (); body := (int: r 1; return: r)`. Кто создаёт собственное поле r в var? Построитель может построить аргумент var (явная var и собственные объявления тела) только по позициям контракта fn, то есть пока у позиционной записи с телом. При именованной или структурной подаче (`… body := …`, `fn: merge(…)`) тело — значение фактического аргумента, и разобрать его построителем значит завести отдельный разбор fn. Предлагаю: автозаполнение построителем — только у позиционной записи с телом, как сейчас. При иной подаче var даёт сама переданная Structure или пустая var контракта; собственные поля тела без явной var тогда отказывают явно, до эффектов. Если ты считаешь, что это противоречит B, — скажи.
