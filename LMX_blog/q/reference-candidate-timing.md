# Поле-ссылка тела Structure с кандидатом-Structure: связывается при построении или при выполнении тела

Статус: РЕШЕНО по утверждённым общим правилам, 2026-10-12. Вопрос задавал `fable_pc` при срезе R6-2 (4) тикета
[critical_general_receiver_routes_bug](../../steps/tickets/critical_general_receiver_routes_bug.md)
([перепись](../../steps/receiver-routes-census-20261010.md), раздел «Slice R6-2 (4)»); передан автору через
Codex почтальоном `lmx_uds` (STATUS FABLE-STATUS-20261011-27).

## Контекст

Книга ([L2 §12](../../docs/L2_spec_ru.md)): для отсутствующего `b` записи `b: A` и `@: b A` равнозначны —
явное присваивание ссылки; преобразование и `implements` относительно потребителя предшествуют записи.
Общее правило инициализации ([семантика, #dynamic](../../docs/LMX_semantics.ru.md#dynamic)): вычисляемая
инициализация — два обычных соседних оператора, присваивание выполняется, когда управление доходит до строки;
скрытой фазы *исполнения вычисляемого выражения* при создании графа нет. Это не запрещает хранить уже известное
начальное значение прямо в типизированной ячейке, как в `int: a 1`.

Транслятор сегодня (замер на `2a711a13`, native и walkroot) делает две формы по-разному:

- связывание `p: Model` в теле юнитовой Structure `Holder` — строка связывания (`l2_ns_bind_item`,
  `l2_emit_ns_refs`): после `h: merge: Holder` ячейка `h\p` сразу указывает на Model;
- типизированная форма `@: Model p Model` в том же теле — оператор тела: после `h: merge: Holder` ячейка `h\p`
  пуста, после голого оператора `h` (Structure выполнена) указывает на Model и `h\p\v` читает 11; `@: Model p q`
  (q — поле-ссылка выше) связывается так же, через q; `@: Model p Other` без поля v — отказ «implements is false
  in assignment»; `@: Model p 5` — «assignment value has incompatible type».

Пять зафиксированных фикстур (`unit_local_reference_model_copy_deep` и родственные, срез COPIER-FULL-COPY
2026-10-10) закрепляют текущее отложенное связывание для локальных Structure метода с вложенным референтом.
Эти оракулы не доказывают языкового исключения: при создании локального вхождения `@: Inner ref Inner`
должно ссылаться на его собственный `Inner`, а при полном `merge` — на копию референта по общей карте.

## Решение

При известном кандидате `Model` `p: Model` (отсутствующее `p`) создаёт ссылочную ячейку с начальным адресом
уже существующей Structure `Model`: это **не `merge` и не копия**. Форма `@: p Model` равнозначна; форма
`@: Model p Model` добавляет типизированное требование и допуск, но не меняет способ или момент связывания.
Это аналог известного начального значения `int: a 1`: запись можно представить значением типизированной
ячейки при создании соответствующего вхождения графа, сохранив возможность восстановить исходную Structure.
Создание вхождения — не исполнение его тела; если вхождение копируется `merge`, ссылка на копируемый референт
перенаправляется общей картой копирования. Вычисляемый кандидат, напротив, требует обычного исполняемого
действия при достижении строки. Прежний вывод Codex, что раннее заполнение `p: Model` — баг и обе формы
непременно должны исполнять `PUT` в теле, был ошибкой.

## Что зависит от ответа

Срез R6-2 (5) (операторы тела результата merge: какие объявления тела — данные, какие — код); срез ядра по
дефекту [MERGE-REFERENCE-TO-OPERAND](../../steps/defects.md#merge-reference-to-operand) (какие ссылки на
со-операнд видны статически); свидетели `unit_ns_ref_statement`, `unit_ns_ref_var`, `unit_ns_ref_zero`,
закрепляющие старое поведение. До исправления транслятор остаётся расходящимся с правилом: `p: Model`
сразу получает известный адрес, а типизированная форма с тем же известным кандидатом откладывает запись
до вызова тела. Старые оракулы надо пересмотреть вместе с кодом; не менять общий маршрут вычисляемых кандидатов.
