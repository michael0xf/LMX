# Спецификация L1

Область — язык L1, трансляция в C99 и реализация ядра L2 на L1/C. Основание — `l1src/` (16 файлов с корня L1) и `l2src/` (песочный снимок ядра), коммит L1 `b2a7c98aa59aaf9654f2180e6f2a149e58aa48ee`. Семантика L3 — [основная спецификация](LMX_semantics.ru.md). Операции и модель ядра на уровне L2 — [спецификация L2](L2_spec_ru.md). Срез и расхождения — [журнал миграции](../steps/l1-l2-migration.md).

Каждый механизм ядра имеет основное определение в L2; здесь — как он записан на L1 и во что опускается в C99. Не повторять общие правила: ссылаться на якорь L2.

<a id="scope"></a>
## 1. Предмет

Translator-L1 (`l1src/l1trans.lm1`) — синтаксически направленный понижатель wrapperless `.lm1` в одну единицу трансляции ANSI C99 на вызов. Это не L2: в профиле L1 нет онтологии `Lmx`, арены Message и таблиц `implements` как языковых форм. Ядро L2 **написано** на L1 и является входом того же транслятора. Самосборка: `l1src/build_l1.lm1`, поколения gen0…gen3 (см. `l1src/README.md`). Пин рабочего `l1trans.exe` в корне L1: `L1_PIN.txt` = `4E0B7F5D942C291AFD4C2CEB8FBBA5B20EECC44BF7B455A40D8E564846D80DE7`. Парсер P0 — `parser.lm1` + `p0.h` / `p0.h.lm1` + `own.lm1`.

<a id="translator"></a>
## 2. Транслятор

Вход: файл с конечным расширением `.lm1`. Временный совместимый путь явного `L1:` в `.lm2` не делает два транслятора взаимозаменяемыми. Понижение членов в C — не контракт разрешения путей L2 через граф `Lmx`.

Префикс `@` в L1 — взятие адреса C этой привязки (`p: @ value` → `&value`). Длинные прогоны `@` в деклараторах — звёзды указателя C, не повторный address-of. Обратный слэш: ведущий `\` — сырая загрузка указателя; `value\field` — поле, в C `->`. Повторяющиеся короткие объявления, `c.array`, `define`/`ifdef`, `os: win:/default:` — приняты проверяемыми наборами `tests/l1/run_*.ps1` в дереве L1 (исторические прогоны; в LMX не импортированы как норма).

Дверь в libc — объявления в `l1src/libc_abi.lm1` и вызовы `c.имя`. Заголовочные единицы L1 объявляют; исполняемое тело в заголовке отказывается.

Измеренные ловушки транслятора (deepseek, не норма языка, пока автор не подтвердит): `\` по значению эмитится как `->`; присваивание не объявляет локальную; на измеренной платформе `ulong` 4 байта, `size_t` 8; `predef:` тянет весь исходник. Форма `@(TYPE) name` не разбирается; нужно `@(TYPE name)` или `@: TYPE name` (коммит L1 `18bdab8`).

<a id="lmx"></a>
## 3. `Lmx` на L1

Определение полей — [L2 §2](L2_spec_ru.md#lmx). На L1 это `struct: Lmx` в `l2src/lmx.h.lm1`; C-заголовок порождается транслятором. Поля — L1-типы `@: Lmx`, `int`, `@: void`. Нет отдельного тега в записи. Слот ребёнка — ячейка массива `void *`; адрес слота даёт `lmx_arena_refs` / прежний `lmx_branch_slot`.

<a id="type-by-range"></a>
## 4. Тип по диапазону на L1

Правило — [L2 §3](L2_spec_ru.md#type-by-range). Перечисления и `LmxRange` — тот же `lmx.h.lm1`. Индекс принадлежит арене; классификация — функции `lmx_range_*` из `lmx_arena.h.lm1`, тела в `lmx_range.lm1` / `lmx_arena.lm1`. Домены механизмов — `#define` в `lmx_implements.h.lm1`, не поля `LmxMsg`.

<a id="pool"></a>
## 5. Пул на L1

Правило — [L2 §4](L2_spec_ru.md#pool). Структуры чанка и пула — `lmx.h.lm1`. Акты `lmx_pool_open`, `lmx_pool_make`, `lmx_pool_take`, `lmx_pool_take_n`, `lmx_pool_add_chunk` объявлены в `lmx_pool.h.lm1`, реализованы в `lmx_pool.lm1`. Рост — новый чанк как блоки арены, чтобы `revert` снял интервал вместе с ними.

<a id="method-array"></a>
## 6. METHOD и Array на L1

Правило — [L2 §5](L2_spec_ru.md#method-array). `fnptr: LmxEntry () void`; `struct: LmxMethod` и `LmxArrayDesc` в `lmx.h.lm1`. Типизированные пулы Array — модули `lmx_array_owned`, `lmx_array_ref_owned`, `lmx_chars_owned`, `lmx_value_owned`.

<a id="arena"></a>
## 7. Арена на L1

Правило — [L2 §6](L2_spec_ru.md#arena). `struct: LmxArena` и прототипы — `lmx_arena.h.lm1`; тела — `lmx_arena.lm1`. Блоки — `lmx_arena_blocks.h.lm1` / `.lm1`. Слоты Structure — `lmx_arena_refs.h.lm1` / `.lm1`. Поколение сборщика — поле `generation`; простой режим — `simple`.

<a id="message"></a>
## 8. Message на L1

Правило — [L2 §7](L2_spec_ru.md#message). `type: LmxFlag uint_fast8_t`; `struct: LmxMsg` в `lmx_message.h.lm1`. Комментарий исходника задаёт чтение `running` / `handoff_ready` через нагрузку вроде `__atomic_load_n(..., RELAXED)` там, где это совпадает с обычной volatile-нагрузкой, без RMW и без лишнего fence; это описание реализации, не новое правило L3. Самотест порядка полей — `lmx_message_selftest.lm1`. Хуки опроса объявлены в `lmx.h.lm1` (`lmx_msg_poll_abort`, `lmx_msg_poll_escape`), тела — на стороне ядра.

<a id="thread"></a>
## 9. L3 Thread на L1

Правило — [L2 §8](L2_spec_ru.md#thread). `struct: LmxThread` / `LmxLink` — `lmx_thread.h.lm1`; тела — `lmx_thread.lm1`. Ход — `lmx_thread_turn`. Планировщик объекта — `lmx_manager` / `lmx_schedule`, открывается `lmx_thread_scheduler_open`. Цепочка детей — ячейки арены родителя. Для одного такта выбирается ровно один путь тела — нативный или интерпретируемый; режим следующего такта фиксирует `endturn`. Стековая активация обоих путей использует одну модель own-load/dirty и не копирует метод при входе.

<a id="mailbox"></a>
## 10. Почта на L1

Правило — [L2 §9](L2_spec_ru.md#mailbox). `struct: LmxPost`, кольцо inbox и списки outbox/staged — `lmx_post.h.lm1`; тела — `lmx_post.lm1`. Допуск цели — `lmx_post_admits` через домен адреса. Доставка между объектами — `lmx_deliver`.

<a id="own"></a>
## 11. Own на L1

Правило — [L2 §10](L2_spec_ru.md#own). `lmx_own_load` / `lmx_own_write` / `lmx_own_checkpoint` — `lmx_own.lm1`. Смежная книга dirty на ходе — `lmx_dirty.h.lm1`.

<a id="call"></a>
## 12. Вызов на L1

Правило — [L2 §11](L2_spec_ru.md#call). `fnptr: LmxCallEntry (@: Lmx node) int`; `lmx_call0` — `lmx_call.lm1`. Сопоставление сигнатуры — обязанность транслятора, не этого модуля.

<a id="child"></a>
## 13. Ребёнок на L1

Правило — [L2 §12](L2_spec_ru.md#child). `lmx_child_create` / `reserve` / `publish_prepared` / `drop_prepared` / `handoff` — `lmx_child.lm1`.

<a id="copy-merge"></a>
## 14. Копия и merge на L1

Правило — [L2 §13](L2_spec_ru.md#copy-merge). `lmx_graph_copy_owned.lm1`, `lmx_merge_owned.lm1` и парные `.h.lm1`.

<a id="implements"></a>
## 15. `implements` на L1

Единственный механизм допуска определён в [L3 §7](LMX_semantics.ru.md#admission); роль L2 — в [L2 §14](L2_spec_ru.md#implements). В перенесённом коде `lmx_implements` сравнивает род и тип по диапазону, а `lmx_runtime_implements` сопоставляет числовые позиции полей. Последний не реализует требуемую проверку именованных путей и подлежит полной замене. Эти функции вызываются только собственными self-tests в исследованном срезе. Функции классификации адресов из того же модуля остаются инфраструктурой общего индекса арены; их используют почта и вызовы.

<a id="gc"></a>
## 16. Сбор на L1

Правило — [L2 §15](L2_spec_ru.md#gc). `lmx_gc_collect` — `lmx_gc.lm1`.

<a id="c99"></a>
## 17. Опускание в C99

Один вызов транслятора даёт один `.c`. Строгая сборка поколений: `-std=c99 -Wall -Wextra -Wpedantic` и `-Werror=` на несовместимые указатели, отброшенные квалификаторы, неявные объявления. `os:` выбирает Windows или POSIX (`l1trans.lm1`). `include:` / `predef:` становятся включениями C. Агрегаты L1 `struct:` / `enum:` / `fnptr:` / `type:` опускаются в C99 typedef/struct. Это не модель памяти L2: модель памяти задаёт арена ([L2 §6](L2_spec_ru.md#arena)).

<a id="unresolved"></a>
## 18. Неразрешённое

См. [L2 §17](L2_spec_ru.md#unresolved) и [журнал](../steps/l1-l2-migration.md). Дополнительно по транслятору: пробелы разбора на модулях порта mixa (`empty colon Frame`, `unsupported statement atom`, trailer на узле) записаны deepseek как измерения, не как правила L1.

<a id="lowlevel-scope"></a>
## 19. Машинная поверхность L1 и связь с L2

Эти разделы раскрывают прямые машинные операции перенесённого [Translator-L1](../l1src/l1trans.lm1). Исторические основания — `L1_spec.txt`, §11–13 и §20 общей спецификации; факты реализации сверены по названным ниже функциям. Полный контракт соответствующего семейства L2 дан [в L2](L2_spec_ru.md#lowlevel-scope). Он не переносится автоматически на одинаковое написание L1.

Главное различие: в L1 переменная и поле C-агрегата не являются графовой ячейкой Lmx. Здесь нет own-кэша языка, скрытого допуска `implements` или автоматической арены. L1-код ядра явно вызывает библиотеку арены и тем самым реализует механизмы L2. Наличие такой библиотеки не меняет семантику `@`, массива или присваивания в самом L1.

<a id="lowlevel-address"></a>
## 20. Указатели, поля и адресуемые цели

| L1 | Выход C99 | Условие |
| --- | --- | --- |
| `@: int p` | `int *p` | Явное объявление указателя |
| `@@: char pp` | `char **pp` | Каждая декларативная `@` добавляет уровень |
| `p: @x` | `p = &x` | x — адресуемая C-цель |
| `\p` | `*p` | Адрес должен быть действительным и подходящего типа |
| `\p: value` | `(*p) = value` | Цель допускает запись |
| `p\field` | `p->field` | p указывает на агрегат с известным полем |
| `a[i]: value` | `a[i] = value` | Сырой индекс C; автоматической проверки нет |

`l1_emit_assign_head` разбирает ведущие разыменования, корень, суффиксы полей и индексов. `l1_assign_index_close` учитывает вложенные скобки, строки и экранирование; `l1_emit_assign_index` передаёт содержимое индекса обычному разбору выражения. Пустой индекс, незакрытые скобки, отсутствующее имя после `\` и некорректная цель диагностируются. Это разбор lvalue, не создание объявления или нового поля.

Обычное `value\field` всегда понижается как шаг указателя. У агрегата C по значению нужен явный C-доступ, например `c.value.field`; нельзя считать сгенерированное `value->field` корректным только потому, что исходная форма разобрана. В L2 обычный графовый путь имеет другой контракт [адресации](L2_spec_ru.md#lowlevel-address).

В выражении `@` — address-of, а в форме типа `@: T` — декларатор указателя. Поэтому `c.sizeof(@: char)` обозначает размер `char *`, а `c.sizeof(@ x)` — размер адреса x. Лишние поля указательного типа/параметра не должны теряться: транслятор имеет диагностики `pointer type has extra fields` и `pointer parameter has extra fields`. Приведение и указательный декларатор сами по себе не проверяют живость, выравнивание, границы и права доступа к объекту.

`const: @(char p)` понижается в `const char *p`: защищены символы, не ячейка указателя. L1-`immutable` — групповое применение этого C-квалификатора к объявлениям; это не глубокая графовая неизменяемость L3 и не `RuntimeImmutable`. Перепривязка p остаётся допустимой, запись через него — нет. Вложенные обёртки сводятся к одному C `const`; не следует обещать на этой основе защиту всех псевдонимов изменяемого внешнего объекта.

<a id="lowlevel-array"></a>
## 21. Массивы машинного профиля

В L1 обе обработанные семьи `[]:` и `c.array:` понижаются в массивы C. Это отличается от обычного Array L2, где `[]:` строит дескриптор. `l1_emit_bracket_array` обрабатывает последовательность измерений; `l1_emit_c_array` — явно обёрнутое объявление. Формы, подтверждённые исходным справочником и кодом: `[]: int values 3 2 4 6`, `[][]: int matrix 2 2`, `c.array: [3]: int: values 2 4 6`, `c.array: []: char buffer 256`.

Результат — непрерывное C-хранилище, без `LmxArrayDesc`, метаданных арены и скрытых проверок индекса. Прямоугольный `matrix` не превращается в массив отдельно выделенных строк. Тип элемента и его указательная глубина формируют C-декларатор; `const` квалифицирует базовый элемент. `l1_emit_c_array` отвергает несколько логических дочерних объявлений, отсутствующий тип или имя, неправильную внешнюю голову; тело инициализатора выдаётся через `l1_emit_inits`.

Отличие от графового Array L2 — способ нахождения хранилища, не наличие проверок: в L2 индекс и дескриптор при доступе тоже не проверяются. `@array[i]` в L2 адресует настоящий элемент backing, после чего понижение использует обычный машинный адрес. Проверяемая операция принадлежит L3; [контракт и расхождения транслятора](L2_spec_ru.md#lowlevel-address) описаны отдельно.

Размеры, время жизни, инициализация и преобразование массива в указатель после понижения подчиняются C99. Нельзя выводить из успешного разбора, что транслятор самостоятельно проверил все ограничения C: часть ошибок обнаруживается следующим компилятором. Нельзя также переносить все описанные варианты L2 `c.array` на этот эмиттер: [L2](L2_spec_ru.md#lowlevel-array) отдельно различает широкий контракт и узкую поддержку фронтенда.

Сохранение адреса автоматического массива после возврата не продлевает его жизнь. Для кода ядра долгоживущее хранилище выделяется явно через [арену](#arena) либо внешний API с определённым освобождением. Сырые C-массивы, используемые транслятором как временные буферы, не являются доказательством поддержки обычных графовых Array в исходном L2.

<a id="lowlevel-abi"></a>
## 22. Приведения, C-интерфейс и объявления ABI

`l1_emit_cast` понижает `cast: (T) expression` в явное C-приведение, включая допустимый указательный тип и последовательность слов C-типа, например `unsigned long`. Это не проверяемое преобразование чисел высокого уровня: диапазон, выравнивание и допустимость последующего доступа определяются C и контрактом вызываемого API.

Префикс `c.` открывает явный доступ к C-символу: `c.malloc`, `c.memcpy`, `c.sizeof` и т. п. В компактной C-форме транслятор снимает `c.` и обрабатывает разрешённые пути; это не общий текстовый интерпретатор L1 внутри круглых скобок. Вложенный receiver с двоеточием, например `c.sizeof((cast: (unsigned) 0))`, имеет отдельную диагностику; двоеточие внутри строкового/символьного литерала либо согласованного C-тернарного выражения не должно ошибочно считаться receiver.

Внешнее определение типа объявляется `foreign: Name`: имя регистрируется для транслятора, само определение должен дать включённый C-заголовок. `extern: @: Lmx object` выдаёт объявление объекта другой единицы. `type: Alias …`, `struct:`, `enum:`, `fnptr:` в заголовочной единице описывают реальный C ABI, не обычные структуры L3. `fnptr` — тип C-указателя функции; он не заменяет METHOD и контракт вызова L2.

Заголовочный источник `name.h.lm1` выдаёт `name.lm1.h`. Заголовок допускает объявления, не исполняемые тела. `l1_hdr_*` упорядочивает зависимости: forward-объявления достаточны для указателей, но поля по значению требуют завершённого типа; цикл таких зависимостей ошибочен. `include` подключает указанный файл, `predef` заголовка сохраняет относительный путь, чтобы одноимённые файлы разных каталогов не столкнулись. Это работа транслятора, не runtime-реестр имён.

`external` экспортирует объявленную функцию/процедуру; `prototype` задаёт её объявление. `os`, `ifdef`, `define` выбирают и выражают явно заданный машинный профиль. Наличие зарезервированных `C`, `L1`, `L2`, `L3` не означает, что текущий L1 исполняет старый `C:`-escape. В частности, предложенные общей спекой `c.struct`/`c.union` нельзя объявлять готовыми обработчиками этого транслятора. Статус и более широкий L2-контракт — [в L2](L2_spec_ru.md#lowlevel-abi).

<a id="lowlevel-expression"></a>
## 23. Выражения C, обновление и управление

`l1_emit_expr`, `l1_emit_expr_range`, `l1_emit_one_expr` и обработчики целей формируют C-выражения. Исходное `=` в сравнении становится `==`; `target: expression` — присваиванием. Указательные операции описаны [выше](#lowlevel-address). Арифметические, логические, битовые операции, сдвиги, `++`/`--` сохраняют требования выбранных C-типов; автоматической проверки арифметического переполнения или границ здесь не обещается.

Реализация содержит `if`/`else`, `while`, трёхчастный `for`, `break`, `continue`, `switch`/`case`/`default` и возврат. У `switch` нет автоматического `break`: проваливание соответствует C, а не контракту L3 `match`. Голое видимое имя нульаргументной функции в позиции оператора может выдаваться как вызов; это не метка. `goto` не делает произвольную исходную форму допустимым объявлением цели. Старые ограничения пустого colon-Frame относятся к фактическому P0 и отдельно проверяются корпусом новой грамматики.

Текущий L1 имеет собственное ограниченное понижение `throw`/`catch`/`finally`: служебный код и `long`-нагрузка до восьми полей. Эта реализация не является полным типизированным контрактом результатов/отказов L2 и тем более готовой валидацией L3. Нельзя переносить её ограничения на норму L3. Совместное подмножество и машинные роли — [L2](L2_spec_ru.md#lowlevel-expression).

<a id="lowlevel-sync"></a>
## 24. Синхронизация: что требуется и что реализовано

Контракт L2 `synchronized`, включая освобождение при выходах, сохранён [в L2](L2_spec_ru.md#lowlevel-sync). Поиск по перенесённым `l1trans.lm1` и `l2trans.lm1` не обнаружил обработчика этого receiver. Не следует выдавать пример с `lm_synchronized_enter/leave` из старой спеки за реально генерируемый код.

Ядро написано на L1 и использует явные машинные/внешние операции для реализации [почты](#mailbox) и рукопожатия. Их порядок памяти и допустимые писатели определяются соответствующим модулем, не названием `synchronized`. `volatile` не подменяет атомарную операцию, а наличие атомарных вызовов не означает поддержки исходной структурной области синхронизации. Добавление такой поддержки — отдельная работа транслятора, не выполненная настоящей редакцией документации.
