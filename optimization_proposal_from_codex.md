# Предложение Codex по ускорению сборок LMX

Дата: 2026-10-28. Статус: предложение, не реализация и не новое условие приёмки.

## Краткий вывод

Главный кандидат на ускорение — работа самого L2→L1 frontend на больших модулях,
а не GCC, линковка или мелкие проверки заголовков. В исходниках видны повторные
полные обходы таблиц и рост некоторых массивов ровно на один элемент. Это хорошие
места для ограниченного измерения и локального улучшения, но ещё не установленный
профилированием источник большей части времени.

Предлагаемый порядок:

1. Довести уже запущенный whole bootstrap до фактического результата, не прерывая его ради оптимизации.
2. В рабочем цикле пользоваться существующим компонентным rebuild и не повторять неизменную работу.
3. На следующем необходимом большом переводе получить несколько фазовых времён и счётчиков,
   затем изменить один подтверждённый горячий участок в поддерживаемом L2/L3.
4. Отдельно, если оправдается измерением, попробовать более быстрый backend/tool binary.

Ниже нет обещаний ускорения в определённое число раз. Codex при подготовке документа
не менял код, не запускал сборок и не принимал writer/build обратно у `fable_pc`.

Суммировать их как измеренное время whole bootstrap или приписывать им точные

Boot43 на момент подготовки ещё не принят как завершённая bootstrap-цепочка.

## 2. Быстрый рабочий цикл без новой системы сборки

### Использовать уже существующее разделение задач

В `S/tools/suite.lm2:1467–1528` уже есть rebuild для `frontend/runtime/tool/none`.
При изменении recipe или одного инструмента не надо предварительно пересобирать
неизменные FE/runtime. После локальной проверки всё равно выполняется нужный whole
bootstrap: компонентный rebuild — средство разработки, а не его замена.

Не менять frozen входы и не запускать дополнительные compiler pipeline параллельно
текущему. Блокирующие исправления собирать в маленькие dependency-closed кандидаты:
достаточно ранней проверки формы и зависимости, затем один необходимый дорогой перевод.
Не повторять тот же перевод только ради нового каталога, названия шага или отчёта.

### Сохранить уже реализованное «собрать один раз, выполнить много»

- `S/tools/suite.lm2:329–347`: один build для каждого реального native/forced
  варианта, затем запуски root0/root1.
- `S/tools/build.lm2:208–250`: L2/L1/C-компиляция выполняется один раз, после
  чего возможна линковка с несколькими runtime-вариантами.

Это уже существующие оптимизации. Дальнейшее объединение строк suite имеет смысл
только там, где действительно совпадают source + parts + compiler + flags + runtime.
Другой ожидаемый результат, root или выходной каталог сами по себе не требуют
новой компиляции. Native/forced и production/observed — разные реальные варианты;
объединять их как одну сборку нельзя. Перепись фактических дубликатов для этого
документа не проводилась, поэтому дополнительная экономия пока неизвестна.

Новый универсальный cache, scheduler или параллельный runner сейчас не предлагается.
Любое разрешённое повторное использование артефакта требует тех же producer bytes,
входной closure, argv/flags, target/ABI и разрешённых include/import путей. Один
совпавший исходник или наличие старого файла рядом этого не доказывает.

## 3. Кандидаты внутри frontend

Это **гипотезы по коду**, не результаты CPU-профиля. Выбирать следующий участок
следует по измеренной доле времени, а не по длине его исходника.

### 3.1. Списки относящихся к владельцу строк вместо полных переборов

В `S/src/l2src/l2_frontend_emit.lm2:16451–16458,16519–16543` для каждого метода
повторяются проходы по всей таблице `own_n`. В `lm_compiler_emit_ns_cells`
(`1997–2055`) и `lm_compiler_emit_ns_refs` (`2076` и далее) таблица полей также
фильтруется по конкретному namespace.

Предложение: один раз сформировать компактные списки строк namespace и реально
используемых методом own-полей; при emission обходить только эти списки. Полный
перебор «каждый метод × все own rows» тогда заменяется обходом соответствующих
отношений. Выигрыш зависит от их разреженности и стоимости нынешних предикатов.

Критические границы:

- сохранить исходный порядок полей и записи состояния;
- method-list нельзя строить только по `own_mi = method`: внешние/захваченные
  поля и результаты обычных `own_used/own_direct/own_cached` тоже обязательны;
- списки строить после готовности соответствующих данных либо правильно обновлять;
- это внутренние структуры одной компиляции, не runtime-поиск переменных и не singleton.

Что достаточно измерить: время emission, просмотренные строки и строки, реально
прошедшие фильтр. Если здесь малая доля общего времени, эту правку отложить.

### 3.2. Геометрическая ёмкость уже существующих таблиц

`S/src/l2src/l2_frontend_core.lm2:10471–10517`:
`lm_compiler_m2_cert_find` линейно ищет `(source_node, mi)`, а добавление записи
в `lm_compiler_m2_cert_note` выполняет три `realloc(n + 1)` для параллельных массивов.
Похожий рост по одному есть у `call_body_sites:10356–10387`.

Первая локальная оптимизация — отделить length от capacity и увеличивать ёмкость
с запасом. Это сокращает число allocator-вызовов; фактическое копирование при
`realloc` зависит от allocator и пока не измерено. Индекс `(source_node, mi)` —
отдельный следующий шаг, только если заметен именно поиск.

Сохранить overflow checks, обработку частичного allocation failure и прежнее
разрешение конфликта `body → -1`. Новые сертификаты, проверки поведения или
основания отказа не добавляются. Число find-сравнений, размер таблицы и число
расширений дают достаточную первичную оценку без отдельной тестовой кампании.

### 3.3. Индекс имён для существующего прохода

`S/src/l2src/l2_frontend_core.lm2:11176–11265`: `lm_compiler_m2_open_name`
для каждого сегмента перебирает все методы; рекурсивный `m2_scan_names` вызывает
его для атомов и части frame heads. Число сравнений растёт как произведение
числа обрабатываемых сегментов на число методов.

Предложение: индекс «байты имени → все соответствующие method rows» на время
этого прохода. Важно вернуть **все** нынешние совпадения, не только первое;
не менять scope, shadowing, активность вызовов или состав выполняемого анализа.
Перед реализацией посчитать реальные вызовы и сравнения: сам вид цикла ещё
не доказывает, что он съедает значительную часть часа.

### 3.4. Поиск own occurrence без вложенных полных сканирований

`S/src/l2src/l2_frontend_resolve.lm2:2235–2314`:
`lm_compiler_method_part_own_seg` и `lm_compiler_own_seg_scan` проходят по `own_n`;
при явно указанном occurrence внутри подходящей строки запускается ещё один
полный проход. На большом наборе одноимённых объявлений это условный
квадратичный участок.

Предложение: индекс по фактическому ключу разрешения — method, host/part, имя —
с сохранённой последовательностью source occurrence. Нельзя заменить его просто
«последним объявлением имени»: `own_source_after`, shadowing и разные физические
объявления должны остаться различимыми.

Приоритет ниже, если occurrence-запросы редки. Достаточные счётчики: plain/occurrence
запросы, просмотренные строки, длина одноимённых цепочек. Оптимизация не должна
менять грамматику, границы аргументов или допустимые пробелы вокруг `\`.

## 4. Что уже есть и что не следует оптимизировать вслепую

- `application_site_find` уже обращается к индексу
  (`S/src/l2src/l2_frontend_resolve.lm2:594–615`).
- Prepared path уже сохраняет разобранную форму и семантический результат,
  учитывая method/revision (`там же:4191–4239`). Нельзя предлагать «впервые
  убрать повторный разбор всех путей» или отключить revision invalidation.
- Нет оснований обвинять конкатенацию всего выходного текста: emitter пишет
  через `fprintf/fputs`, а text helper запоминает вычисленную длину
  (`S/src/l2src/l2_frontend_helpers.lm2:2467–2470`). Буферизацию менять только
  после измерения formatting/I/O.
- Не ограничивать число раундов уже существующего семантического замыкания ради
  времени. Если оно окажется дорогим, отдельно исследовать очередь изменившихся
  зависимостей с тем же результатом; это более рискованный, не первый срез.

Любые внутренние индексы/кэши принадлежат конкретной компиляции и стадии модели.
Нельзя переносить ответ через изменение модели без правильной инвалидизации,
закэшировать UNKNOWN как вечный отказ или заменить обычный допуск особым shortcut.
Первая часть допуска по-прежнему проверяет только используемый интерфейс;
дополнительный анализ остаётся исключительно в явно выбранном программистом `test`.

## 5. Флаги C-компиляции: ограниченный эксперимент, не первая ставка

В candidate43 frontend уже получает `-O1 -fno-strict-aliasing`
(`S/tools/build.lm2:713`), тогда как backend и сам build tool собираются с `-O0`
(`там же:5943–5962` и `2784`). Можно при удобном следующем кандидате сравнить
один вариант backend/tool с `-O1`: потратить немного больше времени на создание
часто исполняемого инструмента, если его последующие запуски действительно ускорятся.

Проверять нужно сумму «стоимость построения инструмента + стоимость нужных переводов»,
а не только скорость нового binary. Сохранить исходную политику aliasing, диагностику
и реальные результаты; смена optimization flags создаёт новый вариант, не тот же
самый артефакт под другим именем. Без замера не переходить массово на `-O2/-O3`,
LTO, PGO, native-only CPU flags или отключение проверок.

Декомпозиция generated C на отдельно компилируемые units может помочь будущему
инкрементальному циклу, но сейчас GCC warm41 занимает около 28 секунд. Новая
сложность linkage/ABI/зависимостей ради этой части не выглядит первой инвестицией
на фоне часовых L2-переводов.

## 6. Небольшие резервы recipe — после главного узкого места

1. `S/tools/suite.lm2:1372–1374` выполняет `tool_works` внутри поколения;
   parent bootstrap затем повторяет G2-проверку (`1448–1449`). Можно использовать
   уже сохранённый успешный child-result с привязкой к тем же байтам, если он
   действительно покрывает ту же проверку. Это малая экономия, не причина
   переделывать работающий bootstrap сейчас.
2. `bld_headers` переводит все найденные `.h.lm1`
   (`S/tools/build.lm2:595–658`). Более узкая consumer-closure может исключить
   ненужные заголовки, но разные проходы используют previous и новый backend
   (`5917` и `2668`). Равенство текста header не делает их одной producer-сборкой.
   Свежая L3-генерация до потребителей и отсутствие рукописного fallback обязательны.
3. Snapshot/copy/hash могут со временем работать потоково:
   `generation_snapshot` — `S/tools/suite.lm2:1228–1272`, `stage_copy` —
   `S/tools/replay.lm2:251–287`; нынешний `file_copy:41–55` читает файл целиком.
   Совмещение чтения source с hash/copy способно сократить повторное I/O и пиковый
   буфер, но проверка destination bytes остаётся. Наблюдённые 159 файлов за ~1,24 с
   пока не дают основания ставить эту работу впереди frontend.

Проверка provenance не является лишней по определению. `bld_step_t`
(`S/tools/build.lm2:21–76`) связывает executable/input/output bytes;
`verify_record` уже не перечитывает каждое старое вхождение пути, а проверяет его
финальное вхождение (`S/tools/replay.lm2:519–529`). Не заменять хеши одним mtime.

## 7. Как проверить полезность без новой кампании

На следующем **и так необходимом** переводе достаточно времён нескольких крупных
стадий — parse/model, существующая подготовка/проверка/замыкание, emission — и
агрегированных счётчиков выбранного участка. Это предложение минимальной
инструментации в поддерживаемом L2/L3, не команда немедленно её вводить и не
новый Python/PowerShell profiler/runner. Не печатать запись на каждое поле:
такая трасса сама может стать нагрузкой.

Для одного выбранного изменения сохранить:

- исходные байты, compiler/toolchain bytes, argv, flags, target и входную closure;
- phase wall time, по возможности CPU time и peak memory;
- фактический terminal и результаты существующей короткой проверки;
- generated output: для изменения только алгоритма поиска/ёмкости ожидать
  совпадения; реальное отличие разобрать, не нормализовать его молча.

Не устраивать серию одинаковых часовых прогонов ради красивой статистики.
Если старый замер получен на другом compiler или source, явно отметить несопоставимость;
не объявлять разницу выигрышем оптимизации. Если выигрыш мал либо память выросла
существенно, не усложнять основной маршрут.

## 8. Что остаётся обязательным

Рабочий incremental/rebuild не заменяет whole quick. Quick не превращается в
однокомпонентный smoke: сохраняет цепочку компонентов и поколений, сокращает
тестовую ширину. FULL остаётся отдельным режимом. Обе действительные самосборки,
проверки и замены G1/G2 нельзя заменить выдачей старых артефактов из cache.
Изменение producer binary между поколениями — реальная новая зависимость.

Все поддерживаемые изменения — L3/L2; generated L1/C остаются результатами,
внешние compiler/linker — инструментами. Никаких новых обходных грамматик,
рукописных заголовков, скрытых root/singleton или ослабления допуска ради скорости.
Идущий bootstrap не останавливать, защиты памяти не обходить, обычное продолжение
не задерживать ожиданием этого документа или разрешительного ревью Codex.

Приоритет: **сначала работающая самосборка; затем подтверждённое ускорение её
дорогого шага, одним небольшим изменением за раз**.
