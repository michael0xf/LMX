## Конструктор сигнатур `->`

Каноническое имя конструктора сигнатур изменено с `to` на `->` в нормативном описании, каталоге, реализациях, примерах и средствах проверки. Прежнее имя не остаётся callable alias. Не связанные с конструктором поля и параметры с именем `to` не переименованы.

Форма операнда: `A0 -> A1 R`. Ресиверная форма использует тот же идентификатор в обратных кавычках: `` `->`(A0; A1; R) ``. Сначала перечисляются типы входов, последним — тип результата. Конструктор не создаёт тело функции и не добавляет неявное каррирование. Вложенная сигнатура записывается явно: `int -> (int -> int)`. Непосредственное именование результата через `f :: int -> int int` следует общему CODE-потреблению Expression и собственному декларационному договору `::`.

### Исправление группировки и потребления описания

Предпочитаемая запись группирует всё выражение конструктора:

```lmx
f :: (int -> int int)
```

Без внешних скобок тот же охват выражения задаётся приоритетами:

```lmx
f :: int -> int int
```

Каждая запись — отдельный пример. Готовый приоритет `::` равен `sys\priority(":=")`, ниже `->` с `sys\priority("+")`. Обе формы передают объявлению одно описание: два входа `int`, результат `int`. Равнозначность относится к полученному описанию; P0 сохраняет написанные группы. Приоритет задаёт охват выражения, а его значение получается обычным механизмом потребления CODE.

У `int -> (int int)` справа **один** структурный аргумент. Он не превращается в два аргумента и не равнозначен `int -> int int`. Допуск всей этой Structure как полного TYPE проверяется отдельно. Отдельный профиль раскрытия правого списка, ошибочно добавленный в предыдущую доставленную редакцию, удалён; его предполагаемые следствия для `int -> ()` и дополнительных скобок также сняты. Прежняя формулировка об условном открытии RHS объяснена через общий группировщик, текущий структурный уровень и отдельную подготовку применения. Целая модель TYPE не получает последовательностного договора только из-за формы левого аргумента.

По авторскому уточнению исправлена более общая ошибка документации: разрешённая системная функция сохраняет собственный смысл, а Expression имеет роль CODE. Обычная пользовательская форма внутри Expression является вызовом и не объявляет новую Structure. При этом `::`, `const` и `private` сохраняют свои декларационные действия и в CODE. Поэтому у `S :: (makeSignature())` нет выведенной ранее альтернативы «объявить пустую Structure makeSignature» внутри Expression.

Смысл самого ресивера отделён от договора его аргументов. **Модификаторы всегда потребляют DATA; `::` также потребляет все свои аргументы исключительно как DATA.** NAME слева — имя объявления; описание справа предоставляет список деклараций. Безымянная Structure либо структура по ссылке раскрывается в непосредственные поля общим механизмом namespace по требованию принимающего договора. `::` пользуется этим механизмом без отдельного исключения. Вложенные модели и `return` не раскрываются рекурсивно, формальные инициализаторы и тело не выполняются.

Получение списка полей отделено от внешнего CODE-выбора W/E и от границ операнда `->`. Подготовка операций в Expression следует общей политике приоритетов; у `::` нет собственного CODE-потребления или `eval` правой части. DATA-роль не определяет значение `PASS_ARGS_AS_IS`: неподтверждённая привязка этого флага к builtin `::` снята, общий RAW-договор сохранён. Безымянные Structures выполняются на месте в CODE/Expression и не создают вызова или новой активации. [Разбор с короткими примерами и псевдокодом](SIGNATURE_EXPRESSION_REVIEW.md), [общая норма](LMX_semantics.ru.md#receiver-context-invariance), [общий механизм списков](LMX_semantics.en.md#receiver-structure-sequences) и [приёмочные случаи](validation/signature_expression_cases_20261124.json) согласованы с авторскими уточнениями.

Исходник builtin `::` в пакет не входит; парсер, транслятор и runtime остаются **NOT_RUN**. Это предел проверки реализации, а не незавершённость семантического решения автора. Исправленный архив заменяет редакцию с SHA-256 `20f01dcddfe6c0d2050d1148a2a459fab571d923cdecae0ac4e4fd55bd43ec1e` и по-прежнему накладывается непосредственно на исходную авторскую загрузку.

### Работа группировщика Expression

Expression использует обычное дерево LMX и общий группировщик для приоритетов и групп. Отдельный шаг анализа готовит применение: один `left`, массив ссылок `right`. Это сохраняет принцип компактной записи `head: arg0 arg1 arg2`; публичный `OPERANDS_TEMPLATE` остаётся прежним. Вопрос об обобщении интерфейса закрыт.

`1 + ((2))` даёт 3. В `(a b c) := (a c b)` группировщик выделяет текущие последовательности слева и справа, после чего анализатор упаковывает левую последовательность в один аргумент. Каждая Expression-группа обрабатывается рекурсивно: одиночные оболочки прозрачны, несколько единиц сохраняются одной подгруппой. Три соседние материальные подгруппы остаются тремя элементами, а операции внутри вычисляемых групп планируются полностью. `(a b c) := copy(d)` непосредственно принимает поток полей; оболочка `(copy(d))` для этого группового присваивания не требуется. Все правые значения и проверки предшествуют первой записи.

Группировщик не удаляет контейнеры `(copy(Model))` в позиции целого значения, не превращает результат вызова в исходный код и не запускает RAW, DATA-инициализаторы или отложенные тела при планировании. TYPE-модели сохраняют собственные границы. Дополнительное уточнение заменяет прежнюю проверку `(target) := ((x y))`: `(a b) := (((x y)))` получает два значения, а `(a b) := (((x y))) z` — подгруппу и соседний атом. Авторский пример `1 + 2 (((5 6))) (4) 5` нормализуется к `1 + 2 (5 6) 4 5`; несоответствие числовому договору проверяет сам `+`, не группировщик. У RAW целое внутреннее Expression сохраняется одним исходным вхождением с контекстом, без раннего исполнения.

[Полное описание с псевдокодом](EXPRESSION_GROUPING.md), двуязычная семантика, руководства, библиотечные договоры и примеры согласованы. Добавлены нормативные случаи группировки и parent-развилки; вместе со случаями сигнатур их точное число и статус **NOT_RUN** приведены в отчёте проверки.

Чистый граф разрешает также прежнюю неопределённость ссылки на Structure: безымянная Structure — группа; именованная с **другим** фактическим `parent` — группа; именованная с лексическим `parent` текущего выражения — обычный вызов/ресивер. Группировщик не видит скобок, не переподчиняет граф и не выполняет лексическую подстановку. Сохранены принимающие VALUE/TYPE/DATA-договоры.

В архив включены [подробный алгоритм разбора](EXPRESSION_ALGORITHM.md), [его проверочная реализация](tools/expression_grouping_reference.py) и host-тесты. Алгоритм явно сохраняет отсутствующий `left`, различает группировку и упаковку аргумента, учитывает действующую PLACE-зависимость `1 + v := 2 + 3` и направленные правила степени. Это исполняемый эскиз планирования над графом, а не поставленный production-парсер LMX.

В окончательном алгоритме нет флага или ветви разбора для присваивания. Общий вид каждого левого вхождения сохраняет атом и окружающий вычислительный контекст; потребление решает сам метод. `(:= a 1)` приходит с отсутствующим `left` и двумя правыми аргументами, `(a := 1)` — с одним левым и одним правым. Их одинаковый смысл реализован в самом методе операнда, без перестановки в парсере или при передаче. Прижатые слева/справа унарные формы описаны общим классом.
