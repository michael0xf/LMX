# Пояснения к семантике LMX

<a id="p0-container-correction"></a>
## 1. Пустая Structure и единственный контейнер в P0

Снятие единственного непустого анонимного контейнера в P0 ошибкой не
является: прежнее требование исправить это в коде P0 снято по прямому
указанию автора ([уточнение автора 2026-11-10](../LMX_blog/2026-11-10.md)).
Подача единственной аргументной Structure как всей структуры фактических
аргументов — правило семантики уже разрешённого вызова функции или метода
при подготовке аргументов, а не P0.

Раскрытие пустой структуры на P0 тоже ошибкой не является ([уточнения
автора 2026-11-09](../LMX_blog/2026-11-09.md)). Три одинаковые по смыслу
формы с пустой Structure дают одно дерево P0: `A{}`, короткая форма
`A: {}` и блочная запись `A` с пустым телом. Блок закрывается по общим
правилам границ, например так:

```lmx
A{}
A: {}
A:
---
A:
end: A
```

Короткая форма `A: {}` равна `A{}`, только когда она завершается переводом
строки и возвратом на прежний уровень. Это следствие общих правил уровней и
завершения короткой и блочной форм, а не исключение разбора: если за
`A: {}` следует закрытие блока `A`, запись блочная, и пустая Structure —
её единственное поле.

```lmx
A: {}
end: A    # A{{}}, а не пустая A
```

Раскрытие не стирает различие формы вызова и невызовной записи: `A()` P0
помечает как вызов. Вызов записывается `A(args)` или `A()`; `A(): args` и
блочная `A():` — редкое дополнительное оформление того же вызова
([ниже](#call-forms)). Фигурные скобки никогда не вызов, отдельные `(...)` —
тоже (короткая `A: ()` — та же пустая Structure, что `A: {}`), и Frame
с двоеточием `A: args` вызовом не является.

<a id="data-receiver-correction"></a>
## 2. Удаление двухаргументных форм приёмников данных и типов

**ТРЕБОВАНИЕ К КОДУ. Удалить поддержку всех двухаргументных форм
приёмников данных и типов, включая `int` и `@` и их аналоги.** Имя
объекта и его значение больше нельзя передавать как два соседних
аргумента такого приёмника. Удалённые формы должны отклоняться
семантическим допуском; совместимого старого варианта и неявного
переписывания в новую форму нет. P0 сохраняет общую структуру Frame
и не разбирает приёмники по именам.

При передаче значения или кандидата имя объекта находится во внешнем
описании, а приёмник получает один операнд:

```lmx
i{ int: 5}
i: int: 5
ptr: @: 0
ptr: @: Model
ptr: @: myFunc
add5: @: makeAdder(5)
```

Это альтернативные примеры, а не последовательные объявления одного
объекта. **Удалённые и отклоняемые формы** приведены только для миграции:

| Удалённая форма — отклонять | Действующая форма |
| --- | --- |
| `int: i 5` | `i{ int: 5}` или `i: int: 5` |
| `@: ptr 0` | `ptr: @: 0` |
| `@: ptr Model` | `ptr: @: Model` |
| `@: ptr myFunc` | `ptr: @: myFunc` |
| `@: add5 makeAdder(5)` | `add5: @: makeAdder(5)` |

Одноаргументные `int: x` и `@: ptr`, задающие место без начального
значения, остаются допустимыми. Пустые формы `int()` и `@()` также
сохраняются. Удаление относится к двум аргументам приёмников данных
и типов; оно не ограничивает число аргументов обычных методов,
`merge`, `print`, `fn`, `post` и других независимых приёмников.

**Редакция 4: 2026-11-09.**

Эти два требования и разделы «Новый синтаксис», «Двусторонняя видимость
и накопленные изменения», «Прямой индекс и номер именованного вхождения»,
«Выражение — Structure», «Structure через Array @» и «typeof: тип по арене
указуемого объекта» фиксируют принятые изменения;
им соответствует обновлённая [грамматика](new_LMX_grammar.ru.md). Прежние версии
[L3](new_LMX_semantics.ru.md) не отменяют эти изменения и подлежат согласованию
с ними. Остальные разделы — короткие ненормативные примеры: для не затронутых
изменениями правил действуют семантика и обновлённая грамматика.

<a id="new-syntax"></a>
## Новый синтаксис

Фигурные скобки описывают обычную Structure и используются для
невызовных группировок; `name{...}` — именованное описание. Квадратные
скобки ограничивают Mix: `[color: red]`. Круглые скобки сохраняются
у вызовов и их структур фактических аргументов, при выделении массива
и индексировании массива.

```lmx
{i: int: 1}           # описание Structure с начальным значением
{i: int}              # описание Structure без начального значения

f(1)                  # вызов метода с позиционным аргументом
f(i: 1)               # вызов метода с именованным аргументом

arr: (): int          # выделение массива int
arr(1)                # элемент массива
arr(2)                # следующий элемент массива

x: 5                  # запись в известное место x
x +: 1                # составное присваивание
x = 5                 # сравнение
```

Формы `(1)` и `(i: 1)` — структуры фактических аргументов вызова.
Прежний оператор `:=` заменён на `:`; в составных присваиваниях знак `=`
заменён на `:`: `+:`, `-:`, `*:`, `/:`, `%:`, `<<:`, `>>:`, `&:`, `^:`,
`|:`, `**:`. Операторы сравнения сохраняют своё значение. Двоеточие также
продолжает отделять голову Frame от её аргументной Structure; конкретный
смысл определяет разрешённая голова, а не сам знак.

Обычная Structure не имеет формальных параметров. `s()` исполняет её без
явно переданной отдельной Structure данных; `s(data)` исполняет код `s`
на переданной Structure `data`. Оператор `call` удалён. Выбор данных при
`s()` определяется общими правилами исполнения. У метода сохраняется
вызов с фактическими аргументами: `f(1)` вызывает метод, а не индексирует
его поля. Прямой позиционный доступ к Structure записывается `s\(index)`.
Без `\` запись `s(1)` не получает индексного смысла для Structure.
Доступ через присвоение в Array `@` также остаётся доступным.

<a id="name-visibility"></a>
## Двусторонняя видимость и накопленные изменения

**Имена видимы в обе стороны в своей допустимой области связывания.**
Это относится и к методу, и к обычной Structure, и к ссылочному или
примитивному месту. Приоритет — «назад последняя»: последнее применимое
предшествующее определение или уже накопленное изменение имеет
приоритет. Применимость определяется именем и областью связывания,
а не успехом допуска: выбранное значение проверяется по обычному
контракту, и несовместимость не разрешает взять более раннее значение.
Если предшествующего источника нет, имя и подготовленное место можно
найти вперёд. Выбора по близости нет: в области кода имени соответствует
одно подготовленное место, записи последовательно меняют его значение;
поле data находится однозначно, а несколько одноимённых вхождений без
индекса дают ошибку неоднозначности ([уточнение автора
2026-11-09](../LMX_blog/2026-11-09.md)).

### Уже выполненная запись определяет следующее чтение

```lmx
x: int: 1
print(x)
x: int: 2
print(x)
x: int: 3
```

Первый `print` получает 1, второй — 2. Последняя строка ещё не выполнена
во время этих чтений и не подставляет в них 3. Все три записи относятся
к одному месту `x`; они не создают три одноимённых поля данных.
Обходчик накапливает достигнутые изменения. Нативный код должен
сохранять тот же порядок записей и чтений, а не подменять его
безусловным выбором последней записи во всём исходнике.

### Метод и обычная Structure могут быть описаны дальше

```lmx
read_later: fn: int () {}
    return: Later\value + later()

Later{ value: int: 5}

later: fn: int () {}
    return: 2

read_later()
```

Из тела `read_later` доступны и позднее имя обычной Structure `Later`,
и позднее имя метода `later`. Голое имя и путь читают выбранные значения;
`later()` явно вызывает метод. В этом примере `read_later()` стоит
после построения обеих целей. Правило видимости не исполняет их
объявления, инициализаторы или будущие записи заранее. Если программа
обращается к подготовленному месту до заполнения, одна лишь видимость
не даёт ему нулевого или иного придуманного значения; действует
существующий контракт такого места.

### Подготовка полей и границы правила

Автозаполнение `var` заранее обеспечивает полный состав собственных
полей метода. Теперь двусторонняя видимость — общее правило языка,
а не особое исключение только для этих полей. Подготовка полного набора
мест не вычисляет инициализаторы из тела и не переносит будущие эффекты
на вход в метод. Для нативного понижения нужно заранее согласовать
раскладку полного набора полей и адресные карты, затем сохранить
семантический порядок исполнения.

P0 по-прежнему хранит все исходные вхождения, их порядок и контейнеры;
он не выбирает «победившее» определение и не сворачивает повторные
записи. Области связывания и приоритет динамического источника перед
лексическим не расширяются. Смысл `parent`, `node` и `independent`
не меняется. У неоднозначного явного `data\field` по-прежнему нужен
номер вхождения `data\(N)field`; правило «назад последняя» не выбирает
одно из этих полей автоматически. Общий индекс `data\(N)` и Mix также
сохраняют свои контракты. Нормативные правила — в [семантике](new_LMX_semantics.ru.md#fields)
и [грамматике](new_LMX_grammar.ru.md#name-visibility), изменения кода —
в [списке исправлений](new_bugs_for_fixing.md).

<a id="structure-index"></a>
## Прямой индекс и номер именованного вхождения

`struct\(index)` без следующего имени выбирает непосредственный элемент
Structure по его общей позиции. Нумерация начинается с нуля; вложенная
Structure остаётся одним непосредственным элементом, а не раскрывается
в поля родителя. Этот путь доступен для любой Structure, включая метод.

Существующая форма `struct\(index)field` сохраняется: она выбирает
вхождение конкретной головы `field:` на корневом уровне Structure,
рассматриваемой как данные. Счёт также начинается с нуля, но только
среди вхождений выбранного имени, а не среди всех элементов.

У функции `f` части упорядочены как `{return args var body}` (return
первым везде, [уточнение автора 2026-11-09](../LMX_blog/2026-11-09.md));
у `sub` и `catch` результата нет, их части — `{args var body}`:

```lmx
f\(0)                # элемент с общей позицией 0: return
f\(0)return          # вхождение имени return с номером 0
f\return             # единственное вхождение имени return
f(1)                 # вызов метода с аргументом 1
```

Первые три обращения выбирают часть `return` разными путями; `f\(1)`
выбирает `args`. Запись `f\(1)return` потребовала бы второго вхождения
имени `return`, которого в этой структуре функции нет; это не другая
запись `f\(1)`. Голое
`struct\field` по-прежнему требует единственного вхождения этого имени.

Нумерованный именованный путь служит для обращения к исходным головам
в Structure-as-data. Он не разрешает повторные материализованные поля
данных. Прямой позиционный путь также не меняет этого ограничения.

<a id="expression-structure"></a>
## Выражение — Structure

**Выражение является Structure.** В `{a + b}` сохраняются поля выражения,
их порядок и вложенность; описание выражения не тождественно результату
его вычисления. Фигурные скобки явно задают границу этой Structure.

```lmx
{a + b} * c
```

В контексте вычисления потребитель выражений использует значение
внутреннего `a + b` как операнд умножения на `c`. P0 сохраняет внутреннюю
Structure и её поля, не заменяет её результатом и не снимает контейнер.
Само наличие описания `{a + b}` не означает его немедленного вычисления:
роль и вычисление определяет семантический потребитель выражения.

К Structure выражения применим тот же общий путь `\(index)`.
Он выбирает непосредственные элементы сохранённой структуры; числовая
раскладка операторов или отдельный ABI выражений этим не вводятся.

<a id="structure-array"></a>
## Structure через Array @

Помимо прямого пути `f\(index)`, Structure можно представить как массив
void-ссылок `@` и индексировать этот массив. Для этого явно объявляется
массив ссылок, затем ему присваивается Structure:

```lmx
arr{ (): @}; arr: f; arr(0)
```

`arr{ (): @}` — именованный дескриптор, объявляющий Array `@`.
`arr: f` присваивает массиву представление Structure метода `f`; голое
имя `f` читает функцию и не исполняет её. `arr(0)` возвращает Structure
`return` функции `f`, доступную через соответствующую ссылку массива.

Порядок частей функции — `{return args var body}`, нумерация — с нуля:

| Прямой путь | Через Array `@` | Часть функции `f` |
| --- | --- | --- |
| `f\(0)` | `arr(0)` | `return` |
| `f\(1)` | `arr(1)` | `args` |
| `f\(2)` | `arr(2)` | `var` |
| `f\(3)` | `arr(3)` | `body` |

Array `@` — дополнительный способ доступа; для прямого `f\(index)`
объявлять его не требуется. Именованные пути `f\args`, `f\return`,
`f\var`, `f\body` сохраняют соответствующие части.

<a id="arena-typeof"></a>
## typeof: тип по арене указуемого объекта

`typeof(p)` принимает указатель и возвращает код типа арены, к которой
принадлежит указуемый объект. Для массива ссылок из предыдущего раздела:

```lmx
typeof(arr(0))
```

Аргументом служит ссылка на Structure `return` функции `f`. Результат —
код типа арены этой Structure, а не статический тип `@` самого указателя
и не тип значения, возвращаемого вызовом `f`. Определение типа по арене
предполагает, что её код однозначно определяет тип размещённых в ней
объектов; конкретные числовые коды здесь не назначаются.

Код типа арены сам по себе не заменяет проверку полного интерфейса
Structure. Если разные структуры имеют общий тип арены, этот код не
различает их наборы полей, формалы и требования допуска. Для обычного
массива `int` нельзя молча считать значение его элемента указателем:
контракт `typeof` требует именно ссылку на проверяемый объект.

<a id="fn-declaration"></a>
## Объявление fn

Имя функции стоит снаружи, части ресивера `fn` идут в порядке
`return args var body`. Аргументы удобно описывать анонимной круглой
Structure; все части можно записать одной строкой (пример автора):

```lmx
f: fn: int (arg: int) {variable: int} {body: int}
```

Здесь `int` — `return`, `(arg: int)` — `args`, `{variable: int}` — `var`,
`{body: int}` — `body`. Круглые скобки после пробела без головы —
анонимная Structure, а не вызов. Без `var` получается короткая форма,
без тела — дескриптор интерфейса.

Закрывать уровни, как и в Python, не требуется: блок завершает обычное
снижение уровня. Только для закрытия нескольких уровней нужны общие
средства — `end: name` или терминальный `return`, который, сохраняя своё
действие, чаще всего и служит trailer ([напоминание автора
2026-11-09](../LMX_blog/2026-11-09.md)).

<a id="call-forms"></a>
## Запись вызова и три способа сократить аргументы

Основная форма вызова — `f(args)`, нульарного — `f()`. Внутри круглых
скобок допустимо всё, что внутри `{}`, включая блоки, поэтому и большой
аргумент пишется в `f(args)`. `f: args` вызовом не является: двоеточие
служит именованию, присваиванию и ресиверам ([уточнения автора
2026-11-09](../LMX_blog/2026-11-09.md)). Правило вызова не относится
к ресиверам и операторам: у `fn:`, `int:` и других ресиверов нет
дилеммы «вызов или присваивание», их формы и контракты не меняются. Круглые скобки ресиверу тоже разрешены и ничего не меняют: `int(5)` и `int: 5` — одно и то же.

Явно записанные аргументы можно сократить тремя способами.

**1. Вложенный метод — лексическое связывание.** Метод внутри другого
читает имена объемлющей области:

```lmx
area: fn: int (w: int; h: int)
    doubled: fn: int ()
        return: w * h * 2
    return: doubled()
```

`area(3, 4)` даёт 24; `doubled()` вызывается без аргументов.

**2. Приоритетное динамическое связывание.** Свободное имя вызываемого
получает ближайшую привязку вызывающего, раньше лексического поиска:

```lmx
greet: sub: ()
    print(prefix + name)

welcome: sub: (name: Text)
    prefix: Text: "Hello, "
    greet()
```

`welcome("Ann")` печатает `Hello, Ann`: `prefix` и `name` в `greet`
берутся из активации `welcome`. Без такого входа и без лексического
источника вызов `greet()` недопустим.

**3. Одиночная Structure как список аргументов** — как в математике
подставляют точку в `f(x)`:

```lmx
sum: fn: int (x: int; y: int)
    return: x + y

p: {x: int: 3; y: int: 4}
r: int: sum(p)       # 7, как sum(3, 4) и sum(x: 3; y: 4)
```

Поля `p` сопоставляются с формалами на стадии вызова; P0 структуру
не раскрывает ([семантика](new_LMX_semantics.ru.md#whole-arguments)).

Тот же вызов можно оформить через `f():` — короткой записью `f(): args`
или блоком:

```lmx
f():
. 3
end: f
```

Это дополнительное оформление того же вызова, без отдельного выбора
`data`, исполнения или связывания; в обычном коде оно почти не нужно
(пример автора — сверхдлинный `print`).

Анонимные вложенные скобки красивее чередовать: начинать с фигурных,
рядом со скобками вызова тоже ставить фигурные, внутри фигурных —
круглые: `{a * (b + {c - d})}`, `f({a b})` ([пожелания автора
2026-11-09](../LMX_blog/2026-11-09.md)). Это стиль, а не правило разбора:
контейнеры не добавляются и не убираются ради вида.

<a id="callable-description"></a>
## Явная композиция тела метода

```lmx
add: fn: int (int: x; int: y) {}
    return: x + y

add5: fn: int (int: x) {}
    merge(y: int: 5; add\body)
```

У `add` отдельно хранятся `return`, `args` с формалами `x` и `y`, `var` и
`body` с оператором `return: x + y`. Путь `add\body` выбирает именно тело.
`merge` строит для `add5` тело с `y: int: 5` и этим оператором; `add5(1)` даёт 6.
Заголовок `add5` объявляет только формал `x`: поле `y` нового тела не
становится формалом или значением формала по умолчанию. Запись
`merge(add; y: int: 5)` не равнозначна: у внешней Structure метода `add` есть
части `return`, `args`, `var` и `body`, но нет непосредственного поля `y`.

Другой вариант `add5` помещает инициализацию в явную `var`, сохраняя тело `add`:

```lmx
add5: fn: int (int: x) {y: int: 5}
    add\body
```

Третий, альтернативный вариант изменяет уже `args`: здесь `y` — формал
с умолчанием 5, а не поле тела или `var`:

```lmx
add5: fn: int merge(add\args; y: int: 5) {}
    add\body
```

Это три взаимоисключающих определения `add5`, а не три последовательных
объявления в одной области. Имя функции стоит снаружи, части ресивера `fn`
идут в порядке `return args var body`. Полная форма `fn` явно передаёт `var`
после `args`; короткая запись без этого аргумента допустима и создаёт
в результате ту же адресуемую пустую часть `var`. Однополевое `int: x`
описывает типизированное место без начального значения, в сигнатуре —
формал без умолчания.

Результат `merge` отдельно проходит [допуск](new_LMX_semantics.ru.md#admission);
свободные имена тела — [динамическое разрешение](new_LMX_semantics.ru.md#dynamic).

Заголовок `add: fn: int (int: x; int: y)` **без тела** — третья форма:
только дескриптор интерфейса, который можно передать по ссылке, но нельзя
прямо исполнить как тело `add`. Если после этого заголовка есть тело,
это короткое исполняемое определение с адресуемой пустой `var`. Полная
форма с `{}` после `args` задаёт её явно.

<a id="receiver-arities"></a>
## Место и значение: отдельное имя и приёмник типа

Это альтернативные записи, не последовательные операторы одной программы:

```lmx
x: int()       # место int без начального значения
int: x         # то же место
x: int: 5      # int со значением 5
x{ int: 5}     # то же значение: имя во внешнем описании

ptr: @()       # void-ссылка без заданного адреса
@: ptr         # то же место
ptr: @: 0      # void-ссылка с явным нулевым адресом
ptr{ @: 0}     # то же значение: имя во внешнем описании
```

В `x{ int: 5}` и `x: int: 5` приёмник `int` получает один операнд `5`;
имя `x` относится к внешнему описанию. Для ссылки на существующую Structure
работает пара `ptr: @: Model` / `ptr{ @: Model}`; это уже не пустой
void-указатель. Первое определение выделяет место, повторная форма
с кандидатом записывает в него после допуска; повторная форма без
кандидата только сверяет требование.

<a id="callable-admission"></a>
## Что проверяет интерфейс вызываемого

Методы с формалами `{int: x; y: int: 5}` и `{int: x}` оба допускают `f(1)`, но
записанное у Consumer обращение `f(1; y: 25)` допускает только первый.
Проверяются необходимые явно использованные обращения, не совпадение
списков формалов и не предполагаемое поведение тела. Пользовательские
проверки поведения — отдельный этап.

<a id="method-pointer"></a>
## Имя метода и указатель на него

`myFunc()` вызывает объявленный метод напрямую. После
`ptr: @: myFunc` форма `ptr()` вызывает метод через указатель; повторное
`ptr: @: otherFunc` присваивает существующей ячейке другой совместимый
метод. Голое `myFunc` или `ptr` лишь читает значение.
`{\ptr}()` — вызов после явного разыменования; `\ptr()` применяет `\`
к **результату** вызова согласно обычному приоритету, а не является особым
способом вызвать указатель.

<a id="native-merge"></a>
## Нативное тело в копии

Копия сохраняет собственный изменяемый граф; общий адрес машинной реализации
не делает граф общим. Если merge выбирает другое тело, старый native-вход
не описывает новый код. При той же реализации данные могут передаваться как
граф копии только при совместимых используемой раскладке и адресной карте;
при отсутствии пригодного native-входа исполняется готовый граф. Карта
`implements` сопоставляет физические поля, но не выбирает код и не хранит
имена в runtime. Разделение кода и данных в `code(data)` и адресуемые части метода —
[утверждённая кодируемая цель](../next_core_tasks_v3.md); совместимый ABI
ещё не реализован полностью.

<a id="factory-result"></a>
## Возвращённый метод

`add5: @: makeAdder(5)` **вызывает** фабрику и сохраняет возвращённый
метод. Затем `add5(1)` вызывает его через ссылку. Просто определить
`add5: makeAdder 5` — не значит вызвать фабрику. Если тело возвращённого
метода читает свободное `n`, динамический вход вызывающего имеет приоритет
перед скопированным лексическим запасным источником.

<a id="dynamic-fallback"></a>
## Динамический и лексический источники

Пример не является синтаксисом LMX: в скопированном лексическом контексте
`x = 10`, вызывающий передаёт `x = 25`. Свободное `x` читает 25;
`node\x` явно читает 10. При следующем вызове с `x = 40` свободное
`x` читает 40, а без динамического источника — лексические 10.

<a id="message-conversion-context"></a>
## Контекст преобразований Message

Схема `a → int` в Message A и `a → String` в Message B — не синтаксис
LMX. Один метод с требованием `a` получает смысл из контекста данного
Message; B не наследует преобразования A из-за доставки письма. Примитивное
`Foot → Meter` не доказывает `implements` для двух произвольных Structure.
При вызове могут понадобиться два разных маршрута: аргумент
`int → double` и результат `double → int`. Оба должны быть доступны в
контексте соответствующего Message.

<a id="post-transport"></a>
## post: один вызов, несколько доставок

Три обращения `getPixel` исполняются трижды. Если у каждого результата
три адресата `answer`, получаются три исходных ответа и девять доставок,
а не девять исполнений. Связь ответа с запросом задаёт исходный Message,
не позиция ветки и не новый числовой ID. `answer` готовят до отправки
`ask`; недоставка одного запроса не останавливает остальные.

`undelivered` получает уже сформированные аргументы исходного запроса;
объявленный отказ идёт в `catch`. Timeout считают от фактической отправки:
при пороге 500 мс обработчик может наблюдать 512 мс, но само пороговое
поле остаётся 500. Поздний ответ не удаляется автоматически. Полный
контракт и матрица T01–T26 — в [семантике](new_LMX_semantics.ru.md#thread-message-api)
и [почтовом плане](../next_core_tasks_v3.md).

<a id="tables-and-registries"></a>
## Таблицы и провайдеры как данные

Явная Table может дать написание `u8 → "uint8_t"` или ключ реализации
`plus(decimal)(int) → decimal_int_add`. Она не объявляет типы, не создаёт
runtime-пространство имён и не ищет провайдеров автоматически. Порядок
источников, разрешение конфликтов и маркер отсутствующей ячейки задаёт
выбранный потребителем профиль, а не универсальный скрытый реестр.
