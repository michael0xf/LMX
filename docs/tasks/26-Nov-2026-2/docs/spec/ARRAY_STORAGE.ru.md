# Мерность, хранение Array и квадратные значения

Редакция 26 ноября 2026. `int[][][]: arr` задаёт мерность одного плоского
Array с элементами int. Мерность и размеры осей сохраняются в служебной
записи арены рядом с capacity. Заголовок Lmx, записи `{type value}` и
пользовательские поля Structure не расширяются.

<a id="rank"></a>
## 1. Повторные постфиксы и готовое значение

```lmx
int[]: line
int[][]: plane
int[][][]: arr
```

Серия из N пустых постфиксов `[]` описывает N логических осей одного Array.
Для плотного int-хранилища это один непрерывный C-блок int; строки и слои
не выделяются отдельными объектами. Последняя координата изменяется быстрее.
Полное требование остаётся перед двоеточием. Объявление без инициализатора
сохраняет обычное `uninit:T`: оно не выделяет пустой массив, не выбирает
размеры осей и не добавляет неявные нули.

Раннее описание `int[][]` как отдельного «массива массивов» заменено этим
правилом. `int[]@[]` остаётся обычной композицией требований к ссылкам и Array;
нового вида контейнера она не создаёт. Structure — обычный Array ссылок `@[]`.
Его элемент может ссылаться на другую обычную Structure, как любой другой
элемент графа. Для этого нет отдельного вида, раскладки или диспетчера.

<a id="dynamic-postfix"></a>
### 1.1. Динамическая запись мерности и глубины указателя

**DOC_SPEC_ADDITION — только спецификация.** `int[](N)` равнозначно N
повторным `[]` после int, а `int@(N)` — N повторным `@`. Например:

```lmx
int[](1): [1 2 3 4]
int@(2): ptr_to_ptr
```

В первой строке rank равен 1, length равен 4; N не задаёт длину или ёмкость.
Во второй объявляется uninit-место для указателя глубины 2, без выделения
цепи объектов. `int[](3): arr` без инициализатора также остаётся uninit.

N — обычное выражение с положительным конечным целочисленным результатом,
которое TYPE-потребитель получает один раз при потреблении полного требования.
Нулевой или отрицательный счётчик не стирает тип и не вводит rank=0.
Общий P0 сохраняет область N без вычисления; повторные постфиксы и полная
левая модель остаются равноправными способами описания требования.

Это сокращение не меняет storage: rank/extents по-прежнему находятся во
внешней записи рядом с capacity, указатели не получают новых полей Lmx.
Порядок композиции и различие с безлевыми компактными объявлениями описаны
в [полном договоре](TYPE_DECLARATION_FORMS.md#dynamic-postfix).
Реализация и новые тесты не добавлены; production P0/транслятор/runtime —
**NOT_RUN**. 14 прежних host-проверок этой главы не проверяют новые формы.

<a id="side-metadata"></a>
## 2. Служебная запись рядом с capacity

Существующее соответствие арены «идентичность/адрес дескриптора → capacity»
сохраняет также rank и extents. Для готового прямоугольного значения:

```text
metadata = arena entry selected by identity(array)
metadata.rank = number of extents
array.length = product(metadata.extents)
metadata.capacity >= array.length
```

Это эскиз внутреннего обращения, не новые системные функции или поля LMX.
Rank конечен и положителен; extents — неотрицательные целые. Нулевой extent
даёт length=0, сохраняя остальные размеры и сам rank. Вычисление произведения
и смещений не должно переполняться в допустимое маленькое значение.

`length` — число всех элементов, capacity — резерв в элементах. Размер
элемента/его физический stride следует фактическому типу хранения. Row-major
шаги осей выводятся из extents; если реализация кеширует их в той же служебной
записи, они должны согласовываться с ней. Имена shape, rank, extents, strides
и size в host-моделях не становятся дополнительными полями Array.

У Lmx по-прежнему только `parent`, `length`, `storage`. Нет поля rank даже
во «внутреннем расширенном Lmx», скрытого префикса перед ним или поля в
TYPE-record. `sys\descriptor` возвращает прежние три адреса настоящих полей;
`sys\capacity` читает прежнюю ёмкость. `arr\rank` не становится служебным
доступом: такое имя может быть только обычным явно имеющимся полем.

<a id="indexing"></a>
## 3. Плоский индекс, координаты и обычный путь

| Запись | Действие |
| --- | --- |
| `arr[k]` | Один линейный индекс от 0 до length−1, в том числе при rank>1 |
| `arr[i][j][k]` при rank=3 | Полный координатный доступ к тому же плоскому хранилищу |
| `arr[start:stop:step]` | Обычная одномерная выборка линейной последовательности |
| `plane[i][:]` | Явный выбор строки через цепочку осей |
| `plane[1:3][::-1]` | Выбор по двум сохранённым осям; последняя обращена |
| `struct\struct2\field` | Обычный путь по именованным полям Structure |
| `struct[i]\[j]\[k]` | Тот же механизм пути, с выбором обычных элементов по индексам |

Если i выбирает поле struct2, а j — поле field, соответствия точны:

| Именованная/смешанная запись | Индексная запись |
| --- | --- |
| `struct\struct2\field` | `struct[i]\[j]` |
| `struct\struct2\field[k]` | `struct[i]\[j]\[k]` |

У второй строки есть ещё один выбор элемента k; его нельзя потерять при
сопоставлении путей.

Цепочка соседних суффиксов без `\` относится к осям одного Array. Разделитель
пути `\` продолжает доступ к значению выбранного обычного поля; он не
включает особую операцию «массива массивов». Смешение имени и индекса следует
тем же правилам обычных путей.

При форме `[d0,d1,d2]` координатный индекс равен `(i*d1+j)*d2+k`.
Для extents `[2,2,2]` доступы `arr[5]` и `arr[1][0][1]` выбирают одно место.
Один суффикс не создаёт неявный Array строки. Неполная многокоординатная
цепочка из одних скалярных индексов не получает скрытого view; нужен один
линейный индекс либо полный координатный набор. В цепочке со срезами
скаляр снимает соответствующую ось, срез сохраняет её с новой длиной,
а неупомянутые оставшиеся оси сохраняются целиком.

Получение source и индексов остаётся однократным и упорядоченным. Сохранение
extents не вводит новых проверок каждой верхней границы координаты: действует
существующий договор сведения к итоговому индексу и проверки этого элемента.
Недопустимый отрицательный Array-индекс не становится отсчётом с конца.
Интерпретация L2/L3 и L3 проверяют доступ по действующему договору;
нативное L2 сохраняет отсутствие автоматической проверки. Для относительного
смещения адреса используются обычные указатели.

Для полной скалярной цепочки сначала вычисляется один row-major индекс,
а проверяется лишь итоговый элемент: при extents `[2,3]` координаты `[0][3]`
и `[1][0]` дают k=3. Нормализация границ среза работает по отдельному договору
выбранной оси и не добавляет скалярной цепочке проверки каждой координаты.

<a id="constructors"></a>
## 4. Самостоятельное `[items]` — одно значение

В позиции VALUE самостоятельная квадратная группа создаёт обычный анонимный
Array со свободными типами элементов, как `@[]: [items]`. Это дополнение
к уже имевшемуся квадратному инициализатору объявления, а не новый parser.

```lmx
int[]: arr2 [10 20]
@: whole [arr2]
@: empty []
@: pair [1 2]
```

`whole` имеет ровно один элемент, содержащий исходное значение arr2 с его
идентичностью. Это не копирование элементов arr2 и не автоматическое
расширение singleton до чужой формы. `[]` даёт один присутствующий пустой
Array. `[1 2]` даёт два элемента. Полный тип результата не угадывается
пробным получением первого элемента.

Каждое выражение элемента получается один раз в обычном порядке;
явные потоки `copy`/`merge` потребляются по существующему договору
инициализатора. Готовое VALUE не исполняется повторно как граф. После
построения квадратный Array остаётся одним значением даже при нуле или
одном элементе: Expression не применяет к нему прозрачность круглой группы.

P0 сохраняет структурную форму конструктора, исходные вхождения и контекст.
Группировщик видит этот договор в графе, а не распознаёт символы скобок.
`T[]`, `arr[i]`, `arr[:]`, `[items]` и `.(expression)op` различаются
структурным положением и принимающей ролью общего P0.

### 4.1. Строки типизированного многомерного инициализатора

Объявленный rank задаёт, как принимающий ресивер потребляет уже разобранные
области инициализатора. Разделитель `;` на текущем уровне инициализатора
заканчивает строку; явные группы строк задают те же границы. Эти формы равны:

```lmx
int[][]: [a b c; a b d; a b c]
int[][]: [[a b c] [a b d] [a b c]]
```

При `a=1`, `b=2`, `c=3`, `d=4` обе дают extents `[3,3]` и один плоский
storage `[1,2,3,1,2,4,1,2,3]`. Числовой пример имеет extents `[3,2]`:

```lmx
int[][]: [1 2; 3 4; 5 6]
int[][]: [[1 2] [3 4] [5 6]]
```

Длины строк должны совпадать. Следующие две формы имеют длины 3, 4, 5
и получают диагностику формы транслятора либо достигнутого интерпретатора:

```lmx
int[][]: [a b c; a b c d; a b c d e]
int[][]: [[a b c] [a b c d] [a b c d e]]
```

Отдельный отрицательный пример автора также ошибочен: длины 3, 3, 4.

```lmx
int[][]: [[a b c] [a b d] [a b c d]]
```

Это не новые перехватываемые LMX-исключения. Ни ragged-хранилища, ни таблицы
границ строк, ни промежуточные объекты row Array не создаются. При rank больше
двух тот же договор применяется к уже ограниченным областям следующих осей.

Получение формы и значений использует общий P0 и общий контракт инициализатора:

1. Сохраняются исходные узлы и контексты; разделители определяют области.
   `;` внутри вызова, литерала или вложенной области не является разделителем
   внешней строки. Вне инициализатора `;` по-прежнему заканчивает короткую форму.
2. По объявленному rank сверяется прямоугольность текущих областей. Уже известное
   несоответствие диагностируется до получения элементов; динамические потоки
   используют обычную последовательную проверку своего контракта.
3. Значения элементов получаются один раз в исходном порядке и допускаются по T.
   Обычный Array VALUE сам по себе не превращается в поток. Явные `copy`/`merge`
   сохраняют имеющийся контракт потока инициализации.
4. Заполняется один flat storage; rank/extents сохраняются рядом с capacity.
   Исходный текст и живой граф не переписываются в иной граф строк.

При отсутствии достаточного описания пустых оставшихся осей модель не угадывает
их размеры по length=0. Полное уже заданное описание, например `[2,0,3]`,
сохраняется целиком.

### 4.2. Обычные безымянные поля Structure в DATA

Прямоугольность — требование типизированного rank-конструктора, а не любого
набора Structure. Следующие формы DATA равнозначны и корректны:

```lmx
Struct: [a b c] [a b d] [a b c d]
Struct: (a b c) (a b d) (a b c d)
```

Каждая объявляет три обычные безымянные Structure-поля с длинами 3, 3, 4.
Общая Structure есть `@[]`; её поля могут содержать обычные ссылки, без особого
вида «массив массивов». Здесь принимающая DATA-роль сохраняет три структурных
значения и не требует для них одной прямоугольной формы.

Это не правило группировщика по виду исходных скобок. В VALUE `[arr2]`
обычный конструктор Array уже потреблён и отдаёт одно готовое значение с одним
целым полем arr2. В DATA принимается граф анонимных полей. Группировщик не читает
символы скобок и не использует flags «было квадратным/круглым» для раскрытия.

<a id="mutation"></a>
## 5. Одномерные операции остаются доступны

Мерность не запрещает обычный одномерный обход, выборку, запись элемента
или операцию изменения размера. Многомерные операции также сохраняют доступ
к тем же элементам через extents. Никакого преобразования всего графа между
двумя представлениями для этого не требуется.

Плоский sequence-потребитель читает действительный тип T, length и storage
исходного Array при любом rank. Сам выбор одномерного профиля не строит
новый Array, не вызывает reshape, не переписывает служебный rank на 1
и не меняет тип исходника. Явный пользовательский контракт с ограничением
rank сохраняет собственный допуск; его нельзя смешивать с общим запретом
одномерных операций над многомерным значением.

Операция, сохраняющая форму результата, сохраняет согласованные extents.
Новая плоская выборка может иметь rank=1, не изменяя shape исходника.
Конкретный договор результата определяет эту форму; одна только смена записи
индекса не меняет rank существующего объекта. Whole-присваивание сохраняет
обычные правила ссылки и допуска; поэлементная запись сохраняет назначение.

`sys\reserve` меняет ёмкость, сохраняя length и extents. Изменяющая length
операция, включая `sys\resize`, обязана одновременно согласовать служебное
описание по своему объявленному договору; старые extents с неверным
произведением оставлять нельзя. Нельзя запретить саму операцию по одному
только rank, но нельзя и угадать новые оси из одного числа элементов.
Нового публичного reshape API эта глава не вводит. Прямая запись length
через существующий L2 descriptor также сохраняет обязанность согласованности.

<a id="reconstruction"></a>
## 6. Копирование, восстановление и native

Метаданные привязаны к идентичности действительного дескриптора. Две ссылки
на один Array видят одну запись rank/extents. При копировании Array запись
переносится на новый дескриптор в общем отображении source→copy; изменение
резерва или адреса storage не создаёт другой языковой объект.

Восстановление может выбрать capacity=length, но не может потерять rank и
extents: например, length=12 не различает `[2,6]` и `[3,4]`. Форму сохраняют
либо восстанавливают из уже сохранённого полного описания данного значения.
Это служебная информация сериализации, не дополнительные узлы исходного
графа и не второй постоянный граф. При attach, освобождении и повторном
использовании памяти запись сопровождает свой дескриптор по общему владению.

Native-код может использовать известные размеры как обычные константы,
но готовое значение по-прежнему сохраняет достаточное служебное описание
для интерпретатора, динамического кода и последующих допустимых операций.

<a id="depth"></a>
## 7. Depth использует логические оси плоского Array

[Глубина операции](OPERATOR_DEPTH.ru.md#evaluation) использует сохранённые
оси, а не число выделенных C-блоков. У плоской матрицы rank=2 depth=1
выбирает логические строки; depth=2 доходит до координатных элементов.
Для `*` это даёт матричное произведение на depth=0, векторные произведения
пар строк на depth=1 и скалярные произведения элементов на depth=2.

Логическая часть Array передаётся через временную информацию offset/shape
обычного исполнения. Для строк не выделяются объекты графа и не создаётся
дерево вложенных Array. Если обычный элемент действительно содержит ссылку
на Structure, дальнейшее потребление следует тем же правилам значения и
сохранённой глубины; отдельной категории вложенных контейнеров нет.
