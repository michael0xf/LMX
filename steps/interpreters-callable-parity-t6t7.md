# §7 "Интерпретаторы: те же два примера или явное unsupported" — замер (Sonnet, 2026-09-26)

Read-only. Ядро (`lmx_*.lm1`, `dev/l3_interp/`) не трогал. Задание Opus: что делают `lmx_walk`
(нативный walker, ROOT + `--walk-methods`) и `l3_exec` (`dev/l3_interp`, отдельный L3-интерпретатор)
с двумя примерами T6/T7 (`unit_make_adder.lm2`, `unit_t7_convert.lm2`), предложить parity-строки
harness или явный located «unsupported».

## 1. `lmx_walk` + `--walk-methods`: измерено напрямую (два l2trans-прогона, диф L1)

- **`unit_make_adder.lm2`** (`fn: makeAdder (int: n) fn: (int: x) int` / вложенный `fn: addN`):
  генерированный L1 **побайтно идентичен** с `--walk-methods` и без него. Ни `makeAdder`, ни
  `addN` не переходят в op-дерево ни при каком режиме — оба остаются полностью нативными.
  Причина по коду (`l2_rw_may`, `l2trans.lm1:21714-21749`, комментарий читает норму дословно):
  «a result that is a number... or none» — `makeAdder`'s объявленный результат `fn: (int: x)
  int` (сам callable-тип), не число → `l2_rw_may(makeAdder) = 0` сразу. `addN` формально
  подходит под числовой результат/формал, но harness `Debt` уже называет его прогон через
  `lmx_call_prim(` (динамический нативный вызов callable-формала/PAP-инстанса, T6's
  `l2_mad_on`-механизм) — измеренный факт: `addN` тоже остаётся вне walkable-подмножества
  (нулевой диф подтверждает это на уровне L1, не только по Debt-строке).
- **`unit_t7_convert.lm2`** (`add`, `wrap` — строит `return: merge(y: k; add)`, `five`, `bin`,
  `take (bin: op)`, `passed`): **3 из 6 методов реально переходят в op-дерево** под knob (диф
  L1 — ровно 3 строки `l2_entry_leaf\native: (cast: (LmxEntry) l2_mN_tr)` пропадают для `m0`,
  `m2`, `m3`, т.е. для `add`, `five`, `bin` — простые числовые тела без merge/callable-формала).
  Оставшиеся 3 (`wrap`, `take`, `passed`) остаются нативными и под knob: `wrap` строит callable
  через явный `merge(...)` (уходит через `l2_pap_steps`/`l2_pap_on`, отдельный путь с
  собственным условием `l2_rw_may(model)`, но сам PAP-инстанс не отражается в walk-режиме как
  видно по нулевому дифу именно на этих трёх), `take (bin: op)` имеет **callable-формал**
  (`l2_rw_may`: «A callable formal... stay out», исключение явное), `passed` зовёт `take` с
  merge-актуалом.

**Вывод по walker:** обе фикстуры полагаются на T6/T7 (PAP/merge-построенный callable),
и именно эта часть *категорически* не входит в walkable-подмножество ни в одном из двух
файлов — knob лишь дополнительно op-три-фицирует случайно-простые СОСЕДНИЕ методы
(`add`/`five`/`bin`), которые к самому тестируемому механизму (T6/T7) отношения не имеют.
`--walk-methods` не даёт ни одного шанса реально проверить op-дерево PAP/merge-callable
сегодня — не потому что кто-то забыл включить эти два файла в WalkMethods-корпус (у них и нет
`WalkMethods = $true` в `tools/l2_harness.ps1:968,972`), а потому что **сам механизм построения
шагов не покрывает PAP-модель как класс** (T6's `l2_mad_on` не появляется в `l2_rw_may`'s
собственном разборе типов вообще; T7's `l2_pap_steps` требует `l2_rw_may(model)`, но ничего не
делает с самим PAP-инстансом узла — только с моделью-донором).

## 2. `l3_exec` (`dev/l3_interp`): категорический, не частичный пробел

`grep -l "merge\|MERGE" dev/l3_interp/*.lm1` = **0 файлов**. Не «эти два примера дают
unsupported» — у L3 вообще нет узла для merge:

- Полный список объявленных `L3_NODE_*` (`dev/l3_interp/l3_recv.h.lm1:36-53`): `RETURN`,
  `IF`, `WHILE`, `MATCH`, `EACH`, `YIELD`, `FINALLY`, `THROW`, `EXPECT_INT`, `ASSIGN`, `CALL`.
  **Нет `L3_NODE_MERGE`** — ни объявленного неиспользуемого номера, ни диспетчерской ветки.
  Сравнил с нативным walker'ом: там тоже нет `LMX_WALK_OP_MERGE` (`lmx_walk.h.lm1:212-270`,
  полный список 31 кода) — merge у walker'а идёт через **общий примитивный вызов**
  (`LMX_WALK_OP_PRIM` → `lmx_walk_merge_model`/`lmx_walk_merge_into_map`, обычная нативная
  C-функция, не интерпретируемый узел). У L3 **нет и самого класса PRIM**-диспетчеризации
  (в списке узлов выше PRIM тоже отсутствует) — значит L3 не может выразить merge даже
  окольным путём через «вызови нативный примитив».
- Отдельно от op-кода: `dev/l3_interp/tests/` — это **рукописный** корпус (L3-фикстуры пишутся
  вручную как op-деревья через C-конструкторы селфтеста, не переводятся из `.lm2` транслятором).
  Ни `unit_make_adder.lm2`, ни `unit_t7_convert.lm2` никогда не попадают в L3 сегодня — вопрос
  «что делает l3_exec с этими двумя» в буквальном смысле неприменим: их для L3 не существует,
  пока их вручную не переписать в виде L3 op-деревьев (что само по себе невозможно без узла
  merge).

## 3. Предложение (parity-строки harness vs явный unsupported)

Задача формулирует «или-или»; по факту нужны оба, для двух разных получателей:

1. **Walker (`lmx_walk`, `--walk-methods`): явный located unsupported, а не молчаливый
   native.** Сегодня `l2_rw_may`/`l2_pap_steps`/`l2_mad_on` просто НЕ помечают PAP/merge-модель
   как отдельный класс — метод тихо остаётся нативным, без диагностики и без записи «PAP вне
   walkable-подмножества» нигде в выводе транслятора. Это ничем не отличимо от «переводчик ещё
   не добрался» — а надо явно: расширить комментарий/классификатор `l2_rw_may` третьей веткой
   для PAP-моделей (`l2_pap_on(mi)` / `l2_mad_on(mi)`) с собственным диагностируемым «not in the
   walkable subset: a PAP/merge-built callable», как для catch-параметра или callable-формала
   уже сделано текстом комментария (но не диагностикой — там тоже молчаливое исключение, той же
   формы дефекта, просто более старое). **Это правка транслятора** (`l2trans.lm1`), не harness —
   не делаю сейчас, только называю точное место: `l2_rw_may:21720`, ветка после `cls:
   l2_tramp_class(mi)` (:21728) — нужен явный код-класса «6 = PAP model, excluded, diagnosed»,
   не только числовой 0.
2. **Harness: НЕТ parity-строки для этих двух под `WalkMethods = $true`,** потому что она не
   докажет то, что должна: `--walk-methods` не op-три-фицирует ни один из тестируемых T6/T7
   методов (§1) — добавление `WalkMethods = $true` к `unit_make_adder.lm2`/`unit_t7_convert.lm2`
   даст зелёную строку, которая **ничего не проверяет** (тот же класс дефекта, что «проверка,
   которая не может упасть», `steps/gate-audit-20260926-sonnet.md` не про это, но принцип тот
   же — измерено здесь, а не предположено). Parity-строка имеет смысл **только после** правки
   п.1 — тогда WalkMethods-запуск даст «unsupported», и это и будет строка (`Needle` =
   диагностика транслятора, не рантайм).
3. **L3: явный unsupported — большая задача, не строка.** Нужен сначала **дизайн** узла merge
   для L3 (`L3_NODE_MERGE`, номер, семантика, диспетчер) — это НЕ located-диагностика поверх
   существующего механизма (как в п.1), а новая возможность интерпретатора с нуля, потому что
   сегодня нет ни узла, ни PRIM-эквивалента. До этого дизайна честная промежуточная мера — явная
   строка в `next_core_tasks.md` §6 (матрица) «L3: merge/PAP callable — нет узла, нет PRIM-пути,
   T6/T7 не выразимы» вместо тихого умолчания «эти два примера не упомянуты для L3».

## 5. Замер границы op-дерева PAP/merge (Opus, read-only задание после T6b; `l2trans.lm1` не трогал)

Разбор `l2_mad_*`/`l2_pap_*` в текущем `l2trans.lm1` (после T6b, `a0add35`/`93ba9d5`), чтобы
понять, ЧТО именно нужно walker'у, если решение будет «реально ходить», а не «явно
отказывать». Два факта меняют форму задачи по сравнению с §1–§2 выше:

1. **Вызов PAP-строящего метода с корня УЖЕ ходит.** `l2_rw_mad_at`/`l2_rw_mad_store`
   (`l2trans.lm1:22498–22520`) — это семейство `l2_rw_*` (obhodчик), уже эмитирующее
   `LMX_WALK_OP_AT`/`LMX_WALK_OP_CALL` для операторов вида `w: wrap 5` на корне. Замер §1
   («wrap/take/passed остаются нативными») был про **тело метода `wrap`/`take`**, не про
   корневой вызов их — это НЕ противоречие, а два разных места одного явления: корень уже
   умеет звать `wrap` как обычный вызов (её тело исполняется нативно через трамплин), только
   САМО тело `wrap` (и `makeAdder`) нельзя перевести в op-дерево.
2. **Два раздельных, не общих механизма PAP, у каждого свой путь в `l2_rw_methods_count`.**
   `l2_pap_on`/`l2_pap_model` (T7, явный `merge(y: k; add)`) и `l2_mad_on`/`l2_mad_model`
   (T6/T6b, неявный `return: addN`) — РАЗНЫЕ массивы (`l2trans.lm1:21885–21888` против
   `:22546–22549`), не альтернативные проверки одного факта. `l2_rw_methods_count`
   (`:23296` в текущей нумерации) особо обрабатывает **только** `l2_pap_on(i)!=0` через
   `l2_pap_steps` — оно считает шаги МОДЕЛИ (`add`), не самого хоста (`wrap`), и **T7-хосты
   (`wrap`) уже получают `l2_m_steps[wrap] > 0`**, если модель walkable, — то есть по счёту
   шагов `wrap` формально ПРОХОДИТ. Но полная эмиссия под knob для T7-хоста уходит через
   ОТДЕЛЬНЫЙ путь `l2_t7_host_site`/`l2_t7_write` (`l2_mad_emit:22445–22447`, «site >= 0 →
   `l2_t7_write`»), не через обычный «walk body» emit — не проверено, ходит ли этот путь
   под knob вообще (мой диф §1 показывал `wrap` нетронутым методом байт в байт, значит на
   практике — нет, но МЕХАНИЗМ счёта шагов для него формально не такой же «молчаливо
   исключён», как я написал в §1; это нужно уточнить отдельным прогоном, не сделано здесь).
   `l2_mad_on` (T6/T6b, `makeAdder`) в этот особый путь `l2_rw_methods_count` вообще не
   попадает — падает в обычную ветку `l2_rw_may(i)`, где code 16 (callable-результат)
   исключает её прямо, как в §1.
3. **Что реально строит `l2_mad_emit` (`:22434–22489`), если делать эквивалент op-деревом.**
   Не один примитив: (а) Structure на `arity` int-ячеек (для аргументов модели), (б)
   вторая 1-слотовая Structure (self-ссылка модели), (в) **по одной типизированной ячейке
   на каждый захват** — тип из `l2_mcap_ty` (int/size_t/unsigned/ulong, `l2_mcap_new_helper`
   + `l2_own_store_helper` выбираются ПО ТИПУ, значит число и типы шагов различны для
   каждого метода, как у нативного трамплина — не фиксированная арность операции), (г)
   копия диапазона `[2+caps, 2+caps+steps)` из УЗЛА МОДЕЛИ через `lmx_arena_ref_value` в
   цикле (разделяемое тело — само дерево шагов НЕ копируется, только адреса). Ни один
   существующий `LMX_WALK_OP_*` (`lmx_walk.h.lm1:216–270`, 31 код) не делает всё это одним
   шагом; `LMX_WALK_OP_FRESH` (единственный производитель новой Structure) строит ОДНУ
   Structure, не пару + типизированные ячейки + диапазонную копию. Значит либо (i) новый
   составной op, специализированный НА КОНКРЕТНЫЙ метод (как нативный трамплин — с числом
   и типами захватов, зашитыми в операнды на трансляции, а не общими), либо (ii)
   декомпозиция на последовательность из FRESH×2 + (NEW+PUT)×caps + новый op «диапазонная
   копия по адресу узла модели», которого сегодня нет ни одного (ELEM/OF читают по одному
   индексу, не диапазон).
4. **Оценка размера:** это задача масштаба самого T6b (полноценная переносимая часть
   транслятора + новая машинерия ядра walker'а), не диагностика и не строка кода — не
   делать без отдельного решения координатора выделить её отдельным этапом. Не измерено:
   сколько корпусных фикстур реально используют T6/T7 (кроме двух названных примеров) — не
   считал отдельно в этом проходе.

**Учётное замечание fable_pc (REVIEW `a6de5a9`), важное, чтобы не читать это как решение §7:**
эти 19 фикстур **потеряли knob-покрытие до op-деревьев**, а не приобрели его — до п.1 они
переводились под `--walk-methods` (молча оставаясь нативными где нужно), теперь та же команда
**отказывает целиком**. «Явное unsupported вместо молчаливого native» — это именно
диагностика места пробела (что и просил Opus, п.1 задания), **не** реализация PAP/merge в
walker'е и **не** закрытие пункта §7 плана «Интерпретаторы: те же два примера или явное
unsupported» — тот пункт остаётся открытым до реального op-дерева для PAP/merge (§1–§2 выше)
или до архитектурного решения, что PAP/merge никогда не будет walkable и explicit-unsupported —
это и есть постоянная норма, а не временная мера. Второе замечание fable_pc — возможный остаток
состояния `l2_rw_quiet` вокруг нового пути отказа, зафиксирован как измерение для будущего
прохода по `steps/gate-audit-20260926-sonnet.md`, не подтверждён/не опровергнут в этой сессии
отдельным прогоном.

## 6. План op-дерева PAP/merge (Opus, после T6b) — пересмотр §5 в сторону меньшего решения

§5 оценивал задачу как «нужен новый составной op или декомпозиция диапазонной копии» и назвал
её масштабом T6b. Прочитал механизм `LMX_WALK_OP_PRIM` внимательнее (`lmx_walk.lm1:1124–1198`,
`lmx_walk_prim`) — вывод меняется: **новый op не нужен вообще**, PRIM уже достаточно общий.

**Что подтверждено чтением кода.** Форма PRIM-шага — `[prim, rec, catch, ops...]`
(`:1139`) с ПРОИЗВОЛЬНЫМ числом операндов; каждый операнд — обычное walkable-выражение,
вычисляемое `lmx_walk_eval` независимо (`:1180–:1183`), не константа. Собранные значения
(`refs[0..n)`) передаются нативной функции `record\fn(record\owner, refs, n, dest, out)`
(`:1187`) — той же самой сигнатуре `LmxPrimitiveEntry`, что уже используют
`lmx_walk_merge_model`/`lmx_walk_merge_into_map` (сам `merge()` — сегодняшний walkable путь
для ЯЩИКА, не для ОПРЕДЕЛЕНИЯ модели) и генерируемый `l2_mad_call` (`l2trans.lm1:22491–22496`,
уже вызывает `lmx_call_prim` тем же способом на СТОРОНЕ ВЫЗОВА PAP-инстанса). То есть
«позвать нативную C-функцию с N вычисленными операндами и получить ссылку обратно» — это уже
рабочий, доказанный механизм, а не то, что нужно изобретать.

**Пересмотренный план (гипотеза, код не писал, не проверял сборкой):**

1. **Вынести конструирование узла из `l2_mad_emit` в отдельную именованную нативную функцию**
   на сигнатуре `LmxPrimitiveEntry`, по одной на PAP/mad-хозяина (как сегодня по одной
   трамплин-функции на метод) — тело то же самое, что сейчас пишется инлайн в точке
   `return: model` (`l2_mad_emit:22460–22488`: две суб-Structure, N типизированных ячеек
   захвата, диапазонная копия `[2+caps, 2+caps+steps)` из узла модели). Индекс модели и её
   `steps`/`caps` — константы трансляции, зашиваются в тело функции при генерации, не операнды
   PRIM. Операнды PRIM — ровно захваченные значения (то, что `l2_mad_emit` сегодня читает через
   `l2_mad_atom_field`+`l2_eval_fields`, T6b слоты 2..(2+caps), тип по `l2_mcap_ty`).
2. **`l2_rw_may` перестаёт исключать хозяина по коду результата 16 тем же путём, что и
   `unit_make_adder`.** Новая ветка: метод — `l2_mad_on`/`l2_pap_on` хозяин, чьё тело — ordinary
   statements (уже проходят обычную walkable-проверку per-statement, T6b это и доказал: обычные
   int/size_t операторы) плюс один `return: model` в конце (`l2_mad_is_return`, уже есть). Тело
   ходит как обычно (`l2_rw_stmts`, без изменений); ТОЛЬКО точка возврата эмитит не `[ret, V]` с
   числовым V, а `[ret, [prim, rec_for_this_host, 0, at_capture_0, at_capture_1, …]]` — PRIM-шаг,
   операнды которого — AT-чтения захваченных имён В ТЕКУЩЕЙ walked-активации (тот же AT-механизм,
   которым уже читаются обычные own-поля/формалы в любом другом walkable методе).
3. **T7 (`l2_pap_on`, явный `merge(...)`) вероятно тот же путь, но не проверено отдельно** —
   §5 уже отметил, что `l2_mad_emit`'s `l2_t7_host_site`/`l2_t7_write` — ОТДЕЛЬНАЯ ветка эмиссии
   для T7-хозяев, не проверено, использует ли она ТУ ЖЕ конструкцию узла или другую; если другую
   — этот план закрывает только T6/T6b (`makeAdder`), T7 (`wrap`) остаётся отдельной задачей той
   же формы, не автоматически тем же изменением.
4. **Не проверено сборкой ни на шаг** — это план, не патч. Наименьший риск: тела «ordinary
   statements» хозяина сегодня эмитятся через `l2_emit_stmts` (нативный путь) внутри
   `l2_mad_host_body`, а НЕ через `l2_rw_stmts` (walk-путь) — то, что T6b доказало про них
   («operators run in order»), доказано для НАТИВНОЙ эмиссии, не для walk-эмиссии; нужен
   отдельный замер (перевести `unit_make_adder_activation.lm2`-подобный пример с телом хозяина
   под `--walk-methods` и посмотреть, проходит ли `l2_rw_stmts` те же операторы без отказа) до
   того, как п.2 можно считать более чем гипотезой.
5. **Оценка размера при таком плане:** не T6b-масштаб — одна новая функция-экстрактор в
   `l2trans.lm1` (аналог уже существующего `l2_emit_mad_call`/`l2_mad_call`, но для
   КОНСТРУИРОВАНИЯ, не вызова) плюс новая ветка `l2_rw_may`/новая ветка в `l2_rw_trailer` для
   RET-построения PRIM-шага вместо числового — величиной, сравнимой с самим `l2_emit_mad_call`
   (несколько десятков строк), не с T6b целиком. Не делал — ждёт решения координатора и,
   отдельно, замера п.4.
