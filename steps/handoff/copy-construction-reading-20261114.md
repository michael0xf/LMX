# Копия объявления, удержанная F и новое применение fn

2026-11-14, Codex. Уточнение чтения плана после среза381, во время приёмки382.
Это исправление критерия реализации, не новая норма и не результат выполнения нового copy-кода.

## Основания

- [Автор, 2026-11-09](../../LMX_blog/2026-11-09.md): в графе хранится объявление fn,
  именованная функция создаётся при обходе в namespace; специального merge функций нет.
- [Спецификация ядра §3.4](../../docs/spec/kernel-implementation.ru.md): результат применения fn
  получает новую F и собственную новую data. Копия F через merge — обычная Structure;
  функцию из неё делает ресивер. Удержанная ссылкой F остаётся значением графа.
- [Спецификация ядра §6.4](../../docs/spec/kernel-implementation.ru.md): копия не держит привязок
  другого обхода; новый обход строит таблицы по достигнутому графу. `fn: g merge(f1)` — новое объявление.
- [Композиция](../../docs/spec/LMX_semantics.ru.md#composition): одна карта сохраняет внутренние
  ссылки копируемых значений. Вложенное вызываемое копируется как Structure по общему правилу.

## Различие значений

Написанный raw Frame fn содержит свои аргументы. Созданная из него F живёт в таблицах
текущего обхода, если приложение не сохранило на неё явную ссылку графа. Из копирования
scope и raw Frame не следует копирование текущей F из исходного Space.
Поэтому новое имя скопированного raw объявления готовится общим механизмом из его
скопированных аргументов. Подмена этих аргументов текущими частями исходной F не разрешена.

Если сама F — операнд или достижимая цель ссылки графа, копируются её текущие части,
собственная data и алиасы через одну карту. Результат остаётся обычной Structure.
Следующее явное применение fn — отдельное действие общего конструктора: оно создаёт
новую F и новую own data. Карта предыдущего merge не отменяет это новое создание.

В текущем алгоритме merge корни операндов уже отображаются в обычный корень результата.
Нельзя заменять такой map[sourceF] функцией, переносить чужие Space rows, переподчинять
скопированную data или добавлять специальный путь восстановления FN-role.

## Исправленная приёмка

1. Скопировать scope с raw fn, дойти до скопированного объявления и получить новый binding
   из его скопированных аргументов, с правильными scope/source/parent и без чужих таблиц.
2. Прогреть leaf до count3; `merge(leaf)` обязан сохранить count3 как обычное структурное
   значение. Явное `fn: clone descriptor` создаёт отдельную own data: clone() даёт4,
   исходная count остаётся3. Изменение descriptor после создания clone не меняет её own data.
3. Явная ссылка на удержанную F внутри копируемого графа ведёт к копии её текущих частей;
   проверить общий map, внутренние алиасы и отсутствие ссылки на изменяемый исходный граф.
4. Независимый следующий обход восстанавливает свои таблицы из графа, без привязок прошлого обхода.

Прежнее требование «merge(scope) само переносит текущую own data namespace-F, source3 → copied4»
было выводом исполнителя, не следствием перечисленных норм. Оно отозвано. Ожидание3 → 4
сохранено для явного создания функции из текущего структурного значения F.
Срез382 этих классов не закрывал. Ограниченная [приёмка383](../witnesses/m11-copy-bindings-20261114/notes.md)
проверила raw bindings, held state/aliases, явное новое создание и независимые обходы в трёх режимах.
Общий M11, внешние/вычисленные CodeBody и native совместимой копии M14 этим не завершены.
