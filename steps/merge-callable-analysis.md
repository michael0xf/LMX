# Анализ варианта автора (2026-09-24): `struct\x` = последний occurrence и child 0 = массив нативных методов, исполняемых по порядку

Просьба автора (дословно в `LMX_blog/2026-09-24.md`): «надо поменять struct\overrided вызов не на struct\[0]overrided а на struct\[lastIndex]overrided; 2) в поле 0 callable структуры записывать массив где по порядку будут идти адреса нативных смерженных методов чтобы они выполнялись один за другим. Проанализируй этот вариант на противоречия (особенно как работает merge)».

## Что делает merge сегодня (измерено)

- `lmx_merge_owned.h.lm1` :12–:16: результат — одно плоское дерево: слоты = копии прямых детей каждого операнда по порядку (операнд за операндом, ребёнок за ребёнком), затем поля тела; корни операндов не видны. METHOD-дескрипторы — терминалы, разделяемые по адресу (`LmxMethod {addr, sig}`, `lmx.h.lm1` :179–:182); «метод, пришедший копированием, вызывается через результат» (:18).
- `LmxCallable {method, header}` (:192–:195) в child 0 вхождения; `header` — ссылка на дерево дескриптора; копии разделяют дескриптор.
- Нативный код метода адресует свои поля **фиксированными индексами** относительно `self` (`lmx_arena_ref_cell(self, 1U + k)` — запечено в сгенерированном C по раскладке ИСХОДНОГО владельца).
- Транслятор при `R: merge: A B` знает формы операндов статически и адресует поля результата как `bat + aj` (смещение операнда + индекс).

## Следствие 1: `struct\x` = `[lastIndex]x`

1. **Совместимо с уже действующими правилами имён.** Внутри метода присваивание разрешается «последним объявлением» (`l2_own_find_last`, затенение); Q19.2: в граф публикуется последнее состояние. Правило «неуточнённый путь = `[0]`» (план §4 :293, прежнее решение) — единственное место, где побеждает первый; переход на последний устраняет это расхождение. `[N]` с явным индексом остаётся лексическим (0 = первый). Число occurrence известно на трансляции (формы операндов статические) — `lastIndex` вычислим.
2. **Противоречие с admission/implements при append.** Если модель A — первый операнд, её поля идут первыми; `implements(merged, A)` (порт из `lingvamyxa_prev`: предикат по именам/позициям полей модели) сверяет **слот модели** (первый `x`), а программа читает **последний `x`** (переопределение). Проверенное и используемое значения — разные ячейки. Устранимо только если merge пишет переопределение **в слот модели** (вариант А в `q21.md`) — тогда «последний» и «слот модели» совпадают, а дубликата нет.
3. **Методы модели не видят переопределения.** Тело метода A обращается к своему `x` по индексу в области A; при append переопределение B лежит в области B — метод A продолжает работать со старым значением, внешний путь читает новое. Это и есть «merge создаёт то, чего раньше не было нативно». Опять же снимается только записью в слот модели.

## Следствие 2: child 0 = массив адресов смерженных методов, исполняемых по порядку

1. **Фиксированные индексы полей vs плоский merge — главное противоречие.** Метод операнда B скомпилирован против раскладки B (его поля — child 1..n **его** вхождения). В плоском результате поля B лежат со смещением `width(A)`. Вызов метода B с `self = merged` адресует **чужие ячейки** (области A). То же для fn-полей, скопированных из не-первого операнда, — уже сегодня (:18 «вызывается через результат») это работает только для первого операнда или для методов, не трогающих поля. Значит цепочка методов в child 0 невозможна без одного из двух: (а) **позиционно-независимая эмиссия**: каждый элемент массива в child 0 — пара `{method, base}`, а сгенерированный код адресует поля как `self + base + k` (base приходит из дескриптора при входе — новый параметр ABI или чтение child 0); (б) **неплоский merge**: корни операндов остаются детьми результата, каждый со своим child 0; «исполнить merged» = исполнить дескрипторы детей по порядку с `self` = соответствующий ребёнок. Вариант (б) противоречит контракту merge («одно плоское дерево, корни не видны») и меняет все пути `merged\x` (нужен уровень операнда). Вариант (а) — правка транслятора (все `lmx_arena_ref_cell(self, k)` → относительно base) и `LmxCallable` (массив пар вместо одной ссылки); ядро — `lmx_call0` по массиву.
2. **Результат и сигнатура цепочки.** Для именованных Structure (без аргументов и результата — Q20 = Д) последовательное исполнение определено. Для `fn`: два тела — два результата; для разных сигнатур — один вызов не может удовлетворить обе. Нужно правило: в цепочке допустимы только элементы без аргументов и без результата (как `sub`/именованная Structure), либо «результат — у последнего», а `throws:` (S1) — объединение списков по позициям. Без правила — противоречие с N2 («fn — одно выражение с одним результатом»).
3. **Переопределение поля и методы разных операндов.** При «последний побеждает» с append метод A читает A-слот, метод B — B-слот, внешний путь — B-слот: одно имя, два живых значения внутри одного экземпляра. При записи в слот модели (вариант А Q21) метод B, скомпилированный против раскладки B, ищет `x` в области B, где его теперь нет. Обе схемы ломают методы какой-то из сторон, пока адресация полей позиционная и запечена в код. Единственный согласованный вариант — (а) из п. 1: методы адресуют поля от своей base, а «переопределение» между операндами не существует на уровне слотов: у каждого операнда свои поля, `merged\x` = последний по порядку операндов (правило 1), `implements` к модели — по области модели.
4. **Q19.2 не противоречит**: каждое тело цепочки заново инициализирует объявления своей области, checkpoint публикует всё; `S\n` читает без исполнения — как и требуется.
5. **merge разделяемых дескрипторов.** Сегодня дескриптор копируется как разделяемая ссылка на неизменяемый `LmxMethod`; массив в child 0 должен строиться merge заново для результата (конкатенация массивов операндов по порядку) — новая обязанность merge (сейчас он копирует child 0 как поле, если его вообще видит), но она локальна и не противоречит контракту (дескрипторы остаются терминалами).

## Итог

- Следствие 1 само по себе непротиворечиво (согласуется с `find_last` и Q19.2), но вместе с append-merge даёт расхождение «проверенная admission ячейка ≠ читаемая» и «методы модели не видят переопределения». Согласованно оно только при **позиционно-независимых методах** (base в дескрипторе), где `merged\x` = последний операнд, а каждый метод работает в своей области.
- Следствие 2 требует **правки ABI генерируемого кода** (адресация полей от base из child 0) и **правила для результатов/сигнатур** цепочки (без аргументов и результата — как `sub`); в этой форме оно согласуется и с плоским merge, и с Q20 = Д. Без base-адресации массив методов в child 0 ломается на втором операнде.
- Рекомендация: принять оба следствия **при условии** (а) child 0 = массив `{method, base}`; (б) генерируемый код адресует поля от base; (в) в цепочке — только элементы без аргументов и результата (fn с результатом — один, последний, либо отказ); (г) `merged\x` = последний операнд, `implements` к модели — по области модели; (д) merge строит массив child 0 результата конкатенацией. Это единый механизм без «переопределения в слоте» и без name-специалов; объём — транслятор (эмиссия полей от base, ns-индексы), ядро (`LmxCallable` как массив пар, `lmx_call0` по цепочке), merge (child 0).
