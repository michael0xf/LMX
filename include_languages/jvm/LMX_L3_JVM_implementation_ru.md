# L3 на JVM: компилятор и интерпретатор

## Проект реализации с максимальным сохранением устройства C-реализации

**Версия 1.0 · 16 ноября 2026 года**

**Область работы — только L3.** Требуется перенести поведение и основные алгоритмы существующих компилятора, интерпретатора и runtime LMX на JVM. Поддержка пользовательских L2-вставок, сырых машинных адресов и C ABI не входит в этот проект.

**Компиляция должна создавать настоящие Java-методы.** Арифметика, локальные переменные, ветвления, циклы и известные вызовы переводятся в соответствующий исполняемый JVM-код. Сгенерированная обёртка, которая запускает обходчик над прежним телом, не считается реализацией компилятора.

**Указатели L3 сохраняют существующую модель.** Указатель на примитив связан с его местом хранения; указатель на элемент Array связан с дескриптором Array и индексом. JVM-перенос не вводит новую семантику указателей и не ставит задачу эмуляции `&x` и машинного стека C.

Документ задаёт архитектуру, требования к реализации и критерии приёмки. Это проект, а не отчёт о готовом JVM-ядре или его измеренной производительности.

## 1. Основания и приоритет правил

Основные источники:

- [S1] — `LMX_semantics.en(4).md`, включая решения 15–16 ноября 2026 года.
- [S2] — `LMX_grammar.en(4).md`.
- [S3] — `L2_spec_en(4).md`: устройство runtime и реализация контрактов L3. Машинные возможности L2 из него не становятся частью JVM-языка.
- [S4] — `LMX_semantics_guide.en(4).md`, как пояснение, подчинённое норме.
- Последнее решение автора о памяти: одна нетипизированная арена; запись содержит четырёхбайтовый `type` и непосредственно за ним точные байты значения либо дескриптора; начала записей выровнены на четыре байта; в `storage` находится одна служебная ссылка на запись.
- Уточнения этой задачи: только L3 на JVM; результат компиляции — Java-методы с максимально прямым исполнением.

Новая арена заменяет прежнее размещение по типизированным областям. Она не меняет смысл `@`, `sys\typeof`, присваивания, копирования, идентичности и времени жизни.

В исходной редакции имеются два редакционных противоречия. Для этого проекта применяются более поздние явно датированные правила:

| Старый фрагмент в S1 | Действующее правило для реализации |
|---|---|
| §11: отсутствие actual и default само по себе вызывает отказ вызова | Все объявленные входы optional; отсутствие значения сохраняется. `required` отдельно проверяет инициализацию. §11–12, решение 16.11 |
| §11: самостоятельная безымянная Structure в code всегда инертна | Безымянная Structure в позиции code исполняется в текущей активации. §9, решение 16.11 |

Старые описания автоматического сброса `native`, публикации локалов, `flush()`, отдельного растущего List и заголовка со встроенным VoidArray не использовать как основания JVM-архитектуры. Исходные документы этой работой не изменяются.

## 2. Что означает максимальное соответствие C-реализации

Требуется сохранить:

1. Одни правила разбора и разрешения L3.
2. Один структурный граф программы и данных.
3. Одинаковые наблюдаемые значения, порядок эффектов, отказы, результаты проверок, отношения идентичности и время жизни ссылок.
4. Ту же организацию вызовов, локальных мест, приёма аргументов, явной компиляции и границ turn.
5. Плотную арену и дескрипторы вместо обязательного Java-объекта на каждое значение или поле.
6. Прямой скомпилированный маршрут там, где C-транслятор создаёт обычные вычисления и вызовы.
7. Интерпретацию текущего допустимого L3-графа там, где скомпилированной реализации нет.

Численные значения адресов двух процессов, заголовки Java-объектов и ABI C копировать не требуется. Соответствие указателей проверяется по их целям и отношениям aliasing.

Внутренняя реализация библиотеки может пользоваться JVM, Java-библиотекой или разрешённым поставщиком операций. Это не разрешает программе L3 выполнять `c.*`, L1/L2-код или произвольные операции над машинными адресами.

## 3. Общая архитектура

~~~mermaid
flowchart TD
    S["Исходный L3"] --> P["Общий P0 и построитель"]
    P --> G["Живой граф LMX"]
    G --> W["Интерпретатор графа"]
    G --> T["Явная компиляция L3"]
    T --> R["Разрешённые операции и места"]
    R --> C["Существующая эмиссия C"]
    R --> J["Java-методы и class-файлы"]
    W --> M["Общие контракты runtime"]
    J --> M
~~~

На JVM существуют два действительно разных пути исполнения:

| Путь | Что исполняется | Как выполняются операции |
|---|---|---|
| Интерпретатор | Текущий L3-граф | Обходчик читает формы, разрешает их и выполняет |
| Скомпилированный | Сгенерированные Java-методы | JVM исполняет методы, их выражения и переходы; граф читается при необходимых явных или динамических операциях |

Разрешённое представление компилятора — временная структура его работы. Оно не заменяет язык, не является вторым постоянно поддерживаемым графом исполнения и не требуется обходчику как предварительно сохранённый план.

Для общего frontend следует переиспользовать существующие алгоритмы P0, построения и разрешения. Когда буквальное совместное использование исходников пока невозможно, соответствие двух реализаций подтверждается одинаковыми структурными результатами и общими тестами. Не создавать для JVM новую грамматику или особые правила ресиверов.

Позиции P0 сохраняют координаты исходных байтов. Переход через Java String не должен незаметно заменить их индексами UTF-16, нормализовать CRLF или изменить точные байты литералов.

Проект не требует предварительно реализовать общий транслятор произвольного L2 в JVM. Поддерживаемые алгоритмы проекта и платформенные адаптеры следует разделить по действующему порядку разработки; генерируемые Java- и class-файлы не становятся самостоятельной нормативной версией программы.

## 4. Базовая среда и организация ядра

### 4.1. Среда

Для основной реализации принять **JDK 25** как базовую проверяемую среду. Это LTS-линия; необходимые memory API и API генерации class-файлов в ней доступны без выбора экспериментальной модели Java-объектов. [J1] [J5] [J10]

Первый компилятор использует цепочку:

**разрешённый L3 → Java source → javac → class-файлы → загрузка и регистрация.**

Прямая генерация class-файлов допускается позднее из того же представления компилятора. Она не должна менять семантику или становиться условием первой рабочей реализации.

### 4.2. Процедурное ядро

Ядро организовать преимущественно как классы со статическими методами:

| Область | Ответственность |
|---|---|
| `ArenaOps` | Блоки, записи, выделение, владение и освобождение |
| `ValueOps` | Примитивы, ссылки, дескрипторы, плотные массивы |
| `GraphOps` | Копирование, merge, пути и структурные операции |
| `CallOps` | Общий binding, admission и выбор исполнения |
| `Walker` | Действительное исполнение L3-графа |
| `MessageOps` | Turn, почта, дочерние Thread и передача владения |
| `JvmCompiler` | Эмиссия, компиляция и подготовка entries |

Это разбиение исходников, а не требование создавать экземпляры обработчиков. Известный вызов статического метода другого класса использует тот же `invokestatic`. Отдельного виртуального диспетчера из-за границы класса нет. [J2]

Один большой класс допустим для первого прототипа. Его размер сам по себе не даёт преимущества; ограничения class-файла требуют возможности последующего разделения.

### 4.3. Статические поля и состояние

Константы, таблицы неизменяемых свойств типов, подготовленные accessors и layouts хранить в `static final`. Для VarHandle это соответствует рекомендациям документации. [J6]

Изменяемое состояние относится к конкретному runtime, Message, arena или активации. Его можно хранить в небольшом числе служебных объектов и примитивных массивов. Это не объект на каждое значение LMX.

Для одного экземпляра runtime разрешён статический корень его состояния. Он не должен скрыто объединять арены разных Message или превращать локалы всех вызовов в общие переменные. Статическое поле существует в одном экземпляре для данного загруженного класса. [J3]

Статические методы могут явно принимать `RuntimeState`, идентификатор Message и нужные L3-ссылки. Это сохраняет процедурную организацию и допускает несколько независимых runtime.

## 5. Представление значений в арене

### 5.1. Основная запись

Формат одной записи:

| Часть | Размещение |
|---|---|
| `type` | Первые 4 байта |
| Payload | Сразу после `type`, без предварительного выравнивающего промежутка |
| Концевое заполнение | Только сколько нужно для начала следующей записи на позиции, кратной 4 |

Размер записи:

~~~text
recordBytes = alignUp(4 + payloadBytes(type, value), 4)
~~~

`type` обозначает физический вид значения и необходимый способ его чтения. Он не подменяет `implements` и не является пользовательским классом для каждой модели Structure.

Внутренний поток смешанный: следующие друг за другом поля разных физических видов остаются в одном потоке размещения. Не возвращаться к разнесению всех типов по разным аренам как обязательной организации.

### 5.2. Конкретный первоначальный профиль

Для первого JVM-профиля принять 64-битные служебные ссылки и 64-битные поля длины. Значение поля длины интерпретируется по его объявленному L3-типу; signed-носитель Java long сам по себе не меняет этот тип. Перед фактическим выделением и доступом проверяются допустимость размера и ограничения выбранного backend.

| Payload | Байты payload | Запись с type и округлением до 4 |
|---|---:|---:|
| Примитив размером 1–4 байта | 1–4 | 8 |
| Примитив размером 8 байт | 8 | 12 |
| Одна служебная ссылка | 8 | 12 |
| `parent, length, storage` | 24 | 28 |

Один слот `storage` занимает дополнительно одну служебную ссылку — в этом профиле 8 байт. Он не включён в размеры записей таблицы.

Фиксированный `union` с размером наибольшего варианта не используется. Короткое значение не резервирует место под полный дескриптор. Более крупные виды значений получают собственный фактический payload.

### 5.3. Дескриптор Structure и Array

Дескриптор сохраняет три поля:

~~~text
parent
length
storage
~~~

`native`, capacity, имя, требования модели и состояние исполнения не добавляются в этот заголовок. Они остаются в соответствующих служебных таблицах или обычных данных по существующему контракту. [S3, §2 и §6.1]

Дескриптор расположен непосредственно в потоке записей. Для чтения `length` достаточно прочитать это поле по известному смещению. Не требуется создавать Java-объект `Lmx`, копировать весь дескриптор или выполнять его десериализацию.

Числовой `Array<T>` сохраняет отдельный плотный блок самих T. Метку записи перед каждым элементом такого массива не добавлять. Массив ссылок хранит служебные ссылки.

Строковые значения сохраняют действующее представление точной длины в char Array, без добавления завершающего NUL. Java String допустим как служебное средство на границе API, но не как молчаливая подмена представления, длины и индексации строки L3.

### 5.4. Служебные данные

Вне заголовка остаются как минимум:

- канонические имена и таблица «ссылка на вхождение → имя»;
- capacity и сведения об allocation;
- владение блоками и ресурсами;
- call/native entries;
- данные сборщика, необходимые связи и корни;
- временные соответствия конкретного приёма или обхода.

Сведения о размере выделения нужны независимо от текущего `length`. Из прямой записи в поле длины не следует, что был выделен новый backing.

Эти таблицы не должны превращаться в один огромный объект-дескриптор на каждое поле. Использовать компактные записи, примитивные массивы и отдельные таблицы только там, где сведения действительно требуются.

## 6. Служебные ссылки и существующие указатели L3

### 6.1. Три разных сущности

Следует различать в представлении компилятора и runtime:

1. **Служебную ссылку на запись** — например, значение слота `storage`.
2. **Указатель L3 на место** — примитив, ссылочную ячейку или доступное поле.
3. **Указатель L3 на элемент Array** — ссылка на дескриптор Array и индекс.

Одинаковый JVM-носитель `long` не делает эти сущности взаимозаменяемыми. Их операции следуют контрактам L3, а не произвольным операциям над числом.

Для служебных ссылок можно использовать кодирование блока и смещения либо компактный каталог записей. Ноль резервируется для null там, где это соответствует существующему представлению. Отсутствие значения не приравнивается к присутствующей нулевой ссылке.

Точное разбиение битов не является нормой языка. Ограниченный формат `32/32` допустим как исследуемый вариант, но его пределы должны быть явными. Нельзя незаметно ограничить всю модель Array размером одного Java-массива.

### 6.2. Указатели L3 не проектируются заново

Перенести уже существующие primitive-pointer и Array-element-pointer механизмы:

- повторное получение ссылки на то же место сохраняет его идентичность;
- запись через указатель видна при чтении этого же места;
- указатель на элемент следует за текущим backing того же Array через его дескриптор;
- изменение `storage` Array не требует обходить и исправлять все element pointers;
- рекурсивные активации имеют свои локальные места;
- получение ссылки само по себе не меняет время жизни цели.

Не добавлять специальные Java-правила копирования или автоматического продления lifetime. Отдельный объект `Pointer` на каждую операцию `@` не обязателен: представление определяется уже существующим видом ссылки.

### 6.3. Внутренние места дескриптора

`sys\descriptor` сохраняет обращение к живым полям исходного дескриптора. Запись через полученное место изменяет исходное поле; замена ссылки в структуре результата меняет только эту ссылку.

Начало записи с `type` и место внутри её payload — разные служебные позиции. Нельзя считать, что тип произвольного указателя всегда лежит в четырёх байтах перед его целью. Для Array-element pointer и указателя на поле дескриптора вид места уже определяется их общим механизмом.

### 6.4. typeof

`sys\typeof` получает ссылку и возвращает прежний код физического типа. Для обычной служебной ссылки новый in-band tag обеспечивает быстрый путь. Для указателя на элемент или внутреннее поле используется его вид и владеющее описание.

Сохранить поведение для null и ссылки вне допустимой арены, установленное нормой. Числовые коды не объявлять стабильным переносимым ABI: они принадлежат инвентарю типов конкретного runtime.

Метка типа не заменяет проверки требований и не превращает старое соответствие полей в доказательство типа произвольно подменённой записи.

## 7. Реализация памяти средствами JVM

### 7.1. Два backend одного формата

Реализовать общий низкоуровневый контракт чтения и записи с двумя носителями:

| Носитель | Назначение |
|---|---|
| Блоки `byte[]` | Первый проверяемый backend, отладка, сопоставление формата |
| `MemorySegment` с явно управляемой памятью | Крупные непрерывные payload, исследование скорости и управляемого освобождения |

Код ядра в обоих случаях исполняется JVM. Внешнее размещение памяти не означает перевод ядра обратно в C.

На byte[] возможны `byteArrayViewVarHandle` либо представление блока через `MemorySegment.ofArray`. Это варианты accessors, а не обязательная цепочка из нескольких посредников. [J4] [J5]

Выбор носителя делать при создании runtime или блока. Не вводить новый виртуальный `MemoryBackend.read` на каждое поле, если тот же результат достигается прямым подготовленным accessor.

### 7.2. Корректное выравнивание

Выравнивание начала записи на 4 не выравнивает последующий восьмибайтовый payload на 8.

Для общего FFM-доступа принять layouts:

- `JAVA_INT_UNALIGNED`;
- `JAVA_LONG_UNALIGNED`;
- `JAVA_DOUBLE_UNALIGNED` и соответствующие остальные виды.

Их alignment равен 1; это разрешение доступа, а не требование размещать записи с шагом 1. Логическое выравнивание записей остаётся равным 4.

У `MemorySegment.ofArray(byte[])` гарантируемый API alignment также равен 1. Поэтому для него нельзя безоговорочно применять обычный `JAVA_INT` даже на нулевом смещении. [J5] [J7]

Специализированный accessor для внешнего блока может использовать более сильную гарантию, если allocation и смещения ей действительно удовлетворяют. Он не меняет общий формат данных.

### 7.3. Минимальный пример доступа к дескриптору

Ниже — пример для выбранного 64-битного внутреннего профиля. `recordOffset` означает смещение внутри уже выбранного блока, а не произвольную закодированную L3-ссылку.

~~~java
import java.lang.foreign.MemorySegment;
import java.lang.foreign.ValueLayout;
import java.nio.ByteOrder;

final class DescriptorAccess {
    private DescriptorAccess() {}

    static final ValueLayout.OfInt I32 =
        ValueLayout.JAVA_INT_UNALIGNED
            .withOrder(ByteOrder.nativeOrder());

    static final ValueLayout.OfLong I64 =
        ValueLayout.JAVA_LONG_UNALIGNED
            .withOrder(ByteOrder.nativeOrder());

    static final long TYPE_BYTES = 4;
    static final long PARENT_IN_PAYLOAD = 0;
    static final long LENGTH_IN_PAYLOAD = 8;
    static final long STORAGE_IN_PAYLOAD = 16;

    static int type(MemorySegment block, long recordOffset) {
        return block.get(I32, recordOffset);
    }

    static long length(MemorySegment block, long recordOffset) {
        return block.get(
            I64, recordOffset + TYPE_BYTES + LENGTH_IN_PAYLOAD
        );
    }

    static void writeLengthField(
            MemorySegment block, long recordOffset, long length) {
        block.set(
            I64, recordOffset + TYPE_BYTES + LENGTH_IN_PAYLOAD, length
        );
    }

    static long storage(MemorySegment block, long recordOffset) {
        return block.get(
            I64, recordOffset + TYPE_BYTES + STORAGE_IN_PAYLOAD
        );
    }
}
~~~

`writeLengthField` показывает запись самого поля. Координированное изменение размера выполняет `sys\resize`; простой store не выделяет backing.

`MemoryLayout.structLayout` можно использовать для проверки layout и построения accessors. Он описывает байтовые поля, не создавая объект класса для каждого дескриптора. Подготовка layout выполняется один раз, а не при каждом чтении. [J6]

### 7.4. Горячий проход

Где позволяет семантика, перед последовательным циклом один раз получить блок, базовое смещение и границы, после чего читать поля по смещениям. Не создавать slice, view или объект-дескриптор на каждый шаг.

При переходе по произвольной ссылке разрешение нового блока может потребоваться. Этот расход нужно учитывать, а не объявлять бесплатным.

Нельзя сохранять старые `length/storage` через операцию, которая вправе изменить соответствующий Array, и затем использовать их как текущие. Вынос доступа из цикла допустим только при сохранении наблюдаемой семантики.

### 7.5. Порядок байтов и размеры

Для первоначального runtime-образа использовать один явно заданный `FORMAT_ORDER`, равный native order выбранной платформы, как в примере. Переносимая сериализация преобразует этот образ в свой заявленный формат.

Java-массив ограничен длиной типа int. Большой owning Array должен получать подходящий непрерывный allocation, например MemorySegment с длинными смещениями. Не заменять его незаметно массивом строк или цепочкой отдельных LMX Arrays. [J5] [J8]

Большие размеры проверяются до умножения и выделения; переполнение служебной арифметики не должно превращать большой запрос в короткий allocation.

## 8. Структурные операции, массивы и допуск

### 8.1. Изменение состава Structure

Изменение числа полей реализуется изменением `length/storage` стабильного дескриптора. При необходимости выделяется новый backing и переносится массив служебных ссылок. Java-класс при этом не изменяется.

Сами целевые значения не обязаны перемещаться вслед за backing. Ссылки на них сохраняют цели по существующим правилам.

`Structure` и `Array<@>` используют общий механизм. Отличие названия категории не является причиной отказа в операции, которую норма разрешает обоим.

### 8.2. Замена слота

`S[i] := p` заменяет ссылку в слоте. Она не наследует от старого содержимого имя, тип или требование и не вызывает отменённый `slot_prepare/slot_admit`.

Последующее структурное чтение работает с текущим содержимым. Прежнее соответствие индексов не даёт права читать новый target как старый физический тип.

### 8.3. Числовые Arrays

Прямоугольный N-мерный Array остаётся одним плотным payload. Размерности и strides берутся из описания операции, а не восстанавливаются по одному полю общей длины.

L3 вычисляет конечный линейный индекс и делает одну смысловую проверку:

~~~text
0 <= linearIndex < currentLength
~~~

Не вводить проверки каждого измерения, меняющие правило языка. Например, для прямоугольника [2,3] обращения [0,3] и [1,0] имеют один линейный индекс. Вычисление индекса не должно переполнением вернуть ошибочный индекс в допустимый диапазон. [S1, §17]

Проверки bounds самого JVM API могут оставаться дополнительными техническими проверками. Они не должны заменять L3-отказ исключением с произвольным Java-именем.

### 8.4. implements и test

Оставить один механизм приёма:

1. Проверка используемого интерфейса конкретного Consumer.
2. Выполнение предписанных `test` при фактическом admission.
3. Сохранение нужного соответствия мест на время соответствующего приёма или обхода.

Построитель не исполняет пользовательские `test`. Уже сделанная первая стадия не повторяется без основания. Проверка физического tag не является повторным `implements`.

Соответствие индексов устраняет повторный поиск имён там, где оно применимо. Не создавать бессрочный глобальный кэш соответствий, требующий перезаписи при каждой мутации.

## 9. Интерпретатор JVM

Интерпретатор исполняет **живой L3-граф**, построенный общим frontend или изменённый программой. Он не является интерпретатором Java, L1/L2, C или исходного текста LMX.

Основной цикл сохраняет алгоритмы C-обходчика:

- текущие data/code и контекст активации;
- порядок элементов и границы областей;
- общий выбор головы и потребление аргументов;
- обычные пути вычисления, приёма, вызова и выхода;
- управляющий стек и cleanup.

Начальная идентификация головы следует существующей канонизации имён. Метка физического типа записи не становится новым языковым opcode. После разрешения допускается обычное внутреннее ветвление на реализованную операцию.

Служебный стек обходчика хранить компактно и переиспользовать. Отдельный Java-объект для каждого шага, аргумента или поля не требуется.

Все формы вызова проходят один interpreter worker. Не делать отдельные resolver и движки для метода, обычной Structure, `call`, `fncall`, конвертера и `test`.

При этом сохранить различие выбора частей: обычный `s(actuals)` выбирает части callable по своему контракту; явный `call(D s)` исполняет всю переданную Structure `s`, включая случай callable; `call(D s\code)` явно выбирает только её тело. Явный launch не должен автоматически извлекать `s\code` или `s\data`. Это разные входы одного worker, а не разные движки. [S1, §11]

Подготовка не должна исполнять тело. P0 сохраняет анонимные контейнеры, включая единственный контейнер; семантическое раскрытие whole-argument Structure происходит при binding. Безымянный блок в code исполняется по актуальному правилу в текущей активации.

## 10. Вызовы, namespace и локальные места

### 10.1. Общий контракт

Для интерпретатора и компилятора сохраняется общий смысл:

**выбрать вызываемое значение → проверить форму подачи → вычислить и принять actuals по порядку → подготовить независимые локальные места → исполнить тело → передать результат.**

Неверное имя actual или повторная подача обнаруживаются до побочных эффектов аргументов. После выбора callable аргументы вычисляются в написанном порядке, каждый принимается до вычисления следующего. Отказ прекращает дальнейшее вычисление.

Все объявленные data-входы optional. `required` проверяет инициализацию в предписанном месте; отсутствие свободного динамического входа остаётся отдельным случаем существующей нормы.

### 10.2. Инициализация и независимость

На входе нет прохода исполнения defaults. Поданный actual подавляет соответствующий initializer; неиспользованное вычисляемое поле не исполняется заранее.

Namespace удерживает выбранное значение или вычисляемое описание с момента входа, даже если источник позже заменён до первого чтения. Это не означает глубокое копирование всех объектов.

- `x := value` меняет локальное место.
- `data\x := value` меняет исходный граф.
- Явно переданная ссылка сохраняет цель.
- Повторно достигнутое объявление сохраняет вычисление RHS и присваивание по действующей норме.
- Нового скрытого кэширования вычисляемых полей не вводить.

### 10.3. Локалы в скомпилированном коде

Если L3-контракт допускает обычное значение без наблюдаемой ссылки на его место, использовать JVM local соответствующего типа.

Если место наблюдается через существующий указатель L3, использовать его каноническое хранилище. Чтение имени, присваивание и чтение/запись через ссылку должны видеть одно место. Нельзя завести независимую пару «Java local + копия для указателя» и синхронизировать её через вызовы.

Это требование единства существующего места L3, а не новый механизм сырых адресов C. Представление может использовать компактный участок данных активации или уже имеющуюся ячейку. Отдельный Java Frame или объект на каждую переменную не предписывается.

`uninit:T` сохраняет значение существующего вида объявления. Оно не превращается в общий флаг «никогда ещё не записывали»; присваивание, включая первое, не перенаправляет внутренний указатель и сохраняет каноническую ячейку.

### 10.4. Видимость и результаты

Переменные и const имеют последовательную видимость; имена Structures и callables — установленную двустороннюю. `private` исключает динамический источник, но не запрещает явные пути и обычный лексический доступ.

Для свободного входа сохраняется порядок выбора: ближайшее подходящее локальное связывание вызывающей активации, далее доступный унаследованный динамический контекст, затем лексический fallback вызываемого выражения. Неподанный объявленный формал не заполняется этим поиском: он сохраняет своё выбранное описание/default либо отсутствие значения. Метод, который лишь передаёт контекст дальше, не должен заранее читать чужой свободный вход и создавать для него локальное значение. Не вычислять транзитивное замыкание требований всей цепочки вызовов. Например, свободный x при caller-local 25 и lexical fallback 10 получает 25; явный путь к лексическому полю продолжает читать 10. [S1, §12]

Не возвращать автодополнение source data из тела. Body locals принадлежат активации.

Многопольный результат записывается в предусмотренные результатные места. `return` завершает передачу, не вводя обязательное создание Java-кортежа или копирование всей Structure.

Для группового присваивания сначала вычислить все правые значения, затем начать записи; несовпадение числа мест и значений обнаружить до первой записи. В `(a b c) := c, a, b` должны использоваться исходные три значения. Передача результатных мест напрямую в compiled-метод допускается только при сохранении этого порядка и отношений aliasing. Нужные временные значения можно хранить в обычных JVM locals, без обязательного tuple-объекта. [S1, §9]

## 11. Компилятор: настоящие Java-методы

### 11.1. Обязательное отличие от интерпретации

Для переведённого участка компилятор заранее выполняет работу, которую обходчик повторяет при исполнении: разрешает известные операции и места, строит порядок вычислений, выбирает конкретные операции и связи.

Результат — JVM-методы. Внутренний выбор JVM между исполнением bytecode и JIT-компиляцией этих методов не является обходом исходного L3-графа и не меняет это разделение.

Корень файла и обычная исполняемая Structure компилируются по тем же общим правилам, что и тела методов. Не требовать искусственного fn или пользовательского main. Технический Java main принадлежит launcher; значение запуска корня и bare-return сохраняют действующий L3-контракт.

При известном контракте генерировать:

| L3-операция | Скомпилированный путь |
|---|---|
| Простая скалярная арифметика | Обычные типизированные Java-выражения |
| Ветвление | `if`, `switch` или соответствующие bytecode-переходы |
| Цикл | Обычный Java-цикл с локальными переменными |
| Известный вызов | Прямой вызов статического Java-метода |
| Известное чтение поля графа | Подготовленное обращение к нужному месту/слоту |
| Работа с указателем L3 | Операции существующего вида ссылки |
| Динамически выбранный callable | Динамический выбор только в этой точке |
| Созданное во время исполнения тело без compiled entry | Общий обходчик L3 |

Нельзя называть полной компиляцией замену каждого узла на `executeNode(nodeId)`, `evalOpcode(op)` или вызов обходчика. Нельзя оборачивать всё тело в один generated-метод, который только передаёт граф интерпретатору.

### 11.2. Пример результата lowering

Для разрешённого тела с известными int32-операциями, двумя параметрами и int32-результатом ожидается код такого вида:

~~~java
final class Unit_A {
    static int add(int x, int y) {
        return x + y;
    }

    static int sumTo(int n) {
        int result = 0;
        for (int i = 0; i < n; i++) {
            result = add(result, i);
        }
        return result;
    }
}
~~~

Пример показывает форму кода; выбранные операции должны соответствовать числовому профилю L3. Нужные проверки диапазона или особая операция профиля не исчезают ради буквального использования `+`.

В таком фрагменте нет графового диспетчера на каждое сложение, условие и вызов. Если тело действительно обращается к изменяемому графу, соответствующий accessor остаётся в Java-методе ровно для этого обращения.

### 11.3. Представление перед эмиссией

Общее разрешённое представление должно содержать:

- типы значений и виды мест L3;
- конкретные числовые операции и явные преобразования;
- прямые и динамические calls;
- порядок эффектов и проверок;
- области видимости и lifetime мест;
- операции графа и ссылки на нужные соответствия;
- control flow и cleanup.

Не переводить C-текст в Java поиском и заменой. Не вводить отдельное семантическое разрешение JVM после уже выполненного общего разрешения.

Статический вывод используется настолько, насколько его подтверждают программа, текущая единица компиляции и проверенные контракты. Он не даёт права считать произвольный изменяемый слот навсегда имеющим прежнее содержимое.

### 11.4. Сигнатуры

Сигнатура метода выводится из конкретной подачи, результата и действительно нужных скрытых входов. Один L3-code может иметь несколько вариантов для разных actual-наборов.

Не создавать обязательный `Object[]` для каждого вызова. Примитивы передаются примитивами, ссылки L3 — выбранным служебным представлением. Не упаковывать обычные числа в `Integer` или `Double` только для общего интерфейса.

При известном compiled→compiled вызове не нужны call-table lookup, графовый кадр и универсальный trampoline только ради организации вызова. Admission, result и прочие действия остаются там, где их требует L3; отсутствие общего dispatcher не отменяет их.

При действительно динамическом вызове допустима таблица variants и подготовленный типизированный `MethodHandle`. Подготовка entry происходит при его регистрации; преобразование всего к `Object...` не является обязательным ABI.

### 11.5. Граница с обходчиком

Выбор compiled entry или обходчика делается по существующему механизму вызова. При отсутствии подходящего compiled entry допустимый L3 исполняется общим worker.

Не допускается «попробовать выполнить Java, поймать любой сбой и повторить тело обходчиком»: выполненные эффекты тогда повторятся. Ошибка backend, ошибка JVM и отказ языка различаются.

### 11.6. Компиляция yield и возобновления

Приостанавливаемые тела также компилируются в Java-методы. Для них lowering явно сохраняет позицию продолжения, живые локальные места, выбранные входы и незавершённые cleanup в представлении существующей L3-continuation.

Вход возобновления выбирает соответствующий скомпилированный участок по сохранённому состоянию. Внутри участка остаются обычные Java-выражения, циклы и прямые calls. Выбор точки возобновления не превращается в диспетчер каждого оператора графа.

На `yield` нельзя заново выполнять entry binding, defaults и уже произошедшие эффекты; простой Java-return без сохранённого состояния не реализует приостановку. Новый caller `next` не подменяет входы producer своим контекстом. Само приостановление не является окончательным выходом через все finally: cleanup выполняются по соответствующему переходу L3. Неприостанавливаемые методы сохраняют обычный прямой маршрут и не получают универсальную state machine.

## 12. Создание, загрузка и обновление Java-кода

### 12.1. Первая реализация

Использовать `javax.tools.JavaCompiler` с управляемыми compilation units, диагностикой и file manager. Сохранять исходный Java по запросу для сопоставления и отладки. Компиляционная среда должна содержать `jdk.compiler`; отсутствие compiler tool обнаруживается до установки результата. [J9] [J11]

Скомпилированный код загрузить, проверить его ожидаемые entries и сигнатуры и только затем зарегистрировать успешную единицу. Ошибка не устанавливает частично готовый набор.

Загрузка служебного класса и его `<clinit>` не должны запускать пользовательские initializers L3. В них допустима подготовка констант и служебных bindings, а не скрытое исполнение программы.

### 12.2. Повторная компиляция

Для нового результата создавать новую единицу классов с отдельной идентичностью загрузки либо уникальными именами. Общие runtime-типы остаются в общем загрузчике. Не дублировать `RuntimeState` и остальные типы ABI в каждом новом class loader. Идентичность Java-класса включает загрузчик. [J12]

Вызываемые через эту границу методы и типы runtime должны быть доступны сгенерированным классам по правилам JVM. Совпадение имени package само по себе не делает package-private helper доступным из другого загрузчика. Общий прямой API следует предоставить явно; внутренние helpers единицы могут оставаться закрытыми.

Обновление не основывается на изменении полей существующего Java-класса и не требует Enhanced HotSwap.

Сохранить норму явной компиляции:

- запись в граф не обнуляет compiled entry;
- нет dirty, графовых версий и обратных зависимостей для автоматического обновления кода;
- нет сканирования или хеширования графа на каждом endturn;
- перекомпиляция B не перепривязывает старый прямой A→B;
- изменение этой прямой цепочки требует явной компиляции соответствующей общей единицы;
- после успешной компиляции и endturn следующий вход использует подготовленное обновление.

Идентификатор готового артефакта допустим для хранения и загрузки. Он не является счётчиком мутаций каждой Structure.

### 12.3. Время жизни старого кода

Старые активные методы и их finally должны завершиться на своём коде. Таблицы вызовов и активные исполнения удерживают необходимые артефакты.

Не обещать мгновенную принудительную выгрузку class loader. Возможность её выполнения зависит от достижимости; логическое снятие binding и физическое освобождение JVM-класса — разные события. [J13]

### 12.4. Инструментальный интерфейс

В JVM-профиле операция явной компиляции устанавливает JVM-entry с прежними правилами успеха, отказа и turn. Форма артефакта обозначается явно: Java source, class-файлы и сведения о runtime ABI.

Не называть Java-текст L1. Если существующий публичный `sys\translate` обещает именно L1, его результат нельзя молча заменить строкой Java. Для этого проекта Java-эмиссия доступна через интерфейс инструмента JVM-компиляции; изменение публичного результата `sys\translate` не входит в перенос.

## 13. Числовые операции и поставщики

L3 не сводится к фиксированному списку Java-примитивов. Доступные конструкторы, операции, conversions и контексты сохраняют нормы языка.

| Вид | Требование к JVM-реализации |
|---|---|
| Поддержанный целый фиксированной ширины | Точная ширина и знаковость; корректные сравнения, деление, расширения и сужения |
| Поддержанный binary32/binary64 | Операции соответствующего профиля, включая нужное обращение с NaN, signed zero и округлением |
| `bigint` | Совпадение целочисленного контракта |
| `real` | Заданная точность, округление, статусы и traps |
| `decimal` | Заданные exponent limits, precision и quantization |
| Числовой Array | Те же скалярные операции и контексты, без отдельной арифметической семантики |

Java `char` не является автоматической заменой байтового char LMX; Java `long` не назначается всем типам с именем long без проверки профиля. Присутствующие в L3 машинные числовые виды должны совпадать с заявленным профилем C-референса.

Не подменять `real` произвольным `double` или `decimal` любым применением BigDecimal без сверки контрактов. Если библиотека Java подходит, использовать её за тем же L3-интерфейсом.

Числовой provider может быть JVM-реализацией или внутренним адаптером существующей библиотеки. Программа по-прежнему вызывает L3-операцию с описанными результатами и отказами; это не поддержка пользовательских C-вставок.

Числовые контексты не превращать в скрытые общие static-переменные. Они принадлежат явным данным либо фиксированной конфигурации профиля. Известный provider и тип позволяют генерировать прямой вызов без выбора общего провайдера на каждом сложении.

При сравнении с C проверять определённые случаи выбранного профиля. Различия Java и C в переполнении, сдвигах и преобразованиях не скрывать за одинаковыми написаниями операторов. [S1, §19] [J14]

## 14. Копирование, merge и размещение

Копирование и merge используют одну карту `sourceRef → destinationRef`. Соответствие создаётся до рекурсивного обхода исходящих ссылок, чтобы сохранить циклы и разделяемые цели.

Первый operand определяет порядок модельных слотов. Замены и новые поля размещаются по существующим правилам admission и композиции; исходные операнды не меняются.

Копируемые записи выделять последовательным потоком в порядке выбранного обхода. Это сохраняет локальность, ради которой принят новый формат арены.

Переписывать только ссылочные позиции, известные по виду записи и payload. Не сканировать все восьмибайтовые слова как потенциальные ссылки: числовые значения могут иметь те же биты.

Разрешённые `independent: immutable` ветви сохраняются только по действующему контракту владельца. Перенос их reference не означает создание копии или смену parent.

Merge не компилирует тело автоматически и не устанавливает новый call-table binding. Применимая готовая реализация повторно используется только при выполнении существующих условий, а не по внешнему сходству тел.

## 15. Владение, сборка и внешние Java-ссылки

### 15.1. Два уровня управления памятью

JVM управляет Java-объектами блоков и служебных таблиц. Она не видит ссылочные рёбра LMX, записанные как числа внутри буферов.

Сохранить собственные правила владения и достижимости LMX. Допустимый простой режим без внутренней GC удерживает данные до освобождения арены. Полный режим использует существующие корни, виды ссылок и зависимости admission.

Все блоки, на которые ссылается живой LMX-граф, должны удерживаться настоящими Java-ссылками runtime. Числовой идентификатор сам по себе такого удержания не обеспечивает.

### 15.2. Корни исполнения

Ссылки L3 в активных и приостановленных исполнениях должны быть видны LMX collector в его точках сбора. Нельзя рассчитывать, что он самостоятельно прочитает все числовые Java locals.

Использовать существующую модель корней исполнения, компактный стек корней или эквивалентные данные. Это служебная работа GC; она не публикует локалы в source graph и не возвращает `flush`.

В полном режиме сохранить установленную точку сбора: один локальный проход в конце turn, после определения исхода, публикации успешных исходящих Messages либо отмены failed staging и снятия завершённых входных/временных корней. Обычные `return`, `break`, `continue`, `retry`, `redo` и пойманный `throw` не являются отдельными точками GC. Сохраняемая suspended continuation удерживает свои ссылки. Не добавлять сборку посреди произвольной операции только из-за выбора JVM. [S1, §22]

### 15.3. Внешние объекты

Настоящие Java-объекты, например provider, MethodHandle или ресурс платформы, удерживаются таблицей внешних bindings. В арене хранится их идентификатор.

Таблица обязана удерживать объект, пока он нужен по LMX-достижимости, и освобождать binding по его контракту. Одни weak references недостаточны; бессрочный список всех зарегистрированных объектов также недопустим.

### 15.4. Передача арены и FFM

LMX arena и `java.lang.foreign.Arena` не тождественны. Последняя управляет lifetime своих memory segments; первая — владением и графом LMX.

При attach передаётся удержание соответствующих blocks/regions. Старый владелец не закрывает переданную память.

Для Message, который может исполняться разными Java workers, использовать память с подходящим доступом, например `Arena.ofShared()` вместе с сериализацией LMX. `ofConfined()` пригодна только при гарантированной привязке к создавшему Java-thread. Shared scope сам по себе не делает изменяемый граф конкурентно безопасным. [J15]

Unaligned long в арене не считать автоматически атомарной межпоточной ячейкой. Служебные concurrent-счётчики и механизмы публикации размещать в подходящих Java-полях/структурах.

## 16. Message, turn и управление исполнением

Сохранить модель последовательного исполнения одного Thread identity. L3 Thread не обязан соответствовать постоянному `java.lang.Thread`.

Сохраняются:

- закрытая запись Message с `running, success, handoff_ready, graph`;
- отдельные Thread parent и children;
- staged/outbox/inbox и порядок admission;
- inseparable пара target/source_arena;
- передача владения принимающим владельцем;
- общие post/ask/answer и обычные LMX-вызовы внутри них.

Рекурсивные синхронные compiled-вызовы могут использовать обычный стек JVM. Обходчик использует свой управляющий стек. Состояние, действительно переживающее suspension по правилам L3, сохраняется явно; не обещать произвольный снимок стека JVM.

`sys\endturn()` выполняет положенные finally, не перехватывается обычным catch, не возвращается к месту вызова и не сохраняет continuation этого стека. Он сам не выставляет success/running, не публикует локалы и ничего не компилирует.

JVM-переходы через finally, throw, return, retry и yield должны воспроизводить действующий порядок L3. Внутренний сигнал endturn необходимо отделить от пользовательских отказов.

## 17. Ограничения генерации и диагностика

Генератор обязан учитывать ограничения class-файла:

- тело одного метода — меньше 65 536 байт bytecode;
- constant pool и ряд таблиц имеют 16-битные счётчики;
- параметры метода ограничены 255 JVM units, long/double занимают по две;
- большая строковая константа ограничена размером записи modified UTF-8. [J16]

Большой callable разделяется на внутренние Java-методы с сохранением его единой L3-активации, мест, cleanup и порядка эффектов. Это разделение реализации, а не создание дополнительных LMX-вызовов.

Если передача большого числа значений превышает JVM ABI, использовать компактный участок аргументов или подходящую разбивку только для этого случая. Не делать из редкого предела основание упаковывать каждый обычный вызов.

Большие графовые данные загружаются из самостоятельного ресурса/образа. Не помещать всю программу в один литерал или гигантский `<clinit>`.

Диагностика должна различать фазу P0, построение, разрешение, admission, компиляцию Java, verifier/linking и исполнение. Сохранять координаты исходных байтов LMX, имена операций и контекст ошибки. Java stack trace полезен разработчику backend, но не заменяет языковую диагностику.

L2-операция получает явную диагностику выхода за область L3-backend. Передача её обходчику или скрытая компиляция в C не считается поддержкой L3.

## 18. Сохранение и восстановление

`sys\toLmx` сериализует выбранный текущий граф. Он не восстанавливает удалённый initializer и не превращает локальный кадр в опубликованные данные.

Для Thread сохраняются предусмотренные нормой сериализуемые таблицы его арены, включая описание готовых compiled bindings.

Пакет JVM-артефакта содержит:

- образ/описание графа по действующему контракту;
- class-файлы единицы;
- runtime ABI и формат арены;
- идентификаторы entries и сигнатур;
- требования к JDK и providers;
- сведения для восстановления ссылок и диагностик.

Нельзя сохранять process-local номера Java-объектов как переносимые ссылки. При восстановлении создаются новые bindings с прежними логическими связями.

Готовый совместимый class-файл можно загрузить без повторной L3-трансляции. Сохранение JIT-машинного кода и перенос его между процессами не входят в этот проект.

## 19. Требования к производительности

### 19.1. Обязательные свойства реализации

- Нет Java-объекта на каждое обычное поле, число и шаг обхода.
- Нет fixed-size union для всех записей.
- Нет обязательного boxing в compiled сигнатурах.
- Нет обязательного graph frame и lookup на известном compiled→compiled вызове.
- Нет вызова обходчика для каждого заранее разрешённого оператора.
- Нет повторного создания layouts, VarHandles и slices в горячем доступе.
- Плотные числовые payload и последовательное размещение копируемого графа сохраняются.
- Проверки и обращения к графу выполняются там, где их требует реальная динамичность L3.
- Произвольная замена слота не маскируется недействительным предположением о прежнем типе.
- Владение и освобождение памяти не зависят от недоказанной надежды на JVM GC.

Это требования к исходной архитектуре. Возможное удаление проверок и inlining JIT рассматриваются как дополнительный результат, а не как объяснение отсутствующих алгоритмов.

### 19.2. Что измерять

Основная матрица использует одну L3-программу и четыре режима:

| | Интерпретатор | Скомпилированные методы |
|---|---|---|
| C-референс | C walker | Generated C |
| JVM | JVM walker | Generated Java/class |

Отдельно сравнить heap- и native-memory носители JVM, сохраняя одинаковые значения, графы и layout записей.

Наборы нагрузок:

1. Последовательный обход плотно размещённых смешанных записей.
2. Прямой scalar loop без графовых обращений.
3. Цикл по плотному числовому Array.
4. Доступ к изменяемым полям по построенному соответствию.
5. Известные calls и действительно динамические calls.
6. Primitive pointers и Array-element pointers.
7. Рост Array, копирование и merge с общими ссылками и циклами.
8. Message turns, handoff и почтовые очереди.
9. Долгая работа с выделениями и освобождением памяти.

Для каждого результата сообщать объём данных, число проходов, операции, checksum, выделения, объём служебных данных, режим памяти, время старта/компиляции, прогрев и установившееся исполнение. Проверять результат, чтобы измерение не превратилось в удалённую компилятором работу.

Ручная Java-программа на фиксированных классах может служить дополнительным контролем конкретной операции. Она не заменяет сравнение одной L3-семантики между C и JVM.

Не обещать заранее равенство C или конкретный коэффициент ускорения. Выигрыш плотного потока в прежнем C-эксперименте не является замером JVM.

### 19.3. Проверка действительной компиляции

Для характерных участков проверять emitted Java и class-файлы:

- в scalar loop есть обычная арифметика, локалы и переходы;
- известный call ведёт к конкретному методу;
- в нём нет вызова `Walker` или общего вычислителя операции;
- runtime helpers соответствуют действительно нужным операциям графа, admission, conversions, указателям L3, числовым providers и другим явным контрактам;
- boxing и временные allocations имеют объяснимое назначение.

Эту проверку можно выполнять штатными средствами class-file inspection. Она обязательна до обсуждения цифр быстродействия.

## 20. Этапы реализации

### Этап A. Зафиксировать соответствие

Сопоставить actual C-реализацию с действующей нормой. Имеющиеся здесь файлы не заменяют чтение исходников конкретного репозитория.

Выделить общий L3 frontend, графовые операции, вызовы и платформенные примитивы. Определить числовой профиль, формат ссылок и runtime ABI. Не переносить известные старые ошибки ради совпадения с ними.

**Результат:** карта операций, воспроизводимый C-референс и набор L3-свидетелей.

### Этап B. Минимальная арена и ссылки

Реализовать смешанные записи, descriptors, плотные Arrays, внешние метаданные и существующие виды L3-указателей. Начать с проверяемого heap backend.

**Результат:** создание, чтение, изменение, resize, aliasing, copy/merge и lifetime без объектов на каждую ячейку.

### Этап C. Интерпретатор

Перенести общий walker, binding/admission, namespace, control flow и results. Сохранить одну точку семантического выполнения каждого механизма.

**Результат:** реальные L3-программы исполняются без вызова C-interpreter.

### Этап D. Настоящий компилятор методов

Ввести Java-эмиссию для разрешённых L3-тел. Сразу обеспечить ordinary locals, арифметику, ветвления, циклы, прямые calls, pointers L3 и нужные графовые accessors.

**Результат:** загружаемые Java-методы; known scalar/control-flow тесты выполняются без Walker на скомпилированном пути.

### Этап E. Полный lifecycle

Добавить динамические calls, explicit compile, endturn, обновление units, почту, владение, GC и восстановление готовых артефактов.

**Результат:** общий набор L3-контрактов работает в смешанном compiled/walked исполнении.

### Этап F. Оптимизация

Сравнить носители памяти, устранить ненужные allocations и повторные разрешения, исследовать крупные payload и горячие циклы. При подтверждённой пользе добавить прямой class-file emitter того же разрешённого представления.

**Результат:** замеры с проверенными результатами и объяснёнными оставшимися расходами.

Этапы не разрешают считать обязательный контракт поддержанным по одной успешной трансляции. Статус каждого этапа определяется фактическим исполнением соответствующих сценариев.

## 22. Условия готовности первой полной версии

Версия считается выполненной, когда:

1. JVM самостоятельно строит и исполняет поддержанный L3.
2. JVM-интерпретатор действительно обходит граф.
3. JVM-компилятор действительно создаёт и запускает Java-методы.
4. Компилированные scalar/control-flow участки не выполняются скрытым интерпретатором.
5. Плотная арена, descriptors и Array payload соответствуют принятому формату.
6. Указатели L3, идентичность, resize, merge и ownership сохраняют контракт.
7. Admission, calls, defaults, locals и visibility совпадают с текущей нормой.
8. Не возвращены writeback, flush и автоматическое native invalidation.
9. Вызовы и обновление compiled units соответствуют explicit compile/endturn.
10. Общие L3-сценарии реально выполнены в C и JVM; расхождения объяснены конкретной нормой.
11. Ограничения размера, доступные providers и поддержанный профиль явно описаны.
12. Производительность подтверждена отдельными измерениями; удачная архитектурная схема не выдаётся за результат benchmark.

Доставляемые результаты реализации: исходники backend и платформенных частей, генератор Java, runtime, общие тесты, воспроизводимые команды сборки и запуска, примеры emitted Java/class, отчёт о семантическом соответствии и измерениях.
