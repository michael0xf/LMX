# Акт занесения вечной ветви в массив удержания R0: аудит и проект

Записка Fable от 2026-09-20 по тикету Codex `FABLE-ROOT-ETERNAL-ENTER-AUDIT-20260920-03`. Только чтение: ни `lmx_root.*`, ни транслятор, ни другие исходники не правились, тяжёлые тесты не запускались. Это проект и приёмка; реализация — после ответов автора о слоте unit и о типах и после накопившегося полного гейта. Номера строк — по `dev/l2src_sandbox/` на `f2533c0`.

## Что есть сейчас

- `lmx_root_open(root, entry, limit, eternal, methods)` (`lmx_root.h.lm1:182`) строит в постоянном хранилище два графа удержания и открывает у каждого столько слотов ссылок, сколько попросили (`lmx_root.lm1:107-125`), затем кладёт их адреса в граф R0 в слоты `LMX_ROOT_ETERNAL_SLOT` 8 и `LMX_ROOT_METHOD_SLOT` 9 (`lmx_root.lm1:126`, `lmx_root.h.lm1:86-89`).
- `lmx_root_eternal(root)` (`lmx_root.h.lm1:251`, тело `lmx_root.lm1:518`) отдаёт сам массив. Комментарий над ним (`lmx_root.h.lm1:248-250`): вызывающий читает массив, чтобы ЗАПОЛНИТЬ его до первого цикла, после этого в него никто не пишет.
- Заполняют его сырым `lmx_arena_ref_store` (`lmx_arena_refs.lm1:61`), который проверяет одно — что индекс внутри массива. Таких мест два: сгенерированный вход (`l2trans.lm1:14512` — чтение массива из графа и отказ, если ёмкость не равна счёту; `:14554` — запись корня и обратное чтение) и ручной строитель в тесте (`tests/lmx_root_selftest.lm1:59`).
- Значит, ядро принимает в массив ЛЮБУЮ ссылку: Structure из арены Message, член ветви с `node != 0`, ячейку, адрес чужого рантайма, один корень дважды. Единственная проверка — ёмкость — стоит в сгенерированном коде, а его `return: 1` теряется: `lmx_thread_dispatch_native` отбрасывает результат входа (`lmx_thread.lm1:414-430`). Снаружи это сегодня видит только драйвер `harness/l2_eternal_driver.lm1`.

## Акт

```text
fn: lmx_root_eternal_enter (@: LmxRoot root; size_t: index; @: Lmx branch) int
```

Имя — в ряду существующих `lmx_root_eternal` / `lmx_root_methods`; слова `retain` избегаю намеренно: `lmx_root_retention_set` и `LMX_ROOT_ORPHAN_RETENTION` в этом же заголовке означают удержание СИРОТ. Прототип — в `lmx_root.h.lm1` рядом с `lmx_root_eternal`, тело — в `lmx_root.lm1`. Ничего, кроме этой функции и кодов ответа, не добавляется: ни поля в `LmxRoot`, ни флага на значении, ни реестра, ни текста, ни особого случая в сборке мусора.

Проверки идут в этом порядке и ВСЕ предшествуют единственной записи:

| № | Условие | Чем проверяется | Отказ |
| --- | --- | --- | --- |
| 1 | корень открыт, массив есть, `branch` не ноль | `root\state = LMX_ROOT_OPEN`, `root\eternal != 0` | `LMX_ROOT_INVALID` |
| 2 | индекс внутри ёмкости | `index < root\eternal\len` | `LMX_ROOT_ETERNAL_INDEX` |
| 3 | адрес — Structure ЖИВОГО хранилища ЭТОГО корня | `lmx_range_home(@ root\arena, branch) = @ root\perm` и `lmx_range_classify(@ root\arena, branch) = LMX_KIND_STRUCT` | `LMX_ROOT_ETERNAL_FOREIGN` |
| 4 | `independent`: корень без лексического родителя | `branch\node = 0` — читается только после п. 3, когда адрес уже признан Structure хранилища | `LMX_ROOT_ETERNAL_PARENTED` |
| 5 | запись свободна и корень ещё не занесён | `lmx_arena_ref_value(root\eternal, index) = 0` и ни одна запись массива не равна `branch` | `LMX_ROOT_ETERNAL_TAKEN` |
| 6 | запись | `lmx_arena_ref_store(root\eternal, index, branch)` | — |

Коды: `LMX_ROOT_OK` 0 и `LMX_ROOT_INVALID` 1 существуют (`lmx_root.h.lm1:101-102`), 2 занят `LMX_ROOT_DONE`; новые — `LMX_ROOT_ETERNAL_INDEX` 3, `LMX_ROOT_ETERNAL_FOREIGN` 4, `LMX_ROOT_ETERNAL_PARENTED` 5, `LMX_ROOT_ETERNAL_TAKEN` 6. Это коды ОТВЕТА акта, а не коды типа значения: причина отказа видна вызывающему без текста.

Пункт 3 — это и есть правило автора «тип узнаётся по вхождению адреса»: принадлежность квалифицированному типу — членство в диапазонах хранилища, а вопрос «чья таблица ответила» задаётся общим `lmx_range_home` (`f2533c0`). Сравнение идёт с `@ root\perm`, а не с тем, к чему привязана арена: корень владеет хранилищем по значению и сверяет адрес со СВОИМ. Правило «закрытое хранилище не хранилище» приходит вместе с ответом `lmx_range_home`; закрытый корень отсекается раньше, пунктом 1.

**Атомарность отказа.** Запись одна — один указатель в один слот, и она последняя. Любой отказ происходит до неё, поэтому частичного состояния не бывает и откатывать нечего: массив, хранилище и арена R0 после отказа побайтно те же. Сам акт ничего не выделяет.

**Чего акт НЕ проверяет, и почему.** Замкнутость ветви по ссылкам (всё достижимое из неё живёт в хранилище) гарантирует транслятор своими отказами (`l2trans.lm1:9174`, `:9181`, `:13355`). Проверить её в ядре значило бы обойти ветвь, а ветвь может ссылаться на себя (`tests/unit_eternal_shape.lm2`): обход требует множества посещённых, единственное такое множество в ядре — штамп пометки в чанке, то есть ЗАПИСЬ В ХРАНИЛИЩЕ (`lmx_perm.h.lm1`, «WHY A STORE AND NOT A GC ROOT»). Поэтому глубокой проверки нет намеренно. Цена пункта 5 — просмотр массива на каждое занесение, квадрат от числа корней; это однократное построение и счёт, известный при трансляции (в корпусе до 70).

**Что остаётся возможным в обход.** Массив — обычная Structure, и сырой `lmx_arena_ref_store` в него по-прежнему сработает. Акт — узаконенный путь, а не замок; в сгенерированном коде обход запрещает строка харнесса (ниже).

## Отделено от двух нерешённых вопросов

- **Слот unit программы (предложен слот 10, `LMX_ROOT_SLOTS` 10→11) — не нужен акту.** Акт работает с массивом удержания в слоте 8 и с хранилищем; где живёт unit, ему безразлично.
- **Хранение результата входа — не нужно акту.** Результат акта получает его прямой вызывающий.
- **Но МЕСТО ВЫЗОВА зависит от `FABLE-L2-ETERNAL-INIT-ONCE-20260920-01`.** Акту нужен `@: LmxRoot`, а у сгенерированного входа есть только граф (`node`); корень держит обёртка `main`. После разделения построение переезжает в однократную функцию, которую обёртка вызывает сама и результат которой сама читает, — ей естественно принимать корень (`l2_program_init (@: LmxRoot root)`), и отказ акта становится наблюдаемым напрямую. Вызов же из сегодняшнего входа дал бы отказ, который снова потеряется в `lmx_thread_dispatch_native`. Поэтому: акт и его тесты ядра можно сажать независимо; перевод сгенерированного кода на акт — вместе с INIT-ONCE. Заодно запись-однажды превращает находку A (повторное построение на каждом ходу) из тихой в громкую: второй проход получил бы `LMX_ROOT_ETERNAL_TAKEN`.

Вариант акта «от графа» — `(арена, граф R0, индекс, ветвь)`, который можно было бы звать из сегодняшнего входа, — отвергаю: ему пришлось бы верить вызывающему на слово, что граф действительно граф R0, а сверка с `@ root\perm` пропала бы.

## Приёмочные тесты

Новый лёгкий тест ядра `tests/lmx_root_eternal_enter_selftest.lm1` (в гейте линкуется резолвером; поштучно — с отдельным объектом `lmx_perm`, как в `f2533c0`). Перед и после КАЖДОГО отказа сверяются сумма байтов хранилища, число выданных ячеек хранилища и содержимое массива — это и есть проверка атомарности.

| Случай | Ожидание |
| --- | --- |
| корень хранилища, `node = 0`, свободный индекс | `OK`; запись массива — тот самый адрес; у корня по-прежнему `node = 0`; в хранилище изменился один слот |
| ПОДДЕЛКА: Structure той же формы с `node = 0`, построенная в арене R0 | `FOREIGN`; запись пуста |
| значение хранилища с `node != 0` (вложенный член ветви) | `PARENTED` |
| не-Structure хранилища: ячейка `size_t`, слоты ссылок ветви | `FOREIGN` |
| ветвь хранилища ДРУГОГО корня в том же процессе | `FOREIGN` |
| роль хранилища снята рукой при открытом корне (состояние внутри `lmx_perm_close`) | `FOREIGN` |
| корень закрыт (`lmx_root_close`) | `INVALID`, и записи в освобождённую память нет |
| тот же корень в тот же индекс повторно; тот же корень в другой индекс; другой корень в занятый индекс | `TAKEN` все три раза, массив не меняется |
| `index = len`; корень, открытый с ёмкостью 0; все индексы заняты | `INDEX`, `INDEX`, `TAKEN` |
| `root = 0`, `branch = 0` | `INVALID` |
| законная ссылка из другого Message: ребёнок R0 (`lmx_root_create`; арена ребёнка привязана к тому же хранилищу, `lmx_child.lm1:47`) держит ссылку на занесённую ветвь | из арены ребёнка вид `STRUCT`, `lmx_range_home` — хранилище, `lmx_range_pool` — ноль, ветвь — терминал копирования; сборки над ребёнком и над R0 (сначала проверка инструмента) не меняют байтов хранилища, запись массива — тот же адрес |

Мутационный контроль: снять по одной проверке 2–5 — должен упасть ровно соответствующий случай; без проверки 3 обязаны пройти подделка и чужая ветвь, без проверки 4 — вложенный член.

Сгенерированные программы (при переводе транслятора): строки `eternal-runs` в `tools/l2_harness.ps1` требуют `lmx_root_eternal_enter(` и ЗАПРЕЩАЮТ `lmx_arena_ref_store(l2_retained`; драйвер не меняется — он и так смотрит на массив снаружи. `tests/lmx_root_selftest.lm1:59` переводится на акт тем же изменением.

## Открытые вопросы

1. К автору (общий с `dev/graph_interp/ADDR_RANGE_KINDS.md`): задаёт ли тип каждый ресивер по отдельности. Акт проверяет ровно то, что есть сегодня: членство в хранилище плюс `node = 0`.
2. К владельцу `lmx_root.*`: нужен ли симметричный акт для массива дескрипторов методов (`LMX_ROOT_METHOD_SLOT`). Его контракт отдельный, ёмкость сегодня 0, в этот проект он не входит.
3. Время занесения. Заголовок говорит «до первого цикла», а сегодняшний сгенерированный код заносит ВНУТРИ первого хода. Акт времени не проверяет — для этого корню понадобилось бы новое состояние; порядок наводит INIT-ONCE.
