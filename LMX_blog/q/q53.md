# Q53: receiveMessage in nested body — new declaration or take into visible name?

**Date:** 2026-09-29  
**Source:** Opus WALKLOOP-20260929-11, loop scope binding question  
**Status:** CLOSED by author answer, 2026-09-29

## Question (English)

When `receiveMessage: m` appears in a nested body (inside a method's while/for/if body) and the name `m` is already visible outside that nested body, is this:

1. A **new declaration of m** in the nested body scope (a new binding, forward and down only within that body, like `int: m` per Q51), or
2. A **take (read)** of the message into the already-visible `m` from outside?

## Question (Russian)

`receiveMessage: m` во вложенном теле (внутри тела while/for/if метода), когда `m` уже видимо снаружи этого вложенного тела, — это:

1. **Новое объявление `m`** во вложенном теле (новая привязка, вперёд и вниз только внутри, как `int: m` по Q51), или
2. **Чтение письма** в уже видимое `m` снаружи?

## Evidence and Example

### Code (method):
```
fn: peek () int
    int: n 0
    receiveMessage: m
    while: m != 0 && n < 5
        n: n + 1
        receiveMessage: m
    return: n
```

### Current behavior:
- **Native execution:** Returns 5
  - Interpretation: Second `receiveMessage: m` is a new declaration in the while-body scope
  - The while condition `m != 0` reads the outside `m` (unchanged)
  - Loop runs 5 times (while 1 < 5)

- **Root code (unit_next_message_loop, Q10):** Returns 1
  - Interpretation: Root deliberately does NOT open body scopes
  - `receiveMessage: m` writes to outside `m`
  - Loop runs 1 time (m becomes 0 after first message read)

### Contradiction:
If the second `receiveMessage: m` creates a new local `m` in the while body, then:
- Method's while-body has its own `m` (hidden input, not declared field per Q52)
- Condition reads outside `m` → unchanged
- Result: 5 ✓ (native)

If the second `receiveMessage: m` takes into visible `m`:
- All `m` refer to the same outside value
- Condition `m != 0` becomes false after first message
- Result: 1 (not observed natively)

## Why This Matters

The answer determines whether:
- **Root can open body scopes** like methods (allowing fields in root nested bodies, hence root's `for`)
- **Field scope rules** are consistent (forward/down visibility per Q51)
- **receiveMessage** follows same binding as other operations or has special semantics

**Current blocker:** Root's `for` statement is refused because a control body declares a field in a nested body. If root can open body scopes, this restriction lifts.

## Author Answer (2026-09-29) — CORRECTED

**Summary:** Inner receiveMessage: m DECLARES a distinct m (like int: n declares n), not a rebinding. Both method and root should yield 5.

**Exact ruling:**

receiveMessage is a receiver that DECLARES its result, just as `int: n` does. General repeated-declaration semantics permit `int: n` followed by `char: n` as distinct occurrences [0]n and [1]n (per Q25, which explicitly states receiveMessage receiver declares m).

**Therefore Q53 answer is (a):** 
- Inner `receiveMessage: m` **declares a distinct m** in the while-body (visible forward and down there only)
- While condition **before that body** reads the outer m
- **Both method and root should yield 5** (not 1 as previously stated)

**Root's result of 1 is a generic nested-body scope defect**, not a receiveMessage-specific behavior. Fix root scope by the same language rule, never by a receiveMessage-specific branch.

**Re-execution semantics:**
One lexical `receiveMessage` statement executed on later loop iterations updates that **SAME occurrence** in the while-body scope, not a new occurrence each iteration.

**Generic declaration tests:**
- Compare `int: n` / `char: n` (distinct occurrences [0]n, [1]n at the same location, run twice)
- Compare two written `receiveMessage` statements in sequence (distinct occurrences)
- These show the general repeated-declaration rule, not receiveMessage-specific behavior

docs/new_parts/threadMessageAPI_migration.en.md concerns shared mail transport/queue and preserves receiveMessage behavior. It does NOT define name visibility rules — those remain ordinary language rules.

## Author Refinement (2026-09-29)

**Crucial nuance:**

receiveMessage: m is analogous to `int: i getValue()`, NOT to `int: i 5`.

The field produced in this case is **NOT considered data** and is **NOT reachable as struct\m from outside**. Do not turn it into a public graph-data field merely because the receiver declares a local binding.

**Critical rules to preserve:**
- Uniform receiver/declaration and lexical-scope rules
- Do NOT require programmer to predeclare Message type before receiveMessage
- Do NOT add receiveMessage-specific visibility exception
- Do NOT add postal-only scope mechanism

## Author Addendum (2026-09-29) — Q53/Q25: Two valid receiveMessage forms

**Both shapes are valid:**

1. **Standalone receiveMessage: m** (Q53 case): Receiver-produced local binding in its lexical body. NOT externally addressable as struct\m. Inner receiveMessage does not overwrite outer m.

2. **Explicit typed declaration + receiveMessage: m** (Q25 case): `Message: m` / `receiveMessage: m` is ALSO valid. receiveMessage assigns to EXISTING typed m, admits payload against its declared model, stores payload (not envelope). Failure follows ordinary implements/throw.

**Critical distinction:**

Do NOT turn Q53 clarification into absolute rule that every receiveMessage creates new field even when same body has explicit typed m.

**Distinguish the two established shapes:**
- Q53: nested receiver creates its own local occurrence (not assignment to enclosing body m)
- Explicit-declaration: receiveMessage consumes into declared typed m
- Both use ordinary receiver output binding, lexical body scope, admission
- No required Message predeclaration
- No postal-only visibility rule

**Receiver-produced/computed local:** NOT externally exposed as struct\m

**Explicitly declared typed target:** Follows ordinary data-declaration contract (per Q25)

**If ambiguity:** Message as concrete model vs MainLetter creates genuine contract ambiguity — present minimal example in Russian rather than inventing envelope/payload special case.
