# Прямой текстовый протокол LMX

## 1. Один язык, несколько границ доставки

Native-вход принимает целый документ LMX и возвращает фактический LMX-результат. Он подходит терминалу, местной программе и агенту, которым не нужен JSON-RPC envelope. Документ поступает в тот же Service, что MCP и обычный Message.

`sys\fromLmx(text)` строит чистый граф, пригодный для компиляции. Тот же граф допускается к обычному runtime-исполнению. `sys\toLmx(value)` выводит полный LMX любой Structure и любого L3Thread. Native binding решает только границы bytes, доставку и связь ответа с запросом.

Body — обычная LMX-программа в явно выбранном контексте. Например:

```lmx
LmxServerInspect\inspect(runtime := runtime; scope := scope; target := Work; projection := ("name"; "type"; "value"))
```

`runtime`, `scope` и `Work` здесь уже доступны в контексте подготовки. Названия разрешает общий языковой механизм. Вход не ограничен таблицей строковых команд get/set/call. Результат может содержать таблицы, иерархии и общие ссылки.

Транспорт не определяет конец программы по скобкам, пустой строке или правдоподобному префиксу. Пустая строка значима для LMX, но не является разделителем сетевых сообщений. `[]`-подпарсер — часть единого parser ядра; он делегирует выражения и `{...}` основному и продолжает с возвращённой позиции. Группировка также одна, общая для всех потребителей.

## 2. HTTP native profile

Проектный route `POST /lmx` принимает `Content-Type: application/lmx; charset=utf-8` и целое UTF-8 body. Путь задаётся явной обычной route-конфигурацией. Стандартный MCP располагается на отдельно выбранном route, например `/mcp`, со своими JSON-RPC правилами.

HTTP-провайдер уже выделяет body. Дополнительного Content-Length заголовка внутри LMX нет. Нельзя повторно искать закрывающую скобку или делить программу по строкам.

Минимальный профиль — один принятый документ и один фактический Receipt, представленный через kernel toLmx. HTTP 200 сообщает, что native-протокол вернул receipt; `ok` и payload сообщают прикладной исход. Ошибки LMX-подготовки возвращаются как настоящий отказ подготовки. Ошибка framing/encoding до передачи Service даёт транспортный 400 без исполнения. Ошибка до размещения не называется изменением целевого графа.

Ответ имеет `Content-Type: application/lmx; charset=utf-8`. Если I/O сорван после начала исполнения, исход доставки неопределён: отсутствие ответа не доказывает отсутствия изменений. Автоматического повторного выполнения эффектной программы нет.

Когда программа завершает turn или остаётся приостановленной, provider сообщает поддержанное реальное состояние исполнения через continuation/driver. Код, достигший endturn, не изображается обычным синхронным return. Асинхронный профиль с admission ACK и отдельным результатом может использовать существующий Message-механизм; ACK прямо отличается от завершения действия.

Контекст и допустимые действия определяет настройка endpoint/provider. Endpoint не является сырым Thread handle. Средства защиты относятся к реальной границе развёртывания; `private` не заменяет access control. Входные MCP credentials не пересылаются модели как её outbound credentials.

## 3. Native stream profile

Для pipe/socket/stdin native-режима фиксируется простой frame:

- ASCII header `Content-Length: N\r\n\r\n`;
- ровно N байтов UTF-8 LMX-документа;
- следующий frame после этих N байтов.

N — число bytes, не Unicode-символов. Это native transport, не MCP stdio. Режим выбирается при открытии подключения; угадывать его по `{`, `[` или содержимому LMX нельзя.

Начальный профиль допускает один ожидающий запрос на соединение. Ответ использует тот же framing; ID внутри самой программы не нужен. Несколько одновременных exchanges требуют явного transport correlation либо обычного Message-обмена. Correlation не становится ID объекта runtime.

Provider обрабатывает partial reads/writes, overflow/negative length, свой объявленный предел размера, invalid UTF-8, EOF внутри body и неотправленный остаток. До полного тела prepareText не вызывается. При потере frame не исполняется guessed prefix. Diagnostics не смешиваются с protocol bytes.

MCP stdio остаётся стандартным: UTF-8 JSON-RPC messages, разделённые newline. Строка `document` после JSON-декодирования передаётся целиком общему LMX-сервису.

## 4. Местный Message

Местный агент пользуется настоящими ссылками и обычным вызовом либо `post`. [Пример 03](../examples/03_local_messages.lmx) отправляет `service\submitGraph` готовый граф без текстового преобразования.

Чтобы новый вызов использовал текущий handler, письмо адресуют стабильному `submitText/submitGraph`. На owner этот вход читает изменяемую ссылку. Сформированное ранее письмо самому handler не получает новую цель автоматически.

`post` сохраняет обычные binding, typed values, throws, owner, lifetime, sender-owned waits и время исходной отправки. Вторых mailbox, очереди агентов или dispatcher транспорт не создаёт. Timeout ожидания не отменяет чужую работу и не уничтожает маршрут позднего ответа.

## 5. Большие графы и поисковые результаты

Полный экспорт произвольной Structure/L3Thread выполняет kernel toLmx. Поисковая выборка SQLite — отдельно названная проекция. При порционной выдаче нужны границы, continuation, snapshot/scope и признак завершённости. Обрезанный текст не называется полным экспортом и не принимается обратно как законченная команда.

Для устойчивого вывода большого графа provider использует поддержанную границу наблюдения либо удерживаемый снимок с явной основой. Наблюдение нескольких owner не объявляется одним моментальным снимком автоматически.

После runtime edits без compile каталог может описывать прежнюю компиляцию. Полное текущее состояние доступно через toLmx. Файл исходников необязателен: явный экспорт делает toLmx, новое построение — fromLmx.

## 6. LMX-тела и подключения

[boundaries.lmx](../src/boundaries.lmx) содержит три настоящих прикладных тела:

| Callable | Действие |
| --- | --- |
| `LmxServerNativeCommand\exchange` | service.submitText → runtime.present |
| `LmxServerNativeFrame\exchange` | readDocument → native exchange → writeDocument |
| `LmxServerMcpCommand\exchange` | Проверенный decodeCommand → тот же Service → encodeReceipt |

Они требуют реальных провайдеров. HTTP listener, TLS, JSON codec и driver continuation этими заготовками не реализованы. Их статус и критерии приёмки указаны в [плане](IMPLEMENTATION_PLAN.ru.md). Wire MCP описан в [отдельной матрице](MCP_COMPATIBILITY.ru.md).
