## Механизм

- **Маршруты у места вызова.** Число, написанное по имени у связанного вызова (вызываемое выбрано при исполнении: callable-место, callable-формал), принимается сначала формалом, против которого вызов написан (тип S); формал его имени у выбранного может быть другого числового типа D. Место вызова разрешает — так же, как статический приём этой пары в этом вызывающем (`lm_compiler_convert_hit`, `lm_compiler_convert_method`, ресивер одного формала S с результатом D), — прямой ресивер программы S → D для каждого числового D ≠ S (`lm_compiler_direct_receiver`, lower; состояние таблицы вокруг вопроса сохраняется). Позиционный фактический и литерал по имени маршрутов не получают (`lm_compiler_bound_route_source`: профиль места 286 и контекстный литерал 297).
- **Доставка.** Native: массивы `l2_brw` (ранг записи), `l2_brt` (тип), `l2_brc` (вхождение ресивера, прочитанное от корня единицы, как вхождение выбранного) передаются связывателю (`lm_compiler_emit_bound_routes`, новые параметры `lmx_call_bind_actuals`). Обходчик: пары [свидетель типа D, вхождение ресивера] после полезной нагрузки операнда NAMED (`lm_compiler_rw_named_routed`, emit); координата и имя NAMED прежние, форма одна для всех потребителей (`lmx_walk_named_form`: `lmx_walk_prim_source_value`, `lmx_walk_actual_shape`, `lmx_walk_named_route`), маршруты не вычисляются как фактические.
- **Один приём ядра.** Оба связывателя принимают записанные фактические в порядке записи одной функцией `lmx_walk_receive_selected`: типизированное число другого типа при маршруте типа выбранного формала — вызов ресивера через существующий `lmx_walk_convert_capture` (отказ ресивера — неявный `convert` вызывающего до тела, значение не меняется), без маршрута — прежний приём места `lmx_walk_value_receive` (`convert`). При исполнении читается только маршрут выбранного типа (обходчик вычисляет вхождение только у него); неверная форма маршрутов — ошибка графа (INVALID).
- **Порядок.** Структура связывания прежняя: все записанные фактические вычисляются в порядке записи, затем приёмы — в порядке записи, до тела (p301b — 1233); отказ `call` по имени — после эффектов фактических. Норма по решению автора — 1323 и отказ формы до аргументов (CALL-ARGUMENT-ORDER-AXBY): этот вариант её не выполняет.

Ядро (`lmx_walk_values.lm2`) и два модуля frontend изменены; tools/build.lm2 — нет: новые функции ядра внутренние и стоят в конце модуля (в L2-модуле вызов до определения допустим — модуль уже так вызывает `lmx_walk_projection_at`), заголовок ядра пересобирает `build-runtime` (в `lmx_walk_values.h.lm1` у `lmx_call_bind_actuals` четыре новых параметра).

## Границы

- Порядок и момент отказа формы: решение автора 2026-11-07 — проверка имён и формы до аргументов, приём каждого сразу (AXBY; p301b должен дать 13, `f(x: touch())` без формала x — `call` без `touch()`); здесь — ABXY (1233) и отказ после эффектов: долг CALL-ARGUMENT-ORDER-AXBY. Ни один ряд реестра прежний порядок не закрепляет; выбор вызываемого и его проверка остаются до фактических.
- Имена при исполнении: связывание ищет формал выбранного по написанному имени (native — строки `l2_bn` в `lmx_call_bind_actuals`, обходчик — имя строки NAMED в `lmx_callable_bind_written`, оба с 294); по замечанию и поручению автора это не требуемая архитектура — долг IDENTIFIER-CODES (каждый идентификатор обоих исполнителей — код написания, без сравнения строк; найденные Codex строковые пути — в записи реестра). Маршруты 301 в строке NAMED — промежуточная доставка на этом механизме: Codex отозвал рекомендацию считать её окончательной.
- Ресивер маршрута — метод, который называет `lm_compiler_convert_method` (первый метод программы с именем из строки таблицы), как у статического приёма этой пары; другой сигнатуры — маршрута нет (`convert`), без отказа трансляции: приём здесь возможен, а не известен.

## Провенанс

Правки, фикстура, пробы, рецепты и списки записаны вручную инструментами Write и Edit или получены из своих аналогов 300 заменой меток; каждый список разобран при исполнении `steps`/`checks` без отказа строки. Мутанты — ручная правка стейдж-файла с возвратом из варианта (`stage-copy`) и `lmxtool verify` всего стейджа. Подготовка кандидата и стейджа bootstrap, возвраты, приёмка, посадка, рендер документов и архив — `lmxtool steps`/`checks` из своих каталогов запуска; PS-рецепты — запуски одной команды инструмента с охранниками: `tp163-rt` и `tp163-fe` (хэши tool и frontend boot162a), `boot163-quick` и `boot163-detached` (по образцу `boot162-*`), `tp151-probe` (289), `tp152-selftest` (290; форма `ScriptBlock` из текста рецепта, как у 299 и 300). Реестр [registry301-a](records/pins/registry301-a.tsv) — копия `selfbuild/tests/full-suite.tsv` (хэши равны: `03fd77fa…`). Копии десяти сообщений Codex сверены с его текстом в транскрипте relay: каждая непустая строка (с экранированием JSON) найдена в строке транскрипта с `BEGIN_MESSAGE` своего REQUEST_ID, число переводов строки и пустых строк тела совпало. Отступления:

1. Детачированный запуск boot163a шёл из Windows PowerShell 5.1 (фоновая команда `powershell -Command` с текстом рецепта `boot163-detached`), а не из pwsh, как у 300 (`Start-Process pwsh`): `Add-Content -Encoding utf8` начал терминал с BOM, а перенаправление `*>>` записало строку вывода ребёнка (`BOOT163a exit=0`) в UTF-16LE. Запуск и его итог от этого не зависят (EXIT=0; итог bootstrap — в его терминале и логе); git читает копию как двоичную, она сохранена байт в байт с явным `-text` (см. «Документы»).
2. Первая правка мутанта m3 заменена до сборки (см. «Мутанты»).
