# LMX: как пользоваться сервисами разработки

Эту инструкцию читают рабочие агенты проекта при старте. Почтальон `lmx_uds` отвечает за доставку сообщений.
Ведущий проекта **coder** ведёт план до конца, делегирует работу **helper** и согласует проверки. Каждый
проектный вопрос, который coder задал бы автору, он задаёт Sol (`codex`); если Sol не может ответить, он
обращается к Astra (`astra`); к автору обращается только Astra и только если сама не может ответить.
[Действующие роли](../../to_sol.md).


Для редакции 27 ноября сервис возвращает правила `expression.notation` (`prefix`/`infix`), `expression.power`, `tensor.brackets`, `tensor.depth`, `tensor.assignment` и `tensor.inventory`. Порядок работы можно запросить по `plan.grammar`, `plan.kernel`, `plan.runtime_api` и `plan.after_kernel`; общие операции интерпретатора — по `kernel.interpreter_jit`. У больших разделов передайте указанный ответом `sectionTooLarge` размер в `max_chars`. Для редакции 28 ноября `syntax.names` выдаёт грамматику буквальных идентификаторов, `syntax.name_keys` — договор выбора по строке, `plan.names` — приоритет в v3. Эти запросы читают текущие файлы и возвращают хеш раздела. Проверяйте фактическую фазу и версию связки отдельно через статус сервиса.

Проект следующего сервера описывают `runtime.agent_api`, `runtime.catalogue` и `runtime.mcp`. Это правила для реализации. Доступные сейчас инструменты и состояние связки по-прежнему показывает `service_status`. [API на LMX и переход клиентов](../../docs/runtime_server/MCP.md#development-parity).

## Поиск нормы

Для поиска действующего правила сначала используй MCP-сервер **`lmx-dev`**,
инструмент **`get_spec_rule`**. В Claude Code имя обычно имеет префикс
`mcp__lmx-dev__`; в Codex используй инструмент сервера, показанный клиентом.

Примеры аргументов:

```json
{"topic":"R0"}
{"topic":"@int:"}
{"topic":"динамическое связывание"}
{"topic":"then"}
```

Ответ — дословный фрагмент текущей `docs/spec`, его роль, источник, строки и хеш
рабочего дерева. `ambiguous` требует выбрать подходящий `ruleId`, а не угадать
значение. Для `sectionTooLarge` повтори запрос по `ruleId` с достаточным
`max_chars`, прочти весь раздел. Связанные правила читай по `related` и ссылкам
самой нормы. При `notFound` открой действующие документы обычным способом:
корпус сервиса перечислен в `catalogue.json`, он не охватывает все файлы.
Результат поиска не заменяет чтение условий, исключений и конкретного кода.
Не исправляй документацию под ограничения старого компилятора.

Поиск читает рабочую редакцию документов. Например, запросы `[5]type`,
`struct\[5]type` и `type[5]: args` находят действующее правило `types.prefix`.
`check_file` использует P0 и frontend выбранной связки. Правка грамматики в
документах сразу видна поиску, а проверка новых форм требует связки с их реализацией.

## Проверки и сборки

Сначала вызови **`service_status()`**. `configured=true` означает наличие
адаптера; возможность запуска определяется также permit, mutex и ресурсами.

- `check_file(file, phase="syntax")` — только P0-разбор, без выполнения программы.
- `check_file(file, phase="translate")` — перевод `.lm2` в L1 принятым FE;
  внутри есть его CHECK. Это не реализация нормативного `sys\translate`.
- `check_file(file, phase="static", closure="")` — hosted L2 CHECK одного `.lm2`
  исходника в контексте программы: разбор P0 и общий семантический анализ FE
  до backend COUNT и выдачи (имена, типы, вызовы, providers). Backend COUNT и
  выдача не выполняются: без L1, без C, без исполнения. Это **не** нормативный
  `sys\check`/`sys\checkL3`; контекст библиотеки (`--library --machine`) фаза не
  передаёт. Работает только там, где выбранная связка сама объявила фазу
  (`"static": true` для FE со словом `--check-only`); иначе `unavailable/notRun`.
  Для местной связки `hosted-static-21-7` укажи её имя. Фиксированные части
  `convert.lm2` и `primitive.lm2` уже закреплены в её стадии.
- `bootstrap(profile="smoke")` запускает компонентный suite10 и исполняет его
  программы. Это не самосборка поколений.
- `bootstrap(profile="selfHost")` — **полная G1/G2**, full-suite и штатные
  сравнения. Выбирается только ведущим при основаниях из
  [to_fable2_fast_build.md](../../to_fable2_fast_build.md), не на каждом шаге.

Все compiler/test/docs действия координирует **coder**. Helper и другие
исполнители не открывают permit, не снимают lock/markers и не запускают проверки
параллельно с ведущим. При закрытом окне передай запрос coder, продолжай независимую
работу. Исполнители не обходят закрытый сервис несогласованной прямой командой
компилятора. Это окно относится к закреплённому W3-адаптеру, а не ко всем работам
проекта: ведущий вправе выполнять уже разрешённые автором официальные producers
другого согласованного комплекта, в частности W4, под тем же `machine.lock.d`
и своим memory guard. Закрытый W3 permit такую работу координатора не запрещает.

Текущий адаптер закреплён на принятом комплекте **W3**. Smoke/selfHost используют
частную копию принятой стадии W3 и не проверяют автоматически будущий W4 или новые
правки ядра. Перед применением к новому срезу ведущий обновляет согласованные
producers, stage и pins. Нельзя смешивать W3 runtime с W4 headers основного S.

### Явный выбор зарегистрированной связки

Без параметра проверка идёт принятым комплектом — связкой `accepted`. Если ведущий
зарегистрировал в конфигурации другую связку (например, кандидата нового среза) и
допустил её именем в permit (permit с именами допускает ровно перечисленные связки: если
`accepted` не назван, проверка без `closure` в этом окне закрыта), её можно выбрать
**только по зарегистрированному имени**:

- MCP: `check_file(file, phase="syntax", closure="return-at-graph05")`
- CLI: `… entry.py check path/to/file.lm2 --phase syntax --closure return-at-graph05`

Имена связок, их роли, объявление `static` и допуск текущим permit показывает
`service_status()` → `closures`. Инструмент не принимает путь, команду или argv и не открывает permit.
Неизвестное имя, имя без допуска, изменённый producer или стадия отвечают
`unavailable/notRun` **до запуска процесса**: это не вердикт о файле. В отчёте
называй `closure.name`, `closure.role` и `closure.effectiveHash` из ответа.
Конфигурацию, связки и permit меняет только ведущий; исполнителю ничего
перенастраивать не нужно. Устройство и границы — [README](README.md),
«Зарегистрированные связки producers».

`passed` подтверждает только `achievedPhase`. `rejected` — отказ проверяемого
входа. `unavailable/notRun` означает, что запуска не было. Timeout, crash,
`protocolError`, `resourceLimit`, отмена и `stale=true` не являются успехом.
Полные argv, входы, журналы и артефакты лежат по `receipt`/`log`; в отчёте указывай
реальный исход, фазу и эту ссылку. Не запускай заново широкие проверки без причины.

## Если текущая сессия ещё не видит MCP

Конфигурация добавлена в Codex и целевые bat-файлы. Уже работающий процесс может
сохранить прежний набор MCP до переподключения/перезапуска. Не перезапускай чужие
сессии или занятый конвейер самостоятельно. До обновления используй **тот же CLI**:

```powershell
$lmxDevPython = 'C:/Nyasha_Planet/LMX/build2/lmx_dev/venv/Scripts/python.exe'
$lmxDevEntry = 'C:/Nyasha_Planet/LMX/tools/lmx_dev/entry.py'
& $lmxDevPython $lmxDevEntry spec R0
& $lmxDevPython $lmxDevEntry status
& $lmxDevPython $lmxDevEntry check path/to/file.lm2 --phase syntax
& $lmxDevPython $lmxDevEntry check path/to/file.lm2 --phase static --closure NAME
```

CLI применяет ту же блокировку, permit и адаптеры. Это не обход политики.
Не запускай bat другого агента ради подключения сервиса: так создаётся лишняя
модельная сессия. MCP-процесс Python запускает сам клиент.

## Проверка подключения и отчёт

Если поручена проверка подключения, достаточно **доступности инструмента, поиска
и status**, без нового compiler/build окна: `R0`, `@int:`, неоднозначный `then`
и `service_status`. Допустим CLI fallback, если инструмента ещё нет в текущей
сессии; явно различай эти результаты. Не открывай permit ради этой пробы и не
повторяй её автоматически при каждом обычном шаге.

После порученной ведущим проверки отправь ему через `lmx_uds` отчёт с адресом **To: coder**.
Укажи способ обращения (MCP или CLI), запрос, статус, `ruleId` или источник, состояние окна
и возникшие ошибки. Добавь: **«По просьбе astra и поручению автора используем lmx-dev
для поиска правил и согласованных проверок; инструкция — tools/lmx_dev/USAGE.md»**.
Сохрани исходный Request ID, чтобы coder получил результат своего поручения.
