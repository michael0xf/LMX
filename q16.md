# Q16. Что возвращает `sizeof:` для массива — байты или число элементов

Состояние: 2026-09-23, main = `fd7e8fc`. Вопрос поднял Grok Bot блокером во второй части тикета `FABLE-GROKBOT-INCLUDE-AND-SIZEOF-20260923-123` (ввод `sizeof:` и удаление спецветок `c.sizeof`/`c.array`); без ответа часть 2 не пишется. Ответить можно строкой `Q16 A` или `Q16 B`.

## Контекст

По вашему решению (`AUTHOR-SIZEOF-DESIGN-20260922-20`, `next_core_tasks.md` §0/§7a) в L2 вводится **receiver-оператор языка `sizeof:`**: класс `length`/`cast` — зарезервированное имя, не callable, операнд — L2-значение или тип, который **разрешает транслятор** (не сырой текст). Одновременно `c.sizeof(...)` и `c.array(...)` перестают быть особыми ветками транслятора и проходят через сырую дверь `c.*` дословно, как любой `c.name(args)` — их смысл задаёт C.

Перепись использования (мой аудит -21, подтверждённый инвентарём Grok Bot -111): из 41 места `c.sizeof` в `dev/l2src_sandbox` **19** имеют сырой C-операнд (`c.sizeof(c.LmxArena)`, `c.sizeof(stack[0])` над C-типами) — они остаются `c.sizeof` через дверь; **22** имеют L2-операнд (own-ячейка, L2-значение, локал), и сегодня спецветка транслятора подставляет им размер временного или типа — эти 22 переезжают на `sizeof:`. Все 22 хотят **размер хранилища значения в байтах**: они стоят под `lm_own_new_zero(...)`, `lm_own_copy_bytes(...)`, `c.memset(...)`, `c.memcpy(...)` и т.п.

Что уже есть в языке: `length` — число элементов own-массива (L2 §19 ~:208, `l2_array_length_own`). Спека про `sizeof:` молчит; L2 §20 ~:215 говорит только, что `c.sizeof` — это C `sizeof`, а не длина Array, — но это про сырую дверь, не про `sizeof:`.

## Минимальная программа

```
int: [4]: xs
char: [32]: buffer
size_t: a sizeof: xs
size_t: b sizeof: buffer
size_t: n length(xs)
```

- Для `buffer` варианты не различимы (32 и 32).
- Для `xs` различимы: **A** → `a` = 16 (4 × `sizeof(int)`), **B** → `a` = 4 (совпадает с `length(xs)` = 4).

## Варианты

- **A — байты.** `sizeof: x` = размер хранилища значения `x` (для массива — всех его элементов) в байтах, то же, что C `sizeof` для соответствующей C-ячейки, но операнд — L2-значение/тип, разрешённый транслятором. `sizeof:` и `length` — разные операторы: байты и элементы. 22 мигрирующих места получают ровно то, что считали раньше; генерируемый C для них может остаться побайтово тем же.
- **B — число элементов.** `sizeof: xs` = 4. Тогда `sizeof:` для массива дублирует `length`, а 22 мигрирующим местам (им нужны байты) придётся писать `length(xs) * sizeof: int` или уходить обратно в `c.sizeof` над C-типом — т.е. сырая дверь снова окажется единственным способом узнать размер L2-значения.

## Следствия

- A: одна общая семантика «размер хранилища» для примитива, Structure-ссылки (размер ячейки ссылки, `Lmx *`), own-массива (элементы × размер элемента), типа (`sizeof: int`); транслятор эмитит `c.sizeof(<C-ячейка>)` из разрешённого операнда — никаких имён.
- B: нужен второй оператор для байтов, либо признание, что байты L2 не выражает.
- Отдельно (в любом варианте): `sizeof: unknownName` — отказ «unresolved name»; `sizeof:` над `c.*`-типом не нужен — для него есть `c.sizeof`.
