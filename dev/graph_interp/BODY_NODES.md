# Узлы тела и одна активация интерпретатора

Прототип Fable от 2026-09-20. Код: `dev/l2src_sandbox/lmx_walk.h.lm1`, `lmx_walk.lm1`, тест `tests/lmx_walk_selftest.lm1` (26 проверок, все проходят). Это срез на `int`, а не готовый интерпретатор. `lmx_interp.*` Grok не изменён: `lmx_walk_run` написан так, чтобы вызываться из `lmx_interp_run`, а не заменять его.

## Статус после уточнения автора (передано Grok, `GROK-L3-ONLY-20260920`)

Интерпретатор исполняет **только L3** — не низкоуровневые операции L2 и не `c.*`; продукт — подмножество L3 через принимающее выражение L3. Имя этого выражения и состав глав первой версии запрошены у Codex (`GROK-L3-SUBSET-20260920`). Обход по `LmxOp` в песочнице — черновик носителя.

Следствия для этого файла:

- **Таблица кодов 3–14 ниже — не предложение к принятию, а временный набор для проверки механизма.** Перенос их в `lmx_interp.h.lm1` как `LMX_OP_*` снят до названного подмножества L3; набор узлов должен выводиться из него, а не из этого списка.
- **Механизм от набора кодов не зависит и остаётся проверенным:** загрузка собственных полей на входе и позиционная адресация от зарезервированного `node`, dirty-only чекпоинт перед каждым исходящим вызовом и каждым выходом, один порядок выхода, рекурсия на стеке C, копия M на собственном состоянии с общим слотом 0.
- Типизированные C-значения (`int`, `lmx_int_value_known`) в срезе — свойство носителя, а не операций L3; представление значений L3 этим срезом не выбрано.

## Что взято как данность

- Тело — сама M после слота 0, по порядку; каждый `return:` — узел этого дерева, их может быть много (`lmx.h.lm1`, `LmxCallable`; [README](README.md)).
- Узел тела — форма Grok: обычная Structure, в слоте 0 запись `LmxOp {code}` (вид 17 в индексе арены, терминал копирования), остальные дети — операнды по порядку. «Голый» `LmxOp` с кодом RETURN — возврат без значения.
- В графе нет имён, таблица адрес→имя не читается; активация — на обычном стеке C (`LMX_blog/2026-09-20.md`). Рекурсивный вызов — рекурсивный вызов `lmx_walk_run` на той же опубликованной M; в граф на время активации ничего не кладётся.
- Собственные поля, которые тело использует, загружаются на входе в рабочие значения активации; dirty ставит только исполненное присваивание; dirty публикуются перед каждым исходящим вызовом и каждым выходом; чистые не переопубликуются; после вызова ничего не перечитывается (прежняя спецификация 21.5, 21.6; `lmx_own.lm1`).
- Порядок любого выхода один: вычислить аргумент → dirty-only чекпоинт → возврат (`l2trans.lm1`: `l2_emit_ret_tr` и ветка `return` в `l2_emit_body`).

## Временный набор кодов среза

Набор кодов сверх RETURN и CALL и операнды каждого — см. статус выше: это носитель для проверки механизма. Числа внутри узла (литерал, шаг пути) — примитивные ячейки. Тело `if`/`while` — простая Structure той же формы, что M после слота 0: по порядку собственные ячейки и узлы.

| код | узел | смысл |
| --- | --- | --- |
| 1 `ret` | `[ret, значение?]` | возврат; без значения — для void |
| 2 `call` | `[call, путь \| M, аргумент…]` | путь выбирает вызываемую M; принимается и M, записанная прямо в слот 1 (форма `lmx_interp_exec`) |
| 3 `lit` | `[lit, ячейка int]` | литерал |
| 4 `own` | `[own, i0 … ik]` | собственное поле: шаги от зарезервированного `node` вниз через тела, последний — слот поля |
| 5 `arg` | `[arg, k]` | k-й объявленный вход активации |
| 6 `at` | `[at, путь]` | явный путь в граф: читается при каждом исполнении, не кэшируется (21.5) |
| 7 `put` | `[put, путь, значение]` | явная запись в граф, мимо кэша |
| 8 `set` | `[set, own-узел, значение]` | исполненное присваивание собственного поля: ставит dirty |
| 9–12 | `[add\|sub\|lt\|eq, a, b]` | арифметика и сравнение |
| 13 `if` | `[if, условие, тело, иначе?]` | |
| 14 `while` | `[while, условие, тело]` | |

Путь — простая Structure `[up, i0 … ik]`: сначала `up` лексических родителей от `node`, затем вниз по индексам. Адресация позиционная, как у нативного кода (`l2_own_mslot`, `l2_own_ctr`), поэтому копия M исполняется без изменений на собственном состоянии — это проверено тестом через `lmx_graph_copy_owned`.

Коды 1 и 2 совпадают с `LMX_OP_RETURN` и `LMX_OP_CALL` из `lmx_interp.h.lm1` (тест проверяет равенство). Остальные продолжают ту же нумерацию и после согласования должны переехать в тот же заголовок.

## Открытые вопросы

1. **Порядок детей M.** Нативная раскладка сейчас: слот 0, затем собственные поля, затем хосты управляющих тел (`l2trans.lm1:7726-7734, 7787-7788, 7829-7830`). Модель «тело — M после слота 0, по порядку» означает исходный порядок, где поля и операторы перемежаются. Обходчику всё равно (не-узлы он пропускает как данные), но индексы в `own`-узлах и индексы нативного кода должен ставить один и тот же проход `l2trans`, иначе два пути молча разойдутся.
2. **Порядок чекпоинта.** Нативный — по порядку объявления полей; здесь — по порядку первой встречи поля при обходе тела на входе. Наблюдаемо только при сбое публикации посреди чекпоинта.
3. **poll.** Нативный ранний `return:` опрашивает `lmx_msg_poll_escape` между вычислением и чекпоинтом (`l2trans.lm1:13664-13680`), трейлер — нет (`:1950-1971`). В прототипе опроса нет нигде.
4. **Классификация в дочернем Message.** Узел распознаётся через индекс арены (`lmx_range_classify`), а общие записи (`LmxCallable`, `LmxOp`, METHOD) после копии остаются в арене программы; арена дочернего Message их не классифицирует (`lmx_child.lm1:34-36`, `lmx_range.lm1:175-195`). Там ни `lmx_call_ready`, ни этот обход M не распознают. Это прежний долг «method-admit» (`l2trans.lm1:14439`), не новый.
5. **Форма без тела с трейлером** (`fn: ten () int` + `return:`; `l2trans.lm1:9686-9687`, `tests/entry_ret_tr.lm2`). В этой модели трейлер — последний `ret`-узел M; M тогда имеет `len` = 2, а не 1.

## Пределы среза

Значения только `int`; входы `int`; возврат несёт 0 или 1 значение; нет `throw`, массивов, `char`/`size_t`/указательных полей, динамических входов 21.3; `header` из `LmxCallable` не читается. `l2trans` узлов тела не выдаёт — графы в тесте собраны руками.

## Сборка и запуск теста

Готового раннера для selftest'ов ядра в LMX нет. Проверенный способ (транслятор L1 и GCC уже установлены):

1. Каталог-корень единиц с двумя ссылками: `l2src` → `dev/l2src_sandbox`, `l1src` → `C:\Nyasha_Planet\L1\dev\l2src_sandbox\l1src` (в LMX `dev/l2src_sandbox/l1src` пуст, а корневой `l1src/libc_abi.lm1` не объявляет `l1_stdout`).
2. Каждый `l2src/*.h.lm1` и `l1src/*.h.lm1` транслировать в `<out>/<каталог>/<имя>.lm1.h`: `l1trans.exe --unit-root <корень> <единица> <выход>`.
3. Тест и `l2src/l2_libc.lm1` транслировать в `.c`, собрать `gcc -std=c99 -Werror=incompatible-pointer-types -Werror=implicit-function-declaration -Werror=implicit-int -I <out> -I <корень>`.

Под `-Wall -Wextra -Wpedantic` единица `lmx_walk` предупреждений не даёт.
