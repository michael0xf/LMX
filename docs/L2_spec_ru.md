# Спецификация L2

L2 задаёт механизмы ядра и машинные операции. Семантика L3 определяется в [спецификации LMX](LMX_semantics.ru.md), синтаксис — в [грамматике](LMX_grammar.ru.md), понижение в C99 — в [L1](L1_spec_ru.md). Этот документ не повторяет правила разрешения голов, объявления и вызова. Состояние реализации — в [заметках](implementation-notes.ru.md).

<a id="scope"></a>
## 1. Предмет

Целевая цепочка — L3 со вставками L2 → генерируемый L1 → C99. L1 является промежуточным языком. Интерпретатор исполняет сохранённый граф L3; L2-операции требуют нативного понижения.

<a id="lmx"></a>
## 2. Структура `Lmx`

Целевая физическая модель имеет общую основу `Lmx` для объектов графа. Языковой Array — разновидность `Lmx` Structure с фиксированным типизированным хранилищем элементов, а не самостоятельная запись `VoidArray`, на которой основан `Lmx`. И обычная Structure, и Array имеют структурные `parent` и `native`; точная C99-раскладка общей основы и специализации Array ещё выбирается при миграции. Нынешняя обратная раскладка C описана только в [заметках о реализации](implementation-notes.ru.md#l2-status) и не является целевой нормой.

`parent` задаёт структурную вложенность, не родителя Message. У Array, созданного в поле `arr`, родитель — представляющее это поле вхождение графа, а у Structure, созданной как собственный элемент массива, родитель — сам Array. Сохранение в элементе ссылки на уже существующую Structure не меняет родителя её референта. Лексическая видимость определяется местом создания; дополнительный скрытый контекст не создаётся. `native` выбирает нативный вход; нуль означает обход сохранённого тела. Графовый объект не хранит имени, тега модели или дополнительных полей состояния исполнения. Число полей Structure и элементов Array фиксируется при построении, их адресуемые ячейки не перемещаются. Примитивные элементы остаются типизированными ячейками, которым не требуется отдельное поле `parent`.

<a id="interpretable-tree"></a>
### 2.1. Интерпретируемое дерево

Сохранённый граф — программа: объявления, значения, операторы и вложенные тела при построении следуют исходному порядку; последующая запись меняет этот же граф. Нативное понижение не заменяет его вторым AST или графом данных. Примитив уже имеет типизированную ячейку арены; дополнительный `leaf` или обёртка Structure для неё не нужны. Атомы, которые остаются частью текущей программы, сохраняются.

Имена сущностей находятся только во внешней таблице для трансляции и `toLmx`; исполнение не ищет их по строкам. Комментарии не участвуют в диспетчеризации. `toLmx` выводит текущий состав и порядок графа: перезаписанный оператор не восстанавливается из исходника или скрытой копии. Служебные данные запуска, статус вызова и состав детей Thread не дописываются в граф программы.

Ссылки как данные образуют граф и могут создавать циклы. Структурный `parent` образует дерево. Вид значения определяет классификация его адреса; адрес слота и хранимый в нём адрес — разные вещи.

<a id="type-by-range"></a>
## 3. Тип по диапазону адресов

Арена классифицирует адрес по зарегистрированному полуоткрытому интервалу `LmxRange` и пулу-владельцу. Сама ячейка не хранит тег типа. Обычные Structure и графовые Array имеют общую основу `Lmx`, но диапазон различает форму хранения и тип элементов; модели пользователя не порождают по одному C-типу или пулу. Пулы примитивов, ссылок, графовых объектов и backing различаются физическим контрактом доступа. Типизированные массивы внутри арены — хранилище, а не отдельные языковые Array. Обычные и `immutable` Structure выделяются в разных пулах; уже опубликованная обычная Structure не становится `immutable` на месте. Совместимость моделей устанавливает `implements`, а не физический тип.

<a id="pool"></a>
## 4. Типизированный пул

Пул выдаёт ячейки одного размера и растёт добавлением чанка, без `realloc` живых ячеек. Каждый чанк регистрируется как интервал того же типа. Выданный адрес стабилен до освобождения соответствующего владения. Индексом диапазонов управляет арена.

<a id="method-array"></a>
## 5. Нативный вход и Array

`LmxEntry` — слово нативного входа, а не второй объект метода. Графовый Array несёт общую основу `Lmx` и ровно заданное число типизированных элементов. Он не содержит динамического резерва и не перемещает опубликованные адресуемые ячейки. При `arr: []: (...)` значение Array сохраняет своё место в графе; последующее `MyLmxStructFromArray: arr` по общему правилу связывает новое имя ссылкой на тот же Array, а не конструирует второй объект или восстанавливает структуру из байтов. Динамический List — отдельный тип и отдельный контракт; его перемещаемый backing не используется как адресуемые слоты Structure или Array.

<a id="arena"></a>
## 6. Арена

Каждый Message владеет одной логической ареной; она может содержать несколько чанков и диапазонов. `lmx_arena_attach` передаёт владение без перемещения адресов. `mark/revert` откатывают неудачное построение копии или `merge`. Простой режим сохраняет классификацию и стабильность адресов, но не запускает GC. Независимая неизменяемая ветвь может остаться в арене владельца по [контракту L3](LMX_semantics.ru.md#eternal); сам факт отдельного пула такого права не даёт.

<a id="message"></a>
## 7. Запись Message

Закрытый `LmxMsg` содержит ровно `running`, `success`, `handoff_ready` и `graph`. Его локальная идентичность — адрес записи. Почта, планировщик и родитель Thread не являются его полями. `running = 0` во время хода запрашивает остановку; `success = 1` устанавливается пользовательским кодом и достаточно для остановки Thread на границе хода; система не сбрасывает `success` в нуль. `handoff_ready` разрешает передачу хранилища. `graph` ссылается на языковой корень.

<a id="thread"></a>
## 8. L3 Thread

Не каждый Message исполняется. Исполняемый Thread изначально выделяется как `LmxThread` с `LmxMsg` первым членом по значению. Адрес Thread совпадает с адресом этого префикса; доступ к хвосту требует точной классификации Thread. Самостоятельный `LmxMsg` нельзя на месте превратить в Thread.

Прямые дети хранятся в единственном List, удерживаемом полем `Thread.children`. Это состояние Thread, не поле `message.graph`. `Thread.parent` относится к иерархии Message и не меняет `Lmx.parent`. Одну идентичность Thread не исполняют конкурирующие workers.

<a id="root-close"></a>
### 8.1. R0 и закрытие

R0 — обычный дочерний Thread верхнего host-каркаса. Служебные данные запуска и настройки принадлежат каркасу и передаются R0 явно; они не добавляются в исходный граф R0. Верхний каркас не имеет родителя, но не получает особого API. Закрытие каскадно проходит через единственный List прямых детей каждого Thread. Общий timeout всего поддерева контролирует host-watchdog; его истечение завершает процесс, а не объявляет частичное закрытие успешным.

<a id="mailbox"></a>
## 9. Почта

Каждый Thread владеет `LmxPost`. `staged` готовит письма текущего хода, успешная граница публикует их в `outbox`, `inbox` содержит допущенные, но не взятые письма. Элемент `inbox` — неразделимая пара `[target, source_arena]`: producer не изменяет арену получателя; владелец присоединяет donor до выдачи target. Отказ сохраняет пару. Порядок допуска — FIFO.

`inbox` — кольцо на отдельном DynamicArray; его backing может перемещаться, но не является графовым адресуемым слотом. Один реентерабельный monitor самого `LmxPost` охватывает admission, take и count. `outbox` и `staged` остаются локальными владельцу. `post` использует эту же почту для обычного вызова LMX, не отдельный транспорт. Языковой API определён в [L3](LMX_semantics.ru.md#thread-message-api).

<a id="own"></a>
## 10. Исполнение Structure

Исполнение использует полную сохранённую Structure. Нативное тело и обходчик должны давать одинаковую семантику чтения, записи, `dirty` и публикации рабочих полей по [L3 §12](LMX_semantics.ru.md#dynamic). Объявленное поле имеет графовое место хранения; присваивание не добавляет слот к уже созданному `Lmx`. Указатели на графовые слоты должны оставаться действительными. Компоновка метода `args/return/var/body` — утверждённая цель миграции v3; её физический ABI здесь пока не описан как реализованный.

<a id="call"></a>
## 11. Вызов

Выбор между нативным входом и обходчиком определяется `Lmx.native` выбранного кода. Вызов получает выбранный `code` и явно либо сокращённой формой выбранный `data`, фактическую арену, `node` как лексического родителя вызываемого вхождения и подготовленные аргументы. В нормальном разделённом вызове используемая исполняемая часть `code` стабильна при доказанном отсутствии путей записи и алиасов, тогда как `data` изменяется; это роли вызова, не квалификатор `immutable` для всей Structure. Одноаргументный `call: code` выбирает его `var`; отсутствие `var` не означает неявное `data = code`, а запись в локальные поля данных тогда отказывает. Явный `call: code code` передаёт это значение как `data` по общему правилу и служит проверкой универсальности Structure и изменения кода для будущей компиляции на лету, не особым исполнительным путём. Для **любой** допущенной пары Structure доступ к полям и публикация уже вычисленных `dirty`-значений используют одну доказанную адресную карту `implements`; совпадение порядковых номеров не предполагается. Контрольная точка пишет готовое значение в выбранный слот `data`, не выполняя выражение или допуск повторно.

Сам вход в `call`, включая `call: code code`, не инвалидирует `native`. Общий путь записи при определённых и допущенных месте и новом значении проверяет зависимости нативных реализаций: прямой путь — при записи, рабочий `dirty` — на контрольной точке публикации. Запись в физический слот и снятие несовместимых входов атомарны для следующего либо рекурсивного dispatch. Рабочее значение до публикации, отвергнутая запись и не меняющий граф вызов не снимают `native`; совместимый вход остаётся и после изменения обычного значения данных. Зависимость может принадлежать охватывающему коду, а не только Structure со слотом записи. Если L2-тело стало несовместимо с прежним входом, требуется подходящая нативная реализация или отказ **до** публикации изменения: обходчик L3 не исполняет L2. Вызов после эффектов не перезапускают другим движком.

Обычная исполняемая форма с именем в `code`, включая `name: ... end: name` и записи внутри inline-`if`/`for`, присваивает значение подготовленному одноимённому месту выбранного `data`. Она не объявляет новое поле в `code`; объявления через `fn`/`fm`/`sub` сохраняют собственный контракт ресиверов. Карта `data` учитывает головы коренного уровня, но не головы внутри их инициализаторов. При одном исходном вхождении головы допустим путь `data\field`, при двух и более требуется `data\[N]field` с нулевым `N`; первое вхождение автоматически не выбирается и несколько одноимённых полей данных не создаются. Вложенность в `code` не выбирает другое место. Произвольный `data` не дополняется при вызове: если требуемого места нет либо голое обращение неоднозначно, отказ происходит при исполнении/допуске вызова, а не из-за самой формы записи при трансляции. Подготовка `var` метода заранее выделяет его поля отдельно. Только явный вызов `call` или вызываемого метода, включая `fn`, создаёт новую область связывания, где собственное поле может затенить внешнее. Внутри одного callable затенения нет: inline-`if`/`for` — операторы той же активации, а не новые области, хотя они тоже Structure.

Нулевой адрес транспортной ячейки аргумента означает отсутствие аргумента; присутствующий аргумент со значением нулевой ссылки остаётся присутствующим. Число передаётся в хранилище объявленной ширины, объектная ссылка — через каноническую ячейку указательного значения. Статус callback и возвращаемое значение различны; контракт результата отличает `void` от присутствующей нулевой ссылки.

<a id="child"></a>
## 12. Резервация ребёнка

Ребёнок строится в собственной арене. До успешной публикации его нет в `Thread.children`; публикация в конце хода добавляет физическую ссылку в этот List, не меняя исходный граф. Неуспех снимает резервацию, но не откатывает произвольные уже сделанные записи графа.

Переподчинение проверяет, остаются ли владельцы используемых ребёнком ветвей `independent: immutable` в новой цепочке Message-предков. Отказ не меняет членство и `Thread.parent` частично. `adopt: msg newParent` выполняет перенос; `independent: msg newParent` отдельно готовит именно этот перенос, копируя только мешающие ветви в арену `msg` и не меняя родителя. Это операции над иерархией Message, не над `Lmx.parent`.

<a id="copy-merge"></a>
## 13. Копирование графа и merge

`merge` строит новый граф с одной картой адресов источник→копия. Карта сохраняет общие цели и циклы, переписывает внутренние ссылки и `parent` на копии и не создаёт отдельного экземпляра для каждого `lnk`. Копируется весь используемый граф, включая исполняемые записи операций; исключение — квалифицированные `independent: immutable` ветви, явно удерживаемые владельцем. Неизменённая подходящая нативная реализация может использоваться повторно только при сохранённом контракте адресов и типов используемых полей. Неполная копия с адресами освобождаемой исходной арены недопустима.

Первый операнд задаёт порядок слотов модели; совпадающее поле следующего операнда заменяет значение этого слота после допуска, новое дописывается в новом результате. Исходные операнды не меняются. Семантика выбора тела и аргументов — в [L3 §20](LMX_semantics.ru.md#composition).

<a id="implements"></a>
## 14. implements

L2 хранит доказанное соответствие между используемыми полями принимающей модели и физическими полями кандидата для любой допущенной пары Structure. Оно нужно для чтения, записи, взятия адреса и прямой публикации готовых `dirty`-значений, включая разные порядки полей; отдельной карты для `call` или `var` нет. На одном структурном уровне одно имя обозначает одно поле; `s\[N]field` выбирает исходное вхождение головы, а не N-е поле данных. Карта не ищет имена в runtime, не копирует кандидат и не отменяет проверок нового Consumer. Семантика допуска и явно заданных тестов — в [L3 §7](LMX_semantics.ru.md#admission).

<a id="gc"></a>
## 15. Сбор

GC принадлежит арене. Корни включают Message, живой граф, почту, состояние исполнения и `Thread.children`; последний List удерживается состоянием Thread независимо от исходных полей. Созданные `independent: immutable` ветви удерживаются владельцем до уничтожения его арены. Простой режим не выполняет сбор. Правило выгрузки позднего модуля требует отдельного контракта и здесь не изобретается.

<a id="special"></a>
## 16. Специальные операции L2

Ядро предоставляет классификацию адреса, выделение ячейки, attach/revert арены, почту, ход Thread, вызов, резервацию ребёнка, копирование/merge и сбор. Эти операции не создают второго пространства имён или вспомогательного графа исполнения.

<a id="lowlevel-scope"></a>
## 17. Машинный профиль

Машинные типы L2 сохраняют представление и числовую семантику соответствующего типа C99 целевой платформы, в том числе знаковость обычного `char`. L3 не получает сырую память только потому, что его граф реализован указателями. L1 имеет отдельную C-подобную поверхность.

<a id="lowlevel-address"></a>
## 18. Адреса, загрузка и запись

M3 упорядочивает плоские объявления как имя, требование/значение. N1–N6 допускают как место во внешней голове (`ptr: @: Model: 0`), так и дополнительную двухпольную форму `@:`: `@: p 0`, `@: p Model`, `@: p Model: 0`, `@: p Model: Other`. Первое поле — атом имени места и не вызывается; второе поле, в том числе вложенный Frame `Model: Other`, потребляется по обычному правилу выражений. Его потребление само по себе не записывает в `Model`. P0 не выделяет эти формы: разбор общий, роли полей задаёт контракт `@:`. Существующие трёхпольные `@: p Model 0` и `@: p Model Other` отслеживаются отдельно в M3; добавление двухпольной формы само по себе их не отменяет. Первое `@: p` или `@: p 0` создаёт void-ссылку; последующая запись адреса не добавляет ей задним числом требование. Указательная глубина `@ⁿ:` не ограничена особым числом.

Унарное `@x` адресует настоящую ячейку значения: для графовой Structure/Array — слот `void *`, содержащий ссылку на дескриптор, для примитива — типизированную ячейку, для формала — его ячейку активации. Слот, его адрес и референт различны. Нативное обращение к графовому ссылочному слоту идёт через `void **` с конверсией хранимого `void *`; разыменование этого слота как `Lmx **` нарушает C99. Адрес не берётся у временного кэша или ABI-буфера. `@x\field` по приоритету означает `@(x\field)`.

Префикс `\p` следует ссылке; `p\field` обращается к графовому полю либо к явно импортированному машинному ABI в зависимости от категории `p`. `@array[i]` адресует реальный элемент backing. В L2 индекс не получает автоматической проверки границ; проверяемый доступ принадлежит L3. Адресная операция не снимает `const`/`immutable` и не продлевает срок жизни цели.

<a id="lowlevel-array"></a>
## 19. Сырое C-хранилище

Токен `c.*` — явная дверь в C. Языковой Array остаётся объектом графа на общей основе `Lmx` с типизированными элементами; сырой C-массив им не становится. Переход между ними требует явной операции, учитывающей форму и время жизни. Типизированные массивы арены — внутреннее хранилище, не ещё один вид языкового Array. L2 не вводит особую сущность `c.array`.

<a id="lowlevel-abi"></a>
## 20. Внешние типы и ABI

`cast: (T) value` — машинное приведение, не проверяемое преобразование L3 и не доказательство границ, выравнивания или времени жизни. `c.name` выбирает внешний C-символ; адаптер определяет параметры, результат и владение. `c.sizeof` означает C `sizeof`, не длину Array и не число полей Structure. `include` и `os` выбирают явно заданные зависимости и платформенную ветвь, не вводя runtime-поиск модулей.

<a id="lowlevel-expression"></a>
## 21. Машинные выражения

Машинный профиль включает группировку, арифметику, сравнения, логику, битовые операции, `++/--`, индекс и обычное управление. `=` в выражении — сравнение; `target: value` — запись. Переполнение и сырой индекс следуют машинному контракту, не обещаниям L3. `a[i][j]` адресует ровный многомерный Array; `a[i]\[j]` следует через ссылку к отдельному Array. `s\[N]field` в Structure-as-data выбирает исходное вхождение, а не машинный элемент Array.

<a id="lowlevel-sync"></a>
## 22. synchronized

`synchronized: lock body` задаёт структурную область взаимного исключения, не открытую пару lock/unlock. Выход освобождает monitor. Почтовый monitor — конкретное реентерабельное применение без `wait`/`notify`; сырых блокировок в чистом L3 нет.
