# Прямой API ресиверов LMX

## Прямые имена единого ядра

Все **61 ресивер и контейнеры** входят в текущее единое ядро. Пользователь
пишет `partial(...)`, `map(...)`, `signatureTypes(...)`, `bracket(...)` напрямую;
ни import, ни выбор версии/варианта набора ему не требуются.

`fun` — только внутренняя группа исходных описаний ядра. Её общий `const:`
блок является точным исходным набором экспортов. Подготовка ядра включает
эти owning-field declarations в штатный корневой namespace и сохраняет
настоящие DATA/parent методов. Это не отдельный runtime registry, не второй
граф и не обязательный вызов import при каждом старте программы.
Квалифицированные физические пути `fun\const\map` и подобные остаются
средством явно выбрать соответствующий встроенный receiver при коллизии имён.

[Полный каталог с сигнатурами и ссылками](CATALOG.md) — нормативная таблица этого
пакета. Частые имена приведены к аналогам других языков:

| Было в предложении | Публичное имя | Смысл |
|---|---|---|
| `lambda` | `curry` | Последовательное связывание аргументов, не синтаксис лямбда-выражения |
| `fold` | `foldl` | Левая свёртка |
| `scan` | `scanl` | Левые префиксные результаты с начальным значением |
| `memo` | `memoize` | Кеширование по явно заданному равенству |
| `around` | `bracket` | acquire, action, finally release |
| `until` | `runUntil` | Не затеняет существующий управляющий `until` |
| `retry` | `retryCall` | Не затеняет существующий управляющий `retry` |

При одновременной видимости одноимённых операций других профилей, например
математических map/filter/contract, используется физический путь `fun\const\map`,
`fun\const\filter`, `fun\const\contract` либо предусмотренный общий выбор декларации. Никакое прежнее
значение таких имён глобально не перезаписывается.

Это аналогия назначения, а не обещание равенства всем деталям Haskell/Clojure.
Например, LMX `curry` поддерживает любое конечное число параметров; распространённый
Haskell `curry` работает с парой. LMX `bracket` здесь синхронный и не обещает
маскирование асинхронных исключений Haskell.

## Два уровня результата

**Фабрики типизированных callable** (`curry`, `partial`, `uncurry`, `flip`,
`compose`, `pipe`, `identity`, `memoize`, `fix`, `lazy`, `once`, `recover`,
`adapter`, `permute`, `overload`, `predicate`, `guard`, `trace`, `contract`)
возвращают `@` на обычный метод. Вызов этого метода имеет построенные полные
типы входов и точный `R`, включая процедуру без результата. Например:

```lmx
@: add5 partial(Addition\add; prefix := (5))
int: answer add5(7)
```

**Операции с динамическим результатом** (`apply`, `foldl`, `force`, `runUntil`,
`retryCall`, `bracket`, `trampoline`) возвращают указатель на типизированную
запись значения. Это не преобразование полезного значения в `int` или в
универсальный числовой box. Чтение выполняется обычным разыменованием:

```lmx
@: result apply(operation := chosen; args := (7))
int: answer \result
```

Для процедуры `apply` возвращает явную запись `void` без payload. Она отличается
от готового нулевого `@`, пустой структуры и неинициализированного примитива.
`force(delayed)` возвращает запись; прямой `delayed()` возвращает исходный `R`.

## Записи, Structure и массивы

`record` — подготовленный постфиксный операнд. `(value record)` возвращает
долгоживущую запись полученного значения; примитив снимется по значению, ссылка
сохранит свою цель. Сложное выражение явно группируют: `((a + b) record)`.
Пустой RHS операнда присутствует как пустой массив, а не пропущенный аргумент.

Structure уже есть массив `@`. `(5; "x"; 1.5)` непосредственно содержит записи
трёх типов. `partial` не требует упаковывать каждую такую запись повторно:
`prefix := (5)` содержит ровно требуемую запись числа. `list(values)` возвращает
саму структуру записей; объект с дополнительным полем `items` не появляется.

`map`, `filter`, `foldl`, `scanl`, `zipWith`, `groupBy`, `traverse` передают
значение записи callback его обычным контрактом. Callback для `double` получает
`double`, callback для строки — строку. Разнородный список допустим, если
выбранный callback имеет соответствующий контракт/диспетчеризацию для каждого
элемента; само слово «общий» не отменяет проверки типов.

Плотный `Array<int>`, `Array<double>` и строка не объявляются массивом ссылок.
Они могут быть значениями элементов; для поэлементного преобразования плотного
массива в структуру нужно явно материализовать записи элементов штатным
механизмом. Автоматическое `reinterpret_cast` в ядро не вводится.

## Контейнеры

| Контейнер | Физические поля | Операции |
|---|---|---|
| Maybe | `present:int`, `value:@record` | `some(value)`, `none()`, `bind(input;next)`, `traverse(items;next)` |
| Result | `ok:int`, `value:@record`, `reason:@record` | `ok(value)`, `err(reason)`, `bindResult(input;next)` |
| List | сама Structure / Array<@> | `list(values)`, `map`, `filter`, `flatMap`, `foldl`, `scanl`, `zip`, `zipWith` |
| Bounce | `done:int`, `value:@record`, `next:@callable` | `done(value)`, `more(thunk)`, `trampoline(current)` |

`some(value := (5 record))` хранит число, `some(value := ("x" record))` — строку.
`present=0` означает отсутствие; присутствующий `@0`, ноль, пустая строка и
пустая структура отсутствием не становятся. `bind` для Maybe не выдаётся за
единую реализацию всех монад: для Result есть `bindResult`, для List — `flatMap`.
Контейнерные законы зависят также от переданных функций и их эффектов.

`more` принимает nullary callable; `partial(F; prefix := allActualRecords)`
создаёт его для любого `F`. `trampoline` останавливается по `done`, а не по тому,
является ли итоговый результат callable. Callable как значение не запускается.

## Границы текущих фабрик

Сигнатуры анализируются и строятся из текущего графа; знание всех типов при
трансляции не требуется. Точный R и проверка actuals используют обычный механизм
приёма LMX. Слово «статическая» в отчёте проверки пакета относится к проверке
текста и комплектности, а не к системе типов языка.

У сгенерированных callable текущих исходников все оставшиеся входы required/private.
Поэтому фабрики сохраняют полный порядок и требования типов, но не все способы
пропуска actuals исходного callable: default/autofill исходного F не переносится
в остаточный pN. Даже `partial(F; prefix := ())` не обещает поведение F() при
отсутствующих actuals. `uncurry` строит промежуточные Ti → @; допустимость более
узкого результата ступени определяется обычным admission, без специального
стирания требований. Это ограничения адаптеров, не ограничения динамики LMX.

## Именованное объявление и конструктор типов

Для интроспекции используется `signature(operation := F)`, для построения из
типовых токенов — отдельное прямое имя `signatureTypes`:
`R signatureTypes T0 T1 ...` либо
`signatureTypes(left := resultToken; right := inputTypeRecords)`.
`left` явно означает result, `right` — только inputs. Имя результата не
угадывается по первому/последнему элементу вектора. Раздельные имена избегают
непроверенного overload двух одинаковых const-экспортов и сохраняют однозначные
физические пути. Прежнее публичное имя конструктора удалено без alias.

Единственная форма именованного объявления:

```lmx
Name :: (int: x; double: y; return: double)
```

Новый оператор имеет вид **`R signatureTypes T0 T1 ... TN`**: слева токен результата, справа
все токены входов. Его явная квалифицированная форма:

```lmx
@: requirement fun\const\signatureTypes(left := resultToken; right := inputTypeRecords)
```

`Name :: Signature` заменяет прежний declaration receiver полностью;
старого написания и совместимого alias больше нет. Слева от `::` расположен
объявляемый name atom, а не чтение существующей переменной. Справа — обычный
DATA-шаблон сигнатуры. Это объявление само не исполняет callable.

`::` — обычный операнд выражения LMX, обнаруживаемый через общий
`OPERANDS_TEMPLATE`, а не специальный синтаксический разделитель. Он не открывает
Frame: левое имя не создаёт цель `end:`, границы берутся у обычного выражения. Общий режим
сохранения форм (`PASS_ARGS_AS_IS = 1`) передаёт левый объявляемый идентификатор
декларационному потребителю, не читая его как существующую переменную.
Границы правых аргументов остаются написанными:

```lmx
Name :: A B       # right.length = 2: A, B
Name :: (A B)     # right.length = 1: одна Structure с A и B
```

Эти две формы не эквивалентны. Определённый здесь именованный контракт принимает
**один** правый DATA-шаблон (`Name :: DATA`, включая `Name :: (...)`). Анализ его
полей извлекает входы и результат сигнатуры и не является раскрытием аргументов
операнда. Для нескольких правых аргументов новая сигнатурная семантика этим
пакетом не вводится. P0 сохраняет обе написанные формы; результат функции тоже
не открывается. Конструктор `signatureTypes` отдельно имеет явно заданные
`left = result` и `right = inputs`; это его собственный контракт.

`signatureTypes` является обычным обнаруживаемым type-token операндом;
он не разделяет имя с существующим reflection receiver `signature`. Квалифицированный вызов выше
передаёт ему явные left/right; операндная запись получает их общим механизмом.
Существующее отношение именованного описания с `call` не меняется.
В прочих применениях — хранение, передача, `satisfies`,
ограничение ссылки, `signature` и все новые ресиверы — оба конструктора дают
одно и то же **семантическое** требование. Сравниваются число и порядок полных
типов входов, наличие и полный тип результата. Имена, defaults и текст тела не
становятся частью тождества. Имена сохраняются для обычной адресации actuals;
синтетические `p0`, `p1`, ... отображаются по позиции на реальные входы.

Готовая `int`-запись токена содержит код требуемого типа. `uninit:T` читается по
тегу без обращения к отсутствующему payload. Полное существующее описание
сохраняет модель ссылки/массива/функции и квалификаторы; голый физический код `@`
не заменяет такую модель. `void` обозначает отсутствие результата, не последний
входной тип и не числовой нуль.

P0 ничего не раскрывает. Для единственного исключения нужны все три условия:
**написанная безымянная Structure слева**, **right.length = 1** и **написанная
безымянная Structure в right[0]**. Снимается только её внешний правый контейнер,
один уровень. Left остаётся целой Structure; вложенные правые контейнеры повторно
не открываются. Результат функции, именованная ссылка и произвольный массив
по этому правилу не раскрываются. Поэтому `R signatureTypes (T0 T1)` при обычном
левом токене содержит один правый контейнер; для вектора типов используют
явный `fun\const\signatureTypes(...; right := types)` либо записывают цепочку типов без обёртки.
Это не меняет W/E обычного вызова callable.

## Ошибки

В языке исключение проходит через объявленные `throws`; набор ресиверов ядра не вводит
`throws:*`. Общий мост `attempt` перехватывает только явно объявленные исходы
целевого callable и возвращает `Outcome {ok,value,failure,payload}`.

Обычные операции, возвращающие запись (`apply`, `bind`, `map`, `bracket` и т.п.),
передают произвольный пользовательский исход как **`FxCallFailure(outcome)`**.
Изначальные имя и типизированный payload сохранены внутри. Пример обработчика:

```lmx
catch: FxCallFailure (@: outcome)
    # outcome\failure — исходное имя; outcome\payload — исходная запись.
```

Это явный контракт такой границы, а не утверждение, что `catch: OriginalName`
без изменений перехватит оболочку. В создаваемых типизированных адаптерах
`FxWrap` ловит внутреннюю оболочку и поднимает исходное имя в CODE с заранее
вычисленным списком `throws`. Прямые `curry/partial/flip/uncurry` также сохраняют
заявленный контракт своих генерируемых ступеней.

`FxTypeToken`, `FxKernelFailure`, `FxArity`, `FxIndex`, `FxRecordArity` обозначают
ошибки типов/строительства/формы; `FxShape`, `FxLazyCycle`, `FxPredicate`,
`FxNoMatch`, `FxAmbiguous` — явные ядерные условия. Структурные операции
сохраняют `ReceiverIndex`, `ReceiverPermutation`, `ReceiverPatchBase`,
`ReceiverPatchFormat`, `ReceiverParent`. Все они должны быть корректно отражены
в `throws` вызывающего примера. Системные implicit failures не объявляются
обычным Result и не подлежат безусловному retry.

## Состояние и исполнение

Кеши `lazy/once/memoize`, префиксы и self `fix` принадлежат обычным структурам
состояния в одном Message. Это не потокобезопасное общее состояние Thread.
Межпоточные сценарии используют существующие Message и транспорт, а не
общий изменяемый кеш. Адаптер не создаёт скрытый lexical environment чужой
завершённой активации. Native обновляется только явной компиляцией; старый ABI
с изменённым DATA не переиспользуется автоматически.

## Сравнение размеров кода

Принадлежность к ядру сама по себе **не делает реализацию бесплатной** в
сравнении. Её можно исключить из usage-листинга, только если контрольный язык
тоже пользуется библиотекой или обычным оператором, инкапсулирующим ту же работу.
Если контроль показывает собственную реализацию, сравнивается соответствующее
тело LMX и учитываемое замыкание его зависимостей; короткий вызов ядра сохраняется
как дополнительный вариант. Основным выбирается самый короткий из **честно
сопоставимых** вариантов, а второй вариант не удаляется.

При этом архитектурно оптимальный LMX не переписывается ради совпадения алгоритма
контрольного языка. Собственные общие примитивы LMX — copy, merge, binding,
обычный вызов и работа с графом — законно остаются примитивами языка; их runtime
реализацию не разворачивают в каждом сравнительном листинге. Проверка границы
касается сокрытия специфической работы helper за коротким вызовом, когда другая
сторона показывает эту работу вручную, а не требования одинакового алгоритма.
