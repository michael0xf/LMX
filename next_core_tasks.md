## 0. Architectural doctrine (AUTHOR-ARCH-DOCTRINE-20260922-17)

**Mandatory for the current docset and all later implementation.** Every decision must be architectural, not a local patch. When a required contract is missing, **STOP and ask the author directly** — never fill the gap with a name-special parser branch, allowlist, header scanner, hidden registry, shim, fallback, or an extra field in a base kernel type.

Explicit anti-patterns and replacements:

1. **`c.*` is a raw door into C, classified per TOKEN.** Every token spelled `c.*` is a raw C name; every non-`c.*` argument inside the construct stays an ordinary L2 expression under general L2 lowering. So `c.printf("%d", x)` has a raw head and an ordinary L2 argument, and `c.sizeof(c.LmxArena)` passes both tokens raw for C to interpret. Classification is never by concrete name. The translator must not separately recognize `c.sizeof` / `c.puts` / other names, parse `*.h`, or construct an "allowed C" dictionary. Invalid raw C is diagnosed by the C toolchain. Lmx needs use ordinary language receivers/libraries, not `c.*` special semantics.
2. **Base Array** keeps its minimal invariant (`{len, data}`). Dynamic growth belongs to a separate List/ArrayList implementation. Never add capacity or policy fields to Array for one consumer.
3. **Base Message** stays minimal kernel graph/scheduling/message machinery. Win32 UI and application state belong in adapters/application structures referenced through ordinary composition — never embedded into Message.
4. **Similar future demand:** add a separate type/receiver/library/adapter at the correct layer; do not mutate the lower abstraction.
5. **Поправка автора (2026-09-25, дословно в блоге):** слово `Lmx.native` — прямая ссылка на нативную реализацию тела, после `parent` в конце `Lmx`; это не лексический элемент и не поле графа, а снятие скрытой формы `child[0]`-дескриптора; сигнатура — обычное поле графа в `data`. Доктрина остаётся в силе для агентов: это разовый рефакторинг автора, не прецедент и не разрешение добавлять поля; см. §3 «Пара исполнения code/data» п.8.

Dictionary stable-ids: [`architectural-placement`](next_core_tasks_dictionary.md#architectural-placement), [`clean-kernel-acceptance`](next_core_tasks_dictionary.md#clean-kernel-acceptance). Existing violations are **cleanup debt** blocking the clean-kernel checkpoint before self-build.

Dictionary: [
o-defensive-kernel](next_core_tasks_dictionary.md#no-defensive-kernel) — kernel invariants by construction/tests; no defensive close state machines in base kernel types.

**`sizeof:`:** **введён** L2 language receiver-operator (AUTHOR-SIZEOF-DESIGN-20260922-20 / FABLE-GROKBOT-INCLUDE-AND-SIZEOF-20260923-123 part2); not a callable; no global-contract HOLD/OPEN. **Семантика (автор, Q16, 2026-09-23):** размер хранилища значения/типа в БАЙТАХ (для own-массива — все элементы), операнд — L2-значение или тип, разрешаемый транслятором; `length` — число элементов; `c.sizeof(...)` — сырой C через дверь `c.*`.

### Дескрипторы динамических массивов (автор, Q18, 2026-09-23; `LMX_blog/2026-09-23.md`, `q18.md`)

Общее правило автора: базовый дескриптор массива — только `{size_t len; T *data}` без capacity; **любая динамическая реализация, которой нужна capacity, заводит новый описанный тип** `{<T>Array array; size_t capacity}` (пример автора: `Array {size_t len; void *data}`, `DynamicArray {Array array; size_t capacity}`); в C — отдельный дескриптор на каждый тип элемента одной формы, дескрипторы одного типа лежат в арене в своём массиве однотипных дескрипторов. **Уточнение автора (тот же день):** каждый дескриптор динамического массива заводится единообразно по этому правилу **с использованием уже существующего дескриптора фиксированного массива** данного типа как поля `array` — не новый параллельный тип; для void — тот же тип, что вложен в `Lmx` (сегодня `LmxArrayDesc`, единое имя после переименования; сама раскладка `Lmx` — отдельная работа, не эта); по коду не плодить дублёров — всё унифицировать: если типизированный фиксированный дескриптор для `T` нужен и его нет, он заводится один раз и используется и фиксированными массивами `T`. **Второе уточнение автора:** `void` в примере — просто один из типов элементов: дескриптор массива `int` — `{size_t len; int *data}`, никогда не void-дескриптор с приведением; void-дескриптор — только для массивов элементов `void *` (включая вложенный в `Lmx`). Режим и очерёдность — координатор.

  1. **Роль — позиция в исполнении, не свойство Structure.** Пара исполнения = ровно два обычных `Lmx *`: Structure в позиции головы — код (`f(a b)`), Structure в позиции аргумента — данные; та же `f` в `merge: f other`, `send: f` — данные. Слов `code`/`data` в языке нет — это термины спеки для ролей, не виды, квалификаторы или классы хранения. Явный `execute(code, data)` не вводится: вычисленный код связывается (`someCode: selectCode(…)`), затем `someCode(someData)` — обычное правило callable-priority (-130); исполнять несвязанную Structure на месте не нужно (инстанцирование — `Model: fresh`, код — связывание). **Автор (2026-09-25, дословно): «Никакого третьего “callable context graph”.   2. **Код неизменяем в части операторов:** исполнение никогда не пишет в узлы операторов, литералы и слово `native` — только в объявленные поля (`(3 + y) → 7` идёт в поле `x`, не в узел выражения); именно поэтому один граф может быть и кодом, и данными. **Данные — обычная Structure:** объявленные поля тела в лексическом порядке (прототип данных метода — «Pascal var»); вложенные тела `if`/`for`/… — вложенные Structure только с полями, чтобы `M\for\y` остался тем же путём; ни одного оператора.   3. **Вложение данных = вложение кода (выбор автора).** По умолчанию данные вызываемого — его собственный граф: слот лексического родителя, отвечающий этому callable, держит сам `M`, и `M\x` снаружи читает его поля. Свежий экземпляр прототипа (только поля; вложенные тела — вложенные Structure полей) создаётся лишь при повторном входе или при явно переданных данных, живёт в кадре активации и снаружи не виден. `node\x = data\parent\x` — статическая цепочка по `parent`, ничего третьего. Данные корня — сам граф файла (R0, R0).
  4. **Активация = «какие данные передали» (Q28 = второе, автор 2026-09-25).** Обычный вызов исполняет `M` над его собственным графом: объявления кода пишут в поля `M` по порядку, фактические аргументы идут обычной машинной активации (связанный формал берёт значение из данных), код пишет прямо в переданные данные. Свежий экземпляр прототипа создаётся только там, где транслятор не может исключить повторный вход — рекурсия в статическом графе вызовов, динамический вызов по ссылке — или когда данные переданы явно (`merge`/PAP, `Model: fresh`, Structure над чужими данными); такой экземпляр виден только из своего кадра, результат через него не читается; одна Structure, переданная двум активациям, делится ими. Поле, объявление которого в этой активации не исполнилось (не взятая ветка), хранит значение прошлой активации. **Кто передаёт данные — всегда вызывающий, явно (координатор, по OPEN Opus -189 c3):** статический CALL вне цикла статического графа вызовов (включая CALL корня) — data = сам M; статический CALL внутри цикла (повторный вход) и любой динамический вызов по ссылке — data = свежий экземпляр от примитива ядра `lmx_fresh(code)` (та же операция, что `Model: fresh`: копия объявленных полей по раскладке `lmx_plan`, parent = parent кода, без операторов; Grok -188 к.3); транслятор помечает CALL-узлы op-дерева и сайты нативного кода (Opus c3a); трамплин ничего не решает, он получает data аргументом (`self` нативного входа). «Копия на входе / запись на выходе» (21.5/21.6), `dirty`, load, checkpoint, sticky/active selector (§5) исчезают: куда попала запись, решает то, что передали, а не флаги. ### Callable: формирование аргументов/результата до точной сигнатуры; `return` вложенного callable через merge (автор, 2026-09-24; дословно в `LMX_blog/2026-09-24.md`)

Текст автора (дословно):

````text
Нужно внести два связанных изменения в спецификацию и реализацию callable.

1. Требуется: применять обычные правила формирования аргументов и результата ДО проверки конечной callable-сигнатуры
Сейчас в §6 implements фактически требует буквального равенства исходных callable-сигнатур:

sig(aVar.p) = sig(bVar.p) = ExpectedSig(Consumer, p)
а §7.13 отдельно говорит, что converter table не влияет на exact callable signatures.

Это надо изменить.

Смысл должен быть таким:

При прямом вызове и вызове через переданный callable аргументы сначала формируются по общим правилам подстановки и присвоения, включая доступные преобразования и проверки их контрактов. Точное соответствие дескриптору реально выбранного вызываемого выражения требуется после формирования аргументов. Различие исходных типов само по себе не является основанием для отказа, если требуемые аргументы могут быть сформированы по обычным правилам языка.

Возвращённое значение принимается по тем же общим правилам, включая преобразование к типу, требуемому получателем результата.

То есть не надо создавать специальную систему covariance/contravariance или отдельный механизм adapter для callable. Это обычное формирование аргументов и обычное принятие результата, которое уже существует для значений.

Требование конечного точного соответствия можно сохранить. Меняется только точка, в которой оно проверяется:

actual source value
    ↓
ordinary assignment/substitution rules
    ↓
conversion if explicitly available
    ↓
formed argument
    ↓
exact match with selected callable argument descriptor
И аналогично для результата:

selected callable result
    ↓
ordinary receiving/assignment rules
    ↓
conversion if explicitly available
    ↓
value required by the result consumer
Изменение текста §6

sig(aVar.p) = sig(bVar.p) = ExpectedSig(Consumer, p)

invoked_callable(p) ⇒
````
