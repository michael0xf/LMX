# Q51. Точный контракт доступа после «локальные объявления не есть внешние поля»: именованная Structure-процедура, вложенное тело, путь из другого метода

Состояние: 2026-09-28, fable_pc по заданию автора `docs/new_parts/local_declarations_and_explicit_initialization.to_fable.en.md` (§1: «If the current rules do not distinguish the required cases, identify that conflict and ask the author»; §4: «Show explicit structural inspection where that is intended, or ask about the precise access contract»). Решённое применено: объявление в исполняемом теле метода (`fn`/`sub`/`fm`) — локальная переменная, `M\i` снаружи её не открывает, объявление и присваивание остаются в полном графе, инспекция структуры их находит; инициализация вычислением — два оператора; присваивание не создаёт поля. Ниже — три случая, которые нынешние правила не различают.

## 1. Именованная Structure, исполняемая как процедура (Q45)

Книга §11 (до правки): «структурный путь через callable Structure (`Counter\n`) читает её опубликованное поле и не исполняет её». Q45 (2026-09-28): именованная Structure — процедура без аргументов и результата. Записка §1: объявление в исполняемом теле — локал, не внешнее поле; §1 же: «не обобщать локальность исполняемого тела в запрет явно построенных записей данных».

```text
Counter:
    size_t: n 0U
    n: n + 1U
return
Counter
size_t: once 9U
once: Counter\n        # 1 сегодня (unit_named_struct_exec и ещё ~20 строк семейства)
```

По чтению «тело процедуры — локалы» `Counter\n` снаружи — не обычный доступ (остаётся инспекция структуры); по чтению «именованная Structure — запись данных, её объявления и есть её поля» — обычный доступ, 1. Вопрос: поля именованной Structure, которая исполняется как процедура, — обычные внешние поля (запись данных с кодом рядом) или локалы её тела?

## 2. Локал вложенного тела из объемлющего метода

Книга §12, пример `for`/`print`: `int: j i` объявлено в теле `for`, после `end: for` тот же метод читает `for\j`. Сегодня транслятор отказывает «unresolved name» (7b-3). По записке, локал вложенного тела снаружи этого тела — не обычный доступ; объемлющий метод — «снаружи» вложенного тела или его «допустимая область»?

```text
fn: test () int
    int: acc
    for: int(i, 0) (i < 10) i++
        int: j i
        acc: j
    end: for
    print: acc for\j       # обычный доступ (пример книги) или нет?
```

## 3. Явный путь из другого метода в локал метода

Свидетели рабочего состояния 7b-1 (записка Opus, W3 и W11) и трасса S/I2 книги §12: вложенный вызов пишет `test\x: 7` в объявленное поле `test`, пока `test` активен, и книга объясняет через это «после вложенной записи `node\x` рабочее голое `x` вызывающего сохраняет прежнее значение». Если `test\x` из другого метода — не обычный доступ, чем пишут «явную запись в граф» для этой трассы: путём `node\x` из вложенного тела того же метода (лексически внутри), инспекцией структуры, или такого явного пути к локалу метода нет вовсе (и тогда трасса переписывается на объявленное поле единицы/записи данных)?

## Один вопрос на все три

Что есть «допустимая область» локального объявления (§1 записки): только тело, где оно объявлено, и вложенные в него тела; или также объемлющее тело того же метода (случай 2); и есть ли у объявления в теле процедуры-Structure (случай 1) статус поля записи данных? Для случая 3 — какой путь считать явной записью в хранилище объявления.

## Ответ автора (чат fable_pc, 2026-09-28; дословно — `LMX_blog/2026-09-27.md`, запись Q51)

На случай 1: «что такое внешние поля? Почему у вас структура по-прежнему что-то особенное, а не процедура без аргументов и возвращаемых значений? Вы не должны иметь ничего кроме просто структур явно объявленных в языке. Если вы рядом со структурой LMX заводите неявный параллельный контейнер каких-то данных — убирайте его. Наша цель сделать чтобы код и данные лежали точно так как они написаны. В том же порядке». На «один вопрос»: «Обыкновенная видимость вперед и "вниз" (то есть вложенные тела). Каким образом локальное поле будет видно наружу? Как раз доступ снаружи мы тут обсуждаем (этот доступ в обычной работе со структурами только к месту объявления, весь остальной граф для интерпретатора нужно держать там же и в том же порядке как он виден в коде)».

## Остаток — одно чтение на одном примере

Сегодня строка гейта даёт 1:

```text
Counter:
    size_t: n 0U
    n: n + 1U
return
Counter
size_t: once 9U
once: Counter\n
```

Читает ли `Counter\n` из ROOT место объявления `n` — ячейку, лежащую в Counter там, где написано `size_t: n 0U` (после публикации 1)? Тогда пункт 3 свидетельств записки («`M\i` снаружи не открывает локал») читается так: не рабочую переменную активации и не узел инициализатора, а только место объявления; семейство `unit_named_struct_exec`, `for\j` после `end: for` (книга §12) и `test\x` из другого метода (W3/W11, трасса S/I2) остаются, а отказ «unresolved name» на `for\j` — пробел транслятора. Или локал `n` снаружи Counter не открывается ничем (отказ)? Тогда эти строки и примеры переписываются как отказы.

## Окончание (автор, чат fable_pc, 2026-09-28)

«локал `n` снаружи Counter открывается потому что он объявляется там size_t: n 0U -- объявление у нас в любом случае заводит значение». Первое чтение остатка верно: путь снаружи читает место объявления. Закрыто.
