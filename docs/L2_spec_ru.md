# Спецификация L2

L2 задаёт механизмы ядра и машинные операции. Семантика L3 определяется в [спецификации LMX](LMX_semantics.ru.md), синтаксис — в [грамматике](LMX_grammar.ru.md), понижение в C99 — в [L1](L1_spec_ru.md). Этот документ не повторяет правила разрешения голов, объявления и вызова. Состояние реализации — в [заметках](implementation-notes.ru.md).

**Состояние реализации, 2026-11-14, срез392:** ограниченные кодовые gates общего borrowed receiving/name reader пройдены;
G2 render35/14 и оба snapshots, docs-check01/final index02 PASS; generated semantics/grammar unchanged. Commit/push далее.
Model/default сохраняются как исходное описание, `c_names` — только проекция ролей; это не typed storage/admission
или объединение aliases. Полные M11/M13/M14 OPEN. [Контракт и проверки392](kernel-implementation.ru.md).
Этот абзац описывает реализацию прежней нормы (до 2026-11-19); действующая норма — [структурный вызов](LMX_semantics.ru.md#structural-call) и [связывание](LMX_semantics.ru.md#binding-places); замена — [план](../next_core_tasks_v3.md#binding-callables-20261119).

**Норма 2026-11-19 (связывание и вызываемые).** Автор принял норму в [ТЗ](new_parts/LMX_Fable_TZ_Binding_and_Callables_v2_2026-11-19.md); транслятор, интерпретатор чистого графа, ядро, примеры и тесты её ещё не исполняют, работы записаны в [плане](../next_core_tasks_v3.md#binding-callables-20261119). Нормативные абзацы §§ 2, 8.1, 10, 11, 14, 18 и 20 ниже изложены по новой норме; абзацы о фактической реализации сохранены и помечены.

<a id="scope"></a>
## 1. Предмет

Целевая цепочка — L3 со вставками L2 → генерируемый L1 → C99. L1 является промежуточным языком. Интерпретатор исполняет сохранённый граф: код L2 — с теми же проверками, что и код L3, а адресную операцию, которой в L3 нет вообще, — со своими проверками. Нативный код L2 компилируется без этих проверок ([семантика, §1](LMX_semantics.ru.md#scope)).

<a id="lmx"></a>
## 2. Структура `Lmx`

Общая основа Structure и Array — плоский заголовок `parent/length/storage`, без native, capacity
и вложенного VoidArray. В порядке L2: `@: parent Lmx`, `size_t: length`, `@: storage void`.
Ссылка указывает на начало заголовка; код типа записи стоит в четырёх байтах
перед ним ([§3](#value-record)). Structure и Array<@> хранят элементы void* и полностью
взаимозаменяемы: индексирование, именованные пути, допуск, копирование и исполнение общие.
Числовой Array<T> хранит сами T; тип элементов сообщает код записи Array.

Parent — структурный родитель. Передача ссылки на существующее значение не меняет parent и
не раскрывает его в дерево. Для Structure `C`, исполняемой в роли кода, роль данных выполняет её
фактический parent ([§11](#call-receivers)). Дескриптор массива сохраняет адрес; length и storage изменяются общим
механизмом. Отдельный фиксированный контракт Array и особый растущий List отменены.
Native-дескрипторы находятся в таблицах call; поле native у `catch` и у исполняемой Structure — обычная ссылка на них,
добавляемая при трансляции, если её нет. Прежний перечень `fn/sub/catch` сужен, потому что исполняемых `fn` и `sub`
больше нет ([снято](LMX_semantics.ru.md#removed-builtins); чтение исполнителя). Прочим Structure поле автоматически не добавляется.
[Норма](LMX_semantics.ru.md#explicit-compilation), [открытая миграция M13](../next_core_tasks_v3.md#flat-lmx-descriptor).

<a id="interpretable-tree"></a>
### 2.1. Интерпретируемое дерево

Чистый граф сохраняет написанные объявления, операторы, значения и вложенные тела; его порядок
не меняется ради выпуска C. Примитивной ячейке не нужна дополнительная leaf-обёртка. Имена находятся
в общей таблице адресов канонических строк, а не внутри Lmx. Роль кода исполняет выбранная Structure, роль данных — её фактический parent ([§11](#call-receivers)).
Прямой проход data исполняет только корневые ресиверы объявления по общим правилам; ресиверы `private`, `required`, `const`, `immutable` и `independent` при этом исполняются, и переменные, которые им переданы, считаются корневыми ([семантика](LMX_semantics.ru.md#data-root-declaration-execution)).

Граф можно строить и менять обычными операциями. Запись не отслеживается ради native, не проверяет
будущую исполнимость и не запускает компиляцию. Проверки чистого графа выполняет сборщик и его явно
вызванные sys-инструменты. Обходчик исполняет допустимый L3; обновление машинного исполнения задаёт
явная компиляция. `sys\toLmx(S)` сохраняет выбранную S в текущем виде, не восстанавливает старый исходник.
Подробности — [семантика](LMX_semantics.ru.md#source-codec).

<a id="get-descriptor"></a>
### 2.2. descriptor и настоящие поля заголовка

`sys\descriptor(S)` возвращает обычную Structure адресов живых полей S. Без аргумента выбирается
data текущего запуска (parent исполняемой Structure), в том числе внутри вложенных тел управления. Code передаётся явно.

```text
(
    @@: parent Lmx
    @: length size_t
    @@: storage void
)
```

Машинные типы — Lmx**, size_t*, void**. `\(d\length) := n` меняет S.length;
`d\length := p` меняет только указатель в d. Это не копия, прокси или write-back.
Запись length сама не выделяет storage; согласованный размер меняет sys\resize.
Native и capacity не входят в результат: это не поля заголовка. Получение descriptor не продлевает
жизнь S. Адрес первого поля может совпадать с S, но типизированное разыменование не считает его
вторым самостоятельным Lmx. Глубина указателей произвольная конечная.

<a id="header-receivers"></a>
### 2.3. Чтение заголовка и служебных таблиц

parent(S), length(S), sys\storage(S) читают непосредственно parent, length, storage.
sys\native(S) возвращает обычный native-дескриптор из таблиц call, включая варианты сигнатур,
или 0 при отсутствии. sys\capacity(S) читает вместимость в элементах из таблицы арены.
Эти запросы не строят вспомогательный descriptor. Все формы без аргумента выбирают текущую data;
для code аргумент явный. Запись с такой головой в data остаётся обычной Structure, как путь `D\for` к полю данных `D`.
Обычные пути S\parent, S\length, S\storage и S\native выбирают записанные поля, без псевдополей.

Code исполняет выбранная Structure, data — её фактический parent ([§11](#call-receivers)); node — зарезервированная операция и существующий контекст активации.
sys\resize(S, n) меняет длину и обеспечивает storage; sys\reserve(S, n) обеспечивает вместимость
без изменения длины. Все вспомогательные операции находятся в sys, не резервируют глобальные имена.

<a id="system-indexof"></a>
### 2.4. Индекс поля

`sys\indexof(field parent)` возвращает физический индекс единственного вхождения `field` среди
непосредственных элементов Structure `parent`. Если поле отсутствует или та же ссылка встречается
несколько раз, операция сообщает ошибку по общим правилам отказа.

`sys\indexof(field index parent)` выбирает вхождение той же ссылки с номером `index`, считая с нуля,
и возвращает его физический индекс в `parent`. Если указанного вхождения нет, это ошибка.
Номер вхождения и возвращаемый индекс — разные величины: при вхождениях одной ссылки в позициях
2 и 5 вызов с `index = 1` возвращает 5. Обе формы получают `parent` явно; формы без аргументов нет.

Искомое поле определяется его идентичностью/ссылкой, а не совпадением имени или примитивного значения.
Поиск не следует вложенным структурам или графовым ссылкам. Для Structure и Array<@> действует один
механизм чтения непосредственных элементов. Использовать существующую адресацию; отдельная таблица
обратных индексов и её обслуживание при записях не нужны.

<a id="value-record"></a>
## 3. Запись значения: тип рядом со значением

**Решение автора 2026-11-16** ([журнал](../LMX_blog/2026-11-16.md#typed-value-raw-layout)): физический тип и значение хранятся в одной записи, и оба берутся из самой записи. Прежняя схема этого раздела — ячейка без тега типа, тип которой арена узнавала классификацией адреса по зарегистрированным диапазонам — отменена. Код пока исполняет прежнюю схему; переход — [M15](../next_core_tasks_v3.md#typed-value-records).

Значение, на которое ссылается слот Structure или `Array<@>`, ссылка или `parent`, — **запись**: `int type`, код физического типа, и сразу за ним, без промежутка, ровно столько сырых байтов, сколько занимает значение этого типа — число, ссылка либо дескриптор `parent/length/storage` Structure или Array. Элементы Array и слоты Structure лежат в хранилище, которое называет дескриптор, а не в записи. Размер записи равен `sizeof(int) + size(type)`: место под самый большой вид значения не резервируется, раскладка не следует правилам `union` языка C.

Из этого следует, как объявление примитива лежит в графе. Запись `int: x 10` не помещается в граф записью ресивера `int` с аргументами: она и есть элемент Structure — запись «тип `int`, значение 10», а имя `x` держит строка «адрес → имя». Объявление однозначно восстанавливается по типу, значению и имени, поэтому в пути к такому полю нет шага ресивера: `S\x`, а не `S\int\x` ([семантика](LMX_semantics.ru.md#primitive-declaration-is-the-element)).

Каждый слот, как и любая другая ссылка графа, хранит один указатель: адрес значения. Код его типа стоит в четырёх байтах вплотную перед этим адресом (ответ автора 2026-11-16, [журнал](../LMX_blog/2026-11-16.md#typed-value-reference-answer)). Поэтому адрес сохраняет прежний смысл — адрес ячейки `int`, адрес заголовка, — и `@x`, `parent`, таблица имён и дверь C пользуются им без изменений. Чтение известного типа берёт значение по указателю; чтение типа, неизвестного при трансляции, читает код четырьмя байтами раньше и затем значение:

```text
p = storage[index]     # слот: адрес значения
код по p - 4           # код физического типа
значение по p          # сырые байты этого типа
```

**Ни одна операция не узнаёт тип и не читает значение классификацией адреса.** Чтение и запись слота, загрузка значения с типом, неизвестным при трансляции, `sys\typeof`, индексирование, разыменование, допуск `implements`, копирование, `merge` и сборка берут вид и размер значения из кода в его записи. Индекс интервалов адресов остаётся у арены только для владения: какой арене и какому куску принадлежит адрес.

**Выравнивание** (автор оставил выбор реализации: оптимальное и универсальное, не по правилам `union`). Значение стоит по адресу, выровненному так, как требует его тип, но не меньше чем на четыре; код занимает четыре байта вплотную перед ним; заполнение, где оно нужно, лежит между записями. Поэтому код и значение читаются и пишутся обычными типизированными выровненными обращениями на любой платформе, а не копированием байтов, и поля дескриптора сохраняют естественное выравнивание. При восьмибайтовых указателях запись `int` занимает 8 байт, запись `double`, `size_t` или ссылки — 12 байт при шаге 16, дескриптор — 28 байт при шаге 32. Измеренное основание — в [записи исследования](../steps/witnesses/typed-value-research-20261116/notes.md): для восьмибайтового поля в пределах кеша типизированное обращение к выровненному значению стоит 0,97 нс, копирование его байтов — 2,20 нс.

Перечень физических типов — прежний перечень типов областей ([спецификация ядра §2.2](kernel-implementation.ru.md#arena)): числовые примитивы, слово, ссылка, «T без инициализации», обычная, неизменяемая Structure и результат `fn`, Array со своим типом элементов. Модель пользователя своего кода не порождает: совместимость моделей устанавливает `implements`, а не физический тип. Обычная и `immutable` Structure различаются кодом; уже опубликованная обычная Structure не становится `immutable` на месте. Старое расположение, где `Lmx` содержит `VoidArray`, остаётся переходным, а не образцом для новых разновидностей Array. Строка «результат `fn`» этого перечня описывает прежнюю норму (до 2026-11-19): исполняемого `fn` больше нет, результат описывает поле `return` в данных; действующая норма — [`return` в данных](LMX_semantics.ru.md#return-in-data); замена — [план](../next_core_tasks_v3.md#binding-callables-20261119).

Числовой `Array<T>` хранит сами T, плотно и без кодов; тип элементов сообщает код записи Array. Адрес такого элемента — сырой адрес L2, а не указатель на запись. Типизированный native-локал и временный результат — обычные машинные значения и в запись не упаковываются.

Для каждого примитивного типа T есть отдельный тип «T без инициализации». У объявления без начального значения одна запись: код `uninit:T` и сразу за ним полная запись T — код T и ячейка T:

| Объявление | Как поле Structure ведёт к значению |
|---|---|
| `int: x` | Поле → запись `uninit:int`, значение которой — запись `int` места `x` |
| `int: x 0` | Поле → запись `int` места `x`, начальное значение 0 |

Поле Structure здесь — ячейка, хранящая адрес; в спецификации ядра она называется «слотом».
Запись значения — тип и значение. Присваивание в место графа (`S\x := 5`) пишет значение, а если тип записи
другой — «T без инициализации», — меняет и его: место после этого держит обычный T (решение автора 2026-11-17,
[журнал](../LMX_blog/2026-11-17.md#assignment-changes-type)). Правило 2026-11-08 «тип места при первом присваивании не меняется»
отменено. Адрес значения остаётся прежним: заранее взятый `@x` адресует ту же ячейку. `sys\typeof` места отвечает
`uninit:int` до записи и `int` после неё; языковой тип `x` — `int` в обоих случаях.
Присваивание локалу вызова (`a := 5` для формала, которому не подано значение) пишет в выбранное место — собственное
место кадра либо прозрачное место вызывающего ([§11](#binding-places)): граф не меняется и данные не публикуются.
Отсутствие значения записывается `nil: T`, где возможно — просто `nil`; переменную можно сравнить с `nil`
(решение автора 2026-11-17, [журнал](../LMX_blog/2026-11-17.md#typed-nil)).
Сегодняшний код ещё оставляет запись `uninit:T` после присваивания; он приводится к норме отдельным срезом
([план](../next_core_tasks_v3.md#typed-nil-plan)).
Подробное представление — [спецификация ядра §3.2](kernel-implementation.ru.md#primitive-storage).

<a id="pool"></a>
## 4. Выделение записей

У каждой арены один поток записей «код типа, значение»: записи выдаются подряд из её кусков, так что дескриптор, слоты и поля одной Structure лежат рядом (решение автора 2026-11-16, подтверждено 2026-11-18, [журнал](../LMX_blog/2026-11-18.md#one-stream-per-arena)). Кусок никогда не перераспределяется: рост добавляет кусок, а выданный адрес стабилен до освобождения соответствующего владения. Кусков по типам нет, и тип не читается ни из куска, ни из адреса: определения типа по адресу нет. Код приходит к этому в два этапа по решению автора 2026-11-16 ([журнал](../LMX_blog/2026-11-16.md#typed-value-two-stages)). Сначала записи живут внутри нынешних типизированных кусков: ячейка пула становится записью с шагом этого пула, что само даёт выравнивание [§3](#value-record). Затем куски по типам убираются. Первый этап — переходное состояние кода, а не норма.

У графового Array `void *storage` хранит адрес хранилища элементов. У числового `Array<T>` это плотный блок T; L2 получает указатель фактического типа элемента из кода записи Array, а не классификацией адреса хранилища. Нельзя читать уже созданный блок слотов `void *` как массив произвольного `T` только приведением указателя. Адресуемые ссылочные слоты графа сохраняют собственный контракт `void **` и конверсию хранимого значения.

<a id="method-array"></a>
## 5. Нативный вход и Array

Native — обычный дескриптор в таблицах call с вариантами входов, сигнатурами, бинарным модулем/именами входов и путями L1/C. Сами машинные адреса — привязка текущего процесса, не сохраняемый адрес другого запуска. Языковой Array имеет общую основу Lmx и переменные length/capacity; типизированное storage может перемещаться. Строки остаются массивами char точной длины без завершающего NUL; NUL относится к двери C.

<a id="arena"></a>
## 6. Арена

Каждый Message владеет одной логической ареной; она может содержать несколько кусков. `lmx_arena_attach` передаёт владение без перемещения адресов: куски присоединённой арены становятся кусками получателя, их записи сохраняют адреса и коды, и для определения их типов ничего не регистрируется заново. К одной арене нет доступа из нескольких потоков, поэтому кодам и выделению синхронизация не нужна. `mark/revert` откатывают неудачное построение копии или `merge`. Простой режим сохраняет стабильность адресов, но не запускает GC. Независимая неизменяемая ветвь может остаться в арене владельца по [контракту L3](LMX_semantics.ru.md#eternal); сам факт отдельного пула такого права не даёт.


<a id="array-capacity"></a>
### 6.1. Общие изменяемые массивы и capacity

Выделение и изменение размера строятся на общем механизме динамических массивов, включая
служебные массивы. Арена хранит «адрес дескриптора → capacity» в элементах. В Lmx и в скрытом
префиксе capacity нет; отдельное семейство VoidDynamicArray ради роста убрать.
Таблица обслуживается при выделении/изменении размера/освобождении, не при каждом индексном доступе.
Стабильные самостоятельные ячейки и канонические строки не перемещаются; это не требует отдельного
массива на каждую ячейку. При восстановлении можно начать с capacity = length.

L3-указатель на элемент массива — собственный тип с ссылкой на дескриптор Array и явным index.
Он не хранит storage: адрес элемента получается из текущего заголовка и итогового смещения.
Перемещение storage не требует обхода указателей. У L3-указателя на примитив также собственный тип;
переиспользовать типизированные ссылки и uninit:T, сохраняя различие ссылки и отсутствия значения.
L2-указатель остаётся сырым адресом. Произвольная конечная глубина указателей и мерность массивов общие.

<a id="message"></a>
## 7. Запись Message

Закрытый `LmxMsg` содержит ровно `running`, `success`, `handoff_ready` и `graph`. Его локальная идентичность — адрес записи. Почта, планировщик и родитель Thread не являются его полями. `running = 0` во время хода запрашивает остановку; `success = 1` устанавливается пользовательским кодом и достаточно для остановки Thread на границе хода; система не сбрасывает `success` в нуль. `handoff_ready` разрешает передачу хранилища. `graph` ссылается на языковой корень.

<a id="thread"></a>
## 8. L3 Thread

Не каждый Message исполняется. Исполняемый Thread изначально выделяется как `LmxThread` с `LmxMsg` первым членом по значению. Адрес Thread совпадает с адресом этого префикса; доступ к хвосту требует точной классификации Thread. Самостоятельный `LmxMsg` нельзя на месте превратить в Thread.

Прямые дети хранятся в единственном List, удерживаемом полем `Thread.children`. Это состояние Thread, не поле `message.graph`. `Thread.parent` относится к иерархии Message и не меняет `Lmx.parent`. Одну идентичность Thread не исполняют конкурирующие workers.

<a id="root-close"></a>
### 8.1. R0 и закрытие

R0 — обычный дочерний Thread верхнего host-каркаса. У R0 данных нет: это процедурный вход без аргументов. Для него нет искусственной самопривязки данных к коду (`data = code`), пустой служебной Structure и искусственного поля `data`; у R0 могут быть собственные исполняемые объявления и обычные доступные ссылки ([норма](LMX_semantics.ru.md#root-entry)). Параметры запуска рантайма и настройки принадлежат каркасу и передаются R0 явно; они не добавляются в исходный граф R0 и не являются пользовательскими фактическими аргументами. В какой роли читаются записи корня единицы, когда у R0 нет данных, а `sub` снят и `fn` только описывает сигнатуру, не определено: это [открытый вопрос у автора](../LMX_blog/q/current/unit-root-roles-20261119.md). Верхний каркас не имеет родителя, но не получает особого API. Закрытие каскадно проходит через единственный List прямых детей каждого Thread. Общий timeout всего поддерева контролирует host-watchdog; его истечение завершает процесс, а не объявляет частичное закрытие успешным.

<a id="mailbox"></a>
## 9. Почта

Каждый Thread владеет `LmxPost`. `staged` готовит письма текущего хода, успешная граница публикует их в `outbox`, `inbox` содержит допущенные, но не взятые письма. Элемент `inbox` — неразделимая пара `[target, source_arena]`: producer не изменяет арену получателя; владелец присоединяет donor до выдачи target. Отказ сохраняет пару. Порядок допуска — FIFO.

`inbox` — кольцо на общем изменяемом массиве с внешней capacity. Один реентерабельный monitor самого LmxPost охватывает admission, take и count; outbox/staged остаются локальными владельцу. Post использует эту же почту; [языковой API](LMX_semantics.ru.md#thread-message-api).

<a id="own"></a>
## 10. Исполнение Structure

Исполнение использует выбранную исходную Structure `C` в роли кода (её данные — `parent(C)`, у R0 данных нет) и локальный namespace по [норме](LMX_semantics.ru.md#call-frame-20261115). Локалы не публикуются; присваивание элементу не меняет длину. Размер меняется явно общим механизмом. Для времени применения правок к исполняемому code действует отдельная [граница endturn](LMX_semantics.ru.md#explicit-compilation).

<a id="call"></a>
## 11. Вызов

<a id="call-receivers"></a>
<a id="structural-call"></a>
### Структурный вызов и ресивер `call`

Исполняется выбранная Structure `C`: она читается в роли кода, а роль данных у неё выполняет её фактический родитель `D = parent(C)`. Формы после однозначного выбора:

| Форма | Исполняемая Structure | Фактические аргументы | Данные |
|---|---|---|---|
| `call(C)` | `C` | не поданы | `parent(C)` |
| `call(A C)` | `C` | Structure `A` | `parent(C)` |
| `C()` | `C` | пустой хвост | `parent(C)` |
| `C(args)` | `C` | написанные фактические аргументы по общему алгоритму | `parent(C)` |

У `call` параметры называются `args` и `code`. `args` — Structure фактически передаваемых значений, ровно та,
которая является структурой аргументов обычного вызова. Это не объявления формалов, не сигнатура
и не отдельная часть callable. Входные места, требования и умолчания описывают данные `D`.
`call` исполняет саму выбранную `C`; дочернее поле `code` автоматически не ищется.
В одноаргументной форме обязателен `code`, в двухаргументной — `args` и `code`, поэтому `call(code := C)`
двухаргументной форме не подходит: это обычное различение объявлений ([выбор объявления](#declaration-selection)),
без исключения для встроенного `call`. Целая `C` может подойти одной форме `call`, а её поля — другой:
тогда `call(C)` — ошибка неоднозначности, а `call(code := C)` явно подаёт `C` как `code` и исключает
раскрытие этого фактического аргумента. `C(A)` может принять `A` целиком либо передать её поля;
это определяет выбор объявления.

Подставить другие данные самим вызовом нельзя. Для другой комбинации сначала создаётся нужная структурная
связь (объявление, копия, `merge` — по их правилам о `parent`), затем вызывается выбранное вхождение `C`.
`NewContainer: ExistingCode` хранит ссылку на `ExistingCode` и его `parent` не меняет ([`colon-declares`](LMX_semantics.ru.md#colon-declares)).
Прежние `call(D C)` и `C(D)` данные больше не подставляют: первый аргумент двухаргументной формы теперь `args`.
Разные вхождения кода могут использовать одну нативную реализацию, сохраняя собственные данные: ни адрес общей
C-функции, ни путь, которым найдена ссылка, не подменяют `parent` выбранной `C`. Прежнее равенство
`call(C)` = `call(C C)` («Structure — сама себе данные») снято.

`node` сохранён как зарезервированная операция вместе со своим явным лексическим доступом для фактически
выбранного вхождения; нужный ему нативный контекст не удаляется и не заменяется новым пользовательским каналом
передачи данных. Общие правила лексического источника и `node` применяются согласованно к структурной форме
вызова. После перехода на `parent(C)` путь `node\x` адресует поле данных вызова (чтение исполнителя,
[Р107](../LMX_blog/q/fable-self-answers-20261110.md)): прежние явные пути `data\x` записываются `node\x`
либо обычным путём от имени Structure данных (`D\x`).

Структурная форма и обычные вызовы Structure используют в интерпретаторе один путь: разрешить имя вызываемого
и видимые объявления → выбрать объявление по явно поданному материалу → связать явные фактические аргументы
с данными → общий допуск → свежий namespace и неявное связывание → исполнение и результат.
Приём фактических аргументов не меняет исходные данные и не запускает входную инициализацию.
Вызовы из test и преобразователей проходят тот же механизм. Известные native-вызовы
из native по-прежнему могут идти прямо в C, без графовой упаковки.
[Полный контракт и именованная подача](LMX_semantics.ru.md#call-receivers).

<a id="return-in-data"></a>
### Результат: `return` в данных

Результат описывается полем `return` в данных: `return: int` либо вложенный блок. Такое объявление ничего не
присваивает и не является общей изменяемой ячейкой рекурсивных активаций. В коде `return` — ресивер возврата:
`return` без значения сохранён, `return: value` передаёт допустимый результат туда, где он описан,
а достижение конца кода `return` не создаёт. Правила структурного результата, принимающих мест и cleanup
сохраняются. И `call`, и обычный вызов Structure могут вернуть значение по этому контракту; прежний
безусловный запрет «у запуска Structure результата нет» снят вместе с `fncall`.
[Норма](LMX_semantics.ru.md#return-in-data).

<a id="fn-signature"></a>
### Сигнатура `fn`

`fn` описывает сигнатуру — контракт вызова, а не исполняемую реализацию — тем же шаблоном данных:
объявлениями входных мест с их требованиями, умолчаниями и модификаторами и полем `return`. Есть `return` —
контракт значения, нет — процедурный контракт; результата в отдельной внешней позиции после списка входов
и `sub` нет, а структурный результат записывается вложенным блоком внутри `return`. Аргументы `fn` всегда
читаются в роли данных (`fn` входит в группу ресиверов с аргументами в роли данных,
[два вида ресиверов](LMX_semantics.ru.md#whole-arguments)): вложенная структурная форма там — описание,
а не запуск, а чтения W и E выбора объявления к ним не применяются. Отдельной грамматики сигнатур и отдельного
парсера нет; при обработке `fn` исполняемое тело и native-вход не создаются. Канонический шаблон:

```text
fn:
    int: a
    int: b
    return: int
```

компактно `fn(int: a; int: b; return: int)`. Пример реализации целиком:

```text
SumContext:
    int: a
    int: b
    return: int
    sum:
        return: a + b
```

Вызов `SumContext\sum(a := 2; b := 3)` исполняет `sum`; её данные — `SumContext`. Вызов `SumContext()`
исполнял бы другую Structure, а не искал бы `sum` автоматически. Типизированный указатель записывается плоско,
тремя аргументами `@`: `@: sumPtr fn(int: a; int: b; return: int) SumContext\sum` — имя, описание требуемой
сигнатуры и кандидат; скобки держат применение `fn` одним аргументом внешнего ресивера, внутри `fn` действует
роль данных. Вызов через него — `sumPtr(a := 2; b := 3)` — использует тот же контракт выбранного кода,
что прямой вызов. Требование проверяет общий `implements` по контракту вызова кандидата с учётом его `parent`
([§14](#implements)); входные поля и `return` не обязаны физически находиться внутри исполняемого тела `sum`,
отдельного сигнатурного валидатора нет. Исполняемых `fn` и `sub` нет.
[Норма](LMX_semantics.ru.md#fn-signature).

<a id="declaration-selection"></a>
### Выбор объявления

Сначала обычными правилами разрешаются имя вызываемого и набор его видимых объявлений; затем объявление
выбирается только по явно поданному материалу; затем исполняется выбранный вариант и применяется неявное
связывание. Единица выбора — кандидат (видимое объявление, чтение явных фактических аргументов, отображение
фактический аргумент → формал). Чтений два, и они равноправны: чтение W «как записано» и чтение E «раскрытая
единственная Structure» — когда подан ровно один фактический аргумент, он Structure или ссылка на неё и не
задан присваиванием формалу; её непосредственные поля образуют последовательность фактических аргументов,
раскрытие однократное, на один уровень, граф не меняется; `f(arg := S)` чтения E не создаёт. Нет предпочтения
целой Structure, арности или первого найденного объявления, и E не пробуется только после неудачи W. Нет
кандидатов — отказ; ровно один — он исполняется без повторного раскрытия; больше одного — ошибка
неоднозначности. Выбор ничего не исполняет: ни присваиваний, ни значений по умолчанию, ни `test`.
Неявное связывание — автозаполнение, место вызывающего, прежнее связывание — в выборе не участвует: оно не
создаёт кандидата, не спасает отклонённого и не запускает повторный выбор. Этим заменено правило 2026-11-18
«раскрытие — попытка найти другие сигнатуры; сигнатура с одним аргументом ничего не раскрывает».
[Выбор объявления](LMX_semantics.ru.md#declaration-selection),
[таблица обязательных примеров](LMX_semantics.ru.md#selection-examples).

<a id="binding-places"></a>
### Связывание: собственное место и место вызывающего

Результат разрешения имени определяет источник и логическое место. **Собственное место:** явный фактический
аргумент, автозаполнение или прежнее связывание кладут значение либо описание в место текущей активации.
**Место вызывающего:** имя обозначает уже существующую локальную переменную вызывающего, без промежуточной
рабочей копии. В обоих случаях переменная `x` остаётся в языке обычной переменной своего типа `T`: нативный
`T*` — деталь реализации ([§11, исполнители](#binding-executors)), он не делает `x` указателем и не требует
писать `\x` вместо `x`. Обычные `x`, `x := value`, выражения с `x` и `@x` действуют на выбранное логическое
место. Для используемого внешнего имени без собственного активного объявления: если реально видимый лексический
источник `private`, действует лексическая связь; иначе — прозрачное место вызывающего; иначе — прежнее
связывание. Прежнее связывание (запасной путь) сохранено вместе с `node` и своим контекстом лексического
и динамического поиска и стоит ниже двух новых путей (ТЗ, R01, R08).

<a id="binding-autofill"></a>
**Собственное объявленное место и автозаполнение.** Значение попадает в собственное место в порядке:
явный фактический аргумент (определяется фактом подачи, а не значением: `0` не пропуск; отсутствие аргумента
и явный `nil` различаются; `private` явную передачу не отменяет) → собственное готовое значение либо описание
инициализатора (готовое значение одноимённой локалью автоматически не заменяется; вычисляемый инициализатор
не считается отсутствующим только потому, что ещё не выполнен) → **автозаполнение**, то есть значение
одноимённого локального места вызывающего (собственная ячейка, не псевдоним: при `x = 5` у вызывающего
и записи `x := 9` в вызываемом вызывающий сохраняет 5; запрещено, если принимающее место `private` или выбранный
автоматический источник `private`) → обычное неинициализированное `uninit:T`, без неявного `0`, и существующие
проверки `required`. Автозаполнение не участвует в выборе объявления ([выбор](#declaration-selection)).
Сохранение прежнего связывания низшим приоритетом не распространяет его на пропущенные формальные входы.

<a id="binding-caller-place"></a>
**Прозрачное место вызывающего.** Используемое внешнее имя без собственного активного объявления: если реально
видимый лексический источник `private`, динамической подстановки нет и действует лексическая связь; иначе
подходящее доступное локальное место вызывающего становится прозрачным. Чтение даёт его значение,
допустимая запись `x := v` меняет его, `@x` адресует реальное место вызывающего. Запись немедленная, без копии
«на выходе»; взятие адреса записью не является и время жизни не продлевает. Если место вызывающего было `uninit:T`,
запись меняет и его состояние инициализации, наблюдаемое через обычные проверки `nil` и `required`. Для
переменной-ссылки обычным типом остаётся её тип ссылки: переназначение ссылки требует адреса её ячейки,
а не только указателя на общий объект, но этот транспортный уровень к языковому типу не добавляется. Ограничения
записи (`const`, `immutable`, типы) действуют по контракту настоящего адресата.

<a id="binding-fallback"></a>
**Прежнее связывание (запасной путь).** Оно сохраняет прежнюю семантику собственного значения или описания
в кадре (вариант A): у вызываемого собственная рабочая копия, присваивание голого имени меняет её, а не исходное
место; для значения-ссылки копируется ссылка, а не объект, и операции через неё подчиняются обычным правилам.
Копия никогда не становится псевдонимом источника. Запрещены две подмены: прозрачное место вызывающего нельзя
заменять временной копией с копированием на выходе, а копию запасного пути — адресом источника под предлогом
оптимизации; прочитанное число может совпасть, но место записи будет другим. Выбранная связь держится в пределах
своей области действия: новое чтение не выбирает другой источник из-за изменения значений вокруг. Начало действия
вложенного объявления — отдельное событие затенения, а не повторная попытка найти источник прежней связи.

<a id="binding-chain"></a>
**Цепочка A → B → C.** Если у A есть `x`, B сам `x` не использует, а C использует, достижимость сохранена:
B не обязан вводить явный аргумент, фиктивную локаль или транзитивный список потребностей потомков,
а статического транзитивного накопления скрытых требований нет. Если сработало прежнее связывание, C получает
собственное значение, а не псевдоним. Если у B своя копия `x`, место `B.x`, переданное C, меняет `B.x`, но не
исходное `A.x`; если у B прозрачная связь с `A.x`, передача места `B.x` сохраняет адрес `A.x`. Происхождение
копии «раскрутить» обратно в исходный псевдоним нельзя.

<a id="private-binding"></a>
### Ресивер private: двусторонний `private`

`private:` помечает конкретное объявление и соответствующее место и исключает их из всего неявного
динамического связывания в обе стороны. (Источник) `private`-место вызывающего неявно не предлагается —
ни значением, ни местом. (Приёмник) реально видимое `private`-объявление лексического контекста вызываемого
не перекрывается значением или местом из динамического контекста. Правило действует для автозаполнения,
прозрачного места вызывающего и динамической части прежнего связывания, одинаково для всех форм `call`,
`C(args)`, обычных вызовов, интерпретатора и native. Поэтому до принятия внешней динамической привязки
определяется, какое лексическое объявление действительно видно и защищено ли оно `private`; проверки одного
источника недостаточно. `private` — фильтр конкретного места, а не барьер имени и не защита доступа:
`private`-источник пропускается, и допустимый поиск идёт дальше, а `private x` предка не закрывает новое
внутреннее непомеченное `x`. Не запрещены: явная передача (в том числе собственного `private`-значения),
явное заполнение принимающего `private`-места фактическим аргументом, вложенная лексическая видимость, явные
пути и `node`, затенение внешнего `private` новым внутренним объявлением. Ограничения записи (`const`,
`immutable`) `private` не заменяет. Явно переданное значение не переносит историю `private` на свои копии;
запись графа `S\private\field` не превращается в `S\field`. Использовать общий binder без отдельного реестра
или проверок прямых чтений. [Полный контракт](LMX_semantics.ru.md#private-binding).

<a id="call-frame-20261115"></a>
### Кадр вызова

Каждый вызов создаёт собственный namespace. Входы описывают данные выбранной Structure (`parent(C)`):
входные места, их требования, умолчания, модификаторы и поле `return`; `args` у `call` содержит фактические значения.
Краткие заголовки сохраняются. Actual заменяет соответствующее
исходное объявление кадра, и его инициализатор не выполняется. Подготовка собирает только корни
data/code, без обхода ветвей и графовых ссылок и без записи автозаполнения в исходную data.

При входе нет фазы исполнения инициализаторов. Готовые объявления сворачиваются при построении
чистого графа без вызовов программы; uninit:T сохраняется. Неиспользуемое вычисляемое поле data
не выполняется. Чтение получает его значение общим механизмом, как `D\field`: исполняется
написанный RHS, а не неявный вызов полученной ссылки. Для `@: fptr getFuncPtr()` запись
`fptr("hello world")` сначала получает указатель, затем вызывает полученную функцию.

Переменные и const видны с первоначального объявления вперёд в своей области и ниже.
Двусторонняя видимость сохраняется у имён Structure и callable, но не у переменной с указателем
на функцию. Новое имя ветви не выходит наружу.

<a id="shadowing-levels"></a>
Объявление на вложенном уровне затеняет внешнее одноимённое: внутреннее `Text x` затеняет внешний `int x`,
не записывая `Text` во внешнюю `int`-ячейку. На том же уровне затенять нечего, и используется уже существующее
место: повторное `int: x bump()` сохраняет вычисление, допуск и запись существующему x по контракту ресивера —
новая правая часть вычисляется и присваивается, отсутствие правой части значение не обнуляет, второй ячейки нет;
убирается только повторная C-декларация. После выхода из внутренней области снова видно внешнее со своим местом,
режимом записи и `private`. Употребление до более позднего собственного объявления разрешается обычным способом
через доступный внешний контекст: будущее объявление не блокирует всё тело. Физические повторы
полей сохраняются и выбираются `S\[n]x`. Явный путь не ограничивается порядком объявления
голого имени. Чтение объявления через путь ничего не исполняет; RHS исполняется при достижении строки code.

<a id="inline-declaration-control"></a>
Одно место остаётся на чтении исполнителя ([ТЗ §7.4](new_parts/LMX_Fable_TZ_Binding_and_Callables_v2_2026-11-19.md),
[Р106](../LMX_blog/q/fable-self-answers-20261110.md)): новое `int: x` без правой части во вложенной встроенной области,
где нового вызова вызываемого нет, при внешнем `x = 5` остаётся `uninit:int`, потому что автозаполнение определено
между локальным контекстом вызывающего и местом вызываемого при вызове, а встроенная область остаётся в той же
активации; значение 5 потребовало бы нового правила, которое ТЗ вводить запрещает. Это не решение автора.
[Контрольный пример](LMX_semantics.ru.md#inline-declaration-control).

Голое x и @x относятся к выбранному месту. Собственное место кадра не зависит от замен исходного поля сразу
после входа, даже до первого чтения: сохраняется выбранное значение либо вычисляемое описание; правило одно
для явной data, лексического связывания и прежнего динамического связывания, и это не глубокое копирование
объектов по ссылкам. Прозрачное место вызывающего — само место вызывающего ([§11](#binding-caller-place)).
`x := 0` меняет выбранное место: собственное место кадра — не пишет ни в граф, ни вызывающему, прозрачное
место вызывающего — пишет ему сразу; `D\x := 0` меняет исходный граф данных.
Для вычисляемого входа `int: x next()` обращение @x получает значение и адрес локальной ячейки.
При `@(D\field)` и исходном `int: field getValue()` адресуется запись объявления, а не результат
getValue(): явный путь ничего не исполняет (решение автора 2026-11-17; прежнее правило снято).
Готовое место адресуется непосредственно.
Время жизни обычное. @f() было исследовательским примером, не задачей отдельной поддержки или запрета.

Обязательный снимок исполняемого code при входе отменён. До endturn момент применения его правок
не гарантируется. Выбранные значения/описания собственных мест остаются независимыми от исходной data;
связывание передаётся скрытыми аргументами ([§11](#binding-executors)), окружение не копируется. Методы и обычные Structure
компилируются общим механизмом без data=code: данные выбранного вхождения — его `parent`; разные actuals
и разные режимы скрытых входов дают разные C-сигнатуры.
Запись в граф не обнуляет native: обновление требует явной компиляции.

Локальные кадры не публикуются. Load-dirty, общий кеш прямого доступа и flush() отменены;
явные записи наблюдаются через реальные алиасы в порядке исполнения.
[Согласованная норма](LMX_semantics.ru.md#call-frame-20261115),
[единое ТЗ M14](../next_core_tasks_v3.md#native-structures),
[план связывания](../next_core_tasks_v3.md#binding-callables-20261119).

<a id="binding-executors"></a>
### Нативный код, обходчик и мост (bridge)

Прямой вызов native→native сохраняется там, где выбранные реализация, типы и связывание известны.
Автозаполнение опускается как параметр того же `T`, что и явный фактический аргумент; прозрачное место
вызывающего — как скрытый адрес ячейки вызывающего; прежнее связывание (запасной путь) даёт собственное место.
Общее C-тело может быть разделено между режимами через адаптеры, и адаптер обязан сохранить владельца записи
и поведение `@`. При одинаковых явных фактических аргументах режим конкретного скрытого входа может различаться
из-за контекста вызывающего и `private`: существующий native-вход должен соответствовать реальному контракту
либо получать корректное описание места. Один код может иметь несколько фактических сигнатур, в том числе при одном
явном контракте и разных режимах места (собственная копия, место вызывающего). Способ выразить это в нынешнем ABI
определяют работы [плана](../next_core_tasks_v3.md#binding-callables-20261119); новые пользовательские указательные
типы не вводятся. Служебные C-функции, мост и диспетчер `call` не подменяют контекст вызывающего своими служебными
локалями: источники языка определяются программным местом вызова.

У обычной нативной локали нет заголовка арены `[type][value]` ([§3](#value-record)): её тип нельзя прочитать
из четырёх байтов перед адресом. Тип, способ доступа, состояние инициализации и применимые ограничения места следуют
общему представлению места и контракту вызова. Четыре сочетания — native→native, native→обходчик,
обходчик→native, обходчик→обходчик — дают одно наблюдаемое поведение: `x` имеет один логический тип `T`, а допустимая
запись меняет то же логическое место. Для цели времени исполнения, неизвестной при трансляции, сохраняется
существующий механизм доступа к разрешённым локальным контекстам; сырой C-стек не исследуется как словарь имён LMX,
и статического транзитивного замыкания требований нет.

Не возвращаются load-dirty, flush, публикация локальных кадров и копирование обратно при выходах. Чтение через
псевдоним не превращается в снимок без доказательства, что наблюдаемое поведение при вложенных вызовах сохраняется.
Явная компиляция, существующий выбор native/обходчик и граница endturn сохраняются; отсутствие подходящего
native-входа не запускает скрытую компиляцию; постоянных кешей всех окружений и автоматической инвалидации графа
нет. `restrict` не применяется лишь из-за скрытой передачи указателя или `private`: такой C-контракт требует
отдельного доказательства отсутствия запрещённых пересечений.

Прозрачная связь не продлевает время жизни; адрес временной C-локали не становится переносимой структурной ссылкой,
правила Message и арен не меняются. При `yield` выбранная связь не перевязывается к одноимённой локали нового
вызывающего: возобновление использует состояние сохранённой активации и обычные ограничения времени жизни.
[Норма](LMX_semantics.ru.md#binding-executors).

<a id="catch-common-model"></a>
### `catch` в общей модели

`catch` приведён к общей модели данных и вызова с сохранением семантики обработчика. Payload — явно поданные
значения, принимаемые общими правилами; остальные допустимые зависимости обработчика следуют связыванию
и `private`; входы описываются данными с учётом фактической связи `parent` кода обработчика с его данными.
Сохраняются: выбор обработчика по имени failure и области, невыполнение его тела на первоначальном прямом проходе,
различие вложенных и соседних областей, отсутствие двух конкурирующих одноимённых `catch` на одном уровне,
продолжение после обработчика, повторный вызов, `throws` и cleanup. `catch` не исчезает вместе с `sub`
и не становится обычной функцией; у него убрана зависимость от отменённых исполняемых `fn`/`sub`, `fncall`
и отдельной подстановки данных. [Норма](LMX_semantics.ru.md#catch-common-model).

<a id="direct-access-cache"></a>
<a id="explicit-compilation"></a>
### 11.1. Явная компиляция и прямой native-вызов

`sys\compile(S)` — построение/проверка чистого графа → L1 → C → машинная компиляция →
регистрация полученных вариантов в таблицах call. Использовать работающий код сборщика;
runtime получает его части только под эту реальную операцию. sys\translate возвращает L1 и errors,
не LMX и не установленный native. Ошибка компиляции не устанавливает новый вход.

Известный native вызывает известный вариант прямо в C с фактическими и скрытыми аргументами.
Для такого вызова не нужны графовая упаковка, поиск в call или универсальный trampoline.
Динамический выбор использует таблицы call. Один code может иметь несколько фактических сигнатур,
в том числе из-за разных режимов скрытых входов ([исполнители](#binding-executors)).
Явные пути, `node` и необходимая передача их ссылок сохраняются.

Правки графа не отслеживаются ради native. Удалить автоматическое обнуление, сканирование зависимостей,
таблицы обратной инвалидизации и их обслуживание, переносы и генерацию. Не заменять это dirty,
версиями, хешированием на каждом endturn или универсальным журналом. Обычные механизмы памяти
сохраняются лишь для их реальных задач. Без явной компиляции машинный код не обязан обновляться.

Для прямой связи A→B компиляция только B не переписывает старый A. Обновление цепочки требует
явной компиляции общей единицы с нужными вызывающими функциями и целями. Это задача сборщика,
не проверки каждого вызова. Готовые бинарники соответствующего ABI можно связать с восстановленным
чистым графом без повторной трансляции. ToLmx сохраняет выбранную структуру; для L3 Thread
включаются все таблицы его арены, включая call/native. Таблицы принадлежат арене, не полям R0
(у R0 нет данных и искусственных полей, [§8.1](#root-close)); к произвольной S внешние таблицы автоматически не добавляются.

<a id="endturn-receiver"></a>
### 11.2. sys\endturn

sys\endturn() завершает текущий такт через общий механизм выходов. Выполняются зарегистрированные
finally всех покидаемых областей в обратном порядке; обычный catch этот системный выход
не перехватывает. Возврата к месту вызова и сохранённого продолжения стека нет.
После очисток выполняется штатный конец такта. Сам ресивер не меняет running/success и не
означает завершения Message; следующий такт начинается обычным входом.
До границы применение правки к исполнению может различаться между обходчиком и native.
После успешной явной компиляции и endturn следующий вход использует подготовленное обновление.
Один endturn не обнаруживает изменения, не компилирует и не публикует локалы; это не flush.
Старый машинный код не освобождается, пока его кадры и finally ещё исполняются.
[Норма](LMX_semantics.ru.md#endturn-receiver), [источник](../LMX_blog/2026-11-15-explicit-compilation.md).

<a id="child"></a>
## 12. Резервация ребёнка

Ребёнок строится в собственной арене. До успешной публикации его нет в `Thread.children`; публикация в конце хода добавляет физическую ссылку в этот List, не меняя исходный граф. Неуспех снимает резервацию, но не откатывает произвольные уже сделанные записи графа.

Переподчинение проверяет, остаются ли владельцы используемых ребёнком ветвей `independent: immutable` в новой цепочке Message-предков. Отказ не меняет членство и `Thread.parent` частично. `adopt: msg newParent` выполняет перенос; `independent: msg newParent` отдельно готовит именно этот перенос, копируя только мешающие ветви в арену `msg` и не меняя родителя. Это операции над иерархией Message, не над `Lmx.parent`.

<a id="copy-merge"></a>
## 13. Копирование графа и merge

`merge` строит новый граф с одной картой адресов источник→копия. Карта сохраняет общие цели и циклы, переписывает внутренние ссылки и `parent` на копии и не создаёт отдельного экземпляра для каждого `lnk`. Копируется весь используемый граф, включая исполняемые записи операций; исключение — квалифицированные `independent: immutable` ветви, явно удерживаемые владельцем. Копирование не компилирует и не регистрирует native для результата: эту связь устанавливает явная компиляция или восстановление. Неполная копия с адресами освобождаемой исходной арены недопустима.

Первый операнд задаёт порядок слотов модели; совпадающее поле следующего операнда заменяет значение этого слота после допуска, новое дописывается в новом результате. Исходные операнды не меняются. Семантика выбора тела и аргументов — в [L3 §20](LMX_semantics.ru.md#composition).

<a id="implements"></a>
## 14. implements

Доказанное соответствие между используемыми полями принимающей модели и физическими полями кандидата для допущенной пары Structure — данные того приёма или обхода, который его установил (решение автора 2026-11-08 о служебных таблицах обхода, подтверждённое Codex; [спецификация реализации §5.2](kernel-implementation.ru.md#tables)): приём удерживает свою карту на время нужных ему операций — чтения, получения адреса и явной записи в исходный граф, включая разные порядки полей, — а следующий обход строит её заново из графа; постоянного хранилища соответствий у арены нет, отдельной карты для `call` или `data` нет. Локальные места вызова обратно в граф не публикуются. Интерфейсная часть `implements` выполняется один раз для каждого кандидата: при построении чистого графа, если кандидат известен, или при исполнении, если кандидат выбирается динамически ([случаи](../steps/implements-runtime-cases-20261111.md)). При построении графа `test` не исполняется; для динамического кандидата он является вторым шагом допуска ([уточнение автора 2026-11-13](../LMX_blog/2026-11-13.md#implements-and-test-phases)). Присваивание примитивов при исполнении на допустимость не сверяется (решение автора 2026-11-11, [L3](LMX_semantics.ru.md#data-code-roles); правило говорит о допуске `implements`, а не о преобразовании: проверка диапазона при приёме числа другого типа, `u16(256)` в `u8`, остаётся при исполнении); трансляторы этого правила ещё не исполняют ([план](../next_core_tasks_v3.md#m11)). В данных каждая объявляющая запись — вхождение имени: единственное вхождение адресуется `s\field`, при двух и более имя адресуется только с индексом вхождения — повторное объявление прежнего не заменяет и в него не пишет ([L3](LMX_semantics.ru.md#fields)); `s\[N]field` с нулевым `N` адресует N-е вхождение имени — запись данных, объявляющую это имя, — а не элемент Array. Карта не ищет имена в runtime, не копирует кандидат и не отменяет проверок нового Consumer. Семантика допуска и явно заданных тестов — в [L3 §7](LMX_semantics.ru.md#admission).

Требование, полученное из `fn`, проверяется этим же `implements` по контракту вызова кандидата с учётом его `parent`: отдельного сигнатурного валидатора, дублирующего `implements`, нет, а текущие границы интерфейсной проверки, преобразования и `test` сохраняются ([сигнатура `fn`](#fn-signature)).

<a id="gc"></a>
## 15. Сбор

GC принадлежит арене. Вид и размер каждого обходимого значения берутся из кода его записи ([§3](#value-record)). Корни включают Message, живой граф, почту, состояние исполнения и `Thread.children`; последний List удерживается состоянием Thread независимо от исходных полей. От живого значения сборщик следует также по установленному соответствию `implements` к Structure его требования: замена поля графа не освобождает модель, пока действующий допуск к ней нужен этому значению. Временный кадр допуска не удерживается этим правилом; уход кадра удаляет зависящую от него запись. Это зависимости адресного доказательства, а не скрытые поля графа. Созданные `independent: immutable` ветви удерживаются владельцем до уничтожения его арены. Простой режим не выполняет сбор. Правило выгрузки позднего модуля требует отдельного контракта и здесь не изобретается.

<a id="special"></a>
## 16. Специальные операции L2

Ядро предоставляет выделение записи, чтение типа записи, attach/revert арены, почту, ход Thread, вызов, резервацию ребёнка, копирование/merge и сбор. Эти операции не создают второго пространства имён или вспомогательного графа исполнения.

<a id="lowlevel-scope"></a>
## 17. Машинный профиль

Машинные типы L2 сохраняют представление и числовую семантику соответствующего типа C99 целевой платформы, в том числе знаковость обычного `char`. L3 не получает сырую память только потому, что его граф реализован указателями. L1 имеет отдельную C-подобную поверхность.

<a id="lowlevel-address"></a>
## 18. Адреса, загрузка и запись

Адреса полей, возвращённые [descriptor](#get-descriptor), — настоящие типизированные места:
`Lmx **`, `size_t *`, `void **`. Это отличается от адреса обычного графового
слота `void **`: его нельзя произвольно читать как `Lmx **`, тогда как само поле S.parent
действительно имеет тип `Lmx *`. Даже при совпадении адресов S.parent и S явное разыменование
читает поле по его типу. Загрузка и запись общие для любой конечной глубины указателя,
включая ссылки и указатели на функции. Явный путь `S\field := value` и разыменованная запись
не являются присваиванием по голому имени Structure или функции и не запрещаются этим правилом.

M3 упорядочивает плоские объявления как имя, требование/значение. Место объявляет форма `@:` с перечислением аргументов: `@: p 0`, `@: p Model`, `@: p Model 0`, `@: p Model Other`; запись с местом во внешней голове (`ptr: @: Model: 0`), которую допускали N1–N6, снята решением автора 2026-11-10 ([семантика](LMX_semantics.ru.md#receiver-args-only)). Первое поле — атом имени места и не вызывается; остальные поля потребляются по обычному правилу выражений: аргументы ресивера разбираются общим алгоритмом и читаются как код. Требование с кандидатом записывается плоско, тремя полями: `@: p Model Other`, нулевой адрес — `@: p Model 0`. Вложенная форма `@: p Model: Other` требования с кандидатом не записывает: `Model: Other` в аргументах ресивера — вызов `Model` (следствие решения автора 2026-11-11 о разборе аргументов, [роли `data` и `code`](LMX_semantics.ru.md#data-code-roles); чтение исполнителя — [ответы](../LMX_blog/q/fable-self-answers-20261110.md), О4); запись запуска Structure на месте, где нужно значение (операнд выражения, фактический аргумент вызова, начальное значение, операнд `merge`), может давать значение, если контракт этой Structure описывает результат полем `return` в данных ([`return` в данных](#return-in-data)); прежний безусловный запрет «у запуска результата нет» (чтение исполнителя, Р22, пункт 3; Р25, пункт 4) снят нормой 2026-11-19 (R11). P0 не выделяет эти формы: разбор общий, роли полей задаёт контракт `@:`. Первое `@: p` или `@: p 0` создаёт void-ссылку; последующая запись адреса не добавляет ей задним числом требование. Указательная глубина `@ⁿ:` не ограничена особым числом.

В `@: ptr method` ресивер `@` стоит первым, а `ptr` и `method` — голые атомы: атом не является вызовом. Поэтому форма присваивает ссылку в `ptr` по контракту `@`, даже если `ptr` уже содержит callable; `ptr(args)` вызывает его. Унарное `@ptr` отдельно берёт адрес ячейки ссылки. Подробные правила этих форм — в [L3](LMX_semantics.ru.md#ordinary-var) и [присваивании ссылки на метод](LMX_semantics.ru.md#method-reference-assignment); особое имя `data` снято ([что снято](LMX_semantics.ru.md#removed-builtins)).

Унарное `@x` для переменной namespace адресует выбранное логическое место: настоящую локальную ячейку текущего вызова либо, для прозрачного места вызывающего, реальное место вызывающего ([§11](#binding-caller-place)); взятие адреса не является записью и не продлевает время жизни. Для вычисляемого входа `int: x next()` обращение `@x` получает значение и адрес обычной локальной int-ячейки. Если `D\x` выбирает готовое место исходного графа, `@(D\x)` сохраняет его собственный адрес. Если в данных записано вычисляемое объявление `int: field getValue()`, `@(D\field)` адресует запись объявления, а getValue() не исполняется: явный путь ничего не исполняет (решение автора 2026-11-17). Явная запись `D\field := ...` меняет исходное поле. Автоматического переноса между локальным местом и графом нет. [Общее правило](LMX_semantics.ru.md#computed-field-address).

В существующем native-пути `emit_call_result_value` объявляет типизированный `l2_tN`, а `emit_dyn_tail_value` передаёт `&l2_tN` как назначение результата. Для взятия адреса переиспользуется это место, без повторного вызова, второй ячейки или специального выделения ради `@`. Обходчик использует обычную адресуемую ячейку результата. Действуют обычные правила времени жизни существующего места.

Для поля ссылки сохраняется точный тип указателя, для примитива — его типизированная ячейка. Обычный графовый слот физически хранит void*; алиас через Lmx** не подменяет его представление. Глубина указателя произвольна; адрес временного результата вычисления не подменяет собственный адрес готового места.

Префикс `\p` следует ссылке; `p\field` обращается к графовому полю либо к явно импортированному машинному ABI в зависимости от категории `p`. `@array[i]` адресует реальный элемент backing. В нативном коде L2 индекс не получает автоматической проверки границ; проверяемый доступ принадлежит L3, и с теми же проверками интерпретатор исполняет код L2. Адресная операция не снимает `const`/`immutable` и не продлевает срок жизни цели.

L2-индексация `[]`, `[][]`, `[][][]` любой конечной мерности, включая `array[-1]`, вычисляет смещение
без проверок length, знака, арены или бывшего поля. Чтение, запись и взятие адреса используют один путь.
В L3 соседние индексы сводятся к одному линейному индексу и одной проверке по текущей length;
отдельные проверки координат, временные строки и промежуточные дескрипторы не нужны.

<a id="lowlevel-array"></a>
## 19. Сырое C-хранилище

Токен `c.*` — явная дверь в C. Языковой Array остаётся объектом графа на общей основе `Lmx` с типизированными элементами; сырой C-массив им не становится. Переход между ними требует явной операции, учитывающей форму и время жизни. Типизированные массивы арены — внутреннее хранилище, не ещё один вид языкового Array. L2 не вводит особую сущность `c.array`.

<a id="lowlevel-abi"></a>
## 20. Внешние типы и ABI

`cast: (T) value` — машинное приведение, не проверяемое преобразование L3 и не доказательство границ, выравнивания или времени жизни. `c.name` выбирает внешний C-символ; адаптер определяет параметры, результат и владение. `c.sizeof` означает C `sizeof`, не длину Array и не число полей Structure. `include` и `os` выбирают явно заданные зависимости и платформенную ветвь, не вводя runtime-поиск модулей. Действию `include:` и `predef:` нужен один аргумент — имя зависимости, — поэтому аргументов можно записать несколько, и каждый подключается по очереди, в записанном порядке, как у ресиверов [квалификации](LMX_semantics.ru.md#qualification).

`os` выбирает целевую платформенную ветвь, но не вводит отдельного сравнения ветвей на равенство наборов методов, сигнатур или сериализованных контрактов. Различия между ветвями сами по себе не являются ошибкой. Выбранные объявления и тела проходят обычные механизмы L2; там, где принимающее место требует совместимости, применяется обычный `implements` и его адресная карта, как вне `os`. Выбор ветви не создаёт дополнительного общего интерфейса или частного `os`-варианта допуска. [Уточнение автора, 2026-10-23](../LMX_blog/2026-10-23.md).

Существующий ресивер `os` выбирает ветвь для целевой платформы до смысловой обработки её содержимого; отдельный новый оператор для этого не нужен. Общий структурный разбор выделяет ветви, но невыбранные объявления и тела не проходят разрешение имён, проверку типов и контрактов, сбор зависимостей или генерацию кода. Их `include`/`define`/`predef` не добавляют зависимости и объявления в выбранный вариант. Выбранное содержимое проходит тот же общий L2-конвейер, что вне `os`, включая обычный native и обходчик для поддерживаемых тел, без частного разбора, исполнителя или запасного native-маршрута. Целевая платформа согласована на всех стадиях трансляции, а не случайно определяется платформой запуска транслятора. Это утверждённое направление реализации, не заявление о завершённой поддержке. [Уточнение автора, 2026-10-23](../LMX_blog/2026-10-23.md).

Платформенные заголовки и имена, встречающиеся только в невыбранной ветви, не требуются для выбранного варианта. Его обычный код может обращаться к методу, объявленному только в выбранной ветви, без объявления аналога в остальных. Трансляция всех альтернатив в L1/C с последующим скрытием невыбранных через C `#ifdef` этому правилу не соответствует; их зависимости, объявления и тела не генерируются. Общий структурный разбор исходника не означает смысловую трансляцию невыбранной ветви. [Уточнение автора, 2026-10-23](../LMX_blog/2026-10-23.md).

Указанное отсечение ветвей — обязанность трансляции. Оно не требует сохранять результат её выбора или подготовки как условие работы обходчика: тот исполняет текущий граф по [§2.1](#interpretable-tree), не обязательную запись транслятора о выбранном теле.

`implements` остаётся обычным допуском выбранного содержимого, а не статическим сравнением альтернативных платформенных реализаций и не механизмом отключения их трансляции: он выполняется один раз, при построении чистого графа, а при исполнении — только там, где кандидат выбирается во время исполнения (решение автора 2026-11-11, [§14](#implements)). Если далее потребуется дополнительное средство языка, его общее решение обсуждается с автором; для указанного выбора существующим `os` повторное согласование нового оператора не требуется.

В вычисляемом вызове через C-дверь C-функции и макросы получают заранее вычисленные L2-значения, не подстановку текста L2-выражений. L2-аргументы вычисляются один раз в обычном лексическом порядке и по обычным правилам выхода до передачи внешнему вызову; развёртка макроса не повторяет и не отменяет это вычисление. Поэтому при `#define BYTES(x) sizeof(x)` вызов `c.BYTES(touch())` сначала выполняет `touch()` один раз и передаёт его значение макросу, хотя C не вычисляет операнд получившегося `sizeof`. Это также относится к макросу, который использует параметр несколько раз или не использует его.

Буквальный `c.sizeof` имеет роль оператора C, а не вызова C-функции: после общей подготовки его операнд подчиняется правилам C99 `sizeof`, не предварительному вычислению аргумента внешнего вызова. Развёртка произвольного макроса в `sizeof` не передаёт ему эту роль. Различие определяется семантической ролью после общего разбора, без регистрации C-имён или второго парсера. Для обычного типа без переменно-модифицированных компонентов `c.sizeof(touch())` не выполняет `touch()`; правила C99 для variably modified типов этим не отменяются. [Уточнение автора, 2026-10-22](../LMX_blog/2026-10-22.md).

У C-двери есть и обратное направление: машинную функцию L2 можно экспортировать с прямым C-совместимым входом. C-код вызывает её явными аргументами функции, без экземпляра `Lmx`, корня, Message и подготовленного графа; нужные ей состояние и память она получает своим обычным явным контрактом, а не скрытой общей единицей, ареной или singleton. Функция остаётся тем же L2: существующий генератор переводит её общим структурным разбором, разрешением выражений и проверками, без отдельного C-подобного языка, второго парсера или resolver и без маршрута только для List или библиотек. Обычные графовые вызовы L2/L3 сохраняют свой общий механизм; экспорт не снимает семантику с произвольной исполняемой Structure и не вводит новых пользовательских указательных типов: скрытый адрес места вызывающего — деталь нативной реализации при неизменном языковом типе `T` ([исполнители](#binding-executors)). Поддерживаемые исходники остаются L2/L3, их L1/C генерируется; перенесённое тело заменяет старое без постоянного fallback. Это утверждённое направление реализации, не заявление о завершённой поддержке. [Уточнение автора, 2026-10-23](../LMX_blog/2026-10-23.md).

<a id="lowlevel-expression"></a>
## 21. Машинные выражения

Порядок вычисления выражения задают приоритеты и ассоциативность Си (степень `**` — по правилу Python) и получение значений по требованию: у присваивания приоритет низший, его правая часть — всё выражение справа, а потребитель, которому нужен результат присваивания, получает его исполнением этого присваивания. Запись кода `target := a + b` присваивает сумму. `sys\name(identificator)` возвращает обычный массив символов из таблицы имён; функция реализации операнда получает массив ссылок `@` на значения типизированных записей — код типа лежит перед значением — и возвращает такую же ссылку на запись результата; `sys\priority` возвращает `int` ([книга](LMX_semantics.ru.md#assignment-inside-expression)).

Машинный профиль включает группировку, арифметику, сравнения, логику, битовые операции, `++/--`, индекс и обычное управление. `=` в выражении — сравнение; запись — `target := value`. Прежняя запись `target: value` при трансляции присваиванием больше не служит (решение автора 2026-11-10, [L3](LMX_semantics.ru.md#forms-declare-or-call), [журнал](../LMX_blog/2026-11-10.md#forms-declare-or-call)); формы ресиверов с перечислением аргументов, `int: i 5` и `@: p q`, действуют как прежде. Исходные тексты проекта пишут `target := value`; прежней записи транслятор отказывает, и сообщение называет `:=` ([план](../next_core_tasks_v3.md#m7)). Переполнение и сырой индекс следуют машинному контракту, не обещаниям L3. `a[i][j]` адресует ровный многомерный Array; `a[i]\[j]` следует через ссылку к отдельному Array. `s\[N]field` в Structure-as-data выбирает исходное вхождение, а не машинный элемент Array.

<a id="lowlevel-sync"></a>
## 22. synchronized

`synchronized: lock code` задаёт структурную область взаимного исключения, не открытую пару lock/unlock. Выход освобождает monitor. Почтовый monitor — конкретное реентерабельное применение без `wait`/`notify`; сырых блокировок в чистом L3 нет.
