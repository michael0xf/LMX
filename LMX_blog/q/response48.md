## 1. Сначала — исправление трактовки `native`

В `Answer48.md`, §3, пункт 2, процитирована текущая фраза:

> «У результата слово `native` пусто, поэтому он исполняется интерпретатором; операции адресуют поля по слоту `node` и перенумеровываются картой позиций».

**Нет: это не общее правило для всякого результата `merge`.**

Если исполняемое тело копии не изменилось, существующая нативная реализация сохраняется. Она получает нужный граф скрытыми аргументами и работает с предоставленными данными. Другой адрес экземпляра, копирование его лексического состояния или изменение значений данных сами по себе не требуют другой машинной функции.

Для модели из `Answer48.md`, §1:

```text
add:   Code = Cadd    Data = Dadd
add5:  Code = Cadd    Data = merge(Dadd, { y: 5 })
```

`Cadd` остаётся тем же кодом. Если у него есть нативная реализация, `add5` использует её. Если её изначально нет, тот же алгоритм исполняется интерпретатором. `merge` не является командой «перевести результат в интерпретируемый режим».

Здесь «тело изменилось» означает изменение исполняемого кода, а не сам факт изменения данных, находящихся в структурной части с именем `body`.

### Когда нативный адрес не подходит

| Результат операции | Что происходит с кодом и `native` |
| --- | --- |
| Скопирован существующий callable; исполняемое тело не изменилось | Сохраняется соответствующая нативная реализация, если она была |
| Изменены или дополнены только данные; исполняется прежнее тело | Сохраняется код модели и его `native`; существующий код получает новые данные |
| В качестве тела целиком выбран код другого операнда, уже имеющий соответствующую нативную реализацию | Выбирается код этого операнда и относящийся к нему `native`, а не адрес прежнего тела модели |
| Получено изменённое тело, для которого нет соответствующей нативной реализации | Прежний адрес использовать нельзя; результат с пустым `native` исполняется интерпретатором в рамках его обычного L3-контракта |

Следовательно, не нужны ни правило «после любого merge native = 0», ни противоположное правило «старый native годится после любой замены кода». Адрес относится к конкретной исполняемой реализации.

Перенумерация операций также не должна объявляться обязательным эффектом копирования или изменения данных. В рассматриваемом data-only случае сохраняется раскладка, которую потребляет выбранный код: слоты модели остаются на своих местах, новые поля дописываются по общему правилу. Переписывание графовых ссылок в копии — не то же самое, что переписывание самого алгоритма.

### О подтверждении от 2026-09-25

Утверждение, что сейчас автор отменяет прежнее решение, неверно. Подтверждение «результат интерпретируемый» относилось **к случаю изменённого тела**, а не к идентичному коду над другими данными.

В истории решений следует записать **уточнение области прежнего подтверждения**, а не смену решения на противоположное.

## 2. Прямые ответы на четыре вопроса из §5 Answer48.md

### 2.1. Объявленный заголовок — тип места, а не дополнительный операнд?

**Да.**

В обсуждаемой записи объявленный заголовок задаёт принимающее место. Результат композиции допускается в него обычным `implements`/admission и применимыми общими преобразованиями.

Не нужно автоматически добавлять к пользовательской программе:

```text
merge(add; {y: 5}; объявленный заголовок)
```

как обязательную особую процедуру преобразования callable.

Если программа сама явно компонует структуры описаний, действует обычная композиция полей. Например, отсутствие `y` в дополняющей структуре `args = [x]` не является командой удалить `y` из модели `args = [x, y]`.

Фразу «композиция, ничего не заменяется» из §2 `Answer48.md` также не следует читать буквально для всех частей операции: совпадающие поля обновляют слоты по обычному правилу, а выбранное тело может заменяться. Здесь отвергается именно **неявная полная замена описания аргументов одним фактом более короткого объявленного заголовка**.

### 2.2. Операнд с кодом выбирает своё тело, а операнд-данные оставляет код модели?

**Да.**

Если операнд предоставляет исполняемое тело, применяется установленное правило замены тела: кодом результата становится выбранное тело операнда. Если операнд предоставляет только данные, остаётся тело модели.

Машинные тела не склеиваются в новую составную машинную функцию. Это правило выбора целого тела на соответствующем уровне композиции; оно не отменяет обычные вложенные методы, вызовы или структуру программы.

Дальше `native` определяется выбранным телом, как описано в §1 этого ответа. Наличие кодового операнда не означает обязательного уничтожения его собственной подходящей нативной реализации.

### 2.3. Можно ли явно передать формал, у которого уже есть значение?

**Да: `add5(1; y: 25)` даёт 26.**

Наличие предусмотренного значения по умолчанию делает аргумент необязательным для явной подачи, но не удаляет его из принимаемого интерфейса и не запрещает его переопределить в конкретном вызове.

Для рассматриваемого в `Answer48.md` варианта:

```text
формалы add5: x, y
значение по умолчанию для y: 5
тело: return x + y
```

получаем:

```text
add5(1)         -> 6
add5(1; y: 25)  -> 26
add5(1; y: 0)   -> 1
```

Это обычная подготовка аргументов. `merge` лишь компонует данные; механизм вызова использует значение по умолчанию, если соответствующий аргумент не подан.

Слово «необязательный» означает «можно не передавать», а не «больше невозможно передать».

### 2.4. Снимается ли требование интерпретации для операнда-данных?

**Да — снимается его ошибочное распространение на этот случай.**

Но прежнее авторское решение не отменяется: оно изначально относилось к изменённому исполняемому телу. Неизменённый код модели, в том числе его нативная реализация, остаётся пригодным для исполнения над результатом композиции данных.

## 3. Формал с дефолтом и свободный динамический вход — разные случаи

В `Answer48.md`, §2, различение явного формала `y` и свободного имени `n` существенно. Его нужно сохранить, а не переносить один порядок получения значения на оба случая.

### 3.1. Явный формал `y`

В исходном примере:

```text
fn: add (int: x; int: y) int
. return: x + y
end: add
```

`y` объявлен формальным параметром. Если композиция предоставила этому формалу допустимое значение по умолчанию, он **остаётся тем же формалом**, а не превращается в свободное имя тела.

Для этого варианта получение `y` означает:

```text
аргумент y явно подан -> использовать поданное значение;
аргумент y не подан   -> использовать предусмотренный дефолт;
нет ни аргумента, ни допустимого дефолта -> обычный отказ вызова.
```

Одноимённая переменная в окружающем контексте вызывающего не становится автоматически явно поданным формалом. Для её подачи есть обычный вызов с аргументом.

Поэтому при дефолте `y = 5`:

```text
у вызывающего имеется собственное y = 25

add5(1)         -> 6
add5(1; y: 25)  -> 26
```

Это соответствует классификации `y` как формала в `Answer48.md`. Отдельное расширение динамического поиска на пропущенные явные формалы здесь не вводится.

### 3.2. Свободное имя `n`

В другом примере вложенный `addN` имеет явный аргумент `x`, а `n` читает из доступного контекста. Если `n` не объявлен формалом самого `addN`, копирование лексического контекста не делает его формалом.

Тогда сохраняется прежний порядок:

```text
ближайший подходящий динамический источник у вызывающего
    -> уже унаследованный динамический вход
    -> допустимый лексический запасной источник.
```

Явный `node\n` выбирает соответствующий лексический граф непосредственно.

Для такого тела `x + n`:

```text
скопированный лексический n = 5

при x = 1 и без динамического n:
    результат -> 6

при x = 1 и динамическом n = 25:
    результат -> 26
```

Наличие скопированной пятёрки не отключает динамический приоритет. Это именно случай D05–D07 предыдущего задания, а не правило о неявной подаче всякого формала.

### 3.3. Что исправить в объяснении возвращаемого метода

Схема из `Answer48.md`, §3, пункт 4:

```text
Data = merge(D_addN, {n: значение активации})
Code = C_addN
```

выражает сохранение нужных данных и переиспользование неизменённого кода. Объявленный тип результата проверяет получившийся callable обычным способом, не становится третьим неявным операндом.

Но последующее пояснение «значение легло в ячейку формала» применимо **только тогда, когда `n` действительно является формалом выбранного метода**. Для исходного примера вложенного `addN`, где `n` — свободное имя из объемлющего контекста, это неверное название роли.

Не исправляйте пример превращением свободного `n` в новый формальный аргумент или изменением тела. Скопированные лексические данные остаются лексическими данными; прежняя классификация входов сохраняется.

Мой прежний разбор смешивал эти два варианта `add5`/`addN`. Эту неточность не следует закреплять в спецификации.

## 4. Как описать аргументы по умолчанию без нового механизма merge

Аргументы по умолчанию — общая возможность вызовов, а не функция, включающаяся только после `merge`. Один и тот же смысл должен получаться при непосредственном задании такого аргумента и при обычной композиции его данных.

Рекомендуемая формулировка для §11:

> Формальный параметр с предусмотренным значением по умолчанию остаётся частью полного принимаемого интерфейса. При отсутствии явно поданного аргумента используется это значение; при явной подаче используется поданный аргумент, прошедший обычные преобразования и допуск. Наличие дефолта не удаляет формал и не превращает его в свободный динамический вход. Эти правила не зависят от того, были ли данные параметра получены через `merge`.

Значение, неподходящее по контракту, нельзя приравнивать к отсутствующему аргументу и молча заменять дефолтом. Ноль тоже является поданным значением.

Кроме того, надо различать **настроенный источник дефолта** и **значение аргумента текущей активации**. Простая подача `y: 25` для одного вызова не является командой изменить настройку последующих вызовов.

Для обычного дефолта, источник которого явно не менялся, последовательность такова:

```text
add5(1; y: 25) -> 26
add5(1)        -> 6
```

Не превращайте любое значение, оставшееся после прежнего исполнения в рабочей ячейке, в автоматически возникший дефолт. Обычная явная операция изменения того состояния, откуда берётся дефолт, — другой случай.

Эта граница описывает смысл вызовов, а не предписывает новую физическую раскладку, скрытый кэш или отдельный объект хранения. Если текущие правила ячеек и активаций не позволяют выразить её однозначно, покажите конкретное противоречие автору, а не выбирайте между «дефолт» и «последнее рабочее значение» самостоятельно.

## 5. Обязательные входы — не полная сигнатура

В `Answer48.md`, §3, пункт 6, написано:

> «Сигнатура результата = формалы без значения + свободные динамические имена тела».

В такой форме переносить это в книгу не следует. Это описание **остающихся обязательств по предоставлению входов**, но не полное описание всего, что callable способен принять.

У `add5`:

```text
принимаемые формалы:          x, y
можно не подавать явно:       y, если доступен его дефолт
требуется явно в примере:     x
прочие требования тела:       сохраняются
```

Необязательный `y` всё ещё имеет имя, тип и способ передачи; его разрешено предоставить явно. Он не исчезает и из требований неизменённой нативной реализации: до входа в неё нужное значение уже должно быть получено обычным механизмом вызова.

Поэтому фразу «сигнатура add пропадает» лучше убрать, а не оставлять с новым переносным смыслом. Пишите точно:

> Уменьшается набор аргументов, которые необходимо предоставить явно; формалы и остальные требования выбранного тела не исчезают.

Объявленный тип места с одним требуемым аргументом не вырезает поля кандидата и не меняет ABI его машинного тела. Возможность подстановки устанавливается общим admission с обычной подготовкой/преобразованием входов, включая дефолты. Нельзя заменять это ни специальным «merge-биндером», ни объявлением любых двух полных сигнатур одинаковыми только потому, что обе функции можно вызвать одним аргументом.

Если существующая формула `sig` и правило точного совпадения не различают принимаемый интерфейс, обязательную подачу и сформированные входы выбранной реализации, сформулируйте конкретное противоречие для согласования. Не удаляйте необязательные формалы из всех описаний автоматически.

## 6. «Тот же код» не отменяет копирование обычного графа

Сохранение нативной реализации — не сохранение исходного изменяемого callable-вхождения вместе с его состоянием.

Продолжают действовать ранее подтверждённые правила:

- обычные используемые Structure и лексические связи копируются по общему правилу;
- ссылки на соответствующие неизменённые нативные реализации переиспользуются;
- целая исходная графовая ветвь сохраняется по подтверждённому исключению `independent: const: immutable`, с прежними условиями владения и срока жизни;
- копирование не создаёт подписку на дальнейшие изменения оригинального состояния.

Поэтому фразу из `Answer48.md`, §1, что «нативная реализация или дерево операторов … не копируется», нельзя переносить в документацию как неограниченное новое исключение для любого графа операторов.

Нужно различать неизменность выбранного алгоритма и физическую идентичность обычных структур его представления. Если под «тем же деревом операторов» имеется в виду разделение обычной физической Structure, которое не следует из существующих правил, это отдельное утверждение: сопоставьте его с правилом копирования и спросите автора. Не выводите новое исключение только из схемы `Code = Cadd`.

Тем более не нужно ради сохранения `native` оставлять ссылки на исходные изменяемые данные: как раз передача графа скрытыми аргументами позволяет одной реализации работать с разными копиями.

| R48-01 | Копия callable с неизменённым телом и имеющимся `native` | Ссылка на нативную реализацию сохраняется |
| R48-02 | Изменены только данные, в том числе предусмотренный дефолт | Прежний код исполняется над новыми данными; `merge` не обнуляет `native` автоматически |
| R48-03 | Целиком выбрано другое готовое тело со своим `native` | Используется реализация выбранного тела; машинные тела не склеиваются |
| R48-04 | Тело изменено, подходящей нативной реализации нет | Прежний `native` не используется; допустимый L3-граф может интерпретироваться |
| R48-05 | Формал `y` имеет дефолт 5; вызов `add5(1)` | Результат 6 |
| R48-06 | Тот же формал; `add5(1; y: 25)` | Результат 26; `y` остаётся передаваемым параметром |
| R48-07 | Тот же формал; `add5(1; y: 0)` | Результат 1, не 6 |
| R48-08 | Явный формал `y` с дефолтом 5; у вызывающего есть одноимённое значение 25, но аргумент не подан | Для варианта из Answer48 результат 6; это не свободный вход |
| R48-09 | Свободный `n`, лексический запасной `n = 5`, динамический `n = 25`, `x = 1` | Результат 26; без динамического источника — 6; явный `node\n` читает соответствующее лексическое состояние |
| R48-10 | После `add5(1; y: 25)` выполняется `add5(1)`, источник дефолта не изменён | 26, затем 6; не вводится неявный «дефолт из прошлого вызова» |
| R48-11 | Более короткий объявленный тип принимающего места | Проверка общим admission, а не удаление полей или неявный третий операнд `merge` |
| R48-12 | Копирование обычной ветви и встреча квалифицированной вечной ветви | Обычный граф копируется; подтверждённое исключение `independent: const: immutable` сохраняется |

Это случаи для согласования текста и последующих тестов, а не отчёт об уже выполненном тестировании.

## 9. Если обнаруживается противоречие — спросить автора

**Не выбирайте семантику самостоятельно.** Приведите два конфликтующих положения, минимальный пример с различающимися результатами и один конкретный вопрос. До ответа приостанавливается только зависящее от него решение; независимые правки можно продолжать.

Уже отвеченные здесь вопросы не нужно задавать повторно. Но «да» на четыре пункта §5 не означает согласие с любым дополнительным выводом из остальных разделов `Answer48.md`.

Итоговая формула ответа:

> **Неизменённый код сохраняет соответствующий `native` и получает новые данные. Изменённый код не получает старую реализацию автоматически. `merge` не связывает аргументы: обычный формал с дефолтом остаётся явно переопределяемым, а свободный вход сохраняет обычный динамический приоритет. Объявленный заголовок — контракт принимающего места, не скрытый операнд композиции.**
