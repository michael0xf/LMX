# Ускорение трансляции и общий код интерпретатора

Дата: 2026-11-01, America/Sao_Paulo. Автор документа: Codex по прямому
поручению автора LMX. Получатели: Opus для предложений и передачи, затем
fable_pc для дизайна и оптимизации. Статус: требования к изменению архитектуры; реализация
не объявлена готовой.

## Цель

Трансляция должна занимать примерно столько же времени, сколько последующая
C-компиляция соответствующего результата. Часовые переводы небольших модулей
считаются критической проблемой реализации, а не нормальной ценой языка.

Почти весь код, кроме самой генерации текста, должен быть общим с интерпретатором.
Это одна реализация правил и операций, а не два независимо развивающихся
алгоритма с одинаковыми названиями функций или похожими интерфейсами.
Поддерживаемая реализация остаётся на L3 со вставками L2; L1/C — выходы.

Документация читается в обычном техническом смысле с учётом прямых уточнений
автора. Не добавлять проверки «на всякий случай», лишний анализ или
произвольные исключения из явных контрактов, в том числе из объявления
`throws`. Общая логика интерпретатора и транслятора реализуется одним кодом;
отдельными остаются действительно специфичные операции исполнения и генерации.

Проверки типов во время трансляции разрешены только в объёме, необходимом
для формирования корректного C. Языковая совместимость фактического значения
с требованием принимающего места проверяется runtime через implements и его
специальную ошибку. Дополнительный статический типизатор не является частью
сбора, общей валидации или подготовки native; одно C-представление не служит
доказательством языковой совместимости.

Интерпретатор не пытается заранее понять всю программу. Разрешение и проверка
операции происходят при её фактическом выполнении, в том числе при runtime-
приёме значения для текущего вызова или присваивания. Общность реализации не
разрешает перенести удалённый статический анализ в предварительную подготовку
интерпретатора. Он вызывает общий код по мере исполнения, без прогнозирования
будущих ветвей, тел и изменений.

Дословные технические уточнения автора находятся в
[журнале от 1 ноября](LMX_blog/2026-11-01.md). Прежние предложения
[Codex](optimization_proposal_from_codex.md) и
[Fable](optimization_proposal_from_fable.md) сохраняют исторические измерения,
но не разрешают продолжать противоречащую этим уточнениям архитектуру.

## Три обхода дерева

Допускаются только три обхода, в указанном порядке:

1. **Сбор данных.** Учесть узлы, объявления, их владельцев, контексты и места
   использования. Учёт узла не делает позднее объявление видимым раньше
   положенного. Регистрация служебной процедуры не должна заставлять заново
   обходить уже обработанные тела всех методов.
2. **Валидация вызовов и присваиваний.** Применить общие с интерпретатором
   правила к конкретным записанным операциям и их явным контрактам. Не
   прогнозировать ошибки исполнения и не доказывать будущие значения.
   Проверки типов во время трансляции ограничены необходимым для написания C;
   языковой допуск фактических значений остаётся runtime-решением.
3. **Трансляция.** Сформировать выходной текст из уже собранных данных и
   результатов общей валидации, без нового семантического обхода под видом
   emission или вспомогательного поиска.

Первые два обхода — общий код с интерпретатором. Почти вся остальная работа,
кроме печати результата, также должна использовать общие механизмы. Дизайн
обязан показать, где проходит граница общего кода и генератора, и обосновать
каждую оставшуюся часть, специфичную для транслятора.

Нельзя спрятать дополнительные полные обходы в helpers, повторную
классификацию каждого узла, нормализацию или отдельную систему подготовки.
Табличные обращения не должны заново искать исходное вхождение обходом дерева.
Дизайн должен учитывать фактическое количество посещений узлов.

## Runtime и явные контракты

- Анализ ошибок будущего исполнения вне явно написанного программистом `test`
  не выполняется. Первая часть допуска проверяет используемые интерфейсы;
  UNKNOWN сам по себе не означает NO.
- Если контракт вызова требует передачи ошибки, вызывающий обязан явно
  иметь соответствующий `throws` либо обработать её через `catch`.
  Отсутствие обоих — ошибка трансляции. Автоматически распространять признак
  ошибки по графу вызовов и добавлять его вызывающему нельзя.
- При изменении исполняемого кода runtime сбрасывает `native` соответствующей
  структуры в 0. Далее исполняется актуальный граф. Транслятор не предсказывает
  будущие изменения кода анализом тел, записей или алиасов.
- Если проверка присваивания требует анализа исполнения, решение принимает
  runtime через общий допуск `implements`. Известное несоответствие даёт
  специальную ошибку несовпадения типов/`implements`, а не заранее введённый
  запрет динамического случая.
- Явная валидация второго обхода сохраняется. Удалению подлежат её подмены
  прогнозированием исполнения, а не сам второй обход.

Интерпретатор должен работать и с актуальным графом, построенным во время
исполнения: без готового шаблона транслятора, скрытого исходника или обязательной
предварительной трансляции. Общий код не вводит новый разбор, грамматику,
library-only comparator, hidden root или singleton.

## Профиль и сравнение скорости

Сравнивать L3/L2→L1, L1→C и C-компиляцию отдельно, на соответствующем одном
наборе исходников, с указанными compiler bytes, flags, CWD и зависимостями.
Записывать wall time, CPU и память. Для целевого сравнения брать перевод
соответствующего компонента и C-компиляцию его результата, не выбирать
несопоставимые программы или режимы оптимизации.

Ускорение не должно получаться удалением нужного runtime-допуска, изменением
семантики, подменой самосборки готовыми файлами или переименованием этапов.
Цель «примерно столько же» не заменяется самостоятельно придуманным процентным
порогом, но порядки отставания должны быть устранены и показаны измерениями.

perf251 attempt02 с пустым CWD неверен: predef-файлы отсутствовали, его первый
снимок стека отозван. Attempt03 использовал реконструированный контекст из
211 файлов; его фактический terminal и границы берутся из передачи Opus.
Недопустимо выдавать подготовленный запуск или один снимок за причинный профиль.

## Что должен предложить Opus

Создать `optimization_proposal_from_opus.md` на основе этого документа и
действительного кода. Включить:

1. Существующие лишние обходы и анализаторы, точные файлы и функции, зависимости
   от их служебных таблиц и способ удаления без сохранения прежнего анализа
   под другим именем.
2. Предложение общего кода с интерпретатором для сбора, валидации, разрешения
   мест, вызовов, присваиваний и runtime-допуска; отдельную границу генерации текста.
3. Проверку явных throws/catch, специальной runtime-ошибки и сброса native.
4. Измеренные факты и гипотезы раздельно; состояние каждого profiling attempt.
5. Небольшие последовательные шаги миграции, их зависимости и необходимые
   фокусные проверки существующими средствами.

После предложений оформить `to_fable_design_from_opus.md`: SHA/WIP,
изменённые файлы, точные receipts, живые процессы и агенты, незавершённые
операции. Затем сообщить Codex и перейти в ожидание в той же открытой сессии.
Пока Fable владеет работой, Opus не реализует дизайн и не начинает новые
переводы или сборки. Уже сделанный WIP сохранить.
Ненужное измерение безопасно завершить с записью причины, не ждать его час
только ради передачи. Все вопросы — Codex.

## Задача Fable после передачи

fable_pc разрабатывает `optimization_design_from_fable.md` после получения
предложений Opus и перехода Opus в ожидание без пишущих агентов/pipeline. Он сопоставляет предложения
со своими прежними исследованиями, но проектирует решение по новым требованиям.

Нужны структура общего кода, владение данными, точный состав трёх обходов,
границы генератора, runtime-пути отказа и invalidation, удаляемые механизмы,
порядок перехода к рабочей самосборке и способ измерения скорости. Открытые
нормативные вопросы направлять Codex; не придумывать ограничения за автора.

По последнему поручению автора Fable после записи дизайна самостоятельно
переходит к реализации оптимизации, без формального ожидания ревью.
Он получает единственный writer/build; Opus остаётся открытым и ждёт.
После завершения Fable пишет `to_opus_after_optimization.md`, освобождает
writer/build и через Codex передаёт результат Opus для продолжения самосборки.
Если после готового дизайна Fable фактически недоступен, Codex устанавливает
безопасную границу и передаёт дизайн/WIP Opus для продолжения оптимизации.
Ни Codex, ни ожидающий Opus не реализуют изменения параллельно Fable.

## Рабочие границы

Фокусные проверки — под конкретный шаг; whole quick — когда нужен сквозной
результат; FULL — только финальный этап. Новые runner/cache/scheduler и широкая
тестовая кампания не создаются. Корневой `build` не читается и не трогается;
защищённый basename и unrelated patch из действующей передачи сохраняются.
Не reset/clean, не массовый git add, не новые ветки/worktree/PR. Внешние
процессы не останавливать по одному старому PID. Goal Codex остаётся на паузе.
