## Дополнение 2026-11-13: общий native и публикация — OPEN

[M14](../next_core_tasks_v3.md#native-structures) требует native обычной C общим с методами механизмом,
без data = code, искусственного fn и нового runtime. Один вход работает с разными допущенными D
через существующие кадр и карту мест. Dirty кода и данных, стандартная публикация и продолжение
после неё должны совпадать у native и оптимизированного кадрами обходчика.

По чтению main cde574b8 `lm_graph_collect_methods` пока отбирает результаты fn/sub, корень выпускается отдельно.
`lm_graph_emit_methods` устанавливает выпущенный адрес на объявлении; `lmx_graph_fn_make` переносит его
в созданную функцию. Это не компиляция внутри fn и не готовый native произвольной вложенной C.
Код этим документальным уточнением не изменён. Новая норма не утверждает готовности M14;
прежние свидетельства о прямой записи не задают момент публикации в новой реализации.

Следующее уточнение M14: единая семантика без универсального журнала каждого присваивания;
native по возможности определяет записи статически, динамический учёт нужен только необходимым местам.
Локальные рабочие значения сохраняются в своих кадрах. Кеш прямого доступа общий для всех вызовов
одного исполнения и согласует фактическую ячейку, включая алиасы и публикацию локального dirty.
Языковой flush() без аргументов и результата сначала публикует dirty собственных локалов текущего
кадра в общее состояние, затем ожидающие записи общего кеша — в граф; локалы других кадров не трогает.
Исполнение продолжается без новой активации или публикации Message. Повтор без изменений ничего не пишет.
Внутренний `lmx_graph_work_flush` уже публикует dirty своего подмножества рабочих мест и очищает отметки;
это задел общего механизма, не доказательство готовности ресивера или всех требований M14.
[Контракт](LMX_semantics.ru.md#flush-receiver-contract); реализация остаётся OPEN.

По чтению main 035d3fcd локальные снимки и их dirty уже отделены от прямой записи в граф;
это не готовый общий кеш прямого доступа. Срез 369 сохраняет локальный снимок указателя, поэтому
p\x и data\p\x могут законно выбирать разные объекты. При одинаковом адресе устаревшее прямое чтение
недопустимо. Новое разделение требует общей согласованности, а не перезагрузки локалов после вызова.
[Норма](LMX_semantics.ru.md#direct-access-cache); этот документальный срез код не меняет.

## 1. Источники и граница переноса

Поддерживаемый исходный язык ядра, парсера, трансляторов и обычной сборки —
L3 со вставками L2. L1 — только генерируемая ступень L3/L2→L1→C;
платформенный bootstrap однократен. Пока в closure есть поддерживаемые
вручную L1-исходники или внешние build/test-скрипты организуют обычный цикл,
§8 не завершён. Для каждого перенесённого тела и заголовка нужен manifest
зависимостей, тест и удаление старой авторитетной реализации.

<a id="l1-status"></a>
## 2. Translator-L1

Старый L1 seed/pin и историческая самосборка переводчика — переходные
инструменты, **не** самосборка L3/L2. M4 требует единого порядка плоских
объявлений «имя, требование, начальное значение» и в генерируемом L1:
сначала временно читающий оба порядка переводчик, затем перевод всех путей
эмиссии, исходников и тестов, наконец удаление старого порядка и новая
проверка seed/pin. Типовое выражение `@: T` не является объявлением
`@: name T`. Старую L1-ветвь нульарного вызова голым оператором исследовать
отдельно; она не становится нормой L3. Подробности и исходные замеры —
[миграционный тикет](../steps/tickets/unique-name-reference-migration-20261014.md).

Нынешний L1-путь `[]:` ещё понижает голую форму в сырой C-массив. Это
переходное расхождение с [целевым L1 §20](L1_spec_ru.md#lowlevel-array):
обычный `[]:` должен строить графовый Array на основе `Lmx`; только явный
`c.array:` оставляет машинный C-массив. Перенос требует изменить понижение,
конструкторы, классификацию и копирование совместно, а не добавить ещё один
специальный вариант `[]:`.

Прежние возможности `C:`, `c.struct`, `c.union` и `synchronized` нельзя
объявлять реализованными по старым примерам без проверки обработчика.
Машинные ограничения прежнего `throw` payload не переносить в L2/L3.

У обычной Structure и `Array<@>` backing содержит `void *` элементы;
адрес такого слота — `void **`. Числовой Array хранит непосредственно
типизированные элементы T. Количество элементов выбирается при создании;
опубликованный backing не растёт и не переезжает. Миграция сохраняет
типизированное хранение, карту копирования адресов и `parent` для Array и
вложенных Structure. Общие операции должны принимать Structure и
`Array<@>` взаимозаменяемо, без отказа только по категории заголовка.
`descriptor` ещё не реализован: он должен выбирать явно переданную S либо текущую data
при вызове без аргумента: `descriptor() = descriptor(data)`, в том числе во вложенных телах управления.
Оба варианта возвращают реальные адреса полей с записью через обычное разыменование и штатной публикацией кадра
([контракт](L2_spec_ru.md#get-descriptor)). Произвольные конечные глубина
указателя и мерность массива используют существующие общие алгоритмы;
старый парсер заново не пишется. Типизированные массивы арены остаются
хранилищем, не самостоятельными объектами языка. Растущий
`Thread.children` — **отдельный** List/DynamicArray, а не расширение Lmx
или поле программы. Служебные данные запуска принадлежат R0-заглушке.
Норма и устройство — [L2](L2_spec_ru.md#lmx) и
[Thread](L2_spec_ru.md#thread).

При копировании описания сохраняется доказательство его адресной
раскладки. Поздний аргумент может использовать составление уже известных
соответствий к этой раскладке; результат кэшируется как карта адресов,
а не как новая полная проверка принимающего описания или Consumer.

Конструкторы возвращаемого метода сначала собирают ссылки на значения
захватов, затем копируют этот контекст вместе с выбранным методом одной
картой графа. Повторные ссылки на одну захваченную Structure ведут к
одному свежему объекту, не к отдельной копии на имя. Удержание следует
тем же допущенным профилям `independent: immutable`, что обычная копия.
Текущие проверки и остаток — в [рабочем журнале](../steps/current.md).

Коды идентификаторов (IDENTIFIER-CODES; решение автора 2026-11-07,
[книга](LMX_semantics.ru.md#fields)). Сервис процесса `lmx_ids` —

привязки активаций, связыватель именованных фактических, селекторы путей
`(код, вхождение, префикс)` и ключи бросков native и обходчика; копирование
переносит код, не читая написания (срез 302, промежуточный результат).

поручением автора 2026-11-08 до установки в selfbuild — его кандидат сохранён
как WIP в [записи](../steps/witnesses/fix308-20261108/notes.md). Решения автора
2026-11-08 18:00–18:20Z ([журнал](../LMX_blog/2026-11-08.md)): отдельный тип «T без

включая первую, идёт в неё же. По [позднему уточнению](../LMX_blog/2026-11-08.md#uninit-pointer-preserved)
поле Structure и служебный указатель сохраняются: заменять или переключать их при первой записи не нужно.
Это исправляет прежнее пояснение исполнителя, а не вводит новое правило языка. Все

перемещения ячеек. Устройство задаёт [спецификация реализации
ядра](kernel-implementation.ru.md); нынешние `lmx_ids`, `LmxSourceName`,

([реестр дефектов](../steps/defects.md)).

<a id="l3-status"></a>
## 4. Интерпретатор L3 и допуск

Интерпретатор исполняет построенный граф. В [допуске](LMX_semantics.ru.md#admission) два шага:

1. Проверка используемого интерфейса через `implements`. Она выполняется один раз для каждого кандидата:
   при построении графа, если он известен, иначе при фактическом приёме во время исполнения.
   Кандидат, Consumer и будущие тела на этом шаге не исполняются. Без Consumer проверяются явно
   предъявленные требования `bVar`, а не полное совпадение структур.
2. Явно написанные программистом `test` при фактическом допуске во время исполнения. При построении
   графа они не запускаются. Первый результат `0` сразу прекращает допуск; остальные проверки не выполняются.

Известность кандидата при построении не отменяет второй шаг и не требует повторять первый.
Установленное соответствие адресов сохраняется при изменении значений. Замена ветви допускает
нового кандидата **до записи**; сама мутация не повторяет весь набор тестов.
Проверка диапазона при преобразовании числа остаётся проверкой конкретного принимаемого значения;
правило об однократном `implements` её не отменяет.

**Состояние реализации:** перенос первой части на построение чистого графа ещё не завершён —
шаг 7 [M11](../next_core_tasks_v3.md#m11). Обновление нормы не является закрытием этого шага.
Паритет native/walker, публикация состояния и полный граф остаются в [K01–K12](../next_core_tasks_v3.md).
Подробности: [соответствие мест](LMX_semantics.ru.md#correspondence-stability),
[приём аргументов](LMX_semantics.ru.md#argument-compatibility-stage).

<a id="test-receiver-proposal"></a>
### 4.1 test: принятое правило, открытая реализация

`test` — утверждённый ресивер; [контракт](LMX_semantics.ru.md#test-receiver-contract).
Проверки принадлежат принимающему выражению. Без явного Consumer они берутся из `bVar`, не из `aVar`.
Пригодность кандидата для обращений самой проверки устанавливается до её исполнения.
Проверка завершает уже начатый допуск и не начинает тот же допуск заново. Для успешного допуска
нужен успех всех проверок; при первом `0` выполнение списка прекращается.

Прямой проход по `data` исполняет только ресиверы объявления корневого уровня. Выполняемый ресивер
может дойти до переданного ему кода, включая `test`. Само присутствие записи `test:` среди данных
её не запускает; отдельный рекурсивный обход ради тестов не нужен.
Это [общее поведение ресиверов](LMX_semantics.ru.md#data-root-declaration-execution).

**Реализация ещё не закрыта.** Использовать общий P0, разрешение головы, адресацию и обычную
диспетчеризацию native/walker. Не вводить скрытый каталог тестов, runtime-таблицу имён или `skip_tests`.
Имя `test` зарезервировано: пользовательский метод с этим точным именем переименовывается в `mytest`;
`test2`, `test3`, строки и исторические цитаты по подстроке не переименовываются.
Проверки компонентов самосборки переносить в язык по мере переноса самих компонентов.

<a id="assign-named-merge"></a>
### 4.2 `:=`, именованная подача, `merge` аргументов и вся структура аргументов: норма принята, реализация срезов 303–304, частично 307 (остатки по ревью Codex 307 — следующий срез)

Решение автора 2026-11-10 ([книга](LMX_semantics.ru.md#receiver-args-only)): место объявляет только форма
`ресивер: аргументы`, запись поля «имя: тип: значение» (`a: int: 5`) снята. Срезы ниже описаны так, как
исполнялись: с полем операнда `merge` в прежней записи, которую трансляторы пока принимают; по норме оно пишется
`(int: a 5)`. Так же описаны имя, держащее результат `merge` (`pack: merge(...)`), и формал или поле, записанные
структурной формой (`Q: q`): по норме 2026-11-11 ([книга](LMX_semantics.ru.md#data-code-roles)) их объявляют
`@: pack merge(...)` и `@: q Q`. Перевод фикстур и смена чтения — [план M9](../next_core_tasks_v3.md#m9) и
[M11](../next_core_tasks_v3.md#m11).

Нормы — [запись в известное место](LMX_semantics.ru.md#assign-known),
[именованная подача](LMX_semantics.ru.md#named-actuals) и
[вся структура аргументов](LMX_semantics.ru.md#whole-arguments)
(решения автора 2026-11-07). Проба на опубликованном кортеже 301
([запись](../steps/witnesses/named-assign-20261107/notes.md)) показала, что
реализация их не выполняла: `:=` не распознавался, `f(a: 5)` и `f(a(5))`
связывали формал `a` по совпадению имени головы (35 и ни одного вызова
`a`), операнды `merge` в формах `callable\args`, `a: int: 5` и
`(a: int: 5)` не опускались, единственная Structure не принималась как
вся структура аргументов. Срез 303
([запись](../steps/witnesses/fix303-20261107/notes.md); native и обходчик,
оба корня) выполняет первые две нормы и часть третьей:

- `:=` — один операторный токен P0: Frame левой и правой части с флагом
  `LM_P0_FRAME_ASSIGN`; `a := 5` и `a:=5` — одна запись, `a:` головой
  Frame не становится.
- Запись известного места — общий путь присваивания: локал, формал
  (значение активации), поле по пути, преобразование при приёме, ссылка
  на метод (`target := two` переопределяет ссылку без вызова голой правой
  части — natively и в программе обходчика, чей диспетчер прежде читал
  привязку с callable как вызов держимого метода). Неизвестная левая
  часть — отказ трансляции «:= writes a place already known: its left
  side is not one here», в теле метода и в теле именованной Structure;
  поля она не определяет. Местом считаются объявленные формалы, видимое
  поле (поле единицы, видимое методу, — его скрытый вход, Q52), слот,
  локал метода и активация хоста вложенного метода; скрытый вход,
  который сбор делает из свободного имени для `x: v` (норма — единое
  разрешение головы и книга; steps/free-names.md — история механизма,
  его §7 отозван уточнением 2026-10-03), местом для `:=` не является.
  Имя метода как левая часть внутри метода (`one := two`) упирается в
  существующий предел реализации — запись скрытого входа без значения
  активации («writing a hidden input that has no activation value is
  not supported yet»), тот же, что у `x: v`; это не правило языка. По
  норме 2026-11-11 такая запись ошибочна и по правилу языка: слева от `:=`
  не стоит имя функции ([книга](LMX_semantics.ru.md#data-code-roles)).
- Именованная подача — только `f(a := v)`: левая часть выбирает формал
  выбранного вызываемого, правая вычисляется обычно. `f(a: 5)` и
  `f(a(5))` при видимом callable `a` — его обычный вызов, результат
  позиционный (62 и ровно один вызов `a`); неизвестное имя («zz is not
  an argument of tst») и позиционный после именованного — отказы
  трансляции. Части ресивера `table:` связываются по голове его
  грамматики тем же связывателем в режиме `by_head`.
- Операнд `merge`, записанный «имя: тип: значение» — `(a: int: 5)` и
  голый `a: int: 5`, — типизированное поле, как форма объявления
  `(int: a 5)`: пишет слот модели своего имени, остальные поля
  сохраняет, модель не пишет; скобки у второго операнда не обязательны.
- Операнд `merge` «часть вызываемого» `f\args` (срез 304,
  [запись](../steps/witnesses/fix304-20261107/notes.md); native и
  обходчик, оба корня): часть `args` вызываемого читается как Structure
  его формалов — поле на каждый записанный формал, в порядке формалов, со
  значением текущего умолчания формала (то, что формал получает, когда
  вызов его опускает); формал без текущего умолчания — обязательный или с
  записанной формой, которую трансляция не строит, — значения не держит:
  его слот пуст, ноль не придумывается, и операнд допускается, только когда
  поздний операнд того же `merge` пишет это поле, иначе отказ у операнда
  (ревью Codex 304; явный ноль `int: z 0` — значение). Читает
  ядро — одна функция обоих исполнителей (`lmx_callable_args_value`;
  программа обходчика берёт её примитивом над вхождением вызываемого);
  операнд распознаёт общее разрешение пути (последний шаг — часть `args`
  метода), поля результата — типизированные поля объявлений формалов.
  `merge(tst\args; (a: int: 5))` читает `a` = 5 и `c` = 3, голая форма
  `a: int: 5` — так же, `merge(tst\args)` — `c` = 3 и `a` = 0; `tst\args`
  не записан. Пределы реализации, не правила языка: формал не числового
  типа не имеет рода поля в карте результата — отказ у операнда («a formal
  that is not a number is not lowered as a field of the args part yet»);
  чтение поля части args путём (`tst\args\c`) не разрешается («unknown
  field path segment»).
- Вся структура аргументов из одной Structure (срез 307,
  [запись](../steps/witnesses/fix307-20261108/notes.md); native и
  обходчик, оба корня): вызов с единственным аргументом-Structure не
  отличается от вызова с цепочкой её полей. Связыватель отмечает один
  позиционный фактический, который может дать Structure (имя, путь,
  `merge`, вызов), кандидатом и откладывает проверку опущенных формалов;
  проверка решает по статической форме фактического и формалам выбранного
  вызываемого (`lm_compiler_whole_decide`): каждое поле — формал своего
  имени и класса своего рода, каждый прочий формал с построенным
  умолчанием — поля суть аргументы; иначе остаётся обычное позиционное
  чтение; когда Structure годится и первому формалу — Structure-формалу,
  по первой части `implements` при трансляции, как велел автор
  2026-11-08, — а прочие формалы с умолчаниями, применимы оба чтения, и
  ce01c206 отказывает как неоднозначный («the Structure given to k
  is its argument q and its arguments: an ambiguous call», фикстура
  `whole_ambiguous_refused`); ревью Codex 307 установило: это моё
  расширение нормы, не решение автора (он говорил о двух действительно
  подходящих методах; два `fn` одного имени в одной единице трансляция
  отказывает при определении) — отказ снимается следующим срезом,
  обычный однозначный вызов сохраняется, нового приоритета трактовок
  нет, случай двух методов — остаток. Связывание —
  одна функция ядра обоих исполнителей после вычисления единственного
  фактического (`lmx_call_bind_whole`): форма по текущей части `args`
  выбранного вызываемого — каждое поле формал, каждый прочий формал с
  текущим умолчанием, иначе неявный `call`; затем каждый формал в
  собственном порядке принимает поле своего имени, как принимается
  записанный фактический срезов 305–306 (число — маршрутом своего типа
  или неявный `convert`, граф — собственным приёмом входа формала,
  опущенный формал — умолчанием). Поля значения — его именованные
  ячейки: native-раскладка объявленной Structure держит ячейку шага рядом
  с каждым местом (`Args: int: c 4; int: a 6` — четыре ячейки, `c` и `a` в
  0 и 2). `pack: merge(mytest\args; (a: int: 5)); mytest(pack)` = 35,
  как `mytest(a := 5)`; объявленная `Args (c 4, a 6)` у `mytest` — 46,
  `Args` не записана; `Only (a 9)` — 39; поле-Structure у
  Structure-формала, поле char у int-формала через ресивер программы
  (один вызов), вызываемое место `Places\f` (держимое с другими именами
  формалов — неявный `call`); обычное чтение у `take(Point)`,
  `take(p := Point)` и Structure с лишними полями (фикстура
  `whole_arguments`). Второй проход 307 (после ревью Codex; та же
  запись): `merge`, записанный в самом вызове —
  `mytest(merge(mytest\args; (a: int: 5)))`, — поднимается трансляцией в
  скрытое объявление `l2_lift_<метод>_<offset>: merge(...)` перед
  оператором (`lm_compiler_merge_lift_walk` до сбора own и связывания
  вызовов: фактические вызова, значение объявления или `return`;
  операнды merge остаются операндами) и даёт 35 в обоих исполнителях
  (`by_inline`); имена и форма целого проверяются до вычисления
  фактического — ядро `lmx_call_bind_whole_form` по кодам имён
  статических полей против выбранного сейчас вызываемого (native
  `l2_wn`/`l2_wfs` перед вычислением, операнд WHOLE несёт имена):
  держимое с другими именами формалов — неявный `call`, производитель
  со счётчиком не запускается (`early_form`, `Made\n` = 0);
  применимость чтения «единственный аргумент» и допуск полей — общей
  проекцией требований относительно Consumer
  (`lm_compiler_whole_applicable`: uses входа выбираются, пути требования
  проецируются в кандидата), строгой по роду листьев, как обычный допуск
  и приём исполнителей (проба `whole_leaf_convert`: кандидат, допущенный
  таблицей преобразований, останавливал R0 в обоих исполнителях —
  таблица у вложенных листьев остаётся общим остатком); отказ двух
  чтений снят, удержание тоже (ответ автора 2026-11-08, журнал):
  Structure, чьи прямые поля называют формалы, подаётся своими полями
  по базовому правилу — годность её первому формалу как значения
  правило не спрашивает (фикстура `whole_direct_fields`: `k (Q: q; int: z 0)`
  при `QZ (int: z 5; Q: q)` — `q` и `z` из `QZ`, без умолчания, 15; явная
  подача `k(q := QZ)` — 50); поле-Structure без листа, который читает
  вызываемый, отказывается трансляцией (фикстура `whole_field_refused`),
  поле другой модели с нужными листьями допускается (`SArgs` с
  `Shape (x, y, w)` у `g` — 10). Границы:
  операнды `merge`, записанного в вызове, вычисляются до проверки формы
  вызова, как у записанного `pack` (пролог native-оператора читает own до
  его кода — откладывать скрытое объявление к месту вызова нельзя);
  `merge` в фактическом вызова держимого вызываемого по голому имени,
  глубже в выражении или в управляющем операторе не поднимается (прежний
  отказ). Приоритет `:=` среди операций и значение записи
  как выражения нормой не определены; составные присваивания —
  [4.3](#compound-assign-notes).

Записи дефектов — в [реестре](../steps/defects.md).

<a id="compound-assign-notes"></a>
### 4.3 Составные присваивания и `**`: принятая норма, открытая реализация

Норма — [составные присваивания и степень](LMX_semantics.ru.md#compound-assign)
и [грамматика §21](LMX_grammar.ru.md#operators) (поручение автора
2026-11-07, уточнение о группировке `**` как в Python). Реализации нет: P0
не выделяет токены `+=`, `-=`, `*=`, `/=`, `%=`, `<<=`, `>>=`, `&=`, `^=`,
`|=`, `**=` и `**`; понижения составного присваивания в запись известного
места и операции степени нет ни у native, ни у обходчика. Намеченный путь —
общий с `:=`: один токен в P0, понижение `a op= b` как `a := (a op b)` с
однократно вычисленным местом слева (не макроподстановка), `**` как общая
числовая операция ядра для обоих исполнителей. До реализации уточняются:
однократность места с эффектами, типы и преобразования `**`/`**=`,
отрицательная и дробная степень, `0 ** 0`, приоритет присваиваний среди
операций ([план M5](../next_core_tasks_v3.md#m5-assign-operators)).

<a id="open-design"></a>
## 5. Открытые решения

- Точная форма неуспеха набора `test` и её связь с объявленным `throw`.
- Выгрузка позднего модуля, чьи `independent: immutable` ветви по
  физическим адресам удерживаются потребителями; до решения владелец
  явен, скрытого глобального хранилища нет.
- Детали реализации утверждённой компоновки `args`/`return`/`data`/`code`
  и `call: data code`: read-before-write, скрытые входы, `node`, `catch`
  и совместимость native ABI. Они закрываются в N1–N6 плана v3, а не
  возвращают модель в статус факультативного исследования.

<a id="grammar-extraction"></a>
## 6. Граница грамматики и реализации

Грамматика описывает P0-форму, но не доказывает поддержку транслятором.
По решению автора 2026-11-10 P0 единственную анонимную Structure списка
аргументов не раскрывает: `f()`, `f:` и `f:` с явным `---` дают одну пустую
Frame/body-форму, а `f: ()` — то же, что `f(())`: одно поле, пустую
Structure ([грамматика](LMX_grammar.ru.md#empty-colon)). В M8, срез 366,
постпроход раскрытия и запрет голого `f:` удалены; потребители читают
сохранённую группу по контракту. Приёмка и оставшиеся границы M11 —
[свидетельство](../steps/witnesses/m8-preserved-groups-20261113/notes.md).
Голое `f` — атом, а не вызов.
Исторические goldens не автоматически нормативны.
Открытые parser/consumer-разрывы и точные свидетели —
[parser fix](../next_parser_fix.md) и [план v3](../next_core_tasks_v3.md).
Диагностика Mix-меток: метка с ошибкой внутри вне строки — ошибка разбора
(внутри строки она строку не роняет), `{#...}` — метка с комментарием, а не
ошибка ([грамматика §19](LMX_grammar.ru.md#mix)); точные коды ошибок не
выводятся из старого текста по догадке.
