# Спецификация L2

L2 — LMX со специальными операциями низкого уровня. Настоящая спецификация определяет эти операции и устройство ядра. Семантика чистого герметичного LMX (L3) — в [основной спецификации](LMX_semantics.ru.md); грамматика — в [спецификации грамматики](LMX_grammar.ru.md); понижение тех же механизмов через L1 и C99 — в [спецификации L1](L1_spec_ru.md). Состояние реализации, срезы исходников и задания переноса вынесены в [заметки о реализации](implementation-notes.ru.md).

Оба описания задают один механизм на соответствующих уровнях; основное определение располагается здесь или в L1, а связанный документ ссылается на него.

<a id="scope"></a>
## 1. Предмет

L2 — язык механизмов ядра: структуры `Lmx`, типизированные массивы арены, Message, почта, ход (turn) L3 Thread, копирование графа и вызов. Цепочка понижения — L2 → L1 → C99, как определено в [семантике](LMX_semantics.ru.md#scope).

L2 задаёт машинные механизмы, L3 — высокоуровневые программы. Генерируемое промежуточное представление L1 является стадией понижения, а не исходным графом программы. Интерпретатор потребляет только [граф L3](LMX_semantics.ru.md#l3-receiver), а не L2-операции.

<a id="lmx"></a>
## 2. Структура `Lmx`

Основное определение записи узла: `l2src/lmx.h.lm1`, `struct: Lmx`. Три поля, порядок нормативный:

| поле | тип | смысл |
| --- | --- | --- |
| `node` | `@: Lmx` | лексический родитель; у корня — нуль |
| `len` | `int` | число непосредственных детей, не байты и не длина Array |
| `data` | `@: void` | адрес ячейки в типизированном массиве; по ячейке лежит значение или дескриптор в зависимости от массива |

У ребёнка нет тега типа. Тип значения — диапазон адресов, в который попадает **хранимое значение** ребёнка, а не адрес слота. Слоты не добавляются и не удаляются после построения. Вызываемый объект — обычная Structure: физический `child[0]` указывает на запись METHOD, дальнейшие слоты — собственные поля вхождения; `M.node` — лексический родитель. Зарезервированный аргумент `node` вызова — само выбранное `M`. Реализация на L1: [L1](L1_spec_ru.md#lmx).

<a id="type-by-range"></a>
## 3. Тип по диапазону адресов

Реестр грубых родов — `enum: LmxKind` (`NONE`, `PRIMITIVE`, `METHOD`, `ARRAY`, `CHILDREN`, `REF`, `STRUCT`). Конкретный машинный тип представления — `enum: LmxType` (примитивы, дескрипторы Array, METHOD, Structure, указатели, массивы указателей; базы `LMX_TYPE_POINTER_BASE` и `LMX_TYPE_ARRAY_OF_POINTER_BASE`). Один полуоткрытый интервал — `struct: LmxRange` (`lo`, `hi`, `stride`, `kind`, `type`). Классификация адреса — индекс арены: `lmx_range_classify`, `lmx_range_type_of`, `lmx_range_pool` в `lmx_arena.h.lm1`. Ничего не пишется на ячейку, чтобы «сказать, что это». Квалифицированные типы, в том числе результат композиции принимающих выражений `independent: const: immutable`, распознаются тем же механизмом вхождения адреса в типизированный диапазон. Идентичность диапазона/адресного домена несёт квалифицированный тип, а `kind`/`type` задают его физическое представление; для цепочки не вводится отдельный флаг значения, классификатор, `LmxType` или `LMX_DOMAIN_KIND_*`. Роль постоянного хранилища определяет время жизни его диапазонов, но не заменяет их тип. L1: [L1](L1_spec_ru.md#type-by-range).

Механизмы ядра, которых нет в закрытом `lmx.h`, регистрируют **домены** отдельными константами в `lmx_implements.h.lm1` (`LMX_DOMAIN_MSG_RECORD` … `LMX_DOMAIN_POST_RING`), не расширяя запись Message.

<a id="pool"></a>
## 4. Типизированный служебный массив

`struct: LmxChunk` / `struct: LmxPool` в `lmx.h.lm1`; акты в `lmx_pool.h.lm1`. Массив выдаёт ячейки одного `stride` и растёт **добавлением чанка**, не `realloc`: живые адреса не переезжают. Каждый чанк регистрируется в индексе арены как ещё один интервал того же `(kind, type)`. Ячейки поштучно в массив не возвращаются; повторное использование — свободный список владельца (как у почты). Интернированные неизменяемые атомы (например, 256 ячеек символов) могут не расти. L1: [L1](L1_spec_ru.md#pool).

<a id="method-array"></a>
## 5. METHOD и Array

`struct: LmxMethod` — `{addr, sig}`; `addr` — вход C, `sig` — контракт диспетчера, не контракт вызова на этом этапе. Запись не хранит `node`. Копирование графа сохраняет указатель на METHOD.

`struct: LmxArrayDesc` — `{len, data}` без узла `Lmx`. Длина относится к элементам массива, не к полям Structure ([семантика](LMX_semantics.ru.md#values)). L1: [L1](L1_spec_ru.md#method-array).

<a id="arena"></a>
## 6. Арена

`struct: LmxArena` в `lmx_arena.h.lm1`: список блоков владения, N массивов, индекс адрес→дескриптор, поколение GC, флаг `simple`. Менеджер арены — единственный писатель индекса. Ячейки после однократного определения типа пишутся напрямую: адрес ячейки не меняется.

Существенные акты: `lmx_arena_open` / `lmx_arena_open_simple`, `lmx_arena_take` / `take_n`, `lmx_arena_span`, `lmx_arena_attach` (присоединение другой арены без переезда адресов), `lmx_arena_mark` / `lmx_arena_revert` (всё или ничего для merge/copy), `lmx_arena_release`. Простой режим (`simple`): тот же индекс и стабильность адресов, без прохода GC и без многочанкового роста. Блоки — `LmxArenaBlock` в `lmx_arena_blocks.h.lm1`. Ссылки на слот Structure — `lmx_arena_refs`. L1: [L1](L1_spec_ru.md#arena).

<a id="message"></a>
## 7. Запись Message

Закрытая запись `struct: LmxMsg` в `lmx_message.h.lm1`. Ровно пять полей, порядок как в исходнике:

| поле | смысл |
| --- | --- |
| `running` | разрешение продолжать; 0 внутри хода — запрос остановки, не завершение |
| `success` | только фактическое завершение назначенной работы |
| `handoff_ready` | метка безопасной передачи хранилища без копии |
| `graph` | C-проекция языкового корня |
| `index` | индекс у родителя; у корня — 1 |

Тип флагов — `uint_fast8_t` (`type: LmxFlag`). Почта, очередь, планировщик, сроки и семейные связи **не** поля этой записи. Конверт письма — эта запись, не отдельная сущность вокруг неё. L1: [L1](L1_spec_ru.md#message).

<a id="thread"></a>
## 8. L3 Thread

Не каждый Message — L3 Thread. У письма нет хода. Объект `struct: LmxThread` в `lmx_thread.h.lm1` **указывает на** Message (обратное поле запрещено закрытостью записи). Имеет почту, планировщик, состояние хода, список зарезервированных детей, цепочку живых детей в **арене родителя** (`struct: LmxLink`: `alive` — единственная санкционированная межполосная ячейка рукопожатия). Два отдельных API: `LmxThreadApi` и `LmxThreadMailApi`, не смешанная куча. Ход целиком: `lmx_thread_turn`. Тело исполняется в одном из двух взаимоисключающих режимов L3 Thread: нативно либо интерпретатором графа. Отдельная операция явно запрашивает режим следующего такта, а граница `endturn` фиксирует запрос только после успешного такта. При неуспешном такте запрос отменяется: текущий режим сохраняется, запрошенный сбрасывается к текущему, а последующая смена требует нового явного запроса. Диспетчер не выводит режим из наличия `entry`, METHOD или тела и не переключается после ошибки пути. Один Message не запускает оба пути и во время такта принадлежит одному потоку ОС, хотя между тактами может быть передан другому worker. Интерпретируемый вход не копирует метод или граф; служебный кадр допускает переиспользуемое хранилище при сопоставимой с нативным входом стоимости. L1: [L1](L1_spec_ru.md#thread).

<a id="mailbox"></a>
## 9. Почта

Единственная синхронизированная точка ядра — **admission** почтового ящика (`lmx_post.h.lm1`). Мьютексов и семафоров модуль не вводит.

Три полосы: `inbox` (допущенное и ещё не взятое), `outbox` (опубликованное успешным концом хода), `staged` (подготовка текущего хода; чужие не видят). Inbox — **кольцо** фиксированной ёмкости `LMX_POST_INBOX_SLOTS` (256): слоты выделяются владельцем в своей арене при открытии; полный ящик отвечает `LMX_POST_FULL`, не растёт. Счётчики `inbox_head` / `inbox_tail` — атомарные release/acquire. Исходящие и staged — списки `LmxPostLink` (адрес цели + next), узлы из пула ящика. `LmxPostLink` не конверт. FIFO задаётся порядком admission. L1: [L1](L1_spec_ru.md#mailbox).

<a id="own"></a>
## 10. Own-локали и dirty

`struct: LmxOwnLocal` в `lmx_own.h.lm1`: `from` — адрес слота `&children[i]`, `value`, `dirty`. Загрузка на входе — только используемых unqualified-полей. `dirty` ставит только исполненное присваивание (`lmx_own_write`), не сравнение с графом и не возможность записи. Чекпоинт публикует только dirty и сбрасывает свой флаг (`lmx_own_checkpoint`). Явная запись `node\field` в кэш не идёт. L1: [L1](L1_spec_ru.md#own).

<a id="call"></a>
## 11. Вызов

`lmx_call.h.lm1`: вызываемость — `child[0]` попадает в домен METHOD. На этом этапе **нет** проверки сигнатуры (как в Си; полная типизация отдельно). Нульаргументная форма `lmx_call0` передаёт зарезервированный узел — само вхождение. `sig` не декодируется. L1: [L1](L1_spec_ru.md#call).

<a id="child"></a>
## 12. Резервация ребёнка

`lmx_child.h.lm1`: ребёнок строится в **своей** арене; публикация — один store в слот родителя **в конце хода родителя**. До публикации никто кроме родителя не исполняет входящие. Неуспех родителя снимает резервации, не откатывая уже сделанные записи графа. `struct: LmxReservation` живёт в арене родителя. `lmx_child_handoff` присоединяет арену ребёнка к родителю только при `handoff_ready`. L1: [L1](L1_spec_ru.md#child).

<a id="copy-merge"></a>
## 13. Копирование графа и merge

Модули `lmx_graph_copy_owned` и `lmx_merge_owned`. Обход тот же, что при создании Message: переписываются `node`-связи через карту источник→копия; указатели на METHOD и вечные терминалы сохраняются. Неуспех откатывается меткой арены ([§6](#arena)), не частичным графом. L1: [L1](L1_spec_ru.md#copy-merge).

<a id="implements"></a>
## 14. `implements`

L2 обеспечивает [механизм допуска L3](LMX_semantics.ru.md#admission): аналитическую проверку используемых именованных путей дерева и выполнение юнит-тестов принимающего выражения интерпретатором графа. Физическая классификация адресов остаётся отдельной операцией представления значений.

<a id="gc"></a>
## 15. Сбор

`lmx_gc.h.lm1` / `lmx_gc.lm1`. Поколение на арене; чанк помечается сравнением поколения. Корни: запись Message, объект, почта и её узлы/кольцо, расписание, живой граф, цепочка детей. Простой режим арены сбор отказывает. L1: [L1](L1_spec_ru.md#gc).

<a id="special"></a>
## 16. Специальные операции L2

К низкоуровневым операциям относятся классификация адреса, взятие ячейки арены, attach/revert арены, помещение в почтовую очередь, ход `lmx_thread_turn`, `lmx_call0`, резервация/публикация ребёнка, копирование/merge и сбор. Семантический допуск определяется [§14](#implements).

<a id="lowlevel-scope"></a>
## 17. Машинные операции: граница уровня

Следующие разделы определяют машинные контракты L2 отдельно от чистого L3. L1 — другой профиль с прямой C-семантикой; сопоставление находится в [L1](L1_spec_ru.md#lowlevel-scope).

Обычная Structure остаётся графом `Lmx`, Array — ссылкой на дескриптор с хранилищем, примитив — значением своего домена. Машинный адрес, сырое C-хранилище и внешний ABI не подменяют эти категории. L3 не получает машинные операции только потому, что реализация его ссылки использует указатель.

| Семейство | Назначение | Контракт L2 | Понижение L1 |
| --- | --- | --- | --- |
| `@ⁿ:`, `@`, префикс `\` | Адресная ячейка, адрес и загрузка | [Адреса](#lowlevel-address) | [Понижение](L1_spec_ru.md#lowlevel-address) |
| `c.array`, сырой индекс | Машинное прямоугольное хранилище | [Массивы](#lowlevel-array) | [Эмиттер](L1_spec_ru.md#lowlevel-array) |
| `cast`, `c.sizeof`, `c.name` | Приведение C, размер, внешний вызов | [ABI](#lowlevel-abi) | [C99](L1_spec_ru.md#lowlevel-abi) |
| Арифметика и обновление | Операции машинного профиля | [Выражения](#lowlevel-expression) | [Выражения C](L1_spec_ru.md#lowlevel-expression) |
| `synchronized` | Область синхронизации | [Синхронизация](#lowlevel-sync) | [Профиль L1](L1_spec_ru.md#lowlevel-sync) |

<a id="lowlevel-address"></a>
## 18. Типизированные адреса, загрузка и запись

### 18.1. Объявление и глубина

`@: T p`, `@@: T pp`, `@@@: T ppp` объявляют машинные адресные ячейки глубины 1, 2 и 3. Семейство голов из `@` зарезервировано для этих операций; глубина относится к адресным ячейкам, не к обычной структурной ссылке. Префиксное выражение `@x` берёт один адрес. Для следующего уровня адресуют уже объявленную ячейку:

```text
int: x 5
@: int p
@@: int pp
@@@: int ppp
p: @x
pp: @p
ppp: @pp
```

`@:` не конструктор обычного Array. Низкоуровневая строка `@: char "hello"` — адресный примитив, указывающий на C-строку; она не получает автоматически дескриптор длины. Обычная Structure `User` и непрозрачный примитив `FILE` не становятся одним видом значения из-за указателей в их C-представлении. Адресный примитив не обязан быть исходным целым числом: тип адресуемых данных определяется машинным профилем.

### 18.2. Что именно адресует @x

Общий смысл операции — получить адрес выбранных данных, не временной копии. Для поля L2 эти данные размещены в типизированном массиве арены; различие размещения не создаёт второго смысла address-of. Отдельно нужно определить саму адресуемую цель: данные поля, параметр или ячейку, содержащую указатель.

| Категория x | Результат | Эффект записи через результат |
| --- | --- | --- |
| Собственное поле графа | Типизированный адрес его данных после классификации | Меняется граф; рабочая копия не присваивается и не помечается dirty |
| Явный формальный аргумент | Адрес параметра текущей активации | Меняется параметр, без обратной записи |
| Динамический вход | Адрес сквозного параметра текущей активации | Меняется локальный параметр, не исходная привязка вызывающего |
| Машинная адресная ячейка | Адрес самой ячейки | Меняется хранящийся в ней адрес |

Для собственного поля это не адрес слота `void *`, не `Lmx.data` и не адрес own-кэша. Для значения Array адресуется его дескриптор, а не backing; форма `@array[i]` ниже отдельно адресует выбранный элемент backing. Для вызываемой Structure адресуется Structure; переход к METHOD и его исполняемому входу — отдельные действия. Взятие адреса само по себе не увеличивает время жизни и не является записью.

Адрес локальной машинной ячейки нужен, например, для выходного параметра: [printTree.lm2](../l2src/printTree.lm2) передаёт `@document` в `lm_p0_parse_file`, чтобы функция записала указатель результата. Здесь адресуется переменная-указатель, не документ. В [library_struct_local_forms.lm2](../l2src/tests/library_struct_local_forms.lm2) адресуется локальная запись импортированного C ABI. Адрес временной копии не является корректной реализацией адреса выбранных данных.

`@array[i]` — корректное выражение L2. Оно получает адрес настоящего элемента в хранилище графа; отдельный адаптер и предварительная проверка индекса не требуются. Дальнейшие загрузки, записи и адресная арифметика работают по машинному контракту C. Получение адреса нельзя реализовать как чтение элемента во временную переменную с последующим взятием адреса этой копии.

При исходных графовом и рабочем `x = 5` запись `p: @x`, затем `\p: 9` оставляет рабочее голое `x` равным 5, а явное чтение графа видит 9. Если рабочий `x` не присваивался, выход не перепубликует старое 5. Позднейшее присваивание рабочему `x` создаёт dirty-запись, публикуемую по обычному правилу. Адрес аргумента существует только в пределах жизни активации; сохранение указателя в графе не продлевает этот срок.

### 18.3. Загрузка, пути и ограничения

Для аргумента есть отдельное правило одноимённой own-привязки: исполнившееся объявление или присваивание-объявление связывает ту же локальную переменную с полем тела для последующей dirty-публикации. Её адрес и время жизни остаются адресом и временем жизни параметра; прежнее графовое значение не загружается поверх входа, записи до строки привязки не публикуются. Это не разрешение адресовать временную копию обычного графового поля или элемента массива. Семантика момента привязки и тела-владельца — в [L3](LMX_semantics.ru.md#dynamic).

`\p` загружает по типизированному адресу; `\p: value` записывает туда, если запись допустима. `p\field` следует полю явно импортированного машинного ABI либо обычному структурному пути — в зависимости от категории p. Эти случаи нельзя объединять универсальным `->`: для Structure используется граф, для сырого ABI — известная раскладка. В L2 индексирование не проверяет границы — ни для сырого адреса, ни для массива с данными в графе. Проверки индекса и дескриптора при доступе к Array принадлежат L3. Само чтение дескриптора для получения backing не является его валидацией. Цепочки полей и индексов связываются сильнее префиксных `@` и `\`.

`*` не является исходным разыменованием, `&` — взятием адреса, `^` — следованием полю, `.` и `->` — обычным доступом к полю L2. `*`, `&`, `^` могут иметь отдельные арифметические/битовые роли. Доступ к C-агрегату по значению выражается явной C-формой, например `c.value.field`, не переопределением графового пути.

Запись через адрес не снимает `const`/`immutable`, не делает висячий адрес допустимым и не создаёт автоматического владения. Допуск принимающего выражения определяется [единым механизмом](#implements), физическая классификация — [индексом арены](#type-by-range).

<a id="lowlevel-array"></a>
## 19. Сырое хранилище c.array

### 19.1. Вход и результат

`c.array` принимает ровно одно объявление с головой из одной или нескольких групп скобок, возможно внутри единственного `const`. Посторонние дочерние поля и дополнительные объявления не входят в минимальный контракт. Примеры: `c.array: [3]: int: values 2 4 6`, `c.array: []: char buffer 256`.

Непустая группа `[rows]` содержит свой размер. Пустая `[]` забирает один размер после типа и имени, в порядке измерений; оставшиеся поля — инициализаторы. Пропущенный размер — ошибка, не запрос вывести его из инициализатора. Составной размер помещается внутрь непустой группы. Контракт допускает смешанные группы.

Результат — обозначение C-хранилища, не значение Array и не графовый узел. Не создаются арена, владелец, `len`, shape/stride-метаданные или проверки границ. Сопоставление с обычным массивом требует явной операции с адресом backing, формой и временем жизни.

### 19.2. Индекс, размерность и время жизни

Каждый суффикс `[i]` выбирает одно измерение: для двумерного C-хранилища используется `a[i][j]`. Частичная индексация обозначает оставшийся подмассив, полная — lvalue элемента. Это не view. Преобразование одномерного остатка в указатель следует C-профилю; многомерный остаток не сплющивается в случайный `T **`.

Адрес целого массива или подмассива — указатель на массив, не обычное увеличение глубины указателя элемента. Определённый здесь минимальный контракт не вводит такой декларатор и требует отклонить неподдержанную форму, не выдать неправильный тип. Адрес полностью выбранного элемента допустим. `const` квалифицирует базовый элемент; для массива указателей это не автоматически const-ячейки указателей.

Блочное хранилище имеет автоматическое время жизни C; переменный размер подчиняется C99 VLA и не допускает инициализатор. Верхнеуровневое хранилище в hosted-профиле имеет внутреннее связывание, постоянные размеры и статическую инициализацию. Без инициализатора локальные элементы неопределённы, статические — нулевые. При инициализации пропущенные элементы обнуляются, лишние или несовместимые диагностируются. Консервативный многомерный профиль требует явных вложенных групп, не плоского опускания скобок; верхнеуровневый адресный инициализатор требует уже выданного объявления цели.

Сохранение адреса локального массива не продлевает его жизнь. Выход сырого адреса за время жизни хранилища требует явного адаптера/контракта; нельзя молча превращать его в живой Array. Сырые индексы не проверяются автоматически. Статически обнаружимая опасность и недопустимые статические инициализаторы относятся к диагностике машинного профиля.

<a id="lowlevel-abi"></a>
## 20. Внешние типы, преобразования и вызовы

`cast: (T) value` — машинное приведение, не [числовой конвертер L3](LMX_semantics.ru.md#descriptions) и не доказательство безопасности диапазона или времени жизни. `c.sizeof` запрашивает размер машинного типа/объекта, не число полей Structure или элементов Array. Непрозрачный тип можно хранить и передавать без разрешения следовать его полям; сырой доступ требует известного ABI.

`c.name` выбирает внешний C-символ. Обычная L2-функция не требует `c.`. Параметры, результат, владение и освобождение ресурса задаются адаптером. Разрешение C-вызова не создаёт вокруг результата граф и не делает указатель переносимым сообщением. `external` в описательном контракте оборачивает одну `fn`/`sub` и запрашивает внешний вход; адаптер сохраняет контракт исходного метода.

`include` передаёт явно указанные заголовки, сохраняя заданные `<…>`/кавычки; путь без ограничителей оформляется как локальный. `os` выбирает написанную платформенную ветвь, не меняя порядка одноимённых графовых полей. `predef`/импорт связывают выбранные зависимости, не разрешая сканировать каталоги или заранее строить все структуры.

<a id="lowlevel-expression"></a>
## 21. Машинные выражения и обновление

Минимальный профиль включает группировку, префиксные `@`, `\`, `++`, `--`, `+`, `-`, `!`, `~`, постфиксные `++`/`--`, арифметику `+ - * / %`, сравнения `= != < <= > >=`, логические `&& ||` и битовые `& | ^`. Здесь `=` — сравнение, запись — `target: value`. Переполнение, сдвиги, деление, округление и преобразования зависят от выбранного машинного профиля; им нельзя приписывать безусловно проверяемую арифметику L3.

`target[index]` потребляет выражение индекса. Это не квалификатор одноимённого поля `target\[index]field` и не голова конструктора `[]:`. Категория target определяет способ получения данных, но не добавляет проверки границ в L2. Проверяемая операция Array относится к L3; L2 предоставляет машинный доступ к выбранной ячейке. Присваивание не добавляет одноимённое поле и не создаёт namespace.

Управляющие формы — `if`/`else`, `while`, `until`, `for(init, condition, step)`, `return`, `break`, `continue` и [synchronized](#lowlevel-sync). Общие правила ветвлений и циклов находятся в [L3](LMX_semantics.ru.md#branches); `match`, `each`, `retry` и `yield` требуют отдельных L2-операций либо профиля. Понижение в [L1](L1_spec_ru.md#lowlevel-expression) сохраняет различие графового обновления и сырой записи.

<a id="lowlevel-sync"></a>
## 22. synchronized и границы синхронизации

`synchronized` сохраняется как общая низкоуровневая возможность L2. Ограничение ядра на синхронизацию внутри почтового механизма не удаляет операцию из языка. В чистом L3 сырых блокировок нет. Контракт принимает выражение объекта/адреса и структурное тело, а не открытую пару lock/unlock.

```text
synchronized: @object
    updateObject: object
```

Вложенное тело — отдельное структурное поле аргументов. `synchronized: @lock (break)` задаёт его явно; `synchronized: @lock break` оставляет `break` в inline-последовательности и не позволяет парсеру молча назначить его телом.

Мониторный профиль задаёт вход/выход и, если требуется, повторный вход того же потока. Область освобождается при нормальном завершении и покидающих её `return`, `break`, `continue`; общий протокол очистки определяет прочие выходы. Результат удерживается до освобождения. Внутренние вызовы сохраняют обычный порядок вычисления аргументов и публикации dirty-полей.
