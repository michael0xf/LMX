# Голый атом ресивера в позиции вычисления

Дата: 2026-10-06. Статус: **ожидает ответа автора**.
Источник вопроса: Opus → lmx_uds → Codex,
`K03-BARE-RECEIVER-ATOM-20261006-01`, родитель
`OPUS-CODEX-20261005-01`. Это вопрос о неустановленном общем контракте,
не предложение сохранить сборщик операндов и не тикет реализации.

## Единственный вопрос

В позиции вычисления **любой** голый ресивер обрабатывается как его
применение с пустыми аргументами, как `merge()`? Или голая форма допустима
только при отдельно установленном нульарном контракте ресивера?

Минимальный пример:

```text
sub: probe ()
    merge
probe()
```

Сравниваем только голый `merge` с `merge()` на том же месте:

- Применение с пустыми аргументами: транслятор обрабатывает ресивер по его
  обычному контракту; для merge получается ошибка «нужен хотя бы один
  операнд» у самого атома.
- Голая форма отдельно не допущена: у слова известна зарезервированная
  роль ресивера, но это не установленный нульарный оператор; для его
  применения требуется явная форма Frame. Получается ошибка формы у
  самого атома, не поиск неизвестного имени или скрытого входа. Уже
  определённые голые нульарные формы, например `return`, не отменяются.

Решение нужно для **всех** языковых ресиверов в соответствующей позиции,
без исключения для merge. Ни один вариант не потребляет следующие поля
как аргументы. В аргументах принимающего ресивера действует его контракт:
`catch: merge ()` уже является обычным применением catch, не отдельным
применением merge; `fn: test ()` описывает метод, не вызывает test.

## Почему Codex не выбрал правило самостоятельно

[Семантика §9](../../../docs/LMX_semantics.ru.md#construction)
разделяет ресивер как инструкцию транслятору и runtime-вызов callable:
у них общий синтаксис, но разные роли
(`docs/LMX_semantics.ru.md:569`).
[Семантика §11](../../../docs/LMX_semantics.ru.md#execution)
явно задаёт нульарное вычисление голого имени named callable
(`docs/LMX_semantics.ru.md:693`).
[Грамматика §13](../../../docs/LMX_grammar.ru.md#no-inference)
говорит о голом callable-атоме, не устанавливая такой контракт для любого
ресивера (`docs/LMX_grammar.ru.md:1049`).
Проекция EBNF упоминает уже допущенный нульарный оператор/ресивер, но не
универсальную пустую форму для любого ресивера
(`docs/LMX_grammar.en.md:2402`, production `nullary_line_body`).

Из общего синтаксиса нельзя без ответа автора вывести новую семантику
для голого ресивера. Ни рассуждение Opus, ни сегодняшнее поведение кода
не объявлены нормативным решением.

## Измерение, не норма

По отчёту Opus на `a71009cc`, при удалении сборщиков запись
`x: merge Model` больше не превращается в merge с операндом Model,
но атом merge уходит в «unresolved name»; отдельный merge внутри метода
уходит в скрытый вход и даёт «unbound dynamic input merge» у последующего
места вызова. Эти диагностики не принимаются за языковую норму.

Независимые gate/checkpoint свидетеля точного типа null-ячейки, перепись
фактических P0-узлов, удаление сборщиков и миграционный манифест
продолжаются. Только правило голого ресивера и зависящие от него
семантические ожидания остаются открытыми до ответа.
