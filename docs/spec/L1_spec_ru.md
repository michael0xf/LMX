# Спецификация L1

L1 — генерируемое промежуточное представление для понижения ядра в C99. Языковые правила графа задают [L3](LMX_semantics.ru.md) и [L2](L2_spec_ru.md); здесь остаётся только C-проекция. Состояние текущего транслятора и переходного рукописного L1 — в [заметках](implementation-notes.ru.md).

<a id="scope"></a>
## 1. Предмет

`l1trans` понижает `.lm1` в одну единицу C99. L1 сам по себе не определяет арену, `satisfies` или графовую видимость как операции языка. Такие механизмы реализуются явно библиотекой ядра. Цель самосборки — L3 со вставками L2; L1 остаётся промежуточным шагом.

<a id="translator"></a>
## 2. Транслятор

L1 разрешает свои C-подобные объявления и выражения. Префиксное `@x` — адрес C-ячейки `x`, префиксное `\p` — загрузка указателя, `p\field` — доступ к полю через указатель. Декларативное `@ⁿ:` задаёт соответствующую глубину C-указателя. Исторический порядок аргументов указательного объявления в рукописном L1 не является постоянным исключением: целевой промежуточный L1 должен следовать общему порядку L2/L3 «имя, требование, значение». Внешние C-символы доступны через явное `c.имя`.

<a id="lmx"></a>
## 3. Lmx на L1

Целевая C-проекция [L2 §2](L2_spec_ru.md#lmx) — плоский заголовок `Lmx` с полями `parent`, `length`, `storage` именно в этом порядке, без вложенного `VoidArray`. Ссылка на Structure или Array указывает на начало заголовка. Обычная Structure и `Array<@>` хранят в `storage` элементы `void *` и взаимозаменяемы в общих операциях; числовой `Array<T>` хранит непосредственно элементы T. Типизированное storage и общий механизм изменения размера применяются ко всем массивам; capacity хранится в таблице арены. Эта раскладка утверждена, перенос текущего генератора ещё открыт: [состояние реализации](implementation-notes.ru.md#l2-status), [M13](../../next_core_tasks_v3.md#flat-lmx-descriptor). Записи графа не получают имени, тега модели или скрытых полей выполнения. Динамический List детей Thread хранится отдельно.

Понижение обычного ресивера [`sys\descriptor`](L2_spec_ru.md#get-descriptor) возвращает Structure с адресами трёх настоящих полей заголовка: `Lmx **`, `size_t *`, `void **`. Запись через разыменование адресует и изменяет исходное поле непосредственно; запись в поле самой возвращённой Structure меняет её указатель. Прокси, отложенной обратной записи или нового opcode нет. Произвольные конечные глубина указателя и мерность Array проходят общий типизированный путь; L1 сохраняет свой порядок объявлений «тип — имя».

Понижение parent/length/sys\storage читает поля заголовка; sys\native читает native-дескриптор из таблиц call,
sys\capacity — вместимость из таблицы арены. Каждая форма без аргументов выбирает текущие данные; код требует явного
аргумента. Ни один запрос не строит вспомогательный descriptor. Data (parent выбранной Structure), code и node сохраняют
свои роли. sys\resize/sys\reserve используют общий механизм изменяемых массивов. Native и capacity в Lmx нет.

Для `sys\descriptor` также есть явный аргумент S и вариант без аргумента от текущей data
(parent исполняемой Structure); прежняя запись `sys\descriptor() = sys\descriptor(data)` через особое имя `data`
снята ([что снято](LMX_semantics.ru.md#removed-builtins)). Выбор действует и во вложенных телах управления;
понижение обоих вариантов возвращает адреса полей выбранной Structure по одному контракту.

<a id="interpretable-tree"></a>
### 3.1. Проекция дерева

Понижение сохраняет полный граф для обходчика и `sys\toLmx`; последующая мутация меняет именно этот граф. Оно не выделяет `leaf`-обёртку для уже типизированной ячейки примитива и не хранит имена в графовых записях. Таблица имён и комментарии нужны выводу текста текущего графа, не исполнению. Подробный контракт — [L2 §2.1](L2_spec_ru.md#interpretable-tree).

Понижение `sys\indexof(field parent)` ищет единственное вхождение ссылки и возвращает физический
индекс; отсутствие или неоднозначность — ошибка. `sys\indexof(field index parent)` выбирает вхождение
с номером index, с нуля, и возвращает его физическую позицию; отсутствие вхождения — ошибка.
Использовать общую адресацию Structure/Array<@>, без дополнительной таблицы индексов.
[Контракт L2](L2_spec_ru.md#system-indexof).

<a id="type-by-range"></a>
## 4. Тип по диапазону

Норма (решение автора 2026-11-16, [L2 §3](L2_spec_ru.md#value-record)): физический тип значения — код в его записи, он стоит сразу перед значением; у арены один поток записей, и по адресу тип не определяется. Модели пользователя не создают по C-типу на каждую Structure. Обычная и `immutable` Structure различаются кодом записи, сохраняя совместимую физическую запись. Нынешний код ещё классифицирует адреса через `LmxRange` и индекс арены и держит раздельные пулы; это прежняя схема, её снимает [план M15](../../next_core_tasks_v3.md#typed-value-records).

<a id="pool"></a>
## 5. Пул

Записи выдаются подряд из кусков арены. Рост добавляет кусок, а не перемещает живые записи через `realloc`. Куски принадлежат арене. Нынешние `LmxPool` и `LmxChunk`, выделяющие ячейки одного типа, — прежняя схема. См. [L2 §4](L2_spec_ru.md#pool).

При поэтапной самосборке транслятор выдаёт C99-доступ к `void *storage` графового Array через указатель фактического
типа элемента `T *`, выбранного по коду записи Array. Хранилище выделяется для элементов именно этого типа с нужным
выравниванием: приведение не переопределяет тип уже существующего backing. Для графового элемента ссылок действует
отдельное правило `void **`, а не несовместимый доступ как `T **`. Так одна общая Array-Structure понижает разные
типизированные массивы без нового языкового объекта для каждого `T`.

<a id="method-array"></a>
## 6. Нативный вход и Array

Native-дескрипторы — обычные структуры в таблицах call в арене Thread, с вариантами сигнатур, бинарным модулем/именем
входа и путями L1/C. Компиляция не добавляет синтетического поля native в исполняемую Structure или `catch`
([L2 §2](L2_spec_ru.md#lmx)). Array использует общий Lmx и изменяемое типизированное storage;
отдельный механизм роста List и встроенная capacity снимаются. [L2](L2_spec_ru.md#method-array).

<a id="arena"></a>
## 7. Арена

`LmxArena` владеет блоками, пулами и индексом диапазонов. `attach` передаёт владение без перемещения адресов; `mark/revert` обслуживают атомарное построение. Простой режим не выполняет GC. См. [L2 §6](L2_spec_ru.md#arena).

<a id="message"></a>
## 8. Message

`LmxMsg` понижается ровно с четырьмя полями: `running`, `success`, `handoff_ready`, `graph`. Его идентичность — адрес записи, поля числового индекса нет. Почта и семейные связи не добавляются в префикс Message. См. [L2 §7](L2_spec_ru.md#message).

<a id="thread"></a>
## 9. L3 Thread

`LmxThread` содержит `LmxMsg` первым членом по значению, поэтому адрес Thread равен адресу префикса Message. Доступ к хвосту требует точной классификации Thread. `Thread.children` удерживает один List прямых детей вне исходного графа. См. [L2 §8](L2_spec_ru.md#thread).

<a id="root-close"></a>
### 9.1. R0

R0 и верхний host-каркас используют общий механизм Thread. У R0 данных нет: это процедурный вход без аргументов, без искусственной самопривязки данных к коду (`data = code`), пустой служебной Structure и поля `data`. Параметры запуска рантайма принадлежат каркасу, а не скрытым полям графа R0, и не являются пользовательскими фактическими аргументами. В какой роли читаются записи корня единицы, когда у R0 нет данных, а `sub` снят и `Name :: DATA` описывает сигнатуру без исполняемого тела, определяет вывод редакции 2026-11-21: запись, которую исполняет R0, читается как код, а Structure объявляет описание данных, тело которого называет запуск ([вопрос и вывод](../../LMX_blog/q/unit-root-roles-answered-20261121.md)). Каскад закрытия идёт по единственному List детей; timeout всего поддерева контролирует host-watchdog. См. [L2 §8.1](L2_spec_ru.md#root-close).

<a id="mailbox"></a>
## 10. Почта

`LmxPost` хранит `staged`, `outbox` и FIFO `inbox`. Входящий элемент — пара `[target, source_arena]`; владелец
получателя присоединяет donor до выдачи target. Кольцо inbox использует общий изменяемый массив с внешней capacity,
перемещаемым storage и monitor ящика. См. [L2 §9](L2_spec_ru.md#mailbox).

<a id="own"></a>
## 11. Локальный кадр вызова

Норма 2026-11-19 (связывание и вызываемые) принята автором (см. [решения R01–R19](LMX_semantics.ru.md#binding-decisions)) и действует в редакции 2026-11-21; её применение записано в
[плане](../../next_core_tasks_v3.md#docs-20261121). Этот раздел излагает новую норму теми же словами, что
[L2 §11](L2_spec_ru.md#call).

<a id="call-receivers"></a>
<a id="structural-call"></a>
### Структурный вызов и ресивер `call`

Исполняется выбранная Structure `C`: она читается в роли кода, а роль данных у неё выполняет её фактический родитель `D = parent(C)`. Формы после однозначного выбора:

| Форма | Исполняемая Structure | Фактические аргументы | Данные |
|---|---|---|---|
| `call(C)` | `C` | не поданы | `parent(C)` |
| `call(A C)` | `C` | Structure `A` | `parent(C)` |
| `C()` | `C` | пустой хвост | `parent(C)` |
| `C(args)` | `C` | написанные фактические аргументы по общему алгоритму | `parent(C)` |

У `call` параметры называются `args` и `code`. `args` — Structure фактически передаваемых значений, ровно та,
которая является структурой аргументов обычного вызова. Это не объявления формалов, не сигнатура
и не отдельная часть callable. Входные места, требования и умолчания описывают данные `D`.
`call` исполняет саму выбранную `C`; дочернее поле `code` автоматически не ищется.
В одноаргументной форме обязателен `code`, в двухаргументной — `args` и `code`, поэтому `call(code := C)`
двухаргументной форме не подходит: это обычное различение объявлений ([выбор объявления](L2_spec_ru.md#declaration-selection)),
без исключения для встроенного `call`. Целая `C` может подойти одной форме `call`, а её поля — другой:
тогда `call(C)` — ошибка неоднозначности, а `call(code := C)` явно подаёт `C` как `code` и исключает
раскрытие этого фактического аргумента. `C(A)` может принять `A` целиком либо передать её поля;
это определяет выбор объявления.

Подставить другие данные самим вызовом нельзя. Для другой комбинации сначала создаётся нужная структурная
связь (объявление, копия, `merge` — по их правилам о `parent`), затем вызывается выбранное вхождение `C`.
`NewContainer: ExistingCode` хранит ссылку на `ExistingCode` и его `parent` не меняет ([`colon-declares`](LMX_semantics.ru.md#colon-declares)).
Прежние `call(D C)` и `C(D)` данные больше не подставляют: первый аргумент двухаргументной формы теперь `args`.
Разные вхождения кода могут использовать одну нативную реализацию, сохраняя собственные данные: ни адрес общей
C-функции, ни путь, которым найдена ссылка, не подменяют `parent` выбранной `C`. Прежнее равенство
`call(C)` = `call(C C)` («Structure — сама себе данные») снято.

`node` остаётся зарезервированной лексической операцией для выбранного исходного вхождения. Её лексический источник и
необходимый нативный контекст следуют сохранённым правилам связывания. Это не синоним для `parent(C)`, текущего
потребителя DATA или ресивера потока полей. Явный путь `D\x` использует названную Structure D; `node\x` уместен лишь
тогда, когда лексические правила `node` действительно выбирают этот источник. Перемещение существующей ссылки или импорт
метода не переназначает родителя.

Структурная форма и обычные вызовы Structure используют один путь интерпретатора: найти имя вызываемого и видимые
объявления → выбрать по явному материалу → подготовить необходимые принимающие места выбранного namespace → вычислить и
принять фактические аргументы один раз в записанном порядке через общий допуск → применить разрешённое неявное
связывание → исполнить и передать результат. Необходимые принимающие места существуют до того, как фактическое выражение
их запишет. Подготовка namespace и приём фактических аргументов не меняют исходные данные и не запускают общий проход
инициализаторов по входу; явный вызов потока-источника выполняется только тогда, когда того требует обычный контракт
ресивера. Вызовы из test и преобразователей используют тот же механизм. Известные вызовы native-to-native по-прежнему
могут идти напрямую через C без упаковки в граф.
[Полный контракт и именованные аргументы](LMX_semantics.ru.md#call-receivers).

Результат (`return` в данных), именованная сигнатура, выбор объявления, связывание (автозаполнение, прозрачное место
вызывающего, прежнее связывание) и `catch` определены в L2 §11: [`return` в данных](L2_spec_ru.md#return-in-data),
[именованная сигнатура](L2_spec_ru.md#fn-signature), [выбор объявления](L2_spec_ru.md#declaration-selection),
[связывание](L2_spec_ru.md#binding-places), [`catch`](L2_spec_ru.md#catch-common-model).
L1 повторяет только то, что нужно C-проекции.

<a id="private-binding"></a>
### Ресивер private: двусторонний `private`

`private:` помечает конкретное объявление и соответствующее место и исключает их из всего неявного динамического
связывания в обоих направлениях. (Источник) Место `private` вызывающего неявно не предлагается ни как значение, ни как
место. (Ресивер) Действительно видимое `private`-объявление в лексическом контексте вызываемого не переопределяется
значением или местом из динамического контекста. Правило применяется к автозаполнению, прозрачному месту вызывающего и
динамической части прежнего связывания одинаково для каждой формы `call`, `C(args)`, обычных вызовов, интерпретатора и
нативного исполнения. Поэтому прежде чем принять внешнее динамическое связывание, определяется, какое лексическое
объявление действительно видимо и защищено ли оно `private`; проверки одного только источника недостаточно. `private` —
это фильтр конкретного места, а не барьер имён и не защита доступа: источник `private` пропускается, и разрешённый поиск
продолжается; `private x` предка не закрывает новое внутреннее `x` без метки. Не запрещены: явная передача (в том числе
собственного значения `private`), явное заполнение принимающего места `private` фактическим аргументом, вложенная
лексическая видимость, явные пути и `node`, а также затенение внешнего `private` новым внутренним объявлением. `private`
не заменяет ограничения записи (`const`, `immutable`). Явно переданное значение не переносит историю `private` в свои
копии; запись графа `S\private\field` не сглаживается в `S\field`. Используется общий binder без отдельного реестра и
без проверок при прямых чтениях. Walker читает исходный ресивер `private` в чистом графе; компилятор выпускает
соответствующую логику связывания и скрытых аргументов из того же источника. Второй граф меток private или флагов
доступа в бинарнике запрещён, в том числе представленный как подготовленное представление времени исполнения.
[Полный контракт](LMX_semantics.ru.md#private-binding).

<a id="call-frame-20261115"></a>
### Кадр вызова

Каждый независимый вызов имеет собственный namespace. Входы описываются данными выбранной Structure (`parent(C)`);
`args` в `call` содержит явно поданный материал. Подготовка собирает относящиеся корни, не выполняя инициализаторов, не
обходя недостижимые ветви и не записывая связывания в исходные данные. Явное значение заменяет свой источник по
умолчанию в namespace, поэтому это значение по умолчанию не выполняется. Готовые конечные объявления используют свои
сохранённые значения; вычисляемый инициализатор остаётся описанием, пока его контракт этого не потребует. Чтение
собственного вычисляемого входа получает своё значение общим механизмом. Явные пути в исходном графе остаются иными:
`D\field` читает записанную запись и не выполняет её RHS. При `@: fptr getFuncPtr()` обращение к локальному `fptr`
получает ссылку этого инициализатора; затем `fptr("hello world")` вызывает полученный callable, без трактовки голой
ссылки как неявного вызова.

Переменные и const видны с первоначального объявления вперёд в своей области и ниже.
Двусторонняя видимость сохраняется у имён Structure и callable, но не у переменной с указателем
на функцию. Новое имя ветви не выходит наружу.

<a id="shadowing-levels"></a>
Объявление на вложенном уровне затеняет внешнее одноимённое: внутреннее `Text x` затеняет внешний `int x`,
не записывая `Text` во внешнюю `int`-ячейку. На том же уровне затенять нечего, и используется уже существующее
место: повторное `int: x bump()` сохраняет вычисление, допуск и запись существующему x по контракту ресивера —
новая правая часть вычисляется и присваивается, отсутствие правой части значение не обнуляет, второй ячейки нет;
убирается только повторная C-декларация. После выхода из внутренней области снова видно внешнее со своим местом,
режимом записи и `private`. Употребление до более позднего собственного объявления разрешается обычным способом
через доступный внешний контекст: будущее объявление не блокирует всё тело. Физические повторы
полей сохраняются и выбираются `S\[n]x`. Явный путь не ограничивается порядком объявления
голого имени. Чтение объявления через путь ничего не исполняет; RHS исполняется при достижении строки code.

<a id="inline-declaration-control"></a>
Одно место остаётся на чтении исполнителя ([контрольный пример](LMX_semantics.ru.md#inline-declaration-control),
[Р106](../../LMX_blog/q/fable-self-answers-20261110.md)): новое `int: x` без правой части во вложенной встроенной области,
где нового вызова вызываемого нет, при внешнем `x = 5` остаётся `uninit:int`, потому что автозаполнение определено
между локальным контекстом вызывающего и местом вызываемого при вызове, а встроенная область остаётся в той же
активации; значение 5 потребовало бы нового правила, а правила связывания его не вводят. Это не решение автора.
[Контрольный пример](LMX_semantics.ru.md#inline-declaration-control).

Голое x и @x относятся к выбранному месту. Собственное место кадра не зависит от замен исходного поля сразу
после входа, даже до первого чтения: сохраняется выбранное значение либо вычисляемое описание; правило одно
для явной data, лексического связывания и прежнего динамического связывания, и это не глубокое копирование
объектов по ссылкам. Прозрачное место вызывающего — само место вызывающего ([L2 §11](L2_spec_ru.md#binding-caller-place)).
`x := 0` меняет выбранное место: собственное место кадра — не пишет ни в граф, ни вызывающему, прозрачное
место вызывающего — пишет ему сразу; `D\x := 0` меняет исходный граф данных.
Для вычисляемого входа `int: x next()` обращение @x получает значение и адрес локальной ячейки.
При `(@D\field)` и исходном `int: field getValue()` адресуется запись объявления, а не результат
getValue(): явный путь ничего не исполняет (решение автора 2026-11-17; прежнее правило снято).
Готовое место адресуется непосредственно.
Время жизни обычное. @f() было исследовательским примером, не задачей отдельной поддержки или запрета.

Копирование code ради одинакового момента применения правок отменено. Native и обходчик могут
применить правку в разное время до endturn; независимость namespace сохраняется. Связывание идёт
скрытыми аргументами ([исполнители](#binding-executors)), без копирования окружения. Изменение графа не обнуляет native и не запускает
проверку/компиляцию. Методы и обычные Structure компилируются общим механизмом без data=code: данные выбранного
вхождения — его `parent`; разные actuals и разные режимы скрытых входов дают разные C-сигнатуры, заголовок без code описывает вызов.

Локальные кадры не публикуются. Load-dirty, общий кеш прямого доступа и flush() отменяются; явные записи наблюдаются
через реальные алиасы в порядке исполнения. [Согласованная норма](LMX_semantics.ru.md#call-frame-20261115).

<a id="binding-executors"></a>
### Нативный код, обходчик и мост (bridge)

Прямой вызов native → native сохраняется там, где известны выбранная реализация, типы и связывание. Автозаполненное
значение понижается тем же параметром `T`, что и явный фактический аргумент; прозрачное место вызывающего — скрытым
адресом его ячейки; прежнее связывание (запасной путь) даёт собственное место. Общее C-тело может разделяться между
режимами через адаптеры, и адаптер должен сохранять владельца записи и поведение `@`. При одинаковых явных фактических
аргументах режим отдельного скрытого входа может различаться из-за контекста вызывающего и `private`: существующий
нативный вход должен соответствовать реальному контракту или получить корректное описание места. Один код может иметь
несколько сигнатур фактических аргументов, в том числе один явный контракт с разными режимами места (собственная копия,
место вызывающего). Адаптер использует существующие дескрипторы ABI и мест, чтобы сохранить это различие; новые
пользовательские типы указателей не вводятся. Служебные C-функции, мост и диспетчер `call` не подменяют контекст
вызывающего своими служебными локальными переменными: источники языка определяются программным местом вызова.

У обычной нативной локали нет заголовка арены `[type][value]` ([L2 §3](L2_spec_ru.md#value-record)): её тип нельзя прочитать
из четырёх байтов перед адресом. Тип, способ доступа, состояние инициализации и применимые ограничения места следуют
общему представлению места и контракту вызова. Четыре сочетания — native→native, native→обходчик,
обходчик→native, обходчик→обходчик — дают одно наблюдаемое поведение: `x` имеет один логический тип `T`, а допустимая
запись меняет то же логическое место. Для цели времени исполнения, неизвестной при трансляции, сохраняется
существующий механизм доступа к разрешённым локальным контекстам; сырой C-стек не исследуется как словарь имён LMX,
и статического транзитивного замыкания требований нет.

Не возвращаются load-dirty, flush, публикация локальных кадров и копирование обратно при выходах. Чтение через
псевдоним не превращается в снимок без доказательства, что наблюдаемое поведение при вложенных вызовах сохраняется.
Явная компиляция, существующий выбор native/обходчик и граница endturn сохраняются; отсутствие подходящего
native-входа не запускает скрытую компиляцию; постоянных кешей всех окружений и автоматической инвалидации графа
нет. `restrict` не применяется лишь из-за скрытой передачи указателя или `private`: такой C-контракт требует
отдельного доказательства отсутствия запрещённых пересечений.

Прозрачная связь не продлевает время жизни; адрес временной C-локали не становится переносимой структурной ссылкой,
правила Message и арен не меняются. При `yield` выбранная связь не перевязывается к одноимённой локали нового
вызывающего: возобновление использует состояние сохранённой активации и обычные ограничения времени жизни.
[Норма](LMX_semantics.ru.md#binding-executors).

<a id="call"></a>
## 12. Вызов и явная компиляция

Известный native вызывает известный вариант непосредственно в C с выбранной фактической сигнатурой
и нужными скрытыми аргументами. Граф, таблица call, универсальная упаковка actuals и trampoline
ради организации такого вызова не нужны. Динамический вызов выбирает вариант в таблицах call;
детали его внутреннего ABI не становятся обязательной упаковкой всех статических вызовов.

sys\compile(S) явно выполняет построение/проверку чистого графа → L1 → C → машинную компиляцию
и регистрацию входов; sys\translate возвращает только L1 и диагностики. Записи в граф не отслеживаются
ради native: нет автоматического сброса, обратной инвалидизации и пересборки. Для прямой цепочки A→B
обновление A требует компиляции единицы с A и нужным B, а не замены только записи B в таблице.
Поддерживаемый источник компилятора остаётся L2/L3; L1/C — генерируемые артефакты.

sys\endturn() понижается через общий механизм системного выхода с finally до границы такта.
Обычный catch его не перехватывает; вызов не возвращается, продолжение стека не сохраняется.
Running/success самим ресивером не меняются. После успешной явной компиляции и endturn следующий
вход использует подготовленное обновление; без компиляции endturn не обнаруживает и не исправляет
правки. Это не flush и не публикация локалов. [L2](L2_spec_ru.md#explicit-compilation).

<a id="child"></a>
## 13. Ребёнок

Ребёнок строится в своей арене. Публикация добавляет его ссылку в `Thread.children`, не дописывая поле в исходную Structure. См. [L2 §12](L2_spec_ru.md#child).

<a id="copy-merge"></a>
## 14. Копия и merge

`lmx_graph_copy_owned` и `lmx_merge_owned` используют общую карту исходник→копия для полей, внутренних ссылок и parent. Native-дескрипторы и обычные поля native копируются по общим правилам графовых данных; это не доказывает пригодность машинного входа для новой структуры и не регистрирует его автоматически. Привязки входов создаёт явная компиляция или восстановление сохранённых таблиц выбранного корня. [L2](L2_spec_ru.md#copy-merge).

sys\toLmx выбранного L3 Thread сохраняет все таблицы его арены, включая call/native, а не только
поля R0. sys\fromLmx восстанавливает чистый граф и связи с готовыми ABI-совместимыми бинарниками
после перезапуска на той же платформе по модулю/имени входа, без трансляции заново.
Для произвольной S внешние таблицы автоматически не добавляются.

<a id="satisfies"></a>
## 15. satisfies

Установленное соответствие отображает требуемые поля модели на фактические физические поля кандидата, включая иной
порядок полей. Оно принадлежит приёму или обходу, которые его получили, и сохраняется для этих чтений, операций взятия
адреса и явных записей в граф. Арена не имеет постоянного хранилища отображений и отдельного отображения для `call` или
DATA; места, локальные для вызова, не публикуются. Разный порядок полей не сводится к тождеству индексов; чтение,
получение адреса и явная запись в исходный граф пользуются тем же соответствием.
В данных каждая объявляющая запись — вхождение имени: повторное объявление прежнего не заменяет и в него
не пишет, а имя с двумя и более вхождениями адресуется только с индексом вхождения (решение автора 2026-11-11,
[L3](LMX_semantics.ru.md#fields)); выбор «последнего вхождения» не является частью нового контракта. `s\[N]field` с
нулевым `N` адресует N-е вхождение имени — запись данных, объявляющую это имя, — а не элемент Array. Карта не хранит
runtime-имена и не удерживает граф живым сама по себе. См. [L2 §14](L2_spec_ru.md#satisfies).

<a id="gc"></a>
## 16. Сбор

`lmx_gc_collect` реализует сбор по корням арены, включая Message, граф, почту и `Thread.children`. Простой режим арены сбор не выполняет. См. [L2 §15](L2_spec_ru.md#gc).

<a id="c99"></a>
## 17. Выход C99

Один вызов транслятора выдаёт один `.c`. Строгая сборка использует `-std=c99 -Wall -Wextra -Wpedantic` и диагностики несовместимых указателей, отброшенных квалификаторов и неявных объявлений. `struct:`, `enum:`, `fnptr:` и `type:` понижаются в C-объявления. Это не меняет модель памяти арены.

<a id="lowlevel-scope"></a>
## 18. Машинная поверхность

L1 сохраняет представление и числовую семантику C99-платформы. Переменная L1 и поле C-агрегата сами по себе не являются графовой ячейкой Lmx; доступ к графу идёт через библиотеку ядра. Совпадающее написание операции L1 и L2 не делает их семантически одной операцией.

<a id="lowlevel-address"></a>
## 19. Указатели и поля

| L1 | C99 |
| --- | --- |
| `int@: p` | `int *p` |
| `char@@: pp` | `char **pp` |
| `p := @x` | `p = &x` |
| `\p` | `*p` |
| `\p := value` | `(*p) = value` |
| `p\field` | `p->field` |
| `a[i] := value` | `a[i] = value` |

Таблица задаёт целевое единое написание; переходный рукописный L1 может ещё требовать миграции порядка объявлений. Адресуемая цель должна иметь действительное C-хранилище. `value\field` — шаг указателя; доступ к C-агрегату по значению требует явной C-формы. `const: char@: p` понижается в `const char *p` и защищает символы, не ячейку указателя. Это не глубокая неизменяемость L3.

L2-индексация, включая `array[-1]` и любую конечную цепочку соседних индексов, понижается в расчёт
смещения без проверок length/знака/арены. L3 использует собственный тип ссылки на дескриптор
массива с index и одну проверку итогового элемента; storage внутри этой ссылки не хранится.
L3-указатель на примитив также имеет отдельный тип, используя общий задел типизированных ссылок.

<a id="lowlevel-array"></a>
## 20. Array и сырой C-массив

Обычный `[]:` и в L1, и в L2/L3 означает языковой Array — графовую Structure на общей основе `Lmx` с типизированными
элементами и структурным `parent`. Только явная дверь `c.array:` выбирает сырой непрерывный C-массив без графового
`Lmx`, арены и скрытых проверок индекса. Прямоугольный сырой массив не превращается в массив отдельно выделенных строк.
Время жизни автоматического C-массива подчиняется C99; он не отождествляется с графовым Array. Прежнее понижение голого
L1 `[]:` прямо в C-массив — состояние реализации, которое предстоит устранить.

<a id="lowlevel-abi"></a>
## 21. Приведения и C ABI

`cast: (T) expression` выдаёт явное C-приведение, не проверяемое преобразование L3. `c.name` — явный внешний C-символ. `foreign: Name` требует определения типа во включённом C-заголовке; `external` и `prototype` описывают экспорт и объявление, `include` и `predef` — явные зависимости. Заголовочный `name.h.lm1` выдаёт `name.lm1.h` и допускает объявления без исполняемых тел. Поле по значению требует завершённого C-типа, указатель допускает forward-объявление.

<a id="lowlevel-expression"></a>
## 22. Выражения и управление

L1 понижает C-арифметику, логику, битовые операции, `++/--` и обычный поток управления. Исходное `=` в сравнении становится `==`; `target: expression` — присваиванием. `switch` допускает C-fallthrough, в отличие от L3 `match`. L1 `throw/catch/finally` с машинной служебной нагрузкой не определяет типизированные отказы L2/L3.

<a id="lowlevel-sync"></a>
## 23. Синхронизация

L1 не определяет структурный ресивер `synchronized`. Ядро использует явные машинные и внешние атомарные операции; `volatile` не заменяет атомарность. Контракт `synchronized` принадлежит [L2](L2_spec_ru.md#lowlevel-sync).

<a id="receiver-library-l1-boundary"></a>
## Граница для новой библиотеки ресиверов L3

Новые функциональные ресиверы остаются алгоритмами L3 и библиотеки над обычными записями графа и вызовами.
Понижение в L1 не вводит для них особых опкодов lambda, контейнера или curry, второго графа программы и нативных
полей программы. Там, где компиляция запрошена явно, порождённые вызываемые понижаются в настоящие методы с
установленным типизированным ABI. `satisfies` — текущее имя механизма допуска. См. [интеграцию
L2](L2_spec_ru.md#functional-receiver-abi) и [интеграцию в
ядро](kernel-implementation.ru.md#receiver-kernel-integration).
