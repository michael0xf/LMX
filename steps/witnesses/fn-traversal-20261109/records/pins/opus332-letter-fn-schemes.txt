A — принимаю. Lmx объявления сама получает имя fn строкой общей таблицы адрес -> name; её поля 0–4 — аргументы name, args, return, var, body; f — значение поля 0 (аргумент name), а не имя исходной декларации. Механизм общий для всех именованных receiver-форм. Frame `R: a1 a2 …` -> Lmx с именем R и полями [a1, a2, …], построенными по общим правилам: вызов `f(1)` -> Lmx "f" [1], `if: c …` -> Lmx "if" [c, …], `return: x` -> Lmx "return" [x], `x: 5` -> Lmx "x" [5], data-блок `S: … end: S` -> Lmx "S" […] (как и сейчас). Выражение x + 1, путь, `:=` и безымянные Structure не меняются. Роль имени решает потребитель своим разрешением в namespace обхода, по стадии и порядку, без флага. Следствие для обоих потребителей: разрешение имени идёт через namespace обхода, заполняемый объявлениями по порядку (имена fn/sub/fm — на весь блок), а не сканом имён слотов кодового блока. Иначе Frame `x: 5` с именем x нашёлся бы как место x.

B — принимаю, своё предложение снимаю. Автозаполнение var — построение аргумента var декларации: явная var и собственные объявления тела; поля видны с первой строки, инициализаторы исполняются на написанных местах. Сбор методов — отдельный обход потребителя. У декларации с телом аргумент var есть всегда; у дескриптора без тела — три аргумента name, args, return.

C — схема результата (предложение, не норма). Источник: D = Lmx "fn" [слово f, A, R, V, B], где A, R, V, B — безымянные Lmx. Обход, обрабатывая D, создаёт F — Lmx в участке lmx:result (Structure, созданная исполнением ресивера fn, §2.2), с именем "f" по значению аргумента name и четырьмя полями: ячейка ссылки "args" -> A, "return" -> R, "var" -> V, "body" -> B. Это ячейки уже существующего вида LMX_TYPE_GRAPH_LMX_REF (вид 6); каждая со своим именем по своему адресу. A, R, V, B не копируются и не именуются; D не меняется. Путь F\args\x читает поле x самой A (книга :441). Строка namespace f -> F живёт только в таблицах обхода. Новый обход создаёт новые F и ссылки.
Не решено:
c1. Ссылка вида 6 указывает только на Lmx, а return `int` написан атомом. Предлагаю строить аргумент return безымянной Structure из одного поля [int], как требование результата строилось и раньше; автор называет аргументы безымянными структурами. Альтернатива — ссылка на примитив, это новое расширение ссылки.
c2. Ссылка или общая копия (LmxCopyMap). Существующее правило книги :441 и среза 329 говорит о новом месте для уже именованной Structure; здесь цель безымянна, и ссылка нужна, чтобы исходный аргумент остался безымянным и неизменным. Это не прямое применение правила — прошу решения. Копия дала бы независимые экземпляры частей на каждый обход и требует родителя копии тела для лексики.
c3. Строки имён результатов прошлого обхода остаются в таблице адрес -> name до сбора (результаты недостижимы). Следующий обход ими не пользуется.
c4. Результат sub — F(args, var, body), результат fm — как у fn. Все три — в lmx:result. Наличие результата — по наличию поля "return", без признака.

D — разделение декларации и результата и реальное противоречие первичных ответов, на конкретном графе.
- fn (ясно): декларация D = Lmx "fn" [f, A, R, V, B] в графе; результат F создаёт обход (C).
- int — две формы, обе следуют из слов автора.
  Вариант 1 (2026-11-08: «Вы можете положить int: i 5 как атом и _всё_ о нём узнать из адреса»; «Нужен единый механизм во всех стпуктурах, и в сигнатуре тоже. "int: i" значит надо сделать отдельным типом "int без инициализации"» — это был ответ о том, как незаполненный `int: x` выглядит в чистом графе). Источник — сам примитив: ячейка int = 5 со строкой имени i; формал `int: x` — uninit:int -> ячейка int со строкой x. Тип, имя и значение аргументов объявления читаются по адресу. Ресивер int при обходе «создаёт i» строкой namespace i -> эта ячейка, без новой ячейки: декларация и результат совпадают.
  Вариант 2 (2026-11-09: «по тому же правилу по которому int: i 5 создаёт i» вместе с A). Источник — Lmx "int" [слово i, int 5], формал — Lmx "int" [слово x]. Ресивер int при обходе создаёт новую ячейку int = 5 (uninit для x) со строкой имени i. Тогда мест программы в исходном графе нет: состояние программы живёт в созданных обходом ячейках, хотя §1 п.1 говорит «программа, её данные и её текущее состояние — один Lmx-граф». Граф после исполнения корня равен графу до. Ожидания всех фикстур меняются, а выпущенная программа создаёт места при исполнении.
  Тот же выбор касается data-блока `S: int: a 1 end: S` (Lmx "S" — сама Structure S, или Structure S создаётся обходом) и объявления с вычисляемым инициализатором `int: r take(p, 1)` -> Lmx "int" [r, Lmx "take" [p, 1]]. Сейчас его исполнение переписывает слот графа созданным местом, то есть декларация заменяется результатом; при варианте 2 этого быть не должно.
  Прошу решения (при необходимости — автора): какой граф — источник для `int: i 5` у корня, для формала `int: x` и для data-блока.
До ответа делаю A, B и C для fn/sub/fm и остальных receiver-форм. Примитивные объявления, data-блоки и вычисляемый инициализатор держу в нынешней форме варианта 1; это и есть удерживаемая зависимая часть. Нормативы правлю в той же разбивке: «решено» и «открыто D».
