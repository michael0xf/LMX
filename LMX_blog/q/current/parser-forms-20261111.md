# Вопросы 2026-11-11 о парсере: непарная скобка, отметки, строки глубже внутри скобок — открыты

К словам автора 2026-11-11: [парсер везде один](../../2026-11-11.md#same-parser-inside-brackets),
[фигурные скобки — не комментарий](../../2026-11-11.md#braces-are-not-a-comment),
[отметка с ошибкой — ошибка](../../2026-11-11.md#mark-errors-and-string-marks). Спрашивает исполнитель (Fable, чат
«fable2»). «Сейчас» — парсер P0 на коммите `ca16f345` (образ `graph-f27`, hosted frontend `boot-f25`) и старая
версия `lingvamyxa_old_worked_version` (коммит `620db86`); каждая программа прогнана на обоих, ответы одинаковы.
Правка парсера остановлена автором до обсуждения.

## В1. Непарная закрывающая скобка

```text
x: a {)} b
```

Сейчас: принимается; у `x` три поля — атом `a`, пустая отметка Mix, атом `b`. Причина шире отметок: непарная `)`
нигде не ошибка, она молча обрывает перечень полей — `x: a ) b` даёт у `x` одно поле `a`, остаток `) b` пропадает
без сообщения. Рядом: `x: a {(} b` — ошибка разбора 5 «unclosed parenthesized form»; `x: f(a {)} b)` — ошибка 31
«unterminated brace mark».

Автор 2026-11-11: `x: a {)} b` и `x: a {(} b` должны быть ошибкой; какая именно ошибка у первой — вопрос.

Предложение исполнителя: непарная `)` (и `]`) — ошибка разбора с позицией самой скобки, в строке и внутри отметки;
своего кода у неё сейчас нет — вводится новый, «непарная закрывающая скобка».

## В2. Строка глубже внутри круглых скобок

Решение автора: внутри скобок правило уровней то же, что вне скобок. Три формы, которые внутри круглых скобок
сейчас читаются иначе, чем те же строки без скобок.

А.

```text
D: (
    y: a
        b
    z
)
```

В скобках у `y` два поля — `a`, `b`; без скобок (те же строки под `D:`) — `a` и безымянная Structure с `b`.

Б.

```text
D: (
    a
    b
        c
    d
)
```

В скобках у `D` четыре атома; без скобок — `a`, `b`, безымянная Structure с `c`, `d`.

В.

```text
call(
    . int: a b
    . ret: int)
```

В скобках точка после отступа — маркер уровня, у `call` два поля; без скобок (`call:` и те же строки) точка после
отступа — атом `.`, у `call` четыре поля.

Варианты: 1) внутри скобок добавляются только отсекатели и ошибка 13 при перескоке; строки глубже по-прежнему
продолжают перечень полей (А, Б, В читаются как сейчас); 2) внутри скобок всё как вне скобок: строка глубже
открывает вложенную безымянную Structure, точка после отступа — атом (А, Б, В меняют дерево).

Исполнитель читает принцип автора «один парсер в любом блоке» как второй вариант и сказал об этом автору.

## В3. Комментарий внутри отметки

```text
x: a {#)} b
```

Сейчас: ошибка разбора 31 «unterminated brace mark» в `1:6` — комментарий `#` идёт до конца строки и закрывает
собой `}`. С `}` на следующей строке запись принимается с пустой отметкой. Так и в
[грамматике, §19](../../../docs/LMX_grammar.ru.md#mix): «`}` внутри защищённого содержимого не закрывает внешнюю
форму».

Автор 2026-11-11: `{#)}` ошибкой быть не должна.

Вопрос: комментарий внутри отметки кончается на её закрывающей скобке (тогда `{#)}` — пустая отметка без ошибки, и
текст §19 меняется) — так?

## В4. Отметки внутри строк

```text
x: "text{)}text{mix}"
```

Сейчас: дерево — один атом-строка, отметки внутри строки не разбираются вовсе (так же для `x: "text{mix}"`).
Заметка старой версии `Lingvamyxa_parser_P0_mix_marks.txt`, §4: строка остаётся одним атомом, а внутренние отметки
«may still record» будущий сканер Mix; сканера нет ни в старой версии, ни в нынешней.

Автор 2026-11-11: внутри строк фигурные скобки разбираются, только не падают с ошибкой; эта строка должна дать
одно отдельное mix-дерево — для второй, правильной отметки; строка между кавычками при этом сохраняется целиком —
отметки не игнорируемые вставки.

Предложение исполнителя: сканер отметок внутри строкового содержимого — новая часть парсера: правильная отметка
даёт отдельное mix-дерево при строке, отметка с ошибкой пропускается без ошибки; сама строка остаётся атомом.
Где держится это дерево (поле при атоме строки или таблица отметок документа) — вопрос к автору.
