# Спецификация L1

Область — язык L1, его трансляция в C99 и запись механизмов ядра L2 на L1/C. Семантика L3 — [основная спецификация](LMX_semantics.ru.md), операции и модель ядра L2 — [спецификация L2](L2_spec_ru.md). Состояние реализации, проверенные срезы и миграционные задания вынесены в [заметки о реализации](implementation-notes.ru.md).

Каждый механизм ядра имеет основное определение в L2; здесь определяется только удобная промежуточная запись его реализации и понижение в C99. L1 не повторяет графовую семантику L2: граф, `own-load`, `dirty`, динамическая видимость и контекстная роль ресивера уже разрешены до выдачи L1.

<a id="scope"></a>
## 1. Предмет

Translator-L1 (`l1src/l1trans.lm1`) — синтаксически направленный понижатель wrapperless `.lm1` в одну единицу трансляции ANSI C99 на вызов. Это не L2: в профиле L1 нет онтологии `Lmx`, арены Message и таблиц `implements` как языковых форм. Ядро L2 может быть написано на L1 и служить входом того же транслятора.

<a id="translator"></a>
## 2. Транслятор

Вход профиля — файл с конечным расширением `.lm1`. Понижение членов в C — не контракт разрешения путей L2 через граф `Lmx`.

Префикс `@` в L1 — взятие адреса C этой привязки (`p: @ value` → `&value`). Длинные прогоны `@` в деклараторах — звёзды указателя C, не повторный address-of. Обратный слэш: ведущий `\` — сырая загрузка указателя; `value\field` — поле, в C `->`.

Проекция непримитивного значения Lingvamyxa в L1 никогда не является C-агрегатом по значению: Structure и Array передаются, возвращаются и хранятся как скопированное значение физической ссылки на их дескриптор/вхождение. Поэтому исходное `Model: fresh` не понижается в `struct Model fresh`; оно строит графовое значение, а рабочая L1-привязка имеет вид ссылки, концептуально `Lmx *fresh`. Взятие `@fresh` адресует ячейку, уже хранящую эту ссылку, и потому концептуально даёт `Lmx **`. Внутренние записи машинного ABI ядра, явно объявленные через L1 `struct:` и иногда вложенные по значению, не являются проекцией непримитивного значения языка и не отменяют этот запрет.

Дверь в libc — объявления в `l1src/libc_abi.lm1` и вызовы `c.имя`. Заголовочные единицы L1 объявляют; исполняемое тело в заголовке отказывается.

<a id="lmx"></a>
## 3. `Lmx` на L1

Определение полей — [L2 §2](L2_spec_ru.md#lmx). Целевая L1-проекция в `l2src/lmx.h.lm1` задаёт `VoidArray` с `size_t: size` и `@: void data`, затем `Lmx` со встроенным **по значению первым полем** `VoidArray array`, вторым `@: Lmx parent` и третьим `LmxEntry: native` — прямой ссылкой на нативную реализацию тела Structure, нуль при её отсутствии (посажено 2026-09-26 в плоской раскладке `{parent, len, data, native}`; миграция на `{array, parent}` ещё впереди); C-заголовок порождается транслятором. Отдельного псевдонима `LmxArrayDesc` целевой ABI не требует. Это именно встроенный массив физических дочерних ссылок, чей backing зарегистрирован в индексе диапазонов арены, а не дополнительная обёртка над прежними полями `len` и `data`. Нет отдельного тега в записи. Слот поля Structure — ячейка массива `void *`; динамический состав ссылок на дочерние Message является отдельным List (`KIND_LIST`) в графе и не понижается в фиксированный набор таких слотов.

<a id="type-by-range"></a>
## 4. Тип по диапазону на L1

Правило — [L2 §3](L2_spec_ru.md#type-by-range). Перечисления и `LmxRange` — тот же `lmx.h.lm1`. Индекс принадлежит арене; классификация — функции `lmx_range_*` из `lmx_arena.h.lm1`, тела в `lmx_range.lm1` / `lmx_arena.lm1`. Домены механизмов — `#define` в `lmx_implements.h.lm1`, не поля `LmxMsg`.

<a id="pool"></a>
## 5. Пул на L1

Правило — [L2 §4](L2_spec_ru.md#pool). Структуры чанка и пула — `lmx.h.lm1`. Акты `lmx_pool_open`, `lmx_pool_make`, `lmx_pool_take`, `lmx_pool_take_n`, `lmx_pool_add_chunk` объявлены в `lmx_pool.h.lm1`, реализованы в `lmx_pool.lm1`. Рост — новый чанк как блоки арены, чтобы `revert` снял интервал вместе с ними.

<a id="method-array"></a>
## 6. METHOD и Array на L1

Правило — [L2 §5](L2_spec_ru.md#method-array). `fnptr: LmxEntry () void`; `struct: LmxMethod` и `VoidArray` в `lmx.h.lm1`. Дескриптор понижается ровно в два поля `{size, data}` в этом порядке; backing самостоятельного Array содержит ровно `size` ячеек. То же физическое представление первым полем вложено в `Lmx` для дочерних ссылок. У базового Array нет `capacity`, он не растёт и не переключает backing. Динамическое членство — отдельные модули List (`KIND_LIST`), например `lmx_list_owned`. Типизированные пулы Array — модули `lmx_array_owned`, `lmx_array_ref_owned`, `lmx_chars_owned`, `lmx_value_owned`.

<a id="arena"></a>
## 7. Арена на L1

Правило — [L2 §6](L2_spec_ru.md#arena). `struct: LmxArena` и прототипы — `lmx_arena.h.lm1`; тела — `lmx_arena.lm1`. Блоки — `lmx_arena_blocks.h.lm1` / `.lm1`. Слоты Structure — `lmx_arena_refs.h.lm1` / `.lm1`. Поколение сборщика — поле `generation`; простой режим — `simple`. Любой L3 Thread использует тот же механизм типизированных массивов. При создании в его арену попадают только явно переданные данные и ссылки. Начальная сборка может обычными актами массивов разместить постоянные значения начального модуля в арене владеющего им R0 и передать физические ссылки его детям. Поздний DLL-подобный модуль создаёт собственные запечатанные типизированные диапазоны в арене своего владельца. При композиции или квалифицированном понижении конструктора потребитель получает исходную физическую ссылку на `independent: const: immutable` без копирования и смены владельца. Его выгрузка и срок жизни диапазонов пока не определены. L1-понижение не создаёт скрытых таблиц, автоматического наследования, отдельной семантической операции импорта или специальных номеров корневых слотов.

<a id="message"></a>
## 8. Message на L1

Правило — [L2 §7](L2_spec_ru.md#message). `type: LmxFlag uint_fast8_t`; `struct: LmxMsg` в `lmx_message.h.lm1`. Локальная идентичность понижается в физический адрес записи; поля `index` в Message нет. Чтение `running` / `handoff_ready` является обычной атомарной нагрузкой без RMW и без дополнительного fence. Хуки опроса объявлены в `lmx.h.lm1` (`lmx_msg_poll_abort`, `lmx_msg_poll_escape`), тела — на стороне ядра.

<a id="thread"></a>
## 9. L3 Thread на L1

Правило — [L2 §8](L2_spec_ru.md#thread). Исполняемый L3 Thread понижается в одну запись, первым полем которой по значению является закрытая запись Message: `struct: LmxThread; LmxMsg: message; ...`. Поэтому `@thread` и `@thread\message` имеют один физический адрес. Это общий префикс C-layout, а не семантическое наследование: `LmxMsg` остаётся минимальным, тогда как почта, планирование, режим исполнения и остальные API Thread находятся только в хвосте Thread. Обычный отдельный Message остаётся самостоятельной записью `LmxMsg` и не может позднее быть преобразован на месте в Thread; исполняемый объект изначально строится как `LmxThread`. Операции Message могут использовать адрес первого члена, но операции Thread требуют, чтобы точный типизированный диапазон классифицировал выделенный объект как `LmxThread`. Единственный состав непосредственных детей понижается в графовый List (`KIND_LIST`) физических ссылок, выделенный в арене родителя. Планировщик обходит этот List непосредственно; отдельная цепочка `LmxLink` и очередь членства менеджера не порождаются. Ход — `lmx_thread_turn`. Режима исполнения потока и запроса режима на границе такта нет (прежний флаг режима удалён): Structure в позиции кода исполняется нативно, если её слово `native` заполнено, и walker’ом, если пусто ([L2 §10](L2_spec_ru.md#own)). Оба пути работают над объявленными полями исполняемой Structure — обычный вызов над её собственным графом, свежий экземпляр только при повторном входе или явно переданных данных — и не копируют метод при входе; прежней модели own-load/dirty кадра активации больше нет (§11). Её служебное хранилище может быть переиспользуемым, но вход не должен становиться существенно дороже нативного вызова из-за выделения и освобождения памяти на каждую активацию.

<a id="root-close"></a>
### 9.1. R0 и верхний родитель-каркас на L1

Правило — [L2 §8.1](L2_spec_ru.md#root-close). R0 — обычный L3 Thread без дополнительных функций; его родитель-каркас WorldWideMix использует тот же механизм родителя и также не получает root-only API. Только верхний каркас не имеет собственного родителя. Обычный каскад идёт по графовым List прямых детей. Общий timeout всего поддерева принадлежит внешнему host-watchdog и проверяется независимо от срока живучести R0 и индивидуальных сроков потомков. Нормальный путь возвращается только после завершения всего поддерева; истечение верхнего срока опускается host в безусловное завершение процесса ОС, а не в повторяемый вызов `close` или успешный возврат частично закрытого runtime.

<a id="mailbox"></a>
## 10. Почта на L1

Правило — [L2 §9](L2_spec_ru.md#mailbox). Каждый L3 Thread владеет своим `struct: LmxPost` и почтовым API. Явно переданный родителем сервис доставки/адресации только разрешает цель и вызывает admission целевого ящика; он не читает ящик, не планирует адресата и не ведёт членство. Кольцо inbox — DynamicArray своего типа пары-слота плюс `head`/`tail`, рост приблизительно в `3/2` раза с начальной ёмкостью 2 (ёмкость — в поле `*DynamicArray`, не на базовом Array); его единственный реентерабельный monitor без wait/notify и списки outbox/staged — `lmx_post.h.lm1`. Каждый элемент inbox — `[target, source_arena]`: публикация не изменяет арену получателя, а owner получателя присоединяет donor до выдачи target; отказ сохраняет пару. Все enter/leave, рост и операции коллекции сосредоточены в `lmx_post.lm1`. Внутренний backing кольца не является значением графа и может перемещаться только под монитором. Монитор не оборачивает атомарные операции `LmxMsg.running/success/handoff_ready`; они остаются отдельным механизмом Message. `init` и `close` требуют отсутствия одновременных операций с ящиком; close отказывает fail-closed для donor, который не может освободить. Settle закрывает почту до удаления маршрута/членства и до release либо attach арены. Допуск цели — `lmx_post_admits` через домен адреса. Доставка между объектами — `lmx_deliver`.

<a id="own"></a>
## 11. Own на L1

Правило — [L2 §10](L2_spec_ru.md#own): пара исполнения — записи идут прямо в объявленные поля исполняемой Structure; рабочих копий, отметок dirty и контрольных точек нет. Прежние модули `lmx_own` и `lmx_dirty` удалены (2026-09-26); ни порождаемый код, ни walker, ни интерпретатор L3 ничего не публикуют и не перечитывают.

<a id="call"></a>
## 12. Вызов на L1

Правило — [L2 §11](L2_spec_ru.md#call). Переходный METHOD использует `fnptr: LmxCallEntry (@: Lmx node) int`; Callable использует `fnptr: LmxCallEntrySelf (@: Lmx node; @: Lmx self) int`, где `node` — закреплённое для активации лексическое пространство над методом, а `self` — скрытая физическая база own-полей выбранного вхождения. Обычное поле `Lmx.parent` не является словом языка. `lmx_call0` — `lmx_call.lm1`. Сопоставление сигнатуры — обязанность транслятора, не этого модуля.

<a id="child"></a>
## 13. Ребёнок на L1

Правило — [L2 §12](L2_spec_ru.md#child). Создание и резервация готовят ребёнка отдельно, а успешная публикация добавляет его физическую ссылку в List (`KIND_LIST`) детей графа родителя. L1-интерфейс не принимает номер слота ребёнка и не вводит фиксированный размер членства.

<a id="copy-merge"></a>
## 14. Копия и merge на L1

Правило уже определено в [L2 §13](L2_spec_ru.md#copy-merge) и [L3 §8](LMX_semantics.ru.md#construction). `lmx_graph_copy_owned.lm1`, `lmx_merge_owned.lm1` и парные `.h.lm1` являются записанной на L1 реализацией полного обхода `merge`. Сам L1 не решает, является ли `left: right` объявлением, присваиванием или вызовом, не содержит графовой привязки и не моделирует `own-load`/`dirty`. L2-транслятор до выдачи L1 выбирает контекстную роль, выполняет необходимые проверки типа, `const` и `implements`, а затем выдаёт либо однозначный вызов реализации `merge`, либо обычное C-подобное присваивание ссылки. Допустимы разные промежуточные формы, если порождённый C сохраняет выбранную L2/L3-семантику и полный обход `merge`.

<a id="implements"></a>
## 15. `implements` на L1

Механизм допуска определён в [L3 §7](LMX_semantics.ru.md#admission); роль L2 — в [L2 §14](L2_spec_ru.md#implements). Функции классификации адресов обслуживают общий индекс арены, которым пользуются почта и вызовы; классификация сама по себе не является `implements`.

<a id="gc"></a>
## 16. Сбор на L1

Правило — [L2 §15](L2_spec_ru.md#gc). `lmx_gc_collect` — `lmx_gc.lm1`.

<a id="c99"></a>
## 17. Опускание в C99

Один вызов транслятора даёт один `.c`. Строгая сборка поколений: `-std=c99 -Wall -Wextra -Wpedantic` и `-Werror=` на несовместимые указатели, отброшенные квалификаторы, неявные объявления. `os:` выбирает Windows или POSIX (`l1trans.lm1`). `include:` / `predef:` становятся включениями C. Агрегаты L1 `struct:` / `enum:` / `fnptr:` / `type:` опускаются в C99 typedef/struct. Это не модель памяти L2: модель памяти задаёт арена ([L2 §6](L2_spec_ru.md#arena)).

<a id="lowlevel-scope"></a>
## 18. Машинная поверхность L1 и связь с L2

Эти разделы определяют прямые машинные операции Translator-L1. Полный контракт соответствующего семейства L2 дан [в L2](L2_spec_ru.md#lowlevel-scope) и не переносится автоматически на одинаковое написание L1.

Главное различие: в L1 переменная и поле C-агрегата не являются графовой ячейкой Lmx. Здесь нет own-кэша языка, скрытого допуска `implements` или автоматической арены. L1-код ядра явно вызывает библиотеку арены и тем самым реализует механизмы L2. Наличие такой библиотеки не меняет семантику `@`, массива или присваивания в самом L1.

<a id="lowlevel-address"></a>
## 19. Указатели, поля и адресуемые цели

| L1 | Выход C99 | Условие |
| --- | --- | --- |
| `@: int p` | `int *p` | Явное объявление указателя |
| `@@: char pp` | `char **pp` | Каждая декларативная `@` добавляет уровень |
| `p: @x` | `p = &x` | x — адресуемая C-цель |
| `\p` | `*p` | Адрес должен быть действительным и подходящего типа |
| `\p: value` | `(*p) = value` | Цель допускает запись |
| `p\field` | `p->field` | p указывает на агрегат с известным полем |
| `a[i]: value` | `a[i] = value` | Сырой индекс C; автоматической проверки нет |

`l1_emit_assign_head` разбирает ведущие разыменования, корень, суффиксы полей и индексов. `l1_assign_index_close` учитывает вложенные скобки, строки и экранирование; `l1_emit_assign_index` передаёт содержимое индекса обычному разбору выражения. Пустой индекс, незакрытые скобки, отсутствующее имя после `\` и некорректная цель диагностируются. Это разбор lvalue, не создание объявления или нового поля.

Обычное `value\field` всегда понижается как шаг указателя. У агрегата C по значению нужен явный C-доступ, например `c.value.field`; нельзя считать сгенерированное `value->field` корректным только потому, что исходная форма разобрана. В L2 обычный графовый путь имеет другой контракт [адресации](L2_spec_ru.md#lowlevel-address).

В выражении `@` — address-of, а в форме типа `@: T` — декларатор указателя. Поэтому `c.sizeof(@: char)` обозначает размер `char *`, а `c.sizeof(@ x)` — размер адреса x. Лишние поля указательного типа/параметра не должны теряться: транслятор имеет диагностики `pointer type has extra fields` и `pointer parameter has extra fields`. Приведение и указательный декларатор сами по себе не проверяют живость, выравнивание, границы и права доступа к объекту.

`const: @(char p)` понижается в `const char *p`: защищены символы, не ячейка указателя. L1-`immutable` — групповое применение этого C-квалификатора к объявлениям; это не глубокая графовая неизменяемость L3 и не `RuntimeImmutable`. Перепривязка p остаётся допустимой, запись через него — нет. Вложенные обёртки сводятся к одному C `const`; не следует обещать на этой основе защиту всех псевдонимов изменяемого внешнего объекта.

<a id="lowlevel-array"></a>
## 20. Массивы машинного профиля

В L1 обе обработанные семьи `[]:` и `c.array:` понижаются в массивы C. Это отличается от обычного Array L2, где `[]:` строит дескриптор. `l1_emit_bracket_array` обрабатывает последовательность измерений; `l1_emit_c_array` — явно обёрнутое объявление. К профилю относятся формы `[]: int values 3 2 4 6`, `[][]: int matrix 2 2`, `c.array: [3]: int: values 2 4 6`, `c.array: []: char buffer 256`.

Результат — непрерывное C-хранилище, без `LmxArrayDesc`, метаданных арены и скрытых проверок индекса. Прямоугольный `matrix` не превращается в массив отдельно выделенных строк. Тип элемента и его указательная глубина формируют C-декларатор; `const` квалифицирует базовый элемент. `l1_emit_c_array` отвергает несколько логических дочерних объявлений, отсутствующий тип или имя, неправильную внешнюю голову; тело инициализатора выдаётся через `l1_emit_inits`.

Отличие от графового Array L2 — способ нахождения хранилища, не наличие проверок: в L2 индекс и дескриптор при доступе тоже не проверяются. `@array[i]` в L2 адресует настоящий элемент backing, после чего понижение использует обычный машинный адрес. Проверяемая операция принадлежит L3; [контракт L2](L2_spec_ru.md#lowlevel-address) определён отдельно.

Размеры, время жизни, инициализация и преобразование массива в указатель после понижения подчиняются C99. Успешный разбор не означает проверки всех ограничений C: часть ошибок обнаруживает следующий компилятор. Контракт L2 `c.array` определён [отдельно](L2_spec_ru.md#lowlevel-array).

Сохранение адреса автоматического массива после возврата не продлевает его жизнь. Для кода ядра долгоживущее хранилище выделяется явно через [арену](#arena) либо внешний API с определённым освобождением. Сырые C-массивы, используемые транслятором как временные буферы, не являются доказательством поддержки обычных графовых Array в исходном L2.

<a id="lowlevel-abi"></a>
## 21. Приведения, C-интерфейс и объявления ABI

`l1_emit_cast` понижает `cast: (T) expression` в явное C-приведение, включая допустимый указательный тип и последовательность слов C-типа, например `unsigned long`. Это не проверяемое преобразование чисел высокого уровня: диапазон, выравнивание и допустимость последующего доступа определяются C и контрактом вызываемого API.

Префикс `c.` — сырая дверь в C: явный доступ к C-символу (`c.malloc`, `c.memcpy`, `c.sizeof` и т. п.). Дверь не ведёт отдельного реестра объявлений C-имён как нормы языка. В компактной C-форме транслятор снимает `c.` и понижает в C99; это не общий текстовый интерпретатор L1 внутри круглых скобок. Вложенный receiver с двоеточием, например `c.sizeof((cast: (unsigned) 0))`, имеет отдельную диагностику; двоеточие внутри строкового/символьного литерала либо согласованного C-тернарного выражения не должно ошибочно считаться receiver.

Внешнее определение типа объявляется `foreign: Name`: имя регистрируется для транслятора, само определение должен дать включённый C-заголовок. `extern: @: Lmx object` выдаёт объявление объекта другой единицы. `type: Alias …`, `struct:`, `enum:`, `fnptr:` в заголовочной единице описывают реальный C ABI, не обычные структуры L3. `fnptr` — тип C-указателя функции; он не заменяет METHOD и контракт вызова L2.

Заголовочный источник `name.h.lm1` выдаёт `name.lm1.h`. Заголовок допускает объявления, не исполняемые тела. `l1_hdr_*` упорядочивает зависимости: forward-объявления достаточны для указателей, но поля по значению требуют завершённого типа; цикл таких зависимостей ошибочен. `include` подключает указанный файл, `predef` заголовка сохраняет относительный путь, чтобы одноимённые файлы разных каталогов не столкнулись. Это работа транслятора, не runtime-реестр имён.

`external` экспортирует объявленную функцию/процедуру; `prototype` задаёт её объявление. `os`, `ifdef`, `define` выбирают и выражают явно заданный машинный профиль. Зарезервированные головы `C`, `L1`, `L2`, `L3`, `c.struct` и `c.union` не получают поведения без явного определения соответствующего профиля. Более широкий L2-контракт — [в L2](L2_spec_ru.md#lowlevel-abi).

<a id="lowlevel-expression"></a>
## 22. Выражения C, обновление и управление

`l1_emit_expr`, `l1_emit_expr_range`, `l1_emit_one_expr` и обработчики целей формируют C-выражения. Исходное `=` в сравнении становится `==`; `target: expression` — присваиванием. Указательные операции описаны [выше](#lowlevel-address). Арифметические, логические, битовые операции, сдвиги, `++`/`--` сохраняют требования выбранных C-типов; автоматической проверки арифметического переполнения или границ здесь не обещается.

Профиль содержит `if`/`else`, `while`, трёхчастный `for`, `break`, `continue`, `switch`/`case`/`default` и возврат. У `switch` нет автоматического `break`: проваливание соответствует C, а не контракту L3 `match`. Голое видимое имя нульаргументной функции в позиции оператора может обозначать вызов; это не метка. `goto` не делает произвольную исходную форму допустимым объявлением цели.

L1-профиль `throw`/`catch`/`finally` использует служебный код и `long`-нагрузку до восьми полей. Этот контракт относится только к L1; типизированные результаты и отказы L2 описаны [отдельно](L2_spec_ru.md#lowlevel-expression).

<a id="lowlevel-sync"></a>
## 23. Синхронизация

L1 не определяет исходный структурный receiver `synchronized`; его контракт принадлежит [L2](L2_spec_ru.md#lowlevel-sync). Ядро на L1 использует явные машинные/внешние операции для [почты](#mailbox) и рукопожатия. Их порядок памяти и допустимые писатели определяются соответствующим модулем. `volatile` не подменяет атомарную операцию, а атомарный вызов не создаёт структурную область синхронизации.
