# Состояние и последовательные симуляции

Группа дополняет прежний каталог тремя механизмами, которые не сводятся к уже имеющимся State, Cache-Aside или Actor. Каждый пример содержит проверяемый контракт, рабочие контрольные исходники и обе формы LMX.

| № | Механизм | Пара сравнения | Проверяемое свойство |
| --- | --- | --- | --- |
| 106 | [Double Buffer](106_double_buffer_comparision.md) | C++ / Go | Одно поколение читает только предыдущее; два массива переиспользуются |
| 107 | [Dirty Flag](107_dirty_flag_comparision.md) | C++ / JavaScript | Пересчёт только после изменений; несколько записей объединяются |
| 108 | [Fixed Timestep Game Loop](108_fixed_timestep_comparision.md) | C++ / JavaScript | Целые update, перенос остатка, независимые снимки кадров |

## Как читать и собирать LMX

В `examples/lmx/shared/` находится единственная общая часть каждого примера. В `examples/lmx/procedural/` — процедурный вариант; в `examples/lmx/` — функциональный. Для одного сценария используется общая часть и **ровно один** вариант. Варианты объявляют одинаковые публичные имена и не загружаются одновременно.

В [patterns.json](patterns.json) поле `source_files` задаёт полный порядок частей, а `code` содержит их соединение. `source_file` обозначает стилевой фрагмент, а не самостоятельный файл со всеми зависимостями. Это описание сборки примера, не новое правило `import` или раскрытия структуры в LMX. Тестовый загрузчик может объединить два текста до разбора или добавить обе части в одну область графа. Общие определения не нужно копировать в каждый исходник.

После запуска корня обычные операции вызываются через `Evolve\run`, `CacheMake\make` / `CacheWrite` / `CacheRead\get`, `Frames\run`. Новое правило `Main` не вводится. Все изменяемые состояния принадлежат одному последовательному владельцу; сравнение не выдаёт обычное присваивание за межпоточную синхронизацию.

Функциональные формы используют уже имеющиеся `foldl`, `range`, `maximum`, `mapAccumL` и конструктор пары `FxStdPair\make`. Полные тела этих операций находятся в общей библиотеке `LMX_Fn_Receivers` и не повторяются здесь. Буфер и кэш имеют эффекты по своему контракту: их жизненный цикл остаётся явным и в функциональном обходе.

## Граница сравнения

Четыре кандидата в каждой статье: LMX процедурный, LMX функциональный и **два языка из записи конкретного примера**. Верхнее поле `languages` в JSON — объединение языков группы; оно не задаёт одну тройную сравнительную пару для всех строк.



## Проверка

Из этой директории:

```sh
python3 tests/validate.py --write-report
```

При наличии соответствующих инструментов прогон компилирует контрольные C++ и Go, запускает JavaScript, проверяет именованные fixtures, полный набор двоичных колец длиной до 8 на пяти шагах и воспроизводимые случайные сценарии. Для fixed-step используется независимая закрытая формула переходов, а не копия испытуемого цикла. Проверяются ошибки, сохранение входов, повторный запуск, независимость снимков и ленивый счётчик кэша.

Результаты: [validation_results.json](tests/validation_results.json). Контрольные данные: [fixtures.json](tests/fixtures.json), [fixture_expectations.json](tests/fixture_expectations.json). Исполняемые файлы создаются во временной директории и в архив не попадают. При отсутствии конкретного внешнего инструмента прогон отмечает пропуск, а не успешное выполнение.

**LMX parser: NOT_RUN. LMX runtime: NOT_RUN.** Проверка синхронности Markdown, исходников и JSON не заменяет прогон парсера. Новые листинги требуют отдельной проверки тем парсером, которым проверялась исходная документация.

## Источники и стандартная библиотека

Основные первичные источники — главы Robert Nystrom в *Game Programming Patterns* и их оригинальный репозиторий; точные ссылки находятся в каждой статье. Для использованных библиотечных операций приведены Go specification, ECMAScript и рабочий проект стандарта C++.

Новых скрытых операторов или специализированных встроенных функций здесь нет. Сопоставление удобств:

| Контрольная запись | Уже существующий механизм LMX | Где используется |
| --- | --- | --- |
| Go `copy`, JS `slice`, C++ копия массива | `[copy(values)]` с объявлением массива | Независимое исходное состояние |
| Go множественное присваивание / C++ обмен буферов | Групповое `:=` | Публикация поколения |
| C++ `max_element`, JS `reduce` с `Math.max` | `maximum` | Производный максимум |
| JS `map` и состояние между кадрами | `mapAccumL`, `FxStdPair\make` | Снимки фиксированного шага |

Выбор целочисленных сценариев не сужает общие библиотечные операции до `int`: их прежние обобщённые контракты сохраняются.

## Фактический прогон этой версии

C++: 2663 сценария Double Buffer, 107 сценариев Dirty Flag и 110 сценариев Fixed Timestep — PASS. JavaScript: те же 107 и 110 сценариев — PASS. Go — NOT_RUN: найденная команда `/usr/bin/go` является настольной игрой, а компилятор Go не найден. Готовый Go-адаптер сохранён для повторного запуска в среде с настоящим toolchain. Общий статус поэтому PARTIAL; это не ошибка контрольных реализаций, прошедших исполнение.
