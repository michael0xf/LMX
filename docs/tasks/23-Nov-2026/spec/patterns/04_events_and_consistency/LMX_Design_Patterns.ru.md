# LMX: События, распределённое состояние и согласованность

Java представляет явные интерфейсы сервисов и зрелую экосистему транзакционных приложений; Go — компактные сервисные обработчики и явную обработку ошибок. Сравниваются одинаковые протоколы и одинаковые внешние гарантии, а не разные по полноте фреймворки.

Сохранены исходные IDs 11,12,41,48,50,51,55,57; добавлен 86. LMX-обработчики размещаются в исполняемых Message с одной полосой записи и собственными аренами. Между владельцами используются post/send/receive и уже описанный HTTP-профиль §32: endpoint+route, application/lmx, intake/admission, синхронный reply либо replyTo/correlation. Обозначения transport/db/store/coordinator в листингах — явно перечисленные адаптерные контракты, не новые встроенные ресиверы. Их реализация одинаково исключена из всех трёх листингов и длины кода. Серийный turn не заменяет транзакцию БД, consensus, долговременный журнал или дедупликацию. Код собственный; источники задают смысл и ограничения паттернов. LMX-фикстура заранее помещает зависимости и начальное состояние в фактический DATA владельца; входы с потенциальной неоднозначностью позиции передаются явно по имени. Например, account\debit(amount := 30). Листинги контролей рассчитаны на Python 3.10+, C# 12, Java 17 и Go 1.18+ там, где соответствующий язык присутствует.

## Каталог

### 011. [CQRS](011_cqrs_comparision.md)

Разделить модель команды и модель чтения.

**Сценарий:** WriteMessage принимает add(5). Пока событие не доставлено, ReadMessage возвращает 0. После доставки проекции она возвращает 5.

**Наблюдение:** Команда меняет write-state и отправляет snapshot=5; query до доставки даёт 0, после доставки — 5. Query не вызывает командный метод.

Все листинги показывают обработчики двух последовательных владельцев и порт доставки; runtime запуска/сеть не входят в длину. CQRS допускает синхронную проекцию, но здесь специально показано окно eventual consistency.

### 012. [Event Sourcing](012_event_sourcing_comparision.md)

Восстановить состояние из долговременной последовательности событий.

**Сценарий:** Журнал содержит дельты 100,20,-5. Восстановить баланс, затем добавить 10 с ожидаемой версией 3 и восстановить заново.

**Наблюдение:** Баланс 115, затем 125. Append со старой версией отвергается; replay не отправляет повторные внешние платежи.

Во всех языках состояние является результатом одного fold над журналом. Message сериализует собственные обращения, а version check защищает журнал и от других клиентов.

### 041. [Saga](041_saga_comparision.md)

Координировать локальные действия и явную компенсацию при отказе.

**Сценарий:** Заказ посылает Reserve, получает Reserved(true), посылает Charge, получает Charged(false), посылает Release и получает Released(true). Повторить каждый ответ.

**Наблюдение:** Состояния 0→1→2→3→4; действия reserve,charge,release,failed выполняются по одному разу. Дубликаты уже обработанных фаз не порождают действия. Успешный Charge переводит в 5 и даёт done.

Во всех трёх листингах одинаковый конечный автомат, работающий в последовательной полосе владельца. Компенсация — отдельное бизнес-действие, а не автоматический rollback графа или distributed transaction.

### 048. [Transactional Outbox](048_transactional_outbox_comparision.md)

Сохранить бизнес-изменение и исходящее событие одной локальной транзакцией.

**Сценарий:** Команда меняет счёт 7 на 120 и создаёт событие id=51. Relay отправляет событие; в контрольном сбое процесс падает после publish и до markSent.

**Наблюдение:** При rollback нет ни изменения, ни outbox-строки. После commit оба существуют. После контрольного сбоя relay повторно отправляет id=51: потребитель должен уметь подавить дубль.

Все версии явно делают запись в outbox до commit и markSent после публикации. Сама по себе очередь исходящих Message в конце turn не равна durable outbox БД.

### 050. [Materialized View](050_materialized_view_comparision.md)

Поддерживать заранее вычисленную проекцию для дешёвого чтения.

**Сценарий:** ProjectionMessage получает события (seq=1,delta=10),(2,5),дубль (2,5), затем ошибочный пропуск (4,9). Прочитать total.

**Наблюдение:** total=15,last=2. Дубль игнорируется. Пропуск последовательности выдаёт Gap до изменения состояния.

Все три варианта хранят сумму и checkpoint отдельно от источника событий. Дедупликация здесь корректна для одного упорядоченного непрерывного потока.

### 051. [Sharding](051_sharding_comparision.md)

Направлять ключи в выбранные горизонтальные разделы хранилища.

**Сценарий:** Три шарда. Для неотрицательных customerId 7,8,9 вычислить shard=customerId%3 и передать get в соответствующий endpoint.

**Наблюдение:** Ключи идут в шарды 1,2,0. Повторный ключ всегда выбирает тот же shard при неизменном наборе.

Каждый язык вычисляет одну и ту же функцию маршрутизации и вызывает порт. В LMX шарды — отдельные Message/сервисы с независимым состоянием.

### 055. [Leader Election](055_leader_election_comparision.md)

Получить подтверждённое право лидера и защитить ресурс от старого владельца.

**Сценарий:** A получает lease/token=10, B временно не получает. После потери lease B получает 11. Задержавшаяся работа A с 10 пытается записать в ресурс.

**Наблюдение:** Текущий B может записать с 11; запись A с 10 отвергается ресурсом. acquire возвращает 0 при отсутствии лидерства, тогда работа не запускается.

Листинги сравнивают клиентский протокол использования избранного лидера, а не реализации Raft/Paxos. Java и Go получают те же контракты. etcd Election/Lease — пример возможной инфраструктуры, не неявная зависимость LMX.

### 057. [Claim Check](057_claim_check_comparision.md)

Передать ссылку-квитанцию на большие данные, сохранив сами данные отдельно.

**Сценарий:** Сохранить ASCII payload длиной 10000 и послать только ticket(key,length). Получатель проверяет полномочия своего store-порта, читает blob и сравнивает длину.

**Наблюдение:** Через очередь/HTTP идёт маленький DTO из двух чисел; обработчик получает исходный payload длиной 10000. Несовпадение длины выдаёт Payload.

Во всех вариантах сначала завершается сохранение blob, затем публикуется ticket. Это согласуется с LMX HTTP-профилем, допускающим cursor/range для большого тела.

### 086. [Idempotent Consumer / Transactional Inbox](086_idempotent_consumer_inbox_comparision.md)

Подавить повторное бизнес-действие по устойчивому идентификатору доставки.

**Сценарий:** Дважды доставить subscriber=7,event=51,delta=5 при исходном balance=100. Первый commit проходит, но ACK теряется, поэтому broker повторяет доставку.

**Наблюдение:** После обеих доставок balance=105 и ровно одна inbox-запись (7,51). Обе успешные обработки могут ACK. При сбое транзакции ни метка, ни изменение не остаются, ACK не посылается.

Все варианты связывают durable marker с бизнес-изменением одной транзакцией. Обычный set в памяти годится для окна жизни одного процесса, но не эквивалентен transactional inbox после рестарта.
