# Технические уточнения автора — 2026-11-07

## Вычисляемый дефолт формала: момент вычисления

Источник: ответ автора в чате Codex 2026-11-07 на вопрос, который Codex задал по вопросу Opus о формах дефолта
(срез 297, FORMAL-DEFAULT-FORMS); передан Opus сообщением CODEX-OPUS-DEFAULT-TIMING-AUTHOR-20261107-01. Вопрос
Codex автору (не слова автора):

> Как должно работать вычисляемое умолчание fn: f (int: a make_default()) int, если make_default() меняет счётчик?
> Книга говорит, что сигнатура не исполняется, но не определяет момент вычисления такого умолчания. Нужно выбрать
> правило языка; остальные работы продолжаются

Выбранный автором ответ, дословно:

```text
Вычислять при каждом вызове f без аргумента a
```

Следствия, которые Codex назвал при передаче (не слова автора): построение описания `f` не выполняет
`make_default()`; каждый достигнутый вызов `f` с пропущенным `a` вычисляет дефолт для своей активации один раз, с
обычными эффектами и допуском результата; явно поданный `a`, в том числе 0, дефолт не вычисляет, неподходящий явный
аргумент дефолтом не заменяется; первое вычисление не кэшируется, остаток рабочей ячейки прошлого вызова дефолтом не
становится; источник берётся у фактически выбранного callable. Книга: [вызываемые выражения, дефолт формала](../docs/LMX_semantics.ru.md#callables).

## Порядок аргументов вызова и проверка его формы

Источник: ответ автора в чате Codex 2026-11-07 на два вопроса, которые Codex задал по вопросу Opus (срез 301,
CALLABLE-PLACE-TYPED-RECEPTION); передан Opus сообщением CODEX-OPUS-301-AUTHOR-ORDER-SHAPE-20261107-01. Вопросы в
передаче Codex (сообщение CODEX-OPUS-301-PARTIAL-ORDER-ROUTES-20261107-01; не слова автора): (а) ABXY — все
фактические, затем преобразования, либо AXBY — каждый фактический сразу с преобразованием, едино для обычного вызова
и изменяемого callable-места; (б) при отсутствии именованного параметра x у выбранного callable должен ли
`f(x: touch())` выполнить `touch` перед отказом `call`.

Выдержка из ответа автора (технический фрагмент; фраза о передаче и продолжении работы опущена), дословно:

```text
Каждый аргумент сразу преобразуется, затем вычисляется следующий. Имена и форму вызова проверять до вычисления аргументов.
```

Следствия, которые Codex назвал при передаче (не слова автора): выбран AXBY — фактический вычисляется и сразу
принимается с необходимым преобразованием, затем вычисляется следующий; правило едино для обычного вызова и вызова
через изменяемое callable-место, для native и обходчика; отказ вычисления или приёма текущего аргумента — следующие
не вычисляются, тело вызываемого не начинается; выбор callable — один раз, до фактических. Имена и форма проверяются
по фактически выбранному callable до эффектов аргументов: `f(x: touch())` без формала x отказывает без `touch()`;
соответствие имён и позиций, повторная подача одного формала и наличие обязательных входов с учётом умолчаний — на
этой стадии; это проверка достигнутого вызова, не анализ будущих тел; преобразования значений до вычисления этих
значений не исполняются; вычисляемое умолчание по-прежнему вычисляется при каждом вызове без аргумента. Книга:
[вызываемые выражения](../docs/LMX_semantics.ru.md#callables).

## Именованная подача аргументов, `merge` и оператор `:=`

Источник: сообщения автора в чате Codex 2026-11-07, переданные Opus сообщениями
CODEX-OPUS-AUTHOR-NAMED-MERGE-ASSIGN-DISCUSS-20261107-01, CODEX-OPUS-NAMED-COLLISION-SOURCE-20261107-01,
CODEX-OPUS-AUTHOR-NO-COLON-NAMED-BINDING-20261107-01 и CODEX-OPUS-AUTHOR-DOCUMENT-ASSIGN-MERGE-PARENS-20261107-01.
Четыре отдельных сообщения автора, по порядку. Первое автор открыл как предложение для обсуждения; четвёртое поручает
внести оператор `:=` и пример с `merge` в документацию.

Первое сообщение, дословно:

```text
давай 
1)обсудим вопрос именования аргументов при вызове. Там наверняка либо не реализовано либо реализовано неправильно или наполовину. 
fn: test (c: D; a: int)
Если есть callable "a" или "c" то их вызовы будут смешиваться с именованием аргумента
Можно было сделать это с merge
test(merge(test\args; a: int: 5)) #вызов с одной только структурой как ты помнишь у нас не отличается от вызова с цепочкой аругментов
2) проверим что test(merge(test\args; a: int: 5))  автоматически уже работает . 
3) обсудим оператор ":=" для красоты, который много выше по чату и планировалось обсудить после того как модель операций будет причёсана. У нас появился один случай с именованными аргументами (эот самый выше) который хотелось бы записать короче и ещё один случай который тоже хотелось бы записать короче -- присваивание указателя на метод. 
Поэтому моё предложение такое:
3.1)вызовы вообще, и всех ресиверов в частности, оставить как есть, то есть все предыдущие формы
3.2) случаи, когда левая часть неизвестна, остаются определениями новой структуры -- как сейчас есть
3.3) проверку "соответствия типов" перевести на implements (с его таблицей преобразования) при всех переопределениях, переопределения оставить разрешенными
3.4) для переопределения уже известного добавить дополнительный оператор ":=" который будет выдавать ошибку для неизвестного, а для известного: 
3.4.1) делать попытку переопределения любого уже известного значения, в том числе указателя на метод (указатель на метод у нас не должен отличаться от ссылки на структуру метода)
3.4.2) употребление в структуре аргументов callable будет считать именованным вызывом:
test(a:=5)
```

Второе сообщение — вопрос автора к объяснению Codex; строка в кавычках — слова Codex, которые автор цитирует.
Дословно:

```text
"В грамматике нашёл важное различие: она снимает оболочку единственной анонимной структуры, записанной прямо в вызове" -- но если снимает то и с результата merge должна снять?
```

Третье сообщение — уточнение автора после находки Codex в исходниках frontend; строка в кавычках — слова Codex,
которые автор цитирует. Дословно:

```text
"Наличие callable с тем же именем он при этом не проверяет — под это условие попадает и `a(5)`  " -- ну это вроде не совсем правильно так как если есть функция "a" то мы не сможем ее вызвать, надо именованное связывание поменять убрав это, а: 5 не должно быть именованными связыванием, то есть тот вариант что сейчас обсуждаем
```

Четвёртое сообщение, дословно:

```text
и внеси в документацию новый оператор " := " и еще один пример с merge.Только проверьте сначала - какжется надо написать `test(merge(test\args; (a: int: 5)))`  # три скобки потому что "a" должно попасть внутрь
```

Пояснения Codex при передаче (не слова автора): из указанной автором эквивалентности вызова с одной Structure и
вызова с цепочкой аргументов следует приём результата `merge` как всей структуры аргументов; узкое снятие оболочки в
P0 не основание отвергать вычисленный случай. Совпадение головы Frame с именем формала не даёт права считать обычный
Frame именованной подачей: при видимом callable `a` формы `a(5)` и `a: 5` — его обычный вызов и результат; при
неизвестной голове — обычное определение Structure, при иной известной — её общий контракт. Именованная подача явная —
`test(a := 5)`: слева выбирается формал выбранного callable, правая часть вычисляется обычным образом, так что
`test(a := a(5))` отличает целевой формал от обычного вызова справа. Норма `:=` — пункты 3.1–3.4.2 первого сообщения
с третьим: прежние формы вызова ресиверов сохраняются; неизвестная левая часть `:` по-прежнему определяет Structure;
переопределение разрешено с общим допуском `implements` и его преобразованиями (отдельный прежний запрет смены типа
автору не приписывается); `:=` пытается записать существующее известное значение или место, в том числе ссылку на
метод, а неизвестная левая часть — ошибка. В примере внутренние скобки образуют Structure с полем `a`. Ассоциативность
`:=`, значение записи и снятие уровней `@` автор не определял. Имя `test` — слово языка (ресивер `test:`), программа его
не связывает, поэтому примеры документации используют `mytest`. Проверка автора «проверьте сначала» выполнена на
опубликованном кортеже 301 ([запись](../steps/witnesses/named-assign-20261107/notes.md)). Книга:
[запись в известное место](../docs/LMX_semantics.ru.md#assign-known),
[именованная подача](../docs/LMX_semantics.ru.md#named-actuals).

## Оператор `:=` — общий

Источник: уточнение автора в чате Codex 2026-11-07 после поручения довести `:=` и пример с `merge` до работы; передано
Opus сообщением CODEX-OPUS-AUTHOR-ASSIGN-GENERAL-KNOWN-20261107-01. Дословно:

```text
ну и не забудб что ":=" это теперь общий оператор с узкой функцией присваивания известному
```

Пояснение Codex при передаче (не слова автора): `:=` — общий оператор присваивания уже известному месту или значению;
неизвестная левая часть получает ошибку, нового определения он не создаёт; это не особый синтаксис именованных
аргументов — именованная подача есть применение этого оператора к известному формалу в структуре аргументов выбранного
callable; общая запись в известное место, в том числе в место со ссылкой на Structure метода, проходит принятый
`implements` с преобразованием, голый callable справа не вызывается; приоритет, ассоциативность, значение записи и неявное
разыменование уточнением не задаются. Книга: [запись в известное место](../docs/LMX_semantics.ru.md#assign-known).

## Прежняя функциональность сохраняется

Источник: уточнение автора в чате Codex 2026-11-07; передано Opus сообщением
CODEX-OPUS-AUTHOR-ASSIGN-PRESERVE-EXISTING-20261107-01. Дословно:

```text
Вся прежняя функциональность за исключения багфикса с именованными аргументами -- остаётся
```

Пояснение Codex при передаче (не слова автора): это ограничение объёма изменения — общий оператор `:=` добавляется к
существующим формам; прежние вызовы, формы ресиверов, определения и прежние способы присваивания и переопределения
сохраняются, массового перехода на `:=` нет; исключение — исправление NAMED-BINDING-BY-HEAD: обычные `a(5)` и `a: 5` не
поглощаются как именованная подача из-за совпадения головы с формалом, явная именованная подача — `a := value`, ошибочный
перехват не сохраняется как обратная совместимость; прежние решения (допуск `implements` с преобразованием при записи,
ошибка неизвестной левой части `:=`, голый callable — не вызов, единственная Structure как вся структура аргументов)
остаются в силе.

## `:=` — более узкая форма

Источник: поправка автора в чате Codex 2026-11-07 к фразе Codex «:= остаётся дополнительной формой»; передано Opus

```text
`:=`   не просто дополнительная а более узкая. Мы ее не можем скопипастить в другое место где не объявление, для данных как код это важное свойство
```

Пояснение Codex при передаче (не слова автора): существенна более узкая семантика `:=` — оператор требует уже известное
левое место; перенесённая или скопированная исполняемая запись в контексте, где такого места нет, получает ошибку, а не
становится определением нового имени, так что намерение присваивания сохраняется при работе с данными как кодом;
неизвестная голова не расширяет смысл `:=` до общего поведения двоеточия; особой привязки адреса, нового правила захвата
или смены области видимости из реплики не следует. Книга: [запись в известное место](../docs/LMX_semantics.ru.md#assign-known).

## Составные присваивания и степень

Источник: прямое поручение автора в чате Codex 2026-11-07; передано fable_pc сообщением
CODEX-FABLE-AUTHOR-COMPOUND-POWER-DOCS-20261107T190048260Z-01 (явное поручение добавить операторы в документацию и
план, не пересылка обсуждения). Дословно, с разметкой автора:

```text
А добавь вдокументацию и в план такие операторы:



- := — присваивание уже существующей переменной
- **`+=`** — сложение с присваиванием (`a += b` эквивалентно `a = a + b`)
- **`-=`** — вычитание с присваиванием (`a -= b` эквивалентно `a = a - b`)
- **`*=`** — умножение с присваиванием (`a *= b` эквивалентно `a = a * b`)
- **`/=`** — деление с присваиванием (`a /= b` эквивалентно `a = a / b`)
- **`%=`** — остаток от деления с присваиванием (`a %= b` эквивалентно `a = a % b`)
- **`<<=`** — побитовый сдвиг влево с присваиванием (`a <<= b` эквивалентно `a = a << b`)
- **`>>=`** — побитовый сдвиг вправо с присваиванием (`a >>= b` эквивалентно `a = a >> b`)
- **`&=`** — побитовое И с присваиванием (`a &= b` эквивалентно `a = a & b`)
- **`^=`** — побитовое исключающее ИЛИ с присваиванием (`a ^= b` эквивалентно `a = a ^ b`)
- **`|=`** — побитовое включающее ИЛИ с присваиванием (`a |= b` эквивалентно `a = a | b`) [[1](https://en.cppreference.com/c/language/operator_assignment)]
- \*\*= — возведение в степень с присваиванием
- \*\* — возведение в степень для выражений
```

Пояснения Codex при передаче (не слова автора): в цитате сохранено авторское C-подобное `=`; в LMX эквиваленты
записываются через `:=` — `a += b` соответствует `a := (a + b)`, `a **= b` — `a := (a ** b)`; `=` в нынешней грамматике —
сравнение, и поручение его не переопределяет; `**` — степень, `^` остаётся побитовым исключающим ИЛИ; `:=` сохраняет
уже установленный общий узкий смысл записи известного места, включая ссылки на методы и именованную подачу, и новая
краткая формулировка не сужает его до чисел; ссылка автора на C поясняет перечень составных присваиваний и не является
источником правил LMX о приоритетах, ассоциативности, атомарности, допустимых типах или ошибках степени — такие детали
уточняются перед реализацией; табличная эквивалентность не должна молча превращаться в макроподстановку с повторными
эффектами левой части. Это задача документации и плана; код операторов не внедряется в уже собранный срез 302. Книга:
[составные присваивания и степень](../docs/LMX_semantics.ru.md#compound-assign).

## Ассоциативность и приоритет `**`

Источник: уточнение автора в чате Codex 2026-11-07 к поручению выше — вопрос, который Codex принял для текущей записи;
передано fable_pc сообщением CODEX-FABLE-AUTHOR-POWER-PYTHON-20261107T190238835Z-01. Дословно:

```text
ассоциативность ** и приоритет можно сделать как в Python?
```

Пояснения Codex при передаче (не слова автора): ассоциативность и приоритет `**` зафиксированы как в Python
(проверенный первичный источник — https://docs.python.org/3/reference/expressions.html#the-power-operator и
#operator-precedence): `**` группируется справа — `a ** b ** c` есть `a ** (b ** c)`; сильнее `*`, `/`, `%` и `+`, `-`;
обычные вызовы, индексация и доступ к полю образуют операнд раньше `**`; с общими унарными `+`, `-`, `~` — как в Python:
слева `**` связывает сильнее, справа допускается унарный операнд — `-2 ** 2` есть `-(2 ** 2)`, `(-2) ** 2` сохраняет
скобки, `2 ** -2` есть `2 ** (-2)`, `2 * 3 ** 2` есть `2 * (3 ** 2)`; правая сторона `**=` подчиняется той же группировке.
Правоассоциативность не означает вычислять эффектные операнды справа налево; числовые типы и преобразования,
отрицательная или дробная степень, ошибки и поведение `0 ** 0` из Python не копируются; смысл Python `:=` (walrus) и
иной общий синтаксис не переносятся; новых правил для унарных `@` и `\` не задано. Книга:
[составные присваивания и степень](../docs/LMX_semantics.ru.md#compound-assign).
