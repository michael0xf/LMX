# Q17. Имя неявного throw при отказе runtime `implements`

Состояние: 2026-09-23, открыт. Вопрос поднял Opus в дизайне S1 (`FABLE-OPUS-S1-THROWS-DESIGN-20260923-128`, точка X3); без ответа не фиксируется нумерация статусов S1 и не пишется `catch:` для этого случая. Ответить можно строкой `Q17 А`, `Q17 Б` или `Q17 В`.

## Контекст

По вашим ответам Q11–Q14 (`LMX_blog/2026-09-23.md`; план §3 «throws / catch (S1)» :210–:215): объявленные имена — в `throws:` в шапке метода, не отловленные и не перечисленные — ошибка трансляции; **неявные имена операторов** без видимого `throws` (сегодня `merge`, в т.ч. внутри `Model: fresh`) бросают, отлов не обязателен, неотловленные уходят в корень исполняющегося Message (`running = 0`, без результата, код выхода 1); `catch: merge` обрабатывает стандартно. Payload `throw` связывается с параметрами `catch` обычным присваиванием, верифицируемым стандартным runtime `implements` (Q12).

Одновременно по Q12/§7 транслятор в S3 (часть 2a, Opus) вводит runtime-admission для **нетипизированных графов**, приходящих в типизированное место: `nextMessage: m` в поле `Model: m`, перепривязка такого поля, аргумент типизированного формального параметра. Проверка — стандартный runtime `implements`; при отказе (граф не реализует объявленный тип) — «стандартный путь отказа admission». Сегодня в коде это три места с одним и тем же статус-возвратом, у которого нет имени.

Для S1 нужна одна нумерация статусов на метод: объявленные имена 1..d, затем неявные d+1… в фиксированном общем порядке (`merge` = 1, отказ admission = 2). Чтобы этот отказ можно было ловить `catch:`, у него должно быть **имя**; если он не ловится — это должно быть сказано явно.

## Минимальная программа

```
Model:
    size_t: value 1U
end: Model

Model: m
nextMessage: m
catch: ??? ()
    return: 7
return: 0
```

Письмо пришло с графом, который не реализует `Model` (нет поля `value` нужного типа). `nextMessage: m` — обычное присваивание с admission; admission отказывает.

## Варианты

- **А — `implements`**: имя неявного throw = имя оператора, который отказал, как у `merge`: `catch: implements ()`. Неявное имя №2 в общем порядке; отлов не обязателен; неотловленный — в корень Message (`running = 0`, код 1). Полностью симметрично `merge`.
- **Б — не ловится**: отказ admission — не throw, а инвариант исполнения (маршрут диагностики, как проверка checkpoint: stderr + остановка), `catch:` для него нет. Тогда программа выше — ошибка трансляции «неизвестное имя catch», а письмо с чужим графом останавливает поток без возможности обработать.
- **В — то же имя `merge`**: отказ admission бросает `merge` (admission = часть слияния значения в поле). Тогда `catch: merge` ловит оба случая и различить их нельзя.

## Следствия

- А: у каждого неявно бросающего оператора своё имя; список неявных имён — таблица транслятора (сегодня два: `merge`, `implements`); интерпретаторы — явное «unsupported» до своей реализации.
- Б: письмо с неподходящим графом невозможно обработать программно — только остановка потока; противоречит «`success=1` — пользовательское решение» лишь косвенно, но лишает `nextMessage:` штатной ветки отказа.
- В: одно имя на разные операторы; `catch: merge (x)` без payload (Opus рекомендует: у `merge` payload нет).
