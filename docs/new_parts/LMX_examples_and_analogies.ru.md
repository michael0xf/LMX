# LMX: примеры, Haskell-аналоги и обратные задачи

Редакция: 21 ноября 2026 года. Для Михаила и проверки реализации Fable.

Здесь собраны заново записанные примеры из обсуждения: функции высшего порядка, `makeAdder`, варианты `add5`, композиция, отложенное вычисление, состояние, обобщённость, код как граф, операнды, массивы, `implements`/`test`/`catch`, mock и интеграционная проверка, Message и обмен результатами. В конце — соответствие всем 23 шаблонам проектирования и прежнему регрессионному корпусу.

Это изложение текущей редакции языка. В частности, здесь уже действуют `copy` для одного принятого источника, потоковые результаты `copy`/`merge`/`import`, обычные CODE-аргументы этих трёх ресиверов и сохранение исходного графа. Старые формы с исполняемым `fn`, одноисточниковым копированием под именем `merge` и неявным захватом локального кадра не переносятся в новые листинги.

**Как читать проверки.** Числа после примеров — ожидаемые результаты, выведенные из действующих правил, для запуска Fable. Это не журнал исполнения LMX или GHC. Листинги с пометкой «самостоятельный пример» имеют все показанные пользовательские определения; ядро и явно оговорённый профиль предоставляет обычная среда. «Сценарий стенда» задаёт конкретные исходные данные, действия и проверяемый результат там, где проверяется физическая идентичность, транспорт или окружение Message. Такая запись не вводит новый синтаксис языка.

Последнее имеет приоритет в этих вопросах. [Редакция 2 про потоки полей](newdocs/TZ/LMX_Fable_TZ_Import_Copy_Merge_Field_Streams_2026-11-21.md) уточняет предыдущие ТЗ по своему предмету. Подробные правила находятся в [семантике](newdocs/LMX_semantics.en.md), [грамматике](newdocs/LMX_grammar.en.md) и [L2](newdocs/L2_spec_en.md). Папка `Old_TZ` содержит [действующие принятые дополнения](newdocs/README.md#accepted-supplements), а не набор альтернативных версий.

Упоминания Haskell опираются на [Haskell 2010 Report: выражения](https://www.haskell.org/onlinereport/haskell2010/haskellch3.html), [типы и объявления](https://www.haskell.org/onlinereport/haskell2010/haskellch4.html), [I/O](https://www.haskell.org/onlinereport/haskell2010/haskellch7.html) и [Data.Array](https://www.haskell.org/onlinereport/haskell2010/haskellch14.html). Примеры ниже написаны для этого сравнения. Haskell-код показывает наблюдаемое поведение; он не объявляется представлением внутреннего устройства LMX.

### 1.2. Шесть правил, которые существенно меняют чтение

| Запись или понятие | Текущее значение |
| --- | --- |
| `Context: ... method: ...` | `method` — обычная Structure. При её вызове DATA берётся из её фактического `parent`, здесь `Context` |
| `fn: Unary (int: x; return: int)` | Именованное описание позиционной сигнатуры; исполняемого тела здесь нет |
| `@: p Context\method` | Ссылка на существующую Structure без вызова; `p(...)` — отдельный вызов |
| `copy(A)` / `merge(A B)` | Потоки скопированных / объединённых полей. Один структурный результат записывается `(copy(A))` / `(merge(A B))` |
| Свободное `x` / `node\x` | У свободного имени участвует динамическое связывание. `node\` явно выбирает лексический источник; это не «подняться на одного родителя» |
| Присваивание локальному месту | Меняет значение текущей активации. Оно не заменяет своим результатом исходный инициализатор и не создаёт новое поле |

Основание: [вызовы и сигнатуры](newdocs/LMX_semantics.en.md#callables), [связывание](newdocs/LMX_semantics.en.md#binding-places), [активации](newdocs/LMX_semantics.en.md#call-frame-20261115), [потоки](newdocs/TZ/LMX_Fable_TZ_Import_Copy_Merge_Field_Streams_2026-11-21.md).

### 1.3. Почему здесь по-прежнему один граф

Чистый граф полностью отражает написанную программу: ресиверы, выражения, вложенные структуры, объявления, границы групп и конечные примитивные листья. Примитивный лист уже лежит в своём виде `{type value}` по адресу, на который указывает ячейка структуры `Lmx`. `for`, `if`, `merge`, `copy` и `import` сохраняются как написанные ресиверы вместе со своими аргументами. Их выполнение не заменяет эти записи вычисленными результатами.

Прочтение графа создаёт текущие значения и связи в namespace. Например, `int: i findValue()` сохраняет вычисляемое объявление; присваивание текущему `i` не превращает его исходный вызов в число. У неинициализированного примитива `{uninit_int}` размер value равен нулю: будущей ячейки `int` в нём нет. Явное присваивание графу заменяет выбранный фрагмент новым — например, `{uninit_int}` на `{int 5}`. Таким же способом можно заменить структуры, содержащие исполняемые ресиверы; для требуемого обновления машинного исполнения используется описанная компиляция и граница `endturn`. См. [уточнение автора](newdocs/TZ/LMX_Author_Clarification_Uninit_Graph_Assignment_2026-11-21.md) и R09–R10 ниже.

Namespace не требует ещё одной постоянной Structure со спрятанными полями программы. Это механизм текущего прочтения и связывания; native-исполнитель может держать обычные локальные значения в своём кадре и регистрах. Таким образом сохраняются и полный интерпретируемый код, и обычные локальные переменные, и возможность компиляции. Удаление протокола `load`/`dirty`/`flush` не означает повторного вычисления уже полученного локального значения при каждом чтении. См. [активации](newdocs/LMX_semantics.en.md#call-frame-20261115) и [действующее дополнение dirty](newdocs/Old_TZ/dirty.md).

Других скрытых частей программы к этому не добавляется. `parent` и `length` чистого графа определяются логически из исходника; содержимое структуры `Lmx` лежит в массиве указателей. Рядом находится бинарник с откомпилированными нативными методами — в нём только методы. R0 представляет собой обычный C-метод с **локальным указателем на граф R0**. Интерпретируемое исполнение тоже работает с бинарником и имеет бинарный R0. Это устройство не требует скрытых данных программы в C, отдельного callable-графа или иной модели корня для интерпретатора. [Основание](newdocs/TZ/LMX_Author_Clarification_Uninit_Graph_Assignment_2026-11-21.md#graph-and-methods-binary).

**Удаление рабочего графа — требование № 1.** Оно относится и к устройству реализации: нельзя восстановить второй граф программы под именем namespace, развёртки, временной копии исполняемого тела или скрытого набора данных. Локальное значение в кадре не требует копии исходного узла; временность второй копии программы тоже не делает её допустимой. Явный `copy`, написанный самим приложением, сохраняет свой обычный смысл и не оправдывает автоматическое создание рабочего графа на каждом входе. [Основание](newdocs/TZ/LMX_Author_Clarification_Uninit_Graph_Assignment_2026-11-21.md#no-working-graph).

Например, `private:` уже присутствует в чистом графе. Интерпретатор определяет его действие по этой записи, транслятор учитывает её в генерируемом методе. Отдельный граф меток `private` в бинарнике был бы возвращением рабочего графа. Полнота исходного графа проверяется в том числе этим простым случаем. [Основание](newdocs/TZ/LMX_Author_Clarification_Uninit_Graph_Assignment_2026-11-21.md#private-without-marked-graph).

В листингах пустая физическая строка завершает корневой блок. Внутри продолжающейся структуры используются допустимые отступы и, при необходимости, `---`. Внешние вызовы в пояснении — точки входа стенда; они не задают новую семантику запуска R0.

## 2. Haskell → LMX

<a id="h01"></a>
### H01. `apply`: передать действие и вызвать его

Haskell:

```haskell
apply :: (Int -> Int) -> Int -> Int
apply f x = f x

twice :: Int -> Int
twice x = x * 2

-- apply twice 7 == 14
```

Самостоятельный LMX-пример:

<!-- example: H01 -->
```lmx
Arithmetic:
    int: value
    return: int
    twice:
        return: value * 2
    plusOne:
        return: value + 1

Application:
    @: operation
    int: value
    return: int
    apply:
        return: operation(value)

ApplyProbe:
    return: int
    run:
        @: chosen Arithmetic\twice
        int: first Application\apply(chosen; 7)
        chosen := Arithmetic\plusOne
        int: second Application\apply(chosen; 7)
        return: first * 100 + second
```

`ApplyProbe\run()` → **1408**, то есть `14` и `8`. Присваивание `chosen` заменяет ссылку, не вызывает действие. DATA выбранного метода остаётся `Arithmetic`; размещение ссылки в `Application` этого не меняет. Внешний `apply` имеет собственные входы `operation` и `value`, а внутренний вызов явно передаёт одно число.

Это практический аналог функции высшего порядка. Для него не требуется объявлять отдельный `fn`, как и отдельный класс-обёртку. Именованная сигнатура нужна, когда её ограничение входит в задачу. [Основание](newdocs/LMX_semantics.en.md#call-receivers).

<a id="h02"></a>
### H02. Сигнатура, имена аргументов и тело — разные части

Самостоятельный пример:

<!-- example: H02 -->
```lmx
fn: PairOperation (int: a; int: b; return: int)

Candidate:
    int: b
    int: a
    return: int
    encode:
        return: b * 10 + a

SignatureProbe:
    return: int
    run:
        @: selected PairOperation Candidate\encode
        int: throughSignature selected(a := 2; b := 7)
        int: directly Candidate\encode(a := 2; b := 7)
        return: throughSignature * 100 + directly
```

`SignatureProbe\run()` → **2772**. Через сигнатуру внешнее `a` обозначает первую позицию, то есть собственное `b` кандидата. Прямой вызов использует имена кандидата. Проверка `fn` сопоставляет порядок и типы входов и результат; она не переставляет входы по совпадающим именам.

Haskell-аналог позиционного контракта — `Int -> Int -> Int`. Имена параметров реализации не входят в этот тип. В LMX именованная передача дополнительно делает публичные имена сигнатуры наблюдаемыми. Из одинаковой сигнатуры не следует равенство `x + 1` и `x * 2`; значения проверяются обычным вызовом или `test`.

Дополнительные проверки: поменять местами разные типы — отказ сигнатуры; поменять только имена — позиционное соответствие сохраняется; заменить default в описании `fn` — default кандидата не меняется. [Основание](newdocs/LMX_semantics.en.md#fn-signature); подробные B-10–B-12 и T02 находятся в [корпусе](LMX_regression_examples.to_fable.en.md#binding).

<a id="h03"></a>
### H03. `makeAdder`: вернуть метод вместе с нужным ему лексическим состоянием

Именно этот результат был в обсуждении:

```haskell
makeAdder :: Int -> (Int -> Int)
makeAdder n = \x -> n + x

closureExample :: (Int, Int, Int)
closureExample =
  let add5 = makeAdder 5
      add100 = makeAdder 100
  in (add5 1, add100 1, add5 1)
-- (6,101,6)
```

В текущем LMX значение сохраняется явно в копии. Здесь фабрика даже не меняет общий прототип:

<!-- example: H03 -->
```lmx
AdderPrototype:
    int: saved 0
    inputs:
        int: x
        return: int
        add:
            return: x + node\saved

AdderFactory:
    int: increment
    return: @
    create:
        @: instance (copy(AdderPrototype))
        @: lexicalOwner parent(instance\inputs)
        lexicalOwner\saved := increment
        return: instance\inputs\add

ClosureProbe:
    return: int
    run:
        @: add5 AdderFactory\create(5)
        @: add100 AdderFactory\create(100)
        int: saved 1000
        int: first add5(1)
        int: second add100(1)
        int: again add5(1)
        return: first * 1000000 + second * 1000 + again
```

`ClosureProbe\run()` → **6101006**, кодировка `(6, 101, 6)`. Исходный `AdderPrototype\saved` остаётся `0`. Обе фабричные активации закончились, но возвращённые методы имеют свои скопированные лексические связи. Локальное `saved = 1000` у проверяющего не переопределяет `node\saved`.

Копия не извлекала `increment` из исчезающего кадра: значение попало в нужную ветвь через явно написанное `lexicalOwner\saved := increment`. Владелец выбран как фактический родитель скопированной `inputs`. Внешняя группа `(copy(...))` собирает поток полей в отдельный контейнер со своими ячейками. Они отличаются от ячеек скопированного лексического корня. Замена её ячейки `saved` меняет именно эту ячейку и не меняет ячейку в лексическом корне. Возвращается ссылка на метод графа, а не адрес локальной переменной `instance`. Сохраняется нужное лексическое окружение по общей карте глубокого копирования; специально упаковывать весь кадр вызова не требуется.

`add5(1; saved := 25)` здесь **отклоняется**: `saved` не является входом DATA `inputs`. Это отличает пример от следующего. [Основание](newdocs/LMX_semantics.en.md#composition); [возвращаемые методы](newdocs/LMX_semantics_guide.en.md#factory-result).

<a id="h04"></a>
### H04. Другой `add5`: настоящий default, который можно переопределить

<!-- example: H04 -->
```lmx
Addition:
    int: x
    int: y
    return: int
    add:
        return: x + y

DefaultProbe:
    return: int
    run:
        int: y 100
        @: fiveContext (merge(Addition; (int: y 5)))
        @: add5 fiveContext\add
        int: first add5(1)
        int: explicit add5(1; y := 25)
        int: zero add5(1; y := 0)
        int: again add5(1)
        return: first * 1000000 + explicit * 10000 + zero * 100 + again
```

`DefaultProbe\run()` → **6260106**, кодировка `(6, 26, 1, 6)`. Готовый default `5` имеет приоритет над одноимённой локалью вызывающего. Явный `25` переопределяет его в данном вызове; `0` — такое же явно переданное значение. После вызова default остаётся `5`.

Haskell-выражение `add 5`, где `add x y = x + y`, частично применяет функцию и оставляет один параметр. У него нельзя затем «переопределить связанный аргумент по имени». Для точного поведения LMX можно написать явную модель выбора:

```haskell
addWithDefault :: Int -> Maybe Int -> Int
addWithDefault x supplied = x + maybe 5 id supplied

-- map (addWithDefault 1) [Nothing, Just 25, Just 0, Nothing]
-- [6,26,1,6]
```

Это не предлагаемая замена LMX-default на `Maybe`. Это обратный перевод его наблюдаемого поведения. Формальный вход остаётся в интерфейсе, потому что `merge` меняет значение поля модели, а не удаляет позицию. [Основание](newdocs/LMX_semantics.en.md#binding-autofill), [model slots](newdocs/LMX_semantics.en.md#composition).

<a id="h05"></a>
### H05. Третий случай: свободное имя остаётся динамическим после копирования

<!-- example: H05 -->
```lmx
Source:
    int: y 5
    methods:
        int: x
        return: int
        dynamic:
            return: x + y
        lexical:
            return: x + node\y

BindingProbe:
    return: int
    run:
        @: copied (copy(Source))
        Source\y := 8
        int: y 25
        int: a copied\methods\dynamic(1)
        int: b copied\methods\lexical(1)
        return: a * 100 + b
```

На свежем источнике результат — **2606**: динамический вариант получает `25`, лексический — скопированное `5`. Оригинал уже содержит `8`. `copy` не отключает динамический приоритет; `merge` также не вводит особого связывания.

У динамического метода `y` свободно, поэтому `dynamic(1; y := 25)` не превращается в допустимую явную передачу несуществующего формала. Оно может прийти обычным динамическим связыванием, но это другой механизм.

Удобная Haskell-модель такого динамического источника — явно передаваемое окружение `Env -> Int -> Int`; для лексического варианта — функция, созданная с конкретным `Env`. Это способ представить зависимость, а не утверждение, что Haskell сам использует неявное динамическое связывание. [Основание](newdocs/LMX_semantics.en.md#binding-caller-place).

<a id="h06"></a>
### H06. Композиция функций и композиция структур

Haskell:

```haskell
-- ((+1) . (*2)) 4 == 9
-- ((*2) . (+1)) 4 == 10
```

LMX, самостоятельный пример:

<!-- example: H06 -->
```lmx
Functions:
    int: x
    return: int
    twice:
        return: x * 2
    next:
        return: x + 1

Composition:
    @: outer
    @: inner
    int: value
    return: int
    apply:
        return: outer(inner(value))

CompositionProbe:
    return: int
    run:
        int: a Composition\apply(Functions\next; Functions\twice; 4)
        int: b Composition\apply(Functions\twice; Functions\next; 4)
        return: a * 100 + b
```

Результат **910**. Порядок вызовов задан зависимостью значений. Это функциональная композиция. `merge` выполняет другую работу: получает структуры, совмещает соответствующие поля и копирует нужные связи. Полученную структуру можно затем исполнять; сам `merge` не означает ни `outer(inner(x))`, ни последовательное выполнение всех методов.

Контроль: счётчики у `inner` и `outer` должны увеличиться по одному на каждый `apply`; перестановка ссылок меняет результат с `9` на `10`. [Основание](newdocs/LMX_semantics.en.md#assignment-inside-expression), [композиция графа](newdocs/LMX_semantics.en.md#composition).

<a id="h07"></a>
### H07. Значение, отложенное действие и исходное выражение

В Haskell `let x = expensive in x + x` обозначает разделяемую зависимость от `x`; `let action = readSensor in action >> action` по-прежнему задаёт два исполнения действия. Функция, значение, исходное выражение и thunk не становятся одним понятием только из-за отложенности. Нестрогость Haskell и порядок `IO` рассматриваются отдельно в [описании выражений](https://www.haskell.org/onlinereport/haskell2010/haskellch3.html) и [I/O](https://www.haskell.org/onlinereport/haskell2010/haskellch7.html).

LMX различает подготовленные значения операнда и исходные occurrences явно:

<!-- example: H07 -->
```lmx
Meter:
    int: calls 0
    return: int
    next:
        node\calls += 1
        return: node\calls

PreparedOps:
    @: left int
    []: @(int) right
    const: int: PASS_ARGS_AS_IS 0
    const: int: PRIORITY sys\priority("+")
    return: int
    twice:
        return: \left + \left

RawOps:
    @: left
    []: @ right
    const: int: PASS_ARGS_AS_IS 1
    const: int: PRIORITY sys\priority("+")
    return: int
    twice:
        int: first sys\eval(left)
        int: second sys\eval(left)
        return: first + second

Evaluation:
    return: int
    prepared:
        import: PreparedOps
        return: (Meter\next() twice 0)
    raw:
        import: RawOps
        return: (Meter\next() twice 0)
```

| Два последовательных вызова; перед каждой серией `Meter\calls := 0` | Результаты | Всего вызовов `next` |
| --- | --- | ---: |
| `Evaluation\prepared()` | `2`, `4` | 2 |
| `Evaluation\raw()` | `3`, `7` | 4 |

В первом случае два чтения используют одно полученное значение. Во втором два явных `sys\eval` исполняют одну исходную форму дважды в её сохранённом контексте. Простое разыменование ссылки не является `eval`. Ни одна серия не записывает вычисленное число вместо выражения в исходный граф.

Это проверяется числом эффектов, а не только арифметикой. Нельзя оптимизировать raw-вариант до одного вызова, если его эффект наблюдаем. [Основание](newdocs/LMX_semantics.en.md#operand-receiver), [исходные occurrences](newdocs/LMX_semantics.en.md#raw-operands).

<a id="h08"></a>
### H08. Состояние и вложенное действие без результата

<!-- example: H08 -->
```lmx
Own:
    int: y
    step:
        y += 3

Free:
    step:
        y += 3

StateProbe:
    return: int
    ownCopy:
        int: y 0
        Own\step()
        return: y
    callerPlace:
        int: y 0
        Free\step()
        return: y
```

`StateProbe\ownCopy()` → **0**. Объявленный `Own.y` — собственное место вызова, первоначально заполненное копией `0`. `StateProbe\callerPlace()` → **3**. У `Free\step` собственного `y` нет, и текущая норма разрешает прозрачную связь со свободным именем в непосредственном вызывающем контексте.

Это существенное изменение относительно раннего обсуждения, где любое внешнее имя трактовалось как локальная копия. Сейчас надо учитывать наличие собственного объявления. `node\y` дополнительно обозначает явный лексический доступ и имеет свой смысл.

У Haskell чистый переход состояния можно записать `step y = y + 3` и передать новое значение дальше. Действие с общей изменяемой ячейкой потребует явно выбранного механизма состояния, например `IORef` внутри `IO`. LMX допускает обе организации, но точное место записи определяется его правилами связывания.

Дополнительный отрицательный случай: внутри той же активации создать новое `int: y` без RHS во вложенном inline-блоке. Оно затеняет внешнее `y`, но не создаёт нового caller; при отсутствии `y` у реального caller новое место остаётся `uninit:int`. `required: y` должно обнаружить это, внешнее значение не меняется. [Основание](newdocs/LMX_semantics.en.md#shadowing-levels).

<a id="h09"></a>
### H09. Итератор, генератор и передаваемое объявление

Haskell-результат:

```haskell
iteratorExample :: Int
iteratorExample = sum (map (*2) [1,2,3])
-- 12

finitePrefix :: Int
finitePrefix = sum (take 3 (map (*2) [1..]))
-- 12
```

LMX использует переданное объявление шага и обычное тело:

<!-- example: H09 -->
```lmx
Numbers:
    int: position 0
    return: int
    next:
        throws: Stop
        if: node\position >= 3
            throw: Stop()
        node\position += 1
        return: node\position
    demo:
        node\position := 0
        int: total 0
        Cycles\iterate: int: item Numbers\next()
            item *= 2
            total += item
        return: total

Cycles:
    @: iteration
    @: body
    iterate:
        while: 1
            iteration()
            catch: Stop ()
                break
            body()
```

`Numbers\demo()` → **12**. `next` вызывается четыре раза: три значения и один `Stop`. Тело исполняется три раза. Форма `int: item Numbers\next()` сохранена; очередной шаг исполняет её в принимающем корневом namespace, а тело использует полученное место `item`. Повторного вычисления инициализатора только ради входа в тело нет.

Нулевой элемент тоже является элементом, а не концом потока. Отдельная серия `−2, 0, 4, Stop`, где тело прибавляет `3` и дважды читает `item`, даёт **22**, три исполнения тела и четыре вызова шага. Это D-01 из [корпуса](LMX_regression_examples.to_fable.en.md).

Haskell-список `[1..]` и этот stateful-итератор дают одинаковый конечный префикс, но организуют хранение и продвижение различно. Повторное чтение уже полученного элемента LMX не должно неявно вызывать следующий шаг. [Основание](newdocs/LMX_semantics.en.md#declaration-arguments); [полное сравнение Iterator](01_iterator_comparison.md).

<a id="h10"></a>
### H10. Обобщённость и стабильные типовые связи

Haskell:

```haskell
identity :: a -> a
identity x = x

double :: Num a => a -> a
double x = x + x
```

Здесь `a` — переменная полиморфного типа; отдельные употребления могут получать разные допустимые типы. У LMX структурная обобщённость часто означает, что потребитель требует только используемые им поля и операции. Отдельное символическое имя типа, если оно используется для связи нескольких позиций, фиксируется **на Message**, а не заново на каждом вызове. Это разные правила, и перевод `a -> a` одной строкой без контекста был бы неточным. [Haskell: типы](https://www.haskell.org/onlinereport/haskell2010/haskellch4.html); [LMX: контекст Message](newdocs/LMX_semantics.en.md#conversion-context).

Конкретный сценарий стенда:

| Подготовка | Проверка |
| --- | --- |
| Message A явно получает связь `a → int` | Все входные и выходные употребления `a` в A используют эту связь |
| Два вызова в A пытаются трактовать `a` по-разному | Второй вызов не создаёт независимую новую инстанциацию `a` |
| Message B явно получает `a → Array<char>` | B имеет свою согласованную связь |
| В B не передали таблицу A | Родство или доставка письма не устанавливают её автоматически |

Для структурного потребителя, которому нужен только `x`, кандидат с полями `x, note, extra` допустим при соблюдении остальных требований. Если же явно передана полная модель с `x` и `check`, то наличие обоих требований обязательно, даже когда ближайшее тело читает лишь `x`. Физический порядок полей кандидата может отличаться: строится соответствие, а не копия в «правильном» порядке. Это T01/T03/T04/T07 английского корпуса.

<a id="h11"></a>
### H11. Обратный адаптер: `int → string → int`

Из старого обсуждения сохраняем задачу: вызвать действие над строкой через потребителя числа, если текущий контекст явно допускает нужные преобразования.

В Haskell маршрут виден в программе:

```haskell
appendOne :: String -> String
appendOne s = s ++ "1"

adapted :: Int -> Int
adapted = read . appendOne . show
-- adapted 10 == 101
```

Сценарий LMX: потребитель передаёт `int 10`; кандидат принимает строку, добавляет символ `1` и возвращает строку; результат потребителю нужен как `int`. В контексте Message заданы обе конкретные конверсии: десятичное число в текст и текст в число. Ожидается **101**. `implements` проверяет доступность и пригодность маршрутов без их исполнения; фактическое потребление исполняет каждую нужную конверсию отдельно.

Контрпримеры обязательны: нет обратной конверсии — нет скрытого поиска по процессу; результат `"10x"` — ошибка формата; значение за диапазоном назначения — ошибка диапазона. Этот пример не означает, что произвольные отличающиеся `fn`-контракты всегда взаимозаменяемы: сравнение конкретной сигнатуры и разрешённые конверсии подчиняются текущему требованию потребителя. [Основание](newdocs/LMX_semantics.en.md#descriptions), [конверсии при потреблении](newdocs/LMX_semantics.en.md#conversion-context).

<a id="h12"></a>
### H12. Варианты данных, чистота и эффекты

Haskell может выразить закрытые варианты непосредственно:

```haskell
data Event = Sample Int | Finished

eventValue :: Event -> Int
eventValue (Sample x) = x
eventValue Finished = 0
```

В LMX описания вариантов можно организовать обычными структурами и потребителями. Если профиль выбирает явные поля `kind` и `value`, он обязан проверить допустимые сочетания: само наличие двух числовых полей не устанавливает инвариант варианта. Если выбирает разные структурные требования и диспетчеризацию по ним, проверяются именно эти требования. Не следует называть любую пару полей автоматически алгебраическим типом Haskell; не следует и добавлять новый встроенный `enum` только для этого примера.

Аналогично, наличие `return: int` не доказывает чистоту тела. Оно может читать устройство или менять явно доступное состояние. Для чистого вычисления LMX применяет выбранный pure-профиль с допустимыми операциями; для эффекта — обычные правила действий и владения. В Haskell порядок I/O выражается композициями действий типа `IO a`. Эти контракты позволяют решать сходные задачи, но не являются одним и тем же правилом типизации. [LMX: чистые профили](newdocs/LMX_semantics.en.md#mathematics), [Haskell: I/O](https://www.haskell.org/onlinereport/haskell2010/haskellch7.html).

Действие LMX без описания результата не обязано возвращать скрытый `unit` или ACK. Это особенно заметно в Message: обычный процедурный вызов не становится запросом, который должен дождаться отсутствующего ответа.

<a id="lmx-to-haskell"></a>
## 3. Обратные аналоги: начать с возможности LMX

Здесь исходная задача задаётся LMX: взять структуру программы, прочитать её, скопировать, объединить, передать или исполнить. Затем рассматривается, как выразить ту же задачу средствами Haskell. Совпадение числового результата само по себе ещё не воспроизводит доступность графа и его связей.

<a id="r01"></a>
### R01. `merge` как композиция данных и поведения

<!-- example: R01 -->
```lmx
RecordModel:
    int: width 2
    int: height 3

RecordPatch:
    int: height 5
    int: depth 7

MergeProbe:
    return: int
    run:
        @: result (merge(RecordModel; RecordPatch))
        return: result\width * 100 + result\height * 10 + result\depth
```

Результат **257**. `height` занимает соответствующий слот модели с новым значением `5`; `depth` добавляется. Поля обоих источников не изменены. Вариант с подходящими методами использует тот же контракт копирования и связывания, а не особую операцию над классами.

Haskell может выразить обновление заранее известной записи:

```haskell
data Size = Size { width :: Int, height :: Int, depth :: Int }

recordExample :: Size
recordExample = (Size 2 3 0) { height = 5, depth = 7 }
```

Здесь поле `depth` заранее входит в `Size`. Чтобы добавлять произвольные именованные узлы вместе с исполняемым содержимым, потребуется выбранное представление данных: словарь, AST, граф или другая явная модель и её операции. Обычное значение типа `Int -> Int` само по себе не даёт API перечисления и замены внутренних узлов функции. Это граница рассматриваемого аналога, а не запрет решить задачу на Haskell. [Haskell: записи и объявления](https://www.haskell.org/onlinereport/haskell2010/haskellch4.html); [LMX: композиция](newdocs/LMX_semantics.en.md#composition).

Если затем приложение явно переназначит ссылку на `result`, оно будет использовать новую ветвь. Независимо сохранённая другая копия автоматически не обновится. «Изменение структуры» и «глобальная синхронизация всех когда-либо созданных копий» — разные обязательства.

<a id="r02"></a>
### R02. Поток полей, группировка и W/E

Самостоятельный пример группового присваивания:

<!-- example: R02 -->
```lmx
Pair:
    int: first 2
    int: second 7

StreamProbe:
    return: int
    run:
        int: a 0
        int: b 0
        (a b) := copy(Pair)
        return: a * 10 + b
```

Результат **27**. Вход `copy` один, выходных полей два. Имена `first/second` справа не переставляют соответствие `a/b`: присваивание позиционное. Все правые значения читаются до первой записи.

| Форма | Что получает окружающий потребитель |
| --- | --- |
| `copy(Pair)` | Два поля потоком |
| `(copy(Pair))` | Одна явно собранная Structure с двумя полями |
| `f(copy(Pair))` | Поток на границе аргументов `f` |
| `f((copy(Pair)))` | Сначала одну группу; далее обычный выбор W/E у `f` |
| `f(arg0 := (copy(Pair)))` | Целую группу конкретному существующему формалу `arg0`, без E |
| `copy(Empty)` | Ноль выходных полей из одного пустого источника |
| `(copy(Empty))` | Один пустой структурный результат |

**Скобки сохраняют группу, но не отменяют обычный выбор аргументов следующего ресивера.** Если целая структура подходит как W и её поля подходят как E, результатом является неоднозначность. Нельзя всегда предпочитать W из-за скобок или E из-за нескольких полей.

Важный отрицательный тест для оптимизации: один написанный `merge(S)` не обязательно означает один принятый источник. Если `S` содержит два допустимых структурных источника и единственное подходящее чтение — E, `merge` получает два источника. Написанную арность нельзя проверять до выбора W/E. Для `copy` принятых источников должно быть ровно один, для `import` — один или несколько.

При `(c b d a) := a b c d` из `1,2,3,4` получаем `a=4, b=2, c=1, d=3`. При несовпадении числа мест и значений запись ни в одно левое место не начинается. Это правило не обещает откат эффектов вычисления правой стороны. [Основание: stream-ТЗ §§6–8](newdocs/TZ/LMX_Fable_TZ_Import_Copy_Merge_Field_Streams_2026-11-21.md).

Haskell-ближайший аналог позиционного обмена — новая привязка кортежа из старых значений. LMX-поток при этом не нужно объявлять Haskell-кортежем: у него свой способ передачи обычному namespace-потребителю.

<a id="r03"></a>
### R03. `import` сохраняет исходного родителя; `copy` создаёт соответствующие копии

<!-- example: R03 -->
```lmx
Provider:
    int: value 7
    return: int
    read:
        return: value

ImportProbe:
    return: int
    run:
        import: Provider
        int: value 99
        int: original read()
        @: copied (copy(Provider))
        @: copiedOwner parent(copied\read)
        copiedOwner\value := 12
        int: changed copied\read()
        return: original * 100 + changed
```

Ожидается **712**. `import` делает доступным имя исходного метода `read`, сохраняя его фактического родителя `Provider`. Готовое собственное значение `7` не вытесняется вызывающим `99`. У копии явно выбран фактический DATA метода: `parent(copied\read)`. Этот скопированный родитель и контейнер, собравший поток, — разные структуры с разными ячейками. Замена поля `value` у выбранного родителя даёт методу `12`; ячейка `copied\value` в контейнере остаётся со значением `7`. `Provider\value` тоже остаётся `7`.

| Операция | Что оказывается в потоке | DATA и лексический владелец метода |
| --- | --- | --- |
| `import` | Ссылки на подходящие исходные const-объявления | Исходный владелец; идентичность метода и его связей сохранена |
| `copy` | Глубоко скопированный граф одного принятого источника, выдаваемый полями | Соответствующий скопированный владелец |
| `merge` | Глубоко скопированная композиция принятых источников по общей карте операции | Соответствующий скопированный владелец с результатом композиции |

Явная группа в каждом случае имеет собственные ячейки. Она собирает ссылки на выданный материал, не становится лексическим владельцем метода и не делает ещё одно глубокое копирование. Общая вложенная цель при этом остаётся общей: если два пути через разные контейнеры приходят в одну `child`, то запись в её `child\x` выбирает одну и ту же внутреннюю ячейку. Различаются ячейки внешних контейнеров, а связи внутри результата сохраняются по карте операции.

Само изменяемое поле `Provider.value` не импортируется. Пользовательская Structure `read` имеет константное имя по природе объявления; это не обещание неизменяемости всех её достижимых данных. `fn`-имя также импортируется как подходящее константное объявление, но имя ресивера `fn` не импортируется заодно.

Три дополнительных проверки:

1. `Struct: merge(A B)` объединяет только `A` и `B`. Уже написанное `Struct.x` не становится модельным слотом операции.
2. Два самостоятельных `merge` в одном DATA имеют две карты копирования. Приём второго потока — обычный приём объявлений, а не скрытый `merge` с накопленным получателем.
3. `f(import(A B))` отдаёт поток `f`; побочного дополнительного импорта в caller нет. `Producer()` внутри источников исполняется при потреблении по обычному CODE-контракту и в DATA, и в CODE. Построение P0 его не исполняет.

Основание: [import](newdocs/LMX_semantics.en.md#import-receiver) и [stream-ТЗ §§2–7](newdocs/TZ/LMX_Fable_TZ_Import_Copy_Merge_Field_Streams_2026-11-21.md).

<a id="r04"></a>
### R04. Код рядом с локальной переменной: присваивание не портит инициализатор

<!-- example: R04 -->
```lmx
ReadSource:
    int: calls 0
    return: int
    next:
        node\calls += 1
        return: 40 + node\calls

ComputedInput:
    int: value ReadSource\next()
    return: int
    changeLocal:
        int: seen value
        value := 99
        return: seen

LocalProbe:
    return: int
    run:
        ReadSource\calls := 0
        int: first ComputedInput\changeLocal()
        int: second ComputedInput\changeLocal()
        return: first * 100 + second
    explicitInitialization:
        ReadSource\calls := 0
        int: i
        i := ReadSource\next()
        i += 3
        return: i
```

`LocalProbe\run()` → **4142**, два вызова источника. `LocalProbe\explicitInitialization()` → **44**, один вызов источника. Исходная форма вычисляемого объявления остаётся в графе. Локальные `99` и `44` не публикуются обратно в её место.

Из внешнего чтения исходного пути не следует исполнение `ReadSource\next()`. Если требуется адрес исходной записи, он не становится адресом результата будущего вызова. Если требуется обычная текущая локаль, используется её собственное логическое место; native-исполнитель не обязан создавать для неё отдельный аренный узел с заголовком перед C-переменной.

Контрпример: убрать `int: i`, не оставив никакого допустимого собственного, caller- или fallback-места. Присваивание должно быть отклонено; оно не объявляет поле. Другой контрпример: не читать вычисляемый default либо явно заменить его входным аргументом. Невостребованный источник должен исполниться **ноль** раз.

Сравнивать надо исходную запись и её операции. Полная сериализация всех достижимых узлов может закономерно измениться из-за явно изменяемого `ReadSource.calls`; это не порча исходного кода. [Основание](newdocs/LMX_semantics.en.md#path-reads-no-execution), [локальные объявления](newdocs/Old_TZ/local_declarations_and_explicit_initialization.to_fable.en.md).

<a id="r05"></a>
### R05. Один интерпретируемый граф и native-реализация

Сценарий стенда: метод получает `x=7` и имеет тело `return: x + 1`. Ожидаемый результат **8**. Создать копию с тем же телом и корректными скопированными данными — результат также **8**; пригодная reusable native-связь сохраняется по общему контракту, само копирование не запускает компилятор и не регистрирует новую реализацию автоматически.

Затем организованно изменить тело на `x + 3`, выполнить явную компиляцию/обновление соответствующей единицы и перейти через `endturn`. Новый вход должен дать **10**. Обычная запись в граф не заменяет этот протокол автоматической инвалидизацией или dirty-наблюдением.

| Вызывающий → вызываемый | Что сравнить после нужной подготовки |
| --- | --- |
| Интерпретатор → интерпретатор | Значение, логические места, объявленные выходы |
| Интерпретатор → native | Те же наблюдения; вызов использует native при наличии пригодной записи |
| Native → интерпретатор | Общий контракт аргументов и локалей при переходе |
| Native → native | Прямой машинный путь не добавляет другой семантики |

Нельзя объявлять все промежуточные входы между редактированием и границей обновления заведомо новым кодом. Проверка привязана к определённому контрактом моменту. В чистом графе при этом остаётся полное тело для интерпретации и последующей генерации кода.

Это также отвечает на вопрос о «компилируемости»: генерация C с последующей машинной компиляцией остаётся компиляцией программы. Способ получения машинного кода надо отличать от наличия исходного графа, выбора пути конкретного вызова и момента явного обновления. Здесь сравниваются именно эти три свойства. [Основание](newdocs/LMX_semantics.en.md#explicit-compilation), [L2: реализации вызовов](newdocs/L2_spec_en.md).

<a id="r06"></a>
### R06. Общая цель и цикл внутри копии

Самостоятельный пример общей цели:

<!-- example: R06a -->
```lmx
SharedValue:
    int: value 7

SharedPair:
    @: left SharedValue
    @: right SharedValue

SharingProbe:
    return: int
    run:
        @: copied (copy(SharedPair))
        copied\left\value := 21
        return: copied\right\value * 100 + SharedValue\value
```

Результат **2107**. Две ссылки в результате указывают на одну соответствующую копию узла; исходный изменяемый узел остаётся со значением `7`. Сохранение отношения «обе ссылки на одну цель» не означает сохранение физической ссылки на исходную изменяемую цель.

Самостоятельный пример цикла:

<!-- example: R06b -->
```lmx
Ring:
    int: value 3
    @: self

CycleProbe:
    return: int
    run:
        Ring\self := Ring
        @: copied (copy(Ring))
        copied\self\value := 8
        return: copied\self\value * 10 + Ring\value
```

Результат **83**. Цикл замыкается внутри копии и не вызывает бесконечного копирования. Явная внешняя группа, собравшая поток, — отдельная структура со своим дескриптором и своими ячейками. Поэтому запись идёт через `copied\self`: она выбирает именно копию `Ring`, содержащую цикл. Её поле меняется на `8`, а отдельная ячейка `copied\value` внешнего контейнера остаётся со значением `3`. Группа не выполняет ещё одно глубокое копирование и не переназначает лексические связи.

Отдельная проверка исключения: допустимая ветвь `independent: immutable` с требуемыми квалификациями может сохранить исходную физическую ссылку. Обычные изменяемые узлы, только `independent` или только `immutable` этого исключения не получают. Дополнительный `const` не отменяет уже выполненных условий. [Основание](newdocs/LMX_semantics.en.md#eternal), [общая карта](newdocs/LMX_semantics.en.md#composition).

<a id="r07"></a>
### R07. Собственный операнд и сохраняемое вычисление

Вместо отдельного AST приложения можно сохранить само LMX-выражение:

<!-- example: R07 -->
```lmx
Operands:
    @: left
    []: @ right
    const: int: PASS_ARGS_AS_IS 0
    const: int: PRIORITY sys\priority("+")
    return: int
    add:
        return: \left + \right[0]
    Example:
        int: n
        return: int
        calculate:
            return: (n add 3) add n
        demo:
            return: calculate(2) + calculate(5)
```

`Operands\Example\demo()` → **20**, то есть `7 + 13`. Один записанный граф выражения исполняется с двумя входами. Операнд находится по обычному имени метода и структурному DATA-контракту; отдельной регистрации в словаре операторов нет.

Обычный Haskell-аналог вычисления — `calculate x = (x + 3) + x`. Если нужно также *осматривать и преобразовывать узлы*, можно явно выбрать AST:

```haskell
data Expr = Number Int | Variable | Add Expr Expr

evalExpr :: Int -> Expr -> Int
evalExpr _ (Number n) = n
evalExpr x Variable = x
evalExpr x (Add a b) = evalExpr x a + evalExpr x b

tree :: Expr
tree = Add (Add Variable (Number 3)) Variable
-- evalExpr 2 tree + evalExpr 5 tree == 20
```

Этот Haskell-код уже содержит представление дерева и его интерпретатор. Он решает расширенную задачу, поэтому сравнивать его длину только с `calculate` без оговорённой границы задачи было бы некорректно. В LMX исходное исполняемое представление уже принадлежит общей модели языка.

Проверки операндов: `30 subtract 4 * 3` при приоритете `+` должно дать **18**; `30 subtract 4 subtract 3` — **23**; массив из 17 элементов, переданный одним правым occurrence, остаётся одним правым аргументом, а не 17. `PASS_ARGS_AS_IS 1` позволяет написать управляющий операнд, который исполнит только выбранную ветвь через `sys\eval`; непрочитанная ветвь не производит эффектов. Полные OP01–OP18 — в [корпусе](LMX_regression_examples.to_fable.en.md#operands).

<a id="r08"></a>
### R08. Сериализовать, восстановить и продолжить работу с графом

Сценарий стенда: взять комбинацию R04 и R06, добавить массив и сериализовать выбранный граф через `sys\toLmx`, затем восстановить через `sys\fromLmx`.

| Материал | После восстановления |
| --- | --- |
| Явно записанное хранимое значение `21` | Сохраняется `21` |
| Неизменённый вычисляемый инициализатор | Остаётся вычисляемой исходной формой |
| Две ссылки на один изменяемый узел | Обозначают одну восстановленную цель |
| Цикл | Замыкается в восстановленном графе |
| Массив | Сохраняет порядок, длину и тип элементов |
| Записи `import`, `copy`, `merge` и группы | Сохраняются как написанные формы, а не заменяются прежним результатом namespace |
| Локальное `value := 99` из завершённой активации R04 | Не подменяет исходное объявление |

Сравниваются значения и отношения идентичности, а не равенство числовых адресов между процессами. Для сохраняемых native-таблиц выбранного Thread используется отдельный предусмотренный контракт платформы и модулей. Файловый дескриптор или адрес временной C-переменной не становится переносимым ресурсом оттого, что его число попало в текст. [Основание](newdocs/LMX_semantics.en.md#source-codec).

Haskell-обратный аналог для показанного `Expr` — сериализация своего AST и повторная интерпретация. Сериализация произвольной функции вместе с её внутренностями — уже другая задача, не эквивалентная стандартному `show` над `Expr`.

<a id="r09"></a>
### R09. `uninit` без value: локальная запись и замена фрагмента графа

Самостоятельный пример:

<!-- example: R09 -->
```lmx
UninitializedGraph:
    int: number
    @: reference
    return: int
    localWrite:
        number := 5
        return: number
    graphWrite:
        UninitializedGraph\number := 5
        return: UninitializedGraph\number

ReadyValues:
    int: number 0
    @: reference 0
```

На свежем графе `UninitializedGraph\number` представлен записью `{uninit_int}`. **`sizeof(value) = 0`**: есть код типа, а хранилища под будущий `int` нет. Для `reference` тоже выбран соответствующий неинициализированный тип без payload. Для сравнения `ReadyValues` содержит готовый числовой ноль и готовую нулевую ссылку. `nil` в текущей спецификации обозначает типизированное отсутствие, поэтому его нельзя использовать здесь как готовую нулевую ссылку.

Последовательность проверки:

1. Инспектор графа подтверждает код `uninit_int` и нулевой размер value. Он не читает выдуманное неинициализированное число из зарезервированного места.
2. `UninitializedGraph\localWrite()` возвращает **5**. После выхода исходный `number` по-прежнему `{uninit_int}`. Повторный вход снова получает исходное отсутствие значения, прежде чем выполнит своё локальное присваивание.
3. `UninitializedGraph\graphWrite()` возвращает **5**. Теперь выбранная ячейка структуры указывает на `{int 5}`: выполнена явная замена фрагмента графа.
4. Инспектор проверяет новое содержимое именно по структурному месту. Равенство прежнего и нового сырых адресов записи или value не является условием успешности.

Если две ссылки выбирают одну и ту же структуру и один слот, обе увидят замену. Если два разных слота только ссылались на один прежний примитив, это не превращает их в один слот: замена одного не распространяется автоматически на другой. Отсюда явный выбор владельца в H03, R03 и R06.

Основание: [уточнение автора §§2–3](newdocs/TZ/LMX_Author_Clarification_Uninit_Graph_Assignment_2026-11-21.md#uninit-zero-payload); подробная проверка G13 находится в [корпусе](LMX_regression_examples.to_fable.en.md#uninit-graph).

<a id="r10"></a>
### R10. Все ресиверы видны в графе и доступны для замены

Для этого сценария не нужен второй язык описания AST. Используются уже написанные программы: H09 с `for`, V02 с `if`, R01 с `merge`, R02 с `copy` и R03 с `import`.

| Наблюдение | Ожидается |
| --- | --- |
| Построить граф без исполнения программы | Каждый написанный ресивер, его аргументы и вложенные структуры присутствуют |
| Найти конечный примитивный лист | Ячейка `Lmx` указывает на его `{type value}`; это часть того же исходного графа |
| Выполнить соответствующий пример | Обычное вычисление не стирает `for`/`if`/`merge`/`copy`/`import` и не подставляет результат на место исходной записи |
| Явно заменить выбранную структуру другим фрагментом | В графе находится именно замена; прежний вид ресивера не даёт ей особой защиты |
| Для изменённого исполняемого тела выполнить требуемую компиляцию и `endturn` | Следующий вход использует подготовленную новую реализацию |
| Проверить граф и полученный бинарник | Содержимое программы находится в полном графе; бинарник содержит нативные методы, а R0 использует локальный указатель на граф R0 |
| Выбрать интерпретируемое исполнение | Бинарник и бинарный R0 остаются; дополнительной скрытой модели программы не появляется |
| Проследить выполнение в интерпретаторе и native | Второй рабочий граф не строится, в том числе под именем namespace или временной копии тела |
| Проверить написанный `private:` | Оба исполнителя соблюдают правило по исходной записи; бинарник не содержит отдельного графа меток доступа |

Конкретный контроль результата уже задан в R05: тело `return: x + 1` при `x = 7` даёт **8**; после замены на `return: x + 3`, явной компиляции и границы `endturn` следующий вход даёт **10**. Для остальных ресиверов стенд меняет выбранный фрагмент на заведомо различимое допустимое выражение и проверяет его результат после того же предусмотренного обновления. Проверка должна читать фактический граф, а не реконструированный текст из другого скрытого представления.

Основание: [полнота исходного графа](newdocs/TZ/LMX_Author_Clarification_Uninit_Graph_Assignment_2026-11-21.md#complete-source-graph), [замена исполняемых структур](newdocs/TZ/LMX_Author_Clarification_Uninit_Graph_Assignment_2026-11-21.md#receiver-replacement), [компиляция и `endturn`](newdocs/LMX_semantics.en.md#explicit-compilation).

## 4. Массивы и структуры

<a id="a01"></a>
### A01. Structure и массив ссылок: один дескриптор, те же слоты

Самостоятельный пример показывает именованный и индексный доступ к одной структуре:

<!-- example: A01 -->
```lmx
Slots:
    int: x 1
    int: y 2

Replacement:
    int: z 9

SlotProbe:
    return: int
    run:
        @: same Slots
        same[1] := Replacement[0]
        return: length(Slots) * 100 + Slots\z
```

На свежем графе результат **209**. `same` и `Slots` обозначают тот же дескриптор. Индексная запись заменила ссылку во втором слоте; она не сохранила для нового содержимого прежнее имя `y` или прежний контракт слота. Последующий структурный доступ интерпретирует текущее содержимое, поэтому доступно `z` со значением `9`. Сам новый узел не был скопирован или переподчинён из-за записи указателя.

Дополнительный сценарий стенда: предоставить тот же дескриптор как `Array<@>` и как Structure. Длина, слоты и изменённая ссылка совпадают; конверсия не выделяет второй контейнер или backing. Это и есть важная унификация «массива void-ссылок» и структуры. Поле, *содержащее ссылку* на массив, остаётся отдельным содержащим полем.

В Haskell запись и `Data.Array` являются разными объявленными типами; можно написать явное представление графа поверх массива ссылок, но обычная запись от этого сама не получает индексного API `Array`. [LMX](newdocs/LMX_semantics.en.md#structure-index); [Haskell Data.Array](https://www.haskell.org/onlinereport/haskell2010/haskellch14.html).

<a id="a02"></a>
### A02. Числовой массив не превращается в массив указателей

Сценарий стенда: плотный `Array<int>` с элементами `10,20,30`; две обычные ссылки на этот массив. Записать `27` во второй элемент через первую ссылку — через вторую читается `27`, длина остаётся `3`. Переназначение первой локальной ссылки на другой массив не переназначает вторую.

Отдельное графовое копирование создаёт независимое backing: изменение копии не меняет исходные числовые элементы. Но никакое структурное представление не позволяет трактовать машинные числа `10,20,30` как физические адреса трёх полей. Общий дескриптор контейнера и общие операции длины не отменяют тип хранения элементов. [Основание](newdocs/LMX_semantics.en.md#arrays).

Haskell `Data.Array` из Report — неизменяемый массив: `(//)` возвращает новое значение с обновлениями. Для разделяемых изменяемых ячеек выбирается соответствующий механизм эффектов; это надо оговаривать, а не приписывать обычному неизменяемому массиву поведение LMX-ссылок.

<a id="a03"></a>
### A03. Прямоугольный массив: проверяется итоговый линейный индекс

Исходные данные: `Array<int>` формы `2 × 3`, row-major значения `10,11,12,13,14,15`. Размеры/strides известны из описания; backing — единый прямоугольный блок.

| Доступ | Линейный индекс | Ожидается |
| --- | ---: | --- |
| `[0][0]` | 0 | `10` |
| `[1][0]` | 3 | `13` |
| `[0][3]` | 3 | `13`, тот же элемент |
| `[1][2]` | 5 | `15` |
| `[2][0]` | 6 | L3-отказ `interpreter` |
| Координаты с переполнением машинного расчёта индекса | Математически вне допустимого диапазона | Отказ; переполнение не возвращает индекс в разрешённый диапазон |

`length` здесь равно **6**, не `2`. Промежуточный `matrix[i]` не требует нового дескриптора строки. Массив ссылок на массивы — другая организация: каждый следующий доступ тогда идёт к реальному другому массиву.

Для Haskell `Array (Int,Int) Int` обычная проверка индекса выполняется относительно заданных границ индекса. Поэтому `[0][3] → [1][0]` из LMX нельзя автоматически переносить на Haskell-массив пар индексов. [LMX: индексация](newdocs/LMX_semantics.en.md#arrays); [Haskell: границы](https://www.haskell.org/onlinereport/haskell2010/haskellch14.html).

<a id="a04"></a>
### A04. Рост backing и сохранённая ссылка на элемент

Сценарий: длина массива `3`, удерживается L3-ссылка на элемент с индексом `1`. `sys\reserve` увеличивает capacity так, что backing перемещается. Дескриптор остаётся прежним; запись `27` через удерживаемую ссылку меняет элемент `1` нового backing. Сама операция reserve длину не меняет.

Затем `sys\resize` уменьшает длину до `1`. Удерживаемая ссылка на индекс `1` больше не обозначает допустимый элемент и должна получить обычный L3-отказ. Проверяются и чтение, и запись.

Такое поведение обеспечивается L3-ссылкой «дескриптор + индекс». Ранее полученный сырой L2-адрес в backing этим обещанием не охвачен. В одном тесте нельзя подменять один вид ссылки другим. Таблица capacity хранится по обычному контракту арены, без нового семейства `DynamicArray`. [Основание](newdocs/LMX_semantics.en.md#l3-array-reference).

<a id="a05"></a>
### A05. `map`, `filter`, `reduce`, `scan` и умножение

Конкретные входы для математического профиля LMX:

| Операция | Вход | Ожидаемый результат |
| --- | --- | --- |
| Чистый `map` удвоения | `1,2,3,4` | `2,4,6,8` |
| `filter` чётных | `1,2,3,4` | `2,4` |
| Упорядоченная сумма / `reduce` | `1,2,3,4`, identity `0` | `10` |
| Inclusive `scan` суммы | `1,2,3,4` | `1,3,6,10` |
| Поэлементное `*` | `1,2,3` и `4,5,6` | `4,10,18` |
| `dot` тех же векторов | `1,2,3` и `4,5,6` | `32` |
| `filter` без совпадений | `1,3`, чётность | Новый массив длины `0` |

Haskell-аналоги на списках:

```haskell
-- map (*2) [1,2,3,4]                   == [2,4,6,8]
-- filter even [1,2,3,4]                == [2,4]
-- foldl (+) 0 [1,2,3,4]                == 10
-- tail (scanl (+) 0 [1,2,3,4])          == [1,3,6,10]
-- zipWith (*) [1,2,3] [4,5,6]           == [4,10,18]
-- sum (zipWith (*) [1,2,3] [4,5,6])     == 32
```

Выбраны целые числа без переполнения, чтобы результат не зависел от порядка округления. Для вещественных reduce отдельно фиксируются порядок и числовой контекст. Чистый `map` допускает реализацию с векторизацией или параллельным вычислением без изменения результата; эффектный обход требует оговорённого порядка. Обычный `*` не становится матричным умножением. [Основание](newdocs/LMX_semantics.en.md#array-operations).

<a id="a06"></a>
### A06. Пустая структура, пустой поток, отсутствующее значение

Три теста должны различаться:

1. `copy(Empty)` — один допустимый источник и ноль выходных полей.
2. `(copy(Empty))` — одно структурное значение с нулём полей.
3. Неинициализированная ссылка или явно переданный `nil` — соответствующее состояние/значение ссылки, а не автоматически пустая структура.

У числа `0` также нет значения «аргумент не передали». Это уже проверено H04. Нельзя заменять эти случаи одним false-like состоянием ради удобства реализации. [Основание](newdocs/TZ/LMX_Fable_TZ_Import_Copy_Merge_Field_Streams_2026-11-21.md), T05/G07 английского корпуса.

## 5. `implements`, `test`, `catch` и проверка настоящего кандидата

<a id="v01"></a>
### V01. Проверка интерфейса плюс проверка поведения

Вопрос из обсуждения «как лучше проверить пригодность, чем интерфейсом и тестами?» получает здесь конкретное разделение обязанностей:

| Этап | Пример того, что устанавливается | Чего для этого не выполняют |
| --- | --- | --- |
| Структурная или `fn`-проверка | Кандидат допускает нужный вызов и соответствующие типы/выходы | Тело кандидата, вычисляемые default и конвертеры ради перебора кандидатов |
| Явно требуемый `test` потребителя | Конкретный вызов даёт нужное число, строку, отказ или обратную связь | Неизвестное будущее поведение не объявляется доказанным одним совпадением интерфейса |
| Рабочий вызов | Выполняется выбранная операция с её действительными аргументами | Не создаётся новый специальный «почтовый» или «тестовый» язык вызовов |

`test` принадлежит принимающему требованию/Consumer. Кандидат не может подставить вместо него свой более мягкий тест. Проверяющее действие получает настоящего кандидата; если нужны mock-зависимости, они передаются ему обычным способом, как в V03.

`test: operation Check\check` — связь обычного принимающего места и обычной проверяющей Structure. Её присутствие глубоко внутри непотреблённого DATA не запускает скрытый поиск тестов по дереву. При выполнении проверок `1` означает успех, `0` — отказ; после первого `0` последующие проверки не исполняются. Повторно встретить то же незавершённое допущение — не получить готовый успех рекурсии.

Фазы проверки реализации фиксируются отдельно:

| Сценарий | Наблюдение |
| --- | --- |
| Построить чистый граф с тестами | Ноль исполнений тел тестов на этом этапе |
| Достичь одного теста в предкомпиляционной интерпретаторной фазе | Одно исполнение; отказ препятствует приёмке сборки и последующей C-компиляции |
| Исполнить подготовленный native-вызов без явно написанного `implements` | Нет добавленной автоматической runtime-проверки `implements` |
| Достичь вызова в интерпретаторе | Используется общий `implements`, без предварительного обхода недостигнутых ветвей |
| Явно вызвать checker дважды | Два обычных вызова и их предусмотренные эффекты |
| Checker внутри интерпретаторной фазы вызывает пригодный native-метод | Обычный dispatch сохраняется; интерпретаторная внешняя фаза не превращает все вложенные вызовы в walker |

Тестирование интерпретатором само по себе не изолирует устройство и не откатывает эффекты. Ограниченность теста определяется его алгоритмом, явно предоставленными зависимостями и правами. [Основание](newdocs/LMX_semantics.en.md#admission), [контракт test](newdocs/LMX_semantics.en.md#test-receiver-contract).

<a id="v02"></a>
### V02. Аналог RegEx: проверить всю строку `AA-00`

<!-- example: V02 -->
```lmx
TicketCode:
    []: char candidate
    return: int
    accepts:
        if: length(candidate) != 5
            return: 0
        if: candidate[0] < 'A' || candidate[0] > 'Z'
            return: 0
        if: candidate[1] < 'A' || candidate[1] > 'Z'
            return: 0
        if: candidate[2] != '-'
            return: 0
        int: position 3
        while: position < 5
            if: candidate[position] < '0' || candidate[position] > '9'
                return: 0
            position += 1
        return: 1
```

Задана точная ASCII-проверка двух заглавных букв, дефиса и двух цифр. Профиль текста в этом сценарии — ASCII.

| Вход для `TicketCode\accepts(...)` | Результат |
| --- | ---: |
| `"AB-09"`, `"QZ-70"` | 1 |
| `""`, `"AB-9"`, `"AB-090"` | 0 |
| `"ab-09"`, `"AB-0X"`, `"XAB-09Y"` | 0 |
| Пять символов `A, B, NUL, 0, 9` | 0 |

Сначала проверяется длина, затем элементы. Поиска подстроки нет. Все эти значения могут иметь одинаковый интерфейс массива символов; различие содержимого устанавливает исполняемый checker. Его можно использовать как требуемую проверку при допуске, а можно вызвать напрямую, как здесь.

Haskell-эквивалент проверки:

```haskell
accepts :: String -> Bool
accepts [a,b,'-',c,d] = all upper [a,b] && all digit [c,d]
  where
    upper x = x >= 'A' && x <= 'Z'
    digit x = x >= '0' && x <= '9'
accepts _ = False
```

Этот пример не претендует на полную реализацию синтаксиса регулярных выражений. Он показывает, как требование к содержимому становится обычным проверяющим кодом рядом с интерфейсом. [Основание](newdocs/LMX_semantics.en.md#graph-tests).

<a id="v03"></a>
### V03. Куда вставляется mock

<!-- example: V03 -->
```lmx
Measurement:
    int: gain
    @: read
    return: int
    sample:
        return: read() * gain
    biased:
        return: read() * gain + 1
    readsTwice:
        int: discarded read()
        return: read() * gain

SamplingCheck:
    @: candidate
    int: calls 0
    return: int
    fixedRead:
        node\calls += 1
        return: 7
    check:
        node\calls := 0
        @: read fixedRead
        int: result candidate(gain := 4)
        return: result = 28 && node\calls = 1
```

| Вызов | Вердикт | Число чтений |
| --- | ---: | ---: |
| `SamplingCheck\check(candidate := Measurement\sample)` | 1 | 1 |
| `SamplingCheck\check(candidate := Measurement\biased)` | 0 | 1 |
| `SamplingCheck\check(candidate := Measurement\readsTwice)` | 0 | 2 |

Выполняется настоящий кандидат. Подменена его зависимость `read`, а не весь проверяемый алгоритм. Собственное незаполненное `read` кандидата получает обычную локальную ссылку checker через autofill; `gain` передан явно. Счётчик mock расположен в явно доступном лексическом состоянии.

Последний кандидат специально возвращает правильное число `28`, но делает два чтения. Проверка только результата пропустила бы дефект. Haskell-аналог — параметр `readSample :: IO Int` у `sample`, с тестовым действием, которое возвращает `7` и увеличивает `IORef`. Подмена зависимости не требует отдельного языка тестов ни в одном варианте.

Контрольный повтор первого вызова опять даёт `1` и ровно одно чтение: checker явно сбрасывает свой счётчик. [Основание](newdocs/LMX_semantics.en.md#binding-autofill); V02 английского корпуса.

<a id="v04"></a>
### V04. `catch` рядом с проверяемым действием

<!-- example: V04 -->
```lmx
UnavailableSensor:
    return: int
    read:
        throws: NoSample
        throw: NoSample()
    zero:
        return: 0

FailureCheck:
    @: candidate
    return: int
    check:
        candidate()
        return: 0
        catch: NoSample ()
            return: 1
```

`FailureCheck\check(candidate := UnavailableSensor\read)` → **1**. С `UnavailableSensor\zero` получается **0**. Нормальный нулевой результат не является ожидаемым отказом. Другой объявленный `throw` не считается автоматически успехом проверки.

Haskell можно дать явный результат `Either Failure Int` и сопоставить `Left NoSample`, либо выбрать механизм исключений для `IO`. Это альтернативные интерфейсы результата. В LMX здесь проверяется именно объявленный выход `NoSample` и обычный `catch`, расположенный рядом с вызывающим кодом. Обёртка `try` для этого примера не вводится. [Основание](newdocs/LMX_semantics.en.md#catch-common-model).

<a id="v05"></a>
### V05. Интеграционный тест: лампочка действительно загорелась?

Из обсуждения автомобиля берём одну законченно определённую процедуру: включить индикатор, прочитать обратную связь, выключить, снова прочитать. ACK команды и состояние датчика проверяются отдельно.

<!-- example: V05 -->
```lmx
Indicator:
    int: command
    int: fault 0
    int: commanded 0
    int: sensed 0
    int: writes 0
    int: reads 0
    int: trace 0
    return: int
    set:
        node\commanded := command
        node\writes += 1
        node\trace := node\trace * 10 + command
        if: node\fault = 0
            node\sensed := command
        if: node\fault = 1
            node\sensed := 0
        if: node\fault = 2
            node\sensed := 1
        return: 1
    observe:
        node\reads += 1
        node\trace := node\trace * 10 + 2
        return: node\sensed

Commissioning:
    @: candidate
    return: int
    check:
        int: onAck candidate\set(command := 1)
        int: onSeen candidate\observe()
        int: offAck candidate\set(command := 0)
        int: offSeen candidate\observe()
        return: onAck = 1 && onSeen = 1 && offAck = 1 && offSeen = 0
```

Для каждой строки стенд создаёт свежую копию `device = (merge(Indicator; (int: fault F)))`, подставляя конкретное значение `F`, и вызывает `Commissioning\check(candidate := device)`. Это запись подготовки стенда; присваивание без объявления новой переменной не предлагается.

| `fault` | Обратная связь | Вердикт | Конечное commanded / sensed | Writes / reads | Trace |
| ---: | --- | ---: | --- | --- | ---: |
| 0 | Следует команде | 1 | `0 / 0` | `2 / 2` | 1202 |
| 1 | Всегда выключено | 0 | `0 / 0` | `2 / 2` | 1202 |
| 2 | Всегда включено | 0 | `0 / 1` | `2 / 2` | 1202 |

Оба дефектных устройства отвечают `1` на обе команды. Проверка всё равно их отвергает. Последнее выключение выполняется и после неверного первого наблюдения, потому что четыре действия явно записаны до итогового вердикта. При выброшенном исключении действуют обычные правила выходов и обработки; из этого листинга нельзя вывести несуществующий автоматический rollback.

Чтобы проверить подключённое устройство, checker получает его действительные `set` и `observe` с тем же требуемым контрактом. Чтобы проверить алгоритм стенда воспроизводимо, он получает показанный `Indicator`. Различие задаётся переданной зависимостью. Если `observe` читает только программный регистр команды, это проверка регистра; физическую лампочку за него язык не наблюдает.

В этом и смысл интеграционной интерпретации: тест может быть реальным действием системы с явно выбранной последовательностью и проверкой результата. Автоматическое клонирование внешних ресурсов, подавление всех эффектов или восстановление прежнего состояния не следуют из слова `test`. [Основание](newdocs/LMX_semantics.en.md#graph-tests), [пригодность внешнего ресурса](newdocs/LMX_semantics.en.md#admission-case-14).

<a id="messages"></a>
## 6. Message: те же вызовы в условиях владения и доставки

Message — изолированный граф с владением. Исполняющий объект создаётся как Thread; обычное письмо не превращается в поток автоматически. У исполняющего владельца одновременно активен не более чем один turn; разные владельцы могут работать параллельно. Наличие всех этих механизмов не означает отдельного OS-потока для каждого Message. [Основание](newdocs/LMX_semantics.en.md#messages).

В следующих сценариях **адреса владельцев и маршрут транспорта задаются стендом через существующий API**. Локальные тела показаны на LMX. Таблицы `ask/answer` описывают конкретные маршруты и наблюдения, не изобретают ещё один синтаксис почтовых адресов.

<a id="m01"></a>
### M01. Полная операция над состоянием выполняется у владельца

<!-- example: M01 -->
```lmx
Counter:
    int: value 0
    int: delta
    return: int
    add:
        node\value += delta
        return: node\value
    read:
        return: node\value
```

Стенд размещает `Counter` у одного исполняющего владельца. Два отправителя адресуют ему обычные вызовы `add(delta := 4)` и `add(delta := 9)`. Именованная передача нужна здесь потому, что в DATA перед `delta` объявлено поле `value`. Начальное значение `0`. После обоих вызовов `read()` возвращает **13** при любом порядке поступления. Промежуточные ответы могут быть `(4,13)` или `(9,13)` по порядку исполнения, но ни один update не теряется.

Контрпример: начальное `10`; оба отправителя отдельно читают `10`, затем каждый присылает запись `11`. Итог **11** допустим при таком протоколе. Последовательные turns не объединяют несколько отдельных сообщений в одну транзакцию. Исправление задачи — отправлять целиком `add(delta := 1)`, а не добавлять mutex вокруг чужого графа. [Основание](newdocs/LMX_semantics.en.md#delivery).

На Haskell аналог владельца можно построить обычным циклом обработки `Chan Request`, запущенным через `forkIO`, и возвращать результат через `MVar`. В таком варианте счётчик передаётся следующей итерации цикла как обычное число. Это библиотечная реализация модели владения, а не автоматическое свойство любого Haskell-объекта. Полный пример находится в [Analogies.hs](examples/haskell/Analogies.hs).

<a id="m02"></a>
### M02. `ask` и fan-out: три запроса не превращаются в девять вычислений

Пусть настоящий `getPixel(x,y)` у источника увеличивает счётчик вызовов и возвращает уникальный для `(x,y)` цвет. Каждый из трёх приёмников результата увеличивает свой счётчик и сохраняет полученные координаты/цвет по подготовленному маршруту.

| Настройка `post` | Исполнений `getPixel` | Исходных результатов | Доставок результатов |
| --- | ---: | ---: | ---: |
| 1 `ask`, 3 `answer` | 1 | 1 | 3 |
| 2 `ask`, 3 `answer` | 2 | 2 | 6 |
| 3 `ask`, 3 `answer` | 3 | 3 | 9 |

Конкретная серия: запросы Q1=`getPixel(1,10)`, Q2=`getPixel(2,20)`, Q3=`getPixel(3,30)`; ответы адресованы `Display`, `Archive`, `Inspector`. Стенд организует поступление ответов в порядке Q3, Q1, Q2 до их допуска в соответствующий inbox; уже принятую почту он не переставляет. Каждый маршрут должен получить три соответствующих результата с сохранением установленного FIFO-порядка, а исходный счётчик равен **3**.

Корреляция идёт по исходным письмам; пользователю не требуется добавлять номера ответов. Ряды `ask` и `answer` не сопоставляются по позиции. Подготовленные маршруты допускаются до отправки; при получении результата не начинается новый поиск «какой обработчик похож по типу». [Основание](newdocs/LMX_semantics.en.md#thread-message-api), [транспорт T10–T12](newdocs/Old_TZ/threadMessageAPI.en.md).

<a id="m03"></a>
### M03. `undelivered`, `unanswered` и `catch` обозначают разные события

Используем Q2 из M02 и независимые свежие запуски:

| Событие | Ожидаемый обработчик и данные | Проверка |
| --- | --- | --- |
| Письмо отказано до исполнения у получателя | `undelivered`, исходный адрес и уже сформированные `(2,20)` | `getPixel` для Q2 не исполнился |
| Вызов объявленно выбросил `axisOutOfBound` | Соответствующий `catch` и payload | Не подменять исключение нормальным цветом или доставочным отказом |
| Истёк срок ожидания | `unanswered`, исходные данные и состояние ожидания | Источник мог уже исполняться; его работа не отменяется автоматически |
| Ответ вычислен, но один маршрут доставки ответа отказан | Событие доставки этого ответа | Исходный успешный вызов не становится недоставленным запросом |

Другие Q1 и Q3 продолжают по своим явно заданным маршрутам. Отказ одного письма не задаёт скрытый общий abort или барьер всей группы. [Основание](newdocs/LMX_semantics.en.md#thread-message-api).

<a id="m04"></a>
### M04. Таймаут считается от отправки; аргументы не вычисляются заново

Подготовка Q2 исполняет `nextX()` и `nextY()` по одному разу, получая `(2,20)`. После отправки исходные локали отправителя меняются на `(99,99)`. Задана форма `timeout: ms: int: time 500`; путь настройки — `timeout\ms\time`, без дополнительного узла `int`.

Стенд удерживает ответ до **512 ms** после исходной отправки. Проверяются отдельно исходные аргументы `(2,20)`, неизменная настройка `timeout\ms\time = 500` и фактическое время, переданное обработчику `unanswered`. Истечение может быть обслужено уже после достижения `500 ms`; само удержание ответа до `512 ms` не предписывает точного времени запуска обработчика. В детерминированном варианте стенд впервые обслуживает это ожидание при `512 ms`, и тогда наблюдаемое время равно `512`, а настройка по-прежнему `500`. Счётчики производителей остаются по **1**. Подготовка описания до отправки не является началом этого интервала.

Обработчик только записывает диагностику. Затем приходит запоздавший результат. Он всё ещё проходит подготовленный маршрут ответа: логирование таймаута не отменило действие и не удалило ожидание автоматически. Если приложению нужна отмена, дедупликация или запрет позднего результата, это должно быть явно определено его протоколом. [Основание](newdocs/LMX_semantics.en.md#thread-message-api), T13/T15–T20 транспортного дополнения.

<a id="m05"></a>
### M05. Процедура без результата не должна посылать выдуманный ACK

Самостоятельное локальное тело:

<!-- example: M05 -->
```lmx
Lamp:
    int: state 0
    int: command
    set:
        node\state := command
```

У `Lamp\set` нет описания `return`. Локальный или транспортируемый вызов с `command=1` меняет явное состояние и не создаёт прикладной ответ только ради транспортной схемы. Отсутствие такого ответа само по себе не становится `unanswered`. Успешная доставка письма и подтверждённое приложением исполнение команды — разные сведения.

Для подтверждения фактического состояния приложение выбирает явный интерфейс с результатом или отдельное наблюдение, как V05. В Haskell `IO ()` явно описывает результат действия как unit; здесь важно не перенести его механически в несуществующую LMX-декларацию результата. [Основание](newdocs/Old_TZ/threadMessageAPI.en.md), T26.

<a id="m06"></a>
### M06. Копирование, ссылка и передача владения

| Операция стенда | Проверяемое отношение |
| --- | --- |
| Передать обычную ссылку внутри допустимого владельца | Тот же объект; никакой скрытой независимой копии |
| Создать новый исполняющий Message из явно заданного шаблона | Отдельная арена и копии обычного изменяемого графа по общей карте |
| Передать явно допустимую eternal-ветвь | Сохранение ссылки только при выполнении общего квалификационного исключения |
| Передать storage неисполняемого письма принимающему владельцу | Адреса могут остаться прежними; ответственность освобождения переходит получателю |
| Перенести supervision работающего дочернего Thread | Меняется управляющий родитель; это не копирование и не усыновление остановленного storage |
| Сериализовать для другой машины | Переносимое описание связей; сырые локальные адреса не становятся удалёнными адресами |

Для копирования взять R06: общая цель внутри нового владельца остаётся общей копией, исходный изменяемый узел не разделяется. Для передачи storage проверить, что прежний владелец больше не освобождает переданные chunks. Операция приёма не меняет автоматически лексический `parent` принятого корня: прикладное присоединение задаётся явно.

Типовой контекст нового Message тоже передаётся явно, как H10/H11. Нельзя заодно скопировать весь живой контекст родителя «для удобства». [Основание](newdocs/LMX_semantics.en.md#delivery), [контекст](newdocs/LMX_semantics.en.md#conversion-context).

<a id="m07"></a>
### M07. Параллельность владельцев и последовательность одного владельца

Создать два исполняющих владельца A и B, каждому явно передать независимую копию Counter. Послать каждому свою серию приращений. Проверить:

1. У A никогда не пересекаются два активных turn; то же у B.
2. A и B могут продвигаться одновременно, не меняя чужой граф.
3. За один turn один владелец исполняется на одном OS-потоке; перенос между worker допустим между turns.
4. Режим отдельного OS-потока и пошаговое обслуживание родителем дают одинаковые допустимые значения и порядок уже принятой FIFO-почты.
5. Обычное получение письма как данных не запускает его содержимое; запуск отдельного дочернего Thread явный.

Это проверка runtime-модели. Отсутствие пользовательских mutex в таком приложении не означает отсутствия механизма координации доставки внутри runtime. [Основание](newdocs/LMX_semantics.en.md#messages), [общий mailbox L2](newdocs/L2_spec_en.md#mailbox).

<a id="m08"></a>
### M08. Граница turn: исходящие письма, сбой и завершение

Сценарий A: обработчик меняет своё хранимое поле на `5`, подготавливает исходящее письмо, затем завершается с отказом до успешной публикации. Ожидается: ещё не опубликованное письмо из staging не выдаётся получателю; уже выполненная запись `5` не откатывается автоматически.

Сценарий B: обработчик готовит финальное письмо и явно устанавливает `success := 1`. На успешной границе финальная исходящая почта публикуется по обычному правилу, а главный алгоритм не получает нового turn.

Сценарий C: mailbox пуст, но `success` не установлен. Пустая очередь не означает завершение background-работы. Дочерние участники обслуживаются через предусмотренный единственный `Thread.children`; ещё один глобальный реестр или отдельная очередь членства не нужны.

Сценарий D: ручной `receive` и протокольная обработка `post` конкурируют за одно письмо. Письмо может быть принято только одним маршрутом, поскольку используется один inbox и общий механизм владения. [Основание](newdocs/LMX_semantics.en.md#lifecycle), [публикация](newdocs/LMX_semantics.en.md#delivery), [post](newdocs/LMX_semantics.en.md#thread-message-api).

Дополнительные binding-проверки, которые важно не потерять за основными аналогиями:

- **Цепочка A → B → C.** Если B не установил связи с именем, C не должен автоматически пройти сквозь B к изменяемому месту A. Вариант с явно установленной у B прозрачной связью проверяется отдельно. В B-04 корпуса это различается значениями `5` и `8`.
- **`private` в обе стороны.** Проверяются и недоступность источника для неявного связывания, и запрет динамической подмены защищённого принимающего места. Явные допустимые пути и явно переданные actuals сохраняют свой контракт.
- **Порядок actuals.** Выражения исполняются один раз в написанном порядке; именованная передача сопоставляет формалы, но не переставляет эффекты вычисления. Имена, совпавшие с ожидаемой позицией, и именованный переход к другой позиции проверяются раздельно.
- **Присваивание внутри actual.** Это обычная операция над выбранным местом активации, а не новое объявление или безусловно второй именованный аргумент. Приём готовой формы объявления имеет отдельный явно описанный контракт.
- **Обязательное значение.** `required` проверяет выбранное место после установленного связывания. Готовый `0`, отсутствие default и явный `nil` должны различаться.

### 8.3. Минимальная последовательность для Fable

1. Разобрать сохранённые исходные формы, группы, пустые строки и `---`; убедиться, что построение графа не исполняет источники `import/copy/merge`.
2. Пройти H01–H06 и R01–R03: именно они различают ссылку/вызов, фактический DATA, default, динамический источник, копию и поток.
3. Проверить H07–H09/R04 не только по числам, но и по количеству исполнений, месту записи и неизменности исходных форм.
4. Проверить типовой и структурный допуск, затем реальные checker-вызовы V01–V05; не смешивать их счётчики с фазой построения графа.
5. Пройти графовые/массивные fixtures R06/R08–R10/A01–A06: отдельные отрицательные тесты должны ловить shallow copy, лишнюю копию общей цели, выдуманный payload у `uninit`, порчу исходных ресиверов, неверную распаковку и старый backing.
6. Для подготовленных единиц сравнить предусмотренные native/interpreter пути и обновление после явной компиляции/`endturn`.
7. Пройти M01–M08, отдельно считая исходные исполнения, исходные ответы, доставки, события таймаута и явные изменения состояния.

Если устаревшая формулировка однозначно исправляется действующим ТЗ, её надо исправить. **Вопрос Михаилу нужен при явном противоречии действующих требований, для которого приоритет источников не определяет решение.** Ранее выделенный вопрос о физическом представлении `uninit` закрыт прямым уточнением автора и отражён в R09–R10. Результаты проверки документов приведены в [отчёте](LMX_consistency_review.ru.md). Ни один ожидаемый результат этого документа не следует выдавать за уже выполненный runtime-тест.
