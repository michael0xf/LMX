## 1. Задача и обязательные изменения

Реализовать и согласованно описать семь изменений:

1. Добавить `sys\operand`: регистрацию пользовательского операнда с функцией реализации и обязательным приоритетом. Применение: `(1 foo 2 3 4)` и `(foo 1 2 3 4)` по обычным правилам наличия аргументов.
2. Закрепить именованную сигнатуру реализации `fn: OperandSignature (@: left; []: @ right; return: @)`: одно значение слева операнда и массив значений справа, представленные ссылками на типизированные записи; результат — такая же ссылка `@`. Наличие и отсутствие аргументов разрешаются стандартными правилами LMX.
3. Разделить самостоятельный именованный аргумент и присваивание, встроенное в выражение аргумента. Встроенное присваивание изменяет соответствующее `data` и возвращает значение в выражение; отдельного actual argument из него не возникает.
4. Привести приоритеты и ассоциативность поддерживаемых операций к Си. Для `**` сохранить указанное ниже правило Python.
5. Вычислять необходимые значения по требованию потребляющего их ресивера. Связанное с конкретным вхождением присваивание исполняется и при более низком приоритете, сохраняя свою правую часть и возвращая присвоенное значение.
6. Добавить `sys\name(identificator)`: получение написания любого идентификатора из существующей служебной таблицы как обычной LMX-строки — массива символов переменной длины.
7. Добавить `sys\priority`, чей контракт описывается именованной сигнатурой `fn: PrioritySignature ([]: char name; return: int)`: получение приоритета операнда по строке с его именем.

Автор отменил предложенное в предыдущих редакциях этого ТЗ общее раскрытие Array в цепочку аргументов. Вместо него вводится конкретный интерфейс функции реализации операнда. Ранее действовавшие правила передачи единственной обычной Structure этой поправкой не пересматриваются.

Последние решения автора имеют приоритет над противоречащими им фрагментами предыдущих редакций. Требуется обновить примеры и реализацию, а не дописать рядом ещё одну несовместимую норму.

Выражение остаётся Structure. Сохраняются один общий парсер, чистый граф и существующие механизмы разрешения имён, приёма аргументов и исполнения. Приоритеты относятся к анализу и исполнению выражения после P0. Изменения не дают P0 права удалять контейнеры, менять написанную вложенность или переустраивать `parent` и `length`.

## 2. Пользовательский операнд: `sys\operand`

### 2.1. Группа и форма регистрации

Оба специальных ресивера находятся в группе `sys`:

- `sys\operand` — регистрация пользовательского операнда;
- `sys\priority` — получение приоритета по имени; §8.

Форма регистрации, принятая в этом ТЗ:

```text
sys\operand: foo new_op p
```

Здесь `foo` — имя нового операнда, `new_op` — функция его реализации, `p` — обязательное целочисленное значение приоритета.

Новый операнд явно выделяется из множества идентификаторов. Само наличие обычной функции или Structure с именем `foo` этой роли не создаёт. Лексически имя может оставаться идентификатором; его объявленную роль учитывает общий механизм expression.

Расположение регистратора в `sys` не переносит туда имя `foo`. Видимость регистрации и разрешение имён следуют обычным правилам контекста.

### 2.2. Именованная сигнатура и функция реализации

Контракт реализации описывается именованной сигнатурой:

```text
fn: OperandSignature (@: left; []: @ right; return: @)
```

У `fn` два аргумента: имя `OperandSignature` и data-шаблон в скобках. Внутри шаблона описаны два входных места: `left` — одно значение слева операнда, представленное ссылкой `@` на его типизированную запись; `right` — массив переменной длины с элементами `@`, содержащий значения справа. Поле `return: @` находится внутри того же data-шаблона и описывает результат, а не третий входной аргумент.

`fn` создаёт именованное описание сигнатуры, а не исполняемую функцию. `new_op` — отдельно объявленный обычный исполняемый метод/Structure с соответствующим контрактом вызова. В `sys\operand: foo new_op p` передаётся ссылка на эту реализацию, не на описание `OperandSignature`. Само описание сигнатуры без реализации не является целью регистрации.

Например, в:

```text
(1 foo 2 3 4)
```

`left` получает ссылку на значение `1`, а `right` — массив из трёх ссылок на `2`, `3`, `4` в этом порядке. Число элементов `right` не превращается в число формалов: у интерфейса остаются два входных места.

В форме `(foo 1 2 3 4)` слева от операнда значение не написано; четыре правых значения образуют `right`. Разрешение отсутствующего `left` следует стандартным правилам аргументов LMX. Массив `right` не сдвигается в позицию `left` и не теряет свой смысл второго параметра. Отдельного правила наличия/отсутствия для операндов не вводится: применяются обычные defaults, `required` и связывание там, где они применимы. Физический смысл ссылок и возврат результата определены в §3.

Проверяется контракт исполняемого кандидата, а не наличие у него старой формы executable `fn`. Обычная Structure без требуемого контракта не становится подходящей реализацией только потому, что является Structure.

### 2.3. Приоритет

Приоритет принадлежит зарегистрированному операнду `foo` и участвует в том же анализе выражений, что приоритеты встроенных операций. Использовать существующую шкалу и механизм сравнения; отдельная шкала для пользовательских операндов не вводится.

Приоритет обязателен. Отсутствующее значение не заменяется неявным нулём или придуманным приоритетом. Проверка его типа использует обычный контракт `int`.

Получить приоритет уже существующего операнда можно через §8, например:

```text
sys\operand: foo new_op sys\priority(sys\name(`+`))
```

Здесь `foo` получает такой же приоритет, как `+`. Числовые значения уровней не приходится дублировать в пользовательском коде.

Для равных приоритетов использовать существующее общее правило expression. Регистрация сама по себе не вводит новую пользовательскую ассоциативность и не меняет специальные правила `**` и присваиваний.

Приоритет определяет границы и обработку операций. Необходимое конкретному потребителю вхождение `foo` может быть вычислено по требованию согласно §5; временного повышения его приоритета при этом нет.

### 2.4. Общие механизмы

Регистрация, ссылка на `new_op` и значение приоритета представлены обычным образом в чистом графе. Производный индекс доступных операндов может использоваться существующей обработкой контекста; самостоятельного скрытого реестра программы не требуется.

P0 сохраняет написанную структуру. Объявленные роли и приоритеты применяет общий анализ после P0. Для пользовательского операнда не появляется отдельный парсер.

Поддержать применение с одним значением слева и цепочкой справа — `(left foo …)` — через общий механизм expression. Сохраняется форма `(foo …)` без написанного левого значения; её допуск определяется обычными правилами отсутствующего аргумента (§2.2). Объявление новых символических токенов или макросистемы этим ТЗ не требуется.

При известной регистрации транслятор генерирует обычный вызов `new_op` с раздельными входами `left` и `right` и стандартным приёмом присутствующих либо отсутствующих аргументов. Наличие пользовательского операнда само по себе не требует запускать интерпретатор из нативного метода.

## 3. Левое значение, массив правых значений и указатель на результат

### 3.1. Что передаётся в `left` и `right`

Общий анализ expression определяет фактические операнды применения `foo` с учётом структуры, группировок и приоритета: одно значение слева и последовательность значений справа. Эти значения получают по обычным правилам. Ссылка на левое значение поступает отдельно в `left`; ссылки на правые значения собираются в `right` в их исходном порядке.

Для `(1 foo 2 3 4)` логическая схема такова:

```text
left = p1
right = Array<@>(p2, p3, p4)
result = new_op(left := left; right := right)
```

Это поясняющая запись, а не новая форма синтаксиса LMX. `p1`…`p4` указывают на типизированные значения `1`…`4`. Имя `foo`, значение приоритета и служебные головы операций в значения аргументов не включаются. Левый операнд не дублируется в начале массива `right`.

Для `(foo 1 2 3 4)` соответствующая схема подачи написанных значений:

```text
right = Array<@>(p1, p2, p3, p4)
result = new_op(right := right)
```

Здесь `left` не подан этой записью; его отсутствие обрабатывается обычным механизмом аргументов. Схема показывает соответствие параметров, не задаёт специального алгоритма исполнения префиксной формы и не подставляет `0`, `nil` или иной маркер вместо отсутствующего значения. Параметр `has_left` или иной дополнительный параметр не вводится.

Наличие или отсутствие правого аргумента также разрешается стандартным контрактом. Переданный пустой массив является присутствующим значением и не равен отсутствующему аргументу. Это ТЗ не устанавливает для операнда собственных правил обязательности, неявного значения или подмены отсутствия пустым массивом.

В `left` и элементах `right` находятся ссылки на результаты вычислений. Встроенное присваивание даёт один результат в соответствующей левой или правой позиции, не создавая дополнительного именованного аргумента; правила §§4–5 сохраняются.

Функция реализации получает подготовленные значения по обычному контракту вызова метода, описанному именованной сигнатурой. Этот интерфейс не вводит передачи отложенных вычислений. Внешняя логическая операция может пропустить всё применение `foo` вместе с вычислением его аргументов; встроенное короткое замыкание сохраняется.

### 3.2. Контейнер остаётся одним операндом

Если фактический операнд сам является Array или Structure, он передаётся одной ссылкой: отдельно в `left`, если стоит слева, либо одним элементом `right`, если стоит справа.

| Применение | `left` | Содержимое `right` |
|---|---|---|
| `(1 foo 2 3 4)` | Ссылка на `1` | Три ссылки на `2`, `3`, `4` |
| `(foo 1 2 3 4)` | Не подан написанной формой; применяется обычный контракт | Четыре ссылки на `1`, `2`, `3`, `4` |
| `(foo A)`, где `A` — Array | Не подан написанной формой; применяется обычный контракт | Одна ссылка на значение/дескриптор `A` |
| `(A foo B C)`, где значения — контейнеры | Одна ссылка на `A` | Две ссылки на `B` и `C` |

Элементы `A` не становятся операндами `foo` автоматически. Общая база `Lmx` не является основанием раскрывать этот Array через обработку обычной Structure.

Сбор правых операндов в параметр `right` — контракт реализации нового операнда. Он не вводит общее правило раскрытия Array для обычных вызовов. Отменённые положения и проверки такого раскрытия необходимо удалить.

Существующий выбор прочтений единственной обычной Structure остаётся в своей прежней области действия; заново проектировать его ради `new_op` не требуется.

### 3.3. Смысл указателя `@`

Аргумент `left`, элементы `right` и возвращаемый `new_op` указатель используют существующий контракт storage: ссылка ведёт к значению типизированной записи `{type, value}`. По этой записи доступны физический тип и само значение.

Сохраняется действующая адресность L2:

```text
p = storage[index]
value находится по p
type находится непосредственно перед p
```

В текущей норме L2 код типа занимает четыре байта перед адресом значения. Слова «указатель на запись `{type, value}`» не меняют `p` на адрес тега типа. Никакого фиксированного C `union` или новой оболочки `TypedValue` ради этого интерфейса не вводится.

Если аргумент — контейнер, указатель ведёт на его типизированный дескриптор. Плотный `Array<T>` нельзя превращать в `Array<@>` переинтерпретацией его storage: сами числовые элементы не являются указателями на записи с индивидуальными тегами.

Готовые записи использовать через их существующие указатели. Если нативное вычисление дало только машинное временное значение, его адрес сам по себе не является допустимым `@` на типизированную запись; при необходимости передать такую ссылку применяется существующий механизм представления значения в storage.

### 3.4. Возврат результата

`new_op` возвращает один `@` на запись своего результата. **Результатом применения операнда для expression служит указанное типизированное значение.**

Если возвращённый указатель ведёт на запись с типом `int` и значением `10`, результат операнда — это целое число `10`. Машинный адрес не становится числовым результатом выражения и не требует отдельного пользовательского разыменования.

Если указанная запись сама имеет тип `@`, логический результат операнда имеет тип `@`. Дополнительного автоматического снятия уровней ссылки нет.

Функция может возвратить подходящую уже существующую запись, в том числе запись аргумента, или запись вычисленного результата. Обязательной копии всех аргументов и отдельной упаковки возвращаемого указателя поверх записи результата не требуется.

Запись остаётся доступной потребителю в пределах действующих правил времени жизни и владения. Новая модель памяти этим интерфейсом не вводится.

Для интерпретатора и нативной генерации контракт один: отдельная ссылка на левое значение, массив ссылок на правые значения и одна ссылка на типизированный результат; наличие и отсутствие входов разрешаются стандартными правилами. Существующее разграничение admission при трансляции, интерпретации и подготовленном нативном исполнении сохраняется.

## 4. Именованный аргумент и встроенное присваивание

### 4.1. Два разных структурных случая

| Случай                                                       | Значение                                                                               |
| ------------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| `v := expression` занимает самостоятельную позицию аргумента | Именованный actual argument `v`, получающий результат правой части                     |
| `v := expression` находится внутри выражения аргумента       | Запись в соответствующее `data`; присвоенное значение участвует в окружающем выражении |

Встроенное присваивание не создаёт дополнительный actual argument, не занимает дополнительную позицию и не сдвигает позиционный курсор. Результат всего выражения передаётся как один аргумент.

Различие определяется структурным положением записи после общего разбора. Если потребителю требуется результат встроенного присваивания, он получает его по правилу §5: связанное присваивание вычисляется и при более низком приоритете. Одного совпадения имени с формалом для такой связи недостаточно.

### 4.2. Основной пример без дополнительных скобок

```text
f(1 + v := 2 + 3)
```

Написанная цепочка:

```text
1 plus: v let: 2 plus: 3
```

Разбор исполнения:

1. Первому `plus` нужны `1` и результат конкретного встроенного присваивания, связанного с этим вхождением `v`.
2. `plus` требует этот результат. Меньший приоритет `let` не запрещает исполнить его для получения нужного значения.
3. В правой части присваивания `plus` имеет более высокий приоритет, чем `let`. Поэтому сначала вычисляется `2 + 3 = 5`.
4. В соответствующее **data вызываемой `f`** записывается `v := 5`. Значением этого присваивания является `5`.
5. Первый `plus` получает `1 + 5 = 6`.
6. `f` получает **один** позиционный actual argument `6`.

По результату и записи в `v` это соответствует:

```text
f(1 + (v := 2 + 3))
```

Скобки в последней записи лишь показывают получившееся вычисление. В исходный граф дополнительный контейнер не добавляется.

Запись не превращается в `f(v := 5; 6)`. Отдельное одноимённое место `v` вызывающего контекста не становится целью присваивания.

В проверочной функции первый формал должен называться, например, `x`, а `v` быть другим полем её `data`. Наблюдаемый результат: `x = 6`, `v = 5` и ровно один actual argument. Даже если `v` уже содержало `100`, результат именно этого выражения остаётся таким же.

Использовать существующее соответствующее `data` получателя. Это требование само по себе не вводит копию графа, новую модель кадра или специальный механизм обратной записи.

### 4.3. Явная группа задаёт другой эффект

```text
f(1 + (v := 2) + 3)
```

Здесь правая часть сгруппированного присваивания — только `2`:

1. В data `f` записывается `v := 2`.
2. Значение присваивания `2` участвует в окружающем выражении.
3. Вычисляется `1 + 2 + 3 = 6`.
4. Передаётся один позиционный actual argument `6`.

Эта запись также допустима. В ней `v = 2`, тогда как в §4.2 `v = 5`. Совпадение итогового аргумента `6` не означает совпадения эффектов.

### 4.4. Самостоятельный именованный аргумент

```text
f(v := 2 + 3; 6)
```

даёт:

```text
f(v := 5; 6)
```

Здесь два actual arguments: самостоятельный именованный `v := 5` и следующий позиционный `6`.

Для этого положительного примера формал `v` должен стоять первым. По действующему правилу именованный аргумент на своей позиции считается позиционным, и передача может продолжиться позиционно.

Если `v` находится на другой позиции, сохраняется общее ограничение: после именованного аргумента вне своей позиции следующие аргументы тоже должны быть именованными.

Исполнение по требованию внутри выражения не меняет структурную роль этой самостоятельной записи и не отменяет правил именованной передачи.

### 4.5. Сопоставление редакций и проверка эффектов

В прежней норме присваивание имело высокий приоритет. Текущая норма сочетает низкий приоритет присваивания с вычислением необходимого результата по требованию.

| Запись               | Прежний высокий приоритет: `v` / аргумент `f` | Текущая норма: `v` / аргумент `f` |
| -------------------- | --------------------------------------------- | --------------------------------- |
| `f(1 + v := 2 + 3)`  | `2 / 6`                                       | `5 / 6`                           |
| `f(10 * v := 2 + 3)` | `2 / 23`                                      | `5 / 50`                          |
| `f(1 + v := 2 * 3)`  | `2 / 7`                                       | `6 / 7`                           |

В среднем примере новое исполнение: `2 + 3 → 5`, запись `v := 5`, затем `10 * 5 → 50`. Это отличает новую норму от ошибочного временного повышения приоритета `let`, которое сохранило бы `v = 2` и дало бы `23`.

Убрать из предыдущей редакции ТЗ тезис, что после понижения приоритета присваивания пример без скобок остаётся без определённого результата и обязательно требует скобок. Новое правило определяет и результат, и записанное значение.

При переводе примеров проверять оба наблюдаемых результата. Скобки добавлять только для выражения требуемой границы вычисления; механическое добавление скобок может изменить значение присваивания.

## 5. Исполнение по требованию и эффекты

### 5.1. Общее правило

> Перед исполнением ресивера вычисляются необходимые ему значения. Если необходимое значение является результатом другого ресивера, тот исполняется по требованию независимо от сравнительного приоритета этих двух ресиверов. Его аргументы и правая часть сохраняют границы, определяемые структурой и приоритетами.

Приоритет определяет обработку и принадлежность операций в выражении. Зависимость по значению определяет, что необходимо вычислить до завершения потребителя. Более высокий приоритет потребителя не запрещает ему сначала получить результат зависимой операции с меньшим приоритетом.

В примере §4.2 низкий приоритет `let` позволяет вычислить внутри его правой части `2 + 3`; зависимость левого `plus` от результата `let` требует завершить присваивание перед сложением с `1`.

**Исполнение по требованию не повышает приоритет присваивания.** Вызвать `let` раньше потребителя не означает взять только первый атом `2`, оставив `+ 3` снаружи. Правая часть вычисляется по действующим низким приоритетам присваивания.

Правило относится к общему механизму expression, включая зарегистрированные пользовательские операнды. Функция `new_op` получает подготовленные значения по контракту §3. Для остальных ресиверов сохраняется их собственный контракт потребления: например, логическая операция может не потребовать правый операнд и пропустить целое применение пользовательского операнда.

Исполнение по требованию следует связям получения значения, установленным общим анализом выражения. Само соседство записей такой связи не создаёт. В `10 * 2 + 3` умножению требуется непосредственно число `2`; вычисляется `(10 * 2) + 3 = 23`. В `10 * v := 2 + 3` потребляемое вхождение связано с результатом конкретного присваивания `v`; его правая часть даёт `5`, поэтому результат равен `50`. Приоритеты обычных арифметических цепочек сохраняются.

### 5.2. Связь с конкретным вхождением

Связь между потребляемым вхождением и производящей его значение операцией устанавливает общий анализ выражения после P0.

В `1 + v := 2 + 3` нужен результат **этого** присваивания `v`. Наличие старого значения у места не отменяет требование получить результат. При прежнем `v = 100` новое значение равно `5`, а результат выражения — `6`.

Обычное чтение имени сохраняет свою роль. Оно не запускает поиск ещё не выполненных одноимённых присваиваний в окружающем коде. Обычное имя Structure также не превращается в неявный вызов.

В обычной записи кода:

```text
v := v + 1
```

правое `v` читает значение уже известного места до этой записи. При `v = 100` оно даёт `100`, сумма — `101`, присваивание записывает `101`. Правое `v` не требует повторно исполнить само это присваивание.

Таким образом, требование значения привязано к конкретной операции выражения, а обычное чтение переменной — к соответствующему месту по действующим правилам разрешения.

### 5.3. Однократность и результат операции

В одном динамическом вычислении конкретное вхождение операции исполняется один раз. Если оно уже исполнено по требованию, последующее достижение этого вхождения обходчиком использует результат и не повторяет эффект.

Например, при `read_once()`, возвращающем `4`:

```text
f(1 + v := read_once() + 3)
```

получаются одно чтение, `v = 7` и один аргумент `8`. Тело `f` запускается после получения аргумента.

Сохраняется результат операции — присвоенное ею значение. Его получение потребителем не подменяется повторным чтением изменяемого места после возможных других записей.

Однократность относится к конкретному исполнению выражения. Новый вызов, новая итерация или новая проверка условия выполняют его заново. Вычисленный однажды результат не становится постоянным кэшем в исходном графе.

При ошибке вычисления необходимого значения потребитель не получает выдуманного результата; применяются обычные правила отказа и обработки ошибок. Вычисление по требованию не оправдывает пробные исполнения при переборе сигнатур.

### 5.4. Скобки и короткое замыкание

Приоритет и группировка не разрешают заранее выполнить все вложенные группы и присваивания независимо от потребности в результате.

Для поддерживаемых `&&` и `||` сохраняется короткое замыкание:

```text
0 && (x := 1)
1 || (x := 1)
```

В обоих случаях правый операнд не требуется и `x` не изменяется. Аналогично не исполняется вызов с эффектом внутри пропущенной части выражения.

Сначала потребитель определяет, какие значения нужны на достигнутом пути, затем запрашивает их. Общего предварительного прохода по всем присваиваниям и скобкам нет. Пропущенная операция не должна позднее исполниться лишь потому, что обходчик дошёл до её записи.

Порядок вычисления действительных аргументов остаётся установленным правилами LMX. Перенос таблицы приоритетов Си не переносит автоматически все особенности или неопределённости порядка вычисления в Си.

### 5.5. Условие `while`

Автором подтверждена следующая пара:

```c
while ((c = getchar()) != EOF)
```

```text
while ((c := getchar()) != EOF)
```

У `while` используется то же `data`, что у окружающего callable. На каждой проверке условия:

1. Сравнению нужно значение сгруппированного присваивания.
2. `getchar()` исполняется один раз.
3. Результат записывается в `c` этого общего `data` и становится значением присваивания.
4. Это значение сравнивается с `EOF`.
5. `while` получает одно логическое значение условия.

Дополнительного именованного аргумента `c` нет. Присваивание не выносится в однократную подготовку перед циклом и не исполняется второй раз при той же проверке.

Проверка на источнике, последовательно возвращающем `A`, `B`, `EOF`: три чтения, два исполнения тела, после последней проверки `c` содержит `EOF`. Тип `c` должен допускать значения символов и `EOF`.

Не объявлять эквивалентной форму `while(c := getchar() != EOF)`. В присваивании с такой правой частью сначала вычисляется сравнение, поэтому присваиваемое значение — его логический результат; кроме того, самостоятельная именованная запись проверяется по контракту аргументов `while`. Исполнение по требованию не отрезает `!= EOF` от правой части.

## 6. Приоритеты и ассоциативность

### 6.1. Основная таблица

Привести к следующему относительному порядку все перечисленные операции, которые уже поддерживаются соответствующим профилем LMX. Сверху — сильнее. Отдельное правило `**` дано в §6.2.

| Уровень                   | Операции                                                                  | Ассоциативность |
| ------------------------- | ------------------------------------------------------------------------- | --------------- |
| Постфиксный               | Вызов, индекс, доступ к полю; постфиксные `++` и `--`                     | Слева направо   |
| Унарный                   | Префиксные `+`, `-`, `!`, `~`, `++`, `--`; существующие адресные операции | Справа налево   |
| Умножение                 | `*`, `/`, `%`                                                             | Слева направо   |
| Сложение                  | `+`, `-`                                                                  | Слева направо   |
| Сдвиги                    | `<<`, `>>`                                                                | Слева направо   |
| Отношения                 | `<`, `<=`, `>`, `>=`                                                      | Слева направо   |
| Равенство                 | `=`, `!=`                                                                 | Слева направо   |
| Побитовое И               | `&`                                                                       | Слева направо   |
| Побитовое исключающее ИЛИ | `^`                                                                       | Слева направо   |
| Побитовое ИЛИ             | `\|`                                                                      | Слева направо   |
| Логическое И              | `&&`                                                                      | Слева направо   |
| Логическое ИЛИ            | `\|\|`                                                                    | Слева направо   |
| Присваивание              | `:=` и существующие составные присваивания, включая `**=`                 | Справа налево   |

Объявленный через `sys\operand` приоритет включается в этот же механизм. Он обязателен; его можно получить по имени другого операнда через `sys\priority` (§8). Специальной шкалы для пользовательских операндов нет.

В LMX `=` остаётся сравнением, соответствующим `==` в Си. Присваивание записывается `:=`. Написание существующих составных присваиваний этой задачей не меняется.

Существующие в машинном профиле преобразования типов и `sizeof` должны быть согласованы с соответствующими отношениями в грамматике Си. Отсутствующие `?:` и оператор запятой вводить не требуется. `,` и `;` сохраняют свои структурные функции LMX.

Таблица задаёт относительный порядок, а не конкретные числовые значения внутренних приоритетов. Получение необходимых значений происходит по §5; низкий приоритет источника значения не запрещает вычислить его до потребителя. Основание для сопоставления с Си — грамматика выражений N1256, §§6.5.2–6.5.16; ссылка в §12.

### 6.2. Исключение: степень `**`

Сохранить действующее Python-подобное связывание:

- вызов, индекс и доступ к полю связывают сильнее `**`;
- `**` связывает сильнее `*`, `/` и `%`;
- цепочка степеней группируется справа;
- слева `**` связывает сильнее унарных `+`, `-`, `~`;
- справа `**` допускает унарный операнд.

Обязательные примеры:

```text
-2 ** 2       → -(2 ** 2)       → -4
(-2) ** 2                       → 4
2 ** -2       → 2 ** (-2)
2 ** 3 ** 2   → 2 ** (3 ** 2)   → 512
2 * 3 ** 2    → 2 * (3 ** 2)    → 18
```

Для `2 ** -2` здесь фиксируется группировка. Числовой результат и допустимые типы определяет числовой контракт LMX; вся числовая семантика Python автоматически не переносится.

Это асимметричное правило нельзя заменить одной строкой «степень выше всех унарных операций». Для остальных унарных операций, не имеющих такого аналога в Python, не приписывать Python выдуманное поведение. Сохранить действующие отношения LMX и явно отразить их в полной таблице реализации.

### 6.3. Приоритеты Си и зависимость по значению

Запись:

```text
1 + v := 2 * 3
```

остаётся структурной цепочкой:

```text
1 plus: v let: 2 mult: 3
```

Ресивер присваивания связан с написанным `v`. Нельзя пересобрать его левую часть в `1 + v` и выдать ошибку «присваивание сумме», ссылаясь на грамматику Си.

Исполнение по текущей норме:

1. Левому `plus` нужен результат связанного с этим вхождением `let`.
2. Для получения результата `let` вычисляет свою правую часть: `2 * 3 = 6`.
3. `let` записывает `v := 6` и возвращает `6`.
4. `plus` вычисляет `1 + 6 = 7`.

Итог определён: **`7` и `v = 6`**, в том числе при другом ранее записанном значении `v`. Нельзя читать прежнее значение только потому, что `plus` имеет более высокий приоритет, чем `let`.

В этом примере явная запись:

```text
1 + (v := 2 * 3)
```

даёт тот же результат и тот же эффект. Это совпадение конкретных вычислений; исходная форма без скобок не получает новый анонимный контейнер в P0.

Для согласованного с Си подмножества проверить:

```text
c := (a := 10) + (b := 20) * 2
```

Сгруппированные присваивания возвращают `10` и `20`; умножение даёт `40`, сумма — `50`, затем записывается `c := 50`. Итог: `a = 10`, `b = 20`, `c = 50`.

Для правой ассоциативности:

```text
a := b := 10
```

внешнему присваиванию нужен результат внутреннего: сначала `b := 10`, затем `a := 10`.

Меняются приоритеты и правила получения значений, а базовая структурная грамматика сохраняется. Допустимость дополнительных форм LMX, запрещённых в Си, сама по себе не противоречит совпадению результатов на общем подмножестве.

Backend получает результат анализа LMX. Текстовая замена `:=` на `=` с передачей исходного выражения Си-компилятору не является реализацией этого требования.

### 6.4. Интерпретация и нативная генерация

Интерпретатор получает результат необходимой операции через общий механизм исполнения и не повторяет уже выполненное в текущем вычислении вхождение.

При статически известных связях транслятор может заранее выстроить последовательность вычислений. Например, для `f(10 * v := 2 + 3)` она состоит из сложения, записи в data `f`, умножения полученного значения на `10` и вызова `f` с одним аргументом.

Вычисление по требованию не требует динамически искать присваивание при каждом чтении переменной. Рабочие результаты исполнения и временные значения нативного кода не должны превращаться в новые постоянные поля чистого графа.

## 7. `sys\name(identificator)`: имя как LMX-строка

### 7.1. Нормативный контракт

> `sys\name(identificator)` принимает написанный идентификатор и возвращает его имя как обычную строку LMX — `Lmx` Array символьных элементов переменной длины. Написание получается из существующего представления канонического имени и служебной таблицы имён.

Пример:

```text
sys\name(foo) → "foo"
```

Ресивер потребляет аргумент **как идентификатор**. Он не разрешает его как переменную, не читает связанное значение, не вычисляет инициализатор и не вызывает Structure или метод. Имя не обязано иметь объявление: «из любого идентификатора» включает любое корректное написание, уже распознанное общим парсером.

Если `foo` — переменная со значением `42`, результатом остаётся строка `"foo"`. Если `foo` — метод или зарегистрированный через `sys\operand:` операнд, получение имени не запускает его исполнение. Для указателя `ptr` возвращается `"ptr"`, а не имя объекта, на который он указывает.

Эта форма принимает один идентификатор. Она не вводит универсального преобразования произвольных значений в текст. Несоответствующий аргумент обрабатывается по существующим правилам недопустимой формы.

### 7.2. Написание идентификатора

Возвращается значение имени после обычного разбора идентификатора. Оформление exact identifier снимается по действующему правилу: внешние обратные кавычки удаляются, удвоенная обратная кавычка внутри становится одной.

```text
sys\name(foo)          → "foo"
sys\name(`foo`)        → "foo"
sys\name(`long name`)  → "long name"
sys\name(`a``b`)       → "a`b"
sys\name(``)           → ""
```

Прочие допустимые символы имени сохраняются. Пустой exact identifier даёт пустой массив символов. Новая кодировка, нормализация регистра или ограничение длины имени не вводятся.

Это получение написания идентификатора из существующего представления, а не сериализация значения переменной или повторный разбор исходного текста.

### 7.3. Представление и получение результата

В текущей норме одно написание представлено одной повторно используемой канонической строкой со стабильным адресом. Имя сущности получается через существующую служебную таблицу. Старую схему отдельных числовых кодов идентификаторов восстанавливать не требуется.

Реализация:

1. Получить каноническое имя написанного аргумента через существующее представление идентификатора и служебную таблицу.
2. Выдать его как обычную строку LMX, используя имеющееся строковое представление.
3. Сохранить обычные контракты владения и доступа к этому представлению.

Результат имеет общий дескриптор `Lmx` и обычный массив `char` переменной длины. Других видов массивов по фиксированности длины текущая модель не вводит. Для `foo` длина результата равна `3`; для пустого имени — `0`. Завершающий NUL не входит в строку LMX.

Использовать существующую строку и служебную таблицу. Новая таблица регистрации, повторное построение написания или обязательная аллокация и копирование на каждый вызов не требуются. Точная выдача ссылки или копии следует существующему контракту строк и служебных имён; это ТЗ не добавляет отдельной гарантии адресного тождества результатов.

Интерпретатор и подготовленный нативный код должны получать одинаковое содержимое и обычный Lmx-результат. Во время трансляции не требуется исполнять код обозначенной идентификатором сущности ради получения её имени.

Основания текущего представления: §4 семантики — канонические имена и служебная таблица; §5 грамматики — bare/exact identifiers; §5 L2 — строки как Array точной длины. Ссылки приведены в §12.

### 7.4. Связь с остальными ресиверами

Полное имя получения строки — `sys\name`. Оно находится непосредственно в `sys`; специальные операции регистрации и запроса приоритета находятся в `sys`.

Контракт `sys\name` потребляет написанный идентификатор. Общее исполнение не должно сначала вычислять этот аргумент как обычное значение или требовать результата зарегистрированного операнда с тем же именем.

Возвращённая строка является одним Array. В обычных вызовах:

```text
f(sys\name(foo))
f(a := sys\name(foo))
```

строка передаётся целиком, соответственно позиционно или по имени. Отменённое правило превращения строки в цепочку символов не применяется.

Для запроса приоритета имя преобразуется в строку явно:

```text
sys\priority(sys\name(foo))
```

Получение строки не вызывает `foo`; запрос приоритета также не вызывает его реализацию.

## 8. `sys\priority`: приоритет по имени

### 8.1. Сигнатура и значение

Контракт ресивера в группе `sys` описать именованной сигнатурой:

```text
fn: PrioritySignature ([]: char name; return: int)
```

У `fn` два аргумента: имя `PrioritySignature` и data-шаблон с входом `name` и полем результата `return`. Это описание сигнатуры; оно не создаёт исполняемый ресивер. Полное имя вызова реализации — `sys\priority`.

`name` — один обычный массив `char` переменной длины, содержащий имя операнда. Результат — `int` с объявленным приоритетом найденного операнда в общей системе expression.

Запрос работает для встроенных и зарегистрированных пользовательских операндов. Полученное число совпадает с тем значением приоритета, которое используется общим анализом выражения для этого операнда.

Запрашивается свойство конкретного именованного операнда. Для `"+"` и `"-"` в этом контракте это приоритет сложения и вычитания; для `"*"` — умножения. Контекстные унарные, префиксные и постфиксные роли анализируются по §6 и сами по себе не меняют результат запроса по тому же имени. Если общий механизм представляет такие роли отдельными операндами, их приоритеты получают по их собственным существующим именам. Имя, которое не позволяет однозначно выбрать операнд, даёт обычную ошибку разрешения; выбирать произвольный уровень по контексту вызова запроса нельзя.

### 8.2. Примеры

```text
sys\priority(sys\name(`+`))
sys\priority(sys\name(foo))
```

Первый вызов получает приоритет встроенного `+`, второй — приоритет доступного зарегистрированного `foo`.

Пример полного объявления:

```text
sys\operand: foo new_op sys\priority(sys\name(`+`))
```

После него запрос приоритета `foo` возвращает то же число, что запрос приоритета `+`. Здесь используются три обычные формы с полными именами; отдельного синтаксиса для выбора «уровня сложения» не требуется.

Имя можно передать любой обычной LMX-строкой с тем же содержимым. Аргумент не обязан быть результатом `sys\name`:

```text
sys\priority("+")
```

### 8.3. Поиск имени и отсутствие эффектов

Строка служит именем для поиска в существующем механизме доступных операндов. Её наличие не регистрирует новый операнд.

Одинаковое содержимое имени должно давать тот же результат и для отдельно созданного массива символов. Нельзя требовать совпадения адреса произвольной пользовательской строки с адресом канонического имени. Приведение строкового имени к существующему представлению имён выполняется на границе этого явного запроса, без изменения обычных правил сравнения уже разрешённых идентификаторов.

Запрос использует ту же видимость и ту же информацию о приоритете, что анализ expression в соответствующем контексте. Расположение самого ресивера в `sys` не ограничивает поиск именами полей этой служебной группы.

Чтение приоритета не запускает `new_op`, не вычисляет её аргументы и не изменяет регистрацию. `sys\name` может получить написание необъявленного имени; `sys\priority` требует, чтобы полученное имя обозначало доступный операнд. При отсутствии такого операнда применяется обычная ошибка разрешения; фиктивный приоритет не подставляется.

### 8.4. Реализация

Использовать существующую информацию о приоритетах встроенных операций и сохранённые значения регистраций пользовательских операндов. Запрос и анализ expression не должны поддерживать расходящиеся таблицы.

Описанный этой сигнатурой ресивер возвращает обычный `int`. Это отдельный служебный запрос, а не функция реализации пользовательского операнда с контрактом `(left: @, right: Array<@>) → @`.

При статически известном имени транслятор может заранее получить известное значение. При вычисляемом строковом имени используется соответствующий обычный механизм поиска. Семантика и результат должны совпадать с интерпретатором.

## 9. Требования к выполнению работ

### 9.1. Общие точки реализации

Перед изменениями определить действующие места, отвечающие за:

- разрешение роли головы и идентификатора;
- регистрацию операнда, его функции реализации и приоритета;
- обработку expression после P0 и связь конкретного вхождения с производящей его значение операцией;
- получение необходимых значений по требованию и однократность в рамках текущего вычисления;
- раздельную подготовку `left` и массива `right`, стандартный приём отсутствующих аргументов и передачу возвращённой типизированной записи потребителю;
- обычное связывание actual arguments с формалами и выбор соответствующего `data` для записи;
- генерацию нативного исполнения;
- получение канонического имени и выдачу его как LMX-строки;
- поиск приоритета по строковому имени в общем механизме операндов.

Обновить эти общие механизмы. Регистрация, применение и запрос приоритета используют одно согласованное представление операнда. `sys\name` использует существующее представление идентификаторов и таблицу имён.

Проверки и вычисления отделять по их контракту. Выбор кандидата обычного вызова не должен многократно выполнять пользовательские аргументы, писать в несколько кандидатных `data` или запускать тела. Для функции реализации операнда применять фиксированный интерфейс из §3.

### 9.2. Перевод старых примеров и требований

Найти и исправить:

- «сначала все скобки, затем присваивания, затем остальные операции»;
- примеры, сохраняющие прежний высокий приоритет присваивания;
- утверждение, что меньший приоритет присваивания заставляет сначала прочитать прежнее или отсутствующее значение его цели;
- требование обязательно добавлять скобки в `f(1 + v := 2 + 3)` ради возможности исполнения;
- обходы, повторно исполняющие уже вычисленный по требованию ресивер или исполняющие пропущенную логическую ветвь;
- превращение встроенного присваивания в дополнительный именованный actual;
- отменённое общее раскрытие Array, в том числе строки, в аргументы вызова;
- допущение реализации без требуемого контракта и обратное устаревшее требование объявлять исполняемую функцию через `fn`;
- старый единственный массив `args` вместо раздельных `left` и `right`;
- старые формы `fn` без обязательного имени сигнатуры и отдельную внешнюю позицию результата вместо поля `return` внутри data-шаблона;
- регистрацию пользовательского операнда без приоритета;
- старые полные имена `operand`, `priority` и `string` в примерах этих новых ресиверов.

Полные имена текущей редакции: `sys\operand`, `sys\priority` и `sys\name`. Имя `PrioritySignature` в §8.1 обозначает описание сигнатуры; вызываемый ресивер сохраняет имя `sys\priority`.

Существующие правила обработки единственной обычной Structure не заменять отменённым расширением на Array. Из P0 или исходного графа никакие контейнеры ради передачи операндов не удаляются.

Если в документах сохранены исторические цитаты, отделить их от действующей нормы. При исправлении примеров проверять итоговое значение, записанные значения и число эффектов. Добавление скобок не должно незаметно подменять требуемый эффект.

Согласовать места, называющие expression «чистым»: они не должны случайно запрещать уже допускаемые присваивания и вызовы с эффектами. Действующие ограничения отдельных профилей описать отдельно.

### 9.3. Диагностика

Проверять регистрацию по полному контракту: имя операнда, исполняемый метод/Structure с двумя входными местами `left: @` и `right: Array<@>` и результатом `return: @`, обязательный целочисленный приоритет. Контракт описывает именованная сигнатура `fn: OperandSignature (@: left; []: @ right; return: @)`. Проверка использует общий admission с учётом данных вызываемого кода. Одно описание сигнатуры без реализации или исполняемый кандидат с неподходящим интерфейсом не является подходящей целью регистрации. Наличие и отсутствие входов проверяются стандартным механизмом, без специальной политики операнда.

Для незарегистрированного `foo` не имитировать регистрацию по факту разрешения обычного имени. В `sys\priority` сообщать об отсутствии операнда по переданному имени; в `sys\name` отсутствие объявления у корректного идентификатора ошибкой не является.

Ошибки присваивания описывать через реальное место и правило LMX. Существующую диагностику неоднозначности обычных вызовов сохранять в её действующей области применения; отдельная передача `left` и подготовка массива `right` не вводят нового выбора между «целым массивом» и «раскрытой цепочкой».

| P01 | `2 + 3 * 4`                                                      | `14`                                                                   |
| P02 | `(2 + 3) * 4`                                                    | `20`                                                                   |

Для поддерживаемых сдвигов, сравнений, побитовых и логических операций добавить минимальные проверки границ соседних уровней таблицы. Не ограничиваться арифметикой, оставляя остальные уровни по прежней схеме.
