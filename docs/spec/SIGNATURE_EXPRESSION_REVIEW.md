# Ресиверы, DATA, Expression и границы сигнатуры

**Авторские уточнения от 24 ноября 2026 года.** Способ потребления аргументов определяется собственным договором конкретного ресивера. Модификаторы всегда потребляют аргументы как DATA. Объявление сигнатуры `::` также рассматривает все свои аргументы исключительно как DATA. Expression выполняется как CODE; безымянные Structures могут выполняться в CODE и Expression, но никогда не вызываются как функции.

Документ исправляет прежнее смешение роли окружающего материала, смысла ресивера, договора его аргументов и выполнения выражения. Раскрытие Structure или структуры по ссылке в список полей — общий механизм, которым `::` пользуется для DATA-деклараций. Отдельный селектор DATA/VALUE, самостоятельный `eval` правой части внутри `::` и особое раскрытие списка TYPE у `->` не вводятся.

## 1. Правило выводится из договора конкретного ресивера

Разрешённый ресивер сохраняет собственный смысл. Системная функция не становится объявлением одноимённой пользовательской Structure из-за внешнего DATA. Декларационный ресивер не становится обычным пользовательским вызовом из-за внешнего CODE: `::` продолжает объявлять сигнатуру, `const` задаёт константность, `private` — доступность.

Это не означает одинакового поведения всех ресиверов. Их существующее разделение по потреблению аргументов сохраняется:

| Группа или конкретный ресивер | Потребление аргументов |
| --- | --- |
| Модификаторы, в том числе `const`, `private`, `immutable`, `independent` | Всегда DATA, по конкретному договору модификатора. |
| Объявление сигнатуры `::` | Только DATA: объявляемое имя и одно цельное описание сигнатуры. |
| Ресивер уровня `L2` | DATA по собственному договору уровня. |
| Обычные callable и ресиверы с CODE-аргументами | CODE с сохранением предусмотренных договором ролей отдельных аргументов. |
| `import`, `copy`, `merge` | Собственный CODE-договор источников и потока полей независимо от размещения записи. |
| Переданная форма объявления места | Сохраняется как DATA-аргумент по договору принимающей операции; её инициализатор не запускается самой передачей. |

NAME, TYPE, шаблон, тело и готовое значение описывают назначение материала внутри договора конкретного ресивера. Они не дают внешнему контексту права заменить этот договор. В частности, NAME слева у `::` — имя объявления, потребляемое в DATA, а не существующая переменная для вычисления.

`return` сохраняет свой отдельно описанный договор результата и передачи управления. Данное уточнение не сводит его или другие специальные ресиверы к обычным функциям. Основания: [инвариантность ресивера](LMX_semantics.ru.md#receiver-context-invariance), [группы потребления аргументов](LMX_semantics.en.md#two-kinds-of-receivers), [формы объявлений как аргументы](LMX_semantics.en.md#declaration-arguments).

### Общее раскрытие списка и роль его элементов

Если принимающий договор требует список полей или деклараций, общий механизм namespace читает непосредственные поля переданной Structure либо структуры, полученной по ссылке. DATA/CODE определяет, **как потребляются элементы списка**, а не создаёт отдельный способ обхода контейнера. Модификаторы и `::` используют DATA; другие получатели следуют своим договорам. Если требуется одно целое значение или модель TYPE, структура принимается целиком. Вложенные контейнеры не раскрываются рекурсивно.

Это обобщение не является автоматическим переносом CODE-выбора W/E в DATA. W/E сравнивает альтернативные внешние списки фактических аргументов при выборе вызова. Чтение полей уже принятого DATA-описания происходит по выбранному договору; оно не запускает повторный выбор арности. Иначе, например, вариативный модификатор мог бы одновременно принять одну группу и несколько её деклараций и получить искусственную неоднозначность. [Общее потребление списка](LMX_semantics.en.md#receiver-structure-sequences), [общий namespace](LMX_semantics.en.md#data-root-declaration-execution), [потоки полей](LMX_semantics.en.md#composition).

## 2. Что именно делает `::`

```lmx
S :: (int: x; int: y; return: int)
```

`::` потребляет объявляемое имя `S` и DATA-Structure с описанием входов и результата. Его DATA-договор требует список деклараций, поэтому **общий механизм раскрывает переданную безымянную Structure в этот список**. Если предоставлена ссылка на DATA-шаблон, тот же механизм проходит по ссылке и читает непосредственные поля шаблона. Без такого шага содержимое шаблона не стало бы объявлением сигнатуры.

Внешне написан один правый структурный аргумент; его поля потребляются как декларации входов и результата через общий механизм, без исключения по имени `::`. Это раскрытие списка DATA, а не вызов структуры, CODE-выбор W/E или дополнительный профиль TYPE-tail для `->`. DATA-роль сама по себе не запрещает раскрывать принятый материал. Вложенные модели и структурный `return` сохраняются целиком: раскрывается уровень описания, а не все вложенные поля рекурсивно.

```lmx
S :: (int: x touch(); return: int)
```

`touch()` остаётся написанным инициализатором описанного формального параметра. Создание сигнатуры не запускает этот инициализатор и не заменяет формальную декларацию его результатом. Это конкретный DATA-договор `::`.

Готовое описание также передаётся как DATA:

```lmx
S :: (int: a; int: b; return: int)
F :: S
```

`F` сохраняет позиционные требования и публичные метки готового описания `S`. Для уже готовой сигнатуры используется её существующий позиционный профиль; раскрывать её служебное физическое представление как новые формальные параметры не требуется. Ни одна из этих строк не создаёт исполняемое тело функции.

В библиотеке `FxSignatures\make` уже создаёт DATA, выполняет `Built :: data` и возвращает `Built`: [исходник](patterns/LMX_Fn_Receivers/src/generic_functions.lmx). Конструктор `->` использует тот же построитель: [исходник](patterns/LMX_Fn_Receivers/src/fn_operand.lmx). Полученное описание не требуется снова отражать через `signature(result)`.

Внутри `::` нет отдельной CODE-ветви, решения «попробовать вычислить, затем прочитать как DATA», классификации по наличию деклараций или проверки буквального имени производителя. Его действия выводятся из собственного DATA-договора.

## 3. Expression, приоритеты и короткая запись

Группировщик Expression определяет операции, их группы и зависимости по исходному дереву и готовым приоритетам. Отдельный шаг анализа Expression затем готовит один `left` и массив ссылок `right`. Эта асимметрия сохраняет компактный принцип `head: arg0 arg1 arg2`; публичный шаблон не меняется. `::` имеет `sys\priority(":=")`, `->` — `sys\priority("+")`. Поэтому целое выражение конструктора относится к правой части объявления:

```lmx
f :: (int -> int int)
```

```lmx
f :: int -> int int
```

Это независимые формы одного примера: два входа `int`, результат `int`. Построение описания принадлежит конструктору `->` в общем Expression; `::` потребляет предоставленное описание как DATA. Оно не переключает свой режим, чтобы самостоятельно вызвать конструктор. Все последствия приоритетов относятся к общей политике Expression, а не к исключению для сигнатур.

P0 сохраняет написанную группу. Равенство результата этих форм не означает тождества исходных деревьев или удаления DATA-контейнера. Сигнатура остаётся описанием; её получение не создаёт тело и не добавляет неявное каррирование. [Группировщик и подготовка применения](EXPRESSION_GROUPING.md) описаны отдельно, с примерами вложенных выражений и последовательностей текущего уровня.

| Независимый пример | Упорядоченные входы | Результат |
| --- | --- | --- |
| `f :: (int -> int int)` | `int`, `int` | `int` |
| `f3 :: (int -> int int int)` | `int`, `int`, `int` | `int` |
| `fNested :: int -> (int -> int)` | `int` | Одна сигнатура `int -> int` |
| `` f0 :: `->`(int) `` | Нет | `int` |
| `fModel :: int -> Model` | `int` | Полное требование доступной модели `Model` |
| `fReady :: ReadySignature` | Из готовой сигнатуры | Из готовой сигнатуры |
| `fData :: (int: x; int: y; return: int)` | `int`, `int`, метки `x`, `y` | `int` |

Модели и готовые сигнатуры предполагаются доступными и допустимыми. В последовательности конструктора может быть любое допустимое конечное число TYPE; последний задаёт результат. Голая форма `f :: int int int` не вводится.

### RAW не равен DATA

`PASS_ARGS_AS_IS 1` — отдельный договор передачи исходных вхождений без предварительного выполнения. Он не является универсальным обозначением DATA-роли. Из того, что `::` потребляет DATA, нельзя вывести значение этого поля у builtin `::` или приписать ему самостоятельный `sys\eval` правой части.

Реализация и объявление режима builtin `::` не поставлены в этом комплекте. Поэтому неподтверждённое назначение ему `PASS_ARGS_AS_IS=1` удалено. Общий RAW-договор остальных операндов сохранён. Приоритеты определяют связывание операций; точная реализация их общего выполнения проверяется на реальном трансляторе, а не подменяется специальной ветвью `::`. [Общий RAW-договор](LMX_semantics.en.md#raw-operands).

## 4. Безымянная Structure выполняется, но не вызывается

У безымянной Structure нет вызываемой головы. В CODE она выполняется на месте в текущем исполнении; в Expression её содержимое обрабатывается общим механизмом выражения. Сама группа не создаёт отдельного вызова, DATA вызываемой функции, нового call frame или неявной обёртки-callable. Обычная вложенная область видимости сохраняет собственные правила.

| Материал | Что происходит |
| --- | --- |
| `(2 + 3)` в исполняемой позиции Expression | Выполняется выражение; отдельного вызова группы нет. |
| `(tick())` в исполняемой CODE-позиции | Группа выполняется на месте; вызывается только явно написанная `tick()`, если её договор допускает этот вызов. |
| `()` в CODE | Присутствующая пустая группа не выполняет действий и не создаёт вызова. |
| `(int: x; return: int)` как DATA-описание для `::` | Общий механизм читает список деклараций из Structure по DATA-договору сигнатуры; эти декларации не выполняются как тело. |
| Группа как аргумент другого ресивера | Применяется договор именно этого ресивера; скобки сами не выбирают DATA, CODE, вызов или раскрытие. |

Само чтение пути, хранение формы или её RAW-передача не запускает содержащиеся вызовы. При фактическом потреблении системные и обычные операции сохраняют собственные договоры. Поэтому прежняя фраза «системная функция в DATA объявляет одноимённую Structure» неверна, но и противоположное утверждение «нахождение вызова в группе заставляет немедленно выполнить её» не является правилом языка.

При фактическом обходе чистого графа в CODE/Expression ссылка на Structure разрешается к тому же узлу. Безымянный узел является группой. Именованный узел является группой только при другом фактическом `parent`; совпадение с лексическим `parent` разбираемого выражения означает обычную обработку вызова/ресивера. Признак ссылки или исходные скобки не заменяют эту проверку. [Точная развилка](LMX_semantics.en.md#expression-structure-parent-guard), [алгоритм](EXPRESSION_ALGORITHM.md).

## 5. Границы аргументов и принимающий договор

```lmx
int -> int int
int -> (int int)
```

В первой строке справа два аргумента. Во второй справа одна целая Structure в позиции полного TYPE. Группировщик и подготовка применения сохраняют этот договор; сборщик получает `[int, целая группа]`. Допуск группы как полного TYPE проверяется отдельно. Она не становится автоматически кортежем, двумя формальными параметрами или каррированным результатом. Это не исключение из-за написанного `int` слева: различается потребление целой модели и последовательности.

| Фрагмент | Правые вхождения |
| --- | --- |
| `int -> int int` | Два отдельных TYPE-вхождения. |
| `int -> (int int)` | Один структурный аргумент. |
| `int -> (int -> int)` | Одно вложенное выражение, дающее один полный TYPE результата. |
| `int -> ()` | Один присутствующий пустой структурный аргумент; не пустой вектор `right`. |
| `int -> ((int int))` | Один целый внешний контейнер; дополнительных раскрытий нет. |
| `(a b) := (((x y)))` | Единственная Expression-группа нормализуется к `(x y)`; последовательностный договор получает два элемента `x`, `y`. |
| `(a b) := (((x y))) z` | Два соседних элемента: нормализованная подгруппа `(x y)` и `z`. |

Таблица фиксирует границы, а не обещает допуск всех групп как TYPE. Нульарная сигнатура записывается `` `->`(int) ``; `int -> ()` не является её сокращением. У `Name :: A B` два внешних правых вхождения, у `Name :: (A B)` одно DATA-описание, из которого общий механизм читает непосредственные декларации. Предыдущая неподтверждённая иллюстрация раскрытия TYPE в `(int int) -> ((char char))` снята: одна форма левого аргумента не разрешает раскрывать модель справа. [Точная норма текущего уровня](LMX_semantics.en.md#operand-right-only-opening).

Для группового присваивания прежнее наблюдение о единственной правой группе следует из общего плана: `(a b c) := (a c b)` даёт две последовательности текущего уровня; подготовка применения упаковывает левую в один actual, а справа оставляет три значения. Три соседние материальные группы дают три подгруппы; внутренние Expression-операции и одиночные оболочки обрабатываются рекурсивно. Дополнительного прохода у адаптера нет: он получает уже нормализованный план. Для целого TYPE в таблице сохраняется его собственный договор, а не переносится последовательностное потребление. По той же причине `(a b c) := copy(d)` принимается без оболочки вокруг уже выданного потока полей.

## 6. Как `::` использует общий механизм

Общий разбор Expression, разрешение операций и политика приоритетов выполняются общим механизмом. Следующий фрагмент показывает только собственный DATA-договор `::`; имена вспомогательных функций обозначают внутренние шаги, а не новые публичные ресиверы.

```python
def consume_signature_declaration(data_left, data_right):
    name = require_declaration_identifier(data_left)
    whole_description = require_one_data_description(data_right)
    source = resolve_data_reference_without_call(whole_description)

    # Общий механизм чтения DATA, без вызова группы, формальных
    # инициализаторов или собственного eval правой части.
    if is_ready_signature_description(source):
        description = existing_positional_profile(source)
    else:
        declarations = namespace_field_sequence(source, role=DATA)
        description = describe_signature_declarations(declarations)

    return declare_constant_signature(name, description)
```

Проверка `is_ready_signature_description` относится к уже предоставленному описанию. Она не выполняет источник, чтобы узнать его тип. `namespace_field_sequence` обозначает общий механизм чтения непосредственных полей Structure/структуры по ссылке после выбора принимающего договора. У `::` этот договор задаёт DATA-список деклараций; модификаторы пользуются тем же принципом со своими действиями над декларациями. `describe_signature_declarations` читает полученный список по правилам входов и результата; вложенные TYPE/модели и инициализаторы не раскрываются и не запускаются. Ошибка допуска не вызывает повторного прочтения исходника в другом режиме.

Для `copy`, `merge`, `import` или другого ресивера применяется его собственный договор, а не алгоритм `::`. В частности, при потреблении вычисляемого источника потока полей его явный вызов может исполняться по CODE-договору этой операции. Это не основание вводить CODE-ветвь сигнатурного объявления или выполнять прочие поля DATA.

## 7. Проверки и пределы реализации

Повторный обзор сравнительных исходников и копий охватил 315 физических LMX-файлов, 513 LMX-блоков Markdown и 504 записи кода в JSON. После согласования группировщика в R02 убрана лишняя оболочка: `(a b) := copy(Pair)`; полный размер уменьшился с 95 до 93 непробельных символов. Обновлены его копии и обе стилевые метрики общего исходника. Такое же сокращение сделано в двух библиотечных примерах и combined-сборке. Библиотечный обзор охватил 40 исходных файлов, 48 частей сборки и 224 API-варианта.

Отдельно исправлены извлечение DATA-метаданных каталога, захватывавшее CODE предыдущего метода, и сохранение авторских описаний при повторной синхронизации. Тела библиотечных алгоритмов LMX этой коррекцией не изменены. [Приёмочные случаи сигнатур](validation/signature_expression_cases_20261124.json) и [случаи группировщика](validation/expression_grouping_cases_20261124.json) фиксируют примеры, границы и отрицательные проверки. [Отчёт обзора](validation/grouping_review_20261124.json) содержит результаты статической проверки и отдельно отмечает отсутствие исполнения реального LMX.

**Парсер, транслятор, builtin `::` и runtime отсутствуют в пакете и не запускались (`NOT_RUN`).** Документация фиксирует авторские правила; статический обзор не выдаётся за подтверждение их реализации.
