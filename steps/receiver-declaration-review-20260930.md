# Объявление без неявного merge: проверка общих правил

Дата: 2026-09-30. Источник решения — [Q56](../LMX_blog/q/q56.md), последняя
реплика автора. Это исследование, не новая нормативная спецификация.
Проверены документы и текущий код рабочего дерева `build/opus_wt` на базе
`de88f38` с незакоммиченным общим resolver/native/runtime WIP.
После нового решения семантических изменений в коде не делали.

## Уже определено автором

- `int: b: 5` при неизвестном b имеет смысл прежнего `int: b 5`:
  int задаёт явный тип, b объявляется, 5 — его начальное значение.
- `A: b` при неизвестном b больше не выполняет `merge(A, empty)`:
  объявляется пустая типизированная ссылка, экземпляр A не создаётся.
- Общая вложенность `a: b: c: d: ...` остаётся общим механизмом.
- Удаление `@` из L3 пока является предположением, а не принятым решением.

Из этого не следует изменение самого `merge`, создание скрытого графа,
передача Structure по значению или удаление машинного `@` из L2.

## 1. Разбор не препятствует изменению

Проверка существующим `build/fable127_printTree/printTree.exe`:

```text
int: b 5       -> Frame int [atom b, atom 5]
int: b: 5      -> Frame int [Frame b [atom 5]]
int(b: 5)      -> Frame int [Frame b [atom 5]]
int:           -> Frame int [Frame b [atom 5]]
    b: 5
---
a: b: c: d     -> Frame a [Frame b [Frame c [atom d]]]
```

Значит новая запись уже имеет обычное дерево. Внешний ресивер получает его
полностью; внутреннее неизвестное b не надо сначала исполнять как отдельное
присваивание и отвергать за неизвестность. Принимающий контракт определяет
имя, явный тип и кандидат. Согласованные два варианта int дают одну операцию
объявления/инициализации, не требуют подмены текста в парсере.

Не надо из этого выводить равенство всех списков и вложенных применений:
при вызываемой голове `f(b: c)` — один именованный аргумент, а `f(b c)` —
два позиционных. Существующие правила получателя и разрешения имён сохраняются.
Это существенно и для b уже известного: новая инициализация неизвестного
имени не разрешает превратить произвольный вызов в объявление.

Происхождение замера: старый готовый printTree от 2026-09-23, SHA256
`0956054E093428CF4FAE060DA0A2FCF6C47C565F2231182683178B3845202040`;
исходник пробы — `build/receiver_declaration_probe_20260930.lm2`.
Это диагностическое свидетельство формы, не свежий gate парсера текущего HEAD.
В той же пробе `a[i]\[j]\[k]` сохраняет все индексные/backslash-токены,
а `a[i]\[j]: 5` приходит как Frame с составной головой.

## 2. Главное неразрешённое столкновение: привязка и вызов

```text
A: b
b: c
b()
```

Первой строкой теперь не создан вызываемый экземпляр A. Но прежнее правило
callable-first считает привязку, разрешённую как callable, целью вызова,
а не присваивания. Если этот признак следует из типа A и для b, вторая
строка не заполняет ссылку. Уже известное b в `A: b c` также не объявляется
повторно: по прежней норме это вызов A с аргументами b и c.

Нужно одно общее решение, не переключение операции по признаку null:

- либо b остаётся вызываемой привязкой и для её записи нужен явно
  определённый ссылочный путь;
- либо b — перепривязываемая ссылка, а вызов полученного значения выбирается
  общей операцией доступа/вызова этого значения.

Второй вариант не позволяет молча различить `b()` и `b: ()`: все формы
одного применения по-прежнему синонимы. Первый не позволяет делать
«первый раз присваивание, после заполнения вызов». Решение не выбрано.

Норма: [семантика §9](../docs/LMX_semantics.ru.md#construction),
[§11](../docs/LMX_semantics.ru.md#callables). Код: `l2_colon_bound_before`,
`l2_check_struct_call`, `l2_check_body`, `l2_colon_bind_shape`.

## 3. Пустая ссылка, отсутствующее поле и пустая Structure различны

`A: b` оставляет объявленное место b и его типовой контракт A. Оно не создаёт
полей A. Реальная `()` — существующий дескриптор пустой Structure; отсутствие
объявления b — ещё один, отличный случай. Аналогично несвязанная ссылка на
Array не равна существующему Array длины 0; `length` нельзя молча возвращать
0 для отсутствующего дескриптора.

В коде прямой Structure-слот уже может содержать пустую ссылку:
`l2_own_is_slot`, `l2_emit_cell_new`, `lmx_walk_work_make`.
Дополнительная pointer-ячейка или скрытый экземпляр A из этого не следуют.
`@:` сегодня использует другое представление; переносить его автоматически
нельзя. Физическая возможность пустого слота не определяет поведение чтения.

Для прежнего `@:` спецификация требует связывания до первого чтения.
Естественное сохранение этого контракта — ошибка использования несвязанного b,
без ленивого `merge`, подстановки A и автоматического превращения в `()`.
Нельзя без решения заменить это nullable-значением с новой семантикой None.

`implements` должен получать описание A из объявления/принимающего контракта,
а не пытаться восстановить его по отсутствующему референту. Нулевой ребёнок
Consumer сейчас пропускается в `lmx_implements_walk`/`lmx_implements_through`:
подставить null вместо типового требования означало бы потерять проверку.
У транслятора уже есть метаданные объявленной модели и явный операнд допуска
(`l2_rw_admit`, `l2_emit_admit`, `l2_nsp`); новый реестр имён не нужен.

## 4. Что упрощается без противоречия

Формал `(A: b)` уже описывает принимающее место, не строит A при определении
или вызове. `test(c)` проверяет `implements(c, A, Consumer)` и передаёт
дескриптор, не непримитивный объект по значению. Объявление с кандидатом
`A: b c` при неизвестном b уже имеет тот же смысл. Новое объявление без
кандидата убирает различие между этими случаями, а не требует новой модели
формалов или нового bind-оператора.

Примитив по-прежнему передаётся как значение. Связывание существующей
Structure/Array сохраняет её идентичность, parent, native и backing;
объявление ссылки не переподчиняет референт. Явный `merge` остаётся способом
получить отдельное значение; буквальное определение Structure тоже не
исчезает. Рекурсивный ссылочный тип не требует рекурсивного создания всех
возможных потомков при одном объявлении ссылки.

Код: `l2_typed_formal`, `l2_check_call`, `l2_check_bind`, `l2_rw_call`,
`l2_rw_model_bind`. Базовый Array ABI и механизм native/walker этим
изменением не затрагиваются.

## 5. Квалификаторы и вычисляемый кандидат

```text
const: A: b
immutable: A: b
independent: A: b
```

Теперь здесь нет автоматически построенного A. По действующей норме const
защищает привязку — значит нельзя молча разрешить ей одну позднюю запись;
immutable квалифицирует значение, а independent задаёт parent создаваемого
корня. Нужно определить результат этих общих композиций над несвязанной
ссылкой. Возможные последовательные решения — квалифицированный контракт
будущего кандидата либо отказ там, где требуется реальное значение.
Ни один вариант не должен неявно вернуть merge. Не выбран новый смысл.

`int: b: 5` определён автором. Для `int: b: getValue()` надо одновременно
сверить действующее правило [§12](../docs/LMX_semantics.ru.md#dynamic):
вычисляемая инициализация записывается объявлением и отдельным присваиванием,
вызов остаётся в полном графе. Если общий вложенный вариант допускается,
он обязан сохранить это разделение места значения и исполняемого оператора,
не превратить вызов в данные или скрытую однократную фазу. Это граница
действующего текста, не повод сделать особый парсер для литерала 5.

## 6. Уходит ли @ из L3

Отпадает первоначальная необходимость писать `@: A b` только ради
отказа от создания A. В документах обсуждались и самостоятельные возможности:

- ссылка на примитивную ячейку вместо копирования её значения;
- ссылки большей глубины;
- получение ссылочной идентичности без вызова/вычисления результата;
- различение привязки и вызываемого референта из раздела 2.

`int: x 5` / `int: y x` даёт копирование значения, не псевдоним ячейки x.
Но возможность добавить псевдоним не доказывает необходимость его в L3.
Не найдено требования ядра L3, которое заставляло бы переносить туда
ссылки на примитивные ячейки или большую адресную косвенность. Примитивы
могут оставаться значениями, Structure/Array — обычными ссылочными значениями;
явное изменение общего состояния уже выражается путём к полю/элементу.

Важная поправка к предварительному выводу Codex: нельзя ссылаться на
работающие адресные операции L2 как на якобы уже необходимую возможность L3.
В текущем `l2_rw_ref_bind` высокоуровневый маршрут ограничен ссылкой на
существующую Structure, а `l2_rw_stmt` после `l2_own_ref_decl` отправляет
остальные @-формы в отказ машинной операции. Универсальная primitive-alias /
reference-to-reference возможность L3 этим кодом не доказана.

Таким образом, перечисленные возможности сами по себе не удерживают @ в L3.
Решение об удалении из L3 остаётся открытым до согласования привязки и вызова;
машинные операции @ в L2 остаются без изменений. Не вводится обязательство
в будущем вернуть в L3 адресные возможности L2.

## 7. Старые противоречия, обнаруженные при проверке

Они не порождены новым предложением; использовать их как норму нельзя.

1. Семантика §12 сначала разрешает `@value` в L3, затем таблица запрещает
   `@x`, а следующий абзац снова запрещает prefix address-of. Грамматика
   дополнительно запрещает глубины `@@:`, разрешённые той же семантикой.
   Последние авторские решения нужно провести по всем связанным абзацам.
2. Семантика §9/L2 §18.1 ещё пишут `@fresh -> Lmx**`, тогда как L2 §18.2,
   CORE и Q26.2 адресуют сам референт Structure, не child-slot. Это старая
   несогласованность смысла адресуемого объекта.
3. CORE §4 сохраняет старый приоритет callable до объявления и описывает
   Model как non-callable, хотя обычная именованная Structure вызываема.
   Он также ошибочно называет `Model: fresh` при известном fresh присваиванием.
   Семантика §9 уже различает отсутствие и присутствие правого имени.
4. `lmx_copy_value` копирует прямую ссылку на Structure вместе с её целью,
   но pointer-ячейку @ копирует с удержанием прежнего изменяемого pointee;
   это закрепляет `lmx_copy_ptr_share_selftest`. Текущий §20 требует копии
   достигнутого обычного изменяемого графа. Поэтому нельзя реализовать новое
   A:b просто переименованием старого @-пути: так незаметно выбирается одна
   из разных политик копирования. Типизированная ссылка сама по себе не
   означает shallow-copy при явном merge.
5. `lmx_merge_profiles_owned` всё ещё создаёт корень с пустым native
   независимо от сохранности кода; §20 требует сохранять native неизменного
   тела. Это отдельный уже существующий дефект, не следствие пустой ссылки.

## 8. Точная граница будущей реализации

Удалять неявное построение необходимо одновременно из:

- native-ветви объявления Model:fresh в `l2_emit_stmts`;
- `l2_rw_model` и его `lmx_walk_merge_model` в walker;
- конструкции Model-поля внутри named Structure (`l2_take_ns_body`, kind 3);
- анализа merge-отказов `l2_body_throws` и расчёта scratch `l2_merge_nested`.

Сохранить регистрацию объявления и модели, admission кандидата, явный merge,
явное создание `()`, обычный граф операторов, правила аргументов и публикации.
Тесты, которые после одного Model:fresh читают скопированные поля модели
или требуют merge-failure, больше не доказывают новую норму. Примеры:
`unit_model_fresh_synonyms`, `unit_colon_model_decl`,
`unit_typed_decl_vertical`, `unit_named_struct_exec_instance`.

Обязательные свидетели: синонимы int-инициализации; пустое типизированное
место без merge; обязательный допуск кандидата и сохранение его идентичности;
неуспешный допуск без изменения прежней привязки; согласованное чтение/вызов
несвязанного значения; известные имена без fallback в объявление; явный merge
создаёт отдельный объект; формалы и defaults; поля/locals/вложенные тела;
native/walker; квалификаторы и выбранный контракт ссылочных операций.
