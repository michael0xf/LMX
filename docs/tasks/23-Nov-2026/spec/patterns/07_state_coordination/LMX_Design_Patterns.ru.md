# LMX: Координация состояния: Message и общая память

Java показывает мониторы, volatile и TLS; Rust — Mutex/RwLock, OnceLock и безопасные области доступа. Они делают видимыми свойства, которые у LMX заменяются владением Message, а не исчезают бесплатно.

Все шесть исходных паттернов сохранены отдельно. LMX-альтернатива через Message обеспечивает выбранные наблюдения, но не притворяется shared-memory RW lock, DCL fast path или OS-thread-local storage. Различия параллелизма, affinity и latency указаны по каждому примеру.

## Каталог

### 065. [Read-Write Lock](065_read_write_lock_comparision.md)

Чтение согласованного снимка при исключении пересечения с изменением.

**Сценарий:** Начальное значение 10. Прочитать, записать 20, прочитать снова; затем рассмотреть одновременно пришедшие чтения.

**Наблюдение:** Последовательный сценарий даёт 10,20. Java/Rust допускают параллельных читателей; LMX owner обслуживает их последовательно.

Это функциональная альтернатива для согласованных скалярных чтений, а не реализация самого RW-lock на L3. Параллельный доступ к большому неизменяемому снимку можно вынести в отдельный протокол.

### 066. [Double-Checked Locking](066_double_checked_locking_comparision.md)

Безопасная однократная ленивая инициализация при конкурентных обращениях.

**Сценарий:** Два клиента одновременно запрашивают ресурс; factory строит значение 42 и считает вызовы.

**Наблюдение:** Оба получают 42; factory вызывается один раз. Java использует volatile+DCL, Rust — OnceLock, LMX — единственного владельца.

У LMX отсутствует необходимость двойной проверки, потому что конкурентные клиенты сериализованы у owner. Это смена механизма при той же цели once-only. В Java volatile обязателен для выбранного DCL; Rust использует готовую корректную примитиву.

### 067. [Guarded Suspension](067_guarded_suspension_comparision.md)

Запрос получает результат только после выполнения предиката готовности.

**Сценарий:** Два клиента ждут значение; publish(7) делает его готовым и завершает оба ожидания.

**Наблюдение:** До publish ответов нет; после — оба клиента получают 7. LMX owner продолжает обслуживать publish, пока запросы ждут.

Java/Rust освобождают lock во время ожидания и повторно проверяют predicate. LMX сохраняет запрос и завершает turn, позволяя publish дойти до владельца; это событийная форма guarded wait.

### 068. [Balking](068_balking_comparision.md)

Если действие уже началось, повторный запрос сразу отказывается от выполнения.

**Сценарий:** Начать сохранение, повторить start до finish, завершить, затем снова start.

**Наблюдение:** Результаты start: 1,0,1. Второй запрос не создаёт дополнительной работы.

Balking возвращает отказ, тогда как Guarded Suspension сохраняет ожидание. LMX делает проверку и изменение флага в одном turn; Java/Rust используют atomic compare-and-set.

### 069. [Thread-Local Storage](069_thread_local_storage_comparision.md)

Изоляция счётчика внутри конкретного исполнителя.

**Сценарий:** Участник A вызывает next дважды, участник B один раз.

**Наблюдение:** A получает 1,2; B получает 1. В LMX участник — Message; в Java/Rust — OS/Java thread.

Message-local state сохраняется при миграции turn на другой OS worker. Это полезная альтернатива task/actor-local state, но не тождество TLS: для thread-affine native ресурса нужна именно политика привязки к OS thread.

### 070. [Monitor Object](070_monitor_object_comparision.md)

Объект защищает инвариант всей операции над своим состоянием.

**Сценарий:** Баланс равен 10. Два клиента запрашивают withdraw(7); проверка и списание должны быть одной операцией.

**Наблюдение:** Ровно один запрос успешен; итоговый баланс 3. Отдельные read+write этим свойством не обладают.

Последовательный turn позволяет выражать владельца-инвариант без пользовательского lock на L3. Это не распределённая транзакция: другой владелец не включается в ту же атомарную операцию автоматически.
