Принял разбор C/D/c1/c3/c4 и поручение автора о `fn: prepared` и `fn: new_name merge(f1, f2)`. Обе реплики автора записаны в журнал 2026-11-09 дословно, рядом — пояснение с исправленными примерами. D веду по варианту 1 без стопа: примитивы, формалы и data-блоки — места графа; namespace каждого обхода заново связывает имена; вычисляемый инициализатор публикуется как сейчас.

Работа разбита на два среза одного pipeline.

332 — представление и namespace.
- Построитель: каждый Frame становится Lmx с именем головы (строка таблицы адрес -> name), поля — аргументы. fn/sub -> Lmx "fn"/"sub" [name, args, return, var, body], var автозаполняется для позиционной записи с телом. Примитивы и data-блоки — как сейчас. fm не поддерживается и отказывает явно.
- Потребители (интерпретатор, транслятор, печать, копия/merge): голова берётся из таблицы имён, аргументы — с поля 0. У каждого обхода — namespace из чистых таблиц: имена fn/sub действуют на весь блок, места и data-блоки связываются по порядку. Применение ресивера fn/sub к аргументам декларации создаёт F — Lmx в lmx:result с именем по значению аргумента name и именованными ссылками args/return/var/body на аргументы декларации. Для return-слова — общая ссылка на примитив, как lmx_graph_ref_int, без обёртки [int]. Вызов распознаёт F по адресной классификации, не по форме.
- Свидетели: все прежние проверки на новом представлении; два независимых обхода одного графа (новые адреса F, те же ответы); обход после изменения графа отражает изменение; декларация после обходов неизменна.

333 — применение fn общим связывателем.
- Свидетели: `fn: prepared`; `fn: new_name merge(f1, f2)` с f2 без body (тело f1, сигнатура f2, имя new_name, вызов, f1/f2 целы); `fn: name := "test"; …`; коллизия callable name; однократное вычисление фактических до эффектов. В native раздельно: caller, применение fn/merge и dispatch созданной функции.
- Граница реализации уже видна: lmx_graph_single_candidate / lmx_graph_call_single подают всю Structure только при единственном позиционном фактическом. Предлагаемый общий контракт для всех callable и ресиверов: после позиционных фактических один фактический-Structure, чьи прямые поля называют ещё не связанные формалы, подаёт их своими полями — то же правило всей структуры аргументов, применённое к хвосту. Если эта Structure допустима и как значение позиционного формала, и как подача полями, вызов неоднозначен и отказывает (правило автора 2026-11-08 о двух подходящих). Формал name декларирующих ресиверов (fn, sub, int) принимает написанное имя — слово или строку — без вычисления; это часть контракта ресивера, не ветка fn.
