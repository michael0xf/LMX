## П2. Записи `Имя: (поля)` после решения о раскрытии

Пример автора от 15 октября: `var: (i: int: 5)`, затем `var\i`.

Решения 2026-11-10: P0 единственную Structure не раскрывает, «"struct: ()" соответствует struct(())»; форма с
двоеточием объявляет Structure с хвостом внутри. Вместе они дают: `var: (int: i 5)` объявляет `var`, внутри которой
одна безымянная Structure с полем `i`, и путь `var\i` до поля не доходит. Structure с полем `i` объявляют
`var(int: i 5)`, `var: int: i 5` и блочная форма.

Следствия, которые исполнитель внёс и просит подтвердить.

1. Примеры документов, где имелась в виду Structure с полями, записаны компактной формой: `A(int: x 1)`,
   `var(int: x 2)`, `Batch(put: 7)`.
2. Ответ исполнителя В1 в [прежних ответах](../fable-self-answers-20261110.md) — «объявление со структурным хвостом
   по-прежнему задаёт значение места», приёмка раздела M8 — побайтно прежние L1 и C при неизменных исходных текстах —
   отозван. Перепись раздела M8 считает объявления `Имя: (поля)` с головой, которая не ресивер и не вызываемое; их
   переводит на `Имя(поля)` команда инструмента до смены парсера, и побайтное сравнение идёт на переведённых текстах.

Измерение по тексту поддерживаемых исходников — в [разделе M8](../../../next_core_tasks_v3.md#m8): 18 396 строк, весь
хвост которых — одна группа в скобках; сколько из них объявления, покажет отчёт парсера. Зависит: шаги 1–4 раздела M8.

## П3. Остаётся ли `Struct2` полем корня после `Struct1: Struct2`

Пример автора: `Struct2: a b c`, `Struct1: q w e r t`, `Struct1: Struct2`; ожидаемый дамп в его сообщении печатает
одну `Struct1`, внутри которой `Struct2` с `a`, `b`, `c`.

Исполнение в чистом графе (срез 346): внутри `Struct1` находится сама `Struct2` — тот же экземпляр, без копии, — и
она же остаётся полем корня под своим именем. Дамп после исполнения печатает корень целиком:

```text
Struct2: a b c
Struct1: (Struct2 a b c)
```

Прежних `q w e r t` нет, поле `Struct1` одно. Измерение на том же экземпляре: после `Holder: Model` запись
`Holder\Model\v := 5` читается и как `Model\v`, и через ссылку `@: p Model` (фикстура `declare_forms`).

Вопрос: (а) один экземпляр, достижимый по обоим именам, — как исполнено; (б) `Struct2` переходит внутрь `Struct1` и
в корне её больше нет; (в) `Struct1` получает копию. Второй вопрос — запись дампа: чистый граф печатает вложенную
Structure одной строкой в скобках, в сообщении автора она записана ступенями `. `; содержимое то же.

Рабочее чтение до ответа: (а), формат дампа прежний. Зависит: ожидание фикстуры `declare_structure` и то, что кладётся
в слот атома хвоста.

Дополнение 2026-11-11. Решение о ролях `data` и `code` даёт этой форме новое употребление: объявления Structure
пишутся в блоке данных метода — пример автора `sub: proc () (struct1: Template1; struct2: Template2)`. От ответа
теперь зависит, что получает метод: если внутри `struct1` — сама `Template1`, тот же экземпляр (чтение (а)), то
два объявления по одному образцу и все активации метода делят одну Structure, и запись через `struct1` видна как
`Template1\поле`; если копия (чтение (в)) — у каждого объявления своя. Путь к полю при любом чтении —
`struct1\Template1\поле`: `Template1` находится внутри под своим именем. Зависит: шаг 5 раздела
[M11](../../../next_core_tasks_v3.md#m11) — что реестр данных кладёт в слот атома хвоста.

## П6. Порядок аргументов двухаргументного `call`: `call: code data` или `call(var code)`

Пункт добавлен 2026-11-11 при внесении решения автора о ресиверах `call` и `fncall`
([журнал](../../2026-11-11.md#call-receivers), [книга](../../../docs/LMX_semantics.ru.md#call-receivers)).

Расходятся две записи одного сообщения автора и прежняя норма.

1. Первая фраза сообщения называет схему — «используется схема call(code, data)»: код первым, данные вторыми. Так же
   записана прежняя норма книги и все исходные тексты: `call: code data` (`call: Code Data`).
2. Список форм в том же сообщении и в поправке к нему ставит код последним: `call(args var code)`, `call(var code)`,
   `call(code)`, `fncall(args var return code)`. В двухаргументной форме `call(var code)` данные стоят первыми.

Измерение: в `selfbuild` 91 строка двухаргументного `call: code data` в фикстурах `tests/dyn`, `tests/graph` и
`tests/os_twins`; компактная `call(Code Data)` строится тем же Frame, что `call: Code Data` (пробы `k01`, `k02`).

Вопрос: двухаргументная запись читается как `call(var code)` — данные первыми, и тогда 91 строка исходных текстов и
прежние разделы книги переписываются перестановкой аргументов; или порядок `call: code data` остаётся, а список форм
называет только состав частей?

Рабочее чтение до ответа: формы с тремя и четырьмя аргументами — новые, их порядок берётся из списка автора
(`args var code`, `args var return code`, код последним); двухаргументный `call` и исходные тексты не трогаются и
читаются по-прежнему — `call: code data`. Одноаргументный `call(code)` от ответа не зависит. Зависит: шаги 2 и 4
[раздела M10](../../../next_core_tasks_v3.md#m10).

Дополнение 2026-11-11. Решение о ролях переименовало `var` в `data`: формы списка теперь `call(args data code)`,
`call(data code)`, `call(code)`, `fncall(args data return code)`. Вопрос тот же — данные первыми (`call(data code)`)
или код первым (`call: code data`); рабочее чтение прежнее.

## П7. Запись, которую объявила в данных та же Structure, что исполняет её как код: корень единицы и `call(code)`

Пункт добавлен 2026-11-11 при внесении решения автора о ролях `data` и `code`
([журнал](../../2026-11-11.md#data-code-roles), [книга](../../../docs/LMX_semantics.ru.md#data-code-roles)).

Пример — так написаны все фикстуры и корневые программы инструмента:

```text
Point:
    int: x 1
end: Point
int: hits 0
fn: read () int
    return: Point\x
end: read
hits := read()
send: exit(exit_code := hits + 6; stdout := ""; stderr := "")
```

Корень единицы исполняется над самим собой: он и данные, и код. То же — Structure, запущенная `call(code)`.

Расходятся две записи.

1. Решение 2026-11-11: «в роли code все вообще интерпретируюется как вызов», «никаких объявлений структур вообще
   нет в роли code», а о `Model: KnownStruct` — «В code это вызов и если такого метода нет -- то ошибка». По ним
   запись `Point: … end: Point`, дойдя до исполнения, — вызов `Point`, а метода `Point` нет.
2. Последняя редакция книги ([построение значений](../../../docs/LMX_semantics.ru.md#construction)): «Именованная
   Structure не исполняется при объявлении»; в исполняемом корне она стоит как определение. Автор о решении
   2026-11-11: это сужение, а не изменение правил.

Вопрос. Когда Structure сама себе данные, запись, которую её же роль `data` прочла как объявление Structure,
в роли `code`:

- (а) пропускается — остаётся определением, как сейчас; вызовом в таком коде становится только запись, головы
  которой данные не объявляют;
- (б) вызов и потому ошибка — Structure, запускаемая над собой, и корень единицы не содержат объявлений
  Structure, их выносят в отдельные данные; тогда переписываются все единицы с именованной Structure в корне;
- (в) корень единицы читается только как данные, а его код исполняется иначе.

С тем же связаны два места.

Первое — второе сообщение автора: «никто не мешает нам прямо вызвать объявленный в data f()». Исполнитель читает
его так: вызываемое, объявленное в данных, вызывается по имени, а запись вызова, лежащую в данных как Structure,
можно запустить ресивером `call`. Если же оно значит, что записью `f()` в коде запускается обычная Structure,
объявленная в данных, то запись с головой — именем Structure в коде не ошибка, а запуск, и это расширение правила
«обычная Structure исполняется только через `call`».

Второе — повтор объявления переменной в корне единицы: `int: i 5`, затем `int: i 6`. По третьему следствию решения
о ресиверах (несколько корневых объявлений одной переменной и `call(code)`) обращение к `i` без индекса — ошибка, и
повтор в корне тогда тоже ошибка. Рабочий frontend сейчас даёт `i` = 6, чистый граф оставляет два поля и читает 5.

Рабочее чтение до ответа: (а); запись `f()` в коде, голова которой — обычная Structure данных, отказывает, как
прежде, а запускает её `call`; корень единицы читается как Structure над собой, и обращение без индекса к
переменной, объявленной в нём дважды, отказывает. Зависит: шаги 3, 5 и 8 раздела
[M11](../../../next_core_tasks_v3.md#m11) — сколько исходных текстов переводится и что делает обход корня.
