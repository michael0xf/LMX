# Fable2: короткий цикл сборки LMX

Поручение автора от 2026-11-18: на каждом шаге собирать и проверять затронутые компоненты.
Полную самосборку и полный набор тестов не запускать автоматически после каждого изменения.
Это уточняет прежний порядок приёмки; старые отчёты с полным прогоном каждого среза не обязывают его повторять.

## Что считать быстрым циклом

1. Определить изменённые исходники и их настоящих потребителей. Сохранять текущий принятый набор
   tool/frontend/runtime как исходную точку; записать, что заменяет кандидат.
2. Синхронизировать в рабочую стадию необходимые исходники существующим механизмом и проверить их соответствие.
   Не копировать заново всё дерево build2, старые поколения и журналы. Стадию меняет только владелец конвейера.
3. Собрать только затронутые компоненты по таблице ниже, затем необходимые зависимые исполняемые файлы.
   Повторно использовать неизменённые совместимые компоненты, явно называя их пути.
4. Выполнить минимальный пример исправления и небольшой набор действительно зависимых проверок.
   Для изменения исполнения сравнить нужные пути чистого графа: interp/native/forced;
   для изменения только разбора достаточно соответствующих проверок построителя.
   Нативный L2 и интерпретируемый L2 различаются проверками по норме 2026-11-18;
   не восстанавливать старый запрет интерпретации L2.
5. Записать исходники, команды, использованный набор, результат и границу проверки. Если нового изменения,
   сбоя или конкретного сомнения нет, не повторять уже прошедшие проверки.
6. При правке затронутого механизма сразу выполнить согласованные упрощения и удаление старого обслуживания.
   Быстрый цикл не означает оставить его «до полной сборки».

**bootstrap quick — не компонентная сборка.** Он всё равно строит G1 и G2, включая runtime, frontend
и tool; quick сокращает набор проверок. В принятом срезе типизированных литералов это заняло 19,3 минуты,
а отдельный full-suite — ещё 16,8 минуты
([свидетельство](steps/witnesses/one-graph-typed-literals-20261118/notes.md)).
Не выбирать bootstrap quick только потому, что в названии есть quick.

## Какую команду выбирать

Все команды ниже — существующие команды lmxtool, не новая сборочная инфраструктура.
Их аргументы подтверждены в [диспетчере](selfbuild/tools/lmxtool_methods.lm2),
[рецептах](selfbuild/tools/build.lm2) и [сборке поколений](selfbuild/tools/suite.lm2).

| Что изменено | Что собирать и проверять сейчас |
|---|---|
| Только инструкция, комментарии, описание плана | Проверить diff и затронутые документы. Compiler/runtime и bootstrap не нужны. Генерацию документов запускать, только если изменён их источник. |
| Только программа теста или ожидаемый результат | Запустить эту программу/небольшой список на существующем подходящем наборе; пересборка компилятора не требуется. |
| l2_graph_build.lm2 или l2_graph_tool.lm2 | build-graph. Это переводит построитель и инструмент чистого графа. Если изменённый построитель нужен также hosted frontend — build-frontend-host для него. |
| l2_frontend_graph.lm2 | build-frontend-host: он переводит этот модуль. build-frontend сам по себе этого не делает; build-frontend-link только связывает уже подготовленные результаты. |
| lmx_graph*.lm2, lmx_gc_graph.lm2 или другой модуль ядра | build-runtime, затем build-graph для графового исполнителя с новым driver.o. Если изменённый runtime нужен внутри hosted frontend/tool, пересобрать соответствующего потребителя. Старый exe не получает новый driver.o автоматически. |
| Обычные модули P0/frontend/backend | build-frontend-part с явным набором модулей и существующими reuse/ABI manifests, если их условия выполнены. Иначе компонентный build-frontend-host. Последующий тест запускает именно нужный кандидат. |
| tools/build.lm2, списки exports, генерируемые объявления, рецепт или ABI | Сначала согласовать необходимые зависимости и собрать новый tool через build-self. Новый рецепт должен исполнять новый tool. При изменении ABI пересобрать затронутых потребителей; это основание для проверки самосборки на границе связанного изменения. |
| Только tools/lmxtool* или другие исходники инструмента, без изменения ABI ядра | build-self с выбранными frontend и driver.o; затем проверить изменённую команду инструмента. |

build-runtime сейчас собирает компонент runtime целиком: отдельной команды выборочной сборки одного
его модуля нет. Не выдумывать такую возможность и не вводить ради этой инструкции второй сборщик.

build-frontend-part требует проверяемого набора неизменённых входов/артефактов и ABI.
Передавать MODULE можно списком через запятую. Этот путь предназначен для модулей, известных
bld_p0_part_known; l2_frontend_graph и l2_graph_build туда не входят.
Он не заменяет полный hosted frontend и не означает, что графовые модули были переведены.
REUSE-BUNDLE позволяет повторно использовать существующие l1trans.exe и l2_libc.o при неизменённых
зависимостях. Не переиспользовать старый ABI после изменения его генератора.

## Формы команд

Обозначения: R — репозиторий, S — рабочая стадия, B — прежний BASE из принятой записи сборки,
FE — выбранный frontend, RT — каталог runtime, TOOL — выбранный lmxtool.
Для текущих hosted exe префикс запуска — 0 entry 0 --; у frontend его подтверждает launch.txt.
LABEL/OUT каждый раз новые, принятые результаты не перезаписываются.

Это альтернативы по таблице, а не список, который надо выполнять целиком:

~~~text
TOOL 0 entry 0 -- build-graph R S B FE RT LABEL
TOOL 0 entry 0 -- build-runtime R S B FE LABEL
TOOL 0 entry 0 -- build-frontend-host R S B FE RT LABEL
TOOL 0 entry 0 -- build-self R S B FE RT/driver.o LABEL

TOOL 0 entry 0 -- build-frontend-part R S B FE LABEL MODULE REUSE-MANIFEST ABI-MANIFEST [REUSE-BUNDLE]

TOOL 0 entry 0 -- graph-check R S B FE RT GRAPH-EXE OUT SOURCE EXPECTED [EXPECTED-EXIT [RUNS [ANSWER]]]
TOOL 0 entry 0 -- suite TARGETED-LIST R S B FE RT/driver.o OUT [RT/driver-observe.o]
~~~

build-self и suite принимают файл driver.o; build-graph/build-frontend-host и graph-check — каталог RT.
У graph-check EXPECTED-EXIT=2 означает отказ построения; не переносить старые ожидания отказа,
которые отменены текущей нормой.

Есть готовое сочетание сборки одного компонента с небольшим набором:

~~~text
TOOL 0 entry 0 -- rebuild runtime R S B FE RT LABEL SMALL-LIST
TOOL 0 entry 0 -- rebuild frontend R S B FE RT LABEL SMALL-LIST
TOOL 0 entry 0 -- rebuild tool R S B FE RT LABEL SMALL-LIST
TOOL 0 entry 0 -- rebuild none R S B FE RT LABEL SMALL-LIST
~~~

rebuild frontend вызывает build-frontend-host. rebuild runtime собирает runtime и запускает список
с новыми объектами, но не пересвязывает автоматически все внешние Graph/frontend/tool exe.
Вместо full-suite передавать небольшой подходящий список. Графовые случаи проверять новым Graph exe;
старый набор прежнего исполнительного пути не доказывает исправление чистого графа.

## Когда нужен полный прогон

Полную самосборку G1/G2 с проверкой устойчивости результата проводить при изменении самой цепочки
самосборки, общего ABI, exports/деклараций, формата графа/образа либо при сбое, который указывает
на несогласованность компонентов. Также она нужна на явно выбранной границе законченного этапа,
когда заявляется работоспособность нового общего набора.

Полный набор тестов запускать, когда изменение действительно имеет широкое влияние, локальные результаты
указывают на общую регрессию или сдаётся соответствующий законченный этап. Полный набор и самосборка —
разные проверки; необходимость одной не означает автоматически запуск обеих.

Внутри такого этапа несколько связанных правок проходят короткий цикл; после стабилизации выполняется
одна соответствующая широкая проверка. Правка текста, ожидания одного теста или узкого тела не запускает
всю цепочку заново сама по себе. Компонентную проверку так и называть: она не становится новым G2
или доказательством fixedpoint.

## Память и дисковый ввод-вывод

На машине около 15,4 ГиБ доступной ОС физической памяти. Замер Codex 2026-11-18 в 08:43 UTC:
system cache resident около 0,35 ГиБ; standby около 4,62 ГиБ; available около 5,38 ГиБ.
Это один замер после сообщения Fable, а не замер пика сборки. Сообщённый Fable пик 6,6 ГБ
и падение available до 1 ГБ этим замером не подтверждаются и не опровергаются.

Standby — освобождаемые страницы и часть available. Складывать standby с available как две независимые
занятые величины нельзя. Рост файлового кеша при массовом чтении/записи нормален; отсутствие доступной
памяти, paging и сброс фоновой задачи нужно измерять отдельно. См.
[объяснение Cache Manager от Microsoft](https://learn.microsoft.com/en-us/windows-server/administration/performance-tuning/subsystem/cache-memory-management/).

Практический порядок:

- Один тяжёлый producer в конвейере. Не запускать одновременно bootstrap, full-suite и компиляции помощников.
- После сброса фоновой задачи проверить оставшиеся lmxtool/l2trans/gcc/cc1 и текущий журнал,
  прежде чем запускать ещё одну копию. Исчезновение задачи оболочки не доказывает завершение дочерних процессов.
- Не очищать standby и не отключать файловый кеш на каждом шаге: это вызывает повторное чтение файлов.
- Не чистить build2 и не пересоздавать неизменённые поколения ради «чистой» быстрой проверки.
  Повторно использовать подходящие артефакты по существующим зависимостям.
- При повторном провале памяти записать хотя бы available, resident cache, standby, modified pages,
  paging и private bytes процессов сборки. Называть конкретный счётчик, а не всё число «кешем Windows».
  Изменение служебной переменной Claude Code само по себе память не освобождает и быструю сборку не заменяет.

Короткий замер из PowerShell, без запуска компилятора:

~~~powershell
$mem = Get-CimInstance Win32_PerfFormattedData_PerfOS_Memory
[pscustomobject]@{
    AvailableGiB = [math]::Round($mem.AvailableMBytes / 1024, 2)
    ResidentCacheGiB = [math]::Round($mem.SystemCacheResidentBytes / 1GB, 2)
    StandbyGiB = [math]::Round(($mem.StandbyCacheCoreBytes + $mem.StandbyCacheNormalPriorityBytes + $mem.StandbyCacheReserveBytes) / 1GB, 2)
    ModifiedGiB = [math]::Round($mem.ModifiedPageListBytes / 1GB, 2)
    PagesInputPerSec = $mem.PagesInputPersec
    PagesOutputPerSec = $mem.PagesOutputPersec
} | ConvertTo-Json
Get-Process -Name lmxtool,l2trans,gcc,cc1 -ErrorAction SilentlyContinue |
    Select-Object ProcessName,Id,WorkingSet64,PrivateMemorySize64 |
    ConvertTo-Json
~~~
