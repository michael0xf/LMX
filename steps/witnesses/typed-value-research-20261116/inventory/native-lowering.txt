ОБЩАЯ КАРТА (читать первой)
Выпущенное native-тело графового метода (l2_mN) оперирует тремя вещами:
 (а) C-локалами ТОЧНОГО типа (int, size_t, unsigned, @: void) — рабочие копии и временные;
 (б) записью LmxWalkValue (present, kind, type, объединение number/wide/natural/longnum/byte, ref, model, referent, physical_profile, source_type, scalar_abi…) —
     это УЖЕ типизированная запись «тип + значение + контекст»; она живёт в C-локале (компаньон) и пробрасывается в helper-ы;
 (в) адресом ячейки арены (void*), которая БЕЗ метки: физический тип ячейки узнают helper-ы по диапазону арены (lmx_range_cell_pool → LmxPool{kind,type,stride,profile,sealed,…}).
Прямого разыменования ячейки арены в выпущенном коде нет вообще (ни чтения, ни записи): всегда helper.
Тип в большинстве мест передаёт ТРАНСЛЯТОР статической константой (c.LMX_TYPE_INT и т.д.); классификация адреса даёт другое: права записи (immutable/sealed/profile),
компаньон-контекст ячейки (модель/происхождение), callback-и чтения указателя, и ТИП только там, где транслятор его не знал.

1. Значение известного типа в native-коде
------------------------------------------------------------------------------------------------------
Три вида:
1a. Поле графового кода (own, `int: z`, `@: p`, `[]: T a n`), используемое в теле по голому имени. Эмитирует FE core.lm2:lm_compiler_emit_work_decl 4042–(4150)
    (сайты 4089, 4114) и FE emit.lm2:lm_compiler_emit_unit (сайт 17966 — таблица мест `[]: size_t l2_cpl`). В F (whole_direct_fields l2_m4, строки 2440–2470 артефакта):
        @@: void l2_q0_z_from 0 ; l2_q0_z_from: lmx_arena_ref_cell(self, l2_cpl[0U])   # адрес СЛОТА в Structure данных (void**), не значение
        size_t: l2_q0_z_bound 0U                                                        # номер строки привязки в активации
        int: l2_q0_z 0                                                                  # C-локал ТОЧНОГО типа — рабочая копия
        LmxWalkValue: l2_wv0_z ; lmx_walk_value_clear(@ l2_wv0_z)                       # компаньон: тип+значение, выставлен как execution root
    Указательное поле — `@: void l2_q2_q 0` вместо int. Массив-поле — только компаньон (см. п. 6).
    Запись в такое поле (FE lower.lm2:lm_compiler_own_work_store_value 2452–2514, сайт 2507; F free_field_places 5228–5290):
        value → LmxWalkValue → if: lmx_range_write_exact_blocked(arena, from[0], 0,0,0U) != 0  return 4   # барьер: сам адрес арены, не локал
        LmxWalkPlace{address=@ l2_q5_caught (АДРЕС C-ЛОКАЛА), type=c.LMX_TYPE_INT, context=0} ; lmx_walk_value_store_with_writer(arena,@place,@value,0)
        memcpy(@ l2_wv5_caught, @ received) ; lmx_activation_bind_origin(arena, id, 0, LMX_TYPE_NONE, @ l2_wv5_caught, origin = l2_q5_caught_from)  # один раз на активацию
    Т.е. ЗНАЧЕНИЕ типизированного own-поля лежит в C-локале + компаньоне; ячейка арены служит ИДЕНТИЧНОСТЬЮ (origin) и предметом барьера записи.
    Чтение обратно — не прямое: `c.memcpy(@ l2_cvN, @ l2_wvM)` и `lmx_walk_value_number(@cv,@n,@ty)` + `((cast: (@: int) lmx_walk_value_storage(@ cv))[0])` (F whole_direct_fields 129–133).
    ЧЕГО НЕ ВИДНО в прочитанных телах: записи C-локала обратно в ячейку арены при выходе из активации (это работа рабочего состояния обходчика §7b / lmx_walk.*);
    я её не читал — для исследования стоит проследить, кто и когда пишет `*_from[0]` по значению локала.
1b. Временные результаты: `int: l2_mv17 ((l2_lv15.number))`, `size_t: l2_t39 l2_q1_at` (F local_array_var_index 299), `int: l2_nv44`, `@: void l2_t2 (cast … l2_cv2.ref)`.
    Это обычные типизированные C-локалы; они упаковываются в LmxWalkValue ТОЛЬКО на границе интерфейса: `lmx_walk_value_num(@ mvv, c.LMX_TYPE_INT, (cast: (size_t) mv))` (FE lower.lm2 сайт 11409, 9572, 10240)
    перед записью или вызовом, и распаковываются `lmx_walk_value_storage(@ v)[0]`/`.number` после чтения. Арифметика между ними — обычный C без записей.
1c. Обычные native-функции самого инструментария (frontend.c, lmxtool.c: 11 МБ и 2.8 МБ C) — чистый C с типизированными локалами; lmx_range_* встречается 90 раз в frontend.c и 334 в lmxtool.c (п. 7) — это вызовы рантайма
    встроенных графовых программ и самого рантайма, а не локалы транслятора. Упаковка в TypedValue там не нужна и не используется.
Где значение только в C-локале: 1b целиком; own-поле скаляра (1a) между записью и выходом (по прочитанному). Где в ячейке арены: поля Structure (п. 2), элементы Array (п. 6), слоты ссылок.

4. Карта соответствия полей (place map / exec_slot / implements) → индекс слота → чтение ячейки
------------------------------------------------------------------------------------------------------
Эмиссия: FE emit.lm2:lm_compiler_emit_unit (сайт 17966) — статическая таблица `l2_cptN` {m, k, k строк по (1+m)} и локальный `[]: size_t l2_cpl m`; lower.lm2:lm_compiler_emit_split_admission 18233–18252 (сайт 18237).

    layout = lmx_implements_layout(arena,data) (4635–4645: ЛИНЕЙНЫЙ скан arena->impl по entry->value==data, возвращает entry->layout — идентичность схемы, записанная при допуске);
    строка таблицы выбирается СРАВНЕНИЕМ адреса токена `tokens+row[0] == layout`; row[1+j]==SIZE_MAX → NO; row[1+j] >= data.array.size → UNKNOWN; иначе out[j]=row[1+j].
Одиночный ребро: lmx_call_index(arena,data,code,edge) (RT call 50–68) → lmx_implements_code_slot (RT implements 7179+): если value==code → lmx_implements_exec_slot (7078) ; иначе композиция exec-карты code
    и допуска data к code (lmx_implements_find(arena,code,code)->exec_map, scope arena->call_places). Предварительно lmx_graph_node_in(arena,value) для обоих (классификация: kind ∈ {STRUCT,ARRAY} и stride == sizeof(Lmx)).
    UNKNOWN/NO → note_walk_fail + abort. Результат — size_t индекс слота.
Чтение ячейки после индекса: `from = lmx_arena_ref_cell(self, idx)`, затем на каждое использование `from[0]` (void*) — ТЕКУЩЕЕ значение слота, повторная проверка `if from[0]=0 → заново ref_cell` (F free_field_places 5244–5247).
При ЗАМЕНЕ ссылки в слоте (RT arena_refs lmx_arena_ref_store / lmx_graph_ref_fill_in с lmx_code_rebind_prepare/commit): адрес слота `from` остаётся тем же, читается новый referent при следующем `from[0]`;
    его физический тип/вид заново определяет классификатор по НОВОМУ адресу (lmx_walk_value_cell, п. 3b). Что НЕ обновляется само: C-локал l2_qK_name, компаньон l2_wvK и строка привязки (`_bound`, origin=from) —
    это рабочая копия значения, взятая при записи/загрузке (по прочитанному; см. оговорку п. 1a).
Итого: «слот» — это индекс в массиве void* Structure; запись типа в нём нет; тип referent-а = тип пула по адресу referent-а.

8. Что изменилось бы при собственной метке типа у записи (TypedValue; слот → запись; тип = p->type) и что — нет
------------------------------------------------------------------------------------------------------
ИЗМЕНИЛОСЬ БЫ (убирается/упрощается):
 - п. 3a/3b: lmx_range_type_of / lmx_domain_kind / lmx_domain_type ради ТИПА (FREE-вход, lmx_walk_value_cell, index_place, Array place.type = element(type_of(descriptor)), typeof) — чтение p->type вместо бисекции диапазонов;
   typeof становился бы чтением поля (но «тип региона арены» ≠ «тип записи» для сырых указателей на не-запись — пришлось бы определить).
 - lmx_walk_value_cell: ветвление STRUCT/ARRAY/PRIMITIVE по классификации заменилось бы переключением по p->type; пропали бы FOREIGN-проверки pool->type == ty.
 - п. 2: lmx_pointer_cell_context/lmx_value_cell_context (компаньон по адресной арифметике чанка) могли бы жить В записи (model/referent/source_type), а lmx_value_context_cell_in (обратное отображение) исчез бы.
 - lmx_call_cell («адрес жив в арене») как проверка stale/посторонней ссылки частично заменялась бы валидностью записи (но если слот хранит указатель на запись, то проверка валидности самой записи остаётся).
 - п. 4: слот хранит запись, а не голый void*: «замена ссылки в слоте» меняет саму запись целиком (тип+значение атомарно), тогда как сейчас referent и тип referent-а меняются независимо (тип по новому адресу).
НЕ ИЗМЕНИЛОСЬ БЫ ВОВСЕ:
 - Права записи: lmx_range_write_exact_blocked = immutable(type_of) + sealed_profile (членство в «квалифицированной» ветке) + root_profile — это свойства ПУЛА/ВЕТКИ, а не типа значения; метка типа записи их не несёт.
   52 вхождения в place_map, 32 в free_field_places, 18 в tool — все остаются, пока «квалифицированность»/eternal определяется диапазоном.
 - lmx_range_profile/lmx_range_classify в конструкторах walker-кода (в трёх F: 326 из 451, 878 из 1302, 1665 из 2358 вхождений = 67–72%; весь lmx_range_profile — только там): профиль пула переносится в узел; не зависит от типа значения.
 - Транслятор по-прежнему передаёт тип СТАТИЧЕСКИ в известных случаях (c.LMX_TYPE_INT в place.type): прямые загрузки lmx_int_value_known(storage) остаются, там классификатор не вызывается.
 - Плотные Array<T> и типизированные C-локалы/временные (п. 1b, 6): упаковка в запись не нужна и по условию исследования не вводится; element type — одно поле пула дескриптора.
 - Карты соответствия полей (п. 4): lmx_implements_places/code_slot/layout работают с ИДЕНТИЧНОСТЬЮ схемы data и индексами слотов; запись типа в слоте их не затрагивает.
 - Идентичность/происхождение: lmx_activation_bind_origin(origin = адрес слота-ячейки) — адрес остаётся ключом; запись в слоте дала бы второй уровень адресации (адрес записи vs адрес слота), и origin пришлось бы определить заново.
ОТКРЫТЫЕ ВОПРОСЫ для исследования (я их не закрывал, только вижу по коду):
 - Кто пишет C-локал own-поля обратно в ячейку арены (п. 1a оговорка) — от этого зависит, ЧТО именно «в записи».
 - lmx_range_stride и stride-арифметика в lmx_value_context_cell_in опираются на однородность пула: запись переменного размера или union ломает «тип пула = тип ячейки» для плотных массивов (по условию массивы остаются плотными — значит записи только у слотов Structure, не у элементов Array).
 - typeof(x) для x внутри плотного Array/C-локала: сейчас тип пула; при записи у слотов и плотном массиве без записей потребуется два пути.
