# Алгоритм группировки и разбора LMX Expression

Алгоритм получает **чистый граф**, текущий лексический контекст и договор принимающей позиции. Текста, токенов скобок и признака происхождения структуры на его входе нет. Ссылка разрешается к существующему узлу; имя, `parent`, идентичность и связи этого узла сохраняются.

Здесь описаны общий обход, связывание операций, работа с последовательностями и отдельная подготовка применения. [Проверочная реализация на Python](tools/expression_grouping_reference.py) исполняет ядро планирования над небольшим представлением графа. [Её тесты](validation/expression_grouping_reference_test.py) запускаются обычным Python. Норма Array/depth дополнена [TENSOR_EXPRESSIONS](TENSOR_EXPRESSIONS.md); успешная host-проверка не означает production-приёмки. Это проверка алгоритма, **не поставленный парсер, транслятор или runtime LMX**. Производственные механизмы разрешения имён, договоров, хранения, admission и исполнения подключаются через интерфейс `GraphView` и существующие обработчики.

<a id="single-parser-and-grouper"></a>
## Один парсер и один механизм группировки

**Общий парсер LMX.** Каждая структурная `[` входит в квадратный подпарсер. Каждое выражение и `{...}` разбирает общий P0, который возвращает граф и позицию продолжения. Вложенные формы используют те же входы и политики границы. После разбора работает общий группировщик. [Договор парсера](BRACKET_SUBPARSER.ru.md).

После построения графа действует **один алгоритм семантической группировки с одной общей реализацией**. Интерпретатор, frontend, построение программы и native-перевод вызывают этот общий код для группировки LMX Expression, включая выражения из уже существующего графа. Алгоритм читает готовые свойства выбранных операций и сохраняет роли и контекст. Подготовка actual, Array-планы и генерация кода потребляют его результат; они не группируют выражение заново и не переопределяют его приоритеты.

Все прежние дублирующие алгоритмы, независимые таблицы связывания и обходные пути разбора/группировки подлежат удалению после перевода их потребителей на общий код. Сохранение отдельных механизмов за адаптерами шкал или требование лишь совпадения результатов не выполняет эту норму. Различные исполняющие backend могут потреблять один общий план по своим машинным договорам; собственный алгоритм группировки у backend не допускается. Отдельная подготовка `left/depth/right` остаётся передачей фактических аргументов и не является вторым группировщиком.

Приведённая host-модель проверяет эту норму и не является альтернативным production-маршрутом. Фактическое наличие старых веток в изученном selfbuild описывает работу по их устранению, а не разрешённую целевую архитектуру. Production-приёмка остаётся **NOT_RUN**.

<a id="expression-notation"></a>
## Операторы режима `prefix` и `infix`

Операторы `prefix` и `infix` выбирают запись в следующей области Expression. Скобки сначала задают границы вложенных областей. Внутри своей области оператор режима связывается раньше любой обычной операции, включая `**`. Переключение действует до конца этой области; если отдельные скобки не написаны, границу даёт окружающий разбор выражения. После выхода восстанавливается внешний режим.

В `prefix` операция стоит перед её аргументами. Строгий префиксный разбор не сравнивает приоритеты; вложенность задают группы и однозначные границы применения. В `infix` действует обычный группировщик LMX с приоритетами, ассоциативностью и обычными префиксными применениями. Обе записи используют тот же граф, выбор операнда и договор `left/depth/right`. Режим не создаёт левый аргумент и не меняет формалы метода. Неоднозначная роль или граница требует отказа при трансляции либо при подготовке интерпретируемого выражения до эффектов.

Например, `prefix (op a (sub b c))` передаёт `op` два правых вхождения, `a` и результат группы `sub`; `left` отсутствует. В `prefix (op a (infix (b + c * d)))` умножение связывается раньше сложения только внутри области `infix`. В обычном `a ** b ** c` сохраняется правая группировка. Проверка правила требует сравнения деревьев до исполнения пользовательских операций.

| Проверяемая форма | Наблюдение до исполнения |
| --- | --- |
| `prefix (op (lo a b) (hi c d))` с разными приоритетами `lo` и `hi` | У `op` отсутствует левый атом и есть два правых поддерева. Перестановка значений `PRIORITY` дерево не меняет. |
| `infix (a + b * c)` и `infix ((a + b) * c)` | В первом выражении корень `+`, во втором `*`. |
| `prefix (op a (infix (b + c * d)))` | Обычное связывание вложено в один правый аргумент; далее снова действует внешний режим. |
| Индекс или срез с вложенной областью режима | Следующей позицией и разделителем владеет вызывающий подпарсер. При разборе счётчик эффектов равен нулю. |
| Префиксная последовательность допускает два разбиения по известным договорам | Ранний отказ; явные скобки выделяют требуемые применения. Для известных числовых атомов запись `prefix (2 + 3)` даёт отказ по форме: у первого атома нет роли операции. |

В `a + prefix (op b c) * d` закрывающая скобка завершает префиксную область. Снаружи действует обычная группировка `a + (результат * d)`. В `prefix (op a (b c))` уже записанная группа остаётся одним вхождением до подготовки роли правого аргумента. Если принимающий контракт не допускает его, действует обычный отказ. Текст `prefix` в строковом литерале или компоненте пути сам по себе режим не меняет.

При подготовке режима сохраняются роли RAW/PLACE/TYPE/DATA, востребованность, правило графового атома-ссылки и приём по шаблону `satisfies`. Имена методов, пути, компактные вызовы и разделители принадлежат основному парсеру. Режиму достаточно признака области в общем группировщике; запись `prefix` в числовую шкалу `sys\priority` дала бы неверное связывание в строгой области. Исполнительные примеры ожидают проверки общей производственной связкой.

## 1. Роль вхождения и структурные связи

VALUE, TYPE, DATA, NAME, PLACE и RAW сохраняют собственные договоры. Для атома-ссылки на Structure в Expression трансляция определяет роль обычным `satisfies` по [шаблону операнда](LMX_semantics.ru.md#operand-receiver). Установленная `1` выбирает операнд, установленный `0` сохраняет один целый Array ссылок (`[]@`). Возможность обоих ответов для неизвестной ссылки даёт ошибку до вычисления, как и другие конкурирующие чтения. Группировка использует уже установленный результат проверки. При известной цели, связывании и подготовленном native-входе транслятор генерирует прямой вызов по выбранному плану.

| Установленная роль вхождения | Единица плана |
| --- | --- |
| Цель не является Structure | Один атом с исходным контекстом. |
| Атом-ссылка на Structure, `satisfies = 1` | Операнд с исходным вхождением и разрешённой целью. |
| Атом-ссылка на Structure, `satisfies = 0` | Одно целое значение Array, без обхода полей как CODE. |
| Непосредственная безымянная Structure | Expression-группа. |
| Непосредственная именованная Structure с другим фактическим `parent` | Expression-группа. |
| Непосредственная именованная Structure с текущим лексическим владельцем | Обычный ресивер или вызов по его договору. |

Разрешение ссылки не вызывает цель и не меняет её `parent`. Неопределённая роль атома-ссылки отклоняется до этой развилки и до эффектов.

Развилка по имени и фактическому `parent` относится к Structure вне случая атома-ссылки. Безымянная Structure и именованная Structure с другим родителем образуют группы. Именованная Structure с текущим лексическим владельцем в качестве родителя проходит обычное разрешение ресивера или вызова.

`ReceiverPlan` ещё не выполняет вызов. Обработчик получает собственный договор ресивера: обычный callable вызывается, декларационный ресивер сохраняет декларационное действие, а его DATA-аргументы не становятся CODE. Группировщик не создаёт отдельной активации для `GroupPlan`.

```lmx
data:
    S: a b c d
    code:
        print: 1 + S + 2
        print: 1 + (a b c d) + 2
```

В первой строке при `satisfies = 0` ссылка `S` передаёт целый Array. Во второй строке безымянный узел группируется по общему правилу. Допуск Array и чтение его элементов принадлежат договору `+`.

Нормативное основание: [Structure в контексте Expression](LMX_semantics.en.md#expression-structure-parent-guard).

## 2. Одно прохождение текущего уровня

Обычная форма `head: arg0 arg1 arg2` уже выделяет одну начальную позицию и правый хвост. Expression допускает выбранный операнд в разделяющей позиции:

```lmx
arg0 operand arg1 arg2 arg3
```

Обход получает упорядоченные вхождения текущего уровня. Для каждого операнда обычное разрешение находит готовый договор базовой операции и готовый приоритет; запускать тело, чтобы узнать приоритет, нельзя. При этом исходный граф не переписывается. Временный план хранит ссылки на его вхождения и контексты.

Последовательность соседних атомов без операнда между ними остаётся последовательностью. В бинарном случае справа один элемент. В общем случае правый хвост может содержать несколько элементов; количество формалов не используется как скрытый разделитель исходного выражения.

Внутренняя группа занимает одну позицию внешнего уровня. В допущенном графе Expression её содержимое рекурсивно планируется; одна полученная единица прозрачна, несколько единиц представлены одной подгруппой. Целая операция остаётся одной единицей, её исходные токены наружу не вставляются. Это структурная нормализация без исполнения. Договоры DATA-описания, полного TYPE, RAW и коллектора потока полей сохраняют свои области; возвращённые значения не обходятся заново как код.

## 3. Ровно две формы: без левого атома и с одним левым атомом

| Форма | `left` | `depth` | `right` |
| --- | --- | --- | --- |
| `operand arg0 arg1 arg2` | Отсутствует | Отсутствует | `arg0`, `arg1`, `arg2` |
| `arg0 operand arg1 arg2` | Один атом `arg0` | Отсутствует | `arg1`, `arg2` |
| `.(n)operand arg0 arg1 arg2` | Отсутствует | Значение n | `arg0`, `arg1`, `arg2` |

Это два варианта одного договора. Структурная группа тоже занимает одну левую позицию; свободный массив атомов слева не вводится. Допустимую длину правого хвоста определяет принимающий ресивер.

```lmx
(op 1 2 3)
```

Разбор однозначен:

| Позиция | Материал |
| --- | --- |
| Операция | Разрешённое вхождение `op`. |
| `left` | Отсутствует. |
| `depth` | Отсутствует. |
| `right` | Три исходных вхождения `1`, `2`, `3` в этом порядке. |

Первый правый элемент не переносится в `left`; отсутствующая позиция не подменяется пустой Structure или нулём. Если договор операции требует `left`, обычный допуск отвергает это применение. Если допускает отсутствие, используются его обычные defaults/правила связывания. Синтаксическая однозначность не означает, что любой ресивер принимает любые аргументы.

Операнд в первой позиции правого хвоста также может начинать префиксное применение. Низкий приоритет такого префикса сам по себе не создаёт ему отсутствующий левый атом. В частности, сохраняется установленное направленное связывание `2 ** -2`.

## 4. Связывание приоритетами и граница правого хвоста

Для обычных вычисляющих операндов используется проход с порогом приоритета. Операция более сильного приоритета образует вложенную единицу; более слабая заканчивает текущий правый хвост. Для равного приоритета применяется существующее направление связывания.

| Пример / условие | План |
| --- | --- |
| `1 + 2 * 3` | `+(1, [*(2, [3])])` |
| `a op b c high d`, `high` сильнее `op` | `op(a, [b, high(c, [d])])` |
| `a op b c low d`, `low` слабее `op` | `low(op(a, [b, c]), [d])` |
| `a op b c op d`, равный левосвязывающий приоритет | `op(op(a, [b, c]), [d])` |
| `2 ** 3 ** 2` | `**(2, [**(3, [2])])` |

Эта таблица показывает внутренний план, а не новую пользовательскую запись. У каждого применения один `left`. Неопределённой границы между двумя свободными левыми массивами здесь нет; общий шаблон сохраняет один left, необязательный actual depth и right Array.

Префиксные и постфиксные формы используют уже установленные направленные правила. Для степени сохраняются `-2 ** 2` → `-(2 ** 2)` и `2 ** -2` → `2 ** (-2)`. Они не выводятся из одной универсальной позиции «степень выше всех префиксов». Группировщик читает готовые приоритеты операций; нормативное числовое уточнение для степени приведено ниже. Условные уровни из отдельных проверочных сценариев не заменяют эту шкалу.

<a id="power-priority"></a>
### 4.1. Степень: высокий приоритет и правая ассоциативность

В редакции 27 ноября 2026 года для стандартной степени установлено **`sys\priority("**") = 131`**. Больший числовой приоритет связывает сильнее. Значение выбрано как минимальное целое, строго превышающее и уровень умножения `110`, и существующий порог аргумента унарных `+`/`-`, равный `130`:

Из потребностей следует `p(**) = max(110, 130) + 1 = 131`, то есть
`110 < 130 < 131 < 140`.

Здесь `140` — существующий порог аргумента `!`, а не приоритет самой степени или всех унарных операций. Вызов, индекс и доступ к полю по-прежнему формируют атом до инфиксного связывания. Отношения остальных префиксных и постфиксных форм сохраняются; эта правка не помещает степень выше любого префикса.

Одного увеличения `PRIORITY` недостаточно для правой ассоциативности. При числовом проходе, принимающем следующую операцию при `p(next) >= minimum`, правый порог левосвязывающего инфикса равен `p + 1`, а правосвязывающего — `p`. Поэтому у `**` **правый минимум тоже равен `131`**: внутренняя пара связывания `(p, right_minimum)` равна `(131, 131)`. Следующая степень равного уровня входит в правое выражение. Если оставить безусловное `p + 1`, при любом повышении числа цепочка всё равно сгруппируется слева.

| Операция / роль | Уровень или порог | Правило |
| --- | ---: | --- |
| Инфиксные `+`, `-` | `100` | RHS исключает равный уровень; числовой минимум `101` |
| Инфиксные `*`, `/`, `%` | `110` | RHS исключает равный уровень; числовой минимум `111` |
| Аргумент префиксных `+`, `-` | `130` | Захватывает степень `131` в свой аргумент |
| Инфиксная степень `**` | `131` | RHS включает равный уровень; числовой минимум `131` |
| Аргумент префиксного `!` | `140` | Существующий порог сохраняется |

Это та же общая политика связывания из раздела 4, а не отдельный разбор по имени `**`. Во временном представлении проверочного группировщика она выражается порогом `Limit(131, include_equal=True)`; арифметика `p + 1` при наличии явного правила равенства не нужна. Пара связывания не является новым фактическим аргументом или полем `OPERANDS_TEMPLATE`. Публичным числовым свойством остаётся `PRIORITY`; знак, чётность или биты этого числа не кодируют ассоциативность. Число `131` само по себе также не переопределяет политику любого пользовательского метода с тем же уровнем.

| Выражение | Группировка | Результат при допуске обычных целых |
| --- | --- | ---: |
| `a ** b ** c` | `a ** (b ** c)` | Зависит от значений |
| `2 ** 3 ** 2` | `2 ** (3 ** 2)` | `512` |
| `2 * 3 ** 2` | `2 * (3 ** 2)` | `18` |
| `2 ** 3 * 4` | `(2 ** 3) * 4` | `32` |
| `-2 ** 2` | `-(2 ** 2)` | `-4` |
| `(-2) ** 2` | `(-2) ** 2` | `4` |
| `2 ** -2` | `2 ** (-2)` | Определяется числовым договором |

Префикс в начале RHS сначала распознаётся как форма без левого вхождения и получает свой аргумент; порог инфиксного продолжения не запрещает такой префикс. Поэтому `2 ** -2` остаётся допустимой группировкой независимо от того, допускает ли выбранный числовой тип отрицательный показатель. Унарное `~` сохраняет ранее установленное направленное отношение со степенью; новый числовой код для него здесь не вводится.

Поэлементная степень, её модификация `.(depth)**` и квадратное семейство `[**]` используют тот же уровень `131` и правое связывание. Настройки осей и depth не меняют группировку; конкретный скалярный или матричный метод по-прежнему проверяет типы и арность. `**=` остаётся на низком уровне присваивания, как остальные составные присваивания; только операция степени в его правой части использует `131`.

## 5. Общее левое вхождение и вычислительный контекст

У каждой обычной операции есть отсутствующий либо один левый атом. Группа занимает ту же одну позицию. Для **каждой** операции группировщик сохраняет одинаковый внутренний вид этой позиции: исходное вхождение, область значения по приоритетам и ещё не потреблённый окружающий вычислительный контекст. Никакой проверки имени `:=`, роли PLACE/NAME или особого флага присваивания в разборе нет.

| Состав внутреннего представления `LeftView` | Назначение |
| --- | --- |
| Исходное вхождение | Один выбранный атом или структурная единица; идентичность сохраняется. |
| Область | План полного значения и ещё не потреблённый окружающий контекст. |

Это временная информация namespace, не новый аргумент или новый публичный тип LMX. Парсер не решает, какая часть будет потреблена как PLACE, NAME, RAW или значение. Этот смысл задаёт сам метод операнда через свой обычный договор.

| Запись | Что потребляет метод | Что остаётся выполнить |
| --- | --- | --- |
| `10 * 2 + 3` | Метод `+` получает значение всей левой области `10 * 2` | Добавить 3; результат 23 |
| `1 + v := 2 + 3` | Метод `:=` потребляет конкретное место `v` | Его результат 5 занимает это вхождение; остаётся `1 + 5`, результат 6 |

Во второй строке не происходит присваивания в `1 + v`. Метод использует один выбранный левый атом. Окружающий потребитель получает результат именно этого применения, а не повторно ищет переменную по имени. Поэтому `v := v + 1` читает старое значение отдельного правого вхождения `v` и не создаёт циклическую зависимость от будущей записи.

Группировщик одинаков для обеих строк. Потребление области и возобновление незавершённого контекста принадлежат общему механизму namespace/зависимостей. Другой метод с таким же договором места использует тот же механизм; пользовательский универсальный вход `@` от этого не объявляется PLACE автоматически.

Пути, индексы и составные адресуемые единицы предоставляет существующий анализатор соответствующих форм. Присваивание не получает отдельного синтаксического режима.

### Равнозначность двух записей решает сам метод

```lmx
(:= a 1)
(a := 1)
```

| Запись | Переданный `left` | `depth` | Переданный `right` |
| --- | --- | --- | --- |
| `(:= a 1)` | Отсутствует | Отсутствует | `[a, 1]` |
| `(a := 1)` | `a` | Отсутствует | `[1]` |

**Парсер и передача методу сохраняют это различие.** Первый правый аргумент не переносится в `left`, векторы не нормализуются заранее. Уже внутри метода операнда `:=` эти два входных случая обрабатываются как присваивание 1 в `a`. Это свойство его реализации, а не универсальное обещание эквивалентности любых двух таких форм любого пользовательского операнда.

Метод `:=` выбирает скалярное или Array-назначение по фактическим местам и собственному договору, не по предположению «depth=0 значит whole». Обе переданные формы — `(left отсутствует, 2 right)` и `(left присутствует, 1 right)` — сохраняются до выбора поведения внутри метода. `depth=0` означает максимальную глубину; отсутствие depth сохраняет default метода.

### Общий класс прижатых унарных форм

Операции, прижатые к одному атому слева или справа, сохраняют общий структурный класс с двумя направлениями. У них ровно один аргумент. Например, `++var` и `var++` обозначают разные разрешённые операции этого класса; он не ограничивается перечислением `++` и `--`.

Парсер устанавливает соответствующую структурную форму, а группировщик получает её уже в графе. Он не сканирует пробелы и скобки. В проверочном представлении `Binding.attached = "left" / "right"` отражает этот общий класс, без добавления поля в публичный `OPERANDS_TEMPLATE`. Значение, эффекты и выбор результата определяет метод конкретной операции.

## 6. Основной цикл разбора

Общий проход работает по вхождениям **графа**, читает готовые описания операций и строит временный план без исполнения. У порога есть отношение порядка и правило равенства; прибавлять единицу к реальному `PRIORITY` не требуется.

| Фаза | Точное правило |
| --- | --- |
| Получение связывания | Разрешить текущее вхождение и готовое описание операции. Для `.(expression)op` приоритет берётся у базовой `op`; исходное выражение depth и его контекст сохраняются без получения значения. |
| Начало единицы с обычного атома | Применить развилку раздела 1. |
| Начало единицы с операнда | Сохранить отсутствие `left`. Обычный префикс получает правый хвост по своему префиксному порогу. Прижатая слева операция получает ровно один следующий атом с цепочкой прижатых форм. Прижатая справа операция без предшествующего атома даёт ошибку. |
| Продолжение единицы | Пока следующая операция допускается текущим порогом, присоединять её к общему левому представлению. Обычный инфикс получает правый хвост по собственному правому порогу; прижатая справа операция не получает нового правого хвоста. Неоперанд, прижатая слева форма или недопустимый порог заканчивают это продолжение. |
| Правый хвост | Последовательно выбирать единицы того же структурного уровня. В **первой** позиции хвоста операнд допускается как префикс без левого атома, включая `2 ** -2`. После первой единицы операция, не принятая порогом хвоста, заканчивает хвост; прижатая слева форма начинает следующую единицу. |
| Один прижатый атом | Взять обычный атом либо рекурсивную цепочку прижатых слева операций, затем присоединить непосредственно следующие прижатые справа операции. Отсутствующий атом или обычный неприжатый операнд вместо него — ошибка. Широкий n-арный хвост здесь не потребляется. |
| Фиксация применения | Сохранить конкретное вхождение операции, исходный диапазон графа, контекст, один `left` либо его отсутствие, описание depth и выбранный `right`. |
| Завершение уровня | Повторять выбор единиц до конца уровня. Несколько единиц остаются последовательностью. Вложенные Expression-группы рекурсивно проходят этот же механизм и сохраняют одну внешнюю позицию. |

Например, эти формы используют обычную грамматику LMX:

```lmx
2 * (3 + 4)
2 ** 3 ** 2
2 ** -2
(op 1 2 3)
```

Второй независимый группировщик для Array, квадратных операций, интерпретатора или native-перевода не вводится. Тела операций во время этого прохода не выполняются. Исполняемая **host-модель** этих правил, включая `Limit`, `Cursor`, `LeftView` и `GraphView`, остаётся в отдельном проверочном файле [expression_grouping_reference.py](tools/expression_grouping_reference.py); это Python-инструмент проверки, не код реализации LMX.

## 7. Рекурсивный план и упаковка атомов

Уровень разбирается обычным `Planner.plan`; найденные вложенные Expression-группы проходят тот же алгоритм рекурсивно. После обработки содержимого группы применяется общий принцип **одна внешняя позиция**:

| Единица после разбора уровня | Рекурсивная нормализация |
| --- | --- |
| Группа в допущенной позиции Expression | Тем же алгоритмом обработать содержимое. Одна внутренняя единица становится содержимым одного внешнего атома; ноль или несколько единиц образуют одну материальную подгруппу. Присутствующая пустая группа не означает отсутствие аргумента. |
| Полная операция | Рекурсивно нормализовать только её Expression-аргументы, сохранив границы, приоритетный план, вхождения, стороны и описание depth. |
| TYPE, DATA, RAW или другая собственная роль | Сохранить материал по принимающему договору, без обхода как нового CODE. |
| Последовательность единиц | Применить эти правила к каждой единице. Не объединять поля соседних групп. |

Это внутренние представления, не новые поля исходного графа или системные функции. Необязательный actual depth входит в общий `OPERANDS_TEMPLATE`; описание его ещё не полученного выражения — временная информация применения, а не дополнительный публичный вход. В проверочном коде тонкая обёртка называется `PreparedAtom`, а материальная подгруппа — `PreparedGroup`. У единственного вложенного группового результата нормализуется его представление, поэтому `(((5 6)))` не сохраняет три контейнера в готовом плане: это один внешний атом с подгруппой `(5 6)`. Исходные узлы и контексты остаются доступны через представление.

**Нельзя просто подставить внутренний `Apply` вместо группового атома.** Для `2 * (3 + 4)` вычисляемый payload — целое применение `+`; для внешнего уровня это один атом. Иначе поиск соседнего левого атома может ошибочно войти во внутренний `+` и выбрать только `4`. `PreparedAtom` сохраняет эту границу, а `LeftView` по-прежнему хранит исходное вхождение и вычислительный контекст для каждого присутствующего `left`.

```lmx
1 + 2 (((3))) (4) ((5))       # нормализованный right: 2, 3, 4, 5
1 + 2 (((5 6))) (4) 5        # right: 2, одна подгруппа (5 6), 4, 5
1 + 2 (+ 5 6) 4 5           # right: 2, одна вычисляемая единица, 4, 5
```

Во всех трёх случаях план строится успешно. Внешний обычный `+` получает пять фактических значений и отклоняет такую арность внутри метода; Array-профиль не собирает дополнительные правые аргументы в неявный Array. Группировщик не добавляет операцию между `5` и `6` и не проверяет правила сложения. В третьем случае операция задана: внутренний `+` получает отсутствующий `left` и оба значения справа, что даёт `11` при его собственном запросе. Никакой перенос первого правого аргумента в `left` на этой стадии не допускается; внешняя арность от результата внутренней операции не меняется.

### Выбор последовательности и прежнее правило двух групп

После рекурсивной нормализации последовательностный потребитель выбирает элементы единственной материальной подгруппы либо уже имеющиеся соседние элементы. Этот выбор не вычисляет операции и не повторяет обход графа. В широком правом хвосте нормализованные подгруппы остаются отдельными аргументами.

Для `(a b c) := (a c b)` обе группы содержат по три единицы. Последовательностный договор получает `a, b, c` и `a, c, b`; отдельная подготовка применения передаёт всю левую последовательность одним `left`, а три правые единицы — массивом ссылок. Для `(a b c) := (f g h) (f g h) (f g h)` справа уже три нормализованные подгруппы: их поля не сливаются в девять аргументов.

| Представление | Сохранённая форма |
| --- | --- |
| Выбранные последовательности | Слева `a, b, c`, справа `a, c, b`. |
| Применение `:=` | Вся левая последовательность занимает один `left`; depth отсутствует; `right` содержит три ссылки в порядке `a, c, b`. |

`(a b) := (((x y)))` после нормализации единственной группы получает две правые единицы `x`, `y`. `(a b) := (((x y))) z` получает две единицы `(x y)` и `z`. `(a b c) := (((x y)))` отклоняется по количеству до первой записи. Утверждение прежней редакции, что дополнительные singleton-оболочки обязательно сохраняют внутреннюю группу как единственный элемент выбранной последовательности, заменено этим правилом.

У адаптера применения нет второго независимого раскрывающего прохода: рекурсивная работа принадлежит группировщику, а `prepare_actuals` только упаковывает уже выбранные ссылки. Отсутствующий `left` сохраняется. Полный TYPE, одна готовая структурная величина и DATA-описание сохраняют собственные принимающие договоры; `int -> (int int)` по-прежнему не становится `int -> int int`.

### Граф, контекст и отложенные эффекты

Каждое вхождение сохраняет исходный графовый диапазон и контекст. Ссылки разрешаются без изменения фактического `parent`. Применяется общая развилка имени/`parent`, а не тест написания скобок. Повторные вхождения одной цели остаются разными вхождениями; структурная подготовка не склеивает их эффекты.

Нормализация не является исполнением всего достижимого графа. Тело ресивера, DATA-инициализатор, RAW и возвращённое готовое значение не обходятся как новый CODE по факту наличия структурных полей. `PreparedAtom` хранит готовый план Expression; настоящий запрос результата, порядок эффектов и короткое замыкание обеспечивает общий механизм исполнения. Представление обратного графового ребра в host-модели сохраняет конечный план; оно не устанавливает новые правила выполнения циклических графов LMX.

## 8. Вложенное выражение, поток полей и ссылка

В позиции полного выражения `1 + ((2))` обрабатывается рекурсивно: внутренняя группа предоставляет одну единицу `2`, внешняя — результат этой единицы. Скобки при этом нигде не распознаются. В `target := (2 * 3)` обработка выбранного правого уровня даёт одну вычисляемую единицу `2 * 3`, а не три сырых аргумента `2`, `*`, `3`.

Одного количества физических детей недостаточно для всех случаев. `(copy(Model))` — коллектор потока полей, который создаёт один контейнер при 0, 1 и N полях. Его договор известен до выполнения; нельзя выполнить `copy`, сосчитать поля и задним числом выбрать другой смысл группы.

Для группового присваивания эти формы потребляют одинаковый поток:

```lmx
(a b c) := copy(d)
(a b c) := (copy(d))
```

В первой форме поток уже доступен потребителю. Во второй он собран в контейнер, из которого тот же последовательностный договор читает непосредственный уровень. Скалярное `ptr := (copy(d))` сохраняет один структурный результат; его оболочку удалять нельзя.

Аналогично, `(a b c) := myFn()` сначала получает один целый результат вызова.
Если это единственный Array справа, сам метод `:=` выбирает его непосредственные
элементы для трёх мест. Это приёмка Array, не новое раскрытие или исполнение
результата группировщиком. При трёх соседних Array справа каждый остаётся одним
элементом источника. Метод `:=` использует один общий алгоритм: выбрать реальные скалярные/Array-места, получить требуемые RHS один раз, проверить форму и допуск, затем записать сохранённые значения. Скалярное место получает одно значение; Array-назначение сохраняет свою форму и допускает соответствующие элементы. Это договор поэлементного присваивания, а не выбор между whole и Map по числу depth. Самостоятельный `.:` требует срез-назначение и допускает явное транслирование RHS. Группировщик не содержит ни проверки имени присваивания, ни этих алгоритмов записи.

При установленном `satisfies = 0` цель атома-ссылки на Structure остаётся одним Array в плане. Сохраняются её фактический `parent`, тождество и контекст. Её элементы может прочитать принимающая операция по своему договору.

## 9. Подготовка применения и исполнение

Планирование не выполняет тела. После выбора требуемых единиц адаптер:

1. Сохраняет отсутствие `left` либо получает один левый actual — целую единицу или пакет ссылок на выбранные места.
2. Сохраняет описание depth с исходным контекстом. Если actual задан, после установления востребованности получает и допускает одно значение объявленного int ровно один раз. Если модификатора нет, сохраняет отсутствие; глобальной подстановки 0 нет. Формы `.op` не существует.
3. Создаёт `right` как массив ссылок на элементы правой последовательности в их порядке.
4. Сохраняет исходные вхождения и контекст, необходимые собственному договору метода для NAME/TYPE/DATA/PLACE/BODY/RAW. RAW должен ссылаться на исходную целую единицу графа или её диапазон в текущем уровне; заменять её заново собранной строкой нельзя.
5. Передаёт методу выбранную форму **left, depth, right** без переноса первого right в left. Метод сам потребляет аргументы по своему договору; общий namespace затем возобновляет непотреблённый контекст. Полное внутреннее выражение не исполняется во время планирования.

Передача выполняется только для **уже востребованного** применения. Обычный namespace устанавливает востребованность и сохраняет ранее полученные значения окружающего контекста; последовательный запуск всех найденных синтаксических применений недопустим.

Метод получает неизменные `left`/его отсутствие и выбранную последовательность `right`. Только его собственный договор выбирает VALUE/PLACE/NAME/RAW и эквивалентную обработку префиксной и инфиксной форм. После выполнения namespace подставляет результат в конкретное потреблённое **вхождение**, затем возобновляет непотреблённую область по прежнему порядку эффектов и короткого замыкания. Если левого вхождения нет либо метод потребил всю левую область, результат этого применения уже является её результатом.

В host-модели учёт потребления называется `MethodOutcome`; это не новый публичный тип, скрытый параметр или обязательное поле LMX-метода. Замена определяется идентичностью вхождения графового плана, а не совпадением написанных имён. Для динамического depth требуется обычный запрос значения из namespace; отсутствие такого подключения не заменяется выдуманным числом или пробным запуском.

План сохраняет не только имя и готовый приоритет, но и конкретное вхождение операции (`operation_raw` в проверочном коде). Обработчик выбирается по разрешённой операции и её контексту, а не заново по строке имени. `GraphRange` удерживает исходный графовый диапазон целого выражения для RAW; текстовая реконструкция не требуется.

`RxLogicalArguments.collect` вызывается внутри метода операнда по его собственному алгоритму; `asOperand` помещает такой вызов в создаваемое тело. Передача сохраняет отсутствие depth либо полученный числовой depth между входами, сохраняя исходную форму left/right и не выполняет повторного раскрытия групп. При коротком замыкании не выполняется пропущенная ветвь. Результат одного востребованного вхождения сохраняется на время текущего вычисления; постоянного кеша в исходном графе нет. Разные вхождения ссылки на один узел не склеиваются в один эффект по идентичности узла.

Для группового присваивания порядок выглядит так:

Общее тело [FxArrayAssignPrepared](patterns/LMX_Fn_Receivers/src/array_expression_ops.lmx) сначала получает снимок RHS, затем допускает все значения и лишь после этого начинает записи. Вызов уже подготовленного контекста записывается на LMX:

```lmx
FxArrayAssignPrepared\assign(context; source)
```

`context` здесь — подготовленные реальные места и проверенная геометрия назначения, `source` — уже выбранный источник. Подготовка не выдумывает отдельный цикл записи для каждого оператора.

Таким образом, перестановка не читает уже изменённую левую часть. Ошибка количества или допуска не оставляет частично выполненной записи. Предыдущие побочные эффекты самих RHS при этом не получают новой транзакционной отмены.

## 10. Контракт depth и одного Array-подъёма

Полный договор находится в [OPERATOR_DEPTH](OPERATOR_DEPTH.ru.md). Временное представление уже разобранного вхождения `.(expression)op` сохраняет базовую операцию, её готовый приоритет и выражение/готовое значение depth либо его отсутствие; это не новый тип LMX. Отсутствие actual проверяется у данного применения; одноимённое поле другого динамического контекста модификатора не создаёт.

Общий transport передаёт одно целое, включая отрицательное; custom-метод волен использовать его иначе и не включать Map. Ни группировщик, ни общий transport не проверяют d<=rank. Дальнейшие правила относятся только к выбранному стандартному Array-профилю.

Rank — число осей Array. В этом профиле явный depth=0 означает максимальную глубину: для Array ранга K обходятся все K осей. Положительный d проходит d внешних осей, оставляя ячейку ранга K−d; d>K для итерируемого Array отвергается. Скаляр не создаёт frame и сохраняет обычный допуск скалярного расширения. Удержанный `$x` не участвует во внешнем обходе.

Отсутствие depth не подменяется числом. Default обычного Map — максимальный обход; default целостного `[op]` или потребителя DATA/TYPE/RAW — его собственный договор. После выбора ячеек выполняется **один вызов базового тела на ячейку без повторного автоматического Map**. Например, скалярный базовый `+` отказывается принимать строки матрицы при depth=1; depth=2 либо 0 подаёт её скалярные элементы. Пользовательский kernel может явно иметь договор целой строки.

| Фаза стандартного Array-профиля | Обязательный результат |
| --- | --- |
| Выбор | Метод и профиль выбраны по договору без пробного исполнения. Получение VALUE и явного depth подчиняется востребованности; пропуск depth сохраняется. |
| Внешний frame | Удержанные `$x` исключены из обхода; скаляры не создают осей. При явном d у каждого итерируемого Array обходятся все K осей при d=0 либо первые d при d>0. Значения d<0 и d>K отвергаются **этим профилем**. Остаток составляет ячейку. |
| Совместимость | Итерируемые frame совпадают точно. Тип, форма и размер результата известны до выделения памяти, включая пустой frame; kernel для определения типа не вызывается. |
| Исполнение | Для каждой координаты в объявленном порядке базовое тело получает выбранные ячейки и целые удержанные/скалярные actual ровно один раз. Автоматический Map на полученных ячейках повторно не включается. |
| Результат | Общая сборка сохраняет объявленную форму, тип и профиль хранения; исходный граф не переписывается. |

Для явного depth существующее тело вызывается на LMX:

```lmx
FxArrayDepth\apply(context; depth; inputs)
```

[FxOperandValueEngine](patterns/LMX_Fn_Receivers/src/coreStandardLisp.lmx) сначала проверяет присутствие depth в actual frame. При отсутствии он вызывает исходное тело по его договору; при наличии получает depth один раз, запрашивает общий `operandDepthContext` и вызывает `FxArrayDepth`. Этот исходник не доказывает реализации kernel-порта подготовки контекста.

Выбранный метод может вызвать обычную Array-операцию в собственном теле; это следующее явное применение. Structure `[]@` участвует в том же механизме по фактическим типам элементов и не получает исключения. Нельзя автоматически считать все достижимые ссылки, служебный parent или дескриптор типа дополнительными осями.

Удержание не выбирает скрыто `bias[j]` и не делает объект immutable. Численная точность, эффекты, допуск Array, пустые frame и сборка результата остаются условиями [общей спецификации](TENSOR_EXPRESSIONS.md).

## 11. Источник и граф: квадратные формы

[Квадратный подпарсер](BRACKET_SUBPARSER.ru.md) возвращает граф и позицию после собственной `]`. Компактная продукция `[op …]` распознаётся первой по полному designator и настройке. Пробельное `[ op]` сохраняет грамматику группы. Допустимость продукции в позиции обеспечивает общий P0.

Группировщик получает чистый граф. Для пунктуации и [явного вызова ресивера](BRACKET_SUBPARSER.ru.md#square-receiver) одна подготовка сохраняет границы, роли, порядок и присутствие аргументов и связывает их с объявленным методом.

Граф настройки квадратной операции сохраняет обычные поля. Отсутствие axisRules выбирает whole/default; присутствующий `()` — индексный список без связей. `A [* -> 1 0] B` сохраняет отсутствующий список и default умножение; `A [* ()] B` выбирает внешнее произведение. Опции не создают список осей. Методы не определяются пробным запуском, а точное имя `` `[* 1:0]` `` не переразбирается как конфигурация.

У индексных методов `i:j` выбирает contracted-оси, `i=j` — одну общую выходную ось, `i*j` — составную ось; выбранный метод определяет kernel и reducer. Только бинарный `*` имеет суммирование по умолчанию. Унарные `[+ 1:]` и `[+ 0:1]` — сумма и диагональная сумма; `[* 1:]` и `[* 0:1]` — соответствующие произведения. Геометрические формы без редукции объявляются отдельно. Группировщик не подменяет `[/]` решением через поэлементное `/` или наоборот.

## 12. Условные области, срезы и fuse

Условный метод получает RAW-области условия и обеих ветвей, затем вызывает существующее получение значения только для востребованных частей:

```lmx
condition ? yes : no
`?:`(condition; yes; no)
```

Обе формы передают исходные RAW-вхождения. Метод получает условие один раз, допускает его по договору `if` и получает значение только выбранной ветви в её исходном контексте. Тело другой ветви не запускается, а тождество выбранного результата сохраняется.

Это один договор для `a ? b : c` и `` `?:`(a; b; c) ``; вызов receiver не получает заранее три значения. Приоритет между `||` и присваиваниями, вложение справа. Парсер защищает вложенные двоеточия; группировщик потребляет готовые области. Отсутствующий depth условного метода не подменяется 0.

В VALUE срез создаёт независимый внешний Array без глубокого копирования. В PLACE он обозначает выбранные исходные места. `values[::-1] := values` использует точную форму; `matrix[:][:] .: bias` транслирует bias по фиксированной форме среза с выравниванием осей справа. Оба договора сохраняют снимок перекрывающегося RHS до первой записи; `.:` не является алиасом `:=` с depth=1. [Срезы](TERNARY_AND_SLICES.ru.md), [присваивание](TENSOR_EXPRESSIONS.md#assignment-contract).

Готовый Array `[arr2]` остаётся одним Array VALUE и не распаковывается как singleton-группа. В DATA `[a b]` и `(a b)` могут описывать одно поле Structure; принимающий договор, а не исходная скобка, определяет дальнейшее потребление. Различие TYPE/Array/Expression-группы устанавливается до исполнения, без пробного подсчёта возвращённых полей.

`fuse` получает RAW-план. Обязательная начальная поддержка — Scalar/Map с новым результатом; геометрия допустима только как поддержанный план чтения Map. MapReduce, ContractionMap и потоковые/изменяющие существующее назначение профили требуют отдельной заявленной поддержки. При её отсутствии — диагностика, а не скрытая материализация. `target := fuse(expr)` получает новый результат перед обычной записью; без отдельного договора слияние этой записи не обещано.

## 13. Проверка и границы реализации

Проверочная реализация [expression_grouping_reference.py](tools/expression_grouping_reference.py) и [общий transport depth](tools/operand_depth_reference.py) моделируют ограниченный набор графовых договоров. Проверки запускаются из `spec`:

```bash
python validation/expression_grouping_reference_test.py
```

Они должны проверять отсутствующий left, сохранение отсутствующего depth, единственное получение явного depth, неизменный right, приоритеты, прижатый класс, разные формы префиксного/инфиксного actual, нормализацию групп, целые Array, снимок RHS и допуск до первой записи. Прошлые отчёты host-проверок доказывают только явно указанную в них редакцию; количество прежних проверок не является подтверждением новых production-правил.

Source P0, настоящий транслятор, динамическое разрешение, все виды designator, native calls, численные профили, View и полный runtime этой Python-моделью не поставляются. Реализация нового квадратного подпарсера здесь описана, но не внедрена. Production-приёмка новых LMX-форм имеет статус **NOT_RUN**.
