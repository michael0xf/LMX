Предыдущая редакция с датированными checkpoint доступна в Git (`0e0a2978:steps/current.md`); подробные долги и свидетельства остаются в [плане v3](../next_core_tasks_v3.md), [тикетах](tickets/README.md) и [дефектах](defects.md). ## Полномочия и цель

По передаче 2026-10-17 в [to_codex.md](../to_codex.md) **Codex занимает единственный слот writer/build** ядра и продолжает план v3; OpenRouter после передачи только отвечает на вопросы. Датированный [to_openrouter.md](../to_openrouter.md) описывает прежний порядок, но больше не назначает writer/build. Opus и `fable_pc` не меняют ядро и не запускают сборку без новой явной передачи. Рабочий маршрут — [план v3](../next_core_tasks_v3.md); прежние планы доступны только в истории Git. Цель — полный kernel gate, затем две действительные самосборки из L3 со вставками L2 и почтовая матрица T01–T26. L1 допустим только как генерируемый промежуточный язык к C, не как поддерживаемый рукописный исходник.

В `main` принят N4 срез 1a (`6541e44b`), затем исправлены комментарии шага 9 (`9f08ef21`) и сохранены именованные типизированные поля N4 (`2e9569fe`). Остальная миграция N4/N4-U открыта; текущий `git status` проверять перед каждой правкой. Не объявлять будущие незавершённые изменения принятыми по факту наличия. Проверять точные исходные байты и зависимую полноту каждого среза. Историческая передача Fable/Opus/Grok не назначает второго writer/build; для связи с внешними агентами служит [маршрут](../work_chat/README.md), а не заметки о старых ACK.

## Действующая модель и граница исследования

- Правило языка универсально в своей области: один раз построить дерево P0, один раз разрешить выражение, затем проверить контракт принимающего места. Никаких исключений по имени, форме записи, типу или удобству backend. Если решения конфликтуют, остановить зависимый срез и представить автору минимальный пример с двумя нормами и фактическим поведением; независимую работу продолжать.
- Голый атом читает разрешённое значение или ссылку, но не вызывает. Обычная именованная Structure исполняется через `call: A`; `A()` и `A: ()` не являются её вызовом. Плоские объявляющие хвосты L2/L3 имеют порядок «имя — требование — необязательное значение», например `@: p Model`, как `int: i 5`. Миграция этих правил и затем генерируемого L1 ещё открыта в v3 M1–M4.
- Runtime хранит адреса, а не имена или отдельный граф значений. Обычный `merge` копирует используемый граф и перенаправляет внутренние ссылки через одну карту; допущенные `independent: immutable` ветви имеют отдельное правило владения. Числовой ключ, имя или специальная таблица не заменяют физический адрес. Основной контракт — [L3](../docs/LMX_semantics.ru.md), физический — [L2](../docs/L2_spec_ru.md).
- `Lmx` имеет заданное при построении число слотов и после публикации **не растёт**: адрес `@field` должен оставаться стабильным. Растущий `List` — другой механизм, он не меняет этот контракт.
- Утверждённая цель [K07](tickets/array-as-lmx-20261015.md): графовый Array сам является Structure `Lmx` с лексическим `parent` и обычной адресной идентичностью. Нынешний L1/L2 ABI, где `Lmx` начинается с `VoidArray`, а самостоятельный Array не имеет `parent`, — переходный и подлежит общей миграции единственным kernel writer/build; отдельного преобразования Array → Structure нет.
- Явные части метода `args`/`return`/`var`/`body`, полуавтоматическое наполнение `var` и `call: code data` — **утверждённая цель кодинга, ещё не готовый ABI**. Размер будущего `Lmx` вычисляется до построения; уже созданный узел не расширяется. Если явно переданный `data` не содержит необходимого коду поля, допуск отказывает до исполнения. Действующую инициализацию сохраняем. Решения и зависимые вопросы, начиная с `ptr: int: 5`, собраны в [миграционном описании](next_generation_model_20261014.md); порядок и gate — [v3 §2a](../next_core_tasks_v3.md).
- Исследование двусторонней видимости отложено автором. Не мигрировать код под неё без отдельного решения.

### K03: структурный Frame как значение — частичный срез 2026-10-16

Structure и не попадает в ошибку вызова без результата: он строит свежее
пустое структурное значение и проходит обычный допуск формала. `Model() + 1`

кластер `build/l2_harness/codex_k03_struct_cluster_77/summary.txt` — **15/15**
целей, включая native/walked пары. Полный L2 gate

FAIL**. Сравнение по FAIL-ID с `codex_n4_compound_full_69`: **0 новых FAIL**,
**0 исправленных старых FAIL**, две новые строки `Empty()` — OK, сообщения
остающихся 925 отказов не изменились. Это не закрывает весь дефект:
непустой `Model: (int: v 9)` в позиции значения пока красный в обоих
движках (`codex_k03_struct_frame_fields_76`, см.
[NAMED-STRUCTURE-FRAME-OPERAND](defects.md#named-structure-frame-operand)).
Следующая зависимость — общий конструктор значений из записанного тела

`NS-REDECL-CONSTRUCTOR`. Их native/walked свидетели в этом прогоне OK;
подробные пары и граница доказательства записаны в `steps/defects.md`.
Эта сверка не меняет 925 оставшихся FAIL-ID и не закрывает непустой Frame.

Следующий узкий срез G1 сохранил имя исходной головы Frame непосредственно на её единственном исполняемом вхождении, если Frame занимает всё предложение. Для многопольного выражения вроде `f() + 1` имя первого операнда **не** присваивается итоговому ADD. Перед вызовом записи имени проверяется, что физический слот действительно содержит Structure; это важно, поскольку сам setter имён не проверяет вид значения. Строгий независимый P0→graph-свидетель теперь требует точное имя у корневых исполняемых вхождений 1 и 2 в native и walker, а компаратор тела метода сверяет имя Frame на каждом соответствующем физическом OP-слоте, включая initializer и assignment, не по общему множеству имён графа. ### G1: источник примитива и точный частичный оракул (2026-10-14)

Предыдущие абзацы этого раздела описывают байты указанных там checkpoint, а не текущий layout `PRIM_PUB`. Новый ограниченный G1-оракул для корневого `sendMessage: m\sender exit(...)` теперь разбирает внутренний путь Ref по P0 и сравнивает его с физической цепочкой `OF`: база должна заимствовать именно объявленный `OWN`-узел `m`, координата поля выводится из модели письма, а не из ожидаемого exit code или равенства двух дампов. ### M2: межпроцедурное замыкание кандидатов (Opus, 2026-10-15)

Корневой анализ `l2_m2_root_current` и статический выбор тела по объявленной
модели в методах заменены одним проходом `l2_m2_close`. Он выполняется до CHECK,
то есть до фиксации рёбер вызовов, скрытых входов, `throws` и размеров кадров.
Проход проигрывает тела корня, методов и процедур именованных Structure над
состоянием физических мест: own-строк и мест именованных Structure. Для каждого
места известно одно из трёх: доказанное тело (ns), доказанная пустая Structure
или «неизвестно». Вход метода — объединение состояний всех мест его прямого
вызова, включая вызовы внутри выражений. Процедура Structure получает состояние
тех `call:`, чей сертификат указывает на её тело. Метод, имя которого читается
как значение, передаётся, удерживается или служит шагом пути, а также любой
метод библиотеки начинают с неизвестного состояния. Сертификат каждого `call:`
— объединение всех посещений этого узла. CHECK, подсчёт, native и walker во всех
методах читают один и тот же сертификат. Если сертификат не доказан, вызов
отклоняется с диагностикой `the current Structure body is not proved at this
call`; запасного выбора тела объявленной модели нет. Если операнд вообще не
адресует место, остаётся прежний отказ `executing a named Structure is not
supported yet`.

Место исходной Structure, которое не пишет ни один оператор, везде сохраняет
сконструированное тело. Вызов забывает только места, которые вызываемая
процедура может записать по транзитивной сводке. К ним добавляются места с
взятым адресом, места, записываемые маршрутом, который не назван ни в одной
сводке, а для вызова без названного вызываемого — сводки всех методов,
входимых иначе. Оператор, чью собственную запись нельзя назвать, забывает всё,
кроме сконструированных мест. Запись по пути, включая `Outer\Model()`, забывает
все места, имя которых совпадает с последним шагом. Ветвления объединяются.
После `return`, `throw`, `break` или `continue` путь дальше не идёт. Тело цикла
и обработчик `catch` видят только неизменяемые места. Локальное определение
Structure заново строит на своём операторе сконструированное тело. Результат
`merge` держит тело своего выбранного источника (правило Q8 — в разделе
«M1/M2: голое имя копии, выбранное тело `merge`, две регрессии» ниже).
Вспомогательная проверка «чистоты» тела при вызове удалена: её заменили сводки
записей. До этого она читала контракт пути не в методе процедуры.

Свидетель `unit_named_struct_call_method_rebound_hidden` теперь исполняет B с
её скрытым входом `status`. В сгенерированном `run` вызов `lmx_call_prim`
передаёт один вход. Native и принудительный walker проходят. Добавлены два
свидетеля. Положительный `unit_named_struct_call_method_chain` проводит тело
через два метода и вызовы внутри выражения. Отрицательный
`unit_named_struct_call_method_branch_refused` объединяет два разных тела на
входе метода и даёт отказ в `13:5`. Фокус из 115 прежних M2/копий/Structure
фикстур дал **105 из 118 целей** (`build/opus_m2_close_20261015_01/summary.txt`)
против **86 из 118** на исходной рабочей копии
(`build/opus_m2_baseline_20261015_01/summary.txt`). Восстановлены 19 фикстур, в
том числе восемь `graph_shape_ns_source_*` и пять `unit_named_struct_exec_*`;

### N4: ядро разделённой активации `call: code data` (Opus, 2026-10-15)

Первый шаг N4 — обходчик ядра принимает код и данные раздельно. Правила
`call: code data` записаны в нормах (коммиты Codex `1ce73ea1`, `aa5f9a60`,
`cfb4c237`, `7a1de521`; ответы на OPUS-CODEX-20261015-17…19 и -22):
- исполняемые объявления кода на любой глубине — присваивания в выбранную
  `data`;
- карта полей `data` строится только по головам её корневого уровня;
  `if`/`for` на нём — одна голова, их тела полей не дают;
- если имя встречается два раза или больше, голое обращение неоднозначно и
  требует индекса; «первого вхождения» нет;
- затенение бывает только при явном вызове;
- отсутствующее, неоднозначное или непригодное место — отказ `call` при
  допуске вызова во время исполнения.

Транслятор этих правил ещё не исполняет: он по-прежнему передаёт одну и ту же
Structure как код и данные. Поэтому для существующих программ шаг ничего не
меняет.

Ядро (`lmx_walk.lm1`):
- `EXEC` получает данные в слоте 1. Они вычисляются один раз после кода
  (`lmx_walk_exec_data`). Пустой слот — данными остаётся сам код.
  Удерживаемый null — неявный отказ `interpreter`, не Structure — INVALID.
  Принимающий допуск в слоте 1 читает требование в пространстве кода.
- `node` — родитель кода, а не данных: база `NODE` — `f\code`.
- `EXEC` без контракта проверяет код как Structure без полей и исполняет его
  над любыми данными.
- Принимающие аргументы `CALL`/`EXEC` читают требование в пространстве
  выбранного кода.

Свидетели — одиннадцать новых проверок `lmx_walk_call_data_selftest`:
- проекция полей через запись `(data, code)`;
- без записи — INVALID, а не чтение порядкового номера кода;
- null-данные;
- порядок «код, затем данные»;
- `node` кода;
- `EXEC` без контракта;
- пространство принимающего аргумента.

Шесть мутантов ядра — по одному на каждое правило — роняют свои проверки.

### N4: `call: code data` в трансляторе — срез 1a (Opus, 2026-10-16)

Шаги 4b–8 плана N4. Двухоперандный вызов исполняет код над явно
переданными данными в native и в обходчике. Ответы Codex:
OPUS-CODEX-20261015-19, -23, -24, -25 и OPUS-CODEX-20261016-27.

Форма вызова (шаг 5). Прежний отказ «call expects one Structure reference»
заменён отказом для каждой формы операндов, в своём месте:
- `call()` и голое `call` — «call needs a code Structure»;
- третий операнд — «call takes a code and one data operand: a third operand»;
- неполный операнд данных — «…: the data operand is incomplete»;
- хвост Frame, кроме `end: call`, — «unsupported trailer». `end: call` только
  закрывает Frame: блок `call: / S / end: call` — тот же вызов (-25).

Операнд данных среза 1a — именованная Structure, раскладку которой доказывает
трансляция. Остальное отказывает с названием своего будущего пакета:
- не имя — «waits for the path-operand slice»;
- формал, скрытый вход, перепривязанное место — «the layout of data … is not
  proved at this call; rows for layouts known only at run time are not built yet»;
- код в месте — «the code … is held in a place; running a code held in a place
  over explicit data is not built yet»;
- число — «call: data n is not a Structure»;
- имя, которое корень читает раньше объявления, — «unresolved name».

Карта мест (шаг 6). Строки процедуры кода делятся на классы:
- 1 — число или char в корне или во встроенном теле (`if`, `else`, `while`,
  `until`, `---`, `for`, курсор `for` по -24 Q1 (a)), вне цепочки `catch`:
  место данных. Видимо с позиции объявления, также после тела, и не
  переносит входа. Одно место на имя; его представитель — первая строка
  имени в порядке исходника;
- 5 — вложенный `fn`/`sub`: место кода;
- 2 (ссылки, Arrays, слоты, merge, receive, определения `T:`), 3 (значения
  `catch`), 6 (явная `var:`): отложенный отказ, который называет свой пакет;
- иное — внутренняя ошибка.

Имя класса 1 с другим типом или другим видом на другой глубине — «assignment
value has incompatible type» (R04). Одноаргументный вызов кода с именами
отказывает: его данные — `S\var`, а эта форма ещё не построена (H06).
Строка таблицы для раскладки данных берёт слот корневой строки с той же
буквальной головой и тем же типом. Места нет, оно неоднозначно (две головы
и больше) или непригодно — SIZE_MAX, и тогда вызов может отказать при
исполнении неявным `call`. Место внутри `until` данных отказывает при
трансляции: строке с путём ещё нет. Если квалифицированные данные пишутся
вызовом, это отказ «call would write an immutable field of its data» (D12).

Native (шаг 7):
- у процедуры с именами есть таблица `l2_cpt<P>` = `[m, k, строки (токен
  раскладки, слоты m имён)]`. Пролог выбирает строку по токену своих данных
  (`l2_cpl`); не YES — X1;
- места класса 1 читаются через `l2_cpl`, рабочее значение одно на имя
  (представитель);
- места кода (тела управления, вложенный метод как значение, путь `S\x`
  через имя процедуры) берутся от `l2_call_code`;
- точка вызова выбирает данные рядом с кодом и после скрытых входов и
  публикации допускает их по таблице: NO — неявный `call`, если строка может
  отказать (метод тогда на канале статуса), иначе X1; UNKNOWN — X1;
- в библиотечном режиме имя таблицы хэшируется по модулю, как у остальных
  таблиц модуля.

Обходчик (шаг 8):
- слот 1 `EXEC` — данные. У кода с именами это `CALL_DATA [call_data, data,
  tokens, table]` с той же таблицей `l2_cpt<P>`, иначе сами данные.
  Двухоперандный вызов без решения о данных — внутренняя ошибка, а не вызов
  кода над собой;
- место класса 1 — `OWN/AT/SET/PUT [op, PLACE, r]`, где `PLACE [place,
  tokens, table]`, а `r` — порядковый номер имени. Узел строится в каждом
  проходе, до фиксированных держателей. Рабочее значение — по
  представителю;
- места кода — от `NODE(0)`: корень тел управления, путь через имя
  процедуры, `fn` кода как значение. Держатель 0 или фиксированный держатель
  внутри кода, который всё же дошёл до построения, — внутренняя ошибка;
- ворота обходчика (объявление, чтение, скрытый вход, допуск метода к
  обходу) принимают место класса 1, где бы ни стояла его строка;
- harness: модель графа вычисляет слот 1 `EXEC` и слот 1 `CALL_DATA`.

Ядро (шаг 4b, SF14):
- активация, в которую `EXEC` вошёл с явными данными, не переносит позицию
  кода в данные. Держатель 0 и фиксированный держатель внутри кода там
  INVALID, также без таблицы мест (код без имён). Отметку ставит `EXEC`,
  берёт вход активации, вложенные вызовы её не наследуют;
- проекция `OWN` через запись implements фактической пары остаётся (Codex
  -27: одна общая доказанная адресная связь для любой допущенной пары, не
  особая карта `call`). Тест шага 1 теперь прямо говорит, что запись
  поставлена вручную вместо доказывающего её допуска;

- `CALL` с данными в слоте 2 допуска не делает: строку разрешает вход
  вызываемого, и строка не YES там INVALID (KW13). Native-путь

Допущенная таблица не передаётся вызываемой активации (SF12): точка вызова и

Для N2 подготовлен общий kernel ABI разделённой активации: выбранное
вхождение метода (`code`), исполняемое `body`, исходная схема полей `source`

физического графа. Старый плоский вход использует тот же путь с
`body = source = code`. `OWN` сопоставляет слоты `source` с `data` через
существующую карту `implements`; загрузка рабочих значений и скрытых входов
обходит выбранное `body`, а не весь корень метода. Новый kernel-свидетель
строит `args`/`return`/`var`/`body` как четыре дочерние Structure метода:
два вызова публикуют `var.x` как 5 → 6 → 7 без копии тела или пересоздания
метода. Предварительный gate `codex_n2_parts_188` был RED 2/305 и выявил
отсутствие отдельной `source`; `_189` прошёл новый свидетель, но был RED
1/305 из-за старого тестового вызова с неверной формой доступа к C-полю.

метода в L2, разрешение `method\var\field`, инициализация `var` и общий
native/walker-вызов метода ещё открыты, N2/N3 не закрыты.

### P1 ревью коммита `8f693011` — два дефекта подтверждены, 2026-10-17

Постфактум-ревью Codex (`CODEX-REVIEW-8f693011-20261017T041254Z`) назвало
два P1; оба подтверждены чтением кода, исправление — следующий срез:

1. **Унарный выбор по равенству указателей** (`lmx_walk.lm1:3439`):
   `if: data = code → data: vars` меняет data у **любого** совпадающего
   по адресу вызова, включая явный алиас `call: F F`, который обязан
   передавать сам `F` без поиска var (`docs/LMX_semantics.en.md:416`,
   v3 §2a N4). Тот же путь идёт из `lmx_walk_call_prim_dispatch`, и
   эмитированные унарные хвосты (`l2_mad_call` → `lmx_call_prim(code,
   code)`; `l2_emit_dyn_tail`) сегодня **полагаются** на этот выбор
   (Q8: `call: R` исполняет выбранное тело над `R\var`). Значит
   сигнал обязан быть явным и структурным, не равенством: унарные места
   формы (walker: короткий CALL, CALL с пустым слотом 2, EXEC с пустым
   слотом 1, `lmx_walk_run`; native: унарные хвосты эмиссии) выбирают
   `var` через общий сервис; явно переданный data проходит без
   изменений. Сервис: `lmx_call_unary_data(arena, code)` — fn-голова по
   таблице адрес→имя, 4 части, слот 2; иначе сам `code`. Из
   `lmx_walk_activate` замена по равенству удаляется, валидация
   четырёхчастной формы остаётся. Свидетель: `F` с записываемым полем
   вне `var`, унарный и алиасный вызовы дают разные выходы, native и
   walker.

2. **Разделение var/body у фабричной копии** (`l2trans.lm1:53665-53682`,
   `:54417`; `lmx_walk.lm1:3855`): `lmx_walk_cell_copy` возвращает
   оригинал для любой Structure — var и body части скопированного
   вхождения **разделяются** с источником (старые родители/арена), а не
   копируются картой, как требует полная копия
   (`docs/LMX_semantics.en.md:665,687,693`). Исправление: одна карта
   копирования для присвоенных частей с переписыванием внутренних
   ссылок/родителей; свидетель — возвращённые var/body не алиасятся с
   исходными и native/walker совпадают; если какая-то immutable-ветвь
   умышленно разделяется — доказать её квалификацию явно.

Ревью Codex: не считать N2/K03 dependency-closed по kernel 305/305 и
L3 (полный L2 после фиксов без сводки; фокусные пробы красные).

После принятого фокуса `_66` этот избыточный `_60` намеренно остановлен
для освобождения ресурсов итоговому `_65`; конечного verdict у `_60`
нет. Он не является полным gate окончательного варианта. Общий §8 ещё не выполнен.

`codex_p1_capture_alias_probe_63`: два аргумента фабрики ссылаются на
одну `Model`, возвращённый метод меняет `a\v` и читает `b\v`; ожидается
2 при неизменном исходном объекте (1). Прежний `lmx_walk_capture` делал
отдельную частичную копию на имя, поэтому связь терялась: exit 81 в
native и walked-root. Теперь C сначала содержит реальные ссылки на
значения захватов; C и модель копируются двумя корнями **одной общей
карты**, с сохранением алиасов и допущенных адресных соответствий.
Отдельных field-by-field копий Structure в конструкторах больше нет;
устаревшие расчёт/массив списка полей удалены. Временная стадия C не
является вторым авторитетным графом исполнения.

Фокус `codex_p1_capture_map_focus_64` — 26 фикстур, 25 GREEN; единственный
FAIL — старый текстовый oracle с одним корнем копии. Новый alias-тест и
его `--walk-methods` вариант GREEN, прочие поведенческие проверки,
включая Wide-аргумент, GREEN. Oracle переведён на два корня одной карты;
повтор `_66` — **10/10 целей GREEN**. Полный окончательный снимок —
`build/l2_harness/codex_p1_capture_full_65`, не `_60`.
Свежий kernel `codex_p1_copy_final_kernel_62` — **305/305 GREEN**;
после него общие kernel-файлы не менялись. Код остаётся WIP до полного
`_65`, сравнения FAIL-ID/диагностик с `_30` и оценки зависимой полноты.

Дополнительная проба `_68` (`codex_p1_capture_distinct_probe_68/run.ps1`)
передаёт фабрике две **разные** копии Model одинакового типа, формы и
содержимого. Запись через `a` не меняет `b` и ни один исходный объект:
оба режима генерации (native и `--walk-methods`) проходят с нативным
и с принудительно обходимым корнем (четыре запуска, exit 0). Это
дополняет alias-свидетель: карта сохраняет тождество адреса, но не
склеивает одинаковые значения. Ни snapshot `_65`, ни ядро ради пробы
не менялись.

Дополнительная scratch-проба `_57/probe_node.lm2` читает `node\n` у
соседнего вложенного метода. На `_58` и на базовом трансляторе `_30`
она одинаково даёт «a field path met no Structure» (native и walked-root);
это прежний разрыв адресации, не новая регрессия полной копии. Материалы
и скрипт сравнения остаются в `build/l2_harness/codex_p1_copy_sibling_probe_57`.

### Следующий срез M2 — фактический код метода в общем call

Read-only разбор после `_59`: `l2_m2_constructed` и состояния
`l2_m2_call_site` хранят идентичность тела только как индекс обычной
именованной Structure; `l2_struct_call_plan` не получает от этого прохода
источник результата `fn`. Это не основание делать отдельное разрешение
алиаса по равенству адресов. Нужны общий учёт фактического тела/вхождения
из уже имеющихся source-полей (`l2_source_definition_method` наряду с
`l2_source_definition_ns`), его рёбер и записи в него, затем тот же
допуск выбранных данных и одинаковые native/walker-пути.

Три минимальные scratch-пробы `build/l2_harness/codex_m2_method_probes_61`
на трансляторе `_60` одинаково отказаны при трансляции с «the current
Structure body is not proved at this call»: метод без own-полей с
`call: step step`, метод с явно подходящей `Data` в `call: step Data`,
и алиас метода с локальным `x`, которого нет в корне самого `step`.
Последний случай нельзя объявлять положительным по одному факту алиаса:
передана именно Structure `step` с `args/return/var/body`, не её `var`.
Норма §method-parts требует общий допуск нужных полей выбранной `data`;
отсутствующее поле даёт отказ допуска/исполнения, а не подмену данных и
не отказ исходной трансляции `call`. Старый scratch-свидетель
`stage4/witness_p1_alias.lm2` не является отдельной нормой для такой подмены.
Это следующий срез после принятого полного gate P1#2, не отдельная
ветка разрешения алиаса и не часть текущего WIP копировщика.

Вторая обязательная зависимость найдена в native-привязке собственных
полей: `l2_split_data_row` и `l2_split_close` классифицируют только
процедуры обычных именованных Structure (`l2_m_nsof`), а ветка `fn` в
`l2_own_from_expr` берёт место из части выбранного `l2_call_code`, не из
произвольной переданной `data`. Те же NS-only ограничения есть в
`l2_rw_split_data` и `l2_emit_struct_call`. Поэтому одного расширения
сертификата тела недостаточно: общий контракт own-мест/карты допуска
нужен для чтения, `@` и публикации в обоих движках. Операторы/исходные
значения остаются в выбранном code, изменяемое поле выбирается в data.
`explicit_data.lm2` в `_61` использует постоянную запись `x: 6`, чтобы
проверка `Data\x = 6`, `step\var\x = 1` не зависела от отдельного
незавершённой реализации исполнения инициализаторов N3. Не включать fn в
M2 через исключение «нет own-полей» и не подменять переданную data.

Дополнительный адресный дефект измерен пробой `_69`: формал `n` и
третье локальное поле попадают в один C-слот 4. На базовом `_30` и
текущем `_66` все четыре режима дают ошибочный exit 81 вместо 7;
сама программа ожидает 73. Конструктор точно показывает две записи
разных значений в `lmx_arena_ref_store(l2_madc, 4U, ...)`.
[Полный минимальный пример](defects.md#capture-context-coordinate-collision)
сохранён для общего M2/N4-контракта исходных мест, без подгонки offset.
Это старая ошибка подготовки C, не новая регрессия копии, и она не закрыта.

### Перепроверка отложенного body-path семейства

`codex_body_path_probe_67` на снимке P1#2 `_65`: **12 целей, 8 FAIL**
(9 фикстур + build/scope). Все восемь `unit_walk_body_path_*` сохраняют
ровно FAIL-ID и диагностику базового `_30` (exit 3); положительный
контроль отказа по отсутствующему имени также совпадает. Полная копия
фабрик это семейство не исправила и новых расхождений в этом фокусе нет.

До исправления AT-цепочки сверить смысл oracle с текущим разделением
code/data: старые источники читают `else\hosted` и другие inline-тела.
Норма §node/§method-parts требует место состояния в выбранной data,
без отдельного локального хранилища inline-оператора. Чтение самого
code-графа и чтение опубликованного состояния — разные проверки;
нельзя безусловно закрепить старое размещение own-поля в коде, просто
сделав walker похожим на старый native. Сам ticket не отменён:
его проверка следует за зависимым общим контрактом M2/N4 и миграцией
свидетелей, как записано в очереди `to_codex.md`.

### Инвентаризация §8 без запуска переноса

Пока полный P1#2 gate идёт, read-only аудит проверил фактические входы
существующих build runners. [Карта closure](closure-map.md) переписана:
старые назначения сентября по удалённому `next_core_tasks.md` оставлены
в Git, текущий текст описывает v3 и не является готовым manifest G0.
Kernel/L3 runners берут kernel-side `dev/l2src_sandbox/l1src`, не
одноимённый корневой набор. Частичные `parser_scan_port.lm2` и
`parser_alloc_port.lm2` сохраняют L1 headers/вызовы и ещё не замкнуты.
`dev/l3_interp/l3_exec.lm1` и `l3_recv.h.lm1` сохраняют legacy
`LmxOp`/`L3_NODE_*`: 11 GREEN suites не доказывают новую модель L3.
План §8 теперь ссылается на эту инвентаризацию; перенос по-прежнему
не начинается до принятого чистого ядра. Рукописные L1 не объявлены
generated, PS/Python orchestration не засчитан language-owned самосборкой.
