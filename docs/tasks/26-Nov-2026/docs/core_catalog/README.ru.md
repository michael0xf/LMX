# Каталог ядра LMX и компактных C99-библиотек

Это патч с описью, предложением пакетов, исходниками обёрток и руководством
подключения к ядру. **Первичные данные находятся в LMX-файлах.** Таблицы
Markdown и поисковые JSON-файлы являются их справочными проекциями.
Нормативная основа — текущая `docs/spec`, а не более старый самосборщик.

Файлы `docs/core_catalog/` подготовлены для дальнейшей работы агентов.
Они не регистрируют тысячи новых функций в работающем интерпретаторе.
Опись теперь охватывает **все 180 компонентов текущего SOURCES.json**:
включены 23 компонента, уже присутствовавшие в загруженном снимке,
но отсутствовавшие в его каталоге, и 25 новых C-компонентов этого
дополнения. Нативные сборки и их выбранные профили проверяются отдельно;
точная область каждого результата приведена в
[сводке проверок](validation/README.ru.md).

## Что посчитано

В загруженном снимке было 155 C-компонентов, а каталог описывал только 132:
32 122 записи и 19 331 кандидата вызова. Текущая полная опись содержит
**54 261 записей**, **33 048 различных кандидатов на публичный
вызываемый API** и **1 592 исходных поверхностей заголовков**.
Сравнение с загруженным снимком находится в
[api_census_delta.json](validation/api_census_delta.json), сверка состава
LMX-плана и моделей — в [catalog_scope_check.json](validation/catalog_scope_check.json).

Сохранены все прежние идентичности публичных callable. Исправлены 47
ошибочных исторических callback-идентичностей: декларации с calling convention
или скобками вокруг имени typedef раньше ошибочно назывались по возвращаемому
типу, например `void` или `int`. Теперь у них восстановлены настоящие имена,
а обычные integer/void-pointer параметры не становятся ложными callbacks.
Каждая такая замена перечислена в
[таблице миграции](validation/callback_identity_migration.json).

Число кандидатов не является числом готовых функций L3. Каталог отдельно
хранит обычные функции, inline, callable-макросы, callbacks, шаблоны деклараций,
SQL-регистрации и другие записи. Разные объявления одной функции, в том числе
extern/static/inline, объединены с сохранением всех вариантов и исходных мест.
Заявленные, но отсутствующие реализации, условная компиляция и выключенные
профили остаются явно видимыми. Генератор не создаёт включаемую native-ветку
для отсутствующего профиля или обязательного application hook.

Большие публичные наборы требуют дополнительных различий. GL/EGL prototypes
в interoperability headers SDL — контракты внешнего графического драйвера,
а не тысячи реализаций внутри SDL. SDLTest относится к отдельной тестовой
библиотеке; `SDL_main` и `SDL_App*` — к host application. APR skiplist сохранён
как недоступный выбранному strict-C99 профилю. У embedded libc публикуется
только фактически собранный façade из 80 префиксованных функций.

Сверка с native `.a` считает только совпадения имён определений. Она не
доказывает ABI, доступность устройства/драйвера или возможность связать все
объекты одной командой. Профиль и область наблюдения указаны в
[expanded_archive_symbols.json](validation/expanded_archive_symbols.json)
и [сводке проверок](validation/README.ru.md).

В [core/README.ru.md](core/README.ru.md) отдельно описаны 215 имён текущего
LMX-ядра, 227 вариантов договоров, системные receiver, значения, языковые
формы, будущие профильные договоры и исторический индекс самосборщика.
Исторические и проектные записи не прибавляются к числу готовых функций ядра.

## Как пользоваться обёртками

Простая скалярная форма, отобранная по извлечённой сигнатуре, содержит
непосредственный вызов именованного C entry. Её header, ABI и профиль ещё
проверяются при интеграции в LMX. Сложная форма вызывает свой именованный C shim;
его полная исходная C-сигнатура и договор данных находятся в описи.
Строкового универсального диспетчера C-функций здесь нет.

`BridgeLower\open(request, catalog, entry)` — явный **контракт будущей
интеграции**, а не уже существующая функция ядра. Он должен проверить
модель, владельца, доступ, размеры и взаимосвязи аргументов, затем удержать
ресурсы и подготовить временный C frame. Сразу регистрируется `finally`;
`finish` переносит проверенный результат в обычные LMX-данные, `release`
освобождает оставшиеся удержания на любом выходе. Одна проверка поколения
без удержания памяти недостаточна при callback/reentry.

Полные однотипные C-шаблоны не размножены на десятки тысяч файлов. Три
образца лежат в `c_shims/`; конкретный файл можно получить из самого
LMX-каталога, без исходного промежуточного JSON:

```sh
python3 docs/core_catalog/tools/build_c_catalog.py \
  --catalog-root docs/core_catalog \
  --emit-shim compress2 --component base:zlib \
  --shim-output build/compress2_bridge.c
```

По умолчанию такой шаблон возвращает `REVIEW_REQUIRED`. Для рабочего
адаптера нужно реализовать именованные преобразования и проверки его
реальной сигнатуры: pointer/length, in/out, callback, ownership, ошибки и
квоты. Пустое тело или успешный нулевой результат не используются как
замена отсутствующей интеграции. Декларации без реализации не получают
включаемую ветку фиктивного native-вызова.

[compress2_example.c](bridge/compress2_example.c) показывает завершённый
адаптер одного такого шаблона: реальный zlib-вызов, связанная проверка
ёмкости и длины, typed in/out-ячейка и публикация результата. Его 67
проверок включают сжатие/распаковку двоичных данных и отказ до входа в C
при неверном владельце, сроке жизни, типе, правах или пересечении буферов.
Три не включённых шаблона отдельно проверены на явный `REVIEW_REQUIRED`.
См. [generated_shim_tests.json](validation/generated_shim_tests.json).

Пакет остаётся обычным путём в графе. Его определение с
`independent: immutable:` совместно используется через ссылки: **сам объект,
CODE и неизменяемые DATA не копируются в арены акторов**. Bootstrap явно
передаёт выбранные ссылки, сохраняя действительные parent-связи и lifetime
владельца. `Message` не означает автоматического доступа ко всему R0.
Изменяемые данные активации, C contexts и рабочие буферы имеют отдельных
владельцев; поле `request` в учебной обёртке относится к конкретному вызову.
Подробный договор — в [ARCHITECTURE.ru.md](ARCHITECTURE.ru.md#5-r0-акторы-и-общие-неизменяемые-определения).

## Общие данные и новые примитивы

`Buffer`, `Tensor`, `Image`, `Audio`, `ComplexBuffer`, `NetworkAddress`,
`Resource` и остальные модели описывают обычные LMX-данные. Они помогают
использовать несколько C-библиотек без размножения одинаковых видов
пользовательских значений. Несовместимые C structs не становятся одним
типом из-за совпадения имён или размера. Подробности — в
[types/README.ru.md](types/README.ru.md).

Основные новые числовые примитивы:

| Значение | Основная реализация | Альтернативы и границы |
|---|---|---|
| `bigint` | Уже имеющаяся LibTomMath | IMath и integer API LibBF через явные преобразования |
| `decimal` | Уже имеющаяся MPDecimal | decNumber и decimal API LibBF с проверкой precision, rounding, quantum и status |
| `real` | LibBF, произвольная двоичная точность | LibTomFloat как явно экспериментальная реализация; binary64 только явное сужение |

Для `real` написан работающий C99 reference: отдельный контекст владельца,
квота native-памяти, очистка, rollback и явное клонирование обычного
изменяемого значения в контекст другого владельца. Для совместно используемого
`independent: immutable:` значения сохраняется ссылка без клонирования payload. Проверено сохранение `1+2^-100` при 256 битах и работа копии после
уничтожения исходного контекста. Код учитывает естественное выравнивание
payload и четырёхбайтовый код перед ним. Инструкция и исходники находятся
в [new_primitives/README.ru.md](new_primitives/README.ru.md).

Контекст точности и ресурсные пределы передаются явно. Квота памяти не
является гарантией времени исполнения любой C-функции: размер входа и
precision надо ограничивать до вызова. На процессорах класса 100–200 МГц
эти реализации не измерялись.

## Компактность и независимые реализации

Текущее расширение и ранее пропущенные 23 компонента перечислены в
[обзоре покрытия](additions/COVERAGE_2026-11-26.ru.md). Отдельно описаны
[научные форматы и netCDF-5 / CDF-5](additions/SCIENTIFIC_FORMATS.ru.md).
Исторический [обзор первых 20 добавлений](additions/OVERVIEW.ru.md)
сохраняет их собственные измерения, лицензии и результаты; он не является
итоговым списком всей сегодняшней коллекции.

Состав сохраняет полезное дублирование: FFT, RNG, большие числа, Unicode,
хеширование и другие задачи могут иметь несколько независимых реализаций.
Общая модель данных не обещает одинаковые округление, нормировку, порядок
байтов, время жизни результата или безопасность потоков у всех backend.

В поставку входят исходники выбранных профилей, нужный платформенный код,
локальные входы сборки, лицензии, короткие пояснения, код примеров и тестов.
Скачанные дистрибутивы целиком, история Git, большие manuals, build trees,
готовые `.o/.a` и длинные логи не включены. Происхождение задаётся ссылками
на upstream; имеющиеся короткие контрольные суммы не требуют хранения
скачанных архивов. Степень сокращения измерена фактически, а не задана
условным коэффициентом для каждой библиотеки.

Ранее для небольших самостоятельных библиотек проверялся предел менее
1 000 000 байт выбранного native-архива. Для богатых многопрофильных наборов
это ограничение снято по текущему решению пользователя; объёмы всё равно
измеряются. Сумма `.a` не равна размеру executable или потребляемой памяти.
Цель порядка 30 MB относится к конкретной окончательной композиции LMX,
которую документационный каталог сам не строит. Поставляемые исходники
остаются очищенными от ненужных дистрибутивных файлов.

## Применение и воспроизведение

Архив содержит пути `docs/...` и `third_party/...`. Распаковать его в корень
исходного проекта LMX, поверх загруженного `LMX-26-Nov-2026.tar.gz`. Все не затронутые
файлы нужны из исходного проекта; этот патч не является отдельной полной
копией коллекции. Из `selfbuild/` ничего не удаляется и не изменяется.

Для общей сборки и проверок через `LMX::all`:

```sh
cmake -S third_party/lmx_c99_compact -B build/c99 \
  -DCMAKE_BUILD_TYPE=Release -DLMX_BUILD_CATALOG_CHECKS=ON
cmake --build build/c99 --parallel 4
ctest --test-dir build/c99 -R '^catalog\.' --output-on-failure
```

Нужны установленный C99 toolchain и системные development inputs исходной
коллекции. Полный состав использует также CMake, Python, make/shell,
Bison/Flex/m4 и графические headers выбранной платформы. Сборка не
скачивает эти инструменты или библиотеки из Интернета. Отдельные группы
можно собирать по их коротким README.

Проверка reference-границы и статических форм:

```sh
python3 docs/core_catalog/bridge/run_tests.py \
  --source third_party/lmx_c99_compact --sanitize
python3 docs/core_catalog/new_primitives/run_reference.py \
  --collection third_party/lmx_c99_compact \
  --numeric-extra third_party/lmx_c99_compact/extensions/numeric_extra \
  --build-dir build/primitive_reference --sanitize
python3 docs/core_catalog/tools/check_lmx_sources.py docs/core_catalog
```


Для воспроизведения описи из текущих headers и первичного LMX-плана:

```sh
python3 docs/core_catalog/tools/extract_inventory.py \
  third_party/lmx_c99_compact build/catalog-census
python3 docs/core_catalog/tools/validate_inventory.py \
  third_party/lmx_c99_compact build/catalog-census/inventory.json
python3 docs/core_catalog/tools/build_c_catalog.py \
  --inventory build/catalog-census/inventory.json \
  --plan docs/core_catalog/package_plan.lmx \
  --output docs/core_catalog --replace-generated \
  --native-verification docs/c99_archive/VERIFICATION_2026-11-26.json
python3 docs/core_catalog/tools/check_lmx_sources.py docs/core_catalog
```

Промежуточный полный JSON и preprocess/build trees остаются во временной
директории. Они не нужны в overlay-поставке: все метаданные уже сохранены
в LMX и проверены полным round-trip.

Параметр `--native-verification` связывает каталог с конкретной проверкой
нативной композиции; при новой сборке сначала обновляется этот отчёт.
Пять consumers `LMX::all` и общий CTest имеют собственное свидетельство,
а статус запуска будущих LMX-обёрток остаётся `NOT_RUN`.

Статическая проверка LMX не является P0-парсером или исполнением новым
ядром. Runtime LMX, Windows/QNX cross-builds, полный набор upstream suites
и производительность на малых процессорах отмечены как `NOT_RUN`.
Сводка выполненных проверок — в [validation/README.ru.md](validation/README.ru.md).
