# Объявление, инициализация и передача аргументов: исследование

Дата: 2026-09-30. Источник — [реплики автора в Q56](../LMX_blog/q/q56.md).
Статус: исследование и обсуждение; реализация остановлена по просьбе автора.
Проверены документы и код на `6a3ac8d`; предшествующий resolver/native/runtime
WIP в `build/opus_wt` сохранён и не является доказанной новой семантикой.

## Исправление ошибочного статуса предыдущей редакции

В `6a3ac8d` Codex ошибочно назвал обсуждаемые предположения уже принятыми
правилами и записал отмену неявного merge как задание. Эта интерпретация
отозвана, включая прежний раздел «Точная граница будущей реализации».
Не было разрешения менять правила, зависимые тесты или убирать `@` из L3.

Уточнение автора, исправившее ту редакцию, сохраняло прежний смысл `A: b` как построения
через merge. `int: i` оставляет неизвестное значение в выделенном месте,
а не отсутствие значения: отсюда нельзя вывести пустую ссылку для `A: b`.
Общая композиция ресиверов и их способность потреблять несколько аргументов
не вводят специального правила «вложенная цепочка означает инициализацию».

## 1. Что действительно показала проверка парсера

Проверка существующим `build/fable127_printTree/printTree.exe`:

```text
int: b 5       -> Frame int [atom b, atom 5]
int: b: 5      -> Frame int [Frame b [atom 5]]
int(b: 5)      -> Frame int [Frame b [atom 5]]
int:           -> Frame int [Frame b [atom 5]]
    b: 5
---
a: b: c: d     -> Frame a [Frame b [Frame c [atom d]]]
```

Эти формы уже представлены обычными деревьями. Само дерево не доказывает
равенства их смысла. `int: i 5` предоставляет имя и начальное значение как
два аргумента. Ресивер определяет, какие операнды и в какой роли потребить;
вложенное применение не следует автоматически разворачивать в плоский список.

Автор привёл `int: i: j: getValue(j): 5`: int потребляет имя i, затем
возникает попытка вызова i, то есть ошибка. Требуется общий алгоритм
разрешения, который сохраняет эту границу; не цепочка особых распознавателей
и не доказательство равенства `int: i: 5` и `int: i 5` по их внешнему сходству.

Происхождение замера: старый готовый printTree от 2026-09-23, SHA256
`0956054E093428CF4FAE060DA0A2FCF6C47C565F2231182683178B3845202040`;
исходник пробы — `build/receiver_declaration_probe_20260930.lm2`.
Это диагностическое свидетельство формы, не свежий gate парсера текущего HEAD.
В той же пробе `a[i]\[j]\[k]` сохраняет все индексные/backslash-токены,
а `a[i]\[j]: 5` приходит как Frame с составной головой.

## 2. Что снято вместе с предположением о пустой ссылке

```text
A: b
b: c
b()
```

В первой строке не отменено построение b. По уточнению автора, при известном
c вторая строка вызывает b(c), при неизвестном c применяется то же правило
построения, что в первой строке. Прежний вопрос «заполнить пустой b или
вызвать его?» был следствием неверно принятого предположения о пустой ссылке.
Не нужно решать его проверкой null или новым оператором присваивания.

Явно объявленная ссылка и вызываемое структурное значение различаются.
Последний пример автора использует присваивание ссылок `e: c` и обращение
к референту `\e: d`; это не изменение роли `A: b` в ссылочное объявление.
Полные примеры сохранены дословно в Q56. Их запись `@: c b` / `@: e A`
нельзя молча переписать в прежнее `@: Type var`: согласование формы ссылки
не завершено этой заметкой.

Норма: [семантика §9](../docs/LMX_semantics.ru.md#construction),
[§11](../docs/LMX_semantics.ru.md#callables). Код: `l2_colon_bound_before`,
`l2_check_struct_call`, `l2_check_body`, `l2_colon_bind_shape`.

## 3. Найденное расхождение: новое значение и сохранённая ссылка

Автор уточнил: при неизвестном d запись `A: d b` аналогична `int: i 5` —
выделяется место для нового значения, которое инициализируется кандидатом;
это не просто связывание d с существующим b. Предыдущая реплика автора
оборвалась на «то есть»; её продолжение не следует дописывать за автора.

В текущем тексте и коде зафиксировано другое:

- [Семантика §9](../docs/LMX_semantics.ru.md#construction), строка 567
  среза `6a3ac8d`: `A: b c` при неизвестном b связывает b с существующим
  дескриптором c без копирования; это уподоблено заполнению формала `(A: b)`.
- [L2 §13](../docs/L2_spec_ru.md#copy-merge) повторяет эту трактовку.
- `dev/l2src_sandbox/l2trans.lm1`, `l2_emit_stmts`, строки 32212–32234
  того же среза: ветвь `l2_colon_bind_shape` вычисляет кандидата, выполняет
  нужный admission и передаёт его дескриптор в `l2_own_store`; merge отсутствует.
- Там же `l2_rw_model_bind`, строки 24443–24484: walker строит
  `PUT_REF(b, OWN(c))`, при необходимости через admission, также без merge.
- Соседнее объявление без кандидата, напротив, вызывает `lmx_merge_owned`
  (native) либо `lmx_walk_merge_model` (walker).

Это свидетельство расхождения, не основание предпочесть реализацию словам
автора. Выделить только новую ячейку и положить в неё прежний дескриптор —
ещё не создать отдельное структурное значение: референт останется прежним.

Нужно раздельно рассматривать три действия: допуск кандидата по `implements`,
создание/инициализацию значения и передачу аргумента. Способ передачи
дескриптора не определяет действие принимающего выражения. Получатель может
использовать переданный по ссылке источник для построения значения, не
передавая C aggregate по значению. Но это не тождественно прежнему обещанию
сохранить идентичность кандидата в формале.

Открытая граница обсуждения — одинаковый смысл объявления с кандидатом в
теле и заполнения формала. Нельзя одновременно обещать новое структурное
значение для `A: d b`, прежнюю идентичность b в формале `A: d` и называть
это одной операцией без различающего общего правила. Конкретный механизм
инициализации и итоговое правило формалов здесь не выбираются.

## 4. @ в L3 не удалён

Снята предпосылка, будто `A: b` уже заменяет явное объявление ссылки.
В документах также обсуждались самостоятельные возможности:

- ссылка на примитивную ячейку вместо копирования её значения;
- ссылки большей глубины;
- получение ссылочной идентичности без вызова/вычисления результата;
- различение привязки и вызываемого референта.

`int: x 5` / `int: y x` даёт копирование значения, не псевдоним ячейки x.
Но возможность добавить псевдоним не доказывает необходимость его в L3.
Не найдено требования ядра L3, которое заставляло бы переносить туда
ссылки на примитивные ячейки или большую адресную косвенность. Примитивы
могут оставаться значениями, Structure/Array — обычными ссылочными значениями;
явное изменение общего состояния уже выражается путём к полю/элементу.

Важная поправка к предварительному выводу Codex: нельзя ссылаться на
работающие адресные операции L2 как на якобы уже необходимую возможность L3.
В текущем `l2_rw_ref_bind` высокоуровневый маршрут ограничен ссылкой на
существующую Structure, а `l2_rw_stmt` после `l2_own_ref_decl` отправляет
остальные @-формы в отказ машинной операции. Универсальная primitive-alias /
reference-to-reference возможность L3 этим кодом не доказана.

Перечисление этих возможностей не доказывает их необходимость, но и
отвергнутая гипотеза о пустой ссылке не позволяет удалить @. Последнее
объяснение автора использует явные ссылки. Никакого сокращения L3 или
изменения машинных операций @ в L2 этим исследованием не принято.

## 5. Отдельные старые расхождения, обнаруженные при проверке

Они не порождены новым предложением; использовать их как норму нельзя.

1. Семантика §12 сначала разрешает `@value` в L3, затем таблица запрещает
   `@x`, а следующий абзац снова запрещает prefix address-of. Грамматика
   дополнительно запрещает глубины `@@:`, разрешённые той же семантикой.
   Последние авторские решения нужно провести по всем связанным абзацам.
2. Семантика §9/L2 §18.1 ещё пишут `@fresh -> Lmx**`, тогда как L2 §18.2,
   CORE и Q26.2 адресуют сам референт Structure, не child-slot. Это старая
   несогласованность смысла адресуемого объекта.
3. CORE §4 сохраняет старый приоритет callable до объявления и описывает
   Model как non-callable, хотя обычная именованная Structure вызываема.
   Он также ошибочно называет `Model: fresh` при известном fresh присваиванием.
   Семантика §9 уже различает отсутствие и присутствие правого имени.
4. `lmx_copy_value` копирует прямую ссылку на Structure вместе с её целью,
   но pointer-ячейку @ копирует с удержанием прежнего изменяемого pointee;
   это закрепляет `lmx_copy_ptr_share_selftest`. Текущий §20 требует копии
   достигнутого обычного изменяемого графа. Согласование политики обхода
   явных ссылок при merge требует отдельного разбора; новая декларационная
   семантика в качестве обходного решения не вводится.
5. `lmx_merge_profiles_owned` всё ещё создаёт корень с пустым native
   независимо от сохранности кода; §20 требует сохранять native неизменного
   тела. Это отдельное расхождение, не следствие обсуждения объявлений.

## 6. Исследование предложения о явной ссылочной передаче

Следующая реплика автора, сохранённая в Q56, предлагает оставить общие
правила инициализации и изменить прежнюю неявную ссылочную передачу аргументов.
Ниже — анализ этого предложения на `f9683ab`, не принятая норма и не тикет
реализации. Код и runtime в этом исследовании не запускались и не менялись;
источники и тесты прочитаны. Незавершённый WIP не выдаётся за подтверждение.

### 6.1. Цепочки — отдельный вопрос

`timeout: ms: int: time 500` уже объяснено в
[описании Message API, §8.1](../docs/new_parts/threadMessageAPI.ru.md):
настройка имеет путь `timeout\ms\time`, а int потребляет имя time и значение
500, не создавая дополнительного поля int. Это обычная вложенная структура
с ресивером объявления на конце, не новый способ передачи аргументов.
Ни ссылочная, ни копирующая передача не требует менять её дерево или вводить
разбор цепочек по именам timeout/ms. Новая parser-проверка здесь не заявлена.

### 6.2. Согласованное прочтение предложения

Объявление принимающего места определяет его инициализацию. Для примитива
это новое место со значением кандидата; для структурного значения — обычное
построение с существующим merge, а не сохранение старого дескриптора под новым
именем. Формал должен получать значение тем же способом, что аналогичное
объявление с кандидатом в теле. Явно ссылочное место получает ссылочное
значение, а не построенную копию референта. Admission нужен в обоих случаях.

Схема для обсуждения, не новое утверждение о поддержке транслятором:

```text
sub: work (A: x)             # принимается и инициализируется значение
    ...
work(b)

sub: edit (@: A x)           # принимается явно ссылочное значение
    ...
edit(@b)
```

`work(@b)` не должно молча превращать нессылочный формал в ссылочный;
совместимость определяется принимающим контрактом и общими объявленными
преобразованиями. Иначе выбор семантики снова окажется скрытой догадкой.

Важно различать создание ссылки и её дальнейшую передачу. Если r уже
объявлено ссылкой и содержит @b, передача r сохраняет ссылочное значение;
добавление ещё одного @ — не обязательная метка вызова, а адресация самого r
по общему правилу глубины. Это соответствует примеру автора `e: c` и не
требует нового исключения для ранее объявленной ссылки.

Сохранение `Lmx *` в ABI не противоречит новому значению: можно построить
отдельный граф и передать его дескриптор. Но копирование самого указателя или
C-записи `{array, parent, native}` не заменяет merge: backing, дочерние данные,
связи и лексические предки останутся прежними. Общий обход уже имеет карту
источник→копия и правила для циклов, квалифицированных ветвей и native.

- `lmx_graph_copy_owned.lm1`, `lmx_copy_value:428` и
  `lmx_graph_copy_many_profiles_owned:696`: механизм глубокого построения

Все пути выше находятся в `dev/l2src_sandbox/`. В WIP `build/opus_wt` уже
перерабатывается описание ресиверов и типов; посадка той работы не равна
реализации предложенной семантики аргументов.

### 6.4. Следствия, которые нельзя оставить старыми исключениями

1. **Скрытые входы и значения по умолчанию.** Источник сначала выбирается
   по прежним правилам видимости/default, затем применяется то же правило
   инициализации входа. Иначе явный аргумент копируется, а тот же объект через
   свободное имя всё ещё разделяется неявно. Условие/цикл не создаёт активацию,
   поэтому копирование на каждой итерации из этого не следует. `node\…`
   остаётся явным путём к лексическому графу, не скрытым аргументом.
2. **Callable как значение.** Выбор «результат callable или само callable»
   надо отличать от выбора «построенное значение или явная ссылка». Допуск
   callable-значения не обязан его исполнять. Обычный callable-формал больше
   нельзя автоматически описывать как удержание исходного вхождения;
   ссылочный — должен быть явно ссылочным. Копия состояния может использовать
   ту же неизменённую native-реализацию. Descriptor-only fn остаётся контрактом,
   не получает вымышленное тело. Сам вызов выбранного метода не означает
   копирования его тела или создания второго постоянного графа активации.
3. **Array.** Внешний дескриптор — способ представления, не разрешение
   неявного совместного владения значением. Передача обычного Array и явной
   ссылки на Array должна следовать той же границе; depth/rank и разбор
   вложенных ресиверов не являются основанием для разных правил.
4. **Возвращаемое значение.** §9 и §22 сейчас также обещают сохранение ссылки
   при возврате Structure. Изменение только входов не определяет, что должно
   означать `return: b` при результате A и при результате `@: A`. Если «везде
   через @» охватывает результаты, эту границу надо согласовать с тем же
   правилом принимающего места; не вставлять слепо второй merge уже построенного
   результата и не сохранять исходную идентичность молчаливым исключением.
5. **Повторный кандидат.** Два параметра, получающие один объект, должны
   вести себя как два соответствующих объявления с инициализацией в теле.
   Карта копирования одного merge сохраняет внутренние общие цели; это не
   разрешает общей кеш-таблице всех вызовов склеить самостоятельные результаты.
   Это обязательный наблюдаемый свидетель, не новая таблица в ядре.
6. **Receivers и ABI.** Нельзя делать особые исключения для отдельных имён
   операторов. Контракт принимающей операции определяет роль операнда:
   имя объявления, требование, вычисляемое значение или ссылка. Механизм
   передачи машинного указателя сам по себе не определяет режим значения
   в исходном языке. Изменение способа передачи входит в сигнатуру и проверку
   callable admission (семантика §7), а не только в emitter; одинаковая
   C-проекция `Lmx *` не делает два режима семантически взаимозаменяемыми.

### 6.5. Оставшиеся реальные границы, не повод выдумывать исключения

**Что строит объявление с кандидатом.** Не следует без проверки записать
формулу `merge(A, b)` или `merge(b, empty)`: эти операции различаются, если
у A есть собственные поля/defaults, отсутствующие у b. Admission относительно
Consumer не требует полного равенства структур: это прямо видно в
`unit_bind_method_thin_other.lm2` и `unit_formal_thin_other.lm2`.
Глава §20 уже задаёт порядок операндов и сохранение слотов модели, а для
callable отдельно запрещает добавлять принимающий заголовок ещё одним
неявным операндом (§20, «Явное описание вызываемого»). Поэтому переход
к построению формала должен ссылаться на согласованную общую инициализацию,
не молча вводить срез полей, иной merge или подстановку недостающего поля
перед implements. Это уточнение не возвращает ссылочное связывание вместо
построения: отдельное значение требуется в обоих рассматриваемых вариантах.

**Ссылка внутри копируемого значения.** §20:899–903 требует переписать
ссылки на копии изменяемых целей. Но `lmx_copy_value:538–554` копирует
явную pointer-ячейку и оставляет исходную цель; это утверждает
`lmx_copy_ptr_share_selftest.lm1`. Минимальное различие: у b есть явно
ссылочное поле r на изменяемое t; после построения d из b ссылка d.r ведёт
на исходное t или на его копию? Это старое расхождение документа/кода,
но обещание «@ явно сохраняет ссылку» требует согласованного ответа и здесь.
Не выбирать shallow/deep политику по месту передачи или по native/walker.

**Квалификация.** §10:592 обещает сохранение идентичности любого immutable
значения при передаче, а общий merge удерживает исходную ветвь по совокупности
`independent: const: immutable`. Применение общего merge к аргументам нельзя
совместить с обоими обещаниями без уточнения текста; это уже существующая
несогласованность, не основание добавить новую оптимизационную ветку.

**Native.** `lmx_merge_profiles_owned:260–268` оставляет native результата
нулевым вопреки §20:928 для неизменённого кода. Массово использовать этот
путь для аргументов, не устранив ранее обнаруженный дефект, означало бы
необоснованно терять нативное исполнение. Новая семантика этого не требует.

### 6.6. Оценка и остановка

Основная идея допускает единое правило: инициализировать принимающее место
по его объявлению, а разделяемую ссылку выражать явно. Она не требует нового
оператора присваивания, C by-value агрегатов, смены Array ABI или скрытого
data-графа. Однако фраза «изменить одно правило» описывает архитектурный
принцип, а не объём правок реализации: надо согласовать объявление с кандидатом,
подготовку явных/скрытых/default-входов и оба способа исполнения.

Стоимость глубокого построения зависит от объёма обходимого графа, а не от
размера указателя. Численного замера нет. Явный ссылочный вход сохраняет путь
без копирования референта; нельзя автоматически выбирать его для большого
объекта, если программа объявила обычное значение.

Проверка после будущего решения должна различать изменение кандидата через
обычный и ссылочный формал; захваты/defaults; два входа от одного кандидата;
Array/backing; callable/native; ссылку внутри merge; возврат результата и
время жизни; отказ admission до входа и отсутствие частичной публикации.
Новые тесты и реализация не начаты. Из результатов исследования не следует
разрешение менять нормы или возобновить самосборку без обсуждения.

## 7. Альтернатива: явное построение и сохранение ссылочной передачи

Источник — новое предложение автора в Q56. Проверен срез `775b243`.
Статус: исследование другого варианта, не принятое изменение семантики.
Раздел 6 не становится планом реализации и не смешивается с этим вариантом.
Ниже нет требования внедрить какой-либо из них до ответа автора.

### 7.1. Разделение операций

Предложение отделяет построение от вызова:

- `merge: b A` объявляет результат b копированием A;
- `merge: b A C` объявляет результат b композицией A и C;
- применение уже существующей Structure `A: b` вызывает A; неизвестный
  аргумент b не переключает операцию в создание нового экземпляра;
- `@: A p` объявляет ссылочную переменную; `p: @B` перепривязывает её после
  допуска. Само наличие вызываемого объекта за p не меняет присваивание
  ссылки в вызов этого объекта; обращение к референту — отдельная операция;
- описание аргумента в сигнатуре не исполняется как оператор тела. Поэтому
  роль `A: b` в заголовке не требует сохранять конструирование A в теле.

Это общий разбор по роли выражения и разрешённой сущности, не исключение для
конкретного имени. Блочная, короткая и скобочная формы сохраняют эквивалентность.
Цепочки вроде `timeout: ms: int: time 500` — отдельный механизм структуры
принимающего выражения и не требуют смены значения из-за этой альтернативы.

Внутреннему API `lmx_merge_owned` не требуется запретить возвращать дескриптор
через out: это реализация, а не форма поверхностного ресивера. Изменяется
получение места результата из первого аргумента merge. Текущий
`l2_merge_frame:30915` ищет merge под внешним `R: …`; новый контракт должен
идти через общую информацию о декларации, не вторым независимым распознавателем.
Сам алгоритм композиции графа от такой перемены формы не меняется.

### 7.2. Подача аргументов без нового копирования графа

Предложение допускает общее правило подачи: примитив передаётся значением,
непримитив — ссылкой на свои данные, существующий указатель — своим значением.
При ожидаемой ссылке на A это даёт:

| Фактическое | Что поступает | Результат по предложению |
| --- | --- | --- |
| b, где b — Structure | ссылка на b | допустимо после admission |
| @b, где b — Structure | та же ссылка на b | то же |
| p, где p уже ссылка на A | значение ссылки p | допустимо после admission |
| @p | ссылка на ссылочную ячейку p | не тот уровень, отказ |

Последняя строка — ошибка совместимости с этим формалом, не запрет на @p
вообще. Нельзя автоматически понизить глубину. Произвольный отдельно заданный
конвертер имеет свой контракт; не добавлять неявное разыменование ради этого
примера. Примитивные `(int: x)` и `(@: int x)` не становятся синонимами.

Это правило подачи не надо смешивать с обычным присваиванием в теле или
с исполнением текста сигнатуры. Автор отдельно уточнил: `(A: b)` и
`(@: A b)` предлагаются как синонимы **в сигнатуре**; тело не является
сигнатурой. Из способа описания параметра нельзя вывести исполнение `A:b`
или `@:A b` при входе. Нельзя также потребовать для каждой отдельной
Structure свою строку `B -> @B`: таблица преобразований описывает
примитивные значения, а не каталог моделей (см. следующий раздел).

### 7.3. Таблица преобразований действительно существует

Прочитаны `dev/l2src_sandbox/convert.lm2`, `convert_impl.lm2` и соответствующие
материалы `C:/Nyasha_Planet/lingvamyxa_prev/lm2/`.

- Текущая таблица `primitive.convert` содержит 120 строк отношений:
  from, to, forbidden, kind, receiver, impl. Есть числовые, текстовые,

  и к потреблению кандидата. Отсутствие необходимой примитивной конверсии
  не разрешает скрытый fallback или поиск по всему процессу. Это не требование
  иметь строки соответствия каждой пары пользовательских Structure.
- `l2_convert_hit:7812` ищет точное совпадение имён from/to; выбранный receiver

- `l2_check_value_convert_core:8206`, `l2_check_value_convert_field:8245`,

  через `l2_prim_code_name`. Само ограничение таблицы примитивами не является
  дефектом: это её область, а не незавершённый каталог всех типов графа.
- `lmx_value_owned.lm1:24`, `lmx_node_new_profiled`, выделяет заголовок через
  `lmx_arena_take_profiled` с `sizeof(Lmx)`, `LMX_KIND_STRUCT`,
  `LMX_TYPE_STRUCT`. Начальный комментарий того же файла прямо запрещает
  per-value array: массив принадлежит арене, тип — массиву. Это существующее
  общее представление Structure, а не предложение нового параметризованного
  `Reference<T>`-реестра.

**Исправление первоначального вывода Codex.** Требование отдельных строк
`A -> @A`, `B -> @B` было ошибкой исследования. Все обычные Structure имеют
один физический тип `Lmx`; различные чанки/арены не делают каждую модель
отдельным типом хранения. Совместимость содержимого проверяет
`implements(B, A, Consumer)`, а не табличный конвертер именованных моделей.
Для предусмотренного предложением `p: B` нельзя требовать конверсию,
зависящую от имени или экземпляра B. Это **не отсутствие конверсии**:
указатель является примитивным значением. Как отдельно уточнил автор,
сначала конверсия получает указатель на B, затем `implements` проверяет
структуры по требованию типизированного указателя p. Табличное отношение
относится к общему представлению, не к каждой модели. Из отсутствия строки
с именем B в `primitive.convert` отказ этой записи не следует.

Порядок для уже объявленного `@: A p`:

```text
p: B
    B -> conversion taking a pointer -> @B
    -> implements(B, A, Consumer)
    -> store the admitted reference in p
```

Конверсия не вызывает B и не выполняет merge. Положительная конверсия
не заменяет структурный допуск; при несовместимом референте присваивание
не происходит. Здесь проверяются структуры, потому что указатель
типизирован, а не только одинаковая ширина указателей или их грубый
машинный тип. Это не требует каталога именованных структур или массива
из одного элемента для каждой из них.
Это исправление архитектурного обоснования, а не свидетельство уже
реализованного нового контракта присваивания. Адрес Structure и адрес
ссылочной ячейки по-прежнему различаются (L2 §18.2).

Направленность admission сохраняется: если B — кандидат, A — требование,
в текущих обозначениях это `implements(B, A, Consumer)`. Сокращённое
`implements(A, B)` в предложении не принято за изменение трёхаргументного
контракта или перестановку кандидата и требования.

### 7.4. Реальные следствия и вопросы перед изменением норм

**Сигнатура не исполняется.** Предыдущий вывод Codex «оба описания должны
сделать b обычной non-callable переменной, поэтому вызов надо переписать
через `\b`» отозван. Автор не объявлял синтаксические формы синонимами в
исполняемом теле. Сигнатуры описывают один принимаемый контракт; как этот
параметр используется в теле, определяют контракт и общие правила тела,
а не исполнение оператора объявления из заголовка. Текущий тест
`unit_value_formal_call_refused` различает способы описания формалов —
это свидетельство реализации, не довод потребовать новую семантику тела.
При реализации предложенной синонимии потребуется проверить единое
описание параметра независимо от его написания. Из неё не следует отмена
`return: f` для callable-формала или обязательный новый способ его вызова.

**Никогда неявного merge — шире Model:fresh.** §20:932 и
`tests/unit_make_adder.lm2` сейчас связывают `return: addN` с автоматическим
построением вхождения из метода и данных активации. При буквальном запрете
неявного merge этот захват также должен стать явной композицией в программе.
Нельзя убрать копирование только из объявления, оставив этот маршрут скрыто.
Не копировать вообще — тоже не прежнее поведение makeAdder: сохранённого
снимка состояния тогда не будет. Какой вариант принят, здесь не решено.

**Merge как только объявление.** Уже есть `return: merge(…)` и merge прямо
в аргументе (`unit_t7_convert.lm2`, `unit_t7_header.lm2`). Если новое применение
обязательно получает имя, эти места нуждаются в явном объявлении результата
перед его передачей; прежняя безымянная expression-форма не сохраняется
молча. Нужно определить, даёт ли сам объявляющий ресивер значение выражения.
Для повторного имени следует общее правило объявляющего ресивера, а не
специальное «первый раз объявление, потом присваивание» внутри merge.

**Граница исходной Structure.** `A: ()`, имя с буквальным телом и
`timeout: ms: int: time 500` материализуют явно написанную структуру.
Отмена клонирования уже существующей модели не тождественна запрету такого
построения. Пункт о вызове применяется к уже разрешённой Structure A;
не объявлять исходные буквальные определения отменёнными без уточнения.

**@ с инициализатором.** Уточнение «конверсия в указатель, затем структурный
implements» даёт общий маршрут для кандидата B в `@: A p B`; отдельная
конверсия именованной модели не нужна. Уже готовое указательное значение q
нужно отличать от `@q`, то есть адреса самой ссылочной ячейки. Нельзя
автоматически добавить лишний уровень только потому, что объявляющий
ресивер называется `@`, или автоматически снять его при несовпадении.
Нынешний `l2_ptr_local_ty:6382` принимает два/три аргумента для части
низкоуровневых типов, но `l2_ref_formal_ns:18074` — два для именной Structure;
это ещё не реализованный общий новый контракт.

**Пустая ссылка и void.** Дефолт 0 — именно пустое ссылочное значение,
не экземпляр A, не произвольный адрес и не прежнее неизвестное значение
примитивной ячейки. `@: p` дополнительно предполагает значение по умолчанию
для типа (void) либо отказ за отсутствие типа: одним дефолтом третьего
аргумента это не определяется. Исходный комментарий «попытка объявить void
ссылку» сохранён, но положительный исход такой попытки здесь не выдуман.
Поведение использования пустой/void-ссылки и доступные операции L3 нужно
согласовать с его переносимой ссылочной семантикой, не числовыми Address
конверсиями таблицы L2.

### 7.5. Вывод и масштаб

Этот вариант устраняет прежнюю развилку «неизвестное b превращает A:b в
построение» и сохраняет существующий способ передачи аргументов без массового
копирования. В архитектуре не обнаружено необходимости менять минимальный
Array/Lmx, делать C by-value значения или заводить дополнительный data-граф.
Основная работа — общий resolver ролей, объявляющий контракт merge, описание
и использование ссылочных привязок, типизированные конверсии и согласование
синонимии формалов. Парсерный синтаксис заново изобретать не требуется;
новые примеры парсером/транслятором в этом исследовании не прогонялись.

Ограничения старого copier (политика @-целей и native) остаются отдельными
долгами явного merge; новая форма сама их не устраняет. Ни этот вариант,
ни предыдущий не приняты как новые нормативные правила и не реализованы.
Codex вышел за пределы исследовательского поручения, внеся в спецификации
уточнения об общем типе Lmx, примитивной области таблицы конверсий и
неисполняемой роли сигнатур. Автор попросил уже внесённое не откатывать,
но не разрешил продолжить изменение норм или реализацию предложения.
Последний порядок «конверсия в указатель, затем implements» записан здесь
как уточнение исследования; дальнейшее редактирование норм не выполняется.
После исследования сохраняется пауза для обсуждения с автором.
