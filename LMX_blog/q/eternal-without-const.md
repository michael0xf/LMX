# Удерживает ли merge ветвь `independent: immutable:` без `const`

Статус: итоговое уточнение автора 2026-10-12; удержание без `const` разрешено, реализация и проверка переноса Message остаются открытыми. Вопрос задаёт `fable_pc` при проектировании среза RR2
([дизайн](../../steps/qualifier-receivers-20261010.md); тикет
[critical_qualifier_receivers_bug](../../steps/tickets/critical_qualifier_receivers_bug.md)); передан
автору через Codex почтальоном `lmx_uds`.

## Контекст

По книге ([квалификация](../../docs/LMX_semantics.ru.md#qualification), [вечные ветви](../../docs/LMX_semantics.ru.md#eternal))
`const` защищает привязку, `immutable` — значение через все псевдонимы, `independent` — владение
значением без внешнего структурного родителя. Прежняя редакция требовала для удерживаемой ветви
всю тройку `independent: const: immutable`; это требование `const` отменено последним уточнением автора. По правилу
автора 2026-10-10 три квалификатора — обычные ресиверы, принимающие любую Structure, и каждый
допустим отдельно.

Физически квалифицированное значение — дерево в пулах своего профиля, запечатанных после
проверки; `independent` даёт корню `parent = 0`. `const` не оставляет в значении следа: он
защищает привязку (имя), а не хранилище. Значение `independent: immutable: X` без `const` и
значение полной цепочки физически неразличимы, в том числе когда значение передано по ссылке
и привязка уже не видна.

## Вопрос

Удерживает ли `merge` по ссылке (как вечную ветвь) значение, построенное `independent: immutable:`
без `const`, — или копирует его?

## Итоговое уточнение автора 2026-10-12

«Удержать» здесь означает оставить в результате `merge` **исходный физический адрес** ветви.
Автор разрешил сохранить уже реализованное удержание `independent: immutable` без `const`:
`const` для него необязателен. При `merge` такая доказанно квалифицированная ветвь сохраняет
исходный адрес, а обычная изменяемая ветвь копируется. Самого признака запечатанного пула и
нулевого структурного `parent` недостаточно, чтобы произвольное значение признать подходящей
ветвью.

Объявленная ветвь `independent: immutable` может находиться не только в корне
Message, в том числе внутри обычного окружающего тела. Сборщик владельца сохраняет каждое
такое созданное вхождение до удаления **всей арены**, даже если обычная достижимость через
окружающий граф впоследствии пропала. Перед переносом Message в другую ветвь иерархии Message
проверяется, останется ли владелец каждой используемой вечной ветви в цепочке его новых
Message-предков. Если нет, перенос отказывается до изменения связи: прежняя цепь взаимного
контроля уже не сможет гарантировать существование арены владельца в течение жизни
перенесённого Message. Это не изменение структурного `Lmx.parent` или языкового `node`.

Ранний ответ того же дня предписывал полное копирование без `const`; это изменено
последним уточнением. Требование `independent` и его проверка структурной связи
ветви не отменены: ветвь должна быть независимой от внешнего структурного
родителя. Это требование отдельно от проверки цепочки родителей Message при
переносе, которая обеспечивает срок жизни арены владельца.

Проверка реализации: `unit_rr2_qualified_merge_decl.lm2` уже доказывает тройное объявление
значения в методе, вне корня Message. Но отдельная форма именованной ветви `(): E` пока
регистрируется `l2_take_eternal` только в корневом проходе `l2_unit_role`; вложенное
объявление этой формы не доказано. `lmx_merge_retain_profile` сейчас выбирает удержание по
физическому профилю и `parent = 0`; запечатанность затем проверяет
`lmx_copy_profiles_valid`. `lmx_gc_mark_value` и `lmx_gc_block_live`
освобождают от сбора **любой** sealed pool. Нужны отдельные положительные/отрицательные
свидетели доказанного контракта `independent: immutable`, вложенного объявления и смены
надзирающего родителя Message; один `sealed` этого не доказывает.
