# Спецификация L1

L1 — генерируемое промежуточное представление для понижения ядра в C99. Языковые правила графа задают [L3](LMX_semantics.ru.md) и [L2](L2_spec_ru.md); здесь остаётся только C-проекция. Состояние текущего транслятора и переходного рукописного L1 — в [заметках](implementation-notes.ru.md).

<a id="scope"></a>
## 1. Предмет

`l1trans` понижает `.lm1` в одну единицу C99. L1 сам по себе не определяет арену, `implements` или графовую видимость как операции языка. Такие механизмы реализуются явно библиотекой ядра. Цель самосборки — L3 со вставками L2; L1 остаётся промежуточным шагом.

<a id="translator"></a>
## 2. Транслятор

L1 разрешает свои C-подобные объявления и выражения. Префиксное `@x` — адрес C-ячейки `x`, префиксное `\p` — загрузка указателя, `p\field` — доступ к полю через указатель. Декларативное `@ⁿ:` задаёт соответствующую глубину C-указателя. Исторический порядок аргументов указательного объявления в рукописном L1 не является постоянным исключением: целевой промежуточный L1 должен следовать общему порядку L2/L3 «имя, требование, значение». Внешние C-символы доступны через явное `c.имя`.

<a id="lmx"></a>
## 3. Lmx на L1

C-проекция [L2 §2](L2_spec_ru.md#lmx) сохраняет порядок полей `VoidArray array`, `Lmx *parent`, `LmxEntry native`. `array` встроен по значению первым членом; его backing содержит фиксированные слоты `void *`. Запись не получает имени, тега модели, отдельного `len/data` верхнего уровня или скрытых полей выполнения. Динамический List детей Thread хранится отдельно.

<a id="interpretable-tree"></a>
### 3.1. Проекция дерева

Понижение сохраняет полный исходный граф для обходчика и `toLmx`. Оно не выделяет `leaf`-обёртку для уже типизированной ячейки примитива и не хранит имена в графовых записях. Таблица исходных имён и комментарии нужны восстановлению текста, не исполнению. Подробный контракт — [L2 §2.1](L2_spec_ru.md#interpretable-tree).

<a id="type-by-range"></a>
## 4. Тип по диапазону

`LmxRange` и индекс арены классифицируют физические адреса, а не читают теги из ячеек. Модели пользователя не создают по C-типу на каждую Structure. Обычные и `immutable` Structure имеют разные пулы, сохраняя совместимую физическую запись. См. [L2 §3](L2_spec_ru.md#type-by-range).

<a id="pool"></a>
## 5. Пул

`LmxPool` и `LmxChunk` выделяют фиксированные ячейки. Рост добавляет чанк, а не перемещает живые ячейки через `realloc`. Пул и диапазон принадлежат арене. См. [L2 §4](L2_spec_ru.md#pool).

<a id="method-array"></a>
## 6. Нативный вход и Array

`LmxEntry` — тип слова нативного входа; второй записи метода нет. Базовый `VoidArray` имеет ровно `size` и `data`, без `capacity`. Динамический List реализуется отдельно и не подменяет фиксированные слоты `Lmx.array`. См. [L2 §5](L2_spec_ru.md#method-array).

<a id="arena"></a>
## 7. Арена

`LmxArena` владеет блоками, пулами и индексом диапазонов. `attach` передаёт владение без перемещения адресов; `mark/revert` обслуживают атомарное построение. Простой режим не выполняет GC. См. [L2 §6](L2_spec_ru.md#arena).

<a id="message"></a>
## 8. Message

`LmxMsg` понижается ровно с четырьмя полями: `running`, `success`, `handoff_ready`, `graph`. Его идентичность — адрес записи, поля числового индекса нет. Почта и семейные связи не добавляются в префикс Message. См. [L2 §7](L2_spec_ru.md#message).

<a id="thread"></a>
## 9. L3 Thread

`LmxThread` содержит `LmxMsg` первым членом по значению, поэтому адрес Thread равен адресу префикса Message. Доступ к хвосту требует точной классификации Thread. `Thread.children` удерживает один List прямых детей вне исходного графа. См. [L2 §8](L2_spec_ru.md#thread).

<a id="root-close"></a>
### 9.1. R0

R0 и верхний host-каркас используют общий механизм Thread. Служебные данные запуска принадлежат каркасу, а не скрытым полям графа R0. Каскад закрытия идёт по единственному List детей; timeout всего поддерева контролирует host-watchdog. См. [L2 §8.1](L2_spec_ru.md#root-close).

<a id="mailbox"></a>
## 10. Почта

`LmxPost` хранит `staged`, `outbox` и FIFO `inbox`. Входящий слот — пара `[target, source_arena]`; владелец получателя присоединяет donor до выдачи target. Кольцо inbox использует отдельный DynamicArray с перемещаемым backing и monitor ящика; это не `Lmx.array`. См. [L2 §9](L2_spec_ru.md#mailbox).

<a id="own"></a>
## 11. Рабочее состояние

L1-код ядра реализует загрузку используемых own-полей, отметку `dirty` и публикацию на контрольных точках. Это понижение [семантики L3](LMX_semantics.ru.md#dynamic), не второе определение языка. Графовые слоты остаются физически стабильными.

<a id="call"></a>
## 12. Вызов

Общий callback нативного входа и примитива имеет форму:

```c
int (void *owner, void **refs, size_t nargs,
     void *dest, void **out, LmxArena *arena, Lmx *code)
```

`owner` обозначает активные данные, `code` — выбранное исполняемое вхождение, `arena` — фактическую арену вызова. Ненулевой `refs[k]` указывает на хранилище значения аргумента, нулевой означает отсутствие. Объектное указательное значение помещается в каноническую ячейку `void *`; приведение `T **` к `void **` не заменяет конверсию значения. Целочисленный возврат callback — статус, не пользовательский результат. `dest` и `out` передают результат по объявленному контракту; нулевая ссылка может быть присутствующим результатом. Выбор native/walker и карта code→data заданы в [L2 §11](L2_spec_ru.md#call).

<a id="child"></a>
## 13. Ребёнок

Ребёнок строится в своей арене. Публикация добавляет его ссылку в `Thread.children`, не дописывая поле в исходную Structure. См. [L2 §12](L2_spec_ru.md#child).

<a id="copy-merge"></a>
## 14. Копия и merge

`lmx_graph_copy_owned` и `lmx_merge_owned` реализуют полный обход через одну карту источник→копия: повторные ссылки ведут к одной копии, внутренние ссылки и `parent` перенаправляются. Типизированные записи исполняемых операций копируются с телом. Слово `native` переносится лишь при сохранении тела и доказанном адресном/типовом контракте. L1 не решает заново, является ли исходный Frame объявлением, присваиванием или вызовом. См. [L2 §13](L2_spec_ru.md#copy-merge).

<a id="implements"></a>
## 15. implements

Таблица `LmxImplEntry` хранит доказанное соответствие адресов полей кандидата и принимающего описания. Разный порядок полей не сводится к тождеству индексов. На одном структурном уровне нет нескольких полей одного имени; старые цели `[N]name` и выбор «последнего вхождения» не являются частью нового контракта. Карта не хранит runtime-имена и не удерживает граф живым сама по себе. См. [L2 §14](L2_spec_ru.md#implements).

<a id="gc"></a>
## 16. Сбор

`lmx_gc_collect` реализует сбор по корням арены, включая Message, граф, почту и `Thread.children`. Простой режим арены сбор не выполняет. См. [L2 §15](L2_spec_ru.md#gc).

<a id="c99"></a>
## 17. Выход C99

Один вызов транслятора выдаёт один `.c`. Строгая сборка использует `-std=c99 -Wall -Wextra -Wpedantic` и диагностики несовместимых указателей, отброшенных квалификаторов и неявных объявлений. `struct:`, `enum:`, `fnptr:` и `type:` понижаются в C-объявления. Это не меняет модель памяти арены.

<a id="lowlevel-scope"></a>
## 18. Машинная поверхность

L1 сохраняет представление и числовую семантику C99-платформы. Переменная L1 и поле C-агрегата сами по себе не являются графовой ячейкой Lmx; доступ к графу идёт через библиотеку ядра. Совпадающее написание операции L1 и L2 не делает их семантически одной операцией.

<a id="lowlevel-address"></a>
## 19. Указатели и поля

| L1 | C99 |
| --- | --- |
| `@: p int` | `int *p` |
| `@@: pp char` | `char **pp` |
| `p: @x` | `p = &x` |
| `\p` | `*p` |
| `\p: value` | `(*p) = value` |
| `p\field` | `p->field` |
| `a[i]: value` | `a[i] = value` |

Таблица задаёт целевое единое написание; переходный рукописный L1 может ещё требовать миграции порядка объявлений. Адресуемая цель должна иметь действительное C-хранилище. `value\field` — шаг указателя; доступ к C-агрегату по значению требует явной C-формы. `const: @(char p)` понижается в `const char *p` и защищает символы, не ячейку указателя. Это не глубокая неизменяемость L3.

<a id="lowlevel-array"></a>
## 20. Машинные массивы

L1-профиль `[]:` и явная дверь `c.array:` понижаются в непрерывный C-массив, без дескриптора `VoidArray`, арены и скрытых проверок индекса. Прямоугольный массив не превращается в массив отдельно выделенных строк. Время жизни автоматического массива подчиняется C99. Обычный Array L2 — отдельный дескрипторный объект.

<a id="lowlevel-abi"></a>
## 21. Приведения и C ABI

`cast: (T) expression` выдаёт явное C-приведение, не проверяемое преобразование L3. `c.name` — явный внешний C-символ. `foreign: Name` требует определения типа во включённом C-заголовке; `external` и `prototype` описывают экспорт и объявление, `include` и `predef` — явные зависимости. Заголовочный `name.h.lm1` выдаёт `name.lm1.h` и допускает объявления без исполняемых тел. Поле по значению требует завершённого C-типа, указатель допускает forward-объявление.

<a id="lowlevel-expression"></a>
## 22. Выражения и управление

L1 понижает C-арифметику, логику, битовые операции, `++/--` и обычный поток управления. Исходное `=` в сравнении становится `==`; `target: expression` — присваиванием. `switch` допускает C-fallthrough, в отличие от L3 `match`. L1 `throw/catch/finally` с машинной служебной нагрузкой не определяет типизированные отказы L2/L3.

<a id="lowlevel-sync"></a>
## 23. Синхронизация

L1 не определяет структурный ресивер `synchronized`. Ядро использует явные машинные и внешние атомарные операции; `volatile` не заменяет атомарность. Контракт `synchronized` принадлежит [L2](L2_spec_ru.md#lowlevel-sync).
