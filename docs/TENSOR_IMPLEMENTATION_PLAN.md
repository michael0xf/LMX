# Предложение по реализации тензорного ТЗ LMX v0.4

**27 ноября 2026 года · предложение по плану работ.** Основание — исправленная документация и чтение приложенного текущего `selfbuild.tar.gz`. Это план следующих изменений ядра; в данном выпуске production-исходники не изменялись, сборка и исполнение новых форм имеют статус **NOT_RUN**.

Основная работа — соединить существующие разбор, граф, типизированные значения и места записи с общей подготовкой операций и обходом Array. Действующие память, header, TypeRef, вызовы и исключения дают основу для этого. Поэлементный цикл, индексный план и запись следует реализовать общими механизмами, затем подключать к ним семейства методов.

**Обязательная архитектура:** в ядре один общий парсер. Его подпарсер `[]` разбирает только свой каркас и вызывает основной парсер для вложенного содержимого; вместе они составляют один парсер языка. Группировка выражений тоже имеет **один общий механизм и одну реализацию**, которой пользуются все потребители. Найденные три старых механизма — технический долг для удаления. Их отдельные таблицы, алгоритмы и обходные ветки заменяются вызовами общего кода; согласование копий через адаптеры не является выполнением этого требования.

Использовать штатные `selfbuild/tools/build.lm2`, `tools/suite.lm2` и manifest `tests/full-suite.tsv`. Рабочая последовательность сборки — затронутые компоненты и зависимые цели согласно политике проекта. `selfbuild/README.md` ссылается на `../to_fable2_fast_build.md`: в приложенном архиве этого внешнего файла нет, поэтому при реализации надо прочитать его из полного checkout. Исторические команды полного bootstrap не подменяют эту политику. Полный цикл поколений/fixed point запускается по действительным условиям проекта.

**Приёмка:** записаны revision/хэши, точные команды, используемые frontend и runtime, результаты существующих затронутых тестов. Сбой исходной сборки отделён от отказа новой возможности. Новые случаи из документации зарегистрированы с ожидаемым состоянием, без фиктивного PASS и без молчаливого пропуска невыполненного теста.

В снимке найдены 40 `tests/graph/expr_*.lm3` с expected-файлами, но их регистрация в `tests/full-suite.tsv` поиском не обнаружена. Для каждого входа зарегистрировать разбор со spans/diagnostic в штатном `parser-suite`, а режимы исполнения и ожидаемую фазу отказа проводить через существующий `graph-check` в `selfbuild/tools/lmxtool_methods.lm2`. Указать реально использованный список; отдельно сохранить результаты каждой из 40 строк и отсутствующие покрытия. Число −1 из прежнего `expr_p17` не различает две группировки, поэтому для transport нужны также structural/argument-capture проверки.

## 4. Этап 1: единый парсер и единственный механизм группировки

### 4.1. Подпарсер квадратных скобок

**Исходное авторское требование, воспроизведённое из сообщения:**

> Еще уточнение: надо добавить новый парсер, который разбирает грамматику внутри квадратных скобок. Это парсер также должен понимать уже добавленные Python-подобные формы var[arg:arg2:arg3]. Но этот парсер надо сделать таким, чтобы он вызывал основной для разбора любого выражения, начало которого он определил, а также текста в фигурных скобках {} (содержимое которых он должен игнорировать и также как и в случае выражений даже не пытаться сам найти закрывающую скобку -- просто основной парсер должен вернуть управление с определенной позиции ). То есть мы фактически вводим подпарсер основного который активизируется от "[", причем форму "[op" (без пробелов) надо закрепить как повод для вызова подпарсера.

Указанный «новый парсер» — подчинённая часть единственного общего парсера языка. Оформить этот компонент для компактного `[op` и postfix INDEX, включая `var[arg:arg2:arg3]`. Контекст выбирает основной парсер. Обычные квадратные Structure/TYPE сохраняют свои правила; `[ op]` не нормализуется в `[op]`.

Точная исходная граница: `selfbuild/src/l2src/p0_parser.lm2:2283–2389` уже делегирует содержимое INDEX общему parser, но получает заранее найденный `close_index`; caller ищет его на `2461–2468`, scanner расположен на `2789–2849`. Общую cursor/stack-машину следует расширять на `3385–4161` и в wrapper `4164–4173`. Mix частично уже делегируется: `record_mix_mark` вызывает nested parser на `1968`. Следовательно, требуется изменить владение границей и возврат позиции, сохранив пригодный общий разбор.

Подпарсер владеет только своим внешним каркасом. Начало любого выражения, включая `{...}`, передаётся основному парсеру с позицией и политикой границы. Возвращаются обычный граф и `nextPosition`. Предварительный поиск конца выражения, `}` или внешней `]` через делегированную область исключается. Общий парсер владеет вложенностью, строками, комментариями и точными именами.

«Игнорировать содержимое» здесь означает, что подпарсер его не просматривает и не разбирает сам. Основной парсер сохраняет результат в обычном графе и возвращает управление с определённой им позиции; подпарсер продолжает строго оттуда. Он не отбрасывает результат и не перепроверяет найденный конец собственным сканированием.

Развести собственные двоеточия среза и тернарное `?:`; сохранить `::` в его контексте, неделимые `:=`/`.:`, вложенные вызовы и выражения осей. Поля отсутствующей границы, явного пустого списка осей и отсутствующего списка не смешиваются. Builder получает реальные Expression-проекции вместо нынешних безусловных отказов slice/conditional/depth.

Разделить реализацию на два небольших изменения: сначала общий region/cursor и INDEX, затем compact `[op` и единственная depth-форма `.(expression)op`, включая `.(n)[op …]`. Текущие старые `.op`-ветви (`p0_parser.lm2:2943–2957`) и designator без bracket-операции (`3057–3109`) требуют миграции. Отказы legacy lowering (`6791–6820`) снимаются только вместе с корректной проекцией. При изменении parser API обновить фактические экспорты в `selfbuild/tools/build.lm2:4511–4534`.

**Приёмка:** `a[lo():hi():step()]`, `a[flag ? 1 : 2:6]`, `a[::2]`, `a[::-1]`, вложенные `{...}` и точные имена с `]` дают правильный граф и следующую позицию; на этапе разбора нет пользовательских эффектов. `A [*] B`, `A [* ()] B` и обычная квадратная Structure различаются. Проверяются также отсутствующая закрывающая скобка и закрытие блоков пустой строкой.

### 4.2. Один общий группировщик, приоритеты и степень

В актуальном коде обнаружены следующие несовместимые внутренние масштабы:

| Путь | Нынешние значения и правило | Исходник |
| --- | --- | --- |
| Graph Expression | `+100`, `*110`, пороги префиксов `130/140`; RHS `p+1` | `selfbuild/src/l2src/lmx_graph.lm2:3907–3920,4013–4025,4135–4139` |
| Source graph builder | `+5`, `*6`, префикс `7`, доступ/индекс `8`; RHS `p+1` | `selfbuild/src/l2src/l2_graph_build.lm2:154–171,289–292,356–369` |
| Ordinary frontend | `+9`, `*10`; выбор правейшего минимального оператора, начальное `bestp=99` | `selfbuild/src/l2src/l2_frontend_helpers.lm2:3022–3037,3222–3244`; consumer `l2_frontend_lower.lm2:9616–9727` |

Новый нормативный уровень уже выведен в [документации](spec/EXPRESSION_ALGORITHM.md#power-priority): `p(**)=max(110,130)+1=131`. Общий цикл продолжает правую часть, пока приоритет следующего инфиксного оператора не ниже её порога. У левоассоциативного оператора порог равен `p+1`, у степени он равен `p`. Так правая часть степени принимает вторую степень того же уровня и производная пара связывания равна `(131,131)`. Это даёт `a ** (b ** c)` и приоритет выше умножения и аргумента унарного знака. Правое связывание не получается одним повышением числа при сохранении `p+1`.

Реализовать группировку один раз в общем коде и перевести на неё source graph builder, graph evaluator и все frontend/native-потребители. Удалить их самостоятельные precedence-таблицы, вычисление границ и fallback-ветки, повторяющие общий алгоритм. Преобразование входных данных к общему интерфейсу не получает собственной логики связывания. Сохранение трёх реализаций с адаптированными уровнями не допускается. Вставка `131` в прежние таблицы без удаления дублирования не выполняет задачу. Новый публичный флаг `OPERANDS_TEMPLATE` или кодирование ассоциативности знаком/чётностью числа не вводятся.

**Приёмка:** одинаковое дерево на всех применимых маршрутах для `2 ** 3 ** 2` → `512`, `2 * 3 ** 2` → `18`, `2 ** 3 * 4` → `32`, `-2 ** 2` → `-4`. `2 ** -2` группируется как `2 ** (-2)`; результат `0.25` относится к числовому профилю, допускающему такую степень. Правильная группировка не расширяет молча integer admission. `**=` остаётся присваиванием низкого приоритета.

Дополнительно приёмка проверяет устройство кода: каждый потребитель вызывает единственный группировщик, прежние независимые алгоритмы и таблицы удалены. Одного совпадения результатов трёх оставленных реализаций недостаточно.

## 5. Этап 2: обычный вызов операнда, роли и востребованность

Связать подготовленное применение с существующими разрешением метода, callable binder, допуском и исключениями. Передавать один/отсутствующий `left`, отсутствие/явный actual `depth` и правые вхождения `right`. Префиксная форма не переносит первый right в left. Лишний right не означает автоматического fold: его допустимость определяет метод. Старое scalar-поведение `lm_graph_emit_tree` должно быть согласовано с этим договором.

Группировка не вычисляет пользовательские значения. При востребованном применении depth и удержанные actual получаются один раз в исходном контексте. RAW, TYPE, NAME, PLACE, VALUE и отдельные входные роли сохраняются; готовое VALUE не выполняется повторно как исходный CODE. Приёмка custom-операнда необходима наряду со встроенной арифметикой: текущий builtin-only список ещё не подтверждает общий operand-dispatch.

Для выбора и вызова использовать действующие `lmx_graph_select_call` и `lmx_graph_call_selected` (`selfbuild/src/l2src/lmx_graph_run.lm2:7297–7402`): structural probe уже имеет `run=0`, а выбранный вызов пользуется обычными Values/roots/invoke. Группы нормализуются по принимающей роли; готовый Array и VALUE `[arr2]` сохраняют контейнер, идентичность и размерность. Условная ветвь не подготавливает невостребованные actual заранее.

Подключить scalar `**` через действующий типизированный числовой механизм и выбранные правила ошибок. `lmx_walk_values.lm2:1729–1815` даёт существующую нижнюю основу binary операций, но её текущий список не содержит степени. Все варианты числового домена не объявляются реализованными одной регистрацией имени.

Native lowering вызывает соответствующий выбранному методу механизм степени: печать infix spelling в `lm_graph_emit_tree` (`selfbuild/src/l2src/l2_graph_tool.lm2:890` текущего дерева; строка 889 проверяет делитель) нельзя расширить простой печатью `**` как C-оператора.

**Приёмка:** custom-метод видит исходные left/depth/right, различает отсутствие и `0`, получает собственное допустимое signed значение depth. Стандартный Map применяет свои ограничения только после выбора этого профиля. Счётчики подтверждают однократный demand, нулевой demand пропущенной ветви и отсутствие пробных вызовов при планировании. Исходный `parent`, идентичность и список `throws` сохраняются.

## 6. Этап 3: общий Array/access и один Map

Использовать действующие TypeRef, Array construction, `LmxWalkValue` и `LmxWalkPlace`. Текущий int-путь уже проверяет прямоугольный literal, уплощает его в один backing и сохраняет исходный type reference (`lmx_graph_run.lm2:6200–6276`). Этот путь следует расширить, сохранив полные требования и доступность геометрии.

Общий access получает геометрию из TYPE, length и доступного instance context, предоставляет typed cell и создаёт результат по объявленному договору. Невыводимая форма не угадывается по потерянным строкам initializer. Flat-операции остаются допустимыми там, где им достаточно length. Header сохраняет parent/length/storage; необязательный capacity-entry и его fallback к length реализуются через существующий контекст, без обязательного нового поля header.

Для `[]@` использовать действительный тип прочитанной записи. Число в pointer-слоте не становится адресной арифметикой; настоящая ссылка сохраняет ссылочный смысл. Скалярные kernels используют существующий типизированный receive/bin/unary, без общего приведения всех чисел к `double`.

Один Map подготавливает frame и cell, затем вызывает базовое тело один раз на ячейку. Положительное depth проходит указанное число внешних логических осей; `0` означает максимум. Отсутствие сохраняет default метода. Для стандартного Map Array-frame совпадают точно; singleton Array не получает скрытого broadcasting. Скаляр и удержанный `$actual` не приобретают осей.

**Приёмка:** формы `(2,3,4)` при depth `1`, `2`, `0` дают соответственно cell `(3,4)`, `(4)`, scalar; второй автоматический Map отсутствует. Пустой frame tuple даёт один вызов, нулевая ось — ни одного. Проверены `d>rank`, отрицательный standard depth, смешанный `[]@`, пустой типизированный результат, overflow объёма и различие unknown shape/zero shape. Полные requirements и actual-типы совпадают между interpreter и native.

## 7. Этап 4: View, срезы и общий механизм записи

Сначала реализовать нормализацию индексов/срезов и affine access: offset и signed strides в единицах элементов, композицию относительно непосредственной source region, проверку прав и удержание владельца. Текущий checked Array-index выбирает flat-элемент и отвергает negative; signed pointer helper сам по себе не является View (`lmx_walk_values.lm2:3429–3540`).

Python-like правила отсутствующих и отрицательных границ относятся к срезам. Они не расширяют автоматически прежний договор одиночного индекса Structure или raw L2 pointer access; для каждого входа сохраняется его нормативная роль.

View получает обычный parent-контекст с source, картой и правами. Существующие parent/GC roots используются для достижимости; отдельно проверяются запрет инвалидирующего resize/move/release, границы borrowed region и отсутствие усиления прав. Пустая область не вычисляет адрес несуществующего элемента. Escaping View удерживает источник; краткоживущая depth-cell может пользоваться действующим call lifetime.

На этих местах построить общий writer: подготовка назначения → получение и snapshot требуемых RHS → допуск всех записей → commit. Использовать существующие Value/PLACE и rooted scratch-векторы. `:=` допускает точную форму либо предусмотренное scalar fill; `.:` сначала транслирует RHS к полной форме назначения, после чего depth меняет только гранулярность обхода. Compound update выбирает назначение один раз и пользуется тем же writer.

**Приёмка:** reverse/transpose View, GC, read-only и запрет недопустимого resize проверены реально. Перестановка мест и overlap читают прежний RHS; поздняя ошибка admission не оставляет записанного префикса. Singleton broadcasting `1→N` и `1→0` допустим только по соответствующему договору, `0→N` отвергается. Пустое назначение не требует лишнего чтения элемента. Identity/length/shape назначения сохраняются. Совпадающие физические адреса назначения отвергаются без отдельного реализованного deterministic scatter/reduce-профиля.

## 8. Этап 5: индексные связи и reducer

Здесь требуется реализация поверх общего access и проверенных осей. Расписку модели reducer использовать как ожидаемые значения и форму для производственного теста.

Из обычной DATA-конфигурации строить один проверенный coordinate plan: связи `i:j`, `i=j`, `i*j`, свободные оси, диагонали и перестановка выхода. Оси внутри `.(d)[op]` относятся к выбранной cell. Отсутствующий axisRules и явно пустой `()` остаются разными состояниями. Ни подпарсер, ни переводчик не выбирают математический метод по готовому массиву с callable в первом поле.

Отделить pair/cell kernel от reducer: входной, accumulator и выходной типы могут различаться. Реализовать seed/first/identity/finalize, независимые изменяемые состояния, пустую reduction и пустой внешний frame. Начальный порядок — последовательный нормативный обход. Неассоциативные операции, FP-округления, min/max ties и исключения не получают несуществующих алгебраических законов.

**Приёмка:** outer/dot/matvec/matmul, unary sum/product, диагональная сумма/произведение и min-plus сверяются по значениям, типам и форме. Проверяются повторные/недопустимые оси, несовпадение размеров, пустота, supplied ошибочный reducer и случай без reduced axes. `[*]` и `[* ()]` различаются. Left/right solve не реализуются свёрткой скалярных делений.

## 9. Этап 6: минимальный fuse

Эта стадия опирается на общий план Map и карты доступов writer из этапов 3–4. Наличие декларации метода в каталоге не устанавливает его машинный вход.

Получать RAW Expression до появления промежуточных Array. Принятый план ограничить Scalar и Map→Map со свежим конечным результатом и уже поддержанными картами чтения. Применять общие scalar kernels/access/result construction, сохраняя тип и округление промежуточного scalar-значения, дерево, demand и наблюдаемый порядок отказов.

**Приёмка:** инструментирование выделений показывает отсутствие промежуточного Array в `fuse(A * B + C)` и наличие только разрешённого конечного результата. Значения, actual-типы и эффектный trace совпадают с договором неслеянного выражения. Если порядок отказов сохранить нельзя, план отвергается. Неподдержанные Reduce/Contraction/callback/streaming-write дают диагностику без скрытого eager fallback. Внешнее `:=`/`.:` получает готовый результат и сохраняет обычный writer; терминальный store не включается в fuse автоматически.

## 10. Этапы 7–8: каталог, whole-методы и производительность

529 идентификаторов каталога сохраняются как полный нормативный реестр. Реализацию вести пакетами по семействам и подтверждённым профилям: базовые scalar/cell kernels; reducer/aggregate/scan; geometry и axis algorithms; whole linear algebra; специальные числовые и структурные методы. У каждого пакета фиксировать опубликованные имена, роли, типы, empty/error contracts и действительно доступные execution modes. Недостающие семейства остаются явным остатком полного ТЗ.

Whole-методы `solve`, factorization, `rank`, matrix functions и подобные операции получают собственные математические реализации и проверки. Общий Map/reducer не реализует их автоматически. Сначала переиспользовать существующие LMX-тела и договоры имён; при подключении C-каталога проверить настоящий ABI, layout, типы индексов и чисел, out-параметры, ownership, ошибки, сборку и линковку. Обычная и операндная формы вызывают одну реализацию.

SIMD/FMA/reassociation, параллельная reduction, sparse/device-профили, contraction epilogue и streaming store добавляются только с соответствующим объявленным договором и приёмкой. Для sparse отдельно проверяются отсутствие против присутствующего нуля и structural/value mask; для streaming store — aliasing и поздние отказы. Сначала фиксируется корректный общий результат, затем измеряется выигрыш на воспроизводимых задачах. Число C-символов и наличие capability-поля не считаются реализованной возможностью.

## 11. Общая приёмка каждого этапа

Для стадий 0–1 предъявить фактическую базу, структуру, roundtrip и единое дерево потребителей. Исполняемые результаты последующих стадий сверять на доступных интерпретируемых, native и forced маршрутах по мере их реализации. Различать отказ при разборе, при подготовке, при трансляции и при исполнении. Первый сквозной результат §12 включает исполнительные стадии и достигается после приёмки ядра и сервера на LMX.


1. **Единый код и Source → graph:** один основной parser с делегирующим `[]` и один общий группировщик обслуживают всех потребителей; старые дублирующие алгоритмы удалены. Сохранены роли, отсутствующие поля, исходные occurrences, parent и границы; пользовательские выражения при разборе не исполняются.
2. **Interpreter → native/forced:** совпадают значения, полный тип, форма, выбранная ошибка и порядок видимых эффектов. Протокол показывает реально выполненный путь. Совпадение через один и тот же fallback не доказывает новую native-генерацию. Намеренно raw L2-доступ проверяется отдельно от checked L3.
3. **Demand и изменение данных:** динамические shape/depth/config получаются в действительном текущем контексте. Два написанных вызова остаются двумя; одно удержанное occurrence вычисляется один раз. Повторный вызов не пользуется устаревшим результатом по имени или адресу графа.
4. **Memory и запись:** roots/owner/context переживают необходимые вызовы и unwind; source-region/права проверены; snapshot и admission выполняются до первого store по договору bulk-записи.
5. **Диагностики:** неподдержанная форма или профиль отмечены явно. Отказ в проверке не переименовывается в runtime-успех и не скрывается молчаливым переключением frontend.
6. **Документация и примеры:** новые production receipts привязаны к конкретному снимку и командам. После изменения генераторов их повторный запуск не возвращает прежние rank/depth, срезы и приоритеты. Тестовые примеры и опубликованные копии остаются согласованными.

Текущая документационная проверка дала **209 host test methods**, **7371 вектор срезов** и **54 зарегистрированных примера в 108 местах**; [отчёт](spec/validation/tensor_models_20261127.json) фиксирует область каждого результата. Эти случаи служат основой production-corpus, но не заменяют выполнение LMX. Для source-проверки, lifetime, native и новых библиотечных адаптеров нужны наблюдения средствами самого проекта.

## 12. Предлагаемые контрольные результаты

**Первый сквозной результат:** один parser с делегирующим bracket-компонентом и один общий группировщик Expression, настоящий custom operand transport, scalar power, dense/`[]@` Map с depth, базовые срезы и writer. Пользовательские программы проходят реальные маршруты через общий код, а неподдержанные профили получают точные диагностики.

**Второй результат:** общий indexed/reducer-план и минимальный Scalar/Map fuse с проверенным распределением памяти, спросом и ошибками. Эти две ветви могут завершаться независимо при соблюдении общих access/Value-договоров.

**Полное закрытие ТЗ:** все обязательные семейства каталога и заявленные профили реализованы либо имеют согласованную в норме явную границу; для каждого доступны production receipts, синхронизированные примеры и проверенная документация. Первый сквозной результат и минимальный fuse сами по себе не объявляются выполнением всех 529 позиций.

Календарные оценки разумно уточнять после этапа 0 и первого сквозного изменения: чтение архива не даёт данных о скорости полной сборки, внешней инфраструктуре и объёме фактических регрессий. До этого план задаёт проверяемые результаты и зависимости, позволяющие делить работу без дублирования ядра.
