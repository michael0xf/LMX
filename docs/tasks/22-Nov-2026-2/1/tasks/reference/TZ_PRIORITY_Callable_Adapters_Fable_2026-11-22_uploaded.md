## 1. Что исправляем

Устранить два ограничения предложенных реализаций:

1. Фабрики восстанавливают callable в основном из списка типов и результата, а публичные входы делают `required/private`. Теряются собственные defaults, требование инициализации и разрешённое автозаполнение исходного callable. Дополнительно общая обёртка заранее читает все входы, что может заставить ненужный computed default или обратиться к неиспользуемому `uninit`.
2. `uncurry` заранее задаёт всем промежуточным ступеням результат `@`. Он должен работать и с обычными допустимыми цепочками, промежуточные результаты которых имеют точное callable- или Structure-требование, сохраняя штатные проверки LMX.

**Это работа над адаптерами, а не введение новых ограничений языка.** Совпадение сигнатур по типам само по себе не означает сохранения поведения вызова. Нужно исправить реализацию и обеспечить заявленное поведение, а не снять обещание из документации или потребовать от пользователя всегда передавать все аргументы явно.

Первое ограничение видно непосредственно в проекте исходников и контракте builder. Во втором случае доказано построение `Ti → @`, но конкретный runtime-отказ цепочки с более узким результатом в этом комплекте не воспроизводился: LMX-ядро не запускалось. Сначала проверить фактический admission текущего ядра. Если обычные правила уже допускают некоторый такой случай, сохранить его и добавить регрессию; не добавлять для него лишнее преобразование.

Это ТЗ уточняет и разворачивает §11 `docs/tasks/TZ_Receivers_Satisfies_2026-11-22.md`. Оно заменяет ограничения разделов «Границы текущих фабрик» и соответствующих комментариев к builder как целевой контракт исправленной реализации. Остальные правила языка и смысл операций сохраняются.

## 3. Неподвижная граница: сигнатура и поведение вызова

Сигнатурная совместимость по-прежнему сравнивает число и порядок полных входных требований, наличие результата и его полное требование. Имена формальных параметров, defaults, requiredness, throws и исполняемое тело не становятся новой identity сигнатуры. `satisfies` не должен отвергать совместимые типовые описания только потому, что отличаются defaults.

Вместе с тем адаптеру, сохраняющему поведение входов конкретного F, недостаточно одной такой сигнатуры. Нужен доступ к **реальным объявлениям и правилам вызова выбранного F**: собственным defaults, required/private, соответствию позиций, именам для неявного связывания и происхождению вычисляемых описаний. Это сведения существующего графа/вызова, а не новый вид функции.

Не брать defaults из произвольного именованного шаблона сигнатуры: шаблон не заменяет правила фактического кандидата. При вызове через именованное требование публичные имена actuals отображаются на позиции по прежним правилам; разрешённый autofill использует собственные имена и объявления кандидата, а не случайные `pN` генератора.

Обычный `Name :: DATA` и `signatureTypes` остаются описаниями одного вида сигнатуры. Публичный `fn` не возвращать. Существующее отношение именованной сигнатуры с `call` не переписывать.

## 4. Исправление A: сохранить политику входов

### 4.1 Требования к переносу

Для неизменённых позиций сохранять поведение исходного входа. Для `partial` применять это к остаточным позициям с учётом уже принятого префикса; для `flip/permute` переносить вместе тип, позиционное соответствие и политику соответствующего объявления. Имена публичного интерфейса берутся из заявленного контракта адаптера; они не должны случайно подменять имена, по которым исходный F выполняет неявное связывание.

Сохранить следующий порядок и различия [S8]:

1. Явный actual заполняет выбранное место и подавляет исходный initializer. Его несовместимость не лечится подстановкой default.
2. При отсутствии actual остаётся собственное готовое значение или описание computed default. Одноимённая переменная caller не заменяет их.
3. Если собственного initializer нет, допускается обычный autofill из разрешённого контекста текущего вызова.
4. Private источника и реально видимого принимающего объявления фильтрует неявное связывание в обе стороны; явная передача сохраняется.
5. При отсутствии допустимого заполнения остаётся `uninit:T`; само наличие optional-входа не означает обязательного чтения его значения.

Отсутствие actual — не явные `0`, `nil`, нулевая ссылка, пустая структура и не запись `uninit:T`. Нельзя передавать фиктивное значение вместо отсутствия: это подавит собственный default или изменит выбор кандидата.

Input `required` без actual и собственного applicable default должен по-прежнему отклонять вызов на стадии выбора; скрытый autofill его не спасает. Required со своим default рассматривается обычным механизмом. Достигнутый `required` в CODE проверяет текущее место в момент исполнения. Не сливать эти проверки в новую обязательность всех параметров.

### 4.2 Ленивые defaults и декларационные actuals

При построении адаптера, отражении сигнатуры, проверке `satisfies` и подготовке неиспользуемой ветки не исполнять computed defaults. Не превращать их в eager-снимки. Если исходный F не читает optional-поле, общая обвязка тоже не должна читать его только ради формирования вектора.

Сохранить происхождение default: его лексические ссылки, `node`, фактический DATA и доступ к остальным местам той же целевой активации. Простого копирования текста initializer в новый DATA недостаточно.

Обязательный случай: у F входы `x` и `y`, default `y` зависит от `x`; `partial(F; prefix := (5))` при пропущенном `y` использует принятый `x = 5` и исходный смысл default. Удаление `x` из публичного остаточного списка не удаляет его из целевой активации и не заставляет default читать одноимённую переменную фабрики.

Обычные декларационные actuals сохраняют форму и namespace-подстановку, где это допускает исходный callable. Не сводить все такие actuals к заранее вычисленному payload. Уже готовый типизированный префикс `partial` сохраняет свой нынешний договор: примитив принимается по значению, ссылка сохраняет цель; это не основание глубоко копировать цели или исполнять сохранённую декларацию сверх обычного приёма.

### 4.3 Места, контекст и private

Служебные `state`, `engine`, `record`, временные указатели и счётчики остаются защищёнными от случайного динамического связывания. **Нельзя исправить проблему массовым удалением `private` со всех полей.** Отделить служебные зависимости адаптера от политики пользовательского входа.

Autofill должен использовать разрешённый контекст текущего вызова, а не контекст создания фабрики и не случайные locals внутреннего engine. Для двух вызовов одного адаптера из разных разрешённых контекстов результат связывания должен соответствовать этим двум вызовам.

Сохранить различие собственного места и прозрачного места caller в документированном договоре конкретного адаптера. Заполнение объявленного входа не превращается в alias caller; выбранное прозрачное связывание не превращается в копию с записью обратно при выходе. Для тождественного пустого `partial` эталон — прямой F. Для обёртки со своей последовательностью вызовов явно определить точку связывания и применить обычные правила цепочки. Это не требование пропустить промежуточный вызов B в A → B → C: если B только передаёт имя и не сформировал прозрачную связь, обычный fallback C может дать собственную копию, а не место A. Такую цепочку не выдавать за тождественный прямой вызов. Не обходить private, не собирать статически требования всех потомков и не заводить глобальный снимок окружения.

Lifetime не продлевается наличием ссылки. Если отложенное описание зависит от закончившейся активации, применять существующие правила допустимости/захвата; не маскировать dangling pointer скрытым глубоким копированием произвольного графа.

### 4.4 Где изменить реализацию

Переработать путь `FxSignatures → FxBuild/FxKernel\callable` так, чтобы описание типов не использовалось как замена исходному договору заполнения. Использовать доступные объявления графа и штатную подготовку вызова. При нехватке сведений минимально расширить существующий внутренний bridge; конкретные имена внутренних полей определяет реализация, этот документ не вводит новый публичный ресивер.

Пересмотреть `FxTargetCallText`: не генерировать фиктивную явную передачу каждого отсутствующего остаточного параметра. Сохранять факт отсутствия, принятое позиционное отображение и отложенную форму через штатный механизм target call либо доказуемо эквивалентную подготовку его активации.

Переработать `FxWrap`: исключить безусловное чтение всех `pi` перед входом в engine. Использовать существующие места, отложенные описания и транспорт выбранных actuals. Здесь требуется сохранение наблюдаемого поведения; универсальный «ленивый массив», отдельная VM или постоянный дополнительный граф не предписываются.

`partial(F; prefix := ())` можно оптимизировать до F, если это удовлетворяет объявленному интерфейсу и наблюдаемому договору. Такая оптимизация не заменяет исправление непустого префикса и остальных фабрик.

Для конструктора, которому даны только типы и нет исходного F, не выдумывать defaults или происхождение имен. Его собственные входы строятся обычными объявлениями с явно заданной политикой. Требования, вытекающие из смысла операции, выражаются её обычным контрактом, а не универсальным правилом `required/private` для любого generated callable.

## 5. Собственное поведение обёрток

Не требовать от `once`, `trace` или `guard` полного совпадения всех эффектов с голым F: у этих операций есть собственный смысл. Требуется сохранить поведение входов, кроме действий, которые прямо составляют договор операции. Общий `FxWrap` не должен навязывать дополнительные чтения.

| Операция | Что сохраняется | Допустимые собственные действия |
| --- | --- | --- |
| `partial(F; пустой prefix)` | Обычный допуск, пропуски, defaults, связывание и результат F при соответствующем отображении actuals | Дополнительный запуск F/default при построении не допускается |
| `partial` с непустым prefix | Семантика остаточных входов в целевой активации с уже принятым prefix | Принятие явного prefix при создании; независимые последующие вызовы |
| `flip/permute` | Политика каждой переставляемой позиции, результат, исходы и связи | Объявленная перестановка позиций |
| `once` | Обычная подготовка явно написанных actuals при каждом вызове; первый успешный результат и повтор после неуспеха | На cache hit F не исполняется; невостребованные omitted-defaults не форсируются общей обвязкой |
| `guard/contract` | Входы не читаются до потребности предиката/тела; чтения и подстановки согласованы | Предикат может сам потребить аргумент, вызвать его default и отклонить вызов; post может потребить результат |
| `trace` | Наблюдение не требует автоматически вычислить все omitted-defaults | Явные действия sink, обычные enter/return/leave-without-result; его ошибки сохраняют заявленную политику |
| `memoize` | Отсутствие не смешивается с нулём/nil; неуспех F не кешируется | Вычисление ключа и `sameKey` — собственное наблюдение; востребованные ими значения могут вычисляться |
| `compose/pipe`, `recover`, `predicate`, `fix` | Политика соответствующих внешних/остаточных входов выбранной операции | Их объявленная композиция, handler, преобразование результата или связывание self |

Для `trace` убрать скрытую предпосылку, что `event.args` всегда полный заранее вычисленный вектор. Для ранее поддержанных полностью подготовленных actuals сохранить доступность значений. Для пропусков/отложенных описаний явно представить наличие и состояние обычными структурами либо иным уже существующим способом; построение события не должно само исполнять default. Если sink сознательно запрашивает ещё не вычисленное значение, его действие и lifetime должны быть описаны и проверены отдельно. Пассивный sink не заставляет default.

Для `memoize` до реализации зафиксировать точную политику ключа: из каких позиций/состояний он строится, когда читает значения и когда фиксирует ключ. Проверить `sameKey` на omitted/default/autofill. Нельзя объявлять cache hit для разных принятых значений только из-за того, что в обоих вызовах ничего явно не передано. Нельзя объявить чтение ключа «бесплатным» или случайно изменить существующую политику во время вызова F.

Проверить все клиенты изменённых builder/transport, включая `curry`, `adapter`, `overload`, `repeat`, `retryCall`. У каждого сохраняется собственный документированный договор: например, `curry` поэтапно принимает входы, а `retryCall` повторяет вызов с предусмотренным снимком. Требование «без ограничений адаптера» не означает удалить смысл поэтапности, кеширования, явного контракта или снимка.

## 6. Исправление B: uncurry без искусственного Ti → @

### 6.1 Сохраняемый интерфейс

Сохранить `uncurry(curried; contract; failures)`. Явный плоский `contract` задаёт количество N входных позиций, их полные требования и окончательный R/void; `failures` задаёт разрешённые именованные исходы ступеней. Обычная цепочка может происходить из `curry` или быть построена пользователем самостоятельно.

Для N > 0 выполнить ровно N ступеней. Для N = 0 вызвать исходный nullary callable один раз. Для N = 1 выполнить один вызов. Если окончательный R — callable или Structure, вернуть его как результат: не выполнять дополнительный шаг. Условие остановки «пока результат вызываемый» запрещено.

Фабрика не запускает ступени, не пробует их на фиктивных аргументах и не вычисляет defaults ради узнавания следующей функции. Не требовать от пользователя привести все промежуточные результаты к `@` или вручную оборачивать каждую ступень.

### 6.2 Получение точного договора ступени

Вместо безусловной таблицы `Ti → @` использовать фактическое описание текущей ступени. Где оно заранее известно без исполнения, сохранить его полным. Где следующая ступень зависит от значения/ветви, продолжить обычный анализ после получения действительного результата предыдущего вызова.

Проверка входа и результата выполняется штатными правилами LMX. Не добавлять отдельную статическую ковариантность, безусловное стирание модели до `@` или запрет более узких результатов. Проверять полное требование: callable-сигнатуру, структурную модель, тип элементов и квалификаторы там, где они входят в обычный admission.

Концептуальный алгоритм, **не новый синтаксис LMX и не новый интерпретатор**:

```text
при создании U:
    прочитать плоский contract и сохранить исходную operation
    построить обычный callable U; ни одну ступень не вызывать

при вызове U:
    сохранить обычные подготовку actuals, выбор и контекст вызова
    current := исходная operation
    если N = 0:
        выполнить один обычный nullary-вызов current
        вернуть результат по R/void
    иначе для i от 0 до N-1:
        получить действительный договор current без исполнения его тела
        проверить/подготовить этот unary-вызов штатным механизмом
        вызвать current с actual, соответствующим позиции i
        если i = N-1:
            вернуть действительный результат по окончательному R/void
        иначе:
            использовать действительный результат как следующую ступень
            сохранить его полное описание и проверить допустимость,
            когда следующий вызов действительно достигнут
```

Указатель на типизированную запись результата и payload callable/Structure не смешивать. Внутренний транспорт может пользоваться `@` как ссылкой на запись; это не делает объявленный тип результата всех ступеней равным `@`. Точная модель результата сохраняется до обычного приёма и следующего вызова.

Если промежуточный результат нельзя использовать как следующую ступень, получить обычный отказ в соответствующей точке; последующие тела не выполнять. Если промежуточный вызов завершился declared failure, сохранить имя и payload, а не превращать его в ошибку якобы статического типа.

При N > 0 сохраняется договор unary-цепочки. Поддержка более точного результата не означает произвольную замену одной unary-ступени многовходовой функцией.

### 6.3 Порядок эффектов

Плоский вызов U имеет обычный порядок подготовки его явно написанных actuals. Не обещать равенство эффектов плоского вызова и отдельно написанной вложенной цепочки, если в них разные моменты вычисления аргументных выражений. Для сравнения самих ступеней использовать уже подготовленные значения; порядок вычисления внешних actuals проверять отдельно.

Отложенные defaults и связывание U подчиняются исправлению A. Не переносить late-default в eager-подготовку ради того, чтобы удобнее построить `stages`.

## 7. Архитектура и эффективность

Использовать один штатный анализатор и механизм вызова. Generated callable остаётся обычным owner → DATA → CODE с настоящим `parent`; состояние хранится обычными структурами в допустимой арене Message. Любая Structure уже является последовательностью `@`; не добавлять вокруг неё обязательную коробку `items`.

Не создавать второй исполняемый граф, постоянную копию namespace, глобальную таблицу closure-environment или скрытую публикацию locals в граф. Служебные сведения текущей активации и транспорта допустимы по существующей модели; они не становятся вторым представлением всей программы.

Не переразбирать сгенерированный текст на каждом вызове. Если выбранный native-вызов и договор уже подготовлены, использовать прямой путь и существующие таблицы. Динамическая проверка остаётся там, где её требует реальный достигнутый вызов; не добавлять универсальный обход всех сигнатур на каждом native-шаге.

Компиляция явная. Не присваивать новому ABI чужой native entry, не объявлять автоматическую перекомпиляцию и не добавлять произвольную инвалидацию вне существующих правил graph edits/`endturn`. Проверить поведение после разрешённых изменений графа именно на предусмотренной языком границе.

После семантической приёмки сравнить прямой F, пустой/непустой `partial`, `once` miss/hit и `uncurry` на уже подготовленных значениях. Измерить число чтений/вызовов/выделений и время при одинаковой работе. Не заменять корректность выигрышем на одном тесте и не встраивать новый обязательный универсальный вектор в прямой native-путь, если существующий транспорт обходится без него.

## 8. Приёмочные регрессии A

Использовать журнал эффектов, идентичности ссылок и состояния мест, а не только конечный `return`. Следующие записи задают наблюдения; Fable должен оформить их в настоящем текущем синтаксисе LMX и подключить к стенду.

| ID | Случай | Обязательное наблюдение |

| A01 | У F собственный `x = 7`, у caller одноимённый `x = 50`; F() и пустой partial | Оба используют 7; имя p0 не меняет правило |

| A03 | Required без initializer, actual отсутствует, у caller есть одноимённое значение | Обычный отказ выбора; autofill не спасает required |
| A04 | Required с собственным default; отдельно reached CODE required после обычного заполнения | Оба случая следуют своим нормативным моментам проверки; default не исполняется ради перечисления кандидатов |

| A15 | Неизвестное имя, дубликат, избыток actuals, одиночная Structure, явно именованная Structure | Сохраняются выбор, W/E и проверки до эффектов; внутренний транспорт повторно не раскрывает готовую структуру |

Проверки A и B выполнить в поддерживаемых сочетаниях interpreter→interpreter, interpreter→native, native→interpreter и native→native. Native-методы должны действительно исполняться там, где заявлен native-путь; незаметный переход всего теста на интерпретатор не считается покрытием.

Отдельно сохранить регрессии общего parser/operand handler: анонимный left + один анонимный аргумент right открывает один внешний уровень **только справа**; left целиком, P0 ничего не снимает, рекурсивного раскрытия нет. `Name :: (A B)` сохраняет один правый шаблон; W/E обычного callable остаётся своим правилом.

## 12. Критерий готовности

Работа завершена, когда обязательные A/B-наблюдения подтверждены настоящим ядром; обычные сигнатуры и named-call отношения не изменены; нет требования к пользователю дописывать actuals, стирать промежуточные модели до @ или вручную оборачивать ступени ради обхода дефекта адаптера.

Отчёт Fable должен содержать пути/символы и суть исправления, исполняемые случаи и команды запуска, результаты каждого режима, журнал значимых эффектов и отдельные ограничения, если какие-то проверки ещё не выполнены. Проверку текста, сборку файла и наличие assertions не выдавать за runtime PASS.

Документацию о снятии ограничений обновлять по фактически подтверждённым результатам. Если реальный механизм ядра уже решает часть задачи, использовать его; если недостаёт узкого входа к нему, реализовать этот вход и проверить его, сохраняя общую динамическую модель LMX.
