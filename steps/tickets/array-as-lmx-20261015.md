Утверждённая автором цель: язык сохраняет один граф «код = данные». Графовый
Array — разновидность Structure `Lmx`, а не самостоятельный языковой объект с
одним дескриптором `{size, data}`. В L1/C99 массивный узел должен происходить
от общего `Lmx`-заголовка, а не наоборот: нынешний `Lmx`, начинающийся с
встроенного `VoidArray`, — переходный ABI, который нужно заменить. Типизированные
массивы ячеек арены могут оставаться физическим backing; они не создают второй
вид графового значения. Фиксированное число слотов и стабильные адреса остаются.

## Наблюдаемое правило

В `arr: []: (...)` лексическое место `arr` принадлежит текущей Structure,
графовый Array связан с этим местом и имеет его как структурного родителя;
структурные элементы, сформированные обычным разбором аргумента `[]`, имеют
родителем Array. Скобки не создают дополнительный узел, если P0 по общему
правилу делает единственную анонимную Structure прозрачной. Для примитивного
элемента родительство определяется его местом в Array; отдельная Lmx-обёртка
примитивной ячейки из этого не следует.

`MyLmxStructFromArray: arr` связывает новую ссылку с **тем же** Array, не
восстанавливает, не преобразует и не копирует его. Поэтому Array сохраняет
собственный `parent`, `native`, адресную идентичность и обычные правила
`merge`, `implements`, `toLmx` и вызова по фактическому коду. Имя результата
не выбирает особый маршрут.

## Миграция для единственного kernel writer/build

1. Зафиксировать общий физический `Lmx`-префикс и производный графовый Array
   с полями фиксированной длины и типизированного backing. Обычная Structure
   и Array должны классифицироваться как графовые `Lmx`-узлы при сохранении
   различия типов элементов через пулы арены: вид результата определяет
   общий конструктор разрешённого ресивера, а не сходство полей уже
   объявленной `data`-структуры. Та же граница действует для результата `fn`:
   только исполнение ресивера создаёт объект его пула. Пул классифицирует
   адрес, но не хранит имя в графе и не заменяет `implements` или таблицу
   имён, которой обходчик определяет написанную голову. Не приводить старый `VoidArray *` к `Lmx *`:
   у него нет `parent/native`. Определить физическое представление места
   `arr` как устойчивого графового вхождения, а не подменять `Lmx.parent`
   адресом голого слота `void **`. Обычный `[]:` даже в генерируемом L1
   создаёт графовый Array; только явный `c.array:` обозначает сырой C-массив.
2. Одним зависимым срезом перенести создание всех Array, адресные диапазоны,
   типизированные пулы, пути и `@`, обходчик, native-понижение, копирование,
   `merge`, квалификацию `immutable`, GC и `toLmx`. Копия обязана перенаправлять `parent` и внутренние
   ссылки по общей карте; алиас на исходный Array не создаёт третьего
   экземпляра. Смена кода проверяет пригодность `native` общим механизмом.
   Типизированный backing выбирается пулом: `void *data` графового Array
   даёт сгенерированному L1/C указатель фактического типа элемента, но не
   позволяет читать пул `void *`-слотов как произвольный `T`. На ступенях
   самосборки генерировать этот доступ из одной нормы L2, без частных
   языковых Array-типов по каждому `T`.
3. Проверить `arr: []: (...)`, чтение/запись элемента, лексический путь из
   вложенного структурного элемента, алиас `MyLmxStructFromArray: arr`,
   `immutable`-Array, перенос/полную копию между аренами и обратную запись `toLmx`. Сверить
   native и walker на одном графе, включая типизированный примитивный Array,
   массив ссылок и вложенные массивы. Не принимать один частный GREEN за
   закрытие ABI или самосборку.
