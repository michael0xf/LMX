# Пояснения к семантике LMX

Это короткие ненормативные примеры. При расхождении действуют
[семантика](LMX_semantics.ru.md) и [грамматика](LMX_grammar.ru.md).

<a id="data-receiver-execution"></a>
## Что исполняется при проходе по data

Данные не становятся телом программы. Прямой проход исполняет только ресиверы объявления корневого
уровня; выполнение такого ресивера может вызвать переданный ему код обычным способом.

Фрагмент данных, при отдельно объявленном методе `makeValue`:

```lmx
Values:
    int: x makeValue()
    Nested:
        int: y makeValue()
end: Values
```

При проходе по данным `Values` ресивер `int` объявляет `x` и получает значение через вызов `makeValue()`.
Запись `Nested` объявляет вложенную Structure. Её `int: y ...` не исполняется этим проходом: это уже
другой уровень данных. Если выполнение `makeValue` доходит до `test`, тот исполняется по обычным правилам;
искать `test` внутри данных отдельным обходом не нужно.

`end: Values` здесь закрывает два уровня. Для одного уровня достаточно уменьшить отступ; `return`
может служить трейлером исполняемого определения. Это [оформление](../LMX_blog/2026-11-13.md#one-level-formatting),
не новое ограничение парсера. Норма — [проход по данным](LMX_semantics.ru.md#data-root-declaration-execution).

<a id="admission-stages"></a>
## Два шага допуска

| Когда | Что происходит |
|---|---|
| Построение графа, кандидат известен | Проверяется используемый интерфейс. `test` не исполняется. |
| Фактический допуск при исполнении | Если первая часть уже выполнена, она не повторяется. Затем исполняются заданные `test`. |
| Первая проверка вернула `0` | Допуск немедленно прекращается; оставшиеся проверки не исполняются. |

Известность кандидата при построении не отменяет второй шаг при фактическом допуске. Само изменение
значения не запускает все проверки заново. Норма — [допуск и test](LMX_semantics.ru.md#admission).

<a id="callable-description"></a>
## Явная композиция тела метода

```lmx
fn: add (int: x; int: y) int ()
return: x + y

fn: add5 (int: x) int ()
    merge((int: y 5); add\code)
```

У `add` отдельно хранятся `args` с формалами `x` и `y`, `return`, `data` и
`code` с оператором `return: x + y`. Путь `add\code` выбирает именно часть `code`.
`merge` строит для `add5` тело с `int: y 5` и этим оператором; `add5(1)` даёт 6.
Операнд `(int: y 5)` записан в скобках: список аргументов читается как код, и
голое `int: y 5` в нём было бы вызовом ресивера, а не полем операнда.
Заголовок `add5` объявляет только формал `x`: поле `y` нового тела не
становится формалом или значением формала по умолчанию. Запись
`merge(add; (int: y 5))` не равнозначна: у внешней Structure метода `add` есть
части `args`, `return`, `data` и `code`, но нет непосредственного поля `y`.

Другой вариант `add5` помещает инициализацию в явную `data`, сохраняя тело `add`:

```lmx
fn: add5 (int: x) int (int: y 5)
    add\code
```

Третий, альтернативный вариант изменяет уже `args`: здесь `y` — формал
с умолчанием 5, а не поле тела или `data`:

```lmx
fn: add5 merge(add\args; (int: y 5)) int ()
    add\code
```

Это три взаимоисключающих определения `add5`, а не три последовательных
объявления в одной области. Полная форма `fn` явно передаёт `data` после
описания результата; короткая запись без этого аргумента допустима и создаёт
в результате ту же адресуемую пустую часть `data`. Однополевое `int: x`
описывает типизированное место без начального значения, в сигнатуре —
формал без умолчания.

Результат `merge` отдельно проходит [допуск](LMX_semantics.ru.md#admission);
свободные имена тела — [динамическое разрешение](LMX_semantics.ru.md#dynamic).

Заголовок `fn: add (int: x; int: y) int` **без тела** — третья форма:
только дескриптор интерфейса, который можно передать по ссылке, но нельзя
прямо исполнить как тело `add`. Если после этого заголовка есть тело,
это короткое исполняемое определение с адресуемой пустой `data`. Полная
форма с `()` после результата задаёт её явно.

<a id="receiver-arities"></a>
## Место и значение у `int` и `@`

Место объявляет форма ресивера с перечислением его аргументов. Это отдельные
примеры, не последовательные операторы одной программы:

```lmx
int: x         # место int без начального значения
int: x 5       # int со значением 5

@: ptr         # void-ссылка без заданного адреса
@: ptr 0       # void-ссылка с явным нулевым адресом
@: ptr Model   # ссылка на существующую Structure, уже не пустой void-указатель
```

Первое определение выделяет место; в коде повторная форма с кандидатом
записывает в него после допуска, а повторная форма без кандидата только
сверяет требование (в данных повторная форма — ещё одно вхождение имени,
[имена и пути](LMX_semantics.ru.md#fields)). Составные записи с местом во внешней голове — `x: int()`,
`x: int: 5`, `ptr: @()`, `ptr: @: 0`, `ptr: @: Model` — сняты решением
автора 2026-11-10 ([семантика](LMX_semantics.ru.md#receiver-args-only)):
`ms: int: time` в данных объявляет Structure `ms` с полем `time`, а не место
`ms`.

<a id="header-receivers"></a>
## Как прочитать заголовок Structure

`parent(S)` даёт структурного родителя, `native(S)` — нативный вход либо 0,
`length(S)` — число элементов, `storage(S)` — указатель на их хранилище.
Все четыре читают значения; `native(S)` сам полученный вход не вызывает.

| Без аргумента | Равнозначный явный аргумент |
| --- | --- |
| `parent()` | `parent(data)` |
| `native()` | `native(data)` |
| `length()` | `length(data)` |
| `storage()` | `storage(data)` |

В `call(D C)` это данные D; чтобы выбрать C, пишут, например, `length(code)`.
Вложенное тело `if` не переключает данные запуска. Голое имя ресивера не выполняет вызов.
Запись `length: 7` в данных остаётся обычной Structure `length`: при одном вхождении
её выбирает `data\length`, а `length()` читает длину самих данных. Так же работают
записи parent/native/storage; особых путей к заголовку нет.

Поля физического заголовка теперь называются parent/native/length/storage.
`data` и `code` остаются аргументами-Structure запуска; `node` сохраняет прежний смысл
контекста активации. Для чтения этих четырёх значений descriptor не нужен;
он возвращает адреса для записи, как показано ниже. [Контракт](LMX_semantics.ru.md#header-receivers),
[открытая реализация M13](../next_core_tasks_v3.md#flat-lmx-descriptor).

<a id="get-descriptor"></a>
## Адреса полей заголовка через descriptor

`descriptor(S)` выбирает S; `descriptor()` без аргумента — текущую data, как `descriptor(data)`.
Это правило сохраняется во вложенных телах управления. Для code нужен явный аргумент.
Формы `descriptor: S` и `descriptor:` имеют те же контракты; в data запись остаётся обычными данными.

Пусть d — результат обычного вызова `descriptor: S`. Это Structure с
адресами полей `parent`, `native`, `length`, `storage` плоского заголовка S.
Например, `\(d\native) := 0` записывает ноль в настоящий S.native:
после штатной публикации следующий вызов S идёт через обходчик. Запись `d\native := 0` меняет
только указатель внутри d. Ни снимка, ни последующей синхронизации нет.

Явный путь к полю или типизированное разыменование допускает обычную запись,
в том числе ссылок и указателей на функции; запрет менять голое имя Structure
не запрещает этот путь. Глубина указателя и мерность массива независимы и
не ограничены фиксированным числом. Полученный адрес живёт в обычных границах
жизни S. Контракт утверждён, код ещё предстоит реализовать:
[`descriptor`](LMX_semantics.ru.md#get-descriptor),
[M13](../next_core_tasks_v3.md#flat-lmx-descriptor).

<a id="callable-admission"></a>
## Что проверяет интерфейс вызываемого

Методы с формалами `(int: x; int: y 5)` и `(int: x)` оба допускают `f(1)`, но
записанное у Consumer обращение `f(1; y := 25)` допускает только первый.
Проверяются необходимые явно использованные обращения, не совпадение
списков формалов и не предполагаемое поведение тела. Пользовательские
проверки поведения — отдельный этап.

<a id="method-pointer"></a>
## Имя метода и указатель на него

`myFunc()` вызывает объявленный метод напрямую. После
`@: ptr myFunc` форма `ptr()` вызывает метод через указатель; повторное
`@: ptr otherFunc` в коде присваивает существующей ячейке другой
совместимый метод (в данных повторная форма — ещё одно вхождение имени).
Голое `myFunc` или `ptr` лишь читает значение.
`(\ptr)()` — вызов после явного разыменования; `\ptr()` применяет `\`
к **результату** вызова согласно обычному приоритету, а не является особым
способом вызвать указатель.

<a id="native-structures"></a>
## Native обычной Structure и публикация

Одно тело C получает машинный вход общим с методами механизмом и работает с любой допущенной D:
`call(D C)`. Иной порядок полей D учитывает существующая карта мест. `call(C C)` — тот же случай;
искусственный fn и своя версия native для каждой D не нужны. Если S используется только как данные,
её собственный native для этого не требуется; native(S) читает указатель, не компилирует S.

Принятая запись меняет рабочее место кадра и dirty. После вычисления аргументов перед передачей
управления, на предусмотренных выходах и при yield готовые изменения публикуются по разрешённым адресам.
Путь или разыменование выбирает настоящий адрес и не задаёт немедленную публикацию.
Публикация правки кода снимает связанные native, запись обычных данных сохраняет вход.
Обнуление указателя не заменяет уже исполняемые машинные инструкции и не повторяет эффекты.
Обходчик должен переиспользовать подготовленный кадр и совпадать с native по продолжению после
публикации и вложенного вызова. Новая копия графа или реестр версий для этого не вводятся.
[Норма](LMX_semantics.ru.md#native-structures), [открытая реализация M14](../next_core_tasks_v3.md#native-structures).

<a id="native-merge"></a>
## Нативное тело в копии

Копия сохраняет собственный изменяемый граф; общий адрес машинной реализации
не делает граф общим. Если merge выбирает другое тело, старый native-вход
не описывает новый код. При той же реализации данные могут передаваться как
граф копии только при совместимых используемой раскладке и адресной карте;
при отсутствии пригодного native-входа исполняется готовый граф. Карта
`implements` сопоставляет физические поля, но не выбирает код и не хранит
имена в runtime. Разделение `call: data code` и адресуемые части метода —
[утверждённая кодируемая цель](../next_core_tasks_v3.md); совместимый ABI
ещё не реализован полностью.

<a id="factory-result"></a>
## Возвращённый метод

`@: add5 makeAdder(5)` **вызывает** фабрику и сохраняет возвращённый
метод. Затем `add5(1)` вызывает его через ссылку. Запись данных
`add5: makeAdder 5` лишь объявляет Structure `add5` и фабрику не вызывает; среди
исполняемых записей та же запись — вызов своей головы `add5`: вызываемое (метод
или указатель на него) вызывается, а обычная Structure запускается над данными
после двоеточия; аргумент записи один, `data`, поэтому для Structure `add5` два
поля `makeAdder` и `5` — ошибка
([журнал](../LMX_blog/2026-11-11.md#structure-call-by-name); чтение
исполнителя — [ответы](../LMX_blog/q/fable-self-answers-20261110.md), Р21,
п. 4 и 6). Если тело
возвращённого метода читает свободное `n`, динамический вход вызывающего имеет
приоритет перед скопированным лексическим запасным источником.

<a id="dynamic-fallback"></a>
## Динамический и лексический источники

Пример не является синтаксисом LMX: в скопированном лексическом контексте
`x = 10`, вызывающий передаёт `x = 25`. Свободное `x` читает 25;
`node\x` явно читает 10. При следующем вызове с `x = 40` свободное
`x` читает 40, а без динамического источника — лексические 10.

<a id="message-conversion-context"></a>
## Контекст преобразований Message

Схема `a → int` в Message A и `a → String` в Message B — не синтаксис
LMX. Один метод с требованием `a` получает смысл из контекста данного
Message; B не наследует преобразования A из-за доставки письма. Примитивное
`Foot → Meter` не доказывает `implements` для двух произвольных Structure.
При вызове могут понадобиться два разных маршрута: аргумент
`int → double` и результат `double → int`. Оба должны быть доступны в
контексте соответствующего Message.

<a id="post-transport"></a>
## post: один вызов, несколько доставок

Три обращения `getPixel` исполняются трижды. Если у каждого результата
три адресата `answer`, получаются три исходных ответа и девять доставок,
а не девять исполнений. Связь ответа с запросом задаёт исходный Message,
не позиция ветки и не новый числовой ID. `answer` готовят до отправки
`ask`; недоставка одного запроса не останавливает остальные.

`undelivered` получает уже сформированные аргументы исходного запроса;
объявленный отказ идёт в `catch`. Timeout считают от фактической отправки:
при пороге 500 мс обработчик может наблюдать 512 мс, но само пороговое
поле остаётся 500. Поздний ответ не удаляется автоматически. Полный
контракт и матрица T01–T26 — в [семантике](LMX_semantics.ru.md#thread-message-api)
и [почтовом плане](../next_core_tasks_v3.md).

<a id="tables-and-registries"></a>
## Таблицы и провайдеры как данные

Явная Table может дать написание `u8 → "uint8_t"` или ключ реализации
`plus[decimal][int] → decimal_int_add`. Она не объявляет типы, не создаёт
runtime-пространство имён и не ищет провайдеров автоматически. Порядок
источников, разрешение конфликтов и маркер отсутствующей ячейки задаёт
выбранный потребителем профиль, а не универсальный скрытый реестр.
