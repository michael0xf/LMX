## 1. Нормативные формы

В таблицах T — разрешённый код или полное описание типа/требования. `type` в примерах автора может обозначать имеющийся целочисленный код типа. `Struct` — обычная доступная Structure, используемая как модель/требование в типовой позиции. Это обозначения ролей, а не новые ключевые слова.


### 1.1. Массивы

| Форма | Значение |
| --- | --- |
| `[]: variable` | Объявить неинициализированную переменную «любой массив». Это допустимое требование, поскольку массивы — структуры LMX. |
| `[]: [data]` | Создать безымянную обычную Structure / void-массив из явно написанной группы, без объявления переменной. |
| `[]: variable [data]` | Инициализировать объявленную переменную группы массивов/структур значением написанной группы. |
| `type[]` | Найти тип «массив с элементом type» в действующей арене либо создать его при отсутствии; результат — обычный int-код этого типа. Массив-значение не создаётся. |
| `Struct[]` | То же для полного структурного требования Struct. |
| `[](type)` | Обычная компактная форма `[]: type`: попытка объявить неинициализированную переменную с именем type типа «любой массив». Это не получение кода `type[]`. |
| `type[]: [copy(squares)]` | Создать безымянный массив конкретного типа из значений, выданных copy внутри квадратной группы. |
| `Struct[]: [copy(squares)]` | Создать безымянный массив под требование Struct. |
| `(Struct)[]: [copy(squares)]` | Построить массив под полное требование, полученное из написанной группы (Struct) общим нормализатором. Группа не снимается автоматически. |
| `type[]: new_variable [copy(squares)]` | Построить массив конкретного типа и объявить new_variable с полученным значением. |
| `type[]: new_variable` | Объявить неинициализированную переменную «массив конкретного типа». |
| `int[]: [1 2 3 4]` | Безымянный массив целых. |
| `int[]: values [2 3 7]` | Именованное построение; тип находится в голове ресивера. |
| `int[]: []` | Инициализированный пустой массив целых, отличный от неинициализированной переменной. |
| `@[]` | Код общего типа обычной Structure / void-массива; @ — описание универсальной ссылки в типовой позиции. |

`[]: variable` **не означает** `@[]: variable`. Первая переменная допускает любой подходящий Array, включая плотные массивы и обычную Structure / void-массив; вторая имеет конкретное требование общего ссылочного массива.

### 1.2. Указатели

| Форма | Значение |
| --- | --- |
| `@: ptr` | Неинициализированная переменная ptr универсального, void-указательного типа. |
| `@: array [data]` | Инициализировать универсальную ссылочную переменную array безымянным массивом/Structure. |
| `@Struct` | Взять адрес выбранного обычного значения Struct. Это префиксная адресная операция. |
| `@(Struct)` | Обычная компактная форма `@: Struct`: попытка объявить void-указатель с именем Struct. Применяются обычные правила допустимости и занятости имени. |
| `int@` | Найти/создать код типа «указатель на int». Код получается и без двоеточия. |
| `Struct1@` | Найти/создать код указательного типа с полным требованием Struct1. |
| `Struct1@: ptr` | Использовать этот тип как голову ресивера и объявить неинициализированный указатель ptr. |
| `(Struct1)@: ptr` | То же построение указательного типа из полного требования написанной группы; её смысл сохраняется. |
| `Struct1@: ptr 0` | Объявить указатель конкретного типа, инициализированный нулевым указательным значением. Это не uninit. |
| `int@: ptr` | Неинициализированный указатель на int. |
| `int@@: ptr` | Неинициализированный указатель на указатель на int. |
| `int@@@: ptr 0` | Инициализированный нулём указатель третьего уровня на int. |
| `@@: ptr`, `@@@: ptr`, … | Универсальные указательные объявления следующих уровней через тот же расширяемый механизм. |

Двоеточие начинает Frame, использующий полученный тип как голову декларационного ресивера. Оно не меняет значение префиксного @ и не служит условием существования типа: `T@` уже получает его код, `T@: ptr` использует тот же код для объявления.

### 1.3. Три разных результата

Не смешивать:

1. **Код типа:** `int[]` или `int@` возвращает обычное значение int, обозначающее тип.
2. **Объявленное место без значения:** `int[]: pending` либо `int@: ptr`.
3. **Созданное значение:** `int[]: [1 2 3]` либо инициализированное указательное место.

`typeof` значения-кода сообщает, что само это значение имеет тип int. При употреблении его как кода типа общий normalizer читает обозначаемый тип из payload. Эти действия имеют разные предметы.

### 1.4. Structure и void-массив — одно значение

**Обычная Structure и массив void (в новой типовой записи @[]) неразличимы по общему контракту LMX.** Это не два вида объектов, между которыми нужен конвертер.

Поэтому и `[]: array [data]`, и `@: array [data]` могут инициализировать переменную ссылкой на безымянную Structure. Разница требований сохраняется: [] ограничивает цель массивом/Structure, @ допускает и другие значения. Наличие имени переменной не создаёт иной вид целевого объекта.

В DATA формы `array(...)` и `array: ...` объявляют обычную именованную Structure; она одновременно является массивом. Имя такой Structure сохраняет свой обычный декларационный договор и не смешивается с присваиваемой переменной, содержащей ссылку. В CODE эти формы сохраняют обычную роль вызова.

Две отдельные написанные группы создают собственные значения по обычному договору построения. Если две переменные получили одну уже существующую Structure, обе указывают на неё: само принятие через [] или @ не выполняет copy, не создаёт обёртку и не меняет parent.

<a id="common-parsing"></a>
## 2. Один общий путь разбора — обязательное требование автора

**Все перечисленные формы разбирать и разрешать общим путём. Не добавлять исключения для отдельных написаний [], @, @@, имён int/Struct или конкретных примеров.**


### 2.1. Сначала полная структура формы

P0 сохраняет написанные операнды, аргументы, группы и границы Frames. Он не интернирует типы, не запускает copy, не выполняет объявления и не строит отдельное представление программы.

Общий порядок обработки:

1. Сохранить исходную форму и её границы.
2. Определить роль, в которой потребитель принимает форму: имя объявления, описание типа либо обычное значение.
3. Разрешить форму по этому общему договору.
4. Выполнить достигнутую операцию в установленном порядке.

Внешнее двоеточие и постфиксные части головы определяются структурно. Нельзя сначала исполнить фрагмент, а потом по его результату или ошибке обнаружить, что он служил частью головы либо описанием типа.

### 2.2. Постфиксный тип и голова Frame

`T[]` и `T@` получают обычный int-код производного типа. В головах:

~~~lmx
T[]: [copy(squares)]
T[]: new_variable
T@: ptr
(T)[]: [copy(squares)]
(T)@: ptr
~~~

результат общего разрешения типа используется существующим механизмом декларационного ресивера. Ни для массива, ни для указателя не нужен отдельный parser типизированных объявлений.

Обычные завершённые компактные формы:

~~~lmx
[](type)
@(Struct)
~~~

по-прежнему эквивалентны соответственно `[]: type` и `@: Struct`. Они не служат сокращениями `type[]` или `Struct@`.

Прежнее специальное типовое чтение `[](T): …` и `@(T): …` также отозвано. Не превращать их неявно в новые постфиксные головы. Это не запрет байтов такой записи: если общая грамматика допускает Frame или иной результат в роли головы, его допустимость и смысл определяются обычным разрешителем. Отдельный режим совместимости для старого типа не добавляется.

Обновить общий контракт головы Frame и EBNF, если прежнее перечисление ограничивало голову простым именем или символом. Компактную эквивалентность нельзя реализовать ранней текстовой подстановкой, теряющей роль и границы формы.

### 2.3. Группы не исчезают из графа

Квадратная группа после типизированной головы — явно написанный источник элементов. Ресивер читает её по своему договору. Это не глобальное правило снятия любых скобок.

Группа слева от типового постфикса также сохраняет обычную семантику. `(Struct)[]` и `(Struct)@` используют полное требование, полученное общим нормализатором из этой группы. Не объявлять их безусловно равными `Struct[]` и `Struct@`. Если (Struct) означает самостоятельную одноэлементную анонимную Structure, это другая структурная модель. Совпадение нормализованных требований устанавливается общим механизмом, а не удалением скобок.

Пустая группа остаётся пустой группой; группа с одним элементом не исчезает из-за числа элементов. Все написанные группы сохраняются в чистом графе и при roundtrip.

Общее правило Expression об условном открытии единственного правого анонимного аргумента при анонимном left не меняется. Нельзя вводить для новых типов второй operand ABI или отдельный разбор «математики типов».

### 2.4. Типовая роль, адрес и положение @

В обычном выражении значения префикс `@x` получает адрес x. Постфикс `T@` получает тип указателя на T. Выбор закреплён написанной формой, ролью операнда и общими границами Expression/Frame, а не содержимым int-переменной.

В частности:

~~~lmx
int: value 7
int: typeCode sys\typeof(@value)
~~~

Далее `@typeCode` — адрес int-места typeCode; `typeCode@` — код указательного типа для типа, записанного в typeCode; `typeCode[]` — код соответствующего массива. Числовое совпадение payload с известным type-id не меняет адресную операцию.

Типовой постфикс потребляет левую форму как описание типа. Общий нормализатор принимает допустимый код, описание/модель и символический атом типа, а не только bare_identifier. Поэтому в `@[]` левый @ обозначает существующее требование универсальной ссылки. Вся форма получает код обычной Structure / void-массива; она не исполняет адресную операцию над пустой группой и не создаёт экземпляр массива. Это применение общего договора TYPE-role к символическому типу, без проверки строки «@» в частном array-parser.

В VALUE-role использовать обычный механизм prefix/postfix: в начале требуемого выражения @ может начать адресный операнд; после завершённого левого операнда @ может быть типовым постфиксом. Этот механизм применяется внутри уже установленных границ аргумента/Expression. Он не отменяет символические типовые атомы в TYPE-role.

В `int@: p @value` типовая голова заканчивается двоеточием, p потребляется как имя, а initializer начинается с адресного выражения. `F(T@; @x)` содержит два явно разделённых actual; не угадывать границы по будущей сигнатуре F и не выбирать разбор пробным исполнением.

Не вводить специальные проверки имён «int», «Struct» или «type». Полная модель и её типовой код не заменяются одним общим физическим тегом Structure.

### 2.5. Расширяемость @, @@, @@@, …, n и композиция

Семейство указательных форм имеет произвольную конечную глубину. Реализовать одну параметризованную операцию над глубиной n либо эквивалентное общее рекурсивное построение, а не отдельные алгоритмы для одного, двух и трёх @.

Это относится одновременно к:

- типам `T@`, `T@@`, `T@@@` и далее;
- универсальным объявлениям `@: p`, `@@: p`, `@@@: p` и далее;
- типизированным головам `Struct@@: p` и `(Struct)@@: p` с сохранением полного левого требования;
- обычной компактной форме `@@(name)`, эквивалентной `@@: name` в позиции завершённого Frame;
- композиции с массивами и другими допустимыми производными требованиями.

Постфиксы применяются последовательно слева направо:

| Форма | Полное требование |
| --- | --- |
| `int@[]` | Массив указателей на int. |
| `int[]@` | Указатель на массив int. |
| `int[][]` | Массив массивов int. |
| `int@@` | Указатель на указатель на int. |
| `int@@[]` | Массив указателей глубины 2 на int. |
| `@[]` | Общий ссылочный массив — обычная Structure / void-массив. |

Не задавать языковой максимум «три указателя», фиксированный массив из трёх описаний или закрытый enum глубин. Ограничения фактических ресурсов обрабатываются обычным отказом, без усечения или переполнения n.

В обычной адресной роли сохраняются адресуемость и время жизни каждого участвующего места. Глубина типа не заказывает создания цепочки объектов. Нулевая инициализация `int@@@: p 0` не выделяет три промежуточные ячейки.

### 2.6. Почему []: variable и []: [data] не неоднозначны

Ресивер различает исходную форму аргумента до lookup объявляемого имени, вычисления initializer и возможного потребления потока:

| Написанные аргументы | Роль | Результат |
| --- | --- | --- |
| Один идентификатор Name | Имя объявления; initializer отсутствует | `[]: Name` объявляет место без значения. |
| Одна квадратная группа [data] | Безымянные данные | `[]: [data]` создаёт Structure / void-массив. |
| Идентификатор Name и квадратная группа [data] | Имя и явный initializer | `[]: Name [data]` создаёт значение и инициализирует место. |

Для типизированного ресивера T[] эти же формы различаются тем же способом; тип результата/места уже определён головой.

Обычная инициализация уже готовым значением также сохраняется: `[]: destination Source` и `@: destination Source` принимают подходящее существующее значение Source после явно написанного имени destination. Это не безымянное чтение `[]: Source`: единственное имя в последней форме по-прежнему является именем объявления.

Это общий договор декларационного ресивера: имя потребляется как написанный идентификатор, а не как прочитанное значение одноимённой переменной. Если имя уже существует, действуют обычные правила повторного объявления и scope; выбор между объявлением и безымянным построением от его прежнего значения не меняется.

`[]: [Name]` содержит группу с одним элементом. Она не сворачивается в `[]: Name`. `[]: []` содержит присутствующую пустую группу и создаёт пустое значение; отсутствие initializer — другое состояние.

Не превращать `Name [data]` в вычисляемое индексирование имени до его потребления в позиции имени объявления. В этой позиции Name не является индексируемым выражением. Следующая отдельная группа остаётся initializer. В позиции обычного значения индексирование сохраняет общий Expression-договор.

Для этого не вводится глобальное новое правило «любой пробел запрещает индекс» и не создаётся специальная ветка parser для []. Текущая грамматика уже относит прикрепление index suffix к допускающему expression/update/receiver profile. Если реализация склеивает имя с группой раньше определения роли, исправить эту раннюю перегруппировку в общем пути.

Не угадывать пропущенные квадратные скобки и не выбирать другую ветвь по успешности вычисления значения. Классификация написанной формы однозначна; недопустимая форма получает обычную диагностику.

### 2.7. Пустой типовой суффикс и индексирование

В `T[]` скобки **написаны без индекса**. Это типовой конструктор. В `a[i]` написан индекс, поэтому действует общий договор индексирования.

Пустота определяется исходной формой до вычисления её содержимого. Пробелы и комментарии внутри иначе пустой пары скобок не создают индекс. Написанное выражение, группа или позиционный пропуск, напротив, не исчезают из-за того, что вычисление впоследствии выдало пустой поток.

Поэтому `a[()]` и `a[copy(empty)]` не превращаются в получение типа после вычисления пустого результата. Это написанные индексные формы; допустимость их индекса проверяет обычный механизм индексирования.

Отдельное `[]` без левой формы сохраняет свою обычную роль литерала/символа ресивера в соответствующей позиции. Оно не становится применением постфиксного конструктора к несуществующему левому аргументу. Прикрепление суффиксов выполняется в допускающем профиле; этот раздел не вводит нового глобального запрета или разрешения на пробел перед скобками.

<a id="type-codes"></a>
## 3. Коды типов и интернирование

### 3.1. Публичное представление

Тип обозначается обычным int-кодом, используемым `typeof`. Не вводить пользовательскую коробку Type, новый класс токенов или указатель на служебное описание вместо этого числа.

В текущих документах физический запрос обычно записан `sys\typeof`. Сокращение typeof в указании автора не требует второго API: согласовать оба описания с одним действующим запросом.

Пример получения производного типа:

~~~lmx
int: numbersType int[]
int[]: numbers [1 2 3]
~~~

numbersType содержит код конкретного массива целых. Запрос типа созданного numbers должен согласовываться с этим кодом через обычную семантику reflection.

`sys\typeof(@numbersType)`, напротив, получает тип самой int-переменной. Не подменять это значением numbersType.

### 3.2. Один разрешитель для всех потребителей

Использовать общий путь нормализации и разрешения в:

- типовых операндах T[] и указательных типах;
- типизированных головах и объявлениях;
- typeof, проверке кодов и доступе к сведениям о layout;
- satisfies и полных сигнатурах;
- interpreter, native lowering и общих транспортах вызова;
- copy/merge, сохранении и восстановлении значений.

Для готового int-токена типовой потребитель читает код из payload. Для `uninit:T` действующее получение требования T использует код записи и не читает отсутствующий payload. Обычное получение адреса int-переменной не становится такой нормализацией без типовой роли.

### 3.3. Каноническое получение типа

В действующей арене повторное получение одного производного типа по тем же полным параметрам возвращает уже существующий код. Если типа ещё нет, ядро регистрирует его один раз и возвращает код.

Ключ интернирования различает как минимум конструктор и его полное исходное требование:

- массив с элементом T;
- указатель на T, включая все уровни глубины;
- вложенные композиции этих требований.

`int[]`, `char[]`, `int@` и `int@@` не сливаются только из-за равенства машинного размера. Длина и capacity конкретного изменяемого массива не требуют нового типа при каждом resize.

Для Struct требуется сохранить полное структурное требование. Два разных требования нельзя потерять, заменив оба физическим кодом обычной Structure. При этом каждой произвольной пользовательской Structure не присваивается новый физический тип просто из-за её имени: производный тип создаётся при действительном применении типового конструктора.

Разрешение @[] должно использовать уже существующий общий тип обычной Structure / void-массива. Не регистрировать второй искусственно различимый STRUCT/ARRAY-kind для того же значения. Общий контракт typeof/descriptor, индексации, именованных полей и вызова остаётся единым.

Интернирование — служебная работа существующего контекста типов. Оно не создаёт экземпляр массива, не исполняет initializer модели и не компилирует код.

### 3.4. Владение, attach и восстановление

Код сохраняет смысл, пока живы значения и законные ссылки на соответствующее описание типа. Не оставлять в таблице записи, ссылающиеся на освобождённые либо отменённые временные данные.

Сохранить действующий договор attach арен: перенос chunks не переписывает адреса и коды уже существующих записей. Поэтому в области совместимых для такого переноса арен одно число не может одновременно обозначать разные типы. Использовать или расширить общую выдачу кодов ядра; локальный индекс произвольного независимого вектора не является достаточным кодом для этого договора.

При attach сохранить доступность описаний производных типов и их зависимостей. Два эквивалентных ранее полученных кода можно распознавать общим механизмом эквивалентности; не требуется переписывать все старые записи ради одного номера.

При восстановлении в другом контексте применяются существующие механизмы восстановления типов. Случайное равенство чисел из независимых контекстов не доказывает равенства типов.

Не добавлять новый глобальный пользовательский реестр, управляющие ресиверы или граф описания всей программы. Таблица кодов содержит сведения о типах; CODE, DATA и исполняемый namespace туда не копируются.

<a id="arrays"></a>
## 4. Массивы: объявление и построение

### 4.1. Любой массив и конкретный массив

~~~lmx
[]: anyArray
int[]: integers
@[]: references
~~~

Все три места неинициализированы. Их требования различны:

- anyArray — любой допустимый Array, включая обычную Structure / void-массив;
- integers — Array с элементами int;
- references — Array с элементами универсального ссылочного типа @.

Они не являются тремя готовыми пустыми массивами. Любой массив допускается как самостоятельное требование без знания конкретного элемента заранее. Для получения конкретного элемента реализация использует фактический код уже полученного значения.

### 4.2. Квадратная группа и безымянное значение

~~~lmx
int[]: [1 2 3 4]
type[]: [copy(squares)]
Struct[]: [copy(squares)]
(Struct)[]: [copy(squares)]
~~~

Квадратная группа явно обозначает список элементов для построения. Copy выдаёт свой обычный поток внутри этого списка. Записи вида `type[]: copy(squares)` без квадратной группы не использовать как эквивалентный безымянный конструктор и не добавлять для них специальную совместимость.

Конструктор выдаёт одно значение Array и не объявляет имени. Обычный Expression может потребить его непосредственно:

~~~lmx
2 * (int[]: [1 2 3 4])
~~~

Ожидаемый результат — [2,4,6,8].

### 4.3. Именованное значение

~~~lmx
int[]: values [2 3 7]
type[]: new_variable [copy(squares)]
~~~

Имя следует после типизированной головы; группа значений следует за именем. Объявление использует те же обычные правила места, scope и admission, что другие объявления. Не вводить второе выполнение initializer ради получения результата Expression.

Форма без группы:

~~~lmx
type[]: new_variable
~~~

означает отсутствие значения, а не пустой массив. Пустой инициализированный массив запрашивается явно:

~~~lmx
type[]: new_variable []
~~~

### 4.4. Поток и вложенное значение

~~~lmx
@[]: [S]
@[]: [copy(S)]
~~~

В первой форме S — один элемент-ссылка. Во второй элементы поступают из явно выполненной copy. Не раскрывать S автоматически только потому, что это массив или Structure.

Copy и merge сохраняют свои существующие глубокое копирование, карты и лексические отношения. Сборка потока не является второй copy, не делает контейнер владельцем скопированных методов и не запускает тела хранимого кода.

Обычные выражения, явно написанные для получения элементов, исполняются в установленном порядке один раз. Потребление готового поля графа не превращается в запуск его вычисляемого объявления.

### 4.5. Представление

Сохранить общий Lmx-дескриптор parent/length/storage. Для плотного T[] элементы читаются по фактическому виду T; для @[] storage содержит указатели непосредственно на значения {type value}. Capacity остаётся отдельно; все Arrays имеют изменяемую длину.

Типовые операции не добавляют тег к каждому плотному элементу. Универсальный вход через @ не требует предварительно превращать плотный массив в @[].

Если новое типовое требование принято через satisfies, это не разрешает читать фактическое storage с размером или шагом другого элемента. Тип приёма и физическое представление существующего значения согласуются через обычный доступ/конверсию.

### 4.6. Инициализированные общие формы и DATA-декларации

Поддержать вместе:

~~~lmx
[]: array [1 2 3]
@: pointer [1 2 3]
[]: [1 2 3]
~~~

Первые две формы создают инициализированные переменные. Третья создаёт только безымянное значение. Общие [] и @ допускают здесь обычную Structure; для её принятия не требуется типизированный T[] или превращение в отдельный объект Array.

В DATA обе следующие формы являются обычными объявлениями структуры-массива; строки показывают альтернативные записи одного намерения:

~~~lmx
array(int: first 1; int: second 2)
~~~

~~~lmx
array:
    int: first 1
    int: second 2
~~~

Последовательностные операции могут принимать такую Structure непосредственно. Именованные поля и физические слоты остаются её обычными полями и элементами. Чтение графа не запускает хранимые в нём receiver-формы, а наличие методов не создаёт отдельного callable-контейнера.

<a id="references"></a>
## 5. Указатели и произвольная глубина


### 5.1. Адрес спереди, указательный тип сзади

~~~lmx
@Struct
Struct@
int@
~~~

Первая форма получает адрес Struct. Вторая получает код указательного типа для полного требования Struct. Третья получает код указателя на int. Наличие будущего двоеточия для этого различия не требуется.

Типизированные головы:

~~~lmx
Struct@: ptr
(Struct)@: ptr
~~~

используют общий нормализатор левого требования. Группа во второй строке сохраняет своё значение; равенство требований этих двух примеров не предполагается. Уже полученный код применяется как голова декларационного ресивера, без промежуточного получения адреса модели.

### 5.2. Неинициализированный и нулевой указатель

~~~lmx
@: ptr
Struct@: typedPtr
Struct@: nullPtr 0
~~~

ptr и typedPtr не имеют значения. nullPtr имеет обычный указательный payload со значением 0 и полное требование своего типа. Не выдавать uninit за null и не читать у uninit несуществующее место payload.

Обычная инициализация универсального указателя значением, например `@: p Model`, сохраняет свою роль: p получает ссылку на Model. Требование теперь задаётся в типизированной голове, например `Model@: p Candidate`. Старую трёхаргументную форму задания требования переносить в эту голову; не поддерживать два конкурирующих стандарта объявления типов.

### 5.3. Глубина — параметр общего механизма

В роли типа n последовательных постфиксов @ означают n уровней указателя. Вложенное требование каждого уровня сохраняется.

Пример обычной цепочки адресуемых мест:

~~~lmx
int: value 7
int@: p1 @value
int@@: p2 @p1
int@@@: p3 @p2
~~~

Каждый следующий уровень адресует соответствующее реальное место предыдущего уровня. Нельзя заменить адрес ячейки p1 её сохранённой целью или сократить число уровней из-за одинакового размера машинного указателя.

Все те же правила работают для n > 3. Глубина указателя не является размерностью массива; `int@[]`, `int[]@`, `int@@` и `int[][]` обозначают разные композиции требований.

### 5.4. Старые адресные скобки

После отмены прежнего смысла bare `@(…)` обновить и адресные примеры:

| Было в прежнем тексте | Запись для сохранения адресного смысла |
| --- | --- |
| `@(node\x)` | `@node\x` либо группа всего выражения `(@node\x)` |
| `@(D\field)` | `@D\field` либо `(@D\field)` |

Цепочки полей/индексов имеют действующий приоритет относительно prefix @. Не оставлять старое `@(D\field)` исключением, которое вдруг продолжает означать адрес. Если compact-объявление получает недопустимое имя, применяется обычная диагностика имени.

Взятие адреса не продлевает lifetime и не превращает local активации в поле чистого графа.

<a id="admission"></a>
## 6. satisfies и таблица проверенных соответствий

### 6.1. Правило массивов задано автором

Типовое соответствие определяется рекурсивно:

~~~text
A[] satisfies B[]  ⇔  A satisfies B
~~~

Направление сохраняется. Не подменять это равенством кодов A и B, равенством размеров storage либо симметричным отношением.

Для пустого массива действует то же правило типов: пустота не делает его тип подходящим ко всем требованиям. Длина и capacity не являются основанием заново выводить типовую совместимость.

Полные модели, ссылочные требования, вложенные Array-типы и callable signatures остаются частью A и B. Сопоставление не должно стирать их до общего тега Structure или void pointer.

Эта норма не устанавливает новым текстом произвольное дополнительное правило для всех указательных типов. Для указателей использовать существующий общий договор соответствия их полных требований, повторяемый на каждом уровне глубины.

### 6.2. Таблица проверенных типов нужна

По указанию автора satisfies строит таблицу уже проверенных направленных соответствий типов. Это разрешённая служебная таблица ядра. Старую общую фразу «никаких caches» нельзя использовать как запрет этой таблицы.

Ключ и область применимости должны учитывать:

- исходный тип A и требуемый тип B в правильном порядке;
- полные нормализованные требования;
- действующий контекст типов/допустимых преобразований, если от него зависит ответ.

Повторная проверка тех же устойчивых требований использует завершённый результат. Промежуточное посещение пары при обходе рекурсивных требований не публикуется как уже доказанный положительный ответ.

### 6.3. Что эта таблица проверяет

Типовая совместимость не является проверкой конкретного текста по Pattern, запуском функции, выполнением преобразователя либо проверкой произвольного изменяемого состояния объекта.

Таблица типов не заменяет:

- соответствие физических полей конкретному приёму;
- проверку конкретного значения там, где она требуется;
- допустимость фактического диапазона при преобразовании;
- явно предусмотренный test;
- обычные lifetime/ownership и права на конкретное действие.

Для неизменных полных описаний типов допускается повторное использование между вызовами. Если часть требования действительно зависит от изменяемого графа, текущий приём читает эту часть по действующему договору; старый успех конкретного объекта не становится вечным свойством одного физического кода.

Не создавать для поддержания таблицы второй рабочий граф, копию всех объектов или наблюдателя за каждой записью. Новое ТЗ разрешает кеш типовых фактов, а не постоянный кеш любой проверенной программы.

### 6.4. Соответствие не меняет storage

Успех `A[] satisfies B[]` не перетипизирует уже созданный Array<A> и не меняет шаг его dense storage.

Чтение идёт через фактическое A. При необходимости значения преобразуются обычным разрешённым путём при потреблении; сама проверка типов преобразователь не запускает. Запись должна быть допустима для фактического массива и его элемента. Из принятия по B не следует разрешение записать байты B в ячейку размера A.

Это требование к общему доступу, а не добавление инвариантности вместо заданного автором направленного правила.

<a id="graph"></a>
## 7. Граф, отсутствие значения и исполнение

### 7.1. Неинициализированное значение

Для `[]: variable`, `T[]: variable`, `@: ptr` и типизированных указателей без initializer действует общее представление `uninit:T`:

~~~text
sizeof(value) = 0
~~~

Не резервировать в чистом графе фиктивный Array-дескриптор, указательный payload или место максимального размера. Валидность неинициализированной переменной означает допустимость её объявления и дальнейшей работы по обычным правилам uninit; она не означает, что length или разыменование получили готовое значение.

Локальное присваивание в активации не меняет исходное объявление в графе. Явная графовая запись заменяет выбранный фрагмент новым {type value} и не обязана сохранить адрес отсутствовавшего payload.

### 7.2. Полный исходный граф

Все операнды [], @ и их составные головы, группы, copy/merge, декларации и выражения остаются исходными формами в чистом графе. Конечные примитивные листья сохраняют обычное представление.

Таблицы интернирования типов и checked type pairs — метаданные существующего ядра. Они не являются отдельным executable-графом, копией DATA, «рабочим графом» или второй программой.

### 7.3. Runtime и native

Получение типа, объявление переменной, построение массива и интерпретация изменённого графа не требуют предварительной native-компиляции либо endturn.

fromLmx(text) строит обычный граф из текста. Готовый граф изменяется непосредственно runtime, без обязательного текстового roundtrip. Интерпретатор выполняет предусмотренные проверки достигнутых операций.

Явная компиляция и endturn относятся к установленной процедуре обновления машинной реализации. Этот слой не превращается в допуск к использованию нового типа или конструктора. Соблюсти тот же типовой договор в подготовленном native-коде, не добавляя автоматической слежки за всеми graph writes.

## 8. Миграция документов и ядра


### 8.1. Основные замены

| Прежнее применение | Новая запись / действие |
| --- | --- |
| `[]T` / `[]Struct` как тип массива из промежуточной редакции | `T[]` / `Struct[]`. |
| `[]T: [copy(S)]` / `[]T: name [copy(S)]` | `T[]: [copy(S)]` / `T[]: name [copy(S)]`. |
| `[](Struct): [copy(S)]` как прежняя группированная типовая голова | `(Struct)[]: [copy(S)]` с сохранением полного требования группы. |
| `@int` / `@@int` как коды указательных типов | `int@` / `int@@`. Префиксная адресная роль @ сохраняется. |
| `@Struct: p` / `@(Struct): p` как прежние typed heads | `Struct@: p` / `(Struct)@: p`. |
| `[]@` как прежняя запись типа Structure / void-массива | `@[]`; старое написание не является алиасом общего типа. |
| `[]: int values …` как типизированное объявление | `int[]: values […]`. |
| `[]: char text` как типизированный formal | `char[]: text`. |
| `return: []: int` / `return: []: char` как описание результата | `return: int[]` / `return: char[]`. |
| `[]: @ right` | `@[]: right`. |
| `[]: @(int) right` | `int@[]: right`. |
| `[]: int [1 2 3 4]` из прежнего TZ | `int[]: [1 2 3 4]`. |
| `[](T)` как конструктор кода Array<T> | `T[]`; сама `[](T)` теперь имеет обычный компактный декларационный смысл. |
| `@(int)` либо `@: int` как тип «указатель на int» | `int@`; компактные формы сохраняют обычное чтение объявлений. |
| `@: ptr Model Candidate` как typed declaration | `Model@: ptr Candidate`. |
| `@: ptr Model` как инициализация универсальной ссылки | Сохранить инициализацию ссылкой на Model; не объявлять её теперь uninit. |
| `@(D\field)` как адрес | `@D\field`, при необходимости `(@D\field)`. |
| Закрытые реализации @ / @@ / @@@ | Один механизм глубины n для универсальных ресиверов и постфиксных типов. |
| Запрет любого хранения результатов satisfies | Разрешить таблицу завершённых типовых соответствий по §6; сохранить границу конкретного admission. |

Это миграция текущего языка. Отозванные типовые прочтения не сохраняются в качестве второго неявного стандарта или parser-path. Старые байтовые формы могут иметь иной обычный смысл; он разрешается общим механизмом, без специального восстановления прежнего типа и без нового общего запрета этих токенов.

## 9. Приёмочные проверки

Ниже — требования к исполняемым fixtures, а не отчёт об уже выполненных тестах. Для доказанно эквивалентных форм сравнивать наблюдаемое поведение. Группированные формы проверять по их полному нормализованному требованию, без предположения, что скобки исчезают; исходные графы сохраняют все написанные группы.


### 9.1. Разбор и роли

| ID | Сценарий | Ожидаемое наблюдение |
| --- | --- | --- |
| P01 | `[]: variable` | Валидная uninit-переменная «любой массив», не конкретное @[]-требование и не пустой Array. |
| P02 | `[](variable)` и `[]: variable` | Один обычный декларационный договор; нет построения кода variable[]. |
| P03 | `@(name)` и `@: name` | Один договор void-указательного объявления; обычная диагностика недопустимого/занятого имени. |
| P04 | `Struct[]: [copy(S)]` и `(Struct)[]: [copy(S)]` | Каждый тип построен из своего полного левого требования; одноэлементная группа не снимается и не объявляется равной модели без проверки. |
| P05 | `Struct@: p` и `(Struct)@: p` | Оба объявления typed uninit; группированная модель сохраняется, равенство требований не предполагается. |
| P06 | `@Struct`, `int@` и `@x`, где int-переменная x хранит допустимый type-id | Адрес Struct, код указательного типа и адрес x соответственно; нет эвристики по числовому payload. |
| P07 | Вычисляемое типовое описание в голове и значения с эффектами | Каждая достигнутая операция исполняется один раз в общем установленном порядке. |
| P08 | Исходные группы с 0/1/несколькими элементами | Группы сохранены в графе и roundtrip; нет автоматического снятия одиночного контейнера. |
| P09 | Составная голова другого допустимого ресивера | Тот же parser/resolver path; []/@ не имеют отдельного мини-парсера. |
| P10 | `@D\field` и `(@D\field)` | Адресный смысл сохранён; старое bare `@(D\field)` не используется как адресный alias. |
| P11 | Безскобочное `T[]: copy(S)` | Не принимается как безымянная array-форма через специальный fallback, угадывающий пропущенную группу. |
| P12 | Source inspection формы с copy и типовой головой | Ничего не исполняется только из-за чтения/сериализации графа. |
| P13 | `[]: Name`, `[]: [data]`, `[]: Name [data]` | Неинициализированное место, безымянное значение и инициализированное место различаются по исходной форме. |
| P14 | `[]: Name` против `[]: [Name]`; имя уже существует | Первая форма потребляет имя объявления, вторая сохраняет группу с элементом. Lookup не переключает ветвь. |
| P15 | Имя и группа в объявлении; индексирование в позиции значения | Нет преждевременной склейки имени с initializer; общий index-профиль в позиции значения сохранён. |
| P16 | `T[]` против `a[i]` | Написанный пустой суффикс получает тип, непустой использует индексирование; решение принято до вычисления содержимого. |
| P17 | `a[()]` и `a[copy(empty)]` | Пустой результат не превращает написанную индексную форму в типовой конструктор. |
| P18 | `@[]` | Символический type atom принят общим нормализатором; получен код Structure/void-массива, без адресной операции и без нового Array. |
| P19 | `int@[]`, `int[]@`, `int[][]` | Постфиксы применены слева направо; разные композиции требований не смешаны. |
| P20 | `int@: p @value` | Типовая голова, сырое имя и адресный initializer имеют свои обычные границы; @ перед value не поглощён как продолжение имени. |
| P21 | Старые `[](T): …` и `@(T): …` | Нет прежнего специального типового чтения; возможный иной смысл и допустимость определяет общий resolver. |
| P22 | `F(T@; @x)` | Два actual сохранены; первый получает type-id, второй адрес, без выбора разбора по сигнатуре или успеху пробного вычисления. |

| ID | Сценарий | Ожидаемое наблюдение |

## 10. Порядок реализации и завершение

1. Согласовать общие postfix/prefix-правила, пустой суффикс, структуру головы и роли потребления; затем lexer/P0, resolver и соответствующие roundtrip-примеры.
2. Реализовать типовые коды и интернирование через существующие metadata/arena facilities.
3. Провести через общий путь [], указатели всех глубин, typeof, normalizeType и satisfies.
4. Мигрировать объявления, operand headers, сигнатуры и адресные примеры.
5. Применить обновлённые ТЗ последовательностей и Regex. Их приёмка использует это ядро.
6. Выполнить fixtures §9 и связанные регрессии, обновить нормативные документы, guide, исходники и производные файлы одним согласованным комплектом.

**Когда спрашивать автора:** только если после применения этой приоритетной нормы остаётся прямое противоречие двух действующих требований. В вопросе привести обе конкретные формы/фразы и минимальный пример, который невозможно удовлетворить одновременно. Старое прочтение в документации не является таким противоречием: оно явно заменено данным ТЗ. Не решать обнаруженный настоящий конфликт скрытым parser-исключением.
