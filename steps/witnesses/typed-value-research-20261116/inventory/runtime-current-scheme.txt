## 1. Выделение: пулы, ячейки, чанки, диапазоны

Записи (порядок полей как в заголовке):
- LmxRange (lmx.h.lm1): lo, hi, array(LmxPool*), owner(void*), chunk(void*), chunk_gen(size_t), links(LmxCodeLink**),
  slot_owner(Lmx**), holder(Lmx*), side_cells(size_t), side_stride(size_t), kind(int).
  ≈96 Б. Одна запись на ИНТЕРВАЛ (чанк), не на пул.
- LmxPool: head, tail (LmxChunk*), stride, chunk_capacity (size_t), kind, type (int), role (unsigned),
  pointer_read, pointer_write (fn*), scalar_abi (const LmxScalarABI*), profile (Lmx*), sealed (unsigned),
  next (LmxPool*), chain_gen (size_t). ≈104 Б.
- LmxChunk: cells (LmxCharDynamicArray{len, data, capacity} = 24 Б), value_contexts (LmxWalkValue*), next, mark
  (unsigned). ≈48 Б.
- LmxArena (lmx_arena.h.lm1): blocks (LmxArenaBlock*), arrays (LmxPool* — односвязный список всех пулов),
  index (LmxRangeDynamicArray{len, data, capacity}), generation, simple, source_view (unsigned), impl, impl_len,
  reset_gen, activation, call_places, execution_roots, impl_cap.
- Lmx (= LmxArray, `type: LmxArray struct Lmx`): parent (Lmx*), native (LmxEntry), array (VoidArray{size, data}) — 32 Б.
- LmxArenaBlock: base, n, class, dispose, next — ≈40 Б; на каждый чанк их ДВА (полезная нагрузка и запись чанка).

Виды и типы (lmx.h.lm1, enum LmxKind / LmxType).
- Виды: PRIMITIVE 1, ARRAY 3, CHILDREN 4, REF 5, STRUCT 6, LIST 21, SOURCE_NAME 22, SOURCE_SYMBOL 23,
  FIELD_ADDRESSES 24.
- Типы: CHAR 1, INT 2, SIZE_T 3, UNSIGNED 15, UNSIGNED_CHAR 17, ULONG 19, REFS 7 (массив указателей на детей),
  LMX 8, DESC 9, STRUCT 13, CHAR_PTR 14, ARRAY_OF_* 5/6/10/11/16/18/20, FOREIGN 40,
  POINTER_BASE 1024 + id (указатель @T — свой домен), UNINIT_INT 1001024, GRAPH_INT_REF / GRAPH_LMX_REF / GRAPH_REF /
  UNINIT_GRAPH_* 1001025–1001029, CELL_POINTER 1088. Отрицательный тип — неизменяемый вариант (lmx_type_base: -t → t).

Пул:
- выбор на каждое выделение — lmx_arena.lm2:lmx_arena_find_profiled:147-178 [код]. ЛИНЕЙНЫЙ проход по списку
  arena\arrays со сравнением (kind, type, profile, role) плюс проверка указательных колбэков. Ключ включает profile
  (Lmx-профиль места), поэтому пулов — (тип × профиль), а не по одному на тип;
- новый пул — lmx_pool.lm2:lmx_pool_make_profiled:419-523: один calloc на запись пула + первый чанк + контексты.
  chunk_capacity := count первого запроса (стр. 471).

Рост: lmx_pool.lm2:lmx_pool_add_chunk:116-240 [код].
- Ёмкость нового чанка = max(pool\chunk_capacity, want). Геометрического роста НЕТ.
- Значит, пул, рождённый одноячеечным take (lmx_scalar_new_physical_profiled → lmx_arena_take_profiled(count 1)),

- Каждый чанк — 4 calloc: полезная нагрузка, LmxChunk(+контексты), 2 × LmxArenaBlock — плюс lmx_arena_span →

- Для указательных и FOREIGN-пулов к LmxChunk приклеен массив LmxWalkValue по одному на ячейку (value_contexts,
  стр. 147-150): у таких ячеек уже есть внеполосная запись на ячейку.

Выдача: lmx_pool.lm2:lmx_pool_take_n:341-417 — плюс lmx_range_interval_pool (одна бисекция) на каждую выдачу, проверка
регистрации хвостового чанка.

Регистрация диапазона: lmx_range.lm2:lmx_range_add_view:169-280.
- Бисекция места, проверка перекрытия, lmx_range_reserve (рост таблицы).
- Затем СДВИГ хвоста индекса поэлементно, 12 полей на запись, O(n) — малой ценой только при вставке в конец (адреса

Размер ячейки = stride пула:

## 2. Классификация адреса — фактическая стоимость

Базовая операция — lmx_range.lm2:lmx_range_entry_at:343-366 [код].
- Двоичный поиск по отсортированному массиву LmxRange: ⌈log2 N⌉ итераций, в каждой 1–2 сравнения указателей.
- Каждая итерация зовёт lmx_arena_index_data(arena) — отдельная C-функция с проверкой arena=0 (lmx_arena.lm2:36-44),
  без кеша последнего диапазона.
- null → 0; адрес вне арены → 0.

lmx_range_cell_pool:457-482 — «живая ячейка ровно с этого адреса»:
- entry_at (бисекция);
- lmx_range_entry_chunk:405-433 — кешированный в записи чанк проверяется по chain_gen и lo; промах — проход цепочки
  чанков пула, O(чанков);
- проверки cells ≤ room, offset % stride == 0 (внутренний адрес ячейки → 0), индекс < выданных.
Итого: 1 бисекция + ~6 разыменований + 2 деления.

Построены поверх cell_pool, каждый — ОТДЕЛЬНЫЙ полный проход, без общего результата:
- lmx_range_classify:495-506 → pool\kind;
- lmx_range_type_of:508-519 → pool\type;
- lmx_range_stride:521-532;
- lmx_range_profile:663-669;
- lmx_range_pool:537-545 — делает cell_pool, затем ещё entry_at;
- lmx_pointer_pool_in:381-387 — cell_pool + 5 проверок.
lmx_domain_kind / lmx_domain_type (lmx_implements.lm2:41-47) — обёртки classify / type_of.

Элемент плотного массива классифицируется как ячейка своего backing-пула: элемент — ячейка stride = размер элемента.
Внутренний байт ячейки или поле внутри Lmx-заголовка → NONE.

Источник контекста:
- lmx_value_owned.lm2:lmx_value_cell_context:367-380 — ячейка → контекст: cell_pool + чанк;
- lmx_value_context_cell_in:389-432 — ОБРАТНО (контекст → ячейка): ЛИНЕЙНЫЙ проход по ВСЕМ записям индекса с
  lmx_range_cell_pool на каждую, O(N log N) на вызов. Зовётся из GC на каждый корень Value с referent
  (lmx_gc_graph.lm2:lmx_gc_value:65-81).

Графовые аксессоры (lmx_arena_refs.lm2) — главная стоимость обхода [код, подсчёт по тексту].
- lmx_graph_node_in:27-37 = classify + stride = 2 бисекции.
- lmx_graph_backing_cell_in:39-~90 — около 7 бисекций:
  - node_in(массив) — 2;
  - cell_pool(data), stride(data), entry_at(data) — 3;
  - classify и type_of(массив) — 2;
  - lmx_pool_chunk_at — ЛИНЕЙНЫЙ проход цепочки чанков пула детей;
  - финальный cell_pool(cell) — ещё одна.
- lmx_graph_cell_in:93-115 = backing_cell_in + classify(cell) (+ ветка FIELD_ADDRESSES: cell_pool и type_of заголовка).
- lmx_graph_value_in:222-240 = graph_cell_in + ещё cell_pool(cell).
Итого ≈ 9–11 бисекций + 1 проход цепочки чанков на ОДНО чтение слота графа.
lmx_graph_ref_struct_in = value_in + node_in (+2).

## 4. LmxWalkValue и LmxWalkPlace

LmxWalkValue (lmx.h.lm1) ≈112 Б при 8-байтовом ulong; точный размер ulong — по C-маппингу L1, не проверял.
- Поля: present, kind, type (int); ref (void*); number (int); wide (size_t); natural (unsigned); longnum (ulong);
  byte (char); model, references (Lmx*); referent (LmxWalkValue*); scalar_abi; physical_profile (Lmx*);
  source_type (void*).
- Дублирует с ячейкой: type (физический тип значения); ref (адрес для ссылок); referent (контекст ячейки-владельца);
  physical_profile (профиль пула).
- Числа хранятся в ОТДЕЛЬНЫХ полях по типам (не union): number/wide/natural/longnum/byte.

LmxWalkPlace (lmx_walk.h.lm1) 32 Б: address, storage (void*), type, descriptor (int), context (LmxWalkValue*).

Временные создаются на C-стеке почти в каждой функции (c.LmxWalkValue: temp/value/current …) и в scratch-векторах
lmx_walk_value_vector:22-~50 (вектор + дескриптор корней). Каждый живой Value регистрируется в
lmx_execution_roots_push для GC.

## 9. Числа без запуска

- [артефакт] Дамп арены R0 крошечной пробы e5_length (S/o410-probe-01/e5_length-native/run-root0.log) — 64 пула:
  - Structure-пул a0: 35 заголовков по 32 Б;
  - дочерние REFS-пулы kind 4 type 7 по 1–6 слотов каждый — их десятки (a1, a4, a6, a7, a10, a13…);
  - int-пул a9: 7 ячеек; SourceName a5: 22 строки по 72 Б.
  Число ЧАНКОВ (= диапазонов) дамп не печатает. По коду (п. 1) пулы с chunk_capacity 1 дают по диапазону на ячейку,
  так что диапазонов не меньше 64, вероятно в разы больше.
- [оценка] N диапазонов ≈ Σ чанков ≈ число одноячеечных выделений в «одноячеечных» пулах + по чанку на прочие.
  Бисекция — ⌈log2 N⌉; при N ~ 10^3–10^4 это 10–14 итераций на запрос, и ~10 запросов на одно чтение слота графа.
- Метаданные на одну 4-байтовую int-ячейку в одноячеечном пуле [оценка по раскладкам]:
  - LmxRange 96 + LmxChunk 48 + 2 × LmxArenaBlock 80 = ≈224 Б;
  - плюс накладные malloc на 4 calloc;
  - у указательной ячейки ещё +112 Б контекста.

## Оценка: что уходит при метке типа в записи, что остаётся

Перестают нуждаться в классификации, если у записи есть свой type (p->type):
- lmx_walk_value_cell / numeric_type / work_make (kind+type слота);
- domain_kind/domain_type в deref, index, value_load указательных;
- lmx_graph_node_in («это Structure?») и проверка stride;
- typeof;
- выбор приёма по типу места (receive_root, receive_cell — только тип, не допуск модели);
- обход ячеек GC по типу;
- классификация при копировании и merge;
- lmx_walk_code_in для оператора.
Главный выигрыш — graph_value_in/cell_in: сейчас ≈9–11 бисекций и проход цепочки чанков на чтение слота. С меткой —
одно разыменование слота плюс чтение type.

Остаются (общий адресный API для произвольных адресов):
- неизменяемость и запечатанные профили (lmx_range_write_exact_blocked по интервалу) — пока она привязана к диапазону;
- принадлежность арене и время жизни (owner/home: lmx_range_home, импортированные view при attach);
- GC: «чей чанк» и освобождение блоков; если единица владения останется чанком, адрес→чанк всё равно нужен;
- внутренние адреса (адрес поля внутри записи, байт массива, C-память) и внешние C-указатели: метки у них нет,
  классификация по диапазону остаётся единственной;
- обратная карта контекст→ячейка (сейчас линейная) — исчезает, если контекст живёт в самой записи;
- поиск имён (линейный, по адресу) — от метки типа не зависит, но тот же ключ-адрес.
Отдельно от метки — линейные места:
- lmx_arena_find_profiled;
- lmx_source_name_local;
- lmx_pool_chunk_at;
- lmx_value_context_cell_in;
- сдвиг индекса при вставке;
- чанки ёмкостью 1.
Это стоимость текущей реализации, которую честное сравнение должно учитывать отдельно от «тег против диапазона».
