# Ответы на действующие вопросы о языке

Сверено с документацией 2026-11-15. Ниже — актуальные редакторские ответы на вопросы
из обсуждений Fable, а не дословная запись прежних ответов исполнителя.
Номера сохранены для ссылок. Вопросы о завершённых миграциях и прежних дефектах удалены.
Норма — [семантика](../../docs/LMX_semantics.ru.md) и [грамматика](../../docs/LMX_grammar.ru.md);
готовность реализации отмечается отдельно в [плане v3](../../next_core_tasks_v3.md).

### А7. Каким именем отвечает поле после `S[i] := p`?

Числовая запись заменяет только указатель в выбранной ячейке массива. Она не переносит
имя или требование прежнего значения на новый адрес и не запускает допуск поля.
Последующий именованный путь интерпретирует текущее содержимое по таблице
«адрес → каноническое имя». Если записанный адрес именован j, он участвует в выборе
j; повторные вхождения требуют явного индекса. Произвольная запись void-указателя
сама по себе не обещает осмысленного именованного поля.

Structure и `Array<@>` используют одну операцию. В L2 индекс — вычисление смещения без
проверок length, знака или требования прежнего поля; в L3 проверяется итоговый индекс.
См. [сырой индекс](../../docs/LMX_semantics.ru.md#correspondence-stability) и
[индексацию](../../docs/L2_spec_ru.md#lowlevel-address).

### Б3. Как писать групповое позиционное присваивание?

Запись — `(a b c) := c, a, b` или `(a, b, c) := myFn()`.
Все правые значения вычисляются до первой записи; поля результата сопоставляются по позиции.
Слева стоят доступные места, а не объявления новых переменных или имена Structure/callable.
Видимость переменных и const последовательная.
[Групповое присваивание](../../docs/LMX_semantics.ru.md#group-assign),
[видимость](../../docs/LMX_semantics.ru.md#declaration-visibility).

Автор подтвердил написание в [журнале](../2026-11-10.md#no-structure-head), дословная выдержка:

> акутальность поддержки head в виде структуры получается исчезла -- мы присваиваем (a, b, c):=myFn() # правильно я понял?

### Б5. Меняется ли запись присваивания в генерируемом L1?

L1 остаётся отдельным промежуточным языком со [своей спецификацией](../../docs/L1_spec_ru.md).
Действующее правило L2/L3 о := не меняет автоматически синтаксис выпускаемого L1.
Перенос L1 следует за L2/L3 по общей инструкции проекта.

### В3. Как отличить короткую форму `head:` без аргументов от начала вертикальной формы?

Следующая строка более глубокого уровня открывает вертикальное тело.
Без неё `head:` — допустимый Frame с пустым телом, как `head()`.
`head: ()` и `head(())` содержат одно поле — пустую Structure.
[Грамматика §18](../../docs/LMX_grammar.ru.md#empty-colon).

### В4. Нужны ли дополнительные скобки для передачи Structure одним аргументом?

`s((a))` сохраняет одно поле-Structure в дереве P0. Парсер не раскрывает единственную
анонимную Structure и не подбирает группировку по сигнатуре.
Как вызываемое получает её поля, определяет общий контракт связывания, одинаковый
для написанной Structure и вычисленного результата merge.
[Грамматика §18](../../docs/LMX_grammar.ru.md#empty-colon),
[подача всей Structure](../../docs/LMX_semantics.ru.md#whole-arguments).

### Д5. Как записать поле операнда merge?

`merge(Model; (int: v 9))`. Форма ресивера объявляет поле v с требованием int.
`(v: 9)` объявляет Structure v и не заменяет это поле.
Совпавшее по имени и типу поле записывается в место модели, а новое дописывается
после её полей. Это контракт композиции, не выбор первого повторного имени.
[Композиция](../../docs/LMX_semantics.ru.md#composition).

### Е7. Как записать поле-ссылку в операнде merge?

`(@: p int @N\a)` объявляет место p с требованием int и кандидатом `@N\a`.
Действует общий плоский порядок «имя — требование — кандидат», без особого разбора merge.
[Объявляющие формы](../../docs/LMX_semantics.ru.md#receiver-args-only).

### М2. `int: big` при известном big — проверка значения или повтор объявления?

Голое имя в объявляющем аргументе задаёт место: в code повторное `int: big`
проверяет совместимость существующего места, не создавая второй локальной переменной.
Без RHS нового значения для записи нет. В data повтор остаётся отдельным физическим
вхождением имени. `int: (big)` потребляет выражение со значением big.
[Контракт ресивера](../../docs/LMX_semantics.ru.md#receiver-args-only).

### М4. Что означает ресивер с непредставимым числовым литералом?

Одноаргументная форма со значением, например `int: 342348523485629384569384`,
проверяет это значение; отказ приёма должен следовать общему контракту ресивера,
а не подмене литерала другим числом. Форма со значением возвращает принятое число
либо отказ, принимаемый catch.
[Контракт](../../docs/LMX_semantics.ru.md#receiver-args-only).

Отдельно в [M11](../../next_core_tasks_v3.md#m11) отмечен предел реализации:
литерал, который не вмещает ни один поддержанный числовой тип трансляции,
отвергается до исполнения. Этот предел не становится новым правилом языка
и не доказывает готовности пути отказа через catch.

### М5. Чем отличается `int: x 4294967296U` от проверки одного значения?

Здесь объявлено принимающее место x и написан кандидат. В data это описание поля;
в code ресивер получает кандидат, выполняет предусмотренный допуск/преобразование
и записывает результат в локальное место. Несовместимое значение не становится
допустимым из-за этой формы. Для известного при построении кандидата применима
первая часть допуска; проверки преобразования относятся к самому значению.
[Приём кандидата](../../docs/LMX_semantics.ru.md#admission),
[объявляющий контракт](../../docs/LMX_semantics.ru.md#receiver-args-only).
Ограничения понижения литералов отмечаются в M11 отдельно от нормы.

### О2. Присваивание в data считается вхождением имени?

Нет. `ptrToModel := ptrToKnownStruct` в data не исполняется и не объявляет
ptrToModel. До самой записи можно дойти числовым индексом. Вхождения имени
составляют корневые объявления этого имени, а не все упоминания или присваивания.
[Роли data/code](../../docs/LMX_semantics.ru.md#data-code-roles).

### О3. Повторное объявление Structure в data заменяет прежнее?

Нет. Оба объявления остаются отдельными вхождениями. При повторе имени
`S\field` неоднозначно; нужное вхождение выбирается через `S\[N]field`.
Это не повторное объявление локальной переменной в code.
[Имена и пути](../../docs/LMX_semantics.ru.md#fields).

### О4. Что означают `@: ptr Model: Other` и `@: ptr Model: 0`?

Вложенная форма Model: Other в аргументах ресивера — вызов Model.
Требование и кандидат задаются соседними полями: `@: ptr Model Other`,
а нулевой адрес — `@: ptr Model 0`.
Если Model — обычная Structure, её запуск не даёт результата для передачи в @.
[Объявляющие формы](../../docs/LMX_semantics.ru.md#receiver-args-only).

### О5. Как подать поля письма по имени?

`send: exit(exit_code := 7; stdout := ""; stderr := "")`.
Именованные фактические аргументы подаются через :=. Структурная форма
`exit_code: 7` среди аргументов читалась бы как вызов головы exit_code.
[Именованные аргументы](../../docs/LMX_semantics.ru.md#named-actuals).

### О8. Что означает data в code?

data — явная ссылка на данные запуска; `data\field` и `data\[N]field` идут
в исходный граф. `data := ptr` меняет эту ссылку для последующих явных путей,
но не уже выбранные локальные места namespace. `data()` запускает текущую data
над ней самой; `data(D)` — над D. Это вызовы, а не переобъявление или публикация данных.
[Особое имя data](../../docs/LMX_semantics.ru.md#ordinary-var),
[кадр](../../docs/LMX_semantics.ru.md#call-frame-20261115).

### О9. Где действуют объявления fn, sub, catch?

В обеих ролях: в data как объявления, в code как вызовы объявляющих ресиверов.
У callable одна входная data; вызов создаёт новый namespace.
Параметр args у call/fncall содержит actuals, а не отдельное описание входов.
Имена callable видны в обе стороны, переменные с указателями на callable — последовательно.
[Части вызываемого](../../docs/LMX_semantics.ru.md#method-parts),
[видимость](../../docs/LMX_semantics.ru.md#declaration-visibility).

### О10. Когда выполняются implements и test?

Первая, интерфейсная часть выполняется один раз для кандидата: при построении
чистого графа, если он известен, иначе при фактическом выборе во время исполнения.
test при построении не вызывается. При фактическом допуске во время исполнения
он составляет второй шаг; первый результат 0 прекращает проверки.
Завершённая первая часть не повторяется только из-за перехода к исполнению.

Сырая запись `S[n] := p` не является именованным допуском и не получает этих проверок.
Проверки преобразования числового значения сохраняют свой контракт.
[Допуск](../../docs/LMX_semantics.ru.md#admission),
[ответы о test](sol-answers-20261113.md).

### Р2. Как показывать ссылку на Structure при выводе графа?

Ссылка не превращается во вложенное лексическое дерево. `sys\toLmx` сохраняет выбранный
текущий граф, включая общие ссылки, циклы, имена и типы, так, чтобы его можно было
восстановить. Бесконечное раскрытие указуемого вместо ссылки этому не соответствует.
Для Thread сохраняются и таблицы его арены; произвольная Structure сама по себе
не означает сохранения всей арены.
[Контракт sys\toLmx](../../docs/LMX_semantics.ru.md#source-codec).

### Р3. Как обрабатывать ссылки и циклы при обходе и копировании?

Лексический обход и обход графа — разные задачи: ссылка не становится лексическим
ребёнком. merge копирует полный используемый граф с необходимыми ссылками и
лексическими цепочками; одна карта «источник — копия» сохраняет общие цели и циклы
для всех операндов. Обычные ссылки направляются на соответствующие копии.
Произвольные внешние изменяемые цели не остаются исходными только потому,
что они не были написаны вложенным поддеревом.

Исключения ровно те, что заданы общим контрактом: переиспользуемая native-реализация
и допустимая ветвь `independent: immutable`. При допуске уже посещённые пары
обрабатываются общим механизмом, без запрета циклов.
[Композиция](../../docs/LMX_semantics.ru.md#composition).

### Р6. Как запускается корень единицы?

Как Structure над самой собой: `call(root)`, то же `call(root root)`.
Для этого случая действуют общие роли data/code, namespace и повторные вхождения;
отдельных правил и обратной публикации локальных значений нет.
[Ресивер call](../../docs/LMX_semantics.ru.md#call-receivers).

### Р10. Как адресуются записи вызовов и управления в data?

Как Structure с именем своей головы: `data\if`, `data\f`, а при повторе —
путь с индексом вхождения. Запись не исполняется лишь от своего присутствия в data.
Имя вызываемого и графовая запись вызова — разные места: запись вызова метода
не создаёт второе объявление его имени в namespace.
[Имена и пути](../../docs/LMX_semantics.ru.md#fields),
[роли](../../docs/LMX_semantics.ru.md#data-code-roles).

### Р28. Что адресует `@x` формального или скрытого входа?

Собственную локальную ячейку namespace текущего вызова, ту же, которую читает голое x.
Запись через этот адрес не меняет источник связывания. После входа локальное место
независимо от последующей замены исходного поля; это не глубокая копия всех целей ссылок.
Явный путь `@(node\x)` или `@(data\x)` вычисляет свой операнд в исходном графе.

Если путь выбирает готовую ячейку, адресуется она; если вычисляемое объявление,
адресуется результат его исполнения. У @ нет отдельного правила продления жизни
значения или обязательного выделения в куче.
[Кадр](../../docs/LMX_semantics.ru.md#call-frame-20261115),
[вычисляемое поле](../../docs/LMX_semantics.ru.md#computed-field-address).

### Р21. Как вызывается обычная Structure по имени?

В code `S()` равнозначно `call(S S)`, `S(D)` и `S(data := D)` — `call(D S)`.
У запуска один необязательный аргумент data; он должен давать Structure.
Голова разрешается общим механизмом: ссылка на callable вызывает callable,
ссылка на обычную Structure запускает её. Число, нулевой адрес или неизвестное
имя не становятся вызываемыми. Запуск Structure результата не возвращает:
на месте фактического значения или операнда merge такая форма ошибочна.

В data `S()` объявляет пустую Structure, `S(D)` — Structure с полем D.
При запуске над собой действуют обе роли. Дополнительное объявление S может
дать повтор имени или выбрать собственную S вместо внешней; call с явными
данными и кодом использует те же правила без такого объявления.
`data()` также подчиняется общему запуску. Никакого ограничения `data = code`
для исполнения или native-компиляции нет.
[Структурные формы](../../docs/LMX_semantics.ru.md#forms-declare-or-call),
[роли data/code](../../docs/LMX_semantics.ru.md#data-code-roles).

Для явной подачи actuals предусмотрены call(args data code) и fncall(args data return code),
а также четыре сокращения из [общего контракта](../../docs/LMX_semantics.ru.md#call-receivers).
args — та же Structure поданных значений, что у обычного вызова; data описывает входы.
Интерпретатор не выделяет для этих форм отдельный исполнитель.

### Р27. Один ли парсер внутри всех скобок и что делать с потерянной скобкой?

Круглые, квадратные и фигурные скобки используют один P0 с общими правилами
уровней, комментариев, вложенных форм и трейлеров. Непарная закрывающая скобка
в разбираемом коде — ошибка; защищённый текст подчиняется своему обычному контракту.
Ошибка Mix внутри строки не делает ошибочной всю строку.
[Грамматика §14](../../docs/LMX_grammar.ru.md#bounded),
[Mix](../../docs/LMX_grammar.ru.md#mix), [ответы о парсере](parser-forms-answered-20261111.md).

### Р29. Где пишется ресивер `required` и где он действует?

Слова автора 2026-11-16 и вывод исполнителя по его поручению ([журнал](../2026-11-16.md#required-anywhere),
[вопрос и ответы](required-anywhere-answered-20261116.md)). По словам автора: `required` пишется где
угодно и в любом объявлении, как `private:`; `required: (int: a)` в заголовке и строка `required: a` в
коде — разные пути к одной проверке; возможны все сочетания (в `data` и в `code`, пометкой объявления и
строкой с именем поля) и любое число проверок одной переменной. В `data` запуска поле сначала
заполняется аргументами, и если значения ему не досталось — ошибка; в `code` проверка выполняется на
той же строке. Отдельного прохода «все `required`» нет: при входе в вызываемое нет ходов инициализации,
кроме подачи аргументов. Первое чтение исполнителя, оставлявшее только строку в коде, автор отверг.
Вывод исполнителя из слов «правила видимости `required` изменить не может»: пометка срабатывает только
там, где её объявление само действует — как входное место запуска или как достигнутая запись кода;
помеченное поле остаётся видимым и доступным по общим правилам — лексически, динамически и по явному
пути, — и тот, кто получил его по этим правилам, пометкой не проверяется; строка `required: a` не видит
переменную, объявленную ниже, и имя ветви после выхода из неё; проверка однократна.
[Ресивер `required`](../../docs/LMX_semantics.ru.md#required-receiver),
[ресивер private:](../../docs/LMX_semantics.ru.md#private-binding),
[видимость](../../docs/LMX_semantics.ru.md#declaration-visibility).

### Р30. К чему относится «все аргументы необязательны»?

Чтение исполнителя к решению автора 2026-11-16 ([слова автора](../2026-11-16.md#optional-inputs-required)),
не слова автора. Слово «все» относится к объявленным входным местам `data`: вход без значения,
которому не подано значение, вызову не отказывает и держит «T без инициализации». Правило о
неразрешённом свободном имени не меняется: динамический вход без источника по цепочке активаций
и без лексического источника по-прежнему делает вызов недопустимым. Проверка формы вызова
наличие значений у объявленных входов не проверяет; инициализацию данного поля проверяет `required`.
[Ресиверы `call` и `fncall`](../../docs/LMX_semantics.ru.md#call-receivers),
[динамические входы](../../docs/LMX_semantics.ru.md#dynamic).

### Р31. Каким отказом отказывает `required`?

Чтение исполнителя к решению автора 2026-11-16 ([слова автора](../2026-11-16.md#optional-inputs-required)),
не слова автора. В `data` запуска — отказом допуска входа при подаче аргументов, до первой записи
`code`; в `code` — отказом достигнутой записи на её строке. Точный вид отказа уточняется при
реализации и помечен в плане как OPEN ([M10](../../next_core_tasks_v3.md#m10)).
[Ресивер `required`](../../docs/LMX_semantics.ru.md#required-receiver).

### Р32. Что делает чтение входа без значения в теле?

Чтение исполнителя к решению автора 2026-11-16 ([слова автора](../2026-11-16.md#optional-inputs-required)),
не слова автора. Вход без значения и без поданного actual держит «T без инициализации»: начальное
значение не обещано, проверки эти байты не читают и не требуют ни нуля, ни случайности, ни особой
ошибки. Чтение такого входа не отказывает и не даёт обещанного значения; инициализацию проверяет
только явный `required`. Фикстура поэтому не закрепляет прочитанное значение: наблюдаемы проход
вызова, тип места `uninit:T` и значение, записанное в теле.
[Примитив, §3.2](../../docs/kernel-implementation.ru.md#primitive-storage),
[ресивер `required`](../../docs/LMX_semantics.ru.md#required-receiver).

### Р33. Возвращает ли откат построения ячейки, выданные из прежних чанков?

Решение исполнителя по ходу [M15](../../next_core_tasks_v3.md#typed-value-records), не слова автора.
Нынешний `revert` освобождает куски, присоединённые после метки, но не возвращает ячейки, выданные
после неё из уже существовавших чанков: на путях отказа `merge` и копии они остаются занятыми до
освобождения куска. Это утечка, не порча памяти. До шага6 M15 она остаётся: снимок хвостов всех
пулов с диапазонным снятием имён, связей и контекстов был бы работой на выброс. Шаг6 переводит метку
на пару «кусок, смещение», а в этапе2 откат становится усечением потока.

### Р34. Где записан признак «хранилище Structure — адресная таблица», если тип не узнаётся по адресу?

Решение исполнителя по ходу [M15](../../next_core_tasks_v3.md#typed-value-records), поправленное автором в тот же
день. Адресная таблица — приём нынешнего ядра (`lmx_graph_fields_bind`): когда Structure собрана из слотов, уже
существующих в других местах и лежащих не подряд, её `storage` указывает на блок адресов этих слотов, а не на
собственные слоты. Сегодня читатель слота узнаёт это классификацией адреса хранилища (пул FIELD_ADDRESSES).
Плотное хранилище кодов не несёт, поэтому признак переносится в запись заголовка: Structure с адресной таблицей —
отдельный код типа, и операция ядра, меняющая форму хранилища, в том же действии пишет соответствующий код.

Первый вариант этого ответа вводил отдельный бит в слове кода и правило «код записи после создания не меняется».
Автор: «зачем тебе снимать и выставлять биты если есть 4 млрд кодов для 4 млрд типов? … Тип то просто любой
удобный тип». Бит, маски и правило сняты: различие, нужное ядру, выражается отдельным кодом типа. `sys\typeof`
для такой Structure отвечает кодом обычной через общий перевод «код → тип»: форма хранилища программе не видна.
Нужна ли адресная таблица после норм M14 о независимых локалах без write-back — отдельный вопрос упрощения, не решён.
