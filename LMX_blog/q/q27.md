# Q27. Пара исполнения code/data: исходное предложение и выбор автора

Исходное предложение принёс автор 2026-09-25 (файл `ыыы.md`, здесь дословно); реплики автора — `LMX_blog/2026-09-25.md`; принятая формулировка — `next_core_tasks.md` §3 «Пара исполнения code/data», спеки L2 §10/§11, L3 §11/§12, `CORE.md` §3.

## Исходное предложение (дословно)

Да, идея выглядит рабочей именно потому, что **не отменяет принцип “любая Structure может быть чем угодно”, а разделяет роли только на момент исполнения**.

Я бы сначала вообще не придумывал новый синтаксис. У вас уже есть почти идеальная синтаксическая граница: **Frame = head + body**. При вызове это естественно читается как:

```text
f(a b)
```

где после разрешения:

```text
code graph = f
data graph = (a b)
```

То есть не `f` «является функцией по типу», а **в этой операции Structure `f` поставлена в позицию исполняемого графа, а `(a b)` — в позицию входного графа**.

Это очень хорошо продолжает старый принцип receiving expression:

```text
Structure сама по себе
    ≠ код
    ≠ данные

роль появляется при потреблении:

execute(CodeGraph, DataGraph)
```

И та же Structure в другом месте совершенно законно будет данными:

```text
save: f
merge: f other
send: f
```

Никакого флага `is_code`, отдельного класса MethodStructure или другого мусора не требуется.

### Я бы физическую модель сделал предельно тупой

Исполнение получает ровно:

```text
execute(code, data)
```

где оба:

```c
Lmx *
```

И всё.

`code` — Structure, которую сейчас интерпретируют/транслированный метод которой сейчас запускают.

`data` — Structure, над которой это исполнение сейчас работает: собственные поля/состояние/фактическая конкретизация этого кода.

Например после вашего:

```text
merge(y: 5; add)
```

может оставаться:

```text
code:
    add
        signature
        body: x + y

data:
    y: 5
```

и следующий `merge` может создать **новый data graph при том же code graph**.

Это как раз убирает необходимость физически изображать:

```text
callable Structure
    method
    body
    own fields
    signature
    ещё что-нибудь
```

как один специальный мутант.

### Причём ваши Haskell-примеры от этого становятся даже чище

Исходное:

```text
fn: add (int: x; int: y) int
return: x + y
```

может дать некоторый `code(add)`.

Дальше:

```text
add5: merge(y: 5; add)
```

не обязан вообще трогать тело.

Получается:

```text
add:
    Code = Cadd
    Data = Dadd

add5:
    Code = Cadd
    Data = merge(Dadd, { y: 5 })
```

Разница сигнатур тоже может быть частью структурного результата `merge`, но **машинное тело остаётся одним**.

Это очень близко к тому, что мы обнаружили у Haskell closure/PAP, только без специального объекта PAP:

```text
Haskell:
    code pointer + environment

LMX:
    code graph + data graph
```

При этом оба компонента остаются обычными LMX Structures.

## А самый приятный вариант синтаксиса — вообще ничего не добавлять

Например:

```text
add5: 10
```

После resolution известно, что `add5` сейчас используется как receiving/executable expression.

Runtime/compiled call уже имеет:

```text
execute(
    code(add5),
    data(add5 + actual arguments)
)
```

Но **в source никакого `execute`, `code`, `data` нет**.

Это мне кажется лучше всего, потому что иначе получится странно: вы сначала говорите «Structure не имеет врождённой роли», а потом вводите:

```text
code: foo
data: bar
```

и постепенно эти слова начнут восприниматься как два вида Structure.

Я бы оставил их только как термины спецификации:

> **Execution pair** consists of exactly two Structure roots: the executable Structure selected as the code graph and the Structure supplied as its data graph. `code` and `data` denote roles in one execution, not kinds, qualifiers, storage classes, or persistent properties of a Structure.

### Где всё-таки понадобится явная форма

Только когда **оба графа являются вычисленными значениями**, и обычная head-position уже не говорит, какой из них исполнять.

Например:

```text
someCode: selectCode(...)
someData: makeData(...)
```

и хочется выполнить первый над вторым.

Вот здесь можно иметь один универсальный receiver, условно:

```text
execute: someCode someData
```

или:

```text
run: someCode someData
```

Но это не новая модель вызова, а просто **явная запись той же операции**, когда синтаксически нельзя использовать обычное:

```text
someCode(someData)
```

Хотя я бы сначала проверил, нельзя ли **вообще обойтись последним вариантом**. Если head может быть не только статическим именем, но и выражением/ссылкой на Structure, то:

```text
someCode(someData)
```

уже однозначно означает:

```text
execute(code = value(someCode),
        data = value(someData))
```

И специального `execute:` не требуется вообще.

---

Мне кажется, здесь может обнаружиться очень полезное упрощение ядра:

**раньше**

```text
Structure
    parent
    callable descriptor
        method
        signature
    body
    own state
    ...
```

**после разделения**

```text
execution:
    Lmx *code
    Lmx *data
```

А всё остальное — свойства самих этих двух обычных графов и результат resolution.

И даже `node` становится концептуально чище: надо только точно решить, **какой из двух графов является его исходной точкой**. Скорее всего это и есть главный вопрос, который надо проговорить с Fable до реализации, потому что именно тут очень легко снова получить скрытую третью сущность вроде `self/environment/context`.

Я бы жёстко поставил ограничение:

> **Никакого третьего “callable context graph”. Если для выполнения чего-либо недостаточно `code` и `data` плюс обычной машинной activation с аргументами/locals, значит надо сначала выяснить, почему.**

Мне кажется, именно это может вычистить значительную часть нынешних костылей.

## Уточнение автора: выбор из предложенных вариантов (2026-09-25)

Вопрос предложения «какой из двух графов — исходная точка `node`» автор закрыл выбором варианта fable (дословно из чата, выбранный текст):

```text
данные вкладываются так же, как код. Экземпляр данных вызываемого создаётся полем данных лексического родителя, в слоте, отвечающем этому callable (как сейчас occurrence метода — поле юнита). Тогда node\x = data\parent\x — статическая цепочка Pascal'я, но это цепочка parent графа данных, ничего третьего. Побочный подарок: слот родителя держит экземпляр последней активации → M\x снаружи и липкие фикстуры -67 работают, а «копия на входе / запись на выходе» (21.5/21.6) становится «свежий экземпляр в слот» — без dirty и без перекладывания байтов. Рекурсия: каждая активация — свой экземпляр, слот показывает последний.
```

Явный receiver `execute(code, data)` не вводится: голова — код, аргумент — данные; вычисленный код связывается и вызывается общим правилом. Q27.1 (результат) снят автором: `return` — оператор кода, поля результата в данных нет; результат — обычный возврат машинной активации (аргументы/локалы/возврат); формалы — аргументы машинной активации, полем данных аргумент становится по правилу L3 §12 или связыванием через merge.
