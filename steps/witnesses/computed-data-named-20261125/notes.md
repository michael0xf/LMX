# Вычисляемый производитель с написанным именем в собственных данных: чтение достигает объявления, 2026-11-25

Строка регрессии `computed_data_named` (pin `0 1 0`) записана в плане 29.3 (д5) как дефект ядра: отказ
`lmx_graph_receiver_bind` помечается −2 и глотается, имя не замыкается. Трасса показала другое: binder отвечает −1 по
своему контракту, а обход не достигает объявления — у имени с написанным именем нет свободной строки кадра, и чтение
заканчивается подготовкой письменных объявлений. Интерпретатор отвечал 3. Исправление — два места в `lmx_graph_run.lm2`
(кандидат C по решению Sol и Astra): чтение голого имени достигает записи в собственных данных и применяет её одним
применением, а список кандидатов вызова считает уровень с неприменённой записью написанного имени ближайшим. Голый вызов
`local(a := 3)` даёт 9. Второе поле строки — прежняя форма `fncall(int; outer\data\local)` — не менялось: fncall над
построенным callable исполняет его самого (решение автора 2026-11-16). Строка сохранена как устаревший свидетель с
историческим ожиданием 9/6; добавлены семь постоянных строк контроля с ожиданиями, выведенными из нормы до прогона.

## Решения

Sol и Astra: `CODER-D5-CAUSE-20261125-01-SHADOW-CONTROL`, `CODER-D5-CAUSE-20261125-01-ASTRA-ANSWER`,
`CODER-D5-CANDC-20261125-01-ANSWER`.

- Кандидат A — свободная строка кадра для записи-производителя в `lmx_graph_work_capture_context` — отклонён до
  приёмки по теневым контролям: внешнее одноимённое готовое значение затеняет собственное объявление (измерено на
  кандидате: внешний готовый `fn: local` — 5, корневое место `int: local 5` — 8, место `int: local 77` у вызывающего — 8).
- Кандидат B — применение в `lmx_graph_binding_source_read` — отклонён: явный путь ничего не исполняет
  (`#path-reads-no-execution`).
- Кандидат C принят. Исходная ветка DATA в `lmx_graph_work_capture_context` сохранена. Достижение — только в чтении
  голого имени, в собственном кадре, по выбранной записи. Прежний `lmx_graph_data_reach_next` остаётся для имени, которое
  неизвестно до вычисления. Порядок смешанных безымянных форм не перестраивался; подменённые DATA не расширены.
- Для реального вызова: сначала ближайший видимый уровень с учётом написанного имени, затем штатный отбор кандидатов
  этого уровня; приоритет видимого ближнего CODE сохранён. Чистые запросы `lmx_graph_call_candidates` и запросы эмиттера
  не исполняют `lmx_graph_fn_apply`.
- Приёмка компонента ограничена: голый вызов достигает 9; затенение — три контроля; точные отказы — два контроля.
  Результаты пути и fncall — отдельные наблюдения, не принятая часть д5.
- `computed_data_named` сохраняется с историческим ожиданием 9/6; прежний `by_path` не заменяется вызовом внутреннего
  `\code` ради зелёного.
- В чистом запросе сначала фильтр по написанному имени, затем вопрос о построении: запрос построения обходит строки
  пространства.

## Норма

- Видимость объявлений (`provenance/semantics-book.md:3210`, #declaration-visibility): имена именованных Structure и
  callable видимы в обоих направлениях; правило управляет и разрешением головы вызова, и прочими употреблениями имени.
- Там же (`:3214`): вызов создаёт новое пространство имён; подготовка собирает корневые объявления данных и кода и не
  исполняет заблаговременно начальные значения вычисляемых мест; объявление вложенного уровня создаёт своё место и
  затеняет внешнее с тем же именем. `:3216`: описание callable — данные с общими правилами видимости.
- Отбор объявления по вызову (`:3759`, `:3767`, #declaration-selection): имя и его видимые объявления разрешаются
  обычным образом; неиспользуемое вычисляемое значение по умолчанию не исполняется ради перечисления кандидатов.
- Кадр вызова (`:4482`, `:4484`, `:4486`, #call-frame-20261115): вычисляемое объявление хранит свой записанный код, и
  отдельной входной фазы, которая его исполняет, нет; неиспользуемое вычисляемое поле входных данных не исполняется;
  локальное присваивание собственному месту не пишет обратно; чтение вычисляемого места голым именем — работа вызова.
- Явный путь (`:4491–4493`, #path-reads-no-execution): чтение вычисляемого объявления по явному пути ничего не исполняет.
- Журнал (`LMX_blog/2026-11-09.md:27`): «мы в любой момент можем подставить заготовленную структуру ресиверу fn и это
  будет объявлением функции в namespace».
- Журнал 2026-11-16, раздел `call(D s)` (для отдельного наблюдения): ресивер запуска не выбирает часть внутри поданной
  Structure.
- Словарь ответов интерпретатора (`lmx_graph_run.lm2:2510–2515`): 3 — неизвестное имя; 4 — запись отказана; 5 —
  оператор, который этот срез не исполняет (значение, которое формал не принимает).

## Причина по трассе

Номера строк — `lmx_graph_run.lm2` на `dd76729c9` (до правки). Протоколы — `CF/d3-01/dbg/gdb.log`,
`CF/d3-01/dbg/gdb-d5b.log`; gdb, отладочный graph producer комплекта `coder-c99x`.

1. Для `fn: local prepared` binder при evaluate = 0 выбирает четвёртую форму договора fn — `(name parts)`
   (`lmx_graph_receivers_open`, `:8830`). `lmx_graph_bind_formals` (`:3123–3187`) связывает по позиции и рода
   фактического не смотрит. `lmx_graph_receiver_bind` (`:9223–9227`): формал `parts` — Structure, фактический — слово, не
   письменная группа; ответ −1 ("an actual needs evaluation"). `lmx_graph_space_declare` (`:9463–9471`) возвращает −1,
   `lmx_graph_space_declarations_part` (`:9501–9502`) глотает его по контракту: применить там, где обход достигнет записи.
   Запись плана о пометке −2 неточна.
2. Запись стоит в части DATA; `lmx_graph_block_body` применяет записи только тела (`:5011–5013`).
3. Второй путь — достижение чтением: `lmx_graph_select_binding` (`:2647–2655`) зовёт `lmx_graph_data_reach_next`
   (`:9603–9626`), а та — `lmx_graph_fn_apply`, но только при свободной строке кадра (`row\cell = 0`, `row\slot = −1`).
4. У имени `local` строки нет: `lmx_graph_work_open_row` (`:1297–1298`) для записи fn/sub строку не открывает;
   `lmx_graph_work_capture_context` (`:820–824`) видит в реестре данных одну запись имени — именованный Lmx с головой
   `fn` — и отвечает 0 без строки. Имя без написанного имени (`fn: prepared`) записи в реестре не имеет, и строку
   открывает `lmx_graph_work_pending` (`:573–614`) — асимметрия.
5. Чтение `local` в `return: local(a := 3)`: `lmx_graph_input_row` отвечает 0; `lmx_graph_binding_source_read`
   (`:2339–2357`, prepare = 1) зовёт только `lmx_graph_space_declarations`; `lmx_graph_application_head` (`:6251–6252`)
   отвечает 3. Образы native и forced идут теми же функциями ядра: выход 1.

## Что изменено

`selfbuild/src/l2src/lmx_graph_run.lm2`:

- `lmx_graph_select_binding`, блок реестра данных активации: после `lmx_graph_binding_read` с ответом 0 и пустым
  значением — только при prepare ≠ 0, dynamic = 0 и данных кадра, равных собственным данным callable, — запись
  выбранного слота есть fn или sub с `lmx_graph_fn_decl_name = name`: `lmx_graph_fn_apply(g, data, at)`; отказ
  применения — ответ чтения; после успеха значение берёт `lmx_graph_binding_method`.
- `lmx_graph_call_candidates`: неприменённая запись написанного имени в данных callable (после того как его блок code не
  дал кандидатов) останавливает обход уровней наружу; кандидатов нет, вызов читает голову как прежде.
- Новый чистый запрос `lmx_graph_fn_pending`: запись fn или sub с этим написанным именем среди полей блока, ещё не
  построенная (`lmx_graph_binding_method = 0`).

Эмиттер не менялся: на переводе `lmx_graph_call_selects` задаёт тот же чистый вопрос, отобранный вызов не эмитится, образ
читает голову через `lmx_graph_application_head` и приходит в то же чтение.

## Строка computed_data_named — устаревший свидетель

Источник, pin `0 1 0` и ожидание 9/6 сохранены. На новом комплекте интерпретатор отвечает 4 (на HEAD 3). Голый вызов
достигает результата (`lmx_graph_place_store_int(number = 9)` в трассе принятого комплекта, `CF/d5-02/dbg`,
`gdbc-final-row.log`), затем корневое поле
`int: by_path fncall(int; outer\data\local)` отказывает 4. Место отказа: `lmx_graph_step` читает `outer\data\local` через
`lmx_graph_binding_source_read` — построенный callable, без применения; `lmx_graph_launch_value` (`:7018–7019`,
`:7062` на HEAD) подаёт его как code, data и body — дескриптор исполняется сам, `lmx_graph_work_open_parts` открывает
строку его поля `return`, `lmx_graph_work_snapshot` отвечает 4. Это правило автора 2026-11-16 (та же форма, что д3).

Отдельные наблюдения (не принятая часть д5; программы и ожидания — `CF/d5-01/pair/NORM-BEFORE-RUN-Q.md`, прогоны —
`CF/d5-02/q`). Одно явное чтение по пути не строит callable: `fncall(int; outer\data\local)` до всякого голого вызова
(`q3_legacy_path_before`) отвечает 3 в трёх маршрутах, `D\here` 0 — `lmx_graph_step` через `lmx_graph_binding_source_read` не
получает значения, применения нет; после голого вызова та же форма отвечает 4 (поле строки выше). Прежние 6 по пути штатной
формой не получены: моя проба `fncall(int; outer\data\local\data; outer\data\local\code)` оказалась неверной — три
позиционных операнда `fncall` связываются с формалами `[data, return, code]` (`lmx_graph_receivers_open`), и `int` попал в
`data`: ответ 3 на первом операнде (трасса `CF/d5-02/dbg`, `gdbc-q1c.log`); кроме того, у построенного callable часть кода
безымянна (в трассе голого вызова `body` без имени), так что пути `\code` к ней нет.
