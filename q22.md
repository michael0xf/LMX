# Q22. `offset` и метод, объявленный ВНЕ Structure (`A: fn: M`)

Состояние: 2026-09-24, открыт (Opus -154, перед коммитом 1; Grok -153 ещё не на main).

## Измерено

Сегодня поле `A: fn: M` в Structure — **ссылка** на вхождение метода `M`, объявленного на уровне unit (kind 4, `unit_base + mi`); методов, объявленных внутри Structure, транслятор пока не строит. Лексический родитель `M` — unit, и `node\tag` в теле `M` разрешён в раскладке **unit** (индекс j по unit). Свидетель `q20-next.md` §2 (`R\M()` = 7) проходит только потому, что `tag` стоит под индексом 1 и в unit, и в `A` — совпадение раскладок.

## Минимальная программа (раскладки не совпадают)

```text
A:
    fn: M
    size_t: tag 7U
end: A

size_t: other 5U
size_t: tag 3U

fn: M () size_t
    return: node\tag
end: M

R: merge: A
return: R\M()
```

`tag` в unit — индекс 2 (`other`, `tag`), в `A` — индекс 1 (`M`, `tag`); `R` = {копия M, tag} — два слота.

## Измерено на интегрированном дереве (`5214386` = main + Grok -153, транслятор без коммита 1 -154)

- Программа выше: **entry 90** до и после -153 — `t1` ни 3, ни 7: `M` читает `node\tag` по индексу 2 (раскладка unit) из двухслотного `R` → мусор, без X1 (D-33). Значит `node` копии = `R` (parent переписан), чтение I как реализовано.
- Программа `q20-next.md` §2 (`R: merge: A`, `Q: merge: B A`; проверяет 3): до -153 — entry 81 (`R\M()` = 7, совпадение раскладок); после -153 — **X1 «merge result check 78»**: COW-клон дескриптора для callable во ВТОРОМ операнде ломает эмитируемый транслятором инвариант «дескриптор разделяется по адресу» (D-30, Opus -154 к.1).

Примечание к моей формулировке в «Чтении II»: план -154 ожидал `R\M()` = 7 (чтение I), а программа q20-next §2 проверяет 3 (чтение II) — противоречие в моих же артефактах; ответ Q22 снимает его.

## Чтения

- **I (правило как записано: `node, offset + j`, j из лексического родителя M = unit):** `R\M()` читает `R[0 + 2]` — за пределами `R` → X1-abort. Правило точно только когда лексический родитель метода — сам операнд, т.е. метод **объявлен внутри** Structure (`A: fn: M () size_t … end` внутри тела `A`, уровень L3). Для ссылки на внешний метод оно неверно по построению.
- **II (ссылка на внешний метод остаётся ссылкой):** `A: fn: M` — общая ссылка на вхождение unit-метода (книга: «ссылки на общие методы — терминалы своих контрактов»); merge её **не копирует** и `parent` не переписывает — `node` для вызова остаётся лексическим родителем `M` (unit). Тогда `R\M()` = 3 (tag unit'а), `Q\M()` = 3; ожидание `q20-next.md` §2 (= 7) было неверным. `offset` нужен только методам, объявленным внутри Structure (и там точен: j — индекс в раскладке самой Structure). makeAdder: `addN` объявлен внутри `makeAdder` → возвращаемая Structure строится с раскладкой тела `makeAdder` (используемые значения на своих индексах, остальные слоты пусты) — `offset + j` точен.
- **III (статический отказ):** как I, но транслятор отказывает `node\x` в методе, на который ссылается поле операнда merge, если индекс `x` в раскладке операнда не совпадает с индексом в лексическом родителе (проверяемо статически для каждого `fn: M`-поля). Пинит совпадение раскладок как правило — сомнительно.

## Рекомендация координатора

**II**: «метод видит поля своего лексического родителя» — единственная универсальная формулировка; `A: fn: M` — ссылка, а не переезд метода в `A`. Метод, которому нужны поля Structure, объявляется внутри неё (L3-Structure с методом — как раз то, что интерпретируется по новым правилам). Следствие для -154: коммит 1 (offset в прологе) применяется только к вхождениям, чей `LmxCallable` лежит в теле Structure; коммит 2 (`merged\x` = последний) не зависит от этого и идёт сейчас.

Вопрос автору: **II?** Если нет — какое чтение, и что должен вернуть `R\M()` в программе выше.

## Q22.2. Область правила «неуточнённое имя = последнее вхождение»

Ваша формулировка была про merge: «merged\field означает merged\[lastIndex]field». В книгу (§fields, §10, §composition, CORE §3.1; `7e1ba7c`) я записал её **общим** правилом для всех повторных имён. Opus в -154 к.2 (`2fe2dcc`) реализовал её **только для результатов merge** (`R\x` = последнее, `R\[N]x` — по порядку операндов); для повторных объявлений одного имени в теле метода (`test\[N]arg`, Sonnet -146) неуточнённый `test\arg` по-прежнему `[0]`.

Минимальная программа:

```text
fn: test () int
    int: arg 1
    int: arg 2
    return: 0
end: test

test()
return: test\arg
```

- **A (общее правило, как в книге):** `test\arg` = 2 (последнее вхождение); `test\[0]arg` = 1.
- **B (только merge):** `test\arg` = 1 (первое, как сегодня); последнее — только в результатах merge. Тогда книгу надо сузить обратно.

Вопрос: **A** (одно правило на все повторные имена) или **B**?
