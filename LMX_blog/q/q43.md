# Q43. Ресивер `table` над обыкновенными Structure: как пишется строка таблицы

Состояние: 2026-09-27 открыт (Opus; уточнение к ответу Q41, `LMX_blog/2026-09-27.md`); в тот же день отвечен
автором в чате Opus, с двумя дополнениями через несколько минут. Дословно — `LMX_blog/2026-09-27.md`, «Q43: строка таблицы».

## Факт

Ответ Q41: «ресивер table должен потреблять обыкновенные структуры аргументами (ничего не парсить специально для
table row и так далее!!!!)».

Сегодня (`convert.lm2`, как в `lingvamyxa_prev`) строки пишутся строками атомов:

```text
table:
    source
    name: `primitive.convert`
    columns: (class: from) (class: to) (categoryFlag: forbidden) (@: char kind) (@: char receiver) (@: char impl)
    rows:
             int       int        0  identity  None                         "convert_impl.lm2"
             size_t    int        0  sign      lm_stg_convert_size_t_int    "convert_impl.lm2"
```

P0 делает из `rows:` одну Structure из всех атомов подряд (для двух строк — 12 полей): граница строки есть только в
раскладке текста, в дереве её нет. Поэтому транслятор режет атомы по числу столбцов — это и есть «специальный разбор
строки таблицы» (`l2_convert_walk`, и прежний `lm_registry_source_table_from_frame` в `lingvamyxa_prev` — тоже).

## Вопрос

Как пишется строка, чтобы она была обыкновенной Structure?

1. Каждая строка — Structure в скобках, поля по порядку столбцов `columns:`:
   `(size_t int 0 sign lm_stg_convert_size_t_int "convert_impl.lm2")`.
2. Каждая строка — Structure с именованными полями, `columns:` не нужен:
   `(from: size_t; to: int; forbidden: 0; kind: sign; receiver: lm_stg_convert_size_t_int; impl: "convert_impl.lm2")`.
3. Иначе.

## Предложение Opus

1 — вид таблицы сохраняется (столбцы и строки как в `lingvamyxa_prev`), строка — обыкновенная Structure, ресивер берёт
её поля по номеру столбца, имя столбца — из `columns:`.

## Ответ автора (2026-09-27)

Дословно — `LMX_blog/2026-09-27.md`. Как прочитано (Opus; при расхождении действует цитата):

1. Строка не пишется ни одним из трёх способов вопроса: таблица остаётся как есть. `rows:` потребляет не строки, а
   цепочку — и (дополнение) не атомов, а **аргументов**: ячейка может быть Structure. Это стандартный механизм, как
   везде в языке, без исключений: `columns:` — список типизированных формалов (как у вызова), `rows:` — цепочка
   фактических аргументов, и потребитель режет её на строки, потому что число столбцов знает из `columns:`; каждая
   строка — N аргументов к этим N формалам. Это не «специальный разбор строки таблицы», запрещённый Q41.
   Второе дополнение обобщает: ничего не подразумевать; у ресивера есть аргументы — это общий вид; каждый аргумент
   может быть атомом, Structure и даже массивом, и всё идёт через общие ворота (то же связывание аргументов, что у
   любого вызова), без особого пути для таблицы.
2. «Проверьте парсер» — проверено (printTree копии парсера песочницы, скретчпад Opus `forms/cv_head`): заголовок
   `convert.lm2` с двумя строками даёт кадр `rows` с телом из 12 атомов подряд — границ строк в дереве нет;
   `columns` — Structure из шести полей, каждое — Structure с одним кадром-формалом (`class: from`, …, `@: char impl`).
3. Для плана: чтение B2 (`l2_convert_columns` — имена столбцов из `columns:`, `l2_convert_keep` — ячейка по номеру
   в цепочке, строка каждые N ячеек) режет цепочку так же, но ячейкой считает только атом: не-атом в `rows:`
   `l2_convert_walk` обходит рекурсивно и ячейкой не засчитывает — ячейка-Structure молча выпадает из разметки
   строк (дальше — отказ «not whole rows» или сдвиг). Это против дополнения; у `convert.lm2` сегодня все ячейки —
   атомы, так что поведение на ней не меняется. Ресивер `table` берёт ячейки как аргументы — атом, Structure или
   массив — и привязывает их к формалам столбцов через общие ворота аргументов; переходным в B2 остаётся и это, и обход одной таблицы
   (`convert.lm2`) вместо ресивера для любой (`primitive.description`, B1).
