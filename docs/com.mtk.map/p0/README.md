## 1. Основание в реальных исходниках

В [p0_parser.lm2](../../../selfbuild/src/l2src/p0_parser.lm2) уже существуют:

| Точка | Что уже есть | Что добавить при интеграции |
| --- | --- | --- |
| `lm_p0_record_mix_mark` | MIX-флаг, исходный byte span, `lm_p0_parse_nested` для содержимого | Прямой Cursor, Var и ссылка на отдельный документ содержимого. |
| `lm_p0_record_string_mark` | Отдельный MIX-узел в `atom_node.marks`, `atom_char`, тихое отклонение неправильной метки | Сохранить существующую позицию; привязать к документу строкового overlay и к исходному byte span. |
| `lm_p0_parse_nested` | Локальный корень и тот же основной парсер | Передавать ограниченный источник и local document identity; не запускать альтернативную грамматику. |
| `lm_p0_parse_stream` | Indent stack, form stack, pending delimiter, pending MIX | Выделить сохраняемое continuation-state и общий вход продолжения. |
| `lm_p0_probe_*` | Наблюдение границ и позиции возврата | Использовать для проверки новых hooks; наблюдение само по себе не является инкрементальным API. |
| `lm_p0_parse_bytes_observed` | Копирование всего буфера, создание и замораживание нового дерева | Оставить как обычный полный вход; общий алгоритм также должен читать Cursor-source и продолжать с checkpoint. |

В этом архиве нет готового `lmxtool`/P0 executable и части bootstrap-заголовков,
на которые ссылаются исходники. Поэтому новые hooks и LMX-примеры имеют
production-статус **NOT_RUN / REQUIRE_IMPLEMENTATION**. Старые parser goldens
служат основаниями ожидаемого результата, а не расписками нового запуска.

Сохраняется **один общий парсер с подпарсером `[]`, вызывающим основной,
и один общий механизм группировки**. Подпарсер активизируется от `[`;
форма `[op` без пробела закреплена как вход в квадратную операторную
грамматику. Он понимает также `var[arg:arg2:arg3]`. Обнаружив начало
выражения либо `{...}`, он передаёт разбор основному парсеру, не разбирает
внутренний текст `{...}` и не пытается самостоятельно найти закрытие
выражения или фигурной области. Основной парсер возвращает управление
с точной позицией продолжения. Сохранённое состояние и новый Cursor-reader
должны обслуживать этот общий код; отдельные пути группировки удаляются.
Это нормативный договор интеграции, а не утверждение о готовности новых
hooks в приложенном selfbuild.

## 2. Владение и три разных отношения

Для первого рабочего профиля один L3 Thread владеет изменяемым MIX-документом,
его Cursor/Tag/Var, привязками и P0. P0 — модуль этого владельца. UI, редакторы
и агенты присылают ему целую операцию через обычный `post`. У разных документов
могут быть разные владельцы и параллельные turns. Внутри одного владельца
прямые ссылки не требуют сериализации, цифрового object registry или mutex
вокруг каждого обращения.

`Message` не вводит блокировку потока и не создаёт взаимного ожидания.
В LMX-части `synchronized` не используется: этот оператор остаётся
низкоуровневому L2. Уведомление P0 и ответ представлены обычными `post` /
`answer`; обработчики заканчивают свой turn, сохраняя данные протокола.
Ни завершение, ни обработка ошибки не ждут ответного Message синхронно.

Различать:

1. Дерево размещения MIX — страницы и ветви, включая неодинаковую глубину.
2. Дерево P0 — синтаксические узлы, поля, Frames и локальные корни документов.
3. Overlay MIX — Var и перекрывающиеся интервалы Tag. Он не становится деревом
   P0 и не обязан иметь XML-вложенность.

Каждый узел P0 получает ссылку `sourceBinding`. Binding удерживает реальные
`sourceBegin`, `sourceEnd` и `sourceTag`; Cursor может ссылаться обратно на узел.
Это обычные данные интеграции в том же owner, не второе дерево программы.
Нативный адаптер должен зарегистрировать эти ссылки в действующих корнях и
сохранять их lifetime. Публикуемый синтаксический payload и изменяемые исходные
якоря имеют разные договоры: физическое замораживание P0 arena не должно
молчаливо замораживать живой Cursor. Вставить binding до freeze; изменяемую
служебную часть держать в обычной owner-арене и явно описать удержание.

При вынесении разбора в отдельный Thread передаются immutable snapshots и
версионированные результаты. Живой изменяемый Cursor, Tag или P0 pointer через
чужую арену не передаётся. Прямые ссылки остаются у владельца документа.

У журнала изменений два явных профиля. В автономном `P0MixOpen` P0 —
единственный потребитель и подтверждает очередь сам. При подключении к
общему `MapDocumentMessage` через `P0MixSubscribe` включается
`journalExclusive=0`: P0 возвращает `MapNoticeAck`, а общий владелец удаляет
историю только до минимальной подтверждённой ревизии всех подписчиков.
P0 не может своим подтверждением удалить события, ещё нужные UI или агенту.
Общие правки в этом профиле проходят через `MapOwnerApply` и его публикацию;
однобайтовый автономный helper проверяет профиль перед изменением.

## 3. Первичная загрузка — один источник и одновременное построение

Общий P0 получает чтение из `P0MixReader`. При первом чтении нового фрагмента
reader добавляет эти же байты в MIX и отдаёт их парсеру. При возврате к уже
прочитанному месту используется сохранённый диапазон. Заполнение MIX и
построение P0 идут совместно; повторный разбор всего готового текста для
расстановки меток не нужен.

Вход `sourceBytes` — вектор `[]@` скалярных byte records из
поля `units` результата `MapBytes\fromText` либо проверенного `MapBytes\view`.
При добавлении каждый байт проверяется на диапазон 0–255 и получает
собственный record в документе. Изменение исходного вектора после открытия
не изменяет MIX в обход журнала.
`document.p0Source=1` распространяет тот же договор на все последующие
общие операции storage: весь payload проверяется до удаления старого
диапазона, каждый byte record копируется. `MapOwnerApply`, Cursor и
MapSpan используют этот общий admission. Операции `clearBody/wholeDelete`
для такого документа отказывают до изменения и направляют к source splice
владельца; служебные P0 Tag удаляет только parser retire/discard.

Hooks начала/конца узла получают точную позицию общего scanner и создают
Cursor, пока позиция доступна, затем прикрепляют их к создаваемому узлу.
Последовательный reader удерживает собственный Cursor и не ищет каждый байт
заново от начала документа. Полный byte-offset lookup допустим для отдельного
скачка, а не как алгоритм последовательного чтения.
Перед каждым новым source-resume числовой cache `nextOffset` сбрасывается:
Cursor уже перемещён правками, а прежнее число само не обновилось.
Первое чтение один раз восстанавливает положение, последующие снова
используют последовательный Cursor.

На загрузке один source batch имеет origin=1; P0 metadata, созданные внутри
него, принадлежат этому же batch. После commit P0 подтверждает принятую
ревизию. При последующем обновлении derived metadata использует origin=2:
это bookkeeping, без новой source revision и без уведомления самого себя.
Вставка/удаление исходного текста в origin=2 запрещены.

Начальное открытие фиксируется metadata-событием с identity документа:
поэтому даже пустой источник имеет однозначную первую ревизию. Она передана
основному P0 через `dirty.revision` до разбора; после commit проверяется
точное совпадение. Все ссылки на hooks явно передаются в `session.sink`.
Синтаксическая диагностика — обычный результат: исходник дочитывается и
сохраняется целиком. Исключение при создании или отказ адаптера прерывают
конструирование ещё не опубликованной session; cleanup не пытается
добавить оставшийся текст или повторить неудачный commit.

## 4. Обычная правка и инкрементальный разбор

`MapTree.begin/commit` объединяет изменения одного owner в batch. Это граница
уведомления, а не обещание rollback при исключении: операция предварительно
проверяет входы и необходимые ресурсы; частичная фактическая правка должна
получить честный результат и запись, а не исчезнуть из истории.

`MapChange` хранит `beforeRevision`, `revision` и упорядоченный список edits.
Координаты каждого edit относятся к состоянию непосредственно перед этим
edit. Нельзя брать min/max координат разных промежуточных состояний.
[incremental.lmx](incremental.lmx) последовательно переводит dirty interval
через edits и выбирает предшествующий checkpoint.

В рабочем пути:

1. Cursor-правка обновляет только затронутые страницы и их реальные якоря.
2. После commit владелец отправляет обычный Message о наличии правок своему
   обработчику P0. Очередь изменений сохраняется до подтверждения.
3. Обработчик проверяет непрерывность ревизий и вычисляет область изменений.
   Неизвестный пропуск не объявляется обработанным.
4. Выбирается checkpoint **строго перед** изменённой границей, включая
   предшествующий токен при возможном склеивании. При правке в начале нужен
   корневой checkpoint; это не требует по умолчанию перечитывать весь suffix.
5. Тот же P0 продолжает с сохранённым контекстом. Он вправе закончить после
   изменённой области только в старой живой границе, где совпадает полный
   continuation-state и доказано неизменное продолжение источника.
6. Общий builder готовит замену затронутых P0-фрагментов, диагностик и
   привязок. Публикация проверяет исходную ревизию ещё раз. Неизменённые узлы
   и ссылки переиспользуются; копирование изменённого пути к родителю не
   означает клонирование всего дерева.
7. Только после принятия результата очередь подтверждается. Повторно
   доставленное уведомление о принятой ревизии не выполняет edit ещё раз.

Смешанный batch текста и semantic attributes выполняет оба шага:
публикацию синтаксиса и инвалидирование зависимых потребителей.
`semanticRevision` отдельно отмечает завершённую обработку атрибутов.
`pendingSemantic`, `pendingRetired` и данные отвергнутого кандидата хранятся
на session до успешного завершения. Если cleanup или semantic hook отказал,
следующий turn сначала завершает его, без повторной публикации source splice.
Hook инвалидирования идемпотентен по identity документа/ревизии/элемента.
Native discard выполняется после снятия LMX-аннотаций; неудачный detach
не разрешает освободить память под живой ссылкой.

`P0MixStatus.ready` и поле `ready` в receipt требуют актуальной source
ревизии, завершённой semantic ревизии и отсутствия pending-работ.
У документа также должен быть закрыт source batch (`txDepth=0`).
Незавершённый после отказа batch требует восстановления owner и не
выдаётся за принятую ревизию.
ACK не проходит раньше этого барьера. Проверку используют MIX scan
и подключение общего подписчика; такой же вход нужен компиляции.

Checkpoint включает lexical mode, полные form/indent stacks, текущую локальную
границу документа, pending delimiter/MIX, состояние строк/комментариев/
exact identifiers, параметры ограниченной формы и курсор вставки результата.
Сравнение — точное по существенному состоянию и тождеству удерживаемых
контекстов; совпадение одного hash или отступа недостаточно. Приоритеты и
разрешение имён принадлежат последующей общей семантике, не новому P0.

Изменение числа внутри закрытого выражения обычно ограничивается этим
выражением. Удаление открывающей кавычки, fence или структурного закрытия
может изменить смысл большого suffix, вплоть до EOF. Cursor точно указывает
позицию, но не делает прежнее lexical state истинным после такой правки.
Область расширяется по реальной зависимости; произвольный порог не разрешает
публиковать некорректное локальное дерево. Общий полный вход остаётся явно
наблюдаемой крайностью при отсутствии пригодного checkpoint.

При неправильном новом тексте сохраняется диагностика его ревизии.
Старое валидное дерево можно удерживать как явно устаревшее представление,
но нельзя объявлять его деревом новой ревизии или компилировать как новое.
Диагностика копируется как обычные LMX данные с ревизией и byte span до
освобождения отвергнутого native-кандидата. Указатели внутрь его арены
в diagnostic не допускаются. Старые native-узлы также удерживаются, пока
существуют связанные с ними binding; публикация нового корня не разрешает
освободить память под ещё живой привязкой.

## 5. `{LMX}` как отдельный MIX-документ в `{MIX}`

Здесь `{LMX}` и `{MIX}` обозначают содержимое документов; новые обязательные
ключевые слова `LMX` и `MIX` не вводятся. Каждый корректный ограниченный
LMX-фрагмент получает:

- свой `MapSpan` / child-document identity и локальные координаты;
- два живых Cursor родительского источника на границах содержимого;
- собственный локальный корень P0 и ссылку на него;
- Var-якорь в родительском MIX с `childDocument` и исходными атрибутами;
- обратную ссылку от P0-узла к тому же Var и child document.

`MapSpan` — ограниченный документ над существующим источником. Байты не
копируются во второй редактируемый буфер. Правка через child scope сначала
проверяет локальные границы, затем идёт через общую mutation родительского
документа. Для закрытия допускается читать только свой диапазон; внешний
MIX-контекст и строковый overlay имеют отдельные локальные корни.

Вложенность областей-источников нужна для координат и lifetime. Она **не
задаёт** пары Var и не запрещает перекрытие итоговых Tag.

### Что делает отдельный MIX-анализатор

[anchors.lmx](../src/anchors.lmx) проходит документ своим Cursor один раз,
читает уже подготовленные Var и их атрибуты и связывает начала и концы:

- открытие добавляется в упорядоченный active set;
- `{end}` выбирает последнее активное открытие;
- `{end: red}` выбирает последнее активное открытие с close value `red`,
  независимо от имени головы;
- связывание устанавливает `partner` в обоих Var и общий Tag; оба Var
  сохраняют свою identity и ссылки P0;
- закрытие `red` не закрывает более поздний `green`;
- незакрытые/непарные Var сохраняются как явный результат/диагностика профиля;
  конец документа не превращается в выдуманное закрытие.

Поэтому `red-open, green-open, red-close, green-close` даёт два
перекрывающихся интервала. Глобальная active chain и индекс по close value
не являются XML-stack. P0 не обязан заранее назначать обоим концам общий
pairId: идентичность пары появляется после сопоставления. Анализатор
не ищет `}` в LMX-коде и не вызывает второй LMX-парсер. Разбор каждой
`{...}`-области и возврат позиции остаются у единого P0.

Для каждого child document и строкового overlay существует свой scan state.
Вход в `Var.childDocument` использует готовый локальный документ, а не
повторное обнаружение его текстовых границ. После изменения атрибутов одного
якоря достаточно пересвязать затронутый поток от сохранённого состояния до
совпадения active set; первый базовый вариант scanner выполняет один полный
линейный проход **меток данного документа**, не новый разбор всего LMX.

## 6. Координаты источника и отображения

Существующий `span.offset` измеряется в исходных байтах.
`lm_p0_count_characters` и текущие goldens считают `atom_char` в Unicode
code points **исходного токена**. Открывающая кавычка и C-prefix участвуют;
для block string отсчёт начинается с текста блока. Это не UTF-16 units и
не автоматически индекс декодированного строкового значения.

Из [current expectations](../../../tests/parser/current/expectations.json):
`"a{}b"` имеет mark at 2; `"🙂{a}"` — at 2, хотя `{` стоит после пяти UTF-8
байтов токена; `L"ab{c}"` — at 4. Эти ожидания здесь прочитаны, не исполнены.
Эти значения характеризуют текущий наблюдатель P0. Для языковых якорей
действует [правило грамматики для Mix](../../spec/LMX_grammar.ru.md#mix).
Символ в отображаемом тексте задаёт положение якоря. Символ вне BMP занимает одну позицию.

В binding сохраняются раздельно `rawByteOffset`, `sourceTokenChar`,
`coordinateKind`, исходный atom и child document. Для координаты отображения
используется соответствие с исходником, построенное тем же декодером с
учётом escape sequences, CRLF и raw quotes. Нельзя просто
прибавить `atom_char` к byte offset или вычесть одну кавычку для всех форм.

Скалярные offsets удерживаемого старого P0-узла и `rawByteOffset` Var относятся
к ревизии, в которой были записаны. Текущая позиция получается из живого
Cursor в binding; она не читается из устаревшего числа. Так вставка перед
неизменённым suffix не требует переписать каждый замороженный узел.
Native API диагностик и извлечения source span также должен использовать
binding для текущей ревизии. `targetRevision` кандидата проставляет одинаковую
ревизию новым узлам, checkpoint и child document, включая начальную загрузку.

## 7. Приёмка

Нужны наблюдения за количеством прочитанных байтов и реально заменённых
узлов; одно совпадение итогового текста не доказывает инкрементальность.
Проверить локальную числовую правку, слияние токенов, blank-line full close,
скобки и `{...}` внутри строк, изменение fence/quote, перекрывающиеся Tag,
пустой child document, вставки точно на обоих концах, Unicode/CRLF/escapes,
удаление Var и обоих концов пары, изменение metadata без self-loop,
несколько последовательных edits, повтор/пропуск сообщений и устаревший
результат отдельного parser worker.

Пример замены одного байта использует `MapCursor.replace`: заранее готовятся
значение, запись изменения и новая очередь событий, затем публикуется
замена без удаления/вставки Cursor. Ответ `P0MixReceipt` содержит только
скалярные поля; изменяемая session остаётся у владельца. Если уведомление
не доставлено, неподтверждённое событие остаётся в очереди для следующего
вызова обработчика. Повторное уведомление подтверждает уже принятую
ревизию без повторной замены текста.

Проверки P0, графа, Message execution и чистой арифметики dirty ranges
фиксируются отдельно. [LMX cases](cases.lmx) и их
[ожидания](../validation/p0_cases.json) готовы для обычного вызова из R0.
[Host oracle](../validation/p0_host_oracle.py) сравнивает сведение dirty ranges
с независимым переносом всех накопленных границ, перебирает допустимость
checkpoint и сверяет координаты с исходными fixtures.
[Отчёт](../validation/p0_host_report.json) содержит результаты именно этих
проверок. Успешный host oracle не является запуском LMX.
