# Merge методов: тело операнда дописывается или заменяет тело модели (анализ для автора, 2026-09-25)

Принято сегодня: merge методов допустим только в интерпретируемый результат (один дескриптор без нативного адреса); поля — по Q21 = А (одноимённые поля операнда пишутся в слоты модели, новые дописываются); тела — op-деревья: **ops операнда следуют за ops модели** (дописывание). Вопрос автора: что сломается и что починится, если тело операнда **заменяет** тело модели.

Разделение, на котором держится анализ (G3, -158): в теле callable объявления — поля (слоты), операторы — op-узлы. «Тело» ниже = op-узлы; поля живут по правилу полей в обоих вариантах.

## Что даёт замена (чинится)

1. **Обратный пример автора** `add: merge(add5, fn: add (int: y) int (return: x + y))` — работает: поля `x` (от add5), `y` (новое, дописано); тело — операнда; `x` в теле операнда разрешается транслятором в слот модели (карта позиций). При дописывании не работает: `return: x + 5` модели выполняется первым.
2. **Ловушка мёртвого тела исчезает.** При дописывании любой операнд-метод, приписанный к модели с `return`, никогда не исполняется — «специализация», чьё тело мертво, молча. Замена делает переопределение поведения таким же явным, как переопределение поля.
3. **Один принцип на всё:** поздний операнд специализирует модель — его поля пишутся в слоты, его тело — тело результата. Совпадает с переопределением поля-метода внутри Structure (Q21 = А: `B\M` замещает слот `A\M` целиком, тела не смешиваются) — сегодня это уже так на уровне полей, замена делает уровень самих callable таким же.
4. Заголовок: формалы модели (с переопределениями на месте) + новые формалы операнда; объявленный снаружи заголовок (`fn: add5 (int: x) int merge(...)`) — заголовок результата (сигнатура модели пропадает, как в прямом примере). Оба варианта одинаковы здесь.

## Что ломается (или требует оговорки)

1. **Последовательная композиция через merge исчезает.** «Сделать тело модели, затем тело операнда» больше не выражается merge’ем — только явным вызовом обоих из нового тела. (Первоначальная картина Q20 «массив адресов, исполняемых по порядку» — именно последовательность; она была снята стопом; замена закрывает её окончательно.)
2. **Не-callable операнд.** `add5: merge(add; y: 5)` — операнд `(y: 5)` тела не имеет. Правило нужно уточнить: **тело заменяет только callable-операнд**; Structure без тела даёт только поля, тело модели сохраняется. Без оговорки прямой пример получил бы пустое тело.
3. **Операторы объявлений модели не исполняются.** По Q19.2 объявление в теле — оператор на своём месте (переинициализирует ячейку). При замене тела ops модели, включая её инициализаторы, в результате не выполняются; значения полей модели — те, что скопированы merge’ем из экземпляра модели. Это согласуется с «merge специализирует экземпляр» (значения переносятся копией, поведение — операнда), но надо записать явно: результат не переинициализирует поля модели при исполнении.
4. **Catch-площадки и `throws:` модели** уходят вместе с телом (площадка покрывает своё тело); `throws:` — часть заголовка → переопределяется/дописывается по имени как поле.
5. **Вложенные методы модели** (объявленные в теле) — поля → остаются (переопределяются по имени операндом); их тела не смешиваются.
6. Свидетели, которые придётся переписать: q20-next §2 и §4-фикстуры merge с callable в операндах (после порта op-деревьев тел методов; сегодня op-дерево есть только у корня, потому merge методов ещё не исполняется ни в одном варианте — ломается только план, не код).

## Рекомендация

**Замена, с оговоркой 2** (тело заменяет только callable-операнд) и явной записью 3 (поля модели не переинициализируются — значения из экземпляра). Правило: «merge специализирует модель: поля операнда — в слоты модели, новые — в конец; тело результата — тело последнего callable-операнда, перенумерованное картой позиций; последовательность поведений выражается вызовом, не merge’ем».
