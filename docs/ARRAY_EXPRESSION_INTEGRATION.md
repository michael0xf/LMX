# Интеграция тензорных выражений, 27 ноября 2026

Нормативный текст полностью включён в [spec/TENSOR_EXPRESSIONS.md](spec/TENSOR_EXPRESSIONS.md).
Основные разделы Array, depth, fuse, грамматики и семантики согласованы с ним.
Это сопроводительное описание необходимых изменений транслятора/интерпретатора;
наличие описания и LMX-тел не означает внедрения нового production парсера.

## Порядок интеграции

В ядре действует **один общий парсер**: квадратный подпарсер является его частью и вызывает основной для любого вложенного выражения и `{…}`. Полное исходное авторское описание воспроизведено в [договоре подпарсера](spec/BRACKET_SUBPARSER.ru.md) и [плане реализации](TENSOR_IMPLEMENTATION_PLAN.md#integration-v3). Для чистого графа используется **один общий механизм группировки**, вызываемый всеми потребителями. Старые самостоятельные алгоритмы, таблицы приоритетов и обходные ветки подлежат удалению; отдельные binding-адаптеры, сохраняющие это дублирование, не допускаются.

Общий transport depth принимает целое со знаком и сохраняет отсутствие. Custom-метод может считать его иной настройкой и не включать Map. Ноль как максимум, неотрицательность и проверка d<=ранга Array относятся к выбранному стандартному Array-обходу, а не ко всем применениям синтаксиса или транспорта.

1. Общая лексика `.(` и контексты квадратных форм. `[op` без пробела запускает
   соответствующую ветвь подчинённого разбора. Пробельное `[ op …]` этим правилом
   не становится тем же оператором: остальные квадратные формы сохраняют свой
   обычный путь разбора Structure и типов. Индексы и Python-подобные срезы
   `var[arg:arg2:arg3]` разбираются тем же подпарсером в индексном контексте.
2. [Подпарсер](spec/BRACKET_SUBPARSER.ru.md) разбирает свои внешние разделители и
   `]`, а любое выражение и `{…}` передаёт основному парсеру. Основной возвращает
   результат и nextPosition. Подпарсер не сканирует их содержимое и не ищет
   вложенные закрывающие границы самостоятельно.
3. Граф сохраняет отсутствие depth/axisRules отдельно от нуля/пустого списка.
   Внутри index `::` — два разделителя среза, а внутри вложенного Expression
   действует обычная сигнатура `::`. Тернарное двоеточие принадлежит основному
   parser; `:=` и `.:` остаются цельными знаками.
   Source builder, interpreter и все frontend/native-потребители передают этот
   граф единственному общему группировщику; собственная группировка в этих
   путях удаляется. Приоритет степени 131 и правое связывание задаются один раз.
4. Шаблон операнда left/depth/right, traversal depth и обычный typed VALUE transport.
   Depth не считывается из случайной одноимённой динамической переменной при
   отсутствии модификатора. Явное выражение сохраняет собственный контекст.
   Явный depth=0 означает максимум; положительный d проходит d внешних осей
   Array и проверяет d <= rank. Базовое тело получает ячейки без повторного
   автоматического Map. Отсутствие depth сохраняет default выбранного метода.
5. Общий indexed executor с LMX-профилями kernel/reduce/state/finish; whole
   профили [op] отдельно. Обычная арифметика остаётся поэлементной.
6. Общий snapshot/admission/write для := и срезового .:, с разными RHS maps.
7. Минимальный fuse: Scalar/Map и свежий результат. Всё вне поддержанного
   профиля — диагностика. Расширения Reduce/Contraction не включаются молча.

В [первом этапе v3](../next_core_tasks_v3.md#grammar-complete-20261127) завершить всю грамматику и обе области записи выражения, включая `prefix` и `infix`. Синтаксическое дерево квадратного метода или `fuse` проверяется в этот срок. Исполнение его семейства планируется после завершения ядра. Общие контракты обхода графа, приёма, хранения корней и выхода интерпретатора проектировать по [плану совместных операций](LMX_INTERPRETER_JIT.md#kernel-before-jit).

## Данные и контекст

TypeRef — адрес канонического описания, не счётчик. Форма массива определяется
требованиями TYPE и известными размерами; capacity и экземплярные свойства
не входят в тождество типа. Основной Array-дескриптор не получает обязательного
дополнительного поля strides или owner. Контекст View — обычная структура в
parent: source, границы, отображение индексов, lifetime и права. Он создаётся
общими copy/merge. Ссылка на Array позволяет найти этот контекст.

[]@ не исключается из выражений: проверяется допустимость операции для
фактических ячеек. Текст остаётся []char. Переходы графа не являются осями
плоского размерного Array; parent не превращается в элемент последовательности.

## Правило пустой строки

Пустая строка закрывает блоки первого и более глубоких уровней. Следующий
после неё код начинается с нулевого уровня. Поэтому завершающие `---` и `end`
перед такой строкой не возвращаются только ради обхода ошибки parser.

**Инструкция Haiku:** если такой пример отвергается из-за отсутствия закрытия,
включить в план исправление обработки пустой строки основным parser. Не
исправлять нормативный пример вставкой лишнего `---`/`end`. Подпарсер квадратных
форм должен пользоваться теми же базовыми правилами и не дублировать layout.

## Матричный обзор 28 ноября

Whole-матрицы используют общий путь подготовки и собственные математические
методы. [Матрица существующих backend и альтернатив](core_catalog/matrix/README.ru.md)
описывает конкретные C entry, targets, layout, типы, ошибки и ограничения;
[общие модели](core_catalog/types/README.ru.md) задают signed strides,
CSR/CSC, комплексные буферы и отдельные fixed/binary floating преобразования.
Структуры bridge не добавляют обязательные поля в обычный Array.

Целая матричная степень имеет одно общее LMX-тело
[FxMatrixPower](spec/patterns/LMX_Fn_Receivers/src/array_expression_ops.lmx),
использующее принятые identity/copy/solve/multiply. Остальные методы не
получают фиктивную реализацию из декларации capability. Численный профиль,
finite/cutoff правила, проверка ошибок native API и сохранение RHS до первой
записи входят в допуск каждого подключения. Уточнённая последовательность —
в [этапах 7–8](TENSOR_IMPLEMENTATION_PLAN.md).
