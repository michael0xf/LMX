# L2/L3: инструкция разработчику

**Обязательный порядок сборки, 2026-11-18:** [to_fable2_fast_build.md](to_fable2_fast_build.md).
Обычные шаги, включая их приёмку и публикацию, проверяются компонентной сборкой и адресными случаями.
Полная самосборка и полный набор тестов имеют отдельные основания из этой инструкции; новый срез или коммит
не требуют их автоматически. `bootstrap quick` тоже строит G1/G2 и не является компонентным циклом.

`private:` исключает поле из динамического связывания вызовов; прямая и обычная лексическая
видимость сохраняются. Использовать общий binder без системы ограничений доступа:
[норма](docs/LMX_semantics.ru.md#private-binding), [задача M14](next_core_tasks_v3.md#private-binding-plan).

Этот файл задаёт рабочий порядок, а не новую норму языка и не журнал запусков. Текущий маршрут — [план v3](next_core_tasks_v3.md), состояние и владелец работы — [steps/current.md](steps/current.md), обязательные правила проекта — [READ.ME](READ.ME). Подробные зависимости и исторические свидетельства — в [словаре](next_core_tasks_dictionary_v2.md), [карте ядра](CORE.md), тикетах и [дефектах](steps/defects.md); старые планы остаются в истории Git. Не превращать прежний checkpoint в доказательство нынешней рабочей копии.

Нормативные источники: [семантика L3](docs/LMX_semantics.ru.md), [грамматика](docs/LMX_grammar.ru.md), [контракт L2](docs/L2_spec_ru.md) и [контракт L1](docs/L1_spec_ru.md), вместе с их английскими версиями. При расхождении этой инструкции со спецификацией сначала установить точную норму и предъявить конфликт, а не выбирать удобную реализацию.

## Единый вызов

call(args data code), call(data code), call(code);
fncall(args data return code), fncall(data return code), fncall(return code).
args содержит фактические значения обычного вызова; входы и требования описывает data.
Пропущенная args означает отсутствие дополнительной подачи, пропущенная data — code.
Обычный вызов, указатель, fn/sub/catch, запуск Structure и явные ресиверы идут через один
interpreter worker с общими binding/admission/namespace/result. Не создавать второй
dispatcher; изменить существующие launch/invoke/walk. Известный native→native остаётся
прямым C-вызовом. [Полная норма](docs/LMX_semantics.ru.md#call-receivers),
[зависимости и приёмка M10](next_core_tasks_v3.md#m10).

Срез393: чистый Source interface использует необязательный reader имени/fact прежнего implements resolver.
`Fact.type` остаётся physical pool type (прежняя схема: по норме физический тип — код записи значения); borrowed declared descriptions/receiving chains не являются C ABI binding

Полный runtime/current Value/typed storage bridge остаётся задачей основного M11/M13; [свидетельство393](steps/witnesses/m11-declared-facts-20261114/notes.md).

Цель — чистое ядро, затем **две действительные самосборки из L3 со вставками L2**, затем общая почта T01–T26. L1 остаётся только генерируемым промежуточным языком перед C; поддерживаемые исходники ядра, парсера, трансляторов и обычного build/test-цикла не пишутся вручную на L1.

Единственный writer/build ядра определяется [текущим состоянием](steps/current.md); прежнее назначение любого агента не действует после подтверждённой автором передачи слота. Помощникам можно поручать чтение, ревью и непересекающиеся документы; параллельной правки ядра или конкурирующей сборки нет. Перед каждым срезом проверить грязное рабочее дерево, владельца путей и точные входные файлы. Несвязанный WIP не исправлять, не включать в коммит и не маскировать.

## Общий алгоритм, а не набор исключений

1. Сначала строить полную исходную модель «receiver — arguments»; затем одним алгоритмом разрешать выражение во всех принимающих местах. Контракт места проверяет готовое значение, но не создаёт и не подавляет вызов своей веткой разбора. Обходчик распознаёт голову Frame по существующей таблице «адрес → имя», транслятор видит дерево парсера, готовому `native` имя не нужно. Не вводить отдельные resolver, fallback, opcode или таблицу runtime-связывания переменных для `@`, `merge`, `return`, формала или отдельного ресивера; после распознавания головы действуют адреса графа и карты мест.
2. Голый атом читает значение/ссылку, но не вызывает. Прямой метод и указатель на метод вызываются явной формой; обычная Structure исполняется через `call: A` или, в коде, записью `A()` (абзац «Запуск Structure по имени в коде» ниже). В данных `A()` и `A: ()` — объявления, ничего не вызывающие: `A()` объявляет пустую Structure `A`, `A: ()` — `A` с одной пустой безымянной Structure внутри; в коде такая запись — вызов головы `A`: вызываемое она вызывает, а обычную Structure запускает — `A()` над самой собой, как `call(A, A)`, `A(D)` и `A: D` над поданными данными, как `call(D, A)` (так, `A: ()` — над написанной пустой Structure; чтение исполнителя), — и ошибочна, когда голова не называет ни вызываемого, ни Structure ([роли `data` и `code`](docs/LMX_semantics.ru.md#data-code-roles), [журнал](LMX_blog/2026-11-11.md#structure-call-by-name)). Оператор `\` и группировка работают по общей грамматике: не менять их под прежний ошибочный пример `\ptr_f()`. Проверять одно выражение одинаково в аргументе, `return`, инициализаторе, поле и вложенном ресивере.
3. M3 упорядочивает плоские хвосты L2/L3 как **имя — требование/значение**. Место объявляет только форма ресивера с перечислением его аргументов (решение автора 2026-11-10, [книга](docs/LMX_semantics.ru.md#receiver-args-only)): `int: i 5`, `@: ptr 0`, `@: ptr Model`, `@: ptr Model 0`. Композиция с местом во внешней голове (`i: int: 5`, `ptr: @: Model: 0`), которую поддерживали N1–N6, снята: `ms: int: time` в данных — Structure `ms` с полем `time`; исходные тексты и фикстуры проекта её не пишут, и ни один путь трансляции не читает её как объявление места ([M9](next_core_tasks_v3.md#m9)). Первое поле формы ресивера — атом имени места, оно не вызывается; второе поле вычисляется как обычное выражение. Аргументы ресивера разбираются и читаются как всякие аргументы — как код (решение автора 2026-11-11, [книга](docs/LMX_semantics.ru.md#data-code-roles)): вложенная `Model: Other` в `@: ptr Model: Other` — вызов `Model`, а не требование с кандидатом. Требование и кандидат записываются плоско, тремя полями: `@: ptr Model Other`, нулевой адрес — `@: ptr Model 0`. Запись запуска Structure на месте, где нужно значение (операнд выражения, фактический аргумент вызова, начальное значение, операнд `merge`), ошибочна: у запуска результата нет (чтение исполнителя — [ответы исполнителя](LMX_blog/q/fable-self-answers-20261110.md), Р22, пункт 3; Р25, пункт 4). Контракт аргументов остаётся собственным у каждого ресивера, P0 не разбирает `@` и `int` особо. Повтор объявления читается по роли: в коде повтор объявления ресивером (`int: i 6` при известном `i`) — внеочередная проверка типа с присваиванием, второго поля не возникает; в данных повторное объявление — ещё одно вхождение имени: прежнего оно не заменяет и в него не пишет, после него имя адресуется только с индексом вхождения, а обращение без индекса — ошибка. В данных `Struct1: Struct2` объявляет Structure `Struct1` с одним атомом `Struct2` — указателем на Structure `Struct2`, неизменяемым по имени: упоминание известной Structure не раскрывается, и в дереве под `Struct1` стоит только этот атом ([книга](docs/LMX_semantics.ru.md#colon-declares)); в коде та же запись — вызов `Struct1`. Имена Structure и функций не присваиваются: запись `Struct1 := Struct2`, которую решение 2026-11-10 называло присваиванием, автор снял 2026-11-11; атом справа от двоеточия ничего не присваивает, указатель-переменную объявляет `@: ptr Model`, ей и присваивают. Прежнюю неоднозначную реализацию `node\[N]field` удалить, а [N4-U](next_core_tasks_v3.md#code-data-occurrences) возвращает этот путь как индекс **вхождения** имени на коренном уровне Structure в роли `data`; вхождение — запись данных, объявляющая это имя, будь то объявление ресивером места или структурная запись с такой головой: при единственном вхождении доступен `s\field`, при двух и более требуется `s\[N]field`. Не смешивать его с `arr[i][j]` и массивом ссылок `arr[i]\[j]`.
4. Результат обычного `merge` — самодостаточная копия используемого графа: одна карта копирования перенаправляет внутренние ссылки, сохраняет sharing и циклы. Не оставлять зависимость от освобождаемой арены. Удерживаемые `independent: immutable` ветви — отдельное утверждённое правило жизни арены, а не повод для произвольного исключения. Число слотов созданного `Lmx` фиксировано; стабильный адрес `@field` не допускает удлинения готового узла.
5. Native и действительно walked исполнение должны иметь одинаковые наблюдаемые значения, адреса, отказы и side effects. При копировании и слиянии runtime сохраняет слово `native` для сопоставленных физических адресов и ABI. При фактической записи в исполняемый код ядро сбрасывает слово у зависимых исполняемых вхождений. Диспетчер читает его после вычисления операндов и публикации.
6. Структурные формы — со скобками, короткая и блочная — только объявляют или вызывают; присваивания они не делают (решение автора 2026-11-10, [книга](docs/LMX_semantics.ru.md#forms-declare-or-call)). Что из двух, задаёт роль: в данных форма объявляет, в коде вызывает (решение автора 2026-11-11). Значение в известное место записывать `name := value`, в том числе по пути, индексу и разыменованию; слева от `:=` стоит место примитива или указатель-переменная, имя Structure или функции слева — ошибка. Повторное объявление формой ресивера с перечислением аргументов (`int: i 6`, `@: p q`) остаётся — в коде это внеочередная проверка типа с присваиванием; составная `i: int: 6` снята (пункт 3). Код и тесты писать с `:=`: исходные тексты проекта уже записывают присваивание этим оператором, а трансляторы отказывают форме с двоеточием, которую прежде понижали как запись в известное место ([M7](next_core_tasks_v3.md#m7)).

Если две утверждённые нормы противоречат друг другу или реализация требует ветки по имени, типу, форме записи либо месту в трансляторе, зафиксировать минимальную программу, обе нормы и измеренное поведение. Задать автору **этот** вопрос, не пришивать shim и не закреплять его зелёным тестом. Остановить только зависимый срез; независимую работу продолжить.

Выражения — тот же общий алгоритм. Приоритеты и ассоциативность операций — как в Си, у присваивания низший
приоритет: правая часть присваивания — всё выражение справа. Значения вычисляются по требованию: ресивер,
которому нужен результат другого ресивера, получает его исполнением этого ресивера — один раз за вычисление,
без повтора эффекта при обходе и без постоянных полей в чистом графе; пропущенная ветвь `&&` и `||` не
исполняется. Встроенное в выражение аргумента присваивание пишет в `data` вызываемого и отдельным аргументом
не становится. При статически известных связях транслятор выстраивает последовательность вычислений заранее
и не ищет присваивание при каждом чтении переменной. `sys\name(identificator)` берёт написание из служебной
таблицы имён и ничего не исполняет. Функция реализации операнда имеет один вид — `fn: new_op ([]: @ args) @`:
массив ссылок на типизированные записи хранилища и ссылка на запись результата. Адрес нетегированного
временного значения такой ссылкой не служит, плотный числовой массив в массив ссылок не переинтерпретируется.
Приоритет операнда обязателен; запрос приоритета и анализ выражения пользуются одной таблицей. Особых случаев
по имени ресивера быть не должно
([книга](docs/LMX_semantics.ru.md#assignment-inside-expression),
[ТЗ и приёмочные проверки](docs/new_parts/to_fable_operands_arguments_priorities.md)).

Действующая [видимость](docs/LMX_semantics.ru.md#declaration-visibility), уточнённая2026-11-15: переменные и const доступны от первоначального объявления в своём блоке и ниже; именованные Structure и callable видны в обе стороны. Переменная с callable-значением остаётся переменной. Root-only сбор namespace не открывает будущие локалы code; порядок задаёт итоговое лексическое дерево, не byte offsets разных файлов. Новое имя ветви наружу не выходит, повторное объявление видимого имени сохраняет RHS, допуск и запись. До своего объявления возможна обычная доступная внешняя связь, без TDZ.

[M14](next_core_tasks_v3.md#native-structures) объединяет args/data в одну входную data и сохраняет сокращённые заголовки. Каждый вызов, включая call(D,C), получает локальные места без обратной публикации; только корни data/code участвуют в подготовке namespace. Исходная data не дополняется из code. При входе инициализаторы вообще не исполняются: построитель чистого графа сворачивает готовые объявления без вызовов программы, вычисляемые описания сохраняются. Поданный actual заменяет свой default; неиспользованный вычисляемый вход не вызывается. Входы data доступны code. Для @: fptr getFuncPtr() выражение fptr("hello world") сначала вычисляет написанный RHS, затем вызывает результат; это общий механизм чтения поля, не неявный вызов голого callable.

Выбранные локальные значения/описания независимы от источника сразу после входа, в том числе до первого чтения и при лексическом/динамическом связывании. Ссылки внутри значения сохраняют цели. x := 0 меняет namespace; data\x := 0 меняет исходный граф. @x адресует локальную ячейку и тоже вычисляет вычисляемый вход. Для int: field getValue() в data форма @(data\field) адресует результат в существующем l2_tN (&l2_tN) либо обычной ячейке обходчика, не переписывая исходное объявление и не создавая отдельное хранилище результатов. Для готового поля адресуется его ячейка. Обычное время жизни сохраняется; @f() не становится отдельной задачей поддержки или запрета.

Одноаргументный call(code) равен call(code code). Обязательное копирование code при входе отменено;
выбранные локальные значения/описания остаются независимыми, связывание передаётся скрытыми аргументами.
Методы и обычные Structure компилируются общим механизмом без data=code; сигнатуры выводятся из реальных
вызовов, разные подачи дают разные варианты. Известный native вызывает известный native прямо в C,
без графового кадра и lookup только ради вызова. Правки графа не обнуляют native.
sys\compile явно выполняет чистый граф → L1 → C → машинную компиляцию/регистрацию; sys\translate выдаёт L1.
sys\endturn выходит через зарегистрированные finally к обычной границе такта, без перехвата catch
и возврата к месту вызова, без остановки Message/Thread. Сам не проверяет/не компилирует/не публикует.
До границы момент применения правок code не гарантирован; после успешной явной компиляции и endturn
следующий вход использует обновление. Подробности и удаление отслеживания — [M14](next_core_tasks_v3.md#explicit-compilation-plan).

`data` — зарезервированное имя явной ссылки на данные текущего запуска; оно допускает обычное объявление в данных, первое и повторное, и присваивание указателя оператором `:=`. По умолчанию его значение — данные запуска: `data\x` — путь к месту `x` этих данных, `data\[N]x` — к N-му вхождению имени, `data\if` — к записи ресивера управления. Привязку меняет присваивание указателя, `data := ptr`, и дальнейший `data\field` использует новое значение; следующий явный путь использует новое значение ссылки; это не меняет уже выбранные локальные связи и не вводит dirty или кеш. Структурная запись с головой `data` читается по роли, как всякая другая: в данных `data(...)` объявляет обычную Structure `data`, а повторная такая запись — ещё одно вхождение имени, не замена и не присваивание; в коде это вызов головы: `data()` — запуск данных текущего запуска над ними же, `data(D)` — запуск данных текущего запуска над поданными `D` (по решению автора 2026-11-11, [журнал](LMX_blog/2026-11-11.md#structure-call-by-name); чтение исполнителя — [ответы исполнителя](LMX_blog/q/fable-self-answers-20261110.md), Р21, п. 1, 5 и 7; Р24, п. 5); привязки запись не меняет. Структура не является вызовом, а объявление не исполняет её содержимое. Часть `data` метода имеет свой описанный контракт; одноаргументный `call: code` дочерний блок `data` не выбирает — он исполняет код над самим собой, а данные передаются явно (решение автора 2026-11-11, [ресиверы `call` и `fncall`](docs/LMX_semantics.ru.md#call-receivers); чистый граф исполняет это со среза 353, рабочий frontend — ещё нет, [план](next_core_tasks_v3.md#m10)). Для присваивания ссылки на метод писать `@: ptr method`: `@` стоит первым, `ptr` и `method` — голые атомы, а **атом не является вызовом**. `ptr(args)` — явный вызов, `@ptr` — адрес ячейки. Скрытый вход тоже имеет собственную локальную ячейку; `@x` не адресует источник связывания. [Норма RU/EN](provenance/semantics-book.md#ordinary-var), [дословные подтверждения и найденная история](LMX_blog/2026-11-03.md).

**Роли `data` и `code` (решение автора 2026-11-11, [книга](docs/LMX_semantics.ru.md#data-code-roles), [журнал](LMX_blog/2026-11-11.md#data-code-roles)).** Решение сужает предыдущий и следующий абзацы (кроме смены написаний `var` → `data`, `body` → `code`, порядка `call: data code` и момента допуска `implements`, [журнал](LMX_blog/2026-11-11.md#data-code-roles), [порядок](LMX_blog/2026-11-11.md#data-before-code)). Structure участвует в запуске как данные или как код; роль задаёт запуск, а не сама Structure. Запись читается по роли, и транслятору не нужно выяснять, где вызов, где объявление Structure и где присваивание. Особое имя явной ссылки на данные запуска, одноимённая часть вызываемого и блок данных называются `data`, часть с исполняемыми записями и одноимённый аргумент ресиверов `fn`, `sub`, `catch` — `code`; части вызываемого — `args`, `return`, `data`, `code`. В данных: структурная запись объявляет Structure, какой бы ни была голова, — запись вызова и ресиверы управления там тоже Structure, названные своей головой; объявления ресиверами мест действуют; присваивания и прочий код не исполняются, присваивание там — просто поле, до которого доходят индексом; одноимённые записи различает индекс вхождения, `data\[N]имя`, к записи ресивера управления ведёт путь `data\if`, к вложенной — `data\if\if`. В коде: всякая запись — вызов; объявление ресивером — проверка типа с присваиванием в место данных; структурная запись — вызов своей головы, и это ошибка, когда голова не называет ни вызываемого, ни Structure; объявлений Structure нет, объявления `fn`, `sub`, `catch` остаются; вызываемое, объявленное в данных, вызывается прямо по имени и связывает свободные имена по общим правилам — сначала динамический вход, затем лексический источник; обычная Structure данных запускается записью с её именем в голове (абзац «Запуск Structure по имени в коде» ниже). Безымянная Structure в коде вызовом не считается: `(a b c) := myFn()` — групповое присваивание ([книга](docs/LMX_semantics.ru.md#data-code-roles), [журнал](LMX_blog/2026-11-11.md#unnamed-structure-not-call)). Присваиваются только значения — примитивы и указатели на Structure и на функции: слева от `:=` место примитива или указатель-переменная (`@: ptr KnownStruct`), имя Structure или функции слева — ошибка; имя Structure или функции на месте значения указателя даёт указатель без записи `@Struct`. Аргументы вызовов и ресиверов разбираются общим алгоритмом и читаются как код: `f(arg: v)` — вызов `arg`, именованный аргумент — только `f(arg := v)`; входные места единой `data` объявляют ресиверы (`int: arg default`, `@: arg Template`), а именованные Structure остаются данными. У fn/sub/catch отдельной части формальных `args` нет; `args` ресиверов запуска содержит передаваемые значения. Например, `sub: proc (struct1: Template1; struct2: Template2) ()` явно пишет данные и пустой код. Сокращённые заголовки сохраняются по общему правилу частей ([книга](docs/LMX_semantics.ru.md#method-parts)); прежняя схема `args/data` отменена. Запись запуска Structure на месте, где нужно значение (операнд выражения, фактический аргумент вызова, начальное значение, операнд `merge`), ошибочна: у запуска результата нет (чтение исполнителя — [ответы исполнителя](LMX_blog/q/fable-self-answers-20261110.md), Р22, пункт 3; Р25, пункт 4). Следствия, принятые в книге (чтения исполнителя): письмо выхода пишется `send: exit(exit_code := 7; stdout := ""; stderr := "")`; именованные части ресиверов `fn`, `sub` подаются только через `:=` — `fn: name := k1; args := (int: a); return := int; code := (return: a + 1)`; имя, держащее результат `merge`, объявляет `@: R merge(A; B)`. Интерфейсная часть `implements` выполняется один раз для каждого кандидата: при построении графа для известного кандидата, иначе при фактическом приёме; `test` — второй шаг при исполнении, с прекращением при первом `0`. Случаи выбора кандидата при исполнении — в [документе](steps/implements-runtime-cases-20261111.md); присваивание примитивов при исполнении на допустимость не сверяется (правило говорит о допуске `implements`, а не о преобразовании: проверка диапазона при приёме числа другого типа, `u16(256)` в `u8`, остаётся при исполнении). Из этих правил транслятор исполняет пока лишь часть, и только чистый граф: со среза 354 он читает `data`, `code` и `call: data code` и прежних написаний не принимает (шаг 4 [раздела M11 плана](next_core_tasks_v3.md#m11)); подшаг 5а шага 5 он исполняет со среза 355, первую часть подшага 5б — со среза 356, остальное чтение по ролям — подшаг 5в и остатки подшагов 5б, 5г, 5д и 5е — ещё нет; рабочий frontend, который вместе со своими фикстурами читает прежние `var`, `body` и `call: code data`, этих правил не исполняет (шаг 8); там же — снятие ветвей выбора.

**Ответы автора 2026-11-11 к этому решению** ([журнал](LMX_blog/2026-11-11.md#known-name-not-expanded), [книга](docs/LMX_semantics.ru.md#colon-declares)). Упоминание имени известной Structure не раскрывается — ни парсером, ни при построении чистого графа: в `Model: knownModel` у `Model` один атом `knownModel` — указатель на Structure `knownModel`, неизменяемый по имени. Ссылаться на неё он начинает при интерпретации и трансляции, и путь через него продолжается в её поля — `Model\knownModel\a` есть поле `a` самой `knownModel`, — но поддерева под `Model` не возникает: место Structure в дереве задаёт её `parent`, и у `knownModel` он не меняется. Не строить ни раскрытия, ни копии, ни «перехода» Structure внутрь другой. Слот атома адресуется индексом, и присваиванием по индексу (`Model[0] := …`, `data[index] := …`) в него можно записать что угодно; изменяемую ссылку объявляет ресивер — в `Model: @: ptr knownModel` имя `ptr` есть указатель-переменная внутри `Model`. В `Struct1: (Struct2 a b c)` внутри `Struct1` одна безымянная Structure с четырьмя атомами: `Struct1[0]\Struct2\a` — поле `a` Structure `Struct2`, а `Struct1[0]\a` — собственный атом безымянной Structure. Ссылки по имени могут замкнуться (`A: B` и `B: A`) — это не ошибка; так же, по имени и без раскрытия, называют Structure аргументы вызовов. Дамп чистого графа печатает дерево — атом, а не содержимое указуемого (чтение исполнителя — [ответы исполнителя](LMX_blog/q/fable-self-answers-20261110.md), Р2). Данные стоят перед кодом в каждой записи: двухаргументный запуск пишется `call: data code` и `call(data code)` ([журнал](LMX_blog/2026-11-11.md#data-before-code)). У Structure, запущенной над самой собой, своих правил нет, и пропуска «своих» объявлений нет ([журнал](LMX_blog/2026-11-11.md#self-launch-no-own-rules)); отсюда чтения исполнителя (те же ответы, часть Р). Корень единицы запускается как Structure над самой собой. Объявление Structure среди исполняемых записей по-прежнему, как правило, ошибочно, но по другой причине: запись, которой те же данные объявляют обычную Structure, в коде запускает эту Structure, и её собственный хвост стоит на месте аргумента — два и более поля в хвосте не дают определённого числа аргументов, одно поле — данные запуска и должно давать Structure; не отказывают лишь вырожденные записи — пустой хвост, единственный атом, называющий Structure, единственная безымянная Structure в скобках (чтение исполнителя — [ответы исполнителя](LMX_blog/q/fable-self-answers-20261110.md), Р21, п. 6). Поэтому исполняемая Structure — корень единицы, тело метода, Structure, запускаемая `call` или по имени, — объявлений Structure не содержит: их пишут в данных — в части `data` метода, в Structure, которую запуск получает данными, в написанной Structure на месте значения. Запись вызова в данных — Structure с именем своей головы и адресуется `data\f`; голое имя `f` в коде по-прежнему называет метод.

**Запуск Structure по имени в коде (решение автора 2026-11-11, [журнал](LMX_blog/2026-11-11.md#structure-call-by-name); чтение исполнителя — [ответы исполнителя](LMX_blog/q/fable-self-answers-20261110.md), Р21).** В коде запись, голова которой — обычная Structure, запускает её (до решения 2026-11-11 такая запись в коде отказывала, а обычную Structure исполнял только ресивер `call`): `S()` — то же, что `call(S, S)` (Structure над самой собой), `S(D)` — то же, что `call(D, S)` (Structure над поданными данными); так же короткая форма `S: D` и блочная. Это самостоятельная запись запуска, а не форма ресивера: ресиверы `call` и `fncall` остаются общим механизмом ([ресиверы `call` и `fncall`](docs/LMX_semantics.ru.md#call-receivers)), у явных ресиверов доступны все шесть форм, включая подачу actuals через `args`; это не отдельная часть формальных объявлений callable. Аргумент у записи один и называется `data` — тем же именем, которым исполняемый код называет данные своего запуска ([особое имя `data`](docs/LMX_semantics.ru.md#ordinary-var)): `S(D)` и `S(data := D)` — одна запись. Он должен давать Structure (имя, путь, место-ссылка, написанная в скобках безымянная Structure), иначе ошибка; ошибкой будут и аргумент с другим именем, и два и более позиционных аргумента. Голова — место со ссылкой: вызывается то, на что ссылка указывает, — вызываемое (вызов через указатель) или Structure (запуск по тем же формам); место числа, пустая ссылка и неизвестное имя — ошибка, как и голова, не называющая ни вызываемого, ни Structure. `data()` в коде — запуск данных текущего запуска над ними же. В данных ничего не меняется: `S()` по-прежнему объявляет пустую Structure `S`, а `S(D)` — Structure `S` с атомом `D`; ничего не вызывается (для `S()` подтверждено автором, [журнал](LMX_blog/2026-11-11.md#structure-head-call-refuses-in-code); для `S(D)` — чтение исполнителя, Р21, п. 2). В Structure над самой собой и в корне единицы каждая запись читается по обеим ролям, поэтому запись `S()` там — сразу объявление ещё одной `S` и вызов: если `S` объявлена в той же Structure, у имени два вхождения, без индекса оно не отвечает, и вызов отказывает; если `S` объявлена снаружи, запись объявляет собственную пустую `S`, и запускается она, а не внешняя. Особого правила нет, и ту же Structure там запускает ресивер `call`; вызов метода и ресивера это не задевает. Чистый граф со среза 356 исполняет запись запуска Structure по имени в коде метода и в коде над поданными данными — `S()`, `S(D)`, `S(data := D)` — и запись с головой — местом со ссылкой на обычную Structure везде, включая корень единицы, а также именованную подачу аргументов у `call` и `fncall`; в корне единицы и в Structure над самой собой роль кода у записи с головой — обычной Structure по имени он пока не исполняет (подшаг 5г [плана](next_core_tasks_v3.md#m11)). Рабочий frontend читает прежние имена и порядок и запуска по имени не исполняет (шаг 8).

Объявление ресивером места в code связывает новое локальное место либо сохраняет RHS, допуск и присваивание уже видимому месту namespace; исходную data оно не расширяет и назад не пишет. Новое имя inline-ветви видно в ней и ниже, снаружи не видно. Повтор видимого имени не создаёт другую C-переменную. Физические объявления в данных остаются отдельными вхождениями: при повторе имени требуется S\[N]field, автоматического выбора первого нет. Явное раннее чтение вычисляемого объявления не отменяет исполнения его строки при последующем достижении.

Интерфейсная часть implements выполняется один раз для кандидата: для известного при построении графа, иначе при фактическом приёме. Test — второй шаг при исполнении, с прекращением при первом 0; построитель пользовательские test и прочие программные вызовы не выполняет. Соблюдать общую границу data/code: прямой проход данных обрабатывает корневые объявления, а произвольный код не запускается только из-за присутствия в data. К выполнению переданного кода приводит его обычное потребление ресивером. Готовые объявления сворачиваются при построении чистого графа; отдельного входного прохода инициализаторов нет. Разрешённые места и обычная таблица «адрес → имя» используются общим обходом, без отдельного opcode или специальных путей ресиверов.

При реализации call: data code удалить load-dirty, обратную публикацию, work_flush, отдельный кеш и flush() вместе с их таблицами, переносами и ветками генератора. Прямой путь пишет исходный граф сразу, с тем же результатом через aliases. S[n] := p — сырая запись void*, идентичная Array<@>, без требований бывшего поля; именованная запись использует контракт поля, по возможности проверенный сборщиком. Нужные физические свойства памяти сохранять; инвалидацию code, её таблицы, переносы и ветви генератора удалить, без замены отслеживанием другого вида. Построение и проверка чистого графа сначала работают в сборщике; переносить общий код в runtime только под конкретную задачу, без универсальных обёрток и состояний «на будущее».

Явные вспомогательные операции группировать в sys: check/checkL3, translate (L1 + errors, не LMX), compile, endturn, capacity/resize/reserve, indexof и операции заголовка/сериализации из M14. Parent и length остаются общедоступными. Sys\indexof(field parent) требует единственного вхождения той же ссылки; sys\indexof(field index parent) возвращает физический индекс указанного с нуля вхождения. Отсутствие/неоднозначность диагностирует явный indexof, а не обычная запись массива; обратный индекс не создавать. Общие имена коротких операций не резервировать глобально. Проверки соразмерны изменению; применять языковой test по мере переноса самосборки.

## Стиль записи: закрытие блоков

**Оформление по просьбе автора 2026-11-13:** в новом и переписываемом коде один уровень никогда не закрывать
лишним `end:` или оградой. Использовать уменьшение отступа либо трейлер `return` для исполняемого определения.
Это правило оформления, не изменение грамматики или парсера ([слова автора](LMX_blog/2026-11-13.md#one-level-formatting)).

**Повтор автора 2026-11-16** ([журнал](LMX_blog/2026-11-16.md#new-types-not-bits)): «при последовательном снижении по одному
уровеню они не требуются -- как в Python; Функцию лучше закрывать return в роли trailer если return и так идет
последним оператором». Функция, у которой `return` — последний оператор, им и закрывается: строка `end: имя`
после него не пишется. Приёмка каждого среза проверяет его diff: добавленная строка `end: имя` или ограда `---`
допустима только там, где она закрывает больше одного уровня. Старые записи не переписываются ради правила.

## Новое различие — новый тип

Слова автора 2026-11-16 ([журнал](LMX_blog/2026-11-16.md#new-types-not-bits)): «заводите просто новые типы себе и
всё»; «зачем тебе снимать и выставлять биты если есть 4 млрд кодов для 4 млрд типов?». Когда ядру или транслятору
нужно отличить один вид значения от другого, заводится новый код типа в перечне типов. Биты-признаки, маски и
составные «слова кода» не вводятся. Разные Structure при этом не разные типы: модель пользователя кода типа не
порождает ([L2 §3](docs/L2_spec_ru.md#value-record)).

Слова автора 2026-11-11: [один отступ закрытия не требует](LMX_blog/2026-11-11.md#one-level-needs-no-close), [все трейлеры закрывают и более чем один уровень](LMX_blog/2026-11-11.md#trailers-close-many-levels), [внутри скобок то же правило, парсер везде один](LMX_blog/2026-11-11.md#same-parser-inside-brackets), [согласие с правками парсера](LMX_blog/2026-11-11.md#one-parser-everywhere-no-unwrap); правило — [грамматика §14](docs/LMX_grammar.ru.md#bounded), [§15](docs/LMX_grammar.ru.md#levels) и [§17](docs/LMX_grammar.ru.md#close).

Закрытие блоков. Блок закрывается отступом, как в Python: строка, вернувшаяся на один уровень, закрывает блок, и закрывающего слова не нужно. Отсекатель — видимая форма трейлера: `end: имя`, ограда `---` или терминальная форма (`return`, `until:`) в разрешённой позиции — нужен только там, где уровень следующей строки снижается больше чем на один (перескок); без него такое снижение — ошибка разбора. Один отсекатель, допустимый в своей позиции и профиле, закрывает и несколько уровней сразу. Правило одно во всех блоках: внутри скобок — круглых, квадратных и фигурных — оно то же, что вне скобок, и парсер везде один (слова автора). Отсекатель внутри скобок действует на уровни, открытые внутри тех же скобок, и непарную скобку не закрывает. После блока в один уровень `end: имя` писать не требуется (состояние парсера — абзац ниже).

Один уровень — закрытие не нужно: блок `Point` закрывает строка `int: after 1`, вернувшаяся на один уровень.

```text
Point:
    int: x 4
int: after 1
```

Два уровня — нужен отсекатель: от `int: x 4` к `int: y 2` уровень снижается на два, поэтому стоит `end: Point` (на том же месте годится и ограда `---`, если её допускает профиль и позиция однозначна, [грамматика §16](docs/LMX_grammar.ru.md#markers)); без этой строки перескок — ошибка разбора.

```text
D:
    Point:
        Inner:
            int: x 4
    end: Point
    int: y 2
```

Строки внутри скобок читаются так же, как вне скобок: строка глубже предыдущей открывает вложенную анонимную Structure (в примере у `y` атом `a` и анонимная Structure с `b`), точка после пробелов отступа — обычный атом, не маркер уровня, а закрывающая скобка без открывающей — ошибка разбора ([грамматика §14](docs/LMX_grammar.ru.md#bounded), формы А, Б, В).

```text
D: (
    y: a
        b
    z
)
```

Состояние парсера. Проверенные сборки P0 и оставшиеся ограничения — в [заметках реализации](docs/implementation-notes.ru.md). Пакет общего разбора блоков, однократной постобработки, потерянных скобок и Mix не закрывает M8: раскрытие единственной Structure пока сохраняется; M8 — следующий шаг [передачи](to_sol.md).

Существующие записи с `end: имя` после блока в один уровень допустимы и не переписываются: именованному Frame не обязательно иметь явный `end:` ([грамматика §17](docs/LMX_grammar.ru.md#close)).

## Проверка и публикация среза

- По [последнему уточнению автора от 2026-10-22](LMX_blog/2026-10-22.md) **все тесты и скрипты переносить на L2/L3**, не на рукописный L1/C/Python/PowerShell. Предыдущее разрешение на L1-тесты отменено. Это включает source-linked/fault/lifetime probes, test helpers и простые prepare/build/verify/checkpoint/receipt/audit/post runners, генераторы/классификаторы и обработку результатов. Сохранять assertions, внутренние инварианты, negative controls, mutants и реальные native/walker значения, а не заменять их успешной трансляцией. В bounded inventory для каждого maintained input указать L2/L3-замену, языковой запуск, соответствие наблюдений и новые hashes. Не прятать старую логику в строку, другой shell или thin wrapper; после переноса нет активного fallback на старый скрипт. L1/C остаются только генерируемыми артефактами; внешний C compiler/linker и OS допустимы. Недостающую общую операцию реализовать на L2/L3 в языке/библиотеке. Старые receipt не переписывать, неизвестные/чужие файлы не удалять по одному расширению.
- До правки записать базовый commit/SHA, затронутые пути, зависимость плана и ожидаемые свидетели. Менять один dependency-closed срез, не подкручивать старые golden-файлы ради сокрытия отказа.
- Выбирать сборку и проверки по [короткому компонентному циклу](to_fable2_fast_build.md): затронутые компоненты и необходимые зависимости, минимальный пример и зависимые случаи. Изменение исполнения проверять на нужных native/interp/forced путях; отрицательные случаи и mutants выбирать по конкретной правке. Полную самосборку и полный набор запускать по их отдельным основаниям, после стабилизации связанного изменения; это не условие каждого среза или коммита. Для каждого результата сохранить команду, число целей, FAIL-ID, фазу и диагностику. Сбой общей проверки назвать точно, а не объявлять gate пройденным.
- При изменении нормы править её первичный источник и обе языковые версии: [семантика](provenance/semantics-book.md) и [языковой генератор](selfbuild/tools/docs_semantics.lm2), [грамматика](provenance/grammar.json) и [языковой генератор](selfbuild/tools/docs_grammar.lm2), либо соответствующие парные L1/L2-файлы. Справочные объяснения и измеренные ограничения держать вне нормативного текста. Реплики автора архивировать в `LMX_blog/` дословно по [READ.ME](READ.ME), организационные сообщения туда не переносить.
- При изменении источников генерируемых документов выполнять соответствующие `docs render` / `docs check` текущим проверенным tool по [командам](READ.ME#docs-cycle). Для правок инструкций и плана проверить текст, ссылки и `git diff --check`; неизменённые документы не регенерировать, compiler/runtime и bootstrap не собирать. Python-версии не являются активным fallback. Коммитить только перечисленные проверенные пути и push в `main`; не включать чужой WIP. Непроверенная правка или ACK агента не являются опубликованным завершением; компонентную приёмку не выдавать за полный gate.
