# Пояснения к семантике LMX

Это короткие ненормативные примеры. При расхождении действуют
[семантика](LMX_semantics.ru.md) и [грамматика](LMX_grammar.ru.md).

<a id="data-receiver-execution"></a>
## Подготовка не выполняет программу

Построитель сворачивает готовые объявления без вызовов. Подготовка namespace учитывает только корневые
объявления data и code; вложенные ветви и ссылки графа не обходит. В последовательности

```lmx
mark()
int: y makeValue()
```

подготовка не переносит makeValue() перед mark(). Выполнение достигнутого ресивера остаётся обычным
вызовом и может исполнить переданный код; это не разрешает заранее запускать все инициализаторы data.
Поданный actual подавляет соответствующий инициализатор. [Норма](LMX_semantics.ru.md#call-frame-20261115).

<a id="admission-stages"></a>
## Два шага допуска

| Когда | Что происходит |
|---|---|
| Построение графа, кандидат известен | Проверяется используемый интерфейс. `test` не исполняется. |
| Фактический допуск при исполнении | Если первая часть уже выполнена, она не повторяется. Затем исполняются заданные `test`. |
| Первая проверка вернула `0` | Допуск немедленно прекращается; оставшиеся проверки не исполняются. |

Известность кандидата при построении не отменяет второй шаг при фактическом допуске. Само изменение
значения не запускает все проверки заново. Норма — [допуск и test](LMX_semantics.ru.md#admission).

<a id="callable-description"></a>
## Входное описание и композиция

У вызываемого одна входная data: роль данных исполняет фактический `parent` выбранной Structure
([структурный вызов](#call-receivers)), а фактические значения передаёт отдельный `args`. Data не дополняется
полями тела: локалы code возникают в namespace вызова. Поэтому старые три примера add5 с отдельными args/data
больше не задают действующую норму. merge по-прежнему явно строит новый граф; его правила не являются
скрытой инициализацией вызова. Сигнатуру без исполняемого кода описывает `fn` тем же шаблоном данных
([сигнатура `fn`](#fn-signature)); C-параметры выводятся из реальных подач аргументов.
[Точная постановка и оставшаяся синтаксическая миграция](../next_core_tasks_v3.md#native-structures);
[план нормы 2026-11-19](../next_core_tasks_v3.md#binding-callables-20261119).

<a id="receiver-arities"></a>
## Место и значение у `int` и `@`

Место объявляет форма ресивера с перечислением его аргументов. Это отдельные
примеры, не последовательные операторы одной программы:

```lmx
int: x         # место int без начального значения
int: x 5       # int со значением 5

@: ptr         # void-ссылка без заданного адреса
@: ptr 0       # void-ссылка с явным нулевым адресом
@: ptr Model   # ссылка на существующую Structure, уже не пустой void-указатель
```

Первое определение выделяет место; в коде повторная форма с кандидатом
записывает в него после допуска, а повторная форма без кандидата только
сверяет требование (в данных повторная форма — ещё одно вхождение имени,
[имена и пути](LMX_semantics.ru.md#fields)). Составные записи с местом во внешней голове — `x: int()`,
`x: int: 5`, `ptr: @()`, `ptr: @: 0`, `ptr: @: Model` — сняты решением
автора 2026-11-10 ([семантика](LMX_semantics.ru.md#receiver-args-only)):
`ms: int: time` в данных объявляет Structure `ms` с полем `time`, а не место
`ms`.

<a id="header-receivers"></a>
## Заголовок и служебные таблицы

Плоский заголовок Lmx состоит из parent/length/storage. `parent(S)`, `length(S)` и `sys\storage(S)`
читают эти поля напрямую. `sys\native(S)` возвращает native-дескриптор с вариантами из таблиц call
либо 0; `sys\capacity(S)` — резерв из таблицы арены. Все пять форм без аргумента выбирают данные
текущего вызова; для code нужен явный аргумент. Чтение не компилирует и не вызывает native.

Эти ресиверы выполняются только в code; одноимённые записи data остаются обычными данными.
Например, путь `D\length` (`D` — Structure данных) выбирает пользовательское поле, а length() — длину
данных вызова. Параметры `call` называются `args` и `code`; node сохраняет прежний смысл.

Structure и Array<@> взаимозаменяемы; числовой Array<T> хранит элементы T. Все массивы имеют переменную
длину и общий механизм выделения. sys\resize(S,n) меняет length, sys\reserve(S,n) только резерв.
Capacity хранится в таблице арены, не в заголовке. Адрес дескриптора сохраняется, storage может переместиться.
В L2 индекс, включая отрицательный, лишь вычисляет смещение. В L3 соседние [i][j] дают один линейный
индекс и одну проверку длины; L3-ссылка на элемент содержит ссылку на дескриптор массива и index,
а не storage. Сырой L2-адрес при перемещении storage не исправляется.
[Контракт](LMX_semantics.ru.md#array-capacity), [реализация OPEN](../next_core_tasks_v3.md#flat-lmx-descriptor).

<a id="get-descriptor"></a>
## Адреса полей заголовка через descriptor

`sys\descriptor(S)` возвращает обычную Structure из трёх адресов настоящих полей parent/length/storage:
Lmx **, size_t *, void **. Без аргумента выбираются данные текущего вызова, в том числе внутри тела управления.
Ни native, ни capacity в этом результате нет.

Если d = sys\descriptor(S), `\(d\length) := n` непосредственно меняет длину в S; `d\length := p`
меняет указатель в самом d. Первый пример сам по себе не выделяет хранилище: для согласованного
изменения размера служит sys\resize. Нет копии заголовка, прокси, write-back или особого присваивания.

Обычные типизированные разыменования и пути допускают запись ссылок и указателей на функции;
запрет менять голое имя Structure не запрещает путь. Глубина указателей и мерность массивов —
произвольные конечные; время жизни адресов обычное.
[Точная форма](L2_spec_ru.md#get-descriptor).

<a id="system-indexof"></a>
## Индекс поля

`sys\indexof(field parent)` возвращает физический индекс единственного вхождения `field` среди
непосредственных элементов Structure `parent`. Если поле отсутствует или та же ссылка встречается
несколько раз, операция сообщает ошибку по общим правилам отказа.

`sys\indexof(field index parent)` выбирает вхождение той же ссылки с номером `index`, считая с нуля,
и возвращает его физический индекс в `parent`. Если указанного вхождения нет, это ошибка.
Номер вхождения и возвращаемый индекс — разные величины: при вхождениях одной ссылки в позициях
2 и 5 вызов с `index = 1` возвращает 5. Обе формы получают `parent` явно; формы без аргументов нет.

Искомое поле определяется его идентичностью/ссылкой, а не совпадением имени или примитивного значения.
Поиск не следует вложенным структурам или графовым ссылкам. Для Structure и Array<@> действует один
механизм чтения непосредственных элементов. Использовать существующую адресацию; отдельная таблица
обратных индексов и её обслуживание при записях не нужны.

<a id="callable-admission"></a>
## Что проверяет интерфейс вызываемого

Методы с формалами `(int: x; int: y 5)` и `(int: x)` оба допускают `f(1)`, но
записанное у Consumer обращение `f(1; y := 25)` допускает только первый.
Проверяются необходимые явно использованные обращения, не совпадение
списков формалов и не предполагаемое поведение тела. Пользовательские
проверки поведения — отдельный этап.

<a id="method-pointer"></a>
## Имя метода и указатель на него

`myFunc()` вызывает объявленный метод напрямую. После
`@: ptr myFunc` форма `ptr()` вызывает метод через указатель; повторное
`@: ptr otherFunc` в коде присваивает существующей ячейке другой
совместимый метод (в данных повторная форма — ещё одно вхождение имени).
Голое `myFunc` или `ptr` лишь читает значение.
`(\ptr)()` — вызов после явного разыменования; `\ptr()` применяет `\`
к **результату** вызова согласно обычному приоритету, а не является особым
способом вызвать указатель.

<a id="structural-call"></a>
### Структурный вызов: `call`, `C()` и `C(args)`

Исполняется выбранная Structure `C`: она читается в роли кода, а роль данных у неё исполняет её фактический
родитель `parent(C)`. Особого слова для данных, отдельного параметра данных у `call` и подстановки данных
самим вызовом нет.

| Форма | Исполняется | Фактические аргументы | Данные |
|---|---|---|---|
| `call(C)` | `C` | не поданы | `parent(C)` |
| `call(A C)` | `C` | Structure `A` | `parent(C)` |
| `C()` | `C` | пустой хвост | `parent(C)` |
| `C(args)` | `C` | написанные `args` | `parent(C)` |

Параметры `call` называются `args` и `code`: в одноаргументной форме обязателен `code`, в двухаргументной —
`args` и `code`, поэтому `call(code := C)` двухаргументной форме не подходит. `call` исполняет саму выбранную `C`;
дочернее поле `code` автоматически не ищется. `args` — Structure фактически передаваемых значений, ровно та, которая
является структурой аргументов обычного вызова: это не объявления формалов и не сигнатура. Входные места,
требования и умолчания описывают данные, то есть `parent(C)`.

Подставить другие данные самим вызовом нельзя. Чтобы исполнить код над другими данными, сначала создают структурную
связь — объявление, копию, merge по их правилам о `parent` — и затем вызывают выбранное вхождение.
`NewContainer: ExistingCode` хранит ссылку и `parent` не меняет. Прежние `call(D C)` и `C(D)` данные больше
не подставляют: первый аргумент двухаргументной формы теперь `args`.

Любой вызов — `call`, `C()`, `C(args)`, вызов через указатель — идёт в интерпретаторе одним путём:
выбор объявления → связывание actuals с данными → общий допуск → свежий namespace → исполнение и результат.
Приём actuals не меняет исходные данные и не запускает входную инициализацию. Вызовы из test и преобразователей
проходят тот же механизм. Известные native-вызовы из native по-прежнему могут идти прямо в C, без графовой упаковки.
[Полный контракт и именованная подача](LMX_semantics.ru.md#call-receivers),
[структурный вызов](LMX_semantics.ru.md#structural-call).

<a id="root-entry"></a>
R0 — процедурный вход без данных и без пользовательских аргументов: искусственного `D = C`, пустой служебной
Structure и поля `data` у него нет. У R0 могут быть собственные исполняемые объявления и обычные доступные
ссылки; параметры запуска рантайма — не фактические аргументы пользователя. В какой роли читаются записи корня
единицы, когда у R0 нет данных, ещё не определено: [открытый вопрос](../LMX_blog/q/current/unit-root-roles-20261119.md).
[R0 без данных](LMX_semantics.ru.md#root-entry).

<a id="removed-builtins"></a>
Снято: особый смысл имени `data` (особое слово, путь `data\…`, присваивание `data := …`), отдельный параметр
данных у `call`, встроенные `fncall` и `sub`, исполняемая форма `fn`. Слово «data» как название роли и как обычное
пользовательское имя остаётся. Прежний путь `data\x` теперь записывают как `node\x` либо обычным путём от имени
Structure данных (`D\x`): это чтение исполнителя (Р107, [ответы](../LMX_blog/q/fable-self-answers-20261110.md)),
по которому `node\x` адресует поле данных вызова. [Что снято](LMX_semantics.ru.md#removed-builtins).

<a id="fn-signature"></a>
### Сигнатура `fn` и `return` в данных

`fn` — только сигнатура: шаблон входных мест по форме данных (требования, умолчания, модификаторы) вместе с
полем `return`. Есть `return` — контракт значения, нет — процедурный контракт; `sub` не нужен. `fn` ничего
не исполняет и не создаёт ни тела, ни native-входа; результат не стоит отдельной позицией после списка входов и
не становится фактическим аргументом.

```lmx
fn:
    int: a
    int: b
    return: int
```

Компактная запись — `fn(int: a; int: b; return: int)`. Структурный результат — вложенный блок внутри `return`.
Все аргументы `fn` читаются в роли данных: вложенная Structure там описание, а не запуск. `fn` входит в группу
ресиверов с аргументами в роли данных, и чтения W/E [выбора объявления](#declaration-selection) к ним не
применяются ([два вида ресиверов](LMX_semantics.ru.md#whole-arguments)). Отдельной грамматики сигнатур нет:
разбор один.

Пример целиком — контекст данных `SumContext` и вложенная Structure кода `sum`:

```lmx
SumContext:
    int: a
    int: b
    return: int
    sum:
        return: a + b
```

```lmx
SumContext\sum(a := 2; b := 3)
@: sumPtr fn(int: a; int: b; return: int) SumContext\sum
sumPtr(a := 2; b := 3)
```

Первая строка исполняет `sum` над данными `SumContext`; `SumContext()` исполнил бы другую Structure, а не найденное
поле `sum`. Во второй у `@` три аргумента: имя `sumPtr`, требуемая сигнатура `fn(...)` и кандидат
`SumContext\sum`. Требование проверяет общий `implements` по контракту вызова кандидата с учётом его `parent`:
входные поля и `return` не обязаны лежать внутри тела `sum`. Третья строка — тот же вызов через указатель.
Исполняемых `fn`/`sub` для `SumContext` или `sum` не нужно.

<a id="return-in-data"></a>
Результат описывает поле `return` в данных: `return: int` либо вложенный блок. Это объявление ничего не
присваивает и не является общей изменяемой ячейкой рекурсивных активаций. В коде `return` — ресивер возврата:
`return` без значения сохранён, `return: value` передаёт результат туда, где он описан, а достижение конца кода
`return` не создаёт. Значение могут вернуть и `call`, и обычный вызов Structure; прежний запрет «у запуска
Structure результата нет» снят вместе с `fncall`. `catch` приведён к той же модели данных и вызова с сохранением
семантики обработчика: он не исчезает вместе с `sub` и не становится обычной функцией.
[Сигнатура `fn`](LMX_semantics.ru.md#fn-signature), [`return` в данных](LMX_semantics.ru.md#return-in-data),
[`catch`](LMX_semantics.ru.md#catch-common-model).

<a id="declaration-selection"></a>
### Выбор объявления: чтения W и E

Сначала обычными правилами разрешаются имя вызываемого и набор его видимых объявлений; затем объявление выбирается
только по явно поданному материалу; затем исполняется выбранный вариант и применяется неявное связывание. Единица
выбора — (видимое объявление, чтение явных фактических, отображение фактический → формал). Чтений два, и они равноправны:

- W — «как записано»: явные фактические сопоставляются с формалами в поданном виде.
- E — «раскрытая единственная Structure»: подан ровно один фактический, он Structure или ссылка на неё и не задан
  присваиванием формалу; её непосредственные поля образуют последовательность фактических. Раскрытие один раз, на
  один уровень, граф не меняется. `f(arg := S)` чтения E не создаёт.

Нет предпочтения целой Structure, арности и первого найденного объявления; E не пробуется после неудачи W. Нет
кандидатов — отказ; ровно один — он исполняется без повторного раскрытия; больше одного — ошибка неоднозначности. Выбор
ничего не исполняет: ни присваиваний, ни значений по умолчанию, ни `test`. Автозаполнение, место вызывающего и
прежнее связывание в выборе не участвуют, отклонённого кандидата не спасают и выбор не перезапускают. Этим заменено
правило 2026-11-18 «раскрытие — попытка найти другие сигнатуры; сигнатура с одним аргументом ничего не раскрывает».
[Полный контракт](LMX_semantics.ru.md#declaration-selection).

<a id="selection-examples"></a>
Записи контрактов в таблице аналитические: это не новая грамматика объявления перегрузок.

| Условия | Вызов | Результат |
|---|---|---|
| `f(int a)` и `f(int a; int b)`, `b` необязателен | `f(5)` | два варианта, ошибка |
| `f(int a)` и `f(int a; required int b)`; `b` у вызывающего существует | `f(5)` | первый; `b` вызывающего второй не спасает |
| те же контракты | `f(5; 6)` | второй |
| только `f(required int b)` без значения по умолчанию; `b` у вызывающего существует | `f()` | нет варианта |
| только `f(required int b = 9)` | `f()` | допустимо собственное значение по умолчанию |
| только `f(int a; int b)`; у вызывающего `b = 6` | `f(5)` | выбор без `b`; затем допустимое автозаполнение может заполнить `b` |
| `S` целиком подходит одному формалу; E не подходит | `f(S)` | W; `S` передаётся целиком |
| `h(int x)`; `Arg` содержит `int: x 9`, целый `Arg` не подходит | `h(Arg)` | E с одним полем; `h` получает 9 |
| поля `S` подходят двум формалам; целый `S` не подходит | `f(S)` | E; передаются выбранные поля |
| W и E подходят одному объявлению | `f(S)` | два итоговых варианта, ошибка |
| W подходит одному объявлению, E — другому | `f(S)` | ошибка без приоритета между ними |
| `S` явно присвоена формалу | `f(a := S)` | только W, без E |
| целый `C` подходит `call(code)`, поля `C` — `call(args code)` | `call(C)` | ошибка неоднозначности |
| тот же `C` явно подан как `code` | `call(code := C)` | раскрытия нет; скрытый `args` второй формы не создаёт |
| `fn` содержит вложенную Structure | `fn(...)` | роль данных; W/E вызовов роли кода не применяются |

[Таблица в семантике](LMX_semantics.ru.md#selection-examples).

<a id="binding-places"></a>
### Связывание: собственное место и место вызывающего

Собственное объявленное место вызываемого получает значение в порядке: явный фактический → собственное готовое
значение либо описание инициализатора → [автозаполнение](#binding-autofill) значением одноимённого локального места
вызывающего → обычное неинициализированное состояние и существующие проверки `required`. Автозаполнение запрещено, если
принимающее место `private` или выбранный источник `private`; готовый инициализатор одноимённой локалью автоматически
не заменяется, а явно поданный `0` — не пропуск.

Используемое внешнее имя без собственного активного объявления связывается так: если реально видимый лексический
источник `private`, действует лексическая связь и динамической подстановки нет; иначе — [прозрачное место
вызывающего](#binding-caller-place); иначе — [прежнее связывание](#binding-fallback) (запасной путь). Во всех случаях `x`
в языке — обычная переменная своего типа `T`; скрытый адрес — деталь нативной реализации, `x` не становится `@T`.

Четыре случая на одних и тех же значениях: у вызывающего `x` равно 5, вызываемый пишет `x := 9`. Собственное объявление
`x` есть у `Ctx`; у `Free` его нет.

```lmx
Ctx:
    int: x
    code:
        x := 9

Top:
    explicit:
        int: x 5
        Ctx\code(x)
    autofill:
        int: x 5
        Ctx\code()
```

```lmx
Free:
    code:
        x := 9

Mid:
    run:
        Free\code()

Caller:
    transparent:
        int: x 5
        Free\code()
    chain:
        int: x 5
        Mid\run()
```

| Случай | Вызов | `x` у вызываемого на входе | `x` у вызывающего после `x := 9` | `@x` адресует |
|---|---|---|---|---|
| явный фактический | `Ctx\code(x)` | 5 | 5 | собственное место вызываемого |
| автозаполнение | `Ctx\code()` | 5 | 5 | собственное место вызываемого |
| прежнее связывание (запасной путь) | `Free\code()` из `Mid\run()` | 5 | 5 | собственную рабочую копию в кадре вызываемого |
| прозрачное место вызывающего | `Free\code()` из `Caller\transparent` | 5 | 9 | место `x` вызывающего |

Во всех четырёх строках `x` имеет один тип `int`; транспортный указатель в языке не виден.

<a id="binding-autofill"></a>
**Автозаполнение.** Принимающее место объявлено, но не заполнено, и фактического нет: оно получает значение
одноимённого локального места вызывающего. Это собственная ячейка, а не псевдоним, поэтому запись `x := 9` вызывающему
не видна.

<a id="binding-caller-place"></a>
**Прозрачное место вызывающего.** Собственного объявления нет, видимый лексический источник не `private`: чтение,
`x := v` и `@x` действуют на место вызывающего. Запись немедленная, без копии «на выходе»; если место вызывающего было
`uninit:int`, меняется и состояние инициализации. Связь время жизни не продлевает.

<a id="binding-fallback"></a>
**Прежнее связывание (запасной путь).** Если нового источника нет, действуют прежние источники, а значение попадает
в собственную рабочую копию в кадре вызываемого: запись меняет копию, а не исходное место, и копия никогда не
псевдоним. Для ссылки копируется ссылка, не объект. Две подмены запрещены: прозрачное место нельзя заменить
временной копией с копированием на выходе, а копию запасного пути — адресом источника. Прочитанное число может
совпасть, место записи — нет.

<a id="binding-chain"></a>
**Цепочка A → B → C.** У `A` есть `x`, `B` его не использует, `C` использует: достижимость сохранена, `B` не нужны
ни явный аргумент, ни фиктивная локаль, а статического транзитивного накопления скрытых требований нет. Если
сработал запасной путь, `C` получает собственное значение, как в третьей строке таблицы. Если у `B` собственная копия
`x`, запись `C` в место `B.x` меняет `B.x`, но не `A.x`; если у `B` прозрачная связь с `A.x`, передача места `B.x`
сохраняет адрес `A.x`.
[Порядок связывания](LMX_semantics.ru.md#binding-places), [автозаполнение](LMX_semantics.ru.md#binding-autofill),
[место вызывающего](LMX_semantics.ru.md#binding-caller-place), [запасной путь](LMX_semantics.ru.md#binding-fallback),
[цепочка](LMX_semantics.ru.md#binding-chain).

<a id="private-binding"></a>
### Ресивер private: в обе стороны

Двусторонний `private:` запрещает неявное динамическое участие конкретного объявления в обоих направлениях — для автозаполнения,
прозрачного места вызывающего и сохранённой динамической части прежнего связывания:

- источник: `private`-место вызывающего неявно не предлагается — ни значением, ни местом;
- приёмник: реально видимое `private`-объявление лексического контекста вызываемого не перекрывается значением или
  местом из динамического контекста.

Проверять только `private` у источника недостаточно: прежде чем принять внешнюю динамическую привязку, надо установить,
какое лексическое объявление реально видно и защищено ли оно. Не запрещены: явная передача, явное заполнение
принимающего `private`-места фактическим, вложенная лексическая видимость, явные пути и `node`, новое внутреннее
объявление, затеняющее внешнее `private`. `private` не заменяет `const`/`immutable`: допустимость записи определяет
контракт настоящего адресата. Это фильтр конкретного места, а не барьер имени и не проверка доступа на каждом явном
пути: `private`-источник пропускается и поиск идёт дальше, а `private` внешнего объявления не закрывает новое
внутреннее публичное `x`. Запись графа `S\private\field` не сплющивается.
[Полный контракт](LMX_semantics.ru.md#private-binding).

<a id="private-examples"></a>
Источник; вызываемый `Ctx` — тот же, что выше:

```lmx
Top:
    hidden:
        private: int: x 5
        Ctx\code()
    given:
        private: int: x 5
        Ctx\code(x)
```

В `hidden` `private`-значение не предлагается: `x` у `Ctx` на входе остаётся в обычном состоянии без значения. В `given`
явная передача разрешена: `x` у `Ctx` на входе равно 5.

Приёмник; у вызывающего публичный `x = 11`:

```lmx
Closed:
    private: int: x
    return: int
    code:
        return: x

Outer:
    private: int: x 7
    Ctx:
        return: int
        code:
            return: x

Top:
    ownPrivate:
        int: x 11
        int: r Closed\code(x := 20)
    lexicalPrivate:
        int: x 11
        int: r Outer\Ctx\code()
```

В `ownPrivate` явный фактический разрешён: `r` равно 20; без него автозаполнение значением 11 запрещено. В
`lexicalPrivate` вложенный `code` читает `private`-поле `Outer\x` лексически, динамической подмены нет: `r` равно 7, а не 11;
тот же `Outer\x` читает и явный путь. Без `private` у `Outer\x` свободное `x` связывалось бы по общему порядку, с
местом вызывающего. [Примеры в семантике](LMX_semantics.ru.md#private-examples).

<a id="shadowing-levels"></a>
### Затенение уровней

Правило автора (ТЗ §7.1):

> «объявление на вложенном уровне затеняет внешнее одноименное объявление. На одном уровне затенять нечего, используется родительское».

Правило применяется через владельца объявления и лексическую область, а не по совпадению строки где-либо в теле.
Внутреннее `Text x` затеняет внешний `int x`: это не запись `Text` во внешнюю ячейку `int`, а после выхода из
внутренней области снова видно внешнее со своим местом, режимом записи и `private`. На том же уровне затенять
нечего: повтор объявления работает с уже существующим местом по контракту ресивера — новая правая часть вычисляется и
присваивается, отсутствие правой части значение не обнуляет, второй ячейки нет. Последовательная видимость сохранена:
употребление `x` до более позднего собственного объявления разрешается обычным способом через внешний контекст.
[Затенение уровней](LMX_semantics.ru.md#shadowing-levels).

<a id="inline-declaration-control"></a>
Контрольный пример (ТЗ §7.4): в текущем кадре внешний `x = 5`; во вложенном встроенном блоке, без нового вызова
вызываемого, стоит новое `int: x` без правой части и значения по умолчанию, затем читается внутренний `x`; у
вызывающего этого кадра одноимённого `x` нет. Затенение и отдельность внутреннего места определены, спорно только
начальное значение. **Чтение исполнителя** (не решение автора; Р106,
[ответы](../LMX_blog/q/fable-self-answers-20261110.md)): место остаётся `uninit:int`, а не 5. Автозаполнение определено
между локальным контекстом вызывающего и местом вызываемого при вызове, а встроенная область остаётся в той же
активации; значение 5 потребовало бы нового правила «объемлющая встроенная область — источник автозаполнения», которое
ТЗ вводить запрещает. [Контрольный пример](LMX_semantics.ru.md#inline-declaration-control).

<a id="call-frame-20261115"></a>
### Кадр вызова

Каждый вызов создаёт собственный namespace. Входы описывают данные вызова (`parent` выбранной Structure; у `fn` —
только сигнатура, у `catch` — общая модель данных и вызова); `args` в `call` содержит фактические значения.
Краткие заголовки сохраняются. Actual заменяет соответствующее исходное объявление кадра, и его инициализатор не
выполняется. Подготовка собирает только корни data/code, без обхода ветвей и графовых ссылок; связывание полей в
исходные data/code не добавляет, а граф остаётся графом исходных форм.

При входе нет фазы исполнения инициализаторов. Готовые объявления сворачиваются при построении
чистого графа без вызовов программы; uninit:T сохраняется. Неиспользуемое вычисляемое поле data
не выполняется. Чтение получает его значение общим механизмом, как `D\field`: исполняется
написанный RHS, а не неявный вызов полученной ссылки. Для `@: fptr getFuncPtr()` запись
`fptr("hello world")` сначала получает указатель, затем вызывает полученную функцию.

Переменные и const видны с первоначального объявления вперёд в своей области и ниже.
Двусторонняя видимость сохраняется у имён Structure и callable, но не у переменной с указателем
на функцию. Новое имя ветви не выходит наружу. Повторное `int: x bump()` сохраняет вычисление,
допуск и запись существующему x; убирается только повторная C-декларация. Физические повторы
полей сохраняются и выбираются `S\[n]x`. Явный путь не ограничивается порядком объявления
голого имени. Чтение объявления через путь ничего не исполняет; RHS исполняется при достижении строки code.

Для собственного места (явный фактический, автозаполнение, прежнее связывание) голое x и @x относятся к месту
кадра, независимому от замен исходного поля сразу после входа, даже до первого чтения: сохраняется выбранное
значение либо вычисляемое описание. Это не глубокое копирование объектов по ссылкам. `x := 0` меняет выбранное
место: namespace вызова либо, при прозрачном месте, место вызывающего ([связывание](#binding-caller-place));
`D\x := 0` меняет исходный граф (`D` — Structure данных).
Для вычисляемого входа `int: x next()` обращение @x получает значение и адрес локальной ячейки.
При `@(D\field)` и исходном `int: field getValue()` адресуется запись объявления, а не результат
getValue(): явный путь ничего не исполняет (решение автора 2026-11-17; прежнее правило снято).
Готовое место адресуется непосредственно.
Время жизни обычное. @f() было исследовательским примером, не задачей отдельной поддержки или запрета.

<a id="binding-executors"></a>
Обязательное копирование исполняемого code при входе отменено, включая прежнюю копию только кода
C-функции. Независимость выбранных локальных значений/описаний сохраняется, копии окружения нет. Четыре
сочетания native → native, native → обходчик, обходчик → native и обходчик → обходчик дают одно наблюдаемое
поведение: автозаполнение опускается как параметр `T`, прозрачное место вызывающего — как скрытый адрес ячейки,
запасной путь даёт собственное место; у нативного локального места нет заголовка арены `[type][value]`. Методы
и обычные Structure компилируются общим механизмом; разные реальные подачи дают разные C-сигнатуры. Известный
native вызывает известный native прямо в C. Правка графа не обнуляет native: обновление требует явной компиляции и
границы endturn. До границы момент применения правки исполняемого графа не гарантируется. Скрытой компиляции,
постоянных кешей и копирования «на выходе» нет; прозрачная связь время жизни не продлевает, а при `yield`
выбранная связь не перевязывается к одноимённому месту нового вызывающего.

Локальные кадры не публикуются. Load-dirty, общий кеш прямого доступа и flush() отменены;
явные записи наблюдаются через реальные алиасы в порядке исполнения.
[Согласованная норма](LMX_semantics.ru.md#call-frame-20261115),
[исполнители](LMX_semantics.ru.md#binding-executors),
[единое ТЗ M14](../next_core_tasks_v3.md#native-structures),
[план нормы 2026-11-19](../next_core_tasks_v3.md#binding-callables-20261119).

<a id="flush-receiver-contract"></a>
<a id="direct-access-cache"></a>
Старые примеры flush() и общего кеша сняты: исходный граф меняется только явными операциями,
локальные переменные назад не публикуются.

<a id="native-merge"></a>
## Компиляция, изменение и следующий такт

Дескрипторы native всех Structure принадлежат таблицам call в арене. Прежняя формулировка «только fn/sub/catch
получают обычное поле native, ссылающееся на тот же дескриптор» описывает реализацию прежней нормы (до
2026-11-19); действующая норма — [что снято](LMX_semantics.ru.md#removed-builtins) и [сигнатура
`fn`](LMX_semantics.ru.md#fn-signature) (исполняемых `fn`/`sub` нет, у `fn` native-вход не создаётся); замена —
[план](../next_core_tasks_v3.md#binding-callables-20261119). Известные native-вызовы внутри native идут
прямо в C; автозаполнение и прозрачное место передаются параметром `T` и адресом ячейки
([исполнители](#binding-executors)). Копия/merge сами не компилируют новое тело и не создают
ему готовую запись в call; явно выбранная компиляция или восстановление устанавливает эту связь.

`sys\compile(S)` строит и проверяет чистый граф без запуска программы, транслирует в L1/C,
компилирует/связывает машинный код и регистрирует успешный результат; ошибки возвращаются.
Запись в граф не сбрасывает native и не запускает отслеживание. Если A прямо вызывает B,
для изменения этого вызова компилируется единица с A и B, а не только B.

`sys\endturn()` выходит к обычной границе такта через все зарегистрированные finally.
Catch этот выход не перехватывает, к месту вызова управление не возвращается; сам ресивер
не останавливает Thread/Message. До границы момент применения правки исполняемого графа
не гарантирован. После успешной явной компиляции и границы следующий вход использует обновление.
Один endturn ничего не компилирует, не проверяет и не публикует локалы.
[Полный контракт](LMX_semantics.ru.md#explicit-compilation).

`sys\toLmx(Thread)` сохраняет выбранный Thread и сериализуемое содержимое всех таблиц его арены,
в том числе таблиц call/native. После перезапуска на той же платформе используются готовые бинарники
по идентификаторам модуля/входа, без повторной трансляции. Для произвольной S внешние таблицы
не добавляются скрыто; R0 — частный Thread, а не единственный корень такого сохранения.

<a id="factory-result"></a>
## Возвращённый метод

В code строка `@: add5 makeAdder(5)` **вызывает** фабрику и сохраняет возвращённый
метод. Затем `add5(1)` вызывает его через ссылку. Запись данных
`add5: makeAdder 5` лишь объявляет Structure `add5` и фабрику не вызывает; среди
исполняемых записей та же запись — вызов своей головы `add5`: вызываемое (метод
или указатель на него) вызывается, а обычная Structure исполняется в роли кода
([структурный вызов](#call-receivers)). Прежняя фиксация «обычная Structure запускается над данными
после двоеточия; аргумент записи один, `data`, поэтому для Structure `add5` два
поля `makeAdder` и `5` — ошибка»
([журнал](../LMX_blog/2026-11-11.md#structure-call-by-name); чтение
исполнителя — [ответы](../LMX_blog/q/fable-self-answers-20261110.md), Р21,
п. 4 и 6) описывает прежнюю норму (до 2026-11-19); действующая норма —
[структурный вызов](LMX_semantics.ru.md#call-receivers); замена —
[план](../next_core_tasks_v3.md#binding-callables-20261119). Если тело
возвращённого метода читает свободное `n`, источник выбирает [порядок связывания](#binding-places): лексический
`private`-источник, иначе место вызывающего, иначе прежнее связывание.

<a id="dynamic-fallback"></a>
## Динамический и лексический источники

Пример не является синтаксисом LMX: в скопированном лексическом контексте
`x = 10`, вызывающий передаёт `x = 25`. Свободное `x` читает 25;
`node\x` явно читает 10. При следующем вызове с `x = 40` свободное
`x` читает 40, а без динамического источника — лексические 10. Это общий
[порядок связывания](#binding-places): свободное `x` без собственного объявления берёт место вызывающего
(запись в него меняет `x` вызывающего сразу), а без такого источника прежнее связывание даёт собственную копию.

<a id="message-conversion-context"></a>
## Контекст преобразований Message

Схема `a → int` в Message A и `a → String` в Message B — не синтаксис
LMX. Один метод с требованием `a` получает смысл из контекста данного
Message; B не наследует преобразования A из-за доставки письма. Примитивное
`Foot → Meter` не доказывает `implements` для двух произвольных Structure.
При вызове могут понадобиться два разных маршрута: аргумент
`int → double` и результат `double → int`. Оба должны быть доступны в
контексте соответствующего Message.

<a id="post-transport"></a>
## post: один вызов, несколько доставок

Три обращения `getPixel` исполняются трижды. Если у каждого результата
три адресата `answer`, получаются три исходных ответа и девять доставок,
а не девять исполнений. Связь ответа с запросом задаёт исходный Message,
не позиция ветки и не новый числовой ID. `answer` готовят до отправки
`ask`; недоставка одного запроса не останавливает остальные.

`undelivered` получает уже сформированные аргументы исходного запроса;
объявленный отказ идёт в `catch`. Timeout считают от фактической отправки:
при пороге 500 мс обработчик может наблюдать 512 мс, но само пороговое
поле остаётся 500. Поздний ответ не удаляется автоматически. Полный
контракт и матрица T01–T26 — в [семантике](LMX_semantics.ru.md#thread-message-api)
и [почтовом плане](../next_core_tasks_v3.md).

<a id="tables-and-registries"></a>
## Таблицы и провайдеры как данные

Явная Table может дать написание `u8 → "uint8_t"` или ключ реализации
`plus[decimal][int] → decimal_int_add`. Она не объявляет типы, не создаёт
runtime-пространство имён и не ищет провайдеров автоматически. Порядок
источников, разрешение конфликтов и маркер отсутствующей ячейки задаёт
выбранный потребителем профиль, а не универсальный скрытый реестр.

## Приоритеты, исполнение по требованию и явная группа в выражении

Приоритеты и ассоциативность операций — как в Си; у присваивания приоритет низший, и его правая часть — всё
выражение справа до конца группы. Значения вычисляются по требованию: если ресиверу нужен результат другого
ресивера, тот исполняется первым, каким бы ни был его приоритет, и исполняется один раз. Чистый граф при этом
не меняется.

```text
f(1 + v := 2 + 3)
→ f(1 + (v := 5))    # v = 5
→ f(6)

f(1 + (v := 2) + 3)
→ f(1 + 2 + 3)    # v = 2
→ f(6)

f(v := 2 + 3; 6)
→ f(v := 5; 6)
```

Первые две записи подают один аргумент 6 и различаются значением `v` в data `f`: скобки задают границу
вычисления. Третья запись подаёт два аргумента: присваивание на самостоятельной позиции — именованный аргумент.
Встроенное присваивание отдельным аргументом не становится, и одноимённая переменная вызывающего не меняется.
Короткое замыкание сохраняется: в `0 && (x := 1)` и `1 || (x := 1)` переменная `x` не меняется.
`while ((c := getchar()) != EOF)` на каждой проверке читает один символ, записывает его в `c` и сравнивает.
`sys\name(foo)` даёт имя идентификатора строкой `"foo"` и значение `foo` не читает. Пользовательский операнд
регистрируют с функцией реализации и приоритетом: после `sys\operand: foo new_op p` запись
`(foo 1 2 3 4)` вызывает `new_op` с одним массивом из четырёх ссылок на значения; приоритет существующего
операнда даёт `sys\priority("+")`. Норма —
[книга](LMX_semantics.ru.md#assignment-inside-expression).
