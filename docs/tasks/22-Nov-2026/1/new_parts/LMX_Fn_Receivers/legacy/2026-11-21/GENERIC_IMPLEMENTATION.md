# Общие функциональные ресиверы: границы реализации

`generic_functions.lmx` заменяет бинарные демонстрации с `int` настоящими алгоритмами для произвольного конечного числа входов и разных требований типов. Это исходники целевой реализации ТЗ: они зависят от четырёх явно предложенных методов `FxKernel`; готовность существующего ядра и выполнение этих примеров не заявляются.

## Публичные точки входа

| Метод | Полученный callable |
|---|---|
| `FxLambda\lambda(operation := F)` | По одной обязательной позиции на ступень; последняя возвращает исходный `R`. Для нулевой арности — отложенный вызов без аргументов. |
| `FxPartial\partial(F; prefix)` | Связывает первые `k` из `n` позиций, оставляет `n-k` входов и исходный `R`. Полный префикс даёт callable без аргументов. |
| `FxFlip\flip(operation := F)` | Переставляет первые два входа вместе с их типами и подстановкой значений. Остальные позиции и `R` сохраняются. При `n<2` — `FxArity`. |
| `FxUncurry\uncurry(operation; contract; failures)` | Создаёт функцию полной явно заданной сигнатуры и вызывает ровно столько ступеней, сколько в ней входов. Нулевая арность вызывает исходную функцию без аргументов. |

`uncurry` всегда принимает три аргумента. Автоматического одноаргументного варианта по скрытой регистрации фабрики нет. Его протокол промежуточной ступени — `Ti -> @`, последней — `Tn-1 -> R`. Все цепочки, созданные `lambda`, удовлетворяют этому протоколу. Для внешней цепочки с уточнённым требованием к промежуточному результату нужен обычный адаптер: имеющаяся норма `signatureTypes` не обещает стирать такое требование при сравнении сигнатур.

Публичные метки построенных функций — `p0`, `p1`, … . Все оставшиеся входы обязательны и `private`; исходные необязательность и вычисляемые defaults не переносятся. При вызове исходной функции fn-алиас отображает эти метки на позиции её собственного DATA. Источник DATA не подменяется.

## Что именно написано на LMX

На LMX реализованы копирование массива ссылок без копирования их целей, проверка длины префикса, отдельное принятие его значений через обычный типизированный callable, построение каждой сигнатуры обычным `Built :: data`, конкатенация строк, запись десятичных индексов, генерация тел с явно именованными аргументами, построение цепочки, перестановка позиций и последовательный вызов стадий.

В файле нет `makeLambda`, `invokeValue`, второго диспетчера вызовов или общей замены результата всех пользовательских функций типом `@`. Такой результат имеют фабрики, возвращающие callable, промежуточные ступени и внутренний получатель записи. Финальная ступень, `partial`, `flip` и `uncurry` сохраняют полный результат исходного контракта, включая структурный и процедурный.

Четыре зависимости от ядра:

1. `FxKernel\signature(subject)` — открывает уже существующий анализ полной сигнатуры. Поля результата: `inputTypes`, `resultType`, `hasResult`, `names`, `throws`.
2. `FxKernel\normalizeType(token)` — нормализует предложенные формы обозначения типа. Сырые неинициализированные `@`-записи нормализуются в явных местах исходника; `FxSignatures\make` принимает уже нормализованные требования.
3. `FxKernel\signatureData(inputs; result; labels)` — строит обычное DATA-описание. Именованную сигнатуру создаёт последующий штатный `signatureTypes`.
4. `FxKernel\callable(contract; labels; bodyGraph; state; failures)` — соединяет обычные owner, DATA и CODE с правильными лексическими ссылками. Тело получено общим `sys\fromLmx`, а `state` доступен как `node\private\state`. Повторного использования несовместимого native-прототипа и автоматической компиляции нет.

Создание графа сначала связывает полное окружение тела, включая `state`, и лишь затем анализирует разрешение операндов. Один `sys\fromLmx` сохраняет синтаксические группы и не обязан разрешать `node\private\state\record` до установки этого окружения.

## Захват и время жизни

`prefix` содержит готовые типизированные записи значений в Structure/Array<@>. Плотный числовой массив не превращается в такой префикс. При приёме каждой позиции созданный получатель `Ti -> @` выполняет обычную проверку/преобразование типа, а postfix operand `record` получает запись принятого значения по существующему prepared-протоколу.

Для `(value record)` общий обработчик выражений передаёт присутствующий пустой массив `right`. Это не отсутствующий или неинициализированный аргумент: `length(right)` определён и равен нулю.

Для примитива хранится принятое значение; для ссылки сохраняется её цель. `copy(prefix)` намеренно не применяется, поскольку это копировало бы графы целей. Копируются лишь массивы ссылок на уже захваченные записи. Каждая ветка цепочки получает отдельный такой массив.

Ядро должно обеспечить обычное время жизни опубликованной записи значения. Нельзя сохранить адрес native-слота завершившейся или переиспользуемой активации; нельзя начать читать тип перед сырым адресом временной переменной. Повторный вызов того же intermediate callable не должен менять примитивную запись предыдущего захвата. Это проверка существующего общего механизма материализации адресуемых значений, а не лицензия на новый механизм боксов специально для `lambda`.

## Ошибки и эффекты

Ошибки библиотечных фабрик — `FxIndex`, `FxArity`, `FxRecordArity`; методы предложенного bridge объявляют `FxTypeToken` и `FxKernelFailure`. В `FxKernel\callable` передаётся массив строк имён failures, который общая сборка графа интернирует для обычного `throws`.

Промежуточные `lambda`-ступени объявляют исходы построителя и `record`; исходная функция на них не вызывается. Финальные адаптеры наследуют имена исходов исходной функции. Для `uncurry` вызывающий явно передаёт совокупность исходов всей цепочки: `signature(F)\throws` одного первоначального `F` недостаточно, если промежуточные ступени могут сообщать ошибки создания следующих функций.

Все actuals плоского `uncurry` принимаются его обычным вызовом до запуска последовательности стадий. Он не обещает ту же последовательность эффектов, что отдельно написанные вложенные вызовы, где выражение следующего аргумента вычисляется между стадиями. Захват префикса не откатывает уже выполненные эффекты приёма предыдущих позиций, если последующая позиция не прошла проверку.

## Проверка исходников

Встроены примеры трёх разных входов (`int`, `double`, строка), результата `double`, повторного использования ветви, пустого и полного префикса, функций без аргументов, процедуры, структурного результата и результата, который сам является callable. В последнем случае библиотека завершает цепочку по арности и возвращает callable, не исполняя его автоматически.

Для трёх входов генерируемое тело `uncurry` имеет следующий вид. Разные имена `fx_stage0` и `fx_stage1` нужны потому, что их требования типов различны: повторное объявление одного места не должно менять его первоначальный контракт.

```lmx
private: @: fx_current node\private\state\operation
private: @: fx_stage0 node\private\state\stages[0] fx_current
fx_current := fx_stage0(p0 := p0)
private: @: fx_stage1 node\private\state\stages[1] fx_current
fx_current := fx_stage1(p0 := p1)
private: @: fx_last node\private\state\stages[2] fx_current
return: fx_last(p0 := p2)
```

Механически проверены литералы, пары скобок, отступы и явные завершители при уменьшении вложенности больше чем на один уровень. Это статическая проверка текста. Ни LMX-парсер, ни интерпретатор, ни native backend здесь не запускались: четыре предложенных bridge-метода ещё должны быть реализованы и проверены по ТЗ.
