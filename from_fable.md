## 7. Как принимать сдачу помощника

Порядок, которым приняты срезы этого дня. Все команды — из каталога `S`; префикс запуска — `0 entry 0 --`.

1. Проверить, что сборочных процессов нет (`lmxtool-tool`, `l2trans`, `gcc`, `cc1`, `graph_trans-prod`), и что
   `HEAD` равен `origin/main`.
2. Дифф дерева сравнить со сданным по SHA-256: `git diff -- <файлы>` и файл диффа из квитанции. Список новых
   файлов сравнить со сданным списком.
3. Манифест: `T ... manifest R/selfbuild/inputs.list R/selfbuild OUT.sha256`, затем
   `T ... verify OUT.sha256 R/selfbuild` и `T ... verify OUT.sha256 S`. Число файлов и SHA сверить со сданными.
4. Хэши tool, frontend, runtime, Graph. Runtime, собранный итоговым frontend, сравнить с кандидатом через `cmp`;
   Graph — после обнуления в PE полей TimeDateStamp и CheckSum.
5. Прочитать дифф: нет ли веток по имени ресивера, битовых флагов вместо нового кода типа, фиксированных
   пределов; закрыватель `---` только при спуске на два уровня; новых `end:` нет.
6. Свой прогон строк на итоговой цепочке — hosted frontend из итоговых исходников, runtime и Graph, собранные
   им: `LMX_TOOL=<tool> sh rows_run_any.sh МЕТКА FE RT GRAPH ИМЕНА ЗАКРЕПЛЕНИЯ`. Гнать порциями по 36 строк на
   переднем плане, порция идёт около 50 секунд. Старые строки обязаны совпасть с базой, новые — с закреплением.
   Другой запуск, которым принят срез отказов: список команды `checks` (строка — путь программы, ожидание и три
   числа закрепления) и `sh steps/witnesses/one-graph-level2-record-20261118/graph-baseline-rows.sh СПИСОК С ПО
   ПРЕДЕЛ_СЕКУНД ЖУРНАЛ S TOOL МЕТКА` — каждая строка под своим пределом времени.
7. Свои пробы интерпретатором: `GRAPH 0 entry 0 -- run ФАЙЛ 1`, запуск из `S/src`. Программа — с ведущей группой
   `Observed` и строкой `@: shared data[0]`; Structure-аргументы объявляются в данных метода как `Имя(поля)`.
   Граф строки-отказа сверяет сама команда `graph-check` — начиная с tool `ps-tool-r101`.
8. Мутанты помощника: последняя строка по каждому должна быть KILLED. Строке SURVIVED не верить и не отмахиваться
   от неё: запустить Graph мутанта напрямую на строках-кандидатах. Правило, у которого мутант неотличим от
   кандидата, получает свидетеля или снимается.
9. Свидетельство в `steps/witnesses/<имя>/` и правки READ.ME, плана, чек-листа, `steps/current.md`, журнала
   ответов и этого файла — скриптом, сначала на копиях. Пересоздать `selfbuild/inputs.sha256`.
10. `git add` по точному списку, проверка документов, и только при её успехе коммит и пуш одной цепочкой через
    `&&`. Перед коммитом вывести `git diff --cached --name-status` и сверить число файлов.

Проверка документов: создать каталог `O/docs-indexN`, перейти в него и выполнить
`T2 0 entry 0 -- docs check R R/provenance/semantics-sources/l1.txt R/provenance/semantics-sources/older.txt
C:/Git/cmd/git.exe O/docs-indexN`. Подпись коммита: `git -c user.name=fable commit`, заголовок с `[fable]`.

Мои скрипты приёмки лежат копиями в `O/scratch-backup-20261118/`: `rows_run_any.sh`, `accept_a1.py`,
`accept_d1.py`, генераторы проб `gen_prq33.py` — `gen_prq36.py`, правки документов `edit_r97.py` —
`edit_r102.py`.

## 8. Как вести помощников

- Задача — отдельным сообщением: норма со ссылками, границы файлов, что сдать, что не трогать. Жетон конвейера
  передаётся словами и только одному.
- Вопрос помощника сначала решать самому по написанной норме. Перед любым решением, которое закрепляет ожидаемое
  значение, искать в журнале за все дни и в книге по существительным механизма. Ответ записывать в
  [журнал ответов](LMX_blog/q/fable-self-answers-20261110.md) с пометкой «ответил fable».
- Вопрос, который норма не решает, сразу класть в `LMX_blog/q/current/`, коммитить и называть автору в чате —
  с минимальной программой и наблюдаемыми вариантами. Работу при этом не останавливать.
- Утверждение помощника о сегодняшнем поведении проверять однострочной пробой, прежде чем повторять автору.
- Субагентов и ревьюверов не запускать — ни мне, ни opus, ни sonnet. Проверка — настоящими прогонами.
- С 2026-11-19 помощник — отдельный запуск скрипта, а не живая сессия:
  `python C:/claude/new/{sonnet,opus,haiku}_chat.py --session ИМЯ [--new] --cwd C:/Nyasha_Planet/LMX --prompt-file
  ПОРУЧЕНИЕ.md --out ОТВЕТ.md`. Запуск одноразовый: процесс выходит на первом законченном ходе помощника.
  Одновременно — не больше одного opus и одного sonnet; haiku — для коротких задач, её может запускать и помощник.
- В поручении писать прямо: ждать сборку и прогоны на переднем плане, не вызывать `ScheduleWakeup` и не «закончить
  ход до уведомления» — в одноразовом запуске пробуждений нет, помощник просто выходит без сдачи.
- Если помощник оставил фоновую команду, следующий запуск той же сессии может выйти через несколько секунд с
  пустым ответом: первый ход забирает служебное уведомление о ней. Тогда то же поручение отправить ещё раз.
- Сдачу помощник кладёт в каталог квитанций с файлом хода (`PROGRESS.md`) и отчётом (`REPORT.md`); по файлу хода
  видно, где он остановился, если запуск оборвался.
- Сборка помощника и проверка документов не идут одновременно. Протокол: перед `docs check` создать файл-метку
  `O/tz-20261119/docs-check.running`, убедиться, что сборочных процессов нет, после проверки метку удалить;
  помощник перед сборкой проверяет, что метки нет.
