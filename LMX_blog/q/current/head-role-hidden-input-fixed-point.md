# Роль головы `h: хвост`, когда вход `h` ничем заранее не установлен

Статус: вопрос автору передан через Codex 2026-10-03 (FABLE-CODEX-20261003-04);
ответа пока нет. Это узкий вопрос о правиле языка, не выбор следующего тикета.
До ответа спецификация не меняется, ожидания перечисленных строк не
переворачиваются.

## Уже установленные правила

- Неизвестная голова сохраняет общее построение именованной Structure с её
  записанным содержимым; примитив получает присваивание по своему контракту
  ([разрешение головы](../../../next_core_tasks_dictionary_v2.md#head),
  [семантика §9](../../../docs/LMX_semantics.ru.md)).
- Присваивание уже разрешённому скрытому входу меняет только значение текущей
  активации: поля не создаётся, обратной записи вызывающему нет
  ([рабочее состояние](../../../docs/LMX_semantics.ru.md#dynamic)).
- Одного лишь одноимённого локального значения у вызывающего недостаточно,
  чтобы установить вход. В `unit_free_write` и
  `unit_free_write_literal_refused` у `peek` нет установленного `k`, и `k: 1` /
  `k: 1U` определяет Structure с литеральным телом, хотя у вызывающего есть
  `int: k 5` ([уточнение статуса](../../../steps/free-names.md)).
- Положительный свидетель `unit_graph_hidden_literal_binding`: видимое внешнее
  `unsigned: k 3U` устанавливает привязку; значение 5 вызывающего выигрывает
  при выборе значения входа; вызываемое возвращает локально изменённое 1;
  5 у вызывающего и 3 в лексическом источнике не меняются; поля `peek\k` нет.
- Исполняемое свободное чтение имени до первой записи — самостоятельный факт
  использования входа (так в `unit_own_dirty_rhs`: `if: quote = 65` стоит до
  `quote: 88`).

## Что измерено в реализации

Сбор объявлений (`l2_collect_asgn_binds`) выполняется до того, как установлен
хоть один динамический вход, поэтому `l2_local_ns_shape` отвечает «определение»
для любой такой строки, и последующее чтение имени находит локальную строку.
Это дефект порядка для уже установленных входов, он записан в
[журнале исправления](../../../steps/critical-graph-pointer-fix-20261002.md).
Он не решает вопрос ниже: там роль не установлена ничем, кроме самой строки
или более позднего чтения.

Красные строки, ожидающие ответа: `unit_colon_hidden_update`
(`hidden: hidden + 1`, затем `return: hidden`) и `target` в `unit_free_conv`
(+ walk) (`k: j`, затем `return: k`).

## Вопрос

В этом примере у f нет формала x, видимого внешнего x или чтения x до строки x: j:

```text
fn: f () int
    int: j 3
    x: j
    return: x
fn: g () int
    int: x 4
    return: f()
```

Может ли последующее return: x установить x как скрытый вход f, так что x: j
является присваиванием и f возвращает 3, не меняя x=4 у g?
Или x: j при отсутствии уже установленной привязки объявляет именованную
Structure x, а return: x затем ошибочен как возврат безрезультатного callable
вместо int?

Тот же вопрос для первой строки hidden: hidden + 1: может ли чтение hidden
внутри её собственного хвоста установить скрытый вход, или это круговое
обоснование роли?

Не предлагается правило «есть одноимённое значение у любого вызывающего»: оно
противоречит уже закреплённому случаю k: 1, который остаётся объявлением при
неустановленном k.
