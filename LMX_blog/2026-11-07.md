# Технические уточнения автора — 2026-11-07

## Вычисляемый дефолт формала: момент вычисления

Источник: ответ автора в чате Codex 2026-11-07 на вопрос, который Codex задал по вопросу Opus о формах дефолта
(срез 297, FORMAL-DEFAULT-FORMS); передан Opus сообщением CODEX-OPUS-DEFAULT-TIMING-AUTHOR-20261107-01. Вопрос
Codex автору (не слова автора):

> Как должно работать вычисляемое умолчание fn: f (int: a make_default()) int, если make_default() меняет счётчик?
> Книга говорит, что сигнатура не исполняется, но не определяет момент вычисления такого умолчания. Нужно выбрать
> правило языка; остальные работы продолжаются

Выбранный автором ответ, дословно:

```text
Вычислять при каждом вызове f без аргумента a
```

Следствия, которые Codex назвал при передаче (не слова автора): построение описания `f` не выполняет
`make_default()`; каждый достигнутый вызов `f` с пропущенным `a` вычисляет дефолт для своей активации один раз, с
обычными эффектами и допуском результата; явно поданный `a`, в том числе 0, дефолт не вычисляет, неподходящий явный
аргумент дефолтом не заменяется; первое вычисление не кэшируется, остаток рабочей ячейки прошлого вызова дефолтом не
становится; источник берётся у фактически выбранного callable. Книга: [вызываемые выражения, дефолт формала](../docs/LMX_semantics.ru.md#callables).

## Порядок аргументов вызова и проверка его формы

Источник: ответ автора в чате Codex 2026-11-07 на два вопроса, которые Codex задал по вопросу Opus (срез 301,
CALLABLE-PLACE-TYPED-RECEPTION); передан Opus сообщением CODEX-OPUS-301-AUTHOR-ORDER-SHAPE-20261107-01. Вопросы в
передаче Codex (сообщение CODEX-OPUS-301-PARTIAL-ORDER-ROUTES-20261107-01; не слова автора): (а) ABXY — все
фактические, затем преобразования, либо AXBY — каждый фактический сразу с преобразованием, едино для обычного вызова
и изменяемого callable-места; (б) при отсутствии именованного параметра x у выбранного callable должен ли
`f(x: touch())` выполнить `touch` перед отказом `call`.

Выдержка из ответа автора (технический фрагмент; фраза о передаче и продолжении работы опущена), дословно:

```text
Каждый аргумент сразу преобразуется, затем вычисляется следующий. Имена и форму вызова проверять до вычисления аргументов.
```

Следствия, которые Codex назвал при передаче (не слова автора): выбран AXBY — фактический вычисляется и сразу
принимается с необходимым преобразованием, затем вычисляется следующий; правило едино для обычного вызова и вызова
через изменяемое callable-место, для native и обходчика; отказ вычисления или приёма текущего аргумента — следующие
не вычисляются, тело вызываемого не начинается; выбор callable — один раз, до фактических. Имена и форма проверяются
по фактически выбранному callable до эффектов аргументов: `f(x: touch())` без формала x отказывает без `touch()`;
соответствие имён и позиций, повторная подача одного формала и наличие обязательных входов с учётом умолчаний — на
этой стадии; это проверка достигнутого вызова, не анализ будущих тел; преобразования значений до вычисления этих
значений не исполняются; вычисляемое умолчание по-прежнему вычисляется при каждом вызове без аргумента. Книга:
[вызываемые выражения](../docs/LMX_semantics.ru.md#callables).

## Имена аргументов в выполняемом коде

Источник: замечание автора в чате Codex 2026-11-07 на объяснение Codex нынешнего механизма именованных аргументов
(срез 301); передано Opus сообщением CODEX-OPUS-301-AUTHOR-NAMED-ADDRESSES-20261107-01. Строка в кавычках в пункте 1
— слова Codex, которые автор цитирует. Дословно:

```text
1) "native передаёт имена отдельным массивом строк, обходчик хранит имя у узла `NAMED`.   " -- куда передаёт, что за узел named, если есть АДРЕС структуры? Вы так и не убрали имена из выполняемого кода (как native так и байт-кода интерпретируемого) ?
2) Нет, я имел в виду транслируемую запись просто с указанием имени аргумента, возможно вы вызов с именованными агументами не поддержали?
```

Пояснение и выводы Codex при передаче (не слова автора): автор говорит об обычной транслируемой записи с именованным
аргументом, не о вычисляемом имени, нового синтаксиса не нужно; правила AXBY и проверки имён и формы до вычисления
аргументов остаются в силе. Написанное имя разрешается на стадии построения и связывания к конкретному месту;
выполняемый вызов использует подготовленную адресную привязку, а при изменяемом callable — установленное соответствие
выбранному вхождению (карта implements между адресами полей описания и кандидата), без строкового поиска формалов при
исполнении и без замены строк хэшами или intern-ID с тем же поиском. Книга: [семантика](../docs/LMX_semantics.ru.md).
Формулировку о хэшах и intern-ID Codex позже сузил (CODEX-OPUS-301-IDENTITY-MAPPING-CLARIFICATION-20261107-01), а
поручение автора о кодах идентификаторов (следующий раздел) её заменило.

## Коды идентификаторов вместо имён-строк

Источник: прямые сообщения автора в чате Codex 2026-11-07 (срез 301), переданные Opus сообщениями
CODEX-OPUS-301-IDENTITY-MAPPING-CLARIFICATION-20261107-01, CODEX-OPUS-AUTHOR-INCREMENTAL-IDENTIFIER-IDS-20261107-01,
CODEX-OPUS-AUTHOR-SAME-SPELLING-SAME-ID-20261107-01 и CODEX-OPUS-AUTHOR-ALL-IDS-TWO-TABLES-20261107-01. Четыре
отдельных сообщения автора, по порядку.

Вопрос автора после замечания об именах аргументов (вопрос, не решение; ответ Codex автору был консультативным),
дословно:

```text
Возможно, есть ситуации когда адресов не достаточно, нужны общие идентификаторы?
```

Поручение автора, дословно:

```text
1) Сделайте максимально простой механизм. Заведите тупо уникальный код для каждого единичного идентификатора, не хеш-код, а инкрементируйте просто, ВСЁ,  и уберите наконец строки отовсюду.
2) А native коду зачем имена-строки? Что он с ними делает?
```

Уточнение автора к поручению, дословно:

```text
то есть строка id1 будет иметь код какой-то единый в любом месте , вот и всё
```

Следующее уточнение автора — выдержка (два технических фрагмента одного сообщения; фраза между ними о пропавшем
сообщении опущена), дословно:

```text
Это касается всех идентификаторов, не только именованных аргументов. Проверьте и native, и интерпретатор, чтобы строковых сравнений имён больше не осталось.
```

```text
Таблиц code->name и name->code только две, и обе информационного характера для дальнейших toLmx fromLmx, в остальных местах никаких name нигде не должно быть, code вычисяйте просто инкрементом, никаких хешкодов и сравнений строк
```

Пояснения Codex при передаче (не слова автора): код назначается написанию идентификатора — одинаковое `id1` в любом
месте, независимо от файла, метода, аргумента, формала и области видимости, имеет один код; это не код вхождения,
объявления или связанной переменной и не квалифицированное имя; разные места с одним написанием различаются
контекстом разрешения и адресами; новое написание получает следующий код, без хеширования. Правило охватывает все
идентификаторы (головы и ресиверы, формалы, поля, свободные и скрытые входы, пути, throws/catch) и оба исполнителя; за
пределами двух информационных таблиц нет параллельных полей и массивов написаний, таблиц имён по подсистемам и
запасного сравнения строк, идентификаторы не маскируются сырыми адресами строк; пользовательские строковые значения —
не имена идентификаторов; для уже связанных мест действует подготовленное адресное соответствие. На вопрос 2 Codex
проверил: строки нужны только оставшейся реализации поиска и сопоставления формалов (`l2_bn` →
`lmx_call_bind_actuals` → `lmx_callable_bind_prefix` → `lmx_callable_named_formal` → `lmx_implements_same_name`), а
не исполнению самого тела native. Прежнюю рекомендацию Codex против intern-ID поручение автора заменило. Книга:
[имена и пути](../docs/LMX_semantics.ru.md#fields).
