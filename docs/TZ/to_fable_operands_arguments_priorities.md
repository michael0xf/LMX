## 1. Задача и обязательные изменения

Реализовать и согласованно описать следующие изменения:

1. Обнаруживать пользовательский операнд через обычное разрешение имени метода и структурную проверку его DATA. Имя операнда совпадает с именем метода; `sys\operand` и отдельная регистрационная запись удаляются.
2. Использовать два операндных входа: ссылку `left` и массив ссылок `right`. Отдельный шаблон заголовка дан в §2.2. Поля `PASS_ARGS_AS_IS` и `PRIORITY` обязательны; проверка шаблона не заполняет отсутствующие поля.
3. `const: int: PASS_ARGS_AS_IS 0` выбирает подготовленные значения, `const: int: PASS_ARGS_AS_IS 1` — передачу исходных аргументных вхождений «как есть». Другие значения не допускаются. Числовой приоритет задаётся отдельно через `const: int: PRIORITY ...`.
4. Метод возвращает обычное значение объявленного типа. `return: int` даёт число, `return: @` — обычную ссылку. Физическое представление результата в типизированном storage обеспечивает общий механизм expression.
5. Предоставить `sys\eval(fragment)` как доступ к единому исполнителю expression для явного получения значения сырого аргумента с сохранением его исходного контекста. Разыменование `\` остаётся обычным разыменованием.
6. Сохранить обычную передачу ссылки `@: ptr Struct`. Префиксное `@Struct` означает явный числовой адрес; пример: `int: value 1 + @Struct`.
7. Различать самостоятельный именованный actual и присваивание внутри выражения actual. Встроенное присваивание пишет в соответствующее DATA и возвращает значение в выражение; отдельного actual из него не возникает.
8. Привести приоритеты и ассоциативность поддерживаемых операций к Си; для `**` сохранить Python-подобное правило §6.2. Необходимые значения получать по требованию, с однократностью внутри конкретного вычисления и сохранением короткого замыкания.
9. Поддержать `sys\name(identificator)` — написание идентификатора как обычную LMX-строку — и `sys\priority(name)` — приоритет доступного операнда по строковому имени.
10. Сохранить отдельный смысл `fn: name data`: позиционная сигнатура вызова и её ветвь общего `implements`. Обнаружение операнда использует структурный шаблон, а не обязательную специальную fn-сигнатуру.

Один общий парсер сохраняет написанный чистый граф. Роли, приоритеты и планы исполнения определяются после P0 и не дают ему права удалять контейнеры или переустраивать `parent` и `length`. Общее раскрытие Array в аргументы не вводится. Обычные правила приёма одной Structure сохраняются.


## 2. Пользовательский операнд как обычный метод

### 2.1. Разрешение имени и роль

Общий механизм разрешает имя в текущем namespace. Для найденного исполняемого кандидата `C` его DATA остаётся фактическим `parent(C)`. Подходящее описание входов и постоянных свойств позволяет использовать этот метод в операторной позиции expression.

Импорт, ссылки, затенение и `private` работают по общим правилам. Потребляющая позиция различает передачу ссылки, обычный вызов и применение операнда:

| Запись | Смысл |
|---|---|
| `@: ptr add` | Сохранить обычную ссылку на метод; ничего не исполнять |
| `add(...)` | Явный вызов с обычными actuals |
| `a add b` | Операторное применение подходящего метода |
| `@add` | Явно получить числовой адрес |
| `\ptr` | Обратиться по ссылке; код этим не запускается |

Отдельный реестр имён операндов не нужен. Производный индекс разрешённых описаний допустим в рамках существующего анализа. Готовая ссылка на callable не становится вызовом только потому, что потребителю нужно значение.

### 2.2. Отдельный структурный шаблон заголовка

Минимальное общее требование оформляется обычной структурой:

```lmx
operand_template:
    @: left
    []: @ right
    const: int: PASS_ARGS_AS_IS
    const: int: PRIORITY
```

Это шаблон входов и постоянных свойств в DATA, а не полная fn-сигнатура, исполняемый метод или готовый набор значений для вызова. Все четыре поля должны присутствовать в описании кандидата. Отсутствие инициализаторов в шаблоне означает, что он не фиксирует одно конкретное значение свойств; у используемого операнда их допустимые постоянные значения должны быть определены. У `left` и элементов `right` могут быть дополнительные требования к адресуемым значениям, например `int`; они проверяются обычным механизмом приёма.

Тип результата в общем шаблоне намеренно не фиксируется. Наличие результата и его совместимость с потребителем проверяет обычный контракт использования callable в выражении. Конкретный метод объявляет, например, `return: int`, `return: @` или другой допустимый тип. Одно совпадение с шаблоном заголовка не разрешает процедуре без результата поставлять значение. Запись `return: @` не является заменой «результат любого типа».

Если для конкретного потребителя требуется также целочисленный результат, полный специализированный шаблон можно записать отдельно:

```lmx
int_operand_template:
    @: left int
    []: @(int) right
    const: int: PASS_ARGS_AS_IS
    const: int: PRIORITY
    return: int
```

Этот второй шаблон ограничивает адресуемые входные значения и результат. Он подходит числовому примеру из §3.5; общий сырой обработчик произвольных форм использует общие ссылки из первого шаблона и собственное объявление результата.

Шаблон сравнивает заданные им имена и требования. Тело реализации и дополнительные поля не становятся частью требования только из-за своего присутствия у кандидата. Если тело или вложенное поле явно включено в сам шаблон, оно участвует в обычной структурной проверке.

### 2.3. Обязательные поля и значения

| Поле | Обязательный контракт кандидата |
|---|---|
| `left` | Ссылочное входное место; позиция 1 операторной подачи |
| `right` | Входной массив ссылок; позиция 2 операторной подачи |
| `PASS_ARGS_AS_IS` | Готовое постоянное целое значение `0` или `1` |
| `PRIORITY` | Готовый постоянный целочисленный приоритет из общей шкалы expression |

Отсутствующее `PASS_ARGS_AS_IS` не означает `0`. Отсутствующий `PRIORITY` не получает неявного уровня. Если поле есть, но не даёт готового допустимого значения к моменту анализа операторного применения, контракт не выполнен.

Проверка соответствия шаблону ничего не добавляет в кандидата. Шаблон с записанным default также не материализует отсутствующее поле при одном лишь `implements`. Поля можно написать непосредственно, как в демо, либо получить обычной явной композицией `merge`; после композиции проверяется фактическое описание. Проверка и построение структуры — разные операции.

Обязательность полей описания не делает каждый actual обязательным. Пропуск левого или правого actual, defaults, `required` и допустимое связывание разрешаются стандартным контрактом метода. Операторная форма подаёт `left/right`, а свойства `PASS_ARGS_AS_IS/PRIORITY` читает из выбранного описания. Для const-полей не вводится отдельная категория вне DATA.

Готовые постоянные свойства не заменяются одноимёнными локалами вызывающего. Их чтение не запускает тело операнда. Подготовка свойств выполняется общим механизмом получения постоянных значений; обращения вроде `sys\priority("+")` должны дать значение до группировки. Циклическая или неопределённая зависимость свойств не разрешается пробным исполнением тела.

### 2.4. Приоритет и режим аргументов

Режим и приоритет задаются независимо. Для сырого операнда:

```lmx
const: int: PASS_ARGS_AS_IS 1
const: int: PRIORITY sys\priority("+")
```

Для обычного операнда используется та же форма с `PASS_ARGS_AS_IS 0`. Никакое значение режима не кодируется специальным числом в поле приоритета.

`PRIORITY` включается в общую шкалу §6. Равные приоритеты, ассоциативность и группировки обрабатываются обычным expression. Правый хвост не получает невидимых скобок из-за передачи через `right`: общий анализ сначала определяет его аргументные вхождения, затем режим определяет, нужно ли их выполнить до входа в метод.

До исполнения пользовательских аргументов должна быть однозначно определена группировка и способ потребления. Неустранённые варианты одного имени с разными свойствами дают обычную диагностику неоднозначности. Варианты с одинаковыми свойствами могут проходить дальнейший обычный выбор по явным actuals. Неявное связывание не становится способом выбора сигнатуры.

Для префиксной формы `(foo 1 2 3 4)` написанного левого actual нет; правые значения остаются массивом позиции 2. Отсутствие обрабатывается общими правилами без переноса первого правого значения в `left`, дополнительного `has_left` или нового маркера отсутствия.

### 2.5. Структурный шаблон и `fn` сохраняют разный смысл

| Требование | Что сравнивается |
|---|---|
| Обычный структурный шаблон | Имена, поля и всё явно заданное им дерево требований |
| `fn: name data` | Число и типы входов в написанном порядке и результат; имена формалов и тело не сравниваются |

В `operand_template` имена `left`, `right`, `PASS_ARGS_AS_IS` и `PRIORITY` значимы. Прежнее разрешение любых `lhs/rhs` через позиционную `OperandSignature` больше не определяет роль операнда. Оно сохраняется как общее правило `fn`, когда потребитель действительно предъявляет fn-сигнатуру.

Например, обычная позиционная сигнатура для независимых проверок:

```lmx
fn: PairSignature (@: first; []: @ rest; return: int)
```

Метод с входами `lhs: @`, `rhs: Array<@>` и результатом `int` может соответствовать этой сигнатуре. Через ссылку `pair`, принятую с требованием `PairSignature`, `pair(rest := makeRest(); first := makeFirst())` направляет значения в позиции 2 и 1, а RHS исполняет в написанном порядке. Прямой вызов этого метода использует его реальные имена `lhs/rhs`.

Именование на своей позиции считается позиционной подачей. Именование вне позиции отключает счётчик, после него разрешены только именованные actuals. Нормализация имён через fn-ссылку не переставляет эффекты RHS и не переименовывает кандидата.

Defaults, `required`, `throws` и неявное связывание принадлежат фактическому кандидату. Значения defaults в fn-описании не заменяют его источники; их различие само по себе не меняет сравнение сигнатур. Неявное связывание использует реальные имена кандидата, не метки fn. Поле `return` не считается входом. Данные принятого callable остаются `parent(C)`; шаблон не подставляется вместо них. Сходство C-представления не заменяет соответствие требованиям типов LMX.


## 3. Аргументы, обычный результат и передача «как есть»

### 3.1. Подготовленные значения: `PASS_ARGS_AS_IS 0`

Общий анализ expression определяет одно левое вхождение и последовательность правых с учётом написанной структуры и приоритетов. Необходимые значения вычисляются по §5. Ссылка на левое значение поступает в `left`, ссылки на правые — в массив `right` в исходном порядке.

Для `(1 foo 2 3 4)` поясняющая схема:

```text
left  = ссылка на значение 1
right = массив ссылок на значения 2, 3, 4
result = обычный вызов foo с этими двумя actuals
```

Для `(foo 1 2 3 4)` правый массив содержит четыре ссылки; левый actual написанной формой не подан. Пустой Array, поданный в `right`, и отсутствующий actual различаются обычным механизмом. Имя операции и её постоянные свойства в массив значений не включаются; левое значение там не дублируется.

Встроенное присваивание даёт один результат в соответствующей позиции и не создаёт именованный actual. Каждое необходимое вхождение подготавливается один раз для этого применения. Повторное чтение полученного параметра исходное выражение не запускает. Готовая Structure или callable сама может быть значением; обычная передача ссылки на неё не является вызовом.

Операторная подача и явный вызов направляются одному методу. Форму `a foo b` нельзя механически заменить на `foo(a; b)`: второй вход метода — массив ссылок. Одинаковые уже подготовленные actuals и одинаковый контекст дают одну семантику тела и один логический тип результата.

### 3.2. Контейнер остаётся одним операндом

| Применение | `left` | Содержимое `right` |
|---|---|---|
| `(1 foo 2 3 4)` | Ссылка на `1` | Три ссылки на `2`, `3`, `4` |
| `(foo 1 2 3 4)` | Не подан написанной формой | Четыре ссылки на `1`, `2`, `3`, `4` |
| `(foo A)`, где `A` — Array | Не подан написанной формой | Одна ссылка на значение/дескриптор `A` |
| `(A foo B C)`, где значения — контейнеры | Одна ссылка на `A` | Две ссылки на `B` и `C` |

Элементы контейнера автоматически не раскрываются. Сбор правых вхождений в `right` не меняет передачу Array обычным вызовам. Существующий выбор прочтений единственной Structure остаётся в своей области действия.

### 3.3. Ссылки, числовой адрес и storage

Обычные ссылки в `left/right` используют существующий storage: ссылка ведёт к значению типизированной записи `{type, value}`. В действующей норме код типа занимает четыре байта непосредственно перед значением:

```text
p = storage[index]
value находится по p
type находится непосредственно перед p
```

Слова «ссылка на запись» не меняют адрес значения на адрес тега. Если значение — контейнер, ссылка ведёт на его типизированный дескриптор. Плотный `Array<T>` нельзя переинтерпретировать как `Array<@>`: числовые элементы не являются указателями на отдельные типизированные записи.

Готовые записи использовать по существующим ссылкам. Если нативное вычисление дало машинное временное значение, его адрес сам по себе не выдаётся за адрес типизированной записи. При необходимости действует общий механизм представления значения в storage. Новые `union`, обёртки каждого значения или обязательные копии всех аргументов не вводятся.

По последнему уточнению автора:

```lmx
@: ptr Struct
int: value 1 + @Struct
```

Первая строка сохраняет обычную ссылку. Вторая явно получает число-адрес для арифметики. `@` не требуется для передачи ссылки на метод и не является маркером подавления его операторной роли. Префиксное `\` следует по ссылке, сохраняя обычные требования к типу, доступу и времени жизни; оно не исполняет код по ссылке.

### 3.4. Обычный тип результата

Метод возвращает значение объявленного типа. `return: int` даёт `int`; `return: @` даёт обычную ссылку. Операторное применение и обычный вызов одного метода не снимают разные количества уровней ссылки.

Общий механизм expression предоставляет результат следующему потребителю. Если потребителю нужна ссылка на типизированную запись полученного числа, используется существующее представление значения в storage с надлежащим временем жизни. Для уже имеющейся подходящей записи обязательная копия не требуется.

Прежний универсальный контракт «метод возвращает `@`, а expression извлекает произвольное логическое значение из указанной записи» отменяется. Старые методы, возвращавшие запись числа ради числового результата, переводятся на обычный числовой `return`. `return: @local_sum` не является такой заменой: это явный числовой адрес с обычным временем жизни места.

Физическая передача записи результата внутри интерпретатора или native ABI не меняет логический тип. Существующее разграничение admission при трансляции, интерпретации и подготовленном нативном исполнении сохраняется.

### 3.5. Полное демо: обычный `add`

```lmx
operands:
    @: left int
    []: @(int) right
    const: int: PASS_ARGS_AS_IS 0
    const: int: PRIORITY sys\priority("+")
    return: int
    add:
        return: \left + \right[0]

Example:
    int: n
    return: int
    calculate:
        import: operands
        return: (n add 3) add n
    demo:
        return: calculate(2) + calculate(5)
```

Это пример автора с последним оформлением обязательных свойств: `PASS_ARGS_AS_IS 0` и `PRIORITY` прописаны явно. Пустая строка закрывает предыдущий корневой блок по действующему правилу.

| Вызов | Вычисление | Результат |
|---|---|---:|
| `Example\calculate(2)` | `(2 + 3) + 2` | 7 |
| `Example\calculate(5)` | `(5 + 3) + 5` | 13 |
| `Example\demo()` | `7 + 13` | 20 |

Внешний `add` получает слева ссылку на уже готовый результат внутреннего `add`. `\left` читает число. Всё выражение хранится в обычном графе `calculate` и может исполняться с другим `n`; это не требует сырого режима каждого арифметического операнда.

Этот короткий метод использует один правый аргумент. Для библиотечного бинарного контракта ограничение длины `right` задаётся существующей проверкой; для вариадического сложения реализация должна обойти весь массив. Новая таблица арностей или неявная свёртка массива не вводится.

### 3.6. Исходные вхождения: `PASS_ARGS_AS_IS 1`

Этот режим сохраняется как самостоятельная возможность. Общий анализ определяет границы аргументов по тем же приоритетам, но передаёт исходные вхождения без исполнения. В аргументе могут находиться литерал, имя, вызов, присваивание или сгруппированное выражение.

Сырой обработчик произвольных форм использует общие ссылки `@: left` и `[]: @ right`. Требование `@: left int` не приобретает смысл «код, который когда-нибудь вернёт int»: оно по-прежнему требует адресуемый `int`. Ограничения на сами допустимые исходные формы проверяются без их исполнения ради получения другого типа.

Непотреблённый аргумент не вызывает эффектов. Явное исполнение аргумента несколько раз повторяет его эффекты. Чтение или сохранение ссылки само по себе исполнения не вызывает. Группировка не отменяет сырой контракт потребителя и не требует заранее вычислить все скобки.

Сохраняются обычная передача контейнеров одним аргументом и порядок вхождений в `right`. Не вводится общее раскрытие Array.

### 3.7. `sys\eval(fragment)` и исходный контекст

`sys\eval` — доступ к единому механизму получения значения expression. Он получает переданное исходное вхождение, исполняет его по общим правилам и возвращает обычное значение. Новый parser или второй алгоритм вычисления не создаётся.

Литерал даёт значение, имя разрешается по обычным правилам, написанный вызов исполняется. Сохранённая ссылка на callable остаётся ссылкой, пока сама форма не требует её вызвать. `\fragment` не является сокращением `sys\eval(fragment)`.

Каждый явный вызов `sys\eval` начинает новое вычисление переданного вхождения. Однократность §5 действует внутри этого вычисления; два вызова означают два исполнения. Не создаётся постоянный кеш результата в исходном графе.

На время применения сырого операнда сохраняется связь аргументного вхождения с контекстом, в котором оно вычислялось бы как обычный аргумент в исходной точке. Эта связь сохраняется при передаче аргумента вспомогательному методу. Служебная одноимённая переменная реализации не перехватывает имя исходного выражения.

Исходный контекст включает действующие правила выбора соответствующего DATA для встроенных присваиваний (§4), связывания и `private`. Он не означает, что все записи теперь направляются в переменные вызывающего. Исполнение аргумента в его контексте также не даёт самому оператору права неявно получать закрытые private-поля.

Для реализации допустим транспорт ссылки на действующий контекст через существующие кадры и скрытые параметры. Одного адреса исходной структуры недостаточно для восстановления разных активаций. Передача в сыром режиме не продлевает время жизни активации и не восстанавливает завершённый вызов. Длительно живущее вычисление оформляется обычным callable с DATA и явной композицией/`merge`, где она нужна.

При статически известном фрагменте общий механизм может использовать его нативную реализацию. Наличие `sys\eval` не требует повторного текстового разбора или интерпретации каждого вызова.

### 3.8. Демо того же выражения с аргументами «как есть»

```lmx
raw_operands:
    @: left
    []: @ right
    const: int: PASS_ARGS_AS_IS 1
    const: int: PRIORITY sys\priority("+")
    return: int
    add:
        int: a sys\eval(left)
        int: b sys\eval(right[0])
        return: a + b

RawExample:
    int: n
    return: int
    calculate:
        import: raw_operands
        return: (n add 3) add n
    demo:
        return: calculate(2) + calculate(5)
```

Здесь внешний `add` получает в `left` исходную группу `(n add 3)`, а в `right[0]` — исходное правое вхождение `n`. Его `sys\eval(left)` выполняет группу, включая внутренний сырой `add`; `sys\eval(right[0])` получает значение правого `n`.

`RawExample\calculate(2)`, `RawExample\calculate(5)` и `RawExample\demo()` дают соответственно `7`, `13` и `20`. Арифметический результат совпадает с §3.5, но момент и необходимость исполнения каждого аргумента теперь контролирует реализация операнда. Она может пропустить, повторить, исследовать или сохранить переданное вхождение.


## 4. Именованный аргумент и встроенное присваивание

### 4.1. Два разных структурных случая

| Случай                                                       | Значение                                                                               |
| ------------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| `v := expression` занимает самостоятельную позицию аргумента | Именованный actual argument `v`, получающий результат правой части                     |
| `v := expression` находится внутри выражения аргумента       | Запись в соответствующее `data`; присвоенное значение участвует в окружающем выражении |

Встроенное присваивание не создаёт дополнительный actual argument, не занимает дополнительную позицию и не сдвигает позиционный курсор. Результат всего выражения передаётся как один аргумент.

Различие определяется структурным положением записи после общего разбора. Если потребителю требуется результат встроенного присваивания, он получает его по правилу §5: связанное присваивание вычисляется и при более низком приоритете. Одного совпадения имени с формалом для такой связи недостаточно.

### 4.2. Основной пример без дополнительных скобок

```text
f(1 + v := 2 + 3)
```

Написанная цепочка:

```text
1 plus: v let: 2 plus: 3
```

Разбор исполнения:

1. Первому `plus` нужны `1` и результат конкретного встроенного присваивания, связанного с этим вхождением `v`.
2. `plus` требует этот результат. Меньший приоритет `let` не запрещает исполнить его для получения нужного значения.
3. В правой части присваивания `plus` имеет более высокий приоритет, чем `let`. Поэтому сначала вычисляется `2 + 3 = 5`.
4. В соответствующее **data вызываемой `f`** записывается `v := 5`. Значением этого присваивания является `5`.
5. Первый `plus` получает `1 + 5 = 6`.
6. `f` получает **один** позиционный actual argument `6`.

По результату и записи в `v` это соответствует:

```text
f(1 + (v := 2 + 3))
```

Скобки в последней записи лишь показывают получившееся вычисление. В исходный граф дополнительный контейнер не добавляется.

Запись не превращается в `f(v := 5; 6)`. Отдельное одноимённое место `v` вызывающего контекста не становится целью присваивания.

В проверочной функции первый формал должен называться, например, `x`, а `v` быть другим полем её `data`. Наблюдаемый результат: `x = 6`, `v = 5` и ровно один actual argument. Даже если `v` уже содержало `100`, результат именно этого выражения остаётся таким же.

Использовать существующее соответствующее `data` получателя. Это требование само по себе не вводит копию графа, новую модель кадра или специальный механизм обратной записи.

### 4.3. Явная группа задаёт другой эффект

```text
f(1 + (v := 2) + 3)
```

Здесь правая часть сгруппированного присваивания — только `2`:

1. В data `f` записывается `v := 2`.
2. Значение присваивания `2` участвует в окружающем выражении.
3. Вычисляется `1 + 2 + 3 = 6`.
4. Передаётся один позиционный actual argument `6`.

Эта запись также допустима. В ней `v = 2`, тогда как в §4.2 `v = 5`. Совпадение итогового аргумента `6` не означает совпадения эффектов.

### 4.4. Самостоятельный именованный аргумент

```text
f(v := 2 + 3; 6)
```

даёт:

```text
f(v := 5; 6)
```

Здесь два actual arguments: самостоятельный именованный `v := 5` и следующий позиционный `6`.

Для этого положительного примера формал `v` должен стоять первым. По действующему правилу именованный аргумент на своей позиции считается позиционным, и передача может продолжиться позиционно.

Если `v` находится на другой позиции, сохраняется общее ограничение: после именованного аргумента вне своей позиции следующие аргументы тоже должны быть именованными.

Исполнение по требованию внутри выражения не меняет структурную роль этой самостоятельной записи и не отменяет правил именованной передачи.

### 4.5. Сопоставление редакций и проверка эффектов

В прежней норме присваивание имело высокий приоритет. Текущая норма сочетает низкий приоритет присваивания с вычислением необходимого результата по требованию.

| Запись               | Прежний высокий приоритет: `v` / аргумент `f` | Текущая норма: `v` / аргумент `f` |
| -------------------- | --------------------------------------------- | --------------------------------- |
| `f(1 + v := 2 + 3)`  | `2 / 6`                                       | `5 / 6`                           |
| `f(10 * v := 2 + 3)` | `2 / 23`                                      | `5 / 50`                          |
| `f(1 + v := 2 * 3)`  | `2 / 7`                                       | `6 / 7`                           |

В среднем примере новое исполнение: `2 + 3 → 5`, запись `v := 5`, затем `10 * 5 → 50`. Это отличает новую норму от ошибочного временного повышения приоритета `let`, которое сохранило бы `v = 2` и дало бы `23`.

Убрать из предыдущей редакции ТЗ тезис, что после понижения приоритета присваивания пример без скобок остаётся без определённого результата и обязательно требует скобок. Новое правило определяет и результат, и записанное значение.

При переводе примеров проверять оба наблюдаемых результата. Скобки добавлять только для выражения требуемой границы вычисления; механическое добавление скобок может изменить значение присваивания.

## 5. Исполнение по требованию и эффекты

### 5.1. Общее правило

> Перед исполнением ресивера вычисляются необходимые ему значения. Если необходимое значение является результатом другого ресивера, тот исполняется по требованию независимо от сравнительного приоритета этих двух ресиверов. Его аргументы и правая часть сохраняют границы, определяемые структурой и приоритетами.

Приоритет определяет обработку и принадлежность операций в выражении. Зависимость по значению определяет, что необходимо вычислить до завершения потребителя. Более высокий приоритет потребителя не запрещает ему сначала получить результат зависимой операции с меньшим приоритетом.

В примере §4.2 низкий приоритет `let` позволяет вычислить внутри его правой части `2 + 3`; зависимость левого `plus` от результата `let` требует завершить присваивание перед сложением с `1`.

**Исполнение по требованию не повышает приоритет присваивания.** Вызвать `let` раньше потребителя не означает взять только первый атом `2`, оставив `+ 3` снаружи. Правая часть вычисляется по действующим низким приоритетам присваивания.

Правило относится к общему механизму expression, включая пользовательские операнды. При `PASS_ARGS_AS_IS 0` метод получает подготовленные значения; при `PASS_ARGS_AS_IS 1` — исходные вхождения по §3.6 и сам запрашивает их исполнение через `sys\eval`. Для остальных ресиверов сохраняется их контракт потребления: логическая операция может не потребовать правый операнд и пропустить целое применение пользовательского операнда.

Исполнение по требованию следует связям получения значения, установленным общим анализом выражения. Само соседство записей такой связи не создаёт. В `10 * 2 + 3` умножению требуется непосредственно число `2`; вычисляется `(10 * 2) + 3 = 23`. В `10 * v := 2 + 3` потребляемое вхождение связано с результатом конкретного присваивания `v`; его правая часть даёт `5`, поэтому результат равен `50`. Приоритеты обычных арифметических цепочек сохраняются.

### 5.2. Связь с конкретным вхождением

Связь между потребляемым вхождением и производящей его значение операцией устанавливает общий анализ выражения после P0.

В `1 + v := 2 + 3` нужен результат **этого** присваивания `v`. Наличие старого значения у места не отменяет требование получить результат. При прежнем `v = 100` новое значение равно `5`, а результат выражения — `6`.

Обычное чтение имени сохраняет свою роль. Оно не запускает поиск ещё не выполненных одноимённых присваиваний в окружающем коде. Обычное имя Structure также не превращается в неявный вызов.

В обычной записи кода:

```text
v := v + 1
```

правое `v` читает значение уже известного места до этой записи. При `v = 100` оно даёт `100`, сумма — `101`, присваивание записывает `101`. Правое `v` не требует повторно исполнить само это присваивание.

Таким образом, требование значения привязано к конкретной операции выражения, а обычное чтение переменной — к соответствующему месту по действующим правилам разрешения.

### 5.3. Однократность и результат операции

В одном динамическом вычислении конкретное вхождение операции исполняется один раз. Если оно уже исполнено по требованию, последующее достижение этого вхождения обходчиком использует результат и не повторяет эффект.

Например, при `read_once()`, возвращающем `4`:

```text
f(1 + v := read_once() + 3)
```

получаются одно чтение, `v = 7` и один аргумент `8`. Тело `f` запускается после получения аргумента.

Сохраняется результат операции — присвоенное ею значение. Его получение потребителем не подменяется повторным чтением изменяемого места после возможных других записей.

Однократность относится к конкретному исполнению выражения. Новый вызов, новая итерация или новая проверка условия выполняют его заново. Вычисленный однажды результат не становится постоянным кэшем в исходном графе. Каждый явный `sys\eval` также является новым вычислением: два вызова одного сырого вхождения повторяют его эффекты, сохраняя однократность внутри каждого из этих вызовов.

При ошибке вычисления необходимого значения потребитель не получает выдуманного результата; применяются обычные правила отказа и обработки ошибок. Вычисление по требованию не оправдывает пробные исполнения при переборе сигнатур.

### 5.4. Скобки и короткое замыкание

Приоритет и группировка не разрешают заранее выполнить все вложенные группы и присваивания независимо от потребности в результате.

Для поддерживаемых `&&` и `||` сохраняется короткое замыкание:

```text
0 && (x := 1)
1 || (x := 1)
```

В обоих случаях правый операнд не требуется и `x` не изменяется. Аналогично не исполняется вызов с эффектом внутри пропущенной части выражения.

Сначала потребитель определяет, какие значения нужны на достигнутом пути, затем запрашивает их. Общего предварительного прохода по всем присваиваниям и скобкам нет. Пропущенная операция не должна позднее исполниться лишь потому, что обходчик дошёл до её записи.

Порядок вычисления действительных аргументов остаётся установленным правилами LMX. Перенос таблицы приоритетов Си не переносит автоматически все особенности или неопределённости порядка вычисления в Си.

### 5.5. Условие `while`

Автором подтверждена следующая пара:

```c
while ((c = getchar()) != EOF)
```

```text
while ((c := getchar()) != EOF)
```

У `while` используется то же `data`, что у окружающего callable. На каждой проверке условия:

1. Сравнению нужно значение сгруппированного присваивания.
2. `getchar()` исполняется один раз.
3. Результат записывается в `c` этого общего `data` и становится значением присваивания.
4. Это значение сравнивается с `EOF`.
5. `while` получает одно логическое значение условия.

Дополнительного именованного аргумента `c` нет. Присваивание не выносится в однократную подготовку перед циклом и не исполняется второй раз при той же проверке.

Проверка на источнике, последовательно возвращающем `A`, `B`, `EOF`: три чтения, два исполнения тела, после последней проверки `c` содержит `EOF`. Тип `c` должен допускать значения символов и `EOF`.

Не объявлять эквивалентной форму `while(c := getchar() != EOF)`. В присваивании с такой правой частью сначала вычисляется сравнение, поэтому присваиваемое значение — его логический результат; кроме того, самостоятельная именованная запись проверяется по контракту аргументов `while`. Исполнение по требованию не отрезает `!= EOF` от правой части.

### 6.1. Основная таблица

| Логическое ИЛИ            | `\|\|`                                                                    | Слева направо   |
| Присваивание              | `:=` и существующие составные присваивания, включая `**=`                 | Справа налево   |

Обязательное const-поле `PRIORITY` выбранного описания включается в этот же механизм; значение можно получить по имени другого операнда через `sys\priority` (§8). Обязательное `PASS_ARGS_AS_IS` выбирает способ потребления аргументов независимо от числового приоритета. Специальной шкалы для пользовательских операндов нет.

В LMX `=` остаётся сравнением, соответствующим `==` в Си. Присваивание записывается `:=`. Написание существующих составных присваиваний этой задачей не меняется.

Существующие в машинном профиле преобразования типов и `sizeof` должны быть согласованы с соответствующими отношениями в грамматике Си. Отсутствующие `?:` и оператор запятой вводить не требуется. `,` и `;` сохраняют свои структурные функции LMX.

Таблица задаёт относительный порядок, а не конкретные числовые значения внутренних приоритетов. Получение необходимых значений происходит по §5; низкий приоритет источника значения не запрещает вычислить его до потребителя. Основание для сопоставления с Си — грамматика выражений N1256, §§6.5.2–6.5.16; ссылка в §12.

### 6.2. Исключение: степень `**`

Сохранить действующее Python-подобное связывание:

- вызов, индекс и доступ к полю связывают сильнее `**`;
- `**` связывает сильнее `*`, `/` и `%`;
- цепочка степеней группируется справа;
- слева `**` связывает сильнее унарных `+`, `-`, `~`;
- справа `**` допускает унарный операнд.

Обязательные примеры:

```text
-2 ** 2       → -(2 ** 2)       → -4
(-2) ** 2                       → 4
2 ** -2       → 2 ** (-2)
2 ** 3 ** 2   → 2 ** (3 ** 2)   → 512
2 * 3 ** 2    → 2 * (3 ** 2)    → 18
```

Для `2 ** -2` здесь фиксируется группировка. Числовой результат и допустимые типы определяет числовой контракт LMX; вся числовая семантика Python автоматически не переносится.

Это асимметричное правило нельзя заменить одной строкой «степень выше всех унарных операций». Для остальных унарных операций, не имеющих такого аналога в Python, не приписывать Python выдуманное поведение. Сохранить действующие отношения LMX и явно отразить их в полной таблице реализации.

### 6.3. Приоритеты Си и зависимость по значению

Запись:

```text
1 + v := 2 * 3
```

остаётся структурной цепочкой:

```text
1 plus: v let: 2 mult: 3
```

Ресивер присваивания связан с написанным `v`. Нельзя пересобрать его левую часть в `1 + v` и выдать ошибку «присваивание сумме», ссылаясь на грамматику Си.

Исполнение по текущей норме:

1. Левому `plus` нужен результат связанного с этим вхождением `let`.
2. Для получения результата `let` вычисляет свою правую часть: `2 * 3 = 6`.
3. `let` записывает `v := 6` и возвращает `6`.
4. `plus` вычисляет `1 + 6 = 7`.

Итог определён: **`7` и `v = 6`**, в том числе при другом ранее записанном значении `v`. Нельзя читать прежнее значение только потому, что `plus` имеет более высокий приоритет, чем `let`.

В этом примере явная запись:

```text
1 + (v := 2 * 3)
```

даёт тот же результат и тот же эффект. Это совпадение конкретных вычислений; исходная форма без скобок не получает новый анонимный контейнер в P0.

Для согласованного с Си подмножества проверить:

```text
c := (a := 10) + (b := 20) * 2
```

Сгруппированные присваивания возвращают `10` и `20`; умножение даёт `40`, сумма — `50`, затем записывается `c := 50`. Итог: `a = 10`, `b = 20`, `c = 50`.

Для правой ассоциативности:

```text
a := b := 10
```

внешнему присваиванию нужен результат внутреннего: сначала `b := 10`, затем `a := 10`.

Меняются приоритеты и правила получения значений, а базовая структурная грамматика сохраняется. Допустимость дополнительных форм LMX, запрещённых в Си, сама по себе не противоречит совпадению результатов на общем подмножестве.

Backend получает результат анализа LMX. Текстовая замена `:=` на `=` с передачей исходного выражения Си-компилятору не является реализацией этого требования.

### 6.4. Интерпретация и нативная генерация

Интерпретатор получает результат необходимой операции через общий механизм исполнения и не повторяет уже выполненное в текущем вычислении вхождение.

При статически известных связях транслятор может заранее выстроить последовательность вычислений. Например, для `f(10 * v := 2 + 3)` она состоит из сложения, записи в data `f`, умножения полученного значения на `10` и вызова `f` с одним аргументом.

Вычисление по требованию не требует динамически искать присваивание при каждом чтении переменной. Рабочие результаты исполнения и временные значения нативного кода не должны превращаться в новые постоянные поля чистого графа.

## 7. `sys\name(identificator)`: имя как LMX-строка

### 7.1. Нормативный контракт

> `sys\name(identificator)` принимает написанный идентификатор и возвращает его имя как обычную строку LMX — `Lmx` Array символьных элементов переменной длины. Написание получается из существующего представления канонического имени и служебной таблицы имён.

Пример:

```text
sys\name(foo) → "foo"
```

Ресивер потребляет аргумент **как идентификатор**. Он не разрешает его как переменную, не читает связанное значение, не вычисляет инициализатор и не вызывает Structure или метод. Имя не обязано иметь объявление: «из любого идентификатора» включает любое корректное написание, уже распознанное общим парсером.

Если `foo` — переменная со значением `42`, результатом остаётся строка `"foo"`. Если `foo` — метод, в том числе подходящий для операторной роли, получение имени не запускает его исполнение. Для указателя `ptr` возвращается `"ptr"`, а не имя объекта, на который он указывает.

Эта форма принимает один идентификатор. Она не вводит универсального преобразования произвольных значений в текст. Несоответствующий аргумент обрабатывается по существующим правилам недопустимой формы.

### 7.2. Написание идентификатора

Возвращается значение имени после обычного разбора идентификатора. Оформление exact identifier снимается по действующему правилу: внешние обратные кавычки удаляются, удвоенная обратная кавычка внутри становится одной.

```text
sys\name(foo)          → "foo"
sys\name(`foo`)        → "foo"
sys\name(`long name`)  → "long name"
sys\name(`a``b`)       → "a`b"
sys\name(``)           → ""
```

Прочие допустимые символы имени сохраняются. Пустой exact identifier даёт пустой массив символов. Новая кодировка, нормализация регистра или ограничение длины имени не вводятся.

Это получение написания идентификатора из существующего представления, а не сериализация значения переменной или повторный разбор исходного текста.

### 7.3. Представление и получение результата

В текущей норме одно написание представлено одной повторно используемой канонической строкой со стабильным адресом. Имя сущности получается через существующую служебную таблицу. Старую схему отдельных числовых кодов идентификаторов восстанавливать не требуется.

Реализация:

1. Получить каноническое имя написанного аргумента через существующее представление идентификатора и служебную таблицу.
2. Выдать его как обычную строку LMX, используя имеющееся строковое представление.
3. Сохранить обычные контракты владения и доступа к этому представлению.

Результат имеет общий дескриптор `Lmx` и обычный массив `char` переменной длины. Других видов массивов по фиксированности длины текущая модель не вводит. Для `foo` длина результата равна `3`; для пустого имени — `0`. Завершающий NUL не входит в строку LMX.

Использовать существующую строку и служебную таблицу. Новая таблица регистрации, повторное построение написания или обязательная аллокация и копирование на каждый вызов не требуются. Точная выдача ссылки или копии следует существующему контракту строк и служебных имён; это ТЗ не добавляет отдельной гарантии адресного тождества результатов.

Интерпретатор и подготовленный нативный код должны получать одинаковое содержимое и обычный Lmx-результат. Во время трансляции не требуется исполнять код обозначенной идентификатором сущности ради получения её имени.

Основания текущего представления: §4 семантики — канонические имена и служебная таблица; §5 грамматики — bare/exact identifiers; §5 L2 — строки как Array точной длины. Ссылки приведены в §12.

### 7.4. Связь с остальными ресиверами

Полное имя получения строки — `sys\name`. Оно находится непосредственно в `sys`; запрос приоритета `sys\priority` и доступ к исполнителю `sys\eval` также находятся в `sys`.

Контракт `sys\name` потребляет написанный идентификатор. Общее исполнение не должно сначала вычислять этот аргумент как обычное значение или требовать результата операнда с тем же именем.

Возвращённая строка является одним Array. В обычных вызовах:

```text
f(sys\name(foo))
f(a := sys\name(foo))
```

строка передаётся целиком, соответственно позиционно или по имени. Отменённое правило превращения строки в цепочку символов не применяется.

Для запроса приоритета имя преобразуется в строку явно:

```text
sys\priority(sys\name(foo))
```

Получение строки не вызывает `foo`; запрос приоритета также не вызывает его реализацию.

## 8. `sys\priority`: приоритет по имени

### 8.1. Сигнатура и значение

Контракт ресивера в группе `sys` описать именованной сигнатурой:

```text
fn: PrioritySignature ([]: char name; return: int)
```

У `fn` два аргумента: имя `PrioritySignature` и data-шаблон с входом `name` и полем результата `return`. Это описание сигнатуры; оно не создаёт исполняемый ресивер. Полное имя вызова реализации — `sys\priority`.

`name` — один обычный массив `char` переменной длины, содержащий имя операнда. Результат — `int` с объявленным приоритетом найденного операнда в общей системе expression.

Запрос работает для встроенных и структурно определённых пользовательских операндов. Полученное число совпадает с тем значением приоритета, которое используется общим анализом выражения для этого операнда.

Запрашивается свойство конкретного именованного операнда. Для `"+"` и `"-"` в этом контракте это приоритет сложения и вычитания; для `"*"` — умножения. Контекстные унарные, префиксные и постфиксные роли анализируются по §6 и сами по себе не меняют результат запроса по тому же имени. Если общий механизм представляет такие роли отдельными операндами, их приоритеты получают по их собственным существующим именам. Имя, которое не позволяет однозначно выбрать операнд, даёт обычную ошибку разрешения; выбирать произвольный уровень по контексту вызова запроса нельзя.

### 8.1.1. Отличие от обычного `PrioritiesTemplate`

Если нужен обычный минимальный структурный шаблон данных, он записывается без метода `lookup`:

```text
PrioritiesTemplate:
    []: char name
    return: int
end: PrioritiesTemplate
```

Такой шаблон не превращается в `fn`: обычный `implements` проверяет всё явно заданное им дерево. Если в него дополнительно включить `lookup` с некоторым содержимым, это тоже станет частью структурного требования. Поэтому метод `lookup` не надо включать в минимальный шаблон только ради описания аргумента и результата.

`PrioritySignature` задаёт другую проверку — позиционную сигнатуру вызова. Например:

```text
PriorityProvider:
    []: char query
    return: int
    lookup:
        return: sys\priority(query)
end: PriorityProvider

@: priorityCall PrioritySignature PriorityProvider\lookup
priorityCall(name := "+")
```

При сравнении сигнатуры `query` допустим вместо `name`, а `lookup` не обязан называться `priority`. Именованный actual `name` через `priorityCall` соответствует позиции 1 и поступает в фактический `query`. Тело `lookup` и остальные не входные части данных не входят в сравнение `fn`; его данные остаются `PriorityProvider`. Это не переименовывает служебный ресивер `sys\priority` и не меняет его контракт получения приоритета.

### 8.2. Примеры

```text
sys\priority(sys\name(`+`))
sys\priority(sys\name(foo))
```

Первый вызов получает приоритет встроенного `+`, второй — приоритет доступного подходящего метода `foo`.

В DATA метода `foo`, соответствующего §2, записываются постоянные свойства:

```lmx
const: int: PASS_ARGS_AS_IS 0
const: int: PRIORITY sys\priority(sys\name(`+`))
```

Запрос приоритета доступного `foo` возвращает то же число, что запрос приоритета `+`. Отдельная регистрация не выполняется. Полные примеры метода приведены в §§3.5 и 3.8.

Имя можно передать любой обычной LMX-строкой с тем же содержимым. Аргумент не обязан быть результатом `sys\name`:

```text
sys\priority("+")
```

### 8.3. Поиск имени и отсутствие эффектов

Строка служит именем для поиска в существующем механизме доступных операндов. Её наличие не регистрирует новый операнд.

Одинаковое содержимое имени должно давать тот же результат и для отдельно созданного массива символов. Нельзя требовать совпадения адреса произвольной пользовательской строки с адресом канонического имени. Приведение строкового имени к существующему представлению имён выполняется на границе этого явного запроса, без изменения обычных правил сравнения уже разрешённых идентификаторов.

Запрос использует ту же видимость и ту же информацию о приоритете, что анализ expression в соответствующем контексте. Расположение самого ресивера в `sys` не ограничивает поиск именами полей этой служебной группы.

Чтение приоритета не запускает тело метода и не вычисляет его операндные аргументы. Оно читает готовое `PRIORITY` того же описания, которое использует expression. `sys\name` может получить написание необъявленного имени; `sys\priority` требует, чтобы полученное имя обозначало доступный операнд. При отсутствии такого операнда применяется обычная ошибка разрешения; фиктивный приоритет не подставляется.

### 8.4. Реализация

Использовать существующую информацию о приоритетах встроенных операций и поля `PRIORITY` подходящих пользовательских методов. Запрос и анализ expression не должны поддерживать расходящиеся таблицы.

Описанный этой сигнатурой ресивер возвращает обычный `int`. Для ветви `fn` существенны один вход `Array<char>` и результат `int`; имя входа и имя метода в это сравнение не входят. Это служебный запрос с обычной fn-сигнатурой. Обнаружение пользовательского операнда проверяет структурный заголовок §2 и обычную возможность метода дать требуемый результат.

При статически известном имени транслятор может заранее получить известное значение. При вычисляемом строковом имени используется соответствующий обычный механизм поиска. Семантика и результат должны совпадать с интерпретатором.

## 9. Требования к выполнению работ

### 9.1. Общие точки реализации

Обновить существующие механизмы:

- обычное разрешение имени и роли головы; структурную проверку `operand_template`;
- получение обязательных `PASS_ARGS_AS_IS` и `PRIORITY` из DATA выбранного callable до исполнения аргументов;
- обработку expression после P0 и связь конкретного вхождения с производящей его значение операцией;
- подготовку `left/right` в обычном режиме и передачу исходных вхождений в сыром;
- единый доступ `sys\eval`, сохранение происхождения сырого аргумента и действующего контекста;
- общий результат метода и представление значения в storage при необходимости;
- приём actuals, соответствующее DATA для присваивания, однократность эффектов и короткое замыкание;
- отдельную позиционную ветвь `fn` в `implements` и нормализацию named actuals через fn-ссылку;
- нативную генерацию того же результата анализа;
- каноническое имя как LMX-строку и запрос приоритета по содержимому строки.

Обнаружение, применение и `sys\priority` используют одно описание метода. Исходный чистый граф не дополняется отдельной регистрацией операнда или постоянным кешем вычисления. Проверка кандидатов не должна пробно исполнять пользовательские аргументы или писать в несколько кандидатных DATA.

При статически известном методе допускается обычная генерация нативного вызова с двумя операндными actuals. Поддержка сырого режима использует тот же исполнитель и существующий транспорт действующего контекста; отдельная VM не требуется.

### 9.2. Перевод старых требований

Удалить или исправить следующие действующие формулировки и примеры:

- обязательную регистрацию `sys\operand`, отдельное имя `foo` для реализации `new_op` и утверждение, что подходящего обычного метода недостаточно;
- обязательную `OperandSignature` как основание обнаружения операнда; роль `fn` сохранить отдельно;
- обязательный ссылочный результат каждого операнда и извлечение произвольного значения из него только при операторном применении;
- необязательное свойство режима с неявным значением; оба поля `PASS_ARGS_AS_IS` и `PRIORITY` должны присутствовать и иметь допустимые постоянные значения;
- прежние записи свойства режима через `arguments` и свойства приоритета через `priority`; нормативные имена полей — `PASS_ARGS_AS_IS` и `PRIORITY`;
- специальный sentinel сырого режима в числовом приоритете;
- исполнение кода через обычное разыменование `\` или обещание, что ссылка на физический `int` одновременно обозначает произвольное невыполненное выражение;
- «сначала все скобки, затем присваивания, затем остальные операции» и прежний высокий приоритет присваивания;
- чтение старого значения вместо результата связанного с вхождением присваивания и требование обязательно добавлять скобки в `f(1 + v := 2 + 3)`;
- повторное исполнение эффекта в одном вычислении, исполнение пропущенной ветви и постоянное кеширование результата в исходном графе;
- превращение встроенного `:=` в дополнительный named actual;
- общее раскрытие Array или строки в цепочку аргументов;
- старый единственный массив `args` вместо `left/right`;
- executable `fn`, fn без имени, результат вне data-шаблона и смешение структурной проверки с позиционной fn-сигнатурой;
- подмену `parent(C)` шаблоном, перенос defaults из fn или использование меток fn для hidden binding;
- старые краткие имена служебных запросов вместо `sys\priority` и `sys\name`.

Полные имена служебных операций этой редакции: `sys\priority`, `sys\name`, `sys\eval`. `PASS_ARGS_AS_IS` и `PRIORITY` — поля описания метода, а не дополнительные ресиверы.

Существующие правила обычных Structure, `private`, DATA/CODE и нативного admission не заменять специальными исключениями для операндов. Исторические цитаты отделять от действующей нормы. При обновлении примера проверять и результат, и записи, и число эффектов.

### 9.3. Диагностика

Диагностика должна различать:

1. Имя не разрешилось в подходящий исполняемый кандидат.
2. DATA не соответствует структурному заголовку: отсутствует поле или несовместим интерфейс.
3. `PASS_ARGS_AS_IS` не даёт постоянное `0/1` либо `PRIORITY` не даёт постоянный целочисленный приоритет.
4. Приоритет или режим неоднозначны до исполнения аргументов.
5. Конкретные actuals или объявленный результат несовместимы с обычным контрактом потребителя.
6. При сыром исполнении не соблюдён обычный контракт доступа или времени жизни исходного контекста.

Совпадение с шаблоном заголовка не отменяет проверки конкретного вызова. Для `sys\priority` отсутствие подходящего операнда — ошибка разрешения; для `sys\name` отсутствие объявления корректного идентификатора ошибкой не является. Ошибки присваивания описываются через реальное место и правила LMX.


## 10. Приёмочные проверки

Проверки — требования к Fable, а не заявление о выполненном запуске реализации. Проверить интерпретатор и применимые нативные пути с учётом действующего admission. Не добавлять автоматические проверки там, где их не предусматривает нативный контракт.

| F04 | Другое число/тип входов или другой результат | Обычная диагностика fn; `return` не считается входом |
| F05 | Через fn-ссылку поданы `first := p`, `rest := arr` | Попадают в `lhs/rhs` по позициям без переименования кандидата |
| F06 | `pair(rest := makeRest(); first := makeFirst())` | Эффекты в написанном порядке, подача в позиции 2 и 1 |
| F07 | Разные значения defaults при одинаковых типах | Сравнение fn не меняется; источники берутся у кандидата |
| F08 | У кандидата есть `required` и `throws` | Обычные требования конкретного вызова сохраняются |
| F09 | Доступны имена fn-меток и реальные имена кандидата | Hidden binding использует реальные имена, не участвует в выборе сигнатуры |
| F10 | Кандидат принят по fn | DATA остаётся `parent(C)`, шаблон его не заменяет |
