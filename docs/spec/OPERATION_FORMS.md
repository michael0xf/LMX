# Ресиверная и операндная формы одной операции

Парсер автоматически допускает все ресиверы в Expression. Транслятор направляет уже разобранные ресиверные и операндные применения в существующую семантику операции, сохраняя роли, типы, порядок эффектов и исходный контекст.

Вызов `` `+`(a; b) `` выбирает метод, объявленный с точным трёхбайтовым именем. У голой операции `+` собственный ключ. Существующий ресивер `@` кавычек не требует. Одноаргументные варианты изменения имеют имена `++var` / `var++` и `--var` / `var--`.

Ниже находятся нормативные договоры и исполняемый Python-эталон трансляции. Его 26 проверок относятся к модели; LMX runtime, production-транслятор и нативная интеграция — **NOT_RUN**. Связанные разделы: [общие операции](GENERIC_OPERATIONS.md), [монадические операции](MONADIC_OPERATIONS.md).

## 1. Принятые решения

1. Проверить **все ресиверы**, включая объявления типов, управление потоком, контракты, работу с графом и Message. Для уже разобранной Expression-формы подключить существующую семантику ресивера в трансляторе. Прежнее исключение для типообъявляющих ресиверов не используется как основание пропустить их аудит.
2. Проверить **все операнды**, включая символьные, словесные, пользовательские и профильные. Для каждого дать обычное ресиверное представление либо точно назвать ещё не реализованное общее подключение.
3. Не создавать вторые алгоритмы ради второй формы. Транслятор направляет обе записи в существующий обработчик операции. Готовый `asOperand` используется там, где действительно строится пользовательский callable; системным ресиверам отдельная callable-обёртка для Expression не требуется.
4. Сохранить правило единых имён. Старые названия не остаются вызываемыми алиасами; кавычки тоже не создают alias.
5. Вторая форма не делает операцию допустимой в любой роли. Процедура без результата не подставляет выдуманный `0` в выражение; L2-операция не становится L3-операцией; разделитель не становится callback.
6. Сохранить фактические типы, named actuals, динамическое связывание, `private`, `required`, владельца и `throws`. Не заменять пользовательские данные на `int` или универсальную коробку.
7. `@` — существующий ресивер. `` `@name` `` — одно точное имя; его содержимое не разбирается как применение `@`.
8. `++var`, `var++`, `--var`, `var--` — четыре имени двух форм для двух операций. У каждой формы ровно один PLACE-аргумент; `var` обозначает позицию аргумента, а не конкретную переменную.

Символьный точный токен допускает любую разрешённую длину и сохраняет все записанные байты. Голая символическая операция использует свой лексически распознанный ключ. Явный строковый поиск разрешает передать его как текст в позиции имени. Значение имени определяется его действительным объявлением.

## 2. Общая норма имён — на базовом уровне


### 2.1. Полный токен как ключ имени

Граф интернирует длину и все байты токена. Обе внешние обратные кавычки и оба байта каждой внутренней пары входят в ключ. Сравнение внутри таблицы имён использует её обычные канонические адреса. Выбор роли следует договору потребителя.

| Написание | Ключ |
| --- | --- |
| `print` / `` `print` `` | Два разных ключа. |
| `+` / `` `+` `` | Имя голой операции и отдельное точное имя. |
| `::` / `` `::` `` | Два ключа. Лексическая роль голого `::` по-прежнему зависит от контекста. |
| `->` / `` `->` `` | Имя голой операции и отдельно объявляемое точное имя. |
| `` `a``b` `` | Шесть байтов `60 61 60 60 62 60`. |
| Токен из двух обратных кавычек | Два байта `60 60`, независимо от пустого строкового ключа. |

`sys\name` выдаёт все байты написанного токена без вычисления значения. При явном строковом поиске `sys\priority("+")` адресует голую операцию. Ключ из трёх байтов `60 2B 60` адресует другое имя. Ссылки в старых примерах, которые использовали прежнее равенство, проверяются при миграции. [Грамматика](LMX_grammar.en.md#identifiers) · [Имена и пути](LMX_semantics.en.md#fields) · [Строковый выбор](LMX_semantics.en.md#field-name-keys).

### 2.2. Разрешённые символы

Точный токен сохраняет пробелы, переводы строк, знаки операций, `#`, `:`, скобки и обратную косую черту. Пара обратных кавычек внутри проходит как два байта одного токена. Пунктуация внутри него сохраняется как часть имени. NUL и незакрытый токен дают исходную диагностику. Исходные диапазоны используются для печати и диагностики.

### 2.3. Подмножество SQLite

Фиксируется совместимая **форма идентификаторов**: существующие bare-имена LMX и точные имена в обратных кавычках. SQLite поддерживает такие кавычки; см. [официальное описание](https://www.sqlite.org/lang_keywords.html).

Не требуется импортировать все остальные SQL-кавычки, keywords и SQL lookup. В LMX двойные кавычки уже обозначают строки, квадратные скобки участвуют в типах, индексировании и явных инициализаторах Arrays. Подмножество не меняет этих ролей и не вводит превращение строки в имя в зависимости от успеха lookup.

Сохранять регистр и исходные байты Unicode.

### 2.4. Имя отличается от составного выражения

| Запись | Значение |
| --- | --- |
| `@` | Существующий ресивер; кавычки для его обычного применения не требуются. |
| `` `@name` `` | Одно полное имя вместе с обратными кавычками. |
| `ns\op` | Путь. |
| `` `ns\op` `` | Одно буквальное имя с backslash. |
| `@Model` | Составное TYPE-выражение. |
| `` `@Model` `` | Одно буквальное имя. |
| `a+b` | Выражение из нескольких токенов. |
| `` `a+b` `` | Одно имя. |
| `` ns\`+`(a; b) `` | Вызов точного имени `+` через путь `ns`. |
| `` FxToTokens\`->` `` | Квалифицированная ссылка на точное имя конструктора. Ключ этого сегмента включает обе кавычки. |

Содержимое кавычек не разбирается повторно. Ключ `node` сохраняет служебную роль. Токен `` `node` `` даёт отдельный пользовательский ключ там, где он допустим.

## 3. Формы обращения

[Expression](LMX_semantics.ru.md#expression-structural-grouping) — тот же граф с группировщиком приоритетов и структурных групп. Группировщик выдаёт единицы операций и потоки текущего уровня. Затем другой участок — подготовка применения — передаёт левую последовательность одним actual/пакетом, затем вход `depth` с сохранением отсутствия, правую — Array ссылок. Общая форма `arg0 operand arg1 arg2 arg3` содержит обычную бинарную как частный случай `length(right) = 1`; автоматической свёртки и переноса первого right в отсутствующий left нет. Получатель определяет whole/sequence и свои DATA/TYPE/NAME/PLACE/RAW роли; одного ABI недостаточно, чтобы открыть произвольную модель. Пакет left не создаётся группировщиком и не записывается в P0.

Ниже пары записей для подключения к одному обработчику в трансляторе. Парсер уже принимает общую структуру; таблица не предлагает менять его грамматику и не является отчётом о runtime-исполнении.

```lmx
print(message)
`print`(message)

a + b
`+`(a; b)

a = b
`=`(a; b)

value <<< count
`<<<`(value; count)

m bind f
bind(m; f)
`bind`(m; f)

A0 -> A1 R
`->`(A0; A1; R)

Name :: (int: x; return: int)
`::`(Name; (int: x; return: int))
```

`<<<` — названная автором операция. В проверенной нормативной таблице найдены `<<` и `>>`. В реализации связать оба написания `<<<` с реальным определением; отсутствие его в доступном пакете не заменять догадкой о значении.

Для `` `:=`(target; value) `` первый аргумент имеет роль PLACE, а не чтение старого значения. Для `` `::`(Name; DATA) `` роли — NAME и целая DATA; `Name` не обязан предварительно существовать.

У `->` все логические аргументы имеют роль TYPE: входы следуют по порядку, результат последний. Ресиверная форма `` `->`(R) `` описывает сигнатуру без входов. Приоритет `->` — `sys\priority("+")`, а `::` — `sys\priority(":=")`. Записи `f :: (int -> int int)` и `f :: int -> int int` дают одно описание: Expression конструктора имеет роль CODE, а `::` сохраняет свой декларационный контракт ([неизменность](LMX_semantics.ru.md#receiver-context-invariance)). Готовая сигнатура сохраняет свой профиль; явно поданный DATA-шаблон не исполняет инициализаторы. Эти нормативные цели имеют статус исполнения **NOT_RUN**. Прежнее словесное имя `to` не является callable-алиасом.

`int -> (int int)` имеет один правый аргумент, а `int -> int int` — два. У `int -> (int -> int)` один вложенный результат-сигнатура. Форма `` `->`(int) `` нульарная; `int -> ()` содержит одну пустую Structure, допуск которой как TYPE проверяется отдельно. [Границы аргументов](LMX_semantics.ru.md#signature-grouping) следуют структурному группировщику и целому TYPE-договору; форма левой группы сама по себе не разрешает раскрыть модель. Ни локального DATA/value-селектора, ни дополнительного раскрытия или автоматического каррирования нет.

**Кавычки не являются признаком вызова.** `` `+` `` само по себе — имя. Вызов задаёт обычный Frame, например `` `+`(a; b) ``. В Expression написанное точное имя разрешается по общему операндному контракту кандидата с таким ключом. Потребители сравнивают ключи и выбирают роль без отдельного флага кавычек.

При существующем `head: body` двоеточие остаётся структурным разделителем, не частью имени. Новые имена `+:`, `<<<:` или `bind:` не вводятся. Основная запись символьных ресиверов в этом разделе — компактная:

```lmx
`%`(a; b)
`**=`(target; exponent)
```

`%` внутри точного имени не является маркером отключённого пункта. Соответствующее правило `%` вне кавычек менять не требуется.

Production-исходники транслятора в проверенном пакете не найдены. Поэтому ниже дан эталон обработки уже разобранных форм и схема его подключения к существующим обработчикам. Уточнение автора о готовом P0 принято как исходное условие. Ограничение доступных исходников влияет на проверяемость интеграции, а не создаёт новую задачу изменения грамматики.

### 4.1. Доступ к объявленному договору ошибок

`target\throws` обозначает конечное описание recoverable failures **выбранной операции**, а `throws: copy(target\throws)` принимает его поля обычным механизмом field stream. Чтение этого пути не вызывает target, не вычисляет его аргументы и не запускает его тело. Обычный метод, библиотечная публикация, символьный операнд и системный ресивер предоставляют одно представление своего действительного договора.

Для системных операций путь имеет тот же смысл: `sys\resize\throws` относится к операции `sys\resize`, а `sys\reserve\throws` — к `sys\reserve`. Реализация публикует здесь фактические конечные имена recoverable failures и их DATA-контракты, которыми пользуется общий исполнитель соответствующей операции. Это описание не заполняется пустым списком из-за того, что тело реализовано нативно, не подменяется произвольным `FxKernelFailure` и не дублирует алгоритм resize. Если существующий системный вход хранит договор в служебном определении, обычный путь адресует это самое определение; отдельный исполнитель или второй граф программы не создаётся.

```lmx
Resize:
    []: target
    int: size
    change:
        throws: copy(sys\resize\throws)
        sys\resize(target; size)
```

Здесь NAME `throws` принадлежит `Resize\change`, а источник списка — операция `sys\resize`. Статическое разрешение пути должно находить непустой фактический список, если эта операция имеет recoverable failures. Пустое описание допустимо только для действительно не имеющего таких исходов договора, с подтверждением исполнителя. Непубликация системного договора — незавершённая интеграция, а не основание молча считать список пустым.

У перегруженного имени `bind`, `parse`, `format` и любого другого семейства нельзя читать случайную первую ветвь без actuals. Клиент с уже определённой ветвью использует её адрес, например `FxListBind\bind\throws`; общий клиент описывает конечное объединение реально достижимых ветвей. Контракт публичной адаптации дополнительно учитывает её собственные failures: копирование тела не скрывает ошибки admission, подготовки или транспорта, если они достигают клиента.

В список не превращаются диагностические ошибки трансляции, системный выход или прекращение Thread. Для существующих implicit failures сохраняется различие между доступным описанием и обязанностью явно ловить ошибку: публикация метаданных не меняет установленную норму implicit/declared propagation. Если wrapper включает эти имена в собственный `throws`, он публикует обычный явный договор. Соответствие опубликованного списка реальному исполнителю, чтение без эффектов и обе формы вызова проверяются отдельно в interpreted/native и смешанных режимах. Эти runtime-проверки в данном пакете — **NOT_RUN**.

## 5. Матрица аудита всех классов

Роли: **VALUE** — фактическое значение; **NAME** — написанное имя; **TYPE** — полное требование; **DATA** — сохранённое описание; **BODY/RAW** — исходный фрагмент; **PLACE** — настоящее место; **CONTEXT/CONTINUATION** — исходная область, активация, cleanup или возобновление.

Каждое действительное определение текущей реализации сопоставить строке матрицы. Не пропускать типообъявляющие, управляющие или пользовательские ресиверы из-за отсутствия простой value-сигнатуры.

| Семейство / операции | Договор второй формы |
| --- | --- |
| Обычные callable, библиотека, math/provider methods | VALUE/declaration actuals; точный R/void, defaults/private/required/throws. Использовать общий `asOperand` и общий вызов. |
| `+ - * / % ** = != < <= > >= & \| ^ ~ ! << >>` и реальные расширения | Один исполнитель; numeric admission, Array-профили, установленная арность. Не вводить автоматический fold. |
| `&&`, `\|\|` | RHS вычисляется только при необходимости и в ресиверной записи. |
| `:=`, `+= -= *= /= %= <<= >>= &= ^= \|= **=` | PLACE слева, VALUE справа; цель один раз; named actual отличается существующей структурной ролью. |
| Групповое присваивание | Все RHS и проверка количества до первой записи; последовательность текущего уровня, один левый PLACE-пакет, идентичность целей. `copy` допустим с внешним коллектором и без него. |
| `++var`, `var++`, `--var`, `var--` | Один PLACE; два положения относительно атома; общий update-алгоритм, разные возвращаемые результаты. См. разделы 7–8. |
| `@`, `@x`, `\p`, индексирование, поля | Существующие роли NAME/TYPE/PLACE/VALUE и реальные адреса; прежние L2/L3 checks. Кавычки не выбирают роль. |
| `if`, `else` | Условие один раз; только выбранный BODY; прежняя связь со следующим sibling `else`. |
| `while`, `until`, `for` | RAW condition/step, BODY и loop targets; условие не вычисляется один раз навсегда. |
| `each`, `yield`, iterator/`next` | Исходная continuation, `Stop` и None как возможный обычный элемент. |
| `break`, `continue`, `redo`, `retry`, `retryable` | Настоящие label/region/continuation, cleanup и restart policy. |
| `return` | DATA: TYPE результата. CODE: VALUE/void и выход из исходной активации, а не обёртки. |
| `finally` | Регистрация отложенного BODY в исходном cleanup scope. |
| `throw`, `catch` | NAME ошибки, payload, DATA параметров, BODY handler и landing-pad. |
| `throws` | Конечный список NAME/DATA и field streams; имена не вычисляются как значения. |
| `required`, `private` | Admission/живое место и двусторонняя граница связывания; сохранить DATA/CODE-контекст. |
| `const`, `immutable`, `independent` как qualifications | Construction и полные требования до публикации; без раннего запуска initializer. |
| `T:`, `@:`, `@T:`, `[]:`, `[]T:`, `[N]T:` | TYPE head, NAME места, VALUE/сохранённый initializer; declaration actual остаётся DATA. |
| `@T`, `[]T`, `[N]T`, `nil: T` | TYPE → TYPE/typed absence. Не смешивать с адресацией и индексированием. |
| `Name :: DATA` | Все аргументы DATA, включая NAME; одно описание раскрывается самим `::` в список деклараций без изменения внешних actuals. Expression производителя имеет роль CODE; собственные роли аргументов сохраняются по [контракту ресивера](LMX_semantics.ru.md#signature-description-consumption). Не возвращать удалённый `fn`. |
| `call`, `C(args)`, `C: args` | Один resolver, W/E, actual mapping; настоящий `parent(C)`. |
| `copy`, `merge`, `import` | CODE-источники во всех позициях; FIELD STREAM. Не заворачивать поток в один Array. |
| `satisfies`, `test` | Неисполняющий interface inspection отдельно от явно достигнутого checking BODY. |
| `sys\name`, `sys\priority`, `sys\eval` | NAME; строка и namespace; RAW и исходный контекст соответственно. |
| `parent`, `length`, `sys\native/storage/capacity/typeof/indexof` | Реальная запись/identity и текущий фактический тип. Нулевой вариант относится к исходной DATA, не DATA адаптера. |
| `sys\descriptor` | Каноническая системная TypeRef → та же неизменяемая Structure описания типа; эта ветвь имеет приоритет для системного TYPE. Обычный Array/Structure VALUE → три живых адреса основного Lmx. `sys\descriptor(typeof(obj))` не ищет int-код и не выделяет второй дескриптор экземпляра. Нулевая форма сохраняет исходную DATA. |
| `sys\resize`, `sys\reserve`, Array mutation | Настоящая цель и её storage profile, прежний результат/отказы. |
| `sys\check/checkL3/translate/compile/toLmx/fromLmx` | Graph/text, phase policy и explicit compilation; осмотр не запускает программу. |
| `sys\assert`, `sys\endturn`, `print/log/error` | Сохранить вид диагностики, system exit, cleanup; не делать всё recoverable throw. |
| `post`, `ask`, `answer`, `timeout`, `undelivered`, `unanswered`, `send`, `receive` | Exchange DATA, отложенные вызовы/handlers, Message owner; подготовка целого описания до publish. |
| `adopt`, `independent: msg newParent` | Message identities/владение; preflight и отсутствие частичной публикации. |
| `L1/L2/L3`, `include`, `predef`, `os`, `cast`, `c.sizeof`, `c.name`, `synchronized` | Конкретные DATA/TYPE/NAME/BODY-роли и границы профилей. |
| Пользовательские операнды | Настоящие DATA, режим, приоритет, результат; receiver ведёт в тот же метод. |
| Дополнительные библиотеки/провайдеры | Та же классификация; отсутствующий provider не объявляется реализованным. |

Источники: [виды ресиверов](LMX_semantics.en.md#two-kinds-of-receivers), [ветвления](LMX_semantics.en.md#branches), [выходы](LMX_semantics.en.md#exits), [ошибки](LMX_semantics.en.md#exceptions), [композиция](LMX_semantics.en.md#composition), [типы](CORE_SEQUENCES_REGEX.en.md#types), [Message](LMX_semantics.en.md#thread-message-api), [L2](L2_spec_en.md).

### Структурные формы тоже проверить, но не выдумывать callable

`: , ;`, скобки, fences и `end:` обслуживают исходную структуру. Они входят в аудит как синтаксические формы, не становятся автоматически исполняемыми функциями.

`()` может быть пустой Structure, группировкой или частью вызова. Для отдельно сохранённого head `(): value` не приписывать identity/call/tuple contract без определения.

`data` и `code` — роли; `node` имеет контекстное значение. Не добавлять фиктивные `data()/code()/node()` ради симметрии. Удалённые `fn/fncall/sub` не возвращаются.

## 6. Общая архитектура исполнения

Путь остаётся одним:

1. Существующий P0 сохраняет Frames, Expression, группировку, имена и исходные spans.
2. Транслятор получает уже разобранную форму и канонические имена. Для прижатого одноаргументного применения использует уже определённую связь оператора с атомом.
3. Один resolver разрешает каждую запись по её ключу. Ресиверная и операндная формы выбранного семейства используют его общий контракт.
4. Общий обработчик определяет роли и отображение actuals до соответствующих эффектов.
5. Транслятор сохраняет прежнюю последовательность приёма и исполнения каждого достигнутого actual.
6. Существующий исполнитель или его нативная трансляция выполняет операцию в установленном контексте.

Исходное написание определяет ключ и сохраняется для roundtrip. При разрешении и выборе роли используется общий механизм без отдельного флага кавычек.

### 6.1. Сохранять не только VALUE и R

| Вид результата | Договор |
| --- | --- |
| VALUE | Настоящий тип, без универсального разыменования. |
| Void | Отсутствие значения, без подставленного нуля/контейнера. |
| FIELD STREAM | Поток полей и границы групп. |
| Перенос управления | Исходная цель return/loop/throw/retry/cleanup. |
| Приостановка/Message | Действительные owner, continuation и время жизни. |

Для VALUE-callable используется существующий механизм функций. BODY, DATA, PLACE и управление проходят прежний role consumer, а не вызов, сначала вычисляющий всё как значения.

### 6.2. Одна подготовка

[Структурный группировщик](LMX_semantics.ru.md#expression-structural-grouping) строит приоритетные операции и последовательности текущего уровня. Отдельная подготовка применения формирует один left actual, вход depth с сохранением отсутствия и right Array ссылок. Получатель выбирает целое значение либо последовательность; второе написание операции не выполняет эту подготовку повторно. Обычный W/E остаётся своим правилом допуска.

Для обычного поэлементного `:=` left обозначает один пакет PLACE, RHS предоставляет текущий поток значений, в том числе от голого `copy`. При единственном готовом Array справа его непосредственные элементы выбирает сам последовательностный профиль операции; группировщик возвращённые значения не раскрывает. Три соседние RHS-группы дают три Structure, не рекурсивное уплощение. Целые TYPE/модели, скалярные места, DATA и RAW сохраняют собственные договоры; одна лишь форма left не задаёт неизвестному операнду последовательностного контракта.

Отсутствующий `left` не кодируется значением `0`, `nil`, пустой Structure или дополнительным пользовательским флагом. Остаётся отсутствие actual; действуют настоящие defaults/required/private объявления. Пустой переданный `right` и отсутствие actual различаются.

Для named actuals сохранять **исходный порядок**. Написанное сначала выражение для `right` не переносится после `left` ради удобства адаптера. Ошибка при приёме текущего actual останавливает эффекты последующих.

### 6.3. Контекст и динамическое связывание

RAW переносит исходное occurrence и исходную живую активацию существующим транспортом. Адрес исходного текста сам по себе не идентифицирует активацию. Новая глобальная registry окружений и удержание завершённого кадра не нужны.

`sys\eval` остаётся общим явным вычислителем: один запуск — одно вычисление, два запуска — повтор эффектов. Разыменование RAW-ссылки не является исполнением.

`return`, `break`, `finally`, `catch` и аналогичные операции сохраняют исходный scope. Callable-обёртка не становится новой целью возврата или владельцем cleanup. Служебные локальные имена адаптера не захватывают имена пользовательского фрагмента.

## 7. Готовые формы и имена шаблонов

### 7.1. Вход транслятора

Все ресиверы уже могут находиться в Expression на уровне парсера. Транслятор должен обработать готовое применение через семантику соответствующего ресивера. Список допустимых Expression-ресиверов в P0 не добавляется.

Обычный ресивер `@` обрабатывается под своим существующим именем и с существующей ролью. Написание `` `@name` `` даёт отдельное целое имя `@name`. Внутри этого имени не выделяются ни оператор `@`, ни ссылка на переменную `name`.

Точный идентификатор проходит обычный lookup. Имя `` `++counter` `` также не превращается в изменение `counter`. Написание `` `++var`(counter) `` вызывает операцию с буквальным именем `++var`; её единственный аргумент — `counter`.

### 7.2. Две одноаргументные формы

Используются две группы применений: оператор стоит непосредственно слева от атома либо справа от него. Для `++` и `--` их полные имена в трансляторе и ресиверной записи закрепляются так:

| Операндная запись | Имя варианта | Ресиверная запись | Изменение места | Результат |
| --- | --- | --- | --- | --- |
| `++x` | `++var` | `` `++var`(x) `` | Увеличение | Новое сохранённое значение |
| `x++` | `var++` | `` `var++`(x) `` | Увеличение | Значение до изменения |
| `--x` | `--var` | `` `--var`(x) `` | Уменьшение | Новое сохранённое значение |
| `x--` | `var--` | `` `var--`(x) `` | Уменьшение | Значение до изменения |

Это принятый договор этой редакции. Наличие двух положений `++`/`--` уже отражено в [таблице операторов](LMX_grammar.en.md#operators) и [семантике выражений](LMX_semantics.en.md#assignment-inside-expression). Явное указание результата перенести в документацию и приёмку обеих форм.

`var` — метаобозначение **одного аргумента**, а не часть фактического имени изменяемой переменной. `++x`, `++counter` и `++items[index]` выбирают один вариант `++var`. Отдельные операции `++x`, `++counter` и т. п. из этих выражений не создаются.

Аргументом служит целый уже сгруппированный атом, способный обозначать PLACE. Поэтому обычное вычисление поля или индекса сохраняется:

```lmx
items[next()]++
`var++`(items[next()])
```

Эти записи — альтернативы одного применения. В каждом случае `next()` достигается один раз, определяется одно место, выполняются одно чтение прежнего значения и одна успешная запись нового. Общая норма однократного определения назначения уже задана для [изменяющего присваивания](LMX_semantics.en.md#compound-assign).

Положение берётся из существующей структуры применения. Исходные spans можно использовать для диагностики и roundtrip. Для созданного или изменённого графа достаточно порядка и связи в самой структуре; наличие исходного текста не становится новым требованием. Правила допустимых пробелов P0 этой спецификацией не меняются.

Тот же способ именования применять к другим **действительно объявленным** одноаргументным вариантам, если различение их положения требуется для ресиверной записи. В описании операции фиксируется имя всего шаблона с `var` на месте аргумента. Если имя совпало с другим реальным определением, действует обычный контроль перегрузок и конфликтов — без скрытой замены определения. Существующий ресивер `@` продолжает обрабатываться по своему договору.

### 7.3. Каноническое имя и форма применения

Канонизация имени и выбор варианта готового применения — последовательные обычные действия. Например, `++` — имя распознанного оператора, а всё применение с атомом слева выбирает вариант `var++`. Кавычки этот выбор не выполняют.

Вызов `` `var++`(x) `` разрешается тем же resolver и теми же правилами перегрузки, что соответствующее операндное применение. Литеральная часть `var` в **имени операции** не является wildcard для поиска других имён.

## 8. Код трансляции уже разобранных форм

### 8.1. Исполняемый эталон

Отдельный Python host-эталон участка транслятора использует [общий helper depth](tools/operand_depth_reference.py). Он проверяет ограниченную модель уже разобранного графа; документационные примеры операций и общие тела ниже записаны на LMX. Файл эталона: [translator_reference.py](reference/operation_forms/translator_reference.py).

`OperationUse`, `AttachedUpdate` и `Actual` — небольшие представления данных для эталона, получаемые из существующего графа. Это не новые типы операндов LMX и не предложение менять P0. В частности, `operatorBeforeAtom` читается из уже определённого положения операции в графе.

`resolveExistingOperation` и `lowerExistingOperation` обозначают интеграцию с существующими механизмами выбора и трансляции. Названия этих двух Python-методов иллюстративны: документ не утверждает наличие такого API в доступном архиве.

Полный исполняемый host-инструмент сохранён отдельно: [translator_reference.py](reference/operation_forms/translator_reference.py). Его язык и статус указаны явно; это вспомогательная проверка, а не LMX-тело ядра.

### 8.2. Обязательства общего обработчика

`translateOperation` одинаково передаёт существующему обработчику `@`, `return`, `finally`, `copy`, обычную функцию, пользовательский операнд и нормализованное унарное применение. Для каждого сохраняются исходные роли. Внутри общего пути не появляется цикл «сначала вычислить все аргументы как значения».

Полный аудит из раздела 5 выполняется по обработчикам транслятора. Если реализация ресивера уже существует, его Expression-форма направляется в неё. Если конкретная форма ещё не переводится, дополняется общий обработчик или общее отображение аргументов; P0 продолжает передавать прежнюю структуру.

`UPDATE_RULES` показывает четыре описания выбранных операций для эталона. В production свойства берутся из существующего описания разрешённой операции. Таблица не становится вторым глобальным реестром и не перехватывает пользовательские имена перед обычным lookup.

`lowerUpdate` — одно базовое скалярное тело всех четырёх вариантов. Выбор глубины и получение скалярной ячейки предшествуют этому телу; для Array его использует [общий подъём операции](OPERATOR_DEPTH.ru.md#evaluation); локальная копия обхода Arrays в этом эталоне не вводится. Числа `+1/-1` обозначают только направление шага. Само значение не приводится к `int`: `stepValue` использует действительный профиль операции, а `storeValue` — требования настоящего места.

Интерпретатор выполняет существующие операции backend, нативный транслятор порождает соответствующие действия в том же порядке. Там, где update-алгоритм уже есть, обе формы используют его; эталон задаёт наблюдаемый договор и не требует второго тела реализации.

`readValue` сохраняет прежнее значение, а не изменяемую ссылку на сам слот. `storeValue` возвращает сохранённое значение без второго чтения. При отказе определения места, профильного шага или admission сохраняются исходное имя и payload ошибки. Нового общего catch или преобразования всех ошибок в текст нет.

`Actual.context` сохраняет происхождение аргумента. `OperationUse.context` сохраняет контекст применения. Если они различаются после переноса RAW или прохода через чужую функцию, обработчик применяет существующие правила исходного контекста и динамического связывания; контекст применения не подменяет происхождение аргумента.

### 8.3. Порты, группы и порядок

Для общего Expression-шаблона сохраняется действительное расположение входов:

```text
(op a b)       → left отсутствует, depth отсутствует, right = [a, b]
(a op b)       → left = a, depth отсутствует, right = [b]
(a op)         → left = a, depth отсутствует, right = []
(.(n)op a b)   → left отсутствует, depth = значение n, right = [a, b]
```

Это варианты записи общего шаблона, не три новых типа операндов. Для обычной функции и её операндной формы используется существующее отображение логических входов. Для встроенного или пользовательского операнда — отображение его действительного контракта.

У четырёх унарных вариантов отображение уже определено: один исходный атом передаётся как единственный PLACE. Ни ручного выбора `left/right` пользователем, ни дополнительного view для различения старого и нового значения не нужно.

Для остальных операций перенос входов сохраняет их исходные occurrences, именованные actuals, отсутствие actual, группы и порядок потребления. Переход ко второй форме не повторяет W/E или подготовку текущего уровня аргументов. DATA, NAME, TYPE, RAW и PLACE не становятся VALUE вследствие смены записи.

## 9. Подключение существующего кода LMX

Для системных и управляющих ресиверов общий путь проходит через их существующий обработчик транслятора. Он сохраняет текущую активацию, cleanup, BODY и другие роли непосредственно.

Обычный операнд уже является методом. Его ресиверная запись вызывает тот же метод по каноническому имени. Это особенно просто для буквенного имени:

```lmx
return: some(x) bind half bind half
return: bind(bind(some(x); half); half)
```

Это альтернативные записи одного вычисления. Каноническое имя монадической операции остаётся `bind`. Оба применения имеют реальные типы и конечный договор исключений соответствующих перегрузок.

Когда пользователь действительно строит операнд из готового callable, используется существующий `FxAsOperand` из [coreStandardLisp.lmx](patterns/LMX_Fn_Receivers/src/coreStandardLisp.lmx). Для необходимого построения callable уже есть `FxFullPolicy` / `FxForwardEngine` в [adapter_frames.lmx](patterns/LMX_Fn_Receivers/src/adapter_frames.lmx) и `FxWrap` в [generic_runtime.lmx](patterns/LMX_Fn_Receivers/src/generic_runtime.lmx).

При таком построении сохраняются точный R/void, defaults, `private/required`, реальные typed records и ошибки построителя. Эти библиотечные механизмы применяются по своему назначению; поддержка ресивера в Expression не требует обязательного вызова фабрики `asReceiver`.

Свойства `PASS_ARGS_AS_IS` и `PRIORITY` остаются в настоящем DATA операции и готовы к соответствующей стадии группировки/исполнения. Нет второго графа реализации, отдельных алгоритмов для кавычек или скрытых переименований вроде `plusReceiver`.

## 10. Закреплённые обязанности транслятора

Вопросы о кавычках для `@` и выборе результата прижатых `++`/`--` сняты авторским уточнением и договором раздела 7. Они не остаются условиями, блокирующими работу.

| Случай | Требуемая обработка |
| --- | --- |
| Существующий `@` | Обычный ресивер со своей ролью в текущем контексте; специальное заключение в кавычки не требуется. |
| `` `@name` `` | Одно каноническое имя; его содержимое не превращается в другую конструкцию. |
| `++var` / `var++` и `--var` / `var--` | Один PLACE, уже выбранное положение и результат из таблицы; общий update lowering. |
| `return` в DATA или CODE | Существующий TYPE-договор либо выход из исходной активации. |
| `finally`, `catch` и loop transfer | Прежние scope, BODY, cleanup и continuation. |
| Пользовательский operand | Его действительный шаблон left/depth/right, priority, режим и роли. |
| `end:`, fences, разделители | Существующая структурная обработка; их участие в аудите не создаёт произвольных runtime callback. |

Две записи с тем же каноническим именем, тем же контекстом и тем же отображением actuals ведут в одну семантику. Сохранённое написание используется для исходника и диагностики, а не для выбора другого поведения.

## 11. Карта реализации и миграции

Для каждого реального определения текущей реализации зафиксировать:

| Поле аудита | Содержание |
| --- | --- |
| Имя и источник | Каноническое содержимое, реальный файл и владелец. |
| Формы | Ресиверная, операндная, обе либо структурная роль. |
| Обработчик | Существующая реализация трансляции и место подключения второй формы. |
| Аргументы | Роли каждой позиции и контекста, named actuals, arity, defaults. |
| Результат | Точное R/void/FIELD STREAM/transfer/suspension. |
| Эффекты | Порядок, ленивость, запись, admission, cleanup. |
| Контекст | Parent/DATA, исходная активация/namespace, Message owner. |
| Отображение | Left/depth/right, omission, группы, положение одноаргументной формы; обычные receiver actuals не сдвигаются. |
| Ошибки | Полный конечный договор; построение отдельно от исполнения. |
| Статус | Поддержано; требуется подключение; отсутствует общий обработчик; найден конкретный конфликт определений. |

Ни одно определение не пропускается из-за сложности обработки. Структурная форма отмечается со ссылкой на грамматику; отсутствующий provider не объявляется работающим.

Порядок реализации:

1. Инвентаризировать обработчики всех системных, библиотечных, профильных и пользовательских операций в актуальном трансляторе.
2. Сопоставить уже разбираемые ресиверные и Expression-формы с этими обработчиками.
3. Подключить отсутствующие формы к общему пути с сохранением аргументных ролей и исходного контекста.
4. Для прижатых одноаргументных вариантов закрепить имена `++var` / `var++`, `--var` / `var--` и аналогичные имена существующих шаблонов.
5. Проверить буквальные ключи и границы точных токенов через P0 и потребителей. Граф и транслятор получают полные байты без повторного разбора.
6. Устранить только реально обнаруженные пробелы общей трансляции. Конфликт конкретных определений документировать с именами и источниками, а не объявлять все формы неоднозначными заранее.
7. Обновить каталог, нормативные главы, короткие примеры и генераторы LMX. Сохранить полные `throws`.
8. Исполнить runtime-приёмку на обеих формах и на интерпретируемом/нативном пути.

Канонические имена следуют общей таблице миграции: `bindResult/flatMap → bind`, Pattern `sequence → then` и остальные. Прежние имена не остаются вызываемыми aliases. Все действующие исходники, каталоги и примеры используют эти канонические имена.

## 12. Приёмка

### 12.1. Имена и готовая структура

- P0 передаёт все ресиверы в Expression прежним общим способом.
- `@` переводится как существующий ресивер, без требования кавычек.
- Обычное и точное написания имеют разные ключи и выбирают разные места.
- Точные имена `@name`, `++counter`, `counter++` и `a+b` не делятся на токены при трансляции.
- Удвоенная кавычка, пустое имя, пробел, newline, punctuation, backslash и Unicode сохраняют базовый договор.
- NUL отвергается; цифра `0` принимается.
- Имя не обрезается по пределу 3/4 символа.
- Qualified exact segment отличается от одного exact name с backslash.
- Служебное имя определяется полным ключом. Проверить `node` и токен `` `node` `` в допустимых ролях.
- Для созданного программой графа отсутствие исходных текстовых spans не препятствует выбору готовой формы.

### 12.2. Операции

- У всех четырёх унарных вариантов сравнить обе записи, новое состояние места, возвращаемое значение, реальный тип и отказы.
- У `++items[next()]` и `items[next()]++` вызов индекса и определение цели происходят по одному разу; результат различается по таблице.
- Неподходящая арность отвергается до эффектов аргументов.
- Ошибки определения места, профильного шага и admission сохраняют имя/payload и прежнюю последовательность эффектов.
- Не ограничивать проверку одним `int`: покрыть реальные поддержанные числовые/пользовательские профили.
- У `&&/||` пропущенный RHS не имеет эффектов в обеих формах.
- У assignment цель с эффектом вычисляется один раз; все RHS групповой записи готовы до первой записи.
- У `::` имя не lookup-ится как значение; DATA actual не запускает initializer.
- У `copy/merge/import` сохраняются поток, группы и parent методов.
- `return/finally/break/retry/catch` воздействуют на исходный scope.
- Нулевые контекстные запросы не смотрят на DATA обёртки.
- RAW со свободными именами проходит через чужую функцию без захвата служебными локальными именами; происхождение actual сохраняется отдельно от контекста применения.
- Message-операции сохраняют owner, порядок подготовки/publish и время жизни.
- Admission failure текущего actual предотвращает эффекты последующего.
- Группировка, подготовка вектора actuals и W/E не выполняются повторно.

## 13. Итоговый договор

Парсер уже допускает все ресиверы в Expression. Транслятор подключает их к существующим обработчикам и сохраняет роли, контекст, типы и полный договор ошибок.

Ресиверная и операндная записи используют одну операцию. Прижатые одноаргументные варианты получают явные имена шаблонов; точные идентификаторы остаются непрозрачными именами. Канонизация кавычек сохраняется на существующем базовом уровне.

## 14. Общая глубина обхода depth

Общий transport depth принимает целое со знаком и сохраняет отсутствие. Custom-метод может считать его иной настройкой и не включать Map. Ноль как максимум, неотрицательность и проверка d<=ранга Array относятся к выбранному стандартному Array-обходу, а не ко всем применениям синтаксиса или транспорта.

[Общий договор](OPERATOR_DEPTH.ru.md) сохраняет порядок **left, depth, right**.
Обычные поэлементные операции используют максимальную глубину. Явный
`depth=0` также означает максимум; положительное N задаёт ровно N внешних
логических осей. Ранг Array остаётся числом его осей, а не новым именем depth.

У Array ранга K после N осей остаётся ячейка ранга K-N. Положительное N>K
диагностируется; исходный scalar не добавляет ось и повторяется по общему
scalar-договору. Выбранное базовое тело получает ячейку без повторного
автоматического Map: иначе параметр не ограничивал бы обход. Явные операции
внутри пользовательского тела остаются обычным кодом.

| Expression | Договор |
| --- | --- |
| `a * b` | Максимальный обычный Map |
| `a .(0)* b` | Явно максимальный Map |
| `a .(2)* b` при rank(a)=rank(b)=2 | Скалярные ячейки после двух осей |
| `a .(1)* b` при rank(a)=rank(b)=2 | Строки передаются базовому `*`; scalar-only тело их не принимает |
| `a [*] b` | Whole матричное произведение, внешний depth отсутствует |
| `a .(1)[*] b` при rank(a)=rank(b)=2 | Скалярное произведение каждой пары строк |
| `a [* ()] b` | Явный indexed-профиль без связей: внешнее произведение |
| `target := source` | Обычное поэлементное присваивание |
| `target[:] .: source` | Присваивание срезу с транслированием RHS |

Пропущенный depth сохраняется отдельно от явного 0 до выбора профиля.
Для plain Map результат выбора совпадает; whole `[op]` при отсутствии depth
принимает целый объект. Явное `.(0)[op]` задаёт максимальный внешний обход
и должно быть допустимо фактическому базовому обработчику. Нельзя молча
превращать полученные скаляры обратно в whole матрицы.

Структурная форма использует базовое имя и именованный аргумент depth:
`` `+`(a; b; depth := 0) ``. Это не механический перенос служебного ABI в
позиционные аргументы обычного ресивера. Для custom-метода форма явна:

```lmx
DepthProbe\apply(left := first; depth := levels; right := arguments)
```

Отсутствующий left не пополняется из right. Отсутствующий depth не захватывает
случайную одноимённую динамическую переменную. Явное выражение depth получает
значение один раз в исходном контексте и только при востребовании операции;
невыбранные ветви не создают его эффектов. Формал вложенной пользовательской
функции с именем depth сохраняет собственную принадлежность.

`:=` получает снимок RHS и проверяет назначения до stores. `.:` — отдельный
договор среза с выравниванием RHS справа, равными длинами либо длиной 1.
Они используют один snapshot/admission/write с разными подготовленными картами.
Минимальный `fuse` — Scalar/Map со свежим результатом; последующий `:=` обычный.
Неподдержанный план даёт диагностику без материализующего запасного пути.

`.(` всегда начинает модификатор, не часть числа. Общее Expression внутри
разбирает основной parser. `.op`, `..op` и `...op` не являются сокращениями.
Точное имя `` `.(2)+` `` не разбирается заново; имена с точками не создаются.
[Квадратный подпарсер](BRACKET_SUBPARSER.ru.md) делегирует выражения и `{…}`
основному parser, возобновляя работу с nextPosition. Он не сканирует их границы.

[Полный тензорный договор](TENSOR_EXPRESSIONS.md). Python-модели проверяют
отдельные контракты уже разобранного графа. Production parser/translator/LMX
runtime этой редакции: **NOT_RUN**.
