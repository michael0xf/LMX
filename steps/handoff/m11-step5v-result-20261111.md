## 7. Вопросы (минимальной программой, с наблюдаемыми вариантами)

**1. Метод «только данные» без строк кода.** Документы и слова автора (`LMX_blog/2026-11-11.md`, строка 140: «sub: proc () (struct1: Template1; struct2: Template2)»; CORE.md около 433; L2_L3_CODING_INSTRUCTION.md:36) пишут объявления Structure в блоке данных метода так.

```
sub: proc () (struct1: a b; struct2: c d)
int: n length(proc\data)
```

Сейчас: `n` 0 — дамп печатает `struct1`, `struct2` телом `proc` (группа прочитана кодом). С явной пустой частью кода после группы — `sub: proc () (struct1: a b; struct2: c d) ()` — `n` 2. (Пробы `q50a.lm2`, `q50b.lm2`, `P/runs/sonnet-5v-01/t0/`.) Варианты: А) в примеры документов дописывается `()` (девять переведённых фикстур уже так пишут); Б) единственная группа без строк кода читается данными (тогда метод с группой-телом и без данных пишется иначе).

**2. `@: R merge(…)` в коде метода.** Ответ fable2: не обязано, в список.

```
S: (int: k 1)
Model: (int: v 2)
fn: f () int
    @: R merge(Model; S)
    return: 0
end: f
int: seen f()
```

Сейчас: ответ 3 (то же без записи запуска: проба `s560` — контроль для `s542`); та же запись в корне — 0 (`s562`); `@: R merge(Model; S())` в корне — 5 (`s561`); в части `data` метода любая запись `@:` — 5.

**3. `@:` с начальным значением-адресом и перенацеливание ссылки.** (Читатель `b09`.)

```
int: j 40
sub: main () (int: seen 0)
    @: q int @j
    seen := \q
main()
```

Сейчас: 3 (объявление `@: q int @j` в коде метода). В части `data` метода — 5. В корне: `@: q int` + `q := @j` — 3; `@: q int 0` + `q := @j` + чтение `\q` — 4. Вопросы: где допустимо объявление `@: q int @j` с начальным значением; перенацеливает ли `q := @j` место-ссылку.

**4. Атом, называющий место той же части `data`, внутри кода метода.**

```
sub: main () (
    int: i 1
    Pair: i
    int: seen 0
)
    data\[0]Pair\i := 9
    seen := i
main()
int: r_seen main\data\seen
int: r_i main\data\i
```

Сейчас: код читает `i` = 1 (`r_seen` 1), корень после запуска читает `main\data\i` = 9: запись через атом попадает в место описания, а код читает копию данных запуска. Варианты: А) запись через атом называет то же место, что видит код (`r_seen` 9); Б) как сейчас (атом ищется лексически от места атома наружу, комментарий над `lmx_graph_atom_target`). В `declare_forms` записи через атом оставлены в корне.

**5. Печать графа (кандидат в дефекты).** Минимальная пара: сбой —

```
int: j 40
sub: main () (
    S:
        int: a 1
        int: b 2
)
    S[0] := @j
main()
@: q int main\data\S[0]
```

Ответ 0, но «graph: the graph does not print» (печатается `BEFORE`, `AFTER` нет, `rc` 1); норма — тот же текст с пустой группой кода и записью в корне (`sub: main () (…) ()`, затем `main\data\S[0] := @j`): печатается `@: q int @j`. Пробы `pr2.lm2`, `pr2_root_write.lm2`.

#### Сомнения

1. Блок-тело внутри круглых скобок (`if:` с телом блоком отдельными строками) строится иначе, чем в корне: одно тело-оператор раскрывается в хвост записи; тело из `int: absent 8` или из двух операторов даёт ошибку построения 2. Это выглядит как следствие отдельного цикла полей в круглых скобках (P0-BRACKET-CONTENT-SEPARATE-LOOP). В фикстурах тело записано в скобках (`if: ... (int: absent 8)`), там IR как в оригинале. Если правка P0 изменит чтение такой строки, control_missing, control_flow и post_loop надо перепроверить.
2. (г) в трёх файлах (known_assignment, known_assignment_selected, post_loop): раздельная запись данных и кода обходится без дочернего блока, и часть проверяемого теряется: «блок `data:` внутри кода не выбирается» стало «отдельная Structure CodeData не подана»; RepeatOwn теперь повторяет Repeat над Data. Дочерний `data:` в data main пока проходит (probe_ka_g), но по Р9 после 5г он станет вызовом `data`.
3. post_loop читает `main\data\Data\x` и `main\data\RepeatOwnData\x` в корне до первого `main()` (значение 0); на graph-f27 работает. Если читать данные метода до вызова не должно, значения до запуска можно снять кодом main в места его data.
4. `Self` записан с объявлением `int: x 0` дважды (поле и копия в теле `until`); так исходный текст строил трейлер, но в новой записи это два написанных объявления.
5. Лишние закрытия (`end: имя` после блока в один уровень) сняты во всех шести файлах целиком, в том числе в нетронутых методах, и замыкающая `---` в known_assignment; оставлены только `end: choose` и `end: while` в control_flow (перескок на два уровня, без них ошибка 2).

#### Выбранная форма

Все четыре положительные и одна отрицательная фикстуры — вид (е)/(з): проверяемая вещь — само объявление или путь к нему. Поэтому:

- объявления обычных Structure уходят в часть `data` метода `sub: main () ( … ) ()`: блоки в один уровень, без строк закрытия;
- у `main` нет кода, поэтому вызова `main()` нет: последний `()` — пустая часть `code` (без него группа в скобках, за которой не стоит ни кода, ни ещё одной группы, читается как код, а не как данные: проба ds1, `main\data\…` отвечает 3);
- всё остальное остаётся в корне, как было (места `int:`, `@:`, присваивания, вычисляемые места); пути к Structure получают префикс `main\data\` (наблюдение путями и `length(...)` из корня — правило вида (е));
- схема «места в `data` main, записи в коде main, `main()` в корне» (рецепт по умолчанию) для declare_forms не годится: атом `i` внутри `Pair` в `data` main называет не то место, которое видит код main (проба mc1: после `i := 6; data\[1]Pair\i := 9` код читает `i` = 6, а `data\[1]Pair\i` = 9; корень читает `main\data\i` = 6). В корне атом называет место корня (declare_forms, проба df4). Для declare_nested рецептурная схема тоже работает (проба dn2), но корневая точнее хранит слова фикстуры «читается и пишется путём».

#### Сомнения

1. Форма fn_prepared и merge_code_descriptions отходит от рецепта «операторы в код main»: `fn` с операндом-Structure не исполняется в коде метода (5), а `@:` в коде метода отвечает 3, поэтому ресиверы `fn` и места-ссылки `@: имя main\data\имя` остаются в корне, а в `main` ушли объявления Structure и вызовы/чтения.
2. Место-ссылка на Structure из части data метода по пути (`@: prepared main\data\prepared`) принята graph-f27 и по виду повторяет `@: P M` из reference_alias; план называет формой подачи ресиверу `fn` написанную Structure на месте значения ссылки (5е, сейчас отвечает 2). Не знаю, считает ли автор путь в data метода окончательной формой.
3. Добавлены места, которых в оригинале не было (p_calls, p_fields, p_parts, av_a, av_fields, d1_b, d2_b, d2_args, d1_parts, d2_parts): дамп оригинала показывал целые блоки prepared, AV, d1, d2, а новый дамп печатает описание `main` как написано, и без этих мест проверка «остаются как написаны» (merge и `fn` не правят свой операнд) стала бы невидимой. Если лишние места не нужны, их можно убрать: значения оригинала от них не зависят.
4. Все закрытия `end: Имя` сняты в файлах целиком (были только одноуровневые), в том числе у не переносимых `fn` (descriptor_merge, fn_return_forms, merge_arguments, merge_call_*). Дампы descriptor_merge и fn_return_forms без закрытий побайтно равны прежним.
5. Для неизвестной головы операнда `merge` ответ зависит от положения: 5 в инициализаторе места корня, 3 в присваивании внутри метода. #### Отнесение к «корню как данным» (замечание к пачке)

#### Сомнения

1. Режимы native и forced у graph-check не запускались (запрещено): подтверждён только интерпретатор `graph-f27`. 5. Снято правкой f09: имя `seen` теперь стоит только в корне (в `data` `main` его больше нет), затенения имени нет.
6.
