# ТЗ: общий signatureTypes и прямые ресиверы

Редакция **2026-11-22**. Основная постановка миграции находится в
[docs/tasks](../../tasks/TZ_Receivers_Satisfies_2026-11-22.md); этот документ
фиксирует интеграцию конкретных LMX-исходников в ядро.

## Обязательные условия

1. P0 сохраняет каждую написанную Structure. Нельзя снимать единственный
   анонимный контейнер на уровне парсера. Исключение требует сразу трёх условий:
   слева написана безымянная Structure, right.length = 1, right[0] — написанная
   безымянная Structure. Снимается только внешний правый контейнер и только один
   уровень; left остаётся целым. Function result, именованная ссылка и массив
   сами по себе не раскрываются. Обычный callable W/E остаётся отдельным контрактом.
2. Публичное `implements` переименовывается в `satisfies`, без изменения
   направленности/глубины анализа. Случайный bool-result или runtime-пробный
   вызов candidate этим переименованием не вводится.
3. Существующие двухаргументные формы объявлений примитивов из текущих docs
   не запрещаются повторно историческим пунктом старых редакций. Работать по
   приложенному текущему синтаксису, а не по давно отменённым промежуточным ТЗ.
4. Именованное объявление целиком перенесено в `Name :: DATA`; прежний declaration receiver удалён без alias. Type-token signatureTypes даёт тот же вид сигнатуры.
   Взаимозаменяемость действует для всех применений, кроме намеренного
   сохранения существующего отношения именованной сигнатуры с receiver call.
5. Новые часто используемые функции доступны прямыми именами в стандартном namespace
   единого ядра без пользовательского import. Не добавлять отдельный registry и parser branch по каждому
   имени. Общий код и контейнеры остаются LMX, а не переносятся в ядро целиком.

## Именованная форма `::` через общий операнд

`Name :: Signature` целиком заменяет старую именованную форму, сохраняя её
контракт единственного правого DATA-шаблона. `::` — обычный операнд выражения с
общим `OPERANDS_TEMPLATE`, режимом сохранения форм и декларационным потреблением
левого идентификатора. Нельзя добавлять отдельную грамматику separator или
приравнивать `Name :: A B` к `Name :: (A B)`: в первом right.length = 2, во втором
right.length = 1. Извлечение полей принятого единственного шаблона не раскрывает
правые аргументы операнда. `FxSignatures\make` сохраняет `Built :: data`.

Приёмочные формы зафиксированы в
[signature_operand_shapes.json](tests/signature_operand_shapes.json).
Это задания для реального общего parser/operand resolver; текущая текстовая
проверка пакета не выдаётся за их исполнение. Смысл дополнительных правых форм
именованной сигнатуры этим ТЗ не изобретается.

## signatureTypes через OPERANDS_TEMPLATE

Выбранная форма: `R signatureTypes T0 T1 ... TN`. `left` обозначает тип результата, все
`right` — входы; последний правый тип не отнимается как Haskell-result.
Прямой qualified вызов `fun\const\signatureTypes(left := R; right := typeRecords)` использует
тот же [метод](src/fn_operand.lmx). Именованное объявление `Name :: DATA` использует общий вид требования;
оно не является ещё одной формой явного вызова ядерного операнда.

Оба пути используют одну нормализацию полных требований и существующее
объявление `Built :: DATA`, как это явно сделано в FxSignatures\make. Имена и значения defaults
не участвуют в signature identity. Полные типовые модели и result/void участвуют.
Параметры p0…pN — адресация actuals через позиционное отображение, не новые типы.

В [fn_equivalence.lmx](examples/fn_equivalence.lmx) подготовлены оба направления:
новый type-contract принимает старый callable; старый named-contract принимает
созданный общим builder callable. Есть mixed types, void и нулевая арность.
Uninit type tokens отдельно проверены в
[fn_and_assignment.lmx](examples/fn_and_assignment.lmx). Прежний corpus взаимодействия именованных сигнатур с call
обязан сохранить прежние ожидания.

## Обобщённость и ошибки

Каждая Structure — прямой массив @. Этот факт используется для фактических
аргументов, captured prefixes, списков, outputs, индексов и патчей. Нет
фиксированной пользовательской арности, IntBox-only payload или int-only R.
int для индекса, type code, логического состояния и счётчика не отменяется.
Контейнеры хранят адреса полных value records, включая primitive, pointer,
string, array, structure, callable и явный void там, где он обозначает результат.
Чтение отсутствующего payload uninit остаётся обычной ошибкой, кроме чтения
самого type token без его значения.

Для произвольных declared callback failures обычные record APIs используют
FxCallFailure с сохранёнными name/payload. Generated typed wrappers переносят
полный конечный список throws и восстанавливают исходное имя. Реализация не
опирается на фиктивное throws:* или молчаливую универсальность handler.

## Единое ядро и честное сравнение

Все описанные операции являются одной текущей частью ядра; optional packages,
выбор версий и пользовательские imports для этих имён не вводятся. Исторические
исходники — происхождение и процедурные аналоги, не исполняемые альтернативы.
Включение ядровых тел остаётся конкретной задачей реализации, пока не выполнена
проверка реального runtime; наличие текста не является подтверждением запуска.

В сравнении kernel helper бесплатен только когда другая сторона также использует
библиотеку или обычный оператор, скрывающий эту работу. Если контроль реализует
приём самостоятельно, считаются LMX-тело и оговорённые общие зависимости.
Выбирать основным самый короткий **сопоставимый по этим условиям** вариант;
другой и процедурный аналог сохранять. Короткий core-вызов, не удовлетворяющий
этой границе, остаётся дополнительным, а не подменяет основное сравнение.

При этом архитектурно оптимальный LMX не переписывается ради совпадения алгоритма
контрольного языка. Собственные общие примитивы LMX — copy, merge, binding,
обычный вызов и работа с графом — законно остаются примитивами языка; их runtime
реализацию не разворачивают в каждом сравнительном листинге. Проверка границы
касается сокрытия специфической работы helper за коротким вызовом, когда другая
сторона показывает эту работу вручную, а не требования одинакового алгоритма.
