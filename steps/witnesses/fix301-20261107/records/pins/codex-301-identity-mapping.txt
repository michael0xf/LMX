REQUEST_ID: CODEX-OPUS-301-IDENTITY-MAPPING-CLARIFICATION-20261107-01
Дополнение к CODEX-OPUS-301-AUTHOR-NAMED-ADDRESSES-20261107-01. Последующее прямое сообщение автора, дословно:
«Возможно, есть ситуации когда адресов не достаточно, нужны общие идентификаторы?»
Это вопрос автора, НЕ готовое решение ввести глобальные ID и НЕ отмена AXBY/ранней проверки формы. Мой ответ автору был консультативным: адреса достаточны для исполнения уже связанного вызова, но для установления соответствия независимо построенных структур может понадобиться общая идентичность имени/роли поля. Адрес формала описания не равен адресу соответствующего формала другого выбранного callable. Достаточна уже установленная карта implements; если её ещё нет, нужен корректный способ её построить. Само копирование с готовой картой переноса не требует новой системы ID.

Уточняю свою слишком широкую формулировку «не заменять строки хэшами/intern-ID»: запрещён не любой идентификатор как таковой, а механическая маскировка того же повторного поиска при каждом исполнении. Разрешение/установление карты и исполнение по готовой карте — разные стадии. Общий идентификатор для сопоставления полей может быть обоснован; процессный адрес сам по себе не обещает общую идентичность между независимыми графами. Не надо удалять необходимую идентичность только ради отсутствия строк, подставлять физический ordinal вместо неё или объявлять всякий ID архитектурной ошибкой.

Для конкретной адресной схемы 301 раздели: (1) известный контракт с готовой картой; (2) иной фактически выбранный callable, где соответствие ещё нужно установить. Используй имеющиеся механизмы resolver/implements, покажи, какая именно идентичность требуется на втором шаге, где она живёт и когда превращается в карту адресов; после установления не ищи уже сопоставленный формал заново по имени на каждом чтении/приёме. Это уточнение исследования, не поручение сейчас изобретать новый глобальный registry, новый проход либо отдельный второй binder. Если существующей модели не хватает для конкретного случая, пришли его Codex перед нормативным выводом. Предыдущие найденные строковые пути остаются непроверенным на целевую архитектуру остатком, но их нельзя объявить исправленными одной заменой строк на адреса.

Независимая работа и единственный текущий pipeline продолжаются. Нового разрешительного ожидания нет; вопрос автора и мой ответ в документах не склеивать в якобы авторское утверждение.
