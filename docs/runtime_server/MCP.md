# MCP на LMX и совместимость агентов

<a id="runtime-mcp"></a>
## Входы сервера

Вход MCP реализует LMX-приложение. Стандартный клиент передаёт JSON-RPC, а LMX-клиент может выбрать обычный локальный Message или прямой текстовый транспорт. Во всех трёх случаях выбор операции, контекст, допуск, выполнение и расписка принадлежат одному Service. Отдельное соединение **от** LMX к провайдеру модели используется операцией `ask`. Сервер может работать и без провайдера модели. [Тело граничных адаптеров](src/boundaries.lmx) · [Операции](API.md#runtime-operations).

| Вход | Граница документа | Как передать результат |
| --- | --- | --- |
| Локальный LMX | Обычный вызов или `post` к разрешённому входу с готовыми значениями и ссылками | Ответ по обычному маршруту Message с соблюдением владения |
| Прямой текст LMX | HTTP `POST /lmx` с полным телом UTF‑8 (проектный media type `application/lmx`). Для трубы или сокета профиль задаёт `Content-Length: N\r\n\r\n` и ровно N байтов | Полный LMX-документ через `sys\toLmx` или фактический транспортный отказ |
| MCP | Отдельный `/mcp` по Streamable HTTP либо stdio выбранной ревизии. В stdio одна JSON-RPC запись UTF‑8 на строку, служебные логи идут в stderr | Стандартный result/error с исходным id. LMX-результат можно выдавать как текст и заявленный `structuredContent` |

Фреймер учитывает многобайтовый текст, несколько чтений/записей, лимит длины и EOF посреди документа. Пустая строка является частью LMX. Обрыв до конца кадра оставляет ноль исполненных команд. Потеря ответа после передачи владельцу оставляет исход неизвестным до расписки. Отдельно испытываются два кадра подряд и два клиента с разными областями. [Пример обмена](examples/04_remote_documents.lmx).

## Профили протокола

По состоянию на 27 ноября 2026 года проект привязывает основной профиль к `2026-07-28` и совместимый профиль к `2025-11-25`. Версия, перечень провайдеров и реально проверенные capabilities видны клиенту. Стандартный слой охватывает протокол каждой заявленной ревизии. Всё богатство графа доступно поверх него через инструменты и ресурсы LMX. [Версии MCP](https://modelcontextprotocol.io/specification/versioning) · [Спецификация 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28).

| Область | 2026-07-28 | 2025-11-25 |
| --- | --- | --- |
| Начало и версия | Каждый запрос несёт версию и метаданные клиента по правилам ревизии. Сервер реализует `server/discover`. Клиент может сразу начать с полезного запроса. В HTTP сверяются обязательные заголовки и поля тела. | `initialize` → ответ с согласованными версией и capabilities → `notifications/initialized`. Дальше действуют правила согласованной сессии. |
| Предметные методы | `tools/list` и `tools/call`, при наличии провайдеров — ресурсы, шаблоны ресурсов, prompts, completion. Полный документ для инструмента `lmx` передаётся в `arguments.document`. | Те же предметные возможности через схему методов, аргументов и результатов этой ревизии. Сохраняются `ping` и её механизмы уведомлений. |
| Дополнительный ввод и события | При необходимости `input_required` запрашивает ввод, клиент продолжает с `inputResponses`. `subscriptions/listen` и первое подтверждение фильтров связывают поток с запросом. Учитываются progress, cancellation, pagination и область кэширования. | Дополнительные запросы сервера, progress, cancellation и подписки работают по договору этой сессии и только в согласованных возможностях. |
| Долгая работа | Отдельное расширение Tasks предлагается при наличии поддержки всего объявленного жизненного цикла. Состояние опирается на действительную Job и её сохранённый исход. | Экспериментальные Tasks этой версии испытываются отдельно при их объявлении. |

Тестировать обе версии на stdio и HTTP. Для текущей ревизии проверять дискриминатор результата там, где он предусмотрен, ошибки версии, обязательные `_meta` и согласованность `Mcp-Method`/`Mcp-Name` с телом, когда заголовок применим. Для обеих — недоступный метод и отсутствующее право до отправки команды владельцу. Отказ транспорта или JSON-RPC и прикладной отказ допущенного LMX-инструмента имеют разные представления. Пагинация, отмена, протокольный повтор запроса с дополнительным вводом и переподключение не должны повторять уже исполненную запись. HTTP проверяет Origin и полномочия как для ресурса, так и для операции. Кэш, подписка и продолжение принадлежат тому же клиенту и scope. [Основной транспорт](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports) · [Авторизация HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) · [Инициализация 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle) · [Векторы протокола](fixtures/mcp/MANIFEST.json).

<a id="mcp-projection"></a>
## Как выразить запрос агента

У `tools/call` с `name="lmx"` аргумент `document` содержит законченную **команду**. Чтобы исследовать присланный исходник, агент передаёт его как текстовый аргумент обычного `sys\fromLmx`. Например, команда `sys\toLmx(sys\fromLmx("int: counter 0"))` возвращает построенную структуру. Более крупный документ можно получить через разрешённый ресурс и передать тому же ресиверу как значение. Поиск, чтение ресурса и построение такого графа оставляют тела исходника до отдельного вызова. Клиент передаёт строки средствами JSON-кодека. [Текст и готовая ссылка](API.md#runtime-operations) · [Вектор tools/call](fixtures/mcp/2026-07-28/positive/03_lmx_tool_call.json).

| Возможность MCP | Что получает клиент LMX |
| --- | --- |
| `resources/list`, `resources/templates/list`, `resources/read` | Правило с хешем, разрешённый исходник, страницу каталога или конкретную расписку. В URI снимка входит его token. Чтение текущего графа требует заново проверить область и помечается как живое наблюдение. |
| `prompts/list`, `prompts/get`, `completion/complete` | Описания сценариев и доступные значения аргументов из уже разрешённого контекста. Выбор подсказки оставляет исполнение отдельному запросу. |
| Дополнительный ввод, уведомления, progress, cancellation | Запрос сведений или согласия, извещение об изменившейся публикации, фактическое продвижение или остановка. Отмена запроса, остановка Job и судьба уже доставленной команды отражаются раздельно. |
| Расширения и прежние клиенты | Для Tasks, roots, sampling, elicitation и logging отмечаются версия, направление, согласованные флаги и реальный провайдер. Например, прямой ответ провайдера модели в Job сам по себе не реализует MCP sampling. |

Контроль покрытия сопоставляет объявленные сервером методы и их схемы со спецификацией выбранной версии. Для каждого метода воспроизводятся успешный обмен, отказ по правам или capability и поддерживаемые формы результата. В описании процесса указывается, какая часть этого протокола доступна в данной сборке. [Схема 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/schema) · [Схема 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/schema).

## Переход с действующего lmx-dev

Python/FastMCP сегодня предоставляет четыре инструмента. Первое переключение реального клиента разрешает совпадение контрактов, включая неудачные ответы, при одинаковых источниках и принятой связке. Общий permit и блокировка машинного конвейера действуют для обоих серверов. [Текущая реализация](../../tools/lmx_dev/server.py) · [Инструкция для агентов](../../tools/lmx_dev/USAGE.md).

| Существующий вызов | Что обязано сохраниться при переносе |
| --- | --- |
| `get_spec_rule(topic, max_chars, include_history)` | Тот же ruleId, authority, точный текст, файл, строки, hash раздела и редакции. Неоднозначность возвращает кандидаты, большой раздел — требуемый размер. Результаты из документации и наблюдения runtime различимы. |
| `service_status()` | Покрытие операций, состояние permit и общего lock, выбранная связка и причины недоступности. Клиент узнаёт, что действительно доступно *сейчас*. |
| `check_file(file, phase, closure)` | Прежние `syntax/static/translate`, допустимые имена связок, проверка путей, лог, host exit и логический ответ, диагностика, свежесть артефакта. Статическая проверка доступна согласно выбранной связке. Тело, тест или bootstrap этим вызовом не запускаются. |
| `bootstrap(profile)` | `smoke` и явный `selfHost` используют координированный конвейер и реально запускают целевые программы. Закрытый permit и занятый lock дают прежний отказ. |

Сначала публикуются операции только на чтение и проверяется совпадение на одних входах. Эффектные операции сравниваются на независимых эквивалентных состояниях или по уже записанным распискам. После подтверждения этих четырёх контрактов и сквозных проверок переключается один клиент, затем остальные. Смена endpoint обратно на `lmx-dev` сохраняет прежнюю схему вызова. Начатые Job остаются у принявшего их владельца с исходной корреляцией. Запрос команды на запасной endpoint автоматически не переотправляется.
