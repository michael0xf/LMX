LMX_ETERNAL_STORE — storage for `independent: const: immutable` branches (LMX-ETERNAL-R0-44D)
Written 20.09.2026 by deepseek, BEFORE any edit, as the durable form of the claim sent to Codex
under 44D.  Status: ACCEPTED AND LANDED -- see the closing section, which records what the
kernel actually does and every place it departs from the proposal below.  The body of this
document is kept as written, because the reasoning is what the code is answerable to.

THE INVARIANT (author's wording, as relayed)
  Branches qualified `independent: const: immutable` are translation-known, stored by Root Thread
  R0 for process lifetime, arena GC must not touch them, while pointers to them may occur in other
  Messages.

THREE MECHANISMS OF THE SAME MACHINE: STORE / CLASSIFY / TERMINAL
  A permanent store = an ordinary LmxArena carrying a NEW role flag, owned by R0, holding the
  eternal arrays and every branch body.  Every other arena carries a NON-OWNING pointer to it.
  GC never marks, never stamps and never sweeps it -- and never visits it at all.  classify gains
  ONE fallback: local bisection first, then the store's bisection, so a pointer into the store
  resolves from ANY Message with no per-Message classifier list.  copy/merge calls store-resident
  values terminal, so a pointer is SHARED, not cloned.

WHY THIS SHAPE (measured anchors, all under dev/l2src_sandbox)
  1. Today's storage is wrong by construction.  lmx_root.lm1:84-100 allocates the two retention
     arrays with lmx_node_new_owned(@ root\arena) + lmx_arena_refs_open_owned -- R0's OWN arena --
     and lmx_turn.lm1:134-147 hands that same arena to lmx_gc_collect.  GC therefore traverses
     them.  The comment at lmx_root.lm1:79-83 states the arrays survive "without the collector
     knowing anything about branches": that is the property the author has now rejected, so the
     comment is rewritten, not preserved.
  2. The translator already knows.  l2trans.lm1:9168 does l2_ns_eternal[root] = l2_ebr_n after
     l2_ebr_reserve(l2_ebr_n + 1).  The generated open is `lmx_root_open(..., 0U, 0U)`
     (l2trans.lm1:11913) -- a value that was never PASSED, not a value that could not be computed.
     Sizing needs no estimate: the store is an arena (bump allocation over blocks), not one
     pre-sized malloc.
  3. The cross-arena gap is solved for the store and ONLY for the store.  Split, and the split is
     load-bearing: classify / type_of = "what kind of thing is this" and MAY consult the store;
     range_pool = "whose storage is this" and stays LOCAL to one arena.  If range_pool gained the
     fallback, GC's early return at lmx_gc.lm1:105-118 would hand back the STORE's pool and the
     next lines would stamp the store's chunk -- the exact mutation the invariant forbids.

THE ADMISSION RULE IS THE LANGUAGE'S, NOT MINE (evidence, not opinion)
  tests/unit_eternal_shape.lm2:  E = {size_t a, char mark, inline (): inner, E: self, size_t z};
                                 F = {E: peer, size_t c};
                                 Holder = {E: kept, size_t mutable_cell};
                                 main: `R: merge: E Holder`, reads E\a, E\mark, E\inner\b.
  tests/unit_eternal_xref.lm2:   E has inline (): deep; F has `deep: into`; main reads E\deep\d.
  Three consequences:
    * CLOSED UNDER REFERENCE is already the admitted shape (F: E: peer; deep: into) -- so no
      arena-resident object can be reachable only through the store, and GC may skip it entirely.
    * SELF-REFERENCE (`E: self`) is why "never visit" beats "visit but do not free": a cyclic
      immutable graph needs a visited set, and this kernel's only visited set is the per-chunk
      `mark` stamp (lmx_gc.lm1:110-117).  Visiting would mean writing into the store.
    * POINTERS FROM MUTABLE STATE are already in the corpus: `Holder: E: kept` is an ordinary
      mutable Structure holding an eternal, and the corpus then MERGES them.  That is why
      lmx_copy_is_terminal changes instead of a pre-check at each call site.
  Consequence to keep on the record: a branch pointing at ordinary arena state becomes
  INEXPRESSIBLE rather than refused at runtime.  If the author ever wants that, this design must be
  revisited whole -- the admission rule is what buys GC's silence.

EXACT ABI
  A) lmx_arena.h.lm1:19-34, two new fields (the whole ABI cost, subject to Codex's agreement):
       @: LmxArena perm    non-owning; 0 = no store; never freed through it
       unsigned: permanent 1 = THIS arena is a store; chunks are process-lifetime; GC never
                           marks/sweeps them; only lmx_perm_close releases it
     Precedent for a role flag on the arena already exists: lmx_gc_collect:273 short-circuits
     `if: arena\simple != 0U return: c.LMX_GC_OK`.
  B) NEW lmx_perm.h.lm1 / lmx_perm.lm1: lmx_perm_open(root, eternal, methods),
     lmx_perm_store(root), lmx_perm_contains(perm, p), lmx_perm_classify(perm, p),
     lmx_perm_close(root).
  C) Changed, signatures unchanged: lmx_range_classify / lmx_range_type_of gain the fallback;
     lmx_gc_collect gains the permanent short-circuit beside :273; lmx_gc_mark_value gains one
     lmx_perm_contains test BEFORE lmx_range_pool (answer "not mine to walk" with no stamp and no
     descent); lmx_copy_is_terminal gains store-resident => 1.  The KIND_NONE => UNSUPPORTED branch
     (lmx_graph_copy_owned.lm1:249-254) stays, and the comment at :206 becomes true by
     construction instead of by assumption.
  D) Attachment in THREE kernel sites, no caller and no selftest learning a new call: R0's arena in
     lmx_root_open; child arenas by propagation in lmx_child_handoff; letter arenas in
     lmx_service_post.  lmx_message.h.lm1 and lmx_thread.lm1 are NOT touched -- LmxMsg has no arena
     field and LmxThread stores no arena, and none is added.

WHAT THE REPLACEMENT TEST MUST ASSERT (and why the old one cannot stay)
  tests/lmx_root_selftest.lm1:205-207 today asserts the branch survives BECAUSE the array is a GC
  root, and proves it with `lmx_range_classify(arena, branch) = LMX_KIND_STRUCT` where `arena` is
  R0's own -- true only because the branch sits in that arena.  That is evidence for the opposite
  property.  The replacement (new tests/lmx_perm_selftest.lm1) asserts the pair that separates
  ownership from resolvability:
    * lmx_range_pool(r0_arena, branch) = 0        -- R0's arena does NOT own it (today: non-zero)
    * lmx_range_classify(r0_arena, branch) = LMX_KIND_STRUCT   -- resolvable through the store
    * lmx_range_classify(child_arena, branch) = LMX_KIND_STRUCT -- from another Message too
    * checksum of the store's bytes identical before and after lmx_gc_collect on the child arena
      AND on R0's arena -- the strong form of "GC does not touch", replacing survival-by-root
    * the branch's cell still reads 7 after both collections
    * lmx_copy_is_terminal(store-resident) = 1, and a same-shape MUTABLE graph still copies/frees
      normally (control), and two roots/runtimes stay isolated (no process-global state)
  Then the full dev kernel gate, with command, target count, exit code and evidence path recorded.

OPEN QUESTIONS PUT TO CODEX (before any edit)
  1. Agreement for A): two LmxArena fields, or one role word?
  2. lmx_graph_copy_owned.lm1 -- who makes the is_terminal change (Fable has 4 authorized lines
     there)?
  3. (answered in this document's evidence section) is "closed under reference" the intended
     semantics?  The corpus says yes; if a branch must be able to reference arena state, the design
     changes shape.

WHAT LANDED (20.09.2026), AND WHERE IT DEPARTS FROM THE PROPOSAL ABOVE
  A) AS PROPOSED.  Two fields on LmxArena: the non-owning store link and the role flag.  Open
     question 1 is answered -- two fields, not one role word.
  B) SMALLER, AND THE DIFFERENCE IS DELIBERATE.  lmx_perm.lm1 has exactly five functions:
     lmx_perm_open(store), lmx_perm_close(store), lmx_perm_bind(arena, store),
     lmx_perm_store_of(arena), lmx_perm_is_store(arena).  There is NO lmx_perm_contains and NO
     lmx_perm_classify -- the qualified type of a branch is decided by membership in the store's
     ranges, and lmx_range_classify and friends already ask that.  A wrapper would be a second
     way to ask one question, and the header says why that is harmful rather than merely
     redundant.  The signatures also lost their root argument: a store IS an arena, so nothing
     in lmx_perm needs to know what an LmxRoot is.
  C) THE FALLBACK LANDED; ONE PROPOSED GC EDIT DID NOT, BECAUSE IT PROVED UNNECESSARY.
     lmx_range_classify, lmx_range_type_of and lmx_range_stride each gained the fallback;
     lmx_gc_collect gained the permanent short-circuit; lmx_copy_is_terminal gained
     store-resident => 1.  But lmx_gc_mark_value needs NO membership test: because
     lmx_range_pool stays LOCAL by contract, its existing early return already answers "an
     address this arena never handed out" for every store address, at no per-edge cost.  The
     comment at lmx_gc.lm1:276-283 carries that reasoning, so the absence is a decision.
  D) ATTACHMENT LANDED EARLIER THAN PROPOSED, AND ELSEWHERE.  R0's arena binds in lmx_root_open
     as proposed.  A child's arena binds in lmx_child_create BEFORE THE MARK -- not in
     lmx_child_handoff -- so that a revert on any later failure cannot leave a half-bound arena
     behind, and so that the copy itself can resolve store addresses while it runs.

  BEYOND THE PROPOSAL, found while landing it:
    * A CLOSED STORE IS NOT A STORE.  lmx_perm_close releases the store and clears its role, but
      nothing clears the link in the arenas bound to it, and there is no unbind anywhere -- a
      store deliberately does not know its binders, so no walk at close is possible.  The link
      is therefore made to answer for itself: lmx_perm_store_of and the three range fallbacks
      follow it only while the target still carries the role.  Lifecycle, not classification:
      it asks whether the store still EXISTS, never what a value is.
    * THE SOURCE ARENA IS THE ARENA THE SOURCE LIVES IN, and lmx_root.h.lm1 now states it on
      lmx_root_create.  Two red tests on 20.09 were violations of exactly that rule, and neither
      presented as one: the first as a service failure, the second as an access violation.

  OPEN QUESTION 2 is answered: the is_terminal change is at lmx_graph_copy_owned.lm1:194 and
  uses the pool pair, not a new constant.  OPEN QUESTION 3 stands as answered above -- the
  corpus says closed under reference.

WHAT IS MEASURED, AND WHERE
  tests/lmx_root_selftest.lm1:216-240 -- the single-runtime half: resolvable from R0's arena and
  not owned by it, type and stride agreeing with the store's, node = 0, the cell reading 7, a
  permanent root copying to the same address, a mutable control still copying.
  tests/lmx_perm_selftest.lm1 -- the half nothing asked, and the one where a wrong answer is a
  leak rather than a refusal: resolution from a SECOND Message of the same runtime; two runtimes
  in one process isolated in both directions, including a live store refusing an arena already
  bound elsewhere; the store's bytes unchanged across collections of two different bound arenas,
  with the instrument FIRST shown able to see a change at all; an eternal root returning itself
  rather than a silent OK with a null; an ordinary address of a third arena still refused with a
  null out; an eternal callable ready, resolved and run from another Message and refused to
  another runtime; merge sharing an eternal cell instead of cloning it, with the destination not
  coming to own it.
  tests/lmx_perm_child_selftest.lm1 -- creation from a store-bound source, and the release pair
  in both directions.

WHAT IS NOT DONE, EXACTLY
  * THE TRANSLATOR CANNOT POPULATE THE STORE YET, AND "PASS THE COUNT" IS NOT THE WHOLE OF IT.
    Traced 20.09 at HEAD 523553c (46U), with the proposal's own line numbers corrected where they
    had drifted:
      - THE COUNT IS NOT THE SYMBOL THE PROPOSAL NAMED.  l2trans.lm1:9213 sets
        l2_ns_eternal[root] to l2_ebr_n and l2trans.lm1:9219 then increments l2_ebr_n, so
        l2_ns_eternal[ni] is an INDEX into the branch table while l2_ebr_n is the COUNT.  The
        expression to pass is l2_ebr_n, not l2_ns_eternal[root].  The method side is l2_m_n,
        incremented once per method at l2trans.lm1:9701.
      - WHAT THE TWO ARGUMENTS ACTUALLY DO.  lmx_root.lm1:107-125 builds two graphs IN THE STORE
        and opens each with that many REF SLOTS, then puts them in R0's graph at slots 8 and 9.
        They size the two RETENTION ARRAYS.  They do not allocate a branch body, and they do not
        move one.
      - SO PASSING THEM ALONE WOULD BE WRONG, NOT MERELY INCOMPLETE.  The generated program
        builds its eternal branches with lmx_node_new_owned(l2_program_arena) at
        l2trans.lm1:14468, and l2_program_arena is lmx_root_arena of the root -- R0's ORDINARY
        arena.  Passing the counts would create store arrays that nothing fills while the
        branches stayed GC-visible in R0's arena: exactly the survival-by-being-a-root shape that
        lmx_root.lm1:102-106 rejects.  The translator already says so, at l2trans.lm1:14480,
        :14501, :14507 and :14521 -- "DEBT: eternal ranges/bootstrap-admit absent in new kernel".
        The generated program also builds its own branch array in the program arena
        (l2trans.lm1:14447), separate from R0's retention array, so there are two arrays and only
        one of them is in the store.
      - THE STORE IS REACHABLE WITHOUT INVENTING ABI.  lmx_root.lm1:85 binds R0's arena to the
        store, so lmx_perm_store_of(lmx_root_arena(root)) IS the store.  Nothing has to be added
        to lmx_root.h.lm1; the EMISSION has to move, and that is a larger change than two numbers.
        Both call sites hardcode the pair today: l2trans.lm1:11913 (the library open) and
        l2trans.lm1:14623 (the program open), each inside a single fputs of a literal string, so
        passing anything at all also means turning those into fprintf.
      - AND THE ETERNAL PATH DOES NOT BUILD TODAY.  l2trans.lm1:13907 emits, whenever l2_ebr_n is
        non-zero, a predef of lmx_owned_ranges.h.lm1 -- a file that exists NOWHERE in this
        repository, neither under dev/l2src_sandbox nor under l2src.  Any program with an eternal
        branch therefore emits L1 source with an unresolvable predef, before any of the above
        matters.  This is the first thing to fix and the cheapest.
      - NOTHING RUNS .lm2 HERE.  tools/build_l2src.ps1 neither builds l2trans nor translates a
        fixture; dev/l2src_sandbox/run_self_build.ps1 is the L1 chain and does not mention .lm2;
        no .ps1 under dev/l2src_sandbox does.  The 280 .lm2 files under tests/ -- including
        unit_eternal_branch, _many, _shape, _two and _xref -- are referenced only as documentation
        examples in docs/L2_spec_*.md.  So an end-to-end proof that a GENERATED program shares a
        branch across Message arenas is not expressible by the present harness, and producing one
        means building that harness first.  That is the honest order of work: harness, then the
        missing header, then move the emission into the store, then pass the counts.
      - MULTI-ROOT IS NOT REPRESENTABLE, SO THE TU-GLOBAL TOTALS ARE THE RIGHT EXPRESSIONS.
        l2trans.lm1:14612 calls l2_emit_library_wrappers() and l2trans.lm1:14616 is its `else`
        emitting main, so one translation unit emits EITHER the library wrapper OR the program,
        never both: exactly one lmx_root_open per generated output.  There is therefore no
        missing per-root counter -- l2_ebr_n and l2_m_n are TU-global because the root is.  The
        single-root contract is real but IMPLICIT, and nothing in the translator states or checks
        it; making it explicit is part of the emission slice, not a separate one.
      - THE LIBRARY FORM HAS ITS OWN, SEPARATE BLOCKER, AND THE TRANSLATOR STATES IT.  The text
        emitted at l2trans.lm1:11913 declares LmxRoot as a FUNCTION LOCAL and carries its own
        TODO: "need persistent LmxRoot storage (by-value aggregate is illegal at module scope --
        currently local, so open cannot stay open across calls)".  On that path the root dies at
        return, so sizing its store would size storage that is released immediately.
  * lmx_service_post does not bind a letter's arena.  It performs no copy today (only
    lmx_arena_attach), so nothing is wrong yet; a letter that ever copied from a bound source
    would need the bind first, and that is the condition to watch, not a defect to fix now.
  * The three range fallbacks' role guard is held for consistency with lmx_perm_store_of but is
    NOT independently measured: a released store answers nothing anyway, because its own index
    is gone.  The store_of guard itself IS measured, as a red-then-green pair.
