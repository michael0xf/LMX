# ТЗ для Fable: `signatureTypes` через `OPERANDS_TEMPLATE` и общие адаптеры функций

Историческая основа: 21 ноября 2026 года. Написания и границы операндов
согласованы с текущим ядром; это не подключаемая альтернативная версия.

## 1. Задача и последние решения автора

Реализовать создание обычной сигнатуры `signatureTypes` из передаваемых описаний типов через уже существующий протокол пользовательских операндов. Все описания помещаются в общий `@`: среди них числовые коды типов, неинициализированные примитивные записи, `void` и полные структурные требования. Именованная форма — `Name :: Signature`; прежний declaration receiver удалён.

Обобщить `lambda`, `partial`, `uncurry`, `flip` на произвольное конечное число аргументов, разные типы входов и исходный тип результата. В архиве приложены их LMX-алгоритмы и весь прежний набор из 50 позиций; `signatureTypes` занимает прежнюю позицию отвергнутого ресивера. Специализации для `int` сохранены как примеры и вспомогательное семейство. Они больше не являются единственной реализацией четырёх общих адаптеров.

**Последнее уточнение автора сохраняет групповое присваивание:**

```lmx
(a b c) := (b c a)
(a b c) := (copy(s))
```

Исключение действует только при одновременном выполнении трёх условий: слева написана безымянная Structure; в правой последовательности ровно один аргумент; этот аргумент сам является написанной безымянной Structure. Снимается только её внешний правый контейнер, ровно на один уровень. Левый left остаётся одной целой Structure. Вложенные правые контейнеры повторно не открываются; ссылка на структуру, значение массива и возвращённая функцией Structure сами по себе не раскрываются. P0 не снимает никаких контейнеров. Обычные callable W/E сохраняют отдельный действующий контракт. Присваивание остаётся операндом выражения; это не ограничивает всё семейство операндов одним правым значением.

**Грубую ошибку со снятием единственного анонимного контейнера в P0 исправлять в общем коде.** P0 не знает, какая последующая операция и как употребит структуру. Удаление группы при разборе затрагивает также объявления, обычные значения и вложенные контейнеры. Раскрытие должно происходить при семантическом потреблении аргументов, ровно в предусмотренном месте.

Этот файл сохраняет историческую постановку задачи. Действующая спецификация находится в родительском docs и текущем API пакета. Старые формулировки не образуют отдельной версии ядра; здесь они нормализованы по точному правилу выше.

## 2. Конкретный интерфейс предлагаемого `signatureTypes`

Для этой реализации выбрано следующее размещение данных в общем шаблоне:

| Поле общего шаблона | Значение для `signatureTypes` |
|---|---|
| `left` | Ссылка на описание типа результата |
| `right` | Массив ссылок на описания входных типов, в порядке аргументов |
| `PASS_ARGS_AS_IS` | 0: используется обычный протокол подготовленных значений |
| `PRIORITY` | Готовый приоритет из `sys\OPERANDS_TEMPLATE`, в поставленном профиле — приоритет `+` |
| Результат метода | `@` на обычное описание сигнатуры `signatureTypes` |

Размещение результата слева — **предлагаемая здесь форма интерфейса**, развивающая просьбу использовать `OPERANDS_TEMPLATE`. Оно не выдаётся за ранее существовавшую норму языка. Последний элемент правого массива не получает особого значения: каждый его элемент описывает вход.

Операндные записи с обычным ядерным именем `signatureTypes` имеют разные границы RHS:

```lmx
result_type signatureTypes arg0_type arg1_type arg2_type
result_type signatureTypes (arg0_type arg1_type arg2_type)
```

Первая запись передаёт три type-токена. Во второй справа одна Structure; обычный левый type-токен не удовлетворяет условию раскрытия. Она не равна первой и может обозначать один вход только если сама Structure является допустимым type-токеном; иначе принимающий контракт отказывает. Здесь `result_type` и `argN_type` обозначают допустимые типовые токены, а не новые ключевые слова. `void` на месте результата описывает процедуру; пустой `right` — отсутствие входов. Результат-функция остаётся обычным результатом описываемого типа, а не указанием продолжать каррирование.

Фактическая LMX-реализация находится в [src/fn_operand.lmx](fn_operand.lmx) и называется `FxSignatureOperand\make`. Она копирует шаблон первой строкой DATA, нормализует `left` и каждый `right[i]`, затем вызывает `FxSignatures\make`. Она не открывает контейнеры заново; границы right уже определены общим механизмом по точному правилу §3.

После копирования стоит существующая отметка `required: left right`: оба входа должны быть переданы и инициализированы. Это не повторное объявление полей. Пустой `right` допустим как присутствующий массив длины 0. Указатель на `uninit:T` также инициализирован: обязательность самого указателя не требует читать payload его цели.

### 2.1. Именованная форма и type-token конструктор

Именованное объявление целиком перенесено в `Name :: DataTemplate`: слева
объявляемый name atom, справа DATA-шаблон. Прежнего declaration receiver и
совместимого alias нет. Описание остаётся константным именованным требованием,
не исполняемым телом и не native-entry. Отношение такого требования с `call`
сохранено; в остальных контекстах оно взаимозаменяемо с результатом type-token
конструктора.

`signatureTypes` теперь обычное ядерное имя операнда. Его находят общим разрешением
имён и проверкой OPERANDS_TEMPLATE; специальный compatibility hook для старой
головы больше не требуется. `FxSignatureOperand\make` остаётся фактическим методом,
экспортируемым под коротким именем. Второй парсер или реестр не вводятся.

### 2.2. Что именно находится в типовом токене

`normalizeType(token)` получает указатель на одну типизированную запись. Способ чтения зависит от тега **этой** записи:

| Полученная запись | Интерпретация |
|---|---|
| Инициализированный `int` | Значение `int` — код описываемого типа. Сам тег `int` ещё не является ответом |
| `uninit:T` | Получить требование `T` из тега, не читать отсутствующий payload |
| Существующее описание `void` | Отсутствие возвращаемого значения |
| Полное описание требования | Сохранить все его ограничения по действующим правилам типов |

Например, результат `sys\typeof(...)` — целое с кодом типа; когда оно передано операнду как значение, подготовленный указатель ведёт к записи этого целого. Напротив, готовое число 5 не означает «образец int»: оно означает код типа 5, если такой код допустим в текущем профиле. Числовые значения кодов в библиотеке не закреплять.

Прямой вызов с именованными `left` и `right` позволяет передать указатели на исходные неинициализированные записи без попытки прочитать их значения. Обычное чтение неинициализированного имени в выражении не превращать в универсальную разрешённую операцию ради этого API. Подготовка не должна пытаться прочитать отсутствующий payload только для получения типа.

Нулевой указатель, готовый `@: p 0`, отсутствие аргумента, `uninit:@` и `void` — разные случаи. Не разыменовывать всякий `@` автоматически в поисках другого типа. Уровень ссылки является частью контракта. Если выражение вычисляет ссылку на числовую ячейку, его тип — ссылочный; это не то же самое, что значение числа в этой ячейке.

Один физический код достаточен не для каждого требования. Например, сам код `@` не восстанавливает модель конкретной структуры или полную сигнатуру функции. В таких случаях передаётся существующее полное описание. Новая форма не должна молча заменять узкое требование общим `@`. Основания: [typed records](../../reference/newdocs/L2_spec_en.md#value-record), [type queries](../../reference/newdocs/LMX_semantics.en.md#get-type), [signatureTypes requirements](../../reference/newdocs/LMX_semantics.en.md#fn-signature).

## 3. Однократное раскрытие структуры у операндов

Исключение действует только при одновременном выполнении трёх условий: слева написана безымянная Structure; в правой последовательности ровно один аргумент; этот аргумент сам является написанной безымянной Structure. Снимается только её внешний правый контейнер, ровно на один уровень. Левый left остаётся одной целой Structure. Вложенные правые контейнеры повторно не открываются; ссылка на структуру, значение массива и возвращённая функцией Structure сами по себе не раскрываются. P0 не снимает никаких контейнеров. Обычные callable W/E сохраняют отдельный действующий контракт. Общее правило не сводит вариативный `right` к одному значению.

Левый `left` сохраняет контракт ссылки. В групповом присваивании выбранный операнд присваивания интерпретирует левую структуру как список мест назначения. Перечень мест и перечень полученных правых значений — разные вещи; раскрытие не должно превращать место назначения в заранее прочитанное число.

| Форма | Потребление |
|---|---|
| `R signatureTypes T0 T1 T2` | Три правых описания входов |
| `R signatureTypes (T0 T1 T2)` | Один правый контейнер при обычном левом type-токене; не три описания |
| `(target) op ((inner))` | При написанном левом group снимается только внешняя правая Structure; right содержит одну inner-Structure, left остаётся целым |
| `(a b c) := (b c a)` | Получить старые значения `b`, `c`, `a`, затем записать их в `a`, `b`, `c` |
| `(a b c) := (copy(s))` | Выполнить `copy(s)` по его общему контракту; скобки собирают результат, затем присваивание получает его непосредственные значения |

`copy(s)` не получает специального поведения только для присваивания. Он по-прежнему использует обычную карту копирования и свои правила ссылок/родителей. Пустая написанная правая Structure даёт пустую цепочку только при написанной безымянной Structure слева. Тождество Structure и Array<@> не отменяет это условие исходной формы: произвольный массив или ссылка не разворачиваются. Плотный Array<int> и строка не переинтерпретируются как массив указателей.

Для присваивания правые выражения вычисляются и значения сохраняются до первой записи в левую часть. Количество мест и значений должно совпасть; несоответствие обнаруживается до записи. Обычный допуск типов сохраняется. Это не обещает транзакционного отката побочных эффектов уже выполненных правых выражений или пользовательских преобразований. Полные правила повторных левых мест и ошибок допуска брать из общего контракта группового присваивания, не изобретать отдельную версию для `copy`.

Режим `PASS_ARGS_AS_IS=1` сохраняет исходные формы и их контекст. Снятие единственного внешнего RHS-контейнера при всех трёх условиях не означает выполнение его дочерних вызовов. Нельзя заранее вызвать выражение только ради выяснения, не выдаст ли оно структуру. Если raw-операнд сам вызывает `sys\eval`, эффекты возникают именно при этом явном действии; полученные им значения не возвращаются повторно в P0.

Обычные именованные actuals методов сохраняют действующий контракт передачи целого значения. В адаптерах используются `p0 := value`, `p1 := value`, чтобы структура, являющаяся одним параметром целевой функции, не становилась несколькими параметрами. Это не особое исключение для адаптеров. Основания: [declaration selection](../../reference/newdocs/LMX_semantics.en.md#declaration-selection), [raw operands](../../reference/newdocs/LMX_semantics.en.md#raw-operands), [copy/merge](../../reference/newdocs/LMX_semantics.en.md#composition).

## 4. Общая реализация четырёх адаптеров

Вход фабрики — уже выбранный callable. Его настоящие входы определяются семантическим анализом DATA, а не простым перечислением физических полей `parent(F)`. Порядок входов, их полные требования и результат сохраняются. Поле `return`, методы, константы и свободные динамические имена не превращаются в дополнительные позиционные аргументы.

Фабрика возвращает `@` на созданную обычную исполняемую структуру. **Созданная функция имеет конкретную сигнатуру**, а не универсальный публичный результат `@` вместо любого исходного типа. Для результата `double` последняя ступень возвращает `double`; для процедуры не создаётся выдуманное значение; для результата-callable возвращается именно эта ссылка без дополнительного вызова.

| API | Контракт |
|---|---|
| `FxLambda\lambda(operation)` | Создаёт цепочку из N одноаргументных ступеней по формальным входам. Промежуточная ступень возвращает следующую функцию; последняя возвращает исходный результат |
| `FxPartial\partial(operation; prefix)` | Принимает готовый префикс длины K, сохраняет принятые значения и создаёт функцию с N−K оставшимися входами |
| `FxFlip\flip(operation)` | Для N≥2 меняет первые две позиции вместе с их полными типами; остальные позиции и результат сохраняет |
| `FxUncurry\uncurry(operation; contract; failures)` | Создаёт обычную N-аргументную функцию из цепочки, используя явно переданную конечную сигнатуру и набор объявленных исходов |

### 4.1. Граничные случаи

- Для N=0 `lambda` возвращает нульарный callable. Конструирование не вызывает исходное тело.
- `partial` принимает K=0 и K=N. При полном префиксе возвращается отложенный нульарный callable, а не немедленно вычисленный результат.
- Для N=1 `lambda` имеет одну ступень с исходным результатом. `flip` для N<2 отказывает по объявленному контракту.
- Структура, строка или массив, заданные одним формалом, занимают одну позицию независимо от внутренней длины.
- `uncurry` останавливается по заданному числу входов. Алгоритм «вызывать, пока результат является функцией» неверен.
- `uncurry` в приложенных исходниках всегда принимает `contract` и `failures` явно. Автоматическое извлечение происхождения произвольной цепочки не обещается.
- Промежуточная ступень принимаемой цепочки имеет точный контракт `Ti -> @`, последняя — исходный `R`. Цепочки этого `lambda` ему соответствуют. Чужая цепочка с более узким требованием промежуточного результата требует обычного адаптера: fn-match не объявляется автоматическим стиранием этого требования до `@`.
- Адаптеры требуют явного заполнения оставшихся формалов (`required`). Defaults и автозаполнение исходного callable не сокращают число ступеней.

При вызове uncurry-обёртки её actuals сначала подготавливаются по обычным правилам одного вызова, затем выполняется последовательность ступеней. Это не обещание того же чередования эффектов, что у отдельно написанных вызовов с вычислением следующего actual между ними.

### 4.2. Захват и состояние

Примитив сохраняется как уже принятое значение; поздняя запись в исходный локал не меняет захваченный префикс. Ссылочное значение сохраняет идентичность цели. Для добавления элемента префикса создаётся новый контейнер ссылок на сохранённые записи. Глубокий `copy(prefix)` здесь был бы ошибкой: он может скопировать сами цели ссылок.

В исходниках используется небольшой постфиксный операнд `(value FxRecordOperands\record)`: он возвращает подготовленный `left`, используя общий путь материализации типизированных значений. Это позволяет писать собственно алгоритмы на LMX. Возвращаемая запись должна сохранять срок жизни после выхода из принимающей ступени; это обязательная проверка общего механизма. Нельзя удержать адрес завершившегося C-локала и назвать его постоянной записью арены.

Для такого постфиксного применения общий обработчик передаёт присутствующий пустой `right`, чтобы `length(right)=0` было определено. Оба входа record отмечены `required`; отсутствующий или неинициализированный массив не подменяется пустым.

Состояние располагается в настоящем владельце созданного DATA/CODE под `private\state`. Созданное тело обращается к нему как `node\private\state`. Исходный target сохраняет свой реальный parent и обычные правила свободных имён. Простое помещение ссылки на чужой CODE в новый контейнер не меняет его DATA. Весь контекст первоначального вызова фабрики скрыто не захватывается.

### 4.3. Генерация тела и точный вызов

Приложенная реализация строит короткий LMX-текст и передаёт его единственному существующему `sys\fromLmx`. Тело явно читает полученные формалы `p0`, `p1`, …, затем делает обычный вызов через типизированную ссылку на target. Публичные метки `signatureTypes` отображаются по позиции на собственные имена target. Это работает также при повторяющихся именах исходных формалов: в сгенерированном интерфейсе метки различимы.

Значения текущей активации не читаются из исходного графа `parent(target)[i]`: там лежат исходные объявления, а не переданные actuals. Специальный `invokeByIndex`, обходящий обычный вызов, в этой реализации не нужен.

Код генератора находится в [src/generic_functions.lmx](generic_functions.lmx). Его небольшие строковые помощники, построение меток, префиксов, перестановки и исходников тел также написаны на LMX; они не спрятаны в `makeLambda` внутри ядра.

|---|---|
| `signature(subject)` | Выдать `inputTypes`, `resultType`, `hasResult`, `names`, `throws` из общего семантического анализа callable либо fn-описания |
| `normalizeType(token)` | Привести допустимый типовой токен к существующему полному требованию без исполнения пользовательского тела |
| `signatureData(inputs; result; labels)` | Построить обычный DATA-шаблон из уже нормализованных требований |
| `callable(contract; labels; bodyGraph; state; failures)` | Создать реальный owner/DATA/CODE, связать состояние и объявления исходов, вернуть CODE |

Имена `FxKernel` обозначают интерфейс реализации этого ТЗ. В исходниках нет пустых успешно возвращающихся заглушек и утверждения, будто такие `sys`-ресиверы уже доступны. Анализ типов, построение графа, typed records и общий парсер уже предусмотрены документацией; к ним нужен согласованный вход.

Проверить динамическое создание обычной сигнатуры через `Built :: data`, где `data` — подготовленный DATA текущего вызова. Возвращаемое описание должно существовать независимо от завершившейся активации, не превращая локальное имя `Built` в изменяемый глобальный singleton.

Для прежних `names` и `rename` нужен доступ к существующей таблице канонических имён по записи. Таблицу заново не создавать. Отсутствие имени отличается от допустимого пустого exact identifier. Переименование записей не выдаётся за рефакторинг всех упоминаний имён в теле. Эти два API сохранены в каталоге как явно отключённые заготовки до определения доступа.

## 6. Компиляция и стоимость

Построенные структуры могут исполняться обычным интерпретатором. Машинная компиляция остаётся явной. Фабрика не запускает скрытый `sys\compile`, изменение графа не переносит native-entry от прототипа с другим ABI. Основание: [explicit compilation](../../reference/newdocs/LMX_semantics.en.md#explicit-compilation).

При явной компиляции создавать настоящие типизированные методы для конкретных входов и результата. Служебный `@` фабрики и записи захваченного состояния не требуют превращать каждый прямой native-вызов программы в упаковку всех аргументов в универсальный массив.

Приложенный путь через LMX-текст — прозрачная исходная реализация построения. Его стоимость приходится на создание адаптера, включая новые промежуточные lambda-ступени, и должна измеряться отдельно от вызова готовой последней функции. При реализации можно использовать общие конструкторы графа и заранее подготовленные неизменяемые формы, сохраняя тот же наблюдаемый результат. Повторный парсинг, построение одинаковых описаний и лишние глубокие копии следует устранять там, где это не меняет состояние, родителя и время выполнения эффектов.

Счётчики и размеры в этой исходной реализации должны помещаться в `int` выбранного профиля. Отсутствие бинарного ограничения не отменяет обычных ограничений размера массивов и памяти.

Не вводить ради оптимизации скрытое глобальное окружение или второй рабочий граф. Разделять можно доказанно совместимую реализацию, сохраняя отдельную идентичность экземпляров и состояние их префиксов. Численные обещания скорости без выполнения на ядре в этом пакете не даются.

## 7. Ошибки и приёмка

Ошибки входа выражаются обычными именованными исходами. В пакете используются `FxTypeToken`, `FxKernelFailure`, `FxIndex`, `FxArity`, `FxRecordArity`; конкретные исходы целевой функции сохраняются отдельно. Массив `failures` содержит имена строками. Само совпадение с fn-сигнатурой не переносит `throws`, defaults или requiredness, поэтому эти сведения нельзя выводить только из положительного fn-match.

Промежуточные ступени lambda объявляют исходы вызываемых построителей. Финальные тела, вызывающие target, объявляют его исходы. Для чужой curry-цепочки `uncurry` получает полный набор разрешённых исходов явно; одного `throws` исходного некаррированного target недостаточно, если промежуточные ступени дополнительно строят граф.

[tests/ACCEPTANCE.md](tests/ACCEPTANCE.md) задаёт матрицу запуска. Подготовленные LMX-примеры проверяют три разных типа входа, дробный результат, независимые ветви одного префикса, пустой и полный префикс, нульарный случай, процедуру и функцию как конечный результат. Отдельные примеры проверяют новый signatureTypes и групповое присваивание.

Должны пройти интерпретатор, явная нативная компиляция и оба перехода между ними. Обязательны: корректный срок жизни захвата; сохранение ссылочной идентичности; отсутствие вызовов при построении; точный последний результат; правильный parent; отсутствие случайного динамического связывания со служебными именами.

В этом архиве выполнены только перечисленные в [tests/STATIC_REPORT.json](tests/STATIC_REPORT.json) статические проверки пакета. LMX-компилятор и интерпретатор не запускались; проверка скобок, путей и покрытия не заменяет выполнение. Поставщик `FxKernel` должен быть подключён согласно ТЗ до запуска общего семейства.

## 8. Порядок работы для Fable

1. Применить ровно тройное условие §3 и снять только внешний правый контейнер; left не раскрывать; сохранить группы P0 и оба новых примера присваивания.
2. Предоставить четыре согласованных входа `FxKernel` к существующим механизмам и проверить единый уровень ссылки/материализацию.
3. Запустить `FxSignatureOperand\make` по квалифицированному имени; проверить типовые токены, пустой набор входов и отсутствие результата.
4. Подключить операндное написание `signatureTypes`, сохранив прежний DATA-контракт явного объявления.
5. Запустить общие четыре фабрики и остальные исходники, затем пройти матрицу смешанного и нативного исполнения.
6. Подключить чтение/запись существующей таблицы имён для `names`/`rename`; не выдавать отключённые заготовки за готовые тела.

Критерий завершения — исполняемые общие адаптеры с точными типами и обычными правилами LMX, подтверждённые результатами запуска. Текст ТЗ и наличие исходников сами по себе этому критерию не равны.
