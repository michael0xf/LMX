# ТЗ · Буквальное написание идентификаторов и обращение к именам по строке

28 ноября 2026 года. Изменить правило идентичности имени на пути от исходного текста до чистого графа и обратно. Новое требование заменяет прежнее равенство написаний из §26.3 плана v3.

## 1. Какое имя получает граф

**Именем написанного идентификатора служат все байты его токена.** У точного идентификатора обе внешние обратные кавычки (U+0060) входят в имя. P0 по-прежнему использует их для определения границ токена. Если внутри встретилась пара обратных кавычек, сканер проходит её как внутреннюю пару, а в имя попадают **оба** байта. Пробел, перевод строки, обратная косая черта, скобка или знак операции внутри защищённого участка сохраняются по общим лексическим правилам. Повторного разбора содержимого нет.

В позиции, где потребитель явно принимает **название строкой**, ключом служат длина и содержимое строкового значения `[]char`. Для строкового литерала это результат обычного чтения литерала LMX. Его внешние двойные кавычки ограничивают литерал. Запрос по вычисленной строке использует те же байты, что запрос по равному ей литералу. В позиции значения строка остаётся данными.

```text
Идентификатор   Имя в графе, hex     Длина    Строка для поиска этого имени
x               78                     1      "x"
`x`             60 78 60               3      "`x`"
`a+b`           60 61 2B 62 60         5      "`a+b`"
`a``b`          60 61 60 60 62 60      6      "`a``b`"
``              60 60                  2      "``"
```

У внешнего поля с фактическим именем `a+b` байты `61 2B 62`. Строковый запрос `"a+b"` выбирает его по этим трём байтам. В выражении `a+b` парсер распознаёт сложение. Написание `` `a+b` `` даёт один идентификатор из пяти байтов.

Минимальный исходник для проверки на обычной Structure:

```lmx
S:
    int: x 11
    int: `x` 22
```

По новому правилу `S\x` читает `11`, а `` S\`x` `` читает `22`. Если записать `33` во второе поле, первое сохраняет `11`. Для такого различения достаточно существующего представления имени в графе.

Для допустимых имён действует одно сравнение по длине и байтам, с сохранением регистра и без нормализации Unicode. Каноническая строка и сравнение канонических адресов внутри существующего контекста сохраняются. Идентификатору не нужен признак «был в кавычках». Встроенные, пользовательские и импортированные имена проходят через ту же границу.

## 2. Контракты потребителей

| Место | Требуемое поведение |
| --- | --- |
| Объявление и использование | Голова ресивера, имя поля, формальный параметр, имя фактического аргумента, имя типа, цель `end` и ссылка на метод используют одно написание. Поля `x` и `` `x` `` могут сосуществовать. При записи через одно из них меняется выбранное место. Если существует только одно, поиск другого завершается обычным отказом. |
| Путь и область видимости | Каждый написанный сегмент даёт собственный ключ. Разделитель внутри точного токена принадлежит имени. Сохраняются область поиска и правила затенения. В DATA два поля с одинаковыми байтами по-прежнему требуют индекса вхождения `S\[n]field`. В CODE применяется правило достигнутого переобъявления. Физический индекс `S[n]` имеет прежний смысл. |
| Явный выбор по тексту | Владелец или область поиска задаётся договором операции. Для одного сегмента `"a+b"`, `"A\\B"` и `"two words"` обозначают полные названия. Их содержимое не разбивается на выражение, путь или несколько полей. Две независимо созданные строки с одинаковыми байтами выбирают одно и то же место при тех же владельце и номере вхождения. |
| `sys\name` | Получает записанный идентификатор. `sys\name(x)` возвращает один байт `78`. `` sys\name(`x`) `` возвращает три байта `60 78 60`, в том числе при необъявленном имени. Значение переменной, инициализатор и тело метода для этого не исполняются. |
| Операторы и служебные слова | В `a+b` имя распознанной операции — один байт `2B`. `sys\priority("+")` запрашивает эту операцию. `` sys\priority("`+`") `` запрашивает другое имя и проходит обычное разрешение. Аналогично, служебный смысл `node` принадлежит ключу `node`. `` `node` `` имеет другой ключ. Проверка зарезервированности производится по реально выбранному имени и роли. |
| Таблицы | Имя таблицы, внешнее название столбца и текстовый ключ строки, когда схема задаёт именно текст, можно передавать обычными строками. Числа, ссылки, вызываемые объекты и прочие типизированные ячейки сохраняют тип согласно схеме. Разрешение дублей строк по-прежнему определяет политика таблицы. |

**Обращение к произвольному названию.** Для реализации нужна пара симметричных действий. При создании именованного поля принимаются владелец и точные байты названия. При обращении принимаются владелец, те же байты и при необходимости номер вхождения. На выходе получается обычное именованное место графа, доступное предусмотренным для него операциям. Строка может содержать обратные кавычки как данные. Пустая строка при допустимом пустом имени задаёт ключ длины ноль, который отличается и от имени из двух обратных кавычек, и от безымянного места. Встроенный NUL на границе имени даёт отказ до поиска или публикации. Строка с таким байтом в обычных данных подчиняется правилам строк.

В рабочих разделах об именах, таблицах и сериализации опубликованной пары для произвольного поля Structure по вычисляемой строке при сверке не найдено. `sys\name` выдаёт написание, `sys\priority` ищет приоритет, табличный запрос выбирает строку по политике таблицы. На этапе грамматики закрепить общую запись именования поля и явного выбора по строке. До миграции показать на действующем LMX создание и последующую запись и чтение одного внешнего поля. Контроль в условной записи выглядит так: `создать_поле(S, "a+b", 7)`, затем `поле_по_имени(S, "a+b")` даёт то самое место со значением `7`. Это обозначения для ТЗ. [Имена и пути](../../spec/LMX_semantics.ru.md#fields) · [Запросы по имени](../../spec/LMX_semantics.ru.md#string-identifier) · [Табличные запросы](../../spec/LMX_semantics.ru.md#registries).

При чтении текста в чистый граф буквальное строковое название известно сразу. Написанное вычисление названия сохраняется в графе до исполнения соответствующей операции. Динамический поиск вычисляет выражение ключа один раз. Когда выбранное место служит целью вызова, к нему применяется общий договор вызова, включая проверку возможной неоднозначности до эффектов. При статически известных цели и соответствии аргументов сохраняется прямой вызов подготовленного нативного тела.

## 3. Что менять в реализации и в какой последовательности

1. **Грамматика, P0 и Expression.** Закрепить сырые байты идентификатора и строковую форму для роли имени в общем фронтенде. Сохранить исходные диапазоны, защиту разделителей, правила для удвоенной кавычки и диагностику незакрытого токена. Пройти головы, компактные вызовы, `end`, сегменты пути и префиксные типы. В `lm_p0_head_is_call` различать известное служебное слово и написание с другими байтами. Для `+`, `::`, `->` и пользовательских операций проверить и синтаксис операции, и явную ссылку на её каноническое имя. Выбор роли Expression и допуска вызова выполняется до эффектов в соответствии с действующей спецификацией. [Грамматика](../../spec/LMX_grammar.ru.md#identifiers) · [Формы операций](../../spec/OPERATION_FORMS.md) · [Разбор скобок](../../spec/BRACKET_SUBPARSER.ru.md) · [P0](../../../selfbuild/src/l2src/p0_parser.lm2).
2. **Построитель и разрешение имён.** В `lm_graph_name_bytes` сейчас снимаются границы токена и сворачивается внутренняя пара. Передавать в `lmx_graph_intern` исходные адрес и длину токена идентификатора. Провести объявления, `lm_graph_p0_name_word` и сегменты `lm_graph_build_selector` через одну границу. Для явного названия строкой входом служит готовое содержимое строки. `lmx_graph_intern_find` уже различает длину и байты. При поиске сохранить правила выбранного владельца, наличие/отсутствие имени и индекс вхождения. Проверить Graph, интерпретатор и подготовленное нативное тело на одних данных. [Построитель](../../../selfbuild/src/l2src/l2_graph_build.lm2) · [Таблица имён графа](../../../selfbuild/src/l2src/lmx_graph.lm2) · [Имена и пути](../../spec/LMX_semantics.ru.md#fields).
3. **Hosted-фронтенд и самосборка.** Проверить `lm_compiler_exact_ident`, `lm_compiler_bind_spelling` и `lm_compiler_bind_admit`, включая действующий отказ для некоторых имён в обратных кавычках. Заменить снятие кавычек в `lm_compiler_payload_same` и `lm_compiler_payload_eq` с учётом роли их вызывающего кода. Сравнение двух идентификаторов получает байты токенов, сравнение текстовых ключей — байты значений. Применить это и при обнаружении дублей, и при последующем поиске. Проверить, что разные имена не схлопываются при генерации имён и ссылок в L1/C. [Вспомогательные функции](../../../selfbuild/src/l2src/l2_frontend_helpers.lm2) · [Сбор объявлений и таблиц](../../../selfbuild/src/l2src/l2_frontend_core.lm2) · [Связывание и поиск таблиц](../../../selfbuild/src/l2src/l2_frontend_lower.lm2).
4. **Профили и пользовательские данные.** Сначала обеспечить чтение настоящего строкового значения там, где профиль ожидает название. Затем перенести `name` таблиц `primitive.description` и `primitive.convert` на строки, согласовать их закрывающие `end` с договором этой формы и проверить штатные `lm_compiler_table_find` и `lm_compiler_table_col`. Отдельно проверить ключи строк, названия столбцов, привязку реального преобразователя и дубли. Для исходников, зависевших от старого равенства, определить целевой ключ по назначению. Ссылка на обычное имя получает это имя, внешнее название передаётся строкой, буквальное имя с кавычками сохраняет все байты. Это относится и к метаданным операций, написанных прежде через обратные кавычки. [Профиль примитивов](../../../selfbuild/src/l2src/primitive.lm2) · [Таблица преобразований](../../../selfbuild/src/l2src/convert.lm2) · [Правила таблиц](../../spec/LMX_semantics.ru.md#registries) · [Пример строковых названий столбцов](../../runtime_server/examples/01_table_and_tree.lmx).
5. **Обратная запись и загрузка.** `sys\toLmx` выбирает запись, которая при чтении восстанавливает в точности исходное имя. Для внешнего `a+b` нельзя безусловно добавлять обратные кавычки — получится пятибайтовое имя. Использовать явное строковое название в позиции имени, если буквальный идентификатор с нужными байтами там не представим. Если имя уже содержит обе границы и представляет само себя, повторное обрамление меняет его. Проверить `lmx_graph_dump_selector_name` и другие принтеры отдельно от полного кодека. `sys\fromLmx` принимает как независимый рукописный вход, так и текст сериализатора. В ранее сохранённом чистом графе имя `x` уже состоит из одного байта. Восстановить факт прежнего цитирования можно лишь из сохранившегося исходника. При переносе не вводить поиск по прежнему псевдониму. [Контракт кодека](../../spec/LMX_semantics.ru.md#source-codec) · [План внедрения fromLmx](../../FROM_LMX.md).
6. **Книга, модели и план.** Внести синтаксическую часть в первую очередь грамматики/P0/Expression плана v3. Граф, таблицы и кодек включить в их действующие этапы. Переписать прежний §26.3 и согласовать с §26.4. Синхронизировать RU/EN через штатные источники грамматики и книги, L2, правила операций и глубины, примеры `sys\name` и `sys\priority`, модели транслятора, каталог примеров и ответы `lmx-dev`. Пересмотреть проверки `formal_quoted` и `node_quoted` по тому, что они наблюдали. Новые примеры использовать в современном синтаксисе обычных Structure. Сохранённые исторические расписки оставить свидетельствами прежнего поведения. ## 4. Приёмка

| Проверка | Наблюдаемый результат |
| --- | --- |
| 1. Границы P0 | Примеры из таблицы байтов, точный токен с пробелом, переносом, `#`, точкой, скобками и разделителем пути сохраняют один токен и его диапазон. После закрытия следующий токен читается штатно. Незакрытый токен и NUL внутри него дают диагностику в исходнике. |
| 2. Два имени в одной Structure | Объявить `x` со значением `11` и `` `x` `` со значением `22`. Прочитать каждое путём и по соответствующей строке. Записать `33` во второе. При повторном чтении получаются `11` и `33`. Если убрать второе объявление, запрос второго ключа завершается отказом. |
| 3. Настоящие дубли | Добавить в DATA второй `x`. Поиск `"x"` без индекса сообщает неоднозначность. Вхождения `0` и `1` доступны раздельно. Ключ из трёх байтов продолжает однозначно выбирать своё поле. |
| 4. Внешнее имя | Создать в одном владельце поля с байтами `61 2B 62` и `60 61 2B 62 60`. Получить разные места. Повторить для одного имени с пробелом, имени с одним буквальным байтом `60` и имени, содержащего разделитель пути. Поиск по их тексту выбирает целое поле. |
| 5. Строка и имя | Две строки из разных ячеек с равным содержимым дают один результат. В явно динамическом запросе поставщик строки вызывается один раз. При передаче того же текста обычным аргументом он остаётся `[]char`. Строка с NUL внутри не выбирает поле по префиксу. |
| 6. Служебное имя, формал и закрытие | Голый `node` выполняет служебную роль. Объявление `` `node` `` там, где разрешено пользовательское имя, читается по собственному ключу. Проверить разрешение одноимённого написанного формала и несовпадение написаний в именованном аргументе и в форме `end`, которая требует совпадения. |
| 7. Имена операций и `sys\name` | Проверить сложение `2+3` и поиск `sys\priority("+")`. При наличии отдельного пользовательского `` `+` `` различить адреса и эффект двух операций. `sys\name` для байтов из первой таблицы возвращает указанные длины и содержимое. Счётчик одноимённого метода остаётся нулевым. |
| 8. Таблицы | Обе штатные таблицы профиля обнаружены по строковым названиям. Получены ожидаемые столбцы и прежний результат одного реального преобразования. Идентичные текстовые ключи в разных ячейках обрабатываются по политике дублей. Отдельные ключи с кавычками и без выбирают разные записи. |
| 9. Круговой проход | Взять один граф с обоими `x`, внешним `a+b`, настоящим пустым именем, именем из двух кавычек, безымянным полем и двумя ссылками на одну цель. После `fromLmx(toLmx(S))` в свежем контексте сверить длины и байты, порядок вхождений, отсутствие имени и тождество общей цели. Независимый рукописный вход должен дать те же наблюдения. |
| 10. Совпадение маршрутов | На одном современном примере сверить результаты интерпретатора, принудительного обхода и обычной нативной трансляции, включая отсутствие побочных эффектов при отказе выбора. Для статически однозначной прямой ссылки проверить сохранение подготовленного вызова в порождённом коде. |

Задача закрыта, когда по каждому пункту есть воспроизводимый исходник, ожидаемое и фактическое наблюдения и указание проверенного маршрута. Для P0 фиксируются байты и диапазоны, для графа — запрошенный ключ и выбранное место, для кодека — результат повторной загрузки. Готовность таблиц подтверждается реальным потребителем профиля. Готовность правил проверяется также запросом `syntax.names` к сервису по обновлённой книге.
