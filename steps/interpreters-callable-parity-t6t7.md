# §7 "Интерпретаторы: те же два примера или явное unsupported" — замер (Sonnet, 2026-09-26)

Read-only. Ядро (`lmx_*.lm1`, `dev/l3_interp/`) не трогал. Задание Opus: что делают `lmx_walk`
(нативный walker, ROOT + `--walk-methods`) и `l3_exec` (`dev/l3_interp`, отдельный L3-интерпретатор)
с двумя примерами T6/T7 (`unit_make_adder.lm2`, `unit_t7_convert.lm2`), предложить parity-строки
harness или явный located «unsupported».

## 1. `lmx_walk` + `--walk-methods`: измерено напрямую (два l2trans-прогона, диф L1)

- **`unit_make_adder.lm2`** (`fn: makeAdder (int: n) fn: (int: x) int` / вложенный `fn: addN`):
  генерированный L1 **побайтно идентичен** с `--walk-methods` и без него. Ни `makeAdder`, ни
  `addN` не переходят в op-дерево ни при каком режиме — оба остаются полностью нативными.
  Причина по коду (`l2_rw_may`, `l2trans.lm1:21714-21749`, комментарий читает норму дословно):
  «a result that is a number... or none» — `makeAdder`'s объявленный результат `fn: (int: x)
  int` (сам callable-тип), не число → `l2_rw_may(makeAdder) = 0` сразу. `addN` формально
  подходит под числовой результат/формал, но harness `Debt` уже называет его прогон через
  `lmx_call_prim(` (динамический нативный вызов callable-формала/PAP-инстанса, T6's
  `l2_mad_on`-механизм) — измеренный факт: `addN` тоже остаётся вне walkable-подмножества
  (нулевой диф подтверждает это на уровне L1, не только по Debt-строке).
- **`unit_t7_convert.lm2`** (`add`, `wrap` — строит `return: merge(y: k; add)`, `five`, `bin`,
  `take (bin: op)`, `passed`): **3 из 6 методов реально переходят в op-дерево** под knob (диф
  L1 — ровно 3 строки `l2_entry_leaf\native: (cast: (LmxEntry) l2_mN_tr)` пропадают для `m0`,
  `m2`, `m3`, т.е. для `add`, `five`, `bin` — простые числовые тела без merge/callable-формала).
  Оставшиеся 3 (`wrap`, `take`, `passed`) остаются нативными и под knob: `wrap` строит callable
  через явный `merge(...)` (уходит через `l2_pap_steps`/`l2_pap_on`, отдельный путь с
  собственным условием `l2_rw_may(model)`, но сам PAP-инстанс не отражается в walk-режиме как
  видно по нулевому дифу именно на этих трёх), `take (bin: op)` имеет **callable-формал**
  (`l2_rw_may`: «A callable formal... stay out», исключение явное), `passed` зовёт `take` с
  merge-актуалом.

**Вывод по walker:** обе фикстуры полагаются на T6/T7 (PAP/merge-построенный callable),
и именно эта часть *категорически* не входит в walkable-подмножество ни в одном из двух
файлов — knob лишь дополнительно op-три-фицирует случайно-простые СОСЕДНИЕ методы
(`add`/`five`/`bin`), которые к самому тестируемому механизму (T6/T7) отношения не имеют.
`--walk-methods` не даёт ни одного шанса реально проверить op-дерево PAP/merge-callable
сегодня — не потому что кто-то забыл включить эти два файла в WalkMethods-корпус (у них и нет
`WalkMethods = $true` в `tools/l2_harness.ps1:968,972`), а потому что **сам механизм построения
шагов не покрывает PAP-модель как класс** (T6's `l2_mad_on` не появляется в `l2_rw_may`'s
собственном разборе типов вообще; T7's `l2_pap_steps` требует `l2_rw_may(model)`, но ничего не
делает с самим PAP-инстансом узла — только с моделью-донором).

## 2. `l3_exec` (`dev/l3_interp`): категорический, не частичный пробел

`grep -l "merge\|MERGE" dev/l3_interp/*.lm1` = **0 файлов**. Не «эти два примера дают
unsupported» — у L3 вообще нет узла для merge:

- Полный список объявленных `L3_NODE_*` (`dev/l3_interp/l3_recv.h.lm1:36-53`): `RETURN`,
  `IF`, `WHILE`, `MATCH`, `EACH`, `YIELD`, `FINALLY`, `THROW`, `EXPECT_INT`, `ASSIGN`, `CALL`.
  **Нет `L3_NODE_MERGE`** — ни объявленного неиспользуемого номера, ни диспетчерской ветки.
  Сравнил с нативным walker'ом: там тоже нет `LMX_WALK_OP_MERGE` (`lmx_walk.h.lm1:212-270`,
  полный список 31 кода) — merge у walker'а идёт через **общий примитивный вызов**
  (`LMX_WALK_OP_PRIM` → `lmx_walk_merge_model`/`lmx_walk_merge_into_map`, обычная нативная
  C-функция, не интерпретируемый узел). У L3 **нет и самого класса PRIM**-диспетчеризации
  (в списке узлов выше PRIM тоже отсутствует) — значит L3 не может выразить merge даже
  окольным путём через «вызови нативный примитив».
- Отдельно от op-кода: `dev/l3_interp/tests/` — это **рукописный** корпус (L3-фикстуры пишутся
  вручную как op-деревья через C-конструкторы селфтеста, не переводятся из `.lm2` транслятором).
  Ни `unit_make_adder.lm2`, ни `unit_t7_convert.lm2` никогда не попадают в L3 сегодня — вопрос
  «что делает l3_exec с этими двумя» в буквальном смысле неприменим: их для L3 не существует,
  пока их вручную не переписать в виде L3 op-деревьев (что само по себе невозможно без узла
  merge).

## 3. Предложение (parity-строки harness vs явный unsupported)

Задача формулирует «или-или»; по факту нужны оба, для двух разных получателей:

1. **Walker (`lmx_walk`, `--walk-methods`): явный located unsupported, а не молчаливый
   native.** Сегодня `l2_rw_may`/`l2_pap_steps`/`l2_mad_on` просто НЕ помечают PAP/merge-модель
   как отдельный класс — метод тихо остаётся нативным, без диагностики и без записи «PAP вне
   walkable-подмножества» нигде в выводе транслятора. Это ничем не отличимо от «переводчик ещё
   не добрался» — а надо явно: расширить комментарий/классификатор `l2_rw_may` третьей веткой
   для PAP-моделей (`l2_pap_on(mi)` / `l2_mad_on(mi)`) с собственным диагностируемым «not in the
   walkable subset: a PAP/merge-built callable», как для catch-параметра или callable-формала
   уже сделано текстом комментария (но не диагностикой — там тоже молчаливое исключение, той же
   формы дефекта, просто более старое). **Это правка транслятора** (`l2trans.lm1`), не harness —
   не делаю сейчас, только называю точное место: `l2_rw_may:21720`, ветка после `cls:
   l2_tramp_class(mi)` (:21728) — нужен явный код-класса «6 = PAP model, excluded, diagnosed»,
   не только числовой 0.
2. **Harness: НЕТ parity-строки для этих двух под `WalkMethods = $true`,** потому что она не
   докажет то, что должна: `--walk-methods` не op-три-фицирует ни один из тестируемых T6/T7
   методов (§1) — добавление `WalkMethods = $true` к `unit_make_adder.lm2`/`unit_t7_convert.lm2`
   даст зелёную строку, которая **ничего не проверяет** (тот же класс дефекта, что «проверка,
   которая не может упасть», `steps/gate-audit-20260926-sonnet.md` не про это, но принцип тот
   же — измерено здесь, а не предположено). Parity-строка имеет смысл **только после** правки
   п.1 — тогда WalkMethods-запуск даст «unsupported», и это и будет строка (`Needle` =
   диагностика транслятора, не рантайм).
3. **L3: явный unsupported — большая задача, не строка.** Нужен сначала **дизайн** узла merge
   для L3 (`L3_NODE_MERGE`, номер, семантика, диспетчер) — это НЕ located-диагностика поверх
   существующего механизма (как в п.1), а новая возможность интерпретатора с нуля, потому что
   сегодня нет ни узла, ни PRIM-эквивалента. До этого дизайна честная промежуточная мера — явная
   строка в `next_core_tasks.md` §6 (матрица) «L3: merge/PAP callable — нет узла, нет PRIM-пути,
   T6/T7 не выразимы» вместо тихого умолчания «эти два примера не упомянуты для L3».
