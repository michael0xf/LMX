## 2. Целевая архитектура: один движок, две двери

Граница представлений. Транслятор читает дерево парсера (`LmP0Node`/`LmP0Frame`/
`LmP0Structure`/`LmP0Field`/`LmP0Text`, p0.h.lm1:79–134); интерпретатор исполняет граф
`Lmx` в арене, роли узлов — по домену адреса, имена — внешняя таблица. Эти представления
различны по природе (текст против адресов), и READ.ME закрепляет обе двери: «обходчик
распознаёт написанную голову через таблицу адрес→имя; транслятор видит дерево парсера».
Общий код поэтому начинается **после загрузки имён в адреса** и состоит из операций над
графом/местами/контрактами; специфичным остаётся ровно то, что требует текста или
печатает текст.

Специфично для транслятора (обосновано):
1. **Чтение C-словаря** (`predef:`/`include:` заголовки, `define`, `--machine` имена):
   у интерпретатора нет текста; эти декларации нужны только чтобы написать C
   (имена и C-типы функций/типов/fnptr). Индексируется один раз.
2. **Загрузчик P0 → граф объявлений** (обход 1): превращает текст в адреса. Интерпретатор
   получает граф уже построенным (нативными конструкторами программы или runtime).
3. **Печать** (обход 3): L1 нативных тел, конструкторов графа (`rw_*` → `lmx_walk_frame`
   и др.), C-двери, машинных модулей, заголовков; CLI/части/профили сборки.
4. **Диагностика по координатам источника** (span/строка/колонка) — у графа их нет.

Общее — одно определение каждого правила, два вызывающих пути. Представление общего
кода — граф (`Lmx`, роли по адресу `lmx_walk_role_in`, имена во внешней таблице
`lmx_source_name_*`). Транслятор получает его от загрузчика (п. 2 выше): `lm_compiler_load_unit`
строит в арене перевода граф **как написано**, теми же конструкторами, которыми напечатанная
программа строит свой при старте (`lmx_walk_plain` walk_values.lm2:821, `lmx_struct_new_owned`,
`lmx_source_name_prepare/publish`): каждый Frame → узел с исходной головой (написание в
таблице имён) и аргументной Structure (дети), т. е. общая модель «receiver — arguments»
READ.ME и книги; Structure → простой узел; атом → ячейка `LMX_KIND_SOURCE_SYMBOL` с
написанием. **Никакой роли загрузчик не ставит** — ни слову языка, ни имени: смысл головы
(слово-ресивер `if`/`while`/`return`/`throw`/`catch`/`fn`/объявление, или имя callable/места)
устанавливает одно общее разрешение `lmx_walk_named_role` (ниже), которое транслятор
вызывает в обходе 2 над узлом, а walker — при достижении узла. Результат разрешения —
внутренняя метка роли в голове (`lmx_walk_frame_profiled` :4099 ставит её; `lmx_walk_op`
:799 читает) — есть **следствие** общего разрешения, которое печатается в конструкторы
обхода 3 и которое runtime-построенный код получает при первом достижении; метка не второй
алгоритм загрузчика (замечание Codex P1-2, редакция 2). Таблица слово→`LMX_WALK_OP_*` эмиттера
`rw_frame` (emit.lm2:3900–7617) переезжает внутрь `lmx_walk_named_role` как таблица
ресиверов языка — часть общего разрешения, одна для обеих дверей.

**Общий сборщик описаний (обход 1) и снимки исполнения — две разные операции.**
Одно определение сбора — чистая функция над одним узлом, без кадра, значений и scratch:
**`lmx_collect_node(arena, node, parent, sink)`**: по голове узла (роль, если уже
установлена; иначе NAMED-написание) сообщает приёмнику описание — объявление поля/ссылки
(ресивер-слово объявления и имя), callable (fn/fm/sub/catch с частями), именованная
Structure, pad с ключом, заголовок THROWS, операция данного вида с её узлом, бare имя в
голове или аргументе. Она **ничего не вычисляет и не разрешает**: ни проекций, ни значений,
ни типов. Два драйвера одного определения:
- транслятор: загрузчик `lm_compiler_load_unit` вызывает `lmx_collect_node` на каждом узле **в
  момент его создания** из P0 (строит узел → сообщает его описание) — одно посещение дерева
  даёт и граф, и таблицы обхода 1 (списки операций по методам, объявления с владельцем и
  областью, индекс узел→строка); отдельного прохода по готовому графу нет, и счётчик
  посещений (§3) считает это посещение один раз;
- интерпретатор: `lmx_collect_body(arena, body, sink)` — рекурсия по owned-рёбрам тела с тем
  же `lmx_collect_node` на каждом узле — вызывается при входе **достигнутой** активации
  только чтобы узнать, какие own-поля тела читаются/пишутся по голому имени (OWN/SET):
  это описания, не значения.
**Снимки исполнения** — специфичная работа walker над результатом сбора, при входе
активации: рабочие строки §7b создаются `lmx_walk_work_make` только для **уже определённых
мест допущенной активации** — own-полей её code/data по описаниям OWN/SET (holder = сама
активация, slot известен без вычислений), снимок ARG_ENTRY удерживаемых входов (RU §9) и
места PLACE допущенного вызова. Произвольная проекция OWN_OF/SET_OF (holder-выражение,
сегодня вычисляемое `lmx_walk_work_cell` :1662–1705 → `lmx_walk_eval` :1683 при входе) при
входе **не вычисляется**: её строка создаётся при достижении операции (`lmx_walk_eval`
→ OWN_OF/SET_OF handler → `work_cell` → `work_make`), после чего ведёт себя как всякая строка
(норма 470: bare snapshot не обновляется физической записью). Удержанные входы и норма 470
сохранены; поздним чтением общего поля ничего не заменяется. Фокусный свидетель S4: OWN_OF/
SET_OF в невыбранной ветви с holder, чья проекция при входе отвергалась бы, — активация
исполняется, n и f одинаково.
Транслятор над загруженным графом получает от того же сбора множество own-полей тела
(OWN/SET) и входов ARG_ENTRY — ровно то, что сегодня `lm_compiler_emit_work_decl`
core.lm2:4057 и `lm_compiler_emit_native_input_entry` lower.lm2:7577 печатают по
frontend-таблицам; строки OWN_OF/SET_OF в нативном тексте — при достижении операции, как у
walker.
Объявления (методы, именованные Structure, поля, catch-pads, throws-заголовки) — узлы
графа, построенные загрузчиком и описанные сборщиком при создании; владелец = `parent`,
контекст = лексическая цепочка `node`, видимость — правило по положению в цепочке (методы и
pad — весь блок, поля и именованные Structure — вперёд и вниз), применяемое функцией
разрешения ниже.

**Общий validator текущей операции (обход 2 по операции).** Семейство функций с одним
определением каждая, вход — кадр и узел операции в графе:
- вызов: `lmx_walk_call_shape` :3204 (форма CALL/EXEC), `lmx_walk_select_call` :4130 (callee:
  прямая ссылка или NAMED-голова через `lmx_source_name_get` и лексическую цепочку —
  существующий именованный путь :2443/:2480/:3409/:4363), `lmx_callable_source_count` и
  `lmx_implements_exec_slot` (части `args`/`return`, арность — `lmx_walk_call_in` :4590–4700),
  **новая `lmx_call_obligation(arena, callee, caller_code, call_node)`**: множество ключей
  явного заголовка THROWS callee (`lmx_walk_throws_node` :698) ⊆ ключи THROWS вызывающего ∪
  ключи PAD охватывающих тел от `call_node` до тела активации (`lmx_walk_pad_find` :3905 по
  цепочке `parent`); неявные ключи `merge`/`implements`/`interpreter` обязательств не создают
  (книга :553/:555);
- присваивание/чтение места: `lmx_walk_slot_place`, `lmx_walk_projection_at`,
  `lmx_walk_values_arg_place` :1178, `lmx_walk_value_deref_place`, witness-тип
  `lmx_walk_witness_type`; приём Structure в типизированное место — `lmx_walk_value_admit`
  :227 / `lmx_walk_admit_against` :2347 (только по фактическому значению, runtime);
- роль написанной головы: `lmx_walk_role_in` :685 для узлов с уже установленной меткой;
  **новая `lmx_walk_named_role(f, node)`** для узла с написанной головой: сначала таблица
  ресиверов языка (слово → контракт ресивера и метка роли: `if`, `while`, `for`, `return`,
  `throw`, `catch`, `fn`/`fm`/`sub`, объявления `int:`/`@:`/`Model:`, `merge`, `call`, …),
  иначе имя из таблицы → поиск по лексической цепочке (формал/вход активации, поле или
  именованная Structure, видимые по положению; метод/pad — весь блок; C-слово — только у
  транслятора через словарь) → результат: вызов callable, запись в место, объявление по
  контракту ресивера, иначе «unresolved name». Это одно определение сегодняшних `is_asgn`
  lower.lm2:748, `call_head_method`, `call_head_held`, `site_method`, условий `is_known` и
  выбора роли в `rw_frame`.
Вызывающие пути: walker — обработчики `lmx_walk_eval` в момент достижения операции
(`lmx_walk_call_in` вызывает `select_call` → `lmx_call_obligation` → `dispatch_values`; никакой
операции не касается до её достижения, никакого прохода по программе); транслятор —
обход 2 один раз по списку узлов-операций загруженного графа с кадром перевода, затем печать.

Остальное общее, как и сегодня: `lmx_implements`/`register`/`slot` и специальная ошибка
`LMX_WALK_NAME_IMPLEMENTS`; ключи/pad/граница активации `lmx_walk_boundary_status`; карты
мест PLACE/OF_EDGE/`lmx_implements_slot`, рабочая таблица §7b и публикация dirty; сброс
`native` в общем пути записи (§4.4); разрешение свободных имён по цепочке активаций (§4.5).

Момент работы общего кода различен по природе и это не две реализации: интерпретатор
вызывает те же функции **в момент исполнения операции** (автор: «не должен пытаться всё
понять до самого выполнения»); транслятор вызывает их **один раз над записанной
операцией** в обходе 2, потому что печатает C для этой операции, и печатает вызов
runtime-допуска там, где решение требует фактического значения. Ни одна из дверей не
выводит фактов о будущем исполнении; интерпретатор не получает whole-program прохода.

Честное состояние: на стороне транслятора этого общего кода сегодня нет (frontend держит
собственные правила над P0), `lmx_call_obligation` и `lmx_walk_named_role` ещё не написаны.
Срезы S2–S7 сводят frontend к трём обходам и удаляют анализы, оставляя его правила над P0;
S8 вводит загрузчик и переключает обход 2 на общие функции по видам операций (вызов → NAMED
→ места → приём), удаляя с каждым видом соответствующее frontend-правило (`is_asgn`,
`call_head_*`, `bind_calls`, `check_call`, `colon_check_assignment`, …). Общая функция
обязательства нужна раньше — в S2, потому что walker применяет её к динамическому callee
(§5), а транслятор — к статическому.

Что проверяет транслятор (обход 2), ровно столько, сколько нужно для C:
- разрешение каждого написанного имени в место/callee/слово C-словаря (иначе C не
  написать) — «unresolved name» остаётся ошибкой трансляции;
- C-тип каждого места из его **объявления** (`int: x`, `@: T p`, `Model: m`) — чтобы
  объявить переменную/формал в C; никаких доказательств совместимости моделей;
- арность написанного вызова против части `args` callee — чтобы написать вызов в C;
  нативный транспорт отсутствующего входа — как сейчас (absent);
- обязательство throws/catch: каждое имя из явного `throws:` callee есть в `throws:`
  вызывающего или покрыто `catch:` того же блока по правилам видимости catch (книга
  §exceptions :545–553); иначе ошибка трансляции в месте вызова. Неявные имена
  (`merge`, `implements`, `interpreter`) обязательств не создают;
- формы, которые эмиттер печатать не умеет, — located refusal (UNSUPPORTED), как и
  сейчас; это не анализ, а граница реализации.

Всё остальное из нынешних `check_*` (43 функции emit.lm2, 22 core.lm2, `check_body`
emit.lm2:5145 как сверка контрактов значений, `check_fields`, `check_receiving_value`,
`check_value_convert_field`, `colon_check_assignment`, `check_literal_kind` в части
совместимости моделей, `emit_formal_admits`, `emit_class_admit`, D-105) удаляется;
в месте приёма Structure печатается вызов общего runtime-допуска, несовпадение — бросок
`implements`.

## 3. Владение данными и точный результат каждого обхода

Таблицы транслятора остаются таблицами перевода одного unit (сбрасываются в
`translate_unit`), но заполняются ровно одним обходом каждая и получают индекс.

**Обход 1 — сбор (один проход по дереву unit: корень, выбранная ветвь `os`, части).**
Результат:
- строки методов (`l2_m_*`): fn/fm/sub/catch и процедуры именованных Structure, в
  порядке встречи; локальная именованная Structure получает строку `ns_proc_add`
  **в момент встречи** (`local_ns_entry` core.lm2 → `ns_proc_add` emit.lm2:384), а её
  тело собирается тем же проходом как вложенное поддерево — цикл :5767 и повторные
  `collect_asgn_binds` исчезают. Учёт не меняет видимость: методы видимы в обе стороны
  (книга :321), именованные Structure и поля — вперёд и вниз; эти правила применяет
  обход 2 при разрешении, а не порядок регистрации;
- строки own (`l2_own_*`): типизированные объявления (`own_decl_ty`), `Model: fresh`,
  merge-объявления, receive-формы, ссылочные объявления `@: M r`, с владельцем (метод),
  областью (scope) и узлом объявления; слот/layout — финальный шаг обхода 1 по таблице
  (`layout_owns` переносится сюда, это счёт по таблице, не обход дерева);
- машинные локалы (`ml_*`) каждого метода — в той же встрече; хранятся по методу, не
  пересобираются (`ml_rebuild` уходит);
- списки мест обхода 2 по методу: узлы вызовов, присваиваний/привязок (`h: v` без
  типа — кандидат, роль решает обход 2), throw-ов, pad-ов (`catch:`), merge-операндов
  (вместо `merge_scan` ×2), узлов walked-графа с их счётом (вместо `rw_methods_count`);
- индекс: узел (`@: LmP0Node`) → строка таблицы (own/ns/method/ml/call-site) — открытая
  хеш-таблица по адресу в frontend_alloc; и (метод, interned имя) → строки own/formal/ml.
  Имена интернируются один раз (`l2_frontend_intern` уже есть);
- C-словарь: один проход по закрытию predef/include (как сейчас `snap_document`, каждый
  документ один раз) строит таблицу имя → {type, fnptr, function, define}; `is_known`,
  `predef_has_type/_function/_fnptr`, `predef_receiver` становятся обращениями к ней.

Владение: все таблицы — frontend_alloc текущего перевода, освобождаются в
`lm_compiler_release`; дерево P0 остаётся собственностью документа; индекс хранит адреса
узлов, не копии.

**Обход 2 — валидация записанных вызовов и присваиваний (один проход по спискам обхода 1,
тело за телом, с теми же scope-правилами видимости).**
Результат на каждый узел списка:
- вызов: callee (метод/процедура ns/C-функция/fnptr/held callable/EXEC с контрактом),
  арность, разрешённые места актуалов, обязательство throws/catch (одна функция
  `obligation(callee_declared, caller_declared, pads_of_block_chain)`), транспорт
  (где печатать runtime-допуск: типизированные Structure-формалы); статусный канал
  — у всех нативных не-machine методов единообразно (§4.2);
- присваивание/привязка: роль головы один раз (все методы известны): до S8 — существующий
  `is_asgn`, с S8 — общая `lmx_walk_named_role` (§2); место цели (own/formal/dynamic
  input/path), C-тип места по объявлению; для приёма Structure в типизированное место —
  печать runtime-допуска, не проверка;
- свободные имена метода (`dyn_local` остаётся локальным): имя, не разрешённое в
  локалы/формалы/методы/ns/C-словарь — динамический вход этого метода; его тип — из
  объявления, если имя где-то объявлено в unit тем же методом/моделью, иначе транспорт
  графа (как сейчас `dt`), без замыкания по вызывающим (§4.5).
Обход 2 не создаёт новых обходов дерева: только списки обхода 1 и индекс.

**Обход 3 — печать.** Один проход по телу каждого метода печатает L1 (нативное тело и/или
walked-граф), читая только таблицы обходов 1–2 через индекс по адресу узла; все
`*_find` по имени в эмиттере — табличные обращения. `emit_unit` печатает предef-строки,
заголовки, типы, методы, конструкторы и корень; `pub_prepare`/`place_tables_declare`
печатают по готовым таблицам. Любая функция эмиттера, которой нужен факт, не
записанный обходами 1–2, — дефект дизайна, а не повод для вспомогательного поиска.

Счёт посещений: ровно один полный проход в обходе 1, один по спискам в обходе 2 (каждый
узел-операция один раз), один по телам в обходе 3. Для честности в срезах добавляется
диагностический счётчик посещений узлов по обходам, печатаемый в stderr при
`L2_PASS_COUNTS=1` (как существующий `L2_EXPR_PLACES_OUT`), и он входит в записи
измерений.

## 4. Удаляемые механизмы, их потребители и замены

### 4.1 Повторный сбор и predef
Удаляются: цикл emit.lm2:5767–5779, вызовы `collect_asgn_binds` :5808/:5881,
`ml_rebuild` в `dyn_local`/`check_body`, `free_name_at` core.lm2:4887 (узел берётся из
индекса). Potребители `ns_proc_add` остаются; `local_ns_proc` emit.lm2:1468 становится
частью обхода 1 (сохранение/восстановление scope — как сейчас). Замена predef-обходов —
индекс C-словаря (§3); негативный кэш не вводится (неудачных открытий в корректном дереве

### 4.4 Сброс `native` при изменении кода (общий путь записи)
Исполняемый код выбирает `operand\native` любого операнда (`lmx_walk_callable_addr` :4083,
`dispatch_values` :4261), не только FN: нативное слово может быть у метода, у обычной
исполняемой Structure (`call: A`), у корня. Поэтому правило — не по роли FN и не по слоту 3,
а по тому, **что именно записано**. Одна функция ядра `lmx_code_changed(arena, cell, holder)`
в пути записи:
- **узел кода** — `code_node(arena, x)`: графовый узел с уже установленной меткой роли
  (`lmx_walk_shape_op(arena, x) != NONE`, walk_values.lm2:3178 — читает **голову** Structure,
  ячейку LmxOp; `lmx_walk_role_in` принимает саму ячейку головы, не Structure, и для
  holder'а дала бы NONE — поправка Codex P2-5), **или** узел с написанной головой ещё без
  метки: ключ таблицы имён — сам узел-вхождение (`lmx_source_name_get(arena, x) != 0` по
  адресу узла; lmx_source_names.lm2:1–4 и lmx_walk.h.lm1:11–14: голова-ресивер вхождения
  ключуется адресом вхождения, имя **поля** — адресом владеющей дочерней ячейки, поэтому
  именованные поля данных узлами кода не считаются). Так runtime-построенная записанная
  операция — код до всякой lowered-метки, без исполнения и без prepared-флага;
- предикат «записан код» — по **фактическому месту записи и его текущей роли в коде**,
  без прогнозов: `code_write(arena, holder, slot, old, new)` истинно, если (1) holder —
  узел кода (запись в LIT-ячейку, операнд SET/PUT/CALL/IF/…, элемент THROWS-заголовка, pad,
  операнд NAMED-вхождения); (2) старый или новый ребёнок слота — узел кода: замена статьи
  тела, вставка написанной операции на место данных обычной native-Structure, замена
  статьи данными; (3) holder — callable (пул роли FN) и slot — одна из его частей
  `args`/`return`/`var`/`body` (0–3), какой бы ни была форма ребёнка: замена целой части
  `body`/`args` обычного callable — код; (4) holder — часть callable (сам узел
  `body`/`args`/`return` или описание `var`: его `parent` — callable и он стоит в слоте 0–3) —
  запись любого его слота меняет код (статья тела, формал, описание результата). Тогда
  `native: 0` у **каждого** предка по `parent`, у которого `native != 0` — его откомпилированное
  слово зависело от этого поддерева (L2 §88: зависимость может принадлежать охватывающему
  коду); обычная исполняемая Structure (`call: A`), чьи статьи — узлы кода среди её полей,
  покрыта (1)–(2), вложенная операция — (1) и подъёмом;
- запись — **данные** во всех прочих случаях: holder — узел данных (поле модели, слот
  данных `var` при публикации, элемент Array), слот держит и получает значение/данные:
  `native` всех предков сохраняется (L2 §88: «a compatible entry survives an ordinary
  data-value change»); так SET/публикация dirty в слоты `var` метода не сбрасывают его
  слово (публикация пишет значение в слот данных, (4) к нему не относится: слот `var` —
  данные, его описание — часть);
- рабочее значение до публикации не трогает граф — ничего не сбрасывает; сброс — в момент
  физической записи/публикации (§7b), атомарно с ней.
**Откуда запись знает свои места в коде (реальный путь; поправка Codex к редакции 4).** Редакция 4
держала у ячейки одну пару holder/slot в companion-метаданных и два поля `LmxWalkPlace`. Это неверно
в трёх местах: (а) одна физическая ячейка стоит сразу в нескольких местах кода (числовая `p` —
операнд C1 и C2 двух нативных слов; узел — статья двух тел): одна пара описывает только
последнюю установку, запись через `@p` должна снять оба слова, а подъём от C2 первого не
достигает; (б) companion — `chunk\value_contexts` (lmx.h.lm1:348–361; lmx_pool.lm2:181/485: хвост
записи чанка, один LmxWalkValue на ячейку указательного пула) — при каждом `lmx_value_cell_fill`
:495 переписывается целиком (`lmx_value_context_copy(stored, @ saved)`, затем present/kind/ref):
метаданные места в нём не выживают; (в) ребёнок устанавливается не в одной точке:
`lmx_graph_ref_fill_in` :198 (`\slot: value`; через неё `lmx_graph_ref_store_in` :189 — PUT_REF
:2039/:5166, `lmx_walk_store_*` :22–81, merge_owned, прямые вызовы graph_copy_owned :2757–3525),
`lmx_arena_ref_store` lmx_arena_refs.lm2 (тот же `\slot: value`; им пишут l2_driver.lm2:433–1457 и
сгенерированный код потребителя, l2_consumer_uses.lm2:261/327/393) и запись значения через
место-слот: `lmx_value_cell_access` :449–456 для пула kind CHILDREN/REF выдаёт
`lmx_arena_pointer_void_write` (lmx_arena.lm2:441), так что `lmx_walk_slot_place` :1505 →
`lmx_walk_value_store_with_writer` :1293 → `lmx_value_cell_store` :480 → `lmx_value_cell_fill`
перепривязывает ребёнка графа, минуя `lmx_graph_ref_fill_in`.

Замена — **связи ячейка → места кода**, отдельно от companion:
- **Запись связи** — пара (holder, slot), одна на каждую **текущую** установку ребёнка в место
  кода. Ведутся только рёбра кода: установка, при которой `code_write(holder, slot, old, new)`
  истинно по (1)–(4) (holder — узел кода или часть callable; или ребёнок — узел кода). Установка в
  данные (поле модели, элемент Array данных, слот `var` при публикации) записи не создаёт: ячейки
  данных связей не имеют и ничего не стоят. Рёбра известны в момент установки — никакого анализа
  алиасов и никакого предсказания.
- **Хранение** — «адрес ребёнка → цепочка записей (holder, slot)»: голова цепочки — в ленивом
  боковом массиве чанка ребёнка по порядковому номеру ячейки (чанк находится по адресу, как
  companion: `lmx_range_cell_pool` → `lmx_pool_chunk_at`), записи — в free-list C-heap,
  принадлежащем записи арены (`arena\code_links`), вне `arena\blocks` (поправка Codex к ред. 5;
  ниже, «Срок жизни таблицы»). Не ячейки графа: GC их не маркирует и не чистит, копирование и merge
  их не видят. Companion остаётся saved Value-context и о местах ничего не знает;
  `lmx_value_cell_fill` его переписывает, как сегодня.
- **Поддержание** — одна функция ядра `lmx_graph_slot_rebind(arena, holder, slot, old, new)`,
  через которую идут все три физических пути перепривязки: `lmx_graph_ref_fill_in` (holder/index
  — аргументы, old — текущее `\slot`), `lmx_arena_ref_store` (parent/index — аргументы) и
  `lmx_value_cell_fill` для ячейки kind CHILDREN/REF, у которой holder и slot восстанавливаются
  из самой ячейки-слота: пул CHILDREN — массив детей ровно одной Structure
  (`lmx_arena_refs_open_profiled` lmx_arena_refs.lm2:248–283: `lmx_pool_make_profiled` на каждую,
  `parent\array.data` = данные его чанка) — в запись пула добавляется обратная ссылка `holder`,
  проставляемая там же, slot — порядковый номер ячейки в чанке. Пул REF — backing Array ссылок —
  общий для всех Array своего типа (`lmx_array_ref_new_physical_profiled` lmx_array_ref_owned.lm2:37–73
  → `lmx_arena_take_n_profiled` lmx_arena.lm2:333–365, `lmx_arena_find_profiled`: один пул на (kind,
  type, profile), несколько Array в одном пуле и чанке), поэтому обратной ссылки пула holder'у REF
  не дать; и Array **может** быть узлом кода: `lmx_graph_node_in` lmx_arena_refs.lm2:22–33 принимает
  LMX_KIND_STRUCT и LMX_KIND_ARRAY с заголовком Lmx, `lmx_walk_shape_op` :3178–3195 читает через него
  голову, `lmx_source_name_prepare` :80–101 не исключает Array как ключ вхождения (поправка Codex к
  ред. 6: запрет по типу снят; решают фактическая роль/карта и место, как у Structure). Holder и slot
  REF-ячейки восстанавливаются из **текущего backing range**: при создании Array (там известны
  descriptor, base и count) и при росте (`lmx_array_grow_owned`, новый backing) ячейкам backing
  проставляется владелец в ленивом боковом массиве их чанка (`chunk\slot_owner[ordinal] = descriptor`;
  O(count) там, где создание и так O(count); пул не переиспользует выданные ячейки — «an address
  handed out earlier never moves», lmx_pool.lm2), slot = (ячейка − `holder\array.data`) / stride. Один
  lookup на запись, без поиска всех Array, без preflight и whitelist. Дальше `code_write` решает по
  (1)–(4) с holder = этот Array: Array с головой роли или вхождения — узел кода, его элементы — места
  кода (связи, сброс); обычный Array данных — запись данных, native сохраняется. Семантика: old ≠ 0 → снять ровно запись old → (holder, slot) (остальные связи old
  остаются: перепривязка одного слота не трогает актуальную связь другого); new ≠ 0 и ребро — код
  → добавить new → (holder, slot); затем сброс по `code_write`, как выше.
- **Использование при записи в ячейку** (`lmx_walk_value_store_with_writer`: числа —
  `lmx_walk_store_numeric_raw`, ссылки — не-слотовая ячейка; место любого вида: слот, проекция,
  ELEM, deref): один lookup по `place\address`. Нет связей → данные, ничего не сбрасывается. Есть →
  для каждой (h, s): `native: 0` у h и подъём от h — у узла с собственными связями по **всем** его
  holder'ам, у узла без связей (ребро данных вверх) по цепочке `parent` с `native != 0`, как выше.
  Так запись через `@p` снимает слова C1 и C2 — оба и ровно их. Поля holder/slot у `LmxWalkPlace`
  не нужны и из дизайна сняты.
- **Уход хранилища** (поправка Codex к ред. 5: `lmx_arena_array_drop` — не единственная и не
  своевременная точка: `lmx_pool_release` lmx_pool.lm2:292–311 сначала снимает интервалы чанков и
  обнуляет head/tail, `lmx_arena_drop` lmx_arena.lm2:231–290 снимает отдельный чанк через
  `lmx_pool_chunk_drop` :680, оставляя пул, и этим путём идут `lmx_arena_revert` :305–331 и sweep
  GC). Хук — **`lmx_range_drop`** lmx_range.lm2:267–300: единственное место, где интервал хранилища
  покидает индекс арены, и там уже стоит прецедент того же рода — `lmx_source_names_drop(arena,
  lo, hi)` :278–280 («spelling keys/text must retire while this storage is still registered and
  readable, before its address can be reused»; lmx_source_names.lm1:253). Рядом с ним —
  `lmx_code_links_drop(arena, lo, hi)`: ячейки [lo, hi) ещё зарегистрированы и читаемы; для чанка
  пула CHILDREN снимаются связи его занятых (`lmx_chunk_cells` lmx_pool.lm2:57) ненулевых слотов (ребёнок →
  (holder, slot); O(занятых слотов), которые drop и так освобождает), для любого чанка
  освобождаются цепочки по адресам его ячеек вместе с боковым массивом голов. Все пути ухода —
  `lmx_pool_release` :301, `lmx_arena_drop` :288 (revert, GC, dispose), lmx_arena.lm2:636,
  lmx_range.lm2:772 — проходят через эту функцию; частичный drop/revert снимает ровно связи
  ушедшего интервала, остальные живые связи остаются.
- **Срок жизни таблицы.** Головы — боковой массив чанка (`chunk\code_links`, поле LmxChunk; 0 до
  первой связи ячейки этого чанка; C-heap; освобождается хуком при уходе чанка, как и `chunk\slot_owner`
  REF-чанков; S4 проверяет обе C-heap части — головы и записи — на drop, revert и bulk
  `lmx_arena_release`); записи (child,
  holder, slot, next) — free-list C-heap в записи арены (`arena\code_links`), не блок
  `arena\blocks`: `lmx_arena_revert` (снимает блоки до метки) и GC их не трогают, освобождение —
  только в `lmx_arena_release` :690. Таблица никогда не держит адрес снятой записи или ушедшего
  чанка: запись освобождается при снятии связи, головы — с чанком, хук срабатывает до потери
  контекста. Связи слабые: держателя не удерживают, маркировка GC их не видит.
- **Обход сброса** — обычный обход графа связей с меткой посещения (generation-stamp в записи
  арены: узел посещён, если его штамп равен номеру текущего обхода; очистка между обходами не
  нужна): завершается на циклах и общих подграфах, каждый holder сбрасывается и раскрывается один
  раз.
Ничего из этого не запрещает допустимое разделение ячейки, не обходит и не проверяет программу
и не снимает native на записях данных.
Так оба исполнителя — walker и нативный код — пишут в граф теми же функциями ядра
(проверяется в S4: все эмиттерные записи в граф идут через них, не прямым присваиванием в
слот). Стоимость — O(1) на установку ребра кода (загрузчик: размер кода), O(1) lookup связей на
запись данных, O(связей × глубина) только на запись в код. Транслятор ничего не предсказывает;
никакого анализа будущих мутаций и алиасов.

**Реализация (срез 253, tp115; запись `steps/witnesses/fix253-20261102/notes.md`) — отличия от текста выше.**
- Боковое хранилище — в **записи индекса** (`LmxRange`: `links`, `slot_owner`, `holder`, `side_cells`,
  `side_stride`, `kind`), не в записи чанка: `lmx_pool_make_profiled` кладёт блок записи (пул + чанк) в список
  арены ПОСЛЕ блока payload, поэтому revert и sweep освобождают запись чанка раньше, чем
  `lmx_range_drop` видит интервал payload; запись индекса живёт ровно столько, сколько интервал,
  `lmx_arena_attach` переносит её поля, `lmx_range_side_release` освобождает всё при bulk release.
  Записи (`LmxCodeLink {child, holder, slot, next, mark, work}`) — C-heap узлы ровно одной цепочки (malloc/free),
  без free-list в записи арены; `mark`/`work` — штамп и нить рабочего списка сброса (ниже). Шаг и вид массива
  копируются в запись при вставке интервала (`side_stride`, `kind`, fix05): при drop запись массива может быть уже
  освобождена.
- `lmx_graph_slot_rebind` реализован парой вокруг физической записи (fix05, P1-B Codex):
  `lmx_code_rebind_prepare(arena, cell, old, new, &record, &code)` **до** записи — решение код/данные по
  состоянию до записи (`lmx_code_write`), выделение записи связи и голов цепочки (`lmx_range_link_prepare`),
  сброс слов выше holder'а; отказ (1) — ничего не записано и не связано (слова выше уже сняты: слово меньше,
  не устаревшее слово); `lmx_code_rebind_commit(arena, cell, old, new, record)` **после** записи — снятие записи
  старого ребёнка и вставка подготовленной (`lmx_range_link_commit`), без аллокаций; `lmx_code_rebind_abandon`
  — запись не состоялась (отказ callback'а записи в `lmx_value_cell_fill`). Прежний порядок «запись → malloc →
  return при отказе» оставлял изменённый код со старым словом. (holder, slot) восстанавливаются из
  **физической** ячейки слота (`lmx_range_slot_holder`: holder интервала CHILDREN, владелец REF-ячейки) на всех
  трёх путях, в том числе в `lmx_graph_ref_fill_in` и `lmx_arena_ref_store`; связи ключуются физическим
  holder'ом (view merge-результата на ячейку операнда называет операнд).
- Критерий (1)–(4) по фактической раскладке: (1) holder с головой-операцией — любой слот; (2) уходящий
  или приходящий ребёнок — операция или именованное вхождение; (3) callable и слот 0–3; (4) часть callable
  **или именованное вхождение без головы-операции** — только когда уходит или приходит **узел**.
  Собственные ячейки метода лежат в слотах 0.. его части body (`l2_qN_from: lmx_arena_ref_cell(part3, k)`),
  а вхождение метода само ключует таблицу имён, поэтому «любой слот части/вхождения — код» делал бы каждую
  публикацию (`lmx_publish_*`) и каждую запись поля именованной Structure записью кода. Для слота 0 голова
  судится по заменяемому значению: установка собственной головы кадра — конструкция, не изменение кода.
- Сброс поднимается **только по рёбрам кода**: от holder'а — по его связям к holder'ам выше, и так далее
  (рабочий список — сами записи связей, нить `work`; штамп посещения — поколение сброса арены
  `LmxArena.reset_gen`, записываемое в `mark` записи: сброс не аллоцирует и не может отказать, цикл рёбер кода и
  общий подграф завершаются, потому что запись берётся один раз за поколение; `lmx_arena_attach` берёт
  наибольшее поколение двух арен; у `Lmx` нет поля для штампа — fix05); по `parent` подъёма нет. Запасной подъём
  текста выше («у узла без связей — по цепочке `parent`») снят по boot115c: после установки слов программы
  конструкция продолжается таблицами использований вызовов (`l2_cc_uses…` — свежие Structure под узлами
  владельца, принимающие вызываемые узлы кода), а при исполнении библиотечные экземпляры (S8.1) строятся под
  владельцем; каждая такая установка — запись кода по (2), и подъём по `parent` снимал слово корня владельца
  и дескрипторов предоставленных конструкций, которые этого кода не содержат (lib_owner: WalkRoot без слова,
  затем UNSUPPORTED). Зависимость слова от кода — ровно цепочка рёбер кода, которую хранят связи: узел,
  достигнутый по ребру данных (callable в поле, экземпляр под владельцем, таблица использований), вызывается
  своим словом.
- Срок жизни владельцев Array при общем REF-интервале (fix05, P1-A Codex). Дескрипторы Array лежат в своём
  пуле (ARRAY), их backing — ячейки общего REF-пула; уход интервала дескрипторов из индекса (revert/sweep чанка
  пула дескрипторов, `kind = LMX_KIND_ARRAY`) снимает владение его дескрипторов в ещё зарегистрированных
  REF-интервалах (`lmx_range_descriptors_retire` в `lmx_range_side_drop`: `slot_owner[k] = desc → 0`, записи детей с
  `holder = desc` вырезаются), пока дескрипторы читаемы; остальные Array того же REF-чанка продолжают работать.
  `lmx_range_slot_owner_set` при смене владельца ячейки вырезает записи старого владельца (путей re-backing
  сегодня нет; правило держится и для будущего). Владелец/holder проставляются **до** публикации указателя
  данных (`va\data` в `lmx_arena_refs_open_profiled`, `array\data` в `lmx_array_ref_new_physical_profiled`):
  отказ оставляет Structure без массива детей или Array без backing, а не массив без владельца. Фокусная
  проверка — в self-check драйвера: шаг пула дескрипторов = первый запрос (1 ячейка на чанк), шаг REF-пула =
  первый запрос (8); второй и третий Array делят один REF-чанк, третий создаётся после mark и уходит с revert — у
  его ячеек нет владельца, запись установленной в него операции снята, второй Array держит владельца и принимает
  запись; плюс цикл двух операций, держащих друг друга: сброс по значению операнда завершается и достигает
  обеих.
- `lmx_arena_ref_store(arena, parent, index, value)`: arena передаётся всеми фактическими и генерируемыми
  вызывающими (ядро, driver, fixture native_closure_values, эмиттеры); переходного символа нет — L1 машинных
  модулей не строит графов, программы печатает только новый эмиттер.
- Остаётся на срез C: сырые записи ячеек значений эмиттером (`l2_entry_slot[0]: lmx_int_new_profiled(…)`) —
  по критерию это данные, записи не создают; проверка «все записи эмиттера через функции ядра» переведёт их.

### 4.5 Динамические входы без замыкания
Удаляются `dyn_close`, `cfl_close`, `cfa_apply`, `dyk_close`, `anchor_close`, `dyn_step`,
`dyn_typed`, `wait_*`/`wait_run`, `note_call`, `d105a_close`, `ide_*`. Остаётся локальный
`dyn_local` (свободные имена самого метода, `dyn_add` context.lm2:777).
Замена — **цепочка активаций**, одинаковая для обоих исполнителей, по книге §12 (RU :464):
источник имени — ближайшая локальная привязка вызывающего, затем его унаследованный
динамический вход, затем лексический fallback callee; пересылающий метод ничего не
формирует. Реализация без замыкания: каждая активация имеет запись контекста
(walker — `LmxWalkFrame`, уже есть; native — такая же запись `LmxNativeFrame` в C-кадре:
таблица метода «ключ имени → смещение места», указатель на базу локалов, родительская
запись; таблица метода — статическая, печатается обходом 3 по строкам обхода 1).
При входе активации callee для каждого своего свободного имени один раз поднимается по
цепочке записей (сравнение interned ключей, не текста), берёт место первой привязки
(локал вызывающего или его уже разрешённый динамический вход); не найдено — лексический
fallback callee (уже эмитируемый `arg` fallback). После входа — только места/карты
(«без повторного поиска имени на чтении»). Это не скрытый root, не companion graph и
не глобальный реестр: записи живут ровно столько, сколько активация, как `LmxWalkFrame`.
Walker берёт ключи локалов из таблицы адрес→имя (`lmx_source_name_get`), нативный код —
из напечатанной таблицы метода; ширина входов callee больше не зависит от замыкания
frontend (`lmx_walk_input_width` читает только записанные формалы + собственные свободные
имена callee).
Нормативная правка в том же срезе: фраза книги «Требования статически известных вызовов
распространяются до неподвижной точки, в том числе через взаимную рекурсию»
(provenance/semantics-book.md:729 RU, :779 EN → docs/LMX_semantics.*) заменяется правилом
цепочки активаций с ссылкой на выдержку автора 2026-11-01; генерация
`python tools/build_semantics.py` и проверки docs — после правки.

## 5. Общие маршруты: вызов, присваивание, допуск/ошибка, сброс native

- **Вызов.** Транслятор (обход 2): callee по голове через таблицы обхода 1
  (метод/ns-процедура/C-слово/fnptr/held), арность по `args`, обязательство throws,
  печать: нативный вызов с единым статусным каналом и транспортом значений
  (`l2_input_values/refs`), либо `CALL`/`EXEC` узел графа. Walker: `lmx_walk_select_call`
  → `lmx_walk_dispatch_values`, тот же транспорт, тот же статус. Адресные карты
  (`lmx_implements_slot`, PLACE) сохраняются; имена сопоставляются при допуске, доступы —
  по адресам.
- **Присваивание.** Место по объявлению (own/formal/dynamic input/путь), запись через
  общий `lmx_walk_value_store`/`lmx_graph_ref_store_in` (сброс native внутри),
  рабочее значение и dirty по §7b (норма 470: `node\field` не обновляет bare snapshot
  — сохраняется). Приём Structure в типизированное место — runtime-допуск.
- **Допуск/ошибка.** Только `lmx_implements` семейство; NO → бросок `implements`;
  UNKNOWN не NO (книга 2.5.1, lmx_implements.lm2:114). Транслятор не доказывает и не
  запрещает динамический случай.
- **Исключения.** Обязательство по объявленным именам — одна функция `lmx_call_obligation`
  (§2). Статически известный callee: транслятор вызывает её в обходе 2 над записанным
  вызовом — нарушение есть ошибка трансляции в месте вызова. Динамически выбранный callee
  (`call: code data`, callable-значение, fnptr): объявленный `Bad` остаётся объявленным — он
  **не** переквалифицируется в неявный; обязательство проверяет та же функция в
  `lmx_walk_call_in` после `select_call` и до `dispatch_values`, т. е. при фактическом допуске
  вызова и до исполнения callee; нарушение — отказ вызова обычным путём допуска вызова
  (тот же `LMX_WALK_INVALID`, которым `lmx_walk_call_in` :4590–4700 отвергает вызов, чей
  контракт не выполнен), без нового исключения, без переквалификации и без запрета
  динамических вызовов. Неявные имена — без обязательств; runtime — ключи/pad/граница как
  сейчас; статусный ABI (единый канал) — транспорт, не обязательство: он ничего из этого не
  отменяет.
- **Сброс native.** §4.4; следующая диспетчеризация видит `native = 0` и идёт walker по
  актуальному телу (`lmx_walk_dispatch_values` выбирает на границе, после эффектов —
  уже так).
- **Видимость и семантика текущих значений** не меняются: forward/down для полей и
  именованных Structure, двусторонняя для методов и catch; значения — текущий граф.

## 7. Измерения и путь к working selfbuild

Замер каждого среза — на одних байтах входов и одном дереве CWD:
- **L3/L2 → L1**: `l2trans` по argv строки записи G1 (`bld_machine_module`, --library,
  --machine ×N, --header, входы stem/convert/primitive) из частного дерева; wall по
  старту/выходу процесса, CPU и пиковый working set/commit по процессу (как perf251
  attempt03); для useplan, Lower, Core, Emit отдельно; счётчик `L2_PASS_COUNTS`;
- **L1 → C**: `l1trans` корня frontend (`frontend-source.lm1` → `frontend.c`), wall/CPU;
- **C**: `gcc -O2 -fno-strict-aliasing` frontend.c того же результата (строка 386
  записи), wall/CPU/WS; это «компиляция соответствующего результата» для цели
  «≈ столько же»: отношение Σ(L2→L1 модулей frontend) / T(gcc frontend.c) публикуется
  в каждом срезе; базовая точка G1 full100: 137,74 мин / ≈40 с.

против boot98/full100 по записям (`record.txt` времена шагов). Результаты и границы — в
`build_performance_profile_from_fable.md` (создаётся с S1) и в записях срезов.

Путь к самосборке: после S1–S6 — whole quick (G0 = G1 full100 tool `E8150E60…` или
boot89 `7FD2E824…`, previous frontend G1 full100 `bf6d713e…`, свежий stage только из
