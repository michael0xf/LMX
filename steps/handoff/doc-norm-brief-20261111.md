## 1. Нормы (слова автора; номера — для ссылок в отчёте)

**Н1. Роли `data` и `code`.** Structure участвует в запуске как данные или как код; роль задаёт запуск, а не сама
Structure. Одна и та же запись читается по роли.

- В роли **данных**: структурная запись (`Имя: хвост`, `Имя(хвост)`, блок `Имя: … end: Имя`) объявляет Structure —
  какой бы ни была её голова. Запись вызова и ресиверы управления (`if`, `for` …) в данных — тоже Structure,
  названные своей головой; до них доходят путём `data\if`, вложенные — `data\if\if`, с индексом при нескольких.
  Действуют объявления ресиверами мест (`int: x 5`, `@: ptr KnownStruct` и остальные). Присваивания `:=` и весь
  прочий код в данных **не исполняются**; присваивание там — просто поле, до которого доходят индексом.
- В роли **кода**: всякая запись — вызов. Объявление ресивером — вызов ресивера: проверка типа с присваиванием в
  место данных. Структурная запись — вызов своей головы: `Model: KnownStruct` в коде вызывает `Model`, и если
  такого метода нет — ошибка. Объявлений Structure в коде нет вовсе: код пользуется именами Structure из данных.
  Объявления вызываемых — `fn`, `sub`, `catch` — остаются и в коде.
- Вызываемое, объявленное в данных, вызывается прямо по имени и связывает свободные имена по общим правилам:
  сначала динамический вход, затем лексический источник.

**Н2. Имена.** Особое имя явной ссылки на данные запуска, одноимённая часть вызываемого и блок данных называются
`data` (прежде `var`). Часть с исполняемыми записями и одноимённый аргумент ресиверов `fn`, `sub`, `catch` —
`code` (прежде `body`). Части вызываемого: `args`, `return`, `data`, `code`. Пути: `f\data\x`, `f\code`,
`data\x`, `data\[N]x`. Формы ресиверов запуска: `fncall(args data return code)`, `fncall(data return code)`,
`fncall(return code)`, `call(args data code)`, `call(data code)`, `call(code)`.

**Н3. Порядок: `data` перед `code` — везде.** Двухаргументный запуск пишется `call: data code` и
`call(data code)`. Прежняя запись `call: code data` (в примерах `call: Code Data`, `call: named named\var`,
`call: code var`) переписывается перестановкой двух аргументов. Схема называется `call(data code)`; фраза автора
«используется схема call(code, data)» — цитата из журнала, её можно упоминать только как слова автора.
Одноаргументный `call(code)` (то же, что `call(code code)`) исполняет Structure над самой собой; дочерний блок
`data` он **не** выбирает — данные передаются явно.

**Н4. Присваивание.** Только между значениями: примитивами, указателями на Structure и указателями на функции.
Имена Structure и функций друг другу не присваиваются: `Model := KnownStruct3` — ошибка. Указатель-переменная
объявляется `@: ptr KnownStruct`; `ptrToModel := ptrToKnownStruct` в коде допустимо. Имя Structure или функции на
месте значения указателя даёт указатель без записи `@Struct`.

**Н5. Аргументы.** Аргументы вызовов и ресиверов разбираются одним общим алгоритмом и читаются как код.
`f(arg: Struct)` — вызов `arg`, без вариантов (без метода `arg` — ошибка). Именованный аргумент — только
`f(arg := Struct)`. Формалы объявляют ресиверы: `sub: proc (int: arg default)`,
`sub: proc (@: arg1 Template1; @: arg2 Template2)`. Запись `sub: proc (arg1: Template1; arg2: Template2)`
запрещена: это были бы объявления двух Structure, а не переменные; объявления Structure пишут в блоке данных —
`sub: proc () (struct1: Template1; struct2: Template2)`. Следствия (чтения исполнителя, принятые в книге): письмо
выхода пишется `send: exit(exit_code := 7; stdout := ""; stderr := "")`; именованные части ресиверов `fn`, `sub`
подаются только через `:=` (`fn: name := k1; args := (int: a); return := int; code := (return: a + 1)`), подача
частей по голове (`fn: name: k2; args: …`) снята; требование с кандидатом пишется плоско — `@: ptr Model Other`,
`@: ptr Model 0`, а не `@: ptr Model: Other`; имя, держащее результат `merge`, объявляет `@: R merge(A; B)`.

**Н6. `implements`.** Выполняется один раз — при построении чистого графа. После построения он нужен только там,
где кандидат выбирается во время исполнения (эти случаи собраны в
`steps/implements-runtime-cases-20261111.md`). Присваивание примитивов при исполнении на допустимость не сверяется.

**Н7. Упоминание известной Structure не раскрывается.** В `Model: knownModel` (в данных) объявляется Structure
`Model` с одним атомом `knownModel`. Ни парсер, ни построение чистого графа содержимое `knownModel` внутрь
`Model` не помещают: в **дереве** под `Model` стоит один узел — атом. Этот атом — указатель (`void *`) на Structure
`knownModel`; ссылаться на неё он начинает при интерпретации и трансляции, и путь через него продолжается в её
поля: `Model\knownModel\a` — поле `a` самой `knownModel`. Нового дерева не возникает: место Structure в дереве
задаёт её `parent`, и у `knownModel` он не меняется. По имени ссылка **неизменяема**; слот атома адресуется
индексом, и присваиванием по индексу (`Model[0] := …`, `data[index] := …`) в него можно записать что угодно.
Изменяемую ссылку объявляет ресивер: `Model: @: ptr knownModel` — `ptr` есть указатель-переменная внутри `Model`.
В `Struct1: (Struct2 a b c)` внутри `Struct1` — одна **безымянная** Structure с четырьмя атомами;
`Struct1[0]\Struct2\a` — поле `a` Structure `Struct2`, а `Struct1[0]\a` — собственный атом безымянной Structure
(это два разных `a`). Ссылки по имени могут замкнуться (`A: B` и `B: A`) — это **не ошибка**. Так же, по имени и
без раскрытия, называют Structure аргументы вызовов. Копии нет, «перехода» Structure внутрь другой нет.

**Н8. Видимость в данных — в обе стороны.** Имя, объявленное записью данных (место, обычная именованная
Structure, ссылка на метод), доступно и коду над этими данными, и остальным записям тех же данных, стоят ли они
выше или ниже объявления. Методы `fn`, `sub` видны в обе стороны своего блока. Прежнее правило «обычная
именованная Structure и ссылка на метод видны лишь с места объявления вперёд и вниз» снято; фразы вида «видимость в
данной позиции», «позднее объявление не видно назад», «исходная позиция определяет доступность имени»,
«двусторонняя видимость отложена» больше не верны. Доступность имени не означает, что значение уже вычислено:
порядок исполнения операторов прежний.

**Н9. У Structure, запущенной над самой собой, своих правил нет.** `call(code)` (то же `call(code code)`) и корень
единицы: каждая запись читается по обеим ролям общими правилами; где они не дают определённого результата — ошибка.
Никакого «пропуска своих объявлений» нет.

**Н10. Повтор объявления.** В коде повтор объявления ресивером (`int: i 6` при известном `i`) — внеочередная
проверка типа с присваиванием, второго поля не возникает. В данных повторное объявление — ещё одно вхождение имени:
прежнего оно не заменяет и в него не пишет; после него имя адресуется только с индексом вхождения
(`data\[index]Model`), а обращение без индекса — ошибка. Structure, которая сама себе данные, сначала
инициализирует переменные своего корневого уровня.

**Н11. Решения 2026-11-10, на которые опираются правила выше** (в книге уже внесены, сверяйся с её разделами
`receiver-args-only`, `forms-declare-or-call`, `assign-known`, `values`): место объявляет только форма
`ресивер: аргументы` (`int: i 5`, `int: x`, `@: ptr Model`); составная форма `имя: ресивер: значение`
(`i: int: 5`, `ptr: @: 0`) переменную не объявляет — это Structure с вызовом ресивера внутри; структурные формы
только объявляют или вызывают, значение в известное место записывает `:=`; P0 не раскрывает единственную
Structure в скобках: `A: (b)` — `A` с одной безымянной Structure внутри, а Structure с полем `b` пишется `A(b)`
или `A: b`; `var: (int: i 5)` → к полю ведёт `[0]\i`.

**Н12. Чтения исполнителя (не слова автора; в текстах помечаются как чтение исполнителя или даются со ссылкой на
«ответы исполнителя, часть Р»).** Р6: корень единицы запускается как Structure над самой собой. Р7: структурная
запись, до которой дошло исполнение, без метода с именем её головы ошибочна — в том числе запись, которой те же
данные объявляют обычную Structure; поэтому исполняемая Structure (корень единицы, тело метода, Structure,
запускаемая `call`) объявлений Structure не содержит; их пишут в данных — в части `data` метода, в Structure,
которую запуск получает данными, в написанной Structure на месте значения. Р8 (подтверждено автором 2026-11-11:
«отказыввает в code, да, но не в data где это просто пустая структура f»): запись `f()`, голова которой — обычная
Structure данных, в коде отказывает; в данных та же запись `f()` — просто объявление пустой Structure `f`; обычную
Structure запускает `call`. Р9: блок `data:` внутри исполняемой
Structure в коде — вызов `data`, он отказывает; данные и код пишут раздельно — двумя Structure данных или частями
`data` и `code` метода (`call(m\data m\code)`). Р10: запись вызова в данных — Structure с именем своей головы,
адресуется `data\f`; голое имя `f` в коде по-прежнему называет метод. Р2: дамп чистого графа печатает дерево —
атом, а не содержимое указуемого.

**Состояние трансляторов (важно для формулировок).** Ни один транслятор этих правил 2026-11-11 пока не исполняет:
и чистый граф, и рабочий frontend читают прежние имена `var`/`body`, прежний порядок `call: code data`, связывают
атом в момент исполнения объявления, пропускают объявления Structure в исполняемом корне. Работа записана разделом
M11 плана `next_core_tasks_v3.md` (шаг 4 — имена и порядок в чистом графе, шаг 5 — чтение по ролям, шаг 8 —
рабочий frontend и перевод исходных текстов). В нормативном тексте пиши норму; там, где документ описывает, что
код делает **сейчас**, оставляй это описанием реализации и не выдавай его за норму.

## 2. Что менять — по видам мест

1. **Имена.** `` `var` `` как особое имя, часть, блок, аргумент ресивера, сегмент пути → `` `data` ``; `` `body` ``
   как часть или аргумент ресивера → `` `code` ``. Проверь каждое вхождение по смыслу: во фразе, где уже есть
   «выбранная `data`», слепая замена даёт бессмыслицу («переданная `data` — такая же Structure, как любой
   `data`») — такую фразу перепиши заново. Русское слово «тело» как описание (тело метода, тело блока) оставь;
   меняется только имя части в коде и в бэктиках. Оговорки вида «в этом разделе ещё записано прежними именами»
   после правки убери. Историческое упоминание допустимо одно на раздел: «до решения 2026-11-11 — `var`».
2. **Порядок.** Все двухаргументные `call` — данные первыми; в примерах поменяй местами два операнда и перечитай
   окружающий текст («первый аргумент — код» и подобное).
3. **Видимость.** См. Н8. Перепиши утверждения о видимости вперёд/назад, о «позиции», об «отложенной двусторонней
   видимости».
4. **Раскрытие, «внутри находится», «тот же экземпляр», копия.** См. Н7. Формулировки «`Struct1: Struct2` —
   Structure `Struct1`, внутри которой находится `Struct2`», «обозначает саму эту сущность, без копии», «дамп
   печатает вложенную Structure» замени на: атом — указатель на Structure, в дереве под `Struct1` только атом.
5. **Записи в коде.** Утверждения, что структурная запись в исполняемом теле «объявляет», «определяет»,
   «записывает в место», «не исполняется при объявлении», «остаётся определением», что «`A()` / `A: ()` — формы
   объявления» без оговорки о роли, — по Н1 и Н9: в данных объявляет, в коде вызывает.
6. **Аргументы, формалы, присваивание имён, `merge` в имя.** См. Н4 и Н5.
7. **Повторы.** См. Н10: в данных повтор не заменяет и не «пишет в то же поле»; фразы «повторное объявление
   заменяет содержимое», «несколько одноимённых полей данных запрещены» — исправить по Н10.
8. **Вопросы автору.** Вопросы П1–П7 закрыты (ответы — `LMX_blog/q/colon-declares-answered-20261111.md`); в
   `LMX_blog/q/current/` открытых вопросов нет. Фразы «спрошено у автора», «до ответа», «ждёт ответа автора» про
   эти пункты убрать, заменив нормой.
9. **Примеры в блоках кода.** Меняй механически только то, что однозначно: имена `var`/`body`, порядок двух
   аргументов `call`, подачу по голове → `:=`, формалы `Point: p` → `@: p Point`, `@: ptr Model: Other` →
   `@: ptr Model Other`. **Не перестраивай** пример в программу другой формы. Если пример в одном блоке смешивает
   объявление обычной Structure и исполняемые записи (по Р7 такая единица, исполняясь над собой, отказывает),
   блок оставь, в сопровождающем тексте назови, какие строки — записи данных и какие — кода, и занеси пример в
   отчёт (вид «пример со смешанными ролями») — решение примет исполнитель.

## 3. Чего не менять

- Дословные цитаты автора (в блоках и в кавычках-ёлочках) и исторические записи со словом «прежде», датой и
  ссылкой на журнал — их смысл: «так было». Не превращай действующую норму в «прежде» и наоборот без основания.
- Описания измеренного поведения кода и срезов («срез 346», «фикстура …», «проба …»).
- Главы и абзацы, которых эти правила не касаются. Не «улучшай» стиль попутно.
- Якоря `<a id="…"></a>` не переименовывай и не удаляй; новых не добавляй.

## 4. Формат книги (файлы в каталоге `book/`)

Книга — пары глав: в каждом блоке `@@ id | заголовок RU | заголовок EN | …` сначала идёт русская часть (`[RU]`),
затем английская (`[EN]`). Большие блоки разрезаны на куски `*.pN.ru.md` и `*.pN.en.md` — русский и английский
куски с одним номером содержат одно и то же.

- Один абзац — одна строка файла. Число абзацев, заголовков (и их уровни), таблиц и блоков кода в русской и
  английской частях должно совпадать; порядок тот же.
- Блоки кода (```` ```text ````) в русской и английской частях **побайтно одинаковы** — меняя пример, меняй оба.
- Ссылки: в соответствующих абзацах RU и EN — те же цели в том же порядке. Якоря одинаковы.
