# Красота LMX: почему «худший» пример оказался самым выразительным

21 ноября 2026 года. [English version](lmx_beauty.en.md).

В сравнении 23 шаблонов проектирования пример Interpreter оказался самым невыгодным для LMX по длине относительно Python: **232 непробельных символа против 185, то есть на 25,41% больше**. И именно этот пример особенно хорошо показывает достоинство языка, которое подсчёт символов не замечает: сколько устройства программы видно непосредственно в записи и сколько читатель должен восстановить в голове. Исходные листинги и методика измерения находятся в [23_interpreter_comparison.md](23_interpreter_comparison.md).

Задача очень проста: сохранить выражение `(x + 3) + x`, вычислить его при `x = 2` и `x = 5`, затем сложить результаты. Получаются `7`, `13` и в итоге `20`. В LMX переменная называется `n`; смысл вычисления тот же.

## Сверху — операция, снизу — выражение

Вот полный LMX-листинг из [сравнения Interpreter](23_interpreter_comparison.md):

```lmx
operands:
    @: left int
    []: @(int) right
    const: int: PASS_ARGS_AS_IS 0
    const: int: PRIORITY sys\priority("+")
    return: int
    add:
        return: \left + \right[0]

Example:
    int: n
    return: int
    calculate:
        import: operands
        return: (n add 3) add n
    demo:
        return: calculate(2) + calculate(5)
```

Верхняя часть показывает контракт пользовательского операнда: какие значения он принимает, в какой форме получает аргументы, какой у него приоритет и что он возвращает. Само сложение записано непосредственно:

```lmx
return: \left + \right[0]
```

Нижняя часть показывает применение этой операции:

```lmx
return: (n add 3) add n
```

Формула остаётся узнаваемой. Чтобы увидеть два сложения, не приходится сначала переводить вложенные конструкторы в арифметическую запись.

Поле `PASS_ARGS_AS_IS 0` указывает, что операция получает ссылки на подготовленные значения. `\left` и `\right[0]` читают их. `PRIORITY sys\priority("+")` задаёт приоритет встроенного сложения, а `return: int` объявляет обычный числовой результат. Пригодность метода в роли операнда определяется его DATA; `import: operands` делает имя доступным в выражении. Эти правила описаны в [ТЗ об операндах, аргументах и приоритетах, редакция 6](reference/to_fable_operands_arguments_priorities.md).

Здесь на виду вся пользовательская часть определения новой операции и её связь с выражением. Общий разбор и исполнение обеспечивает механизм expression языка. Пример показывает, как подключиться к этому механизму обычным методом.

## Почему короткий Python приходится мысленно разворачивать

Python-вариант в [том же сравнении](23_interpreter_comparison.md) выглядит так:

```python
def number(value):
    return lambda x: value

def variable():
    return lambda x: x

def add(left, right):
    return lambda x: left(x) + right(x)

def demo():
    v = variable()
    tree = add(add(v, number(3)), v)
    return tree(2) + tree(5)
```

Сложность чтения связана с тем, что привычные имена обозначают вещи другого уровня:

| Запись | Что она означает в этом примере |
|---|---|
| `number(3)` | Создать функцию, которая при последующем вызове вернёт `3`. |
| `variable()` | Создать функцию, которая при последующем вызове вернёт переданный ей аргумент. |
| `add(left, right)` | Создать функцию, которая потом вызовет `left` и `right` и сложит результаты. |
| `tree(2)` | Запустить собранное вычисление с аргументом `2`. |

Поэтому `v` здесь — функция. `number(3)` тоже возвращает функцию. `add(...)` при построении выражения ещё ничего не складывает. Отдельного явного объекта «дерево» в этом Python-листинге нет: `tree` — составная функция, сохраняющая связи с другими функциями.

Короткое `lambda` создаёт объект функции; его тело выполняется при последующем вызове. В [справочнике Python](https://docs.python.org/3/reference/expressions.html#lambda) эта форма сопоставляется с обычным определением функции, возвращающей значение выражения.

Чтобы увидеть устройство нашего `add`, достаточно развернуть эту запись:

```python
def add(left_calculator, right_calculator):
    def calculate(x):
        left_value = left_calculator(x)
        right_value = right_calculator(x)
        return left_value + right_value

    return calculate
```

Создаётся новая функция, сохраняющая доступ к двум другим функциям. После возврата из `add` она продолжает ими пользоваться. Это и есть работа замыкания в данном примере.

Теперь строка:

```python
tree = add(add(v, number(3)), v)
```

читается так: собрать вычислитель суммы; слева поставить вычислитель другой суммы, соединяющий чтение переменной с выдачей постоянной тройки; справа снова поставить чтение переменной.

Весь алгоритм присутствует в листинге. Однако читателю нужно одновременно держать в голове **построение будущего вычисления** и **его последующий запуск**. Имена `number`, `variable` и `add` сами по себе этого различия не показывают. Короткая запись вмещает создание функций, сохранение связей с внешними именами и отложенное выполнение.

Опытный читатель Python может узнавать эту конструкцию сразу. Тем не менее число символов не сообщает, сколько предварительного знания требуется для такого узнавания.

## Что дают дополнительные 47 символов

Разница между полными листингами составляет:

```text
232 − 185 = 47
47 / 185 × 100 ≈ 25,41%
```

А только две строки LMX:

```lmx
const: int: PASS_ARGS_AS_IS 0
const: int: PRIORITY sys\priority("+")
```

занимают **61 непробельный символ**:

| Явно заданное свойство | Непробельных символов |
|---|---:|
| `const: int: PASS_ARGS_AS_IS 0` | 26 |
| `const: int: PRIORITY sys\priority("+")` | 35 |
| **Всего** | **61** |

Описание двух свойств пользовательского операнда уже занимает больше всей разницы размеров. В Python-листинге правила включения нового имени в синтаксис инфиксных выражений не задаются: `add` используется по обычным правилам вызова функций.

Эти строки остаются в подсчёте — они обязательны для полноценного LMX-примера. Числа показывают, какое содержание занимает место: **явный режим получения аргументов и явный приоритет операции**. Дополнительно в листинге присутствуют требования к значениям и тип результата.

Поэтому фраза «LMX длиннее на четверть» сама по себе очень мало говорит о выразительности этого примера. Все числа относятся к конкретным листингам [23_interpreter_comparison.md](23_interpreter_comparison.md), включая их объявления и демонстрационные методы.

## Почему и остальные варианты выглядят иначе

В выбранных реализациях одно выражение представлено разными способами:

| Языки | Как представлено вычисление |
|---|---|
| Python, C++, Go | Функциями, которые сохраняют связи с дочерними вычислениями и вызывают их. |
| Java, C# | Объектами `Number`, `Variable`, `Add` с методом `eval` / `Eval`. |
| TypeScript | Объектами с методом `eval`, использующим сохранённые связи. |
| Rust | Вариантами `enum` и рекурсивным вычислением через `match`. |
| LMX | Обычным выражением языка с подключённым пользовательским операндом. |

Это описание именно листингов из [файла сравнения](23_interpreter_comparison.md). Java, C# и Rust довольно явно показывают узлы и обход. Однако саму формулу там приходится восстанавливать из конструкторов и служебной записи. В Python, C++ и Go создание вычисления дополнительно выражено через возвращаемые функции.

Обычную арифметическую формулу Python тоже позволяет записать непосредственно. В этой подборке его пример реализует отдельное представление вычисляемого выражения. LMX использует для показанной задачи собственный механизм выражений: новый метод становится частью привычной записи.

## Архитектурная красота: общий механизм работает на пользователя

В LMX для этого примера не потребовались отдельные пользовательские конструкции «число как вычислитель», «переменная как вычислитель» и «сумма как создатель вычислителя». Форму вычисления уже хранит граф тела `calculate`. Два вызова передают разные значения входа, сохраняя записанное выражение.

Общий механизм expression берёт на себя разбор, подготовку аргументов и исполнение операций. Пользователь определяет свой метод, задаёт его контракт и использует его в выражении. Сложность однажды решена в общей модели и доступна через обычную запись языка.

Это соответствует замыслу LMX: получать разные возможности из небольшого числа общих механизмов. На данном примере обычный метод, его DATA, разрешение имени и механизм выражений вместе дают пользовательский операнд. Для чтения применения этого операнда достаточно видеть саму формулу.

Режим `PASS_ARGS_AS_IS 1` также предусмотрен контрактом: он позволяет получать исходные аргументные вхождения и явно вычислять их через `sys\eval`. В показанном сложении используется режим `0`. Оба режима описываются тем же обязательным полем; приоритет остаётся отдельным свойством. Так расширение возможностей сохраняет видимый контракт операции. [Правила двух режимов](reference/to_fable_operands_arguments_priorities.md).

## Краткость, понятность и содержательность

Подсчёт символов отвечает на один точный вопрос: сколько знаков занимает конкретная запись. Для оценки примера полезны ещё два вопроса:

- Насколько непосредственно из записи виден ход вычисления?
- Какие свойства и договорённости явно выражены в этих знаках?

Interpreter показывает, почему ответы могут различаться. Python даёт самый короткий из приведённых листингов. LMX явно описывает контракт пользовательского операнда и оставляет его применение в обычной математической форме.

Читатель LMX может пройти пример сверху вниз: увидеть входы, правила получения аргументов, приоритет, результат и тело операции, затем прочесть выражение и два его вызова. Эти части расположены рядом и объясняют друг друга.

**Сверху определена операция. Снизу написано выражение с этой операцией. Дополнительные символы делают устройство видимым.**

Именно поэтому «худший» по одному численному показателю пример может оказаться самым выразительным объяснением замысла языка.
