# Ответы на действующие вопросы о языке

Сверено с документацией 2026-11-15. Ниже — актуальные редакторские ответы на вопросы
из обсуждений Fable, а не дословная запись прежних ответов исполнителя.
Номера сохранены для ссылок. Вопросы о завершённых миграциях и прежних дефектах удалены.
Норма — [семантика](../../docs/LMX_semantics.ru.md) и [грамматика](../../docs/LMX_grammar.ru.md);
готовность реализации отмечается отдельно в [плане v3](../../next_core_tasks_v3.md).

### А7. Каким именем отвечает поле после `S[i] := p`?

Числовая запись заменяет только указатель в выбранной ячейке массива. Она не переносит
имя или требование прежнего значения на новый адрес и не запускает допуск поля.
Последующий именованный путь интерпретирует текущее содержимое по таблице
«адрес → каноническое имя». Если записанный адрес именован j, он участвует в выборе
j; повторные вхождения требуют явного индекса. Произвольная запись void-указателя
сама по себе не обещает осмысленного именованного поля.

Structure и `Array<@>` используют одну операцию. В L2 индекс — вычисление смещения без
проверок length, знака или требования прежнего поля; в L3 проверяется итоговый индекс.
См. [сырой индекс](../../docs/LMX_semantics.ru.md#correspondence-stability) и
[индексацию](../../docs/L2_spec_ru.md#lowlevel-address).

### Б3. Как писать групповое позиционное присваивание?

Запись — `(a b c) := c, a, b` или `(a, b, c) := myFn()`.
Все правые значения вычисляются до первой записи; поля результата сопоставляются по позиции.
Слева стоят доступные места, а не объявления новых переменных или имена Structure/callable.
Видимость переменных и const последовательная.
[Групповое присваивание](../../docs/LMX_semantics.ru.md#group-assign),
[видимость](../../docs/LMX_semantics.ru.md#declaration-visibility).

Автор подтвердил написание в [журнале](../2026-11-10.md#no-structure-head), дословная выдержка:

> акутальность поддержки head в виде структуры получается исчезла -- мы присваиваем (a, b, c):=myFn() # правильно я понял?

### Б5. Меняется ли запись присваивания в генерируемом L1?

L1 остаётся отдельным промежуточным языком со [своей спецификацией](../../docs/L1_spec_ru.md).
Действующее правило L2/L3 о := не меняет автоматически синтаксис выпускаемого L1.
Перенос L1 следует за L2/L3 по общей инструкции проекта.

### В3. Как отличить короткую форму `head:` без аргументов от начала вертикальной формы?

Следующая строка более глубокого уровня открывает вертикальное тело.
Без неё `head:` — допустимый Frame с пустым телом, как `head()`.
`head: ()` и `head(())` содержат одно поле — пустую Structure.
[Грамматика §18](../../docs/LMX_grammar.ru.md#empty-colon).

### В4. Нужны ли дополнительные скобки для передачи Structure одним аргументом?

`s((a))` сохраняет одно поле-Structure в дереве P0. Парсер не раскрывает единственную
анонимную Structure и не подбирает группировку по сигнатуре.
Как вызываемое получает её поля, определяет общий контракт связывания, одинаковый
для написанной Structure и вычисленного результата merge.
[Грамматика §18](../../docs/LMX_grammar.ru.md#empty-colon),
[подача всей Structure](../../docs/LMX_semantics.ru.md#whole-arguments).

### Д5. Как записать поле операнда merge?

`merge(Model; (int: v 9))`. Форма ресивера объявляет поле v с требованием int.
`(v: 9)` объявляет Structure v и не заменяет это поле.
Совпавшее по имени и типу поле записывается в место модели, а новое дописывается
после её полей. Это контракт композиции, не выбор первого повторного имени.
[Композиция](../../docs/LMX_semantics.ru.md#composition).

### Е7. Как записать поле-ссылку в операнде merge?

`(@: p int @N\a)` объявляет место p с требованием int и кандидатом `@N\a`.
Действует общий плоский порядок «имя — требование — кандидат», без особого разбора merge.
[Объявляющие формы](../../docs/LMX_semantics.ru.md#receiver-args-only).

### М2. `int: big` при известном big — проверка значения или повтор объявления?

Голое имя в объявляющем аргументе задаёт место: в code повторное `int: big`
проверяет совместимость существующего места, не создавая второй локальной переменной.
Без RHS нового значения для записи нет. В data повтор остаётся отдельным физическим
вхождением имени. `int: (big)` потребляет выражение со значением big.
[Контракт ресивера](../../docs/LMX_semantics.ru.md#receiver-args-only).

### М4. Что означает ресивер с непредставимым числовым литералом?

Одноаргументная форма со значением, например `int: 342348523485629384569384`,
проверяет это значение; отказ приёма должен следовать общему контракту ресивера,
а не подмене литерала другим числом. Форма со значением возвращает принятое число
либо отказ, принимаемый catch.
[Контракт](../../docs/LMX_semantics.ru.md#receiver-args-only).

Отдельно в [M11](../../next_core_tasks_v3.md#m11) отмечен предел реализации:
литерал, который не вмещает ни один поддержанный числовой тип трансляции,
отвергается до исполнения. Этот предел не становится новым правилом языка
и не доказывает готовности пути отказа через catch.

### М5. Чем отличается `int: x 4294967296U` от проверки одного значения?

Здесь объявлено принимающее место x и написан кандидат. В data это описание поля;
в code ресивер получает кандидат, выполняет предусмотренный допуск/преобразование
и записывает результат в локальное место. Несовместимое значение не становится
допустимым из-за этой формы. Для известного при построении кандидата применима
первая часть допуска; проверки преобразования относятся к самому значению.
[Приём кандидата](../../docs/LMX_semantics.ru.md#admission),
[объявляющий контракт](../../docs/LMX_semantics.ru.md#receiver-args-only).
Ограничения понижения литералов отмечаются в M11 отдельно от нормы.

### О2. Присваивание в data считается вхождением имени?

Нет. `ptrToModel := ptrToKnownStruct` в data не исполняется и не объявляет
ptrToModel. До самой записи можно дойти числовым индексом. Вхождения имени
составляют корневые объявления этого имени, а не все упоминания или присваивания.
[Роли data/code](../../docs/LMX_semantics.ru.md#data-code-roles).

### О3. Повторное объявление Structure в data заменяет прежнее?

Нет. Оба объявления остаются отдельными вхождениями. При повторе имени
`S\field` неоднозначно; нужное вхождение выбирается через `S\[N]field`.
Это не повторное объявление локальной переменной в code.
[Имена и пути](../../docs/LMX_semantics.ru.md#fields).

### О4. Что означают `@: ptr Model: Other` и `@: ptr Model: 0`?

Вложенная форма Model: Other в аргументах ресивера — вызов Model.
Требование и кандидат задаются соседними полями: `@: ptr Model Other`,
а нулевой адрес — `@: ptr Model 0`.
Если Model — обычная Structure, её запуск не даёт результата для передачи в @.
[Объявляющие формы](../../docs/LMX_semantics.ru.md#receiver-args-only).

### О5. Как подать поля письма по имени?

`send: exit(exit_code := 7; stdout := ""; stderr := "")`.
Именованные фактические аргументы подаются через :=. Структурная форма
`exit_code: 7` среди аргументов читалась бы как вызов головы exit_code.
[Именованные аргументы](../../docs/LMX_semantics.ru.md#named-actuals).

### О8. Что означает data в code?

data — явная ссылка на данные запуска; `data\field` и `data\[N]field` идут
в исходный граф. `data := ptr` меняет эту ссылку для последующих явных путей,
но не уже выбранные локальные места namespace. `data()` запускает текущую data
над ней самой; `data(D)` — над D. Это вызовы, а не переобъявление или публикация данных.
[Особое имя data](../../docs/LMX_semantics.ru.md#ordinary-var),
[кадр](../../docs/LMX_semantics.ru.md#call-frame-20261115).

### О9. Где действуют объявления fn, sub, catch?

В обеих ролях: в data как объявления, в code как вызовы объявляющих ресиверов.
У callable одна входная data; вызов создаёт новый namespace.
Параметр args у call/fncall содержит actuals, а не отдельное описание входов.
Имена callable видны в обе стороны, переменные с указателями на callable — последовательно.
[Части вызываемого](../../docs/LMX_semantics.ru.md#method-parts),
[видимость](../../docs/LMX_semantics.ru.md#declaration-visibility).

### О10. Когда выполняются implements и test?

Первая, интерфейсная часть выполняется один раз для кандидата: при построении
чистого графа, если он известен, иначе при фактическом выборе во время исполнения.
test при построении не вызывается. При фактическом допуске во время исполнения
он составляет второй шаг; первый результат 0 прекращает проверки.
Завершённая первая часть не повторяется только из-за перехода к исполнению.

Сырая запись `S[n] := p` не является именованным допуском и не получает этих проверок.
Проверки преобразования числового значения сохраняют свой контракт.
[Допуск](../../docs/LMX_semantics.ru.md#admission),
[ответы о test](sol-answers-20261113.md).

### Р2. Как показывать ссылку на Structure при выводе графа?

Ссылка не превращается во вложенное лексическое дерево. `sys\toLmx` сохраняет выбранный
текущий граф, включая общие ссылки, циклы, имена и типы, так, чтобы его можно было
восстановить. Бесконечное раскрытие указуемого вместо ссылки этому не соответствует.
Для Thread сохраняются и таблицы его арены; произвольная Structure сама по себе
не означает сохранения всей арены.
[Контракт sys\toLmx](../../docs/LMX_semantics.ru.md#source-codec).

### Р3. Как обрабатывать ссылки и циклы при обходе и копировании?

Лексический обход и обход графа — разные задачи: ссылка не становится лексическим
ребёнком. merge копирует полный используемый граф с необходимыми ссылками и
лексическими цепочками; одна карта «источник — копия» сохраняет общие цели и циклы
для всех операндов. Обычные ссылки направляются на соответствующие копии.
Произвольные внешние изменяемые цели не остаются исходными только потому,
что они не были написаны вложенным поддеревом.

Исключения ровно те, что заданы общим контрактом: переиспользуемая native-реализация
и допустимая ветвь `independent: immutable`. При допуске уже посещённые пары
обрабатываются общим механизмом, без запрета циклов.
[Композиция](../../docs/LMX_semantics.ru.md#composition).

### Р6. Как запускается корень единицы?

Как Structure над самой собой: `call(root)`, то же `call(root root)`.
Для этого случая действуют общие роли data/code, namespace и повторные вхождения;
отдельных правил и обратной публикации локальных значений нет.
[Ресивер call](../../docs/LMX_semantics.ru.md#call-receivers).

### Р10. Как адресуются записи вызовов и управления в data?

Как Structure с именем своей головы: `data\if`, `data\f`, а при повторе —
путь с индексом вхождения. Запись не исполняется лишь от своего присутствия в data.
Имя вызываемого и графовая запись вызова — разные места: запись вызова метода
не создаёт второе объявление его имени в namespace.
[Имена и пути](../../docs/LMX_semantics.ru.md#fields),
[роли](../../docs/LMX_semantics.ru.md#data-code-roles).

### Р28. Что адресует `@x` формального или скрытого входа?

Собственную локальную ячейку namespace текущего вызова, ту же, которую читает голое x.
Запись через этот адрес не меняет источник связывания. После входа локальное место
независимо от последующей замены исходного поля; это не глубокая копия всех целей ссылок.
Явный путь `@(node\x)` или `@(data\x)` вычисляет свой операнд в исходном графе.

Если путь выбирает готовую ячейку, адресуется она; если вычисляемое объявление,
адресуется результат его исполнения. У @ нет отдельного правила продления жизни
значения или обязательного выделения в куче.
[Кадр](../../docs/LMX_semantics.ru.md#call-frame-20261115),
[вычисляемое поле](../../docs/LMX_semantics.ru.md#computed-field-address).

### Р21. Как вызывается обычная Structure по имени?

В code `S()` равнозначно `call(S S)`, `S(D)` и `S(data := D)` — `call(D S)`.
У запуска один необязательный аргумент data; он должен давать Structure.
Голова разрешается общим механизмом: ссылка на callable вызывает callable,
ссылка на обычную Structure запускает её. Число, нулевой адрес или неизвестное
имя не становятся вызываемыми. Запуск Structure результата не возвращает:
на месте фактического значения или операнда merge такая форма ошибочна.

В data `S()` объявляет пустую Structure, `S(D)` — Structure с полем D.
При запуске над собой действуют обе роли. Дополнительное объявление S может
дать повтор имени или выбрать собственную S вместо внешней; call с явными
данными и кодом использует те же правила без такого объявления.
`data()` также подчиняется общему запуску. Никакого ограничения `data = code`
для исполнения или native-компиляции нет.
[Структурные формы](../../docs/LMX_semantics.ru.md#forms-declare-or-call),
[роли data/code](../../docs/LMX_semantics.ru.md#data-code-roles).

Для явной подачи actuals предусмотрены call(args data code) и fncall(args data return code),
а также четыре сокращения из [общего контракта](../../docs/LMX_semantics.ru.md#call-receivers).
args — та же Structure поданных значений, что у обычного вызова; data описывает входы.
Интерпретатор не выделяет для этих форм отдельный исполнитель.

### Р27. Один ли парсер внутри всех скобок и что делать с потерянной скобкой?

Круглые, квадратные и фигурные скобки используют один P0 с общими правилами
уровней, комментариев, вложенных форм и трейлеров. Непарная закрывающая скобка
в разбираемом коде — ошибка; защищённый текст подчиняется своему обычному контракту.
Ошибка Mix внутри строки не делает ошибочной всю строку.
[Грамматика §14](../../docs/LMX_grammar.ru.md#bounded),
[Mix](../../docs/LMX_grammar.ru.md#mix), [ответы о парсере](parser-forms-answered-20261111.md).

### Р29. Где пишется ресивер `required` и где он действует?

Слова автора 2026-11-16 и вывод исполнителя по его поручению ([журнал](../2026-11-16.md#required-anywhere),
[вопрос и ответы](required-anywhere-answered-20261116.md)). По словам автора: `required` пишется где
угодно и в любом объявлении, как `private:`; `required: (int: a)` в заголовке и строка `required: a` в
коде — разные пути к одной проверке; возможны все сочетания (в `data` и в `code`, пометкой объявления и
строкой с именем поля) и любое число проверок одной переменной. В `data` запуска поле сначала
заполняется аргументами, и если значения ему не досталось — ошибка; в `code` проверка выполняется на
той же строке. Отдельного прохода «все `required`» нет: при входе в вызываемое нет ходов инициализации,
кроме подачи аргументов. Первое чтение исполнителя, оставлявшее только строку в коде, автор отверг.
Вывод исполнителя из слов «правила видимости `required` изменить не может»: пометка срабатывает только
там, где её объявление само действует — как входное место запуска или как достигнутая запись кода;
помеченное поле остаётся видимым и доступным по общим правилам — лексически, динамически и по явному
пути, — и тот, кто получил его по этим правилам, пометкой не проверяется; строка `required: a` не видит
переменную, объявленную ниже, и имя ветви после выхода из неё; проверка однократна.
[Ресивер `required`](../../docs/LMX_semantics.ru.md#required-receiver),
[ресивер private:](../../docs/LMX_semantics.ru.md#private-binding),
[видимость](../../docs/LMX_semantics.ru.md#declaration-visibility).

### Р30. К чему относится «все аргументы необязательны»?

Чтение исполнителя к решению автора 2026-11-16 ([слова автора](../2026-11-16.md#optional-inputs-required)),
не слова автора. Слово «все» относится к объявленным входным местам `data`: вход без значения,
которому не подано значение, вызову не отказывает и держит «T без инициализации». Правило о
неразрешённом свободном имени не меняется: динамический вход без источника по цепочке активаций
и без лексического источника по-прежнему делает вызов недопустимым. Проверка формы вызова
наличие значений у объявленных входов не проверяет; инициализацию данного поля проверяет `required`.
[Ресиверы `call` и `fncall`](../../docs/LMX_semantics.ru.md#call-receivers),
[динамические входы](../../docs/LMX_semantics.ru.md#dynamic).

### Р31. Каким отказом отказывает `required`?

Чтение исполнителя к решению автора 2026-11-16 ([слова автора](../2026-11-16.md#optional-inputs-required)),
не слова автора. В `data` запуска — отказом допуска входа при подаче аргументов, до первой записи
`code`; в `code` — отказом достигнутой записи на её строке. Точный вид отказа уточняется при
реализации и помечен в плане как OPEN ([M10](../../next_core_tasks_v3.md#m10)).
[Ресивер `required`](../../docs/LMX_semantics.ru.md#required-receiver).

### Р32. Что делает чтение входа без значения в теле?

Чтение исполнителя к решению автора 2026-11-16 ([слова автора](../2026-11-16.md#optional-inputs-required)),
не слова автора. Вход без значения и без поданного actual держит «T без инициализации»: начальное
значение не обещано, проверки эти байты не читают и не требуют ни нуля, ни случайности, ни особой
ошибки. Чтение такого входа не отказывает и не даёт обещанного значения; инициализацию проверяет
только явный `required`. Фикстура поэтому не закрепляет прочитанное значение: наблюдаемы проход
вызова, тип места `uninit:T` и значение, записанное в теле.
[Примитив, §3.2](../../docs/kernel-implementation.ru.md#primitive-storage),
[ресивер `required`](../../docs/LMX_semantics.ru.md#required-receiver).

### Р33. Возвращает ли откат построения ячейки, выданные из прежних чанков?

Решение исполнителя по ходу [M15](../../next_core_tasks_v3.md#typed-value-records), не слова автора.
Нынешний `revert` освобождает куски, присоединённые после метки, но не возвращает ячейки, выданные
после неё из уже существовавших чанков: на путях отказа `merge` и копии они остаются занятыми до
освобождения куска. Это утечка, не порча памяти. До шага6 M15 она остаётся: снимок хвостов всех
пулов с диапазонным снятием имён, связей и контекстов был бы работой на выброс. Шаг6 переводит метку
на пару «кусок, смещение», а в этапе2 откат становится усечением потока.

### Р34. Где записан признак «хранилище Structure — адресная таблица», если тип не узнаётся по адресу?

Решение исполнителя по ходу [M15](../../next_core_tasks_v3.md#typed-value-records), поправленное автором в тот же
день. Адресная таблица — приём нынешнего ядра (`lmx_graph_fields_bind`): когда Structure собрана из слотов, уже
существующих в других местах и лежащих не подряд, её `storage` указывает на блок адресов этих слотов, а не на
собственные слоты. Сегодня читатель слота узнаёт это классификацией адреса хранилища (пул FIELD_ADDRESSES).
Плотное хранилище кодов не несёт, поэтому признак переносится в запись заголовка: Structure с адресной таблицей —
отдельный код типа, и операция ядра, меняющая форму хранилища, в том же действии пишет соответствующий код.

Первый вариант этого ответа вводил отдельный бит в слове кода и правило «код записи после создания не меняется».
Автор: «зачем тебе снимать и выставлять биты если есть 4 млрд кодов для 4 млрд типов? … Тип то просто любой
удобный тип». Бит, маски и правило сняты: различие, нужное ядру, выражается отдельным кодом типа. `sys\typeof`
для такой Structure отвечает кодом обычной через общий перевод «код → тип»: форма хранилища программе не видна.
Нужна ли адресная таблица после норм M14 о независимых локалах без write-back — отдельный вопрос упрощения, не решён.

### Р35. Почему после запуска графовой фикстуры дамп корня не меняется, и что делать с такими фикстурами?

Решение исполнителя по [базовому прогону чистого графа](../../steps/witnesses/m10-path-leaf-20261116/notes.md)
среза411. Из205 непроходящих графовых фикстур в127 интерпретатор отвечает0, а дамп после запуска совпадает с дампом
до запуска: объявления верхнего уровня корня (`int: t_cell typeof(@i)`) остаются выражениями. Это не дефект, а
действующая норма: [кадры `data` и `code` не публикуются в граф](../../docs/LMX_semantics.ru.md#flush-receiver-contract),
исходный граф меняют только явные операции. Объявление в коде корня — локал исполнения; обратной записи в
определение нет. Коммит b901f2bf (2026-11-15) это реализовал и добавил фикстуру нового вида
`tests/graph/call_frame_local`, но прежние фикстуры, закреплявшие опубликованные значения, не перевёл: их принимали
короткими списками.

Такие фикстуры переводятся на явное наблюдение по образцу `call_frame_local`: блок данных корня с наблюдаемыми
местами и явная запись результата через путь. Логика фикстуры и прежние закреплённые значения сохраняются; значение,
которое запуск после перевода даёт иным, — находка, а не повод менять ожидание. Фикстуры, наблюдавшие то, что без
публикации явной записью не выражается, разбираются поимённо. Остальные78 (ненулевой ответ интерпретатора) под эту
причину не подводятся и разбираются отдельно: отменённая форма, дефект или иной код отказа.

### Р36. Решения по разбору графовых фикстур: что остаётся отказом, что читается, что неоднозначно

Решения исполнителя по ходу разбора [базового прогона чистого графа](../../steps/witnesses/m10-path-leaf-20261116/notes.md);
вопросы поставил sonnet наблюдаемыми вариантами, каждое решение выведено из записанной нормы.

1. **Чтение вычисляемого места по явному пути исполняет написанное выражение объявления** — не отказ.
   `main\data\h` при `@: h Box` и `main\data\seven` при `int: seven get()` сейчас отвечают5 («срез не исполняет»);
   по [норме кадра вызова](../../docs/LMX_semantics.ru.md#call-frame-20261115) чтение вычисляемого места идёт общим
   механизмом, без публикации и без кеша. В чистом графе это не реализовано и для int; правка шага пути — в
   графовом срезе.
2. **`call(D s)` особого правила не получает.** [Callable — просто Structure](../2026-11-16.md#callable-is-structure):
   тело `s` над `D` пишется `call(D s\code)`; фикстуры, писавшие `call(D s)` ради тела, переводятся, ядро под них не
   меняется. Что даёт исполнение самой `s` с её data-группой, не закрепляется.
3. **Запись в имя объекта-функции отказывает.** После `fn: x prepared` запись `x := touch()` — не присваивание
   указателю-переменной: [имена Structure не присваиваются](../../docs/LMX_semantics.ru.md#colon-declares). Ответ0
   после b901f2bf — потерянная проверка; возвращается в общем пути места присваивания.
4. **Объявление кода над местом поданных данных — повторное объявление с общим допуском**, а не свой затеняющий
   локал: своими для вызова становятся только места code, которых нет во входных данных. Проверка не потеряна:
   фикстуры запускали `Types\data`, где объявлений кода больше нет; перевод на `Types\code`.
5. **Голое имя с двумя вхождениями в данных запуска неоднозначно** — ответ3, как у пути `data\x`: поиск имени один,
   у `fn` одна входная data, приоритета формала над собственным полем нет. Сейчас общая ветка неоднозначности
   гасится флагом, и молча читается последнее вхождение (переданное значение теряется) — правка в графовом срезе.
6. **Удержанная ссылка на функцию.** По записанной модели ([спецификация ядра](../../docs/kernel-implementation.ru.md),
   состояние среза390) место `@: held leaf` заполняется при построении ссылкой на F обхода построения со своей data;
   исполнение создаёт для голого имени другую F; ссылки одного обхода делят одну F. Прежние закреплённые 3 и 4 —
   след отменённой публикации; новые ожидания выводятся из модели и закрепляются только при точном совпадении запуска.
7. **`node` в коде самого корня не определён** (пространство над методом; корень не метод): поле корня из кода корня
   читается `data\имя`, из метода корня — `node\имя`. Первое правило перевода, данное исполнителем haiku без
   сверки с книгой, было неверным и исправлено по пробам sonnet.

### Р37. Как переводятся фикстуры полного набора, закреплявшие публикацию кадров и блок `var`, и что входит в срез

Решения исполнителя для перевода красных фикстур полного набора (черновики — haiku, сборка и замеры — sonnet,
срез414); каждое выведено из записанной нормы. Логика фикстуры и закреплённые значения сохраняются; значение,
которое запуск даёт иначе, — находка, ожидание под запуск не подгоняется.

1. **Место, объявленное в коде вызываемого, принадлежит вызову.** Проверки, читавшие или писавшие его снаружи
   через `X\var\имя`, и проверки обратной записи снимаются вместе с якорем, на который ссылались:
   [кадры не публикуются](../../docs/LMX_semantics.ru.md#flush-receiver-contract), локальное присваивание обратно
   не записывается ([кадр вызова](../../docs/LMX_semantics.ru.md#call-frame-20261115)). Поле собственных данных,
   объявленное в заголовке, читается `X\data\имя`.
2. **Эффект, наблюдаемый в данных снаружи, пишется явным путём** `data\имя := …`. Вычисляемое объявление, которое
   фикстура наблюдала снаружи как исполненное, становится литеральным объявлением и явной записью.
3. **`var` заменяется на `data` только в резервном значении** — явная ссылка на данные текущего запуска
   ([резервное имя](../../docs/LMX_semantics.ru.md#ordinary-var)). Дочерний блок с именем `var` в обычной Structure —
   обычное имя: в `data` он не переименовывается; если Structure запускается над собой, его места переносятся в
   неё саму ([ресиверы `call` и `fncall`](../../docs/LMX_semantics.ru.md#call-receivers): часть внутри поданной
   Structure не выбирается).
4. **Порядок операндов один: `call(data code)`.** Рабочий frontend до среза416 читает двухоперандный `call` в
   прежнем порядке (код первым) — открытый пункт M10; порядок в текстах фикстур меняется одним срезом вместе с ним.
   `Box: ([]: int items 2)` пишется `Box: []: int items 2` — единственная Structure в хвосте не раскрывается
   ([объявление Structure](../../docs/LMX_semantics.ru.md#colon-declares)).
   Запись значения-формы становится присваиванием `:=` только там, где слева известное место примитива или
   указатель-переменная: имя Structure и имя функции слева от `:=` не стоят, неизвестная левая часть — ошибка
   ([запись в известное место](../../docs/LMX_semantics.ru.md#assign-known)). Первое указание исполнителя —
   писать `Outer\Empty := ()` и `t := (int: x 2)` — было дано без сверки с этим правилом и отменено по разбору
   opus: фикстура, писавшая в имя Structure, объявляет записываемое место указателем-переменной `@:`, а проверка,
   у которой нет законного чтения, снимается как отменённая посылка.
5. **Запись через адрес локала видна голому имени.** В `free_pointer_paths` проверки98 и99 ждали прежние5 и7U
   после `bump()`, пишущего через свободный указатель на локал вызывающего; по норме `@x` адресует ту же локальную
   переменную, которую читает и меняет голое `x`
   ([унарное `@`](../../docs/LMX_semantics.ru.md#method-reference-assignment)), поэтому ожидания —6 и8U. Изменение
   выведено из текста фикстуры и нормы до запуска; запуск его подтвердил в обоих исполнителях.
6. **В дерево входит только фикстура, зелёная во всех режимах.** Переведённый черновик, оставшийся красным, в
   срез не кладётся и остаётся прежним текстом до разбора причины; его ожидания не меняются.
7. **Правка без свидетеля в срез не входит.** Установка кода типа у рабочего Value после записи во время
   исполнения (правка «B» среза414) снята: мутант без неё дал построчно те же полный набор и графовый список.
   Для локалов-чисел и указателей таблицы ядра тип задаёт привязка по хранилищу; для ссылки на Structure и
   внешнего C-указателя вопрос решается вместе с шагом2 M15 (код перед значением), где есть свидетель.

### Р38. Когда запись `:=` в имя, которого нет в тексте обычной Structure, — ошибка?

Решение исполнителя к срезу417; механизм предложил opus по трассе красных черновиков. Программа:

```
VarNewData:
    int: i 5
    int: got 0
VarNew:
    got := data\i
call(VarNewData VarNew)
```

Наблюдаемые варианты: (а) трансляция отказывает — левая часть `got` в тексте `VarNew` не объявлена (так
сейчас); (б) вызов исполняется, `got` — место вызова, после записи оно равно5.

Ответ — (б). Namespace вызова собирается из объявлений корней `data` и `code`, голое имя — локал вызова
([кадр вызова](../../docs/LMX_semantics.ru.md#call-frame-20261115)). У обычной Structure данные даёт запуск,
поэтому при трансляции её текста корни данных неизвестны: имя, которого нет в тексте, становится скрытым входом
— при записи так же, как уже при чтении. Известно ли место, решается на входе: сначала корневые объявления
данных своего вызова, затем привязки вызывающих. Если источника нет, вызов недопустим — это и есть «неизвестная
левая часть — ошибка»: запись `:=`, перенесённая в контекст, где такого места нет, получает ошибку
([запись в известное место](../../docs/LMX_semantics.ru.md#assign-known)). Запись меняет локал вызова; обратной
записи нет.

Следствия:

1. Строки отказа трансляции `assign_in_structure_refused` и `assign_typed_unknown_structure_refused` (`zz := 5` в
   теле обычной Structure) закрепляли прежнее чтение. Фикстуры переводятся на запуск с пойманным отказом входа.
2. У `fn`, `sub`, `catch` и корня единицы данные свои и известны при трансляции: отказ трансляции для записи в
   имя без места остаётся (`assign_unknown_refused`, `assign_typed_unknown_refused`,
   `assign_typed_unknown_root_refused`). Этот срез его не пересматривает.
3. Поиск свободного имени идёт одной дорогой для запуска `call`, вызова через место callable, `fn` и обходчика:
   корни данных своего вызова спрашиваются первыми. Отдельной ветви под вид вызова нет.

### Р39. Решения по второму разбору чистого графа (остаток 89 красных)

Решения исполнителя по разбору sonnet (одиночные прогоны на рабочем наборе среза415); каждое выведено из
записанной нормы.

1. **Удержанная функция: поправка к Р36, пункт 6.** Там сказано, что прежние закреплённые 3 и 4 — след отменённой
   публикации. Это неверно. Строки закреплены с двумя прогонами на одном построенном графе. F обхода построения,
   на которую ссылаются места `@: p f` и `@: q f`, живёт в построенном графе и переживает прогоны; F исполнения
   для голого имени создаётся заново при каждом входе в блок корня
   ([реализация, срез383](../../docs/LMX_semantics.ru.md#declaration-visibility)). Для

   ```
   fn: f () int (int: n 0)
       data\n := data\n + 1
       return: data\n
   @: Hold (@: p f; @: q f)
   bare1 := f()
   held1 := Hold\p()
   bare2 := f()
   held2 := Hold\q()
   ```

   первый прогон даёт 1, 1, 2, 2, второй — 1, 3, 2, 4; дамп после второго равен прежнему закреплению и совпадает
   во всех трёх исполнителях. Ожидания черновика (1, 1, 2, 2) были выведены для одного прогона. Расхождения
   исполнителей нет: при явном наблюдении интерпретатор, native и forced дают один дамп.
2. **Индексная запись в слот не проверяет прежнее содержимое.** `slot_context_reset` закрепляла отказ4 для
   `Holder\Slots[0] := @j` после `Holder\Slots[0] := Holder\B`. Книга: «`S[i] := p` записывает туда другой
   `void*`. Никакого требования бывшего поля, его имени или вида ячейки эта операция не проверяет и не переносит»
   ([индекс Structure](../../docs/LMX_semantics.ru.md#structure-index)). Закрепление меняется на ответ0 и дамп
   после второго прогона.
3. **Structure рядом с одноимённым местом в данных — второе вхождение имени**, а не «оператор над этим местом»:
   в данных структурная запись объявляет, повторное объявление — ещё одно вхождение, которое без индекса не
   адресуется ([роли `data` и `code`](../../docs/LMX_semantics.ru.md#data-code-roles)). Голое имя с двумя
   вхождениями отвечает3 и тогда, когда в коде объявлен одноимённый локал (продолжение Р36, пункт 5).
4. **Запись ссылки по пути в объявленное `@:`-место, которое ещё не держит значения, законна**: слева стоит
   указатель-переменная ([запись в известное место](../../docs/LMX_semantics.ru.md#assign-known)). Вид места
   берётся из его объявления; отказ4 остаётся для записи в не-место.
5. **Чтение вычисляемого поля по пути исполняет выражение при каждом чтении** (Р36, пункт 1). Фикстура, которой
   нужно одно значение, читает поле один раз в локал.
6. **Бесконечный цикл `computed_body_loop` — в тексте фикстуры**: счётчик `calls := calls + 1` — локал вызова, и
   условие `calls < 3` всегда истинно. С `data\calls` в записи и в чтении программа завершается с закреплённым
   значением.
7. **Ссылочное место создаёт построитель, а не первая запись в него.** `@: name`, типизированная форма без
   кандидата и `@: name 0` («явный нулевой кандидат»,
   [ссылка на метод](../../docs/LMX_semantics.ru.md#method-reference-assignment)) при построении дают ссылочную
   ячейку, как `@: name: int` и как объявление со значением. Создавать ячейку при записи по пути — заплата у
   одного потребителя: чтение по пути, `sys\typeof` и `@(data\p)` потребовали бы того же. Этим пункт4 уточняется.
8. **Голова формы — вычисляемое ссылочное место, указывающее на число** (`deferred_reference_head_refused`):

   ```
   @: D (int: x 40; @: p int data[touch()]; int: before 0)
   @: Code (before := 1; p(); before := 2)
   call(D; Code)
   ```

   Варианты: (а) ответ5, `touch()` не исполнялась — прежнее закрепление; (б) ответ8, `touch()` исполнилась один
   раз; (в) ответ3. Ответ — (б): чтение вычисляемого места исполняет написанное выражение
   ([кадр вызова](../../docs/LMX_semantics.ru.md#call-frame-20261115)), а «число или пустая ссылка не становятся
   вызываемыми» ([структурные формы](../../docs/LMX_semantics.ru.md#forms-declare-or-call)).

### Р40. Что делает объявление в корне кода обычной Structure, запущенной над другими данными?

Решение исполнителя к срезу420; слои и нынешнее поведение измерил opus на принятом наборе среза416+417. Три
программы; наблюдение — явной записью в поле корня.

Первая — имени в данных нет:

```
int: seen 0
D:
    int: a 1
S:
    int: v 5
    node\seen := v
call(D S)
```

Наблюдаемые варианты: (а) вызов отказывает, потому что в `D` нет `v` (так сейчас; по режиму запуска это
необработанный отказ `call`, нативное «a split-called code reached data without its place row» или INVALID
обходчика); (б) вызов исполняется, `v` — локал вызова, `seen` равно5, поля `v` у `D` не появляется.

Ответ — (б). «Корневые объявления D дают входные места, корневые объявления C — остальные местные места»;
«code-локалы не обязаны иметь соответствие в исходной data … это не проверка обязательного наличия всех
code-локалов в D» ([части метода](../../docs/LMX_semantics.ru.md#method-parts)); «Собственные места code, которых
нет во входных данных, принадлежат текущему вызову, а не дописываются в исходную data»
([кадр вызова](../../docs/LMX_semantics.ru.md#call-frame-20261115)).

Вторая — имя объявлено в данных со значением, в коде без значения:

```
int: seen 0
D:
    int: x 7
S:
    int: x
    x := x + 1
    node\seen := x
call(D S)
```

Наблюдаемые варианты: (а) `x` в `S` — ячейка `D`: после вызова `D\x` равно8; (б) `x` — локал вызова, взявший
на входе значение7: `seen` равно8, `D\x` остаётся7; (в) вызов недопустим. Сейчас native отвечает (в): его
локал без значения не получает значение данных на входе. У объявления со значением записи сквозь голое имя в
данные нет ни в одном исполнителе (пробы opus: `x := x + 5` в `S` над `D` оставляет `D\x` прежним).

Ответ — (б). «Голое `x` и `@x` относятся к локальному месту текущего вызова. … Локальное присваивание не
записывается обратно. `data\x` и `code\x` обращаются к исходному графу»
([кадр вызова](../../docs/LMX_semantics.ru.md#call-frame-20261115)). Запись в данные пишется явно:
`data\x := x`.

Третья — имя объявлено и в данных, и в коде со значением:

```
int: seen 0
D:
    int: v 1
S:
    int: v 5
    node\seen := v
call(D S)
```

Наблюдаемые варианты: (а) `seen` равно1 — достигнутое объявление кода ничего не присваивает, читается ячейка
данных (так сейчас); (б) `seen` равно5, `D\v` остаётся1.

Ответ — (б). Повторное объявление уже видимого имени в коде «сохраняет RHS, допуск и присваивание этому месту»
([части метода](../../docs/LMX_semantics.ru.md#method-parts)): локал на входе берёт1, достигнутое `int: v 5`
присваивает ему5; объявление без значения только проверяет.

Два корневых объявления одного имени в данных входа не дают: свободное голое имя неоднозначно, как `data\x`.

Следствие для реализации. Требование, чтобы данные содержали места таблицы кода (допуск запуска, допуски вызова
в обходчике, нативная входная проверка кода split-вызова), и адресация мест кода в данных (таблицы мест кода в
native, перевод собственного места кода в слот данных в обходчике) — отменённое обслуживание; оно удаляется
целиком, сужающих проверок взамен не вводится. Обычный допуск поданного входа по типу остаётся: «Контракты
fn/sub и обычный допуск поданных входов сохраняются». Срез420 идёт двумя измеренными шагами: сначала «имя,
которого нет в данных, — локал вызова» и значение входа для локала без значения, затем снятие таблицы мест и
присваивание достигнутого объявления. Фикстуры, наблюдавшие значение в данных после голой записи, переводятся на
явную запись `data\x := x`; закреплённые значения меняются только там, где они записывали отменённое
поведение, каждое — с причиной в таблице свидетельства.

Типизированная запись `zz := int: 5` в коде обычной Structure читается так же, как нетипизированная (Р38): `:=`
ничего не объявляет ([запись в известное место](../../docs/LMX_semantics.ru.md#assign-known)), цель — скрытый
вход, место решается на входе.

Форма с двоеточием в коде остаётся вызовом головы и при переводе фикстур в запись не превращается: `got: data\i`
при известном месте-числе `got` — ошибка ([структурные формы](../../docs/LMX_semantics.ru.md#forms-declare-or-call)),
и фикстура place_write_form закрепляет именно пойманный отказ.

Кадр `:=` в роли данных — не голова имени: «в данных … запись `:=` не исполняется и остаётся полем, до которого
доходят индексом» ([запись в известное место](../../docs/LMX_semantics.ru.md#assign-known)). Поэтому у Structure с
корнем `int: x 2` и строкой `x := 4` одно корневое объявление `x`: голое `x` и `data\x` однозначны. Счёт корневых
голов рабочего frontend, принимавший такой кадр за второе вхождение имени (правило среза276), в этой части
отменён; до самого кадра по-прежнему доходят индексом. Запись вызова и управляющие формы (`if`, `for`) в роли
данных остаются Structure, названными своей головой ([роли `data` и `code`](../../docs/LMX_semantics.ru.md#data-code-roles)):
их головы счёт сохраняет.

ответил fable, 2026-11-17.

### Р41. У какого вызова спрашивается обязательство `throws`, и что остаётся в данных после отказа формы над числом?

Решения исполнителя к срезу418+419; оба случая нашёл прогон sonnet.

Первое — приём числа машиной:

```
int: i 3
size_t: n 0U
n := i
```

Запись исполняет приём `int` в `size_t`; обходчик делает его вызовом преобразователя ядра, у которого записано
`throws: range`. Наблюдаемые варианты: (а) присваивание отказывает `implements` — у вызываемого есть `throws`, а
`catch: range` в программе нет; (б) присваивание исполняется, `n` равно3; при значении, которое тип не
принимает, возникает неявный `convert`.

Ответ — (б). Обязательство относится к вызову, записанному в программе: «Вызывающее выражение должно
предоставить `catch` для каждого такого имени либо объявить его в собственном `throws`. Вызов без одного из этих
способов обработки отвергается». Приём — оператор машины: «Операторы языка, у которых программист не видит
явного перечисления `throws` … тоже бросают именованный отказ, но отлавливать его не обязательно»
([объявленные отказы](../../docs/LMX_semantics.ru.md#exceptions)); «несовпадение типов в операции или при
приёме — неявное исключение `convert` … а не молчаливое приведение»
([динамические входы](../../docs/LMX_semantics.ru.md#dynamic)). Поэтому `call` обходчика спрашивает обязательство
выбранного кода на обеих дорогах (`call: fn` и `call(D C)`), а у преобразования и приёма не спрашивает; это не
сужение проверки, а её предмет.

Второе — уточнение к Р39, пункт8:

```
@: D (int: x 40; @: p int data[touch()]; int: before 0)
@: Code (before := 1; p(); before := 2)
call(D; Code)
```

Ответ запуска —8, `touch()` исполнена один раз (Р39, пункт8). Наблюдаемые варианты для дампа `D` после отказа:
(а) `before 1` — запись до формы `p()` дошла до данных; (б) `before 0`.

Ответ — (б). `before := 1` в коде — запись в голое имя, то есть в локал вызова: «Локальное присваивание не
записывается обратно» ([кадр вызова](../../docs/LMX_semantics.ru.md#call-frame-20261115)); в данные пишет только
явный путь `data\before := 1`. Закрепление фикстуры deferred_reference_head_refused меняется с5 на8, счётчик
`calls` в её ожидаемом тексте — на1, `before` остаётся0.

ответил fable, 2026-11-17.

### Р42. Решения по третьему разбору чистого графа (остаток62 красных, неположенные черновики)

Решения исполнителя по двум разборам sonnet (одиночные прогоны графового инструмента среза418+419; ответы те же
на инструменте среза416+417). Каждое выведено из записанной нормы; вопросов автору в этом разборе нет. Два
решения первой редакции (пункты2 и3) поправлены замерами sonnet до записи.

1. **Слот, в который записан адрес локала вызова, по имени не закрепляется; фикстуры пишут `@data\j`.**

   ```
   sub: main () (int: j 40; S: int: a 1; int: seen 0)
       S[0] := @j
       seen := S\j
   ```

   Наблюдаемые варианты: (а) 40 — так закреплено в struct_index, struct_index_admit и slot_atom_replace;
   (б) ответ3, а 40 даёт запись `S[0] := @data\j`. Сейчас исполняется (б). Три фикстуры написаны до
   [кадра вызова](../../docs/LMX_semantics.ru.md#call-frame-20261115): «Голое `x` и `@x` относятся к локальному
   месту текущего вызова», а «Внешнее место адресуется явно, например `@(node\x)`»
   ([ссылка на метод](../../docs/LMX_semantics.ru.md#method-reference-assignment)). Закреплённые 40 и 41 — значения
   поля данных, и фикстуры переводятся на `@data\j` с явным наблюдением. Что отвечает по имени слот, держащий
   адрес локала активации, не закрепляется: «Взятие адреса не продлевает срок жизни ячейки», «Имя и тип
   определяются при последующей интерпретации текущего содержимого»
   ([индекс Structure](../../docs/LMX_semantics.ru.md#structure-index)) — это следствие общих механизмов, числа
   такому случаю не назначается ([журнал](../2026-11-16.md#receiver-creates-structure)). Ядро не меняется.
2. **Structure, запущенная над собой, с двумя корневыми объявлениями одной переменной: голое имя — ответ3.**

   ```
   Self: (int: x 2; int: x 3; int: seen 0; x := x + 1; data\seen := x)
   call(Self Self)
   ```

   Варианты: (а) `seen` равно4 — молча взято последнее вхождение (так сейчас, и так же при `call: Self` и при
   `call(Args Self Self)`); (б) ответ3. Ответ — (б): «Общий выбор вхождений действует и для одноаргументного
   `call: code` и равной ему записи `code()`, которые исполняют код над самим собой: при нескольких исходных
   корневых объявлениях одной переменной в таком коде нельзя молча выбрать первое. Обращение из кода к этой
   переменной без индекса вхождения — ошибка», «Общие правила повторных вхождений, роли data/code и допуска
   действуют также при запуске над собой; отдельного исполнительного пути нет»
   ([части вызываемой Structure](../../docs/LMX_semantics.ru.md#method-parts)). При раздельном коде
   (`call(Self Code)`) ответ3 уже исполняется (Р36, пункт5). Закрепление declaration_site_formal_self
   («голое имя выбирает формал», `seen` 6) меняется на отказ3: отдельного формала у запуска нет, `args`
   передаёт значения единой `data`. С одним `x` в `Self` ответ0 и `seen` равно6.
3. **`merge`: совпавшее поле пишется в слот модели, ссылки переводятся на копии; чтение вычисляемого места по
   пути исполняет `merge` заново.** Решает [композиция](../../docs/LMX_semantics.ru.md#composition) и
   [кадр вызова](../../docs/LMX_semantics.ru.md#call-frame-20261115).
   - `@: R merge(M; N)`, где обе объявляют `int: a`: «Поле более позднего операнда…, совпадающее с полем
     модели…, записывается **в слот модели**, а не добавляется рядом». Замер: у результата одно `a` — норма
     исполняется.
   - `@: R merge(...)` в данных — вычисляемое объявление. `data\R\a := 9`, затем чтение `data\R\a`
     даёт значение операнда, а не9: каждое чтение по пути исполняет написанное выражение (Р36, пункт1; Р39,
     пункт5), запись ушла в результат предыдущего исполнения. Ядро право; закрепления merge_reference (9, 7,9)
     старше кадра вызова. Фикстура держит результат в локале (голое `R` в коде — одно исполнение) и пишет и
     читает через него; тогда 9 и7 свидетельствуют следующее правило.
   - Операнд `(@: p int @N\a)` рядом с операндом `N`: «Ссылка внутри копируемого графа не создаёт отдельного
     экземпляра своего указуемого. Она переводится через ту же карту на экземпляр, уже полученный копированием» —
     `p` указывает на `a` результата.
   - `@: copied merge(hold\data)`, где `hold` держит ссылки на `leaf` и её данные: «ссылки результата
     указывают на соответствующие копии, а не на исходный граф». Запись через `copied\payload` исходную
     `leaf\data` не меняет; закрепление copy_held_state (original3, next4) верно. Сейчас все четыре ссылки
     копии указывают в исходный граф, и так же в примере самой книги (`@: R merge(Model; Holder)`) — дефект ядра.
4. **Целый аргумент с полем, которое объявлено без значения и записано позже.** После `P\a := 5` вызов
   `mytest(P)` отвечает4. Место после записи держит значение, вызов принимает Structure целиком
   ([целые аргументы](../../docs/LMX_semantics.ru.md#whole-arguments)) — дефект ядра. Отказ4 у
   `merge(mytest\data; …)` — тот же дефект, а не свойство `merge`.
5. **Запись по явному пути в поле с вычисляемым объявлением заменяет объявление значением.** `data\x := 12` над
   `int: x touch()` отвечает4. «`data\fptr := 0` меняет исходное поле так, чтобы оно читалось как `@: fptr 0`»
   ([кадр вызова](../../docs/LMX_semantics.ru.md#call-frame-20261115)): после записи поле читается как

6. **`fncall` с четырьмя операндами работает**; ответ5 в черновиках call_named и call_receivers давало то, что
   данные запуска не объявляют места для поля `args`: «Имена членов `args` обозначают входы из D»
   ([ресиверы `call` и `fncall`](../../docs/LMX_semantics.ru.md#call-receivers)). Ошибка модели черновика.
7. **Целый callable в роли кода и `return: значение` под `call` фикстуры не закрепляют** (Р36, пункт2): тело
   над другими данными пишется `add\code`, тело функции с результатом запускается
   `fncall(Data int method\code)`. Доходит ли формал callable до его кода над чужими данными, не закрепляется;
   фикстура, которой нужен такой вход, объявляет его в поданных данных.
8. **Атом, называющий место, ведёт к этому месту.** В `Pair: i Model later` атом `i` и поле `i` корня — одна
   ячейка: после `main\data\[1]Pair\i := 9` чтение `data\i` в коде корня даёт9
   ([объявление Structure](../../docs/LMX_semantics.ru.md#colon-declares)); голое `i` после `i := 6` — локал
   запуска корня, 6. Закрепление declare_forms разделяет поле и локал.
9. **Остальные расхождения черновиков с прогоном — ошибки модели черновика**, ядро не меняется: запись в голое
   имя — локал вызова (control_flow, whole_arguments); метод корня читает поле корня как `node\имя`
   (control_flow, finally_scope); `data` внутри метода — данные метода (slot_context_reset); имя будущего
   локала до строки объявления не видно (sub_calls).
10. **reference_model_refused откладывается до среза420**: объявление кода над местом поданных данных там
    переделывается (Р40), закрепление выводится после него.

### Р43. Как читаются две записи `merge` после уточнения автора 2026-11-17?

Уточнение автора — [журнал](../2026-11-17.md#merge-two-forms): два `merge` различаются наличием присваивания
слева. Первое чтение исполнителя автор поправил в тот же день; ответ автора записан ниже, норма — в книге.

```
A: int: x 1
fn: B () @ (...)
@: T
T := merge(A; B())
S: merge: A B()
```

**В данных.** Запись `T := merge(A; B())` не исполняется, как всякое присваивание: «Присваивания `:=` и весь
прочий код в данных не исполняются; присваивание остаётся полем, до которого доходят индексом»
([роли `data` и `code`](../../docs/LMX_semantics.ru.md#data-code-roles)). Места данных получают значения из
своих объявлений и из поданных аргументов; явная запись по пути `data\x := …` — действие кода, а не данных.

Для записи `S: merge: A B()` наблюдаемые варианты: (а) `S` объявлена композицией: `S\x` равно1, а `B()` —
вызов `B`, исполняемый при работе ресивера; (б) `S` объявлена композицией, но `B()` читается по роли данных —
объявляет внутри пустую Structure `B`, ничего не вызывается; (в) `merge` в данных не действует: в `S` лежит
Structure с именем `merge`, путь `S\x` ошибочен, поле достигается как `S\merge\A\x`.

Первое чтение исполнителя было (а): аргументы всякого ресивера читаются как код. **Ответ автора — (б)**
([журнал](../2026-11-17.md#merge-data-form-no-calls)): «для data нужно обязательнто назвать объявляемую структуру ,
как обычно через двоеточие, и тогда внутри такого merge _нет вызовов_, только объявления структур. Тогда этт
будет общее првеление». В данных `S: merge: A B()` объявляет `S` композицией; операнд-слово `A` называет известную
Structure, операнд-форма `B()` объявляет Structure `B` по общему правилу данных; ничего не исполняется. Так
запись в данных подчиняется общему правилу роли: «В роли `data` структурная запись объявляет Structure — какой
бы ни была её голова» ([роли `data` и `code`](../../docs/LMX_semantics.ru.md#data-code-roles)). Следствие
(чтение исполнителя): вычисляемого в такой записи нет, поэтому композиция строится вместе с готовыми
объявлениями при построении чистого графа, без вызовов программы.

**В коде.** `merge` — ресивер, аргументы которого ведут себя как код, — «даже без присваивания» (тот же ответ
автора): `T := merge(A; B())` исполняет `merge` над живыми операндами и присваивает результат
указателю-переменной `T`, `merge(A; B())` на месте значения даёт результат выражению. `S: merge: A() B()` — вызов `S` с аргументом, который
вернул `merge` с аргументами в роли кода, — здесь два вызова; в данных та же строка ничего не вызывает, и в
`merge` уходят объявленные Structure (подтверждение автора — [журнал](../2026-11-17.md#merge-forms-confirmed)).

Что не меняется (чтение исполнителя). Прежняя запись `@: R merge(A; B)` остаётся: в данных она объявляет
указатель-переменную, её кандидат — аргумент ресивера `@:`, то есть код, исполняемый при чтении места; в
коде она присваивает. Обе записи уже есть в корпусе: форма объявления — в фикстурах
рабочего frontend (`Copy: merge: Holder`), запись с присваиванием — в графовых (`dest := merge(A; tap())`);
в чистом графе у формы объявления свидетеля нет.

Слова исполнителя, которые цитирует автор, относились не к аргументам `merge`, а к копированию: роль копируемой
Structure копировщику неизвестна (одна и та же Structure бывает данными в одном запуске и кодом в другом),
поэтому правило копирования (шаг4 графового круга) идёт от цели слова, а не от роли — слово, называющее Structure или вызываемое, в копии
становится адресом копии, слово, называющее место, остаётся словом. Аргументы самого `merge` по ролям не
различаются.

ответил fable, 2026-11-17.

### Р44. Что выводит `sys\toLmx` для записи `S: merge: A B` в данных и где живёт её композиция?

Вопрос автора 2026-11-17: сможет ли `toLmx` восстановить ресиверы `int`, `merge` в роли данных и остальные из
чистого графа. Разбор с фактами — [запись](../../steps/tolmx-receivers-20261117.md). Этим пунктом снимается
фраза Р43 «композиция строится вместе с готовыми объявлениями при построении чистого графа».

```
A: int: x 1
S: merge: A
```

и затем в коде `S\x := 9`. Наблюдаемые варианты вывода `toLmx`: (а) до записи — `S: merge: A`, после неё —
блок `S:` с `int: x 9`; (б) всегда `S: merge: A`; (в) всегда блок `S:` с полями, и до записи тоже.

Ответ — (а). Запись ресивера лежит в графе и при построении не раскрывается: «ресиверы объявления примитивов
не помещаются в граф непосредственно. Остальные ресиверы -- непосредственно помещаются в чистый граф»
([журнал](../2026-11-11.md#single-structure-index-path)) — это исключает (в), где запись заменена полями при
построении и ресивер уже не восстановить. У составленной Structure своё состояние — запись в неё читается
обратно, операнд не меняется (фикстура place_map рабочего frontend) — а `toLmx` обязан его сохранить: «Явно
перезаписанная конструкция выводится в текущем виде; исходник из истории … не восстанавливается»
([вывод текущего графа](../../docs/LMX_semantics.ru.md#memory)) — это исключает (б), где записанное9 теряется.
Поэтому композицию запись даёт при интерпретации и трансляции, когда чтение доходит до `S`, а первая явная
запись в `S` заменяет запись ресивера составленной Structure с этой записью.

Остальные ресиверы. Объявление места восстанавливается из самого места: ресивер — по типу ячейки, имя — по
таблице «адрес → имя», значение — текущее. Записи всех прочих ресиверов лежат в графе как Frame с головой и
выводятся записью. Подготовленный шаг ядра, заменявший запись `merge` композицией при построении, отозван.

ответил fable, 2026-11-17.

### Р45. Решение автора 2026-11-17: явный путь ничего не исполняет — какие чтения исполнителя сняты

Решение — [журнал](../2026-11-17.md#path-reads-no-execution), норма — [книга](../../docs/LMX_semantics.ru.md#path-reads-no-execution).
Запись фиксирует, что оно меняет в прежних ответах; возражений у исполнителя нет.

```
D:
    int: ready 5
    int: field f()
    S: merge: A B
```

Явный путь `D\ready` даёт5 типа `int`. `D\field` даёт запись объявления — Structure ресивера `int` с именем и
написанным вызовом; `f()` не исполняется. Выражение из литералов — тоже запись: при `int: field 5 * 2` путь
возвращает не10, а полную Structure, начинающуюся с `int:` ([журнал](../2026-11-17.md#path-returns-record-not-value)).
`D\S` даёт запись, `merge` не исполняется: `D\S\x` — не поле, к
операнду ведёт `D\S\merge\A\x`. Вычисляемое исполняет только вызов, для которого `D` — данные, когда читает
свой локал по голому имени (`field`, `S`); запись в графе при этом не меняется.

Сняты:

- Р36, пункт1, и Р39, пункт5 («чтение вычисляемого места по явному пути исполняет написанное выражение», «при
  каждом чтении»). Фикстура, которой нужно значение, читает локал вызова по голому имени.
- Р42, пункт3, второе перечисление: чтение `data\R\a` при `@: R merge(M; N)` не исполняет `merge` — путь
  упирается в запись объявления `R`. Перевод merge_reference на локалы `R` и `S` остаётся верным.
- Р43, фраза о `@: R merge(A; B)` «исполняемый при чтении места» — исполняет вызов, читая локал по голому имени.
- Р44 целиком: композицию записи `S: merge: A B` готовит вызов для локала `S`; записи в локал в граф не
  попадают, и `sys\toLmx` всегда выводит запись как написана.

Остаются: Р39, пункт8 (`p()` в коде — голое имя, вычисляемое место читает вызов); Р42, пункт5 (явная запись по
пути в поле с вычисляемым объявлением заменяет запись значением — это и есть самомодификация графа); Р40
(локалы вызова).

Следствия для подготовленного графового круга: свидетель «правая часть читает само вычисляемое поле по пути»
(`data\D\x := data\D\x + 1`) больше не выводится — правая часть даёт запись, а не число; шаг формы
`merge` в данных переопределён (композиция — локал вызова); исполнение вычисляемого объявления на шаге пути в
чистом графе снимается отдельным шагом.

### Р46. Решение автора 2026-11-17: типизированный `nil` — как он сходится с типом «T без инициализации»

Решение автора ([журнал](../2026-11-17.md#typed-nil), [продолжение](../2026-11-17.md#nil-comparison)): отсутствие
значения записывается `nil: int` (вместо `int` — другой примитивный тип), где возможно — просто `nil`, «но это
значение»; нулевой указатель остаётся `0`, где это можно; запись `@: ptr` тоже не `0`, для неё тот же `nil`;
`int: var` объявляет переменную без инициализации, для этого есть отдельный тип — он вводился для передачи
аргументов и остаётся нужен при `required`; отдельного числа `nil` не вводится, но переменную можно сравнить с
`nil`, «так как у нас все равно указатель». Ниже — следствия; новых правил они не вводят.

1. Второго типа и новых кодов не появляется. `nil: T` — запись значения уже существующего типа «T без
   инициализации» (в ядре `uninit:T`, у указателя `uninit:ref`; в чистом графе сегодня это ячейки видов 3, 8 и 9).
2. `int: x` и `int: x nil` — одно и то же место; так же `@: p` и `@: p nil`. `sys\toLmx` выводит короткую форму
   объявления, а значение вне объявления — `nil: T`, где T записан так, как его пишет объявление (`nil: int`).
3. Сравнение с `nil` и `required` спрашивают одно и то же — держит ли место отсутствие значения. Арифметики с
   `nil` нет.
4. `@: p 0` держит нулевой адрес — это значение: `p = nil` ложно, `required: p` проходит; `@: p` держит отсутствие
   значения.
5. Явный путь: `struct\field` при `int: field` отдаёт значение готового места, то есть `nil: int` (Р45).
6. Для передачи аргументов: формал без умолчания, которому не подан actual, держит «T без инициализации»; поданный
   actual принимается в место кадра обычным значением. `fn: f (int: a) int` с первой строкой `if: a = nil`: `f()`
   идёт в ветку, `f(7)` — нет.
7. Сравнение после присваивания решил автор ([архив вопроса](nil-after-assignment-answered-20261117.md),
   [журнал](../2026-11-17.md#assignment-changes-type)): `fn: f (int: a) int` с `if: a = nil` / `a := 5` /
   `if: a = nil` / `return: 1` / `return: a` возвращает 5 для `f()`. Присваивание локалу вызова пишет в место вызова,
   граф не меняется, данные не публикуются; граф меняет прямое присваивание `data\a := 5` — запись значения есть
   тип и значение, и присваивание меняет тип, если он другой. Правило 2026-11-08 «тип места при присваивании не
   меняется» отменено автором и снято из книги, L2 §3, спецификации ядра и плана.
8. Кодировка исполнителя (результат, память и скорость те же): в сегодняшней паре «запись `uninit:T` → ячейка T»
   смена типа — это элемент Structure, который после присваивания адресует саму ячейку T; адрес ячейки и взятый
   раньше `@x` не меняются. В записи M15 «код типа + значение» — запись кода T поверх кода `uninit:T`.

### Р47. Шаг приёма почты на чистом графе: что отвечает норма на вопросы описи

Опись sonnet (`receipts/sonnet/one-graph/MAIL2.txt`, вне репозитория) ставит шесть вопросов к следующему шагу группы
Г1 — приём письма, адрес Message значением графа, письмо с любыми данными. Написанная норма:
[книга, §28](../../docs/LMX_semantics.ru.md#thread-message-api) — «Публичные формы `send`/`receive` …, отбор по адресу,
получение всей доступной почты и `0` как конец итератора сохраняются … получение письма как данных само не вызывает
его содержимое»; [запись о переносе](../../docs/new_parts/threadMessageAPI_migration.ru.md) — «Сохранить
пользовательские `send` и `receive` с прежними сигнатурами и наблюдаемым поведением»;
[§24](../../docs/LMX_semantics.ru.md#messages) — Message есть изолированный граф с собственным владением, в его арену
попадают только данные и физические ссылки, явно переданные создающей операцией;
[§25](../../docs/LMX_semantics.ru.md#delivery) — отдельной политики копирования для Message нет;
[§20](../../docs/LMX_semantics.ru.md#composition) — копируется полный используемый граф, одна карта «источник — копия»,
ссылка переводится через неё на копию указуемого, вечная ветвь `independent: immutable` не копируется.

1. Что кладёт `receive` в место. Сохраняются прежние формы и наблюдаемое поведение. По чтению прежнего пути их три:
   место объявлено с типом Structure T (`MainLetter: m`, затем `receive: m`) — следующее письмо берётся, его
   полезная часть допускается к T обычным допуском, отказ допуска — неявный `throw` `implements`; два имени
   (`receive: m T`) — место держит всё письмо, отправителя и полезную часть, допущенное к модели письма; место без
   типа — ссылка на граф всего письма без допуска. До постройки шага каждое из трёх подтверждается запуском
   прежнего пути; чистый граф делает то же.
2. Пустой ящик. По книге `0` — конец итератора: место получает `0`, а не сохраняет прежнее значение.
3. Ссылка в поле письма. Отказа нет и отдельного правила для письма нет: письмо строится копированием графа, ссылка
   переводится на копию указуемого по общей карте, допущенная вечная ветвь остаётся исходной физической ссылкой.
4. Имена полей письма. Письмо — копия написанной Structure сообщения с вычисленными полями; копия графа переносит
   имена скопированных адресов одним механизмом
   ([срез «признаков мест нет»](../../steps/witnesses/m14-no-place-signs-20261117/notes.md)). Поэтому `send` не
   дописывает строки имён сам: письмо строится через общую дверь копии между аренами, и эта дверь переносит имена
   (сегодня не переносит — это закрывается тем же шагом, вместе с фактом, что происходит с таблицей имён арены при
   передаче хранилища получателю). Ветка «int-ячейка или массив символов по виду значения» в `lmx_graph_send` при
   этом уходит. Хост корневого потока читает письмо `exit` по позициям — для него ничего не меняется.
5. `receive-if`. Формы языка с таким именем написанная норма не называет: публичные формы — `send` и `receive` с
   отбором по адресу и получением всей почты. Примитив ядра остаётся примитивом ядра; оператор не вводится. Какая
   исходная форма прежнего пути выражает «отбор по адресу», опись дополняет фактом.
6. Хост команды `run`. Это обвязка проверки, не норма языка: три режима дают программе одно и то же окружение.
   Инструмент кладёт программе письмо той же формы, что получает корневой поток при нативном запуске, построенное
   той же функцией ядра, из аргументов, написанных в команде после числа запусков; второй, набранной руками формы
   письма не заводится. Строка графового списка аргументов не передаёт ни в одном режиме.
7. `post` и `adopt` в этот шаг не входят; они записаны в книге ([§23](../../docs/LMX_semantics.ru.md#eternal),
   [§28](../../docs/LMX_semantics.ru.md#thread-message-api)) и идут следующими шагами группы Г1.

Порядок шага: (А) `receive` одной функцией для трёх режимов — форма четырёх корней самосборки; (Б) вид значения
для ячейки «ссылка на Message» новым кодом типа и написанный получатель в `send`; (В) письмо как копия Structure
сообщения с именами. Свидетели — новые графовые фикстуры: в полном наборе нет ни одной строки с `receive`, `post`
или написанным получателем.

### Р48. Число, написанное в программе: что кладёт построитель чистого графа и что печатает дамп

Написанная норма: [грамматика, §4](../../docs/LMX_grammar.ru.md#numbers) — «Формы целых и вещественных литералов
следуют ANSI C/C99: десятичные, восьмеричные и шестнадцатеричные целые, суффиксы целых типов, десятичные и
шестнадцатеричные вещественные числа, показатели степени и суффиксы вещественных типов. … Числоподобный текст в
обратных кавычках — точный идентификатор»; автор,
[журнал 2026-11-17](../2026-11-17.md#path-reads-no-execution) — «Примитив мы можем точно восстановить только по
самому значению».

1. Кто решает, что текст — число. Построитель, по исходному тексту программы: `1U` — число, тот же текст в
   обратных кавычках — имя. Слово в графе этого различия уже не несёт, поэтому число становится значением графа
   при построении, а не при чтении операнда.
2. Какой тип у числа. Тот, который даёт константе C99: первый тип списка её записи, который держит величину.
   Десятичная без суффикса — `int`, `long`, `llong`; восьмеричная и шестнадцатеричная без суффикса — `int`,
   `unsigned`, `long`, `ulong`, `llong`, `ullong`; с суффиксами `U`, `L`, `UL`, `LL`, `ULL` — по их спискам;
   вещественная — `double`, с `f` — `float`, с `L` — `flong`. Константа типа `int` — примитив `int` при любой
   записи; любая другая — значение строки своего типа в каталоге примитивов.
3. Константа, которую не держит ни один тип её списка (`9223372036854775808` без суффикса). У неё нет значения:
   построение отказывает на месте, до исполнения; словом, обрезанным числом или числом другого типа она не
   становится. Тот же предел записан для прежнего пути ([план, M9](../../next_core_tasks_v3.md#m9), шаг 4): такой
   литерал отказывает при трансляции.
4. Что печатает дамп. Граф хранит тип и значение, а не написание; дамп пишет значение канонической записью C99.
   Условие одно: прочитанный снова текст даёт тот же тип и то же значение. Целое — десятичным с суффиксом своего
   типа: `0xFFFFFFFFU` печатается `4294967295U`, `3000000000` — `3000000000LL`, `0x1F` — `31`. Вещественное —
   кратчайшим текстом формата `%g`, который читается обратно в то же значение, с `.0`, когда в тексте нет ни
   точки, ни показателя: `1e3` печатается `1e+03`, `5.0` — `5.0`; `float` с `f`, `flong` с `L`.
5. Одна функция чтения. Записи числа читает одна функция ядра; её же вызывает образ выпущенной программы над
   канонической записью. Строка в выпущенном коде — отпечаток графа; второго описания числа нет.

Здесь не решается запись типизированного числа в место другого типа: это срез «присваивание меняет тип записи»
([решение автора 2026-11-17](../2026-11-17.md#assignment-changes-type)) и шаг 2 группы Г2.

### Р49. Приказ автора 2026-11-18 «интерпретатор исполняет и L2»: что из него следует по написанной норме

Написанная норма: [журнал 2026-11-18](../2026-11-18.md#interpreter-runs-l2) — четыре пункта приказа;
[книга, §1](../../docs/LMX_semantics.ru.md#scope) и [индекс](../../docs/LMX_semantics.ru.md#structure-index);
[журнал 2026-11-17](../2026-11-17.md#l3-own-types) — типы L3.

1. Какие проверки названы проверками. Те, что книга относит к типам L3: доступ к элементу массива по текущей
   длине; указатель на Structure или метод принимает только такой же указатель или обнуление; указатель на
   данные — обёртка, а не машинный адрес. Интерпретатор делает их для кода L3 и теми же функциями — для кода L2.
2. Адресная операция, которой в L3 нет вообще. Машинный адрес, адресная арифметика, сырая память, машинное
   приведение `cast:`. В интерпретаторе каждая получает свою проверку, и лежит она в том же модуле, что
   проверки L3. Чем именно закрыта каждая операция, записывает шаг П2 по описи; здесь это не решается.
3. Нативный код. Нативный код L2 вызовов модуля проверок не содержит. Нативный код L3 проверки своих типов
   сохраняет: по книге их делает L3, «как нативный, так и интерпретируемый».
4. Вызов `c.f(...)` из интерпретируемого кода L2. Это вызов, а не адресная операция. Путь вызова определяет
   дескриптор вызываемого вхождения ([§24](../../docs/LMX_semantics.ru.md#messages)); у C-функции есть только
   нативный адрес, и интерпретатор вызывает её по нему. В L3 `c.*` по-прежнему нет.
5. Запись `L2:` без нативного метода. Интерпретатор исполняет её содержимое сам. Отказ «у записи нет нативного
   метода», записанный в плане до приказа, не вводится; нативный метод записи — выбор исполнения по таблицам
   call, как у любого вызываемого.

ответил fable, 2026-11-18.

### Р50. Запись `L2` в чистом графе: откуда берётся уровень и что исполняет срез шага L1

Написанная норма: [книга, §1](../../docs/LMX_semantics.ru.md#scope) — «Расширение файла выбирает внешний профиль:
`.lm1` — прямое понижение L1, `.lm2` — L2, `.lm3` — L3. Код L2 пишется под ресивером `L2:`; его запись лежит в
графе как записана, и по ней транслятор и интерпретатор узнают уровень кода. Файл `.lm2` сам по себе как обёрнут
в этот ресивер»; автор, [журнал 2026-11-17](../2026-11-17.md#lm2-file-wrapped-in-l2) и
[приказ 2026-11-18](../2026-11-18.md#interpreter-runs-l2).

1. Откуда построитель берёт уровень. Из расширения пути, который ему дан: путь на `.lm2` — корень с одним полем,
   записью `L2`, в которой лежат поля файла; любой другой путь — поля файла в корне. Файл, написанный целиком
   под явным `L2:`, даёт ту же запись. Другого носителя уровня нет: ни признака, ни таблицы, ни поля.
2. Что исполняет срез. Исполнители проходят сквозь запись, которая составляет весь файл, и исполняют её
   содержимое, как исполняли: так каждая строка обоих наборов сохраняет ответ. Явный `L2:` в другом месте —
   среди других полей корня или в теле — интерпретатор в этом срезе не исполняет, программа отвечает отказом.
   По приказу автора 2026-11-18 интерпретатор исполняет код под записью `L2:` везде, с проверками: это шаг П2
   плана, а не этот срез (Р49).
3. Программа, которую строит машинная строка набора. Семь строк `tests/dyn/graph_*` пишут программу в файл,
   строят её через `lm_graph_build_file` и читают поля корня. В тексте этих программ операций L2 нет, значит,
   по правилу шага L0 это программы L3: строки называют файл `.lm3`. Сами строки — машинный код L2 с `c.*` и
   остаются `.lm2`.
4. Что печатает дамп. Запись `L2` — блок, как любая Structure с содержимым: строка `L2:`, содержимое на уровень
   глубже, строка `end: L2`. Отдельного правила дампа для неё нет. Ожидания семи программ `.lm2` переписаны этим
   правилом из прежнего текста, а не из прогона.
5. Что считается операцией L2 при переименовании. Формы, которые читаются в тексте: `c.X`, `cast:`, `include:`,
   `predef:`, `define:`, `os:`. Программа `tests/graph` без них — файл `.lm3`. Ссылки `@` любой глубины и числовые
   типы принадлежат L3 ([план](../../next_core_tasks_v3.md#one-graph-plan)).

ответил fable, 2026-11-18.

### Р51. Модуль проверок и типы L3: ответы на вопросы описи (шаги П1–П3)

Опись и предложение opus: `receipts/opus/one-graph/checks/INVENTORY.txt`, `PLAN.txt` (каталог прогонов, вне
репозитория). Написанная норма названа в каждом пункте.

1. Указатель на метод и указатель на Structure — один тип L3. Вызываемое — просто Structure
   ([решение автора 2026-11-16](../2026-11-16.md#callable-is-structure)); «присваиваются только друг другу»
   ([журнал](../2026-11-17.md#l3-own-types)) значит: такой указатель принимает Structure или вызываемое, а не
   число и не адрес данных.
2. Модель указателя модуль проверок не сравнивает. Книга: «Допуск другого кандидата к `Model` выполняется общим
   `implements`, без второго правила для имени `Model`» — это допуск, группа Г3, а не проверка типа L3.
3. Обнуление пишется нулём: `p := 0`. Книга пишет нулевой адрес нулём (`@: ptr 0`, `@: ptr Model 0`), автор:
   «null указатель оставить 0 где это можно» ([журнал](../2026-11-17.md#typed-nil)). `nil` — отсутствие значения
   у места, другое понятие. Чтение, шаг пути и вызов через нулевой указатель отказывают тем ответом, каким эта
   операция уже отвечает на операнд, который ей не подходит; нового ответа не вводится.
4. Явный `L2:` в теле. Книга, §3: «Вложенные управляющие тела того же вызова не создают новую активацию, но новые
   локальные имена принадлежат своей лексической ветви». Запись `L2:` — вложенное тело того же вызова: имена
   объемлющего кода внутри неё видны и пишутся; имена, объявленные внутри, после неё не видны.
5. Операция L2 вне записи `L2`. Вне записи такой операции нет: интерпретатор её не исполняет и отвечает, как
   отвечает сегодня на неизвестное имя. Построитель не отказывает — граф любого профиля пригоден интерпретатору
   (книга, §1); статически о таких местах сообщает `sys\checkL3`.
6. Ответ на индекс вне длины. Книга: такой индекс «вызывает неявный `throw: interpreter`». `throw` на чистом
   графе — группа Г3; до неё проверка завершает исполнение прежним ответом, и место отказа одно — в модуле.
7. Обёртка указателя на данные — типизированная ячейка-ссылка, как сегодня у ссылки на `int`: в L3 адресной
   арифметики нет, ссылка всегда называет одну целую ячейку. Базу и смещение обёртка не хранит.

Не решается здесь и решается в своих срезах: чем закрыт адрес вне областей арены в интерпретируемом коде L2 и
вызов `c.f(...)` в режиме без образа (шаг П2); `os:`, `define:` и `sizeof` типа C-двери (группы Г4 и Г2).

### Р52. `private` и `required` с несколькими аргументами; «корневой уровень» при чтении `data`: что есть сегодня

Написанная норма: [журнал 2026-11-18](../2026-11-18.md#private-required-many-arguments); книга —

Проверка на принятом инструменте чистого графа, режим интерпретации. Программы — пробы исполнителя вне
репозитория; ответ — значение, которое код записал по явному пути, либо ответ отказа.

| запись | где стоит | ответ |
|---|---|---|
| `private: (int: x 20)` | данные метода | 20 |
| `private: (int: x 5)` | данные, поданные запуску `call: Data Code` | код читает `x`: `x + 1` даёт 6 |
| `private: (int: x 20) (int: y 3)` | данные метода | построение отказывает, 5 |

| `required: (int: a)` | данные метода | построение отказывает, 5 |
| `required: a` | код метода | исполнение отказывает, 3 |
| `const: (int: x 5)` | данные, поданные запуску | исполнение отказывает, 4 |

   функция ядра `lmx_graph_receiving_view`, и объявление под `private:` становится входным местом. У пометки она

2. Ресивера `required` на чистом графе нет: слово не входит в список помечающих ресиверов, записи с ним
   отказывают в обоих видах.
3. Чтение нормы. Несколько аргументов — это несколько записей с одним аргументом, в записанном порядке. Аргумент —
   то, что принимает запись с одним аргументом: объявление в скобках у обоих ресиверов, имя видимого поля у
   `required`. Группу с несколькими объявлениями в одних скобках это уточнение не вводит.
4. Объявление под `const:`, `immutable:`, `independent:` в поданных данных отказывает по другой причине: понижение
   этих квалификаторов не сделано. Это отдельная работа, не предмет уточнения.

### Р54. Одна Structure в аргументах, которые считаются code: правило вызова действует и для ресиверов

Написанная норма: книга, [вся структура аргументов](../../docs/LMX_semantics.ru.md#whole-arguments) — «Вызов с
единственным аргументом-Structure не отличается от вызова с цепочкой её полей» и «Это правило связывания вызова,
а не парсера: P0 записанную в вызове анонимную Structure не раскрывает»; автор,
[журнал 2026-11-18](../2026-11-18.md#one-unnamed-structure-for-receivers): общий случай — одна Structure в
аргументах, которые считаются code, записана ли она в скобках или подготовлена и передана ссылкой; это правило
вызова; оно действует автоматически и для ресиверов — везде, где передаваемое ведёт себя как code; в парсере
ничего не раскрывается.

Этим снята последняя фраза пункта 3 ответа Р52. Запись `private: (int: x 20; int: y 3)` не вводится уточнением, а
следует из действующего правила. Примеры с двумя группами в скобках, которые исполнитель внёс в книгу
(`private: (int: x 10) (int: y 20)`), заменены записью с одной группой.

Проверка на принятом инструменте чистого графа, режим интерпретации:

| запись | ответ |
|---|---|
| `f(3; 4)` и `f((3; 4))` при `fn: f (int: a; int: b)` | 7 и 7: вызов вызываемого одну Structure принимает |
| `f(shared\Args)` и `f(prepared)`: подготовленная Structure по пути и по ссылке | 7 и 7 |
| `int: (y 7)` в коде метода | отказ, 3 |
| `private: (int: x 20; int: y 3)` в коде метода, в строку и столбиком | отказ, 3 |
| `call: (Data Code)` | отказа нет, но код не запускается |
| `private: int: x 20` в коде метода, без скобок | 20 |

1. Этот шаг сегодня сделан в связывании вызова вызываемого. Ресиверы языка читают свою группу каждый сам, а
   цепочка квалификаторов раскрывает группу только с одним полем.
2. Чтение нормы. Это один шаг передачи аргументов, общий для вызываемого и ресивера: в аргументах ровно одна
   Structure — аргументами становятся её поля; иначе аргументы — записанный список. Шаг действует
   там, где запись исполняется как code, в том числе когда ресивер исполняется при прямом проходе по данным
   (Р53). В роли data запись остаётся как записана: `f: (a b)` объявляет `f` с одной безымянной Structure внутри.
3. P0 и построитель не меняются: в графе запись лежит как записана, со скобками.

### Р55. Пять записей одного вызова: что отвечает реализация

### Р56. Два вида ресиверов: что снято из Р54 и что следует для кода

Написанная норма: решение автора, [журнал 2026-11-18](../2026-11-18.md#two-kinds-of-receivers), и уточнения
[там же](../2026-11-18.md#tree-is-not-the-call). Ресивер с аргументами как code обращается с ними как вызываемое:
единственная Structure раскрывается, один раз и только при обработке вызова, целиком её подают
`f(arg0 := Struct)`. Ресивер с аргументами как data (L1, L2, L3, модификаторы, форма `: merge` в данных) получает
ровно то, что записано. В дереве разбора и в чистом графе раскрытия нет.

1. Снято из Р54. «Один общий шаг для вызываемого и ресивера» относится только к ресиверам с аргументами как
   code. В записи `private: (int: x 10; int: y 20)` аргумент один — единственная безымянная Structure, которую
   модификатор не раскрывает; план её раскрытия снят автором
   ([журнал](../2026-11-18.md#no-group-form-for-modifiers)). Несколько аргументов пишутся списком —
   `private: int: x 10; int: y 20`, `private(int: x 10; int: y 20)` или столбиком; эти записи поддерживаются.
   Деревья разбора проверены командой `p0` принятого инструмента чистого графа: у трёх списочных записей под
   `private` два объявления, у записи одной группой — одна Structure.
2. Следствие для записи со скобками вокруг одного объявления (чтение исполнителя, автором не подтверждено).
   `private: (int: x 10)`, `const: (@: p T)`, `required: (int: a)` — безымянная Structure под модификатором;
   объявление пишется без скобок, `private: int: x 10` (на чистом графе отвечает уже сегодня). Сегодня код читает
   группу ровно из одного поля как само объявление. Запись со скобками стоит в 2862 строках поддерживаемых
   исходников и в 114 строках тестов. В книге примеры переписаны без скобок; исходники и тесты не тронуты.
3. Ресиверы языка, действие которых применяется к самой поданной Structure, — `call`, `fncall`, `length`,
   `typeof`, `parent`, `return` — исполнитель относит к ресиверам с аргументами как data (чтение, автором не
   подтверждено). Основание: книга, «`call(C)` равнозначен `call(C C)`»; при раскрытии `C` запуск одной Structure
   пришлось бы писать именованно. Так они работают сегодня: `call: Self` запускает `Self`, `typeof(Args)` отвечает
   типом Structure, `call: (Data Code)` запускает группу как записана.
4. Вызываемое: раскрытие безусловно. Сегодня связыватель сначала пробует позиционную форму: `MR(A)` при
   `fn: MR (@: value Model)` отвечает 7, `MR((A))` отказывает. По правилу наоборот: `MR(A)` раскрывает `A`,
   а `MR((A))` и `MR(value := A)` подают `A`. Один уровень раскрытия сегодня выполняется: `g((1 2 3))` — 123,
   `g(((1 2 3)))` — отказ.
5. Ресиверы объявлений принимают аргументы как code (слова автора, раздел 5 журнала): `int: (y 7)` — то же, что
   `int: y 7`; сегодня отказ.
6. `merge` в `code` принимает операнды как code, и одна Structure раскрывается; в блоке `data` и после двоеточия —
   как data.

Случаи вопроса [q/current](one-structure-in-arguments-cases-answered-20261118.md): С0, С1, С3, С4, С5 и С7 решены
автором; С2, С6 и пункт 2 выше ждут его слова.

### Р57. Модификаторы: правило формулируется числом и формой аргументов, а не скобками

Написанная норма: автор, [журнал 2026-11-18](../2026-11-18.md#arguments-by-number-and-form). Отличие записей
модификатора — в числе и форме аргументов; запись со скобками после двоеточия — частный случай. Блок под
`private:`, в котором записана одна безымянная Structure, — тоже один аргумент-Structure. В
`private(int: a 1; int: b 1)` аргументов два, хотя скобки есть.

1. Снимаю свои формулировки Р54 и Р56 «запись одной группой», «запись со скобками», «без скобок». Отдельного
   правила для модификаторов нет. Действует одно деление ресиверов на две группы по тому, как они интерпретируют
   аргументы, — как data или как code (Р56). Модификаторы входят в первую: аргументы они получают как записаны,
   поэтому аргумент, который сам является Structure, остаётся Structure. Сколько аргументов и какие они,
   определяет запись по общим правилам разбора.
2. Деревья разбора (команда `p0` принятого инструмента чистого графа):

   | запись | аргументы модификатора |
   |---|---|
   | `private: int: a 1; int: b 2` | два объявления |
   | `private(int: a 1; int: b 2)` | два объявления |
   | блок под `private:` с двумя объявлениями | два объявления |
   | `private: (int: a 1; int: b 2)` | одна Structure с двумя объявлениями |
   | блок под `private:` с одной безымянной Structure (пример автора) | одна Structure с двумя объявлениями |
   | `fn: f (const(@: p char); int: n) int` | у `const` одно объявление; `n` — следующий формал |
   | `fn: f (const: (@: p char); int: n) int` | у `const` одна Structure с объявлением; `n` — следующий формал |
   | `fn: f (const: @: p char; int: n) int` | у `const` два объявления, `p` и `n` |

3. Откуда запись `const: (@: text char)` в исходниках. В списке формалов на одной строке `;` после двоеточия
   закрывает только внутренний фрейм, и следующий формал становится вторым аргументом `const` (последняя строка
   таблицы). Скобки ставили как границу аргумента, а код раскрывал Structure с одним полем. По правилу аргумент
   там — Structure. Ту же границу с аргументом-объявлением даёт `const(@: text char)`. Перевод 2862 строк
   исходников и 114 строк тестов на эту запись и снятие раскрытия из кода — срез миграции в плане. Пункт 2 Р56
   этим закрыт: это не отдельное чтение исполнителя, а следствие правила.

ответил fable, 2026-11-18.

### Р58. `call`, `fncall`, `length`, `typeof`, `parent`, `return` принимают аргументы как code

Написанная норма: автор, [журнал 2026-11-18](../2026-11-18.md#atom-has-no-call-role). У атома нет роли call,
поэтому `C` в аргументе — всегда ссылка, и в роли code, и в роли data; все эти ресиверы принимают аргументы в роли
code. Пункт 3 Р56 — моё чтение «они в группе data, иначе `call(C)` перестаёт запускать `C`» — снят как неверный.

Факты принятого инструмента чистого графа, режим интерпретации:

| программа | ответ |
|---|---|
| `call(C)`, в `C` две записи: `seen := seen + 1` и `seen := seen + 10` | 11: `C` запущена целиком |
| `call(D C)` при `D: (int: x 5)` и `C: (seen := x)` | 5 |
| `call(P)`, `P` держит ссылки `D` и `C` | 0: запущена сама `P` |
| `length(Outer) * 10 + length(A)`, `Outer` держит ссылку `A`, в `A` два поля | 12 |
| `typeof(Args)` | тип Structure |

Открыто ([вопрос](one-structure-in-arguments-cases-answered-20261118.md), С2). У вызываемого единственная Structure
в аргументах, записанная или переданная ссылкой, раскрывается: `f: Struct` — то же, что `f(arg0 arg1 arg2)`. Если
то же действует для `call`, то `call(P)` — это `call(D C)` и отвечает 5, но тогда `call(C)` — это `call` от двух
записей `C` и отвечает 10, а не 11. Для `length` раскрытие ответа не меняет.

### Р62. `call` и `fncall` — аргументы как data; ресиверы, которым подают одну Structure

Написанная норма: решение автора, [журнал 2026-11-18](../2026-11-18.md#call-fncall-arguments-as-data): `call` и
`fncall` переведены в группу ресиверов с аргументами в роли data; свой аргумент `args` они интерпретируют в роли
code. Этим решена пара программ Р58: `call(P)` запускает саму `P` (0), `call(C)` с двумя записями запускает `C`
целиком (11) — как принятый инструмент отвечает сегодня; код менять не нужно.

Открыто (тот же класс, что `call`; [вопрос](one-structure-in-arguments-cases-answered-20261118.md), С2). В книге
ресиверы `parent`, `length`, `sys\native`, `sys\storage`, `sys\capacity` описаны словами «принимают одну Structure
S»; так же пишутся `sys\typeof(S)`, `sys\toLmx(S)` и `return: S`. По слову автора от того же дня `length`, `typeof`,
`parent`, `return` принимают аргументы как code, а у ресивера с аргументами как code единственная Structure
раскрывается. Тогда `parent(S)` получает не `S`, а её поля, и саму Structure пришлось бы подавать именованно. Для
`length(S)` раскрытие ответа не меняет. До слова автора эти ресиверы в коде не трогаются.

### Р63. Проверка ресиверов: где единственная Structure в роли code даёт противоречие

Поручение автора, [журнал 2026-11-18](../2026-11-18.md#return-stays-code): аргументы `return` остаются в роли code,
противоречий там нет; проверить остальные ресиверы. В Р62 я назвал `return: S` в одном ряду с `parent(S)` — неверно:
`return` возвращает структуру аргументов, и `return: S` даёт `S` при любом прочтении.

Чем проверялось. У ресивера с аргументами как code единственная Structure — вся структура аргументов. Противоречия
нет, когда для ресивера «Structure» и «цепочка её полей» — одно и то же. Оно есть, когда ресиверу нужна сама
Structure: её адрес, заголовок, место в графе.

Противоречий нет (аргументы как code):

| ресивер | что получается с единственной Structure |
|---|---|
| объявляющие: `int` и другие примитивы, `@:`, `fn`, `sub`, `catch` | `int: (y 7)` — то же, что `int: y 7` |
| управление: `if`, `else`, `while`, `until`, `for`, `finally` | `else: (a; b)` — то же, что `else: a; b`; у `else` и `finally` код уже так работает |
| `return` | возвращается структура аргументов: `return: S` даёт `S` |
| `length` | число аргументов равно числу полей `S` |
| `merge` в коде | операнды — поля единственной Structure; записи с одним операндом в книге нет |
| вызываемые `fn`, `sub`, запуск `S(D)` | по правилу; целиком Structure подают `f(arg0 := S)` |
| `test: op check`, `adopt: msg newParent`, `sys\indexof(field parent)` | аргументов два и больше, единственной Structure не бывает |

Ресиверу нужна сама Structure (тот же случай, что у `call`):

| ресивер | что написано в книге или закреплено | что даёт раскрытие |
|---|---|---|
| `parent(S)` | «принимают одну Structure S»: родитель `S` | `parent` получает поля `S` |
| `typeof(S)`, `sys\typeof(S)` | тип самой Structure; фикстура `typeof` ждёт 13 для `typeof(main\data\Box)` | тип первого поля или отказ по числу аргументов |
| `sys\native(S)`, `sys\storage(S)`, `sys\capacity(S)`, `sys\descriptor(S)` | читают заголовок и адрес `S` | получают поля `S` |
| `sys\toLmx(S)`, `sys\check(S)`, `sys\checkL3(S)`, `sys\translate(S)`, `sys\compile(S)` | работают над корнем `S` | получают поля `S` |
| `throw: Stop` | аргумент называет сам `catch`; в `throw: Name(arguments)` аргументы вычисляются | `throw` получает поля `catch` |
| `send: exit(…)` | аргумент — само письмо; его поля вычисляются | письмо исполняется как вызов |

Чтение исполнителя: вторая таблица — одна группа с `call` и `fncall`. Ресивер принимает свои аргументы как data,
то есть получает поданную Structure как она записана; то, что у него внутри читается как аргументы вызова (`args`
у `call`, аргументы `Name(arguments)` у `throw`, поля письма у `send`), вычисляется в роли code. Аргументы этих
ресиверов в книге и фикстурах — атомы, пути, индексы и адреса: ссылки, которые ничего не исполняют, так что для
них роль data ничего не отнимает. Решение за автором; до него эти ресиверы в коде не трогаются, в книге стоит его
прежнее слово.

ответил fable, 2026-11-18.

2. Сняты мои слова в Р56, пункт 4, и в вопросе, случай С1: «у вызываемого раскрытие безусловно, `MR(A)` раскрывает
   `A`». По правилу `MR(A)` при одном формале подаёт `A`.
3. Проверка на баг, принятый инструмент чистого графа, режим интерпретации. `Model` — `(int: x 0)`; `A` — поля 7 и
   8; `One` — одно поле 9; `Pair` — поля 3 и 4.

   | вызываемое | запись | ответ | по правилу |
   |---|---|---|---|
   | `fn: one (@: v Model)` | `one(A)` | 7 | 7: один аргумент, `A` не раскрыта |

   | `fn: two (@: v Model; int: n 3)` | `two(A)` | 73 | `A` раскрывается, 7 не подходит формалу `v` — **баг** |

   | `fn: pair (int: a; int: b)` | `pair(Pair)` | 34 | 34 |
   | `fn: pair (int: a; int: b)` | `pair((3 4))` | 34 | 34 |

   Причина одна: связыватель решает о раскрытии по неудаче позиционной подачи, а не по числу аргументов

   перенесён из `current/`.

### Р80. Вопросы вспомогательных сессий по срезам скана и выбора объявления; поправка к Р73

2. Строка `callable_part_names`. Её закрепление — отказ 3 — верно по сегодняшней норме: уточнением 2026-11-15 прежние

### Р81. `call(P)` по словам автора; два вопроса автору по срезу выбора объявления

Написанная норма: слова автора, [журнал 2026-11-18](../2026-11-18.md#call-one-argument-declaration).

1. `call(P)`. Автор подтвердил пример `call(code := P)` и уточнил порядок для `call(P)`: формы `call` и `fncall` —
   это множество объявлений со всеми наборами аргументов; объявление с одним аргументом есть, поэтому берётся оно;
   раскрытие `P` проверяется на непротиворечивость — не лежат ли внутри ровно два поля, которые сами разрешают
   вызов; затем интерпретатор исполняет вызов, а транслятор пишет нативный вызов Си без проверок. Это совпадает с
   записанным в Р80 и в плане: `call(P)` отказывает, только когда поля `P` сами разрешают другую форму; иначе
   запускается `P`.
2. Открытый вопрос автору:
   [листовое поле в первой части implements](current/implements-first-part-leaf-field-20261118.md).
   Проверка opus показала, что первая часть библиотеки сегодня отказывает только по карте полей и ни одного
   листового поля не отвергает: `int` против ссылки на Structure проходит. Моё предложение — в файле вопроса:
   листовое поле сравнивается там же, по типу и таблице преобразований.
3. Открытый вопрос автору: [число аргументов при выборе](current/selection-exact-count-20261118.md). Книга говорит

   аргументов.
