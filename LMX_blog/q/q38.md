# Q38. Захват Structure в callable-merge: ссылка или копия (остаток пункта 738)

Состояние: 2026-09-27, открыт (вопрос Opus, оформил fable_pc); в тот же день отвечен автором в чате fable_pc (~20:52 UTC), закрыт и перенесён в `LMX_blog/q/`.

## Факт

Сегодня захват Structure моделью callable-merge отказывается located: «a callable merge needs a walkable body» (`l2_mcap_ty_ok` принимает int, char, size_t, unsigned, ulong; указатель и Structure — нет). Пункт 738 «Остаток `return` вложенного callable» требует захват char (сделан, `0acac58`), указателя и Structure.

Два места говорят о графе по-разному.

1. `next_core_tasks.md` :645 (правила обычного `merge`, действующие и для `return` вложенного callable):

   > The ordinary merge rules remain unchanged: it follows the complete used graph and necessary lexical ancestry, copies mutable used state, preserves shared method references under their contracts, rewrites references and parent links, and does not copy unused …

2. Копировщик ядра, `dev/l2src_sandbox/lmx_graph_copy_owned.h.lm1` :25–26 (k.4, Q22 = II):

   > any Structure whose parent lies outside the copied operand subtree is a shared reference … kept by address, not copied.

## Два случая

**(A) Захват Structure-формала хозяина.**

```text
fn: makeReader (Model: m) fn: (int: x) int
    fn: read (int: x) int
        return: m\value + x
    return: read
```

`m` — Structure вызывающего (`left` в корне, родитель — юнит). По k.4 родитель вне операнда, значит ссылка: позднейшая запись `left\value` видна через `read`. По «copies mutable used state» — копия на момент возврата, запись не видна.

**(B) Structure, объявленная хозяином.**

```text
fn: makeReader (int: n) fn: (int: x) int
    Model: loc
    loc\value: n
    fn: read (int: x) int
        return: loc\value + x
    return: read
```

Родитель `loc` — активация хозяина, которая по спецификации не удерживается, значит копия. Вопрос — копия чего: всей `loc` как Structure своего типа `Model` (все слоты; родитель — узел) или только используемых полей (тогда результат уже не `Model`, и `loc\value` из модели не адресуется по слоту типа).

## Вопросы

1. (A): ссылка (как у Structure-формала при обычном вызове, ARG/T4b, и по k.4) или копия (по «copies mutable used state»)?
2. (B): копия всей `loc` как Structure своего типа с родителем-узлом, или обрезка до используемых полей?
3. Если (A) ссылка, а (B) копия: одно правило, читаемое из графа (родитель внутри или вне операнда, как k.4), или два правила по виду захвата?

## Предложение Opus

(A) ссылка; (B) копия всей `loc` как Structure своего типа (родитель — узел), «используемая часть» = `loc` целиком, потому что модель адресует её по типу.

## Мнение fable_pc

Согласен с обоими пунктами и с тем, что это одно правило, а не два: k.4 уже сформулировано через граф («родитель вне операнда — ссылка по адресу»), а «copies mutable used state» говорит о том, что внутри операнда. `loc` в (B) лежит внутри операнда (её родитель — исчезающая активация), формал `m` в (A) — вне. Обрезка `loc` до используемых полей ломала бы адресацию по типу (слот `value` типа `Model`); довод той же природы, что у прозрачности единственного анонимного контейнера (§4.0.1): форма, которую потребляет получатель, не меняется. Решение за автором: правило «copies mutable used state» допускает и чтение «копировать только используемые поля».

## Ответ автора (2026-09-27)

Дословно — `LMX_blog/2026-09-27.md` (раздел Q38). Как прочитано (fable_pc; при расхождении действует цитата):

1. Правило k.4 копировщика («Structure, чей родитель вне копируемого операнда, — общая ссылка по адресу») автор называет чепухой: `merge` не копирует неиспользуемое, поэтому «общей ссылке за пределами копируемого» нет ни адресата, ни смысла — за пределами копируемого ничего не видно. Категории «вне операнда → ссылка» нет: используемое входит в используемый граф и копируется как изменяемое состояние (книга :645, :928), неиспользуемое отсутствует; сохраняются по контракту только общие ссылки на методы (книга: «preserves shared method references under their contracts»).
2. Следствие для (A) и (B): оба — копия используемого состояния на момент возврата, не ссылка; позднейшая запись `leftalue` через `read` не видна (это ответ на вопрос 1 — «копия», не «ссылка»); (B) — копия используемой части `loc` (вопрос 2 — «используемая часть», сколько её нужно модели), а не ссылка на активацию.
3. Открытое следствие для ядра: `lmx_graph_copy_owned.h.lm1` :25–26 (k.4, «Q22 = II, generalized — not only a method occurrence») реализует ту категорию, которую автор отверг; чтение fable_pc — Q22 = II относится к вхождению метода (общая ссылка на неизменяемый метод по контракту), а обобщение на любую Structure и есть «чепуха».
