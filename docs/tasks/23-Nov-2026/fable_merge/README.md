# Fable: проверка и слияние новой редакции

Пакет построен относительно **точно загруженного `spec.tar.gz`**:

```text
SHA-256 4b142bab169cf7cc3fd89766da35b90561f913b68dca3ab1f0725793e4ecb932
```

Рядом лежит полная новая директория [spec](../spec/README.md). Все пути в патчах и `changes.json` относительны корню существующей `docs/spec` или распакованной `spec`, без жёсткой привязки к пути автора. Предыдущая версия, созданная в чате, не используется как база.

## Состав

| Файл | Назначение |
| --- | --- |
| `changes.json` | Добавление, изменение или удаление каждого файла, SHA-256 до/после, размер и класс изменения |
| `source.patch` | Git diff исходников, норм, примеров и генераторов |
| `generated.patch` | Отдельный diff PDF, XLSX, CSV и сгенерированных отчётов/зеркал |
| `base-files.tar.gz` | Точные прежние содержимые изменённых файлов; база для трёхстороннего слияния |
| `merge.py` | Проверка, предварительное слияние, защищённое применение и резервная копия |
| `test_merge.py` | Изолированные проверки поведения инструмента |
| `build_fable_patch.py` | Повторное создание пакета из точной базовой и новой директорий |
| `validate_packet.py` | Воспроизводимая проверка обоих способов применения на временных копиях базы |
| `VALIDATION.json` | Фактически выполненные проверки пакета на копии загруженной базы |

Патчи включают удаления малозначимых дублей. Они не требуют удалять более позднюю локальную редакцию без проверки. Исходный файл, изменённый у Fable после загрузки, сравнивается с обеими сторонами, а не безусловно перезаписывается.

## 1. Только проверить

Python 3.9 или новее; Git требуется для трёхстороннего слияния. Из корня нового пакета:

```sh
python3 fable_merge/merge.py /path/to/docs/spec --check --merge --review /tmp/lmx-merge-review --report /tmp/lmx-merge-review.json
```

Без `--apply` целевая директория не меняется. `--review` сохраняет отдельные текстовые результаты слияния, включая конфликтные маркеры, вне проекта. Перед первым запуском выберите свободные пути review/report.

Основные состояния:

- `ready`: локальный файл точно совпадает с загруженной базой; изменение применимо.
- `alreadyApplied`: локальный файл уже равен новой редакции.
- `merged`: локальные правки и новая редакция сливаются без текстового конфликта.
- `conflict` / `localChanges`: требуется содержательное решение; весь автоматический apply заблокирован.
- `generatedSkipped`: производный артефакт пропущен по умолчанию.

Чистое текстовое слияние не доказывает семантическую совместимость двух изменений. Особое внимание: правило передачи деклараций, DATA/parent, конечные throws, Message/post и связывание новых прямых экспортов.

## 2. Применить проверенный набор

```sh
python3 fable_merge/merge.py /path/to/docs/spec --apply --merge --report /tmp/lmx-applied.json
```

Перед записью инструмент повторно проверяет содержимое всех затрагиваемых файлов. Любой конфликт останавливает весь набор. Старые версии сохраняются в новой соседней директории `fable-backup-...` вместе с `RESTORE.json`; заданный существующий backup не перезаписывается. Для удалений и бинарных изменений требуется точное совпадение базы. Символические ссылки и выход из целевой директории отвергаются.

Запись отдельного файла производится через временный файл и замену. При ошибке инструмент пытается вернуть уже применённые изменения, не перезаписывая обнаруженные внешние правки. Это не транзакция всей файловой системы: на время применения следует закончить параллельное редактирование этих файлов. Резервная копия остаётся для ручного восстановления.

## 3. Артефакты или собственная генерация

Чтобы вместе с исходниками взять готовые PDF/XLSX и другие производные файлы:

```sh
python3 fable_merge/merge.py /path/to/docs/spec --check --merge --include-generated --report /tmp/lmx-all-review.json
python3 fable_merge/merge.py /path/to/docs/spec --apply --merge --include-generated --report /tmp/lmx-all-applied.json
```

Либо примените только исходники и повторите генераторы, указанные в [общей проверке](../spec/patterns/VALIDATION.md), [пакете ядра](../spec/patterns/LMX_Fn_Receivers/README.md) и [наборах примеров](../spec/patterns/examples/README.md). Если ваши дополнительные правки изменяют код, готовые числовые результаты этого пакета уже не описывают итог слияния: статистику надо пересчитать.

`source.patch` и `generated.patch` подходят и для обычного git apply. Проверка выполняется из корня целевой spec:

```sh
git apply --check /path/to/new-packet/fable_merge/source.patch
git apply /path/to/new-packet/fable_merge/source.patch
```

Для дерева с самостоятельными изменениями предпочтителен `merge.py --merge`: он получает базовые содержимые из пакета и не требует, чтобы соответствующий commit существовал в вашем Git. Простой `git apply --3way` без базовых Git objects такого обещания не даёт.

## 4. Что всё равно надо интегрировать в ядро

[CORE_FUNCTIONS.md](../spec/CORE_FUNCTIONS.md) — полный список функций и реализаций. [KERNEL_REQUIREMENTS.md](../spec/patterns/LMX_Fn_Receivers/KERNEL_REQUIREMENTS.md) отделяет 19 узких внутренних входов от пользовательского API. Новый AE01 `attemptAccepted` сохраняет принятую позицию декларации, связанное тело и живые места принимающего исполнения. Он не заменяется произвольным namespace snapshot или поиском по внутреннему имени.

AR01 `acceptsRequirement` наблюдает существующую проверку совместимости без исполнения пользовательского кода. Доказанная несовместимость и невозможность завершить проверку различаются. Эта внутренняя граница устраняет четыре недопустимых использования `satisfies` как булева предиката в прежних Regex-исходниках; публичный `satisfies` своего договора не меняет.

Пакет не объявляет выполненными runtime-тесты LMX. Его source checks, сравнения файлов, размеры и проверки формул отделены от подготовленных семантических случаев `NOT_RUN`.

## 5. Повторить проверку самого diff-пакета

Распакуйте исходный загруженный `spec.tar.gz` в отдельную директорию. Из корня новой поставки выполните:

```sh
python3 fable_merge/validate_packet.py --baseline /path/to/extracted-original/spec
```

Новая редакция по умолчанию читается из соседней `spec`, а фактический результат записывается в `fable_merge/VALIDATION.json`. Путь к распакованной базе — единственный обязательный параметр; никакую рабочую директорию пользователя как цель применения этот инструмент не принимает.

Проверка создаёт две временные копии базы. В первой она запускает `merge.py --check --include-generated`, применение и повторное применение; во второй — `git apply --check` и применение `source.patch` вместе с `generated.patch`. Каждый итог сравнивается со всей новой `spec` побайтово; повторное применение также должно сохранить времена изменения файлов. Используются те же исключения, что в сборщике inventory: `.DS_Store`, `__pycache__`, `.pyc` и `.git`. Исходная база и поставляемая `spec` проверяются на неизменность до и после; временные копии удаляются. Здесь же запускаются восемь изолированных проверок `test_merge.py`. Это проверка доставки файлов и поведения merge-инструмента, а не исполнения программ на LMX или других языках.
