## Унификация по смыслу

`Name :: DATA`, существующие `->` и `record`, postfix-типы `[]T`/`@T` и новые Pattern-слова используют общий Expression-механизм. `then` обозначает последовательность, `times/atLeast/atMost/optional` — ограничения повторения. Существующий `|` получает упорядоченную Pattern-альтернативу и сохраняет прежний числовой/Array-путь. Нового `or`, regex-парсера или отдельного раскрытия аргументов нет.

`range`, `slice`, `concat`, `map`, `filter` и операции изменения имеют обычную и операндную формы одного алгоритма. Все ресиверы уже допускаются в Expression на уровне P0; транслятор сохраняет роли VALUE, TYPE, NAME, DATA, RAW/BODY и PLACE. Имена без кавычек и в обратных кавычках тождественны, а содержимое точного имени не разбирается заново. Похожие внутренние имена не скрывают разные договоры. Например, публичный slice использует begin/end, старый внутренний helper — start/count; append изменяет тот же target, а прежний append создаёт новый контейнер. Эти различия явно переводятся в делегатах.

Каждая Structure уже является `[]@`. Универсальный @ принимает и плотный []T, и Structure без пользовательского boxing всего массива. Actual storage читается по каноническому описанию TypeRef действительного типа. Выбор результата сохраняет оговорённый профиль; copy/merge, parent, lifetime и ошибки остаются обычными.

Общее равенство и `unique(items)` определены в [GENERIC_EQUALITY.md](../../GENERIC_EQUALITY.md); короткие `some(x)` и `bind` всех контейнерных семейств — в [MONADIC_OPERATIONS.md](../../MONADIC_OPERATIONS.md). `then` означает композицию любых Patterns. `->` получает TYPE результата последним, `type` возвращает каноническую TypeRef целого значения. [GENERIC_OPERATIONS.md](../../GENERIC_OPERATIONS.md) задаёт общие профили и единые алгоритмы.

## Единое ядро и статус исполнения

Все перечисленные операции предназначены для прямой публикации в одном текущем ядре по [общему договору форм](../../OPERATION_FORMS.md) и [контракту публикации](PUBLICATION_CONTRACT.md). Опциональных пользовательских версий, client import или второго runtime не вводится. Внутренняя группа fun/const содержит проекцию ссылок на методы с их фактическими DATA/parent; полное семейство задаёт [public_families.lmx](src/public_families.lmx). Квалифицированный путь используется при настоящей коллизии имён. Публикация выбирает роль и семантическое семейство до исполнения; одна const-проекция не доказывает выбор Maybe/Result/Array.

Сборка и отдельные src-файлы представляют одни исходники: загружают либо сборку, либо её части. Определения в reference сохраняют прежние алгоритмы текущего upload для пояснения; они не подключаются одновременно с основными телами. Именованная сигнатура пишется `Name :: DATA`, type-token вариант — существующий `->`; публичный fn не возвращается.

В архиве нет исполняемого ядра LMX. Здесь написаны LMX-алгоритмы и конкретные интерфейсы интеграции, **но ни runtime-приёмка, ни скорость не подтверждены исполнением**. Общие операции metadata/type interning, postfix-head resolution и вызова надо связать с реальным ядром. Алгоритмы последовательностей, backtracking/captures, адаптации и кеширования не заменены непрозрачными вызовами готового движка.

## Приёмка и воспроизводимость

`python3 tools/rebuild_acceptance.py` синхронизирует нормативные наблюдения с действующими главами спецификации; все режимы LMX остаются NOT_RUN. `python3 tools/rebuild_catalog.py`, затем `python3 tools/assemble.py` и `python3 tools/check_static.py` пересобирают каталог/исходник и проверяют комплектность, литералы, скобки, cutters и зависимости. Это ограниченные source checks, не P0 и не LMX-компилятор.

Перед сборкой `python3 tools/sync_effects.py` разрешает повторно используемые
конечные списки `throws`, сверяет их договоры и сохраняет авторскую форму записи.
Внутренний банк `FxThrows` хранит общие списки; отчёт
`tests/effect_contracts.json` содержит разрешённые имена по методам.
Инструмент сохраняет заявленные консервативные контракты и не выдаётся за
полный вывод эффектов или проверку всех динамических вызовов и `catch`.
Сокращение формы не требуется для прохождения проверки; старый режим
`--normalize` включается только явно. На мой взгляд, подробные Throws — преимущество
языка: они предельно ясно показывают, какие ошибки может породить метод.
Обычная обязанность обработать объявленный исход либо передать его через
собственный `throws` остаётся в силе; [API](API.md#ошибки) объясняет границу.

После интеграции уже работающий R0 либо достигнутый обработчик сообщения обычным вызовом `FxAllExamples\run()` явно запускает семь групп подготовленных проверок: прежние пять, последовательности и адаптеры. Запуск программы всегда начинается с обычного L3 Thread R0 без DATA и пользовательских аргументов; имя этого метода не выбирает иной старт. Само чтение файла не выполняет проверки. Regex fixtures загружаются и запускаются по одному согласно их manifest, поскольку у независимых случаев могут совпадать локальные имена и разные ожидаемые ошибки. Каждый случай должен пройти четыре сочетания interpreter/native. До реального запуска в журналах остаётся NOT_RUN.

## Правило честного подсчёта

Для функционального usage-сценария сохраняются две полные LMX-формы одного
договора: процедурная показывает явный алгоритм, функциональная использует
общие операции и Expression. Контрольный язык использует реальную библиотеку
либо оператор с сопоставимым действием; самописный foreign helper из соседнего
документа не импортируется клиентом. Обе LMX-формы учитываются независимо,
включая полные Throws и ссылки на договоры фактически вызываемых методов.
При обоснованном совпадении минимальной формы хранится один исходник с двумя
равными записями метрик. Единое библиотечное тело не копируется ради двух стилей.

При сравнении реализаций считаются полные тела объявленного договора и
оговорённые зависимости. Сам статус «входит в ядро» не даёт исключения из
подсчёта. В PDF/XLSX все равные минимумы полного счёта сопоставимой строки
получают зелёный фон и подчёркнутое число; сокращения Throws при подсчёте нет.
Общие границы и охват 109 клиентских договоров указаны в
[правилах сравнения](../COMPARISON_RULES.md).

При этом архитектурно оптимальный LMX не переписывается ради совпадения алгоритма
контрольного языка. Собственные общие примитивы LMX — copy, merge, binding,
обычный вызов и работа с графом — законно остаются примитивами языка; их runtime
реализацию не разворачивают в каждом сравнительном листинге. Проверка границы
касается сокрытия специфической работы helper за коротким вызовом, когда другая
сторона показывает эту работу вручную, а не требования одинакового алгоритма.
