# LMX: Доменная модель и хранение данных

Python показывает компактные функции, dataclass и явные адаптеры; C# — records, интерфейсы и привычную организацию прикладного доступа к данным. LMX сопоставляется с обоими без обязательной иерархии классов.

19 исходных паттернов 16–34 сохранены отдельно. Листинги показывают одинаковую ограниченную задачу. Внешние БД и коллекции с методами, не заданными языком, перечислены как порты: их цена не считается нулевой. Транзакция БД отличается от последовательного turn Message. HTTP-профиль LMX существует; он доставляет запрос к прикладной границе и не создаёт автоматических гарантий хранения. Все листинги авторские; источники использованы для определения паттерна. LMX-фикстура заранее помещает зависимости и начальное состояние в фактический DATA владельца; входы с потенциальной неоднозначностью позиции передаются явно по имени. Например, account\debit(amount := 30). Листинги контролей рассчитаны на Python 3.10+, C# 12, Java 17 и Go 1.18+ там, где соответствующий язык присутствует.

## Каталог

### 016. [Repository](016_repository_comparision.md)

Доменный интерфейс коллекции скрывает способ получения объектов.

**Реализация используемого компонента:** [094. FindById — implementation](094_find_by_id_implementation_comparision.md)

**Сценарий:** Репозиторий получает две уже материализованные записи: id=7, cents=100 и id=9, cents=250. Найти id=9 и затем отсутствующий id=10.

**Наблюдение:** Первое обращение возвращает исходный объект id=9; второе — отсутствие. Сам поиск не создаёт новый экземпляр.

Во всех трёх клиентах готовый FindById — небольшой прикладной helper для последовательности записей с id, а доменная Account и граница Repository остаются клиентскими. Соседняя реализация раскрывает цикл, ранний возврат и отсутствие во всех языках. Это не сравнение готового LINQ с ручным циклом только в LMX.

### 094. [FindById — implementation](094_find_by_id_implementation_comparision.md)

Реализовать импортируемый поиск первой записи по целочисленному id.

**Примеры использования:** [016. Repository](016_repository_comparision.md)

**Сценарий:** Просмотреть упорядоченную последовательность записей, вернуть первую с нужным id или отсутствие.

**Наблюдение:** Для id 7 возвращается исходная запись 7; при повторном id возвращается первая; неизвестный id и пустой список дают отсутствие.

Во всех трёх языках написаны собственный цикл, сравнение id, ранний return и ветвь отсутствия. Python next/filter и C# FirstOrDefault не используются для реализации helper. LMX и Python требуют поле id структурно, C# выражает тот же нужный доступ через IIdentified.

### 017. [Unit of Work](017_unit_of_work_comparision.md)

Накопить изменения и записать их одной транзакцией.

**Сценарий:** Пометить id=7 значениями 120, затем 130, и id=9 значением 200; выполнить flush. Повторная пометка одного id заменяет предыдущее изменение.

**Наблюдение:** До flush записей в БД нет. Успешный flush записывает (7,130),(9,200) в одной транзакции и очищает dirty. При исключении dirty сохраняется, БД откатывается.

Python использует dict, C# Dictionary, LMX — переданную карту. Атомарность во всех трёх версиях принадлежит одному и тому же db.atomic контракту.

### 018. [Data Mapper](018_data_mapper_comparision.md)

Перевод между схемой строки и независимым доменным представлением.

**Сценарий:** В БД строка [7,1250]; доменный объект имеет именованные поля id и cents. Загрузить его, затем сохранить cents=1300.

**Наблюдение:** После load: id=7,cents=1250. После save в rowStore записана строка [7,1300]. Доменный объект не содержит ссылку на БД.

Маппинг находится в отдельном компоненте во всех языках. Создание record/dataclass в контролях соответствует созданию обычной Structure LMX.

### 019. [Active Record](019_active_record_comparision.md)

Объект строки содержит её данные, доменную операцию и сохранение.

**Сценарий:** Счёт id=7,cents=100 выполняет debit(30), затем save. Попытка debit(80) после этого отвергается.

**Наблюдение:** После первого debit значение 70, save пишет (7,70). Неверное списание не меняет 70 и не пишет БД.

Active Record соединяет правила списания и сохранение в одном объекте. В отличие от Data Mapper, объект знает свой порт хранения.

### 020. [Table Data Gateway](020_table_data_gateway_comparision.md)

Один шлюз обслуживает все строки таблицы.

**Сценарий:** Прочитать balance строки 7, затем обновить balance строки 9 на 200. SQL и параметры сосредоточены в шлюзе.

**Наблюдение:** Вызваны SELECT с id=7 и UPDATE с cents=200,id=9; данные не вставлены в текст SQL.

LMX объединяет операции структурой, Python и C# классом. Это шлюз таблицы, а не объект одной строки.

### 021. [Row Data Gateway](021_row_data_gateway_comparision.md)

Шлюз одной строки хранит её ключ и значения, но не доменные правила.

**Сценарий:** Шлюз строки id=7 получает новое значение cents=150 и вызывает update.

**Наблюдение:** UPDATE получает параметры (150,7). В шлюзе нет правила доступного баланса или списания.

Один экземпляр на строку отличает этот вариант от Table Data Gateway; отсутствие доменного debit отличает его от Active Record.

### 022. [DAO — Data Access Object](022_dao_comparision.md)

Прикладной код зависит от операций доступа, а не от устройства хранилища.

**Сценарий:** Один сервис читает баланс id=7 через DAO. Подставить адаптер БД с результатом 100, затем тестовый DAO с результатом 25.

**Наблюдение:** Сервис возвращает 100 и 25 без изменения своей реализации.

Структурная совместимость LMX, duck typing Python и интерфейс C# выражают одинаковую границу. DAO здесь возвращает scalar, а Repository обычно предоставляет доменную коллекцию.

### 023. [DTO — Data Transfer Object](023_dto_comparision.md)

Собрать разрешённые поля в одно передаваемое значение.

**Сценарий:** Доменная запись имеет id=7, cents=1250 и секретное поле token. Проекция export выбирает только id и cents.

**Наблюдение:** Результат содержит ровно id=7 и cents=1250; token и методы доменного объекта не попадают в DTO.

Во всех трёх вариантах проекция явная. Само наличие сериализатора не делает автоматическую выгрузку всего доменного графа подходящим DTO.

### 024. [Domain Model](024_domain_model_comparision.md)

Разместить бизнес-инвариант рядом с доменным состоянием.

**Сценарий:** Счёт с 100 единицами принимает debit(30), затем debit(80). Только неотрицательная сумма в пределах остатка разрешена.

**Наблюдение:** Первая операция оставляет 70; вторая завершается Funds/исключением и оставляет 70.

Данные и правило принадлежат одному доменному компоненту во всех языках; зависимости от БД нет.

### 025. [Transaction Script](025_transaction_script_comparision.md)

Одна процедура организует один прикладной запрос.

**Сценарий:** Перевести 30 из счёта 1 со 100 единицами на счёт 2 с 20 единицами; повторить в отдельной транзакции недопустимый перевод 200.

**Наблюдение:** Первый запрос атомарно даёт 70 и 50. Второй не меняет остатки и сообщает Funds.

Правило и последовательность работы с БД находятся в одной процедуре каждого языка. Объекты доменной модели не обязательны для этого паттерна.

### 026. [Table Module](026_table_module_comparision.md)

Один модуль вычисляет бизнес-логику над всеми строками набора.

**Сценарий:** Таблица содержит строки quantity=2,price=10 и quantity=3,price=7. Модуль вычисляет сумму заказа.

**Наблюдение:** Итог 41; строки остаются неизменными.

LMX и Python обходят строки, C# использует цикл с тем же умножением и сложением. Здесь важна единица организации логики, а не тип коллекции.

### 027. [Service Layer](027_service_layer_comparision.md)

Одинаковая прикладная операция доступна разным интерфейсам через одну границу.

**Сценарий:** CLI и HTTP-обработчик вызывают checkout(accountId=7,amount=30). Сервис загружает свежую доменную копию, выполняет debit и сохраняет её в транзакции.

**Наблюдение:** Оба входа выполняют одинаковую цепочку load → debit → save. При недостатке средств save не вызывается и транзакция откатывается.

Транспортные интерфейсы тонкие; сервис координирует домен и инфраструктуру. В отличие от Transaction Script, бизнес-правило debit вынесено в доменный объект.

### 028. [Identity Map](028_identity_map_comparision.md)

Одна сессия возвращает один объект для одного ключа.

**Сценарий:** Вызвать get(7) дважды, затем get(9); loader создаёт новый объект при каждом реальном чтении.

**Наблюдение:** Loader вызывается дважды. Два результата для id=7 имеют одну идентичность; объект id=9 другой.

Словарь Python, Dictionary C# и карта LMX хранят именно ссылки. Копирование объекта при каждом get уничтожило бы смысл паттерна.

### 029. [Lazy Load](029_lazy_load_comparision.md)

Загрузить значение при первом обращении и сохранить успешный результат.

**Сценарий:** Дважды прочитать holder.get; loader возвращает 0. В отдельном сценарии первая загрузка бросает исключение, вторая возвращает 0.

**Наблюдение:** В первом сценарии loader вызван один раз. Во втором ошибка не устанавливает loaded, поэтому второе обращение повторяет загрузку.

Во всех версиях одинаковый marker и одинаковый порядок: вычислить, сохранить, затем отметить loaded.

### 030. [Query Object](030_query_object_comparision.md)

Представить запрос данными и централизованно перевести его в параметризованный SQL.

**Сценарий:** Объект диапазона min=100,max=200 выбирает строки с cents внутри включительных границ.

**Наблюдение:** Драйвер получает SQL с двумя placeholders и параметры (100,200); данные 99,100,200,201 дают две подходящие строки.

Объект запроса не обязан строить строку конкатенацией. Все реализации сохраняют значения отдельно от SQL.

### 031. [Specification](031_specification_comparision.md)

Комбинировать предикаты, отделённые от проверяемого значения.

**Реализация используемого компонента:** [095. Specification combinator — implementation](095_specification_combinator_implementation_comparision.md)

**Сценарий:** Соединить nonnegative и below100 через AND; проверить -1,50,100.

**Наблюдение:** Результаты false,true,false. Правый предикат не вызывается, если левый дал false.

Все три клиента определяют конкретные nonnegative/below100 и импортируют готовый combinator для построения reusable-предиката. В LMX запись A both B делает композицию выражением; Python и C# используют вызов фабрики. Соседняя реализация сохраняет проверку значения и короткое замыкание явно во всех трёх языках.

### 095. [Specification combinator — implementation](095_specification_combinator_implementation_comparision.md)

Реализовать импортируемую бинарную композицию двух предикатов с коротким замыканием.

**Примеры использования:** [031. Specification](031_specification_comparision.md)

**Сценарий:** Сохранить две callable-ссылки и вернуть новый int-предикат. При каждом вызове проверить левую часть; правую вызывать только после true.

**Наблюдение:** nonnegative both below100 даёт false,true,false для -1,50,100. При false слева счётчик правых вызовов не растёт. Повторный вызов использует сохранённые ссылки.

LMX явно строит сохраняемый граф и выбирает владельца; Python closure и C# lambda сохраняют ссылки средствами языка. Все три тела показывают собственный AND через &&/and и не вызывают готовый both. Ни SQL-expression builder, ни скрытый AST evaluator не используется.

### 032. [Value Object](032_value_object_comparision.md)

Равенство определяется значением, а не адресом экземпляра.

**Реализация используемого компонента:** [096. Money value equality — implementation](096_money_value_equality_implementation_comparision.md)

**Сценарий:** Сравнить отдельно созданные Money(100,840) и Money(100,840), затем Money(100,978). Currency — числовой код валюты.

**Наблюдение:** Первые два значения равны, третье отличается. demo кодирует эти две проверки как 10; идентичность объектов для равенства не требуется.

Все три клиента создают два значения с одинаковыми компонентами и третье с другой currency, затем вызывают готовое равенство. Реализация вынесена симметрично и показана рядом: LMX — явный equals-операнд, Python — tuple-based Money и явный same, C# — readonly struct и явный Same. Ни размер клиента, ни размер реализации не выдаётся за стоимость универсального dataclass/record generator.

### 096. [Money value equality — implementation](096_money_value_equality_implementation_comparision.md)

Полностью показать конкретный двухкомпонентный Money и его импортируемое равенство.

**Примеры использования:** [032. Value Object](032_value_object_comparision.md)

**Сценарий:** Хранить read-only cents/currency и сравнить обе компоненты в указанном порядке. Defaults 100/840, альтернативная currency 978.

**Наблюдение:** Два независимо созданных Money(100,840) дают true; Money(100,978) даёт false. Прямая запись в компоненты не входит в разрешённый API.

Python использует базовый immutable tuple, запрещает instance dictionary через __slots__ и предоставляет read-only properties; same написан вручную. C# использует readonly struct/get-only properties и ручной Same. LMX использует готовые immutable primitive records и ручной оператор. Вспомогательная библиотека равенства не импортируется собственной реализацией; dataclass/record equality не подменяют показанный алгоритм.

### 033. [Optimistic Offline Lock](033_optimistic_offline_lock_comparision.md)

При сохранении проверить прочитанную версию и атомарно увеличить её.

**Сценарий:** Две сессии прочитали id=7,version=4. Первая сохраняет 120, вторая пробует сохранить 150 со старой version=4.

**Наблюдение:** Первый UPDATE меняет одну строку и версию на 5. Второй меняет ноль строк и сообщает Conflict; 120 сохраняется.

Во всех языках корректность обеспечивается одинаковой DB-операцией; локальная проверка версии перед обычным UPDATE была бы гонкой.

### 034. [Pessimistic Offline Lock](034_pessimistic_offline_lock_comparision.md)

Зарезервировать запись на время бизнес-сессии, не удерживая открытую SQL-транзакцию.

**Сценарий:** Сессия A получает для id=7 lease-токен 41. B получает отказ. После окончания A новая сессия получает токен 42; запоздалый save с 41 отвергается.

**Наблюдение:** В каждый момент только действующий владелец может сохранить запись. Старый токен не оживает после истечения lease.

Все варианты передают токен до места записи. Объект guard или процессный mutex без серверной проверки не защищает редактирование между HTTP-запросами.

## Границы сравнения

Размеры вычислены из трёх листингов каждого сравнения. В связанных парах использование готового компонента и реализация этого компонента посчитаны отдельно и одинаково для всех трёх языков. Runtime, HTTP-хост и БД не подменяются строкой импорта. Номера 1–85 сохранены из исходного списка, 86–90 — добавленные паттерны; номера выше 90 обозначают отдельные реализации библиотечных компонентов.
