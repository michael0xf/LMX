# Операции над последовательностями LMX

Редакция имён: см. [окончательный выбор имён](1/NAMING_2026-11-22.md). Прежний `splice`, возвращавший target, называется **`replaceRange`**. Новый **`splice`** выполняет ту же замену, но возвращает удалённый участок в новом контейнере. Оба принимают `(target; begin; end; values)`. Это разные результаты одного алгоритма; текстовый `replace` из ТЗ Pattern сохраняет свой собственный смысл.

**ТЗ для Fable · проект v0.4 · 22 ноября 2026 года**  
**Единый комплект: LMX-TZ-2026-11-22-postfix-1**

**Изменения v0.4:** типовые конструкторы записываются постфиксно: `T[]`, `T@`, `T@@` и далее. Типизированное построение использует `int[]: [1 2 3 4]` или `type[]: [copy(squares)]`; квадратная группа обязательна. Общий тип Structure / void-массива — `@[]`. Сохраняются общие объявления и безымянные формы `[]:`. Коды типов, указатели любой глубины и satisfies берутся из общего ядра. Отдельный toArray снят; интерпретируемые runtime-правки графа по-прежнему отделены от необязательной native-компиляции.

**Приоритет:** [ТЗ правки ядра](LMX_Array_Reference_Types_Core.ru.md) определяет актуальные постфиксные формы типов `T[]` / `T@`, общие ресиверы `[]:` / `@:`, интернирование int-кодов и таблицу проверенных типов. Его последние авторские уточнения заменяют прежние написания в этом файле и в документах 1/.

Цель — дать понятные операции над последовательностями чисел, произвольных значений и узлов программы, используя существующие Expression и обычные ресиверы LMX. Критерий — ясность смысла: `A * B` для поэлементного умножения, `filter(items := A; accepts := Positive\run)` для отбора, `replaceRange(target := Code; …)` для явного изменения структуры.

**Приоритетные уточнения автора для этого ТЗ:**

1. Универсальные операции принимают значения ссылочного типа `@`. Такая ссылка указывает непосредственно на `{type value}`, где `value` может быть примитивом или дескриптором. Массив `@[]` хранит эти указатели прямо. Это описание значения ссылки, а не утверждение, что всякая запись с символом @ означает взятие адреса.
2. Вид массива однозначно определяется по значению, на которое указывает `@`. Универсальный интерфейс не ограничивается отдельным «форматом последовательностей записей» и не требует от пользователя предварительно упаковывать плотный массив.
3. **Все виды массивов уже имеют изменяемую длину в ядре.** Capacity существует и хранится отдельно от дескриптора. Операции роста используют действующий механизм; новая разновидность DynamicArray не требуется.
4. `T[]` получает int-код интернированного типа; `T[]: [values]` создаёт Array; `T[]: name` объявляет uninit конкретного массива; `[]: name` — uninit «любого массива», включая обычную Structure / `@[]`. Эти четыре случая различаются.
5. `T@`, `T@@` и далее получают коды указательных типов. Prefix `@value` получает адрес места. Постфиксные конструкторы применяются слева направо: `int@[]` — массив указателей на int, `int[]@` — указатель на массив int. Структурное требование находится в голове объявления: `Struct@: ptr candidate`; массив — `type[]: array [values]`. Универсальное `@: ptr Struct` ссылается на сам Struct и не задаёт скрытое требование к другому candidate.
6. `replaceRange` возвращает исходный target, новый `splice` — самостоятельный внешний контейнер удалённых элементов с фактическим типом и профилем хранения target. Имена не являются совместимыми aliases; правила мутации общие.

Операции получают обычное значение по `@` и используют его существующий тип. Ни нового вида последовательности, ни обязательного объекта `items` вокруг неё, ни дополнительной упаковки каждой ссылки этот документ не вводит.

Документ предназначен для размещения **рядом с каталогом `1/`** и двумя другими ТЗ данного комплекта: [ядро](LMX_Array_Reference_Types_Core.ru.md) и [Regex](LMX_Regex_Operands.ru.md). Ссылки в документацию ведут в `1/`. База — комплект `docs_core_signatures_2026-11-22.tar.gz`, SHA-256 `d2575c4509d4da2f85ffa060694b883c795784584ef19a2b48f124ce347f4c8e`; в полученном архиве этот каталог называется `docs/`. ## 1. Общий интерфейс и состав работ

### 1.1. Одно правило для универсальных операций

Параметр, означающий произвольную последовательность, принимается через `@`. По указанному значению определяется действительный вид массива и способ доступа к его элементам.

Это относится к `items`, `source`, `values`, `first/second`, последовательности частей `parts`, строкам `rows` и другим аналогичным входам универсальных операций. Имя параметра описывает его роль, а не дополнительный контейнер в памяти.

`@` не отменяет предметного договора. `slice` требует последовательность; `map` — вызываемый transform; числовое умножение — допустимые числовые значения. Передача ссылки на число туда, где нужна последовательность, не создаёт автоматически одноэлементный массив.

Полные требования к пользовательским параметрам и результатам остаются действующими. Если `Square\run` принимает `int`, универсальный `map` передаёт ему целое обычным вызовом. Переписывать его параметр на `@` не требуется.

Новые имена — обычные объявления в том же текущем ядре. Отдельный пакет, реестр операций, механизм подключения или новая версия контейнера не вводятся.

### 1.3. Быстрый справочник

В примерах `A/B` — Arrays, `S` — произвольная допустимая последовательность, `F/P` — готовые ссылки на методы. Индексы начинаются с 0. Все интервалы **полуоткрытые**: начало включено, конец исключён.

| Намерение | Запись |
| --- | --- |
| Построить массив без переменной | `int[]: [1 2 3 4]` |
| Объявить место «любой массив» без значения | `[]: pending` |
| Получить код типа массива целых | `int[]` |
| Поэлементно перемножить | `A * B` |
| Прибавить ко всем элементам число | `A + 3` |
| Получить маску положительных элементов | `A > 0` |
| Выбрать по маске | `compress(source := A; mask := A > 0)` |
| Преобразовать каждый элемент | `map(items := S; transform := F)` |
| Отобрать по проверке | `filter(items := S; accepts := P)` |
| Свернуть слева | `foldl(items := S; seed := (0 record); step := F)` |
| Сохранить seed и все состояния свёртки | `scanl(items := S; seed := (0 record); step := F)` |
| Получить целые от 2 до 7 | `range(start := 2; stop := 8)` |
| Взять позиции 1, 2, 3 | `slice(source := S; begin := 1; end := 4)` |
| Выбрать позиции 2, 0, 2 | `select(source := S; indices := (2; 0; 2))` |
| Переставить все позиции | `reorder(source := S; permutation := (2; 0; 1))` |
| Выбрать с независимым копированием графа | `project(source := S; indices := (2; 0))` |
| Соединить части | `concat(parts := (A; B))` |
| Повернуть порядок | `reverse(source := S)` |
| Найти первый подходящий индекс | `index(items := S; accepts := P)` |
| Добавить в тот же контейнер | `append(target := S; values := A)` |
| Заменить участок и получить тот же target | `replaceRange(target := S; begin := 1; end := 3; values := A)` |
| Заменить участок и получить удалённые элементы | `splice(target := S; begin := 1; end := 3; values := A)` |

Полные пути `fun\const\map` и подобные применяются при необходимости различить конкретные объявления. В остальном используются прямые имена, как предусмотрено текущим ядром. Арифметический профиль и обычный последовательный вызов имеют явно описанные порядок и результат; квалификация не служит запретом плотных Arrays на универсальном входе.

## 2. Практические примеры

Квадратные списки в пояснениях — запись ожидаемых значений, а не новый синтаксис литералов. LMX-блоки ниже используют обычные декларации и вызовы; новые имена имеют контракты этого проекта. Пустые строки отделяют законченные верхнеуровневые блоки.

### 2.1. Сумма квадратов положительных значений

Определения callback остаются обычными типизированными методами:

~~~lmx
Positive:
    int: value
    return: int
    run:
        return: value > 0

Square:
    int: value
    return: int
    run:
        return: value * value

Addition:
    int: accumulated
    int: value
    return: int
    run:
        return: accumulated + value
~~~

Обработка плотного массива непосредственно:

~~~lmx
int[]: values [-2 0 3 5]
@: positive fun\const\filter(items := values; accepts := Positive\run)
@: squares fun\const\map(items := positive; transform := Square\run)
@: total fun\const\foldl(items := squares; seed := (0 record); step := Addition\run)
int: answer \total
~~~

`positive` содержит `[3,5]`, `squares` — `[9,25]`, `answer = 34`. Пользователь не выполняет промежуточного `records(values)`. Такой обязательный публичный адаптер не вводится.

Для обычной Structure с теми же целыми значения результата совпадают:

~~~lmx
@: values (-2; 0; 3; 5)
@: positive fun\const\filter(items := values; accepts := Positive\run)
@: squares fun\const\map(items := positive; transform := Square\run)
@: total fun\const\foldl(items := squares; seed := (0 record); step := Addition\run)
int: answer \total
~~~

`map` возвращает обычную последовательность `@` на результаты произвольных типов. `foldl` сохраняет существующий договор: `seed` и возвращаемое значение передаются ссылкой на значение. `(0 record)` здесь — существующий способ получить устойчивую ссылку на примитивный seed, а не упаковка входной коллекции в особый формат.

### 2.2. Когда Expression короче и яснее вызова

~~~lmx
int[]: a [2 5 9]
int[]: b [3 4 2]
@: products a * b
@: shifted a + 3
@: distance 20 - a
@: large a > 4
@: selected compress(source := a; mask := large)
~~~

Значения: `products = [6,20,18]`, `shifted = [5,8,12]`, `distance = [18,15,11]`, `large = [0,1,1]`, `selected = [5,9]`.

Для этих операций не нужны `.*`, `.+`, специальный broadcast-синтаксис или новый способ вызова функции. Расширение скаляра — явное уточнение профиля в §4, а не заявление, что оно уже реализовано.

### 2.3. Диапазоны и индексы

~~~lmx
@: positions range(start := 0; stop := length(values))
@: everyThird range(start := 0; stop := length(values); step := 3)
@: selected select(source := values; indices := everyThird)
@: middle slice(source := values; begin := 1; end := 3)
~~~

`range` создаёт обычный плотный `Array<int>`. Универсальный `select` принимает его прямо. `slice` возвращает новый внешний контейнер; `values` не изменяется.

### 2.4. Default callback не теряется

~~~lmx
Scale:
    int: value
    int: factor 3
    return: int
    run:
        return: value * factor
~~~

~~~lmx
@: scaled fun\const\map(items := (1; 2; 3); transform := Scale\run)
~~~

Результат `[3,6,9]`. `map` передаёт один явный actual — очередной элемент. Это не требование «у метода ровно один formal»: второй вход заполняется собственным default по обычному договору вызова.

### 2.5. Поиск и короткое замыкание

При `items = [2,4,5,8]` и проверке «нечётное»:

| Вызов | Результат | Проверенные элементы |
| --- | --- | --- |
| `any(items := items; accepts := Odd\run)` | `1` | 2, 4, 5 |
| `index(items := items; accepts := Odd\run)` | `some(value := (2 record))` | 2, 4, 5 |
| `count(items := items; accepts := Odd\run)` | `1` | 2, 4, 5, 8 |
| `all(items := items; accepts := BelowFive\run)` | `0` | 2, 4, 5 |

`some(value := (0 record))` означает найденный первый элемент. Отсутствие — существующий `none()`; индекс 0 не используется как признак отсутствия.

### 2.6. Состояния свёртки

Для `items = [1,2,3]`:

~~~lmx
@: states fun\const\scanl(items := items; seed := (0 record); step := Addition\run)
~~~

Получается `[0,1,3,6]`. Это существующий `scanl` с seed, а не inclusive numeric `scan`, для которого суммы равны `[1,3,6]`.

### 2.7. Тип массива, объявление и безымянное значение

Получение типа, объявление без значения и построение используют [общий договор ядра](LMX_Array_Reference_Types_Core.ru.md#forms):

~~~lmx
int: integerArrayType int[]
[]: pendingArray
int[]: pendingIntegers
int[]: values [2 3 7]
~~~

integerArrayType содержит обычный int-код типа. pendingArray имеет требование «любой массив», pendingIntegers — конкретный массив целых; обе переменные неинициализированы. values содержит готовый массив [2,3,7].

Общие формы также сохраняются:

~~~lmx
[]: generalArray [1 2 3]
@: generalReference [1 2 3]
[]: [1 2 3]
~~~

Первые две формы дают инициализированные переменные, третья — безымянную Structure / void-массив без имени. Обычная Structure и @[] — одно значение, поэтому общий []-вход и универсальный @-вход принимают её без преобразования или обёртки.

Выбор между `[]: Name`, `[]: [data]` и `[]: Name [data]` определяется написанным именем/группой до lookup и вычисления initializer. Группа `[Name]` не схлопывается до имени объявления. То же общее правило действует у типизированных голов `T[]:`. Оно не устанавливает глобальную зависимость смысла вызова, индексации или типа от одного пробела. См. [общий разбор](LMX_Array_Reference_Types_Core.ru.md#common-parsing).


Безымянный результат:

~~~lmx
int[]: [1 2 3 4]
~~~

Результат — один Array с элементами int, длиной 4 и значениями 1, 2, 3, 4. Имя не создаётся. Внутри Expression:

~~~lmx
@: doubled 2 * (int[]: [1 2 3 4])
~~~

Получается [2,4,6,8]. Только внешний результат имеет имя doubled.

Для squares с готовыми int-значениями 9 и 25:

~~~lmx
int[]: [copy(squares)]
~~~

Получается массив [9,25]. Квадратная группа явно собирает поток одной copy. По последней поправке автора формы `type[]: [copy(squares)]` и `Struct[]: [copy(squares)]` также требуют этой группы; безскобочный вариант не используется.

Copy сохраняет глубокое копирование, одну карту и действительные лексические отношения. Сборка потока не делает вторую copy и не превращает любую ссылку на вложенный Array в поток.

Обычное исполненное объявление внутри Expression по-прежнему возвращает своё значение:

~~~lmx
int: answer 1 + (int: temporary 5)
~~~

Результат answer — 6. Другой пример:

~~~lmx
int: answer 2 * (int: temporary 3 + 4)
~~~

Внутреннее значение — 7, внешнее — 14. Обычные scope, admission и однократное вычисление сохраняются. Передача декларационной формы как DATA, например `g(int: item producer())`, сама по себе не запускает initializer.

Новый toArray и отдельный механизм описаний элементов не нужны. Имя :: сохраняет действующий договор сигнатур; типы элементов используют общие полные требования.

### 2.8. Добавление и замена

~~~lmx
int[]: a [10 20 30]
append(target := a; values := (40; 50))
insert(target := a; position := 1; values := (11; 12))
replaceRange(target := a; begin := 2; end := 4; values := (99))
deleteAt(target := a; begin := 0; end := 1)
~~~

Последовательные состояния:

1. `[10,20,30,40,50]`.
2. `[10,11,12,20,30,40,50]`.
3. `[10,11,99,30,40,50]`.
4. `[11,99,30,40,50]`.

Формы `values := (40; 50)` передают готовые целые обычным универсальным способом. Целевой плотный Array принимает их по своему требованию `int`; не требуется предварительно создавать второй плотный Array.

Если нужны удалённые элементы, применяется новый `splice`:

~~~lmx
int[]: b [10 20 30 40]
@: removed splice(target := b; begin := 1; end := 3; values := (99))
~~~

Теперь b содержит `[10,99,40]`, а removed указывает на новый плотный int-массив `[20,30]`. Возвращённый descriptor отличается от descriptor b. При том же вызове `replaceRange` содержимое b было бы таким же, но результатом стала бы сама b. Для ссылочного target removed содержит исходные ссылки в новом внешнем `@[]`, без глубокой copy.

### 2.9. Те же операции над узлами программы

В этом фрагменте `Program` — граф, полученный обычным `sys\fromLmx(text)` либо уже доступный как значение, `Program\main` — выбранная исполняемая Structure, `Replacement` — последовательность новых узлов. Предварительная компиляция не является условием получения, чтения или изменения графа:

~~~lmx
@: selected select(source := Program\main; indices := (2; 0; 2))
@: independentPart project(source := Program\main; indices := (2; 0))
replaceRange(target := Program\main; begin := 1; end := 2; values := Replacement)
~~~

`selected` содержит исходные значения по исходным ссылкам. `independentPart` использует одну общую операцию copy выбранного графа. Ни чтение элементов, ни их перенос сами по себе не исполняют выбранные `if`, `for`, `merge`, initializer или метод.

Замена — обычная операция языка во время исполнения. Интерпретатор использует выбранный текущий фрагмент и выполняет предусмотренные проверки при достижении операций и вызовов; compile/endturn для подтверждения правки не нужны. Отдельный случай обновления машинной реализации описан в §9.

<a id="universal"></a>
## 3. Значения, массивы и универсальный доступ через @

### 3.1. Представление — действующее, общее для языка

| Значение | Где находится тип | Что находится в value / storage |
| --- | --- | --- |
| Примитив по `@` | В записи `{type value}` | Значение примитива |
| Массив по `@` | В существующей записи и описании массива | Дескриптор и его storage по действующему контракту |
| Structure / `@[]` | Тип каждого выбранного значения доступен по его ссылке | Непосредственные указатели на `{type value}` |
| Плотный Array T | Тип элементов задаётся существующим типом/описанием массива | Элементы T в плотном storage, без отдельного type code перед каждым элементом |

Обычная Structure и `@[]` — одно и то же значение по общему договору: отдельного преобразования, обёртки или различающего STRUCT/ARRAY-kind нет. В DATA записи `array(...)` и `array: ...` объявляют Structure, которая одновременно является массивом. Её обычное постоянное имя не становится присваиваемой ссылочной переменной. Название «последовательность» обозначает роль значения в операции; отдельной физической категории Sequence не требуется.

Плотный storage нельзя читать как `void**`. При этом его нельзя и отвергать в универсальном API лишь потому, что прежний helper предполагал массив указателей. Правильная реализация выбирает доступ по однозначно определённому типу значения, на которое указывает `@`.

**Все эти Arrays уже изменяемой длины.** Общий Lmx-дескриптор сохраняет parent/length/storage; capacity обслуживается существующей отдельной таблицей. `sys\resize` меняет length и при необходимости storage, `sys\reserve` обеспечивает capacity без изменения length. Descriptor сохраняет identity. Не добавлять capacity в header, скрытый префикс или новый growable-тип.

### 3.2. Как универсальная операция получает элемент

Общий алгоритм обхода получает длину и очередное значение по существующему описанию источника:

- Для Structure / `@[]` выбирается уже хранимая ссылка непосредственно на значение.
- Для плотного Array T читается элемент T через действующий типизированный доступ.
- Если обычному call transport нужна адресуемая запись примитивного значения, она подготавливается штатным механизмом значений/actuals с допустимым lifetime. Это не пользовательский формат коллекции и не обязательное предварительное копирование всего массива.
- Подготовленный native-вызов вправе передавать известное T непосредственно по своему обычному ABI. Универсальный контракт не требует создавать запись в арене перед каждым известным прямым вызовом.
- Ссылочное значение сохраняет указанную цель. Вокруг него не создаётся обязательный дополнительный `{value: @}` или иной контейнер только ради участия в обходе.

Это общий доступ к уже существующим значениям, а не постоянный вспомогательный граф программы. Сведения для доступа происходят из действующего типа, описания, дескриптора и обычного namespace.

### 3.3. Граница значения и выполнения

Выбор элемента возвращает значение, не запускает его. В частности:

- Структурный элемент передаётся callback целиком как один actual.
- Array, вложенная Structure, callable или узел кода не разворачиваются рекурсивно.
- Чтение поля с написанным receiver/initializer не означает исполнение этой формы.
- Callback вызывается только операциями, явно предусматривающими его вызов.
- Если callback возвращает callable, этот callable становится элементом результата; дополнительного вызова нет.

Нулевое значение, нулевая ссылка, пустая последовательность, void, `None` и `uninit:T` остаются разными случаями. `uninit:T` имеет только код типа и `sizeof(value)=0`. Перенос ссылки на такую запись не читает несуществующий payload. Чтение значения либо его принятие конкретным callback остаётся обычной проверкой, а не глобальной обязанностью всякого обхода.

### 3.4. Представление результатов

В этой версии выбран следующий явный договор:

| Операция | Результат |
| --- | --- |
| `map, scanl, zip, zipWith, flatMap, list` | Новая обычная Structure / `@[]` на значения результатов |
| `foldl` | Ссылка `@` на последнее значение аккумулятора; для пустого входа — seed |
| `filter, slice, reverse, select, compress, omit, reorder` | Новый контейнер того же профиля хранения элементов, что источник |
| `traverse` | Существующий Maybe: успешное значение — обычная последовательность `@` результатов |
| `groupBy` | Последовательность групп с полями key/items; items — обычная последовательность `@` |
| `project` | Результат одной общей copy после выбора |
| `transpose` | Новая последовательность колонок; колонки — обычные последовательности `@` |
| `concat` | При одинаковом плотном T у всех частей — плотный Array T; иначе обычная последовательность `@` |
| `range` | Плотный Array int |
| `T[]: [values]` / `T[]: name [values]` | Один массив конкретного типа по общему договору ядра; copy выполняется только там, где она явно заказана |
| `replaceRange`, `append`, `insert`, `deleteAt` | Та же ссылка target после изменения |
| `splice` | Новый контейнер удалённых элементов с фактическим типом элементов и профилем хранения target до записи |

Новый внешний контейнер самостоятелен. Его слот можно заменить, не заменяя соответствующий слот источника. Если оба контейнера хранят ссылку на одну изменяемую цель, изменение этой цели видно по обеим ссылкам.

Для плотных примитивов отбор копирует значения в новый storage; это не writable view исходных ячеек. Указатели на самостоятельные объекты сохраняют цели по обычным правилам.

Здесь «сохранить профиль хранения» означает сохранить вид элементов и способ их хранения, а не угадать новую многомерную форму. При линейном обходе рассматриваются непосредственные элементы в физическом порядке; length остаётся общим количеством элементов. Новый выбранный последовательностный результат имеет линейное описание. Операция не достраивает строки или shape по одной длине и не переписывает внешние описания размерностей. Вставка/удаление в плоском backing также не обещает автоматического пересчёта внешнего многомерного описания.

### 3.5. Типовые коды и соответствие массивов

`T[]` — обычный int-код типа, интернированный общим ядром. Он не является пустым массивом и не должен приниматься вместо готовой последовательности только по численному значению. `typeof` самого кода видит int; normalizer типовой позиции получает обозначаемый тип из payload. Если t хранит допустимый int-код, `t[]` и `t@` применяют соответствующие типовые конструкторы, а `@t` получает адрес самого int-места.

Конструкторы применяются слева направо:

| Запись | Требование |
| --- | --- |
| `int[]` | Массив int |
| `int@` / `int@@` | Указатель на int / указатель второго уровня на int |
| `int@[]` | Массив указателей на int |
| `int[]@` | Указатель на массив int |
| `int[][]` | Массив массивов int |

В `@[]` левое описание типа — символический атом @. Общий TYPE-role normalizer принимает такое описание наряду с именами, кодами и полными требованиями; он не ограничен bare_identifier и не выполняет address-prefix для получения этого типа. Результат использует уже существующий общий тип Structure / void-массива. Старое `[]@` больше не является его alias.

Для типовых требований действует авторское правило `A[] satisfies B[] ⇔ A satisfies B`. Направление, полные вложенные требования и контекст преобразований сохраняются. Проверенный результат типов может быть взят из общей таблицы satisfies; не создавать отдельный кеш совместимости в map или slice.

Успех отношения не меняет фактический stride исходного Array<A>. Чтение и запись используют его действительный тип; необходимые преобразования выполняются обычным путём при потреблении. Пустой Array<A> не становится совместимым с любым B только из-за отсутствия элементов.

`[]: pending` и `@[]: pending` различаются: любой массив против конкретного массива универсальных ссылок. Первый принимает и плотный Array, и обычную Structure / `@[]`. После получения значения общий Array-параметр использует его настоящий код. Для uninit действуют нулевой payload и обычная проверка достигнутого использования.

См. [коды типов](LMX_Array_Reference_Types_Core.ru.md#type-codes), [типовое соответствие](LMX_Array_Reference_Types_Core.ru.md#admission) и [общий разбор](LMX_Array_Reference_Types_Core.ru.md#common-parsing).

## 4. Expression и арифметика массивов

### 4.1. Новая грамматика не нужна

Существующие арифметические операнды, сравнения, индексация и присваивание сохраняют свой обычный разбор и приоритет. Постфиксные типовые конструкторы определяет общее ТЗ ядра; этот последовательностный профиль не добавляет своей грамматики поверх него. `*` остаётся поэлементным умножением Arrays. Конкатенация называется `concat`, а матричное умножение — `matmul`.

В v0.4 не вводятся точки Julia, comprehensions, специальный синтаксис среза, новый pipe-оператор или автоматическое превращение любого метода в инфиксный операнд.

`map(items := S; transform := F)` — обычный вызов. Запись `S map F` не объявляется синонимом: существующее объявление map не имеет operand-заголовка. Для обсуждаемого набора именованные параметры уже прямо показывают действие.

### 4.2. Стандартный operand ABI сохраняется

У обычного Expression-операнда остаются `left`, `right`, `PASS_ARGS_AS_IS`, `PRIORITY`. Подготовленные аргументы получают значения по существующему механизму; никаких специализированных parser-ветвей для Array не добавляется.

**Массив right в operand ABI и пользовательский Array как один actual — разные роли.** Параметр `right` остаётся предусмотренным протоколом вектором аргументов. Это не ограничение на вид массива, который может быть одним из этих аргументов.

Сохраняется единственное условное открытие справа: когда left — написанная анонимная Structure, а единственный right — тоже написанная анонимная Structure, открывается один внешний уровень только справа. Left остаётся целым. Именованные ссылки, возвращённые Arrays и вложенные значения не открываются из-за нового алгоритма над последовательностями.

Поэтому в основных примерах используются именованные actuals: `items := S`, `parts := (A; B)`. Обычные W/E для callable и подготовка операнда не подменяют друг друга.

### 4.3. Предлагаемый последовательностный профиль арифметики

Этот подраздел **дополняет** уже установленную поэлементную арифметику точными правилами. Универсальные операнды получают Array через @; вход не ограничен плотным представлением.

1. Для Array–Array берутся последовательности одинаковой длины. Нет усечения до min-length, циклического повторения короткого входа или автоматического растягивания единичного Array.
2. Допустимы плотные Arrays, обычные Arrays @ и смешанные пары этих представлений. Операция над каждой парой значений определяется их действительными типами и обычным скалярным контрактом. Одинаковый физический тип всего входа не является обязательным условием универсального операнда.
3. @[] может содержать значения разных типов. Каждая достигнутая пара должна допускать выбранную операцию; несовместимый элемент не пропускается и не заменяется нулём. Прежние скалярные правила преобразований сохраняются; нового автоматического продвижения типов этот профиль не добавляет.
4. Для Array–scalar и scalar–Array скаляр вычисляется один раз и участвует в каждой элементной операции. Порядок сохраняется: `20 - A` вычисляет `20 - A[i]`, а `A - 20` — `A[i] - 20`.
5. Если все последовательностные входы плотные и выбранный скалярный контракт заранее определяет единое полное требование результата R, результат — новый плотный Array R. Одинаковые int Arrays со стандартным сложением — обычный частный случай.
6. Если хотя бы один последовательностный вход — Structure / @[] либо единое плотное R не установлено контрактом, результат — новый обычный @[] на полученные значения. Нельзя вычислять пробный первый элемент или сканировать результаты ради неописанного угадывания общего типа.
7. Сравнения возвращают значения предиката по своему скалярному контракту — в используемом профиле int 0/1. Для плотных исходных int Arrays это плотная int-маска; для @[] — последовательность @ на int-проверки. Compress принимает обе.
8. Деление сохраняет скалярные тип результата, округление и отказы. Array сам по себе не вводит float-преобразование.
9. Исходные Arrays не изменяются. Пустой вход даёт пустой результат выбранного выше вида без элементных вызовов. Подготовка явных actuals и проверка их общих требований остаются обычными.
10. Несовместимость длин проверяется до элементных операций. Размеры и вычисление объёма не должны переполняться.
11. Чистые операции допускают векторизацию и параллельное выполнение, если сохраняются результат и требуемое поведение отказов. Для наблюдаемых эффектов применяется явно последовательный договор §5 и §8.

Например:

~~~lmx
@: a (2; 5; 9)
@: b (3; 4; 2)
@: products a * b
@: shifted a + 3
~~~

Значения — [6,20,18] и [5,8,12], а результаты здесь являются обычными Arrays @. Плотные версии того же примера приведены в §2.2. Во всех случаях элементы читаются по существующему типу, а не как числовые адреса указателей.

Этот пример намеренно использует ссылки a/b. Форма `(2;5;9) * (3;4;2)` не объявляется новой специальной парой массивов: у двух написанных анонимных групп по-прежнему действует условное открытие right из §4.2. Расширение алгоритма операнда не меняет его группировку или количество подготовленных actuals.

Этот профиль описывает последовательностную, то есть одномерную по смыслу, обработку. Многоосный broadcasting не вводится. Размерности не восстанавливаются из length и не добавляются в header; существующие многомерные Arrays и их собственные операции не отменяются.

### 4.4. Присваивание — обычное

`result := A + B` присваивает полученную ссылку выбранному месту. Оно не означает автоматическую поэлементную запись в прежний Array result.

Составное присваивание продолжает использовать обычный договор места и операции. Этот документ не приписывает `+=` отдельную гарантию изменения старого backing. Когда важна identity целевого контейнера, применяется явно изменяющий ресивер §7.

<a id="existing"></a>
## 5. Существующие ресиверы и их расширение

Ниже сохранены нынешние имена и параметры. Общее изменение — **получение элементов любого допустимого вида Array через универсальный @-вход**. Текущий helper, который напрямую читает `items[i]` как указатель, необходимо обобщить; его сегодняшнее предположение не является ограничением языка.

### 5.1. Преобразование, отбор и накопление

| Ресивер | Порядок / результат |
| --- | --- |
| `map(items; transform)` | По одному явному actual на элемент, слева направо; новая последовательность результатов |
| `filter(items; accepts)` | Один предикатный вызов на элемент; устойчивый отбор; результат сохраняет профиль хранения источника |
| `foldl(items; seed; step)` | Шаг получает два явных actuals: прежний аккумулятор, элемент; строго левая свёртка |
| `scanl(items; seed; step)` | Тот же шаг; результат содержит seed и n последующих аккумуляторов |
| `zip(first; second)` | До меньшей длины; элементы — пары с полями first и second |
| `zipWith(first; second; combine)` | До меньшей длины; combine получает два явных actuals |
| `flatMap(items; next)` | next вызывается один раз на элемент; возвращённые последовательности объединяются на один уровень |
| `traverse(items; next)` | next возвращает существующий Maybe; остановка на первом none |
| `groupBy(items; keyOf; sameKey)` | keyOf один раз на элемент; сравнение ключей явным sameKey; устойчивый порядок групп и членов |

Фильтр использует int-проверку: 0 — не принять, любое ненулевое значение — принять, как в нынешнем алгоритме. Это не неявная truthiness произвольной Structure.

`zip` сохраняет нынешнюю форму пары, а не превращается в плоский неименованный tuple. Для элементов исходной Structure поля пары используют ссылки на исходные значения. Для плотных примитивов необходимое сохраняемое значение представляется обычной записью примитива; адрес внутрь плотного storage не выдаётся за адрес самостоятельной `{type value}`.

`scanl` хранит ссылки на возвращаемые состояния. Если шаг возвращает одну и ту же изменяемую цель, в истории могут быть ссылки на эту же цель. Глубокие снимки не возникают автоматически.

Пустой foldl возвращает исходный seed без callback. Пустой scanl содержит один seed. Пустые map/filter/zip/flatMap дают пустой результат установленного вида.

Traverse и groupBy сохраняют текущие формы результатов. При успехе traverse возвращает Maybe обычной последовательности @. Каждая группа groupBy имеет поля key и items; items — обычная последовательность @ членов. Плотный источник не делает эти вложенные результаты обязательными плотными Arrays.

### 5.2. Выбор и перестановка

`select(source; indices)`, `omit(source; indices)` и `reorder(source; permutation)` расширяются на все подходящие Arrays. Индексы принимаются через `@` как последовательность целых: допустим и плотный Array int, и обычная Structure с целыми значениями.

Существующие правила сохраняются:

- `select` разрешает повторы; порядок результата задаёт список индексов.
- `omit` сохраняет порядок невыбранных элементов; повторение индекса исключения не удаляет дополнительные элементы.
- `reorder` требует полной перестановки: нужная длина, допустимые индексы, отсутствие повторов.
- Индексы полностью проверяются до построения наблюдаемого результата.
- Для Structure / `@[]` сохраняются непосредственные ссылки на выбранные значения; для плотного Array — выбранные значения в новом типизированном storage.

`project(source; indices)` означает выбор и **одну общую copy**. Общие цели, циклы, копируемые лексические владельцы и существующие исключения разделения следуют обычной copy. Нельзя заменить это на независимые copy для каждого выбранного поля.

### 5.3. List, transpose и готовые аргументы

`list(values := S)` получает любую допустимую последовательность и создаёт новый обычный Array `@` на её значения. Для входной Structure это прежний поверхностный внешний контейнер. Для плотных примитивов создаются необходимые самостоятельные примитивные значения. `list` может использоваться для явно нужного представления; он **не обязателен перед map/filter/foldl**.

`transpose(rows := R)` работает с последовательностью строк, каждая из которых является последовательностью. Все строки имеют одинаковую длину. Элементы строк читаются тем же универсальным доступом. Результат — последовательность колонок из обычных значений. Пустой внешний R даёт пустой результат; n пустых строк дают ноль колонок. Это не неявный reshape плоского прямоугольного Array.

Обобщить входные последовательности actuals в `apply(operation; args)` и prefix в `partial` тем же способом, где они по своему договору уже принимают готовые значения. Подготовка actuals остаётся внутренним механизмом обычного вызова. Формальные типы F, defaults, missing actuals и declared exits не стираются.

Для внутренних входов вроде `attempt` разрешён конкретный служебный формат уже подготовленных actuals. Его нельзя выдавать за обязательный пользовательский формат всякой коллекции. Не накладывать W/E повторно на уже выбранный элемент, являющийся Structure.

<a id="new"></a>
## 6. Новые обычные ресиверы

Обязательные параметры новых ресиверов получают явно; отсутствие обязательного actual не заполняется случайным одноимённым local. Собственные default, указанные ниже, сохраняются. Служебные места реализации private. Эти требования не меняют политику пользовательских входов переданного callback.

### 6.1. range(start; stop; step := 1)

Возвращает материализованный плотный Array int.

- При step > 0: `start, start+step, …`, пока значение < stop.
- При step < 0: те же шаги, пока значение > stop.
- step = 0 всегда отклоняется.
- Равные start/stop и направление, не ведущее к stop, дают пустой Array.
- Stop не включается; отрицательные целые разрешены.
- Переданные start/stop/step вычисляются один раз.
- Количество и требуемый объём вычисляются без wraparound.

Не вычислять ненужный следующий элемент после последнего включённого. Например, `range(MAX_INT-1; MAX_INT; step := 2)` содержит ровно один элемент; вычисление несуществующего `MAX_INT+1` не должно создавать искусственный отказ.

Это обычный результат, а не lazy Range, новый вид iterator или грамматическое значение двоеточия.

### 6.2. slice(source; begin; end)

Возвращает новый контейнер непосредственных элементов с индексами `begin <= i < end`.

Требуется `0 <= begin <= end <= length(source)`. Пустой интервал разрешён, включая конец массива. Отрицательные индексы не отсчитываются от конца; выход за границу не обрезается.

Профиль хранения результата совпадает с источником. Для произвольного шага используется `select` с `range`; дополнительный slice-синтаксис не нужен.

Нынешний внутренний `FxSlice\slice(values; start; count)` имеет другой третий аргумент. Новый публичный вход вызывает общий алгоритм через проверенное `count = end - begin`; переименовывать count в end без изменения алгоритма нельзя.

### 6.3. reverse(source)

Возвращает новый внешний контейнер в обратном порядке, сохраняя профиль хранения. Пустой и одноэлементный входы допустимы. Источник не меняется, цели ссылок не копируются глубоко и не переподчиняются.

### 6.4. concat(parts)

`parts` — последовательность последовательностей, переданная одним обычным actual. Соединяются только непосредственные элементы частей в указанном порядке.

Правило результата:

1. Непустой parts, все части — плотные Arrays одного и того же полного T: новый плотный Array T.
2. Все остальные допустимые сочетания, включая смешанные плотные Arrays и Structures: новый обычный Array `@` на значения.
3. Пустой parts: пустая обычная Structure / `@[]`.

Пустая плотная часть по-прежнему несёт своё T и участвует в выборе профиля. Никаких числовых преобразований ради угадывания «общего типа» нет. Если нужен конкретный плотный результат смешанного входа, применяется существующий ресивер [] с выбранным требованием к элементам и обычными допустимыми преобразованиями.

Вложенный Array внутри одной части остаётся элементом; рекурсивного flatten нет. Источники не меняются. На ссылочном результате сохраняются цели и, где уже есть самостоятельная запись, её identity.

Не реализовывать concat через merge: соединение физических элементов не сопоставляет имена полей и не выполняет глубокую модельную композицию.

### 6.5. compress(source; mask)

Принимает источник и последовательность int-проверок одинаковой длины. 0 исключает элемент, ненулевое значение включает.

Результат — устойчивый выбор с тем же профилем хранения, что source. Mask может быть плотным Array int либо обычной последовательностью целых по `@`. Её значения проверяются по действующему типу; массив ссылок не считается маской только потому, что сами адреса ненулевые.

Длина и типы mask проверяются до формирования результата. Пустая маска допустима ровно для пустого источника.

Отдельное имя не даёт перепутать `indices = [0,1]` с маской `[0,1]`. Существующий select продолжает понимать эти числа как индексы.

### 6.6. any / all / index / count

Все четыре ресивера имеют параметры `items; accepts`. Accepts получает один явный actual — очередное значение; возвращаемая int-проверка читается как 0/ненулевое.

| Ресивер | Порядок и остановка | Пустой вход |
| --- | --- | --- |
| `any` | До первого true; int 0/1 | 0 |
| `all` | До первого false; int 0/1 | 1 |
| `index` | До первого true; Maybe нулевого индекса | none() |
| `count` | Все элементы слева направо; число true | 0 |

После решающего элемента последующие callbacks не вызываются. Сам callback не форсируется заранее для «определения типа».

Index возвращает существующий Maybe непосредственно. Present value — обычная ссылка на int-индекс: `some(value := (i record))`. Не добавлять новый SearchResult, sentinel −1 или вторую оболочку вокруг Maybe.

### 6.7. Конструирование через общее ядро T[]

Применяется типизированный ресивер ядра:

~~~lmx
int[]: [1 2 3 4]
int[]: named [1 2 3 4]
int[]: pending
[]: anyArray
~~~

Первая форма создаёт значение без имени, вторая — именованное значение, третья — uninit конкретного Array-типа, четвёртая — uninit «любого массива», включая обычную Structure. Общий безымянный вариант `[]: [data]` также сохраняется; `[]: name [data]` и `@: name [data]` дают инициализированные переменные, способные указывать на такую Structure. Код этого конкретного типа получается выражением `int[]` без двоеточия.

Обязательные следствия для последовательностных операций:

- Квадратная группа — список элементов конструктора. `int[]: []` создаёт готовый пустой массив, а `int[]: pending` не содержит значения и не подменяется пустым Array.
- `T[]: [copy(S)]` и `T[]: name [copy(S)]` принимают обычный поток внутри группы. Copy/merge сохраняют свои договоры, одну карту каждой операции и реальные отношения владельцев.
- `@[]: [S]` содержит одну ссылку на S; `@[]: [copy(S)]` содержит поля выданного потока. Автоматического spread любой ссылки нет.
- В Expression результат конструктора потребляется один раз. Получение type-id, построение Array и работа его будущего callback не сливаются в одну операцию.
- Способ доступа к исходному значению через @ не является типом элементов создаваемого массива. Фактический вид элемента задан общим кодом T[].
- Типизированная голова `Struct[]: [copy(S)]` использует общее полное требование. Bare `[](Struct)` остаётся compact-объявлением `[]: Struct`, а bare `@(Struct)` — `@: Struct`; они не являются типовыми конструкторами.
- Группы в `(Struct)[]` и `(Struct)@` сохраняют обычную семантику группы. Снятие такой группы или равенство результата негруппированному `Struct[]` / `Struct@` не обещается; применяется общий normalizer к фактически полученному описанию.
- Полные требования, включая указательные типы `T@`, `T@@`, `T@@@` и любой дальнейшей глубины n, не обрезаются при хранении, обходе, выборе или построении результата. `int@@[]` — массив указателей второго уровня на int. Универсальные объявления `@: p`, `@@: p` и далее сохраняют свой обычный договор. Частной реализации указательных типов для коллекций нет.
- В чистом графе сохраняются написанные типовые операции, головы, группы и copy/merge. Конструктор выполняется при достижении; чтение source-формы его не запускает.

Нормативные детали и миграция находятся в [основном ТЗ ядра](LMX_Array_Reference_Types_Core.ru.md). Здесь не создаётся второй контракт типов, новый toArray, публичный elementType-протокол либо альтернативный parser.

<a id="mutation"></a>
## 7. Явное изменение последовательности

### 7.1. Один основной алгоритм, два результата

`replaceRange(target; begin; end; values)` заменяет участок `[begin,end)` непосредственными значениями values. Возвращается **та же ссылка target**.

Предусловие: `0 <= begin <= end <= length(target)`. Итоговая длина:

`oldLength - (end - begin) + length(values)`.

Все величины проверяются без переполнения. Values — обычная последовательность любого допустимого вида, получаемая по `@`.

Для target вида Structure / `@[]` записываются непосредственные ссылки на значения. Не проверяется соответствие прежнему имени, типу или требованию физического слота. Для плотного target T каждый вставляемый элемент должен быть допустимым T без скрытого пользовательского преобразования; весь набор проверяется до изменения target.

`splice(target; begin; end; values)` принимает те же четыре аргумента и выполняет ту же замену. Его результат — **новый внешний контейнер значений исходного участка `[begin,end)`**, снятых до первой записи или resize, способных их изменить. Он не возвращает target и не добавляет отдельный mutator engine.

Результат сохраняет фактический тип элементов и профиль хранения target:

- Плотный T[] даёт новый плотный T[] с копиями удалённых значений.
- Structure / `@[]` даёт новый `@[]` с исходными ссылками на записи. Идентичности целей, их полные типы и настоящие lexical parent сохраняются.
- При `begin == end` возвращается инициализированный пустой контейнер того же профиля. Это не null и не uninit.
- При удалении всего `[0,length(target))` возвращаются все прежние элементы. Descriptor самого target остаётся прежним.

Snapshot поверхностный. Замена внешнего слота результата не меняет слот target, но изменение общей ссылочной цели видно через оставшиеся ссылки на неё. Снимок не создаёт нового окружения, AST или глубокую copy. `replaceRange`, которому удалённый результат не нужен, не обязан выделять такой контейнер.

### 7.2. Читаемые специализированные входы

| Ресивер | Эквивалентная операция |
| --- | --- |
| `append(target; values)` | replaceRange с begin = end = исходная length(target) |
| `insert(target; position; values)` | replaceRange с begin = end = position |
| `deleteAt(target; begin; end)` | replaceRange с пустыми values |

Все три возвращают ту же ссылку target. Их реализация использует общий алгоритм, без собственного варианта правил алиасов или типов.

Нынешний внутренний `FxAppend\append(first; second)` строит новый контейнер и не меняет first. Его существующий смысл сохраняется; публичное `append` не выдаётся за простой новый экспорт этого helper.

### 7.3. Алиасы и перекрытия

Наблюдаемый результат определяется значениями выбранного участка values **до первой записи этой операции в target**. Для `splice` к этому добавляется snapshot исходного удаляемого участка: он также фиксируется до сдвигов, resize и любых записей, способных его изменить.

Если values совпадает с target или ссылается на затрагиваемое хранение, реализация фиксирует только необходимые исходные элементы/ссылки до сдвига и resize. Для неперекрывающегося случая отдельный буфер вставляемых values не обязателен. Новый внешний removed-контейнер `splice` остаётся частью его результата и не подменяется view внутрь target.

Таким образом, `append(target := A; values := A)` добавляет исходные элементы A ровно один раз. Рост длины не продлевает собственный обход бесконечно.

Разрешённый временный буфер не является копией лексического окружения, source AST или «рабочим графом». Объекты по сохранённым ссылкам не копируются глубоко.

Ошибки границ, вида и вставляемых типов выявляются до изменения target. Уже выполненные эффекты подготовки actuals не откатываются. Это не общая транзакция над программой и не откат чужих side effects.

После успешной подготовки выполняются необходимые обычные resize/reserve и записи. Внутри commit-фазы не вызываются пользовательские converters, callbacks или initializer. Ошибки ресурсов остаются обычными системными отказами; для них не вводится обещание общей транзакционности.

### 7.4. Identity, указатели и parent

Descriptor target сохраняет identity. Storage может переместиться по действующему механизму capacity, уже общему для всех видов массивов.

L3-ссылка на элемент хранит descriptor и **индекс**. После вставки перед этим индексом она обозначает новое содержимое той же позиции, а не следует за прежним логическим элементом. После сокращения длины доступ по недопустимому индексу проходит обычную bounds-проверку.

Отдельно сохранённая `@`-ссылка на значение продолжает указывать на это значение, даже если соответствующий элемент исключён из контейнера, в пределах обычного lifetime. Raw L2-адреса автоматического ремонта не получают.

Вставка ссылок на графовые значения не меняет их настоящий parent. Если нужен новый лексический владелец, это отдельная структурная операция по действующим правилам copy/merge.

## 8. Вызов пользовательских методов

### 8.1. Обычный вызов с известным числом явных actuals

Map/filter/query передают один явный actual. Foldl/scanl/zipWith передают два. Это число **переданных actuals**, а не искусственная фиксированная арность всех допустимых кандидатов.

Действуют собственные полные требования, defaults, required/private и объявленные exits выбранного метода. Дополнительный допустимый optional-вход не делает callback несовместимым.

В частности:

- Явный actual подавляет initializer соответствующего входа.
- Пропущенный вход с собственным default сохраняет этот default.
- Неиспользуемый computed default не исполняется ради общего транспорта.
- Missing actual не заменяется нулём, пустой Structure, null или искусственной записью uninit.
- Private фильтрует неявное связывание по действующему правилу; явная передача остаётся разрешённой.
- Exact-signature adapters сохраняют конкретные Ti и R. Универсальный @-вход фабрики не превращает подпись созданной функции в «всё принимает и возвращает @».

Состояние служебного обхода защищено от случайного связывания с пользовательскими именами. Нельзя исправлять адаптеры удалением всего private либо объявлением всех входов callback required/private.

### 8.2. Порядок, эффекты и состав источника

Обычные последовательные ресиверы выполняют callbacks в порядке физических позиций, слева направо, в одном Message. Прежний вызов заканчивается до следующего. Они не становятся параллельными или ленивыми по скрытому решению реализации.

На время обхода callback не меняет **состав обходящейся последовательности**: её length и хранимые элементы. Это сохраняет текущую предпосылку коллекционных алгоритмов и распространяется на плотный профиль. Изменения иных объектов допустимы по обычным требованиям и видны последующим вызовам.

Глубокий snapshot источника при начале операции не создаётся. Проверка нарушения предпосылки не требует новой системы отслеживания всех записей; нужны сформулированный договор и корректные положительные регрессии.

Изменяемая цель, на которую ссылается элемент, и слот самой последовательности — разные места. Сохранение порядка не означает автоматического снимка всех достижимых значений.

### 8.3. Структурные значения, DATA и контекст

Вложенная Structure передаётся одним actual. Внутренний транспорт не применяет к ней W/E заново и не исполняет её.

Фактический DATA/parent callback сохраняется. Контейнер items, внутренний engine и место вызова не становятся его новым лексическим владельцем.

Разрешённое динамическое связывание определяется действующей цепочкой вызовов. Если операция добавляет собственный ordinary call, она не обещает автоматически пропустить этот уровень и восстановить alias к любому внешнему caller. Глобальный снимок окружения и transitive closure пользовательских locals не вводятся.

### 8.4. Отказы

У существующих общих вызовов сохраняется `FxCallFailure` с первоначальным именем и payload объявленного отказа. Для новых query-ресиверов используется тот же путь. Exact adapters восстанавливают объявленные exits согласно приоритетному ТЗ.

После отказа на элементе i элементы i+1 и далее не обрабатываются. Частичный результат map/filter/scan не возвращается как успех. Уже совершённые эффекты callbacks сохраняются.

Implicit/system failure не превращается автоматически в FxCallFailure, none, false, retry или универсальный Result. Ошибка — не «элемент не подошёл».

<a id="code"></a>
## 9. Код как массив: изменение, исполнение и native

### 9.1. Основной путь — обычный граф и интерпретатор

`sys\fromLmx(text)` получает полный граф из текста через существующий parser/builder. После этого граф — обычное значение языка: он доступен чтению, композиции, замене фрагментов и интерпретируемому исполнению во время runtime.

Изменение уже имеющегося графа не требует обратного прохода через toLmx/fromLmx. Текстовый fromLmx нужен, когда исходным материалом является текст; replaceRange и обычная графовая запись работают непосредственно с существующими значениями.

Интерпретатор выполняет предусмотренные проверки типов, приёма, доступа и достигнутых вызовов по максимуму своего обычного договора. Для обычного изменения графа и последующего интерпретируемого использования не требуется предварительный `sys\compile`, отдельный `sys\check` или переход через endturn.

Это не предварительное доказательство корректности всех будущих применений графа. Проверяются достигнутые операции и вызовы; неисполненные ветки, computed defaults и произвольные test не запускаются заранее для выдачи графу глобального статуса «проверен».

### 9.2. Граф остаётся полным и непосредственно изменяемым

Чистый граф отражает исходники: if, for, merge, copy, import, вызовы и декларации находятся в нём как написанные структуры; конечные примитивы представлены обычными {type value}. После явной runtime-правки он содержит новые записанные фрагменты. Слово «чистый» не означает «замороженный до компиляции».

Select/slice/reorder/concat/replaceRange работают с ним через те же значения и массивы. Новый AST, callable-граф, persistent data image или «рабочий граф» не требуются.

Различаются обычные действия:

1. Новый внешний контейнер ссылок не меняет исходные слоты.
2. Copy/project создаёт копируемый граф по одной общей карте.
3. Явная запись в выбранный граф меняет его содержимое.
4. Присваивание local активации меняет своё место и не публикуется в граф.

У скопированного метода остаётся его скопированный необходимый лексический владелец. Собирающий контейнер не становится родителем метода только из-за помещения туда ссылки. Раздельные операции copy имеют свои карты; одна общая операция использует одну карту.

Графовая запись не запускает отдельную подготовку или перекомпиляцию native, не очищает entry и не обновляет reverse dependencies. Обычные проверки самой операции и последующего интерпретируемого использования сохраняются. При физической записи в слот Structure не добавляется проверка требования прежнего содержимого слота.

### 9.3. Необязательная подготовка новой машинной реализации

Именно к этому отдельному случаю относится упоминание compile/endturn: программа хочет обновить машинную реализацию изменённого кода.

- Явно компилируется нужная общая единица, например `sys\compile(Program)`, включая необходимые вызывающие методы и цели.
- После успешной компиляции и endturn следующий вход использует подготовленное native-обновление.
- Один endturn не обнаруживает изменения и не выполняет компиляцию.
- Компиляция только B не переписывает старый прямой C-вызов A→B внутри уже скомпилированного A.
- Действующий старый native и интерпретируемые обращения к изменённому графу не получают искусственно одинаковой видимости через дополнительный snapshot.
- Старые активные native-кадры и их finally завершаются по действующему договору.

Эта процедура не является разрешением на графовую запись или на интерпретацию её результата. `sys\endturn()` сохраняет и свой обычный смысл выхода к границе turn; здесь описано только его участие в обновлении машинной реализации.

Полный граф и бинарник методов сохраняют свою архитектуру. Наличие бинарного R0 и бинарной реализации интерпретатора не означает необходимости компилировать каждый полученный или изменённый граф.

## 10. Ошибки, время жизни и реализация

### 10.1. Ошибки операций

Для уже существующих ресиверов сохранить объявленные имена ошибок. Для нового API закрепить следующий минимальный договор:

| Условие | Отказ |
| --- | --- |
| Недопустимый физический индекс или границы slice/replaceRange/splice | `ReceiverIndex` |
| Не полная перестановка | Существующий `ReceiverPermutation` |
| Несовпадение длин числовых Arrays / mask; непрямоугольные rows | `FxShape` |
| Недопустимый или неподдерживаемый type token | `FxTypeToken` |
| Нулевой step range | Новый обычный объявленный `SequenceStep` |
| Нельзя представить размер/длину без переполнения | Новый обычный объявленный `SequenceSize` |
| Элемент не подходит плотному target либо mask содержит не int | Новый обычный объявленный `SequenceElement` |
| Callback accepts нового query вернул значение не int | `FxPredicate` после явной проверки типа полученного результата |
| Объявленный отказ пользовательского callback | Существующий `FxCallFailure` |

Новые имена — обычные объявленные отказы, не новый механизм исключений. Ошибки непосредственной скалярной арифметики, admission пользовательского метода, системные ограничения памяти и implicit failures сохраняют свои действующие каналы.

В новых query тип результата accepts проверяется явно до потребления как int. Это не перехват и переименование implicit failure, уже возникшего при вызове или возврате из callback. Существующий filter сохраняет свой канал обычного принятия результата в int; этот документ не заменяет его автоматически на FxPredicate.

Предметный отказ «ожидалась последовательность» выдаётся обычным приёмом/проверкой этого требования. Случайный raw адрес не принимается как допустимое значение только из-за машинного размера указателя.

### 10.2. Владение и время жизни

Новые результаты используют обычные Message/arena-правила. Ссылка не продлевает жизнь завершившейся активации сама по себе.

Сохраняемое примитивное значение не может указывать на уже завершившийся C-stack local. Перенос и возврат ссылок не разрешают скрытую глубокую copy всего окружения для исправления lifetime.

Результат с исходными ссылками — самостоятельный внешний контейнер, но не обещание независимости всех достижимых объектов. Для независимого графа предусмотрены явные copy/project.

Char Array обрабатывается как Array физических char-элементов точной длины. Внутренний NUL — обычный элемент, терминатор не добавляется. Slice по char-элементам не объявляется Unicode-срезом: для позиций Unicode scalar values используется явно выбранный текстовый профиль из Regex ТЗ.

### 10.3. Общие исполнители и отсутствие лишней работы

Расширять общий доступ к элементу и обычную подготовку вызова, а не создавать отдельные реализации семантики для каждого массива и каждого режима исполнения.

Не вводить обязательную компиляцию, глобальный validation status графа или общий check-pass перед обычной графовой записью и интерпретируемым использованием её результата. Проверки конкретной операции, включая границы и тип принимаемого элемента, остаются.

Приёмочные проверки охватывают interpreter→interpreter, interpreter→native, native→interpreter и native→native. Интерпретатор применяет предусмотренные проверки при исполнении; подготовленный native сохраняет свой действующий договор и прямые вызовы. Это не обещание одинакового автоматического runtime-validation во всех четырёх случаях.

Разрешены обычные оптимизации, сохраняющие значения, identity, порядок эффектов и отказы: прямой typed load, устранение неиспользуемых промежуточных результатов, предварительный reserve, векторизация чистой числовой операции. Они не требуют предварительно создавать массив упаковок для всего источника.

Нельзя объявить обязательными:

- Универсальный объект List/Sequence с полем items.
- Новый persistent граф подготовленных элементов.
- Type tag в каждом плотном элементе.
- `records(source)` перед каждым универсальным вызовом.
- Переписывание Ti/R пользовательского callable в @.
- Скрытые запуск компилятора, dirty/invalidation, публикацию frame locals или повторное исполнение выбранных source-узлов.

Потребовавшийся самостоятельный результат, краткоживущая подготовка actuals и временные значения перекрывающейся вставки имеют свои обычные роли; это не дополнительное представление всей программы.

## 12. Какие документы и исходники изменить

**Поручение Fable:** изменения внутри каталога `1/` выполнить в указанных ниже документах и общих реализациях. Не оставлять новое ТЗ приложением при продолжающих противоречить ему публичных контрактах.

### 12.1. Обязательный параграф об универсальном входе

Заменить ограничивающий параграф в [§37 semantics](1/LMX_semantics.en.md#functional-receivers) и согласовать его производные. Нынешние утверждения «generic API explicitly accepts record sequences» и требование явного адаптера перед входом плотного Array не должны описывать универсальные map/filter/foldl и другие перечисленные операции.

Содержание заменяющего нормативного параграфа:

> Универсальные операторы, операнды и ресиверы получают значения через @. Ссылка указывает непосредственно на {type value}; value может быть примитивом или дескриптором. @[] хранит непосредственные указатели на такие значения. Вид массива определяется по его существующему типу; универсальный обход использует соответствующий доступ к элементу. Плотный Array T не переинтерпретируется как массив указателей и не требует обязательной пользовательской упаковки для универсального вызова. При необходимости обычный транспорт вызова подготавливает отдельное примитивное значение, не создавая второго представления входной последовательности или программы. Все виды Arrays уже поддерживают изменяемую длину и общий механизм capacity, хранимой отдельно от Lmx-дескриптора.

Полное требование конкретного callback, включая Ti, R, defaults и правила связывания, сохраняется. Не заменять исправляемое ограничение новой универсальной сигнатурой `@ → @` для всех функций.

### 12.2. Применить типовые головы T[] и общий договор ядра

Выполнить [приоритетное ТЗ ядра](LMX_Array_Reference_Types_Core.ru.md#migration) и согласовать с ним все примеры, signatures и operand headers внутри 1/. Предыдущая временная форма `[]: int [1 2 3 4]` заменена на `int[]: [1 2 3 4]`. Bare `[]: name` теперь означает uninit «любого массива»; тип конкретного массива находится в голове T[].

Для безымянного результата из copy использовать `type[]: [copy(squares)]`; для именованного — `type[]: new_variable [copy(squares)]`. Квадратную группу сохранять. Типовой операнд T[] и указательные формы всех глубин используют общие int-коды, интернирование и checked type-pair table.

Сохранить общие формы `[]: Name`, `[]: [data]`, `[]: Name [data]` и `@: Name [data]` с выбором по исходному имени/группе до lookup и вычисления initializer. Обычная DATA-структура `name(...)` / `name: ...` уже является void-массивом; sequence-API не требует её конвертировать. Предварительное превращение имени объявления со следующей группой в index expression исправить общим декларационным путём, без исключения для [] и без глобального правила whitespace.

Для `@[]` левое описание — символический атом @, допустимый общим TYPE-role normalizer. Не ограничивать этот путь bare_identifier и не исполнять @ как prefix-адресацию. Общий тип Structure / void-массива получается существующим механизмом интернирования.

Снять старые prefix `[]T` / `@T` именно как aliases типов; текущие конструкторы — `T[]` / `T@`. Именованные декларации имеют головы `type[]: array` и `Struct@: ptr`; прежнее отдельное описание требования после `@:` не восстанавливается. Инициализатор typed reference передаётся после имени, например `Struct@: ptr candidate`, а отсутствие initializer оставляет `Struct@: ptr` uninit. Это не blanket syntax error для тех же байтов: если форма имеет другой смысл по общим правилам, действует этот смысл. В частности, prefix `@value` остаётся адресацией, а bare `[](T)` / `@(T)` — обычными compact-формами `[]: T` / `@: T`. Старое адресное прочтение `@(node\x)` не восстанавливается. Группы в `(Struct)[]` и `(Struct)@` не снимаются ради мнимой эквивалентности негруппированному Struct. Полная миграция перечислена в основном ТЗ. Обычное имя :: и signatureTypes используют те же полные требования.

Сохранить различие исполненного объявления внутри Expression и декларационного actual в DATA-роли. Все формы разбираются общим P0; составная голова не получает отдельного parser-path для [] или @.

Отдельно исправить широкие фразы об исполнении изменённого кода:

- В [чтении source-узлов](1/LMX_semantics.en.md#path-reads-no-execution) фразу об execution of mutable code через compile/endturn сузить до обновления машинной реализации.
- В [explicit-compilation](1/LMX_semantics.en.md#explicit-compilation) запрет автоматического checking при graph write относится к отдельной native-подготовке и не отменяет проверки достигнутых операций интерпретатором.
- В сводных таблицах [kernel-implementation.en.md](1/kernel-implementation.en.md) заменить общее executable updates на native/machine-code updates там, где речь идёт о compile/endturn.
- Описать получение графа через fromLmx и непосредственные runtime-изменения до обсуждения необязательного native build/test-пути. Не вводить обязательный check/compile/endturn перед использованием графа как значения либо его интерпретацией.

### 12.4. Порядок выполнения

1. Выполнить общее ТЗ ядра по типовым головам, int-кодам, указательным глубинам и satisfies. Использовать те же element access и call preparation; не создавать коллекционный вариант этих механизмов.
2. Расширить универсальный вход и согласовать документы §12.1–12.3. Производные типы реализуются один раз в ядре по общему ТЗ; capacity сохраняет действующий механизм.
3. Применить исправления приоритетного ТЗ к адаптерам. Проверить, что универсальный источник и exact callable signature совместимы без потери defaults, missing actuals и lifetime.
4. Довести существующие коллекционные операции до общего контракта и добавить новые обычные ресиверы. Изменяющие операции используют общий алгоритм замены для replaceRange/splice и действующие resize/reserve; результаты target и removed различаются по §7.
5. Выполнить регрессии на реальном ядре, включая четыре сочетания исполнителей и код как Array. Затем синхронизировать каталог, собранные исходники, manifest и примеры.

Исследование без исправленного общего механизма и исполняемых регрессий не считается завершением реализации. Проверка ссылок, lint или подсчёт имён операций не считается запуском LMX.

### 12.5. Когда спрашивать автора

**Спрашивать только при явном противоречии двух действующих требований, которое нельзя разрешить их приоритетом.** Вопрос должен содержать обе точные нормы, минимальный пример и различающиеся наблюдаемые результаты.

Последние уточнения автора про @, непосредственные указатели на значения и изменяемую длину всех Arrays уже разрешают прежние ограничения документации. Повторно спрашивать, «разрешён ли dense Array для map», не нужно.

Рутинные внутренние имена helpers, выбор общей реализации доступа и эквивалентные оптимизации определяются Fable в рамках этого договора. Независимую работу не останавливать из-за одного действительно спорного случая.

### 13.2. Что не входит в v0.4

Нет новой универсальной схемы broadcasting размерностей, скрытых row views, нового reshape-хранилища, ленивого pipeline, рекурсивного flatten или набора синонимов существующим foldl/scanl/each.

Это граница данной работы, а не отмена существующих многомерных Arrays, iterator/yield или возможности обычными структурами описывать другие алгоритмы. Сортировку, оконные операции и расширенный матричный профиль можно специфицировать тем же способом отдельно.

Для последовательного действия без накопления результата уже есть control receivers, включая [each](1/LMX_semantics.en.md#branches). Его существующие правила iterator/yield/Stop сохраняются: None может быть элементом, redo повторяет текущий элемент, continue получает следующий. Нового callback-ресивера с именем each этот документ не объявляет.

Имена `repeat/lazy/pipe/compose` сохраняют свои нынешние значения. В частности, pipe строит композицию callable, а lazy сохраняет результат по своему контракту; это не новые операторы потоковой обработки коллекции.
