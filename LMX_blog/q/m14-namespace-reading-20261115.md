# M14: чтение вычисляемого поля и namespace

Вопросы закрыты. Ответы сверены 2026-11-15 с [контрактом кадра](../../docs/spec/LMX_semantics.ru.md#call-frame-20261115)
и [видимостью](../../docs/spec/LMX_semantics.ru.md#declaration-visibility).
Это правила языка; готовность реализации отмечается в [M14](../../next_core_tasks_v3.md#native-structures).

## Выполняются ли инициализаторы при входе?

Нет. Вызов создаёт собственный namespace и собирает объявления только корней data/code,
не исполняя вычисляемые части. Вложенные лексические ветви и ссылки графа в этот проход
не входят. Поданный actual полностью заменяет описание соответствующего места кадра:
его исходный инициализатор не выполняется. Неиспользуемое вычисляемое поле data не вызывается.

При построении чистого графа готовое `int: i 5` сворачивается в ячейку общим механизмом,
без вызовов программы. Вычисляемое объявление сохраняет написанный код; типы
«без значения» сохраняются. Исходные data и code не автозаполняются.
[Ответ автора](../2026-11-15.md#m14-value-reading).

## Когда видно новое имя?

Переменная и const видны с первоначального объявления вперёд на своём уровне
и во вложенных областях. Будущая локальная переменная не участвует в поиске;
доступные внешние и динамические имена разрешаются по общим правилам.
Двусторонняя видимость остаётся у имён Structure и callable. Указатель-переменная
на callable остаётся переменной.

Входные места data доступны code как входы текущего вызова. Подготовленный
перечень мест code не открывает будущие локалы раньше объявления. Новое имя
ветви наружу не выходит. Явные пути `data\field`, `S[n]` и `S\[n]field` продолжают
обычную адресацию графа независимо от видимости голого имени.
[Уточнение автора](../2026-11-15.md#m14-const-sequential).

## Как читается вычисляемое место?

Исполняется уже написанное в нём выражение. Для `@: fptr getFuncPtr()`
запись `fptr("hello world")` сначала выполняет getFuncPtr(), затем вызывает
полученную функцию. Голое имя само не придумывает вызова callable без аргументов.

В code `mark(); int: y makeValue()` вызов makeValue() происходит при достижении
объявления, после mark(). Если вычисляемое объявление раньше читалось явным путём,
это не отменяет его исполнения при достижении строки в code. Скрытого кеша,
который вычёркивал бы повторный вызов, нет.
[Чтение поля](../../docs/spec/LMX_semantics.ru.md#call-frame-20261115).

## Меняет ли запись в исходную data выбранное место namespace?

Нет. После входа локальное значение или вычисляемое описание независимо
от последующих замен исходного поля. Это одинаково для явной data, лексического
и динамического связывания. Это не глубокая копия объектов, на которые ведут
переданные ссылки.

`fptr := 0` меняет namespace. `data\fptr := 0` меняет исходное поле так,
чтобы оно читалось как `@: fptr 0`. Обратной публикации локалов нет.
[Дословный ответ автора](m14-namespace-source-answered-20261115.md).

## Что остаётся от повторного объявления?

В code повторное объявление уже доступного имени использует то же локальное место.
В `int: x bump()` сохраняются вызов bump(), общий допуск и запись в x;
вторую C-переменную создавать не нужно. Повтор без RHS не придумывает значение.

Два объявления в data остаются физическими вхождениями, доступными через
`S\[0]x` и `S\[1]x`; `S\x` при повторе неоднозначно.
[Объявляющий контракт](../../docs/spec/LMX_semantics.ru.md#receiver-args-only).

## Уточнённое вычисление операнда адресации

Для входного `int: x next()` обращение `@x` получает вычисляемое значение
и адрес обычной локальной int-ячейки. Унарный @ не подавляет вычисление операнда.
`@(data\x)` читает операнд из исходного графа; `@x` использует независимое место
кадра. Само различие источников не означает, что адрес вычисленного результата
обязательно принадлежит исходному полю.
[Дословный ответ](m14-namespace-source-answered-20261115.md#взятие-адреса-вычисляемого-входа).

## Место результата вычисляемого поля

Для `@(data\field)`, где в data записано `int: field getValue()`,
адресуется результат getValue(). Готовая ячейка адресуется непосредственно;
вычисляемое объявление даёт обычную адресуемую ячейку результата.
Запись через адрес результата не заменяет исходное описание поля;
`data\field := ...` остаётся явной записью в граф.

В разобранном native-пути результат уже имеет место `l2_tN` у вызывающей стороны:
используется `&l2_tN` без второго места и специального выделения из-за @.
Время жизни остаётся обычным. Обходчик использует свой общий механизм результатов,
а не отдельное хранилище всех return.
[Контракт](../../docs/spec/LMX_semantics.ru.md#computed-field-address),
[уточнение автора](../2026-11-15.md#m14-address-scope).

## Нужно ли копировать code или отслеживать правки ради native?

Нет. Независимость выбранных локальных мест не требует снимка code
или копии лексического окружения. Локальные значения не публикуются; load-dirty,
общий кеш прямого доступа и flush отменены.

Явные записи меняют граф сразу и не обнуляют native. Машинное исполнение
обновляется явной `sys\compile`; до endturn момент применения правок
не гарантируется. `sys\endturn` проходит все finally и завершает такт,
сам не проверяет и не компилирует граф.
[Действующий контракт](../../docs/spec/LMX_semantics.ru.md#explicit-compilation).
