# Слитый callable по ответу автора на Q48 (книга 1460fc3; `LMX_blog/q/response48.md`)

Строка плана — `next_core_tasks.md` §3, «Слитый callable по ответу автора на Q48». Норма — книга (1460fc3):
- §20: явное описание вызываемого, нативная реализация, возвращаемый вложенный метод, композиция частей;
- §11: формал с предусмотренным значением по умолчанию;
- §12: формал — не свободное имя;
- §7, §8: принимаемый интерфейс, обязательная подача, сформированные входы.

Проверочные случаи — R48-01…R48-12, ответ автора §8.

## 1. Замер (Opus, 2026-09-28, на `7124005`)

Замер — трансляцией, оба режима. Значения при исполнении дадут сборка и прогон, когда будет gcc.

| Случай | Программа | Сегодня (оба режима одинаково) |
|---|---|---|
| R48-05 | T5: `fn: add5 (int: x) int` / `merge(y: 5; add)`; `add5(1)` | принято. `add5` — нативная заглушка `return: 0`, у её листа нет `native`, поэтому вызов исполняет план интерпретатора |
| R48-06 | `add5(1; y: 25)`, позиционно `add5(1; 25)` | «more arguments than add5 has formals»: объявленный заголовок заменил `args`, `y` — связанное поле данных, а не формал |
| R48-07 | `add5(1; y: 0)` | то же |
| R48-10 | `add5(1; y: 25)`, затем `add5(1)` | то же, на первом вызове |
| R48-08 | вызывающий со своим `y = 25` зовёт `add5(1)` | принято; значение — прогоном |
| R48-09 | T6: `add5: makeAdder 5`, вызов `(add5: 1)` из метода | exit 3, «internal: a refusal said nothing» — молчаливый отказ (D-112). Давний: есть и на `3ed919e`. Из корня тот же вызов принят |
| R48-01…04 | нативная реализация слитого | нет: лист результата без `native` |
| книга | `merge(add; y: 5)` — модель первой (правило автора 2026-09-25) | принято, как и `merge(y: 5; add)`; совпадение значений — прогоном |

**Причина R48-09.**
- Вызов удерживаемого callable (`l2_mad_held`) проверка допускает в любом методе.
- Обход строит такой вызов: `l2_rw_mad_call` над помощниками `l2_mad_call`, `l2_mad_call_char` и далее.
- У нативного эмиттера такой ветки нет: `l2_mad_held` встречается только в проверке и в двух местах обхода. Какой-то шаг возвращает ошибку без слова. Частичный L1 обрывается в `go` сразу после выборки ячейки поля единицы.
- Корень обходится — поэтому из корня работает.

Трассой сборки это ещё не подтверждено: это первый шаг S1.

## 2. Срезы (план)

- **S1 — вызов удерживаемого callable из нативного метода.** Нативный эмиттер зовёт тот же помощник `l2_mad_call*`,
  через который вызывает операция обхода. Одна машина в обоих режимах, без отказа-ограждения. Сначала — трасса
  сборкой: какой шаг молчит. Свидетели: `(add5: 1)` из метода, в обоих режимах. После S1 случай R48-09 можно выразить.
- **S2 — объявленный заголовок как тип принимающего места (R48-11).**
  - Результат `merge` сохраняет формалы модели. Значение формала, пришедшее данными `merge`, — его дефолт (R48-05…08, 10).
  - Вызов может подать такой формал именем или позицией (`add5(1; y: 25)` = 26, `add5(1; y: 0)` = 1). Без подачи
    берётся дефолт (`add5(1)` = 6). Одноимённое значение вызывающего не подача.
  - Аргумент одного вызова не становится дефолтом следующего (`add5(1; y: 25)`, затем `add5(1)` → 26, 6).
  - Объявленный заголовок допускает результат обычным допуском, а не удаляет его формалы.
- **S3 — нативная реализация неизменённого тела (R48-01…04).** Код результата — код модели, `native` листа — `native`
  модели. Данные — данные результата (дефолт формала — в ячейке его данных). Изменённое тело без реализации исполняется
  интерпретатором по его обычному контракту.
- **S4 — свободное имя вложенного метода (R48-09, книга §20 «Возвращаемый вложенный метод»).**
  - `n` метода `addN` берётся из динамических источников вызывающего: динамическое `n = 25` даёт 26.
  - Скопированное лексическое `n = 5` — запасной путь: без динамического источника результат 6.
  - Явный `node\n` читает лексическое.
- **R48-12** (копирование обычной ветви и вечная ветвь `independent: const: immutable`) — замер после S1–S4.

Порядок: S1 (молчаливый отказ) → S2 → S4 → S3. У каждого среза — строки в обоих режимах, мутант на механизм и корпус.
L2-спеку §13 править вместе с кодом.

Вопросы автору — только если общие правила дадут два чтения с разным кодом (ответ §9). Сейчас таких нет: книга
(1460fc3) называет результат каждого случая.

## 3. S1 — итог (Opus, 2026-09-28)

**Трасса.** gdb на бинаре `7124005`, без сборки. Цепочка для `int: a (add5: 1)` в методе `go`: `l2_emit_stmts` →
`l2_eval_fields` → `l2_emit_fields` → `l2_prep` → `l2_emit_fields` → `l2_prep`, затем exit 3.

Молчаливый шаг — последний в кадровой ветке `l2_prep`: `if: idx < 0` / `return: 1`. Голова кадра, удерживаемый
callable, не находит вызываемого ни одним путём: метод, путь, callable-формал, fnptr, дверь `c.*`. Второй сайт той же
дыры — `l2_node_has_call`: удерживаемый кадр там не считался вызовом.

**Код:**
- `l2_node_has_call` считает удерживаемый кадр вызовом: справа от `&&`/`||` он вычисляется только в охраняемой ветви,
  как любой вызов.
- `l2_prep` зовёт его через тот же помощник `l2_mad_call*`, что PRIM обхода (`l2_prep_held_call`):
  - `refs` = [узел поля — `l2_own_load` в контексте метода, фактическое в ячейке типа формала заголовка];
  - ячейку делают те же помощники захвата, что у вызова модели D-93 (`l2_mcap_new_helper`, `l2_own_store_helper`);
  - результат — ячейка помощника типа результата заголовка (`l2_mcap_value_helper`);
  - char, как и у D-93, пока не передаётся — отказ у кадра.
- Проверка метит помощник, нужный методу (`l2_mad_need_held`), и блок прототипов его объявляет
  (`l2_emit_mad_call_protos`): помощники определены после тел. Объявляются только те, что метод зовёт нативно — у них
  своя маска `l2_mad_need_native`. Корень метит свои в проходе счёта обхода, до блока прототипов, а берёт их адреса
  после определений. Первый прогон корпуса, объявлявший по общим флагам, дал 38 программам (75 прогонов) с удерживаемым
  вызовом в корне лишнюю строку прототипа `fn: l2_mad_call (...)`. С маской их L1 байт в байт прежний.
- Хвост кадровой ветки говорит у кадра одной строкой — «internal: a call the emitter does not know» (`l2_said_or`: если
  до этого уже что-то сказано, ничего больше).

**Строки** (каждая и обходимым двойником):
- `unit_held_call_method` — вызов из метода значением и справа от `&&`, вход 7. До S1 — exit 3 без слова, в обоих
  режимах.
- `unit_held_call_guarded` — корень зовёт `go(0)` до оператора `add5: makeAdder 5`, узла в поле ещё нет. Охраняемый
  вызов справа от `&&` не должен исполниться, вход 7.

**Мутанты** (копией транслятора):

| Мутант | Что сломано | Что покраснело |
|---|---|---|
| nobranch | ветки удерживаемого вызова в `l2_prep` нет | обе строки, оба режима: «internal: a call the emitter does not know» у кадра, одна строка вместо exit 3 |
| nohas | удерживаемый кадр не считается вызовом | `unit_held_call_guarded`, нативно: вызов уходит до `if`, помощник видит пустой узел — «a callable merge was called outside its header», exit 3. Обходимый двойник зелёный: обход охраняет `&&` своим путём |

## 4. S2 — план (Opus, 2026-09-28; условия REVIEW cbbd955)

**Замер T5 сегодня** (`l2_pap_*`; на `be1ba25`):
- Метод, чьё тело — один `merge(имя: литерал; Модель)`, — результат. Формалы результата — формалы его объявленного
  заголовка. Связанное имя `y` — int-поле данных результата (`l2_own_add`), не формал; `native` = 0.
- Функция результата `l2_mN` — заглушка: пролог, ячейка поля, `return: 0`. Тела merge в ней нет.
- Корень зовёт результат через план интерпретатора и получает 6 (`unit_pap_add5`). А нативный метод зовёт заглушку
  напрямую: `l2_t1: l2_m1(l2_c0\parent, l2_c0, 1)` — по L1 это 0 вместо 6, молча неверное значение. Прогоном
  подтвержу, когда будет gcc.
- `add5(1; y: 25)` — «more arguments than add5 has formals».
- Ограничения: связывается только int-формал, только литералом; заголовок результата не может называть связанный
  формал.

**Механизм (по книге 1460fc3):**
- `merge(add; y: 5)` — модель первая. Результат — `add`, у формала `y` которого значение по умолчанию 5 (:1615 и
  §11). Источник дефолта — ячейка `y` в данных результата, по существующим правилам ячеек.
- Принимаемый интерфейс результата — формалы модели, в её порядке: `x`, `y`. Обязательная подача — `x`.
- Объявленный заголовок `fn: add5 (int: x) int` — тип места (§20, R48-11): результат допускается в него обычным
  допуском. Обязательная подача результата совпадает с заголовком; необязательный `y` в заголовке может не
  называться.
- Вызов результата связывает фактические воротами `l2_bind_actuals` с принимаемым интерфейсом (`x`, `y`).
  - Позиционная подача — по порядку формалов модели.
  - Формал с дефолтом без фактического получает дефолт механизмом вызова у места вызова, до входа в тело: чтение
    ячейки `y` результата в момент вызова.
  - Подача `y: 25` — значение этого вызова; ячейка не меняется, и следующий вызов снова берёт дефолт (R48-10).
- Код результата — код модели. Вызов результата — это вызов модели с `(x, y)`, где `self` — вхождение результата.
  Заглушка `l2_mN` больше не вызывается, и нативный вызов из метода даёт 6.
  - Натив листа результата для обхода и динамического вызова — это S3. В S2 — прямые вызовы.
- `merge(y: 5; add)` — судьба записи (условие REVIEW cbbd955), по книге (:1615, «`merge((n: 5); addN)` … такая Structure
  сама не вызываема»):
  - модель — Structure данных `{y: 5}`, метод `add` ложится в неё вложенным полем, и результат не вызываем;
  - в вызываемое место он не допускается — отказ допуска;
  - фикстуры, написанные до правила автора 2026-09-25 (`unit_pap_add5`, T7 `merge(y: k; add)`), переходят на
    `merge(add; y: 5)` / `merge(add; y: k)`;
  - строка-отказ — на запись с данными первыми.

**Свидетели** (оба режима):
- R48-05…08, 10 — строки по примерам книги: `add5(1)` = 6, `add5(1; y: 25)` = 26, `add5(1; y: 0)` = 1, `y` вызывающего
  не подаётся (6), `add5(1; y: 25)` затем `add5(1)` → 26, 6.
- Позиционная подача `add5(1; 25)` = 26.
- Вызов из нативного метода = 6.
- Отказ записи с данными первыми.

Мутанты: дефолт не подаётся; результат зовёт заглушку; позиция не по формалам модели.
