# Заметки о реализации и миграции LMX

Этот файл **не задаёт семантику языка**. Действующие нормы — в
[L3](LMX_semantics.ru.md), [грамматике](LMX_grammar.ru.md),
[L2](L2_spec_ru.md) и [L1](L1_spec_ru.md). Текущая очередь, точные отказы,
команды и датированные результаты — в [плане v3](../next_core_tasks_v3.md),
[дефектах](../steps/defects.md) и тикетах. Прежний маршрут сохранён в
[архивном плане v2](https://github.com/michael0xf/LMX/blob/0e0a2978eb237e145e54715de805a88e65264ba4/next_core_tasks_v2.md).
Старый успешный прогон не доказывает новой нормы.

<a id="source-migration"></a>
## 1. Источники и граница переноса

Поддерживаемый исходный язык ядра, парсера, трансляторов и обычной сборки —
L3 со вставками L2. L1 — только генерируемая ступень L3/L2→L1→C;
платформенный bootstrap однократен. Пока в closure есть поддерживаемые
вручную L1-исходники или внешние build/test-скрипты организуют обычный цикл,
§8 не завершён. Для каждого перенесённого тела и заголовка нужен manifest
зависимостей, тест и удаление старой авторитетной реализации.

<a id="l1-status"></a>
## 2. Translator-L1

Старый L1 seed/pin и историческая самосборка переводчика — переходные
инструменты, **не** самосборка L3/L2. M4 требует единого порядка плоских
объявлений «имя, требование, начальное значение» и в генерируемом L1:
сначала временно читающий оба порядка переводчик, затем перевод всех путей
эмиссии, исходников и тестов, наконец удаление старого порядка и новая
проверка seed/pin. Типовое выражение `@: T` не является объявлением
`@: name T`. Старую L1-ветвь нульарного вызова голым оператором исследовать
отдельно; она не становится нормой L3. Подробности и исходные замеры —
[миграционный тикет](../steps/tickets/unique-name-reference-migration-20261014.md).

Прежние возможности `C:`, `c.struct`, `c.union` и `synchronized` нельзя
объявлять реализованными по старым примерам без проверки обработчика.
Машинные ограничения прежнего `throw` payload не переносить в L2/L3.

<a id="l2-status"></a>
## 3. Translator-L2 и ядро

Физическая запись — `Lmx {VoidArray array, Lmx *parent, LmxEntry native}`.
`array` содержит `void *` слоты дочерних значений, адрес графового слота
имеет тип `void **`. Количество слотов экземпляра выбирается при его
создании; опубликованный backing не растёт и не переезжает. Растущий
`Thread.children` — **отдельный** List/DynamicArray, а не расширение Lmx
или поле программы. Служебные данные запуска принадлежат R0-заглушке.
Норма и устройство — [L2](L2_spec_ru.md#lmx) и
[Thread](L2_spec_ru.md#thread).

`LmxThread` содержит `LmxMsg message` по значению первым полем; обычный
`LmxMsg` не даёт доступа к хвосту Thread. Единственный List детей,
владение аренами и закрытие проходят общий Thread-путь. Исторические
фиксированные root-слоты, `LmxLink`, отдельный реестр детей и добавление
`settings` в исходный граф отменены. Измерения старого аварийного среза —
в [истории миграции](../steps/voidarray-migration.md), не критерий
закрытия нынешнего gate.

Открыты [critical_graph_bug](../plan_critical_graph_bug_critical_pointer_to_struct_bug_fix.md)
и [critical_pointer_to_struct_bug](../steps/tickets/critical_pointer_to_struct_bug.md).
Особенно нужно проверить типизированные машинные указательные ячейки,
`Array<@T>`, общий доступ через `void **` и полное межаренное копирование.
Положительный selftest одной ячейки не подтверждает все пути генератора,
native/walker и освобождение исходной арены. `implements` строит адресное
соответствие по реально необходимым полям; числовая позиция сама по себе
не является контрактом. Фактические отказы и тесты — [текущий kernel gate](../next_core_tasks_v3.md).

Нынешний kernel уже различает выбранный код и переданные данные при
активации. Единая языковая форма `call: code data` и явная часть `var`
метода — **утверждённая цель кодирования v3**, но ещё не реализованы и не
отменяют текущий `call: A`. Предварительный расчёт фиксированного числа
слотов и проверка полей `data` до исполнения включены в
[план v3](../next_core_tasks_v3.md). Инициализацию не менять по догадке.

<a id="l3-status"></a>
## 4. Интерпретатор L3 и допуск

Интерпретатор исполняет построенный граф, не второе дерево. Действующий
контракт допуска: сначала аналитически проверить явно необходимые
обращения Consumer, затем исполнить явно заданные им поведенческие
проверки. Без Consumer проверяется полная структурная пригодность.
Успешное соответствие адресов остаётся действительным при изменении
значений; присваивание ветки допускает нового кандидата **до записи**.
Нельзя после каждой мутации сбрасывать соответствия или автоматически
повторять все проверки. Совместимость известного статического вызова
устанавливается при трансляции, неизвестного кандидата — при необходимом
динамическом допуске. Нормы:
[стабильность соответствия](LMX_semantics.ru.md#correspondence-stability),
[этап аргументов](LMX_semantics.ru.md#argument-compatibility-stage).

Паритет native/walker, публикация состояния и полный граф ещё входят в
[K01–K12](../next_core_tasks_v3.md); частичные гарантии и прежние
host/root-обходы их не закрывают.

<a id="test-receiver-proposal"></a>
### 4.1 test: принятое правило, открытая реализация

Ресивер `test` **утверждён**, не является новым открытым проектным
предложением; [норма](LMX_semantics.ru.md#test-receiver-contract).
Без явного Consumer проверки берутся из принимающего описания `bVar`,
не из кандидата `aVar`. Аналитическая пригодность необходимых обращений
проверяется перед исполнением теста; успешный поведенческий результат
появляется лишь после его завершения. Тест завершает начатый допуск, не
запускает тот же допуск заново.

Код и проверки ещё не закрыты. Имя `test` зарезервировано; обычные
пользовательские привязки с этим точным именем мигрируют в `mytest`.
Не переименовывать `test2`/`test3`, строки или дословные исторические
цитаты по подстроке. Реализация использует общие P0, разрешение головы,
адресацию и native/walker, без скрытого каталога тестов, runtime-имён,
`skip_tests` и повторного прогона после каждой мутации. Представление
неуспеха **всего** набора тестов пока не решено.

<a id="open-design"></a>
## 5. Открытые решения

- Точная форма неуспеха набора `test` и её связь с объявленным `throw`.
- Выгрузка позднего модуля, чьи `independent: immutable` ветви по
  физическим адресам удерживаются потребителями; до решения владелец
  явен, скрытого глобального хранилища нет.
- Детали реализации утверждённой компоновки `args`/`return`/`var`/`body`
  и `call: code data`: read-before-write, скрытые входы, `node`, `catch`
  и совместимость native ABI. Они закрываются в N1–N6 плана v3, а не
  возвращают модель в статус факультативного исследования.

<a id="grammar-extraction"></a>
## 6. Граница грамматики и реализации

Грамматика описывает P0-форму, но не доказывает поддержку транслятором.
Единственный анонимный контейнер всего списка аргументов прозрачен уже
в P0; завершённые `f()`, `f: ()` и `f:` с явным `---` имеют одну пустую
Frame/body-форму. Незавершённое голое `f:` ошибочно; голое `f` —
атом, а не вызов. Исторические goldens не автоматически нормативны.
Открытые parser/consumer-разрывы и точные свидетели —
[parser fix](../next_parser_fix.md) и [план v3](../next_core_tasks_v3.md).
Диагностика Mix-меток и `{#...}` не выводится из старого текста по догадке.
