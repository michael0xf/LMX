# Синхронизация метаданных после изменения LMX

`sync_lmx_documentation_metadata.py` обновляет существующие метаданные по
актуальным исходникам. Он нужен после очистки закрытий, правки примеров и
семантической миграции: номер строки, хеш и строковое зеркало должны описывать
тот же текущий файл. Это инструмент публикации, а не парсер LMX и не runtime.

## Запуск

Из каталога, содержащего `docs`:

```sh
python docs/tools/sync_lmx_documentation_metadata.py --docs docs --core --listings --markdown-mirrors --report metadata-preview.json
python docs/tools/sync_lmx_documentation_metadata.py --docs docs --core --listings --markdown-mirrors --write --report metadata-sync.json
python docs/tools/sync_lmx_documentation_metadata.py --docs docs --core --listings --markdown-mirrors --check
```

`--core` выбирает метаданные ядра; `--listings` — текущие JSON-листинги.
Без этих двух ключей выполняются обе части. Без `--write` это только просмотр.
`--check` возвращает статус 1, если какие-либо данные ещё требуют обновления.

Если имеется неизменённая предыдущая редакция, добавьте
`--baseline-docs /path/to/previous/docs`. Тогда номера строк для ссылок на
описания и таблицы переносятся по точному содержимому исходной строки.
Используется номер из **предыдущего каталога**, чтобы повторный запуск не
принял уже обновлённый номер за позицию в старом документе. Ненайденная или
неоднозначная привязка сохраняется и указывается в `warnings` отчёта.

Запускайте применение после завершения параллельных правок источников.
Перед записью инструмент проверяет, что прочитанные файлы с момента чтения
не изменились. При обнаруженной одновременной правке нужно повторить запуск.

## Метаданные ядра

В `core_catalog/core` изменяются только существующие поля записей:

- `sourceLine` — фактическое объявление целевого метода либо точная
  привязка к строке документации;
- `sourceSha256` — SHA-256 текущего исходного файла;
- `sourceDeclaration` — написанные DATA-объявления владельца целевого
  метода, извлечённые существующим `catalog_data.owner_data`;
- JSON-проекция `inventory.json` и номера строк ссылок в `README.ru.md`.

Для существующих строк `profile_roles.lmx` используются точные соответствия
`role/package/source` и актуальные заголовки из `profile_role_rows` генератора
каталога. Это обновляет лишь `sourceLine`: состав записей, их контракты и весь
каталог заново не создаются. Такой путь сохраняет привязку к разделу и тогда,
когда автор изменил продолжение его заголовка.

В `LMX_Fn_Receivers/catalog.json` обновляются соответствующие существующие
`implementation_contract.source_declaration`; в `core/summary.json` — хеш
каталога. Инструмент не добавляет API, не меняет семантические семейства,
маршруты, роли аргументов и заявленные результаты исполнения. Новые операции
должны сначала попасть в канонический каталог обычным способом.

`selfbuild_index.lmx` сохраняется целиком. Каталог документации может не
содержать сам `selfbuild/`; его отсутствие не означает пустой исторический
индекс. По этой же причине не следует запускать полный `rebuild_core.py`
только для обновления строк и хешей в документационном архиве. Записи с
недоступными исходниками сохраняются, их количество отражается в отчёте.

## Листинги и метрики

Обрабатываются текущие `patterns.json`, дополнительные сравнения и входные
JSON-каталоги Haskell, Julia, Perl и SBCL. Для `lmx_variants` инструмент
читает существующие `source_files` либо `source_file` в их указанном порядке,
обновляет полный `code` и метрики. Общий исходник учитывается один раз.

Для старых групп без `source_file` источник по шаблону
`examples/lmx/NNN_slug.lm3` используется только после доказательства: в
неизменённой предыдущей редакции его полный текст должен совпадать с полным
LMX-листингом той же записи `patterns.json`. Файлы с дополнительными вариантами
и маркерами границ не подменяют единственный измеряемый листинг.

Ключ `--markdown-mirrors` дополнительно заменяет **только целиком совпавшие**
LMX-fence-блоки, для которых этот запуск установил однозначную пару старого
листинга и его актуального источника. Область — текущие Markdown в
`spec/patterns`; `tests`, `validation`, исторические журналы и receipts
исключены. При неоднозначной паре блок сохраняется с предупреждением.
Иностранные fenced-блоки и окружающий авторский текст не переписываются.
Простая замена fence не пересчитывает его соседнюю таблицу: после неё всё равно
нужен профильный publisher и полный пересчёт метрик.

Если сравнение измеряет замыкание зависимостей, `code` остаётся всем этим
замыканием. Клиент из `entry_source_file` обновляет отдельный `fragment_code`;
он не подменяет полную реализацию. Совместимое старое зеркало функционального
листинга остаётся зеркалом и не превращается в третью сравниваемую запись.

Для активного LMX-кода без ссылки на файл применяется тот же консервативный
редактор закрытий. Метрики сохраняют свою существующую схему и учитывают
полный текст; специальные вычеты для Throws не вводятся.

Исходные `.lmx`/`.lm1`/`.lm2`/`.lm3`, иностранный код, исторические
`before_code`/`after_code`, отвергнутые варианты и хеши импорта не
перезаписываются. Отчёты старых запусков не выдаются за свежую проверку.

## Обновление публикации

После синхронизации листингов актуальные общие данные строятся командами:

```sh
python docs/spec/patterns/tools/refresh_statistics.py --metadata-only
python docs/spec/patterns/examples/tools/refresh_examples_statistics.py
python docs/spec/patterns/tools/build_publication_data.py --text
```

Эти команды проверяют равенство источников, JSON и метрик; они не заменяют
редактирование самих индивидуальных страниц. Для группы 09 имеется
`09_functional_computation/tools/regenerate_publication.py`; у сравнений
Julia, Perl и SBCL имеются собственные `tools/rebuild.py`. Их следует
запускать после синхронизации JSON, поскольку некоторые генераторы пишут
зеркала исходников из этих JSON.

Для групп 10–11 `patterns/tools/refresh_algorithm_publication.py` сверяет
полные исходники с JSON и обновляет соответствующие Markdown-блоки и таблицы
обоих стилей. Старый `refresh_group_publication.py` не является универсальным
генератором двух стилей LMX и для этого обновления не используется.

PDF и XLSX создаются отдельными `patterns/tools/publish_pdfs.py` и
`patterns/tools/publish_workbooks.mjs` из актуальной общей модели. Этот
синхронизатор сам их не запускает. Манифесты хешей обновляются после всех
правок, проверок и финальной генерации экспорта.
