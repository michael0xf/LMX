# Матричные и поэлементные операции в Expression

Нормативное дополнение от 26 ноября 2026 года, включённое в общую спецификацию.
Окончательные обозначения автора: `.=` — поэлементное сравнение на равенство,

Имена `.=` и `.:=` не являются альтернативными именами присваивания.

## 1. Наличие массива выбирает массивный договор

Ресивер получает аргументы по обычному договору Expression. Если среди
полученных значений есть Array, применяется соответствующий массивный
профиль операции. Отдельного типа Matrix или специальной пометки выражения
не требуется. Обычная Structure неотличима от массива элементов свободного
типа `@[]`; именованность её полей не исключает её из этих операций.

Это проверка фактически потребляемых значений. Она не ищет массивы
рекурсивно внутри произвольного объекта и не превращает несколько правых
аргументов в один. Обычная арность, группировка и роли сохраняются.

Физическое хранение и полные требования к элементам берутся из значения и
канонического описания TypeRef. Тип целиком задаётся нормализованным конструирующим
описанием: `int[][][]` задаёт rank=3, а `int[2][2][2]` — ещё и все размеры осей.
Границы строк инициализатора проверяются и дают плоские данные; они не сохраняют
скрытую форму и не специализируют TypeRef. Операция по осям использует заданные
или однозначно выводимые размеры из TYPE и length. Недостаток информации даёт
диагностику только при достижении операции, которой эта информация нужна.

При capacity=length второго дескриптора нет, в том числе у многомерного Array.
Реальный резерв получает необязательную запись capacity, не меняя TypeRef.
Заголовок `parent/length/storage` не расширяется. См.
[канонические типы и совместимость](ARRAY_STORAGE.ru.md#array-profiles).
Structure остаётся обычным `@[]`; её ссылки сохраняют идентичность и общий
доступ по имени/индексу, без отдельной сущности «массив массивов».

На одном значении доступны плоские операции и операции по осям. Плоский
потребитель читает length/storage без reshape, смены типа или прокси rank=1.
Свежая линейная выборка имеет собственный объявленный линейный тип результата.

Результат получает TypeRef полного объявленного/вычисленного требования к нему.
Если операция обещает сохранить выходные размеры, они входят в это требование;
нельзя скрыто уточнять общий `T[][]` по полученным данным. В `a * b + e` временный
план Expression может передать размер `(m,n)` произведения в `+`, но одного
выделения плоских ячеек недостаточно для сохранения формы после операции.
Публикация следует полному типу результата без скрытых полей формы и объектов строк.

Арифметика делегируется выбранному скалярному договору. Машинные числа,
bigint, decimal, real и другие допустимые модели не сводятся неявно к int
или double. Для свёртки произведения нужны совместимые умножение, сложение
и аддитивный нуль правильного типа. Полный тип результата устанавливается
до обхода, в том числе для пустого массива; пробный вызов на первом
элементе запрещён. Плотное хранение результата допустимо, когда полный
тип R установлен общим договором; свободные элементы обрабатываются
обычным доступом к `@[]`.

## 2. Обычные матричные операции

| Запись | Смысл при наличии Array |
| --- | --- |
| `a + b`, `a - b` | Для одинаковой формы — сложение/вычитание соответствующих элементов. Скаляр распространяется на все элементы с сохранением порядка аргументов. |
| `scalar * a`, `a * scalar` | Умножение каждого элемента на один раз полученный скаляр. |
| `a * b`, два вектора | Билинейное скалярное произведение по возрастанию индекса. |
| `a * b`, матрица и вектор | Матрично-векторное произведение. |
| `a * b`, вектор и матрица | Векторно-матричное произведение. |
| `a * b`, две матрицы | `(m,k) * (k,n) -> (m,n)`. |
| `a / scalar` | Деление элементов по выбранному скалярному договору. |
| `a / b` для двух массивов либо скаляр / Array | Обратная матрица и решение системы не угадываются. Скалярное деление выбирают на нужной глубине: `./` для ранга 1, `.(2)/` для ранга 2; для системы — явно выбранный решатель. |
| `a ** exponent` при Array a | Только явно предоставленный алгебраический профиль степени. Скалярную степень выбирают на нужной глубине (`.**` для ранга 1). Эта редакция не добавляет алгоритм обращения или матричной степени. |
| `%`, имеющиеся целочисленные побитовые операции и сдвиги | Их допустимый покомпонентный профиль; точечная форма явно обозначает работу с элементами. |

Свёртка более высокого ранга требует явно предоставленного договора:
автоматического выравнивания, разворачивания в матрицу или broadcasting
размерностей нет. Два вектора в `a * b` теперь дают скалярное произведение;
для прежнего поэлементного произведения пишется `a .* b`.

Матрица результата заполняется в порядке строк. При непустой внутренней размерности
каждая ячейка начинается с первого произведения, затем к нему прибавляются
последующие произведения по возрастающему внутреннему индексу. Выбранный
аддитивный нуль запрашивается только при пустой внутренней размерности и
тогда даёт каждую выходную ячейку. Сопряжение, переассоциация, FMA, параллельная
редукция и преобразование числового типа не вводятся автоматически.

Пример с описанными формами a=(2,3), b=(3,2), e=(2,2):

| Значение | Строки |
| --- | --- |
| a | [1 2 3]; [4 5 6] |
| b | [7 8]; [9 10]; [11 12] |
| e | [1 1]; [1 1] |
| `a * b + e` | [59 65]; [140 155] |

Размерности — часть допуска входов. Таблица не предлагает считать
набор отдельных строк одним непрерывным прямоугольным хранилищем.

```lmx
MatrixExample:
    @: a
    @: b
    @: e
    return: @
    run:
        throws: copy(`*`\throws) copy(`+`\throws)
        return: a * b + e
```

Операнд `a * b` и ресивер `` `*`(a; b) `` используют один исполнитель.
Техническое имя backend matmul не означает второй алгоритм. Имеющиеся
явные профили dot/contract/outer сохраняют свои договоры: различное
сопряжение или выбор измерений нельзя объединить только по сходству имён.

### 2.1. Массив непосредственно в выражении и обычная цепочка

В роли VALUE `[items]` строит один безымянный свободно типизированный `@[]`
через общий P0. Это явное значение Array, а не безымянная группа, которую
Expression может раскрыть. Элементы получаются один раз в установленном порядке;
по первому элементу плотный тип не выводится. Типизированный конструктор,
например `int[]: [10 20]`, получает требование к элементам от ресивера и не обязан
создавать промежуточный `@[]` ради преобразования.

```lmx
int: a 1
int: b 2
int: d 4
@: result a + b + [10 20] + d
# [17 27], группировка ((a + b) + [10 20]) + d.
```

`a + b` получается один раз до содержащей его операции с Array. При наличии
эффектов или обычных числовых ошибок следующие элементы литерала и операнды
не переносятся перед зависимостью, которая ещё может отказать. Явно
типизированная форма `a + b + (int[]: [10 20]) + d` сохраняет те же приоритеты.

```lmx
@: arr0 [[1 2]]
@: arr1 [[10 20]]
@: arr2 [100 200]
@: result arr0 .+ arr1 .+ [arr2]
# [[111 222]]; внешняя длина всех трёх аргументов равна 1.
```

`[arr2]` содержит ровно одно целое значение — тот же arr2. Оно не копируется,
не раскрывается и не запрашивает расширение единичной оси. Поэтому внешняя
размерность больше 1 слева несовместима с `[arr2]` и диагностируется. Это обычная
ссылка на Structure в элементе, без отдельного вида Array.
У типизированного инициализатора ранга 2 `int[][]: [1 2; 3 4]`, равноправного
`int[][]: [[1 2] [3 4]]`, другой принимающий договор: одно плоское прямоугольное
хранилище ранга 2. Строки проверяют прямоугольность, но их размеры не дописываются
в TypeRef `int[][]`; для сохранённой формы 2×2 нужен `int[2][2]`. Этот договор
не делает глобального раскрытия самостоятельного `[arr2]`.

Транслятор может использовать известные форму, время жизни и скалярные договоры,
чтобы убрать ненаблюдаемое создание или промежуточное хранение. Для этого нужны
доказанные сохранение identity, порядка востребования/эффектов/ошибок и числовой
группировки. Скобки не разрешают переассоциацию, FMA, незаметную замену eager на
fuse с другим порядком ошибок или клонирование графа программы.
[Полные примеры](examples/array_expressions/README.md) и host-модель сохраняют эти границы.

## 3. Арифметика как профиль общей глубины операторов

Depth принадлежит [всем семействам операторов](OPERATOR_DEPTH.ru.md), а не
отдельному набору арифметических имён. `op` означает глубину 0, `.op` — 1,
`.(EXPR)op` передаёт явную глубину, включая 0 и 1. Внутри круглых скобок
обычное разобранное Expression: литерал, имя, операция или вызов получаются
один раз при востребовании этой операции. Для большей глубины используется
эта форма, а не повторение точек. Метод оператора получает `left`,
**`int: depth`**, `right`; транспорт аргументов заранее их не уплощает.
Лексическая последовательность `.(` всегда начинает модификатор глубины
оператора/функции, а не десятичную точку. Квадратные скобки конструкторов Array,
индексов и срезов сохраняются. Например, `1 .(3)+ 2 .(2)+ 3` допустимо и даёт 6
по обычному правилу скалярной неподвижной точки и сложения.

Стандартный арифметический VALUE-профиль при каждой положительной глубине
потребляет одну **логическую внешнюю ось**. Её размер и оставшиеся размерности
берутся из сохранённого описания. Строка или плоскость адресуется временным
дескриптором на том же хранилище; обход не выделяет объектов строк, новых
pointer slots или узлов графа. Выбранные размеры согласуются. При оставшемся
depth=0 базовая операция получает выбранные скаляры, векторы или блоки целиком
по собственному договору.

Исходный скаляр может распространяться. Если исходный Array достиг скаляра до
исчерпания запрошенной глубины, этим нельзя подставить недостающую ось другого
Array. Избыток либо несовместимость требуемой глубины диагностируются. Полностью
скалярные исходные аргументы — неподвижная точка. Обычная Structure в поле
остаётся тем же значением и потребляется общим механизмом Array; отдельной
модели «массивов массивов» нет.

```lmx
int[2][2]: a [1 2; 3 4]
int[2][2]: b [[5 6] [7 8]]
@: matrix a * b
# shape (2,2): [19 22 43 50]
@: rowProducts a .* b
# shape (2): [17 53], базовый * сворачивает каждую пару строк.
@: cells a .(2)* b
# shape (2,2): [5 12 21 32], скалярное умножение в каждой координате.
```

Поэтому `.op` всегда означает глубину 1, а не обещание скалярной операции
при любом ранге. Для ранга r запись `.(r)op` достигает скалярных ячеек, если
объявленные элементы скалярны. Ранг 3 даёт три логические оси одного плоского
хранилища. `a .(1)* rowScalars` может выбрать допустимое масштабирование
вектор/scalar; `a .(2)* rowScalars` не может выдумать вторую ось одномерного rowScalars.

Таблица перечисляет удобные формы depth=1, а не отдельно именованные тела:

| Семья | Формы глубины 1 |
| --- | --- |
| Бинарная арифметика | `.+ .- .* ./ .% .**` |
| Унарные знаки | `.+ .-` в унарной позиции |
| Целочисленные побитовые операции и сдвиги | `.& .\| .^ .~ .<< .>>` |
| Сравнения | `.= .!= .< .<= .> .>=` |
| Составные арифметические присваивания | `.+= .-= .*= ./= .%= .**=` |
| Составные побитовые присваивания и сдвиги | `.&= .\|= .^= .<<= .>>=` |
| Прижатые изменения | Префиксные/постфиксные `.++`, `.--` соответствующего прижатого класса |
| Семейство присваивания | `.:`, форма `:=` с глубиной 1 |

Базовые ресиверы прижатых форм — `++var`, `var++`, `--var`, `var--`;
`depth := 1` выбирает формы таблицы. Префикс возвращает изменённые значения,
постфикс — снимок на выбранной глубине. Общий алгоритм изменения один.
Таблица не вводит ограничение длины имени и не придумывает поворот для
отсутствующих в выбранном профиле `<<<`/`>>>`.

Выбранные внешние размеры должны совпадать; при оставшемся depth=0 базовый
договор проверяет оставшиеся целые значения и формы блоков. Одного равенства
общего числа элементов недостаточно. Нет
автоматического расширения единичных осей, обрезания, рекурсивного слияния
соседних групп или числового promotion. Сравнение даёт результат соответствующей
формы из скалярных предикатов, обычно int 0/1, без свёртки в одну истинность.
Нужная редукция `all`/`any` выбирается явно.

```lmx
@[]: a [1 2 3]
@[]: b [1 8 3]
@: equal a .= b
# equal = [1 0 1]; a и b не изменены.
a .: b
# a = [1 8 3]; внешний объект сохранён.
```

Ресиверные формы используют **базовые имена и тот же именованный depth**:
`` `+`(a; b; depth := 1) ``, `` `=`(a; b; depth := 1) `` и
`` `:=`(a; b; depth := 1) ``. Идентификатор с точкой внутри обратных кавычек
остаётся буквальным именем; это не алиас и не команда декодировать глубину.
Согласованная таблица поверхностного семейства присваивания: `:=` при depth=0,
`.:` при depth=1, `.(EXPR):` при явной глубине. В частности, `.(0):`
выполняет базовое присваивание целому месту; `.:=` в это семейство не входит.

Логические, TYPE, DATA, RAW, PLACE и другие ресиверы сохраняют свой принимающий
договор и выбирают поддерживаемую политику глубины. Общий декоратор не превращает
ленивость в eager-вызов и не навязывает рекурсивный VALUE-lifting сигнатурам,
адресам или Pattern. См. [роли и ABI](OPERATOR_DEPTH.ru.md#abi).

## 4. Присваивание и перестановка

`destination .: source` получает реальные места слева на глубине 1.
Для ранга 1 это ячейки, для ранга 2 — логические регионы строк того же плоского
хранилища. Для записанной группы мест общий потребитель
PLACE получает сами места переменных: группа остаётся обычной
Structure/Array свободного типа, а не новым tuple и не копией переменных.

Цель определяется один раз. Все правые значения получаются один раз,
в обычном порядке, **до первой записи слева**. В проверяемом исполнении
форма, число элементов и допуск каждого действительного места проверяются
до записи. Операция сохраняет размер, форму и внешний объект назначения;
обычный результат обозначает назначение без второй копии присвоенных данных.

Для `destination .(n): source` те же правила действуют для настоящих мест,
выбранных через n логических осей. Значения RHS всех выбранных ветвей сохраняются
до любых записей; проверить только первого ребёнка недостаточно. Исходный
скалярный RHS может заполнить выбранные уровни. Исходный Array должен предоставить
нужные уровни и формы: недостающий ребёнок не превращается в scalar broadcast.
При достигнутом depth=0 целевое PLACE принимает целое значение, включая ссылку
на Array или другой допустимый тип. Вложенность прежнего значения и прежний
uninit не мешают обычному целому присваиванию. Поэтому `reference .(0): other`
равно базовому `reference := other`.

У логического региона строки/плоскости нет отдельного pointer slot для
перепривязки. Его базовое присваивание принимает совместимый целый блок той
же остаточной формы, удерживает все исходные ячейки и пишет реальный регион,
не изменяя его размер. Для скалярного заполнения матрицы ранга 2 пишется
`matrix .(2): scalar`; `matrix .: scalar` выбирает целые строки и не обходит
обычный допуск целого блока.

```lmx
int: a 1
int: b 2
int: c 3
(a b c) .: (b c a)
# a=2, b=3, c=1
```

`(a b c) .: copy(d)` и `(a b c) .: (copy(d))` используют общий
потребитель групп и потоков полей. Дополнительного прохода раскрытия
после группировщика нет. Соседние структурные значения справа остаются
отдельными элементами. Скаляр может заполнить выбранные места; Array или
поток полей должен соответствовать форме/числу выбранных мест.

Перекрытие ссылок не превращает перестановку в последовательную порчу
следующего правого значения. Для составного присваивания сначала
получаются прежние значения цели и RHS. `a .+= b` использует общую
арифметику и запись как `a .: a .+ b`, но определяет a только один раз.
Ошибка не откатывает уже выполненные эффекты получения аргументов.
Общей транзакции или rollback не добавляется.

`destination .: fuse(expression)` явно выбирает потоковую запись fused-результата:
форма, места и безопасность alias подготавливаются до записи, но скалярный
результат и его допуск получаются по координатам. Поздняя ошибка арифметики
или допуска может оставить уже записанный префикс. Этот договор запрошен
ресивером `fuse`; компилятор не может незаметно заменить им обычное
присваивание с полностью подготовленной RHS. См. [fusion](FUSION.ru.md).

Срез в роли VALUE создаёт новую выборку. В позиции PLACE у `.:` он
выбирает настоящие ячейки для этой операции, без постоянного типа view.
Размер меняют существующие `replaceRange`/`splice`.
Подробности: [срезы и тернарная форма](TERNARY_AND_SLICES.ru.md).


### Общий алгоритм составного и приклеенного изменения

Составные и приклеенные изменения соединяют поэлементное вычисление с тем же
телом обычного присваивания; второго цикла записи у них нет:

```text
compound(targetOccurrence, rhsOccurrence, baseOperation, depth):
    target = resolvePlaceOnce(targetOccurrence)
    old, rhs = captureRequiredValuesInWrittenDemandOrder(target, rhsOccurrence)
    values = applyAtDepth(baseOperation, old, rhs, depth)
    return ordinaryAssignmentAtDepth(target, values, depth)

attached(targetOccurrence, baseOperation, depth, resultPosition):
    target = resolvePlaceOnce(targetOccurrence)
    old = snapshotSelectedLevels(target, depth)
    if old has elements:
        unit = selectedScalarProfile.unit()
        values = applyAtDepth(baseOperation, old, unit, depth)
        ordinaryAssignmentAtDepth(target, values, depth)
    return old if resultPosition is postfix else target
```

Имена вспомогательных шагов здесь описывают интеграцию, а не объявляют новые
публичные функции LMX. Общие LMX-тела — `FxArrayDepth\apply` и
`FxArrayDepthAssignPrepared\assign`, использующее `FxArrayAssignPrepared\assign`; исполняемый эталон реализует `compound` и
`increment` в [array_expression_reference.py](tools/array_expression_reference.py).
Постфиксная форма сохраняет выбранные уровни, чтобы глубокая запись не меняла
прежние значения снимка; префиксная возвращает изменённое назначение. Ссылки
ниже выбранной границы сохраняют обычную идентичность. При depth=0 действует
базовый договор результата. Единицу задаёт скалярный профиль,
поэтому скрытого преобразования всех элементов в `int` нет.

## 5. Приоритеты и fuse

Точечная арифметика и сравнения наследуют приоритет, арность и
ассоциативность скалярной операции. `.**` сохраняет направленное правило
степени. `.=` находится на уровне равенства; `.:` и составные изменения —
на уровне присваивания. Слева остаётся записанное место PLACE.
Прижатые изменения используют существующий общий класс.

`fuse(expression)` явно выбирает пригодное выражение для одного обхода.
Аргумент RAW не вычисляется заранее в промежуточные массивы.
[Договор fuse](FUSION.ru.md) определяет однократное получение скаляров,
ленивую выбранную ветвь, перекрытия мест и порядок ошибок.
Матричное произведение не становится поэлементным из-за помещения в fuse.

```lmx
@: scores fuse(2 .* left .+ right .* right)
@: mask scores .>= limit
return: compress(scores; mask)
```

Здесь left/right — одномерные последовательности. Для скалярного kernel
матриц ранга 2 глубина выбирается явно: `fuse(a .(2)* b .(2)+ e)`.

Для пригодного выражения гарантированы один обход результата и отсутствие
промежуточных массивов результатов отдельных операций. Именно это даёт
ожидаемое ускорение. Замер времени на всех данных и backend не подменяется
одним названием fuse.

## 6. Общая реализация и проверки

Подготовка получает форму, доступ к исходным значениям, полный тип
результата и выбранные скалярные операции. Обход выполняет общий LMX-код.
Временные сведения одной операции не становятся вторым рабочим графом,
теневыми данными или сохранённым namespace. Прямые известные native-вызовы
и договор compile/endturn сохраняются.

Неверная запрошенная глубина, отсутствующие уровни, несогласованная форма
массивного выражения и непригодность fuse — диагностика транслятора, если это
известно при подготовке, иначе диагностика интерпретатора при достижении.
Это не перехватываемые исключения LMX и не новые строки throws. Обычные
ошибки скалярных/обратных методов, обычный допуск целевого типа и существующие
ошибки allocator/библиотеки сохраняют свои договоры. Списки ошибок копируются
из **базовых** методов, например ``copy(`*`\throws)``, а не из выдуманного
отдельного точечного callable.

Общий VALUE-мост предоставляет source, числовой depth, происхождение исходных
скаляров, проверенный доступ к уровням и полный R/void. Специальные ресиверы
потребляют depth сами. [Договоры реализации](FUSION.ru.md#implementation)
описывают `level`, `publish`, сбор глубоких реальных PLACE и fused leaf writer.
Это явные границы интеграции, не заявление о выполненном production-запуске.
[Примеры](examples/assignment_forms/README.md) включают перепривязку, вложенное
присваивание, динамическую глубину и отдельные диагностические fixtures.

L3 и интерпретируемый L2 применяют общие проверяемые обёртки. Нативный L2
не получает автоматических проверок границ, но их отсутствие не делает
некорректный доступ допустимым. Отрицательное смещение относительно
элемента следует выражать через указатель; отрицательные границы среза
имеют отдельный смысл отсчёта от конца.
