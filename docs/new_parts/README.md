# LMX: 23 шаблона проектирования в восьми языках

Обновлено **21 ноября 2026 года**.

Полный комплект `design_patterns_comparision` содержит 23 сравнительных примера, три руководства на русском и английском языках, три пары таблиц Excel/PDF, два обзора модели языка и справочную документацию LMX. Всего — 45 файлов. В каждом сравнении сначала приведён LMX, затем **Python, Java, C++, C#, TypeScript, Go и Rust**.

Каждый файл задаёт конкретный общий сценарий, приводит восемь листингов, ожидаемый результат, подсчёт исходников и сведения о проверке. Шаблоны представлены средствами соответствующего языка: общую задачу можно выразить функциями и ссылками, если она не требует отдельной иерархии классов. Границы сценария указаны рядом с кодом.

## Основные приёмы в LMX-примерах

Исходная точка этих примеров — короткая реализация общей задачи, часто уже выраженная функциями в Python. В LMX связанные функции собраны в обычные структуры, а их общие данные, ссылки и связывание используются непосредственно. Далее перечислены приёмы, которые встречаются в листингах, и правила, необходимые для их чтения.

### 1. Обычная структура объединяет данные и исполняемые методы

Структура может использоваться как код; DATA вызываемого метода — его фактический `parent`. Поэтому общие входы и `return` объявлены один раз в окружающей структуре. Это видно в `transform` у [Decorator](06_decorator_comparison.md), `checkout` у [Facade](14_facade_comparison.md) и `bridge` у [Bridge](18_bridge_comparison.md). Метод `demo` естественно находится в той же группе; наличие поля в DATA не обязывает каждый метод читать его. [Контракт структурного вызова][B]

В [Flyweight](21_flyweight_comparison.md) `get` принадлежит `glyphs`, а `render` и `demo` — вложенной `drawing`. Сохранены короткие объявления `immutable: thin: int: width 2` и завершающий `return` на уровне объявления `demo`: он завершает тело `demo`. Пустая физическая строка закрывает весь текущий корневой блок, поэтому внутри `glyphs` пустых строк нет. [Грамматика][G] · [Границы блоков][E]

### 2. Общий namespace и импорт объявлений

`import` добавляет в namespace **корневые const-объявления DATA**. Объявление пользовательской структуры константно и без явного `const`, поскольку само объявление структуры не является переменной. Совпадение имён обрабатывается как обычное повторное объявление. Импорт метода не меняет его фактический DATA. [Правила import][D]

Так `import: Product` открывает `create` в [Factory](03_factory_method_node_prototype_comparison.md), а `import: operands` — `add` в [Interpreter](23_interpreter_comparison.md). Вложенная `drawing` в [Flyweight](21_flyweight_comparison.md) находит `get` по лексической видимости и не нуждается в дополнительном импорте.

### 3. Автодозаполнение объявленных входов

Объявленный вход без инициализатора может получить одноимённое значение из локального контекста вызывающего. В [Decorator](06_decorator_comparison.md) `with_three(10)` передаёт `value` дальше через `with_one()` и `base()`. В [Facade](14_facade_comparison.md) `subtotal()` и `fee()` получают нужные им поля из текущего контекста. Повторять полный список одинаковых аргументов на каждом звене не требуется. Готовые defaults сохраняют установленный для них приоритет. [Autofill и порядок связывания][B]

### 4. Прозрачная связь с изменяемым местом вызывающего

Свободное имя может связаться с допустимым местом локального контекста вызывающего. В [Command](07_command_comparison.md) обработчики меняют локальное `value` демонстрации; в [State](10_state_comparison.md) методы переключают локальную ссылку `state`. В пользовательском коде сохраняется тип самой переменной. Скрытый адрес, нужный нативной реализации для изменения этого места, относится к транспорту вызова. [Места вызывающего][B]

Здесь действует граница `private`: он закрывает неявное динамическое связывание в обе стороны — и предоставление источника, и динамическую подмену защищённого поля получателя. Явная передача и допустимый лексический доступ сохраняются. В коротких листингах `private` не требуется; это правило применяемого механизма. [Правила private][B]

### 5. Лексический node для выбранного состояния

`node\` фиксирует **лексическое связывание**. Его смысл не равен переходу к физическому родителю. Через него [Iterator](01_iterator_comparison.md) обновляет `position`, [Factory](03_factory_method_node_prototype_comparison.md) настраивает `payload`, [Observer](05_observer_comparison.md) сохраняет `last` и `total`, а [Builder](15_builder_comparison.md) меняет поля строящегося продукта. Этот доступ отличается от прозрачной связи со свободной переменной вызывающего. [Связывание и node][B]

### 6. Ссылки на методы и требования к callable

Обычная ссылка хранит выбранный метод, а вызов следует её текущему значению. Так работают `operation` в [Strategy](02_strategy_comparison.md), обработчики в [Observer](05_observer_comparison.md), `prepare` и `finish` в [Template Method](08_template_method_comparison.md), звенья в [Chain of Responsibility](11_chain_of_responsibility_comparison.md), `request` в [Proxy](13_proxy_comparison.md), независимые `control` и `output` в [Bridge](18_bridge_comparison.md). Для хранения и вызова таких ссылок отдельное объявление `fn` не требуется. [Ссылки и вызов][B]

Аналитические требования предъявляются к используемым данным и операциям. Если нужен отдельный именованный контракт callable, применяется `fn: name data`: он описывает позиционные типы входов и результат. Обычный структурный шаблон проверяет имена и всё явно заданное им дерево требований. Эти два смысла `implements` различаются; общий `@` в примере не означает, что в листинге записана полная статическая сигнатура каждой ссылки. [Типизация и допуск][S] · [Сигнатуры fn][B]

### 7. Явный merge, когда нужны собственные данные

`merge` применён там, где задача требует независимого состояния или композиции: продукты [Factory](03_factory_method_node_prototype_comparison.md), дерево [Composite](12_composite_comparison.md), результаты [Builder](15_builder_comparison.md), копии [Prototype](16_prototype_comparison.md), снимки [Memento](17_memento_comparison.md), продукты [Abstract Factory](20_abstract_factory_comparison.md) и отдельная комната [Mediator](22_mediator_comparison.md). Обычное сохранение или возвращение ссылки само по себе копию не создаёт. [Композиция и копирование графа][M]

### 8. Общая идентичность и неизменяемое состояние

В [Singleton](19_singleton_comparison.md) `get` каждый раз возвращает одну `Settings`. В [Flyweight](21_flyweight_comparison.md) два `get(0)` возвращают один `thin`, а `get(1)` — `thick`; позиция передаётся отдельно. `immutable` защищает содержимое глифа. Константность имени и неизменяемость содержимого — разные требования. Копирование `merge` в этих сценариях не нужно. [Ссылки, const и immutable][S]

### 9. Пользовательский цикл и диспетчеризация Visitor

[Iterator](01_iterator_comparison.md) реализует `cycles\iterate` обычным методом. Переданная форма `int: item numbers\next()` сохраняется как `iteration` и исполняется заново на каждом обороте; объявленное `item` доступно телу. `body()` меняет `item` и локальный `total` вызывающего. Состояние продвижения находится в итераторе, а `Stop` обрабатывается циклом. [Переданные формы объявлений][D]

В [Visitor](09_visitor_comparison.md) узлы вызывают именованные действия `on_number` и `on_pair`. Контекст `Actions` предоставляет эти действия через установленное динамическое связывание; недостающая операция имеет явный fallback с `NoAction`. Так сохранены роли узлов и посетителя без отдельного visitor-параметра. [Порядок связывания и fallback][B]

### 10. Пользовательский операнд как обычный метод

В [Interpreter](23_interpreter_comparison.md) имя метода `add` используется в выражении после обычного `import`. Пригодность определяется структурой DATA: `left`, `right`, **обязательные** `PASS_ARGS_AS_IS` и `PRIORITY`. Отдельной регистрации в `sys\operand` нет; проверка шаблона не добавляет отсутствующие поля. В листинге явно записаны `PASS_ARGS_AS_IS 0` и `PRIORITY sys\priority("+")`. [Контракт операндов, редакция 6][O]

Режим `0` передаёт ссылки на подготовленные значения; `\left` и `\right[0]` читают их. `return: int` возвращает обычное число. Режим `1` передаёт исходные аргументные вхождения; для их явного вычисления предусмотрен `sys\eval`. Этот режим описан в ТЗ, но для показанного `add` не нужен. Разыменование `\` само по себе не исполняет код. Обычная ссылка передаётся без адресного `@`; форма `@Structure` означает явное получение числового адреса. [Аргументы и адреса][O]

Сохранённая форма `(n add 3) add n` находится в графе `calculate` и вычисляется при `n = 2` и `n = 5`; результат `demo` — `20`. Python хранит ту же форму композицией замыканий. Общий сценарий — повторное вычисление данного выражения; универсальный конструктор произвольных деревьев во время выполнения в коротком LMX-листинге отдельно не показан.

## Метрика и результаты

Основная метрика — **непробельные символы** полного показанного исходника: `sum(not ch.isspace() for ch in code)`. Дополнительные метрики — полный размер и физические строки. Нормализация: LF, удаление пустых строк по краям, один LF в конце.

В подсчёт входят объявления, импорты, необходимые языковые оболочки и `demo`. Внешний вызов, добавленный только для запуска `main`, печать результата, проверочная обвязка и реализация стандартной библиотеки/runtime не включены. Имена не нормализованы; Python приведён без необязательных аннотаций типов. Метрики получены из самих листингов.

Для всей подборки LMX занимает **5776**, Python — **6870** непробельных символов: сокращение **15,92%**. LMX короче Python в **19 из 23** примеров и минимален среди восьми языков в **18**. Python имеет наименьшую сумму среди остальных семи языков. Подробные цифры, исключения и выводы для отдельных частей приведены в [обзоре RU](about_languages_comparision.ru.md) и [обзоре EN](about_languages_comparision.en.md).

Это размеры конкретных реализаций указанных сценариев. Разная степень типизации и дополнительные возможности отдельных представлений описываются отдельно. По числу символов нельзя вывести быстродействие или память; в комплекте нет сравнительного runtime-бенчмарка.
