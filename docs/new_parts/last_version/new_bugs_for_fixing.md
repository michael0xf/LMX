# LMX — требования к исправлению кода

**Редакция 4: 2026-11-09.** Этот файл сопровождает десять документов с префиксом `new_`. Он собирает обязательные исправления, условия согласованности обходчика и нативного транслятора и критерии проверки. Пункты являются заданиями к реализации; отметка о выполнении требует проверки соответствующего кода и результатов обоих исполнителей.

Первые два требования сохранены в прежнем порядке. Новое решение этой редакции: **видимость в обе стороны, приоритет «назад последняя», накопление изменений при обходе**. Подготовка полного набора `var` и размещение объявлений в нативном коде должны обеспечивать это правило с сохранением порядка исполнения.

<a id="p0-container"></a>
## 1. ГРУБАЯ ОШИБКА: снятие единственного анонимного контейнера в P0

**Исправить код P0.** Сохранять каждый явно записанный анонимный контейнер во всех контекстах, включая единственный и пустой. Это относится к круглой структуре фактических аргументов, фигурному описанию Structure и квадратному Mix. Нормализация не должна подменять контейнер его полями.

```lmx
f()
f: ()

f(a b)
f: (a b)
```

В первой паре тела Frame имеют соответственно ноль полей и одно поле — пустую вложенную Structure. Во второй паре имеются соответственно два поля и одно поле-контейнер. **Деревья P0 различаются.** Только семантика уже разрешённого вызова функции или метода может принять единственную переданную Structure как всю структуру фактических аргументов. Исходное дерево при этом сохраняется.

Исправление должно охватить объявления, данные и вложенные выражения: они не наследуют раскрытие аргументов вызова. У обычной исполняемой Structure отдельная `data` также сохраняет свою роль данных, а не становится формальными аргументами метода.

**Проверка готовности:** сравнить построенные деревья всех четырёх форм; проверить единственный и пустой контейнер внутри описания, данных, выражения и Mix; затем отдельно проверить семантическую подачу аргументов. Совпадение результата двух вызовов не доказывает правильность их деревьев.

Норма: [грамматика](new_LMX_grammar.ru.md#empty-colon), [подача всей структуры аргументов](new_LMX_semantics.ru.md#whole-arguments).

<a id="receiver-arity"></a>
## 2. Удалить двухаргументные формы ресиверов данных и типов

**Удалить поддержку форм, передающих одному встроенному ресиверу имя места и значение двумя соседними аргументами.** Старый вариант не сохраняется как fallback и не переписывается неявно перестановкой аргументов. Ограничение применяется после общего структурного P0; P0 не получает частных разборщиков по именам ресиверов.

| Удалённая форма — отклонять | Действующая форма |
| --- | --- |
| `int: i 5` | `i{ int: 5}` или `i: int: 5` |
| `@: ptr 0` | `ptr: @: 0` |
| `@: ptr Model` | `ptr: @: Model` |
| `@: ptr Model: Other` | `ptr: @: Model: Other` |
| `@: ptr method` | `ptr: @: method` |
| `@: add5 makeAdder(5)` | `add5: @: makeAdder(5)` |

В новой форме имя находится снаружи ресивера; вложенный `Model: Other` — один операнд `@`. Первое определение создаёт место, повторная форма с кандидатом записывает в то же место после допуска, включая переприсваивание ссылки на метод.

Сохранить допустимые `int()`, `@()`, `int: x`, `@: ptr` и соответствующие формы остальных ресиверов. Многоаргументные методы, `fn`, `merge`, `print`, `post` и другие самостоятельные операции сохраняют свои контракты.

**Проверка готовности:** удалённые формы отвергаются; новые формы работают при первом определении и повторном присваивании; фабрика вычисляется один раз; повторное описание без кандидата не сбрасывает значение. Само переприсваивание ссылки не вызывает метод.

Норма: [построение значений](new_LMX_semantics.ru.md#construction), [ссылки на методы](new_LMX_semantics.ru.md#method-reference-assignment).

<a id="bidirectional-resolution"></a>
## 3. Единая видимость в обе стороны

Убрать прежнее различие, при котором методы видны в обе стороны, а обычные Structure, примитивные и ссылочные места — только от объявления вперёд. Общее правило действует в существующей области связывания, включая корневую Structure и получившийся после композиции граф файлов.

При разрешении имени приоритет имеет **последнее предшествующее связывание, доступное по имени и области**. При его отсутствии допускается обращение к видимому последующему объявлению или подготовленному месту. Выбор связывания предшествует допуску значения: ошибка совместимости не разрешает искать более раннее «подходящее по типу» значение.

Учитывать собственные объявления по всей области при отделении own-полей от свободных входов. Позднее собственное объявление не должно ошибочно превращать предшествующее употребление в свободный динамический вход лишь из-за позиции текста. Наличие объявления не создаёт отсутствующего поля в произвольно переданной `data`.

**Проверка готовности:** ссылка в более раннем теле на позднюю обычную Structure, поздний метод и позднее ссылочное место разрешается по общей норме. Область, `independent`, `node` и приоритет динамического источника над лексическим сохраняются. Недопущенное текущее значение вызывает обычный отказ без возврата к старому связыванию.

Норма: [видимость объявлений](new_LMX_semantics.ru.md#declaration-visibility), [динамические входы](new_LMX_semantics.ru.md#dynamic).

<a id="walker-state"></a>
## 4. Обходчик должен накапливать изменения

Разделить предварительно известный набор имён и мест и текущее состояние их связываний и значений. Подготовка всей области нужна для видимости вперёд; текущий обход сохраняет изменения, уже принятые к данной точке исполнения.

Достигнутая запись после допуска обновляет то же место. Следующее чтение использует текущее значение по существующему контракту рабочего состояния. Поздняя запись не меняет результат уже состоявшегося чтения, а пропущенная ветка не выполняет содержащуюся в ней запись. Повторный поиск имени не запускает заново инициализатор. Изменения в петле сохраняют обычную последовательность выполнения, а не повторно восстанавливаются из конечного текста блока.

Namespace остаётся служебным состоянием текущего обхода. Таблица канонических написаний не превращается в хранилище значений, а накопление не требует второго постоянного графа или нового поля в `Lmx`.

**Проверка готовности:** несколько записей в одно место и чтения между ними дают последовательные значения. Результат не подменяется последним определением, найденным при предварительном сканировании всей области. Рекурсивные активации сохраняют прежние правила рабочих значений и общей выбранной `data`.

Норма: [обходчик и native](new_LMX_semantics.ru.md#visibility-native), [рабочее состояние](new_LMX_semantics.ru.md#dynamic).

<a id="var-layout"></a>
## 5. Подготовка полного `var` и фиксированных мест

Автозаполнение `var` заранее собирает явные собственные поля и поля конкретного `body` по существующему контракту. Полный набор и физическая раскладка известны до исполнения тела. Повторные записи одного имени используют прежнее место; первый выполненный `if` или проход цикла не добавляет новый слот.

Предварительная подготовка не выполняет инициализаторы `body`, не переносит их в `var` и не меняет момент исполнения сохранённого содержимого `var` при входе в метод. Видимое имя с незаполненным местом не получает вымышленного нуля или будущего результата. Его потребление подчиняется уже принятому контракту значения без инициализации.

Адреса слотов, порядок полей, карты `implements` и различие собственной рабочей ячейки, поля графа и динамического аргумента сохраняются. Общая видимость не вводит автоматическое дополнение произвольно переданной `data` и не расширяет контракт автозаполнения обычной Structure.

**Проверка готовности:** количество и адреса полей не меняются от порядка ветвей; каждый достигнутый инициализатор исполняется в своём прежнем месте и нужное число раз; отказ допуска не оставляет частично добавленного поля.

Норма: [части метода](new_LMX_semantics.ru.md#method-parts), [L2](new_L2_spec_ru.md).

<a id="native-lowering"></a>
## 6. Аккуратное понижение новой видимости в native

Нативный транслятор должен воспроизводить выбор и состояние в каждой точке исполнения. Недопустима привязка всех употреблений к последнему определению имени во всём исходнике.

Подготовить полный набор мест и необходимые C-объявления, прототипы и определения типов до выдаваемых обращений. Порядок их размещения в C может отличаться от расположения LMX-описаний; порядок семантических операций остаётся прежним. Обеспечение C-видимости не переносит вычисление инициализаторов, фабрик, вызовов или присваиваний и не меняет порядок исходных полей графа.

При вызове через изменяемое место читать его текущее связанное значение. Вызываемое выбирается **один раз до вычисления фактических аргументов**; изменение ссылки при вычислении аргумента не перенаправляет уже выбранный вызов. Нельзя заменить эту ячейку постоянным адресом последнего метода из исходника.

Сохранить существующие ABI, преобразования, допуск, code→data-карту, физические адреса, публикацию `dirty` и инвалидирование несовместимого `native`. Новое правило не требует нового глобального namespace, скрытого окружения или дополнительного графа состояния.

**Проверка готовности:** одинаковые программы в native и обходчике дают одинаковые значения, последовательность эффектов и отказы, включая взаимные ссылки методов, повторные записи и изменение callable-ячейки.

Норма: [нативное понижение](new_LMX_semantics.ru.md#visibility-native), [L1](new_L1_spec_ru.md), [L2](new_L2_spec_ru.md).

<a id="separate-contracts"></a>
## 7. Сохранить отдельные контракты путей и областей

При внедрении «назад последняя» не подменять им выбор явного исходного вхождения. `data\field` при нескольких исходных головах остаётся неоднозначным; для него требуется `data\(N)field`. Общий индекс `data\(N)` считает все непосредственные поля. Это отдельные операции над графом, а не поиск текущего голого имени.

Inline-`if` и `for` остаются в области текущей активации. Явный вызов создаёт область вызываемого. Динамический источник свободного имени предшествует лексическому; `independent` отсекает внешнего лексического родителя; `node` остаётся неизменным над-методным пространством. Два одноимённых `catch` в одном блоке по-прежнему запрещены.

Сохранить границы публикации `dirty`, правила чтения рабочих значений после вложенного вызова и инвалидирование `native` при фактическом изменении кода. Видимость имени не публикует рабочее значение автоматически.

**Проверка готовности:** новая видимость не меняет результаты явных индексных путей, поведение Mix, адресацию полей, границы активаций и ранее установленные адресные соответствия.

Норма: [имена и пути](new_LMX_semantics.ru.md#fields), [рабочее состояние](new_LMX_semantics.ru.md#dynamic).

<a id="syntax-migration"></a>
## 8. Проверить полноту реализации уже принятых синтаксических правил

Эти требования остаются действующими вместе с новой видимостью. Проверить их поддержку в P0, семантическом допуске, обходчике, нативном понижении и `toLmx`/`fromLmx`, а не восстанавливать старые написания как обходной путь:

- `{...}` — Structure и выражение; `name{...}` — именованное описание; `[...]` — Mix с собственным локальным уровнем 0.
- Круглые скобки — вызовы, структуры фактических аргументов, выделение и индексирование Array. Обычная Structure исполняется `code()` или `code(data)`; пустой вызов сохраняет существующий выбор `code\var`.
- Присваивание и именованная подача используют `:`. Отдельного оператора `:=` больше нет. `=` остаётся сравнением, `!=`, `<=`, `>=` сохраняются.
- Составные присваивания используют двоеточие; степень `**` сохраняет принятые правила группировки. В C99 для степени требуется понижение, а не выдуманный оператор C.
- `struct\(index)` выбирает непосредственное поле по общей позиции, `struct\(index)field` — нумерованное вхождение конкретного имени. Для частей `{args return var body}` `f\(1)` выбирает `return`; `f(1)` остаётся вызовом метода.
- `arr{ (): @}; arr: f; arr(1)` сохраняется как явный доступ через Array ссылок. `typeof(p)` принимает указатель и возвращает код типовой арены указуемого объекта; код не подменяется статическим `@` или идентичностью общей арены Message.
- Выражение является Structure. Оператор может быть её непосредственным полем, как `+` в `{a + b}`. Дополнительная оболочка выражения и снятие контейнера в P0 не вводятся.

```text
+: -: *: /: %: <<: >>: &: ^: |: **:
```

**Проверка готовности:** новые формы проходят одинаковый путь в обоих исполнителях; сериализация текущего графа использует новую запись, сохраняет порядок и существующую вложенность. Настоящие C99-фрагменты сохраняют C-синтаксис.

Норма: [грамматика](new_LMX_grammar.ru.md), [пояснения](new_LMX_semantics_guide.ru.md).

<a id="acceptance"></a>
## Приёмочные примеры для нового правила

### A. Накопление записей вместо конечного значения всего блока

```lmx
fn: accumulation {} int {x: int: 0}
    x: 1
    print: x
    x: 2
    print: x
    x: 3
    return: x
end: accumulation

print: accumulation()
```

Ожидаемая последовательность выводимых значений: **1, 2, 3**. Видимость будущей записи `x: 3` не меняет два предыдущих чтения. Если второй `x: 2` поместить в пропущенную условную ветку, эта запись не должна менять текущее значение.

### B. Ссылка в более раннем теле на позднюю обычную Structure

```lmx
fn: readLater {} int
    return: Later\value
end: readLater

Later{value: int: 7}
print: readLater()
```

Тело `readLater` может разрешить имя `Later`, записанное позже в той же лексической области. Вызов стоит после построения данных, поэтому ожидается **7**. Этот пример не требует раннего исполнения будущего инициализатора.

### C. Текущая ссылка на метод после переприсваивания

```lmx
fn: one {} int
    return: 1
end: one

fn: two {} int
    return: 2
end: two

fn: referenceProbe {} int {p: @: one}
    print: p()
    p: @: two
    return: p()
end: referenceProbe

print: referenceProbe()
```

Ожидаемая последовательность выводимых значений: **1, 2**. Первому вызову нельзя заранее подставить `two`; второму нельзя сохранить старую цель `one`.

### Дополнительные проверки

| Случай | Требуемый результат |
| --- | --- |
| Видимое впереди место ещё не имеет значения | Действует существующий контракт незаполненного места; ноль и результат будущего вызова не подставляются |
| Два достигнутых вычисляемых инициализатора | Эффекты идут в установленном порядке; каждый выполняется нужное число раз, без запуска из поиска имени |
| Присваивание в inline-`if`/`for` | Используется то же подготовленное место активации; новые поля и области не создаются |
| Отказ допуска нового значения | Сохраняются прежнее значение и действующие правила отказа; нет поиска другого старого совместимого связывания |
| Изменение callable при вычислении аргумента | Текущий вызов сохраняет цель, выбранную до аргументов; последующий вызов видит новую ссылку |
| Две исходные головы для явного `data\field` | Сохраняется требование индекса вхождения; «назад последняя» не выбирает его автоматически |
| Вложенный и рекурсивный вызов | Сохраняются отдельные рабочие кадры, прежние публикации и идентичность выбранной `data` |
| Перенос объявления C перед употреблением | Не меняет порядок вычислений LMX, layout графа и результат `toLmx` |

<a id="forward-candidates"></a>
## Неуточнённый случай: несколько разных будущих кандидатов

Новое решение однозначно устанавливает видимость в обе стороны и приоритет последнего предшествующего связывания. Оно не устанавливает отдельный порядок между несколькими действительно различимыми будущими кандидатами, когда предшествующего связывания нет.

Обычные повторные записи в одно место не относятся к этому случаю: у них один подготовленный слот и последовательные изменения. Сохраняются существующие требования единственности поля и обработчика, а также отдельные контракты сопоставления методов.

Если конкретная допустимая конструкция оставляет несколько разных будущих кандидатов после применения этих правил, для неё нужно уточнить порядок выбора. В этой редакции **не введены** ни «вперёд первая», ни «последняя во всём блоке». До уточнения реализация не должна молча объявлять одну из этих политик общей нормой языка.

## Критерий завершения переноса

Первые два исправления и новая видимость проверены отдельно; native и обходчик совпадают по значениям, выбранным целям вызовов, эффектам и отказам. Подготовка `var` сохраняет единственные физические места и не выполняет будущий код. Примеры и сериализация используют актуальную запись. Результаты проверки следует фиксировать со ссылкой на версию реализации; изменение этих документов само по себе не является подтверждением исправленного исполнителя.
