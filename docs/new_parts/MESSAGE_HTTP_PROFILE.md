# Общий профиль Message, post и HTTP для новых сравнений

Редакция 2026-11-21. Этот файл описывает общую среду листингов групп 05–07 и может использоваться другими группами.

## Статус примеров

Листинги являются авторскими ядрами алгоритмов и протоколов. Нормативные основания — [CORE](../../CORE.md), [семантика Message, §24–28](../LMX_semantics.en.md#messages), [HTTP, §32](../LMX_semantics.en.md) и [контракт post](../Old_TZ/threadMessageAPI.en.md).

В исходном пакете описан контракт `post`, но нет полного буквального parser fixture с `ask`/`answer`. Поэтому деревья `post` ниже и в сравнениях получены применением общих структурных правил к этому контракту. Они не выдаются за листинги, уже принятые действующим компилятором. Имя прикладного метода, входы и его тело приведены; разрешение адресованного пути в конкретном runtime-профиле должно проверяться при интеграции.

HTTP-транспорт уже предусмотрен языковой документацией. Он не заменяется вымышленным новым builtin. Имена `http`, `queue`, `lifecycle`, `sink`, `io`, `replies` обозначают явно поставленные экземпляры обычных библиотечных интерфейсов с перечисленными ниже контрактами.

## 1. Как шаблон становится исполняемым Message

Структура с суффиксом `Message` в примере описывает граф одного будущего владельца. Само объявление такой структуры ничего не запускает. Хост должен:

1. Создать именно исполняемый L3 Thread, содержащий Message-префикс, с отдельной ареной. Обычное письмо не повышается до Thread на месте.
2. Скопировать нужный шаблон и явно передать разрешённые ссылки на провайдеры, цели и начальные настройки. Контекст родителя автоматически не наследуется.
3. Включить ребёнка в штатный `Thread.children` его непосредственного родителя. Дополнительный реестр членства не строится.
4. Связать явно указанные адресованные методы и отправить начальные запросы. Методы остаются обычными Structure с DATA = фактический `parent(C)`.
5. После завершения протокола выполнить обычное закрытие и безопасное освобождение. Сам факт пустого inbox не завершает Message.

Точную новую сигнатуру `spawn` эта подборка не вводит: соответствующий API выбирает L2/host-профиль. Прикладные ссылки `worker0`, `worker1`, `child` допустимы как адресаты операций и не становятся второй таблицей членства.

Один owner выполняет не более одного turn одновременно. Разные owners могут выполняться параллельно. Логический Thread не означает выделенный OS thread: перенос между workers допустим на границах turns.

## 2. Обычный вызов через post

Авторская форма применения описанного `post`-контракта:

```lmx
ClientMessage:
    @: service
    @: sink
    start:
        post:
            ask:
                service\compute(value := 6)
            answer:
                sink\accept

ServiceMessage:
    int: value
    return: int
    compute:
        return: value * 2
```

Здесь хост создаёт разные Message для клиента, сервиса и принимающего результат sink. `sink.accept(value:int):void` — заранее выбранное место доставки результата. Ожидаемый результат — один вызов `compute` и одна доставка `12` в `sink.accept`.

Весь exchange description связывается до публикации. `answer` обслуживается на полосе отправителя, после чего выбранная доставка делает обычный вызов получателя. Позиционное сопоставление строк `ask` и `answer`, поиск всех подходящих методов адресата и дополнительный mailbox не вводятся. Идентичность исходного письма обеспечивает обычную корреляцию `post`; пользовательские ID не добавляются туда ради локального wait.

Чистый source-граф сохраняет `post`, `ask`, `answer` и вложенные формы. Подготовка обмена не публикует локальные значения в исходный граф.

## 3. Запрет ожидания собственного следующего turn

Handler не должен блокировать текущую полосу ожиданием ответа, обработчик которого обязан исполниться следующим turn этого же Message. Иначе answer не сможет быть принят обслуживающим исполнением.

В P54 это выражено событиями:

1. `Worker.start` отправляет `Queue.take` и завершает turn.
2. Ответ выбирает заранее связанный `Worker.received` на следующем входе.
3. `received` исполняет одно задание, отправляет следующий `take` и завершает turn.

То же относится к Future, Guarded Suspension и structured concurrency: ожидание хранится как явно выбранное состояние живого owner; исходный stack frame не удерживается произвольной callback-ссылкой.

В кратких синхронных HTTP-примерах `http.post` означает native/host-вызов **синхронного HTTP-профиля**, который возвращает непосредственно HTTP response. Он не ждёт собственного `post.answer` из следующего turn. Для асинхронного HTTP admission + `replyTo` требуется тот же событийный автомат с поздним входом, что и для локального `post`.

## 4. HTTP-профиль, уже предусмотренный документацией

Путь обработки:

1. Адрес состоит из нормализованного endpoint и route.
2. Поставленный провайдер передаёт точные байты полного документа с `Content-Type: application/lmx`.
3. На приёме decoder строит Message-граф; явная route Table выбирает принимающее выражение и адресата.
4. Обычный admission проверяет совместимость, необходимые tests, полномочия и lifetime, после чего выбранный owner исполняет запрос.
5. Синхронный профиль возвращает семантический ответ в HTTP response. Асинхронный может подтвердить admission и позже послать Message по `replyTo`; `correlation` соответствует `id` исходного HTTP request.

Принятие письма, выполнение операции и её успешный результат — три события. HTTP 202/admission acknowledgement нельзя автоматически считать успешным результатом бизнес-метода. Network timeout не доказывает, что сервер не выполнил операцию. TLS, нормализация URI, limits, auth и byte codec остаются явными обязанностями провайдера и receiving expression.

Нормативный пакет содержит следующий **текстовый пример envelope** для большого тела через cursor. Его маркеры — данные описанного профиля; это не новый синтаксис builtin HTTP-вызова:

```text
message:
    id: "report-42"
    to:
        route: "/reports/process"
    end: to
    expression:
        process:
            body:
                cursor: reportStore\flightLog\segment42
                range: current
                mode: readStream
            end: body
        end: process
    end: expression
end: message
```

Источник: [LMX semantics, §32](../LMX_semantics.en.md). Синтаксис и сериализация конкретного transport fixture должны проходить общий parser/codec; пример envelope сам по себе не является отчётом об успешном сетевом запуске.

## 5. Контракты поставляемых портов

Сигнатуры ниже — договор демонстрационного окружения. Они не объявляются встроенными средствами LMX. Конкретный пример уточняет типы и используемое подмножество.

| Порт | Сигнатура и эффект | Что обеспечивает окружение |
| --- | --- | --- |
| `queue` | `push(int):void`, `size():int`, `pop():int` | FIFO в арене одного owner; `pop` только при непустой очереди; чужой sender её не мутирует |
| `request` | `():int` | Одна завершённая попытка; в HTTP-примерах sync response, а не ожидание собственного inbox; значения ошибок заданы сценарием |
| `http.post` | `(endpoint:string,route:string):int` | Фиксированное request body, application/lmx, decoder/admission, sync semantic response status; не глобальный singleton |
| `delay` | `(duration:int):void` | Таймер выбранного хоста; тест может записывать интервалы вместо реального ожидания; не запускает второй turn owner |
| `store` | `read():int`, `write(int):void` | Хранилище одного фиксированного ключа; операции завершаются до возврата; durability не подразумевается |
| `sink.write`, `collector.accept` | `(value:int):void` | Запись наблюдаемого результата; если sink общий для workers, он сам Message или thread-safe контрольный объект |
| `replies.send` | `(requestId:int,value:int):void` | Доставка конкретному живому клиентскому Message; ID относится к явно выбранному deferred protocol, а не подменяет штатную корреляцию post |
| `io.readReady` | `(fd:int):int` | Реальный nonblocking read: положительное число байт, 0 would-block, −1 закрытие по fixture; вызывается после readiness |
| `io.unregister` | `(fd:int):void` | Снятие подписки на readiness |
| `io.submitRead` | `(fd:int,token:int,target:MessageAddress):void` | Запуск I/O, удержание буфера, последующее уведомление completed после завершённого чтения |
| `lifecycle.startChild` | `(template:Structure):MessageAddress` | Явное создание нового прямого ребёнка с собственной ареной и новой identity |
| `lifecycle.requestStopChildren` | `():void` | Stop requests только прямым детям из штатного Thread.children; остановленных детей допускается пропустить |
| `result.finish` | `(ok:int,total:int):void` | Доставка итога scope только после всех stopped notifications; при ok=0 total не трактуется как успешный результат |
| `lifecycle.reportExhausted` | `():void` | Передача родителю сообщения об исчерпанном restart budget |
| `database.probe` | `():int` | Ограниченная по времени проверка обязательной зависимости; 1 готова, 0 недоступна |

`selfAddress` и `completionTarget` — явно переданные живые Message-адреса для будущей доставки. Их нельзя заменять указателем на стек или произвольным `node`: лексический родитель и Message supervision/address identity — разные отношения.

## 6. Fair comparison и стоимость обвязки

Таблицы считают показанный код ядра. Реализация перечисленных портов, host launcher, HTTP provider, codec, deployment, очередей и тестового harness **не включена** в число символов. Её объём неизвестен и не объявляется равным нулю. Стандартная библиотека Go/.NET/JVM/Erlang и runtime LMX также не включаются в число символов вызова.

Поэтому:

- краткость leaf-handler не доказывает краткость полного сервера;
- наличие Message не доказывает durable delivery, backpressure, exactly-once, rollback или distributed consensus;
- родительство не создаёт автоматический join результатов;
- сохранённый request/fragment не продлевает жизнь завершившегося native frame;
- serial owner не обещает concurrent readers RW-lock или OS-thread affinity TLS;
- deployment Sidecar/Ambassador требует отдельных процессов/контейнеров; два локальных Message сами по себе не дают такую изоляцию.

Контрольные листинги сравниваются в прямо указанном сценарии. Существенные различия дополнительно перечислены в каждом pattern file; в частности, правила cancellation LMX/Go/Erlang различаются.

## 7. Что следует проверить при переносе в живое ядро

Проверяются конкретные наблюдения: исходный граф не меняется при локальной работе; результат `post` исполняется один раз; owner не зависает на собственном answer; очередь не выдаёт одно задание двум worker; графовые слоты принадлежат правильному Message; новый ребёнок действительно имеет отдельную арену; future/scope не удерживает умерший stack; HTTP admission не подменяет semantic success. Эти пункты — обязательства интеграции, а не заявления о уже выполненных runtime тестах.
