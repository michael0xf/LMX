## Норма

Пример §7 (`next_core_tasks.md`, блог 2026-09-25, итог правила merge, пункт 6). Поверхность:

```text
fn: makeAdder (int: n) fn: (int: x) int
    fn: addN (int: x) int
        return: n + x
    return: addN

add5: makeAdder 5
add100: makeAdder 100
```

`return: addN` — один merge с тремя операндами: модель `addN`, `{n: значение текущей активации}`, объявленный заголовок `(int: x) int`. Не два merge и не динамический вход. `makeAdder 5` и `makeAdder 100` — две Structure; поле `n` у каждой своё (5 и 100). Свидетель `[add5: 1; add100: 1; add5: 1]` → `[6 101 6]`.

- Заголовок результата — объявленная сигнатура, не ширина `args` модели. Формал `n` связан полем данных и из сигнатуры уходит. `x` остаётся `ARG 0`.
- Кадры — тело `addN`, та же подмена, что у PAP: связанное имя читается `AT` слота поля, держатель 0. Имени в узле нет, в рантайме поиска по имени нет. `lmx_walk_data_holder` (`lmx_walk.lm1` :516–:545) уже читает держатель 0 как данные этой активации, в том числе когда кадр общий с моделью.
- Значение `n` берётся из активации `makeAdder` в момент возврата и пишется в поле нового узла. Литерал транслятора здесь не при чём: 5 и 100 — аргументы двух вызовов.
- Кадры общие по адресу (терминал копира, K-OT1). `lmx_arena_ref_store` (`lmx_arena_refs.lm1` :61) кладёт указатель в слот и родителя кадра не переписывает. Новый узел на каждый возврат хранит те же кадры и своё поле. Кадр `makeAdder` не копируется. Скрытого окружения нет.
- `native` результата — 0. Вызов — `lmx_call_prim` (`lmx_call.lm1` :144), code и data — этот узел. Не `lmx_fresh` (`l2_emit_dyn_call` :16973): свежий экземпляр стёр бы переданное поле. Данные здесь переданы явно (Q28, merge).
- Тело `addN` вне walkable-подмножества T4a/T4b — located «a callable merge needs a walkable body», узел не строится.
- Имя, которое не формал `makeAdder` и не поле результата, этот срез не захватывает: located-отказ, не динамический вход.
