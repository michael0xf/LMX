# Алгоритм группировки и разбора LMX Expression

Алгоритм получает **чистый граф**, текущий лексический контекст и договор принимающей позиции. Текста, токенов скобок и признака происхождения структуры на его входе нет. Ссылка разрешается к существующему узлу; имя, `parent`, идентичность и связи этого узла сохраняются.

Здесь описаны общий обход, связывание операций, работа с последовательностями и отдельная подготовка применения. [Проверочная реализация на Python](tools/expression_grouping_reference.py) исполняет ядро планирования над небольшим представлением графа; [её тесты](validation/expression_grouping_reference_test.py) запускаются обычным Python. Это проверка алгоритма, **не поставленный парсер, транслятор или runtime LMX**. Производственные механизмы разрешения имён, договоров, хранения, admission и исполнения подключаются через интерфейс `GraphView` и существующие обработчики.

## 1. Роль вхождения и структурные связи

VALUE, TYPE, DATA, NAME, PLACE и RAW сохраняют собственные договоры. Для атома-ссылки на Structure в Expression трансляция определяет роль обычным `satisfies` по [шаблону операнда](LMX_semantics.ru.md#operand-receiver). Установленная `1` выбирает операнд, установленный `0` — группу. Возможность обоих ответов для неизвестной ссылки даёт ошибку до вычисления, как и другие конкурирующие чтения. Псевдокод получает уже установленный результат проверки. При известной цели, связывании и подготовленном native-входе транслятор генерирует прямой вызов по выбранному плану.

```python
def classify_expression_item(item, context, operand_match):
    node = resolve_reference(item)       # без вызова и изменения parent
    if not is_structure(node):
        return AtomPlan(node, context)

    if is_graph_reference_atom(item):
        if operand_match == 1:
            return OperandPlan(item, node, context)
        return GroupPlan(node, context)

    if is_anonymous(node):
        return GroupPlan(node, context)

    if parent(node) is not context.lexical_parent:
        return GroupPlan(node, context)

    return ReceiverPlan(node, context)
```

Развилка по имени и фактическому `parent` относится к Structure вне случая атома-ссылки. Безымянная Structure и именованная Structure с другим родителем образуют группы. Именованная Structure с текущим лексическим владельцем в качестве родителя проходит обычное разрешение ресивера или вызова.

`ReceiverPlan` ещё не выполняет вызов. Обработчик получает собственный договор ресивера: обычный callable вызывается, декларационный ресивер сохраняет декларационное действие, а его DATA-аргументы не становятся CODE. Группировщик не создаёт отдельной активации для `GroupPlan`.

```lmx
data:
    S: a b c d
    code:
        print: 1 + S + 2
        print: 1 + (a b c d) + 2
```

В первой строке рассматривается `S` как уже имеющийся в графе атом-ссылка вне роли операнда. Во второй строке группа безымянная. Группировка сохраняет родителя и контекст обеих групп. Допуск материала определяет договор `+`.

Нормативное основание: [Structure в контексте Expression](LMX_semantics.en.md#expression-structure-parent-guard).

## 2. Одно прохождение текущего уровня

Обычная форма `head: arg0 arg1 arg2` уже выделяет одну начальную позицию и правый хвост. Expression допускает выбранный операнд в разделяющей позиции:

```lmx
arg0 operand arg1 arg2 arg3
```

Обход получает упорядоченные вхождения текущего уровня. Для каждого операнда обычное разрешение находит готовый договор базовой операции и готовый приоритет; запускать тело, чтобы узнать приоритет, нельзя. При этом исходный граф не переписывается. Временный план хранит ссылки на его вхождения и контексты.

Последовательность соседних атомов без операнда между ними остаётся последовательностью. В бинарном случае справа один элемент. В общем случае правый хвост может содержать несколько элементов; количество формалов не используется как скрытый разделитель исходного выражения.

Внутренняя группа занимает одну позицию внешнего уровня. В допущенном графе Expression её содержимое рекурсивно планируется; одна полученная единица прозрачна, несколько единиц представлены одной подгруппой. Целая операция остаётся одной единицей, её исходные токены наружу не вставляются. Это структурная нормализация без исполнения. Договоры DATA-описания, полного TYPE, RAW и коллектора потока полей сохраняют свои области; возвращённые значения не обходятся заново как код.

## 3. Ровно две формы: без левого атома и с одним левым атомом

| Форма | `left` | `depth` | `right` |
| --- | --- | --- | --- |
| `operand arg0 arg1 arg2` | Отсутствует | 0 | `arg0`, `arg1`, `arg2` |
| `arg0 operand arg1 arg2` | Один атом `arg0` | 0 | `arg1`, `arg2` |
| `.(n)operand arg0 arg1 arg2` | Отсутствует | Значение n | `arg0`, `arg1`, `arg2` |

Это два варианта одного договора. Структурная группа тоже занимает одну левую позицию; свободный массив атомов слева не вводится. Допустимую длину правого хвоста определяет принимающий ресивер.

```lmx
(op 1 2 3)
```

Разбор однозначен:

```text
operation = op
left      = ABSENT
depth     = 0
right     = [1, 2, 3]
```

Первый правый элемент не переносится в `left`; отсутствующая позиция не подменяется пустой Structure или нулём. Если договор операции требует `left`, обычный допуск отвергает это применение. Если допускает отсутствие, используются его обычные defaults/правила связывания. Синтаксическая однозначность не означает, что любой ресивер принимает любые аргументы.

Операнд в первой позиции правого хвоста также может начинать префиксное применение. Низкий приоритет такого префикса сам по себе не создаёт ему отсутствующий левый атом. В частности, сохраняется установленное направленное связывание `2 ** -2`.

## 4. Связывание приоритетами и граница правого хвоста

Для обычных вычисляющих операндов используется проход с порогом приоритета. Операция более сильного приоритета образует вложенную единицу; более слабая заканчивает текущий правый хвост. Для равного приоритета применяется существующее направление связывания.

| Пример / условие | План |
| --- | --- |
| `1 + 2 * 3` | `+(1, [*(2, [3])])` |
| `a op b c high d`, `high` сильнее `op` | `op(a, [b, high(c, [d])])` |
| `a op b c low d`, `low` слабее `op` | `low(op(a, [b, c]), [d])` |
| `a op b c op d`, равный левосвязывающий приоритет | `op(op(a, [b, c]), [d])` |
| `2 ** 3 ** 2` | `**(2, [**(3, [2])])` |

Эта таблица показывает внутренний план, а не новую пользовательскую запись. У каждого применения один `left`. Неопределённой границы между двумя свободными левыми массивами здесь нет; общий шаблон сохраняет один left, отдельный числовой depth и right Array.

Префиксные и постфиксные формы используют уже установленные направленные правила. Для степени сохраняются `-2 ** 2` → `-(2 ** 2)` и `2 ** -2` → `2 ** (-2)`. Они не выводятся из одной универсальной позиции «степень выше всех префиксов». Конкретные числовые коды в проверочной модели условны: в LMX берутся реальные готовые приоритеты.

## 5. Общее левое вхождение и вычислительный контекст

У каждой обычной операции есть отсутствующий либо один левый атом. Группа занимает ту же одну позицию. Для **каждой** операции группировщик сохраняет одинаковый внутренний вид этой позиции: исходное вхождение, область значения по приоритетам и ещё не потреблённый окружающий вычислительный контекст. Никакой проверки имени `:=`, роли PLACE/NAME или особого флага присваивания в разборе нет.

```python
@dataclass(frozen=True)
class LeftView:
    occurrence: object   # один выбранный атом/структурная единица
    region: object       # область значения и ещё не потреблённый контекст
```

Это временная информация namespace, не новый аргумент или новый публичный тип LMX. Парсер не решает, какая часть будет потреблена как PLACE, NAME, RAW или значение. Этот смысл задаёт сам метод операнда через свой обычный договор.

| Запись | Что потребляет метод | Что остаётся выполнить |
| --- | --- | --- |
| `10 * 2 + 3` | Метод `+` получает значение всей левой области `10 * 2` | Добавить 3; результат 23 |
| `1 + v := 2 + 3` | Метод `:=` потребляет конкретное место `v` | Его результат 5 занимает это вхождение; остаётся `1 + 5`, результат 6 |

Во второй строке не происходит присваивания в `1 + v`. Метод использует один выбранный левый атом. Окружающий потребитель получает результат именно этого применения, а не повторно ищет переменную по имени. Поэтому `v := v + 1` читает старое значение отдельного правого вхождения `v` и не создаёт циклическую зависимость от будущей записи.

Группировщик одинаков для обеих строк. Потребление области и возобновление незавершённого контекста принадлежат общему механизму namespace/зависимостей. Другой метод с таким же договором места использует тот же механизм; пользовательский универсальный вход `@` от этого не объявляется PLACE автоматически.

Пути, индексы и составные адресуемые единицы предоставляет существующий анализатор соответствующих форм. Присваивание не получает отдельного синтаксического режима.

### Равнозначность двух записей решает сам метод

```lmx
(:= a 1)
(a := 1)
```

| Запись | Переданный `left` | `depth` | Переданный `right` |
| --- | --- | --- | --- |
| `(:= a 1)` | Отсутствует | 0 | `[a, 1]` |
| `(a := 1)` | `a` | 0 | `[1]` |

**Парсер и передача методу сохраняют это различие.** Первый правый аргумент не переносится в `left`, векторы не нормализуются заранее. Уже внутри метода операнда `:=` эти два входных случая обрабатываются как присваивание 1 в `a`. Это свойство его реализации, а не универсальное обещание эквивалентности любых двух таких форм любого пользовательского операнда.

В host-проверке canonical `AssignmentMethod` при depth=0 выбирает `StoreMethod.invoke`, отдельно от группировщика и передачи. Проверка записывает фактически полученные формы `(left отсутствует, 2 right)` и `(left присутствует, 1 right)` до выбора поведения внутри метода.

### Общий класс прижатых унарных форм

Операции, прижатые к одному атому слева или справа, сохраняют общий структурный класс с двумя направлениями. У них ровно один аргумент. Например, `++var` и `var++` обозначают разные разрешённые операции этого класса; он не ограничивается перечислением `++` и `--`.

Парсер устанавливает соответствующую структурную форму, а группировщик получает её уже в графе. Он не сканирует пробелы и скобки. В проверочном представлении `Binding.attached = "left" / "right"` отражает этот общий класс, без добавления поля в публичный `OPERANDS_TEMPLATE`. Значение, эффекты и выбор результата определяет метод конкретной операции.

## 6. Основной цикл разбора

В следующем фрагменте методов `Planner` функция `_binding()` читает готовые описания операций, `classify()` выполняет развилку из раздела 1, а курсор идёт по вхождениям **графа**. У порога есть отношение порядка и правило равенства; прибавлять единицу к реальному `PRIORITY` не требуется.

```python
def _binding(self, cursor, context):
    if not cursor.more():
        return None
    node = self.view.resolve(cursor.peek(), context)
    if isinstance(node, DecoratedOperation):
        node = self.view.resolve(node.operation, context)
    return self.view.binding(node, context)

def _depth(self, occurrence, context):
    node = self.view.resolve(occurrence, context)
    return node.depth if isinstance(node, DecoratedOperation) else 0

def _unit(self, cursor, limit, context):
    start = cursor.index
    def application(operation, operation_raw, left, right):
        return Apply(operation, operation_raw, left,
                     self._depth(operation_raw, context), right, context,
                     GraphRange(cursor.owner, start, cursor.index))
    first = self._binding(cursor, context)
    if first is not None:
        # An operand in the first position has no left occurrence.
        operation_raw = cursor.take()
        if first.attached == "right":
            raise ValueError("right-attached unary operation needs an atom")
        if first.attached == "left":
            if not cursor.more():
                raise ValueError("left-attached unary operation needs an atom")
            right = (self._attached_atom(cursor, context),)
        else:
            right = self._tail(cursor, first.prefix_limit(), context)
        left = application(first, operation_raw, ABSENT, right)
    else:
        left = self.classify(cursor.take(), context)

    while cursor.more():
        operation = self._binding(cursor, context)
        if (operation is None or operation.attached == "left"
                or not limit.accepts(operation)):
            break
        operation_raw = cursor.take()
        right = (() if operation.attached == "right" else
                 self._tail(cursor, operation.right_limit(), context))
        left = application(operation, operation_raw, left_view(left), right)
    return left

def _tail(self, cursor, limit, context):
    result = []
    while cursor.more():
        next_operation = self._binding(cursor, context)
        if (result and next_operation is not None
                and next_operation.attached != "left"
                and not limit.accepts(next_operation)):
            break
        # At the first RHS position, an operand starts a prefix unit;
        # there is no preceding RHS atom to supply its left argument.
        result.append(self._unit(cursor, limit, context))
    return tuple(result)

def _attached_atom(self, cursor, context):
    """Exactly one atom plus its attachment chain, never an n-ary tail."""
    start = cursor.index
    operation = self._binding(cursor, context)
    if operation is None:
        unit = self.classify(cursor.take(), context)
    elif operation.attached == "left":
        raw = cursor.take()
        if not cursor.more():
            raise ValueError("left-attached unary operation needs an atom")
        target = self._attached_atom(cursor, context)
        unit = Apply(operation, raw, ABSENT, self._depth(raw, context), (target,), context,
                     GraphRange(cursor.owner, start, cursor.index))
    else:
        raise ValueError("an attached unary operation requires one atom")
    while cursor.more():
        operation = self._binding(cursor, context)
        if operation is None or operation.attached != "right":
            break
        raw = cursor.take()
        unit = Apply(operation, raw, left_view(unit), self._depth(raw, context), (), context,
                     GraphRange(cursor.owner, start, cursor.index))
    return unit
```

Вызов `_unit` в первой позиции не требует фиктивного левого элемента. Цикл верхнего уровня повторяет его до конца выбранного структурного уровня; несколько результатов остаются последовательностью. Этот проход строит зависимости на одном уровне. Затем `normalize_expression` рекурсивно подготавливает вложенные Expression-группы, сохраняя каждую как один внешний атом и не перенося её токены через границу приоритетов. Оба шага относятся к общему группировщику; ни один не выполняет тело операнда.

Полный код, включая `Limit`, `Cursor`, `LeftView`, разрешение graph view, общий вызов метода с числовым depth без изменения сторон входного вектора и порядок группового присваивания: [expression_grouping_reference.py](tools/expression_grouping_reference.py).

## 7. Рекурсивный план и упаковка атомов

Уровень разбирается обычным `Planner.plan`; найденные вложенные Expression-группы проходят тот же алгоритм рекурсивно. После обработки содержимого группы применяется общий принцип **одна внешняя позиция**:

```text
normalizeUnit(unit):
    если это группа в допущенной позиции Expression:
        children = normalizeExpression(planLevel(unit.graph, unit.context))
        если children содержит одну единицу:
            payload = единственная единица
        иначе:
            payload = Group(children)  # включая присутствующую пустую группу
        вернуть один AtomView(payload, исходное вхождение и контекст)
    если это полная операция:
        рекурсивно нормализовать её Expression-аргументы
        сохранить границы, приоритетный план, исходные вхождения, left/right и описание depth
    иначе:
        сохранить единицу по её принимающему договору

normalizeExpression(sequence):
    вернуть последовательность normalizeUnit(item) для каждого item
    # не соединять поля соседних результатов-Group
```

Это внутренние представления, не новые поля исходного графа или системные функции. Числовой depth входит в общий `OPERANDS_TEMPLATE`; описание его ещё не полученного выражения — временная информация применения, а не дополнительный публичный вход. В проверочном коде тонкая обёртка называется `PreparedAtom`, а материальная подгруппа — `PreparedGroup`. У единственного вложенного группового результата нормализуется его представление, поэтому `(((5 6)))` не сохраняет три контейнера в готовом плане: это один внешний атом с подгруппой `(5 6)`. Исходные узлы и контексты остаются доступны через представление.

**Нельзя просто подставить внутренний `Apply` вместо группового атома.** Для `2 * (3 + 4)` вычисляемый payload — целое применение `+`; для внешнего уровня это один атом. Иначе поиск соседнего левого атома может ошибочно войти во внутренний `+` и выбрать только `4`. `PreparedAtom` сохраняет эту границу, а `LeftView` по-прежнему хранит исходное вхождение и вычислительный контекст для каждого присутствующего `left`.

```lmx
1 + 2 (((3))) (4) ((5))       # нормализованный right: 2, 3, 4, 5
1 + 2 (((5 6))) (4) 5        # right: 2, одна подгруппа (5 6), 4, 5
1 + 2 (+ 5 6) 4 5           # right: 2, одна вычисляемая единица, 4, 5
```

Во всех трёх случаях план строится успешно. Внешний обычный `+` получает пять фактических значений и отклоняет такую арность внутри метода; Array-профиль не собирает дополнительные правые аргументы в неявный Array. Группировщик не добавляет операцию между `5` и `6` и не проверяет правила сложения. В третьем случае операция задана: внутренний `+` получает отсутствующий `left` и оба значения справа, что даёт `11` при его собственном запросе. Никакой перенос первого правого аргумента в `left` на этой стадии не допускается; внешняя арность от результата внутренней операции не меняется.

### Выбор последовательности и прежнее правило двух групп

После рекурсивной нормализации последовательностный потребитель выбирает элементы единственной материальной подгруппы либо уже имеющиеся соседние элементы. Этот выбор не вычисляет операции и не повторяет обход графа. В широком правом хвосте нормализованные подгруппы остаются отдельными аргументами.

Для `(a b c) .: (a c b)` обе группы содержат по три единицы. Последовательностный договор получает `a, b, c` и `a, c, b`; отдельная подготовка применения передаёт всю левую последовательность одним `left`, а три правые единицы — массивом ссылок. Для `(a b c) .: (f g h) (f g h) (f g h)` справа уже три нормализованные подгруппы: их поля не сливаются в девять аргументов.

```text
План последовательностей:   a b c  .:  a c b
Подготовленное применение: := {left: (a b c), depth: 1, right: [a c b]}
```

`(a b) .: (((x y)))` после нормализации единственной группы получает две правые единицы `x`, `y`. `(a b) .: (((x y))) z` получает две единицы `(x y)` и `z`. `(a b c) .: (((x y)))` отклоняется по количеству до первой записи. Утверждение прежней редакции, что дополнительные singleton-оболочки обязательно сохраняют внутреннюю группу как единственный элемент выбранной последовательности, заменено этим правилом.

У адаптера применения нет второго независимого раскрывающего прохода: рекурсивная работа принадлежит группировщику, а `prepare_actuals` только упаковывает уже выбранные ссылки. Отсутствующий `left` сохраняется. Полный TYPE, одна готовая структурная величина и DATA-описание сохраняют собственные принимающие договоры; `int -> (int int)` по-прежнему не становится `int -> int int`.

### Граф, контекст и отложенные эффекты

Каждое вхождение сохраняет исходный графовый диапазон и контекст. Ссылки разрешаются без изменения фактического `parent`. Применяется общая развилка имени/`parent`, а не тест написания скобок. Повторные вхождения одной цели остаются разными вхождениями; структурная подготовка не склеивает их эффекты.

Нормализация не является исполнением всего достижимого графа. Тело ресивера, DATA-инициализатор, RAW и возвращённое готовое значение не обходятся как новый CODE по факту наличия структурных полей. `PreparedAtom` хранит готовый план Expression; настоящий запрос результата, порядок эффектов и короткое замыкание обеспечивает общий механизм исполнения. Представление обратного графового ребра в host-модели сохраняет конечный план; оно не устанавливает новые правила выполнения циклических графов LMX.

## 8. Вложенное выражение, поток полей и ссылка

В позиции полного выражения `1 + ((2))` обрабатывается рекурсивно: внутренняя группа предоставляет одну единицу `2`, внешняя — результат этой единицы. Скобки при этом нигде не распознаются. В `(target) := (2 * 3)` обработка выбранного правого уровня даёт одну вычисляемую единицу `2 * 3`, а не три сырых аргумента `2`, `*`, `3`.

Одного количества физических детей недостаточно для всех случаев. `(copy(Model))` — коллектор потока полей, который создаёт один контейнер при 0, 1 и N полях. Его договор известен до выполнения; нельзя выполнить `copy`, сосчитать поля и задним числом выбрать другой смысл группы.

Для группового присваивания эти формы потребляют одинаковый поток:

```lmx
(a b c) .: copy(d)
(a b c) .: (copy(d))
```

В первой форме поток уже доступен потребителю. Во второй он собран в контейнер, из которого тот же последовательностный договор читает непосредственный уровень. Скалярное `ptr := (copy(d))` сохраняет один структурный результат; его оболочку удалять нельзя.

Аналогично, `(a b c) .: myFn()` сначала получает один целый результат вызова.
Если это единственный Array справа, сам метод `.:` выбирает его непосредственные
элементы для трёх мест. Это приёмка Array, не новое раскрытие или исполнение
результата группировщиком. При трёх соседних Array справа каждый остаётся одним
элементом источника. В проверочном коде `AssignmentMethod` выбирает профиль canonical `:=` по
числовому depth: `StoreMethod` обслуживает depth=0, а
`ElementwiseStoreMethod` при depth=1 выбирает поля групп/Array и вызывает
единый `elementwise_assignment`: получить все правые значения, проверить
форму и допуск, затем записать. Группировщик не содержит этой диспетчеризации: `.:` уже представлено базовой операцией `:=` и depth=1. Большие глубины подключаются к общей реализации подъёма операции.

Атом-ссылка на Structure участвует в этой обработке групп только вне роли операнда. Подготовка сохраняет фактический `parent` адресуемого объекта и выбранную при трансляции роль вхождения.

## 9. Подготовка применения и исполнение

Планирование не выполняет тела. После выбора требуемых единиц адаптер:

1. Сохраняет отсутствие `left` либо получает один левый actual — целую единицу или пакет ссылок на выбранные места.
2. Сохраняет описание depth с исходным контекстом. После установления востребованности получает и допускает одно неотрицательное целое значение, ровно один раз. При отсутствии декорации передаёт 0, для `.op` — 1.
3. Создаёт `right` как массив ссылок на элементы правой последовательности в их порядке.
4. Сохраняет исходные вхождения и контекст, необходимые собственному договору метода для NAME/TYPE/DATA/PLACE/BODY/RAW. RAW должен ссылаться на исходную целую единицу графа или её диапазон в текущем уровне; заменять её заново собранной строкой нельзя.
5. Передаёт методу выбранную форму **left, depth, right** без переноса первого right в left. Метод сам потребляет аргументы по своему договору; общий namespace затем возобновляет непотреблённый контекст. Полное внутреннее выражение не исполняется во время планирования.

Следующий фрагмент относится к **уже востребованному** применению. До его вызова production namespace должен определить востребованность и сохранить ранее полученные значения окружающего контекста. Сам фрагмент не является планировщиком эффектов, не обходит все применения подряд и не проверяет имя операции или роль её входов:

```python
def receive_application(application, method, namespace, evaluate, obtain_depth=None):
    """Receive an ALREADY DEMANDED application, outside the grouper.

    Precondition: the production executor has established demand and retained
    previously obtained surrounding values. This helper is not a scheduler:
    evaluate must resume the existing context, preserving its effect order and
    short-circuit rules. Calling every syntactic Apply eagerly is incorrect.

    The method receives the unchanged left view/absence and unchanged right
    sequence. Only *inside that method* may it choose equivalent handling of
    prefix/infix forms or a PLACE/NAME/RAW/value consumption contract. Neither
    the grouper nor this dispatcher moves right[0] to left. MethodOutcome is
    model bookkeeping for the existing namespace dependency mechanism, not a
    new public LMX result type or an extra return field required of methods.
    evaluate(plan, replacements) substitutes by occurrence identity, never by
    identifier spelling. A production executor retains its demand/effect rules.
    """
    def missing_depth_integration(expression, context):
        raise NotImplementedError("dynamic depth needs the ordinary namespace value request")
    actuals = prepare_operand_arguments(application.left, application.depth,
                                       application.right,
                                       obtain_depth or missing_depth_integration)
    outcome = method.invoke(actuals.left, actuals.depth, actuals.right,
                            namespace, evaluate)
    if application.left is ABSENT:
        return outcome.value
    region = application.left.region
    if outcome.consumed_left_region is region:
        return outcome.value
    return evaluate(region, {id(outcome.consumed_left_region): outcome.value})
```

`MethodOutcome` здесь — учёт потребления в проверочной модели namespace. Это не новый публичный возвращаемый тип, скрытый параметр или обязательное поле LMX-метода. Заменяется конкретное вхождение графового плана, а не все совпадающие имена.

План сохраняет не только имя и готовый приоритет, но и конкретное вхождение операции (`operation_raw` в проверочном коде). Обработчик выбирается по разрешённой операции и её контексту, а не заново по строке имени. `GraphRange` удерживает исходный графовый диапазон целого выражения для RAW; текстовая реконструкция не требуется.

`RxLogicalArguments.collect` вызывается внутри метода операнда по его собственному алгоритму; `asOperand` помещает такой вызов в создаваемое тело. Передача добавляет числовой depth между входами, сохраняя исходную форму left/right и не выполняет повторного раскрытия групп. При коротком замыкании не выполняется пропущенная ветвь. Результат одного востребованного вхождения сохраняется на время текущего вычисления; постоянного кеша в исходном графе нет. Разные вхождения ссылки на один узел не склеиваются в один эффект по идентичности узла.

Для группового присваивания порядок выглядит так:

```python
values = [read_once(item) for item in right_items]
validate_all(targets, values)  # арность, места и типы до первой записи
for target, value in zip(targets, values):
    write(target, value)
```

Таким образом, перестановка не читает уже изменённую левую часть. Ошибка количества или допуска не оставляет частично выполненной записи. Предыдущие побочные эффекты самих RHS при этом не получают новой транзакционной отмены.

## Дополнение 26 ноября: условные области, срезы и поэлементные места

Групповая перестановка записывается `(a b c) .: (b c a)`: Structure — Array элементов свободного типа, и это обычное поэлементное присваивание. `.=` — поэлементное сравнение по скалярному `=`, не присваивание. Скалярный `:=` и примеры `1 + v := 2 + 3` сохраняют прежний договор одного места. Место `.:` определяется тем же LeftView без ветвления группировщика по имени операции. Все правые значения перестановки получают до первой записи.

Составная условная операция имеет одну область условия и две ограниченные RAW-области. Подготовка каждой области сохраняет исходные ссылки и контекст; подготовить область не значит исполнить её. Группировщик получает эти границы от общей структуры и не сканирует исходный текст. Приоритет `?:` — между `||` и присваиваниями, вложение справа. Исполняющий метод получает условие один раз и вызывает обычное получение значения только для выбранной ветви; невыбранная ветвь не даёт эффектов и не читается ради определения результата.

```python
def evaluate_conditional(condition_occurrence, yes_occurrence, no_occurrence):
    condition = obtain_once(condition_occurrence)
    require_int_truth(condition)
    selected = yes_occurrence if condition != 0 else no_occurrence
    return obtain_once(selected)
```

Это одна реализация выбора для `a ? b : c` и ресиверной формы `` `?:`(a; b; c) ``; `obtain_once` обозначает существующее получение в живом контексте, а не новый evaluator с собственными правилами. Новый [исполнимый контрактный пример](tools/ternary_slices_reference.py) моделирует этот интерфейс и нормализацию границ среза отдельно от прежнего reference-планировщика.

Индексный анализатор предоставляет либо скалярную адресуемую единицу, либо описание выбранных индексов среза. У пропущенных start/stop/step сохраняется присутствие отдельно от значения. В VALUE срез выдаёт новый внешний Array; в PLACE для `.:` он обозначает исходные выбранные места. Тип/shape, порядок получения, перекрытие, отрицательный шаг, `a[::-1]` и отличие от недопустимого `a[-1]` определены в [общем договоре](TERNARY_AND_SLICES.ru.md). В нативном L2 отсутствие автоматической проверки не делает отрицательный Array-индекс корректным; для обратного смещения от адреса используется указатель, поскольку интерпретируемое L2 всё равно проверяет Array-границы.

Арифметические/сравнивающие операции с depth используют общий transport left/depth/right и приоритет базового семейства. `.:` — один токен до обработки структурного `:`. Прижатые `.++`/`.--` сохраняют общий класс направленных унарных применений. `fuse` получает RAW-область и работает с временным планом одной операции, сохраняя единственный полный граф и обычные места исполнения. Подробности исходных границ и коллизий: [грамматика §30](LMX_grammar.ru.md#conditional-slice-grammar).


## Глубина операции: план сохраняет выражение, метод получает число

[Нормативные записи](OPERATOR_DEPTH.ru.md#syntax) — `op` (0), `.op` (1),
`.(expression)op` (полученное значение). Повторные точки не кодируют глубину.
Внутри `(...)` после точки общий P0 строит обычную область Expression; группировщик
получает её графовое вхождение и контекст, не исходные скобки. Приоритет,
ассоциативность и прижатый класс сохраняются от базовой операции.

`DecoratedOperation` в Python — только view уже разобранного вхождения.
`_binding` выбирает базовую операцию, а `_depth` сохраняет значение-константу
либо `DepthExpression`, не вызывая её. Рекурсивная нормализация не обходит
depth как новый RHS и не вычисляет его. Общая передача после запроса операции
использует [prepare_operand_arguments](tools/operand_depth_reference.py):
возвращает `left, int depth, right`, сохраняя обе стороны и их отсутствие.
Она не открывает Array, не переносит right[0] в left, не читает PLACE как
VALUE и не реализует сам поэлементный подъём.

`.(0)op` действительно передаёт 0; это не значение «подставить 1».
Нецелый, отрицательный или многозначный результат даёт диагностику
транслятора при установленном статическом случае либо интерпретатора при
достижении. Это не LMX throw и не добавление ошибки в throws. Несовместимая
с заданным depth структура операндов имеет тот же статус. Вычисление вызывает существующий namespace в исходном
контексте ровно один раз для этого востребованного применения. В пропущенной
ветви `?:`, `&&` или `||` не исполняется даже выражение depth. Кеш на будущие
активации не создаётся. Порядок окружающих эффектов остаётся обязанностью
обычного механизма востребованности; этот helper не новый scheduler.

Исходные `.:` и `.(n):` дают семейство `:=` с глубиной 1 и n; в частности,
`.(0):` даёт whole-присваивание. Эта канонизация производится общим
подключением исходных форм, до вызова группировщика, а не проверкой имени
в LeftView. Точное имя `` `.:` `` не разбирается в такую пару.
Ресиверная форма использует базовое `` `:=` `` с обычным именованным
входом depth выбранного профиля. [ABI и формы](OPERATOR_DEPTH.ru.md#abi).

[10 host-проверок depth](validation/operand_depth_reference_report.json)
дополняют 67 проверок планировщика: контекст, отсутствие побочных эффектов
при подготовке, повторная активация, ленивые ветви, неизменность аргументов
и диагностику некорректного depth до входа в метод. Это не проверка исходной грамматики P0;
производственное исполнение новых исходных примеров остаётся **NOT_RUN**.


## Готовое Array VALUE и обычные анонимные поля

Принимающая роль определяет, какой граф обходит группировщик. Самостоятельное
`[arr2]` в VALUE обслуживается обычным конструктором Array и передаёт одно
готовое значение с одним целым полем arr2; `[]` даёт одно пустое значение.
Это не прозрачная singleton-группа Expression. Группировщик не читает исходные
скобки и не получает управляющие flags «квадратные/круглые».

В DATA `Struct: [a b c] [a b d] [a b c d]` и
`Struct: (a b c) (a b d) (a b c d)` задают те же три анонимные Structure-поля.
Их разные длины допустимы. Typed rank-инициализатор, например
`[][]int: [[a b c] [a b d] [a b c d]]`, имеет другой принимающий договор:
он требует прямоугольности и диагностирует длины 3/3/4. Его потребление строк
в flat storage не является дополнительным раскрытием группировщика или
переписыванием живого графа. [Полная норма](ARRAY_STORAGE.ru.md#constructors).


### Лексическая граница модификатора `.(expression)`

Непосредственная пара `.(` вне защищённых лексических режимов всегда начинает
модификатор оператора либо функции, прежде чем точка могла бы войти в число
или layout. Поэтому `1.(2)+3` разбирается как число 1, описание depth=2,
базовый `+`, число 3; запись `1 .(3)+ 2 .(2)+ 3` имеет те же границы без
пробелов: `1.(3)+2.(2)+3`. Это правило записи, не обещание успешного допуска
этих значений на выбранной глубине.

Внутреннее выражение и соответствующую закрывающую границу сохраняет общий
P0. Отдельный числовой parser не вводится. Последующие алгоритмы получают
прежнее описание depth в графе и не ищут скобки в исходной строке. `1.5`,
`.5`, `1.` и `1.+2` сохраняют прежнее числовое чтение; содержимое строк,
комментариев и точных имён не раскрывается. Квадратные Array-формы и
`[](N)int`/`@(N)int` не затронуты. Квадратная запись модификатора не является
alias. [Полный алгоритм P0](LMX_grammar.ru.md#conditional-slice-grammar).
Production P0/LMX execution этих границ — **NOT_RUN**.
