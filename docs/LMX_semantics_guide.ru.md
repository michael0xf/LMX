# Пояснения к семантике LMX

Это короткие ненормативные примеры. При расхождении действуют
[семантика](LMX_semantics.ru.md) и [грамматика](LMX_grammar.ru.md).

<a id="data-receiver-execution"></a>
## Подготовка не выполняет программу

Построитель сворачивает готовые объявления без вызовов. Подготовка namespace учитывает только корневые
объявления data и code; вложенные ветви и ссылки графа не обходит. В последовательности

```lmx
mark()
int: y makeValue()
```

подготовка не переносит makeValue() перед mark(). Выполнение достигнутого ресивера остаётся обычным
вызовом и может исполнить переданный код; это не разрешает заранее запускать все инициализаторы data.
Поданный actual подавляет соответствующий инициализатор. [Норма](LMX_semantics.ru.md#call-frame-20261115).

<a id="admission-stages"></a>
## Два шага допуска

| Когда | Что происходит |
|---|---|
| Построение графа, кандидат известен | Проверяется используемый интерфейс. `test` не исполняется. |
| Фактический допуск при исполнении | Если первая часть уже выполнена, она не повторяется. Затем исполняются заданные `test`. |
| Первая проверка вернула `0` | Допуск немедленно прекращается; оставшиеся проверки не исполняются. |

Известность кандидата при построении не отменяет второй шаг при фактическом допуске. Само изменение
значения не запускает все проверки заново. Норма — [допуск и test](LMX_semantics.ru.md#admission).

<a id="callable-description"></a>
## Входное описание и композиция

У вызываемого одна входная data вместо прежних args и data. Она не дополняется полями тела:
локалы code возникают в namespace вызова. Поэтому старые три примера add5 с отдельными args/data
больше не задают действующую норму. merge по-прежнему явно строит новый граф; его правила не являются
скрытой инициализацией вызова. Сигнатура без code описывает вызов; C-параметры выводятся из реальных
подач аргументов. [Точная постановка и оставшаяся синтаксическая миграция](../next_core_tasks_v3.md#native-structures).

<a id="receiver-arities"></a>
## Место и значение у `int` и `@`

Место объявляет форма ресивера с перечислением его аргументов. Это отдельные
примеры, не последовательные операторы одной программы:

```lmx
int: x         # место int без начального значения
int: x 5       # int со значением 5

@: ptr         # void-ссылка без заданного адреса
@: ptr 0       # void-ссылка с явным нулевым адресом
@: ptr Model   # ссылка на существующую Structure, уже не пустой void-указатель
```

Первое определение выделяет место; в коде повторная форма с кандидатом
записывает в него после допуска, а повторная форма без кандидата только
сверяет требование (в данных повторная форма — ещё одно вхождение имени,
[имена и пути](LMX_semantics.ru.md#fields)). Составные записи с местом во внешней голове — `x: int()`,
`x: int: 5`, `ptr: @()`, `ptr: @: 0`, `ptr: @: Model` — сняты решением
автора 2026-11-10 ([семантика](LMX_semantics.ru.md#receiver-args-only)):
`ms: int: time` в данных объявляет Structure `ms` с полем `time`, а не место
`ms`.

<a id="header-receivers"></a>
## Заголовок и служебные таблицы

Плоский заголовок Lmx состоит из parent/length/storage. `parent(S)`, `length(S)` и `sys\storage(S)`
читают эти поля напрямую. `sys\native(S)` возвращает native-дескриптор с вариантами из таблиц call
либо 0; `sys\capacity(S)` — резерв из таблицы арены. Все пять форм без аргумента выбирают текущую
data; для code нужен явный аргумент. Чтение не компилирует и не вызывает native.

Эти ресиверы выполняются только в code; одноимённые записи data остаются обычными данными.
Например, data\length выбирает пользовательское поле, а length() — длину данных запуска.
data/code остаются аргументами call, node сохраняет прежний смысл.

Structure и Array<@> взаимозаменяемы; числовой Array<T> хранит элементы T. Все массивы имеют переменную
длину и общий механизм выделения. sys\resize(S,n) меняет length, sys\reserve(S,n) только резерв.
Capacity хранится в таблице арены, не в заголовке. Адрес дескриптора сохраняется, storage может переместиться.
В L2 индекс, включая отрицательный, лишь вычисляет смещение. В L3 соседние [i][j] дают один линейный
индекс и одну проверку длины; L3-ссылка на элемент содержит ссылку на дескриптор массива и index,
а не storage. Сырой L2-адрес при перемещении storage не исправляется.
[Контракт](LMX_semantics.ru.md#array-capacity), [реализация OPEN](../next_core_tasks_v3.md#flat-lmx-descriptor).

<a id="get-descriptor"></a>
## Адреса полей заголовка через descriptor

`sys\descriptor(S)` возвращает обычную Structure из трёх адресов настоящих полей parent/length/storage:
Lmx **, size_t *, void **. Без аргумента выбирается текущая data, в том числе внутри тела управления.
Ни native, ни capacity в этом результате нет.

Если d = sys\descriptor(S), `\(d\length) := n` непосредственно меняет длину в S; `d\length := p`
меняет указатель в самом d. Первый пример сам по себе не выделяет хранилище: для согласованного
изменения размера служит sys\resize. Нет копии заголовка, прокси, write-back или особого присваивания.

Обычные типизированные разыменования и пути допускают запись ссылок и указателей на функции;
запрет менять голое имя Structure не запрещает путь. Глубина указателей и мерность массивов —
произвольные конечные; время жизни адресов обычное.
[Точная форма](L2_spec_ru.md#get-descriptor).

<a id="system-indexof"></a>
## Индекс поля

`sys\indexof(field parent)` возвращает физический индекс единственного вхождения `field` среди
непосредственных элементов Structure `parent`. Если поле отсутствует или та же ссылка встречается
несколько раз, операция сообщает ошибку по общим правилам отказа.

`sys\indexof(field index parent)` выбирает вхождение той же ссылки с номером `index`, считая с нуля,
и возвращает его физический индекс в `parent`. Если указанного вхождения нет, это ошибка.
Номер вхождения и возвращаемый индекс — разные величины: при вхождениях одной ссылки в позициях
2 и 5 вызов с `index = 1` возвращает 5. Обе формы получают `parent` явно; формы без аргументов нет.

Искомое поле определяется его идентичностью/ссылкой, а не совпадением имени или примитивного значения.
Поиск не следует вложенным структурам или графовым ссылкам. Для Structure и Array<@> действует один
механизм чтения непосредственных элементов. Использовать существующую адресацию; отдельная таблица
обратных индексов и её обслуживание при записях не нужны.

<a id="callable-admission"></a>
## Что проверяет интерфейс вызываемого

Методы с формалами `(int: x; int: y 5)` и `(int: x)` оба допускают `f(1)`, но
записанное у Consumer обращение `f(1; y := 25)` допускает только первый.
Проверяются необходимые явно использованные обращения, не совпадение
списков формалов и не предполагаемое поведение тела. Пользовательские
проверки поведения — отдельный этап.

<a id="method-pointer"></a>
## Имя метода и указатель на него

`myFunc()` вызывает объявленный метод напрямую. После
`@: ptr myFunc` форма `ptr()` вызывает метод через указатель; повторное
`@: ptr otherFunc` в коде присваивает существующей ячейке другой
совместимый метод (в данных повторная форма — ещё одно вхождение имени).
Голое `myFunc` или `ptr` лишь читает значение.
`(\ptr)()` — вызов после явного разыменования; `\ptr()` применяет `\`
к **результату** вызова согласно обычному приоритету, а не является особым
способом вызвать указатель.

<a id="native-structures"></a>
## Кадры native и обходчика

<a id="call-receivers"></a>
### Ресиверы `call` и `fncall`

| Форма | Переданные значения `args` | Входные данные | Результат |
|---|---|---|---|
| `call(args data code)` | `args` | `data` | нет |
| `call(data code)` | не поданы | `data` | нет |
| `call(code)` | не поданы | `code` | нет |
| `fncall(args data return code)` | `args` | `data` | по `return` |
| `fncall(data return code)` | не поданы | `data` | по `return` |
| `fncall(return code)` | не поданы | `code` | по `return` |

`args` — Structure фактически передаваемых значений, ровно та, которая является
структурой аргументов обычного вызова. Это не объявления формалов, не сигнатура
и не отдельная часть callable. Входные места, требования и умолчания описывает `data`.
`return` — описание результата, `code` — исполняемая Structure. `call` не возвращает
значения; `fncall` возвращает результат согласно `return`.

Во всех формах без `args` дополнительных фактических значений нет. Отсутствующая
`data` означает саму `code`: `call(C)` равнозначен `call(C C)`, `fncall(R C)` —
`fncall(C R C)`. Дочернее поле `data` внутри `code` автоматически не выбирается.
Это сокращения одной операции, без обязательного создания пустой Structure
или нового служебного объекта для пропущенной `args`.

Все формы и обычные вызовы методов/Structure используют в интерпретаторе один путь:
выбор частей → связывание actuals с data → общий допуск → свежий namespace → исполнение и результат.
Приём actuals не меняет исходную data и не запускает входную инициализацию.
Вызовы из test и преобразователей проходят тот же механизм. Известные native-вызовы
из native по-прежнему могут идти прямо в C, без графовой упаковки.
[Полный контракт и именованная подача](LMX_semantics.ru.md#call-receivers).

<a id="private-binding"></a>
### Ресивер private:

`private:` исключает помеченное поле и соответствующую привязку из динамических источников
вызова. Прямая видимость откуда угодно, явные пути и обычный лексический поиск сохраняются;
правила последовательной видимости и явной передачи аргументов не меняются.
Пропуск поля следует общему порядку связывания, одинаковому для всех форм call/fncall,
обычных вызовов, интерпретатора и native. Это свойство поля, не глобальный запрет имени
и не защита доступа. Использовать общий binder без отдельного реестра или проверок прямых чтений.
[Полный контракт](LMX_semantics.ru.md#private-binding).

<a id="call-frame-20261115"></a>
Каждый вызов создаёт собственный namespace. У fn/sub/catch входы описывает единая data;
args в call/fncall содержит фактические значения. Краткие заголовки сохраняются. Actual заменяет соответствующее
исходное объявление кадра, и его инициализатор не выполняется. Подготовка собирает только корни
data/code, без обхода ветвей и графовых ссылок и без автозаполнения исходной data.

При входе нет фазы исполнения инициализаторов. Готовые объявления сворачиваются при построении
чистого графа без вызовов программы; uninit:T сохраняется. Неиспользуемое вычисляемое поле data
не выполняется. Чтение получает его значение общим механизмом, как `data\field`: исполняется
написанный RHS, а не неявный вызов полученной ссылки. Для `@: fptr getFuncPtr()` запись
`fptr("hello world")` сначала получает указатель, затем вызывает полученную функцию.

Переменные и const видны с первоначального объявления вперёд в своей области и ниже.
Двусторонняя видимость сохраняется у имён Structure и callable, но не у переменной с указателем
на функцию. Новое имя ветви не выходит наружу. Повторное `int: x bump()` сохраняет вычисление,
допуск и запись существующему x; убирается только повторная C-декларация. Физические повторы
полей сохраняются и выбираются `S\[n]x`. Явный путь не ограничивается порядком объявления
голого имени. Чтение объявления через путь ничего не исполняет; RHS исполняется при достижении строки code.

Голое x и @x относятся к месту кадра, независимому от замен исходного поля сразу после входа,
даже до первого чтения: сохраняется выбранное значение либо вычисляемое описание.
Правило одно для явной data, лексического и динамического связывания. Это не глубокое копирование
объектов по ссылкам. `x := 0` меняет namespace; `data\x := 0` — исходный граф.
Для вычисляемого входа `int: x next()` обращение @x получает значение и адрес локальной ячейки.
При `@(data\field)` и исходном `int: field getValue()` адресуется запись объявления, а не результат
getValue(): явный путь ничего не исполняет (решение автора 2026-11-17; прежнее правило снято).
Готовое место адресуется непосредственно.
Время жизни обычное. @f() было исследовательским примером, не задачей отдельной поддержки или запрета.

Обязательное копирование исполняемого code при входе отменено, включая прежнюю копию только кода
C-функции. Независимость выбранных локальных значений/описаний сохраняется; связывание передаётся
скрытыми аргументами, без копии окружения. Методы и обычные Structure компилируются общим механизмом
без data=code; разные реальные подачи дают разные C-сигнатуры. Известный native вызывает известный
native прямо в C. Правка графа не обнуляет native: обновление требует явной компиляции и границы
endturn. До границы момент применения правки исполняемого графа не гарантируется.

Локальные кадры не публикуются. Load-dirty, общий кеш прямого доступа и flush() отменены;
явные записи наблюдаются через реальные алиасы в порядке исполнения.
[Согласованная норма](LMX_semantics.ru.md#call-frame-20261115),
[единое ТЗ M14](../next_core_tasks_v3.md#native-structures).

<a id="flush-receiver-contract"></a>
<a id="direct-access-cache"></a>
Старые примеры flush() и общего кеша сняты: исходный граф меняется только явными операциями,
локальные переменные назад не публикуются.

<a id="native-merge"></a>
## Компиляция, изменение и следующий такт

Дескрипторы native всех Structure принадлежат таблицам call в арене. Только fn/sub/catch получают
обычное поле native, ссылающееся на тот же дескриптор. Известные native-вызовы внутри native идут
прямо в C с нужными скрытыми аргументами. Копия/merge сами не компилируют новое тело и не создают
ему готовую запись в call; явно выбранная компиляция или восстановление устанавливает эту связь.

`sys\compile(S)` строит и проверяет чистый граф без запуска программы, транслирует в L1/C,
компилирует/связывает машинный код и регистрирует успешный результат; ошибки возвращаются.
Запись в граф не сбрасывает native и не запускает отслеживание. Если A прямо вызывает B,
для изменения этого вызова компилируется единица с A и B, а не только B.

`sys\endturn()` выходит к обычной границе такта через все зарегистрированные finally.
Catch этот выход не перехватывает, к месту вызова управление не возвращается; сам ресивер
не останавливает Thread/Message. До границы момент применения правки исполняемого графа
не гарантирован. После успешной явной компиляции и границы следующий вход использует обновление.
Один endturn ничего не компилирует, не проверяет и не публикует локалы.
[Полный контракт](LMX_semantics.ru.md#explicit-compilation).

`sys\toLmx(Thread)` сохраняет выбранный Thread и сериализуемое содержимое всех таблиц его арены,
в том числе таблиц call/native. После перезапуска на той же платформе используются готовые бинарники
по идентификаторам модуля/входа, без повторной трансляции. Для произвольной S внешние таблицы
не добавляются скрыто; R0 — частный Thread, а не единственный корень такого сохранения.

<a id="factory-result"></a>
## Возвращённый метод

В code строка `@: add5 makeAdder(5)` **вызывает** фабрику и сохраняет возвращённый
метод. Затем `add5(1)` вызывает его через ссылку. Запись данных
`add5: makeAdder 5` лишь объявляет Structure `add5` и фабрику не вызывает; среди
исполняемых записей та же запись — вызов своей головы `add5`: вызываемое (метод
или указатель на него) вызывается, а обычная Structure запускается над данными
после двоеточия; аргумент записи один, `data`, поэтому для Structure `add5` два
поля `makeAdder` и `5` — ошибка
([журнал](../LMX_blog/2026-11-11.md#structure-call-by-name); чтение
исполнителя — [ответы](../LMX_blog/q/fable-self-answers-20261110.md), Р21,
п. 4 и 6). Если тело
возвращённого метода читает свободное `n`, динамический вход вызывающего имеет
приоритет перед скопированным лексическим запасным источником.

<a id="dynamic-fallback"></a>
## Динамический и лексический источники

Пример не является синтаксисом LMX: в скопированном лексическом контексте
`x = 10`, вызывающий передаёт `x = 25`. Свободное `x` читает 25;
`node\x` явно читает 10. При следующем вызове с `x = 40` свободное
`x` читает 40, а без динамического источника — лексические 10.

<a id="message-conversion-context"></a>
## Контекст преобразований Message

Схема `a → int` в Message A и `a → String` в Message B — не синтаксис
LMX. Один метод с требованием `a` получает смысл из контекста данного
Message; B не наследует преобразования A из-за доставки письма. Примитивное
`Foot → Meter` не доказывает `implements` для двух произвольных Structure.
При вызове могут понадобиться два разных маршрута: аргумент
`int → double` и результат `double → int`. Оба должны быть доступны в
контексте соответствующего Message.

<a id="post-transport"></a>
## post: один вызов, несколько доставок

Три обращения `getPixel` исполняются трижды. Если у каждого результата
три адресата `answer`, получаются три исходных ответа и девять доставок,
а не девять исполнений. Связь ответа с запросом задаёт исходный Message,
не позиция ветки и не новый числовой ID. `answer` готовят до отправки
`ask`; недоставка одного запроса не останавливает остальные.

`undelivered` получает уже сформированные аргументы исходного запроса;
объявленный отказ идёт в `catch`. Timeout считают от фактической отправки:
при пороге 500 мс обработчик может наблюдать 512 мс, но само пороговое
поле остаётся 500. Поздний ответ не удаляется автоматически. Полный
контракт и матрица T01–T26 — в [семантике](LMX_semantics.ru.md#thread-message-api)
и [почтовом плане](../next_core_tasks_v3.md).

## Таблицы и провайдеры как данные

Явная Table может дать написание `u8 → "uint8_t"` или ключ реализации
`plus[decimal][int] → decimal_int_add`. Она не объявляет типы, не создаёт
runtime-пространство имён и не ищет провайдеров автоматически. Порядок
источников, разрешение конфликтов и маркер отсутствующей ячейки задаёт
выбранный потребителем профиль, а не универсальный скрытый реестр.

## Цепочка аргументов и явная группа в выражении

Ресивер-оператор получает всю записанную цепочку аргументов. Это устройство графа, а не порядок вычисления:
невидимых скобок вокруг цепочки нет. Вычислитель выражения идёт по приоритетам: сначала явные блоки —
записанные скобки, затем присваивание, затем остальные операторы; операция меньшего приоритета выносится в
родительское выражение. Чистый граф при этом не меняется.

```text
(1 * v := 2 + 2) * (v + 1)
→ (1 * 2 + 2) * (v + 1)    # v = 2
→ (2 + 2) * (2 + 1)
→ 12
```

Явная группа меняет и результат, и переменную: `(1 + v := (2 + 2)) * (v + 1)` даёт 25, и `v` равно 4; без неё
`(1 + v := 2 + 2) * (v + 1)` даёт 15, и `v` равно 2. В записи кода `v := 2 - 3` переменная получает −1:
выносить `- 3` некуда, снаружи само присваивание, и его правой частью остаётся `2 - 3`. Норма —
[книга](LMX_semantics.ru.md#assignment-inside-expression).
