# Что требуется от ядра для обобщённых исходников

Редакция: 21 ноября 2026 года. Этот документ сопровождает ТЗ на `signatureTypes` и библиотеку ресиверов.

**Проверена предоставленная документация, а не репозиторий работающего ядра.** Поэтому ниже различаются уже заданные механизмы, недостающий документированный интерфейс к ним и проверки реализации. Формулировка «нужен интерфейс» не означает, что соответствующего внутреннего алгоритма нет в коде.

Новая форма `signatureTypes` является обычным операндом с заголовком `sys\OPERANDS_TEMPLATE`: `left` задаёт тип результата, `right` содержит типы входов. Последний элемент `right` не выделяется в результат. Типовые токены передаются ссылками на обычные типизированные записи: готовый `int` может содержать код требуемого типа, `uninit:T` даёт тип по своему тегу без чтения значения, а `void` обозначает отсутствие результата. Полные описания требований используют существующие структуры языка.

Библиотечный метод этой реализации называется `FxSignatureOperand\make` и экспортируется как обычный операнд `signatureTypes`. Именованное объявление теперь имеет только форму `Name :: Signature`; старый declaration receiver удалён. См. §2.0.

## 1. Что уже предусмотрено и не требует нового механизма языка

## 2. Четыре интерфейса, на которые опираются общие исходники

В исходниках используется явный поставщик `FxKernel`. Его имена ниже — **контракт реализации этого ТЗ**. Они не объявляются уже существующими `sys`-ресиверами. Реализовать их следует через действующие части построителя, анализатора и операций над графом, по возможности обычным L2/L3-кодом.

Количество строк в этой таблице не означает добавления четырёх фундаментальных примитивов языка. Один внутренний построитель может обслуживать несколько этих обычных функций.

| Интерфейс | Назначение | Почему он нужен |
|---|---|---|
| `FxKernel\signature(subject)` | Получить семантическое описание callable или уже созданного требования `signatureTypes` | Физические элементы DATA не равны списку аргументов |
| `FxKernel\normalizeType(token)` | Прочитать типовой токен и вернуть каноническое полное требование | Код готового `int`, тег `uninit:T` и описание `void` требуют разного чтения |
| `FxKernel\signatureData(inputs; result; labels)` | Построить обычный DATA-шаблон с нужными объявлениями и результатом | По одному массиву ссылок нельзя автоматически получить именованные типизированные объявления |
| `FxKernel\callable(contract; labels; bodyGraph; state; failures)` | Построить обычный граф владельца, DATA и CODE для нового callable | Существующий чужой CODE нельзя просто положить в контейнер и объявить его новым DATA |

### 2.0. Именованная форма `Name :: Signature`

Прежний именованный declaration receiver полностью удалён. `Name :: Signature`
объявляет тот же вид требования: name atom слева, DATA-шаблон справа.
Библиотечный операнд `signatureTypes` работает обычным структурным обнаружением метода;
зарезервированной одноимённой головы объявления больше нет и compatibility
hook ей не нужен. Квалифицированный `FxSignatureOperand\make` и короткий экспорт
создают то же требование. Не вводить вторую VM, отдельный реестр или изменение
существующего отношения именованного описания с `call`.

### 2.1. `signature(subject)`

Вход `subject` — выбранная исполняемая структура либо описание требования `signatureTypes`. Обычный DATA-шаблон не объявляется сигнатурой по наличию поля `return` или похожему имени.

Результат — обычная структура метаданных:

| Поле | Значение |
|---|---|
| `inputTypes` | `Array<@>` полных требований входов в их семантическом порядке |
| `resultType` | Ссылка на каноническое описание результата; для процедуры — существующее описание `void` |
| `hasResult` | `int`: 1, если результат предусмотрен; 0 для процедуры |
| `names` | Массив строк публичных имён соответствующих входов |
| `throws` | Массив имён объявленных исходов для выбранного callable |

Для callable анализируется его настоящий DATA. Для требования `signatureTypes` извлекается его собственная позиционная форма. Физические поля `return`, методы, константы, кодовые локалы и свободные динамические имена не превращаются в дополнительные позиции. Массив — один вход, независимо от его длины. Модификаторы и потоки объявлений обрабатывает тот же механизм, который уже устанавливает интерфейс выбранного callable.

Операция не выполняет тело, пользовательские инициализаторы, `test` или конвертеры. Если требование невозможно разрешить без ещё не выполненного пользовательского вычисления, нужна обычная диагностика недоступного описания, а не пробный вызов. Подготовленные анализом данные не становятся постоянным вторым пространством имён.

Для одного только требования `signatureTypes` нет обещания восстановить `throws` кандидата: действующий `signatureTypes` не переносит `throws`, defaults и requiredness. Если у требования нет связанного callable, массив `throws` пуст; при оборачивании выбранного callable используются его объявленные исходы. Положительное совпадение типов не доказывает поведение тела.

**Обязательная проверка:** `signature(F)` и действующая проверка `satisfies(F; Requirement)` должны видеть одинаковый порядок и одинаковые полные требования типов. Нельзя сначала извлечь физические теги через `types(parent(F))` и выдать их за этот результат.

### 2.2. `normalizeType(token)`

`token` уже является ссылкой на **саму типизированную запись токена**. Сначала читается её тег, затем выбирается допустимый способ интерпретации. Это ровно один договор ссылочного уровня: функция не ищет типовой токен произвольным разыменованием цепочки `@`.

| Запись | Как читать |
|---|---|
| Готовый `int` | Его значение — код **заданного им** типа; собственный тег `int` ещё не является ответом |
| `uninit:T` | Получить требование `T` по тегу; не читать payload, которого нет |
| `void` | Получить существующее описание отсутствия результата |
| Полное описание требования | Использовать текущие правила типов/структурных требований; сохранить сведения, которые не помещаются в одном физическом коде |

Числовые коды не фиксируются в библиотеке. Они берутся из принятого ядром профиля. Нулевой указатель, готовое число 0, отсутствие элемента массива, `uninit:T` и `void` не объявляются одним состоянием.

В подготовленном операндном применении `left` и элементы `right` указывают на записи **значений выражений**. Например, результат `sys\typeof(...)` даёт готовую `int`-запись с кодом и подходит указанному договору. Написанное выражение `@cell` само даёт ссылочное значение: подготовка может поместить это значение в запись типа `@`. Нельзя молча разыменовать его ещё раз и объявить полученную ячейку токеном — так был бы потерян собственный тип `@` и смешались бы ссылка на токен и ссылочный токен.

При явном вызове метода ссылка передаётся непосредственно по объявленному входу, например `FxSignatureOperand\make(left := Cell[0]; right := Tokens)`, если `Cell[0]` и элементы `Tokens` уже хранят именно указатели на записи токенов. Для выражения, обозначающего `uninit:T`, общий путь подготовленных операндов должен передать запись отсутствующего значения с её тегом: чтение несуществующего payload или попытка предварительно превратить её в готовое `T` запрещены. Полное ссылочное описание требования распознаётся только по явному принятому договору описаний; произвольная запись `@` не получает такого смысла сама собой.

Готовый физический код `@` сам по себе не восстанавливает требование конкретной структуры, ограничение на адресуемый тип, вложенную сигнатуру или все условия массива. Для таких случаев используется полное существующее описание требования. Нельзя молча расширять узкое требование до неограниченного `@` ради успешной генерации.

Нормализация не запускает описываемую функцию, не исполняет объявления и не регистрирует новый физический тип для каждого вызова фабрики. Отсутствующий, непонятный или неоднозначный тип даёт отказ до публикации готовой сигнатуры.

### 2.3. `signatureData(inputs; result; labels)`

Входы уже нормализованы: `inputs` — массив полных требований, `result` — полное требование либо `void`, `labels` — строковые имена соответствующих формалов. Число меток совпадает с числом входов. Для генерируемых адаптеров библиотека использует различимые имена `p0`, `p1`, …; позиционное соответствие задаётся отдельно от исходных имён целевого метода.

Функция создаёт обычный DATA-шаблон с объявленными входами в указанном порядке. При `void` поля `return` нет. При настоящем результате создаётся корректное описание `return`, включая структурный результат и требование callable-результата. Пустая возвращаемая структура остаётся настоящим результатом и не приравнивается к `void`.

Далее библиотечная фабрика `FxSignatures\make(inputs; result)` использует обычную форму:

```lmx
Built :: data
return: Built
```

Динамическое построение здесь нужно закрепить приёмочным тестом: `data` берётся из текущей активации, полученное описание имеет собственную обычную жизнь в графе, возвращённая ссылка не зависит от уже завершённого кадра. Создание требования не создаёт исполняемый метод, не запускает компиляцию и не привязывает имя `Built` как скрытый глобальный singleton.

Построение строк, интернирование имён и создание терминальных объявлений используют те же конструкторы, что P0/загрузчик. Для этого не требуется второй парсер. Запись uninit остаётся с нулевым payload; полное нетерминальное описание типа не сжимается в физический тег с потерей требований.

### 2.4. `callable(contract; labels; bodyGraph; state; failures)`

Это общий конструктор графа. Решения о каррировании, длине префикса, следующей ступени, перестановке аргументов и конце цепочки находятся в LMX-исходниках. Конструктор не содержит отдельного варианта для `lambda`, `partial`, `uncurry` или `flip`.

Он создаёт следующий обычный граф:

```text
владелец с private state
    DATA с формалами и точным return
        CODE из bodyGraph
```

Возвращается ссылка на созданный CODE. Его `parent(CODE)` — созданный DATA, а `node` тела ведёт к установленному лексическому владельцу, содержащему `private state`. Структура состояния передаётся по обычному контракту ссылок; захваченный целевой callable сохраняет собственную идентичность и своего родителя.

Общие исходники требуют от созданных формалов `required` и `private`. Это точный договор адаптеров: очередная ступень получает явно переданное значение, а служебные имена не заполняют свободные входы пользовательского кода. Defaults и скрытое автозаполнение исходного метода не должны завершать каррирование раньше заданного числа ступеней.

`bodyGraph` — граф, полученный общим парсером из сгенерированного LMX-тела либо общим построителем. Конструктор выполняет настоящее построение необходимых связей. Он не меняет parent чужого метода простым добавлением его ссылки в новый контейнер. Внутренние ссылки и имена построенного тела согласуются с новым владельцем обычными правилами построения/копирования.

`failures` задаёт объявления выходов нового тела. Вызовы в нём подчиняются штатной проверке `throws`/`catch`; сигнатура `signatureTypes` не подменяет эту проверку. Публичные имена `p0`… используются через обычное сопоставление сигнатуры с исходным callable. Не вводится альтернативный `invokeByIndex`, обходящий именованные actuals, W/E, допуск или приватность.

Конструктор ничего не исполняет и не компилирует. Нельзя переносить в новое тело машинный entry прототипа с прежним ABI после изменения типов входов или результата. До явной компиляции допустимое новое тело исполняется существующим интерпретатором. После явной компиляции его native-вариант имеет реальные типизированные параметры и исходный тип результата; он не обязан быть универсальным методом с публичным результатом `@`.

## 3. Захват значений: сначала использовать существующий протокол операндов

Постфиксный библиотечный операнд вида `(value FxRecordOperands\record)` получает подготовленный `left` и возвращает его ссылку. Справа у этого конкретного служебного операнда ничего не требуется. Это его собственный договор, а не ограничение общего массива `right` у операндов.

Левый left всегда передаётся как одно целое значение и не раскрывается. Постфиксная форма поэтому захватывает составную структуру целиком; пустой right не запускает исключение для правого контейнера. Цепочка захватов хранится в обычном графе фабрики.

Проверки существующего материального представления:

1. Примитив захватывается по полученному значению; изменение исходного локала после частичного применения не изменяет сохранённое число.
2. Ссылка захватывается с сохранением идентичности её цели. Переданная структура или массив не копируется целиком без явного запроса.
3. Возвращённая запись не является адресом уже завершённой нативной локальной переменной. Используется существующая материализация адресуемого значения в подходящую запись и обычная достижимость графа.
4. Запись ссылочного значения и запись по адресу его цели не смешиваются. Числовой результат и ссылка на числовую ячейку различимы.
5. Разыменование записи на выходе типизированной обёртки сохраняет точный `R`: `int`, вещественное число, ссылку, массив, структуру или callable. Процедурная ветка не читает несуществующий результат.

Если какой-либо из этих пунктов не выполняется, исправляется общий путь подготовки/материализации операндов. Добавлять отдельный скрытый механизм упаковки лишь для каррирования до такой проверки не требуется.

## 4. Что требуется для ранее приложенных `names` и `rename`

Эти функции не нуждаются в новой таблице имён. Таблица «адрес записи → каноническая строка» уже является частью описанного ядра. Не хватает указанного в документах интерфейса чтения и записи по адресу записи.

Нужно предоставить адаптер к существующей таблице с двумя действиями:

- прочитать наличие имени и его каноническую строку для заданной записи;
- установить имя через действующее интернирование, сохранив идентичность самой записи и обычные правила владения.

Отсутствие имени должно отличаться от допустимого пустого точного имени. Повторные имена и повторные ссылки не удаляются. `sys\name(identifier)` остаётся получением написанного идентификатора: `sys\name(ptr)` не превращается в запрос имени объекта по значению `ptr`.

Для библиотечного `rename` применяется одна общая копия исходного графа, затем изменяются выбранные имена копии. Это переименование записей, а не обещание семантически эквивалентного рефакторинга всех ссылок в исходном коде. Правка имени формала сама по себе не переписывает упоминания прежнего имени в теле.

Основание: `LMX_semantics.en.md`, `#fields`, `#string-identifier`, `#source-codec`; `kernel-implementation.en.md`, разделы о канонических именах. В `sys\descriptor` находятся адреса только `parent/length/storage`; это не универсальный дескриптор всех метаданных поля.

## 5. Границы общего вида четырёх адаптеров

Общий вид означает произвольное конечное число входов и произвольные поддерживаемые полные типы. Он не означает неявное восстановление отсутствующей информации.

| Случай | Требование |
|---|---|
| `lambda(F)` | Число ступеней берётся из семантических входов `F`; каждая принимает одно явно переданное значение соответствующего типа |
| Последняя ступень | Выполняется штатный вызов исходного `F`; наружу выходит его точный результат либо процедурный выход |
| Ноль входов | Фабрика возвращает нульарный callable; создание фабрики не запускает `F` |
| `partial(F; prefix)` | Связывает 0…N первых позиций; при N связанных позициях результат — нульарный callable, а не немедленно вычисленный `R` |
| `flip(F)` | Для N≥2 переставляются первые две позиции, остальные сохраняются; N<2 даёт объявленный отказ |
| `uncurry(C; contract; failures)` | Всегда получает конечную сигнатуру и исходы явно; число ступеней известно до вызова |
| Чужая цепочка | Промежуточные ступени имеют точный протокол `Ti -> @`, последняя — исходный `R`; более узкое промежуточное требование требует адаптера |
| Сам результат `R` — callable | `uncurry` останавливается после заданного числа входов; возвращённая функция остаётся результатом, не вызывается автоматически |
| Массивы/структуры | Один такой аргумент остаётся одной формальной позицией; его элементы не становятся дополнительными ступенями |

Для адаптеров выбран протокол явного заполнения оставшихся позиций. Это должно быть видно в основном ТЗ и исходниках. Сохранение всех способов пропуска аргументов, defaults и автозаполнения исходного метода — дополнительный контракт, который нельзя молча получить копированием инициализаторов в нового владельца. Финальный вызов сохраняет действующий DATA и обычные свободные зависимости исходного метода; фабрика не превращает весь контекст первоначального вызова в замыкание.

## 6. Общее раскрытие аргументов операндов и присваивание

Исключение действует только при одновременном выполнении трёх условий: слева написана безымянная Structure; в правой последовательности ровно один аргумент; этот аргумент сам является написанной безымянной Structure. Снимается только её внешний правый контейнер, ровно на один уровень. Левый left остаётся одной целой Structure. Вложенные правые контейнеры повторно не открываются; ссылка на структуру, значение массива и возвращённая функцией Structure сами по себе не раскрываются. P0 не снимает никаких контейнеров. Обычные callable W/E сохраняют отдельный действующий контракт. Отдельный парсер для `signatureTypes` не вводится.

Нужно проверить различие голой правой цепочки и одной написанной правой Structure: их можно свести к одинаковым right-полям лишь при написанной безымянной Structure слева и всех условиях выше. Повторное рекурсивное раскрытие не добавляется. P0 сохраняет написанные группы; выбор способа их потребления выполняется после разбора по контракту операнда. Действующие требования допуска, приоритетов, порядка вычисления и W/E не обходятся скрытой веткой только для этих примеров.

Обязательные случаи:

```lmx
(a b c) := (b c a)
(a b c) := (copy(s))
```

В обоих случаях все правые значения получаются до первой записи, а несовпадение количества мест обнаруживается до неё. Присваивание может участвовать в выражении; это не повод заменить общий массив `right` бинарным интерфейсом. Данная новая договорённость уточняет архивную редакцию о каждом контейнере как одном операнде; противоречащий ей прежний абзац следует исправить в общем разделе операндов, а не оставить рядом две нормы.

## 7. Минимальная приёмка ядра

| Проверка | Ожидаемое наблюдение |
|---|---|
| Старый `Name :: DataTemplate` | Сохраняет прежний DATA-контракт и создаёт только сигнатуру |
| Новый `signatureTypes` как операнд | `left` задаёт результат, все элементы `right` — входы; последняя позиция не изымается |
| Готовый `int`-токен | Читается код из значения, а не просто возвращается код физического `int` |
| `uninit:T` | Тип определяется без чтения payload; отсутствие value не маскируется нулём |
| `void` и пустая структура | Процедура и настоящий пустой структурный результат различаются |
| Сигнатура из трёх разных входов | Порядок и полные требования совпадают с текущим `satisfies` |
| Рефлексия computed DATA | Не вызывает пользовательский initializer ради получения метаданных |
| Переименование публичных меток | `p0`… отображаются по позициям; реальные имена целевого `F` не становятся дополнительными публичными aliases |
| Разные префиксы | `lambda(F)(a)` и `lambda(F)(b)` сохраняют независимые префиксы; общие переданные ссылки остаются общими |
| Lifetime | После завершения создавшего кадра сохранённые примитивы читаются корректно; адрес нативного stack-local не утекает |
| Тип последнего результата | Для `int`, `double`, ссылочного, структурного и callable-результата сохраняется исходный контракт; void-ветка ничего не читает |
| N=0, N=1, N>2 | Нет бинарного или int-only ограничения; фабрики не запускают тело заранее |
| Терминальный callable-результат | `uncurry` возвращает его, не делает лишнего вызова |
| Приватность | Служебные `p0`, `state`, счётчики и временные значения не подменяют свободные входы пользователя |
| Ошибки | Сохраняются объявленные `throws`; ошибка внутри проверки не считается положительным выбором кандидата |
| Native/interpreter | Проверяются оба исполнителя и переходы между ними; новая типизированная обёртка не использует несовместимый entry прототипа |
| Явная компиляция | Фабрика графа не вызывает её скрыто; машинный метод появляется по обычной явной команде |
| Полный граф | Нет второй рабочей копии программы, публикации активации в DATA или отдельного скрытого окружения |
| Два присваивания выше | Перестановка использует старые правые значения; группы остаются в исходном графе |

До этой приёмки общие исходники являются реализацией алгоритмов против явно описанного интерфейса `FxKernel`. Их наличие не является отчётом о работающем ядре. Перечень недостающего доступа остаётся коротким: четыре общих интерфейса построения/анализа и доступ к уже существующей таблице имён; массивы, копирование, вызовы, типизированные записи и парсер заново не создаются.

## 8. Согласование с приложенными исходниками

В `FxSignatureOperand` и `FxRecordOperands` после копирования общего шаблона стоит
`required: left right`: это отметка уже видимых полей, а не повторное объявление.
Она проверяет наличие инициализированных указателя и массива, не читая payload
записи, на которую указывает left. Для постфиксного record общий обработчик
предоставляет присутствующий пустой массив right. Проверка left на нулевую
ссылку в теле не заменяет required-проверку отсутствующего аргумента.


Четыре метода поставщика объявляют `FxTypeToken`/`FxKernelFailure`; библиотечные
построители дополнительно могут объявлять `FxIndex`, `FxArity`, `FxRecordArity`.
`failures` в конструкторе callable — последовательность строк с именами обычных
исходов. `signatureTypes` сам по себе не переносит throws.


Исходники используют `FxUncurry\uncurry(operation; contract; failures)` с тремя
явными аргументами и для библиотечной, и для внешней цепочки. Подготовленный
результат `signature(F)\throws` не включает автоматически исходы фабрик
промежуточных lambda-ступеней; вызывающий учитывает все выполняемые ступени.
Для совместимого промежуточного шага требуется `Ti -> @`; последняя ступень
имеет точный исходный результат. Не обещается стирание уточнённого результата
чужой цепочки до @ при сравнении signatureTypes.


Расположение результата нового signatureTypes слева — конкретное предлагаемое решение
этого ТЗ; автор потребовал общий протокол OPERANDS_TEMPLATE, а не задавал эту
раскладку ранее как существующую норму. Квалифицированный make позволяет
проверить алгоритм через обычное квалифицированное имя операнда.
