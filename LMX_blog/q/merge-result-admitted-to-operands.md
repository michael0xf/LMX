# Ссылка на другой операнд того же merge: что она именует в результате и как через неё читать

Статус: ОТВЕТ АВТОРА 2026-10-12; дефект реализации остаётся открыт. Вопрос задал `fable_pc` при срезе R6-2 (4) тикета
[critical_general_receiver_routes_bug](../../steps/tickets/critical_general_receiver_routes_bug.md) по
дефекту ядра [MERGE-REFERENCE-TO-OPERAND](../../steps/defects.md#merge-reference-to-operand); передан автору
через Codex почтальоном `lmx_uds` (STATUS FABLE-STATUS-20261011-27).

## Контекст

`Holder: p: Model`, затем `R: merge: Model Holder` и чтение `R\p\v`. На `2a711a13` чтение падает нативно
(«a field of an admitted reference is not carried by its value (no record, or a hole)») и даёт INVALID при обходе;
`R: merge: Holder` без Model читает 11. Книга ([L2 §13](../../docs/L2_spec_ru.md#copy-merge),
[семантика, #composition](../../docs/LMX_semantics.ru.md#composition)): одна карта «источник → копия» на все
операнды, ссылки и `parent` переписываются на соответствующие копии; корни
операндов не становятся дополнительными видимыми полями результата. Чтение
этого как обязательного физического поглощения всех копий корней было
предположением вопроса, а не текстом книги.

Механизм (прочитан в ядре, подтверждён пробным ядром): проход `lmx_copy_absorb` переписывает на результат
слоты и `parent` скопированных Structure, указывающие на скопированный корень-операнд, но не pointee
ячейки-ссылки — скопированная p именует отброшенную промежуточную копию Model без записи соответствия. С
добавленным проходом по ячейкам-ссылкам p именует результат, но чтение `R\p\v` всё равно неверно: требование,
с которым читается поле через допущенную ссылку, транслятор берёт из скопированного лексического контекста
(слот Model в копии родителя) — это сам результат, занявший место модели и более широкий, чем Model; ребро
«последней половины» `slot + width(Model)` попадает в другой слот. У результата сегодня только запись
тождества с собой (`lmx_merge_result_layout`); записей «результат допущен к Model / к Holder» нет.

## Ответ автора 2026-10-12

Никакого отдельного правила «результат допущен к каждому операнду» для этого
случая не требуется. `merge` копирует **всю используемую память/граф**, в том
числе ссылочные цели, через одну карту копий. Из лексических предков
оставляются лишь используемые; неиспользуемые отсекаются. Здесь `p`
использует `Model`, поэтому копия `Model` не может быть выброшена как
промежуточный корень: `p` в результате должна указывать на эту копию, а не
на исходную арену и не автоматически на свежий корень `R`. Корень `R`
составляет свои непосредственные поля по обычным правилам `merge`; копия
операнда, достижимая только через `p`, не является лишним видимым полем `R`.
Физическое поглощение всех корней операндов и перенаправление каждой ссылки
на `R` было предположением реализации, не правилом языка. Из него ошибочно
получилась потребность в дополнительных записях `R ↔ Model/Holder`.

Следствие для реализации: исправлять надо общий copier/absorb так, чтобы
выбранная используемая копия операнда сохранялась и типизированное чтение
`p\v` обращалось к ней по модели `p`; не строить специально для этого
допуск результата к каждому операнду. Положительный и различающий alias
свидетели нужны до закрытия дефекта.

## Исходный вопрос (история)

1. Что именует скопированная ссылка на со-операнд в результате: результат (по §13 — соответствующую копию),
   исходный операнд (разделение по адресу — исключение §13 только для вечных ветвей) или такое написание
   отказывается?
2. Если результат: допущен ли результат к модели каждого поглощённого операнда по позициям композиции
   (запись соответствия результат ↔ операнд: тождество для модели, смещения для дописанных операндов), так что
   типизированное чтение через такую ссылку идёт по записи объявленной модели, а не по экземпляру из
   скопированного контекста?

## Прежний план, который ответ отменил

Заготовка `edit_kernel_absorb.py` в `build/fable_handoff_20261011/kernel/`
перенаправляла ссылку на корень результата, после чего требовались особые
записи соответствия результата каждому операнду. Это не выбранное решение:
проба даже превращала падение в молчаливое неверное чтение. До общего
исправления транслятор по-прежнему отказывает по месту `merge` для
статической формы (`unit_merge_ref_cooperand_refused`); обязательный
положительный native/walked свидетель остаётся открытым.
