Маршрут331 уточняю конкретно:
1. Продолжай общий построитель указательного формала и сохранение include/predef в чистом графе. Это зависимость обоих вариантов. Не делай особой обёртки формала/внешней таблицы ролей: типы/имена/состав должны читаться из графа и обычных участков. Требования include/predef и выбранные импорты не объявлять молча отсутствующими: инертность объявления в корне не равна игнорированию зависимости.
2. Адаптируй существующий машинный frontend/lowering к общему Lmx-входу, переиспользуя текущий export/ABI/backend-контракт и общие разбор выражений/имена/проверки. Не копируй весь машинный язык в независимый emitter/resolver. Общий построитель чистого графа должен использоваться и этим frontend, и graph_trans, не отдельное построение для каждого. Название исполняемого файла само по себе не контракт: временная точка входа через graph_trans допустима только как вызов того же переносимого frontend/экспортного режима, а не ещё один авторитетный compiler. Не требуется менять весь F одним коммитом; переноси одну нужную операцию/модуль, сохраняя единственный рецепт. Не делай обратный адаптер Lmx -> P0/обязательное скрытое AST ради старого lowering. P0 живёт только в построении; служебные таблицы lowering принадлежат текущему обходу.
3. Для lmx_schedule сохрани --machine имена/ABI, generated header и реальные машинные записи; произведи L1/C общим путём, скомпилируй, свяжи и исполни runtime с именно этим новым объектом по существующему recipe. Сравнение с F полезно для ABI/диффа, но F не нормативный оракул: нужны реальные значения init/wait/tick/state по исходнику/контракту. Буквенное равенство L1/C не обязательно. После успешной замены перенесённый модуль не откатывается к F автоматически при ошибке. F остаётся только явным seed/неперенесённой частью перехода; не объявлять этим полную closure/G1/G2.
