## 1. Результат и порядок

Требуются два независимых результата:

1. **Граф не теряет исходную программу.** Состав, вложенность и порядок исходных конструкций сохраняются после разрешённой материализации ресиверов. Нативное понижение не заменяет этот граф обеднённой схемой исполнения. Проверка восстанавливает структуру непосредственно из графа и предусмотренных нормой таблицы имён/хранилища комментариев. Если их реальная реализация отсутствует, её требуется выполнить в G1/G4, а не считать готовой по наличию нормы.
2. **Адресуется место хранения, а не уже прочитанное значение.** Для Structure обычное чтение `A` даёт хранимую ссылку; `@A` даёт адрес реальной ячейки этой ссылки, то есть ещё один уровень косвенности. Это же правило действует для Array, ссылочных элементов, формалов и остальных адресуемых значений.

Очередь остаётся последовательной:

```text
G0: исходный срез и исправные свидетели
 -> G1: независимый структурный оракул
 -> G2: один рекурсивный алгоритм построения
 -> G3: выражения, применения и все потребители layout
 -> G4: copy/merge, имена, комментарии и контрольные поломки
 -> G5: полный графовый checkpoint
 -> P0: воспроизведение и инвентаризация реальных ячеек
 -> P1: общее разрешение value/place/depth
 -> P2: native + walker + actuals/returns/admission
 -> P3: указательные свидетели и графовая регрессия
 -> P4: полный указательный checkpoint
 -> structure_reference_application_refactor, отдельный следующий тикет
```

Не смешивать эти три работы. Последующий рефакторинг `b: A`, `@: b A`, обычного вызова через удерживаемую ссылку и явного переприсваивания уже запланирован отдельно. Ремонт графа не должен заранее реализовывать его; ремонт `@A` не должен ждать его реализации.

Никакого нового номинального `Type`, постоянного `data/context`-подграфа, обёртки каждой примитивной ячейки, `LmxUseLeaf`, runtime-реестра разрешённых имён или второго постоянного AST. Временные таблицы компилятора и состояние машинной активации допустимы в своей обычной роли, но не становятся частью пользовательского графа.

## 4. Графовый ремонт

### G0. Зафиксировать срез и привести свидетели в рабочее состояние

1. Проверить ownership и отсутствие второго writer/build. Записать HEAD, tracked/untracked пути WIP, хеши исходников, активные процессы сборки и фактическую команду gate. Не делать checkout/restore/reset/stash/clean/revert.
2. Сохранить старые каталоги результатов. Любой новый прогон — новый абсолютный `OutDir`. `regress_ns_182` не переиспользовать; предложенный `regress_ns_183` использовать только если он действительно свободен.
3. Повторить `unit_body_path_while_pt` и `unit_body_path_until_pt` вместе в отдельном focused gate. Это подтверждает конкретные свидетели, но не универсальность алгоритма.
4. Исправить постановку `unit_body_path_merge_pt`, не семантику merge. В его исходнике `answer` начинается с 64; запись 7 находится только в `catch: merge`. Успешный `Q: merge: P` не входит в обработчик, поэтому 64 сам по себе не доказывает дефект графа.
5. Переиспользовать уже существующий harness-механизм `MergeFail=1`, как у `unit_s1_catch_merge_local` (`tools/l2_harness.ps1`, ~2127). У новой строки (~3198) он сейчас отсутствует. Добавить контроль фактического входа в catch и проверку `Point` внутри сработавшего обработчика. Рядом оставить успешный merge и существующий отказной свидетель.
6. Разобрать 36 старых полных отказов по идентичности: нормативное несоответствие; устаревшая проверка generated layout/диагностики; независимый дефект. Не удалять строки и не менять ожидания только ради зелёного цвета. Для каждого изменения ожидания нужна ссылка на действующее правило и проверка реального поведения.

**Выход G0:** воспроизводимые focused результаты, список точных full-gate отказов и ясное отделение плохого теста от плохого алгоритма. Не новая серия локальных патчей для каждого имени control-body.

### G1. Сделать независимую проверку сохранённой структуры

Нынешние `shape_*` полезны как заготовки, но не являются достаточным доказательством `toLmx`-контракта. Проверяющий код не должен повторять отбор узлов, сделанный транслятором.

1. Получить ожидаемую каноническую структуру из P0 и действующих правил материализации ресиверов. Это временный тестовый оракул, не новый постоянный граф исполнения.
2. Декодировать фактический retained graph через общие сведения его ячеек/диапазонов и существующие средства имён/комментариев. Не читать `l2_rwN`, C/L1-текст генератора, сохранённую строку исходника или отдельную копию P0 вместо графа.
3. Сравнивать **весь** упорядоченный состав каждого контейнера: число исходных вхождений, их роли, вложенность, тела, операнды, литералы и привязку комментариев. Лишний узел — такое же расхождение, как отсутствующий. Поиск следующего подходящего узла с пропуском остальных запрещён как oracle.
4. Убрать `[4]`-стек и предел 16 объектов. Использовать обычный растущий тестовый обход; различать исходное вложение и ссылочные связи. Для sharing/cycles достаточно общего учёта посещений, не особых правил для отдельных форм.
5. Нормализовать только действительно эквивалентные формы P0 и разрешённую материализацию. Типизированная ячейка `int: i 5` не нуждается в leaf. Это не разрешает стереть отдельное `i: 6`, переместить ячейку `j` перед ним или заменить `(2 + 2)` пустотой.
6. Сравнение конструкций и их порядка сначала проводить на построенном графе до исполнения; последующие проверки отдельно наблюдают действительные значения и сохранность конструкций после исполнения. Не вводить историю прежних значений либо теневое хранилище для доказательства сохранности структуры. Если `toLmx`-свидетель после изменения ячейки обнаружит неясность контракта восстановления исходного литерала, предъявить конкретный пример: этот план не разрешает молча ослабить нормативный контракт `toLmx` или сохранить второй AST.
7. Найти фактическую реализацию таблицы имён, хранения комментариев и `toLmx`. Если готового codec нет, выделить необходимую реализацию в явную подзадачу G1/G4. Одной нормы в документах или compile-time массива имён недостаточно. Не изобретать новый runtime словарь разрешения имён.

**Выход G1:** проверка ловит лишние/потерянные/переставленные узлы, работает глубже четырёх уровней и различает больше 16 объектов; её входом служит именно сохранённый граф. Возможности и пробелы name/comment codec указаны честно.

### G2. Один алгоритм рекурсивного построения вместо двух layout

1. Инвентаризировать constructors для unit/root, обычной именованной Structure, метода и его сигнатуры, локальной именованной Structure, анонимного/control-тела, аргументного тела, возвращённого/merged occurrence, native-only тела.
2. Факторизовать проход по исходным детям в их порядке. Для каждого исходного вхождения общий resolution определяет действие и место; ресивер определяет создаваемую ячейку/контейнер; общий проход сохраняет вложенность и очередность.
3. Переиспользовать существующую связь P0-узла с местом как временную информацию компилятора. Не заводить постоянный metadata-record для каждого уже типизированного атома.
4. Если требуется отдельный проход подсчёта и проход заполнения, оба используют одну структурную процедуру. Из её результата получить размеры, позиции полей, вложенных тел, source applications и scratch для merge. Не считать `if`, `while`, `for`, `catch` отдельными копиями структурного алгоритма.
5. Семантические обработчики операторов могут различаться: универсальность вложения не означает одинаковую семантику `if` и `merge`. Нельзя лишь повторно распознавать синтаксис и вводить локальные правила размещения.
6. Перевести callers `l2_m_kids`, `l2_m_width`, `l2_ns_width`, `l2_layout_owns`, `l2_method_field_slot`, `l2_merge_scan` и генерацию published paths на общий результат. Размер и адрес поля должны описывать один и тот же контейнер.
7. Заменить selective `l2_src_eligible` и `l2_m_src_end=-1` fallback. Не просто снять guard до миграции его потребителей: иначе старые индексы станут адресовать новые места.
8. Сохранение графа не обусловливать `l2_rw_may`, native-режимом, наличием side effect, возвратом или возможностью выполнить L2-операцию интерпретатором. Нативный optimizer вправе удалять ненужный машинный код, но не исходное вхождение в retained graph.

**Выход G2:** все перечисленные области используют один source-order layout. Нет незаметного «не подходит — собираем старым способом». Сохранены исходные узлы после `return` и в недостигнутых ветвях.

**Ближайшая связанная граница G2, после проверки первого общего filler.**
`l2_source_inert_container` уже обходит несколько выражений и вложенных
контейнеров, но вызов только из верхнего source-placement не сохраняет такой
контейнер внутри `l2_rw_body`. Безусловное создание нового тела там дублирует
уже созданный `l2_b`; безусловное использование старого `l2_b` оставляет старое
ребро/родителя либо обращается к объекту, который старый layout вообще удалил.
Нужен один владелец построения, а не fallback по ненулевому адресу:

1. Использовать общую временную связь source-container → actual GraphPlace,
   различая P0 Structure и конкретное occurrence/view её построения. По
   возможности расширить уже существующую связь, не заводить второй её индекс
   с теми же сведениями. Вложенное тело `for`/`catch` не отождествлять с Frame,
   который задаёт его лексическую область. Все вызовы `l2_rw_body` должны
   передавать исходную Structure, а не только её `first_field`.
2. Отдельно определить действительно строящиеся occurrence. Пробный проход,
   проверяющий возможность интерпретации, не приобретает ownership. Затем
   выполнить единый committed PLACE-проход по тем же исходным контейнерам;
   COUNT/PLACE/FILL используют одни границы полей и expression spans.
   Текущий `l2_rw_emit=0` не является готовым PLACE: `l2_rw_pads` не создаёт
   PAD, а `l2_rw_catch_stmt` проверяет тело с условным parent/slot вместо
   реального PAD и `1 + np`. В committed проходе common constructors и
   attachment API должны зафиксировать настоящую topology, не выводя код.
   Временная связь constructor temp → его parent/child записывается при
   конструировании и `l2_rw_put`, в том числе когда финальное присоединение
   операции идёт после её вложенных операндов. Не угадывать корень операции
   по `l2_rw_t - 1`; borrowed operand не становится новым owning edge.
3. До вывода builder выбрать ровно один producer каждого объекта. Верхний
   уже размещённый контейнер не становится вторым исполняемым шагом. Дочерний
   контейнер реального `rw_body` занимает свой исходный слот; old global
   producer больше его не выделяет и не присоединяет. Проекции не используют
   объект model occurrence только потому, что совпал исходный P0 pointer.
4. Удалить переданные producer'у деревья из старых списков, пересчитать
   оставшиеся ширины/индексы и заново получить финальные GraphPlace/GraphField,
   schema и merge-размеры. Не запускать старый `l2_layout_owns` после этого:
   он восстановит удалённые старые рёбра. Не оставлять висячих sibling paths.
   `l2_m_for_count`/`l2_for_rank` также исключают переданные producer'у
   верхние деревья: одно изменение `uchild` не исключает их старую ширину.
5. Единственный producer выделяет контейнер, назначает его реальный parent,
   открывает уже вычисленную ширину и записывает одно ребро. FILL только
   заполняет его. Никакого «если объекта нет, попробуем другой layout».
6. Свидетель: несколько вложенных чистых выражений внутри исполняемого тела,
   вместе с соседним объявлением и чтением его опубликованного значения.
   Сверить число объектов/рёбер, родителей, порядок и поля, затем стереть
   выражение без изменения exit. Покрыть и прежний retained shell, и dropped

### G3. Полные выражения, применения и согласованные потребители

1. Сохранить операторы и операнды одиночных атомов, арифметики, строк, пустых/непустых анонимных тел, discarded результатов и применений. `(2 + 2)` остаётся выражением, а не контейнером-заглушкой.
2. Различать материализованную примитивную ячейку и исходный лист тела. Запрет лишнего leaf для `int: i 5` не отменяет исходный атом `b` в определении неизвестного `A: b`.
3. Разрешение определения/применения/присваивания брать из общей семантики, а не из наличия скобок, `return`, `end:`, места в unit или текущего backend. Обычная именованная Structure не получает формальных аргументов от слова «callable»; fn/fm/sub сохраняют свои сигнатуры.
4. Применение сохраняет исходную структуру аргументов по общему правилу прозрачного контейнера. Не вводить исключение для единственного структурного аргумента и не конструировать дополнительный постоянный `data`-подграф.
5. Согласовать representation применения с `lmx_walk_call`, dispatch и kernel/selftest producers. Удалить старую/новую shape-эвристику после миграции всех источников. Машинный CALL-протокол не должен становиться подменой восстанавливаемого исходного тела.
6. Перевести пути/occurrence-выбор и интерфейсный `implements` на новые места. Проверка ожидаемого интерфейса и адресация его полей не являются анализом алгоритмической эквивалентности кандидата. Имена для интерфейсного сопоставления не оправдывают name strings внутри графа.
7. Проверить прямые и внешние пути к полям вложенных тел, включая несколько шагов пути. Не считать зелёный `while\pt\x` доказательством для `test\while\pt\x`.
8. `if/while/for/until` не получают новой method activation. Не переопределять `node` как parent любого control-body. Вызов отдельно именованной Structure и inline-исполнение анонимного тела следуют уже установленным разным правилам.

**Выход G3:** одна сохранённая программа служит для source reconstruction, полевых путей и предусмотренного исполнения; ни один потребитель не требует прежних искусственных prefix/suffix позиций.

### G4. Copy/merge, имена, комментарии и сильные свидетели

1. Проверить copy/merge на исходном порядке, примитивных ячейках, исходных листьях, кодовых телах, повторных вхождениях, sharing/cycles, родительских связях и reusable native references. Сохранить существующие контракты состава merge; не менять алгоритм композиции ради layout.
2. Согласовать установленную name table с реальными адресами копий/результата. Не восстанавливать имена из `char*`-полей графа. Строковый литерал остаётся строковым значением; текст имени — не строковый литерал.
3. Сохранить полные комментарии и их структурные места вне горячего пути value-access/dispatch. Восстановленный исходник допускает только каноническое форматирование и установленные эквивалентности грамматики, а не комментарий-сводку или распечатку внутреннего CALL.
4. Выполнить контрольные поломки: удалить чистое выражение; переместить объявление через оператор; схлопнуть разные source occurrences; заменить непустое тело пустым; вставить лишний узел. Каждая ломает структурную проверку независимо от совпадения exit code.
5. Добавить смешанный свидетель из требования автора:

   ```text
   ( f: 1
   . f: 2
   . 2 * 2
   . f
   )
   ```

   Точки — действующая каноническая запись уровня. Проверить её и эквивалентную свободную отступную форму, не заменять правило новым соглашением. Проверить оба вхождения `f`, выражение и последнее употребление. Ожидаемое исполнение/диагностику установить по действующему resolution, не обещать этому исходнику успешное выполнение вопреки разрешённой роли `f`. Структурная сохранность проверяется отдельно от валидности достигнутого вызова. В положительном runtime-варианте результат помещается в уже существующее место последнего вычисленного значения активации/выражения, не в новый graph slot.
6. Для эквивалентных закрытых `f()`, `f: ()`, вертикальной закрытой формы проверить одинаковый P0-результат; для голого `f` — утверждённую прозрачность при потреблении. Не переоткрывать запрещённое висячее `f:`.
7. Для native/walker брать интерпретируемые L3-свидетели и доказать фактический dispatch каждого исследуемого вызова. Простое обнуление native у root не доказывает, что вложенный метод перестал исполняться нативно.

**Выход G4:** decoder/mutants, effect-tests, copy/merge и name/comment reconstruction проверены совместно. Успехи execution не маскируют потери структуры.

Фактический пробел codec: внешняя runtime-таблица address → source name уже
реализована; её существующие ownership, copy-remap и GC-механизмы следует
использовать, а не создавать вторую таблицу имён. Полный graph-side
`toLmx`/`fromLmx` и удержание комментариев ещё отсутствуют. Имена в P0 и
диагностические комментарии генератора не заменяют этот контракт. P0
уничтожается после `l2_emit_unit`, а парсер пропускает inline/raw comments.
Не требуется менять
их грамматику, но полное содержимое комментариев необходимо независимо
сохранить при построении и связать с actual source places до уничтожения
документа. Данные имён/комментариев копируются или удерживаются по обычному
ownership; адресные ключи ремапятся существующей copy-связью. Исполнение
не начинает резолвить имена через эту таблицу. Проверка roundtrip должна
работать после освобождения исходного P0 и source arena.

### G5. Выпуск графового checkpoint

Убрать superseded constructors/fallbacks и устаревшие assertions, затем выполнить полный последовательный gate. Каждая новая красная строка сначала воспроизводится focused, а затем исправляется по норме.

36 прежних отказов не удалять оптом. Старый generated-text pin можно мигрировать только после установления ожидаемого поведения и source-order проверки. Настоящий дефект не превращается в «старую базу» или разрешённый fallback.

Графовый тикет не объявлять DONE по focused green либо по старым kernel/L3 результатам. Для выпуска нужны структурная acceptance и свежие зелёные полные gates; те же 36 старых отказов не дают этого результата. Если полный gate реально требует ещё не разрешённого изменения другого этапа и получается цикл зависимостей, зарегистрировать точную зависимость/свидетель и вынести конфликт порядка на решение; не начинать указательный этап тайком и не называть красный gate зелёным.

После acceptance синхронизировать перечисленные изменённые исходники sandbox/stable и необходимые fixtures, проверить соответствие байтов, закоммитить и push. Только тогда внести `DONE <sha> <UTC>` в тикет и закрыть соответствующие строки плана. Историю красных прогонов не стирать.

## 5. Ремонт указателя на Structure

### P0. Воспроизведение после графового выпуска

1. Взять именно выпущенный graph checkpoint и его хеши. До него pointer work ограничивается чтением и планом.
2. Создать один минимальный native/walker свидетель, различающий хранимую ссылку и адрес её ячейки: сравнение идентичности места, чтение через него и допустимая запись с наблюдаемым результатом. Сравнения одних generated строк недостаточно.
3. Выписать физические места для root/named/local Structure, own field, formal, hidden input, вложенного пути, Array descriptor и reference-valued элемента. Для каждого записать C-тип ячейки, тип прочитанного значения, lifetime и операцию получения адреса.
4. Включить `lmx_walk_place`, `lmx_walk_value_load/store`, ADDRESS и `lmx_walk_arg_place`, а не ограничиваться четырьмя translator functions из первоначального тикета.

**Выход P0:** доказан конкретный collapse уровня и составлена карта настоящих хранилищ. Никаких дополнительных holders для уже существующего graph slot.

### P1. Общий resolved place, value и глубина

Минимальная модель компилятора/активации:

```text
resolve place -> место существующей ячейки + её фактический тип
read(place)   -> хранимое значение
address(place)-> ссылка на саму ячейку; ровно +1 уровень
store(place)  -> допуск/разрешённое преобразование, затем запись в эту ячейку
```

Это описание операций, не новый постоянный runtime object и не новое поле Lmx.

1. Свести `l2_address_name`, `l2_emit_address`, `l2_own_addr`, `l2_rw_address` к этой общей информации. Descriptor/callable статус не отменяет address-of.
2. Развести value emission и place emission. `lmx_arena_ref_struct(...)` читает ссылку; он не является реализацией `@A`. Для графового reference place адрес уже даёт `lmx_arena_ref_cell(...)`.
3. Любая оптимизированная рабочая ячейка/кэш должна сохранять установленное соответствие с реальным адресуемым местом. Нельзя адресовать временный cache вместо языкового места либо вернуть pointee, чтобы избежать согласования working state.
4. Повторное взятие адреса одного места в пределах его lifetime стабильно. Разные активации имеют разные собственные formal cells. Не возвращать адрес входящего ABI-box либо адрес прежней активации.
5. Переиспользовать существующий activation-owned путь `lmx_walk_arg_place`/`argown`, где он уже даёт стабильную ячейку формала. Проверить его для всех соответствующих классов значения; не создавать постоянный companion graph для formals.
6. Проверить согласование с arena range classification: `LMX_KIND_CHILDREN` описывает backing ссылочных ячеек, а классификация удерживаемого значения описывает его referent. Это разные запросы. Получение адреса места не должно классифицировать pointee вместо storage либо создавать отдельный физический тип для каждой именованной Structure.

**C99-обязательство:** conceptual `Lmx **` описывает два языковых уровня, но доступ обязан соответствовать реальному C-хранилищу. Graph children сейчас лежат в `void *`-ячейках, их адрес — `void **`. Простое приведение `void **` к `Lmx **` и разыменование не доказывает aliasing correctness. Генератор должен читать/писать действительную ячейку через её действительный C-тип и преобразовывать прочитанное значение согласно общему контракту. Для genuinely typed `Lmx *`-ячейки её адрес действительно `Lmx **`. Не отключать strict aliasing и не подкладывать отдельную синхронизируемую копию ссылки. Если raw-C потребление выявит несовместимые требования к типу одной и той же ячейки, предъявить точный C/L2-свидетель до выбора представления.

**Выход P1:** один алгоритм address-of без descriptor exemption, с проверенным effective C type и без потери уровня.

### P2. Согласовать оба исполнения и передачу значений

1. В walker `place.address` должен обозначать storage. Обычное чтение Structure/Array отдельно загружает удерживаемую ссылку; ADDRESS возвращает место, а не результат такого чтения.
2. Пересмотреть flag `descriptor` в `LmxWalkPlace` и его callers: он сейчас смешивает representation значения и отсутствие storage. Сохранить только необходимое различение фактических видов хранения; не вводить новый special case «Structure адресу не подлежит».
3. Реализовать read/store через реальный reference cell в соответствии с admission. Запись меняет выбранную ссылку, не старый descriptor, его parent/native и не независимых держателей той же ссылки.
4. Провести глубину через actuals, formals, returns, primitive conversions и implements. Сигнатура не исполняется, но actual `@A` — исполняемая операция и её уровень нельзя стереть. `test(A)` и `test(@A)` не общие синонимы.
5. Примитивная таблица преобразований и consumer-relative implements остаются разными механизмами. Не строить конверсионную таблицу для каждой отдельной Structure и не анализировать её алгоритмическое поведение.
6. Null в существующей ссылочной ячейке не означает отсутствия объявления/поля. При этом pointer fix не определяет новые правила инициализации или lifetime extension.
7. Поддержать дальнейшие уровни общим алгоритмом, не ветками для `@`, `@@` и предельного количества `@`. Снять старые комментарии/ожидания о descriptor-forwarding вместо address-of.

**Выход P2:** native и walker адресуют одинаковое языковое место, actuals/returns/admission сохраняют глубину и существующие сроки жизни.

### P3. Минимальная достаточная матрица тестов

| Класс | Обязательное наблюдение |
| --- | --- |
| Primitive cell | `@x` адресует данные существующей ячейки; primitive rules не изменились |
| Root и method-local Structure | чтение ссылки отличается от адреса её места; повторное адресование стабильно |
| Own/formal/hidden input | принадлежность ячейки правильной активации; рекурсия/re-entry не используют старое место |
| Path и repeated occurrence | адрес выбранного конкретного вхождения, включая явный индекс; другая ячейка не меняется |
| Array reference | адрес ячейки descriptor reference, не сам descriptor |
| Primitive Array element | адрес действительного элемента в backing data |
| Reference Array element | адрес ссылочной ячейки, а не её pointee |
| Actual/return | exact depth проходит, несовместимая глубина отвергается без implicit dereference |
| Admitted store | меняется selected holder; прежний descriptor/header/native и другие holders не изменяются |
| Null value | существующая ячейка остаётся существующей; отсутствие target не стирает поле |

Прогнать representative witnesses нативно и через реально измеренный walker dispatch. Не строить бессмысленный полный декартов продукт всех форм, но каждую независимую ветвь хранения/потребления покрыть. Добавить мутант, возвращающий descriptor вместо ячейки: его обязан поймать положительный тест. Затем повторить decoder и графовые mutants из G1/G4.

Array-инварианты обоих ремонтов:

- универсальный `VoidArray` остаётся `{size_t size; void *data}`; типизированные массивы сохраняют действительный тип data и установленный spelling длины своего ABI, без shape/rank и runtime-массива длин;
- элементы могут быть ссылками на другие Array; это обычное содержимое Array и композиция receiver-ов, не специальный двухуровневый тип;
- `[]: []: ...` — общая цепочка receiver-ов без фиксированного ограничения глубины; отдельная C-подобная форма ровного массива не смешивается с ней;
- каждый шаг `\[i]` адресует выбранный текущий контейнер/элемент по действующему path-контракту; не выводить происхождение размерностей из длины;
- `length` читает descriptor того массива, к которому применён, и не зависит от вложенности содержимого;
- в L2 индексы не получают bounds checks; L3 использует descriptor и проверяет вычисленное конечное смещение для ровного массива по принятому правилу, без новых per-dimension длин/проверок;
- адресование reference-valued элемента использует его фактическую C99-ячейку. Не добавлять nested-Array исключение к address-of.

**Выход P3:** оба уровня ссылки наблюдаемы, все существенные места покрыты, графовый контракт не регрессировал.

### P4. Выпуск указательного checkpoint

Повторить полные последовательные gates на окончательных байтах; удалить superseded address routes и устаревшие нормы/tests, но не независимые возможности языка. Синхронизировать stable twins только на проверенном срезе. Закоммитить/push точные пути, зафиксировать `DONE` и очередь.

После этого разрешён следующий отдельный `structure_reference_application_refactor`, а не самосборка в обход остального clean-kernel списка. Полная L3/L2 self-build остаётся дальнейшей целью плана, не доказательством, которое автоматически следует из этих двух ремонтов.

## 7. Границы выполнения и критерии остановки

- Этот документ разрешает продолжение через bounded steps после отдельного начала кодовой работы; сам он не утверждает владение WIP и не запускает реализацию.
- Проблема фикстуры, старая диагностическая строка или несовпадение generated temp не являются вопросом автору сами по себе. Исполнитель сначала сверяет норму и реальное наблюдение.
- Настоящее противоречие представления/языковой нормы: минимальный исходник, ожидаемое и наблюдаемое, exact files/symbols; вопрос Codex, и только неразрешимое по документам решение — автору по-русски. Не выбирать удобное исключение.
- Parser не менять для компенсации layout/emitter ошибки. Один уровень отступа закрывается автоматически; trailer закрывает требуемую вложенность в разрешённой позиции; внутренний `return` не превращается в trailer метода.
- Имена сущностей отсутствуют в графе вообще, не только возле primitive atoms. Отдельная таблица поддерживает reconstruction, не скрытое runtime-разрешение значений по строкам.
- Материализация типизированной ячейки разрешена; исчезновение исходного применения, анонимного выражения или комментария — нет.
- Не считать delivery ACK, ownership marker, старый green gate, exit 0 без assertions или частичный focused green завершением тикета.
- Один writer/build, никакой второй сессии, никакой разработки приложения/myxa_manager в рамках этих двух ремонтов.
- Коммитить только явно перечисленные проверенные пути. Не включать marker/tmp/log/bin, чужой WIP или код в документный коммит; не использовать `git add -A`.

Итоговый принцип реализации: **сначала один честный retained graph, затем одна честная операция над его реальным storage place**. Не расширение очередной особой ветви и не дополнительное постоянное описание того, что уже известно из адреса, диапазона и типа.
