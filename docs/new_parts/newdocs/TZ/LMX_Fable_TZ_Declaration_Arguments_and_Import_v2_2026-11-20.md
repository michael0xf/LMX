# ТЗ для Fable, версия 2: ресиверы объявления в аргументах и import корневых const-объявлений

Дата: 20 ноября 2026 года. Основание: последние решения автора и уточнения в текущем обсуждении.

Уточнение версии 2: `import` добавляет в namespace только const-объявления, которые при вызовах считаются корневыми в data. Объявление пользовательской структуры константно и без явного `const`, поскольку структура не является переменной. Правила передачи ресиверов объявления аргументами сохраняются. Дополнительно согласованы именованные сигнатуры `fn: name data`: `fn` сохраняется, а импорт созданного им константного имени подчиняется тому же правилу.

## 2. Термины и окончательные решения

**Ресивер объявления места** — форма вроде `int: item expression` или `@: ptr …`, читаемая по объявляющему контракту соответствующего ресивера. Именно такие формы рассматривает первое изменение.

**Структурная форма с обычной вызываемой головой, не являющейся ресивером объявления места**, например `Producer: tail` или `Producer(...)`, сохраняет обычное чтение по роли. В DATA она может объявлять Structure; в CODE это вызов её головы. Первое изменение не превращает такую форму в неисполняемое объявление только потому, что в другой роли она объявляла бы Structure. Синтаксическая форма сама по себе не различает случаи: `int(item expression)` тоже является Frame, но его голова читается по объявляющему контракту ресивера.

DATA и CODE здесь — обозначения семантической роли, не новые ключевые слова.

Приняты следующие решения автора:

- Ресиверы объявления места, передаваемые аргументами в контексте CODE, читаются как DATA.
- При нахождении соответствующего объявления в data принимаемого вызова в namespace заменяется само объявление, а не присваивается его вычисленное значение.
- В подтверждённом примере `iteration` получает ссылку на форму `int: item numbers\next()`. Корневое объявление этой формы действует как дополнение корневого уровня выполняемого code.
- Каждый достигнутый `iteration()` заново исполняет сохранённую форму. `item` появляется при первом достигнутом обращении/исполнении по общему механизму и обновляется при следующих исполнениях как повторное корневое объявление.
- Счётчик позиций сохраняет прежнее правило: именованная подача на позиции своего имени считается позиционной; именованная подача вне этой позиции отключает счётчик, и дальше допустимы только именованные подачи.
- `import` добавляет в namespace только const-объявления, которые при вызовах считаются корневыми в data. Объявления пользовательских структур константны без явного `const`. Повтор импортируемого имени имеет поведение обычного повторного объявления.

Пояснение автора о DATA-аргументах внутренних ресиверов относится к устройству ядра. Из него не следует дополнительный глобальный чейндж для всех DATA-аргументов, новая группа ресиверов или изменение всех вызовов языка. Ранее прозвучавшее в этом пояснении слово CODE исправлено автором на DATA; само пояснение не является отдельным поручением.

## 3. Изменение 1: передача ресивера объявления

### 3.1. Основная норма

Добавить в раздел передачи actuals следующую норму, согласовав терминологию с документом:

> Ресивер объявления места, переданный как аргумент в контексте CODE, читается как DATA: принимающая сторона получает само записанное объявление. Одна передача этой формы не исполняет её initializer. Если соответствующее объявление найдено в data принимаемого вызова, переданная форма заменяет найденное объявление в namespace данного вызова. Подстановка вычисленного значения вместо объявления не является этой операцией.

Сохраняются общий разбор, выбор сигнатуры, приём аргументов и действующие проверки совместимости. Для этого механизма не вводится отдельный парсер или проверка по конкретным словам `iterate`, `iteration`, `body`, `item`, `int`.

Нужно различать:

- сохранённую форму объявления, которую можно исполнить;
- место, которое её исполнение объявляет или обновляет;
- значение, полученное при одном исполнении её initializer.

В примере первое — содержимое привязки `iteration`, второе — `item`, третье — очередное число, полученное от `numbers\next()`.

### 3.2. Сопоставление с аргументом

Описать три случая раздельно.

| Случай | Сопоставление | Что сохраняется |
|---|---|---|
| Имя переданного объявления найдено в data | По прежним правилам соответствия имени и позиции | Переданное объявление заменяет найденное описание в namespace |
| Имя внутри переданного объявления не найдено в data | Вся форма занимает текущую позицию как одна Structure | Ссылка на форму; её внутреннее имя остаётся внутри объявления |
| Аргумент задан через внешний `name := …` | Адресат задаёт внешний `:=` | Справа может передаваться форма объявления с собственным внутренним именем |

Вторая строка — обязательное следствие подтверждённого автором примера: в data `cycles` есть `iteration` и `body`, но нет `item`. Поэтому `int: item numbers\next()` поступает в `iteration` по позиции. Внутреннее имя `item` не становится неизвестным именованным аргументом и само по себе не отключает позиционный счётчик. Следующий безымянный блок поступает в `body`.

При этом нельзя заменять весь раздел формулировкой «объявления всегда позиционные»: случай найденного имени сохраняет прежнее сопоставление. Например, при входах `a`, затем `b`, запись `g(int: b producer())` обращается к объявлению `b`, а не к первой позиции `a`. Изменяется результат этой подачи: namespace получает объявление, а не заранее вычисленный результат `producer()`.

В записи:

```lmx
iterate(iteration := int(item numbers\next()); body := (item *= 2))
```

адресатом первого actual является `iteration`. Имя `item` внутри правой части не заменяет этот адресат.

### 3.3. Счётчик позиций

Действующее правило сохранить, включая случаи с поданным объявлением, сопоставленным существующему имени:

1. Пока счётчик включён, именование на позиции того же самого имени считается позиционной подачей и не отключает счётчик.
2. Именование не на своей позиции отключает счётчик с этого места.
3. После отключения допускаются только именованные подачи. Счётчик не включается обратно из-за последующего совпадения.
4. Неизвестное явное имя, недопустимая повторная подача и прочие ошибки по общему контракту остаются ошибками.

В частности, для входов `iteration`, затем `body`:

```lmx
iterate(iteration := int(item numbers\next()); (item *= 2))
```

сохраняет позиционный режим после первого actual. А запись:

```lmx
iterate(body := (item *= 2); iteration := int(item numbers\next()))
```

допустима как две именованные подачи после отключения счётчика первым actual. Она не задаёт порядок исполнения тела и шага: этот порядок устанавливает принимаемый код.

Запись с первым `body := …` и последующим безымянным actual должна по-прежнему отвергаться.

## 4. Исполнение принятой формы и namespace

### 4.1. Сохранённая ссылка и повторное исполнение

Для механизма передачи ресивера объявления корневой уровень принятой структуры логически дополняет корневой уровень выполняемого code. Это действие над namespace и разрешением мест; исходный граф не дополняется полями аргумента.

`iteration` удерживает принятую форму. Каждый достигнутый вызов `iteration()` исполняет её заново. Результат предыдущего исполнения не заменяет сохранённую форму в этой привязке.

Первое достигнутое исполнение `int: item numbers\next()` создаёт типизированное место `item` в namespace данного принимающего выполнения. Следующее исполнение обновляет это место по правилам повторного объявления на том же корневом уровне. Не создавать новый изолированный `item` только потому, что записан очередной `iteration()`.

Обычные последовательная видимость, получение вычисляемого объявления по требованию и проверки сохраняются. Подготовка или передача сама по себе не выполняет initializer; недостигнутая и не потреблённая форма не запускается заранее.

### 4.2. Связь с телом

В каноническом примере `body` — переданная структура тела из того же записанного вызова. Её физический parent — структура аргументов этого вызова, содержащая объявление `item`. Это не структура определения библиотечного `cycles\iterate`.

При исполнении тела `item` обозначает уже объявленное место текущего принимающего выполнения. Тело читает и меняет его непосредственно. Вход в `body()` не создаёт ещё одно собственное вычисляемое `item` из исходного описания и не вызывает `numbers\next()` повторно.

Таким образом, у принимающего выполнения сохраняются и исполняемая форма шага, и полученное типизированное место. Отдельные вызовы шага и тела не разрывают эту связь. Новое независимое выполнение принимающего вызова имеет свой обычный контекст; исходное описание не превращается в общее изменяемое состояние всех вызовов.

Это уточнение нужно явно согласовать с прежними общими фразами «каждый вызов создаёт собственные места». Описать поведение переданного ресивера объявления и связанного с ним тела, сохранив обычные кадры самостоятельных методов.

### 4.3. Структура графа и настоящие вложенные уровни

Логическое дополнение корня не меняет физический parent аргумента, не копирует его поля в исходный code и не заменяет исходное объявление последним вычисленным значением. Источник `numbers` продолжает разрешаться по обычному контексту и исходным структурным связям. Состояние обхода находится в итераторе.

Настоящие вложенные области переданной формы сохраняют обычное затенение. Корневое дополнение не выпрямляет все вложенные объявления в один уровень.

Обычные ограничения записи и времени жизни действуют на выбранное место. Этот чейндж не вводит автоматическое продление жизни завершённой активации, публикацию локальных значений в граф или copy-out при возврате.

## 5. Граница правила: вызов остаётся вызовом

Разделить в документах формы:

```lmx
int: item numbers\next()
@: ptr SomeStructure
```

и:

```lmx
Producer()
Producer: argument
```

Первые читаются по объявляющему контракту ресивера. Для их передачи действует уточнение «в аргументах CODE читать как DATA». Во второй группе Producer обозначает обычный callable, а не ресивер объявления места: такие формы в роли CODE остаются вызовами по обычному контракту. Новое правило не захватывает их как неисполняемые объявления Structure. Различие определяется разрешённой головой и её контрактом, а не особым синтаксисом или списком имён.

Общая фраза «все объявления среди аргументов читаются как DATA» недостаточно точна и не должна становиться нормой: она смешивает ресивер объявления места со структурной формой, которая объявляла бы Structure в другой роли.

Не распространять изменение на все обычные значения-Structure и все вызовы. Само получение обычной ссылки `p := S` не делает каждое поле S корневой переменной принимаемого кода. Порядок потребления обычных аргументов продолжает определять их действующий контракт.

### 5.1. Согласование с именованными сигнатурами fn

Применять уточнённый контракт `fn: name data` из §8 ТЗ `LMX_Fable_TZ_Binding_and_Callables_v2_2026-11-19.md`. Обычный структурный template требует всё явно заданное в нём дерево: если модель содержит `lookup`, эта ветвь обязательна; минимальная модель только с входом и `return` её не требует. `fn` задаёт отдельный контракт вызова: сопоставляются число и порядок типов явных параметров и описание результата. Имена параметров, их начальные значения и дерево тела не являются критерием соответствия такой сигнатуре. Совпадение имён не разрешает переставлять параметры кандидата с разными типами.

При явном именованном вызове через ссылку с требованием `fn` публичные имена сигнатуры задают позиции actuals. После обычного сопоставления имени и позиции каждый actual направляется в параметр кандидата с тем же индексом, даже если у него другое имя. Имена кандидата не используются для перестановки этого соответствия; прямой вызов самого кандидата использует его собственные имена. Прежний счётчик позиций сохраняется. Вычисляемые actuals исполняются один раз в порядке записи, а не в порядке полученных позиций. DATA-формы, включая передаваемые ресиверы объявления, сохраняют свой контракт и не получают досрочного исполнения initializer.

При сопоставлении переданного ресивера объявления через fn-интерфейс ветви §3.2 используют ту же внешнюю карту имён и позиций. Она выбирает принимающее место кандидата, но не переписывает внутреннее имя сохранённой формы. Явный внешний `name := …` по-прежнему задаёт адресата, как в §3.2; ни замена объявления, ни передача целой формы по позиции не превращаются из-за fn в досрочное вычисление её значения.

Обязательность, defaults и `throws` определяются фактическим вызываемым кандидатом; значения из описания `fn` не сравниваются как значения и не копируются в него. Скрытое связывание использует настоящие имена кандидата, а не публичные имена сигнатуры. Этот контракт не меняет прямой вызов `iterate` из §§7–8 и не превращает все ресиверы в одну категорию: `fn` читает свои аргументы как DATA по собственному объявленному контракту.

## 6. Изменение 2: import

> `import` добавляет в текущий namespace только const-объявления импортируемых структур, которые при вызовах считаются корневыми в data. Объявление любой пользовательской структуры константно и без явного `const`, поскольку структура не является переменной.

Корневые объявления определяются общими правилами data. Совпадения имён обрабатываются как обычные повторные объявления. Импорт сохраняет содержимое исходных структур и их `parent`.

Пример пользовательской структуры без `const`:

```lmx
Library:
    Settings:
        int: limit 10
end: Library

Use:
    import: Library
end: Use
```

Имя `Settings` добавляется в namespace `Use`: объявление `Settings` корневое в data `Library` и константное по своей природе. Писать перед ним `const` не требуется.

### 6.1. Импорт модели, именованной сигнатуры и реализации

Правило относится к объявленным именам, а не к запрету всех ресиверов: `fn` создаёт константное имя описания сигнатуры, и его корневое объявление импортируется на общих основаниях. Сам ресивер `fn` не становится новым импортированным именем.

```lmx
Library:
    PrioritiesTemplate:
        []: char name
        return: int
    fn: PrioritySignature PrioritiesTemplate
    Priorities:
        []: char name
        return: int
        lookup:
            return: sys\priority(name)
    end: Priorities
    @: selected PrioritySignature Priorities\lookup
end: Library

Use:
    import: Library
end: Use
```

В namespace `Use` добавляются три корневых константных имени: `PrioritiesTemplate`, `PrioritySignature` и `Priorities`. Обычная переменная-ссылка `selected` не импортируется. `name`, `return` и `lookup` не поднимаются из вложенной `Priorities` в корень `Use`. Импорт не меняет `parent`: данные для `Priorities\lookup` по-прежнему находятся в `Priorities`.

`PrioritiesTemplate` — обычная минимальная структурная модель без `lookup`; `PrioritySignature` — именованное описание вызова, созданное `fn` на основе этой модели. Трёхаргументная форма `@: selected PrioritySignature Priorities\lookup` явно разделяет имя ссылки, требование и фактический callable. Не переписывать её как `@: selected PrioritySignature` с утверждением, будто двухаргументная форма уже выбрала реализацию: по общему правилу `@: p Model` первоначально ссылается на сам `Model`.

## 7. Канонический пример

Включить в нормативную семантику и руководство пример автора с единообразными отступами:

```lmx
cycles:
    @: iteration
    @: body
    iterate:
        while: 1
            iteration()
            catch: Stop ()
                break
            body()
end: cycles

use:
    import: cycles
    test:
        iterate: int: item numbers\next()
            item *= 2
end: use

use\test()
```

Для этого примера `numbers` — доступный из внешнего контекста итератор. Его `next()` выдаёт очередное целое значение либо завершает последовательность через `Stop`. Состояние позиции хранится в `numbers`, библиотечный `iterate` его не создаёт.

Объяснение должно прямо фиксировать:

1. `import` добавляет в namespace `use` объявление `iterate`, доступное затем из `use\test`: пользовательская структура константна без явного `const`. Обычные переменные `iteration` и `body` не импортируются; они остаются входами `iterate` в его исходном parent `cycles`.
2. Первая переданная форма — ресивер объявления `item`; как одна структура она принимается параметром `iteration`.
3. Вторая переданная форма — блок тела, принимаемый параметром `body`.
4. При передаче `numbers\next()` не исполняется.
5. Исполнение `iteration()` получает следующий элемент и объявляет/обновляет `item` как корневое выполненное объявление.
6. Исполнение `body()` меняет это же `item`.
7. Следующий оборот снова исполняет сохранённую форму шага.
8. `Stop` прекращает цикл через обычный `catch` и `break`.

В данном расположении catch действует на весь блок итерации, включая `body()`. Это сохранённая область действия обработчика, а не специальная обработка имени `Stop` новым механизмом аргументов.

Если `next()` выдаёт 10, затем 20, затем `Stop`, нормативная трасса такова:

| Оборот | Действие шага | Действие тела |
|---|---|---|
| 1 | Один вызов next, `item` получает 10 | То же место получает 20 |
| 2 | Один вызов next, то же место получает 20 | То же место получает 40 |
| Завершение | Один вызов next, выброшен Stop | Тело не выполняется |

Итого: три вызова next, два успешных получения элемента и два исполнения тела. Чтение item и вход в тело дополнительных вызовов next не создают.

## 8. Именованная запись того же вызова

В исполняемом контексте, где имя `iterate` уже импортировано:

```lmx
iterate(
    body := (item *= 2);
    iteration := int(item numbers\next())
)
```

Это две именованные подачи. Первая стоит не на позиции своего имени и отключает счётчик; вторая также именована, поэтому старое правило соблюдается. Передача body раньше iteration не исполняет тело раньше шага. Оба аргумента принимаются как соответствующие структуры, порядок их последующего исполнения задаёт код `iterate`.

Запись с пустым телом из обсуждения также допустима:

```lmx
iterate(body := (); iteration := int(item numbers\next()))
```

Пустая Structure является переданным значением, а не отсутствием аргумента.

## 11. Текст для английской нормативной версии

Следующий текст можно использовать как основу с обычной редактурой терминов проекта:

> A place-declaration receiver supplied as an argument in a CODE argument context is read as DATA. The argument preserves the declaration itself; supplying it does not, by itself, execute its initializer. When a corresponding declaration is found in the receiving call's data, the supplied declaration replaces that declaration in the call namespace rather than assigning its computed value. The established named and positional argument rules remain in force. When the declared name is absent from the data, the declaration is supplied as one Structure at the current argument position; its internal name does not become an unknown named actual.
>
> Executing the accepted declaration form applies its root declaration at the root level of the receiving execution. The first reached execution establishes the declared place; subsequent executions update that same place under the ordinary redeclaration rules. The accepted form remains available for execution again. The associated body uses the established place, without evaluating the initializer again merely to read it. This namespace effect neither rewrites the source graph nor reparents the supplied Structure.
>
> This rule concerns place-declaration receivers. An ordinary call whose head is not a place-declaration receiver, such as `Producer(args)` or `Producer: tail`, remains a call in CODE. This argument rule does not reinterpret it as a DATA declaration. The distinction follows the resolved head and its contract, not a separate syntax.
>
> The receiver `import` adds to the current namespace only const declarations of the supplied Structures that are treated as root-level declarations in data when making a call. A user Structure declaration is constant even without an explicit `const`, because the Structure is not a variable. Root-level status follows the ordinary data rules. Name collisions follow ordinary redeclaration rules; the source contents and parent links are preserved.
>
> The named signature receiver `fn: name data` remains in the language. An ordinary structural model requires its entire explicitly described tree. A `fn` requirement instead compares the number and ordered types of explicit parameters and the result description; parameter names, initializer values and the implementation body are not matching criteria. Named actuals supplied through a reference constrained by `fn` use the public names of that signature, are mapped to its formal positions, and reach the candidate's parameters at the same positions. This does not reorder candidate parameters by name. The established positional-counter rule remains in force, and evaluated actuals retain source evaluation order. Defaults, requiredness, failures and hidden binding use the actual candidate's contracts and names; initializer values in the `fn` description are not copied into the candidate. DATA arguments retain their declared contracts. A constant named signature created by `fn` is imported by the same root-declaration rule as any other eligible constant name; this introduces no blanket exclusion of declarations produced by receivers.
