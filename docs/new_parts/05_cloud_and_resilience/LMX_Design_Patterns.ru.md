# LMX: Облако, HTTP и отказоустойчивость

Go и C# дают два привычных стиля сетевых сервисов: функции/каналы и .NET delegates/Channel. Сравнивается прикладной алгоритм поверх одинаково описанных transport/provider контрактов; развёртывание учитывается отдельно.

Все 13 паттернов сохраняют исходные номера; 87 добавлен как явный обратный контроль потока. LMX использует Message и уже определённый HTTP-профиль. HTTP admission, исполнение операции и семантический успех различаются. Общая обвязка перечислена отдельно и не считается бесплатной.

## Каталог

### 038. [Circuit Breaker](038_circuit_breaker_comparision.md)

После двух последовательных отказов владелец временно запрещает новые обращения и затем допускает пробу.

**Сценарий:** Вызовы в моменты 0 и 1 завершаются отказом; вызов в 2 должен быть отклонён; проба в 6 успешна.

**Наблюдение:** Результаты 0, 0, −1, 1; провайдер вызывается три раза; после пробы счётчик отказов равен нулю.

LMX выражает автомат состоянием Message; Go и C# используют состояние экземпляра. Единственная проба обеспечивается выбранным последовательным контрактом, а не атомарной проверкой общего флага.

### 039. [Retry](039_retry_comparision.md)

Ограниченный повтор временного отказа с задержкой между попытками.

**Сценарий:** Идемпотентное чтение возвращает 503,503,200. Разрешены три попытки и задержки 1,2 единицы.

**Наблюдение:** Итог 200; три обращения и две задержки. Статус 400 прекращает повторы сразу.

Алгоритм почти одинаков: собственная почта LMX не добавляет автоматический retry. Задержки и предел явно заданы приложением.

### 040. [Bulkhead](040_bulkhead_comparision.md)

Разделение лимитов одновременно выполняемой работы между независимыми направлениями.

**Сценарий:** У направлений A и B по одному разрешению. A занято; второй запрос A отвергается, первый B принимается.

**Наблюдение:** Для A результаты acquire: 1,0; для B: 1. Освобождение A снова разрешает работу.

LMX переносит владение разрешением к двум владельцам; Go и C# используют два независимых семафора. Один общий Message, исполняющий обе долгие операции, не обеспечил бы изоляции задержек.

### 042. [API Gateway](042_api_gateway_comparision.md)

Один HTTP endpoint выбирает явный маршрут к одному из внутренних сервисов.

**Сценарий:** Декодер входа преобразует /orders в route=1, /stock в route=2. Неизвестный путь получает 404.

**Наблюдение:** Маршруты 1 и 2 вызывают соответственно /orders/get и /stock/get; неизвестный маршрут не вызывает провайдера.

У LMX уже есть HTTP-профиль и admission; прикладная таблица маршрутов всё равно нужна. Контрольные листинги используют тот же контракт транспорта.

### 043. [Backends for Frontends](043_backends_for_frontends_comparision.md)

Разные фронтенды получают отдельные операции агрегации поверх общего backend.

**Сценарий:** Backend даёт цену 12 и доставку 3. Мобильный экран показывает цену; web checkout — итог с доставкой.

**Наблюдение:** Mobile возвращает 12 с одним обращением; Web возвращает 15 с двумя.

Различие находится в frontend-specific агрегировании и независимых границах развёртывания. Ни Message, ни короткая функция сами по себе не создают полноценный BFF.

### 044. [Sidecar](044_sidecar_comparision.md)

Служебная обработка выполняется рядом с приложением в отдельном процессе с общим жизненным циклом.

**Сценарий:** Приложение посылает запись 7 локальному журналирующему sidecar, который записывает её в sink.

**Наблюдение:** Sink содержит одну запись 7. Завершение deployment закрывает и приложение, и sidecar.

Основной код мал во всех языках; определяющая часть Sidecar — deployment: два процесса/контейнера, общий lifecycle и endpoint. Локальный дочерний Message в одном процессе имеет более слабую изоляцию.

### 045. [Ambassador](045_ambassador_comparision.md)

Локальный сетевой посредник скрывает внешний endpoint и политику повторов от клиента.

**Сценарий:** Клиент просит получить каталог. Ambassador обращается к заданному endpoint: первый результат 503, второй 200.

**Наблюдение:** Клиент получает 200; внешний провайдер вызван дважды, с одним и тем же endpoint/route.

Message задаёт границу состояния посредника; HTTP остаётся штатным транспортным профилем LMX. В контрольных языках такая же граница создаётся хостом.

### 049. [Cache-Aside](049_cache_aside_comparision.md)

Приложение загружает отсутствующее значение и явно инвалидирует кэш после записи в хранилище.

**Сценарий:** Для одного фиксированного ключа store содержит 7. Выполнить get,get,put(9),get.

**Наблюдение:** Чтения возвращают 7,7,9; store.read вызван дважды. put сначала меняет store, затем сбрасывает ready.

LMX хранит кэш у Message-владельца, контролирующего get и put. Контрольные версии имеют то же confinement; это не многоклиентский распределённый согласованный кэш.

### 052. [Throttling](052_throttling_comparision.md)

Admission ограничивает число запросов в фиксированном временном окне.

**Сценарий:** Лимит два запроса на окно длиной 10. Запросы приходят в моменты 0,1,2,10.

**Наблюдение:** Результаты allow: 1,1,0,1.

Алгоритм и состояние совпадают; Message устраняет конкурентную модификацию счётчика внутри данного владельца. Разные владельцы не делят один глобальный лимит автоматически.

### 053. [Queue-Based Load Leveling](053_queue_based_load_leveling_comparision.md)

Буферная очередь отделяет быстрый приём запросов от ограниченной скорости обработки.

**Сценарий:** В очередь сразу поступают 1,2,3. Каждый tick обрабатывает не более одного элемента.

**Наблюдение:** После первого tick обработан только 1; после трёх — 1,2,3, очередь пуста.

LMX inbox служит доставке, а прикладной буфер и темп обслуживания здесь заданы явно. Ни один листинг не маскирует unbounded очередь как backpressure.

### 054. [Competing Consumers](054_competing_consumers_comparision.md)

Несколько рабочих участников запрашивают работу у единственного владельца очереди.

**Сценарий:** Очередь содержит 1,2,3. Два worker Message по очереди выполняют take до исчерпания.

**Наблюдение:** Каждое значение 1,2,3 выдаётся ровно одному worker в этом безаварийном прогоне; пустая очередь даёт −1.

Worker не конкурируют за выполнение одного LMX Thread: конкурируют запросы к QueueMessage, затем работа идёт в разных Message. Go channel и .NET Channel предоставляют собственную атомарную выдачу.

### 056. [Health Endpoint Monitoring](056_health_endpoint_monitoring_comparision.md)

Раздельные проверки показывают живость процесса и готовность обслуживать запросы.

**Сценарий:** Процесс отвечает, но обязательная БД недоступна. Затем БД восстанавливается.

**Наблюдение:** liveness=200 всегда при достижении handler; readiness меняется с 503 на 200.

LMX HTTP-профиль уже отделяет admission и семантический ответ, поэтому readiness берётся из результата handler. Один факт принятия письма не делает сервис готовым.

### 087. [Backpressure](087_backpressure_comparision.md)

Производитель передаёт элементы только в пределах явно выданного потребителем кредита.

**Сценарий:** Выдан один credit. Производитель пробует отправить 7 и 8, затем получает новый credit и повторяет 8.

**Наблюдение:** Первый 7 отправлен, первая попытка 8 возвращает 0 без отправки, повтор 8 отправлен. In-flight не превышает 1.

Кредит ограничивает передачу до заполнения downstream, а не только отказывает после перегрузки. Mailbox LMX сам по себе такого контракта не даёт; он реализован приложением.

## Границы сравнения

Размеры вычислены из трёх листингов каждого паттерна. Они не измеряют скрытый код поставленных библиотек, runtime, HTTP-хоста или БД. Для полного понимания нужны ограничения каждого отдельного примера. Номер совпадает с исходным списком; номера 86–90 — явно добавленные темы.
