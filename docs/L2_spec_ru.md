# Спецификация L2

## Обязательные требования к исправлению кода

1. **ГРУБАЯ ОШИБКА: снятие единственного анонимного контейнера на этапе P0. ТРЕБОВАНИЕ ИСПРАВИТЬ КОД P0.** Прежнее правило, заменявшее единственную дочернюю Structure её полями, ошибочно: оно разрушает записанную вложенность не только при вызовах, но и в описаниях и данных. Сохранять каждый явно записанный анонимный контейнер во **всех** контекстах, включая единственный, пустой, круглый аргументный, фигурный описательный и квадратный Mix. Ни построение дерева, ни последующая нормализация P0 не должны раскрывать или удалять его.

   Раскрытие переданной структуры аргументов допустимо **только в семантике вызова**, при подготовке аргументов, без изменения исходного дерева. У `f()` тело Frame содержит ноль полей; у `f: ()` — одно поле, пустую аргументную Structure. Эти исходные деревья различны, хотя семантика вызова может подготовить из них одинаковый пустой набор аргументов. Невызовные контексты такого раскрытия не наследуют.

2. **ТРЕБОВАНИЕ УДАЛИТЬ ИЗ КОДА ПОДДЕРЖКУ ДВУХАРГУМЕНТНЫХ ФОРМ ВСТРОЕННЫХ РЕСИВЕРОВ.** Удаляются формы, передающие ресиверу одновременно имя объявляемого места и его описание/значение. Следующие написания приведены **только как удалённые**, а не как допустимые примеры: `int: i 5`, `int(v, j)`, `@: ptr 0`, `@: ptr Model`, `@: ptr Model: Other`. Требование относится к специальным веткам разбора, семантики и примерам; старые формы не должны сохраняться в качестве fallback или автоматически восстанавливаться перестановкой полей.

   Канонические формы: `i{ int: 5}`, `i: int: 5`, `ptr: @: 0`, `ptr: @: Model`. Имя места находится снаружи ресивера, который получает один операнд описания/значения. Допустимые нульарные и самостоятельные одноаргументные формы, в том числе `int: x` и `@: ptr`, этим изменением не удаляются. Требование не ограничивает число аргументов методов, `merge`, `print`, `fn`, `if`, почтовых операций и других конструкций общего Frame-синтаксиса.

**Редакция 4: 2026-11-09.** Спецификация применяет принятые синтаксические и структурные правила действующих [грамматики LMX](LMX_grammar.ru.md) и [пояснений к семантике](LMX_semantics_guide.ru.md). Эти явные изменения имеют приоритет над противоречащим прежним текстом и ссылками на документы реализации. Остальные машинные контракты L2, правила памяти и исполнения сохраняются. Редакция 4 уточняет общую видимость имён, накопление изменений и согласованное понижение в native. Требования к реализации и однозначность поля вместо выбора по близости ([уточнение автора 2026-11-09](../LMX_blog/2026-11-09.md)) приведены в [списке ошибок для исправления](bugs_for_fixing.md).

L2 задаёт механизмы ядра и машинные операции. Семантика L3 определяется в [спецификации LMX](LMX_semantics.ru.md), синтаксис — в [грамматике](LMX_grammar.ru.md), понижение в C99 — в [L1](L1_spec_ru.md). Разрешение голов, объявление и вызов используют эти общие правила; ниже описаны их последствия для L2 без сохранения удалённых форм записи. Состояние реализации — в [заметках](implementation-notes.ru.md).

<a id="scope"></a>
## 1. Предмет

Целевая цепочка — L3 со вставками L2 → генерируемый L1 → C99. L1 является промежуточным языком. Интерпретатор исполняет сохранённый граф L3; L2-операции требуют нативного понижения.

Общие исходные формы: `{...}` — Structure, в том числе группировка выражения; `name{...}` — ограниченное именованное описание; `[...]` — Mix; `(...)` — вызовы, структуры фактических аргументов, выделение Array и индексация Array. Mix сохраняет локальный контекст разбора уровня 0; колонка открытия не становится базой отступов. P0 сохраняет каждый записанный контейнер, включая единственный и пустой. Раскрытие переданной структуры как всей структуры фактических аргументов допускается только семантикой уже разрешённого вызова функции/метода, без изменения исходного дерева. Сырой исходник C99, обозначения типов C, регулярные выражения и математическая метанотация сохраняют собственную запись.

<a id="lmx"></a>
## 2. Структура `Lmx`

Целевая физическая модель имеет общую основу `Lmx` для объектов графа. Языковой Array — разновидность `Lmx` Structure с фиксированным типизированным хранилищем элементов, а не самостоятельная запись `VoidArray`, на которой основан `Lmx`. И обычная Structure, и Array имеют структурные `parent` и `native`; точная C99-раскладка общей основы и специализации Array ещё выбирается при миграции. Нынешняя обратная раскладка C описана только в [заметках о реализации](implementation-notes.ru.md#l2-status) и не является целевой нормой.

`parent` задаёт структурную вложенность, не родителя Message. У Array, созданного в поле `arr`, родитель — представляющее это поле вхождение графа, а у Structure, созданной как собственный элемент массива, родитель — сам Array. Сохранение в элементе ссылки на уже существующую Structure не меняет родителя её референта. Лексическая видимость определяется местом создания; дополнительный скрытый контекст не создаётся. `native` выбирает нативный вход; нуль означает обход сохранённого тела. Графовый объект не хранит имени, тега модели или дополнительных полей состояния исполнения. Число полей Structure и элементов Array фиксируется при построении, их адресуемые ячейки не перемещаются. Примитивные элементы остаются типизированными ячейками, которым не требуется отдельное поле `parent`.

<a id="interpretable-tree"></a>
### 2.1. Интерпретируемое дерево

Разрешённый ресивер при создании результата выбирает его типизированный пул; сходство полей уже объявленной `data`-структуры не превращает её в результат этого ресивера. В частности, пул результатов `fn` получает только структуру, созданную исполнением `fn`, а не произвольную Structure с похожими частями в `data`.

Сохранённый граф — программа: объявления, значения, операторы и вложенные тела при построении следуют исходному порядку; последующая запись меняет этот же граф. Нативное понижение не заменяет его вторым AST или графом данных. Примитив уже имеет типизированную ячейку арены; дополнительный `leaf` или обёртка Structure для неё не нужны. Атомы, которые остаются частью текущей программы, сохраняются.

Выражение является Structure с упорядоченными полями, включая записанные операторы, операнды и вложенные Structure. `{a + b}` явно ограничивает такую структуру выражения. P0 сохраняет её поля и контейнер, не вычисляет выражение и не заменяет контейнер содержащимися в нём полями. Роли операторов, приоритет и вычисление затем определяет потребитель выражения. Это не вводит дополнительной оболочки выражения, фиксированных позиций операторов или автоматического исполнения из-за хранения либо выбора выражения. Общий путь `struct\(index)` применим к его непосредственным полям, как к любой Structure.


Обходчик исполняет текущее подходящее дерево, включая построенное или изменённое во время исполнения: редактирование данных, которые затем передаются как `code`, является построением кода. Предварительная трансляция, сохранённый подготовленный результат транслятора, скрытая копия исходника или флаг «подготовлено» для этого не требуются. Обход текущего графа и обычное разрешение его операций — исполнение, а не запрещённый повторный разбор исходного текста. Общие правила ресиверов, допуска и адресных карт сохраняются; они не требуют одного хранимого представления для native и обходчика. Это норма, а не утверждение о завершённой поддержке runtime-построения в нынешнем ядре. [Уточнение автора, 2026-10-23](../LMX_blog/2026-10-23.md).

Имена сущностей находятся только во внешней таблице. Обходчик может получить по адресу имя написанной головы, чтобы определить её роль; это не поиск переменных по строкам при доступе к полям. Транслятор читает граф единицы, построенный общим построителем, а не дерево парсера: дерево разбора уничтожается вместе с построением ([спецификация реализации §11 п. 3](kernel-implementation.ru.md#transition)); готовый `native` не нуждается в имени для вызова. Комментарии не участвуют в диспетчеризации. `toLmx` выводит текущий состав и порядок графа: перезаписанный оператор не восстанавливается из исходника или скрытой копии. Служебные данные запуска, статус вызова и состав детей Thread не дописываются в граф программы.

Ссылки как данные образуют граф и могут создавать циклы. Структурный `parent` образует дерево. Вид значения определяет классификация его адреса; адрес слота и хранимый в нём адрес — разные вещи.

Все имена и подготовленные места применимой области видны в обе стороны: правило относится также к обычным Structure, примитивным полям и ссылкам, а не только к `fn`, `fm`, `sub` или `catch`. Приоритет имеет последнее предшествующее, уже накопленное связывание данного имени в соответствующей области. Это выбор по имени и области, а не поиск «последнего совместимого» кандидата через типы или тесты; выбранное значение проходит обычный допуск, и отказ не возвращает поиск к более старому значению. При отсутствии предшествующего связывания доступное будущее определение не исключается только потому, что записано ниже. Выбора по близости среди нескольких кандидатов нет: в области кода имени соответствует одно подготовленное через `var` место, выполненные записи последовательно меняют его значение; при обращении к data поле должно находиться однозначно — несколько одноимённых вхождений без индекса дают ошибку неоднозначности, в том числе когда code передан самому себе как data ([уточнение автора 2026-11-09](../LMX_blog/2026-11-09.md), [требования](bugs_for_fixing.md#forward-candidates)).

Предварительное обнаружение имён и мест относится к семантической подготовке текущего графа. Оно доступно и обходчику без обязательной предварительной трансляции, но не исполняет будущие инициализаторы и присваивания только ради разрешения имени. Доступность места не означает наличие уже вычисленного значения и не обещает нуль для неинициализированного примитива. P0 сохраняет исходную форму и порядок, не выбирая runtime-связывания.

Границы областей остаются общими с L3: это правило не объединяет соседние или вложенные области, не меняет `node` как лексического родителя исполняемого вхождения и не обходит `independent`. Прежний порядок динамического поиска и лексического fallback сохраняется; видимость в обе стороны действует внутри соответствующей допустимой области. Новое пространство имён, постоянная глобальная таблица runtime-связываний, opcode или скрытое окружение не вводятся.

<a id="type-by-range"></a>
## 3. Тип по диапазону адресов

Производные графовые объекты сохраняют общий `Lmx`-контракт. Пул и диапазон указывают выбранный при построении физический вид, а для Array — также тип элементов. Это классификация адреса, не поле имени или opcode в графе и не отдельный пользовательский тип для каждой модели Structure. Старое расположение, где `Lmx` содержит `VoidArray`, остаётся переходным, а не образцом для новых разновидностей Array.

Арена классифицирует адрес по зарегистрированному полуоткрытому интервалу `LmxRange` и пулу-владельцу. Сама ячейка не хранит тег типа. Обычные Structure и графовые Array имеют общую основу `Lmx`, но диапазон различает форму хранения и тип элементов; модели пользователя не порождают по одному C-типу или пулу. Пулы примитивов, ссылок, графовых объектов и backing различаются физическим контрактом доступа. Типизированные массивы внутри арены — хранилище, а не отдельные языковые Array. Обычные и `immutable` Structure выделяются в разных пулах; уже опубликованная обычная Structure не становится `immutable` на месте. Совместимость моделей устанавливает `implements`, а не физический тип. Для каждого примитивного типа T есть отдельный тип «T без инициализации», различимый тем же способом — по участку адреса ячейки (решение автора 2026-11-08): у места `int: x` без значения поле ссылается на примитив-указатель «int без инициализации», указывающий на заранее существующую ячейку `int` этого места, `x: int: 0` — на ячейку `int` напрямую; первое присваивание и все дальнейшие записи идут в эту же ячейку; поле не перепривязывается — слот, тип и адрес ячейки не меняются ([спецификация реализации §3.2](kernel-implementation.ru.md#lmx)).

`typeof(p)` принимает указатель и возвращает код арены типа объекта, на который он указывает. В L2 эта классификация определяется по зарегистрированному типизированному диапазону адреса цели и пулу-владельцу; это не идентичность охватывающей логической арены Message, которая может содержать несколько типов. Результат — не статический тип носителя `@` и не тип значения, которое могло бы вернуть исполнение выбранного метода. Конкретные значения кодов здесь не задаются. Код арены типа не заменяет полный допуск Structure и не создаёт отдельного типа для каждой пользовательской модели. Адрес слота и хранимый в ссылочном слоте адрес остаются разными входами: `typeof(arr(index))` для Array `@` исследует объект, на который ссылается выбранный элемент, а не только тип ссылочного слота массива. Обычное числовое значение элемента Array нельзя молча трактовать как указатель.

<a id="pool"></a>
## 4. Типизированный пул

Пул выдаёт ячейки одного размера и растёт добавлением чанка, без `realloc` живых ячеек. Каждый чанк регистрируется как интервал того же типа. Выданный адрес стабилен до освобождения соответствующего владения. Индексом диапазонов управляет арена.

У графового Array `void *data` хранит адрес backing выбранного типизированного пула, а не превращает элементы в нетипизированные значения. L2 получает из него указатель фактического типа элемента для чтения и записи; диапазон арены подтверждает этот тип, размер ячейки и выравнивание. Нельзя читать уже созданный пул слотов `void *` как массив произвольного `T` только приведением указателя. Адресуемые ссылочные слоты графа сохраняют собственный контракт `void **` и конверсию хранимого значения.

<a id="method-array"></a>
## 5. Нативный вход и Array

`LmxEntry` — слово нативного входа, а не второй объект метода. Графовый Array несёт общую основу `Lmx` и ровно заданное число типизированных элементов. Он не содержит динамического резерва и не перемещает опубликованные адресуемые ячейки. При объявлении Array, например `arr: (): int`, значение Array сохраняет своё место в графе; последующее `MyLmxStructFromArray: arr` по общему правилу связывает новое имя ссылкой на тот же Array, а не конструирует второй объект или восстанавливает структуру из байтов. Динамический List — отдельный тип и отдельный контракт; его перемещаемый backing не используется как адресуемые слоты Structure или Array.

Structure также допускает прямой выбор элемента через `struct\(index)`, считающий все непосредственные поля с нуля. Представление в виде Array `@` остаётся другим путём:

```lmx
arr{ (): @}; arr: f; arr(1)
```

У метода `f` части упорядочены как `{args return var body}`. И `f\(1)`, и последнее `arr(1)` выбирают его Structure `return`; во втором случае доступ идёт через соответствующий элемент массива ссылок. `f\(0)return` выбирает первое вхождение именованной головы `return:`, а `f\return` — её единственное вхождение. Прямой индекс и индекс именованного вхождения считают разные последовательности. Правило представления через Array не предписывает переинтерпретацию байтов, выбор между алиасом и копией, новое правило владения или дополнительный физический объект метода. Требования фиксированного хранилища и стабильных адресов выше продолжают действовать для опубликованных адресуемых ячеек.

<a id="arena"></a>
## 6. Арена

Каждый Message владеет одной логической ареной; она может содержать несколько чанков и диапазонов. `lmx_arena_attach` передаёт владение без перемещения адресов. `mark/revert` откатывают неудачное построение копии или `merge`. Простой режим сохраняет классификацию и стабильность адресов, но не запускает GC. Независимая неизменяемая ветвь может остаться в арене владельца по [контракту L3](LMX_semantics.ru.md#eternal); сам факт отдельного пула такого права не даёт.

<a id="message"></a>
## 7. Запись Message

Закрытый `LmxMsg` содержит ровно `running`, `success`, `handoff_ready` и `graph`. Его локальная идентичность — адрес записи. Почта, планировщик и родитель Thread не являются его полями. Запись нуля в `running` во время хода запрашивает остановку; пользовательский код устанавливает `success` в единицу, чего достаточно для остановки Thread на границе хода; система не сбрасывает `success` в нуль. `handoff_ready` разрешает передачу хранилища. `graph` ссылается на языковой корень.

<a id="thread"></a>
## 8. L3 Thread

Не каждый Message исполняется. Исполняемый Thread изначально выделяется как `LmxThread` с `LmxMsg` первым членом по значению. Адрес Thread совпадает с адресом этого префикса; доступ к хвосту требует точной классификации Thread. Самостоятельный `LmxMsg` нельзя на месте превратить в Thread.

Прямые дети хранятся в единственном List, удерживаемом полем `Thread.children`. Это состояние Thread, не поле `message.graph`. `Thread.parent` относится к иерархии Message и не меняет `Lmx.parent`. Одну идентичность Thread не исполняют конкурирующие workers.

<a id="root-close"></a>
### 8.1. R0 и закрытие

R0 — обычный дочерний Thread верхнего host-каркаса. Служебные данные запуска и настройки принадлежат каркасу и передаются R0 явно; они не добавляются в исходный граф R0. Верхний каркас не имеет родителя, но не получает особого API. Закрытие каскадно проходит через единственный List прямых детей каждого Thread. Общий timeout всего поддерева контролирует host-watchdog; его истечение завершает процесс, а не объявляет частичное закрытие успешным.

<a id="mailbox"></a>
## 9. Почта

Каждый Thread владеет `LmxPost`. `staged` готовит письма текущего хода, успешная граница публикует их в `outbox`, `inbox` содержит допущенные, но не взятые письма. Элемент `inbox` — неразделимая пара из `target` и `source_arena`: producer не изменяет арену получателя; владелец присоединяет donor до выдачи target. Отказ сохраняет пару. Порядок допуска — FIFO.

`inbox` — кольцо на отдельном DynamicArray; его backing может перемещаться, но не является графовым адресуемым слотом. Один реентерабельный monitor самого `LmxPost` охватывает admission, take и count. `outbox` и `staged` остаются локальными владельцу. `post` использует эту же почту для обычного вызова LMX, не отдельный транспорт. Языковой API определён в [L3](LMX_semantics.ru.md#thread-message-api).

<a id="own"></a>
## 10. Исполнение Structure

Исполнение использует полную сохранённую Structure. Нативное тело и обходчик должны давать одинаковую семантику чтения, записи, `dirty` и публикации рабочих полей по [L3 §12](LMX_semantics.ru.md#dynamic). Объявленное поле имеет графовое место хранения; присваивание не добавляет слот к уже созданному `Lmx`. Указатели на графовые слоты должны оставаться действительными. Логический порядок частей метода — `{args return var body}`; `f\(1)` выбирает часть `return`. Эта утверждённая цель миграции редакции 3, сохранённая в редакции 4, не означает, что её физический ABI уже реализован. Порядок логических полей не задаёт числовой ABI-раскладки произвольного выражения.

Перед выделением `var` определяется полный набор собственных мест метода: явные поля `var` и отсутствующие среди них собственные поля, обнаруженные в соответствующем `body`. Автозаполнение не зависит от того, находится использование выше или ниже записанного поля. Все подготовленные места доступны с начала области; повторная запись одного имени использует то же место, а не добавляет поле. Сохраняются порядок первых слотов, их физические адреса и доказанная карта code→data. Автозаполнение не дополняет произвольную переданную `data` и не расширяет уже построенный `Lmx`.

Подготовка мест отделена от вычисления значений. Инициализация в `var` выполняется по существующему контракту входа в метод; инициализация в `body` — при достижении своей строки. Полная доступность имён не переносит эти вычисления, не исполняет тело заранее и не восстанавливает уже заменённый инициализатор из скрытой копии.

Обходчик последовательно накапливает принятые изменения текущих мест, а native обязан давать те же результаты в тех же точках. Нельзя подменить каждое обращение статически найденным последним определением всего блока: поздняя запись не меняет задним числом раннее разрешение или чтение. Рабочие значения, моменты установки `dirty`, контрольные точки публикации и инвалидирование `native` сохраняют прежние правила; предварительное обнаружение имени не является записью или публикацией.

<a id="call"></a>
## 11. Вызов

Удалённый оператор `call` заменён явным применением. У обычной Structure нет списка формальных параметров: `code()` исполняет её без явно переданной отдельной структуры данных, а `code(data)` использует переданную Structure `data` как состояние. Метод сохраняет вызовы с формальными аргументами, например `f(1)`; обычное `s(1)` не является позиционным доступом к Structure и не удовлетворяет требованию Structure-данных. Передача `data` не является операцией раскрытия всей структуры фактических аргументов функции/метода. P0 сохраняет разные исходные деревья `f()` и `f: ()`; только семантика вызова может подготовить из них одинаковый пустой список фактических аргументов.

Выбор между нативным входом и обходчиком определяется `Lmx.native` выбранного кода. Исполнение получает выбранный `code` и явно либо сокращённой формой выбранный `data`, фактическую арену, `node` как лексического родителя исполняемого вхождения и подготовленные фактические аргументы при вызове метода. В разделённом исполнении `code` задаёт исполняемое тело, а `data` — состояние. Эти роли не доказывают неизменность кода и не квалифицируют всю Structure как `immutable`. Прогноз путей записи и алиасов не выполняется; фактическое изменение места кода сбрасывает его `native` общим путём записи. Существующий контракт сокращения L2 сохраняется в новой записи: `code()` выбирает `code\var`; отсутствие `var` не означает неявного использования самого `code` как `data`, а запись в локальные поля данных тогда отказывает. Явный `code(code)` передаёт эту же Structure как `data` по общему правилу и служит проверкой универсальности Structure и изменения кода для будущей компиляции на лету, не особым исполнительным путём. Для **любой** допущенной пары Structure доступ к полям и публикация уже вычисленных `dirty`-значений используют одну доказанную адресную карту `implements`; совпадение порядковых номеров не предполагается. Контрольная точка пишет готовое значение в выбранный слот `data`, не выполняя выражение или допуск повторно.

Сам вход в исполнение, включая `code(code)`, не инвалидирует `native`. Общий путь записи при определённых и допущенных месте и новом значении сбрасывает `native` мест кода, связанных с изменяемой ячейкой: прямой путь — при записи, рабочий `dirty` — на контрольной точке публикации. Запись в физический слот и снятие входов изменённого кода атомарны для следующего либо рекурсивного dispatch. Рабочее значение до публикации, отвергнутая запись и не меняющий граф вызов не снимают `native`; изменение обычного значения данных сохраняет вход. Связь с местом кода может принадлежать охватывающей Structure, а не только Structure со слотом записи. Если L2-тело стало несовместимо с прежним входом, требуется подходящая нативная реализация или отказ **до** публикации изменения: обходчик L3 не исполняет L2. Вызов после эффектов не перезапускают другим движком.

Обычная исполняемая форма с именем в `code`, включая `name: ... end: name` и записи внутри inline-`if`/`for`, присваивает значение подготовленному одноимённому месту выбранного `data`. Она не объявляет новое поле в `code`; объявления через `fn`/`fm`/`sub` сохраняют собственный контракт ресиверов. Карта `data` учитывает головы коренного уровня, но не головы внутри их инициализаторов. При одном исходном вхождении головы допустим путь `data\field`, при двух и более требуется `data\(N)field` с отсчётом `N` от нуля; первое вхождение автоматически не выбирается и несколько одноимённых полей данных не создаются. Без имени `data\(N)` выбирает непосредственное поле с общей позицией N; он не выбирает молча N-е вхождение какого-либо подразумеваемого имени. Вложенность в `code` не выбирает другое место. Произвольный `data` не дополняется при вызове: если требуемого места нет либо голое обращение неоднозначно, отказ происходит при исполнении/допуске вызова, а не из-за самой формы записи при трансляции. Подготовка `var` метода заранее выделяет полный набор его полей по §10 отдельно. Правило последнего предшествующего связывания не отменяет неоднозначность явного пути `data\field` и не заменяет нумерованный выбор исходного вхождения. Повторные присваивания тому же месту накапливают его состояние, а не создают новые одноимённые поля. Только явное исполнение Structure через `code()`/`code(data)` либо вызов callable, включая `fn`, создаёт новую область связывания, где собственное поле может затенить внешнее. Внутри одного callable затенения нет: inline-`if`/`for` — операторы той же активации, а не новые области, хотя они тоже Structure.

Нулевой адрес транспортной ячейки аргумента означает отсутствие аргумента; присутствующий аргумент со значением нулевой ссылки остаётся присутствующим. Число передаётся в хранилище объявленной ширины, объектная ссылка — через каноническую ячейку указательного значения. Статус callback и возвращаемое значение различны; контракт результата отличает `void` от присутствующей нулевой ссылки.

При вызове через изменяемую ячейку ссылки на метод используется её текущее связанное значение на границе вызова. Цель выбирается один раз до вычисления фактических аргументов; изменение ячейки во время их вычисления не переадресует уже начатый вызов. Это одинаково для native и обходчика. Сохранённая цель более раннего вызова и последнее определение всего блока не заменяют текущий выбор; отказ обычного допуска выбранной цели не переключает вызов на старое связывание. Эти правила не добавляют новый callback или способ диспетчеризации.

<a id="child"></a>
## 12. Резервация ребёнка

Ребёнок строится в собственной арене. До успешной публикации его нет в `Thread.children`; публикация в конце хода добавляет физическую ссылку в этот List, не меняя исходный граф. Неуспех снимает резервацию, но не откатывает произвольные уже сделанные записи графа.

Переподчинение проверяет, остаются ли владельцы используемых ребёнком ветвей `independent: immutable` в новой цепочке Message-предков. Отказ не меняет членство и `Thread.parent` частично. `adopt: msg newParent` выполняет перенос; `independent: msg newParent` отдельно готовит именно этот перенос, копируя только мешающие ветви в арену `msg` и не меняя родителя. Это операции над иерархией Message, не над `Lmx.parent`.

<a id="copy-merge"></a>
## 13. Копирование графа и merge

`merge` строит новый граф с одной картой адресов источник→копия. Карта сохраняет общие цели и циклы, переписывает внутренние ссылки и `parent` на копии и не создаёт отдельного экземпляра для каждого `lnk`. Копируется весь используемый граф, включая исполняемые записи операций; исключение — квалифицированные `independent: immutable` ветви, явно удерживаемые владельцем. Неизменённая подходящая нативная реализация может использоваться повторно только при сохранённом контракте адресов и типов используемых полей. Неполная копия с адресами освобождаемой исходной арены недопустима.

Первый операнд задаёт порядок слотов модели; совпадающее поле следующего операнда заменяет значение этого слота после допуска, новое дописывается в новом результате. Исходные операнды не меняются. Семантика выбора тела и аргументов — в [L3 §20](LMX_semantics.ru.md#composition).

<a id="implements"></a>
## 14. implements

Доказанное соответствие между используемыми полями принимающей модели и физическими полями кандидата для допущенной пары Structure — данные того приёма или обхода, который его установил (решение автора 2026-11-08 о служебных таблицах обхода, подтверждённое Codex; [спецификация реализации §5.2](kernel-implementation.ru.md#tables)): приём удерживает свою карту на время нужных ему операций — чтения, записи, взятия адреса и прямой публикации готовых `dirty`-значений, включая разные порядки полей, — а следующий обход строит её заново из графа; постоянного хранилища соответствий у арены нет, отдельной карты для вызова Structure либо `var` нет. На одном структурном уровне одно имя обозначает одно поле; `s\(N)field` выбирает исходное вхождение головы, а не N-е поле данных. В отличие от него, `s\(N)` прямо выбирает непосредственное поле с общей позицией N. Оба счёта начинаются с нуля, и ни один из путей не создаёт повторных материализованных полей данных. Карта не ищет имена в runtime, не копирует кандидат и не отменяет проверок нового Consumer. Семантика допуска и явно заданных тестов — в [L3 §7](LMX_semantics.ru.md#admission).

Семантический выбор текущего связывания и последующий доступ по доказанным адресам — разные шаги. Карта `implements` не выбирает имя заново, не применяет правило «назад последняя» к порядковым номерам и не откатывается к более старому значению при отказе допуска. Повторные изменения одного места сохраняют его ячейку; исходные вхождения и пути `s\(N)field`/`s\(N)` остаются различимыми по прежним правилам.

<a id="gc"></a>
## 15. Сбор

GC принадлежит арене. Корни включают Message, живой граф, почту, состояние исполнения и `Thread.children`; последний List удерживается состоянием Thread независимо от исходных полей. От живого значения сборщик следует также по установленному соответствию `implements` к Structure его требования: замена поля графа не освобождает модель, пока действующий допуск к ней нужен этому значению. Временный кадр допуска не удерживается этим правилом; уход кадра удаляет зависящую от него запись. Это зависимости адресного доказательства, а не скрытые поля графа. Созданные `independent: immutable` ветви удерживаются владельцем до уничтожения его арены. Простой режим не выполняет сбор. Правило выгрузки позднего модуля требует отдельного контракта и здесь не изобретается.

<a id="special"></a>
## 16. Специальные операции L2

Ядро предоставляет классификацию адреса, `typeof(pointer)`, выделение ячейки, attach/revert арены, почту, ход Thread, вызов, резервацию ребёнка, копирование/merge и сбор. Эти операции не создают второго пространства имён или вспомогательного графа исполнения.

<a id="lowlevel-scope"></a>
## 17. Машинный профиль

Машинные типы L2 сохраняют представление и числовую семантику соответствующего типа C99 целевой платформы, в том числе знаковость обычного `char`. L3 не получает сырую память только потому, что его граф реализован указателями. L1 имеет отдельную C-подобную поверхность.

<a id="lowlevel-address"></a>
## 18. Адреса, загрузка и запись

M3 упорядочивает плоские объявления как имя, требование/значение. Контракты ресиверов N1–N6 используют имя места снаружи и один операнд требования/значения: `ptr: @: Model: 0`, `p: @: 0`, `p: @: Model`, `p: @: Model: 0` и `p: @: Model: Other`. Доступна и ограниченная именованная форма, например `p{ @: 0}`. В `p: @: Model: Other` имя `p` находится во внешней голове, а единственный операнд ресивера — вложенный Frame `Model: Other`; он потребляется по обычному правилу выражений. Его потребление само по себе не записывает в `Model`. P0 сохраняет общую структуру Frame, не выделяя эти формы по имени ресивера. Прежние двухпольные и трёхпольные указательные формы с именем первым аргументом не сохраняются как совместимые написания: описанный ими кандидат вкладывается внутрь ресивера, имя места остаётся снаружи. Двухаргументную ветку реализации требуется удалить, а не вызывать скрытым fallback. Унарное `@: p` и пустое `@()` остаются допустимыми. Первое `@: p` или `p: @: 0` создаёт void-ссылку; последующая запись адреса не добавляет ей задним числом требование. Указательная глубина `@ⁿ:` не ограничена особым числом.

В `ptr: @: method` внешнее имя `ptr` обозначает место, а ресивер `@` имеет единственный операнд `method`. Голое `method` читает ссылку на метод, не вызывая его. Это записывает допущенную ссылку в то же место, даже если `ptr` уже содержит callable; `ptr(args)` выбирает текущее значение этой ячейки один раз до вычисления аргументов и вызывает выбранный метод по §11. Повторная запись `ptr` не создаёт новый слот и не разрешает native удерживать прежнюю цель для следующего вызова. Унарное `@ptr` отдельно берёт адрес ячейки ссылки. Подробные правила обычной `var` и ссылок — в [L3](LMX_semantics.ru.md#ordinary-var) и [присваивании ссылки на метод](LMX_semantics.ru.md#method-reference-assignment), с учётом явных синтаксических изменений этой редакции.

Унарное `@x` адресует настоящую ячейку значения: для графовой Structure/Array — слот `void *`, содержащий ссылку на дескриптор, для примитива — типизированную ячейку, для формала и скрытого входа из динамической или лексической видимости — собственную локальную ячейку активации. Голое `x` и `@x` относятся к одной локальной переменной; запись не меняет источник связывания. Адрес внешнего поля задаётся явно, например `@{node\x}`. Слот, его адрес и референт различны. Нативное обращение к графовому ссылочному слоту идёт через `void **` с конверсией хранимого `void *`; разыменование этого слота как `Lmx **` нарушает C99. Адрес не берётся у временного кэша или ABI-буфера. `@x\field` по приоритету означает `@{x\field}`.

Префикс `\p` следует ссылке; `p\field` обращается к графовому полю либо к явно импортированному машинному ABI в зависимости от категории `p`. `@array(i)` адресует реальный элемент backing. Прямой `struct\(index)` выбирает непосредственное поле Structure, а `struct\(index)field` — именованное исходное вхождение по §21; эти пути сохраняют различие между слотом, его адресом и референтом. В L2 индекс не получает автоматической проверки границ; проверяемый доступ принадлежит L3. Адресная операция не снимает `const`/`immutable` и не продлевает срок жизни цели.

<a id="lowlevel-array"></a>
## 19. Сырое C-хранилище

Токен `c.*` — явная дверь в C. Языковой Array остаётся объектом графа на общей основе `Lmx` с типизированными элементами; сырой C-массив им не становится. Переход между ними требует явной операции, учитывающей форму и время жизни. Типизированные массивы арены — внутреннее хранилище, не ещё один вид языкового Array. L2 не вводит особую сущность `c.array`.

<a id="lowlevel-abi"></a>
## 20. Внешние типы и ABI

`cast: {T} value` — машинное приведение, не проверяемое преобразование L3 и не доказательство границ, выравнивания или времени жизни. `c.name` выбирает внешний C-символ; адаптер определяет параметры, результат и владение. `c.sizeof` означает C `sizeof`, не длину Array и не число полей Structure. `include` и `os` выбирают явно заданные зависимости и платформенную ветвь, не вводя runtime-поиск модулей.

`os` выбирает целевую платформенную ветвь, но не вводит отдельного сравнения ветвей на равенство наборов методов, сигнатур или сериализованных контрактов. Различия между ветвями сами по себе не являются ошибкой. Выбранные объявления и тела проходят обычные механизмы L2; там, где принимающее место требует совместимости, применяется обычный `implements` и его адресная карта, как вне `os`. Выбор ветви не создаёт дополнительного общего интерфейса или частного `os`-варианта допуска. [Уточнение автора, 2026-10-23](../LMX_blog/2026-10-23.md).

Существующий ресивер `os` выбирает ветвь для целевой платформы до смысловой обработки её содержимого; отдельный новый оператор для этого не нужен. Общий структурный разбор выделяет ветви, но невыбранные объявления и тела не проходят разрешение имён, проверку типов и контрактов, сбор зависимостей или генерацию кода. Их `include`/`define`/`predef` не добавляют зависимости и объявления в выбранный вариант. Выбранное содержимое проходит тот же общий L2-конвейер, что вне `os`, включая обычный native и обходчик для поддерживаемых тел, без частного разбора, исполнителя или запасного native-маршрута. Целевая платформа согласована на всех стадиях трансляции, а не случайно определяется платформой запуска транслятора. Это утверждённое направление реализации, не заявление о завершённой поддержке. [Уточнение автора, 2026-10-23](../LMX_blog/2026-10-23.md).

Платформенные заголовки и имена, встречающиеся только в невыбранной ветви, не требуются для выбранного варианта. Его обычный код может обращаться к методу, объявленному только в выбранной ветви, без объявления аналога в остальных. Трансляция всех альтернатив в L1/C с последующим скрытием невыбранных через C `#ifdef` этому правилу не соответствует; их зависимости, объявления и тела не генерируются. Общий структурный разбор исходника не означает смысловую трансляцию невыбранной ветви. [Уточнение автора, 2026-10-23](../LMX_blog/2026-10-23.md).

Указанное отсечение ветвей — обязанность трансляции. Оно не требует сохранять результат её выбора или подготовки как условие работы обходчика: тот исполняет текущий граф по [§2.1](#interpretable-tree), не обязательную запись транслятора о выбранном теле.

`implements` остаётся runtime-операцией, не статическим сравнением альтернативных платформенных реализаций и не механизмом отключения их трансляции. Если далее потребуется дополнительное средство языка, его общее решение обсуждается с автором; для указанного выбора существующим `os` повторное согласование нового оператора не требуется.

В вычисляемом вызове через C-дверь C-функции и макросы получают заранее вычисленные L2-значения, не подстановку текста L2-выражений. L2-аргументы вычисляются один раз в обычном лексическом порядке и по обычным правилам выхода до передачи внешнему вызову; развёртка макроса не повторяет и не отменяет это вычисление. Поэтому при `#define BYTES(x) sizeof(x)` вызов `c.BYTES(touch())` сначала выполняет `touch()` один раз и передаёт его значение макросу, хотя C не вычисляет операнд получившегося `sizeof`. Это также относится к макросу, который использует параметр несколько раз или не использует его.

Буквальный `c.sizeof` имеет роль оператора C, а не вызова C-функции: после общей подготовки его операнд подчиняется правилам C99 `sizeof`, не предварительному вычислению аргумента внешнего вызова. Развёртка произвольного макроса в `sizeof` не передаёт ему эту роль. Различие определяется семантической ролью после общего разбора, без регистрации C-имён или второго парсера. Для обычного типа без переменно-модифицированных компонентов `c.sizeof(touch())` не выполняет `touch()`; правила C99 для variably modified типов этим не отменяются. [Уточнение автора, 2026-10-22](../LMX_blog/2026-10-22.md).

У C-двери есть и обратное направление: машинную функцию L2 можно экспортировать с прямым C-совместимым входом. C-код вызывает её явными аргументами функции, без экземпляра `Lmx`, корня, Message и подготовленного графа; нужные ей состояние и память она получает своим обычным явным контрактом, а не скрытой общей единицей, ареной или singleton. Функция остаётся тем же L2: существующий генератор переводит её общим структурным разбором, разрешением выражений и проверками, без отдельного C-подобного языка, второго парсера или resolver и без маршрута только для List или библиотек. Обычные графовые вызовы L2/L3 сохраняют свой общий механизм; экспорт не снимает семантику с произвольного `fn`. Поддерживаемые исходники остаются L2/L3, их L1/C генерируется; перенесённое тело заменяет старое без постоянного fallback. Это утверждённое направление реализации, не заявление о завершённой поддержке. [Уточнение автора, 2026-10-23](../LMX_blog/2026-10-23.md).

Нативное понижение общей видимости имён предварительно определяет необходимые C-места, объявления, прототипы и зависимости типов; генератор выдаёт их до использований там, где этого требует C99. Это подготовка раскладки и объявлений, а не раннее выполнение инициализаторов или перестановка записей, вызовов и других эффектов. Изменяемая ссылка на метод читается на границе её вызова по §11; фиксированный прямой вход не может скрыть допустимое изменение выбранной ячейки. Сохраняются реальные адреса слотов, представления значений, карта code→data и правила `dirty`/публикации. Подготовка касается только выбранной ветви `os` и не возвращает семантическую обработку исключённых ветвей. Нового ABI, глобальных runtime-имён или дополнительного opcode не требуется; конкретные исправления перечислены в [списке ошибок](bugs_for_fixing.md).

<a id="lowlevel-expression"></a>
## 21. Машинные выражения

Выражение является Structure с упорядоченными полями и вложенными Structure, а не отдельным неструктурным объектом выражения. `{a + b}` явно ограничивает такую Structure. P0 сохраняет её поля и контейнеры; роли операторов, приоритет и вычисление после разбора определяет семантика выражений. Группировка не разрешает P0 раскрывать Structure или заменять её вычисленным значением. Тот же прямой путь `\(index)` применим к непосредственным элементам выражения без введения фиксированных числовых позиций операторов или отдельного ABI выражения.

Машинный профиль включает фигурную группировку, арифметику, сравнения, логику, битовые операции, `++/--`, индексацию Array, пути Structure и обычное управление. `=` в выражении — сравнение; `target: value` — запись или связывание согласно допускающему контексту. Прежний оператор `:=` удалён. Составные присваивания используют `+:`, `-:`, `*:`, `/:`, `%:`, `<<:`, `>>:`, `&:`, `^:`, `|:` и `**:`; каждое — один токен. Сравнения `=`, `!=`, `<=` и `>=` сохраняют смысл сравнения. Оператор степени и приоритеты выражений определены грамматикой; эта редакция не изобретает дополнительных гарантий преобразований, переполнения и отказов. Переполнение и сырой индекс следуют машинному контракту, не обещаниям L3.

`a(i)(j)` адресует ровный многомерный Array; `a(i)\(j)` следует через ссылку к отдельному Array. Эти формы LMX не переписывают буквальный синтаксис массивов C99. `struct\(index)` выбирает общую позицию среди непосредственных полей Structure с нуля; вложенная Structure остаётся одним полем. `struct\(index)field` вместо этого выбирает исходное вхождение указанной головы `field:` коренного уровня, также с нуля. Голое `struct\field` по-прежнему требует единственного вхождения. Необязательное имя пути следует прежним границам пути; P0 не выводит его из сигнатуры и не захватывает отдельный следующий аргумент.

```lmx
f\(1)                # общая позиция 1: return
f\(0)return          # первое вхождение имени return
f\return             # единственное вхождение имени return
f(1)                 # вызов метода с фактическим аргументом 1
arr(1)               # элемент Array с индексом 1
```

У метода `f` части упорядочены как `{args return var body}`, поэтому первые три пути выбирают его Structure `return`. `f\(1)return` потребовал бы второго вхождения именованной головы `return:`, а не общего поля 1. Обычная Structure по-прежнему исполняется через `s()` или `s(data)`; простое `s(1)` не переосмысливается как индекс. Прямой выбор не требует объявления Array, а представление Array `@` из §5 остаётся доступным.

`typeof(arr(1))` в таком представлении возвращает код арены типа выбранной Structure описания `return`, а не тип значения, которое вернуло бы исполнение `f`. Классификация адресов и требования к указателю заданы в §3; машинный `c.sizeof` сохраняет отдельный контракт C99.

<a id="lowlevel-sync"></a>
## 22. synchronized

`synchronized: lock body` задаёт структурную область взаимного исключения, не открытую пару lock/unlock. Выход освобождает monitor. Почтовый monitor — конкретное реентерабельное применение без `wait`/`notify`; сырых блокировок в чистом L3 нет.
