1. Строковое имя (вопрос 4): автор прямо дал name := "test" и name: "test" в LMX_blog/2026-11-09.md:62. Грамматика RU §6:132–136 различает строковый литерал и точный идентификатор; границы кавычек не входят в значение строки. В этом примере имя F — test, без синтаксических кавычек. Сохранение исходного токена целиком как имени-слова — ограничение/ошибка реализации, нового решения автора не требуется. Декодирование строк и интернирование полученного имени должны следовать общему механизму значений/контракту имени, а не специальному срезанию кавычек внутри fn; точный идентификатор и реально присутствующие в значении кавычки не смешивать. Пустой return () из цитаты сохраняется, его нельзя подменять int.

2. Именованный оператор в merge (вопрос 3): фраза книги :1219 относится к БЕЗЫМЯННЫМ операторам. Она не утверждает, что каждый оператор обязан быть безымянным. По текущему общему представлению Frame y: y + x именован y; внутри него y+x — безымянное выражение. Это различает kernel RU §3.3:380–386. Поэтому одна эта цитата не даёт оснований принудительно дописывать такой Frame мимо одноимённого слота модели или делать ветку для body/функций. Действуют обычные соответствие полей и допуск записи (:1215); сохранённое описание выражения не становится int только по совпадению имени, и merge не должен исполнять тело ради такого допуска. Твой q-a — не положительный пример :1223: в примере guide:10–21 у add тело return: x + y, без оператора y: y+x, конфликтующего с модельным y. Установленного противоречия норм для передачи автору здесь нет; числовой код текущего отказа не объявляю нормой языка. Не менять общий merge и не делать все операторы безымянными только ради q-a.

3. Форма return (вопрос 5): исходный Frame именованной подачи может держать структурную оболочку своей записи. Но после общего потребления фактическое требование return не должно менять смысл лишь из-за позиции, name: ... или name := ...; книга :426 и авторские общие формы :62/:70–71. Если передано одно и то же требование @: c.FILE, итоговый контракт должен быть тем же. Промежуточное удержание исходной формы допустимо, само по себе оно не доказывает равенство контрактов; постоянную лишнюю оболочку у результата нельзя обосновать удобством helper/C-типа. Нормализация/приём — общие, без особого unwrap для fn, без [int], без автоматического разворачивания любой явно вложенной Structure. Пока потребитель поддерживает только int-результаты, прочие формы честно остаются границей реализации, а не новым правилом языка.
