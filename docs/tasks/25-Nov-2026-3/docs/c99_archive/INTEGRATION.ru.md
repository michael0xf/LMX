# Граница между архивом C99 и LMX

## Библиотека предоставляет механизм

Единица отбора — функция, алгоритм, представление данных или протокол с
пригодным для встраивания C API. Система LMX сохраняет управление исполнением,
владением ресурсами, графом объектов, акторами и прикладным смыслом данных.
Наличие `main()` в отдельном upstream-примере не превращает библиотечное ядро
в обязательное приложение. CLI, демонстрации и чужой сервисный lifecycle
не включаются в API как основа архитектуры LMX.

| Механизм | Роль в системе |
|---|---|
| llhttp | Разбор HTTP; приём соединений и исполнение запросов организует LMX |
| SLJIT | Генерация машинного кода; самостоятельный язык Perl для этого не требуется |
| PCRE2 | Специализированное сопоставление регулярных выражений; самостоятельной языковой среды не создаёт |
| JSON reader/writer | Обмен представлениями данных с существующими сервисами |
| PDF/TIFF/MAT I/O | Доступ к внешним документам и массивам в пределах конкретного принятого профиля |
| FatFs/littlefs/SPIFFS | Представление файлов на носителе и вызов предоставленных приложением операций I/O |
| FlashDB | Чтение/запись собственного секторного KV/time-series представления; смысл записей задаёт LMX |
| SQL/запросы внешней БД | Специализированная операция над внешним представлением/сервисом; не замена языка LMX |

Таблица описывает назначение механизмов. Наличие конкретного формата в
проверенной сборке сверяется по [каталогу](CATALOG.ru.md) и
[матрице форматов](FORMAT_MATRIX.json), а не выводится из этой схемы.

## Внешние форматы не определяют LMX

JSON, XML, YAML, TOML и INI рассматриваются по реальному потребителю.
Использование формата внутренней зависимостью библиотеки допустимо.
Вводить за счёт него ещё один способ определения самого LMX не требуется.
Бинарные научные форматы рассматриваются по тем же техническим критериям:
читатель/писатель, C99, переносимость, лицензия, зависимости и размер профиля.
Объём сохранённых с их помощью данных не равен размеру реализации.

Альтернативные библиотеки сохраняются: разные API, зависимости, особенности
алгоритма и требования к памяти позволяют выбрать рабочий путь в имеющейся
среде. Совпадение названий задач не означает тождество возможностей.
Например, декодер baseline JPEG, progressive JPEG reader и универсальный
контейнерный parser имеют разные границы.

## Общие неизменяемые определения

Для ветвей LMX с `independent: immutable:` при создании актора переносится
**ссылка на общий объект**. Сам CODE и неизменяемые DATA не размножаются в
аренах акторов. Размер полного каталога библиотек нельзя умножать на число
акторов как расход таких определений.

Отдельный вопрос — изменяемое состояние нативной C-библиотеки: контексты,
рабочие буферы, файловые handles, callback-данные и C globals. Им необходимо
задать владельца и срок жизни независимо от того, как разделяется код LMX.

| Пример | Значимое состояние |
|---|---|
| libfixkalman | Статические рабочие матрицы и caches; вызовы сериализуются даже между разными фильтрами |
| lwIP `NO_SYS` | Один последовательный владелец raw stack, таймеров, списков интерфейсов и pools |
| Fusion, PID | Контексты у вызывающей стороны; последовательный доступ к одному экземпляру |
| libcanard, coreMQTT, nanoMODBUS | Контекст соединения/узла, transport/time callbacks и правила жизни buffers |
| liblsoda | Контекст решателя; рабочая память плотной матрицы зависит от размерности задачи |
| ERFA | Большинство функций используют переданные данные; изменение общей leap-second table сериализуется |
| FlashDB | Контекст БД/сектора, I/O и locking; C99-адаптер typed callbacks описан в своей группе |

## Будущие L3-обёртки

Текущая поставка даёт нативные библиотеки, профили и примеры вызова. Она не
выдаётся за уже внедрённые функции L3 или новую спецификацию языка. План
прежнего LMX-каталога обновляется отдельно; документация спецификации LMX
остаётся первичной для семантики.

При обёртывании конкретного API нужно закрепить представление входных данных,
длины/формы массивов, владение результатом и штатное освобождение, состояния
ошибки, порядок callback-вызовов и требования к сериализации. Нельзя
автоматически считать каждый экспортируемый внутренний C-символ публичной
функцией L3. Например, внутренний `Add` matio префиксован при сборке, поскольку
такой же символ уже экспортирует NNoM; публичные `Mat_*` API сохранены.

Аналогичный конфликт обнаружен между встроенным в Zstd `divsufsort-lite` и
самостоятельным libdivsufsort: два одинаковых экспортируемых имени имели
разные сигнатуры. В сборке Zstd внутренние `divsufsort` и `divbwt` получили
префикс `lmx_zstd_` через PRIVATE compile definitions. Обе реализации
сохранены, публичные API не изменены. Пример
[`suffix_zstd.c`](../../third_party/lmx_c99_compact/examples/archive/suffix_zstd.c)
проверяет совместную линковку, suffix array/BWT и Zstd roundtrip.

Побитовые и текстовые конвертеры выбираются по смыслу данных. Пропуск точного
целого или decimal через `double` ради единой формы JSON может потерять данные.
И наоборот, наличие CBOR bigfloat/decimal tags даёт представление числа, но
не сам вычислительный backend для нового примитива.
