# Уточнение автора: два `merge` — запись с присваиванием и форма объявления

Дата записи: 2026-11-17. Источник: сообщение автора в диалоге с исполнителем (сессия fable_pc) в ответ на
отчёт о подготовке графового круга. Цитата дословная, с авторским написанием; программы, варианты и
редакционные правила стоят вне цитаты. Действующая норма — в [семантике](../docs/LMX_semantics.ru.md).

<a id="merge-two-forms"></a>
## 1. Два `merge`: `struct := merge …` и `struct: merge: …`

Первая фраза сообщения, взятая автором в кавычки, — слова исполнителя из отчёта. Они относились к копированию
внутри `merge`: что копировщик делает со словом, стоящим внутри копируемой Structure (например, в операнде
объявления `@: p Model`), а не к аргументам самого `merge`.

Сообщение автора:

> "Слово, называющее место, остаётся словом — в роли кода оно может означать локал вызова. " -- то есть для аргументов ресивера merge ты различаешь их роль в code и их роль в data? Не знаю вносили ли мы вообще merge  в ресиверы объявления которые выполняются  в data при их вызове. То есть я просто не упоминал его. Но мысль у тебя здравая -- merge полезен в  data. Только  давай тогда сделаем явное различие , фактически два разных merge, которые различаются  наличием присваивания  слева , то есть struct := merge arg arg2() #внутри всё как в code, но в data у нас присваивания игнорируются(только при заполнения переданными аргументами, скажи если сделали не так), а форма struct:  merge: arg() arg2  # в code это вызов struct,  а вот в data -- объявление по общему правилу

Исполнитель записал своё чтение с наблюдаемыми вариантами ([ответы](q/fable-self-answers-20261110.md), Р43) и
спросил об одном: как в данных читаются аргументы формы `S: merge: A B()` — (а) как код, `B()` — вызов `B`;
(б) по роли данных, `B()` объявляет Structure `B`, ничего не вызывается. Своим чтением он назвал (а).

<a id="merge-data-form-no-calls"></a>
## 2. Ответ автора: в коде `merge` — ресивер и без присваивания; в данных — названная форма, внутри вызовов нет

Ответ автора на этот вопрос:

> То есть даже без поисваивания в роли code это ресивер где аргументы ведут себя как code, а вот для data нужно обязательнто назвать объявляемую структуру , как обычно через двоеточие, и тогда внутри такого merge _нет вызовов_, только объявления структур. Тогда этт будет общее првеление

Ответ — вариант (б); чтение (а) исполнителя снято. Норма — в [семантике](../docs/LMX_semantics.ru.md#merge-two-forms).

<a id="merge-forms-confirmed"></a>
## 3. Подтверждение автора: в коде форма — вызов `struct` с результатом `merge`; в данных в `merge` уходят Structure без вызовов

Исполнитель записал норму обеих записей и сообщил её автору. Ответ автора:

> Да, в data форма struct: merge args() args2() # ничего не вызывает. В роли  code форма даже без присваивания это вызов  merge с обычными аргументами как code. То есть struct: merge args1() args2() #в code делает вызов struct с аргументом который вернул merge с аргументами в роли code, в данном случае два вызова. В data же это всё объявления и в merge уходят структуры без вызовов.

<a id="nested-receivers-not-executed"></a>
## 4. В данных исполняются только корневые ресиверы объявлений; чем `Имя: merge: …` отличается от `int: a 1`

Следующее сообщение автора, после того как исполнитель записал подтверждённую норму:

> Так мы сохраним единообразие -- вложенные ресиверы объявлений в data тоже не выполняются, только корневые. Отличие от int: a 1 #тут в том что  merge возвращает структуру а не переменную и поэтому он разрешен в форме name: merge args, а вот a: int: 1 формы объявления примитива "a"  у нас давно нет, сейчас это либо структура  "a" в data либо вызов "a" в code с аргументом 1, проверенным как int

<a id="path-reads-no-execution"></a>
## 5. Явный путь ничего не исполняет: `struct\field` и `data\field` дают запись объявления

Сообщение автора после разбора исполнителя о `sys\toLmx` ([запись](../steps/tolmx-receivers-20261117.md)).
Техническая выдержка; организационная фраза в конце сообщения опущена.

> Я думаю что я допустил ошибку в правилах обращения к полям. struct\field  и data\field видимо не должны делать вызов f() если объявление int: field f() . Эта скрытая форма вызова -- ненужный костыль. Примитив мы можем точно восстановить только по самому значению, то есть если "int: field 5" то мы это в toLmx легко восстановим и поэтому struct\field тут просто 5 типа int. А вот "int: field f()" это просто структура в случае обращения к ней через struct\field или data\field. То, что call заполняет свой namespace прт struct в роли data , к этой форме обращения отношения не имеет! Соответственно и data\struct не выполняет никакого merge если struct записан как  struct: merge args! Тогда toLmx и самомодификация работают без костылей. А то что call подготавливает данные при обращении к ним -- так это его работа. Изучи этот вопрос и если нет возражений внеси это изменение--упрощение везде в доки и в план  v3

Решением снято правило от 2026-11-15 об адресе вычисляемого поля ([журнал](2026-11-15.md#m14-address-scope)) и
чтения исполнителя, которые на него опирались (Р45 в [ответах](q/fable-self-answers-20261110.md)).
