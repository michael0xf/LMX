# Array в выражениях: поэлементность, depth операции и индексные операции

Эта глава описывает Array-часть полной нормативной [тензорной спецификации](TENSOR_EXPRESSIONS.md). Записанные тела операторов разбираются по [грамматике bracket-subparser](BRACKET_SUBPARSER.ru.md); выражения, имена, роли и обход живого графа сохраняют общие правила. Это документация и требования к реализации, а не заявление о завершённой поддержке production-парсером или исполнителем.

## 1. Значения, типы и выбор метода

Обычная Structure является Array типа `[]@`. Она участвует в Array-операциях с действительными типизированными записями элементов; наличие ссылок или имён полей её не исключает. Если конкретный метод не умеет складывать, умножать или иначе потреблять конкретные элементы, диагностируется это применение, а не запрещается весь тип контейнера. Текст также остаётся Array своего символьного типа. Методы целого текста и целого объекта сохраняют собственные правила потребления.

Заголовок Array остаётся `parent/length/storage`. TypeRef непосредственно указывает на канонический неизменяемый дескриптор типа. Тип задаётся полным нормализованным объявлением слева: `[2][3]int` хранит форму `(2,3)`, а `[][]int` — две оси с неуказанными длинами. Строки инициализатора проверяют прямоугольность и уплощаются, но не специализируют `[][]int` скрыто. Операция получает размеры из actual-типа, однозначно выводимой информации и доступного контекста доступа экземпляра. Недостаток необходимых размеров диагностируется; плоские операции, которым они не нужны, остаются допустимыми.

Системный parent предоставляет полный дескриптор/контекст экземпляра, включая источник и карту доступа View, когда они нужны. Он строится обычными шаблонами Structure и copy/merge. Дополнительное поле заголовка LMX и вторая система типов не вводятся. Равенство length и capacity устраняет необходимость дополнительной информации о резерве, но не запрещает parent-контекст для доступа или времени жизни. [Хранение](ARRAY_STORAGE.ru.md) различает тип, capacity и контекст экземпляра.

Ссылки и обычная идентичность графа сохраняются. `struct[i]\[j]` — обычный путь доступа по индексам, а не свидетельство дополнительной плоской оси. Structure с Array-полями может потребляться принимающим их методом, но произвольные вложенные поля и первый элемент не устанавливают прямоугольную тензорную форму.

Результат собирается под полным объявленным/вычисленным требованием. Плотный результат с постоянными размерами сохраняет их в этом требовании либо в явно определённом контексте доступа. Результаты разной формы могут собираться в обычную Structure. Пустой результат использует объявленный договор: фиктивная первая ячейка для угадывания типа не вызывается.

## 2. Обычные операции поэлементны

| Обычная форма | Договор для Array |
| --- | --- |
| `A + B`, `A - B`, `-A` | Соответствующая скалярная арифметика для каждой допущенной ячейки |
| `A * B` | Поэлементное умножение; не скрытое скалярное или матричное произведение |
| `A / B`, `A % B`, `A ** B` | Соответствующая скалярная операция со своими типами и областью определения |
| `A = B`, `A != B`, сравнения порядка | Поэлементные предикаты с объявленным типом результата |
| Побитовые, сдвиговые и логические методы | Их допущенные поэлементные договоры с сохранением востребованности и ролей |
| `A := B` | Обычное поэлементное присваивание реальным местам |
| `slice .: source` | Отдельное присваивание срезу с транслированием RHS |

Формы/frame перебираемых Array совпадают точно. Скаляры не добавляют осей и могут передаваться в каждое применение, если метод их допускает. Array длины один остаётся Array и не растягивается скрыто. Деление, переполнение, допуск результата, сравнение и короткое замыкание не заменяются общей арифметикой machine double.

```lmx
[2][2]int: A [1 2; 3 4]
[2][2]int: B [5 6; 7 8]
@: components A * B
# [5 12; 21 32]
@: matrices A [*] B
# [19 22; 43 50]
@: mask A > 2
# [0 0; 1 1]
```

`=` — равенство, `^` — XOR, `**` — степень. У степени `sys\priority("**") = 131` и производный минимум RHS `131`: `A ** B ** C` группируется как `A ** (B ** C)`. То же связывание имеют `.(depth)**` и `[**]` с последующим допуском типов и форм каждого метода. `**=` сохраняет приоритет присваивания. [Числовой вывод](EXPRESSION_ALGORITHM.md#power-priority). Общих алиасов `.op`, `..op`, `...op` больше нет. Ресиверные имена в обратных кавычках точны; параллельное семейство dotted-имён не создаётся.

### 2.1. Array непосредственно в выражении

В роли VALUE `[items]` конструирует один безымянный свободно типизированный `[]@` через общий P0. Это один явный Array VALUE, а не безымянная группирующая вершина для раскрытия. Элементы получаются в обычном порядке востребованности; первый элемент не выбирает плотный примитивный тип. Типизированный конструктор `[]int: [10 20]` сразу использует объявленное требование к элементам.

```lmx
int: a 1
int: b 2
int: d 4
@: result a + b + [10 20] + d
# [17 27], группировка ((a + b) + [10 20]) + d.

@: arr0 [1 2]
@: arr1 [10 20]
@: arr2 [100 200]
@: totals arr0 + arr1 + arr2
# [111 222]
```

`[arr2]` содержит одну целую ссылку arr2. Она не копируется, не уплощается, не запрашивает broadcasting и не получает дополнительного обещания мерности. Метод получает действительный элемент по своему договору. Типизированный прямоугольник `[2][2]int: [1 2; 3 4]` строит одно плоское хранилище и проверяет одинаковые длины строк. Формы `[1 2; 3 4]` и `[[1 2] [3 4]]` допустимы внутри такого конструктора.

Убирать конструирование или промежуточное хранилище можно только с сохранением идентичности, времени жизни, скалярных типов, востребованности и порядка отказов. Наличие inline Array само по себе не разрешает reassociation, FMA или опережающее вычисление следующих вхождений.

## 3. Depth и удержанные аргументы

`.(expression)op` передаёт **глубину одного внешнего обхода**. Положительное d проходит d внешних логических осей; явный ноль означает максимальную глубину. Для Array ранга K положительное d требует d≤K и оставляет K−d осей в ячейке. Depth 0 достигает элементов этого Array. Исходные скаляры и явно удержанные actual осей не приобретают. Это не rank ячейки и не номер оси редукции.

Custom-операнд получает объявленный int depth и может определить собственный смысл. Ограничения стандартного Map, включая неотрицательность и depth>K, применяются только при выборе этого профиля, не глобально ко всем методам.

Отсутствующий depth сохраняется и выбирает default метода. Обычная арифметика по умолчанию максимально поэлементна. Whole-матричный метод без модификатора получает целые входы; явный ноль, напротив, требует максимального обхода. Эти случаи нельзя глобально отождествлять.

```lmx
@: cells A .(0)* B
# [5 12; 21 32]
@: explicitCells A .(2)* B
# [5 12; 21 32]
@: rowDots A .(1)[*] B
# [17 53]
@: wholeProduct A [*] B
# [19 22; 43 50]
```

Здесь используются двумерные A и B выше. После выбора ячеек обвязка вызывает **базовое тело без повторного автоматического Map**. Поэтому `A .(1)* B` не отображает строки заново и не превращает их в dot: скалярный базовый `*` диагностирует такие входы, если для него не объявлен отдельный whole-cell допуск. `A .(3)* B` ошибочно: трёх внешних осей нет. `A .(0)[*] B` также требует отдельного допуска скалярных ячеек базовым product-handler; нормальная whole-форма записывается без модификатора.

Явное depth-выражение получается один раз по востребованности в исходном контексте, не при группировке, расчёте приоритета или поиске кандидатов. Общий транспорт — left/depth/right, отсутствие left сохраняется. Эквивалентность prefix/infix устанавливает сам метод операнда.

`$x` или `$(expression)` удерживает actual целиком для текущего обхода, получая один раз без копирования. Для Z `(rows,cols)` и bias `(cols)` запись `Z .(1)rowAdd $bias` передаёт строку и весь bias. Объявленный rowAdd может явно написать обычный `+` в теле; обвязка не добавляет второй Map автоматически. При depth=0 передаётся один элемент Z и весь bias, никогда не скрытый bias[j].

Frame перебираемых Array совпадают точно. Нулевая длина frame не вызывает ядра. Пустой кортеж frame означает один вызов. DATA, TYPE, RAW, NAME, PLACE и void сохраняют объявленные роли. Внутренние оси `.(d)[op ...]` адресуют оставшуюся ячейку. Полный договор — в [depth операции](OPERATOR_DEPTH.ru.md).

## 4. Общие индексные операции и матричные договоры

`[op rules]` — одно общее семейство. Обычная конфигурация LMX задаёт скалярное/ячеечное ядро, необязательный редуктор, начальное состояние, сборку результата, численные настройки и доступ. Это структуры и ссылки на методы, а не новый реестр options и не автоматическая реализация алгоритмов.

| Правило | Смысл |
| --- | --- |
| `i:j` | Общая координата с редукцией; длины осей равны |
| `i=j` | Общая сохраняемая координата; равные длины без растяжения единицы |
| `i*j` | Независимые координаты объединяются в ось длины `dim(A,i)*dim(B,j)` |
| Неупомянутая ось | Свободная независимая ось результата |
| `-> positions` | Перестановка позиций канонического списка выходных осей |

Каждая входная ось участвует не более чем в одной связи. Канонический порядок: оси `=` по порядку правил, составные оси `*` по порядку правил, свободные A, свободные B. В перестановке каждая выходная позиция встречается ровно один раз. Явные правила отключают автоматическое достраивание batch. Одни options не создают список правил.

```lmx
@: matrix A [*] B
@: outer A [* ()] B
@: sums A [+ ()] B
@: shortest A [+ 1:0; reduce := min] B
# [6 7; 8 9]
```

Отсутствие правил выбирает default метода; явно пустой список не связывает ни одной оси. Поэтому `A [*] B` — автоматическое матричное умножение, `A [* ()] B` — внешнее произведение, `A [+ ()] B` — сложение независимых пар. Бинарная свёртка использует отдельно выбранный редуктор: один знак `+` не означает min-plus. При отсутствии редуцируемых осей default редуктора/состояния не используется, identity не получается; явно переданный неподходящий actual reduce диагностируется.

Унарная арифметика отличается от геометрических форм `[*]`:

```lmx
[2][3]int: M [1 2 3; 4 5 6]
@: rowSums [+ 1:] M
# [6 15]
@: rowProducts [* 1:] M
# [6 120]
@: traceValue [+ 0:1] A
# 5
@: diagonalProduct [* 0:1] A
# 4
@: diagonal [* 0=1] A
# [1 4]
@: transposed [* -> 1, 0] M
# [1 4; 2 5; 3 6]
```

Тип результата ядра, тип состояния накопителя и конечный тип независимы. Identity — нейтраль состояния, а не переименование произвольного seed. Начало с первого элемента требует допуска в состояние. Каждый изменяемый накопитель независим. Пустой identity/seed проходит через finish. Min/max сохраняют первую выбранную типизированную запись при равенстве. Параллельное вычисление требует реальных алгебраических и численных разрешений, включая переполнение, NaN, signed zero и округление.

### 4.1. Матричные операции над целым объектом

| Операция | Договор целого объекта |
| --- | --- |
| `[+]`, `[-]` | Сложение/вычитание матриц; унарный `[-]` — противоположная матрица |
| `[*]` | Автоматическое векторное/матричное произведение либо явная индексная свёртка |
| `[\]` | Левое решение `A X = B` |
| `[/]` | Правое решение `X B = A` |
| `[**]` | Целая матричная степень по выбранному численному договору |
| `[=]`, `[!=]` | Один результат равенства/неравенства матриц целиком |
| `inv`, `transpose`, `adjoint` | Обращение, транспонирование, сопряжённое транспонирование |
| `det`, `trace`, `rank`, `norm`, `cond` | Характеристики целого объекта с заданными соглашениями |
| `lu`, `qr`, `cholesky`, `eig`, `svd`, `schur` | Структурные результаты разложений и спектральных действий |
| `pinv`, `nullspace`, `leastSquares`, `kron` | Явная псевдообратная, базис ядра, МНК и произведение Кронекера |
| `math\linear\exp`, `log`, `sqrt`, `sin`, `cos` | Матричные функции в указанном пространстве имён |

Скалярные `/`, `~` и `!` не угадывают обращение. Solve не является индексной редукцией скалярных делений. Real/complex, прямоугольные и сингулярные входы, tolerance, пустые формы, ветви, изменения и отказы определены отдельно в [полной матричной главе](TENSOR_EXPRESSIONS.md#matrix-contracts). В том же документе сохранён весь каталог из 529 записей; присутствие в каталоге или будущий импорт не означает готовую реализацию.

## 5. Присваивание, срезы и перекрытия

`destination := source` сохраняет обычное поэлементное присваивание. Назначение получается один раз. Формы Array совпадают точно; допущенный скаляр может заполнять выбранные места. Значения RHS и все допуски назначений устанавливаются до записи. Группа мест не копируется в чужие переменные:

```lmx
int: a 1
int: b 2
int: c 3
(a b c) := (b c a)
# a=2, b=3, c=1
```

`(a b c) := copy(d)` использует существующее потребление группы/потока полей; лишние скобки не нужны. Общего раскрывающего прохода после вызова не добавляется. Готовый Array назначения сохраняет длину, форму и идентичность. Объявленный ссылочный PLACE сохраняет отдельный обычный допуск присваивания ссылки; реальные области строки/плоскости не получают фиктивных pointer-слотов для переназначения.

`slice .: source` транслирует RHS до уже выбранной формы назначения. Оси RHS выравниваются справа, недостающие ведущие оси считаются единицами; каждая длина источника равна целевой либо единице. Единица может расшириться до нуля; ноль не расширяется до положительной длины. Назначение не изменяет размер.

```lmx
[2][3]int: matrix [0 0 0; 0 0 0]
[3]int: row [10 20 30]
[2][1]int: column [100; 200]

matrix[:][:] .: row
# [10 20 30; 10 20 30]
matrix[:][:] .: column
# [100 100 100; 200 200 200]
```

`matrix[:][:] := row` — ошибка формы. `matrix[:][:] .: [1 2]` — ошибка broadcasting. Плоский `matrix[:]` имеет одну выбранную ось; цепочка `matrix[:][:]` сохраняет две выбранные оси. Broadcasting определяется формой PLACE-среза, а не одним видом знаков.

### Depth в присваивании срезу

В `.(N).:` имя остаётся **depth**; rank — число осей полученного целевого среза. Для `(2,3,4)` положительный depth=1 выбирает `(3,4)`, depth=2 — `(4)`, а 0 означает максимум и отдельные места. PLACE-профиль сначала строит единую карту broadcasting RHS до **полной исходной формы назначения**, затем depth определяет гранулярность обхода подготовленных мест. Generic exact-frame VALUE Map к сырым RHS-формам не применяется. RHS `(4)` поэтому допускается для `(2,3,4)` при depth 0, 1 и 2; ограничения форм и сама карта не меняются. Подготовленные scalar places при depth=0 не становятся ошибкой «не срез». Broadcasting внутри ячейки дополнительно не запрещается. Snapshot всех нужных RHS сохраняется до первой записи по всему frame.

Оба договора используют общие подготовку, snapshot, допуск и запись. При перекрытии берутся значения RHS до записи; broadcasting не требует развёрнутого RHS размером со всё назначение. Повторные физические адреса назначения требуют явно поддержанного детерминированного scatter/reduce, иначе отвергаются. Составное присваивание получает назначение один раз, вычисляет соответствующим базовым оператором и использует тот же writer. Префиксные/постфиксные обновления сохраняют обычные правила результата и снимка прежних значений.

VALUE-срез сохраняет обычный договор новой выборки, если View не выбран явно. PLACE-срез даёт реальные ячейки на время операции. Изменение длины диапазона остаётся отдельным replace/splice. Прямой отрицательный Array-индекс недопустим; для обоснованной относительной адресации используется указатель. [Срезы и тернарное выражение](TERNARY_AND_SLICES.ru.md) задают defaults и границы checked/native.

## 6. Минимальный fuse и граница реализации

```lmx
@: scores fuse(2 * left + right * right)
@: mask scores >= limit
return: compress(scores; mask)
```

`fuse` потребляет RAW Expression. Начальная гарантия охватывает Scalar и Map→Map с новым окончательным результатом без материализации промежуточных Array-результатов. Сохраняются поддержанные карты чтения, actual-типы, численные границы, востребованность и наблюдаемый порядок отказов. Матричные произведения, редукции, произвольные callbacks, потоковая запись и все карты View автоматически не допускаются.

`destination := fuse(expression)` и `slice .: fuse(expression)` сначала получают окончательный новый результат, затем выполняют обычное присваивание. Поздняя арифметическая ошибка не оставляет записанный префикс лишь из-за появления fuse справа. [Fusion](FUSION.ru.md) определяет точный минимум и диагностику неподдержанного плана.

<a id="implementation"></a>
Подготовка выбирает actual-методы, роли, полные требования к результату, размеры и карты доступа. Обычные структуры/шаблоны и copy/merge передают настройки и parent-контекст; исполнитель обязан реально их читать и поддерживать. Граф остаётся живым: расширенной копии программы, второго пространства имён и eager-вызовов при поиске кандидатов нет.

Ошибочный depth, недостаток нужных размеров, несовместимые формы, неверные правила осей и неподдержанный план — диагностика транслятора, если известны заранее, иначе интерпретатора при достигнутой операции. Пользовательские выражения, скалярные методы и внешние библиотеки сохраняют прежние throws. Списки ошибок копируются из действительных базовых методов, не из вымышленных dotted-алиасов.

[Host-модель договора](tools/array_expression_reference.py) и [проверки](tools/test_array_expression_reference.py) проверяют выбранные договоры, но не являются production-реализацией LMX. Поддержка парсером, транслятором и runtime остаётся **NOT_RUN** до проверки средствами проекта. Ускорение и импорт библиотек обязаны сохранять полный выбранный договор.
