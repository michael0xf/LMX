## Q14. Регион обработчика: какие вызовы достигает `catch`

### Контекст

Ваше правило (Q11, уточнение): `catch` может стоять до вызова, после вызова или отдельным вложенным блоком; единственное ограничение — два одноимённых `catch` не могут спорить на одном уровне. Это уже внесено в книгу семантики §14 вместе с дословным старым примером `tests/t2.lmx`.

При переносе Opus нашёл расхождение между **текстом** старой спеки и **старым кодом** (оба — `lingvamyxa_prev`):

- **Текст** (старая спека 19.11.3, дословно перенесено в §14): «После завершения тела `catch` исполнение продолжается в том же блоке с операторов после этого `catch`. Эти последующие операторы, **до следующего `catch` в том же блоке или конца блока**, — участок, который повторно вводится или пропускается в зависимости от того, где `catch` написан… Доставка выбирает обработчик по блоку, из которого вызван бросающий executable, а не одноимённый `catch` соседнего блока».
- **Код** (`lm2/trans_l1_namespace.lm2`, `catch_find` ~:1899; `lm2/trans_l1_statement.lm2` ~:14240-14290, ~:12641): все `catch` блока регистрируются до эмиссии операторов; при вызове поиск обработчика идёт по стеку обработчиков **изнутри наружу** — вызов внутри вложенного `if`/`while`/`---` внутри блока достигает `catch` **внешнего** блока; дубликаты отвергаются только на одной глубине (~:1921); после обработчика код проваливается в остаток блока.

То есть текст читается как «обработчик ловит только вызовы, стоящие прямо в его блоке», а код — «обработчик ловит и вызовы из вложенных операторных блоков внутри своего блока».

### Минимальная программа

```
fn: parsePositive (int: n) int
    throws: NonPositive
    if: n <= 0
        throw: NonPositive(n)
    return: n
end: parsePositive

fn: caller (int: n) int
    int: value 0
    if: n != 7
        value: parsePositive(n)      # вызов ВНУТРИ вложенного if
    ---
    catch: NonPositive (int: bad)
        return: 0 - bad
    return: value
end: caller
```

Вызов `parsePositive` стоит внутри `if`, а `catch: NonPositive` — на уровне тела `caller`, после `if`.

### Варианты

- **T — строго по тексту.** `catch` на уровне тела `caller` ловит только вызовы, стоящие прямо в теле `caller`. Вызов внутри `if` им не покрыт → по §14 «вызов без `catch` или `throws`» — **ошибка трансляции**; чтобы обработать, нужен `catch` внутри того же `if`-блока (обёртка на каждом уровне вложенности) либо `throws: NonPositive` у `caller`.
- **K — как в старом коде.** Обработчик ловит вызовы из вложенных **операторных** блоков (`if`/`while`/`for`/анонимный `---`) внутри своего блока — поиск от внутреннего блока к внешнему, соседний блок по-прежнему не ловит, дубликаты запрещены только на одном уровне. Программа выше валидна, `caller(-4)` = 4.

### Следствия

- T: проще транслятору (таблица «статус → pad» только для прямых вызовов блока), но каждый вызов внутри `if`/`while` требует своего `catch` или `throws` — для `merge` внутри `Model: fresh` в цикле это означает `catch: merge` в теле цикла.
- K: одна таблица на вложенную цепочку блоков; landing pad внешнего блока достижим из вложенного — при структурном понижении (`while: 1` + селектор) каждый промежуточный цикл получает `if: l2_pad != 0 → break`, что транслятор знает статически; повторный вход «до вызова» из вложенного блока тоже определён (регион внешнего блока).
- Текст §14 нужно уточнить в любом случае: сейчас он допускает оба чтения.

### Кто ждёт

Opus (S1, `FABLE-OPUS-S1-CATCH`): таблица диспетчеризации статусов и форма landing pads зависят от ответа.

### Рекомендация

**K** — иначе вызов внутри `if` нельзя обработать без обёртки на каждом уровне, а старый код (единственная работавшая реализация) делал именно K. Формулировка для §14: «обработчик действует на все вызовы своего блока, включая вложенные в него операторные блоки; блок-сосед не покрывается; два одноимённых обработчика на одном уровне — ошибка».

## Q15. Запись поля типа «массив ссылок на массивы» (тип письма с аргументами)

### Контекст

Ваш Q10: аргументы процесса кладутся **внутрь письма**, в поле `mainArgs` — массив строк ровно как пришли из C; программа берёт письмо ресивером `nextMessage:` и читает `m\mainArgs[i]` обычными путями. Представление в ядре согласовано (Opus, S3): `mainArgs` — Array ссылок (`LMX_TYPE_ARRAY_OF_DESC`) на char-Array'и (`LMX_TYPE_ARRAY_OF_CHAR`), каждый с завершающим NUL, всё в арене письма; письмо — Structure (`parent = 0`) с одним слотом. Чтение: `m\mainArgs` — массив, `m\mainArgs[k]` — char-массив, `m\mainArgs[k][j]` — char, `@ m\mainArgs[k][0]` — валидная C-строка (по L2 §18.2 `@array[i]` — адрес элемента в графовом хранилище), `length(m\mainArgs)` = argc.

Проблема: чтобы тип письма был **обычной объявленной Structure** в стандартном prelude/predef (тогда `m` — типизированное значение, его можно передать методу как формал, а транслятор проверяет пути по объявлению), нужен спеллинг поля, чьи элементы — ссылки на char-массивы. Opus проверил `docs/LMX_semantics.*`, `docs/L2_spec_*`, `docs/LMX_grammar.*`, `lingvamyxa_prev/Lingvamyxa_spec.txt` и `l1.txt`:

- `char: []: s "hello" "world!"` (старая 9.1.1) — массив **char-ячеек** («`data` указывает на непрерывный блок символьных ячеек»), не ссылок на массивы;
- `String: []: s …` — массив **ссылок на `String`**, но `String` спека отделяет от `char *`, и в L2 его нет;
- `[][]: x` (грамматика :652) — **прямоугольный** двумерный массив; спека прямо говорит, что «массив ссылок на массивы — другое значение, не замена» (semantics :85, :513);
- композиция ресиверов справа налево (старая 9.1.1: «тип/элемент … и конструкторы Array — обычные головы-ресиверы») подсказала бы форму вроде `char: []: []: mainArgs`, но **такой записи нет ни в одном тексте** — Opus её не выдумывал.

### Минимальная программа (объявление типа письма и его использование)

```
MainLetter:
    <как объявить поле mainArgs: массив ссылок на char-массивы?>
end: MainLetter

fn: firstArg (MainLetter: m) @: char
    return: @ m\mainArgs[1][0]
end: firstArg

nextMessage: m
if: length(m\mainArgs) != 2
    return: 1
if: c.strcmp(firstArg(m), "ok") != 0
    return: 1
return: 0
```

### Варианты

- **(a)** Композиция ресиверов: `char: []: []: mainArgs` — «массив массивов char по ссылке» (внутренний `[]:` — char-массив, внешний — массив ссылок на них). Требует зафиксировать в спеке, что вложенный `[]:` даёт ссылочные элементы, а не прямоугольный массив (`[][]:`).
- **(b)** `String: []: mainArgs`, если `String` в L2 = char-массив с NUL (тогда `String` — не отдельное значение, а имя этого представления).
- **(c)** Другая запись по вашему усмотрению (например, явный ресивер ссылочного элемента).
- **(d)** Тип письма не объявляется в языке: он задан профилем исполняемой программы (как int-результат точки входа), `m` нельзя передать как типизированный формал, но листья (`@ m\mainArgs[1][0]` как `@: char`, `length`) доступны. Это то, что Opus делает **сейчас как временное**, помечая в `next_core_tasks.md` §8.

### Следствия

- (a)/(b)/(c): тип письма объявляется в стандартном prelude, `MainLetter` — обычная Structure; методы принимают `MainLetter: m`; тот же спеллинг становится доступен любой пользовательской структуре (массив строк, массив массивов).
- (d): временная особая описательная таблица в трансляторе для одного типа — под вашим принципом «никаких исключений» долго жить не должна.

### Кто ждёт

Opus (S3, `FABLE-OPUS-S3-MAIL-ARGS`): C1-часть (чтение `root\field[lit]` через диспетчер) и объявление типа письма.

### Рекомендация

**(a)** как самое общее (композиция уже описана как правило для ресиверов-конструкторов), с явной оговоркой в спеке, что вложенный `[]:` — ссылочные элементы; `[][]:` остаётся прямоугольным.
