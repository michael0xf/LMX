# Представление типов и исполнение одного графа

<a id="type-layout"></a>

## Миграция на TypeRef и геометрия Array

Проверять одну и ту же норму в P0, типизированных записях и у потребителей ABI. [TypeRef и выравнивание](../docs/spec/TYPE_REFERENCES.md) · [Размеры, rank и вектор размеров](../docs/spec/TYPE_DECLARATION_FORMS.md#extent-vector-prefix) · [Разбор инициализатора](../docs/spec/ARRAY_STORAGE.ru.md#shape-inference).

1. Сопоставить с документацией префиксы `[]T`, `[E]T`, `@T`, динамические `[](E)T` и `@(E)T`, их композицию и вложенный индекс в выражении размера. Целое положительное значение `[](E)` задаёт число осей, непустой одномерный массив целых неотрицательных размеров задаёт размеры по порядку. Вычисление в исходном контексте однократно. Ноль как размер отличается от незаданного размера. Подать также `[2]Struct: var`, `Struct[2]: args` и `Struct[2] := value` и проверить три разные операции.
2. Проверить общие требования к форме по примерам ниже, включая неполную и избыточную глубину, совместимые соседние сегменты и отказ смешанной неоднозначной записи до публикации значения. Сохранить обычные ошибки пользовательского вычисления и диагностику переполнения.
3. Перевести потребители `{type value}` на прямую ссылку. Проверить выравнивание для разных payload, готовое значение и `uninit`, плотный массив без префикса на каждую ячейку, порядок полей, GC, walker, перенос и восстановление в другой арене. Сопоставить два значения `[]int` разных длин и после reserve, `typeof(typeof(obj))`, обе перегрузки `descriptor` и сохранение TypeRef готового значения при допуске.
4. Проверить отсутствие обязательной второй записи о резерве и отдельно реальный контекст View с геометрией и удержанием источника. Проверить отказ несовместимого старого ABI.

| Фрагмент | Результат |
| --- | --- |
| `[][3]int: [1 2 3 4 5 6]` | Допустим; форму 2×3 можно вывести из TYPE и length |
| `[][3]int: [1 2 3 4 5]` | Ошибка: длина не делится на 3 |
| `[2][5]int: [[1 2 3 4 5] [1 2 3 4]]` | Ошибка формы строк и размера 5 |
| `[][]int: [1 2 3 4 5 6]` | Допустимое плоское хранение; размеры двух осей неизвестны |
| `[][]int: [[1 2 3] [4 5 6]]` | Допустимо; границы строк проверены, но не записаны в TYPE |
| `[][3]int: []` | Допустимо; выводится форма 0×3 |
| `[2][0]int: []` | Допустимая полностью заданная форма 2×0 |
| `[][0]int: []` и `[0][]int: []` | Допустимо; другая ось остаётся незаданной |

### Исходники и зависимые артефакты

- `spec/patterns/LMX_Fn_Receivers/src/reflection.lmx`: int-результаты reflection,
  `RxTypeCodeBox`, возвращаемый `types` массив и его буфер.
- `src/operation_forms.lmx`, `src/generic_functions.lmx`, `src/kernel_contracts.lmx`
  той же директории: результаты `type`, нормализацию TYPE и сигнатуры provider.
- `spec/patterns/LMX_Fn_Receivers/LMX_Receivers.lmx`: пересобрать из исправленных
  исходников; не исправлять числовую копию отдельно от её источников.
- `examples/sequence_examples.lmx` и `tests/generic_operations.lmx` той же
  директории: различить точное равенство TypeRef и направленный допуск;
  пересмотреть числовые предположения в проверках TYPE.
- `core_catalog/new_primitives/primitive_runtime.*`, `numeric_provider.*`,
  `real_provider.*` и проверки: префикс, выравнивание, аллокацию, registry,
  clone/finalizer, attach/restore и ABI интерфейсов.
- Фикстуры Array, которые раньше ожидали сохранение конкретных осей только
  по строкам `[][]int`: задавать размеры в конструирующем TYPE, либо проверять
  неизвестные оси. Принятый готовый вход с более полным типом сохраняет свой TYPE.

Датированные фикстуры прежнего ABI сохраняют собственные результаты. При переходе сверить новые исходники и реальные маршруты. [Проверка редакции размеров](../docs/spec/validation/array_extents_documentation_20261126.json).

## Интерпретатор, AOT и runtime SLJIT

Общие операции подготовить при переработке ядра. В этот период сборки не включают `third_party`. После полного ядра следует API и MCP на LMX. Собственно runtime SLJIT реализуется на следующем этапе, от одной специализации до заявленного набора операций и ABI. [Общие операции и уровни](../docs/spec/INTERPRETER_AND_NATIVE.md#kernel-before-jit) · [Сервис на LMX](../docs/runtime_server/README.md).

1. При переработке интерпретатора выделить общие правила операций, вызовов,
   мест и выходов, сохранив один программный граф.
2. После приёмки ядра и следующего за ним этапа API подключить SLJIT как отдельный backend явной компиляции. Сначала обеспечить
   небольшое законченное подмножество с корректными вызовами и выходами.
3. Для сложных операций переиспользовать runtime и обёртки; для известного
   нативного вызова сразу выдавать прямой вызов.
4. Добавить управление, локальные значения и прямые операции известных типов,
   проверяя каждый поддержанный случай на соответствие его контракту.
5. Оптимизировать только после измерений на целевой конфигурации.

Проверки будущей реализации должны сравнивать результаты и наблюдаемые эффекты:
ветви и циклы, однократное вычисление места, именованные отказы, порядок очистки,
изменяемые привязки, вызовы `c.*`, общий код у разных акторов и принятие обновлений
после явной компиляции/`endturn`. Сравнение L2 должно учитывать различие
проверяемого интерпретируемого и нативного контрактов, а не объявлять их
безусловно тождественными. Сейчас эти проверки не выполнены: записка не содержит
реализации генератора.

Измерять следует отдельно время генерации, размер машинного кода, пиковую память
подготовки и время исполнения. Генератор с вызовом helper на каждую операцию
может дать небольшой выигрыш или оказаться медленнее на отдельных задачах.
Прямая арифметика и управление обычно являются следующими возможностями
улучшения, но конкретное ускорение требует измерений. При вызове той же заранее
собранной тяжёлой C-библиотеки основная вычислительная работа остаётся прежней.

Целевой результат первой версии — компактный и понятный backend, который
использует уже определённые механизмы LMX, сохраняет их контракт и допускает
постепенное улучшение генерируемого кода.
