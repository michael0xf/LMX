## 1. Многострочная часть `data` в скобках: `end:` и `---` внутри скобок

Факты.
- Грамматика (`docs/LMX_grammar.ru.md`; тот же текст — `provenance/grammar.json`, строки 302, 381): §14 (356) «Внутри
  скобок действуют те же короткие формы, разделители и уровни»; §14 (358), §15 (438, 442) закрыватели не заменяют
  недостающую `)` и не закрывают непарную скобку; §17 (524) закрытие пересекает открытые неявные уровни, но не
  незакрытые скобки; §24 (710) отдельного парсера скобок нет — ограниченная форма есть рекурсивный контекст того же
  автомата. Значит, `end: Имя` и ограда `---` внутри скобок допустимы и действуют на уровни, открытые внутри скобок.
- Измерено (`p0`, образ graph-o16). Внутри скобок: `end: Point` — соседний Frame `end` с атомом `Point` (p01, p04);
  `---` — атомы `--` и `-` (p03); голый `return` — атом (p09); пустой `Point:` с `end: Point` — отказ разбора (ошибка
  P0 32; p10). Вне скобок тот же текст: трейлер `end` у `Point` (p02); `---` кончает блок и узла не оставляет (p05,
  p06); пустой `Point:` с `end: Point` допустим (p12).
- Где. Многострочная скобка — одна логическая строка потока: `lm_p0_find_layout_line_end` (`p0_parser.lm2:956–1066`)
  продолжает строку через перенос, пока скобка открыта. Закрыватели решает только потоковый слой:
  `lm_p0_stream_apply_item_event` (3361–3485; роль 3374, цель 3382–3383, `lm_p0_parse_trailer_item` 3402), ограда —
  событие DELIM (`lm_p0_stream_apply_event` 3534–3549 → `lm_p0_stream_resolve_pending_delimiter` 3283). Содержимое
  скобки разбирает `lm_p0_parse_fields_until_with_layout` (2256–2802): уровни ведёт `lm_p0_skip_field_space`
  (1817–1852; тело короткой формы кончается при `next_level <= short_source_level`), но ни роль трейлера, ни ограда там
  не проверяются — строка закрытия становится следующим полем (голова с двоеточием 2567–2599 или атомы).
- Перепись (`git ls-files`, скрипт глубины скобок): 447 `.lm2` в `selfbuild/src`, `tools`, `tests` — ни одной строки
  `end:` или `---` внутри открытой скобки; многострочные скобки — только в шести моих фикстурах 5б (по одной внутренней
  строке, без закрывателей). Корпус P0 (240 `.lmx`): одна находка — отрицательный
  `tests/parser/imported/01-old-worked/tests/invalid_tail_cutter_does_not_close_parenthesis.lmx` (скобка не закрыта,
  ожидание `5@1:2`); он обязан остаться отказом. Правка не меняет ни одного существующего дерева.

Предложение — правка P0, один файл `p0_parser.lm2`, в цикле полей `lm_p0_parse_fields_until_with_layout` перед началом
поля (2377), когда поле открывает физическую строку внутри скобки (перед ним только перенос, отступ и точки уровня —
новая проверка; строку поглощает `continue` цикла, как ветка блочной строки 2330–2351):
- (а) строка с ролью трейлера (`lm_p0_trailer_role`: `end:`, `until:`, `return`) — цель
  `lm_p0_structure_last_colon_frame` текущей структуры, приём `lm_p0_trailer_role_accepts_target`, затем
  `lm_p0_parse_trailer_item`; строка поглощена. Цели нет — как сейчас (запись `end`), паритет с потоком;
- (б) ограда `---` — значение потока: закрывает вертикальное тело с двоеточием своего уровня без узла (как
  `lm_p0_stream_resolve_pending_delimiter`); если дальше идут строки глубже — открывает безымянную Structure этого
  уровня (§16). Если fable2 решит, что внутри скобок нужна только закрывающая роль, — только (б) без второй части;
- ошибка 32 для пустого `Имя:` + `end: Имя` в скобках уйдёт сама: после (а) пустой Frame получает трейлер, и
  проход `lm_p0_close_empty_by_end_in_node` (4544) снимает его, как вне скобок.

Не входит в правку (паритет с потоком): цель `end:` у непустого блока P0 не сверяет — `end: Other` закрывает `Point`
и вне скобок (p11), хотя §17 (522, 528) называет закрытие проверяемым. Это общий вопрос P0, не скобок (его же ставит
sonnet2).

Проверка правки: новые случаи P0 (профиль `tests/parser/current`), дампы `p0`, фикстура чистого графа — часть `data`
метода с блоком, закрытым `end:` и `---` (снимает мой предел 7 части 1). P0 — машинный модуль обоих трансляторов:
полный bootstrap и полный набор запускает fable2.

## 2. Слово `node`: путь `node\имя`, чтение и запись

Норма. Книга (`provenance/semantics-book.md`): 104 — `node` — лексическое пространство над методом, одно на всю
активацию; `node\field` — явный обход из него; голое `field` из лексического запасного источника — скрытый аргумент,
не то же, что `node\field`. 110 — слово зарезервировано: нельзя объявить, затенить, перепривязать, подать как
одноимённое динамическое значение, в том числе в цитированном написании; при понижении — первый параметр `Lmx *node`;
для вызываемого вхождения над-методное пространство задаёт его `parent`, `parent` вложенных тел `node` не меняют;
запись в голое имя меняет только локальное значение; явное изменение — `node\field := value`. Таблица 114. 971 —
явное чтение `node\x` привязки не создаёт. 977 — `node\x`, `reference\x`, `array[index]` обращаются к графу, не
подменяясь динамическим `x`. 987 — внешнее поле меняется только явной записью через `node\x`, это не обязательно
вызывающий. 1000 — после вложенной записи `node\x` рабочее голое `x` вызывающего может держать прежнее значение;
поздняя запись в голое собственное `x` публикуется на следующей границе. 1395 — у `merge` явный `node\…` обращается к
лексическому контексту непосредственно. Журнал 2026-11-11: `#callable-parts-visibility` — внутренний метод лексически
видит данные объемлющего, но меняет их только через `node\var`; «node не путать с parent»; `#unnamed-structure-not-call`
— `node\field` может менять вовсе не вызывающего.

Рабочий frontend (пробы, boot-f24; режимы native и walk).
- Метод корня единицы: `node\hits` читает поле корня; голая запись `hits := v` его не меняет; `node\hits := v` меняет
  (`wf_root`: 7).
- Одна активация: `x := x + 1; node\x := 30; return: x * 100 + node\x` даёт 1130 — голое `x` рабочее, путь — ячейка
  корня (`wf_local`: 7).
- Метод в именованной Structure: `node` — эта Structure, `Box\setv(8)` через `node\v` меняет `Box\v` (`wf_box`: 7).
- Внутренний метод в коде объемлющего: `node\total` при `total` в части `data` объемлющего — отказ «unknown field path
  segment» (`wf_inner_code`); `node\hits` при `hits` в корне — тот же отказ (`wf_inner_root`); собственное поле
  объемлющего, объявленное в его коде, — «internal: a refusal said nothing» (`wf_inner_code2`); `node\data\total` — тот
  же отказ «unknown field path segment» (`wf_inner_path`). То есть `node` внутреннего метода у рабочего frontend не
  называет ни данные объемлющего, ни само объемлющее вызываемое, ни корень. Голое `total` внутреннего метода читает
  данные объемлющего лексически (`wf_inner_parts`: 7).
- Динамическое против явного: голое `x` вызываемого берёт привязку вызывающего (25), `node\x` — поле корня (10):
  `x * 100 + node\x` = 2510 (`wf_dynamic`: 7) — книга 977.
- Метод, объявленный в части `data` другого метода, — «incompatible entry signature» (`wf_inner_data`).
- Отказы: `int: node 5` и формал `(int: node)` — «node is a word of the language: a program cannot bind it»;
  `node := 5` в методе — «unsupported body»; `node\hits` в корне единицы — «unknown field path root».

Чистый граф (graph-o16). `node\x` — 3 в корне (n01), в методе (n02) и даже в неисполняемой ветке (n03): обход кадра
при входе берёт `node` свободным входом (`lmx_graph_work_scan` → `lmx_graph_work_capture` → `lmx_graph_resolve` = 0).
`int: node 5` принят (n04). Голая запись внутреннего метода источник не меняет (n05: 4, 4, 4) — по норме. Вызываемое
F создаётся под своим объявлением (`lmx_graph_fn_make`; `docs/kernel-implementation.ru.md:818–819`): `F\parent` —
Frame `fn`/`sub`, родитель объявления — блок, где оно написано. Вызываемое, объявленное в части `data` метода, чистый
граф пока не создаёт: вызов из кода метода — 5 (n06; это 5г, так же у sonnet2 для данных Structure).

Что называет `node` (предложение).
- Метод корня: корень (родитель объявления).
- Метод в данных — части `data` метода или именованной Structure (после 5г): этот блок; так делает рабочий frontend для
  Structure (`wf_box`).
- Внутренний метод в коде объемлющего: данные объемлющего (слова автора `node\var`). Рабочий frontend этого не делает —
  вопрос В2.1.
- Код обычной Structure, запущенной `call` или записью по имени: вопрос В2.2.
- Корень единицы (активации с кадром нет): `node` нет — 3, как «unknown field path root» рабочего frontend.

Механизм для чистого графа (правки после сигнала).
1. `node` — слово языка в `lmx_graph_language_word`: обход кадра его не захватывает (n03), местом оно не бывает.
2. Значение: в `lmx_graph_resolve` до цепочки активаций (подать его динамически нельзя): `name = node` →
   новая `lmx_graph_node_space(g)` по живому запуску: F = код активации; `decl := F\parent` (Frame `fn`/`sub`),
   `level := decl\parent`; если `level` — написанная часть кода объявления объемлющего вызываемого, ответ — часть `data`
   этого вызываемого (нахождение — как в лексическом круге `lmx_graph_resolve` для Frame `fn`/`sub`), иначе `level`.
   Тела `if`/`for` исполняются в той же активации — `node` у них тот же.
3. Чтение и запись `node\x` — существующими шагом и записью пути (`lmx_graph_step`, `lmx_graph_step_place`,
   `lmx_graph_store_field`): пишется ячейка данных, строки кадра не трогаются; вызывающий свои рабочие значения не
   перечитывает, публикует только `dirty` на границе (`lmx_graph_work_flush`) — это уже правило книги 1000.
4. Отказы объявить, затенить, записать `node` (`int:`, `@:`, `node:` в данных, имя и формал `fn`/`sub`, `node := v`,
   написание в обратных кавычках): одно место для обоих исполнителей — построитель (`lm_graph_build_*`, ответ
   построения 2), либо интерпретатор плюс зеркало в эмиттере. Ответ — вопрос В2.3.
5. Эмиттер: для чтения и записи правок нет (выпущенный код зовёт `lmx_graph_operand_name`, шаг и запись пути) —
   проверю фикстурами в трёх режимах.

Фикстуры (чистый граф). Положительные: `node_read` (метод корня), `node_write` (`sub` пишет `node\hits`, корень видит),
`node_bare_local` (1130, источник 30), `node_unexecuted` (вход не падает), `node_if_body` (тот же `node` в теле `if`),
`node_vs_dynamic` (динамическое `x` 25 против `node\x` 10: 2510), `node_inner_write` и `node_inner_read` (по ответу на
В2.1: при варианте (а) — первый вызов 4, второй 9; публикация `outer\data\total` 9). Отрицательные: `node_root` (3),
`node_declare` (`int: node 5`), `node_formal`, `node_assign` (`node := 5`), `node_quoted`. Мутанты: `node` = родитель
объявления у внутреннего метода (а не данные объемлющего); `node` снова свободный вход (падает `node_unexecuted`);
запись через `node` правит и строку кадра вызывающего (падает `node_bare_local`); `node` из цепочки активаций (падает
`node_vs_dynamic`).

## 3. `data()` в коде

Норма. Книга, `#ordinary-var` (`provenance/semantics-book.md:479–486`): запись `data(...)` в данных объявляет Structure
`data` (повтор — ещё одно вхождение); в коде — вызов головы: `data` называет данные текущего запуска, `data()`
запускает их над ними же по общему правилу запуска Structure, `data(D)` — над `D`.

Факты (graph-o16). `lmx_graph_block` пропускает всякую запись с головой `data` (`lmx_graph_run.lm2:1578`) — в коде
метода (d05; данные из одних объявлений, запущенные над собой, по Р12 не изменились бы, так что запуск виден только с
`data(D)`) и в коде над поданными данными (d06: 1, а запуск дал бы 101). Блок `data:` в корне —
объявление (d01: `data\[0]data\v` = 1); в Structure над собой — объявление, запись пропущена (d02: 1) — так и
останется до 5г. Конфликт: у обычной Structure её поле `data` читается при входе в запуск как модель мест данных
(`lmx_graph_work_open_data`: `lmx_graph_field(code, data)` → модель `lmx_graph_work_open_parts`) — механизм времён `var`;
поэтому `data(Other)` в коде `Code`, запущенном над `D`, — 5 (d07). Так написаны фикстуры `code_data`,
`known_assignment`, `known_assignment_selected`, `post_loop` (запуск над поданными данными: `call: Data Code`,
`call: Code\data Code`) и `call_var_not_selected` (над собой — не задета).

Предложение. Ветка `w_data` в `lmx_graph_block`: в коде, отделённом от данных (`lmx_graph_code_apart`), — запись
запуска: `lmx_graph_launch_head(g, code, data)` (имя `data` разрешается в данные живого запуска) →
`lmx_graph_eval_launch_record` (формы `[]` и `[data]`); в корне, в Structure над собой, во встроенном теле корня —
пропуск, как сейчас. Эмиттер — то же через `lm_graph_emit_apply_or` (голова решается при исполнении). Объём — с
десяток строк в каждом трансляторе. Фикстуры: `data_launch_method` (`fn: f () int (int: n 5)`, код `data(D)`,
`D: (int: n 1)` → `D\n` 5), `data_launch_given` (d06 → 101) — при ответе на В3.

## 4. Атом `code` в данных метода

Факт: уже работает. `fn: f () int (Alias: code)` — `length(f\data\Alias\code)` равно `length(f\code)` (c01: 1, c02: 3);
дамп держит `Alias: code` как написано, без раскрытия (c02). Механизм: данные F — новая Lmx под F
(`lmx_graph_fn_data`), поэтому `lmx_graph_atom_target` от `Alias` поднимается до F, а реестр F отвечает частью `code`
(поле-ссылка, `lmx_graph_part`). Предложение: фикстура `callable_data_code_atom` (текст c02) и мутант на этот подъём
(например, пропуск реестра вызываемого в `lmx_graph_atom_target`).

## Вопросы fable2

- **В2.1. Что называет `node` внутреннего метода, объявленного в коде объемлющего.** Программа:
  `fn: outer () int (int: total 4)` / `    sub: inner ()` / `        node\total := total + 5` / `    end: inner` /
  `    inner()` / `    return: total` / `end: outer` / `int: first outer()` / `int: second outer()`.
  Варианты: (а) данные объемлющего (слова автора `node\var`) — `first` 4, `second` 9; (б) блок кода объемлющего
  (буквальный родитель объявления) — `total` там нет, 3; (в) как рабочий frontend сейчас — отказ «unknown field path
  segment» при трансляции, и так же для `node\data\total` и поля корня. Предлагаю (а); у рабочего frontend это тогда
  его собственный пробел (шаг 8 плана).
- **В2.2. `node` в коде обычной Structure.** Программа: `int: hits 4` / `Bump: (node\hits := hits + 1)` /
  `call: Bump` / `int: seen hits`. Варианты: (а) `node` — родитель `Bump` (корень): `seen` 5; (б) `node` есть только у
  вызываемых: 3.
- **В2.3. Ответ на объявление `node`.** Программа: `int: node 5`. Варианты: (а) отказ построения (ответ 2, обоим
  исполнителям сразу); (б) отказ интерпретатора на строке (5) и тот же отказ в выпущенном коде.
- **В3. Поле `data` обычной Structure, запущенной над поданными данными.** Программа: `Code:` / `    data:` /
  `        int: x 1` / `    end: data` / `    x := x + 1` / `end: Code` / `Data: (int: x 10)` / `call: Data Code` /
  `int: seen Data\x` / `int: own Code\data\x`. Варианты: (а) до 5в/5г поле `data` остаётся моделью мест и как запись
  пропускается; запуск `data(...)` — только в коде вызываемых; фикстуры не меняются; `seen` 11, `own` 1; (б) таблица
  книги действует уже сейчас: запись `data:` в коде — запуск `Data` над блоком (`int: x 10` пишет `x` блока); чтение
  модели снимается; `seen` 11, `own` 10; переписываются `code_data`, `known_assignment`, `known_assignment_selected`,
  `post_loop`. Предлагаю (а) в этом подшаге, (б) — с переводом фикстур 5в.
- **В1. Ограда `---` внутри скобок** — нужна ли вторая роль маркера (открыть безымянную Structure перед строками глубже)
  или только закрытие. Программа: `D: (` / `    Point:` / `        int: x 4` / `    ---` / `        int: y 2` / `)`.
  Варианты: (а) как вне скобок — `int: y 2` в безымянной Structure после `Point` (вне скобок так и есть: p13);
  (б) только закрытие — строка глубже после ограды — ошибка уровня. Предлагаю (а).
