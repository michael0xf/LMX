## Q6. Граф ребёнка: кто делает его independent

**Контекст.** Вы решили: граф, висящий в Thread, всегда `independent`, а `independent` — это `parent = 0`, даже если лексически сверху что-то было; копировщик не меняется — копирует лексическую цепочку до `node = 0`. Для R0 это уже посажено (`lmx_root.lm1`: граф R0 получает `parent = 0`, адаптер больше не требует `node != 0`, коммит `f617ab6`). Остались **дети**: `lmx_child_create_profiled` (`dev/l2src_sandbox/lmx_child.lm1:23-70`) строит граф ребёнка копией `source` через `lmx_graph_copy_profiled_owned`. Копировщик поднимается по лексической цепочке `source` до нуля, поэтому если родительский поток передаёт `source` с лексическим родителем (например, occurrence `M` под единицей, `M.parent = unit`), корень графа ребёнка получает **скопированного** родителя — граф ребёнка не independent. Ядро этого сегодня не проверяет и не исправляет.

**Минимальный случай (уровень ядра; из L2 детей пока не породить).** Родительский Thread вызывает `lmx_child_reserve(t, src, child_arena, result, M)`, где `M` — callable occurrence под единицей.

**Варианты.**
- **R1 — контракт вызывающего.** `source` обязан быть уже independent (`parent = 0`); ядро не проверяет («расстановка — дело программы», ваш Q4); не-independent source — ошибка программы с неопределённым эффектом. Ядро не меняется.
- **R2 — ядро делает граф ребёнка independent само.** После копии корню ставится `parent = 0` (буквальное применение «independent ставит parent = 0, даже если сверху что-то было»). Минус: скопированные предки становятся мусором, который копировщик не должен был создавать; `node` ребёнка = 0.
- **R3 — отказ.** Создание ребёнка отвергает `source` с `parent != 0` (контрактная проверка, новая).

**Следствия.** R1 — ничего не писать, только selftest с independent source; R2 — одна запись в `lmx_child_create_profiled` + selftest; R3 — новый код отказа + диагностика.

**Кто ждёт.** Opus, детская часть тикета -110 (`FABLE-OPUS-THREAD-GRAPH-INDEPENDENT`).

**Рекомендация.** R1 (Opus и я).

**Ответ автора (2026-09-23, дословно в `LMX_blog/2026-09-23.md`):** «файл lm3 lm3 по определению independent (это ты имел в виду под R1 "source"?)». **Итог: R1.** Источник графа ребёнка — единица (`.lm3`), по определению independent (`parent = 0`); ядро не проверяет и не чинит. Закрыт.

## Q7. Доступ к полям C-структур из L2

**Контекст.** По вашему правилу L2 не видит C; всё C — только через `c.*`, и транслятор не распознаёт никаких конкретных C-имён. Инвентарь Grok Bot (-111) показал, что в трансляторе остались **фиксированные коды типов по имени** для типов парсера: `LmP0Text` (ty=5), `LmP0IndentStack` (14), `LmP0TrailerRole` (10), `LmP0Diagnostic` (21), `LmP0Document` (need_p0) — сайты `l2trans.lm1` :5106, :5186, :8178-8300, :9100-9104, :11061, :11163-11165. Они существуют только ради того, чтобы записи вида `formal\data` (поле C-структуры парсера) понижались в C-доступ к члену. Если написать тип через общую дверь (`c.LmP0Text`), то `t\data` сегодня отвергается («unsupported body»): путь `\` в L2 — доступ к полю Structure графа, а не к члену C-структуры. Эти же коды держат порт парсера в L2 (`parser_*_port.lm2`, библиотеки `library_p0_text` и др.).

**Минимальная программа.**
```
fn: len (c.LmP0Text: t) size_t
    return: t\length
end: len
```

**Варианты.**
- **P1 — путь на `c.*`-значении = сырой C-доступ к члену.** Продолжение потокенного правила: всё, что под `c.*`, — сырой C; `t\length` эмитится дословно как `t->length` / `t.length`, проверяет C-компилятор. Фиксированные коды удаляются целиком; никакого знания C-структур в трансляторе.
- **P2 — L2 к полям C-структур не обращается.** Такие данные читают только L1-адаптеры (`lm_p0_*`, объявленные через `predef`), а L2 видит их как непрозрачные `c.*`-указатели. Тогда порт парсера на L2 обязан идти через адаптер на каждое поле.

**Следствия.** P1 — тикет Grok Bot: удалить группу B из -111 (коды 5/10/14/21, `need_p0`, `l2_is_known` per-name include-флаги), мигрировать порт и фикстуры на `c.LmP0*` и сырые пути; P2 — порт парсера переписывается на адаптеры, коды всё равно удаляются, но появляется семейство `lm_p0_*` accessor'ов.

**Кто ждёт.** Grok Bot (следующий тикет после -111 группы A и -116).

**Рекомендация.** P1 — иначе самосборка парсера на L2 упирается в адаптер на каждое поле.

**Ответ автора:** «Q7 -- P1». **Итог: P1** — `\field` на `c.*`-значении = сырой C-доступ к члену; фиксированные коды удаляются (тикет Grok Bot). Закрыт.

## Q8. Вызов метода выше объявления переменной, которую он читает

**Контекст.** Два ваших правила вместе: методы видны в обе стороны; не-callable видны только после точки объявления. Значит метод, объявленный **ниже** переменной, законно её читает, а **вызов** этого метода может стоять **выше** объявления переменной — и при исполнении метод прочитает ячейку до того, как выполнился оператор объявления.

**Минимальная программа.**
```
int: r f()
int: x 5
fn: f () int
    return: x
end: f
return: r
```

**Варианты.**
- **U1 — конструирование.** Литеральный инициализатор поля единицы — часть построенного графа: `x = 5` до любого оператора → выход 5. Минус: пришлось бы различать литерал и выражение (`int: r f()` само по себе выражение) по форме, что правилам противоречит.
- **U2 — оператор.** Объявление — оператор entry на своём месте; ячейка существует с конструирования (own-поле E) и равна нулю, пока оператор не выполнился → выход 0. Согласуется с нативной моделью (каноническая ячейка, dirty load, `:` классифицируется по именам, объявленным выше).
- **U3 — отказ трансляции.** Вызов не может достигать метода, читающего не-callable, объявленный ниже места вызова; требует обхода графа вызовов на каждом месте вызова.

**Следствия.** U2 уже реализован в S2 (`f6f213a`) как временное чтение; U1 потребовал бы формального различия литерал/выражение; U3 — новый анализ.

**Кто ждёт.** Opus (S2 посажен с U2; при другом ответе — правка + фикстура).

**Рекомендация.** U2.

**Ответ автора:** «Q8 -- U2». **Итог: U2** — как реализовано в S2. Закрыт.

## Q9. Что значит `node\x`

**Контекст.** По модели (CORE.md §2–3) `node = M.parent` — зарезервированное лексическое пространство **над** callable occurrence; собственные поля живут в `self`. Транслятор же **не загружает** `node` и не следует в него: `node\x` — это «own-поле `x` самого occurrence (self)», а `node` служит лишь обязательным префиксом написания; то же с `for\x` (Sonnet, -113; я отмечал это раньше в аудите блога как расхождение). При этом общий механизм путей (-113, `4ba8203`) уже умеет `fresh\value` и `m\value` как «поле ОТ корня». Для `node`/`for` оставлено сегодняшнее значение как последний fallback, чтобы переключение было одной правкой.

**Минимальная программа.**
```
Model:
    int: x 1
end: Model
Model: m
fn: f () int
    int: x 2
    return: node\x
end: f
```
Сегодня `node\x` = 2 (своё own-поле метода); по единообразному правилу — поле `x` лексического родителя (единицы) = … (здесь единица поля `x` не имеет — отказ), а своё поле — просто `x`.

**Варианты.**
- **N1 — оставить.** `node\x` — сокращение для «моё own-поле `x`» (исключение по имени корня).
- **N2 — единообразно.** `node\x` следует в `M.parent` и берёт его поле `x` (= `[0]x`); своё поле — `x`; `for\x` — аналогично поле объемлющего `for`-фрейма как Structure. Существующие фикстуры `unit_node_path*`, `unit_node_array_paths`, `unit_forj_*` переписываются; `node`/`for` перестают быть зарезервированными корнями в диспетчере путей.

**Следствия.** N2 → тикет Sonnet: снять fallback в диспетчере, переписать фикстуры, мутант; заодно исчезает последняя «спеллинговая» ветка массивных helper'ов.

**Кто ждёт.** Sonnet (следующий тикет по путям).

**Рекомендация.** N2.

**Ответ автора:** «"убрать N1" правка должна была быть прямо в next_core_tasks.md но в твоем примере q.md … нет никакого "x" у лексического родителя f(). Так как x объявлен внутри Model! То есть и не N2 тоже. N3 -- это ошибка». **Итог:** N1 снят; правило единообразное — `node\x` есть поле `x` лексического родителя (`M.parent`); в моём примере у родителя (единицы) такого поля нет, `x` объявлен внутри `Model`, поэтому программа — ошибка «unresolved name» (мой пример был неверен). Правило внесено в `next_core_tasks.md` §4. Закрыт; тикет Sonnet.

## Q12. Payload у throw и его типизация

**Контекст.** `throws` перечисляет только имена (`docs:485`), но полная сигнатура включает «бросаемые значения» (`docs:172`). В старом t2 (`provenance/semantics-sources/l1.txt`, ~10300) `throw: GreetingRetry(cfg)` ловится `catch: GreetingRetry ()` — catch связывает позиционный **префикс** payload. Дизайн S1: статус-возврат k = позиция имени в объявленном списке throws вызываемого; payload — одна Structure в арене Message, передаётся через существующий out-параметр `l2_out_throw`; имён/текста в рантайме нет; отдельный зарезервированный статус для runtime-провала (сегодняшний merge-провал возвращает 1 и столкнулся бы с позицией 1 — переезжает).

**Минимальная программа.**
```
fn: work () int
    throws: Retry
    throw: Retry(3, 7)
end: work

fn: caller () int
    catch: Retry (int: n)
        return: n
    ---
    return: work()
end: caller
```

**Что подтвердить (одним «да» или поправкой).**
1. Типы payload имени = типы аргументов в месте `throw:`.
2. Все throw-места, которые могут доставить имя в одно место вызова, согласуют префикс, который потребляет `catch:`; проверяется на трансляции, иначе отказ.
3. Intern сигнатуры включает упорядоченный список throws с типами payload каждого имени; callable-формал, чей контракт не перечисляет throws метода, отвергается существующим «incompatible entry signature».

**Кто ждёт.** Opus (S1).

**Рекомендация.** Подтвердить 1–3.

**Ответ автора (2026-09-23, дословно в `LMX_blog/2026-09-23.md`; цитирует мой пункт 2):** «" согласуют префикс, который потребляет `catch:`; " общий механизм верификации присваивания стандартным runtime implements, и поэтому при трансляции его можно вызывать только частично и транслятор может оптимизировать только ограниченно. Если ошибка типа -- стандартный путь». **Итог:** пункты 2–3 в моей формулировке сняты: связывание параметров `catch` с payload — обычное присваивание, верифицируемое стандартным runtime `implements` (receiving expression); на трансляции — только частичная проверка и ограниченная оптимизация; несовпадение типа — стандартный путь отказа admission, не отдельная трансляционная проверка «префикса». Позиционный префикс как факт старого примера (catch берёт первые k аргументов) сохраняется, но типизация — через implements. В intern сигнатуры входят имена throws (по §14); типы payload не фиксируются сигнатурой. Закрыт; S1 (Opus).

## Q13. Место `throws:` в теле и E без throws

**Контекст.** Старая спека (l1.txt ~10205): метод «может объявить имена, которые могут покинуть его тело»; t2 ставит `throws:` первым элементом тела. Единица/E (точка входа) по D2 throws не объявляет.

**Что подтвердить.**
1. `throws:` стоит первым элементом (элементами) тела определения; в любом другом месте — отказ.
2. E никогда не объявляет throws: необработанное объявленное имя, дошедшее до E, — ошибка трансляции «unhandled throw in entry: <Name>» на месте вызова; общее правило §14 не меняется — у E просто нет списка.

**Кто ждёт.** Opus (S1).

**Рекомендация.** Подтвердить 1–2.

## Закрытые сегодня решения (для ориентира; дословно — в `LMX_blog/2026-09-22.md`)

- **D1 = E1:** код выхода процесса = int, возвращённый entry. **D2:** неотловленный явный throw в entry — ошибка трансляции. **D3:** у L2 нет `main`; программа начинается с первой строки единицы; `main` в L1 — наше дело. **D4:** аргументы — стандартный Message от заглушки R0.
- **Пространство имён:** одно для всех идентификаторов L2; `c.*` — отдельный сырой мир; L2 не видит C; никаких реестров C-имён.
- **Q1/Q5 + уточнение:** переменные видны только после объявления (следствие dirty load и перегруженного `:`); методы — в обе стороны; каждое присваивание — occurrence поля объемлющей Structure; `test\field` ≡ `test\[0]field`; видимость назад — для всех не-callable.
- **Q2:** `Model: fresh` не «бросает» без явного throws; неотловленный throw — в корень, поток закрывается.
- **Q3:** приёмник «получить следующее письмо», возвращает письма до 0; общий механизм `lmx_thread`.
- **Q4:** копировщик не меняется, копирует до `node = 0`; `independent` = `parent = 0`; граф, висящий в Thread, всегда independent.
- **`success`:** ставит пользовательский код; `success = 1` — достаточное условие остановки Thread на end turn; система никогда не сбрасывает в 0; система ставит 1 только простому письму — при take получателем после attach (Q-B).
- **Q-S2-4 (решил сам, не правило языка):** column-0 `return:` после закрытого `end:` — обычный элемент единицы (посажено `97cf8e7`).
