# Спецификация L1

L1 — генерируемое промежуточное представление для понижения ядра в C99. Языковые правила графа задают [L3](LMX_semantics.ru.md) и [L2](L2_spec_ru.md); здесь остаётся только C-проекция. Состояние текущего транслятора и переходного рукописного L1 — в [заметках](implementation-notes.ru.md).

<a id="scope"></a>
## 1. Предмет

`l1trans` понижает `.lm1` в одну единицу C99. L1 сам по себе не определяет арену, `implements` или графовую видимость как операции языка. Такие механизмы реализуются явно библиотекой ядра. Цель самосборки — L3 со вставками L2; L1 остаётся промежуточным шагом.

<a id="translator"></a>
## 2. Транслятор

L1 разрешает свои C-подобные объявления и выражения. Префиксное `@x` — адрес C-ячейки `x`, префиксное `\p` — загрузка указателя, `p\field` — доступ к полю через указатель. Декларативное `@ⁿ:` задаёт соответствующую глубину C-указателя. Исторический порядок аргументов указательного объявления в рукописном L1 не является постоянным исключением: целевой промежуточный L1 должен следовать общему порядку L2/L3 «имя, требование, значение». Внешние C-символы доступны через явное `c.имя`.

<a id="lmx"></a>
## 3. Lmx на L1

Целевая C-проекция [L2 §2](L2_spec_ru.md#lmx) — плоский заголовок `Lmx` с полями `parent`, `length`, `storage` именно в этом порядке, без вложенного `VoidArray`. Ссылка на Structure или Array указывает на начало заголовка. Обычная Structure и `Array<@>` хранят в `storage` элементы `void *` и взаимозаменяемы в общих операциях; числовой `Array<T>` хранит непосредственно элементы T. Типизированное storage и общий механизм изменения размера применяются ко всем массивам; capacity хранится в таблице арены. Эта раскладка утверждена, перенос текущего генератора ещё открыт: [состояние реализации](implementation-notes.ru.md#l2-status), [M13](../next_core_tasks_v3.md#flat-lmx-descriptor). Записи графа не получают имени, тега модели или скрытых полей выполнения. Динамический List детей Thread хранится отдельно.

Понижение обычного ресивера [`sys\descriptor`](L2_spec_ru.md#get-descriptor) возвращает Structure с адресами трёх настоящих полей заголовка: `Lmx **`, `size_t *`, `void **`. Запись через разыменование адресует и изменяет исходное поле непосредственно; запись в поле самой возвращённой Structure меняет её указатель. Прокси, отложенной обратной записи или нового opcode нет. Произвольные конечные глубина указателя и мерность Array проходят общий типизированный путь; L1 сохраняет свой порядок объявлений «тип — имя».

Понижение parent/length/sys\storage читает поля заголовка; sys\native читает native-дескриптор из
таблиц call, sys\capacity — вместимость из таблицы арены. Без аргумента выбирается текущая data.
Ни один запрос не строит вспомогательный descriptor. Data/code и node сохраняют свои роли.
sys\resize/sys\reserve используют общий механизм изменяемых массивов. Native и capacity в Lmx нет.

Для `sys\descriptor` также есть явный аргумент S и вариант без аргумента от текущей data:
`sys\descriptor() = sys\descriptor(data)`. Выбор действует и во вложенных телах управления;
понижение обоих вариантов возвращает адреса полей выбранной Structure по одному контракту.

<a id="interpretable-tree"></a>
### 3.1. Проекция дерева

Понижение сохраняет полный граф для обходчика и `sys\toLmx`; последующая мутация меняет именно этот граф. Оно не выделяет `leaf`-обёртку для уже типизированной ячейки примитива и не хранит имена в графовых записях. Таблица имён и комментарии нужны выводу текста текущего графа, не исполнению. Подробный контракт — [L2 §2.1](L2_spec_ru.md#interpretable-tree).

Понижение `sys\indexof(field parent)` ищет единственное вхождение ссылки и возвращает физический
индекс; отсутствие или неоднозначность — ошибка. `sys\indexof(field index parent)` выбирает вхождение
с номером index, с нуля, и возвращает его физическую позицию; отсутствие вхождения — ошибка.
Использовать общую адресацию Structure/Array<@>, без дополнительной таблицы индексов.
[Контракт L2](L2_spec_ru.md#system-indexof).

<a id="type-by-range"></a>
## 4. Тип по диапазону

`LmxRange` и индекс арены классифицируют физические адреса, а не читают теги из ячеек. Модели пользователя не создают по C-типу на каждую Structure. Обычные и `immutable` Structure имеют разные пулы, сохраняя совместимую физическую запись. См. [L2 §3](L2_spec_ru.md#type-by-range).

<a id="pool"></a>
## 5. Пул

`LmxPool` и `LmxChunk` выделяют фиксированные ячейки. Рост добавляет чанк, а не перемещает живые ячейки через `realloc`. Пул и диапазон принадлежат арене. См. [L2 §4](L2_spec_ru.md#pool).

При поэтапной самосборке транслятор выдаёт C99-доступ к `void *storage` графового Array через указатель фактического типа элемента `T *`, выбранного по L2-типу пула. Соответствующий пул выделяет и использует ячейки именно этого типа с нужным выравниванием: приведение не переопределяет тип уже существующего backing. Для графового слота ссылок действует отдельное правило `void **`, а не несовместимый доступ как `T **`. Так одна общая Array-Structure понижает разные типизированные массивы без нового языкового объекта для каждого `T`.

<a id="method-array"></a>
## 6. Нативный вход и Array

Native-дескрипторы — обычные структуры в таблицах call в арене Thread, с вариантами сигнатур, бинарным модулем/именем входа и путями L1/C. При трансляции fn/sub/catch отсутствующее обычное поле native ссылается на этот дескриптор; другим Structure оно не добавляется. Array использует общий Lmx и изменяемое типизированное storage; отдельный механизм роста List и встроенная capacity снимаются. [L2](L2_spec_ru.md#method-array).

<a id="arena"></a>
## 7. Арена

`LmxArena` владеет блоками, пулами и индексом диапазонов. `attach` передаёт владение без перемещения адресов; `mark/revert` обслуживают атомарное построение. Простой режим не выполняет GC. См. [L2 §6](L2_spec_ru.md#arena).

<a id="message"></a>
## 8. Message

`LmxMsg` понижается ровно с четырьмя полями: `running`, `success`, `handoff_ready`, `graph`. Его идентичность — адрес записи, поля числового индекса нет. Почта и семейные связи не добавляются в префикс Message. См. [L2 §7](L2_spec_ru.md#message).

<a id="thread"></a>
## 9. L3 Thread

`LmxThread` содержит `LmxMsg` первым членом по значению, поэтому адрес Thread равен адресу префикса Message. Доступ к хвосту требует точной классификации Thread. `Thread.children` удерживает один List прямых детей вне исходного графа. См. [L2 §8](L2_spec_ru.md#thread).

<a id="root-close"></a>
### 9.1. R0

R0 и верхний host-каркас используют общий механизм Thread. Служебные данные запуска принадлежат каркасу, а не скрытым полям графа R0. Каскад закрытия идёт по единственному List детей; timeout всего поддерева контролирует host-watchdog. См. [L2 §8.1](L2_spec_ru.md#root-close).

<a id="mailbox"></a>
## 10. Почта

`LmxPost` хранит `staged`, `outbox` и FIFO `inbox`. Входящий слот — пара `[target, source_arena]`; владелец получателя присоединяет donor до выдачи target. Кольцо inbox использует общий изменяемый массив с внешней capacity, перемещаемым storage и monitor ящика. См. [L2 §9](L2_spec_ru.md#mailbox).

<a id="own"></a>
## 11. Локальный кадр вызова

<a id="call-frame-20261115"></a>
Каждый вызов, включая `call(D,C)`, создаёт собственный namespace. У fn/sub/catch args/data
объединены в одну входную data; краткие заголовки сохраняются. Actual заменяет соответствующее
исходное объявление кадра, и его инициализатор не выполняется. Подготовка собирает только корни
data/code, без обхода ветвей и графовых ссылок и без автозаполнения исходной data.

При входе нет фазы исполнения инициализаторов. Готовые объявления сворачиваются при построении
чистого графа без вызовов программы; uninit:T сохраняется. Неиспользуемое вычисляемое поле data
не выполняется. Чтение получает его значение общим механизмом, как `data\field`: исполняется
написанный RHS, а не неявный вызов полученной ссылки. Для `@: fptr getFuncPtr()` запись
`fptr("hello world")` сначала получает указатель, затем вызывает полученную функцию.

Переменные и const видны с первоначального объявления вперёд в своей области и ниже.
Двусторонняя видимость сохраняется у имён Structure и callable, но не у переменной с указателем
на функцию. Новое имя ветви не выходит наружу. Повторное `int: x bump()` сохраняет вычисление,
допуск и запись существующему x; убирается только повторная C-декларация. Физические повторы
полей сохраняются и выбираются `S\[n]x`. Явный путь не ограничивается порядком объявления
голого имени. Раннее чтение объявления через путь не отменяет его RHS при достижении строки code.

Голое x и @x относятся к месту кадра, независимому от замен исходного поля сразу после входа,
даже до первого чтения: сохраняется выбранное значение либо вычисляемое описание.
Правило одно для явной data, лексического и динамического связывания. Это не глубокое копирование
объектов по ссылкам. `x := 0` меняет namespace; `data\x := 0` — исходный граф.
Для вычисляемого входа `int: x next()` обращение @x получает значение и адрес локальной ячейки.
При `@(data\field)` и исходном `int: field getValue()` адресуется результат getValue();
в разобранном native-пути уже есть l2_tN, поэтому используется &l2_tN без дополнительного выделения.
Готовое место адресуется непосредственно; исходное объявление от чтения результата не заменяется.
Время жизни обычное. @f() было исследовательским примером, не задачей отдельной поддержки или запрета.

Копирование code ради одинакового момента применения правок отменено. Native и обходчик могут
применить правку в разное время до endturn; независимость namespace сохраняется. Связывание идёт
скрытыми аргументами, без копирования окружения. Изменение графа не обнуляет native и не запускает
проверку/компиляцию. Методы и обычные Structure компилируются общим механизмом без data=code;
разные actuals дают разные C-сигнатуры, заголовок без code описывает вызов.

Локальные кадры не публикуются. Load-dirty, общий кеш прямого доступа и flush() отменены;
явные записи наблюдаются через реальные алиасы в порядке исполнения.
[Согласованная норма](LMX_semantics.ru.md#call-frame-20261115),
[единое ТЗ M14](../next_core_tasks_v3.md#native-structures).

<a id="call"></a>
## 12. Вызов и явная компиляция

Известный native вызывает известный вариант непосредственно в C с выбранной фактической сигнатурой
и нужными скрытыми аргументами. Граф, таблица call, универсальная упаковка actuals и trampoline
ради организации такого вызова не нужны. Динамический вызов выбирает вариант в таблицах call;
детали его внутреннего ABI не становятся обязательной упаковкой всех статических вызовов.

sys\compile(S) явно выполняет построение/проверку чистого графа → L1 → C → машинную компиляцию
и регистрацию входов; sys\translate возвращает только L1 и диагностики. Записи в граф не отслеживаются
ради native: нет автоматического сброса, обратной инвалидизации и пересборки. Для прямой цепочки A→B
обновление A требует компиляции единицы с A и нужным B, а не замены только записи B в таблице.
Поддерживаемый источник компилятора остаётся L2/L3; L1/C — генерируемые артефакты.

sys\endturn() понижается через общий механизм системного выхода с finally до границы такта.
Обычный catch его не перехватывает; вызов не возвращается, продолжение стека не сохраняется.
Running/success самим ресивером не меняются. После успешной явной компиляции и endturn следующий
вход использует подготовленное обновление; без компиляции endturn не обнаруживает и не исправляет
правки. Это не flush и не публикация локалов. [L2](L2_spec_ru.md#explicit-compilation).

<a id="child"></a>
## 13. Ребёнок

Ребёнок строится в своей арене. Публикация добавляет его ссылку в `Thread.children`, не дописывая поле в исходную Structure. См. [L2 §12](L2_spec_ru.md#child).

<a id="copy-merge"></a>
## 14. Копия и merge

`lmx_graph_copy_owned` и `lmx_merge_owned` используют общую карту исходник→копия для полей, внутренних ссылок и parent. Native-дескрипторы и обычные поля native копируются по общим правилам графовых данных; это не доказывает пригодность машинного входа для новой структуры и не регистрирует его автоматически. Привязки входов создаёт явная компиляция или восстановление сохранённых таблиц выбранного корня. [L2](L2_spec_ru.md#copy-merge).

sys\toLmx выбранного L3 Thread сохраняет все таблицы его арены, включая call/native, а не только
поля R0. sys\fromLmx восстанавливает чистый граф и связи с готовыми ABI-совместимыми бинарниками
после перезапуска на той же платформе по модулю/имени входа, без трансляции заново.
Для произвольной S внешние таблицы автоматически не добавляются.

<a id="implements"></a>
## 15. implements

Таблица `LmxImplEntry` хранит доказанное соответствие адресов полей кандидата и принимающего описания для любой допущенной пары Structure. Разный порядок полей не сводится к тождеству индексов; чтение, получение адреса и явная запись в исходный граф пользуются тем же соответствием. Локальные места вызова обратно в граф не публикуются. В данных каждая объявляющая запись — вхождение имени: повторное объявление прежнего не заменяет и в него не пишет, а имя с двумя и более вхождениями адресуется только с индексом вхождения (решение автора 2026-11-11, [L3](LMX_semantics.ru.md#fields)); выбор «последнего вхождения» не является частью нового контракта. `s\[N]field` с нулевым `N` адресует N-е вхождение имени — запись данных, объявляющую это имя, — а не элемент Array. Карта не хранит runtime-имена и не удерживает граф живым сама по себе. См. [L2 §14](L2_spec_ru.md#implements).

<a id="gc"></a>
## 16. Сбор

`lmx_gc_collect` реализует сбор по корням арены, включая Message, граф, почту и `Thread.children`. Простой режим арены сбор не выполняет. См. [L2 §15](L2_spec_ru.md#gc).

<a id="c99"></a>
## 17. Выход C99

Один вызов транслятора выдаёт один `.c`. Строгая сборка использует `-std=c99 -Wall -Wextra -Wpedantic` и диагностики несовместимых указателей, отброшенных квалификаторов и неявных объявлений. `struct:`, `enum:`, `fnptr:` и `type:` понижаются в C-объявления. Это не меняет модель памяти арены.

<a id="lowlevel-scope"></a>
## 18. Машинная поверхность

L1 сохраняет представление и числовую семантику C99-платформы. Переменная L1 и поле C-агрегата сами по себе не являются графовой ячейкой Lmx; доступ к графу идёт через библиотеку ядра. Совпадающее написание операции L1 и L2 не делает их семантически одной операцией.

<a id="lowlevel-address"></a>
## 19. Указатели и поля

| L1 | C99 |
| --- | --- |
| `@: p int` | `int *p` |
| `@@: pp char` | `char **pp` |
| `p: @x` | `p = &x` |
| `\p` | `*p` |
| `\p: value` | `(*p) = value` |
| `p\field` | `p->field` |
| `a[i]: value` | `a[i] = value` |

Таблица задаёт целевое единое написание; переходный рукописный L1 может ещё требовать миграции порядка объявлений. Адресуемая цель должна иметь действительное C-хранилище. `value\field` — шаг указателя; доступ к C-агрегату по значению требует явной C-формы. `const: @(char p)` понижается в `const char *p` и защищает символы, не ячейку указателя. Это не глубокая неизменяемость L3.

L2-индексация, включая `array[-1]` и любую конечную цепочку соседних индексов, понижается в расчёт
смещения без проверок length/знака/арены. L3 использует собственный тип ссылки на дескриптор
массива с index и одну проверку итогового элемента; storage внутри этой ссылки не хранится.
L3-указатель на примитив также имеет отдельный тип, используя общий задел типизированных ссылок.

<a id="lowlevel-array"></a>
## 20. Array и сырой C-массив

Обычный `[]:` и в L1, и в L2/L3 означает языковой Array — графовую Structure на общей основе `Lmx` с типизированными элементами, структурным `parent` и `native`. Только явная дверь `c.array:` выбирает сырой непрерывный C-массив без графового `Lmx`, арены и скрытых проверок индекса. Прямоугольный сырой массив не превращается в массив отдельно выделенных строк. Время жизни автоматического C-массива подчиняется C99; он не отождествляется с графовым Array. Прежнее понижение голого L1 `[]:` прямо в C-массив — состояние реализации, которое предстоит устранить.

<a id="lowlevel-abi"></a>
## 21. Приведения и C ABI

`cast: (T) expression` выдаёт явное C-приведение, не проверяемое преобразование L3. `c.name` — явный внешний C-символ. `foreign: Name` требует определения типа во включённом C-заголовке; `external` и `prototype` описывают экспорт и объявление, `include` и `predef` — явные зависимости. Заголовочный `name.h.lm1` выдаёт `name.lm1.h` и допускает объявления без исполняемых тел. Поле по значению требует завершённого C-типа, указатель допускает forward-объявление.

<a id="lowlevel-expression"></a>
## 22. Выражения и управление

L1 понижает C-арифметику, логику, битовые операции, `++/--` и обычный поток управления. Исходное `=` в сравнении становится `==`; `target: expression` — присваиванием. `switch` допускает C-fallthrough, в отличие от L3 `match`. L1 `throw/catch/finally` с машинной служебной нагрузкой не определяет типизированные отказы L2/L3.

<a id="lowlevel-sync"></a>
## 23. Синхронизация

L1 не определяет структурный ресивер `synchronized`. Ядро использует явные машинные и внешние атомарные операции; `volatile` не заменяет атомарность. Контракт `synchronized` принадлежит [L2](L2_spec_ru.md#lowlevel-sync).
