# Квалификатор `independent: const: immutable` как тип, узнаваемый по диапазону адресов

Записка Fable от 2026-09-20 по тикету Codex `FABLE-ADDR-RANGE-KINDS-20260920-01`: что есть в коде, где оно расходится с правилами автора, что проверено и что предлагается. Номера строк — по `dev/l2src_sandbox/` на момент записи.

## Первоисточник

Слова автора заархивированы дословно в `LMX_blog/2026-09-20.md`, записи «Значение independent» и «Квалификаторы как тип, определяемый по диапазону адресов». Оттуда следуют четыре правила: `independent` означает `node = 0`; эти ресиверы задают тип; любой тип узнаётся только по вхождению адреса в диапазон, без флага на значении и без отдельного кода на каждый случай; вечные данные живут у корневого потока R0, сборка мусора их не трогает, другие Message могут на них ссылаться.

## Механизм, как он есть

Общий механизм — таблица «адрес → дескриптор массива» арены и четыре вопроса к ней в `lmx_range.lm1`:

| Вопрос | Символ | Кто отвечает |
| --- | --- | --- |
| что это за значение | `lmx_range_classify` (`:175`) | своя арена, затем живое привязанное хранилище |
| какого оно типа | `lmx_range_type_of` (`:220`) | так же |
| каков шаг ячейки | `lmx_range_stride` (`:251`) | так же |
| чьё это хранение | `lmx_range_pool` (`:282`) | ТОЛЬКО своя арена |

`lmx_domain_kind` — буквально вызов `lmx_range_classify` (`lmx_implements.lm1:28-29`). Хранилище — обычная арена с ролью (`lmx_perm.lm1`: `lmx_perm_open`, `lmx_perm_close`, `lmx_perm_bind`, `lmx_perm_store_of`, `lmx_perm_is_store`); отдельного классификатора у него нет намеренно (`lmx_perm.h.lm1`: «ask the store DIRECTLY»). Квалифицированный тип — это ЧЛЕНСТВО адреса в диапазонах хранилища, и ни одной новой константы вида или типа под него не заведено. Сборка мусора не заходит в хранилище без особого случая: `lmx_range_pool` локален, поэтому адрес хранилища для сборки — «не моё» (`lmx_gc.lm1:107`), а сборка над самим хранилищем — пустое действие (`lmx_gc.lm1:282`).

## Кто читает квалификатор

Ядро:

- `lmx_range.lm1:213`, `:244`, `:272` — три одинаковых отката к хранилищу, с проверкой, что хранилище живо;
- `lmx_graph_copy_owned.lm1:194` (`lmx_copy_is_terminal`), `:423`, `:530`, `:553` — четыре раза вручную записанный вопрос «адрес принадлежит привязанному хранилищу»; ссылка `\perm` читается напрямую, без проверки, что хранилище живо;
- `lmx_child.lm1:47` — привязка арены ребёнка к хранилищу родителя;
- `lmx_arena.lm1:217-229`, `:286` — хранилище не донор при слиянии арен и не освобождается обычным `lmx_arena_release`;
- `lmx_root.lm1:80-126` — R0 открывает хранилище, привязывает свою арену, держит два массива удержания.

Транслятор `l2trans.lm1`:

- `l2_take_eternal` (`:9206`) принимает ровно одну форму — цепочку `independent:` → `const:` → `immutable:` → `()`, по одному активному члену на каждом уровне; остальное отвергается диагностиками «independent takes one qualified construction», «independent branch requires const», «independent branch requires immutable», «independent qualifies Structure construction»;
- `l2_ns_in_eternal` (`:596`) и `l2_ns_arena` (`:611`) выбирают, в какой арене строится член: `l2_program_arena` или `lmx_perm_store_of(l2_program_arena)`;
- замкнутость ветви по ссылкам: «an eternal branch cannot reference mutable storage» (`:9174`), «an eternal branch cannot hold a callable field» (`:9181`), «an eternal branch field cannot be updated» (`:13355`);
- корень строится с `node = 0` и заносится в массив удержания R0 (`ea21c94`).

Слова `const` и `immutable` встречаются в трансляторе и вне этой цепочки, но там это не типы графа: `const:` — квалификатор формального параметра и указуемого в C-ABI и константная локальная, `immutable:` в теле метода — блок указательных локальных L1 (`tests/entry_immut.lm2`).

Мои единицы: `lmx_plan_home` (`lmx_plan.lm1:98`) — «какая таблица ответила»; `lmx_walk_eternal` (`lmx_walk.lm1:178`) — отказ в записи в хранилище при подготовке тела; публичная граница `lmx_walk_run` — вход обязан классифицироваться. Драйвер `harness/l2_eternal_driver.lm1` смотрит на сгенерированную программу снаружи.

## Соответствие правилам

| Правило | Где выполнено | Чем проверено |
| --- | --- | --- |
| тип — по вхождению адреса | четыре вопроса `lmx_range_*`; ни флага на значении, ни константы под квалификатор | `tests/lmx_range_kinds_selftest.lm1`, `tests/lmx_perm_selftest.lm1` |
| без отдельного кода на каждый вид | один и тот же путь для всех 14 видов значений | таблица в `lmx_range_kinds_selftest` |
| `independent` = `node = 0` | транслятор строит корень через `lmx_node_new_owned`; сгенерированный вход и драйвер проверяют `node = 0` | `tools/l2_harness.ps1`, строки `eternal-runs` |
| вечное живёт у R0, сборка не трогает | хранилище встроено в `LmxRoot`, `lmx_range_pool` локален | `lmx_perm_selftest`, `lmx_walk_perm_selftest`, драйвер |
| на вечное можно ссылаться из других Message | откат классификации к привязанному хранилищу из любой арены рантайма | те же три теста |
| другой рантайм не видит | привязка отказная (`lmx_perm_bind`), ничего глобального | те же три теста |

Новый тест `tests/lmx_range_kinds_selftest.lm1` (177 проверок, 14 видов) — таблица: каждая строка есть один обычный конструктор, выполненный в хранилище и в привязанном Message. Виды: Structure, слоты ссылок Structure, ячейки `int` / `size_t` / `unsigned`, запись METHOD, запись `LmxCallable`, запись операции, запись роли плана, запись массива и его хранение, запись массива ссылок и его хранение, ячейка `char`. Для каждой строки: вид, тип и шаг значения хранилища одинаковы из обоих Message и из самого хранилища; у значения, построенного в Message, ТОТ ЖЕ вид и тип — квалификатор не является вторым кодом вида, отличается только ответившая таблица; другой рантайм не отвечает ничего; вопрос о хранении локален; дом (`lmx_plan_home`) — хранилище для одного и Message для другого; значение хранилища любого вида — терминал копирования из своего рантайма и ни из какого другого. Один раз на всю таблицу: корень и вложенный член хранилища одного вида (`node = 0` — факт Structure, а не диапазона); ЗАКРЫТОЕ хранилище не хранилище — каждый его адрес перестаёт отвечать на все эти вопросы.

Мутационный контроль на приватной копии (чужой `lmx_range.lm1` в дереве не тронут): без отката у `lmx_range_stride` падает свойство «тот же шаг» у всех 14 видов, без отката у `lmx_range_type_of` — «тот же тип» у 14, без отката у `lmx_range_classify` — «тот же вид» у 14.

## Расхождения и что с ними делать

1. **Один вопрос записан от руки в восьми местах.** «Принадлежит ли адрес привязанному хранилищу» — это три отката в `lmx_range.lm1`, четыре копии в `lmx_graph_copy_owned.lm1` (без проверки, что хранилище живо: сегодня безвредно, потому что `lmx_arena_release` обнуляет индекс, но правило «закрытое хранилище не хранилище» там не записано) и одно место у меня. В моих единицах было два таких места; оставлено одно — `lmx_plan_home`: `lmx_walk_eternal` спрашивает его, а проверка дома ролей в `lmx_plan_validate_shape` больше не читает флаг. ПРЕДЛОЖЕНИЕ владельцу ядра: одна функция общего механизма в `lmx_range.lm1` — «какая таблица отвечает за адрес: сама арена, её живое хранилище или никакая» — и через неё выразить три отката и четыре копии в копировщике. Ребра линковки к `lmx_perm.o` это не создаёт: функция живёт в самом `lmx_range`. Поведение не меняется; приёмка — `lmx_range_kinds_selftest`, `lmx_perm_selftest` и `lmx_walk_perm_selftest` остаются зелёными. Сам я чужие файлы ядра не правил.
2. **`independent` = `node = 0` держится только на сгенерированном коде.** Ядро принимает в массив удержания любую ссылку: проверки «корень, `node = 0`, адрес хранилища» при записи в массив нет, а собственный `return: 1` сгенерированного входа теряется, потому что `lmx_thread_dispatch_native` отбрасывает результат входа. Снаружи это сегодня видит только драйвер. Лечится актом ядра для записи в массив удержания — это `lmx_root.*`, не моё и вне тикета.
3. **Тройка слита.** Транслятор знает один тип: полную цепочку; любой ресивер по отдельности отвергается. См. вопрос к автору ниже.
4. **Сгенерированная программа не имеет второго Message**, поэтому «ветвь классифицируется из второго привязанного Message» доказано на ядре, а на сгенерированной программе — нет.
5. Повторное исполнение построения на каждом ходу (`FABLE-L2-ETERNAL-INIT-ONCE-20260920-01`) — на удержании до решения автора о месте unit в графе R0.

## Вопрос к автору по ABI

«Эти ресиверы задают некий тип» — тип задаёт КАЖДЫЙ из трёх ресиверов по отдельности или только их полная цепочка? Сегодня диапазон один (хранилище R0) и тип один. Если `const:` и `immutable:` — самостоятельные типы, которые тоже узнаются по адресу, каждому нужен свой диапазон: например, неизменяемые, но собираемые данные Message — отдельный пул арены Message. `independent:` отдельного диапазона не требует: `node = 0` — факт самой Structure.
