(1) Исходный чистый граф. `fn: f (int: x) int () (return: x)` остаётся тем, что написано: структурой ресивера fn (Frame с головой fn) с ровно пятью её аргументами в написанном порядке, позиционными и безымянными:
    [fn | f, (int: x), int, (), (return: x)]
- name — слово f (примитив-слово, указатель на строку "f"); f не имя никакой Lmx в таблице адрес -> name.
- args — безымянная Lmx из одного поля: формал `int: x` в общей форме места (§3.2: слот -> uninit:int -> ячейка int; её строка "x" — аргумент name этого объявления int; описание формала не исполняется).
- return — слово int, как написано: ссылка на ресивер с именем int, не «безымянное слово» и не захардкоженный int.
- var — пустая безымянная Lmx `()`.
- body — безымянная Lmx с одним полем: Frame `return: x` (голова return, аргумент — слово x).
fn — имя (голова) структуры исходного объявления. Физически это слово-голова в поле 0, как у любого Frame графа (§3.3). Строк таблицы имён у объявления нет: ни "f", ни "args"/"return"/"var"/"body". Построитель не выводит var из тела, не именует части и не создаёт функцию. Прошу подтвердить эту физическую форму головы. Альтернатива — строка таблицы адрес -> name "fn" у самой Lmx, пять аргументов в полях 0–4. Её я не выбираю: это было бы общим изменением всех Frame, и голова-имя смешалась бы с именами мест при поиске имени в полях.

(2) Обход. Каждый обход — интерпретатора или транслятора — начинает с пустых таблиц. Входя в лексический блок объявления (имена fn видны в обе стороны блока, книга :435), он разрешает голову fn в ресивер fn. Пять аргументов связываются с формалами ресивера name, args, return, var, body так же, как вызов связывает фактические с формалами: позиционно, именованная подача возможна. Затем ресивер создаёт в namespace этого обхода под словом аргумента name значение f — Structure из четырёх частей args(), return(), var(), body():
- args -> Lmx аргумента args;
- return -> написанное требование (здесь int);
- var -> аргумент var (здесь пустой). При опущенном var собственные поля берутся из объявлений тела по правилу автозаполнения; это делает обход, а не построитель;
- body -> аргумент body.
Ни слова fn, ни аргумента name в созданном значении нет. Части ссылаются на Lmx аргументов объявления, а не копируют их; само объявление не меняется. Физически это обычная Lmx результата fn (участок lmx:result, §2.2), созданная этим обходом. Строка namespace f -> эта Lmx живёт только в таблицах обхода и уничтожается вместе с ними. Ни в граф, ни в постоянную таблицу имя функции не пишется; имена частей принадлежат созданным ячейкам, а не аргументам объявления.
Новый независимый обход того же графа снова начинает с пустых таблиц, читает то же объявление и создаёт f заново из текущего содержания графа; от прошлого обхода он ничего не берёт. Если граф изменили (например, тело или args), новый f отражает изменение. Это и станет проверкой: два обхода одного графа, затем обход изменённого, без состояния прошлого.

(3) Общий механизм. Объявление — это применение ресивера при обходе, одно правило для всех объявляющих Frame. Построитель строит написанный Frame: голова и аргументы. Примитивное объявление остаётся прежним сжатым атомом: `int: i 5` — ячейка int = 5 с именем i, «имя, тип и значение по адресу» (автор 2026-11-08). Обход разрешает голову и применяет контракт:
- int создаёт место i;
- fn — f(args, return, var, body);
- sub — s(args, var, body); fm — так же;
- `@: p T` — ссылочное место p;
- `S: … end: S` — именованную Structure S.
Потребители читают созданное значение по этому правилу, а не по зашитой форме «пять полей, поле 0 = fn» и не по return = w_int.
merge(f1, f2) особых правил не получает. В namespace обхода f1 и f2 — обычные Structure, созданные ресивером fn: f1(args, return, var, body) и f2(args, return, var) без body. merge работает по общим правилам Structure: f1 — модель, совпадающие по имени поля f2 (args, return, var) пишутся в слоты модели, body f1 остаётся, результат — новая Structure. Сигнатура меняется, тело и источники целы. Для этого нужно лишь, чтобы f1 и f2 были настоящими созданными Structure с частями, — это и даёт механизм объявлений; ветки merge «для функций» не будет. Исполненный во время работы merge даёт новый callable, который интерпретируется: компиляции во время исполнения нет.
