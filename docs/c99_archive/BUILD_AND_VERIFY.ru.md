# Сборка и проверка архива

## Полная композиция

Исходники находятся локально. CMake-адаптеры не должны скачивать зависимости.
Нужны установленный C toolchain, CMake 3.20 или новее и Make либо Ninja.
Для полной исходной Linux-композиции требуются также системные POSIX/thread
и OpenGL development inputs. Унаследованная libpq использует инструменты
генерации, указанные её адаптером; они относятся к host toolchain.

В репозитории LMX корневой файл CMake пакета не установлен (он остаётся только
в архивном снимке пакета): рабочая команда запускается от каталога коллекции —
`cmake -S third_party/lmx_c99_compact -B <build-dir> -DCMAKE_BUILD_TYPE=MinSizeRel -DLMX_ARCHIVE_VERIFY=ON`;
собственные `project` и `CTest` коллекции поддерживают её. Команда ниже относится
к самостоятельной поставке.

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=MinSizeRel -DLMX_ARCHIVE_VERIFY=ON
cmake --build build --parallel 2
ctest --test-dir build --output-on-failure
```

`--parallel 2` — пример, а не требование: на тесной машине можно использовать
один процесс. Без `LMX_ARCHIVE_VERIFY` строятся библиотеки; примеры и проверки
не являются обязательным runtime системы. Для обычного включения из проекта:

```cmake
add_subdirectory(third_party/lmx_c99_compact)
target_link_libraries(my_program PRIVATE LMX::zlib LMX::lsoda)
```

`LMX::all` предоставляет общую композицию targets; выбор отдельных targets
удобнее для конкретного приложения. Наличие архива библиотеки на диске не
означает включение всех его функций в executable. Финальный размер проверяется
после линковки нужной системы и отличается от суммы `.a`.

## Отдельные компактные группы

Команды ниже выполняются из `third_party/lmx_c99_compact` и не требуют
сборки графики или сетевых клиентов всей коллекции.

```sh
cmake -S extensions/storage_extra -B build-storage -DCMAKE_BUILD_TYPE=MinSizeRel
cmake --build build-storage
ctest --test-dir build-storage --output-on-failure

cmake -S extensions/science_extra -B build-science -DCMAKE_BUILD_TYPE=MinSizeRel -DLMX_SCIENCE_EXTRA_BUILD_TESTS=ON
cmake --build build-science
ctest --test-dir build-science --output-on-failure

cmake -S extensions/knowledge_extra -B build-formats -DCMAKE_BUILD_TYPE=MinSizeRel
cmake --build build-formats
ctest --test-dir build-formats --output-on-failure
```

Отдельной `knowledge_extra` нужен локально установленный zlib. При включении
в общую композицию TIFF и matio используют уже имеющийся `LMX::zlib`.
`control_extra` использует сохранённые libfixmath/libfixmatrix; её собственный
README содержит команды автономной проверки. PDFio собирается через
`extensions/pdf_extra`; его README описывает профиль и известное ограничение.

## Что именно проверяется

Общая проверка включает исходные 26 демонстраций, 51 сохранённый сценарий
использования базовых API, пять комбинированных проверок прежних дополнений,
проверки новых групп, сквозное восстановление повреждённого файла и совместную
работу Zstd с самостоятельным libdivsufsort.
Число фактически зарегистрированных и выполненных сценариев фиксируется в
[`VERIFICATION.json`](VERIFICATION.json).

Программы работают в отдельных каталогах build-tree. Вывод PDF, XLSX,
изображений, служебные файлы и испорченный/восстановленный CSV не пишутся
поверх исходников. Звуковое и графическое оборудование, реальная CAN/serial
шина и внешние серверы для этих сценариев не требуются. Сетевые проверки
базовой группы могут использовать локальные loopback sockets.

В C-командах используются `-std=c99`, `C_EXTENSIONS=OFF` и
`-pedantic-errors` на GCC/Clang. Проверки с `assert` принудительно сохраняют
assertions; новые тесты используют также явные проверки return codes и bytes.
Выключение production `assert` в MinSizeRel/Release не должно превращать
проверку в пустой запуск.

## Измерения и границы результата

- Размер `.a` измеряется у реального файла и включает таблицы символов/
  контейнер. В отчётах также может быть сумма text/data/bss из object files.
- Переносимый исходник и фактически проверенная платформа отмечаются отдельно.
  Новые группы проверялись на Linux x86_64; Windows/macOS/embedded branches
  сохранены там, где нужны, но не выданы за выполненную аппаратную матрицу.
- Сборки выполнены на локальных входах. Внешние зависимости означают
  подготовленный host toolchain/SDK, а не разрешение скачать что-либо ночью
  из CMake на машине без сети.
- Выполненные integration tests не равны полному upstream conformance/fuzz
  corpus. Унаследованные и новые исходные тесты сохранены в полезном виде;
  точный запущенный набор перечислен в отчётах.
- Физическая устойчивость flash к power loss и реальные задержки устройств
  не выводятся из успешного RAM/file-backend теста.

## Как продолжать компактную коллекцию

Сначала подобрать конкретный библиотечный механизм и его профиль. Проверить
лицензию всех используемых частей, собрать и выполнить предметный пример.
Затем оставить необходимые входы, переносимые ветви, лицензии, короткую
справку и код тестов/примеров; снова собрать из оставшегося дерева. Измерить
исходники и бинарный профиль отдельно. Добавить source URL, target, границы
возможностей и проверку в опись. Не включать язык или готовый сервис только
потому, что его реализация написана на C.
