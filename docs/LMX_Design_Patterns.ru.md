# Шаблоны проектирования на Lingvamyxa

Русская версия · 20 ноября 2026 года · Девять самостоятельных примеров

Документ учитывает последние согласованные ТЗ: именованные сигнатуры `fn`, их позиционную проверку в `implements`, прозрачное связывание с локальными местами вызывающего, передаваемые формы объявлений и импорт корневых const-объявлений. Здесь считаем эти изменения применёнными. Примеры проверены по правилам документов; запуск компилятором LMX не выполнялся.

## Порядок и состав

Сохранены три ранее обсуждавшихся примера — Iterator, Strategy и Visitor — и добавлены шесть других известных шаблонов. Названия относятся к классическому каталогу GoF; реализации ниже написаны для LMX и не копируют классовое устройство примеров из книги. [G][G]

Порядок — моя ориентировочная оценка практической распространённости и удобства изучения, **не статистический рейтинг всей отрасли**. Первые четыре — базовый набор для обхода, выбора алгоритма, создания и адаптации; следующие четыре — организация взаимодействия и шагов обработки; Visitor оставлен последним как более специализированный пример работы с разными видами узлов. ## Правила чтения примеров

- Каждый раздел — отдельный пример со своим namespace. Повторяющиеся `Demo`, имена сигнатур и другие объявления не надо склеивать в один модуль без переименования.
- Блок с определениями читается в роли DATA. Отдельный короткий блок «Вызов» помещается в исполняемый контекст. Все результаты — возвращаемые значения; неизвестная библиотека печати не предполагается.
- Метод — обычная вложенная Structure. Его data — фактический `parent(code)`; входные места и описание `return` находятся там. `fn` создаёт именованное описание сигнатуры, а не тело. [B, §§4, 8][B]
- `@: p Signature Implementation\method` явно разделяет имя ссылки, требование и кандидата. Для fn-требования сравниваются число и порядок типов входов и результат. Метки fn служат именами явных actuals через эту ссылку; реальные имена реализации могут отличаться. Обычный явно заданный структурный шаблон проверяет всё заданное им дерево. [B, §8][B]
- Defaults, `required` и скрытое связывание относятся к выбранной реализации. Метки fn не создают переименования скрытых зависимостей. Двусторонний `private` действует по обычным правилам. [B, §§5–6, 8.4–8.5][B]
- Bare-присваивание работает с выбранным местом текущего выполнения. Явный путь вроде `numbers\position` обращается к графу. Поэтому локальный аккумулятор Iterator и постоянное состояние Observer записаны по-разному.
- `import` добавляет корневые const-объявления data; пользовательские структуры константны без явного `const`. Импорт не переносит обычные переменные и не меняет parent импортированного метода. [D, §6][D]

Исходный граф каждого примера самодостаточен. Там, где демонстрация изменяет постоянное состояние, драйвер явно задаёт начальное состояние, поэтому его можно повторить с тем же ожидаемым результатом.

## 1. Iterator — итератор и пользовательский iterate

**Задача:** отделить получение следующего элемента от обработки элемента. `numbers\next()` хранит позицию обхода, `cycles\iterate` управляет повторением, а вызывающий задаёт тело. Ниже сохранён согласованный компактный пример с локальным `total`; точка входа названа `run`.

```lmx
numbers:
    int: position 0
    return: int
    next:
        throws: Stop
        if: numbers\position >= 3
            throw: Stop()
        numbers\position += 1
        return: numbers\position
end: numbers

cycles:
    @: iteration
    @: body
    iterate:
        while: 1
            iteration()
            catch: Stop ()
                break
            body()
end: cycles

use:
    import: cycles
    int: total 0
    return: int
    run:
        numbers\position := 0
        iterate: int: item numbers\next()
            item *= 2
            total += item
        return: total
end: use
```

**Вызов:**

```lmx
use\run()
```

**Ожидаемый результат: 12.**

| Вызов next | Получено | item после тела | total |
|---|---:|---:|---:|
| 1 | 1 | 2 | 2 |
| 2 | 2 | 4 | 6 |
| 3 | 3 | 6 | 12 |
| 4 | Stop | Тело не исполняется | 12 |

Первый аргумент `iterate` — сохранённая форма объявления `int: item numbers\next()`. Одна передача формы не вызывает `next`: каждый следующий элемент получается именно при `iteration()`. Исполнение формы создаёт или обновляет `item`, а `body()` работает с тем же местом. Чтение `item` и вход в тело не вызывают `next` повторно. Это применение правил передаваемых ресиверов объявления из [D, §§3–4][D].

`total` в переданном теле связан с локальным местом текущего `use\run`. Начальное значение 0 поступает из объявления `int: total 0`; писать `use\total := 0` или повторно обнулять локальный аккумулятор не требуется. Позиция итератора, напротив, должна сохраняться между отдельными вызовами `next`, поэтому изменяется явным путём `numbers\position`. Драйвер явно сбрасывает её перед новым полным обходом.

`import: cycles` добавляет константное имя пользовательской структуры `iterate`. Переменные `iteration` и `body` остаются в исходном `cycles`, который продолжает быть data для `iterate`.

`Stop` — именованный выход окончания последовательности. Он позволяет выдавать 0 как обычное значение элемента. В этой компактной записи `catch` охватывает весь оборот, включая тело: `Stop`, пришедший из тела, тоже завершил бы цикл. Это существующая область обработчика, а не особое поведение пользовательского `iterate`.

**Что выражено средствами LMX:** протокол шага, переданная форма объявления и её общий контекст с телом. Нового встроенного цикла для этого примера не требуется.

<a id="strategy"></a>

## 2. Strategy — заменяемый алгоритм

**Задача:** менять алгоритм, сохраняя потребителя. `Processor\apply` принимает операцию через ссылку: сначала она удваивает число, затем утраивает.

```lmx
fn: Transform (int: x; return: int)

Algorithms:
    int: value
    return: int
    twice:
        return: value * 2
    thrice:
        return: value * 3
end: Algorithms

Processor:
    @: operation Transform Algorithms\twice
    int: input
    return: int
    apply:
        return: operation(x := input)
end: Processor

StrategyDemo:
    return: int
    run:
        @: selected Transform Algorithms\twice
        int: first Processor\apply(operation := selected; input := 5)
        selected := Algorithms\thrice
        int: second Processor\apply(operation := selected; input := 5)
        return: first + second
end: StrategyDemo
```

**Вызов:**

```lmx
StrategyDemo\run()
```

**Ожидаемый результат: 25** — первый вызов даёт 10, второй 15.

`fn: Transform ...` описывает один вход `int` и результат `int`. Реализации `twice` и `thrice` — обычные структуры; данные обеих находятся в `Algorithms`. В сигнатуре параметр называется `x`, а в реализациях — `value`. Они подходят: `fn` сравнивает типы по позициям.

Вызов `operation(x := input)` использует метку `x` интерфейса `Transform`; она задаёт первую позицию и направляет значение в настоящий параметр `value`. Это явная передача. Она не меняет имена полей реализации и не создаёт переименования для скрытого связывания. [B, §8][B]

`selected := Algorithms\thrice` меняет значение локальной ссылки, сохраняя её fn-требование. Оба вызова `Processor\apply` передают эту ссылку явно, поэтому готовый default поля `operation` заменяется переданным actual.

**Что остаётся от Strategy:** потребитель, контракт операции и выбор реализации. Наследование и отдельный класс на каждый алгоритм не нужны для выражения этих трёх ролей.

<a id="factory"></a>

## 3. Factory Method — заменяемый шаг создания

**Задача:** общий алгоритм сам определяет, когда создать продукт, а конкретный способ создания можно заменить. Здесь роль фабричного метода выражена через контекст LMX: структура наследования классов из классического варианта не воспроизводится.

```lmx
fn: FactorySignature (return: @)

ProductTemplate:
    int: payload 0
    return: int
    read:
        return: payload
end: ProductTemplate

Factories:
    return: @
    small:
        return: merge(ProductTemplate; (int: payload 10))
    large:
        return: merge(ProductTemplate; (int: payload 20))
end: Factories

Workflow:
    return: int
    execute:
        @: product ProductTemplate create()
        return: product\read() + 1
end: Workflow

FactoryDemo:
    return: int
    run:
        @: create FactorySignature Factories\small
        int: first Workflow\execute()
        create := Factories\large
        int: second Workflow\execute()
        return: first + second
end: FactoryDemo
```

**Вызов:**

```lmx
FactoryDemo\run()
```

**Ожидаемый результат: 32** — первый workflow возвращает 11, второй 21.

`Workflow\execute` сохраняет последовательность «создать продукт → прочитать значение → прибавить единицу». Имя `create` не объявлено в его собственных data или code и связывается с локальной ссылкой вызывающего. Изменение `create` выбирает другую фабрику, сохраняя общий алгоритм. Это точка расширения внутри workflow; один самостоятельный `switch`, возвращающий разные объекты, здесь не подменяет фабричный метод.

`FactorySignature` задаёт ноль явных входов и результат-ссылку. Обе фабрики возвращают новую композицию через `merge`: второй операнд содержит объявление поля `payload`, которое заменяет соответствующий слот модели. Скобки сохраняют этот операнд отдельной структурой.

У `product` обычное структурное требование `ProductTemplate`. Оно включает всё заданное дерево модели, в том числе `read`; обе фабрики удовлетворяют ему, составляя продукт из этой модели. Это содержательно отличается от проверки `FactorySignature`, которая сравнивает только типовую форму вызова фабрики. [B, §§8.2–8.3][B]

`merge` сохраняет и перенаправляет связи копируемых вхождений: `read` полученного продукта использует данные этого продукта. Исходный `ProductTemplate` остаётся образцом. Создание ссылки на прежнее тело само по себе такого изменения parent не дало бы.

**Что делает LMX:** передаёт заменяемый метод через контекст и строит продукт обычной композицией. Решение о том, какой продукт создавать, остаётся в фабриках.

<a id="adapter"></a>

## 4. Adapter — согласование интерфейсов

**Задача:** использовать существующую операцию через нужный потребителю интерфейс. Здесь оба параметра имеют тип `int`, но их смысловой порядок в старом методе обратный. Пример специально различает совместимость типов и правильное назначение значений.

```lmx
fn: Difference (int: left; int: right; return: int)

Legacy:
    int: right
    int: left
    return: int
    subtract:
        return: left - right
end: Legacy

DifferenceAdapter:
    int: minuend
    int: subtrahend
    return: int
    subtract:
        return: Legacy\subtract(right := subtrahend; left := minuend)
end: DifferenceAdapter

AdapterDemo:
    return: int
    run:
        @: operation Difference DifferenceAdapter\subtract
        return: operation(left := 8; right := 3)
end: AdapterDemo
```

**Вызов:**

```lmx
AdapterDemo\run()
```

**Ожидаемый результат: 5.**

Интерфейс `Difference` задаёт порядок `left`, затем `right`. Через него 8 попадает в первую позицию адаптера — `minuend`, а 3 во вторую — `subtrahend`. Адаптер явно передаёт старому методу `right = 3`, `left = 8`; тот вычисляет 8 − 3.

Если заменить `DifferenceAdapter\subtract` в объявлении `operation` непосредственно на `Legacy\subtract`, fn-проверка пройдёт: обе типовые формы имеют вид `(int, int) → int`. Но вызов через `Difference` тогда направит 8 в настоящий первый параметр `right`, а 3 — во второй `left`, и результат будет **−5**. Имена кандидата не переставляют позиции его сигнатуры. [B, §8.5][B]

Следовательно, адаптер делает настоящую работу: явно согласует назначение аргументов. `fn` сохраняет типовую совместимость и не угадывает смысл `left` и `right`.

**Граница с Decorator:** Adapter меняет соответствие интерфейсов; Decorator в примере ниже сохраняет интерфейс и дополняет обработку.

<a id="observer"></a>

## 5. Observer — несколько подписчиков события

**Задача:** доставить одно событие нескольким независимым обработчикам. Первый запоминает последнее значение, второй накапливает сумму. Для компактности два подписчика представлены двумя полями; отдельный API контейнера не предполагается.

```lmx
ObserverState:
    int: last 0
    int: total 0
end: ObserverState

fn: ListenerSignature (int: value)

Remember:
    int: observed
    accept:
        ObserverState\last := observed
end: Remember

Accumulate:
    int: amount
    accept:
        ObserverState\total += amount
end: Accumulate

Publisher:
    @: first ListenerSignature Remember\accept
    @: second ListenerSignature Accumulate\accept
    int: event
    notify:
        first(value := event)
        second(value := event)
end: Publisher

Demo:
    return: int
    run:
        ObserverState\last := 0
        ObserverState\total := 0
        Publisher\notify(event := 3)
        Publisher\notify(event := 8)
        return: ObserverState\total
end: Demo
```

**Вызов:**

```lmx
Demo\run()
```

**Ожидаемый результат: 11; в графе `last = 8`, `total = 11`.**

| Доставленное событие | last | total |
|---|---:|---:|
| 3 | 3 | 3 |
| 8 | 8 | 11 |

`ListenerSignature` описывает один вход int без результата. Реальные имена параметров — `observed` и `amount`, но каждый вызов через типизированную ссылку использует внешнюю метку `value`. Эта метка направляет событие в первую позицию выбранного обработчика.

Издатель хранит ссылки и уведомляет оба получателя по порядку. Замена одного обработчика не требует менять другой. Состояние `ObserverState` намеренно лежит в графе: оно должно сохраняться между двумя независимыми уведомлениями. Драйвер явно сбрасывает его перед демонстрационной серией; сами обработчики ничего скрыто не обнуляют.

Это минимальный синхронный вариант Observer с двумя слотами подписки. Динамический список, отписка, очереди и политика ошибок обработчиков здесь не реализованы; они являются отдельной логикой издателя, а не следствием наличия двух ссылок.

**Что делает LMX:** хранит и проверяет callable-ссылки и передаёт события обычными вызовами. Само правило уведомить всех подписчиков написано явно.

<a id="decorator"></a>

## 6. Decorator — обёртки с тем же интерфейсом

**Задача:** дополнить обработку, сохранив интерфейс операции. Базовый метод удваивает число; одна обёртка прибавляет 1 к его результату, следующая умножает полученное на 3.

```lmx
fn: TransformSignature (int: x; return: int)

Base:
    int: value
    return: int
    apply:
        return: value * 2
end: Base

WithOne:
    int: input
    return: int
    apply:
        return: Base\apply(value := input) + 1
end: WithOne

WithThree:
    int: argument
    return: int
    apply:
        return: WithOne\apply(input := argument) * 3
end: WithThree

Demo:
    return: int
    run:
        @: transform TransformSignature WithThree\apply
        return: transform(x := 10)
end: Demo
```

**Вызов:**

```lmx
Demo\run()
```

**Ожидаемый результат: 63**, по цепочке `10 → 20 → 21 → 63`.

Все три метода имеют fn-форму `[int] → int`. Их входы называются `value`, `input` и `argument`, а внешний интерфейс — `x`. Позиционная типизация допускает каждую реализацию. Прямые вложенные вызовы используют реальные имена соответствующих методов и явно передают текущее значение.

В объявлении `transform` можно выбрать `Base\apply` и получить 20 либо `WithOne\apply` и получить 21. Внешний вызов `transform(x := 10)` сохраняется. Каждая обёртка делегирует часть работы прежней операции, а затем добавляет своё действие; исходный метод не переписывается.

Здесь показана композиция функций с заранее заданной цепочкой. Произвольный сборщик цепочек во время исполнения потребовал бы отдельно представить ссылки между слоями. Пример не прячет такую библиотеку в слове Decorator.

**Граница со Strategy:** Strategy выбирает один алгоритм; Decorator строит дополнительное поведение вокруг уже выбранной операции. Эти приёмы можно сочетать.

<a id="command"></a>

## 7. Command — действие как передаваемое значение

**Задача:** отделить место запуска действия от его конкретной реализации. `Invoker` получает команду и исполняет её; он не знает, прибавляет она число или умножает счётчик.

```lmx
Counter:
    int: value 0
end: Counter

fn: CommandSignature ()

AddTwoCommand:
    execute:
        Counter\value += 2
end: AddTwoCommand

DoubleCommand:
    execute:
        Counter\value *= 2
end: DoubleCommand

Invoker:
    @: command CommandSignature AddTwoCommand\execute
    run:
        command()
end: Invoker

Demo:
    return: int
    run:
        Counter\value := 0
        Invoker\run(command := AddTwoCommand\execute)
        Invoker\run(command := DoubleCommand\execute)
        return: Counter\value
end: Demo
```

**Вызов:**

```lmx
Demo\run()
```

**Ожидаемый результат: 4**, состояние счётчика меняется `0 → 2 → 4`.

`fn: CommandSignature ()` задаёт ноль явных входов и отсутствие результата. Оба метода `execute` подходят: их родители содержат только сами пользовательские методы, которые не становятся входными переменными.

В actual передаётся ссылка `AddTwoCommand\execute`, без `()`. Поэтому команда выполняется в `Invoker\run`, когда достигнут `command()`, а не при её передаче. Готовое значение поля `command` — первая команда; второй вызов явно заменяет его другим actual.

`Counter` — общий получатель действий. Он задан лексической ссылкой внутри реализаций; результат сохраняется между отдельными вызовами через явный путь `Counter\value`. Для повторяемости драйвер сбрасывает значение до начала серии.

Этот минимальный Command хранит действие в ссылке. Очередь, параметры отдельного экземпляра команды, журнал и undo можно добавить как обычные данные и методы, но они не возникают автоматически от самого представления команды.

**Граница со Strategy:** здесь вызывающий передаёт запрос «выполнить действие», а Invoker определяет момент исполнения. Для Strategy основной вопрос — каким алгоритмом обработать предоставленный вход.

<a id="template-method"></a>

## 8. Template Method — постоянная последовательность и заменяемые шаги

**Задача:** сохранить последовательность алгоритма, разрешив заменить отдельные шаги. `Pipeline\run` всегда сначала вызывает `prepare`, затем `finish`. Оба шага поступают из контекста вызывающего.

```lmx
fn: StepSignature (int: x; return: int)

Steps:
    int: value
    return: int
    increment:
        return: value + 1
    twice:
        return: value * 2
    square:
        return: value * value
end: Steps

Pipeline:
    int: input
    return: int
    run:
        int: intermediate prepare(x := input)
        return: finish(x := intermediate)
end: Pipeline

Demo:
    return: int
    run:
        @: prepare StepSignature Steps\increment
        @: finish StepSignature Steps\twice
        int: first Pipeline\run(input := 4)
        finish := Steps\square
        int: second Pipeline\run(input := 4)
        return: first + second
end: Demo
```

**Вызов:**

```lmx
Demo\run()
```

**Ожидаемый результат: 35.** Первый проход вычисляет `(4 + 1) × 2 = 10`; второй — `(4 + 1)² = 25`.

В собственных data и code `Pipeline\run` нет объявлений `prepare` или `finish`. Поэтому эти имена могут связаться с локальными ссылками вызывающего. После изменения `finish` алгоритм Pipeline сохраняется: по-прежнему сначала подготовка, затем завершение.

Оба шага имеют одну fn-сигнатуру `[int] → int`; их реализация принимает настоящий параметр `value`, а вызовы через ссылки используют метку `x`. Скрыто передаются сами ссылки на шаги, явные числовые входы каждого шага подаются обычными actuals.

В классическом объектном описании такие шаги часто выражают переопределяемыми методами. Здесь роли шаблонного метода и его точек расширения выражены обычной структурой и контекстным связыванием. Для воспроизведения этой роли наследование не добавляется.

**Граница со Strategy:** у Strategy заменяется используемая операция; здесь фиксирована общая последовательность, внутри которой независимо выбираются несколько операций. Factory Method выше является частным примером заменяемого шага, посвящённого созданию продукта.

<a id="visitor"></a>

## 9. Visitor — действия для разных видов узлов

**Задача:** задавать действия для разных видов узлов, сохраняя сами узлы. Узел выбирает соответствующее имя обработчика, а вызывающий предоставляет его реализацию через контекст. Это вариант Visitor для LMX без отдельного visitor-аргумента.

```lmx
fn: ActionSignature (return: int)
Nodes:
    return: int
    on_number:
        throws: NoAction
        throw: NoAction()
    on_pair:
        throws: NoAction
        throw: NoAction()
    Number:
        int: value 3
        return: int
        accept:
            throws: NoAction
            int: n value
            return: on_number()
    end: Number
    Pair:
        int: left 4
        int: right 5
        return: int
        accept:
            throws: NoAction
            int: a left
            int: b right
            return: on_pair()
    end: Pair
end: Nodes
Actions:
    return: int
    number:
        return: n
    pair:
        return: a + b
end: Actions
Demo:
    return: int
    run:
        @: on_number ActionSignature Actions\number
        @: on_pair ActionSignature Actions\pair
        int: result 0
        result := Nodes\Number\accept()
        result += Nodes\Pair\accept()
        catch: NoAction ()
            result := -1
        return: result
end: Demo
```

**Вызов:**

```lmx
Demo\run()
```

**Ожидаемый результат: 12** — число даёт 3, пара даёт 4 + 5 = 9.

1. `Number\accept` объявляет локальное `n = 3` и вызывает внешнее имя `on_number`.
2. Оно связывается с локальной ссылкой в `Demo\run`; выбранный `Actions\number` получает `n` из контекста непосредственно вызывающего `accept`.
3. `Pair\accept` аналогично предоставляет локальные `a = 4`, `b = 5`; `Actions\pair` возвращает 9.
4. Драйвер складывает результаты двух посещений.

`ActionSignature` задаёт ноль **явных** входов и результат int. `n`, `a`, `b` — скрытые зависимости обработчиков; они не добавляются в арность fn. Соответствие этой сигнатуре само по себе не поставляет скрытые значения: их предоставляет конкретный вызов из accept. [B, §§6, 8][B]

Fallback-методы находятся в `Nodes`, выше непосредственных data `Number` и `Pair`. Поэтому для accept это внешние имена, допускающие динамическую подмену. Если убрать локальное объявление `on_pair` из `Demo\run`, сработает `Nodes\on_pair`, возникнет `NoAction`, и драйвер вернёт **−1**.

Готовое собственное поле обработчика внутри `Number` или `Pair` не было бы автоматически подменено caller-local. `private` также имеет значение: private-источник не передаётся неявно, а private-объявление лексического получателя защищено от динамического замещения.

**Два уровня выбора сохранены:** вид узла выбирает имя действия, контекст выбирает реализацию этого действия. Пример показывает посещение двух узлов; рекурсивный обход дерева и хранение коллекции узлов к нему не приписываются.

## Что эти примеры показывают о LMX

Повторно используются несколько общих механизмов: структуры и их parent, ссылки на методы, fn-требования, явные actuals, контекстное связывание, переданные формы и merge. Отдельная языковая конструкция на каждый шаблон не появляется.

| Общий механизм | Где он заметен |
|---|---|
| Ссылка с fn-требованием | Strategy, Adapter, Observer, Decorator, Command, шаги Template Method |
| Внешнее имя, полученное из контекста | Factory Method, Template Method, Visitor |
| Сохранённая форма объявления и общее место тела | Iterator |
| Обычный структурный шаблон и merge | Создание продуктов Factory Method |
| Явное постоянное состояние графа | Позиция Iterator, Observer, получатель Command |
| Локальное состояние активации | total в Iterator, промежуточные значения и результаты |

При этом содержание шаблона по-прежнему задаёт программа: кого уведомлять, что считать следующим элементом, какие шаги выполнять, что создавать и как обрабатывать отсутствие действия. Наличие подходящей сигнатуры подтверждает форму вызова; смысловую перестановку аргументов в Adapter или правильность алгоритма оно не доказывает.
