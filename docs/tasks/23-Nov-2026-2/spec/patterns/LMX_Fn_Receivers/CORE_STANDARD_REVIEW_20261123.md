## Как учитываются существующие возможности

Новый короткий вызов не должен создавать второй алгоритм. Сначала проверяется, выражается ли операция уже существующим Expression, copy, merge, методом контейнера или прямой функцией ядра. Несколько примеров оказались короче вообще без нового receiver: поэлементная арифметика вместо одноразового map-helper, явный поток `copy(items)` вместо цикла суммирования, concat вместо identity плюс flatMap.

Точное равенство строк уже есть: `matches(byteText(a); b)`. Оно не меняет регистр и не нормализует Unicode. `wholeMatch` даёт Maybe<Match>, `matches` — int. Публичный `sameText` не добавлен; буквальный Pattern и внутреннее сравнение имён используют одно общее тело сравнения единиц. Не добавлены дублирующие `startsWith`, `endsWith`, `replaceText`, `splitText`.

Текстовый repeat использует общий `cycle`, join — `intercalate`, старый decimal-builder — `formatInt`. Варианты trim, padding, удаления affix и поиска экстремума используют по одному общему алгоритму с направлением. Различие настоящих договоров сохраняется: например, `orElse` возвращает payload с уже вычисленным fallback, `orElseGet` вызывает fallback лениво, а `orElseOption` возвращает контейнер Maybe.

Преобразование обычного callable в operand выполняет `asOperand`. `(myOp 1 2 3 4 5)` и `(1 myOp 2 3 4 5)` принимаются одним общим шаблоном операнда; отдельного «префиксного» типа нет. Готовый массив раскрывается только явным потоком. Полный пример настройки приведён в [Expression_examples.lm3](../examples/SBCL_comparison/source/lmx/Expression_examples.lm3).

## Оставшиеся границы

[ТЗ Standard Lisp and Expression](../examples/SBCL_comparison/TZ_Standard_Lisp_and_Expression.md) разделяет реально добавленные тела и оставшиеся группы работы: полный reader/printer и FORMAT, числовые и Unicode-профили, системные streams/files/processes, packages и readtable, CLOS и restart/condition semantics, прочие отмеченные там интерфейсы. Наличие вызываемого имени в другом языке не разрешает обещать такой договор без его реализации.

Часть возможностей уже выражается через обычные DATA, copy/merge, конечные declared failures и Message/post, но их наблюдаемая семантика не автоматически равна foreign API. Например, простой finally не объявляется Java suppressed-exception policy, физические поля Structure — не JavaScript prototype lookup, и owning Message — не lock-free atomic shared memory.

Такой пробел остаётся открытым пунктом ТЗ, а не пустой функцией с отметкой BODY. Данный архив не объявляет завершённым перенос всех стандартных библиотек всех сравниваемых языков.

## Throws: основной и дополнительный подсчёт

На мой взгляд, явные списки ошибок — преимущество LMX: по ним предельно ясно, какие ошибки может породить метод. Общий список и `throws: copy(Throws)` сохраняют это свойство. Сокращать такие записи ради длины не хочется.

Основной размер включает весь исходный код. Дополнительная колонка **«без сложного Throws»** считает заголовки, полные ссылки copy и первый написанный аргумент каждого списка; только последующие аргументы не входят в неё. Сам общий список тоже учитывается один раз в той границе исходников, где находится его определение. Внешняя общая зависимость не прибавляется многократно к каждому клиенту. Метрика не меняет код, эффекты или основной коэффициент сравнения.

Общий алгоритм подсчёта: [throws_metrics.py](../tools/throws_metrics.py), проверенные примеры преобразования — в его отчёте. [sync_effects.py](tools/sync_effects.py) по умолчанию только сверяет авторские конечные объявления и сохраняет их формат; необязательный старый режим `--normalize` не является условием корректности.

## Что проверено

Сборка каталога, соответствие экспортов исходникам, разрешение упомянутых корней, границы конечных declarations, размеры, ссылки и публикации проверяются воспроизводимыми скриптами. Для LMX подготовлены отдельные случаи interpreted/native и обоих смешанных направлений вызова, включая реальные typed records, пустые/нулевые/неинициализированные значения, динамическое связывание и lifetime.

**LMX runtime status: NOT_RUN.** В архиве нет выполняемого LMX runtime. Реальные успешные проверки Perl и SBCL относятся к их контрольным программам и самостоятельным сравниваемым реализациям; они не доказывают выполнение LMX-кода. Для Fable остаётся подключение к существующему ядру и запуск подготовленных semantic acceptance cases.
