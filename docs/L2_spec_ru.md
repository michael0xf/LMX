# Спецификация L2

L2 задаёт механизмы ядра и машинные операции. Семантика L3 определяется в [спецификации LMX](LMX_semantics.ru.md), синтаксис — в [грамматике](LMX_grammar.ru.md), понижение в C99 — в [L1](L1_spec_ru.md). Этот документ не повторяет правила разрешения голов, объявления и вызова. Состояние реализации — в [заметках](implementation-notes.ru.md).

<a id="scope"></a>
## 1. Предмет

Целевая цепочка — L3 со вставками L2 → генерируемый L1 → C99. L1 является промежуточным языком. Интерпретатор исполняет сохранённый граф L3; L2-операции требуют нативного понижения.

<a id="lmx"></a>
## 2. Структура `Lmx`

Общая основа объектов графа — плоская `Lmx` с полями в порядке `parent`, `native`, `length`, `storage`: `@: parent Lmx`, `LmxEntry: native`, `size_t: length`, `@: storage void`. `length` — число элементов, `storage` — адрес их хранилища; промежуточного поля `array: VoidArray` в целевой записи нет. Языковой Array сохраняет эту основу, структурные parent/native и фиксированное типизированное хранилище. У числового Array по storage лежат сами T-элементы, у обычной Structure и Array<@> — элементы `void *`; тип задаётся диапазоном заголовка, а не написанием `void *storage`. Ссылка указывает на начало Lmx. Это утверждённая цель от 2026-11-13; текущая вложенная запись генератора и оставшаяся миграция отмечены в [состоянии реализации](implementation-notes.ru.md#l2-status).

Обычная Structure и массив нетипизированных указателей Array<@> полностью взаимозаменяемы при одинаковом содержимом: индекс, длина, именованный доступ при наличии имён, допуск, копирование, исполнение, `typeof` и получение дескриптора подчиняются одним правилам. Совпадение C-раскладки без этих операций недостаточно. Числовые Array сохраняют своё T-хранилище, а растущий List остаётся отдельным. Заголовок не входит в цепочку элементов: `S[i]` выбирает из storage, `length(S)` читает length.

`parent` задаёт структурную вложенность, не родителя Message. У Array, созданного в поле `arr`, родитель — представляющее это поле вхождение графа, а у Structure, созданной как собственный элемент массива, родитель — сам Array. Сохранение в элементе ссылки на уже существующую Structure не меняет родителя её референта. Так же упоминание имени известной Structure не раскрывается — ни парсером, ни при построении чистого графа: в дереве стоит атом, указатель на неё, а её `parent`, то есть место в дереве, не меняется, и поддерева под упомянувшей её Structure не возникает (ответы автора 2026-11-11, [журнал](../LMX_blog/2026-11-11.md#known-name-not-expanded), [L3](LMX_semantics.ru.md#colon-declares)). Лексическая видимость определяется местом создания в дереве — структурным `parent`, а не положением строки объявления: видимость в данных — в обе стороны ([L3](LMX_semantics.ru.md#declaration-visibility)); дополнительный скрытый контекст не создаётся. `native` выбирает нативный вход; нуль означает обход сохранённого тела. Графовый объект не хранит имени, тега модели или дополнительных полей состояния исполнения. Число полей Structure и элементов Array фиксируется при построении, их адресуемые ячейки не перемещаются. Примитивные элементы остаются типизированными ячейками, которым не требуется отдельное поле `parent`.

<a id="interpretable-tree"></a>
### 2.1. Интерпретируемое дерево

Разрешённый ресивер при создании результата выбирает его типизированный пул; сходство полей уже объявленной `data`-структуры не превращает её в результат этого ресивера. В частности, пул результатов `fn` получает только структуру, созданную исполнением `fn`, а не произвольную Structure с похожими частями в `data`.

Сохранённый граф — программа: объявления, значения, операторы и вложенные тела при построении следуют исходному порядку; последующая запись меняет этот же граф. Нативное понижение не заменяет его вторым AST или графом данных. Примитив уже имеет типизированную ячейку арены; дополнительный `leaf` или обёртка Structure для неё не нужны. Атомы, которые остаются частью текущей программы, сохраняются.

Обходчик исполняет текущее подходящее дерево, включая построенное или изменённое во время исполнения: редактирование данных, которые затем передаются как `code`, является построением кода. Предварительная трансляция, сохранённый подготовленный результат транслятора, скрытая копия исходника или флаг «подготовлено» для этого не требуются. Обход текущего графа и обычное разрешение его операций — исполнение, а не запрещённый повторный разбор исходного текста. Общие правила ресиверов, допуска и адресных карт сохраняются; они допускают разные рабочие формы кадра над одним сохранённым графом. Это норма, а не утверждение о завершённой поддержке runtime-построения в нынешнем ядре. [Уточнение автора, 2026-10-23](../LMX_blog/2026-10-23.md).

Имена сущностей находятся только во внешней таблице. Обходчик может получить по адресу имя написанной головы, чтобы определить её роль; это не поиск переменных по строкам при доступе к полям. Транслятор потребляет тот же построенный Lmx-граф, а готовый `native` не нуждается в имени для вызова. Комментарии не участвуют в диспетчеризации. `toLmx` выводит текущий состав и порядок графа: перезаписанный оператор не восстанавливается из исходника или скрытой копии. Служебные данные запуска, статус вызова и состав детей Thread не дописываются в граф программы.

Ссылки как данные образуют граф и могут создавать циклы. Структурный `parent` образует дерево. Вид значения определяет классификация его адреса; адрес слота и хранимый в нём адрес — разные вещи.

<a id="get-descriptor"></a>
### 2.2. descriptor и настоящие поля заголовка

Ресивер имеет варианты с S и без аргумента: `descriptor()` / `descriptor:` равнозначны
`descriptor(data)` от текущих данных запуска, в том числе во вложенных телах управления.
Для code нужен явный аргумент. Оба варианта возвращают адреса полей выбранной Structure;
одноимённая запись в data остаётся обычной Structure.

`descriptor: S` — обычный ресивер. Его результат d — обычная Structure с четырьмя именованными полями, содержащими адреса полей живой S:

```text
(
    @@: parent Lmx
    @: native LmxEntry
    @: length size_t
    @@: storage void
)
```

Машинные типы значений — соответственно `Lmx **`, `LmxEntry *`, `size_t *`, `void **`. LmxEntry уже является указателем на функцию; адрес его ячейки сохраняет настоящий тип, без приведения к `void **`. `\(d\native) := 0` адресует S.native; после штатной публикации нуля следующий вызов выбирает обходчик. `d\native := 0` меняет только обычное поле-указатель в d. Чтение через ранее полученный адрес видит текущее поле S; повторное получение достигает тех же физических ячеек. Копии заголовка, write-back, прокси или отдельного реестра нет.

Глубина указателя — любая конечная; взятие адреса добавляет уровень, разыменование снимает его. Глубина указателя и конечная мерность массива независимы и обслуживаются общими механизмами. Адрес S.parent может численно совпадать с S: типизированное разыменование Lmx ** обращается к настоящему полю, а не классифицирует этот адрес как второй самостоятельный Lmx. Правила квалификации, явной записи и времени жизни остаются обычными; получение дескриптора не продлевает жизнь S. Обычные пути `S\parent`/`S\native`/`S\length`/`S\storage` выбирают пользовательские поля, без исключения для заголовка. [Решение автора](../LMX_blog/2026-11-13-get-descriptor.md), [открытая реализация M13](../next_core_tasks_v3.md#flat-lmx-descriptor).

<a id="header-receivers"></a>
### 2.3. Чтение заголовка ресиверами

`parent(S)`, `native(S)`, `length(S)` и `storage(S)` возвращают соответственно значения S.parent (`Lmx *`),
S.native (`LmxEntry`), S.length (`size_t`) и S.storage (`void *`). Варианты `parent()`, `native()`, `length()` и `storage()` выбирают
`data` текущего запуска; они равнозначны явному аргументу `data`. Для `code` аргумент передаётся явно.
У корня parent равен 0. Длина относится к элементам, поля заголовка в неё не включаются.
`native(S)` возвращает 0 при отсутствии нативного входа; чтение вход не вызывает.

Это обычные не объявляющие ресиверы: они исполняются в `code`, а одноимённая запись в `data`
остаётся пользовательской Structure, доступной обычным путём и индексом вхождения. Голый атом
не вызывает ресивер. Разбор общий; чтение значения не строит descriptor и не выделяет объект.
`descriptor` отдельно возвращает адреса ячеек `parent/native/length/storage` для явной записи.

Имена физических полей `size` → `length`, `data` → `storage` не меняют аргументы-Structure
`data` и `code` запуска `call`. `node` сохраняет прежний контракт и ABI текущей активации;
нового `node(S)` или скрытого поля Lmx нет. [Семантика и формы](LMX_semantics.ru.md#header-receivers),
[открытая реализация M13](../next_core_tasks_v3.md#flat-lmx-descriptor).

<a id="type-by-range"></a>
## 3. Тип по диапазону адресов

Производные графовые объекты сохраняют общий `Lmx`-контракт. Пул и диапазон указывают выбранный при построении физический вид, а для Array — также тип элементов. Это классификация адреса, не поле имени или opcode в графе и не отдельный пользовательский тип для каждой модели Structure. Старое расположение, где `Lmx` содержит `VoidArray`, остаётся переходным, а не образцом для новых разновидностей Array.

Арена классифицирует адрес по зарегистрированному полуоткрытому интервалу `LmxRange` и пулу-владельцу. Сама ячейка не хранит тег типа. Обычные Structure и графовые Array имеют общую основу `Lmx`, но диапазон различает форму хранения и тип элементов; модели пользователя не порождают по одному C-типу или пулу. Пулы примитивов, ссылок, графовых объектов и backing различаются физическим контрактом доступа. Типизированные массивы внутри арены — хранилище, а не отдельные языковые Array. Обычные и `immutable` Structure выделяются в разных пулах; уже опубликованная обычная Structure не становится `immutable` на месте. Совместимость моделей устанавливает `implements`, а не физический тип.

Для каждого примитивного типа T есть отдельный тип «T без инициализации», различимый по участку адреса.
У объявления без начального значения заранее существуют собственная ячейка T и служебный указатель на неё:

| Объявление | Как поле Structure ведёт к значению |
|---|---|
| `int: x` | Поле → служебный указатель `uninit:int` → ячейка `int` места `x` |
| `int: x 0` | Поле → ячейка `int` места `x`, начальное значение 0 |

Поле Structure здесь — ячейка, хранящая адрес; в спецификации ядра она называется «слотом».
Присваивание меняет только значение в существующей ячейке T. Даже при первой записи поле и служебный
указатель не заменяются и не переключаются на другой адрес; адрес и физический тип ячейки T также сохраняются.
Для `int: x` косвенный путь остаётся тем же до и после `x := 5`, а заранее взятый `@x` адресует ту же ячейку.
Внутреннее хранение не делает `x` указателем языка: его языковой тип остаётся `int`.

`uninit:T` описывает форму объявления без начального значения, а не признак «ещё ни разу не записано».
Прежнее пояснение о переключении поля при первой записи отменено [поздним уточнением автора 2026-11-08](../LMX_blog/2026-11-08.md#uninit-pointer-preserved).
Подробное представление — [спецификация ядра §3.2](kernel-implementation.ru.md#primitive-storage).

<a id="pool"></a>
## 4. Типизированный пул

Пул выдаёт ячейки одного размера и растёт добавлением чанка, без `realloc` живых ячеек. Каждый чанк регистрируется как интервал того же типа. Выданный адрес стабилен до освобождения соответствующего владения. Индексом диапазонов управляет арена.

У графового Array `void *storage` хранит адрес backing выбранного типизированного пула, а не превращает элементы в нетипизированные значения. L2 получает из него указатель фактического типа элемента для чтения и записи; диапазон арены подтверждает этот тип, размер ячейки и выравнивание. Нельзя читать уже созданный пул слотов `void *` как массив произвольного `T` только приведением указателя. Адресуемые ссылочные слоты графа сохраняют собственный контракт `void **` и конверсию хранимого значения.

<a id="method-array"></a>
## 5. Нативный вход и Array

`LmxEntry` — слово нативного входа, а не второй объект метода. Графовый Array несёт общую основу `Lmx` и ровно заданное число типизированных элементов. Он не содержит динамического резерва и не перемещает опубликованные адресуемые ячейки. При `[]: arr (...)` значение Array сохраняет своё место в графе; последующая запись данных `MyLmxStructFromArray: arr` второй объект не конструирует и структуру из байтов не восстанавливает: по общему правилу она объявляет Structure `MyLmxStructFromArray` с одним атомом `arr` — указателем на тот же Array, неизменяемым по имени, и `parent` этого Array не меняется ([§2](#lmx), [L3](LMX_semantics.ru.md#colon-declares)). Указатель-переменную на тот же Array объявляет `@: p arr`; в коде запись `MyLmxStructFromArray: arr` — вызов своей головы, а не объявление. Динамический List — отдельный тип и отдельный контракт; его перемещаемый backing не используется как адресуемые слоты Structure или Array.

<a id="arena"></a>
## 6. Арена

Каждый Message владеет одной логической ареной; она может содержать несколько чанков и диапазонов. `lmx_arena_attach` передаёт владение без перемещения адресов. `mark/revert` откатывают неудачное построение копии или `merge`. Простой режим сохраняет классификацию и стабильность адресов, но не запускает GC. Независимая неизменяемая ветвь может остаться в арене владельца по [контракту L3](LMX_semantics.ru.md#eternal); сам факт отдельного пула такого права не даёт.

<a id="message"></a>
## 7. Запись Message

Закрытый `LmxMsg` содержит ровно `running`, `success`, `handoff_ready` и `graph`. Его локальная идентичность — адрес записи. Почта, планировщик и родитель Thread не являются его полями. `running = 0` во время хода запрашивает остановку; `success = 1` устанавливается пользовательским кодом и достаточно для остановки Thread на границе хода; система не сбрасывает `success` в нуль. `handoff_ready` разрешает передачу хранилища. `graph` ссылается на языковой корень.

<a id="thread"></a>
## 8. L3 Thread

Не каждый Message исполняется. Исполняемый Thread изначально выделяется как `LmxThread` с `LmxMsg` первым членом по значению. Адрес Thread совпадает с адресом этого префикса; доступ к хвосту требует точной классификации Thread. Самостоятельный `LmxMsg` нельзя на месте превратить в Thread.

Прямые дети хранятся в единственном List, удерживаемом полем `Thread.children`. Это состояние Thread, не поле `message.graph`. `Thread.parent` относится к иерархии Message и не меняет `Lmx.parent`. Одну идентичность Thread не исполняют конкурирующие workers.

<a id="root-close"></a>
### 8.1. R0 и закрытие

R0 — обычный дочерний Thread верхнего host-каркаса. Служебные данные запуска и настройки принадлежат каркасу и передаются R0 явно; они не добавляются в исходный граф R0. Верхний каркас не имеет родителя, но не получает особого API. Закрытие каскадно проходит через единственный List прямых детей каждого Thread. Общий timeout всего поддерева контролирует host-watchdog; его истечение завершает процесс, а не объявляет частичное закрытие успешным.

<a id="mailbox"></a>
## 9. Почта

Каждый Thread владеет `LmxPost`. `staged` готовит письма текущего хода, успешная граница публикует их в `outbox`, `inbox` содержит допущенные, но не взятые письма. Элемент `inbox` — неразделимая пара `[target, source_arena]`: producer не изменяет арену получателя; владелец присоединяет donor до выдачи target. Отказ сохраняет пару. Порядок допуска — FIFO.

`inbox` — кольцо на отдельном DynamicArray; его backing может перемещаться, но не является графовым адресуемым слотом. Один реентерабельный monitor самого `LmxPost` охватывает admission, take и count. `outbox` и `staged` остаются локальными владельцу. `post` использует эту же почту для обычного вызова LMX, не отдельный транспорт. Языковой API определён в [L3](LMX_semantics.ru.md#thread-message-api).

<a id="own"></a>
## 10. Исполнение Structure

Исполнение использует полную сохранённую Structure. Нативное тело и обходчик должны давать одинаковую семантику чтения, записи, `dirty` и публикации рабочих полей по [L3 §12](LMX_semantics.ru.md#dynamic). Объявленное поле имеет графовое место хранения; присваивание не добавляет слот к уже созданному `Lmx`. Указатели на графовые слоты должны оставаться действительными. Компоновка метода `args/return/data/code` — утверждённая цель миграции v3; её физический ABI здесь пока не описан как реализованный.

<a id="call"></a>
## 11. Вызов

Выбор между нативным входом и обходчиком определяется `Lmx.native` выбранного кода. Вызов получает `data` — переданные явно либо, у одноаргументной формы, сам `code`, — выбранный `code`, фактическую арену, `node` как лексического родителя вызываемого вхождения и подготовленные аргументы. В разделённом вызове `data` задаёт состояние, а `code` — исполняемое тело. Эти роли не доказывают неизменность кода и не квалифицируют всю Structure как `immutable`. Прогноз путей записи и алиасов не выполняется; фактическое изменение места кода сбрасывает его `native` общим путём записи. Одноаргументный `call: code` исполняет код над самим собой как `data` (решение автора 2026-11-11, [ресиверы `call` и `fncall`](LMX_semantics.ru.md#call-receivers)); прежде он выбирал дочерний блок данных кода, а теперь его не выбирает: данные передаются явно. Двухаргументный запуск записывается `call: data code` — данные стоят перед кодом везде (ответ автора 2026-11-11, [журнал](../LMX_blog/2026-11-11.md#data-before-code)); прежде писали `call: code data`. У всех ресиверов аргументы именованные и подаются по позиции или по имени (оператором `:=`): `call(data := D; code := C)`, `fncall(args := A; data := D; return := int; code := C)` (чтение исполнителя по поправке автора 2026-11-11, [журнал](../LMX_blog/2026-11-11.md#structure-call-by-name)). Роль задаёт и чтение записи (решение автора 2026-11-11, [роли `data` и `code`](LMX_semantics.ru.md#data-code-roles)): в данных структурная запись объявляет Structure и действуют объявления ресиверами мест, а присваивания и код не исполняются; в коде всякая запись — вызов, объявлений Structure там нет. В коде запись, голова которой — обычная Structure, запускает её (до решения 2026-11-11 такая запись в коде отказывала, а обычную Structure исполнял только ресивер `call`): `S()` — то же, что `call(S, S)` (Structure над самой собой), `S(D)` — то же, что `call(D, S)` (Structure над поданными данными); аргумент один и называется `data` — именем, которым код называет данные своего запуска; `S(D)` и `S(data := D)` — одна запись; так же короткая форма `S: D` и блочная. Это самостоятельная запись запуска, а не форма ресивера: ресиверы `call` и `fncall` остаются общим механизмом. Ошибка — когда голова не называет ни вызываемого, ни Structure (решение автора 2026-11-11, [журнал](../LMX_blog/2026-11-11.md#structure-call-by-name); чтение исполнителя — [ответы](../LMX_blog/q/fable-self-answers-20261110.md), Р21). В данных `S()` по-прежнему объявляет пустую Structure `S`, а `S(D)` — Structure `S` с атомом `D`; ничего не вызывается. Безымянная Structure в коде вызовом не считается: `(a b c) := myFn()` — групповое присваивание ([L3](LMX_semantics.ru.md#data-code-roles), [журнал](../LMX_blog/2026-11-11.md#unnamed-structure-not-call)). Особое имя явной ссылки на данные запуска, одноимённая часть вызываемого и блок данных называются `data`, часть с исполняемыми записями и одноимённый аргумент ресиверов `fn`, `sub`, `catch` — `code` (до решения 2026-11-11 — `var` и `body`); допуск `implements` выполняется один раз, при построении чистого графа ([§14](#implements)). Трансляторы исполняют эти правила лишь отчасти: чистый граф со среза 354 читает имена `data`, `code` и порядок `call: data code`, подшаг 5а исполняет со среза 355, а со среза 356 исполняет запись запуска Structure по имени в коде метода и в коде над поданными данными — `S()`, `S(D)`, `S(data := D)` — и запись с головой — местом со ссылкой на обычную Structure везде, включая корень единицы, а также именованную подачу аргументов у `call` и `fncall`; в корне единицы и в Structure над самой собой роль кода у записи с головой — обычной Structure по имени он пока не исполняет (подшаг 5г); остальное — подшаг 5в и остатки подшагов 5б, 5д и 5е — тоже ещё нет, а рабочий frontend читает прежние имена и порядок и запуска по имени не исполняет (шаг 8) ([план](../next_core_tasks_v3.md#m11)). Явный `call: code code` — та же форма: значение передаётся как `data` по общему правилу и служит проверкой универсальности Structure и изменения кода для будущей компиляции на лету, не особым исполнительным путём. У Structure, запущенной над самой собой, — `call: code`, то же `call: code code`, и корень единицы — своих правил нет: каждая её запись читается по обеим ролям общими правилами, а где они не дают определённого результата, это ошибка (ответ автора 2026-11-11, [журнал](../LMX_blog/2026-11-11.md#self-launch-no-own-rules)). Поэтому запись `S()` там — сразу и объявление ещё одной `S`, и вызов: при `S`, объявленной в той же Structure, у имени два вхождения, без индекса оно не отвечает и вызов отказывает, а при `S`, объявленной снаружи, запись объявляет собственную пустую `S`, и запускается она, а не внешняя; особого правила нет, и ту же Structure запускает ресивер `call` (чтение исполнителя — [ответы](../LMX_blog/q/fable-self-answers-20261110.md), Р21). Ресиверы `fncall` и `call` получают части запуска — аргументы, данные, описание результата, код — явно; это дополнение к объявлениям и обычному вызову, через тот же механизм интерпретатор запускает `fn`, `sub` и `catch`. Чистый граф исполняет эти формы со среза 353 (кроме `catch`, которого он пока не исполняет: это состояние реализации, а не норма), рабочий frontend — ещё нет ([план](../next_core_tasks_v3.md#m10)). Для **любой** допущенной пары Structure доступ к полям и публикация уже вычисленных `dirty`-значений используют одну доказанную адресную карту `implements`; совпадение порядковых номеров не предполагается. Контрольная точка пишет готовое значение в выбранный слот `data`, не выполняя выражение или допуск повторно.

Сам вход в `call`, включая `call: code code`, не инвалидирует `native`. Штатная публикация уже допущенной записи сбрасывает `native` мест кода, связанных с изменяемой ячейкой. Явный путь, алиас и разыменование выбирают адрес; запись обновляет общий для всех вызовов одного исполнения кеш прямого доступа; локальные рабочие значения кадра и их dirty остаются отдельными. Запись в физический слот и снятие входов изменённого кода атомарны для следующего либо рекурсивного dispatch. Рабочее значение до публикации, отвергнутая запись и не меняющий граф вызов не снимают `native`; изменение обычного значения данных сохраняет вход. Связь с местом кода может принадлежать охватывающей Structure, а не только Structure со слотом записи. Если L2-тело стало несовместимо с прежним входом, требуется подходящая нативная реализация или отказ **до** публикации изменения: обходчик L3 не исполняет L2. Вызов после эффектов не перезапускают другим движком.

Объявление ресивером места в `code`, в том числе записанное внутри inline-`if`/`for`, — вызов ресивера: проверка типа с присваиванием в подготовленное одноимённое место выбранного `data`; повтор такого объявления — та же проверка с присваиванием, второго поля не возникает, а значение без объявления записывает `name := value` ([§21](#lowlevel-expression)). Нового поля в `code` объявление не создаёт. Структурная запись в `code`, включая `name: ... end: name`, — вызов своей головы, а не объявление и не запись в `data`; объявления Structure пишут в данных, а объявления `fn`, `sub`, `catch` остаются и в коде и сохраняют собственный контракт ресиверов (решение автора 2026-11-11, [роли `data` и `code`](LMX_semantics.ru.md#data-code-roles)). Карта `data` учитывает головы коренного уровня, но не головы внутри их инициализаторов; записи вызовов и ресиверов управления в данных — тоже Structure, названные своей головой: к ним ведут пути вида `data\if`, к вложенным — `data\if\if`, с индексом при нескольких. При одном исходном вхождении головы допустим путь `data\field`, при двух и более требуется `data\[N]field` с нулевым `N`: повторное объявление в данных — ещё одно вхождение имени, оно прежнего не заменяет и в него не пишет, первое вхождение автоматически не выбирается, и обращение без индекса ошибочно (уточнение автора 2026-11-11, [журнал](../LMX_blog/2026-11-11.md#repeat-is-check-and-assignment)). Вложенность в `code` не выбирает другое место. Произвольный `data` не дополняется при вызове: если требуемого места нет либо голое обращение неоднозначно, отказывает допуск вызова ([§14](#implements)), а не сама форма записи при трансляции. Подготовка части `data` метода заранее выделяет её поля отдельно. Только явный вызов `call`, запуск Structure записью по имени (то же действие) или вызов метода, включая `fn`, создаёт новую область связывания, где собственное поле может затенить внешнее. Внутри одного callable затенения нет: inline-`if`/`for` — операторы той же активации, а не новые области, хотя они тоже Structure.

Нулевой адрес транспортной ячейки аргумента означает отсутствие аргумента; присутствующий аргумент со значением нулевой ссылки остаётся присутствующим. Число передаётся в хранилище объявленной ширины, объектная ссылка — через каноническую ячейку указательного значения. Статус callback и возвращаемое значение различны; контракт результата отличает `void` от присутствующей нулевой ссылки.

<a id="native-structures"></a>
### 11.1. Обычная Structure и общий native

Доступная транслятору Structure C, используемая как код, получает native общим с методами выпуском тела
и входом/выходом кадра. Один C.native работает с любой допущенной D через `call(D C)`, включая иной порядок
полей; именованность C, объявление fn/sub и data = code не требуются. Использование S только как данных
не требует её собственного native. Ресивер native(S) читает вход и не компилирует S.

При запуске существующие допуск, карта мест и кадр связывают данные; разрешённые адреса и типизированные
рабочие значения используются повторно. Dirty данных и кода публикуется на штатных границах, после
вычисления аргументов перед передачей управления, на предусмотренных выходах и при yield.
Публикация кода снимает затронутые входы до нового/рекурсивного dispatch, а запись обычных данных сохраняет их.
Обнуление native не заменяет инструкции активного входа и не повторяет эффекты. Обходчик использует
подготовленный кадр с тем же продолжением, в том числе после публикации и вложенного вызова.
Искусственный метод, полная копия графа, постоянные версии и hot-patch/deoptimization не требуются.
Динамически выбранная скомпилированная C использует native, подходящее runtime-тело без входа — обходчик.
Это норма; реализация **OPEN** в [M14](../next_core_tasks_v3.md#native-structures).

Единая семантика публикации не требует универсального журнала присваиваний. Native по возможности
статически определяет записи и условия их публикации, без поиска или выделения памяти на каждую запись
и без обязательного динамического dirty-флага. Динамическим местам достаточно необходимого учёта
локальных изменений в кадре, прямых — в общем кеше исполнения. Оптимизация сохраняет вычисления, проверки, эффекты, чтения через
алиасы и момент наблюдаемой публикации.

<a id="direct-access-cache"></a>
Локальное рабочее значение принадлежит активации и после вложенного вызова автоматически не перечитывается.
Кеш прямого доступа общий для всех вызовов одного исполнения, включая native/обходчик, и прозрачен:
путь, индекс и разыменование одной физической ячейки видят её актуальное общее значение, включая ожидающие
прямые записи. Публикация локального dirty тоже обновляет это состояние. Между независимыми исполнениями
кеш не сохраняется. Основание p в p\x может быть локальным указателем; изменение промежуточной ссылки
требует заново установить конечный адрес, а не использовать устаревший путь. [Норма](LMX_semantics.ru.md#direct-access-cache).

Обычный не объявляющий ресивер `flush()` без аргументов и результата сначала публикует dirty собственных
локальных значений текущего кадра в общее состояние в прямом порядке полей, затем сохраняет ожидающие
записи общего кеша в граф и продолжает исполнение. Локалы других кадров не затрагиваются.
Он использует штатную публикацию и инвалидизацию кода, без нового
кадра, выхода, yield или публикации Message. Вложенные if/циклы используют тот же кадр. Успешная публикация
снимает соответствующие dirty-отметки; повторный flush без изменений ничего не пишет, не перевычисляет
выражения/допуск и не перечитывает локальные значения. Общий кеш согласуется с опубликованными ячейками.
Голый атом не вызывает ресивер; `flush()` в data — обычная Structure.
Форма `flush:` имеет тот же контракт. [Норма](LMX_semantics.ru.md#flush-receiver-contract); код M14 остаётся OPEN.

<a id="child"></a>
## 12. Резервация ребёнка

Ребёнок строится в собственной арене. До успешной публикации его нет в `Thread.children`; публикация в конце хода добавляет физическую ссылку в этот List, не меняя исходный граф. Неуспех снимает резервацию, но не откатывает произвольные уже сделанные записи графа.

Переподчинение проверяет, остаются ли владельцы используемых ребёнком ветвей `independent: immutable` в новой цепочке Message-предков. Отказ не меняет членство и `Thread.parent` частично. `adopt: msg newParent` выполняет перенос; `independent: msg newParent` отдельно готовит именно этот перенос, копируя только мешающие ветви в арену `msg` и не меняя родителя. Это операции над иерархией Message, не над `Lmx.parent`.

<a id="copy-merge"></a>
## 13. Копирование графа и merge

`merge` строит новый граф с одной картой адресов источник→копия. Карта сохраняет общие цели и циклы, переписывает внутренние ссылки и `parent` на копии и не создаёт отдельного экземпляра для каждого `lnk`. Копируется весь используемый граф, включая исполняемые записи операций; исключение — квалифицированные `independent: immutable` ветви, явно удерживаемые владельцем. Неизменённая подходящая нативная реализация может использоваться повторно только при сохранённом контракте адресов и типов используемых полей. Неполная копия с адресами освобождаемой исходной арены недопустима.

Первый операнд задаёт порядок слотов модели; совпадающее поле следующего операнда заменяет значение этого слота после допуска, новое дописывается в новом результате. Исходные операнды не меняются. Семантика выбора тела и аргументов — в [L3 §20](LMX_semantics.ru.md#composition).

<a id="implements"></a>
## 14. implements

Доказанное соответствие между используемыми полями принимающей модели и физическими полями кандидата для допущенной пары Structure — данные того приёма или обхода, который его установил (решение автора 2026-11-08 о служебных таблицах обхода, подтверждённое Codex; [спецификация реализации §5.2](kernel-implementation.ru.md#tables)): приём удерживает свою карту на время нужных ему операций — чтения, записи, взятия адреса и прямой публикации готовых `dirty`-значений, включая разные порядки полей, — а следующий обход строит её заново из графа; постоянного хранилища соответствий у арены нет, отдельной карты для `call` или `data` нет. Интерфейсная часть `implements` выполняется один раз для каждого кандидата: при построении чистого графа, если кандидат известен, или при исполнении, если кандидат выбирается динамически ([случаи](../steps/implements-runtime-cases-20261111.md)). При построении графа `test` не исполняется; для динамического кандидата он является вторым шагом допуска ([уточнение автора 2026-11-13](../LMX_blog/2026-11-13.md#implements-and-test-phases)). Присваивание примитивов при исполнении на допустимость не сверяется (решение автора 2026-11-11, [L3](LMX_semantics.ru.md#data-code-roles); правило говорит о допуске `implements`, а не о преобразовании: проверка диапазона при приёме числа другого типа, `u16(256)` в `u8`, остаётся при исполнении); трансляторы этого правила ещё не исполняют ([план](../next_core_tasks_v3.md#m11)). В данных каждая объявляющая запись — вхождение имени: единственное вхождение адресуется `s\field`, при двух и более имя адресуется только с индексом вхождения — повторное объявление прежнего не заменяет и в него не пишет ([L3](LMX_semantics.ru.md#fields)); `s\[N]field` с нулевым `N` адресует N-е вхождение имени — запись данных, объявляющую это имя, — а не элемент Array. Карта не ищет имена в runtime, не копирует кандидат и не отменяет проверок нового Consumer. Семантика допуска и явно заданных тестов — в [L3 §7](LMX_semantics.ru.md#admission).

<a id="gc"></a>
## 15. Сбор

GC принадлежит арене. Корни включают Message, живой граф, почту, состояние исполнения и `Thread.children`; последний List удерживается состоянием Thread независимо от исходных полей. От живого значения сборщик следует также по установленному соответствию `implements` к Structure его требования: замена поля графа не освобождает модель, пока действующий допуск к ней нужен этому значению. Временный кадр допуска не удерживается этим правилом; уход кадра удаляет зависящую от него запись. Это зависимости адресного доказательства, а не скрытые поля графа. Созданные `independent: immutable` ветви удерживаются владельцем до уничтожения его арены. Простой режим не выполняет сбор. Правило выгрузки позднего модуля требует отдельного контракта и здесь не изобретается.

<a id="special"></a>
## 16. Специальные операции L2

Ядро предоставляет классификацию адреса, выделение ячейки, attach/revert арены, почту, ход Thread, вызов, резервацию ребёнка, копирование/merge и сбор. Эти операции не создают второго пространства имён или вспомогательного графа исполнения.

<a id="lowlevel-scope"></a>
## 17. Машинный профиль

Машинные типы L2 сохраняют представление и числовую семантику соответствующего типа C99 целевой платформы, в том числе знаковость обычного `char`. L3 не получает сырую память только потому, что его граф реализован указателями. L1 имеет отдельную C-подобную поверхность.

<a id="lowlevel-address"></a>
## 18. Адреса, загрузка и запись

Адреса полей, возвращённые [descriptor](#get-descriptor), — настоящие типизированные места:
`Lmx **`, `LmxEntry *`, `size_t *`, `void **`. Это отличается от адреса обычного графового
слота `void **`: его нельзя произвольно читать как `Lmx **`, тогда как само поле S.parent
действительно имеет тип `Lmx *`. Даже при совпадении адресов S.parent и S явное разыменование
читает поле по его типу. Загрузка и запись общие для любой конечной глубины указателя,
включая ссылки и указатели на функции. Явный путь `S\field := value` и разыменованная запись
не являются присваиванием по голому имени Structure или функции и не запрещаются этим правилом.

M3 упорядочивает плоские объявления как имя, требование/значение. Место объявляет форма `@:` с перечислением аргументов: `@: p 0`, `@: p Model`, `@: p Model 0`, `@: p Model Other`; запись с местом во внешней голове (`ptr: @: Model: 0`), которую допускали N1–N6, снята решением автора 2026-11-10 ([семантика](LMX_semantics.ru.md#receiver-args-only)). Первое поле — атом имени места и не вызывается; остальные поля потребляются по обычному правилу выражений: аргументы ресивера разбираются общим алгоритмом и читаются как код. Требование с кандидатом записывается плоско, тремя полями: `@: p Model Other`, нулевой адрес — `@: p Model 0`. Вложенная форма `@: p Model: Other` требования с кандидатом не записывает: `Model: Other` в аргументах ресивера — вызов `Model` (следствие решения автора 2026-11-11 о разборе аргументов, [роли `data` и `code`](LMX_semantics.ru.md#data-code-roles); чтение исполнителя — [ответы](../LMX_blog/q/fable-self-answers-20261110.md), О4); запись запуска Structure на месте, где нужно значение (операнд выражения, фактический аргумент вызова, начальное значение, операнд `merge`), ошибочна: у запуска результата нет (чтение исполнителя, Р22, пункт 3; Р25, пункт 4). P0 не выделяет эти формы: разбор общий, роли полей задаёт контракт `@:`. Первое `@: p` или `@: p 0` создаёт void-ссылку; последующая запись адреса не добавляет ей задним числом требование. Указательная глубина `@ⁿ:` не ограничена особым числом.

В `@: ptr method` ресивер `@` стоит первым, а `ptr` и `method` — голые атомы: атом не является вызовом. Поэтому форма присваивает ссылку в `ptr` по контракту `@`, даже если `ptr` уже содержит callable; `ptr(args)` вызывает его. Унарное `@ptr` отдельно берёт адрес ячейки ссылки. Подробные правила особого имени `data` и этих форм — в [L3](LMX_semantics.ru.md#ordinary-var) и [присваивании ссылки на метод](LMX_semantics.ru.md#method-reference-assignment).

Унарное `@x` адресует настоящую ячейку значения: для графовой Structure/Array — слот `void *`, содержащий ссылку на дескриптор, для примитива — типизированную ячейку, для формала и скрытого входа из динамической или лексической видимости — собственную локальную ячейку активации. Голое `x` и `@x` относятся к одной локальной переменной; запись не меняет источник связывания. Адрес внешнего поля задаётся явно, например `@(node\x)`. Слот, его адрес и референт различны. Нативное обращение к графовому ссылочному слоту идёт через `void **` с конверсией хранимого `void *`; разыменование этого слота как `Lmx **` нарушает C99. Адрес не берётся у временного кэша или ABI-буфера. `@x\field` по приоритету означает `@(x\field)`.

Префикс `\p` следует ссылке; `p\field` обращается к графовому полю либо к явно импортированному машинному ABI в зависимости от категории `p`. `@array[i]` адресует реальный элемент backing. В L2 индекс не получает автоматической проверки границ; проверяемый доступ принадлежит L3. Адресная операция не снимает `const`/`immutable` и не продлевает срок жизни цели.

<a id="lowlevel-array"></a>
## 19. Сырое C-хранилище

Токен `c.*` — явная дверь в C. Языковой Array остаётся объектом графа на общей основе `Lmx` с типизированными элементами; сырой C-массив им не становится. Переход между ними требует явной операции, учитывающей форму и время жизни. Типизированные массивы арены — внутреннее хранилище, не ещё один вид языкового Array. L2 не вводит особую сущность `c.array`.

<a id="lowlevel-abi"></a>
## 20. Внешние типы и ABI

`cast: (T) value` — машинное приведение, не проверяемое преобразование L3 и не доказательство границ, выравнивания или времени жизни. `c.name` выбирает внешний C-символ; адаптер определяет параметры, результат и владение. `c.sizeof` означает C `sizeof`, не длину Array и не число полей Structure. `include` и `os` выбирают явно заданные зависимости и платформенную ветвь, не вводя runtime-поиск модулей.

`os` выбирает целевую платформенную ветвь, но не вводит отдельного сравнения ветвей на равенство наборов методов, сигнатур или сериализованных контрактов. Различия между ветвями сами по себе не являются ошибкой. Выбранные объявления и тела проходят обычные механизмы L2; там, где принимающее место требует совместимости, применяется обычный `implements` и его адресная карта, как вне `os`. Выбор ветви не создаёт дополнительного общего интерфейса или частного `os`-варианта допуска. [Уточнение автора, 2026-10-23](../LMX_blog/2026-10-23.md).

Существующий ресивер `os` выбирает ветвь для целевой платформы до смысловой обработки её содержимого; отдельный новый оператор для этого не нужен. Общий структурный разбор выделяет ветви, но невыбранные объявления и тела не проходят разрешение имён, проверку типов и контрактов, сбор зависимостей или генерацию кода. Их `include`/`define`/`predef` не добавляют зависимости и объявления в выбранный вариант. Выбранное содержимое проходит тот же общий L2-конвейер, что вне `os`, включая обычный native и обходчик для поддерживаемых тел, без частного разбора, исполнителя или запасного native-маршрута. Целевая платформа согласована на всех стадиях трансляции, а не случайно определяется платформой запуска транслятора. Это утверждённое направление реализации, не заявление о завершённой поддержке. [Уточнение автора, 2026-10-23](../LMX_blog/2026-10-23.md).

Платформенные заголовки и имена, встречающиеся только в невыбранной ветви, не требуются для выбранного варианта. Его обычный код может обращаться к методу, объявленному только в выбранной ветви, без объявления аналога в остальных. Трансляция всех альтернатив в L1/C с последующим скрытием невыбранных через C `#ifdef` этому правилу не соответствует; их зависимости, объявления и тела не генерируются. Общий структурный разбор исходника не означает смысловую трансляцию невыбранной ветви. [Уточнение автора, 2026-10-23](../LMX_blog/2026-10-23.md).

Указанное отсечение ветвей — обязанность трансляции. Оно не требует сохранять результат её выбора или подготовки как условие работы обходчика: тот исполняет текущий граф по [§2.1](#interpretable-tree), не обязательную запись транслятора о выбранном теле.

`implements` остаётся обычным допуском выбранного содержимого, а не статическим сравнением альтернативных платформенных реализаций и не механизмом отключения их трансляции: он выполняется один раз, при построении чистого графа, а при исполнении — только там, где кандидат выбирается во время исполнения (решение автора 2026-11-11, [§14](#implements)). Если далее потребуется дополнительное средство языка, его общее решение обсуждается с автором; для указанного выбора существующим `os` повторное согласование нового оператора не требуется.

В вычисляемом вызове через C-дверь C-функции и макросы получают заранее вычисленные L2-значения, не подстановку текста L2-выражений. L2-аргументы вычисляются один раз в обычном лексическом порядке и по обычным правилам выхода до передачи внешнему вызову; развёртка макроса не повторяет и не отменяет это вычисление. Поэтому при `#define BYTES(x) sizeof(x)` вызов `c.BYTES(touch())` сначала выполняет `touch()` один раз и передаёт его значение макросу, хотя C не вычисляет операнд получившегося `sizeof`. Это также относится к макросу, который использует параметр несколько раз или не использует его.

Буквальный `c.sizeof` имеет роль оператора C, а не вызова C-функции: после общей подготовки его операнд подчиняется правилам C99 `sizeof`, не предварительному вычислению аргумента внешнего вызова. Развёртка произвольного макроса в `sizeof` не передаёт ему эту роль. Различие определяется семантической ролью после общего разбора, без регистрации C-имён или второго парсера. Для обычного типа без переменно-модифицированных компонентов `c.sizeof(touch())` не выполняет `touch()`; правила C99 для variably modified типов этим не отменяются. [Уточнение автора, 2026-10-22](../LMX_blog/2026-10-22.md).

У C-двери есть и обратное направление: машинную функцию L2 можно экспортировать с прямым C-совместимым входом. C-код вызывает её явными аргументами функции, без экземпляра `Lmx`, корня, Message и подготовленного графа; нужные ей состояние и память она получает своим обычным явным контрактом, а не скрытой общей единицей, ареной или singleton. Функция остаётся тем же L2: существующий генератор переводит её общим структурным разбором, разрешением выражений и проверками, без отдельного C-подобного языка, второго парсера или resolver и без маршрута только для List или библиотек. Обычные графовые вызовы L2/L3 сохраняют свой общий механизм; экспорт не снимает семантику с произвольного `fn`. Поддерживаемые исходники остаются L2/L3, их L1/C генерируется; перенесённое тело заменяет старое без постоянного fallback. Это утверждённое направление реализации, не заявление о завершённой поддержке. [Уточнение автора, 2026-10-23](../LMX_blog/2026-10-23.md).

<a id="lowlevel-expression"></a>
## 21. Машинные выражения

Машинный профиль включает группировку, арифметику, сравнения, логику, битовые операции, `++/--`, индекс и обычное управление. `=` в выражении — сравнение; запись — `target := value`. Прежняя запись `target: value` при трансляции присваиванием больше не служит (решение автора 2026-11-10, [L3](LMX_semantics.ru.md#forms-declare-or-call), [журнал](../LMX_blog/2026-11-10.md#forms-declare-or-call)); формы ресиверов с перечислением аргументов, `int: i 5` и `@: p q`, действуют как прежде. Исходные тексты проекта пишут `target := value`; прежней записи транслятор отказывает, и сообщение называет `:=` ([план](../next_core_tasks_v3.md#m7)). Переполнение и сырой индекс следуют машинному контракту, не обещаниям L3. `a[i][j]` адресует ровный многомерный Array; `a[i]\[j]` следует через ссылку к отдельному Array. `s\[N]field` в Structure-as-data выбирает исходное вхождение, а не машинный элемент Array.

<a id="lowlevel-sync"></a>
## 22. synchronized

`synchronized: lock code` задаёт структурную область взаимного исключения, не открытую пару lock/unlock. Выход освобождает monitor. Почтовый monitor — конкретное реентерабельное применение без `wait`/`notify`; сырых блокировок в чистом L3 нет.
