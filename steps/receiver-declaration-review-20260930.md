# Объявление, инициализация и передача аргументов: исследование

Дата: 2026-09-30. Источник — [реплики автора в Q56](../LMX_blog/q/q56.md).
Статус: исследование и обсуждение; реализация остановлена по просьбе автора.
Проверены документы и код на `6a3ac8d`; предшествующий resolver/native/runtime
WIP в `build/opus_wt` сохранён и не является доказанной новой семантикой.

## Исправление ошибочного статуса предыдущей редакции

В `6a3ac8d` Codex ошибочно назвал обсуждаемые предположения уже принятыми
правилами и записал отмену неявного merge как задание. Эта интерпретация
отозвана, включая прежний раздел «Точная граница будущей реализации».
Не было разрешения менять правила, зависимые тесты или убирать `@` из L3.

Последнее уточнение автора сохраняет прежний смысл `A: b` как построения
через merge. `int: i` оставляет неизвестное значение в выделенном месте,
а не отсутствие значения: отсюда нельзя вывести пустую ссылку для `A: b`.
Общая композиция ресиверов и их способность потреблять несколько аргументов
не вводят специального правила «вложенная цепочка означает инициализацию».

## 1. Что действительно показала проверка парсера

Проверка существующим `build/fable127_printTree/printTree.exe`:

```text
int: b 5       -> Frame int [atom b, atom 5]
int: b: 5      -> Frame int [Frame b [atom 5]]
int(b: 5)      -> Frame int [Frame b [atom 5]]
int:           -> Frame int [Frame b [atom 5]]
    b: 5
---
a: b: c: d     -> Frame a [Frame b [Frame c [atom d]]]
```

Эти формы уже представлены обычными деревьями. Само дерево не доказывает
равенства их смысла. `int: i 5` предоставляет имя и начальное значение как
два аргумента. Ресивер определяет, какие операнды и в какой роли потребить;
вложенное применение не следует автоматически разворачивать в плоский список.

Автор привёл `int: i: j: getValue(j): 5`: int потребляет имя i, затем
возникает попытка вызова i, то есть ошибка. Требуется общий алгоритм
разрешения, который сохраняет эту границу; не цепочка особых распознавателей
и не доказательство равенства `int: i: 5` и `int: i 5` по их внешнему сходству.

Происхождение замера: старый готовый printTree от 2026-09-23, SHA256
`0956054E093428CF4FAE060DA0A2FCF6C47C565F2231182683178B3845202040`;
исходник пробы — `build/receiver_declaration_probe_20260930.lm2`.
Это диагностическое свидетельство формы, не свежий gate парсера текущего HEAD.
В той же пробе `a[i]\[j]\[k]` сохраняет все индексные/backslash-токены,
а `a[i]\[j]: 5` приходит как Frame с составной головой.

## 2. Что снято вместе с предположением о пустой ссылке

```text
A: b
b: c
b()
```

В первой строке не отменено построение b. По уточнению автора, при известном
c вторая строка вызывает b(c), при неизвестном c применяется то же правило
построения, что в первой строке. Прежний вопрос «заполнить пустой b или
вызвать его?» был следствием неверно принятого предположения о пустой ссылке.
Не нужно решать его проверкой null или новым оператором присваивания.

Явно объявленная ссылка и вызываемое структурное значение различаются.
Последний пример автора использует присваивание ссылок `e: c` и обращение
к референту `\e: d`; это не изменение роли `A: b` в ссылочное объявление.
Полные примеры сохранены дословно в Q56. Их запись `@: c b` / `@: e A`
нельзя молча переписать в прежнее `@: Type var`: согласование формы ссылки
не завершено этой заметкой.

Норма: [семантика §9](../docs/LMX_semantics.ru.md#construction),
[§11](../docs/LMX_semantics.ru.md#callables). Код: `l2_colon_bound_before`,
`l2_check_struct_call`, `l2_check_body`, `l2_colon_bind_shape`.

## 3. Найденное расхождение: новое значение и сохранённая ссылка

Автор уточнил: при неизвестном d запись `A: d b` аналогична `int: i 5` —
выделяется место для нового значения, которое инициализируется кандидатом;
это не просто связывание d с существующим b. Предыдущая реплика автора
оборвалась на «то есть»; её продолжение не следует дописывать за автора.

В текущем тексте и коде зафиксировано другое:

- [Семантика §9](../docs/LMX_semantics.ru.md#construction), строка 567
  среза `6a3ac8d`: `A: b c` при неизвестном b связывает b с существующим
  дескриптором c без копирования; это уподоблено заполнению формала `(A: b)`.
- [L2 §13](../docs/L2_spec_ru.md#copy-merge) повторяет эту трактовку.
- `dev/l2src_sandbox/l2trans.lm1`, `l2_emit_stmts`, строки 32212–32234
  того же среза: ветвь `l2_colon_bind_shape` вычисляет кандидата, выполняет
  нужный admission и передаёт его дескриптор в `l2_own_store`; merge отсутствует.
- Там же `l2_rw_model_bind`, строки 24443–24484: walker строит
  `PUT_REF(b, OWN(c))`, при необходимости через admission, также без merge.
- Соседнее объявление без кандидата, напротив, вызывает `lmx_merge_owned`
  (native) либо `lmx_walk_merge_model` (walker).

Это свидетельство расхождения, не основание предпочесть реализацию словам
автора. Выделить только новую ячейку и положить в неё прежний дескриптор —
ещё не создать отдельное структурное значение: референт останется прежним.

Нужно раздельно рассматривать три действия: допуск кандидата по `implements`,
создание/инициализацию значения и передачу аргумента. Способ передачи
дескриптора не определяет действие принимающего выражения. Получатель может
использовать переданный по ссылке источник для построения значения, не
передавая C aggregate по значению. Но это не тождественно прежнему обещанию
сохранить идентичность кандидата в формале.

Открытая граница обсуждения — одинаковый смысл объявления с кандидатом в
теле и заполнения формала. Нельзя одновременно обещать новое структурное
значение для `A: d b`, прежнюю идентичность b в формале `A: d` и называть
это одной операцией без различающего общего правила. Конкретный механизм
инициализации и итоговое правило формалов здесь не выбираются.

## 4. @ в L3 не удалён

Снята предпосылка, будто `A: b` уже заменяет явное объявление ссылки.
В документах также обсуждались самостоятельные возможности:

- ссылка на примитивную ячейку вместо копирования её значения;
- ссылки большей глубины;
- получение ссылочной идентичности без вызова/вычисления результата;
- различение привязки и вызываемого референта.

`int: x 5` / `int: y x` даёт копирование значения, не псевдоним ячейки x.
Но возможность добавить псевдоним не доказывает необходимость его в L3.
Не найдено требования ядра L3, которое заставляло бы переносить туда
ссылки на примитивные ячейки или большую адресную косвенность. Примитивы
могут оставаться значениями, Structure/Array — обычными ссылочными значениями;
явное изменение общего состояния уже выражается путём к полю/элементу.

Важная поправка к предварительному выводу Codex: нельзя ссылаться на
работающие адресные операции L2 как на якобы уже необходимую возможность L3.
В текущем `l2_rw_ref_bind` высокоуровневый маршрут ограничен ссылкой на
существующую Structure, а `l2_rw_stmt` после `l2_own_ref_decl` отправляет
остальные @-формы в отказ машинной операции. Универсальная primitive-alias /
reference-to-reference возможность L3 этим кодом не доказана.

Перечисление этих возможностей не доказывает их необходимость, но и
отвергнутая гипотеза о пустой ссылке не позволяет удалить @. Последнее
объяснение автора использует явные ссылки. Никакого сокращения L3 или
изменения машинных операций @ в L2 этим исследованием не принято.

## 5. Отдельные старые расхождения, обнаруженные при проверке

Они не порождены новым предложением; использовать их как норму нельзя.

1. Семантика §12 сначала разрешает `@value` в L3, затем таблица запрещает
   `@x`, а следующий абзац снова запрещает prefix address-of. Грамматика
   дополнительно запрещает глубины `@@:`, разрешённые той же семантикой.
   Последние авторские решения нужно провести по всем связанным абзацам.
2. Семантика §9/L2 §18.1 ещё пишут `@fresh -> Lmx**`, тогда как L2 §18.2,
   CORE и Q26.2 адресуют сам референт Structure, не child-slot. Это старая
   несогласованность смысла адресуемого объекта.
3. CORE §4 сохраняет старый приоритет callable до объявления и описывает
   Model как non-callable, хотя обычная именованная Structure вызываема.
   Он также ошибочно называет `Model: fresh` при известном fresh присваиванием.
   Семантика §9 уже различает отсутствие и присутствие правого имени.
4. `lmx_copy_value` копирует прямую ссылку на Structure вместе с её целью,
   но pointer-ячейку @ копирует с удержанием прежнего изменяемого pointee;
   это закрепляет `lmx_copy_ptr_share_selftest`. Текущий §20 требует копии
   достигнутого обычного изменяемого графа. Согласование политики обхода
   явных ссылок при merge требует отдельного разбора; новая декларационная
   семантика в качестве обходного решения не вводится.
5. `lmx_merge_profiles_owned` всё ещё создаёт корень с пустым native
   независимо от сохранности кода; §20 требует сохранять native неизменного
   тела. Это отдельное расхождение, не следствие обсуждения объявлений.

## Состояние после исследования

Исправлены ошибочные утверждения самого исследования и плана. Нормативные
спецификации, код и тесты здесь не изменены. Не выполнять прежнее задание
убрать неявное построение, не продолжать самосборку во время этой паузы.
Предшествующий resolver/native/runtime WIP сохранён. Обсуждение инициализации
и формальных аргументов не объявлено завершённым.
