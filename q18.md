# Q18. Дескрипторы динамических массивов: `Array` / `DynamicArray`

Состояние: 2026-09-23, открыт. Просьба автора (чат fable, дословно): «Найди везде где сейчас динамические массивы и приведи их дескрипторы к такому виду (разумеется вместо void можно использовать тот тип, какой нужен)»:

```c
typedef struct Array {
    size_t len;
    void * data;
} Array;

typedef struct DynamicArray {
    Array array;
    size_t capacity;
} DynamicArray;
```

## Что есть сегодня (инвентарь ядра `dev/l2src_sandbox`, read-only, на `edd3f8f`)

Базовый дескриптор уже совпадает по форме: `LmxArrayDesc {size_t len; void *data}` (`lmx.h.lm1` :206–:209) — отличается только именем. Узел графа: `Lmx {Lmx *parent; int len; void *data}` (:65–:69) — форма «массив внутри» ещё не введена (утром через Codex принято `VoidArray {size_t size; void *data}` и `Lmx {VoidArray array; Lmx *parent}` как план без реализации, `next_core_tasks.md` §1 :52–:63).

Динамические (с capacity) массивы ядра — шесть мест:

| # | Место | Сегодняшняя форма | Что это |
| --- | --- | --- | --- |
| 1 | L1 List (`lmx_list_owned.lm1`) | публичный `LmxArrayDesc {len, data}`, **capacity спрятана в префиксе backing** (`size_t cap`, затем `cap` ячеек); `LmxListDesc` не экспортируется | динамический контейнер языка (членство детей Thread — `KIND_LIST`) |
| 2 | Индекс арены (`lmx_arena.h.lm1` :19–:24) | `LmxArena { … @: LmxRange index; size_t count; size_t capacity; …}` — три поля вразбивку | растущий массив диапазонов адресов |
| 3 | Сервис (`lmx_service.h.lm1` :57–:61) | `LmxService {@: LmxServiceEntry entries; size_t count; size_t capacity}` | упорядоченный массив записей |
| 4 | Ящик Thread (`lmx_post.h.lm1` :127–:131) | `inbox_slots` + `inbox_capacity` + `inbox_head`/`inbox_tail` (кольцо пар `[target, source_arena]`) | подвижный динамический массив-кольцо под монитором |
| 5 | Пул (`lmx.h.lm1` :260–:266) | `LmxChunk {@: void base; size_t capacity; size_t count; @: LmxChunk next; unsigned mark}` — цепочка чанков | кусочное растущее хранилище typed-массивов |
| 6 | Копир графа (`lmx_graph_copy_owned.lm1` :7–:150) | приватные hash-map и стек: `keys/vals/n/cap` через `malloc` | внутренняя структура одного алгоритма |

Вне ядра (не трогаю без указания): таблицы транслятора `l2trans.lm1` (~107 упоминаний capacity/`_cap`), парсер `l1src` (`lm_own_*`), `dev/l3_interp` (3).

## Вопросы

**Q18.1 — имена и поля.** Утром через Codex принято `VoidArray {size_t size; void *data}`, теперь — `Array {size_t len; void *data}`. Считать сегодняшнюю форму окончательной: тип `Array`, поле `len` (утренняя запись заменяется)? И C-имена буквально `Array`/`DynamicArray` (без префикса `Lmx`, как все остальные типы ядра — `LmxArena`, `LmxPool`…) или `LmxArray`/`LmxDynamicArray`?

**Q18.2 — «вместо void тот тип, какой нужен».** В C это означает **несколько** struct-типов одной формы (`{size_t len; Lmx **data}`, `{size_t len; LmxRange *data}`, `{size_t len; LmxServiceEntry *data}` …), а не один тип. Утреннее решение говорило «ровно один C-тип для отдельного Array и вложенного `Lmx.array`». Что верно: (а) один `Array` с `void *data` везде (приведение типа в месте использования, как сейчас у `LmxArrayDesc`), или (б) по одному struct на тип элемента с одинаковой раскладкой (`LmxArray`, `LmxRangeArray`, … и `DynamicArray` над каждым)?

**Q18.3 — объём.** Все шесть мест таблицы? В частности: (1) List — экспортировать `DynamicArray {Array array; size_t capacity}` вместо скрытой capacity в префиксе backing (тогда `LmxListDesc` становится публичным `DynamicArray`, а «базовый Array без capacity» сохраняется как его первое поле); (2)–(3) индекс арены и сервис — заменить тройки полей на `DynamicArray`; (4) ящик — `DynamicArray` + `head`/`tail` (кольцо остаётся кольцом); (5) чанк пула — `DynamicArray` + `next` + `mark` (цепочка остаётся); (6) приватная hash-map копира — тоже, или это внутренность алгоритма и не «массив» в смысле ядра? И: узел `Lmx` в этой же работе переводится на `{Array array; Lmx *parent}` (массив первым, как решено утром), или это остаётся отдельной запланированной миграцией?

**Q18.4 — режим и исполнитель.** Утренний `VoidArray` был «документация и план, не реализация». Эта просьба — реализовать в ядре сейчас (код + документы RU/EN синхронно + гейты) или тоже сначала документ/план? Если код: единственный писатель ядра — предлагаю Grok Bot (свободен после -127) под моим ревью; Opus на S1.1 (транслятор/адаптер), Sonnet на -131 (транслятор) — они ядро не трогают, пересечений нет. Порядок: инвентарь → документы → гейты-свидетели (раскладка, `offsetof`, классификация диапазонов) → код одним SHA.

## Рекомендация

Q18.1: `Array`/`len` окончательно; имена с префиксом (`LmxArray`, `LmxDynamicArray`) — как у всех типов ядра, чтобы не столкнуться с `Array` языка L2 в документации. Q18.2: (а) один тип с `void *data` (как сегодня `LmxArrayDesc`) — иначе «ровно один C-тип» не выполняется. Q18.3: места 1–5 — да; 6 — да, если считать любую растущую последовательность массивом (единообразие), иначе оставить; `Lmx {Array array; Lmx *parent}` — включить, чтобы миграция раскладки прошла одним SHA. Q18.4: код сейчас, Grok Bot, документы и гейты до кода.
