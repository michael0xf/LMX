## 7. Как принимать сдачу помощника

Порядок, которым приняты срезы. Все команды — из каталога `S`; префикс запуска — `0 entry 0 --`.

1. Проверить, что сборочных процессов нет (`lmxtool-tool`, `l2trans`, `gcc`, `cc1`, `graph_trans-prod`), и что
   `HEAD` равен `origin/main`.
2. Дифф дерева сравнить со сданным по SHA-256; список новых файлов сравнить со сданным списком.
3. Манифест: `T ... manifest R/selfbuild/inputs.list R/selfbuild OUT.sha256`, затем
   `T ... verify OUT.sha256 R/selfbuild` и `T ... verify OUT.sha256 S`. Число файлов и SHA сверить со сданными.
4. Хэши tool, frontend, runtime, Graph. Runtime, собранный итоговым frontend, сравнить с кандидатом через `cmp`;
   Graph — после обнуления в PE полей TimeDateStamp и CheckSum. Слова помощника «frontend от правки не зависит»
   принимать только по пересборке и `cmp`.
5. Прочитать дифф: нет ли веток по имени ресивера, битовых флагов вместо нового кода типа, фиксированных
   пределов; закрыватель `---` только при спуске на два уровня; новых `end:` нет; пустых строк внутри блоков нет.
6. Свой прогон строк на итоговой цепочке — hosted frontend из итоговых исходников, runtime и Graph, собранные
   им. Брать все строки последней базы свидетелей, а не малый список помощника. Старые строки обязаны совпасть
   с базой, новые — с закреплением.
7. Свои пробы интерпретатором: `GRAPH 0 entry 0 -- run ФАЙЛ 1`, запуск из `S/src`. Граф строки-отказа сверяет
   сама команда `graph-check`, начиная с tool `ps-tool-r101`.
8. Мутанты помощника: последняя строка по каждому должна быть KILLED. Правило, у которого мутант неотличим от
   кандидата, получает свидетеля или снимается.
9. Свидетельство в `steps/witnesses/<имя>/` и правки READ.ME, плана, чек-листа, `steps/current.md`, журнала
   ответов и этого файла — скриптом, сначала на копиях. Пересоздать `selfbuild/inputs.sha256`.
10. `git add` по точному списку, проверка документов, и только при её успехе коммит и пуш одной цепочкой через
    `&&`. Перед коммитом вывести `git diff --cached --name-status` и сверить число файлов.

Проверка документов: создать каталог `O/docs-indexN`, перейти в него и выполнить
`T2 0 entry 0 -- docs check R R/provenance/semantics-sources/l1.txt R/provenance/semantics-sources/older.txt
C:/Git/cmd/git.exe O/docs-indexN`. Она читает рабочие файлы, поэтому перед ней ставится файл-метка
`O/tz-20261121/docs-check.running`, а помощники не начинают сборку и не пишут документы в дерево, пока метка
стоит. Подпись коммита: `git -c user.name=fable commit`, заголовок с `[fable]`.

Скрипты переноса редакции лежат копиями в `O/tz-20261121/fable/`: `transfer_docs.py`, `fix_moved_links.py`,
`scan_links.py`, `edit_plan_21.py`, `edit_docs_21b.py`. Прежние скрипты приёмки — в `O/scratch-backup-20261118/`.

## 8. Как вести помощников

- Задача — отдельным сообщением: норма со ссылками, границы файлов, что сдать, что не трогать. Жетон конвейера
  передаётся словами и только одному.
- Вопрос помощника сначала решать самому по написанной норме. Перед любым решением, которое закрепляет ожидаемое
  значение, искать решение автора по этому механизму: в требованиях `docs/TZ/`, в журнале за все дни и в книге.
  Ответ записывать в [журнал ответов](LMX_blog/q/fable-self-answers-20261110.md) с пометкой «ответил fable».
- Автору выносится только противоречие двух действующих требований — с обоими пунктами и различающим примером;
  вопрос сразу кладётся в `LMX_blog/q/current/`, коммитится и называется в чате. Работа при этом не стоит.
- Утверждение помощника о сегодняшнем поведении проверять однострочной пробой, прежде чем повторять автору.
- Субагентов и ревьюверов не запускать — ни мне, ни opus, ни sonnet; haiku этот запрет не передаётся.
  Проверка — настоящими прогонами.
- Сдачу помощник кладёт в каталог квитанций с файлом хода (`PROGRESS.md`) и отчётом (`REPORT.md`); по файлу хода
  видно, где он остановился, если сессия оборвалась.
- Запасной способ, которым шла работа 2026-11-19 и 2026-11-20: помощник отдельным запуском скрипта
  `python C:/claude/new/{sonnet,opus,haiku}_chat.py --session ИМЯ --cwd C:/Nyasha_Planet/LMX --prompt-file
  ПОРУЧЕНИЕ.md --out ОТВЕТ.md`. Запуск одноразовый: пробуждений в нём нет, сборки ждут на переднем плане.

## 9. Ошибки, которых не повторять

- Я отвечал помощникам по одному запомненному примеру, не найдя решения автора по этому механизму: блок
  вызовов под `call(C)` (Р101), вычисление аргумента до выбора (Р102), `S: a + b` как три поля (Р99), «`k(5)`
  сегодня принимается» (Р100), группа после результата у `fn` как код (Р104), `literal_line` как дефект
  (Р104). Каждый раз ошибку находил помощник или проба.
- Свидетелям «после отказа значение такое-то» я верил по строке, а строка-отказ граф не сверяла (Р104).
- Скрипты с обратными слешами через heredoc портятся; текст с апострофом в heredoc падает. Такой скрипт писать
  файлом, а слеш брать как `chr(92)`.
- Фоновый ожидатель при нехватке памяти убивает сама среда. Ждать сообщения помощника о сдаче.
- 2026-11-19 запуск fable шёл несколько часов без записи хода и был остановлен извне; продолжать пришлось по
  журналам сессий. После каждого крупного шага писать ход в файл рабочего каталога и не копить приёмку
  нескольких срезов в один конец.
- Число и принадлежность строки списку сверять с таблицей, а не с отчётом помощника.
- Малый список помощника не видел строку, сменившую вердикт. Свой прогон брать шире малого списка.
