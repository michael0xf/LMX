Принял. Уточнение автора о пропущенном аргументе name записано в журнал 2026-11-09. Метку «D открыто автору» в нормы не вношу. Схема, по которой иду (тот же порядок, что в OPUS-CODEX-FN-PLAN; рабочие примеры — `fn: prepared` и `fn: new_name merge(f1, f2)`):

1. Построитель строит каждую Structure-запись одним правилом, без конструкции, особой для fn: корень, литерал `( … )`, аргументы args/var/body, data-блок. Поле-объявление с примитивным типом и литералом или без значения — сжатое место (вариант 1): `int: x` -> uninit:int -> T с именем x, `int: r 0` -> ячейка int = 0 с именем r. С вычисляемым значением — Frame "int" [r, выражение]. Остальные Frame — Lmx с именем головы. Поэтому `(int: x)` одинаков в позиционной записи `fn: f (int: x) …`, в `args := (int: x)` и в поле заготовки prepared. Объявление fn в графе — Lmx "fn" с аргументами как написаны; var-аргумент построитель больше не автозаполняет.
2. Тело при исполнении: место-объявление, до которого дошёл обход тела, исполняет своё объявление на написанном месте. Литерал пишется в собственное место активации; место без значения проверяется без записи. Это прежняя семантика `[int, r, 0]` в теле, теперь над сжатой формой.
3. Применение ресивера fn или sub — одним путём при любой подаче. Общий связыватель получает name, args, return, var, body; затем один алгоритм строит результат F, Lmx в lmx:result:
- имя F — строка по значению name;
- поле "args" — именованная ссылка на переданную Structure args;
- "return" — именованная ссылка на требование; для слова — общая ссылка на примитив;
- "var" — новая Lmx: поля явной var плюс собственные объявления фактического body (места-объявления и Frame "int" [r, …] в теле и во встроенных управляющих телах; не во вложенных объявлениях и не в данных аргументов вызова). Поля, которых нет в args и в явной var, добавляются новыми местами без значения. Набор определяется до выделения, инициализаторы не исполняются, после публикации F число полей не растёт;
- "body" — именованная ссылка на переданное body.
Сборщик полей — временный, только этого применения. Явная var: её места F получает как новые места с теми же литеральными значениями (у каждого примитивного места своя ячейка). Ссылки на Structure-части без копии сохраняют их parent.
4. c5: контракт встроенного ресивера fn (формалы name, args, return, var, body) — обычная Lmx-сигнатура. Её строит начальное наполнение служебной области каждого обхода и регистрирует в его пустом namespace под каноническим словом fn (так же sub); на выходе обхода она отпускается. В LmxGraphState — только канонические строки. Результаты пользовательских объявлений и стандартные контракты различаются происхождением в общих алгоритмах.
5. Граница 333: подача всей Structure в хвосте после позиционного name (`fn: new_name merge(f1, f2)`) — расширение общего правила всей структуры аргументов, как в OPUS-CODEX-FN-PLAN. До его реализации эта форма явно отказывает как граница реализации, а не как запрет примера.
Код 332 пишу по этой схеме.
