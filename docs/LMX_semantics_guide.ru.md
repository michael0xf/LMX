# Пояснения к семантике LMX

Это ненормативные разборы примеров. Правила языка находятся в [спецификации семантики](LMX_semantics.ru.md); при расхождении действует она. Здесь можно подробно разбирать следствия, не превращая нормативный текст в журнал обсуждений.

<a id="callable-description"></a>
## Описание вызываемого при `merge`

В записи `fn: add5 (int: x) int merge(add; y: 5)` заголовок `add5` описывает принимающее место. Он не становится третьим операндом `merge`. В частности, заголовок с одним обязательным аргументом не удаляет остальные формалы из выбранного тела `add` и не меняет его машинный ABI.

Добавленное `y: 5` даёт формалу `y` значение по умолчанию. Это не передача значения из одноимённой переменной вызывающего и не удаление `y` из сигнатуры. Семантическая иллюстрация (не новая форма синтаксиса):

```text
add5: the formal y of add has the default value 5; x is required
add5(1)                        -> 6
add5(1; y: 25)                 -> 26    (y stays an explicitly passable formal)
add5(1; y: 0)                  -> 1     (zero is a supplied value, not an absent one)
caller holds its own y = 25, passes no y:  add5(1) -> 6   (a formal is not a free input)
add5(1; y: 25), then add5(1)   -> 26, then 6   (one call's argument is not a new default)
```

Если программа сама явно компонует структуры описаний, действует обычное правило `merge` для полей. Например, отсутствие `y` в дополнении `args = [x]` не означает удаления `y` из исходного `args = [x, y]`. Результат отдельно проходит [допуск](LMX_semantics.ru.md#admission), а свободные имена тела — обычное [динамическое разрешение](LMX_semantics.ru.md#dynamic).

<a id="callable-admission"></a>
## Что проверяет интерфейс вызываемого

Метод с формалами `x` и `y = 5` и метод только с `x` оба принимают вызов `f(1)`. Но записанный в Consumer вызов `f(1; y: 25)` принимает лишь первый. Проверяется каждое реально использованное обращение, а не равенство исходных списков формалов или предсказание поведения тела. Если ссылка на метод лишь передана дальше, будущие вызовы пока неизвестны и не анализируются как уже записанные. Поведение проверяют отдельные пользовательские тесты принимающего выражения.

<a id="method-pointer"></a>
## Имя метода и указатель на него

```text
fn: myFunc () int
    return: 7
@: ptr myFunc

myFunc()    # прямой вызов объявленного метода
\ptr()     # вызов через указатель
ptr()      # то же, что ptr: (); попытка присвоить пустую Structure
ptr: a     # попытка присвоить указателю значение a
```

Таким образом, одинаковая внешняя форма «голова с аргументами» не делает ссылочное поле методом. При `ptr()` проверка допустимости присваивания может дать отказ; это не повод выполнить метод вместо записи.

<a id="native-merge"></a>
## Нативное тело в копии

Полезно разделять данные экземпляра и исполняемый код. Копия метода с другими данными может исполняться той же нативной реализацией: ей передают граф копии. Если `merge` выбирает код другого операнда, адрес прежней реализации уже не описывает выбранный код; берётся реализация нового кода, если она есть. При отсутствии такой реализации готовый граф исполняет интерпретатор. Изменение значений в структурной части с именем `body` само по себе не доказывает изменения алгоритма.

Вложенные методы остаются полноценными копиями вхождений. Общим может быть адрес машинной реализации, но не изменяемый экземпляр с его лексическим состоянием. Разные физические позиции полей согласуются адресной картой успешного `implements`; карта может быть составлена через несколько композиций. Она не выбирает код и не служит таблицей имён исполнения.

<a id="factory-result"></a>
## Возвращённый метод

В этом примере `makeAdder(5)` действительно вызывается при инициализации ссылки, а `\add5(1)` затем вызывает возвращённый метод по адресу:

```text
fn: makeAdder (int: n) fn: (int: x) int
    fn: addN (int: x) int
        return: n + x
    return: addN

@: add5 makeAdder(5)
@: add100 makeAdder(100)

[\add5(1); \add100(1); \add5(1)]
```

Без динамического `n` у вызывающего ожидается `[6 101 6]`. Определение неизвестной головы `add5: makeAdder 5` не было бы вычислением фабрики. Значение `n` в скопированном лексическом дереве остаётся запасным источником свободного имени, а не скрытым замыканием, которое перекрывает динамический вход вызывающего.

## Динамический и лексический источники

Следующая таблица показывает разрешение свободного `x`, не формала метода; это иллюстрация, не синтаксис LMX:

```text
copied lexical context:  x = 10

read x       -> 25
read node\x  -> 10

no dynamic x from any source:       read x -> 10

```

<a id="message-conversion-context"></a>
## Контекст преобразований Message

`a → int`, `Foot → Meter` и стрелки ниже — схема отношений, не синтаксис LMX и не отдельная таблица имён в runtime. Описания, связи и преобразователи передаются как обычные значения графа.

```text
Message A:  a → int;     String → int
Message B:  a → String;  нет String → int
```

Один и тот же метод `fn: identity (a: x) a` может использоваться обоими Message: внутри A все употребления `a` согласованы с `int`, внутри B — со `String`. B не наследует преобразование A из-за родства или отправки сообщения. Это не инстанцирование нового generic-параметра при каждом вызове.

Для примитивных семантических значений `Foot → Meter` является обычным явно доступным преобразованием. Его наличие не говорит, что произвольная Structure `Foot` подходит на место Structure `Meter`: это отдельный вопрос `implements`. Конвертер не исполняется при аналитическом допуске; при реальном потреблении его результат проверяется по контракту, в том числе по диапазону и точности.

При вызове возможны два последовательных, но разных преобразования: фактический `int` в требуемый выбранным методом `double`, а возвращённый `double` — в `int`, ожидаемый Consumer. Оба маршрута должны быть доступны именно в контексте этого Message.
<a id="post-transport"></a>
## `post`: один вызов, несколько доставок

Здесь Q1–Q3 и R1–R3 — только обозначения в пояснении, не поля LMX. В протоколе все ветви `answer` готовы до отправки `ask`.

```text
post:
. ask:
. . getPixel: x y
. . getPixel: x + 1, y + 1
. . getPixel: x + 2, y + 2
. answer:
. . setRed: uint32: rgb
. . setGreen: uint32: rgb
. . setYellow: uint32: rgb
. timeout: ms: int: time 500
. undelivered: (getPixel: method; int: x; int: y)
. . log\error: "undelivered: " method "( x: " x " y: " y " )"
. unanswered: (ms: int: time; getPixel: method; int: x; int: y)
. . log\error:
. . . "unanswered after " time " ms "
. . . method "( x: " x " y: " y " ) timeout: " timeout\ms\time
. . end: error
. catch: axisOutOfBound (int: value; int: number)
. . println: "axis: " number " value: " value
```

Если все вызовы вернули результат, три выполнения `getPixel` дают три результата, каждый направляется в три назначения: девять последующих доставок, но не девять выполнений `getPixel`. Порядок прихода ответов не меняет связи с исходными письмами. Ни одна строка `answer` не образует позиционную пару со строкой `ask`.

Если Q2 не доставлен, `undelivered` получает адресата и уже сформированные аргументы Q2, например `11, 21` при исходных `x = 10` и `y = 20`. Q1 и Q3 продолжаются. Если Q2 выдал объявленный `axisOutOfBound`, `catch` получает его payload; это не координаты, выведенные почтой из запроса. У Q2 тогда нет результата для `answer`.

Если Q2 ждёт дольше `500` мс, `unanswered` получает время, относящееся к исходной отправке. Оно может быть `512`, тогда как `timeout\ms\time` по-прежнему `500`. Журналирование не отменяет запрос и не удаляет маршруты: поздний ответ идёт по ним, пока пользовательский код явно не выбрал иную политику. Недоставка уже готового результата одному из `setRed`/`setGreen`/`setYellow` не переименовывает успешный Q2 в «исходный запрос не доставлен».

Старые проекты «письмо без тела вызывает все методы», «`answer` заполняет публичный API», нумерация внутренних ответов и отдельная почтовая таблица сигнатур отменены. [Нормативный контракт](LMX_semantics.ru.md#thread-message-api) не зависит от этих исторических предложений.

<a id="tables-and-registries"></a>
## Таблицы и провайдеры как данные

В необязательном табличном профиле строка с ключом `u8` и ячейкой `spelling = "uint8_t"` позволяет явному запросу получить написание для целевого C-кода. Это не объявляет в LMX новый тип и не делает таблицу общим runtime-пространством имён. Строка `plus[decimal][int] → decimal_int_add` аналогично может дать ключ реализации; отдельные связанные таблицы сообщают результат, эффект, способ понижения и провайдера. Пометка `pure` остаётся утверждением описания, а не автоматическим доказательством чистоты.

Представление пар матрицей или группировкой, порядок источников, численный приоритет и конфликтующие строки — явная политика потребителя таблицы. Профиль может выбрать `None` как маркер отсутствующей ячейки; это не универсальный числовой ноль. Конкретные развернутые таблицы и выдержки исходника сохранены в [L1-спецификации](L1_spec_ru.md); они иллюстрируют данные, а не дополнительные правила поиска Structure.
