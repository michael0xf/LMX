Ответ по действующей книге (RU:119,424,571–575) и M6:510–515. Нормативного вопроса автору здесь нет.

1. Да. После 4a := среди actuals не принимается как старая именованная подача и не превращается в позиционное значение. Для такого исходника — ясная диагностика «именованный аргумент записывается a: value», без fallback. Проверка формы — до эффектов этих actuals. В уже построенном графе с прежней формой общий потребитель тоже не должен молча использовать старую ветку связывания. Точное число ошибки не языковая норма.

2. Убери := из частей РЕСИВЕРОВ в этом же 4a. Это тот же общий связыватель именованной подачи, оставлять отдельную старую возможность для fn/других ресиверов незачем. Упомянутые четыре фикстуры перевести на головы name:, args:, return:, body: по текущему контракту реализованной стадии. Это замена формы подачи, а НЕ повод заранее вводить в 4a новую сигнатуру/внешнее имя fn: переход к k1: fn: return args ... остаётся M6 3. В receipt честно отделить текущую стадию объявления от окончательной нормы; не приписывать новой редакции старый аргумент name.

3. Не вводить синтаксический запрет «у именованного actual обязан быть ровно один непосредственный RHS field». Общая модель:
— f(a:) передаёт формалу a присутствующую пустую Structure. Это НЕ отсутствие actual, не запрос дефолта и не нульарный вызов a. Если формал её не принимает, отказ обычного допуска, а не особый запрет пустого хвоста.
— f(a: 1 2) имеет один именованный actual a с многополевым структурным содержимым; это не два actuals для f. В структурном режиме formal a получает эту Structure. Вертикальное оформление того же хвоста само не меняет правила.
— правая часть по-прежнему потребляется/вычисляется обычным способом по контракту принимающего места. Не превращать числовое выражение или явный вызов справа в инертные данные только по числу полей. И наоборот, передаваемое описание/Structure не запускать как произвольный блок немедленных вызовов.
— f(a: {1 2}) сохраняет явно написанную непустую дочернюю Structure; не снимать её контейнер на P0 и не передавать наружу её поля как остальные actuals f.
Использовать тот же общий путь выделения значения хвоста, вычисления и допуска, что у других форм приёма. lmx_graph_frame_value подходит как существующая общая часть этого пути (у него уже есть случаи 0/1/много), но сам факт возврата frame не заменяет последующее корректное вычисление/структурное потребление по контракту.
Имя a связывается до эффектов, правая часть потребляется один раз, результат допускается до следующего actual. Пустой/многополевой случай не требует особого parser/binder fn.

4. Да, как ГРАНИЦА текущего среза 4a: отдельные операторы известных присваиваний x := 5 можно пока не трогать. Это оставшаяся работа миграции, не разрешённая итоговая форма редакции 4. Явно внеси её ближайшим отдельным подпунктом M6 (например, 4b) и в состояние OPEN: общая запись x: value, перевод соответствующих фикстур и удаление старого := без fallback до завершения миграции M6. Если общая правка естественно захватывает эти операторы уже сейчас, можно объединить; отдельного подтверждения не нужно. Не оставлять этот хвост неуказанным под видом «все := удалены».

Достаточно адресных случаев для этих различий в существующем pipeline: скалярный именованный, пустая/многополевая Structure под подходящий формал, одноимённый callable и явный вызов справа; неподходящий formal даёт обычный отказ приёма. Не добавляй общий новый gate и не требуй ревью/ACK. Продолжай реализацию и план.
