## 1. Основное правило

`import`, `copy` и `merge` обрабатывают явно переданные источники. Результат принимает обычный механизм namespace в соответствующем контексте. Для `copy` и `merge` результатом служит поток итоговых полей, а для `import` — поток отобранных константных объявлений по ссылкам.

**У всех трёх ресиверов аргументы всегда читаются как CODE и обрабатываются тем же общим алгоритмом транслятора и исполнителя, что и стандартные аргументы. Отдельных форм с аргументами в роли DATA нет.**

Это одинаково действует для записи самого ресивера в DATA и в CODE. Положение ресивера определяет окружающий контекст потребления результата, но не переключает роль его аргументов.

| Ресивер | Роль аргументов во всех контекстах | Число источников | Результат |
| --- | --- | --- | --- |
| `import` | CODE | Один или несколько | Поток подходящих константных объявлений по ссылкам |
| `copy` | CODE | Ровно один | Поток скопированных полей |
| `merge` | CODE | Два или несколько | Поток объединённых полей |

**Текущая структура не является неявным аргументом ни одной из этих операций. В частности, `merge` объединяет только свои аргументы. Приём его результата текущим DATA-контекстом не является ещё одним merge.**

Чтобы передать структуры непосредственно в CODE, используются обычные ссылки на структуры либо безымянные структуры:

~~~lmx
merge(A B)
merge((int: x 1) (int: y 2))
~~~

`A` и `B` — ссылки; безымянные структуры также являются структурными значениями. Ни одна из этих форм сама по себе не является вызовом. Явная форма `Producer()` остаётся вызовом и вычисляется общим алгоритмом тогда, когда операция потребляет этот источник. Из этого не следует исполнение при построении P0 или переписывание исходного графа.

Содержимое безымянной структуры вполне может включать вызовы, вычисляемые объявления и другие формы. Они обрабатываются по своим обычным контрактам. Группировка не является специальным запретом исполнения вложенных вызовов и не требует заранее выполнить все инициализаторы. Унификация означает общий алгоритм аргументов CODE, а не предположение об отсутствии вызовов внутри структуры.

Число источников и число выдаваемых полей — разные величины. Один источник `copy` может дать ноль, одно или много полей. Обычные чтения W/E применяются к аргументам всех трёх ресиверов независимо от положения записи; подробности — §7.

Новая норма заменяет специальное толкование `Struct: merge(...)` как объявления структуры самим `merge`. Структуру объявляет обычная форма `Struct:`. Вложенные ресиверы поставляют материал для её обычного прочтения в роли DATA.

## 2. Обязательное напоминание: граф и namespace

> **В графе абсолютно все ресиверы лежат «как есть». Все вычисления и преобразования выполняются исключительно в namespace. Исключение в представлении — объявления конечных примитивов: они тоже находятся в графе, непосредственно как `{type value}`.**

Это общее правило относится и к новым формам `import`, `copy` и `merge`.

Из него следуют требования:

1. P0 сохраняет написанные Frames, границы групп и последовательность форм. Он не исполняет эти ресиверы и не заменяет их результатами.
2. В исходном графе запись `merge(A B)` остаётся записью `merge(A B)`; `copy(A)` и `import(A B)` сохраняются так же.
3. Вычисление источников, объединение аргументов, отбор импортируемых объявлений, раскрытие результата и его включение в принимаемый DATA-контекст происходят в namespace.
4. Фраза «поля попадают в текущую структуру» означает их участие в текущем DATA-прочтении через namespace. Она **не означает**, что ресивер вырезается из исходного графа, а вместо него физически записывается вычисленная последовательность полей.
5. Выдача потока не добавляет в исходный граф служебную обёртку, скрытый результат, новую модель или постоянный namespace.
6. Готовый конечный примитив хранится как его тип и значение. Формы, для которых ещё требуется вычисление, сохраняют своё написанное представление; это исключение не разрешает заранее вычислять произвольные RHS.
7. Сериализация исходного графа сохраняет ресиверы и структуру исходной записи; из `{type value}` восстанавливается соответствующее объявление примитива по общему контракту сериализации.

Копирование может создавать необходимые значения и узлы результата по действующему контракту графового копирования. Их использование через namespace не является переписыванием исходного ресивера. Обычные явные записи программы в доступные графовые данные сохраняют собственный контракт.

Это правило обязательно учитывать в примерах и тестах: прямое чтение исходного пути к записи ресивера не должно само запускать его или показывать вместо записи автоматически развёрнутый результат.

## 3. Объявление структуры и несколько операций внутри DATA

Следующие записи имеют один смысл в роли DATA:

~~~lmx
Struct: merge(A B)
~~~

~~~lmx
Struct:
    merge(A B)
~~~

`Struct` объявляется обычным способом. `merge` получает только `A` и `B`, формирует свой поток, а текущий DATA-потребитель принимает его через namespace.

Несколько операций в одной структуре допустимы:

~~~lmx
Struct:
    merge(A B)
    merge(C D)
    copy(E)
~~~

Обработка идёт в написанном порядке. Первая операция объединяет `A` и `B`, вторая — `C` и `D`, третья копирует `E`.

Запрещено толкование этой записи как:

- скрытого `merge(Struct A B C D E)`;
- накопительного наложения каждого следующего результата на текущий `Struct` по правилам `merge`;
- одной операции `merge(A B C D E)` с общей картой копирования.

Внутри каждой операции `merge` действует собственная модель первого аргумента. Между самостоятельными операциями действует обычный приём DATA-полей.

Обычная запись `Struct: extern` сохраняет значение структурной формы в своей роли. Она не приобретает семантику присваивания или автоматического раскрытия `extern`.

### 3.1. Совпадающие имена: два разных уровня обработки

**Внутри одного `merge(A B)`** сохраняется действующее правило композиции: совместимое поле `B`, совпавшее с полем модели `A` по установленным критериям, заменяет значение соответствующего model slot; новое поле добавляется в конец.

**При поступлении отдельных потоков в текущий DATA-контекст** действуют обычные правила повторного объявления DATA. `merge` не даёт своему результату дополнительного права переписать уже существующее объявление.

Например, при `A` с полем `x` и `B` с совместимым полем `x`:

~~~lmx
Struct:
    int: x 1
    merge(A B)
~~~

Поле `x` внутри результата `merge` определяется объединением `A` и `B`. При приёме этого поля непосредственно написанное `int: x 1` не становится model slot этой операции. Повтор учитывается обычным DATA-механизмом, включая несколько occurrences и их обычное разрешение.

Эта формулировка описывает семантическое прочтение. Исходный граф по-прежнему содержит объявление `int: x 1` и запись `merge(A B)`.

## 4. Разделение copy и merge

### 4.1. copy

`copy` — форма для одного источника:

~~~lmx
copy(A)
~~~

Она копирует нужный граф одного источника по общим действующим правилам и выдаёт поток его итоговых полей.

Слово `args` в записи `copy(args)` обозначает один передаваемый источник с таким именем. Оно не означает произвольное количество отдельных аргументов.

Пустой источник и отсутствие источника различаются: `copy(Empty)` с пустой структурой допустим и даёт пустой поток; `copy()` источника не имеет.

### 4.2. merge

`merge` принимает два или больше источников:

~~~lmx
merge(A B)
merge(A B C)
~~~

Первый принятый источник — модель данной операции. Следующие источники обрабатываются последовательно по действующим правилам совпадения полей, допуска типов и сохранения model slots.

Имя `merge` больше не обозначает одноисточниковое копирование. Если после обычного выбора аргументов принят только один источник, используется `copy`.

### 4.3. Что означает «как import»

Сходство относится к поступлению материала в текущий namespace через обычного потребителя.

Оно не переносит на `copy` и `merge` фильтр `import`: копирование и композиция продолжают работать со всеми полями, допускаемыми их действующим контрактом. Обычные изменяемые поля не исчезают из копии из-за отсутствия `const`.

Различие операций:

| Операция | Что берётся из источников | Как обрабатываются связи | Наложение полей источников |
| --- | --- | --- | --- |
| `import` | Подходящие корневые const-объявления DATA | Ссылки на исходные объявления; их идентичность и `parent` сохраняются | Обычные повторные объявления у потребителя |
| `copy` | Поля одного источника по контракту копирования | Общая карта исходных и скопированных узлов | Между источниками отсутствует: источник один |
| `merge` | Поля всех источников по контракту композиции | Одна общая карта на эту операцию | По model-slot правилам только между её аргументами |

## 5. Все формы import

### 5.1. Общее правило отбора

Сохраняется ранее согласованная норма:

> `import` импортирует только const-объявления, которые при вызовах считаются корневыми в DATA источника. Объявление любой пользовательской структуры константно и без явного `const`, поскольку структура не является переменной.

Корневой статус определяется обычными правилами DATA. Его нельзя заменять проверкой только непосредственного физического `parent`: модификаторы и декларативные формы уже имеют общий контракт.

Импортируется объявленное имя. Если ресивер `fn` создаёт подходящее константное имя сигнатуры, оно импортируется по тому же правилу; имя самого ресивера `fn` от этого не импортируется.

Содержимое источников, идентичность импортируемых структур и их исходные `parent` сохраняются. Импорт метода не переносит его DATA к импортирующей структуре.

### 5.2. Запись import в DATA

~~~lmx
Use:
    import(A B C)
~~~

То же через короткую форму:

~~~lmx
Use:
    import: A B C
~~~

Аргументы `import` и здесь читаются как CODE. Голые `A`, `B` и `C` передают ссылки и не вызывают структуры. Отобранные объявления поступают в namespace обычного DATA-прочтения `Use`.

В записи:

~~~lmx
Use:
    import(A Producer())
~~~

`Producer()` является явным вызовом, а не DATA-объявлением. Он вычисляется один раз, когда обычное потребление `import` требует этот источник. Само присутствие записи в исходном графе не означает раннего исполнения при P0.

Для передачи без вызова применяется ссылка `Producer` либо подходящая безымянная структура. Никакой специальной DATA-ветки обработки аргументов import не требуется.

### 5.3. Запись import в CODE

В выполняемом коде:

~~~lmx
import(A B C)
import(A Producer())
~~~

используется тот же алгоритм аргументов CODE. В первой записи источники получаются по ссылкам, во второй `Producer()` вызывается один раз и поставляет структуру.

Из всех полученных структур отбираются одинаковые корневые const-объявления по §5.1. Роль аргументов CODE не снимает фильтр `import`.

Для нескольких вычисляемых источников сохраняется обычный порядок вычисления слева направо. Проверка вариантов передачи не запускает источники повторно.

### 5.4. Несколько источников и получатель результата

`import` принимает один или несколько источников во всех контекстах. Одноисточниковая запись сохраняется:

~~~lmx
import: cycles
~~~

Для нескольких источников импортируются их подходящие объявления в порядке аргументов и обычного обхода объявлений каждого источника.

Самостоятельный `import` передаёт отобранные объявления в текущий namespace. При вложенном использовании поток принимает окружающий потребитель по общим правилам. Одновременного дополнительного импорта тех же имён ещё и в namespace вызывающего не производится.

Таким образом, для вложенной формы `f(import(A B))` поток является материалом аргументов `f`; отдельный скрытый побочный импорт в вызывающий namespace не добавляется. Если нужен один структурный результат, применяется общая группировка `f((import(A B)))` и затем обычный выбор аргументов §7.

Это потоковое уточнение вложенного использования дополняет прежнее ТЗ, которое описывало самостоятельное добавление объявлений в namespace.

При совпадении импортируемых имён применяется обычное повторное объявление в соответствующем контексте. У `import` нет отдельного правила «последний источник побеждает» и нет model-slot наложения `merge`.

### 5.5. Пример отбора

~~~lmx
Library:
    const: int: limit 10
    int: counter 0
    Settings:
        int: width 2

Other:
    Tool:
        int: value 3

Use:
    import: Library Other
~~~

В namespace DATA-прочтения `Use` импортируются:

- `limit` — явное корневое const-объявление;
- `Settings` — пользовательская структура, константная по характеру объявления;
- `Tool` — такая же пользовательская структура из второго источника.

`counter` не импортируется. Вложенные `width` и `value` отдельно в корень `Use` не поднимаются. Импорт `Settings` не делает его содержимое immutable: константность структурного имени и изменяемость его полей имеют свои обычные контракты.

В исходном `Use` остаётся запись `import: Library Other`; список импортированных имён существует в namespace.

## 6. Поток и явная группировка

### 6.1. CODE-результат без неявной упаковки

`copy` и `merge` выдают поля потоком. Они не возвращают автоматически один внешний Structure-контейнер.

~~~lmx
f(copy(A))
f(merge(A B))
~~~

В этих формах окружающий аргументный потребитель получает поток результата.

Если нужен один структурный результат, он записывается явно:

~~~lmx
f((copy(A)))
f((merge(A B)))
~~~

Тот же принцип применяется при присваивании уже объявленной переменной-ссылке:

~~~lmx
struct := (copy(args))
struct := (merge(A B))
~~~

`struct` здесь — переменная, которой обычный контракт допускает присвоить структурное значение. Эта запись не делает присваиваемым имя структурной декларации.

Без дополнительных скобок:

~~~lmx
struct := copy(args)
~~~

правая сторона остаётся потоком. Его допустимость определяется обычным потребителем присваивания. Нельзя автоматически считать эту запись прежним присваиванием одного скопированного контейнера; нельзя и объявлять её безусловной синтаксической ошибкой.

### 6.2. Границы групп сохраняются

В `f((copy(A)))` внешняя группа собирает поток в одну Structure на границе написанных аргументов. Это не специальная синтаксическая форма `copy`.

P0 сохраняет эту группу. В namespace выполняется её обычное прочтение. Пустая группа и группа с единственным полем не исчезают из исходного графа только из-за своего размера.

В частности:

- `copy(Empty)` даёт ноль полей;
- `(copy(Empty))` даёт один пустой структурный результат;
- дальнейшая обработка вызывающим ресивером следует его обычному контракту.

Произвольные Structure и Array не начинают сами разворачиваться во всех выражениях. Здесь определяется результат этих ресиверов; существующие разрешённые раскрытия имеют прежнюю область действия.

## 7. Единый алгоритм аргументов CODE и обычный выбор W/E

У `import`, `copy` и `merge` всегда стандартные аргументы CODE. Положение их собственной записи в DATA не отменяет общий выбор аргументов.

Действующие правила допускают два чтения единственной Structure у CODE-потребителя:

- **W:** передать целиком;
- **E:** раскрыть её непосредственные поля в последовательность аргументов.

Кандидаты рассматриваются равноправно. Один подходящий кандидат выбирается, отсутствие кандидата даёт отказ, несколько — неоднозначность. После выбора повторного раскрытия нет.

Следствия:

1. `f((copy(A)))` создаёт одну упакованную Structure, но не вводит исключения из W/E у `f`. Скобки сами по себе не гарантируют выбор одноаргументной сигнатуры.
2. Если нужно передать целую Structure без E, применяется существующая именованная передача присваиванием формалу: `f(arg0 := (copy(A)))`, где `arg0` — действительное имя формального аргумента.
3. Арность `copy`, `merge` и `import` проверяется по принятой последовательности источников. Запись с единственной написанной структурой `S` может получить несколько источников через обычное E.
4. Поэтому фразу «у merge минимум два аргумента» нельзя реализовать как ранний запрет всякой написанной формы `merge(S)`: E может дать два или больше подходящих структурных источников.
5. Если W и E подходят одновременно, сохраняется обычная ошибка неоднозначности. В частности, библиотека из нескольких структур может дать два чтения для import. `import` не получает скрытого предпочтения W из-за того, где записан ресивер.
6. Несколько полей, выданных `copy`, не превращают его единственный входной источник в несколько источников. Входная арность и выходной поток проверяются на разных этапах.

Порядок позиционных и именованных передач, требуемость источников и их допуск подчиняются общим правилам. Неявное связывание не должно придумывать недостающий источник или участвовать в выборе варианта.

Контракты остальных ресиверов этим не меняются: например, `fn` и модификаторы сохраняют свои DATA-аргументы. Правило о передаваемых ресиверах объявления также остаётся общим: безымянная структура или ссылка на структуру не превращается в вызов только потому, что потребитель получает аргументы CODE.

## 8. Групповое присваивание

Новая выдача полей использует уже существующий механизм:

~~~lmx
(c b d a) := (a b c d)
~~~

Соответствие позиционное. Все правые значения вычисляются до первой записи.

При исходных `a = 1`, `b = 2`, `c = 3`, `d = 4` результат:

| Место | Новое значение |
| --- | ---: |
| `c` | 1 |
| `b` | 2 |
| `d` | 3 |
| `a` | 4 |

Аналогично:

~~~lmx
(a b) := (copy(Pair))
~~~

получает два итоговых поля `Pair` и присваивает их по позициям, если они допускаются соответствующими местами.

> **Уточнение автора 2026-11-21** ([журнал](../../LMX_blog/2026-11-21.md#group-assign-decision)). Утверждённая форма группового присваивания — `() := ()`: справа одна безымянная Structure в скобках. Несколько значений без скобок, `(c b d a) := a b c d`, и поток без скобок, `(a b) := copy(Pair)`, — ошибка; в первой редакции раздела оба примера стояли без скобок. Единственный аргумент `right` операнда, если он безымянная Structure, раскрывается; Structure, возвращённую функцией, не раскрывают.

> **Уточнение автора 2026-11-22** ([журнал](../../LMX_blog/2026-11-22.md#operand-left-unnamed-structure)). Скобки справа раскрываются, когда и `left` — безымянная Structure: в `(a b) := (copy(Pair))` в `right` приходит всё содержимое скобок. При `left`, не являющемся безымянной Structure, скобки не раскрываются: запись §6.1 `struct := (copy(args))` присваивает одну Structure, как написано.

Имена правых полей не меняют позиционное соответствие. Несовпадение количества мест и значений обнаруживается до первой записи. Обычные ограничения записи сохраняются.

Это не обещает отката уже случившихся эффектов вычисления правой стороны: правило «прочитать перед записью» и транзакционный откат — разные контракты.

## 9. Сохранить действующую семантику копирования

Изменение способа выдачи результата не заменяет графовое копирование независимым копированием каждого поля.

Для одной операции `copy` или `merge` сохраняются:

1. Одна общая карта соответствия исходных и скопированных узлов, охватывающая все её источники.
2. Сохранение общих целей ссылок и циклов; повторная ссылка не создаёт дополнительную копию того же узла.
3. Переписывание обычных ссылок и `parent` через эту карту с копированием необходимых лексических цепочек по существующему контракту.
4. Действующие исключения для reusable native implementation references и надлежащим образом квалифицированных `independent: immutable` ветвей.
5. Обычные правила доступа, допустимости источников, владения и времени жизни.
6. Действующий домен структурных источников, включая случаи взаимозаменяемости Structure и reference Array. Искусственное новое ограничение только одним физическим видом контейнера не вводится.
7. Сохранение native-связей по прежнему контракту без автоматической компиляции или регистрации новой реализации.

Отдельные вызовы имеют отдельные операции копирования. Их карты нельзя автоматически объединять только потому, что потоки принимает один namespace.

Принятие потока не меняет само по себе лексические связи скопированных методов. `node` остаётся лексическим оператором; его нельзя переопределять как «текущий получатель потока». Действующие DATA/parent-связи и порядок связывания сохраняются.

Обёртка, написанная для получения одного структурного результата, обрабатывается общим механизмом группировки. Она не запускает второе независимое копирование уже скопированных полей и не возвращает ссылки в исходный изменяемый граф.

При переносе прежних примеров с методами и внутренними ссылками проверять не только список полей, но и сохранение связей внутри полученной копии. Не подменять исходный синтаксический `Struct` вычисленным контейнером результата: записи ресиверов остаются в графе по §2.

Для `import` графового копирования нет: передаются исходные подходящие объявления по ссылкам, с сохранением их исходных `parent`.

## 10. Замена прежних записей

Таблица описывает намерение примера. Нельзя механически добавлять скобки к каждому употреблению: сначала определить, требовался один структурный результат или поток.

| Прежняя запись / намерение | Новая запись |
| --- | --- |
| Один источник `merge(A)` | `copy(A)`, если нужен поток |
| Один источник, нужен один структурный результат | `(copy(A))` |
| Несколько источников, нужен поток | `merge(A B)` |
| Несколько источников, нужен один структурный результат | `(merge(A B))` |
| Передать одну копию аргументом | `f((copy(A)))` с обычным W/E |
| Передать одно объединённое значение аргументом | `f((merge(A B)))` с обычным W/E |
| Передать результаты потоком аргументов | `f(copy(A))` или `f(merge(A B))` |
| Присвоить одну копию переменной-ссылке | `struct := (copy(A))` |
| Присвоить одно объединённое значение переменной-ссылке | `struct := (merge(A B))` |
| Вернуть одну скопированную Structure | `return: (copy(A))` с обычным контрактом `return` |
| Создать переменную-ссылку на один объединённый результат | `@: result (merge(A B))` |
| Прежнее DATA `Struct: merge(A B)` | Та же запись; `Struct` объявляет внешняя форма, `merge` поставляет поток |
| DATA с копированием одного источника | `Struct: copy(A)` |
| Несколько DATA-композиций | Несколько самостоятельных `merge(...)` в теле обычного `Struct` |
| Импорт одного источника | `import: A` сохраняется |
| Импорт нескольких источников | `import: A B C`; аргументы всегда CODE во всех контекстах |

Нельзя восстанавливать отменённое толкование `Struct: source` как присваивания. Нельзя возвращать специальный синтаксический тип «объявление посредством merge».

## 11. Задачи Fable

### 11.1. Семантика и реализация

1. Ввести публичную одноисточниковую форму `copy` и ограничить `merge` двумя или более принятыми источниками.
2. Для всех трёх ресиверов оставить один стандартный контракт аргументов CODE во всех контекстах. Удалить специальные DATA-ветки обработки их источников.
3. Поддержать многоаргументный `import` во всех контекстах, сохранив одноисточниковую форму и общий алгоритм аргументов.
4. Использовать обычный механизм выдачи и потребления полей через namespace. Не создавать отдельный пользовательский тип потока, отдельный парсер или постоянный преобразованный граф.
5. Удалить зависимость DATA-композиции от специальной внешней формы `Name: merge`. Обычная структура может содержать любое допустимое число самостоятельных операций.
6. Разделить внутривызовное объединение `merge` и обычный приём результата. Текущий DATA-контекст не подмешивать в источники и не использовать как дополнительную модель.
7. Сохранить правила импорта const-объявлений, исходные ссылки и `parent`; для повторных имён использовать общий механизм.
8. Сохранить написанные группы и обычный W/E. Проверять арность на семантическом этапе, а не по имени ресивера в P0.
9. Сохранить графовое копирование, его карту и действующие гарантии связей. Общее ядро копирования может обслуживать `copy` и `merge`.
10. Использовать обычную диагностику ресиверов. Ошибки `copy` и `import` должны называться согласно своим контрактам, а не случайно наследовать имя `merge` из общего низкоуровневого помощника.
11. Согласовать наблюдаемое поведение интерпретируемого и нативного путей в рамках их действующих контрактов. Вычисление источников и выдача потока не должны удваиваться при выборе вариантов или упаковке.

### 11.2. Точные места документации

| Документ / раздел | Изменение |
| --- | --- |
| Semantics §9: роли DATA/CODE, structural forms, Explicit copying and pointer variables | Убрать специальное объявление структуры через `merge`; показать обычное объявление и поток; одиночные структурные результаты явно группировать |
| Semantics §9: Group positional assignment | Добавить пример `(a b) := (copy(Pair))`; сохранить чтение RHS до записей |
| Semantics §11: Two kinds of receivers | Отнести import, copy и merge к обычным ресиверам с аргументами CODE во всех контекстах; удалить их из DATA-группы |
| Semantics §11: Whole arguments / Declaration selection | Согласовать входную арность, потоковый результат, упаковку и W/E |
| Semantics §20: Composition and graph copying | Разделить `copy` и `merge`; сохранить графовую карту; описать выдачу полей |
| Semantics §20: The two records of merge | Описать размещение в DATA/CODE при одном контракте аргументов CODE; удалить специальную DATA-форму и обоснование `Name: merge` |
| Semantics §20: Model slots, field matching and ordering | Явно ограничить наложение аргументами одной операции |
| Semantics §20: Returned nested methods и factory-примеры | Заменить одноисточниковый `merge` на `copy`; при возврате одного контейнера добавить группировку |
| Semantics §21: Modules/linking | Согласовать `import` с принятым ТЗ; убрать старое утверждение об отсутствии отдельного import |
| Grammar: Frames, bounded groups, preserved argument boundaries | Добавить парные примеры потока и упаковки; не вводить синтаксическую ветку по имени ресивера |
| Semantics Guide | Показать единые аргументы CODE, ссылки и безымянные структуры без вызова, несколько операций в DATA и различие потока/упаковки |
| L2: copy/merge, namespace consumption и связанные описания | Согласовать интерфейс общего копирования с получателем потока, сохранив существующую модель памяти |
| Ранее принятые ТЗ об import и operands | Согласовать единые аргументы CODE и вложенный import; сохранить const-фильтр, написанные группы и общий выбор аргументов |

Исторические примеры, оставленные в архивных разделах, обозначить как прежние. Текущая нормативная часть не должна одновременно утверждать, что `merge` всегда возвращает один контейнер, и описывать его результат как поток.

## 12. Приёмочные случаи

Ниже — проверяемые различия модели. Для CODE-случаев источники и формальные аргументы подбираются так, чтобы ожидаемое чтение было единственным, кроме тестов на саму неоднозначность.

| № | Случай | Ожидаемое поведение |
| --- | --- | --- |
| G01 | Построен граф с `import`, `copy` и `merge` | Все ресиверы и написанные группы сохранены как есть |
| G02 | Выполнено прочтение DATA с этими ресиверами | Результаты обработаны в namespace; записи в исходном графе не заменены полями |
| G03 | Конечный `int: x 10` | В графе примитивное представление `{type value}`; сериализация восстанавливает объявление |
| G04 | RHS требует вычисления | P0 не вычисляет её заранее и не теряет написанную форму |
| D01 | `Struct: merge(A B)` и вертикальная форма | Одинаковое DATA-прочтение без специального объявления от merge |
| D02 | Два `merge` в одной DATA-структуре | Две самостоятельные композиции; оба потока приняты в написанном порядке |
| D03 | В DATA уже есть одноимённое поле | Оно не становится моделью merge; повтор обрабатывается общим DATA-правилом |
| D04 | Совместимые одноимённые поля внутри одного merge | Действует прежнее model-slot наложение; индекс модельного поля сохраняется |
| A01 | Один принятый источник copy | Допустим; число его полей не влияет на входную арность |

| A05 | Один написанный CODE-источник допускает E с несколькими источниками | Применён общий выбор W/E; раннего синтаксического запрета нет |

## 13. Опорные документы и приоритет решений

Нормативный приоритет для этой задачи:

1. Последние указания автора: import, copy и merge всегда имеют стандартные аргументы CODE; ссылки и безымянные структуры сами по себе не являются вызовами; текущая структура не участвует в merge; import принимает несколько источников; ресиверы сохраняются в графе как есть, вычисления и преобразования происходят в namespace.
2. Ранее принятые ТЗ — в частях, которые эти указания не изменяют.
3. Текущая базовая документация — для общих правил ролей, вызовов, графового копирования, DATA-объявлений и присваивания.

## 14. Критерий завершения

Из документации и реализации однозначно следует один общий порядок: прочитать явные источники стандартным алгоритмом аргументов CODE; выполнить отбор, копирование либо объединение этих источников; передать полученный поток обычному namespace-потребителю; при явно написанной группировке получить один структурный результат.

Исходный граф сохраняет написанные ресиверы. Текущий DATA-контекст не участвует в merge. Различия import, copy и merge определяются их контрактами обработки источников. Положение записи определяет получателя потока; аргументы всех трёх ресиверов всегда обрабатываются как CODE.
