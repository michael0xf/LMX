# Удерживает ли merge ветвь `independent: immutable:` без `const`

Статус: ОТВЕТ АВТОРА 2026-10-12; прежнее правило подтверждено, реализация остаётся открытой. Вопрос задаёт `fable_pc` при проектировании среза RR2
([дизайн](../../steps/qualifier-receivers-20261010.md); тикет
[critical_qualifier_receivers_bug](../../steps/tickets/critical_qualifier_receivers_bug.md)); передан
автору через Codex почтальоном `lmx_uds`.

## Контекст

По книге ([квалификация](../../docs/LMX_semantics.ru.md#qualification), [вечные ветви](../../docs/LMX_semantics.ru.md#eternal))
`const` защищает привязку, `immutable` — значение через все псевдонимы, `independent` — владение
значением без внешнего лексического родителя; вечную ветвь, которую `merge` удерживает по ссылке,
а не копирует, даёт только совместная квалификация `independent: const: immutable`. По правилу
автора 2026-10-10 три квалификатора — обычные ресиверы, принимающие любую Structure, и каждый
допустим отдельно.

Физически квалифицированное значение — дерево в пулах своего профиля, запечатанных после
проверки; `independent` даёт корню `parent = 0`. `const` не оставляет в значении следа: он
защищает привязку (имя), а не хранилище. Значение `independent: immutable: X` без `const` и
значение полной цепочки физически неразличимы, в том числе когда значение передано по ссылке
и привязка уже не видна.

## Вопрос

Удерживает ли `merge` по ссылке (как вечную ветвь) значение, построенное `independent: immutable:`
без `const`, — или копирует его?

## Ответ автора 2026-10-12

«Удержать» здесь означает оставить в результате `merge` **исходный физический адрес** ветви.
Такое исключение из копирования с самого начала принадлежало только совместной
`independent: const: immutable:`. Ветвь `independent: immutable:` без `const` копируется целиком
по общему правилу. Запечатанный профиль и нулевой `parent` сами по себе недостаточны: прежнее
предложение считать `const` безразличным к этому исключению отвергнуто.

Лексически объявленная ветвь полной тройной квалификации может находиться не только в корне
Message, в том числе внутри обычного окружающего тела. Сборщик владельца сохраняет каждое
такое созданное вхождение до удаления **всей арены**, даже если обычная достижимость через
окружающий граф впоследствии пропала. Смена `parent` допускается лишь тогда, когда она не
отсекает такую ветвь от её лексических предков; иначе операция отказывается до изменения.
Это не разрешает удерживать по адресу частично квалифицированные ветви при `merge`.

Проверка реализации: `unit_rr2_qualified_merge_decl.lm2` уже доказывает тройное объявление
значения в методе, вне корня Message. Но отдельная форма именованной ветви `(): E` пока
регистрируется `l2_take_eternal` только в корневом проходе `l2_unit_role`; вложенное
объявление этой формы не доказано. `lmx_merge_retain_profile` сейчас выбирает удержание по
запечатанному профилю и `parent = 0`, не проверяя `const`, а `lmx_gc_mark_value` и
`lmx_gc_block_live` освобождают от сбора **любой** sealed pool, включая профиль без полной
тройной квалификации. Нужны отдельные положительные/отрицательные свидетели и общий способ
сохранить доказательство полного контракта при передаче значения через ссылку; один `sealed`
этого не доказывает.
