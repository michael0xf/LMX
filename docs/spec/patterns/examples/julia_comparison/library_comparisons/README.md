# Полные пары реализаций

Четыре модуля покрывают **все** имена ядра из 24 Julia-клиентов. LMX-алгоритмы извлечены из текущего ядра, а Julia-алгоритмы написаны как самостоятельные реализации объявленного общего договора. Клиенты Julia вызывают реальные Base/SplitApplyCombine и не импортируют эти модули.

| Пара | Операции | Явные зависимости Julia |
| --- | --- | --- |
| [JI01](JI01_comparision.md) | map, filter, foldl, scanl, zip, zipWith, bind, any, all, index, count, record | обычные вызовы, массивы, примитивные операции runtime |
| [JI02](JI02_comparision.md) | range, slice, reverse, compress, concat, transpose | то же; BigInt для проверки диапазона |
| [JI03](JI03_comparision.md) | replaceRange, splice, append | JI02: проверка границ и копия среза |
| [JI04](JI04_comparision.md) | sort, unique, groupBy | JI01: входной профиль и истина предиката |

LMX-общие определения находятся полностью в [shared_dependencies.lmx](shared_dependencies.lmx). Они не повторяются внутри каждого компонентного листинга. [Реестр](../validation/implementation_dependencies.json) показывает зависимости, реальные исходные файлы, SHA-256 тел и объём с устранением повторов. LMX-сигнатуры, alias-пакет публичных имён, FxKernel-контракты и существующие sys-операции берутся из [текущего ядра](../../../LMX_Fn_Receivers/README.md). Это не самостоятельный бинарник.

## Что именно реализовано

Алгоритмы не ограничены двумя int или фиксированным числом элементов. Ссылочные элементы сохраняют свои цели, плотные массивы читаются по настоящему типу. Predicate/comparator имеют явно указанные типы результата. В Julia reference-профиле используются конечные одномерные one-based AbstractVector; для filter добавлена полная обработка AbstractString через последовательность символов. Разреженные, смещённые и многомерные массивы не притворяются реализацией всего Julia Base.

Пустые входы обработаны в каждом алгоритме. Проверяются границы, шаг диапазона, форма маски и матрицы, размер результата, допустимый вид результата callback и его predicate/comparator-тип. Ошибки callback распространяются наружу; нет скрытого catch, превращающего отказ в «пустой результат». LMX передаёт именованные failures по своим обычным правилам, Julia — обычные исключения.

Мутации готовят значения до первой записи в target и поддерживают перекрытие, включая `values === target`. Внешний target сохраняет идентичность. Это не означает rollback при любом отказе runtime; эффекты произвольного пользовательского callback или Julia convert не откатываются. У LMX принятие элемента не вводит новый неявный пользовательский converter. Общие клиентские договоры используют совместимые типы и не требуют совпадения всех правил преобразований языков.

Устойчивая sort использует bottom-up merge sort. unique и groupBy используют явное сравнение, поэтому работают и без hash; худший случай у них квадратичен. Настоящие Julia Base.unique и SplitApplyCombine.group могут использовать hash и специализированные алгоритмы. Пара сравнивает полноту заявленной семантики, а не утверждает одинаковую асимптотику всех библиотечных реализаций.

Операции выполняются последовательно внутри текущей Message. В этой группе нет promise, отправки по HTTP или исполнения чужой арены; поэтому асинхронный протокол не требуется и не заменён пустой заглушкой. Действительное предоставление arrayInfo/read/admit/write и prepare/enter/releaseCall остаётся проверяемым интеграционным договором FxKernel. Его отсутствие отмечено в runtime-статусе.

## Приёмка

[run_implementations.jl](../validation/run_implementations.jl) содержит проверки пустых и неверных входов, типонезависимого поведения, порядка callbacks, alias и сохранения остальных полей записей. Он отдельно загружает четыре comparison-модуля. [run_clients.jl](../validation/run_clients.jl) их не загружает. В среде подготовки Julia недоступна, поэтому оба набора пока `NOT_RUN`.

## Запуск корня и дальнейшие операции

Всегда запускается корень R0 как L3 Thread. У корня нет DATA и пользовательских аргументов. Локальные объявления и вызовы обрабатываются общим механизмом языка.

Именованные операции из invoke, inputs и тестовых cases выполняются корнем или обычным обработчиком уже после старта. Main и Example\run не являются альтернативными точками запуска программы. Заглушка-родитель может иметь собственные аргументы и отправить корню сообщение; эти аргументы не становятся DATA корня.

load_before обозначает необходимые определения фикстуры. Отдельного режима запуска через загрузку в DATA он не вводит; import открывает доступные имена. Для короткого фрагмента явно задаётся принимающий контекст последующей обычной операции. Новая команда CLI или API запуска здесь не определяется. LMX runtime: NOT_RUN. [Норма запуска](../../../../LMX_semantics.en.md#source-entry-profiles).
