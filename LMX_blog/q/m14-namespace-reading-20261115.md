# M14: чтение вычисляемого поля и namespace

Дата: 2026-11-15. Исследование после [ответов автора](../2026-11-15.md#m14-value-reading).
Статус: вопросы закрыты уточнениями автора; нормы синхронизированы в книге, L1/L2, руководстве,
спецификации ядра, to_sol и основном M14. Исследование кода ниже — свидетельство прежнего состояния,
не приёмка реализации новой семантики.

## Что автор уже уточнил

- Вход в вызов не исполняет инициализаторы. Namespace собирает переменные;
  их чтение подчиняется тому же общему механизму, что чтение data\field.
- Свёртывание готовых объявлений выполняется при построении чистого графа, без вызовов программы.
- Раннее вычисление RHS не отменяет его повторного исполнения при достижении строки объявления.
- Для поля `@: fptr getFuncPtr()` вызов `fptr("hello world")` сначала получает указатель
  вызовом getFuncPtr(), затем вызывает полученную функцию. Это общее потребление головы,
  не особый обработчик fptr или отдельная инфраструктура свойств.
- `fptr := 0` меняет namespace; `data\fptr := 0` меняет исходное поле так,
  чтобы оно интерпретировалось как `@: fptr 0`.
- После входа голое имя независимо от последующих изменений исходного поля.
  Это одинаково для явной data, лексического и динамического источника связывания.
  [Дословный ответ](../2026-11-15.md#m14-independent-bindings) закрывает прежний Q1.
- Сокращения заголовков fn/sub/catch сохраняются с единой data вместо args/data.

## Согласованная видимость

Автор предложил отменить двустороннюю видимость и для изменяемых переменных,
и для const, сохранив её для имён Structure и callable
([уточнение](../2026-11-15.md#m14-const-sequential)). Неиспользуемое вычисляемое
поле входной data не вычисляется. Это правило внесено в нормативные документы и оба плана;
кодовая реализация остаётся OPEN.

Следствия, выведенные исполнителем:

- Новое имя переменной из code доступно с объявления вперёд в своей области
  и её вложенных областях. До объявления оно не участвует в поиске голого имени;
  обычный поиск доступного внешнего или динамического имени этим не запрещается.
  Вызов из RHS выполняется при достижении объявления. Const меняет возможность
  последующей записи, но не получает отдельного правила раннего вычисления.
- Речь о способе объявления имени, а не о типе его текущего значения.
  Переменная-указатель на функцию остаётся переменной; наличие callable в её
  значении не превращает имя в двусторонне видимое объявление метода.
- Явный `data\field` выбирает поле исходного графа. Доступность этого поля
  и вычисление выбранного объявления не зависят от доступности одноимённого
  будущего локального имени. Это не даёт оснований ограничивать `S[n]`
  или `S\[n]field` порядком строк.
- Подготовка входного namespace не исполняет вычисляемые объявления.
  Поданный actual заменяет исходное объявление соответствующего места;
  неиспользуемый вычисляемый вход не создаёт вызова. Если значение требуется,
  применяется общий механизм чтения выбранного объявления.
- Повторное объявление уже доступного имени сохраняет вычисление RHS и запись
  в его локальную ячейку. Физические повторные поля графа и их выбор по номеру
  вхождения остаются прежними.

Это снимает прежний пример раннего чтения локального вычисляемого объявления:
до его строки такого локального имени больше нет. Для обычного code не нужны
ни раннее выполнение RHS, ни особый адрес вычисляемого будущего локала.
Вопрос об адресе вычисляемого входа data автор также уточнил (см. ниже).

## Сверенные нормы и код

Книга, [объявляющие формы](../../docs/LMX_semantics.ru.md#receiver-args-only), различает
потребление формы как выражения и её исполнение с записью в объявленное место.
Это позволяет получить результат записанного RHS без неявной записи и повторно выполнить
исходный оператор позже. Правило голого атома требует точного пояснения: вычисляется уже
записанное выражение объявления, а не создаётся скрытый вызов метода, на который указывает результат.

При статическом чтении рабочего дерева после 16ea4e08 обнаружены старые пути реализации:

- `lm_graph_build_place` в l2_graph_build.lm2 уже сворачивает готовые литералы,
  сохраняя вычисляемые объявления как обычные receiver Frame.
- `lmx_graph_work_open_parts` вызывает `lmx_graph_data_run` для собственной data метода;
  `lmx_graph_data_declaration` вычисляет RHS и публикует ячейку. Этот входной проход новой нормой отменён.
- `lmx_graph_step` пока отказывает для вычисляемого объявления, а `lmx_graph_operand_read`
  использует прежние work_load/рабочие значения. Общая семантика чтения ещё не реализована.
- `lmx_graph_application_head` уже выбирает голову через общий reader до вычисления actuals;
  `lmx_graph_eval_application` применяет полученную голову. Здесь не нужен второй диспетчер.
- `lmx_graph_step_place` отделён от чтения значения, но `lmx_graph_eval_assignment`
  после выбора поля пока требует готовую primitive/reference cell. Запись в вычисляемое
  объявление должна использовать общий контракт назначения, не исполняя его прежний RHS.
- `lmx_graph_declaration_parts` уже читает требование и кандидата без исполнения кандидата.
- `lm_compiler_own_source_visible` уже отделяет доступность объявления от поиска
  места, но содержит прежние исключения для data, метода и позиций исходников.
  Это не готовая реализация нового правила. Порядок нужно определять по общему
  лексическому дереву программы, включая подключённые файлы.
- `lmx_graph_data_find` сканирует физические корневые поля, а `lmx_graph_step`
  отдельно читает выбранное поле. Ограничение видимости голого имени нельзя
  переносить в общий поиск полей и тем самым запрещать явные пути.

Это результаты чтения кода, не результаты запуска новой семантики. Код исследователем не изменялся.

## Прежние вопросы после уточнений

Q1 закрыт: голое fptr сохраняет выбранное при входе объявление независимо
от последующей записи `data\fptr := 0`. Вопрос и ответ перенесены
[в закрытые](m14-namespace-source-answered-20261115.md).

К пункту 2 автор уточнил «первоначальное объявление кадра» и предложил изменить
видимость. Для локальных объявлений code прежнюю постановку о чтении до строки
объявления заменяет согласованная последовательная видимость. Оно не вводит отдельного кеша чтения
графа и не разрешает молча менять исходную data при чтении места кадра.

## Уточнённое вычисление операнда адресации

Автор подтвердил: для входного `int: x next()` обращение `@x` выполняет next()
и даёт адрес обычной локальной int-ячейки. Прежняя формулировка вопроса
«не читает, а только берёт адрес» была ошибочной. Вопрос и дословный ответ
перенесены [в закрытые](m14-namespace-source-answered-20261115.md#взятие-адреса-вычисляемого-входа).

Следствие общего правила, выведенное исполнителем: `@(data\x)` также вычисляет
свой операнд `data\x`; унарный `@` не подавляет выполнение записанного RHS.
`@x` использует независимое место кадра, а явный путь — исходный граф.
Это различие источника операнда, но из него нельзя вывести, где хранится
результат вычисляемого поля. Прежнее утверждение исполнителя, что `@(data\x)`
в таком случае обязательно возвращает адрес исходной графовой ячейки, было
необоснованным. Подтверждение вычисления не означает неявную замену объявления
в исходном графе его результатом.

## Место результата вычисляемого поля

Окончательная граница задачи — `@(data\field)`, где в data записано
`int: field getValue()`. Автор подтвердил использование уже существующего
`l2_tN` без специального выделения. `@f()` было лишь исследовательским примером:
отдельной задачи обеспечить эту форму или запретить её по аналогии с C нет
([дословное уточнение](../2026-11-15.md#m14-address-scope)).

Исследование хранения return и примера `@(f())` объясняет этот путь, а не
добавляет самостоятельную возможность в план.
Статическое чтение текущего кода показывает:

- В lmx_graph_run.lm2 `lmx_graph_eval_value` получает обычный int-результат
  в локальную переменную number и при необходимости адресуемого значения
  вызывает `lmx_graph_int(g, number)` (строки 4337–4369). Унарный `@`
  вычисляет составной операнд и строит ссылку на полученную ячейку (4400–4418).
- В lmx_graph.lm2 `lmx_graph_int` выделяет обычную типизированную ячейку
  в арене и записывает число (384–394). Это не общая перезаписываемая ячейка
  всех return и не поле исходного описания выражения.
- Общий native-вход в lmx_call.lm2 получает dest/out от вызывающей стороны;
  эмиттер return в l2_frontend_lower.lm2 пишет в `l2_out_result[0]`.
  Место передачи результата вызова и долговечная адресуемая ячейка не обязаны
  совпадать: адрес нельзя возвращать на уже завершённый кадр вычисления.
- Конкретное native-место уже создаёт `lm_compiler_emit_call_result_value`
  в l2_frontend_values.lm2:2266: обычный локальный `l2_tN` нужного C-типа
  (для int — строка 2297). `lm_compiler_emit_dyn_tail_value` в
  l2_frontend_lower.lm2:13359 передаёт `&l2_tN` через dest. Это существующая
  автоматическая переменная вызывающего кода, а не вызов malloc для результата.
  Повторно выделять ячейку для взятия её адреса не нужно, если её времени жизни
  достаточно. Само это наблюдение не доказывает готовность всего пути вычисляемого
  поля и не отменяет существующие managed scalar/result representations.
- Именно чтение вычисляемого поля через `lmx_graph_step` пока отказывает
  (lmx_graph_run.lm2:1994–1995). Нельзя выдавать общий механизм ячейки
  результата за уже реализованное выполнение `@(data\x)`.

Автор подтвердил, что адресуется вычисленное значение и вопрос касался его
размещения, с использованием обычного решения, возможного в C
([дословное уточнение](../2026-11-15.md#m14-result-storage)).
Применять к вычисляемому полю обычный механизм результата написанного в нём вызова. Вызов даёт значение,
а если требуется адрес, используется обычная адресуемая ячейка этого результата.
Native может получать результат сразу в подходящее место вызывающей стороны;
не требуется отдельная система вычисляемых полей или выделение памяти для
каждого return независимо от потребителя.

`@(data\x)` для готовой ячейки x адресует её, а для сохранённого
вычисляемого объявления адресует результат его исполнения. Запись через адрес
результата не заменяет исходное объявление `int: x next()`; явная запись
`data\x := ...` остаётся операцией над исходным полем. Уточнение внесено в
[план M14](../../next_core_tasks_v3.md#native-structures) и
[задание Sol](../../to_sol.md#call-frame-20261115) и нормативные спецификации;
кодовая реализация ещё не принята. Обычные правила времени жизни
адресуемых значений сохраняются; временная транспортная переменная return не
становится автоматически устойчивым местом для пользовательского указателя.

Сопоставление с C не означает допустимости буквального `&f()`: унарный `&`
не принимает значение вызова как адресуемое место
([N1570, §6.5.3.2](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)).
Это справка о C, не основание вводить запрет в LMX или отдельную задачу поддержки `@f()`.
Обычное понижение для результата типа T — `T result = f(); T *p = &result;`;
при действующем ABI с выходным параметром вызов может сразу записать результат
в подходящую ячейку. Время жизни задаётся общими правилами её хранения, а не
особым правилом для return.

Для указателя, используемого внутри вызывающего кадра, схема с существующим ABI
выходного параметра выглядит так (служебные параметры и обработка статуса опущены):

```c
void caller(void) {
    int l2_t17;
    getValue_native(/* other arguments, */ &l2_t17);
    int *p = &l2_t17;
    use(p);
}
```

Здесь обычное место результата находится в кадре caller; отдельного выделения
в куче нет. Если значение уже представлено нужной ячейкой арены, используется
она. Более длительное хранение не получается из `&l2_t17` автоматически:
для него действуют существующие правила адресуемых значений, без новой системы
escape analysis или обязательного переноса каждого return в кучу.

Удаление входного исполнения, dirty и публикации сохраняется.
Нормативные правки выполнены; новая кодовая приёмка остаётся задачей M14.
