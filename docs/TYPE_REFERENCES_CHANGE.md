# TYPE — адрес системного описания типа

Уточнение автора от 26 ноября 2026. Этот документ подробно фиксирует переход
от числового кода-счётчика к прямой ссылке на описание типа для **всех** типов,
а не только для Array. Он задаёт новый ABI; прежние свидетельства работы
числового ABI не являются проверкой этой редакции.

## 1. Основная норма

Логическая типизированная запись по-прежнему имеет форму `{type value}`.
Поле `type` теперь содержит **адрес канонической системной Structure,
описывающей тип**. Это не индекс таблицы, не последовательный номер и не
число, которое затем требуется преобразовать в адрес описания.

В этой главе `TypeRef` — поясняющее имя машинного типа ссылки, а не новый
синтаксический элемент LMX. Например, если системные описания имеют обычное
представление Lmx, C-проекция может использовать:

```c
typedef const Lmx *TypeRef;
```

Имена C здесь поясняют ABI. Они не добавляют обязательных полей пользовательской
Structure и не заменяют общую модель ссылок LMX.

Правило одинаково для int, char, floating-point типов, обычных ссылок,
Structure, Array, производных указательных типов и остальных примитивных
представлений. Дескриптор описывает требование типа и необходимые правила
физического доступа. Отдельной системы числовых идентификаторов типов нет.
Обычные индексы, размеры и внутренние числовые классификаторы C-бэкенда
по-прежнему могут быть числами; они не являются значением поля `type`.

## 2. Один тип для одинакового полного объявления

```lmx
[]int: var [1 2]
[]int: vr2 [1 2 3]
[5]int: var5 [1 2 3 4 5]
[N]int: varN
```

У первых двух объявлений одно полное требование `[]int`, поэтому используется
один канонический дескриптор этого типа. Имена var/vr2 и текущая длина
инициализатора не участвуют в идентичности типа. `[5]int` — другое требование:
его описание содержит явное ограничение размера 5.

Для `[N]int` выражение N разбирается общим P0 и вычисляется однократно в
контексте потребления TYPE. По полученному полному требованию система ищет
канонический дескриптор или создаёт его, если такого ещё нет. Если N=5,
полное требование совпадает с `[5]int`, и используется то же описание.
Динамичность не означает обязательное создание новой идентичности при
каждом повторном вычислении равного требования.

Количество производных типов не фиксируется заранее языковой таблицей.
Общий механизм канонизации принимает новые полные требования во время
исполнения. Созданное описание неизменяемо и сохраняет стабильный адрес
на протяжении своей допустимой жизни. Другое полное требование получает
другое описание; существующее описание не переписывается под новый размер.

Отсутствие инициализатора у `[N]int: varN` сохраняет обычное uninit-состояние.
Построить описание типа не означает выделить N элементов или заполнить их
нулями. Прежнее различие uninit, пустого значения и null сохраняется.

## 3. Где лежит ссылка на тип

Пусть p — адрес первого байта **готового value в настоящей типизированной
графовой записи**, а B — размер хранимой ссылки TypeRef. Тогда:

```text
адрес ячейки type = byteAddress(p) - B
B = sizeof(TypeRef)
значение этой ячейки = адрес системной Structure описания типа
```

Нужно различать два адреса: адрес ячейки префикса и адрес дескриптора,
прочитанный из этой ячейки. Сам дескриптор типа не лежит непосредственно
перед каждым value: там находится только ссылка на общее описание.

C-проекция при соблюдённых правилах выравнивания и действительном TypeRef
объекте в префиксе:

```c
TypeRef type =
    *(TypeRef const *)((unsigned char const *)value_ptr - sizeof(TypeRef));
```

В варианте загрузчика сериализованных байтов безопасная операция загрузки
должна отдельно соблюдать договор представления и выравнивания; нельзя
просто разыменовать произвольный невыравненный входной буфер как TypeRef.

### Размер префикса

Вычитать следует **размер реально хранимой ссылки**, а не автоматически
`sizeof(size_t)`. Эти размеры могут совпадать на целевой платформе, но такое
совпадение не является определением нового ABI. В байтовой арифметике шаг
равен одному байту; обычное вычитание из типизированного C-указателя может
масштабировать смещение размером его элемента.

Прежние утверждения «код типа int, четыре байта перед value» и фиксированные
числа размеров записей должны быть заменены формулами с B. Например, при
B=8 и payload int размером 4 логический размер равен 12 байтам, но шаг арены
может быть больше из-за выравнивания следующей записи. Это пример конкретной
машинной раскладки, а не обещание одинаковых размеров int на всех целях.

### Выравнивание

Префикс TypeRef расположен непосредственно перед value, без padding между
ними. Арене разрешено добавить padding **до префикса** и между записями так,
чтобы value удовлетворял своему выравниванию, а префикс — выравниванию TypeRef.
Нельзя полагаться на автоматически выбранную компилятором раскладку
`struct { TypeRef type; T value; }`: она может вставить промежуточный padding.

Общий шаг обхода записей должен учитывать B, размер payload по описанию типа
и требуемое выравнивание. Нельзя сохранить старое `+4`/`-4` в walker,
аллокации, копировании, GC или сериализации.

## 4. Уточнение исходной записи LMX

В обычном выражении `struct\field` потребляется как значение поля; это не
универсальное обозначение числового адреса его payload. Уже существующая
явная форма взятия адреса готового поля — `(@struct\field)`.

Не следует подменять её на `@(struct\field)`: в действующей грамматике это
иная компактная форма ресивера. Для C sizeof используется существующий
оператор `c.sizeof` в L2. Имя `TypeRef` выше пока является поясняющим C-именем,
поэтому C-формула задаёт точный ABI без выдуманной исполняемой LMX-функции.

Формула обратного смещения применима только к действительному адресуемому
value с таким префиксом. В частности:

- У элемента плотного C-подобного Array<T> нет отдельного префикса на каждый
  элемент; его тип берётся из описания самого Array и элементного договора.
- Адрес обычной нативной локальной ячейки не обещает графового TypeRef перед ней.
- Uninit-запись сохраняет отсутствие payload; нельзя читать байты воображаемого
  value или превращать её в инициализированную запись заменой одного префикса.
- Адрес исходного вычисляемого объявления не является автоматически адресом
  результата его исполнения.

Так сохраняется единое представление типизированных записей без требования
дублировать type перед каждой машинной ячейкой любого происхождения.

## 5. typeof и системный дескриптор

`typeof(obj)` / `sys\typeof(obj)` получает ссылку TypeRef на фактическое
системное описание типа. Результат больше не является int-кодом счётчика:

```lmx
@: savedType typeof(obj)
@: typeInfo sys\descriptor(savedType)
@: currentTypeInfo sys\descriptor(typeof(obj))
```

Ссылка savedType удерживает выбранное неизменяемое описание по обычному
договору жизни метаданных типа. Сами запросы не исполняют пользовательский
инициализатор, не вызывают converter и не копируют объект.

Поскольку TypeRef уже обозначает системную Structure типа,
`sys\descriptor(TypeRef)` возвращает **то же каноническое описание**.
Эта TYPE-ветвь определяется по системной идентичности и принимающему договору
канонического описания типа. Она имеет приоритет для самого такого объекта;
совпадения имён или набора пользовательских полей для неё недостаточно.

Для обычного Array/Structure, который не является каноническим системным
описанием типа, `sys\descriptor(obj)` сохраняет прежний результат из трёх
живых адресов parent/length/storage. Вариант без аргумента сохраняет прежний
выбор текущего DATA. Нельзя одновременно оставить прежнюю числовую TYPE-ветвь
и объявить, что type теперь есть непосредственная ссылка.

Пример с обычным примитивным типом:

```lmx
@: intInfo sys\descriptor(int)
```

TYPE-потребители, результаты type-конструкторов `[]T`, `[N]T`, `@T`,
сигнатуры и последовательность `types` должны работать с TypeRef.
`types` становится последовательностью ссылок на описания, не []int.
Приём целого числа как скрытого адреса типа не добавляется; машинные casts
L2 сохраняют свой отдельный низкоуровневый договор.

## 6. Совместимость и канонизация

Быстрое равенство ссылок на один канонический дескриптор означает одинаковый
полный тип в данном контексте. Совместимость типов остаётся более общей
направленной проверкой и не сводится к сравнению адресов.

Явные ограничения `[5]int` входят в описание типа. Текущие length и capacity
обычного `[]int` сами по себе не создают новый тип. Из этого следует, что
прежнюю промежуточную схему смены typeof при каждом переходе compact/reserved
нельзя сохранять как универсальную норму.

Наличие отдельной записи capacity можно определять существующей ассоциацией
экземпляра: если запись резерва есть, прочитать capacity; иначе capacity=length.
Так reserve не требует менять TypeRef обычного []int. Размеры осей определяются
полным описанием типа и, когда это однозначно, текущей length — см. раздел 8.

## 7. Жизнь описаний, attach, сериализация и native

Адрес описания должен оставаться действительным, пока типом пользуются записи,
подготовленный код, сохранённые TYPE-ссылки и другие допустимые потребители.
Описание не освобождается вместе с одним из массивов данного типа.
Не вводится собственный независимый type-interner для каждой функции.

В пределах совместимого общего контекста attach может сохранить TypeRef,
если передано необходимое владение или гарантирован срок жизни общего
описания. Между независимыми контекстами требуется обычное согласование
канонических описаний и ссылок; совпадение числовых адресов доказательством
не является.

Сохранённый файл не переносит сырой машинный адрес как устойчивый идентификатор
типа. Сериализация сохраняет типовые описания и связи; восстановление создаёт
или находит соответствующие канонические TYPE-структуры и устанавливает
TypeRef в записях. Повторно используются существующие механизмы графовых
ссылок и их релокации. Нативный модуль связывает свои TYPE-ссылки с действующим
контекстом; старая машинная константа адреса из другого запуска не подходит.

Типы самих системных TYPE-структур также должны иметь конечное описание.
Бутстрэппинг создаёт нужные системные узлы, затем связывает их; допустим
графовый цикл метаописания. Запрос `typeof(typeof(obj))` не должен порождать
бесконечную последовательность новых описаний.

Изменение размера и смысла префикса — новая редакция ABI. Старые бинарные
модули, дампы памяти и реализации с int-кодом не объявляются совместимыми
одним переименованием поля.

## 8. Незаданные размеры не становятся скрытыми параметрами типа

Автор окончательно определил: **тип полностью задаётся нормализованным
описанием слева**. В частности, `[][]int` и `[](2)int` — один тип.
Инициализатор не создаёт более конкретный фактический TypeRef и не добавляет
к нему скрытые размеры.

```lmx
[][]int: a [[1 2 3] [4 5 6]]
[][]int: b [[1 2] [3 4] [5 6]]
```

Обе записи выше используют один TypeRef `[][]int` и дают одинаковый плоский
поток 1..6. Написанные границы строк проверяются при потреблении инициализатора,
но не становятся сохранённой индивидуальной формой массива. Никакого
различающего их второго shape-дескриптора не вводится.

Чтобы задать именно эти две разные формы, автор указывает разные полные типы:

```lmx
[2][3]int: var23
[3][2]int: var32
```

Они имеют разные дескрипторы типов; отсутствие инициализаторов здесь по-прежнему
означает uninit, а не неявно выделенные массивы.

Для `[]int` нужная линейному потребителю длина берётся из length. Для
`[][3]int` единственный оставшийся размер можно вычислить как length/3,
если деление допустимо. Для `[][]int` одних шести элементов недостаточно,
чтобы выбрать 2×3, 3×2 или другие размеры: отсутствующие оси остаются
неизвестными. Обычный плоский доступ при этом разрешён. Операция, которой
действительно нужна неопределённая форма, сообщает диагностику по своему
договору и не поднимает старый инициализатор как скрытые runtime-метаданные.

Следовательно, прежние четыре формы автора с `[][3]int` и `[][]int` могут
давать одинаковые элементы и одинаковое плоское хранилище. После данного
уточнения их разные написанные требования нельзя объявлять одним типом.
Именно объявление, включая явно заданные выражения размеров, определяет TypeRef.

Неполное описание осей само по себе не запрещает создать Array. Например,
`[][]int: [1 2 3 4 5 6]` хранит шесть элементов с незаданными размерами осей;
`[0][]int: []` и `[][0]int: []` хранят пустое значение без угадывания другой
оси. Противоречащие явно заданным размерам длины и непрямоугольные явно
написанные строки по-прежнему отвергаются. Если все размеры заданы, их
произведение должно совпадать с length.

При length=capacity второго дескриптора нет. При резерве необязательная запись
capacity хранит свойство экземпляра, не меняя TypeRef. Таким образом, одинаковая
левая часть остаётся одним типом и при разной длине, и при разном резерве.

TypeRef ABI. Эта редакция — документальная норма и описание необходимых изменений;
производственная реализация и исполнение: **NOT_RUN**.
