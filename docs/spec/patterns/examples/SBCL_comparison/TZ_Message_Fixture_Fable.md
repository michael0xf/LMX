# ТЗ для Fable: исполняемый fixture S24 на существующем Message

## Статус и границы

Этот файл лежит только в `patterns/examples/SBCL_comparison` и не меняет внешние документы или ядро. Нового операнда, ресивера `spawn`, отдельного `await` или нового протокола сообщений здесь **не вводится**. Требуется собрать проверяемый интеграционный fixture для уже описанного механизма Message/post.

Текущий S24 — сопоставление прикладных протоколов. SBCL-сторона выполнена на реальном потоке и mailbox. Для LMX в этом пакете нет исполняемой среды и подтверждённого parser fixture `post`; исходник не выдаётся за пройденный запуск. До выполнения пунктов ниже S24 остаётся `related_analogy` и не входит в итоговые отношения размеров полных пар.

## Подготовка окружения

1. Использовать существующий API L2/host текущего рабочего ядра. Создать три исполняемых L3 Thread с графами `ProducerMessage`, `WorkerMessage`, `CollectorMessage`; обычное письмо не повышать до Thread на месте.
2. У каждого экземпляра своя арена и одна последовательная полоса исполнения. Включить детей в обычный `Thread.children` родителя без второго списка членства.
3. Явно передать Producer массив `items`, адрес Worker в `worker` и адрес Collector в `collector`. Не наследовать весь контекст host. Адресованные вызовы разрешаются существующим транспортом, а не чтением чужой изменяемой памяти.
4. Привязать реальные пути `worker\Add\add`, `worker\Finish\finish`, `collector\accept`. Выбор вызовов/типов/ответа использует общую систему LMX. Не добавлять фасадный список «всех методов», пользовательские числовые корреляции или поиск подходящего answer при получении ответа.
5. Выполнить обычный запуск `ProducerMessage\start`. Host должен дать всем владельцам обслуживать turns и закончить fixture по явному завершению Collector, а не по пустому inbox.

## События и завершающий результат

Producer публикует по одному `add(value)` на элемент и затем `finish()`. Один producer и штатное опубликование в порядке staging дают Worker последовательность с finish после всех add. Каждый add меняет `WorkerMessage.total` только на полосе Worker; нулевое значение — обычное сообщение, не маркер завершения.

`finish` возвращает накопленную сумму и устанавливает обычный `success := 1`. Получение результата должно успеть опубликовать последний reply по штатным правилам успешного конца turn. Producer хранится до обслуживания его pending reply. Предварительно привязанный answer вызывает `CollectorMessage\accept`, который записывает результат, признак completed и завершает свой Thread.

Producer не блокирует свою полосу в ожидании будущего answer. Родитель или host после завершения Collector выполняет штатное закрытие оставшегося Producer, дожидается безопасного конца всех детей и освобождает арены. Не удерживать адрес завершённого стекового кадра как обработчик. Фикстура использует живые владельцы, не фиктивную бессрочную локальную функцию.

Профиль сравнения ограничен локальной доставкой без внешнего прерывания и переполнения int. Внешний тестовый deadline может обнаружить зависание и завершить неудачный тест, но не является выдуманным языковым `timeout`. Ошибки доставки/таймауты не маскируются успешным числом; расширение профиля на них потребует отдельного сравнения. HTTP уже существует в норме; данный локальный пример не требует нового HTTP ресивера.

## Приёмка

| Вход items | Результат | Обязательные наблюдения |
| --- | --- | --- |
| `[1,2,3]` | `6` | Три add, один finish, один нормальный ответ |
| `[]` | `0` | Ни одного add; finish и ответ сохраняются |
| `[-2,0,5]` | `3` | Ноль доставляется и учитывается как обычное число |
| Два последовательных запуска | Независимые суммы | Новые арены/состояние, отсутствие оставшегося total/pending reply |

Дополнительно проверить, что источник имеет ровно один `finish`, Collector получает ровно один результат и никакой callback не исполняется после освобождения его владельца. Записать точную команду запуска, профиль исполнения (native/walker, dedicated/shared thread), версию ядра, результат parser fixture и журнал проверок. Отдельно показать размеры host-кода обеих сторон; не включать bootstrap только у одного языка в сравнение прикладного протокола.

После успешной приёмки можно обосновать изменение статуса S24 и пересчитать его участие в статистике каталога и общей сводке. Непройденный fixture не получает статус полного исполнившегося сравнения только из-за добавления текста или новых общих функций.
