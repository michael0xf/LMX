## Изменение

1. **Построитель — отдельный модуль.** `src/l2src/l2_graph_build.lm2`: P0-аксессоры и построитель чистого графа
   перенесены из `l2_graph_tool.lm2` без изменения байтов кода (сверено по строкам), экспорт `lm_graph_build_file`,
   собственный заголовок. `l2_graph_tool.lm2` (выпуск программы над графом и командная строка graph_trans) читает его
   заголовок; `tools/graph_trans.lm2` подключает оба модуля; `bld_graph` переводит построитель первым.
2. **Вход frontend из чистого графа.** `src/l2src/l2_frontend_graph.lm2`, `lm_compiler_graph_main`: слова машинного
   модуля frontend (`--library --machine NAME … SOURCE [PART …] OUTPUT`) после селектора `--graph`, который читает
   первым корень hosted F `tools/l2trans.lm2` (иначе — прежний `lm_compiler_cli_main`). Трансляция: граф источника в
   арене трансляции (`lm_graph_build_file`; дерево P0 уничтожено построением), обход корня открывает namespace
   трансляции (`lmx_graph_space_open`: каждый записанный `fn:` создаёт там свою Structure с частями args, return, body),
   модуль пишется из этих Structure в форме F: метка (`# Generated by l2trans from the clean graph of …`), преамбула
   (`include: "<stddef.h>"`, predef и include корня), один блок prototype всех функций (своего заголовка нет), каждая
   функция с параметрами `l2_p<функция>_<формал>_<имя>`, как их называет путь P0. Имена тела разрешаются при
   трансляции по адресам написаний среди формалов (`lmx_graph_formal`, имя формала — `lmx_graph_formal_name`, как у
   binder); C-дверь `c.X` и числа с суффиксом (`0U`, слово) — как написаны; int-примитив — значением. Таблицы трансляции
   освобождаются с ней, вывод — во `OUTPUT.tmp`, публикация — только целого модуля.
3. **Подмножество шага.** То, чем написан `lmx_schedule`: записанные `fn:` с результатом (C-скаляр: int, char, size_t,
   unsigned, ulong), формалы `@: name T`, `T: name` (T — C-скаляр) и `int: name`, операторы `if:` (с `else:` после
   него; тела закрываются `---`), `return: value`, запись поля через голову-путь `owner\field: value` (срез 337),
   операции `= != < <= > >= + - * / % && ||` и пути [owner, \, field] от ссылочного формала. Иная форма отказывает
   на месте (`l2trans error: SOURCE: WHERE: WHY`, вывода не остаётся); отката на P0 для модуля, который рецепт переводит
   из графа, нет. Части после источника (`convert.lm2`, `primitive.lm2` каждой машинной трансляции) не читаются: ни одно
   имя машинной функции до них не доходит.
4. **Рецепты.** `bld_machine_module_from(…, graph, …)` — единый рецепт машинного модуля: при `graph != 0` модуль
   переводит hosted F (`graph 0 entry 0 -- --graph --library --machine …`, CWD — `src` стадии), иначе — fe;
   `bld_machine_module` — тот же рецепт без hosted F. `bld_kernel_l2` переводит так `lmx_schedule`; `bld_runtime_from`
   и команда `build-runtime REPO STAGE BASE FRONTEND LABEL [HOSTED-FRONTEND]` (седьмое слово — hosted F). Без седьмого
   слова — прежний путь P0 (им пока строит runtime цепочка поколений). `bld_frontend_host` переводит построитель и
   `l2_frontend_graph` (с заголовками), агрегат (вид 60) подключает их.
5. **Свидетель C-двери.** `tests/cdoor/schedule_machine.lm2` (строка smoke-списка): отказ без слота и без лимита,
   tick без ожидания отвечает состояние, ожидание с 100 при лимите 10 — ещё ждёт на 109, просрочено на 110, позже —
   то же состояние; беззнаковое вычитание — ожидание с `ULONG_MAX - 5` ждёт на 3 и просрочено на 4. Выход 7, 80… —
   номер проверки.

Отличие формы: условие `||` записано прямо (у P0 — временная `l2_t0`), операция в операнде — в скобках:

```text
fn: lmx_schedule_tick (@: LmxSchedule l2_p2_0_slot; ulong: l2_p2_1_now) int
    if: (l2_p2_0_slot = 0) || (l2_p2_0_slot\limit = 0U)
        return: c.LMX_SCHEDULE_INVALID
        ---
    if: l2_p2_0_slot\state != c.LMX_SCHEDULE_WAITING
        return: l2_p2_0_slot\state
        ---
    if: (l2_p2_1_now - l2_p2_0_slot\started) >= l2_p2_0_slot\limit
        l2_p2_0_slot\state: c.LMX_SCHEDULE_OVERDUE
        ---
    return: l2_p2_0_slot\state
end: lmx_schedule_tick
```

## Граница и следующее

1. Цепочка поколений (`bootstrap`, `rebuild runtime`) строит runtime без hosted F: её runtime собирается раньше
   любого hosted F поколения, поэтому `lmx_schedule` там пока переводит путь P0. Шаг 3: поколение строит hosted F на
   предыдущем runtime и передаёт его в `bld_runtime_from`, так что `lmx_schedule` каждого runtime — из графа.
2. Граф-путь пока отказывает `sub`, собственному заголовку модуля (`--header`), локальным местам, циклам, вызовам,
   унарным операциям и записи формала; это следующие машинные модули маршрута.
3. Печать driver hosted F при ненулевом выходе (`FAIL [exit] …`) остаётся строкой журнала шага.
