## Как читать примеры

**Отдельные программы.** Каждый раздел имеет собственный namespace. Повторяющиеся `Demo` и другие имена не надо объединять в один модуль без переименования. Основной блок содержит определения; приведённый после него вызов помещается в исполняемый контекст. Печать и неизвестная библиотечная обвязка не предполагаются.

**Границы блоков.** Пустая физическая строка, в том числе состоящая только из пробельных символов, завершает весь текущий синтаксический блок как `---` на виртуальном уровне `−1` над root. Поэтому внутри открытой пользовательской структуры пустые строки не служат оформлением. Вложенный `---` закрывает только соответствующую внутреннюю структуру и позволяет продолжить внешнюю; он сохранён в Observer и Visitor. Последний обычный блок закрывается на EOF. Одна завершающая LF не является дополнительной пустой строкой. Правило применяется вне защищённых лексических форм, например содержимого литералов. [Правило пустой строки][E]

**Структура и вызов.** Метод — обычная структура. DATA для её выполнения задаётся фактическим `parent(code)`. Это отношение данных и кода нужно отличать от адресации полей: **`node\` — лексический оператор, а не оператор перехода к parent или к вызывающему**. В Factory и Observer он выбирает нужное внешнее лексическое поле, даже если оно находится выше непосредственного родителя метода. [Правила callable и DATA][B]

**Сигнатура и структурный шаблон.** `fn: Name Data` создаёт именованное описание сигнатуры. `Data` может быть уже существующей структурой с входными объявлениями, `return` и методами. Fn-проверка сопоставляет число и порядок типов явных входов и результат; тела вложенных методов в неё не превращаются. Объявленные входы с default также входят в сигнатуру. Обычное структурное требование проверяет всё заданное дерево модели. Поэтому `fn: Transform Algorithms` и требование `Product` выполняют разные проверки. [Правила fn и implements][B]

**Метки аргументов.** В `@: p Signature Candidate\method` явно заданы имя ссылки, требование и реализация. Именованный вызов через fn-ссылку использует метки сигнатуры; они выбирают позиции реальных входов реализации. Если в сигнатуре первый вход назван `x`, а у кандидата `value`, явное `x := ...` направляется в первую позицию. Это не переименовывает зависимости для скрытого связывания. В компактных примерах ниже метки обычно совпадают, поскольку сигнатура получена из самого DATA. [Правила аргументов][B]

**Значение и место.** Объявленный, но не инициализированный вход получает копию одноимённого значения непосредственного вызывающего через autofill. Необъявленное собственными data/code свободное имя может связаться с местом в локальном контексте непосредственного вызывающего; в LMX это прозрачно выглядит как переменная исходного типа. Если такое место уже является alias, его дальнейшая передача сохраняет исходное место. Сохранённый механизм транзитивного fallback сам по себе не превращает копию в alias. Эта разница существенна в Command. Готовый собственный default автоматически не вытесняется одноимённой локальной переменной: его можно заменить явным аргументом. [Правила связывания][B]

**Ограничение private.** `private` закрывает неявное динамическое связывание в обе стороны: private-поле вызывающего не становится скрытым источником, private-лексическое поле вызываемого не подменяется таким способом. Явная передача и обычная лексическая видимость сохраняют свои правила; `private` не запрещает их сам по себе. [Правило private][B]

**Импорт.** `import` добавляет константные объявления, которые при вызове считаются корневыми в DATA. Пользовательская структура константна и без отдельного `const`, поэтому её имя импортируется. Обычные переменные не импортируются, а фактический DATA импортированного метода сохраняется. Например, `import: cycles` открывает имя `iterate`, но его поля `iteration` и `body` остаются в `cycles`. [Правила import и передаваемых объявлений][D]

## 1. Iterator — итератор и пользовательский iterate

**Задача:** отделить получение элемента от его обработки. `numbers\next()` хранит позицию, `cycles\iterate` управляет повторением, вызывающий передаёт объявление элемента и тело.

```lmx
numbers:
    int: position 0
    return: int
    next:
        throws: Stop
        if: node\position >= 3
            throw: Stop()
        node\position += 1
        return: node\position

cycles:
    @: iteration
    @: body
    iterate:
        while: 1
            iteration()
            catch: Stop ()
                break
            body()

use:
    import: cycles
    int: total 0
    return: int
    run:
        numbers\position := 0
        iterate: int: item numbers\next()
            item *= 2
            total += item
        return: total
```

**Вызов:** `use\run()`. **Ожидаемый результат: 12.**

| Вызов next | Получено | item после тела | total |
|---|---:|---:|---:|
| 1 | 1 | 2 | 2 |
| 2 | 2 | 4 | 6 |
| 3 | 3 | 6 | 12 |
| 4 | Stop | Тело не исполняется | 12 |

Первый аргумент `iterate` сохраняет форму объявления `int: item numbers\next()`. Передача не вызывает `next`. Каждый `iteration()` исполняет эту форму, создавая или обновляя `item` в общем для переданной формы и тела контексте. `body()` использует то же место; чтение `item` не запускает итератор повторно.

`total` в теле связан с рабочим местом текущего `use\run`. При новом запуске оно получает начальное значение 0 из объявления. Запись `use\total := 0` не нужна. Позиция должна переживать отдельные вызовы `next`, поэтому сам итератор меняет графовое поле через лексическое `node\position`; драйвер сбрасывает его через `numbers\position` перед новым обходом.

`import: cycles` открывает имя `iterate`, сохраняя его DATA в `cycles`. Объявления `iteration` и `body` не копируются в `use`.

**Граница примера:** окончание передаётся именованным выходом `Stop`, поэтому 0 допустим как элемент. Обработчик `catch` охватывает весь свой блок в обе стороны: `Stop` из тела тоже завершит цикл. Здесь нет отдельной коллекции и общего API контейнеров.

## 2. Strategy — заменяемый алгоритм

**Задача:** потребитель `Processor\apply` сохраняет свой код, а вызывающий выбирает удвоение или утроение.

```lmx
Algorithms:
    int: value
    return: int
    twice:
        return: value * 2
    thrice:
        return: value * 3

fn: Transform Algorithms

Processor:
    int: value
    @: operation Transform Algorithms\twice
    return: int
    apply:
        return: operation()

StrategyDemo:
    return: int
    run:
        import: Algorithms Processor
        @: operation Transform twice
        int: first apply(5; operation)
        operation := thrice
        return: first + apply(5; operation)
```

**Вызов:** `StrategyDemo\run()`. **Ожидаемый результат: 25.**

Первый вызов возвращает `5 × 2 = 10`, второй — `5 × 3 = 15`. Их сумма равна 25.

`twice` и `thrice` используют одно описание DATA в `Algorithms`. `fn: Transform Algorithms` извлекает из него сигнатуру `int → int` с публичным именем входа `value`. Отдельное повторное описание аргумента не нужно; методы `twice` и `thrice` не становятся частью дерева, сравниваемого fn-проверкой.

`apply(5; operation)` явно заполняет два собственных входа `Processor`: числовой `value` и ссылку `operation`. Это сохраняет смысл default: отдельный вызов `apply(5)` использует `Algorithms\twice`, даже если у вызывающего имеется одноимённая локальная ссылка на другую операцию.

Когда `apply` выполняет `operation()`, объявленный неинициализированный `Algorithms.value` получает копию значения из непосредственного контекста `apply`. После `operation := thrice` следующий явный аргумент выбирает утроение. Общее DATA устраняет повторные объявления, а каждый вызов всё равно имеет собственные рабочие значения.

**Граница примера:** показаны потребитель, типизированная ссылка и смена алгоритма. Реестр стратегий, настройка по конфигурации и дополнительные классы не требуются этому сценарию.

## 3. Factory — фабричные методы и копирование прототипа

**Задача:** создать два самостоятельных продукта с `payload = 10` и `payload = 20`, затем передать каждый обычному потребителю `execute`. Фабрика сначала изменяет исходный прототип, затем копирует его.

```lmx
Product:
    int: payload
    return: int
    read:
        return: payload
    create:
        return: Product
        small:
            node\payload := 10
            return: merge(Product)
        large:
            node\payload := 20
            return: merge(Product)

add1:
    @: product Product
    return: int
    execute:
        return: product\read() + 1

Demo:
    return: int
    run:
        import: Product add1
        int: first execute(create\small())
        int: second execute(create\large())
        return: first + second
```

**Вызов:** `Demo\run()`. **Ожидаемый результат: 32.**

`node\payload` в `small` и `large` явно выбирает лексическое поле `payload` структуры `Product`. Это не переход к непосредственному `create` и не поиск поля у вызывающего. `merge(Product)` создаёт самостоятельный продукт с соответствующим значением и связями скопированных методов.

`import: Product add1` делает имена `create` и `execute` доступными в `Demo\run`. В `execute` передаётся уже созданный продукт: `execute(create\small())` возвращает 11, а `execute(create\large())` — 21. В `add1` используется обычное структурное требование `Product`, проверяющее описанное дерево продукта, а не fn-сигнатуру фабрики.

Если сохранить оба результата фабрик отдельно, после второго создания первый `read()` по-прежнему должен возвращать 10, второй — 20. Исходный прототип к этому моменту содержит 20. Каждый фабричный метод сам устанавливает значение перед копированием, поэтому предварительное обнуление прототипа для этой демонстрации не требуется.

**Граница примера:** здесь сочетаются фабричные методы и копирование прототипа. Отдельная иерархия Creator и передача фабричного callable не используются. В сравнении с другими языками проверяется независимость одного числового поля и сохранение вызываемого `read`. Это не приравнивает их поверхностное копирование к общей семантике `merge` для произвольных графов с вложенным изменяемым состоянием.

## 4. Adapter — согласование интерфейсов

**Задача:** вызвать старый метод, у которого входы объявлены в порядке `right`, `left`, через интерфейс `left`, `right`. Оба типа — `int`, поэтому одной проверки типов недостаточно для правильного назначения значений.

```lmx
Legacy:
    int: right
    int: left
    return: int
    subtract:
        return: left - right

Adapter:
    int: left
    int: right
    return: int
    subtract:
        return: Legacy\subtract(right; left)

fn: Difference Adapter

Demo:
    return: int
    run:
        import: Adapter
        @: operation Difference subtract
        return: operation(8; 3)
```

**Вызов:** `Demo\run()`. **Ожидаемый результат: 5.**

`Adapter` задаёт нужный потребителю порядок входов. `fn: Difference Adapter` извлекает соответствующую сигнатуру. Вызов `operation(8; 3)` передаёт адаптеру `left = 8`, `right = 3`; тот делегирует `Legacy\subtract(right; left)`, то есть отправляет 3 в первый вход старого метода, а 8 — во второй. Результат `8 − 3 = 5`.

Если вместо `Adapter\subtract` назначить ссылке `Legacy\subtract`, fn-проверка типов `(int, int) → int` пройдёт. Но вызов через интерфейс `Difference` даст `right = 8`, `left = 3` и результат −5. Имена кандидата не переставляют позиции сигнатуры.

**Граница примера:** адаптер выполняет конкретную перестановку и действительно вызывает прежний метод. Дополнительного объекта-обёртки для этого согласования не требуется. Type shape устанавливает допустимую форму вызова; семантику вычитания обеспечивает сама перестановка.

## 5. Observer — несколько подписчиков события

**Задача:** отправить каждое событие двум обработчикам. Один запоминает последнее значение, другой накапливает сумму. Издатель хранит две заменяемые ссылки.

```lmx
Observer:
    int: last 0
    int: total 0
    Actions:
        int: value
        remember:
            node\last := value
        accumulate:
            node\total += value
    ---
    fn: ListenerSignature Actions
    Publisher:
        int: value
        @: first ListenerSignature Actions\remember
        @: second ListenerSignature Actions\accumulate
        notify:
            first()
            second()

Demo:
    return: int
    run:
        import: Observer\Publisher
        Observer\last := 0
        Observer\total := 0
        notify(3)
        notify(8)
        return: Observer\total
```

**Вызов:** `Demo\run()`. **Ожидаемый результат: 11.**

| Событие | last | total |
|---|---:|---:|
| 3 | 3 | 3 |
| 8 | 8 | 11 |

Поля `last` и `total` находятся в `Observer`, а DATA обработчиков — в `Actions`. `node\last` и `node\total` обращаются к этому внешнему лексическому состоянию. Их смысл не ограничивается непосредственным parent.

`fn: ListenerSignature Actions` извлекает один вход `int` без результата. `last` и `total` находятся вне DATA обработчика, а `first` и `second` — в отдельном `Publisher`, поэтому эти поля не добавляются в сигнатуру подписчика. Разделение этих DATA сохраняет точный контракт без повторных описаний.

`notify(3)` и `notify(8)` явно задают событие. Внутри каждого вызова `first()` и `second()` получают свои копии `value` через autofill от непосредственного `notify`. Дальнейшая запись выполняется в лексическое состояние графа, которое сохраняется между уведомлениями. Драйвер сбрасывает его перед демонстрацией.

Внутренний `---` после `Actions` необходим: он оставляет `ListenerSignature` и `Publisher` внутри `Observer`. Пустая строка на этом месте закончила бы весь `Observer`.

**Граница примера:** два синхронно уведомляемых подписчика, четыре вызова обработчиков за демонстрацию. Динамический список подписок, отписка, очередь событий и политика ошибок требуют собственной логики.

## 6. Decorator — обёртки с одним интерфейсом

**Задача:** расширять вычисление, сохраняя один контракт `int → int`: удвоить число, прибавить 1, умножить результат на 3.

```lmx
Transforms:
    int: value
    return: int
    base:
        return: value * 2
    withOne:
        return: base() + 1
    withThree:
        return: withOne() * 3

fn: TransformSignature Transforms

Demo:
    return: int
    run:
        import: Transforms
        @: transform TransformSignature withThree
        return: transform(10)
```

**Вызов:** `Demo\run()`. **Ожидаемый результат: 63.**

Для входа 10 получается последовательность `10 → 20 → 21 → 63`.

`base`, `withOne` и `withThree` используют DATA `Transforms`. Поэтому вход `value` и результат объявлены один раз. При каждом вызове очередной метод получает собственную копию `value` через autofill. `withThree` передаёт 10 в `withOne`, тот — в `base`; обратная цепочка результатов даёт 20, 21 и 63.

`fn: TransformSignature Transforms` сохраняет проверку callable как `int → int`. Ссылка `transform` может указывать на `base`, `withOne` или `withThree`; для входа 10 результаты будут соответственно 20, 21 и 63. Публичный вход здесь называется `value`, как в исходном DATA.

**Граница примера:** это фиксированная цепочка обёрток. Произвольный конструктор цепочки во время выполнения потребовал бы дополнительных ссылок между слоями. Strategy выбирает операцию; в этой композиции каждый слой делегирует прежней операции и добавляет обработку её результата.

## 7. Command — действие над локальным состоянием вызывающего

**Задача:** `Invoker` выбирает момент исполнения переданной команды. Сами команды меняют локальную переменную `value` текущего `Demo\run`; отдельный общий объект счётчика не требуется.

```lmx
fn: Command ()

Commands:
    addTwo:
        value += 2
    twice:
        value *= 2

Invoker:
    @: command Command Commands\addTwo
    execute:
        required: value
        command()

Demo:
    return: int
    run:
        import: Commands Invoker
        int: value 0
        execute()
        execute(command := twice)
        return: value
```

**Вызов:** `Demo\run()`. **Ожидаемый результат: 4.**

`fn: Command ()` задаёт ноль явных входов и отсутствие результата. Свободное имя `value` не добавляется в эту явную сигнатуру. Ссылка на `twice` передаётся без `()`, поэтому действие выполняется внутри `command()`, а не во время передачи.

`required: value` обращается к уже видимому месту по обычным правилам связывания и проверяет его; собственного объявления `value` не создаёт. До вызова команды `Invoker\execute` тем самым получает место из непосредственного `Demo\run`. Команда получает из контекста Invoker уже установленный alias к той же исходной переменной. Значение 0 является заданным значением и само по себе не означает отсутствия места.

Первый `execute()` сохраняет default `Commands\addTwo` и меняет 0 на 2. Второй явно передаёт `twice`, которая меняет 2 на 4. В конце читается та же локальная переменная `Demo\run`.

Строка `required: value` здесь существенна. Если посредник вообще не потребляет `value`, старый транзитивный fallback может дать глубже вызываемой команде копию. Объявление `int: value` в самом Invoker также означало бы отдельное собственное место. Ни один вариант автоматически не обеспечивает изменение исходного места вызывающего.

**Граница примера:** синхронный вызов при доступном контексте. Ссылка на такую команду сама по себе не является автономным замыканием, сохраняющим локальную переменную после окончания её времени жизни. Очередь, undo и сериализация команд здесь не реализованы. Неявное связывание подчиняется двустороннему `private`.

## 8. Template Method — постоянная последовательность заменяемых шагов

**Задача:** алгоритм всегда выполняет подготовку, затем завершающий шаг, а вызывающий независимо выбирает реализации этих шагов.

```lmx
Pipeline:
    int: value
    return: int
    increment:
        return: value + 1
    twice:
        return: value * 2
    square:
        return: value * value
    execute:
        value := prepare()
        return: finish()

fn: Step Pipeline

Demo:
    return: int
    run:
        import: Pipeline
        @: prepare Step increment
        @: finish Step twice
        int: first execute(4)
        finish := square
        return: first + execute(4)
```

**Вызов:** `Demo\run()`. **Ожидаемый результат: 35.**

`Pipeline` одновременно задаёт DATA и содержит методы шагов и сам `execute`. `fn: Step Pipeline` извлекает сигнатуру `int → int`; тела методов не включаются в это сравнение.

`execute(4)` получает собственное рабочее `value = 4`. Имена `prepare` и `finish` не объявлены в его собственных data/code и связываются с локальными ссылками `Demo\run`.

Вызов `prepare()` автодополняет объявленный неинициализированный вход выбранного шага копией 4. `increment` возвращает 5. Присваивание `value := prepare()` изменяет рабочее место текущего `execute`, после чего `finish()` получает свою копию 5 и возвращает 10 либо 25. В исходное графовое поле `Pipeline.value` этот пример не записывает.

После `finish := square` последовательность `execute` сохраняется. Первый проход даёт `(4 + 1) × 2 = 10`, второй — `(4 + 1)² = 25`; сумма равна 35. Рабочее значение второго вызова снова начинается с явно переданной 4.

**Граница примера:** фиксированная последовательность с двумя заменяемыми шагами. Наследование классов для этой роли не требуется. Связывание ссылок и автодозаполнение числовых аргументов — разные операции: первые приходят как свободные имена, вторые являются объявленными входами шагов.

## 9. Visitor — действия для разных видов узлов

**Задача:** узел выбирает имя соответствующего действия, а вызывающий предоставляет его реализацию через контекст. Отдельный visitor-аргумент не передаётся.

```lmx
fn: ActionSignature (return: int)

Nodes:
    return: int
    on_number:
        throws: NoAction
        throw: NoAction()
    on_pair:
        throws: NoAction
        throw: NoAction()
    Number:
        int: value 3
        return: int
        accept:
            throws: NoAction
            int: n value
            return: on_number()
    ---
    Pair:
        int: left 4
        int: right 5
        return: int
        accept:
            throws: NoAction
            int: a left
            int: b right
            return: on_pair()

Actions:
    return: int
    number:
        return: n
    pair:
        return: a + b

Demo:
    return: int
    run:
        @: on_number ActionSignature Actions\number
        @: on_pair ActionSignature Actions\pair
        int: result 0
        result := Nodes\Number\accept()
        result += Nodes\Pair\accept()
        catch: NoAction ()
            result := -1
        return: result
```

**Вызов:** `Demo\run()`. **Ожидаемый результат: 12.**

1. `Number\accept` создаёт локальное `n = 3` и вызывает `on_number`.
2. Это внешнее имя связывается со ссылкой из `Demo\run`. Выбранный `Actions\number` получает `n` из непосредственного контекста `accept` и возвращает 3.
3. `Pair\accept` создаёт `a = 4`, `b = 5`; `Actions\pair` получает эти места из непосредственного контекста и возвращает 9.
4. Драйвер складывает 3 и 9, получая 12.

`ActionSignature` описывает ноль явных входов и результат `int`. `n`, `a`, `b` являются скрытыми зависимостями, а не дополнительными позициями fn. Пригодность по сигнатуре не создаёт эти значения: их предоставляет конкретный вызов из `accept`.

Fallback-методы находятся в `Nodes`, выше собственных DATA `Number` и `Pair`. Для `accept` это внешние имена, допускающие динамическую подмену. Если убрать локальное `on_pair` из `Demo\run`, сработает `Nodes\on_pair`, возникнет `NoAction`, и обработчик драйвера установит результат −1.

Готовое собственное поле в DATA конкретного узла не вытеснялось бы caller-local автоматически. Двусторонний `private` также сохраняет своё действие: private-источник не передаётся скрыто, private-лексическое объявление не подменяется динамически.

Внутренний `---` между `Number` и `Pair` сохраняет оба узла в `Nodes`. Пустая строка разорвала бы эту структуру.

**Граница примера:** посещаются два известных узла. Рекурсивный обход дерева, коллекция узлов и универсальная система маршрутизации не входят в листинг. Сохранены два выбора: вид узла определяет имя действия, контекст — реализацию.

## Общие механизмы

| Механизм | Где он используется |
|---|---|
| Общее DATA нескольких методов | Strategy, Decorator, шаги и алгоритм Template Method |
| Fn-сигнатура из существующего DATA | Strategy, Adapter, Observer, Decorator, Template Method |
| Копия объявленного входа через autofill | Алгоритмы Strategy, обработчики Observer, Decorator, шаги Template Method |
| Свободное имя и место непосредственного вызывающего | Command, ссылки шагов Template Method, обработчики Visitor |
| Сохранение уже установленного alias через посредника | Command |
| Переданная форма объявления и общее место тела | Iterator |
| Лексическое node и сохраняемое состояние графа | Позиция Iterator, прототип Factory, Observer |
| Обычное структурное требование и merge | Продукт Factory |

Механизмы повторяются, но конкретный алгоритм остаётся в программе: получить следующий элемент, уведомить обоих подписчиков, переставить аргументы, вызвать шаги по порядку или скопировать подготовленный продукт. Типизация подтверждает форму допустимого взаимодействия; назначение значений и нужный результат определяет реализация.

### Условия сопоставления

- Имена не нормализованы. Учтены выбранные объявления и демонстрации; абсолютная минимальность программ не заявляется. Python записан без необязательных аннотаций, поэтому одинаковые статические гарантии между языками не предполагаются.
- Factory сравнивает самостоятельность продукта с одним числовым полем. Общая глубина копирования произвольных графов LMX и объектов других языков этой таблицей не измеряется.
- Observer содержит два слота подписки; Decorator — фиксированную цепочку; Visitor — два посещения. Размер библиотек для произвольных коллекций, маршрутизации и построения цепочек не включён ни в одну версию.
- Command сравнивает конкретную последовательность локальных изменений. В других языках используются локальные замыкания либо локально созданный получатель; LMX Invoker расположен отдельно и получает контекст при вызове. Архитектура представления контекста различается, даже когда демонстрация возвращает одинаковый результат.
- Выбор решений на остальных языках и статусы их запуска подробно указаны в соответствующих файлах сравнений. Подсчёт символов выполнен программно; он не доказывает выполнение LMX, производительность или корректность произвольных расширений.
