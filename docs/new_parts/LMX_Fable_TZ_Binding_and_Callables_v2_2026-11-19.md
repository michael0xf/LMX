# ТЗ для Fable: связывание, сигнатуры и структурный вызов LMX

Редакция 2. Дата: 19 ноября 2026 года. Уточнено 20 ноября 2026 года: `fn: name data`.

## 1. Статус, основание и цель

Это новое самостоятельное ТЗ по последним ответам автора, включая дополнительное уточнение о двустороннем действии `private`. Оно заменяет противоречащие ему требования первого ТЗ `LMX_Fable_TZ_Callable_Simplification_2026-11-19.md`. Исследование вариантов оптимизации служит инженерным обоснованием, но не добавляет норм языка.

Существующая реализация не проверялась при подготовке ТЗ: сначала определить, какие пункты уже выполнены, и менять только необходимое. Последние решения автора имеют приоритет над прежними формулировками и историческими отчётами.

Цель: сохранить существующий механизм связывания как последний источник, добавить два прозрачных способа получения локальных переменных вызывающего, унифицировать callable с обычной Structure и унифицировать сигнатуру с её data-шаблоном. ## 2. Принятые решения автора

| ID | Обязательное решение |
|---|---|
| R01 | Сохраняется весь действующий механизм связывания; относительно двух новых способов он имеет низший приоритет. |
| R02 | Выбран вариант A: прежний fallback сохраняет собственное рабочее значение/описание в кадре. Его нельзя незаметно превратить в alias источника. |
| R03 | Объявленное, но не инициализированное место вызываемого может автоматически получить значение одноимённой переменной локального контекста вызывающего. |
| R04 | Используемое внешнее имя без действующего собственного объявления может прозрачно обозначать локальное место вызывающего. Скрытый указатель относится к нативной реализации; тип и запись переменной в LMX не меняются. |
| R05 | `private` действует в обе стороны для всех видов неявного динамического связывания: private-источник не предоставляется неявно; видимое private-объявление получателя не подменяется динамически. |
| R06 | Явная передача, обычная вложенная лексическая видимость и явные пути не запрещаются через private. Ограничения записи, включая применимые const/immutable, сохраняются. |
| R07 | Прежняя достижимость через цепочку A → B → C сохраняется, даже если B сам не потребляет имя. |
| R08 | `node` сохраняется. Удаление node и прежнего лексического/динамического механизма из первого ТЗ отменено. |
| R09 | Для выбранной исполняемой Structure C роль data выполняет её фактический parent. Специальное слово `data` и отдельный параметр data в call удаляются. |
| R10 | R0 не имеет data: это процедурный вход без аргументов. Для него не создаётся искусственная самопривязка data = code. |
| R11 | `return` описывается полем data. Такое объявление не присваивает результат. В роли code return — ресивер возврата. `fncall` удаляется. |
| R12 | Остаются `call(code)` и `call(args code)`. Любая Structure может исполняться в роли code через `f()` или `f(args)`. |
| R13 | `fn: name data` создаёт именованную сигнатуру и имеет два аргумента: имя сигнатуры и её data-шаблон, включая поле return. Имя затем используется для типизации и присваивания callable-ссылок. Исполняемая реализация не создаётся. Наличие return отличает возвращающий значение контракт от процедурного. `sub` удаляется. |
| R14 | Оба аргумента fn читаются в роли data: первый задаёт имя создаваемой сигнатуры, второй — её data-шаблон. Для fn не применяется раскрытие аргументов, свойственное выбору code-role вызова. |
| R15 | Выбор сигнатуры использует только явные actuals либо поля единственной переданной без присваивания Structure. Чтения равноправны; более одного итогового варианта — ошибка. Неявное связывание не выбирает сигнатуру. |
| R16 | Вложенное объявление затеняет внешнее одноимённое объявление. Одноуровневое употребление не создаёт новый уровень затенения; используется соответствующее родительское место/namespace. Учитываются владелец места и действующая видимость, а не наличие одинаковой строки где угодно в теле. |
| R17 | catch адаптируется к общим правилам представления данных и вызова, сохраняя семантику обработчика. |
| R18 | Граф остаётся графом исходных форм. Записи модификаторов и прочих ресиверов сохраняются по существующим правилам; binding не переписывает их в отдельное семантическое представление. |

Вариант A касается также допустимой записи в собственную fallback-копию: не вводить вместо неё предложенные в исследовании варианты «только чтение» или «всякое внешнее имя обязательно alias».

## 3. Обозначения и единый результат связывания

Для объяснения используются:

- C — конкретная Structure, выбранная для исполнения в роли code.
- D — фактический parent(C), используемый в роли data, когда он имеется.
- F — локальный namespace текущей активации.
- P — локальный контекст вызывающего, доступный новым способам передачи.

Это не новые слова языка, поля графа или обязательные служебные объекты.

Результат разрешения имени определяет источник и логическое место. Для описания реализации различаются:

- **Собственное место:** actual, autofill или прежний fallback дают значение/описание в место текущей активации.
- **Место вызывающего:** имя обозначает уже существующую локальную переменную вызывающего, без промежуточной рабочей копии.

Для LMX в обоих случаях переменная x имеет свой обычный тип T. Если нативный код использует T*, это не меняет пользовательский тип x на указатель и не требует писать `\x` вместо x. Обычные `x`, `x := value`, выражения с x и `@x` действуют на выбранное логическое место.

Для переменной-ссылки обычным типом остаётся её тип ссылки. Адрес её нативной ячейки может иметь ещё один уровень указателя, но этот транспортный уровень не добавляется к типу переменной в LMX.

## 4. Структурный контракт вызова

### 4.1. Формы

| Форма после однозначного выбора | Исполняемый объект | Явные actuals | Data |
|---|---|---|---|
| `call(C)` | C | Не поданы | parent(C) |
| `call(A C)` | C | Структура A | parent(C) |
| `C()` | C | Пустой хвост | parent(C) |
| `C(args)` | C | Написанные actuals по общему алгоритму | parent(C) |

У call остаются имена параметров args и code. Сам call исполняет выбранную Structure C; автоматический поиск дочернего поля code не добавляется.

Сохраняется required-контракт параметров форм call: у одноаргументной формы обязателен code; у двухаргументной — args и code. Поэтому отсутствие args не делает двухаргументную форму подходящей для `call(code := C)`. Это обычное различение деклараций по §9, без исключения для встроенного call.

Таблица не отменяет выбор чтения единственного структурного actual. `C(A)` может принять A целиком или выбрать передачу её полей; это определяется §9. Равенство эффекта разных записей проверяется при одинаковых выбранных actuals, а не произвольной текстовой подстановкой.

Сам `call(C)` также проходит общий выбор между двумя формами call: если целый C подходит одной форме, а его поля другой, возникает неоднозначность. `call(code := C)` явно передаёт C как code и исключает альтернативное раскрытие этого actual.

Служебные C-функции, bridge или диспетчер call не должны подменять контекст вызывающего своими служебными локалями. Источники языка определяются программным местом вызова.

### 4.2. Parent и композиция

Отдельно подставить D на вызове больше нельзя. Для другой комбинации сначала создаётся нужная структурная связь, затем вызывается выбранное вхождение C.

Существующее правило `colon-declares` из §9 семантической спецификации сохраняется: `NewContainer: ExistingCode` содержит ссылку на ExistingCode и не меняет его parent. Поэтому это не автоматическая замена прежнего `call(NewData ExistingCode)`.

Copy/merge должны сохранять или перенаправлять parent по действующим правилам копирования. Разные вхождения code могут использовать одну нативную реализацию, сохраняя собственные данные. Ни адрес общей C-функции, ни путь, которым найдена ссылка, не подменяют parent выбранного C.

Существующий `node` и его явный лексический доступ сохраняются для фактически выбранного вхождения. Не удалять требуемый ему нативный контекст и не заменять его новым пользовательским каналом передачи data. Общие правила lexical source и node применяются согласованно к новой структурной форме callable.

### 4.3. R0

R0 запускается как процедура без data и без пользовательских аргументов. Отсутствие data не компенсировать D = C, пустой служебной Structure или искусственным полем data.

У R0 могут быть собственные исполняемые объявления и обычные доступные ссылки. Это правило не запрещает внутренние параметры запуска runtime и не отрицает существующий способ доступа нативного корня к графу. Они не становятся пользовательскими actuals сигнатуры R0.

### 4.4. Удаляемые встроенные значения

Удалить специальный смысл имени data, отдельный data-параметр call, встроенные fncall и sub. Слова data как роли и обычного пользовательского имени остаются допустимы по общим правилам.

Старый двухаргументный `call(D C)` требует содержательной миграции: теперь D занимает args, а не подменяет parent. Аналогично прежний `C(D)` больше не означает отдельную подстановку data.

`node` остаётся зарезервированной операцией; тесты первого ТЗ на его обычное пользовательское переопределение удалить из плана. Для data/sub/fncall различать удалённый встроенный смысл и явно объявленное обычное пользовательское имя, если оно разрешено общими правилами.

## 5. Двусторонний private

### 5.1. Норма

`private` запрещает неявное динамическое участие конкретного объявления и соответствующего места в обоих направлениях:

1. **Источник:** private-место вызывающего автоматически не предоставляет ни своё значение, ни изменяемое место.
2. **Получатель:** реально видимое private-объявление лексического контекста вызываемого не заслоняется значением или местом из динамического контекста.

Правило распространяется на новый autofill, новый прозрачный доступ к месту caller и сохранённую динамическую часть прежнего связывания. Это не запрет лексического поиска.

Поэтому до принятия внешней динамической привязки нужно установить, какое лексическое объявление действительно видно, и защищено ли оно private. Проверять только private у источника недостаточно.

### 5.2. Что сохраняется доступным

Private не запрещает:

- явно передать собственное private-значение аргументом;
- явно заполнить принимающее private-место, если actual допустим его обычным контрактом;
- вложенному лексическому коду видеть соответствующее поле;
- пользоваться явным путём или node;
- создать новое внутреннее объявление, которое обычным лексическим способом затеняет внешний private;
- выполнять разрешённые операции по типу и изменяемости места.

Private не заменяет const/immutable. Разрешённость самой записи определяется существующим контрактом настоящего адресата.

### 5.3. Фильтр конкретного места

Private-источник пропускается, после чего продолжается разрешённый поиск. Он не запрещает всю последовательность букв x. Более дальний допустимый источник того же имени может оставаться доступен.

Защита получателя относится именно к выбранному видимому лексическому объявлению. Нельзя найти произвольный private x в каком-либо предке и на этом основании закрыть новое внутреннее публичное x.

Явно переданное значение не переносит на все свои будущие копии историю private-источника. Private принадлежит объявлению и его binding. Непомеченное новое место получателя не становится private лишь потому, что значение ранее было взято из private-места.

### 5.4. Граф

Запись private остаётся в исходном графе по действующим правилам. Например, существующий путь `S\private\field` не превращается сам собой в `S\field`. Общие операции namespace учитывают смысл модификатора, не переписывая граф ради binding.

## 6. Приоритеты и поведение мест

### 6.1. Собственные объявленные места

Для действующего собственного объявления:

1. Явный actual заполняет место по обычным правилам. Private не отменяет явную передачу.
2. Если actual не подан, своё готовое значение или описание initializer остаётся источником.
3. Если место без инициализации и actual отсутствует, новый autofill получает одноимённое значение из разрешённого локального контекста вызывающего.
4. Autofill запрещён, когда принимающее место private или выбранный автоматический источник private.
5. Без подходящего заполнения сохраняется обычное состояние без инициализации и существующие проверки required.

Подача значения создаёт/заполняет собственную ячейку, а не alias. Для caller x = 5 и записи callee x := 9 после autofill caller сохраняет 5.

Готовый initializer не заменяется автоматически одноимённой локалью. Вычисляемый initializer не считается отсутствующим только потому, что ещё не выполнен. Наличие явно поданного значения определяется фактом подачи actual, а не его истинностью: 0 не означает пропуск. Сохраняется прежнее различие между отсутствием actual и явно поданным nil.

Прежний механизм свободных имён не распространяется дополнительно на пропущенные формальные входы: §12 текущей семантической спецификации этого не делал. Его сохранение низшим приоритетом не должно само по себе расширять область применения.

### 6.2. Внешнее имя и прозрачное место вызывающего

Для имени без действующего собственного объявления:

1. Если реально видимый лексический источник private, динамическая подмена не выполняется; используется разрешённая лексическая связь.
2. Иначе подходящее доступное локальное место caller может быть получено новым прозрачным способом.
3. Если нового источника нет, используется прежний механизм, с прежними разрешёнными источниками и новым двусторонним private.

При новом способе x в LMX — обычная переменная T, обозначающая место caller. Чтение получает её значение; допустимая запись меняет её; `@x` адресует это место. Взятие адреса не является записью и не продлевает lifetime.

Нативный скрытый T* — способ реализации, а не дополнительный пользовательский уровень адреса. Для переназначения ссылочной переменной нужен адрес её ячейки, а не только указатель на общий объект.

Запись действует сразу, без копирования обратно при выходе. Если место caller было uninit:T, меняется также состояние инициализации, наблюдаемое через обычные nil/required-проверки.

### 6.3. Сохранённый fallback: вариант A

Fallback сохраняет свою прежнюю семантику собственного значения/описания в F. Bare-присваивание меняет эту рабочую копию, а не исходное место. Для ссылочного значения копируется ссылка, не объект; операции через неё подчиняются обычным правилам.

Запрещены две подмены:

- замена нового прозрачного места caller временной копией с последующим copy-out;
- замена fallback-копии адресом исходного caller/lexical места под предлогом оптимизации.

В обоих случаях может получиться то же прочитанное число, но другое место записи.

Выбранная связь удерживается в пределах её обычной области действия. Новое чтение не выбирает произвольно другой источник из-за изменения значений вокруг. Начало действия нового вложенного объявления — отдельное событие затенения, а не повторная попытка найти источник старого binding.

### 6.4. Цепочка вызовов

Для A → B → C, где A имеет x, B сам x не потребляет, а C потребляет, прежняя возможность получить x сохраняется. B не обязан вводить явный аргумент, фиктивную локаль или транзитивный список потребностей потомков.

Если в этом случае сработал прежний fallback, C получает собственное значение. Ответ «получает» не превращает старый канал в alias.

Если B уже имеет собственную копию x, новый доступ C к месту B.x меняет B.x, но не первоначальный источник A.x. Если B имеет прозрачную связь с A.x, передача места B.x сохраняет адрес A.x. Происхождение копии нельзя «раскрутить» обратно в исходный alias.

Сохраняется запрет статического транзитивного накопления скрытых требований из §12 текущей семантической спецификации. Наличие собственных непосредственно используемых входов выбранного тела не означает объединение входов всех его возможных потомков.

### 6.5. Явные пути и запись

Пути `\` и node используют обычное выбранное место графа. Для них не добавляется специальный контроль «это поле принадлежит чужому вызывающему». При этом сохраняются действующие ограничения записи, типы, const/immutable и правила допустимости адреса.

Private регулирует неявную динамическую связь. Он не превращается в проверку доступа на каждом явно написанном пути.

## 7. Уровни, объявления и затенение

### 7.1. Авторское правило

> «объявление на вложенном уровне затеняет внешнее одноименное объявление. На одном уровне затенять нечего, используется родительское».

Применять это правило через владельца объявления и лексическую область. Доступная внешняя binding и собственное объявление текущего уровня не становятся одним и тем же только из-за совпадения имени.

### 7.2. Операционные следствия

Сохраняется последовательная видимость переменных и const. До начала действия собственного объявления имя разрешается обычным способом через доступный родительский/внешний контекст. Объявление ниже или в другой ветви не запрещает раннее употребление во всём callable.

Новое объявление во вложенной области создаёт своё место и затеняет внешнее. В частности, внутреннее Text x может затенить внешний int x; это не попытка записать Text во внешнюю int-ячейку.

Повтор собственного объявления одного уровня работает с тем же местом по общему контракту ресивера. Новый RHS вычисляется и присваивается по обычным правилам; отсутствие нового RHS не обнуляет уже существующее значение. Одноуровневая форма сама по себе не создаёт дополнительную область и ещё одну ячейку.

После выхода из внутренней области снова видно прежнее внешнее binding со своим местом, режимом записи и private. Это обычное разрешение по областям, без публикации внутренних локалей.

Формулировку «не объявлено нигде» для нового динамического способа применять к действующему собственному объявлению в соответствующей области. Не реализовывать её полным предварительным поиском будущих объявлений по всему телу.

### 7.3. Инициализация

Инициализация следует из того, какое место выбрано:

- существующее место при одноуровневом повторе сохраняет значение, пока не выполнена обычная запись;
- новое место с RHS/default получает значение по действующим правилам и времени вычисления;
- новый вход без значения получает autofill там, где выполнен его контракт и private разрешает оба направления;
- при отсутствии допустимой инициализации действует обычное uninit:T, без неявной подстановки 0.

Инициализаторы не исполняются общим предварительным проходом. Для code сохраняется исполнение достигнутой записи; для вычисляемых входных данных — предусмотренное получение по требованию. Требуемые места для присваивания внутри actual-expression существуют к моменту его вычисления.

### 7.4. Один контроль прочтения: новый local внутри inline-блока

Для Fable остаётся точный контроль применения авторской фразы об инициализации:

```text
В текущем кадре: внешний x = 5.
Вложенный inline-блок, без нового callable-вызова:
    новое int: x без RHS/default;
    чтение внутреннего x.
В caller этого кадра одноимённого x нет.
```

Затенение и отдельность внутреннего места определены. Требует сверки именно начальное значение: считается ли локальный контекст родительской inline-области источником обычного автозаполнения нового внутреннего места, давая 5, либо без нового caller-источника место остаётся uninit:int.

Не вводить ради этого примера универсальное копирование всех outer locals, новый входной проход или неявное исполнение defaults. Сначала вывести результат из существующего общего алгоритма namespace и принятого авторского правила. Если для конкретного примера требуется дополнительное правило языка, вынести автору только этот пример. Остальные решения настоящего ТЗ не зависят от ответа.

## 8. Именованная сигнатура fn: name data

### 8.1. Представление

`fn: name data` создаёт именованное описание контракта вызова, а не исполняемую реализацию. У fn два аргумента:

| Позиция | Аргумент | Назначение |
|---|---|---|
| 1 | name | Имя создаваемой сигнатуры; атом имени, а не вызов или имя создаваемой реализации |
| 2 | data | Data-шаблон сигнатуры: объявления входных мест, их требования/defaults/модификаторы, поле return при наличии результата и прочие предусмотренные элементы контракта |

Имя сигнатуры вводится по общим правилам имён и затем обозначает созданное описание в требованиях к callable-ссылкам и при проверке их присваивания. Само имя не становится входным местом описываемого вызова. Исполняемое тело, callable-реализация и native entry этой формой не создаются.

Результат находится внутри второго аргумента, в поле return, а не в отдельной внешней позиции после списка входов. Sub не нужен: отсутствие return означает процедурную сигнатуру.

Каноническая форма с двумя явно различимыми аргументами:

```text
fn: SumSignature (int: a; int: b; return: int)
```

Первый аргумент — имя `SumSignature`; второй — одна Structure data-шаблона. Эквивалентный контракт можно описать ссылкой на отдельно объявленный шаблон:

```text
SumData:
    int: a
    int: b
    return: int

fn: SumSignature SumData
```

Процедурная сигнатура тоже получает имя:

```text
fn: StepSignature (int: step 1)
```

Структурный результат сохраняет обычную запись внутри поля return второго аргумента:

```text
PairData:
    int: count
    return:
        int: x
        int: y
end: PairData

fn: PairSignature PairData
```

Return описывает результат; он не становится дополнительным входным actual. Состав входных мест определяется общим механизмом data-шаблона, без отдельного списка правил для fn. Форма только с шаблоном без имени не заменяет двухаргументное объявление сигнатуры.

### 8.2. Роль аргументов

Оба аргумента fn читаются в роли data. Первый задаёт имя сигнатуры и не исполняется; второй содержит или обозначает её data-шаблон. Вложенная структурная форма в шаблоне является описанием, а не запуском описываемой функции. При обработке fn не создаются исполняемое тело или native entry.

Добавить fn в документированную группу ресиверов с аргументами в роли data; sub удалить. Не применять к аргументам fn алгоритм W/E из §9. Structure второго аргумента не раскрывается этим алгоритмом: fn получает имя и data-шаблон, а не список аргументов code-role вызова. Имя остаётся обязательным отдельным аргументом.

Общий P0 остаётся единственным парсером. Два аргумента и их роли определяются контрактом fn после общего разбора; отдельная грамматика или парсер сигнатур не вводятся.

### 8.3. Полный пример реализации и типизации указателя

```text
fn: SumSignature (int: a; int: b; return: int)

SumContext:
    int: a
    int: b
    return: int
    sum:
        return: a + b
```

В роли code:

```text
SumContext\sum(a := 2; b := 3)
```

Исполняется sum; её data — SumContext. Вызов `SumContext()` означал бы исполнение другой Structure, не автоматический поиск sum. `SumSignature` — имя описания контракта, а `SumContext\sum` — ссылка на исполняемую реализацию.

Типизированная ссылка использует имя уже объявленной сигнатуры и обычную плоскую форму требования и кандидата:

```text
@: sumPtr SumSignature SumContext\sum
```

У `@` три аргумента: имя sumPtr, требование `SumSignature`, кандидат `SumContext\sum`. Требование разрешается по имени `SumSignature`, заданному первым аргументом fn.

Описание, найденное по имени `SumSignature`, проверяется общим implements против контракта вызова кандидата с учётом его parent. Не требовать, чтобы входные поля и return физически находились внутри исполняемого тела sum. Fn получает только имя и data-шаблон; кандидат передан внешнему @, и отдельный сигнатурный валидатор не вводится. При последующем присваивании callable-ссылки этому месту сохраняется то же требование именованной сигнатуры и обычный механизм проверки.

Вызов:

```text
sumPtr(a := 2; b := 3)
```

использует тот же контракт выбранного code, что прямой вызов. Никакого executable fn/sub для объявления SumContext или sum не требуется.

### 8.4. Return

Объявление return в D не присваивает возвращаемое значение. Оно не становится общей изменяемой ячейкой всех рекурсивных активаций.

В code `return` сохраняет действующий выход без значения; `return: value` передаёт допустимый результат там, где он описан. Достижение конца тела не синтезирует return. Правила структурного результата, принимающих мест и cleanup сохраняются.

Call и обычный вызов Structure могут возвращать значение по этому контракту. Прежний безусловный запрет результата у обычной Structure/call отменяется вместе с fncall.

## 9. Выбор сигнатуры: полный алгоритм

### 9.1. Отделение целей и стадий

Сначала обычными правилами разрешается вызываемое имя/ссылка и набор его видимых объявлений. После этого сигнатура выбирается по явно поданному материалу. Затем выполняется выбранный вызов и применяются допустимые неявные способы связывания.

Наличие у caller локальных b, x, code, args или их private не добавляет их в список actuals выбора. Autofill, прозрачный доступ и старый fallback не создают кандидата, не спасают отклонённого кандидата и не запускают повторный выбор после заполнения.

Внутренний подбор native entry для уже выбранного языкового вызова — отдельная реализационная задача. Несколько оптимизированных C-вариантов одной сигнатуры не являются дополнительными конкурирующими объявлениями языка.

### 9.2. Кандидат

Единица выбора:

```text
(видимое объявление, чтение явных actuals, карта actual → formal)
```

Нельзя выбрать только объявление, а чтение аргумента решить заново при запуске. Два подходящих чтения одного объявления тоже дают два итоговых варианта.

### 9.3. Допустимые чтения

**W — как написано.** Явные actuals сопоставляются с формалами в поданном виде.

**E — раскрытая единственная Structure.** Дополнительное чтение рассматривается, когда подан ровно один actual, являющийся Structure или ссылкой на неё, и он не подан присваиванием конкретному формалу.

В E непосредственные поля Structure образуют последовательность actuals. Раскрытие однократно, на один уровень; исходный граф не меняется. Поля, являющиеся именованными объявлениями, сохраняют имена при общем позиционном/именованном сопоставлении.

Для `f(arg := S)` E не создаётся. Это явная подача S целиком конкретному формалу.

W и E равноправны. Нельзя предпочитать целую Structure, большую/меньшую арность, первое найденное объявление или пробовать E только после неудачи W.

### 9.4. Проверка вариантов

Для каждого допустимого сочетания объявления и чтения построить карту подачи по общим правилам:

- соблюдение порядка позиционных/именованных actuals;
- соответствие имени формалу;
- отсутствие неизвестных имён и двойной подачи;
- отсутствие избытка actuals;
- собственные defaults и required выбранного объявления;
- применимая интерфейсная проверка общим implements.

Это сопоставление не исполняет пользовательские присваивания/defaults/test по отдельному разу для каждого кандидата. Не создавать отдельный сигнатурный валидатор, дублирующий implements. Сохраняются текущие границы интерфейсной проверки, преобразования и test, а также различие native/интерпретации.

Для уже вычисленного структурного actual использовать полученное значение; не вычислять его заново ради E или другого кандидата. Проверки формы, доступные до эффектов аргументов, выполнить до них. Этот алгоритм не вводит спекулятивное исполнение программы ради перебора вариантов.

### 9.5. Количество результатов

- Нет допустимых вариантов — отказ вызова.
- Ровно один — сохранить весь выбранный кандидат.
- Более одного — ошибка неоднозначности.

Нельзя объединить два допустимых чтения только потому, что они ведут к одному body или оба дают похожие значения. Нельзя разрешить неоднозначность за счёт скрытых входов или порядка просмотра.

### 9.6. Исполнение выбранного варианта без повторного раскрытия

Если выбран W, где Structure принимается целиком одним actual, передать именно её целиком. Рассмотрение E во время поиска не меняет её на поля после выбора W.

Если выбран E, использовать уже выбранную карту его полей. Не раскрывать их ещё раз и не начинать новый поиск.

Важно: запрет повторного раскрытия не означает «сигнатура с одним формалом никогда не может быть найдена по E». Сохраняется действующий пример:

```text
Arg:
    int: x 9
```

Для входного контракта `h(int: x)` W с целым Arg не подходит, а E с единственным полем x подходит. Передаётся выбранное значение 9. В исполнительной фазе это уже один выбранный actual; новой развёртки нет.

Также не смешивать это с `h((5))`: обработка группы по контракту числового выражения — другой существующий механизм.

### 9.7. Следствия для required

Required в описании входа участвует в допустимости кандидата по существующим правилам. Скрытое значение не учитывается при выборе:

- при вариантах `f(a)` и `f(a; required b)` вызов `f(5)` выбирает первый, даже если caller имеет b;
- при единственном `f(required b)` без default вызов `f()` не получает кандидата за счёт скрытого caller b;
- собственный default объявления может удовлетворять required по прежним правилам;
- optional-вход уже выбранного вызова может заполниться autofill;
- `required: x` в достигнутом code проверяет фактическое состояние места, в том числе после разрешённого autofill.

Не следует снова задавать вопрос, участвует ли autofill в выборе: автор прямо исключил это.

### 9.8. Таблица обязательных примеров выбора

Ниже запись контрактов аналитическая, без предложения новой грамматики объявления перегрузок.

| Условия | Вызов | Результат |
|---|---|---|
| `f(int a)` и `f(int a; int b)`, b optional | `f(5)` | Два варианта, ошибка |
| `f(int a)` и `f(int a; required int b)`; caller b существует | `f(5)` | Первый; caller b не спасает второй |
| Те же контракты | `f(5; 6)` | Второй |
| Только `f(required int b)`, без default; caller b существует | `f()` | Нет варианта |
| Только `f(required int b = 9)` | `f()` | Допустим собственный default |
| Только `f(int a; int b)`; caller b = 6 | `f(5)` | Выбор без b; затем допустимый autofill может заполнить b |
| S целиком подходит одному формалу; E не подходит | `f(S)` | W; S передаётся целиком |
| `h(int x)`; Arg содержит `int: x 9`, целый Arg не подходит | `h(Arg)` | E с одним полем; h получает 9 |
| Поля S подходят двум формалам; целый S не подходит | `f(S)` | E; передаются выбранные поля |
| W и E подходят одному объявлению | `f(S)` | Два итоговых варианта, ошибка |
| W подходит одному объявлению, E другому | `f(S)` | Ошибка без приоритета между ними |
| S явно присвоена формалу | `f(a := S)` | Только W, без E |
| Целый C подходит call(code), поля C — call(args code) | `call(C)` | Ошибка неоднозначности |
| Тот же C явно подан как code | `call(code := C)` | Нет раскрытия actual; скрытый args не создаёт вторую форму |
| DataTemplate содержит вложенную Structure | `fn: SignatureName DataTemplate` | Создаётся именованная сигнатура; оба аргумента в роли data, W/E code-role вызовов не применяется |

## 10. Порядок исполнения и catch

### 10.1. Actuals и кадр

Сохраняется общий протокол actuals: проверить доступную форму и назначения до их эффектов; необходимые места F должны существовать при вычислении выражений, которые обращаются к кадру вызываемого; аргументы вычисляются в написанном порядке, каждый принимается до следующего.

Если вычисление или приём очередного аргумента отказали, последующие actuals и тело не выполняются. Присваивание формалу и объявление локального места в actual-expression работают с соответствующими местами кадра и сами по себе не дописывают поля в исходный граф. Явные записи через пути и побочные действия выполненных вызовов сохраняют обычную семантику. Такие операции не становятся дополнительными скрытыми аргументами. Не менять приоритеты выражений настоящим ТЗ.

После выбранного явного способа подачи применяются допустимые неявные механизмы и собственные исходные описания. Из этого не возникает общей фазы исполнения всех defaults при входе. Интерпретатор продолжает проверять достигнутые обращения, без полного сканирования тела и недостижимых ветвей.

### 10.2. Catch

Обновить catch по общей модели входов и фактической связи parent(handler code) с его data. Payload — явно поданные значения, принимаемые общими правилами; скрытое связывание и private действуют на остальные допустимые зависимости обработчика.

При этом сохраняются нормы §15 текущей семантической спецификации:

- обработчик выбирается по имени failure и соответствующей области;
- его body не выполняется на первоначальном прямом проходе;
- вложенные и соседние области различаются;
- два конкурирующих same-named catch на одном уровне не добавляются;
- продолжение после обработчика, повторный вызов, throws и cleanup сохраняют свою семантику.

Catch не исчезает вместе с sub и не превращается в обычную функцию только потому, что общее представление входов стало единым. Удалить у него зависимость от отменённых executable fn/sub форм, fncall и отдельной подстановки data. Роль его частей должна следовать контракту обработчика; включение fn в data-role группу само по себе не переопределяет catch.

## 11. Native и интерпретатор

### 11.1. Основной путь

Сохранить прямой native-to-native вызов там, где выбранные реализация, типы и binding известны. Autofill-значение может понижаться тем же параметром T, что явный actual. Прозрачное место caller — скрытым адресом его ячейки.

Старый fallback продолжает давать собственное место. Общий C-body может быть разделён между режимами с корректными адаптерами, но адаптер обязан сохранить владельца записи и поведение @.

При одинаковых явных actuals режим конкретного скрытого входа может различаться из-за caller context/private. Existing native entry должен соответствовать реальному контракту либо получать корректное описание места. Способ выразить это в нынешнем ABI — задача Fable; новые пользовательские pointer-типы не вводятся.

### 11.2. Bridge и типы мест

Обычная native local не имеет arena-заголовка `[type][value]`. Нельзя прочитать её тип из четырёх байтов перед адресом. Тип, способ доступа, состояние инициализации и применимые ограничения должны следовать общему представлению места/контракту вызова.

Проверить native → native, native → walker, walker → native и walker → walker. Во всех случаях x имеет один логический тип T, а допустимая запись меняет то же логическое место.

Для неизвестного runtime-target сохранить существующий механизм доступа к разрешённым локальным контекстам; не исследовать сырой C-стек как словарь LMX-имён. Не вводить статическое транзитивное замыкание требований только ради того, чтобы обойти сохранённую цепочку активаций.

### 11.3. Границы оптимизации

Не возвращать load-dirty, flush, публикацию локальных кадров или копирование обратно при выходах. Не превращать read-only использование alias в snapshot без доказательства сохранения наблюдаемого поведения при вложенных вызовах.

Явная компиляция, существующий выбор native/walker и граница endturn сохраняются. Отсутствие подходящего native entry не запускает скрытую компиляцию. Не добавлять постоянные кеши всех окружений или автоматическую инвалидацию графа.

Не применять restrict лишь из-за скрытой передачи указателя или private: допустимость такого C-контракта требует отдельного доказательства отсутствия запрещённых пересечений.

## 12. Сохранение графа, времени жизни и данных

Binding не добавляет собственные поля в исходные data/code и не меняет их структуру. Сохраняются receiver records, общие правила примитивных записей, повторных data-occurrences, copy/merge и сериализации.

Сервисные сведения namespace и соответствий живут в предусмотренных границах, а native descriptors — в существующих call tables. Не делать из них второй граф или постоянное хранилище всех разрешений имён.

Получение прозрачной связи с local не продлевает её lifetime. Сохранение графа не превращает адрес временной C-локали в переносимую структурную ссылку. Правила Message/арен и существующих продолжений сохраняются; новый способ связывания не обещает неявного удержания чужого завершившегося кадра.

При yield выбранная связь не перепривязывается к одноимённому local нового вызывающего next. Возобновление использует действующее состояние сохранённой активации и обычные ограничения lifetime.

## 13. План работ

1. **Сопоставить код с нормой.** Найти действующие binder, поиск lexical/dynamic, private, слоты native/walker, выбор сигнатур, fn/sub/catch, call/fncall, return и R0. Отделить реализованное от исторических описаний.
2. **Зафиксировать единый контракт места.** Сохранить собственную копию и добавить прозрачное место caller. Привести чтение, присваивание, @ и initialization state к одной семантике во всех исполнителях.
3. **Внести двусторонний private.** Проверять источник и реально видимое лексическое объявление получателя; сохранить явную и вложенную лексическую доступность.
4. **Обновить области объявлений.** Реализовать вложенное затенение и одноуровневое использование соответствующего места; сохранить последовательность и общую инициализацию. Контроль §7.4 решить по существующему алгоритму либо вынести точно этот пример.
5. **Обновить структурный callable.** Data = parent(code); R0 без data; убрать специальный data, fncall и sub; сохранить node и fallback; унифицировать return и data-шаблон именованной сигнатуры `fn: name data`. Создаваемое имя использовать в типизации и присваивании callable-ссылок.
6. **Согласовать выбор сигнатур.** Реализовать/проверить кандидаты W/E, равноправность, подсчёт всех вариантов и исполнение сохранённой карты. Hidden inputs не участвуют в отборе.
7. **Привести native ABI и catch.** Обновить подходящие variants/адаптеры и handler payload без изменения общих выходов и cleanup.
8. **Мигрировать ядро, примеры и документы.** Перевести затронутую самосборку и стандартные определения. Не оставлять executable sub/fn, безымянные одноаргументные fn-шаблоны и старые call(data code) в нормативных примерах. Для fn указывать имя и data-шаблон; ссылки типизировать именем созданной сигнатуры.
9. **Проверить поведение.** Выполнить сценарии §14 и обязательные проверки репозитория. Результаты описать как фактически выполненные, отдельно от ещё не поддерживаемых путей.

Не требуется согласовывать с автором каждую внутреннюю C-структуру. Если реализация требует нового видимого ограничения языка, представить конкретный различающий пример, а не скрывать ограничение в ABI или тесте.

| Документ | Обязательные изменения |
|---|---|
| Semantics | Сохранить node и старый fallback; описать новые два способа и прозрачность T; переписать private в обе стороны; уточнить scope/shadowing; заменить call/fncall, special data, executable fn/sub; задать два аргумента `fn: name data` и использование имени сигнатуры; подробно изложить W/E и explicit-only selection; перенести return в data; адаптировать catch |
| Grammar | Сохранить node в специальных именах; снять special data и удалённые встроенные формы; показать `fn: name data` с двумя обычными аргументами в роли data; новые вызовы и именованные сигнатуры без отдельной грамматики |
| Semantics guide | Показать actual/autofill/fallback-copy/transparent-place на одинаковых значениях, оба направления private, nested lexical доступ и все основные W/E случаи; объявить именованные fn-сигнатуры и использовать их имена в типизации/присваивании ссылок |
| L2 spec | R0 без data; parent/code; скрытый адрес как ABI-деталь при прежнем языке T; bridge, init-state, native variants, C export; сохранить необходимые node/legacy context; согласовать два аргумента fn и применение именованной сигнатуры без создания native-реализации |
| CORE | Актуальные представления callable, local place, binding и private; именованная сигнатура `fn: name data` отдельно от реализации; сохранение графа и явной компиляции; отделить новые нормы от исторических receipts |
| Coding instruction | Единый алгоритм, explicit-only выбор, обе private-проверки, области затенения, миграция fn/sub/catch; у fn всегда имя и data-шаблон, в требованиях ссылок — имя сигнатуры; проверки самосборки |

Удалить из действующей нормы первого ТЗ: отмену node, отмену всего прежнего связывания, запрет транзита A → B → C, одностороннее толкование private, отдельный sub для сигнатур и гипотезу участия autofill в выборе сигнатуры.

Не переносить из исследования альтернативы B/C для fallback. Не превращать слова «указатель передаётся скрыто» в требование явной указательной записи LMX.

Исторические отчёты не переписывать так, будто новая семантика действовала всегда: отметить отменённую норму и дать ссылку на текущую. Слова data в описании роли и реальные пользовательские имена не удалять механическим поиском строк.

## 16. Критерии завершения и отчёт Fable

Готовность означает согласованную реализацию новых норм на поддерживаемых путях, миграцию затронутого ядра и самосборки, актуальные примеры во всех шести документах и пройденные различающие проверки.

Отчёт должен содержать:

- что уже соответствовало заданию и что изменено;
- выбранное внутреннее представление собственного/чужого места без изменения типа LMX;
- подтверждение private в обоих направлениях и сохранения явного/лексического доступа;
- результаты таблицы выбора W/E, включая required и отсутствие влияния hidden inputs;
- проверку двух аргументов `fn: name data`, поля return внутри data и использования созданного имени в типизации/присваивании ссылок;
- результаты нативных и смешанных вызовов, проверки места записи и initialization state;
- результат затронутых обязательных проверок bootstrap;
- оставшиеся ограничения с конкретными примерами, включая §7.4, если его не удалось однозначно вывести.

Не объявлять выполненными проверки, которые не запускались, и не менять ожидаемые эффекты теста для удобства реализации. Основные ответы автора в этом ТЗ уже зафиксированы; повторное согласование требуется только при необходимости действительно нового наблюдаемого правила.
