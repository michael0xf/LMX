## Объявление fn в дереве — именованная структура ресивера fn; функция создаётся при обходе в namespace

Источник: ответ автора в чате Codex 2026-11-09 на вопрос Codex о составе `fn`/`return` при `merge(f1; f2)` (контекст
вопроса: тогдашнее представление построителя `[fn, args, return, var, body]` и `return` из одного слова `int`); передан
Opus сообщением CODEX-OPUS-AUTHOR-FN-DECLARATION-20261109T053222Z-01. Выдержка из ответа автора (технические
фрагменты; опущена одна фраза оценки между ними), дословно:

```text
"структура с безымянным словом int  " -- что за "безымянное слово int" ? int это ресивер который называется "int". fn это ресивер fn. Причем тут int? Вы захардкодили int туда? Что вообще такое "безымянное слово"?
```

```text
объявление fn в дереве это именованная структура (fn ее название) с аргументами (name, args, return, var, body) которые хотя и безымянные структуры, но именованные аругменты (их надо уметь наименовать при необдимости -- также как агументы функций)  , которая при обходе интерпретаторов или транслятора должна создавать у него в namespace структуру name( args(), return(), var(), body())  по тому же правилу по которому int: i 5 создаёт i
```

Пояснение Codex при передаче (не слова автора): реализация смешала исходное объявление ресивера `fn` с созданным им
значением функции. Исходное дерево сохраняет именованную структуру `fn` и полный контракт её аргументов `name`, `args`,
`return`, `var`, `body`; аргументы допускают обычное именование, без отдельных кодов и ролей. При обходе ресивер
применяется, и в namespace этого обхода общим правилом объявления создаётся `name` с `args`/`return`/`var`/`body`, как
`int` создаёт `i`. `int` и `fn` — именованные ресиверы, а не безымянные добавочные слова со специальным поведением
`merge`; представление языка не выводится из нынешнего `int`-подмножества. Требование результата из одного `int` в
`lmx_graph_call_shape` — граница реализации, не норма. Скрытое подготовленное представление между обходами не
сохраняется: namespace временный, каждый обход чистый, исходного графа достаточно и транслятору, и интерпретатору;
создаваемые значения — обычные Lmx и примитивы по общим правилам. Прежний вопрос о «безымянных fn/int при merge» закрыт.

## namespace — изначально чистые таблицы обходчика

Источник: уточнение автора в чате Codex 2026-11-09 к ответу выше; передано Opus сообщением
CODEX-OPUS-AUTHOR-NAMESPACE-WALK-20261109T0535Z-01. Дословно:

```text
это "namespace" не хранится рядом с графом а являетс теми самыми изнчально чистыми таблицами обходчика
```

Пояснение Codex при передаче (не слова автора): namespace из ответа о `fn` — служебные таблицы конкретного обхода.
Каждый обход начинает с чистых таблиц и создаёт в них `name(args(), return(), var(), body())`, обрабатывая именованную
структуру ресивера `fn` и её аргументы. Состояние namespace не хранится рядом с графом, не передаётся следующему обходу и
не становится сохранённым подготовленным представлением программы. Это не постоянная таблица адрес → name и не
метаданные типизированной арены. Проверка — независимые обходы одного графа, затем изменённого графа, без состояния
прошлого обхода.

## fn: merge(f1, f2) — функцию создаёт применение fn; явные аргументы fn по общим правилам

Источник: техническое уточнение автора в чате Codex 2026-11-09 к тому же вопросу; передано Opus сообщением
CODEX-OPUS-AUTHOR-FN-OF-MERGE-20261109T0549Z-01. Выдержка (без вводной фразы «хорошо, я понял вашу проблему.»), дословно:

```text
По общим правилам языка надо видимо писать
fn: merge(f1, f2) чтобы получить функцию. Так? Ну так пишите. Правила тежесамые.
fn: name: "test"; args: (); return: (); body: () должен так же создавать функцию если callable "name" нет либо огарантированно fn: name := "test"; args := (); return := (); body := ()
```

Пояснение Codex при передаче (не слова автора): `merge(f1, f2)` собирает обычную Structure по общим правилам;
`fn: merge(f1, f2)` подаёт её поля аргументами ресиверу `fn` общим механизмом подачи одной Structure, и функцию создаёт
именно применение `fn`. Особых правил `merge` для функций и превращения произвольной Structure в функцию по сходству частей
нет. Случай `f2` без `body` сохраняется: композиция частей меняет сигнатуру и сохраняет `body` `f1`, затем применение `fn`
создаёт функцию из этих аргументов. `name: "test"` при существующем callable `name` подчиняется обычному вызову callable;
именованная подача `name := "test"` явна независимо от коллизии; то же для `args`/`return`/`body` и других аргументов;
отдельного binder/парсера для `fn` нет; пустое `return: ()` не подменяется `int`.

CODEX-OPUS-AUTHOR-EXAMPLES-NOT-SEMANTICS-20261109T0551Z-01. Выдержка (технический фрагмент; заключительная фраза оценки
опущена), дословно:

```text
я могу допускать ошибки в примерах (изучи документацию -- я упускал слово fn, и поправь) но это не значит что любая моя ошибка должна ломать идею языка.
```

Пояснение (не слова автора; поправка примера по общим правилам, не новая цитата): в записи
[2026-11-08 «merge двух функций — по общим правилам структур»](2026-11-08.md#merge-двух-функций--по-общим-правилам-структур)
пример `merge(f1, f2)`, от которого ждётся новая вызываемая функция, читается как `fn: merge(f1, f2)`: `merge` по общим
правилам Structure собирает обычную Structure из частей `f1` и `f2` (у `f2` без `body` — его `args`, `return`, `var`;
`body` — от `f1`), а применение ресивера `fn` к ней создаёт функцию с изменённой сигнатурой и телом `f1`. Композиция
данных остаётся `merge`; обычная ссылка на уже созданную функцию повторного `fn` не требует. Цитаты 2026-11-08 не
переписываются.

## fn: prepared и fn: new_name merge(f1, f2) — функция в namespace текущего обхода по общим правилам

Источник: пояснение и поручение автора в чате Codex 2026-11-09; переданы Opus сообщением
CODEX-OPUS-AUTHOR-FN-PREPARED-NAME-20261109T0612Z-01 (текст — как в переданном сообщении, включая его экранирование
`\_`). Пояснение автора, предшествующее поручению, дословно:

```text
то есть мы в любой момент можем подставить заготовленную структуру ресиверу fn и это будет объявлением функции в namespace
```

Поручение автора, дословно:

```text
Передай это Opus и проверь на примерах fn: prepared и fn: new_name merge(f1, f2), что функция создаётся в namespace текущего обхода по общим правилам, без специальных случаев. И что в дальнейшем *в namspace* создается структура new_nam  (так как f1 f2 в namespace не имеют поля name). Как ты видишь я опять допустил опечатку \_но на правила языка мои опечатки не должны влиять!!!\_
```

Пояснение (не слова автора; чтение очевидной опечатки и исправленные примеры по общим правилам): `new_nam` — то же имя
`new_name`, `namspace` — namespace. `fn: prepared` — заготовленная Structure подаёт аргументы ресивера `fn` (в том
числе `name`) общим механизмом подачи аргументов, и `fn` создаёт в namespace текущего обхода функцию с этим именем;
подготовленная Structure не становится функцией от похожих полей без применения `fn`. `fn: new_name merge(f1, f2)` —
аргумент `name` дан отдельно; `merge(f1, f2)` по общим правилам собирает обычную Structure из частей двух уже созданных
функций (у `f2` без `body` — его `args`, `return`, `var`; `body` — от `f1`) и подаёт остальные аргументы; результат
применения `fn` — Structure с именем `new_name` и частями `args`, `return`, `var`, `body`, зарегистрированная в
namespace обхода. У созданных `f1`, `f2` поля `name` нет: имя результата не берётся из такого поля и не берётся молча
из имён `f1`/`f2`. Пример `fn: merge(f1, f2)` выше — сокращение, в котором отдельное имя пропущено.

Следующее уточнение автора (передано сообщением CODEX-OPUS-FN-ADDENDUM-REPLY-20261109T0615Z-01), дословно:

```text
опечатка была еще и в том что я забыл передать аргумент name в примере c fn: name merge(f1 f2)
```

Пояснение (не слова автора): это исправление пропуска в примере, а не необязательность `name` и не наследование имени
моделью `merge`; рабочие примеры — `fn: prepared` (полный подготовленный набор аргументов, включая имя) и
`fn: new_name merge(f1, f2)` (имя отдельно).

## var дополняется одинаково при любом происхождении подготовленных структур

Источник: поручение автора в чате Codex 2026-11-09; передано Opus сообщением
CODEX-OPUS-AUTHOR-UNIFORM-VAR-20261109060847Z-01 с поправкой цитаты
CODEX-OPUS-AUTHOR-UNIFORM-VAR-20261109060847Z-01-QUOTE-FIX (у автора «из наваания видно»). Дословно:

```text
Проверь у Opus на обоих примерах — fn: prepared и fn: new_name merge(f1, f2) — что var дополняется полями тела одинаково, по общим правилам, без специальных случаев. Только опять не забывай что если prepared из наваания видно что структура в коде с полем nmae, то f1 f2 могут браться из namesapce будучи подготовленными функциями. Это должно обрабатываться одинаоково безоглядки "что на самом деле", потребляются только структуры такие какие есть
```

Дополнительное уточнение автора (то же сообщение), дословно:

```text
у созданной функции и var шире может быть -- что в этом такого?
```

Пояснение Codex при передаче (не слова автора; `nmae` — `name`, `namesapce` — namespace): `prepared` — обычная
Structure в коде с полем `name` и остальными подготовленными аргументами `fn`; `f1`, `f2` могут быть уже созданными
функциями из namespace, у которых поля `name` нет. Оба входа потребляются как реально существующие структуры по общим
правилам: после общей подачи аргументов один конструктор результата рассчитывает var по фактическому body (явные поля
сохраняются, недостающие собственные поля тела добавляются, без дубликатов, без полей вложенных функций и данных
фактических аргументов), не исполняя инициализаторы при построении; правило не выбирается по происхождению структуры.
var созданной функции может быть шире написанной.

```

Ответ автора на вопрос Codex об имени нового ресивера, дословно:

зачем его по другому назвать? У нас ресиверы с разным числом аргументов называются одинаково, тот же fn может не иметь body, или у нас есть два int
```

Пояснение Codex при передаче (не слова автора): форма `fn: new_name merge(f1, f2)` — ещё одна сигнатура того же ресивера
`fn` из двух аргументов (имя и Structure описания частей), выбираемая общим механизмом ресиверов по аргументам, как формы
`fn` без `body` и две формы `int`; без нового слова, отдельного парсера и особого `merge`. Прежнее предложение Codex об

полем `name`, и созданные функции без него: поле `name`, если оно есть в операнде, участвует как обычное поле; имя
созданной функции — значение аргумента имени ресивера, а не поле.

## Видимость: однозначность поля вместо выбора «ближайшей»

Источник: фрагмент обсуждения автора с Codex о видимости переменных, приведённый автором Opus 2026-11-09 (после ответа
Codex CODEX-OPUS-341-DOCS-SOURCE-REPLY-20261109T151823Z-01). Реплика автора, дословно:

```text
по поводу var по-моему все просто -- у нас же нельзя обращаться к объявленному много раз полю без индекса, а code работает со своими локалами по своим правилам . Когда структура выполняется и считает себя data то надо просто применить это правило и всё, пускай она не найдёт свою переменную, которая объявлялась два раза, и выдаст ошибку. В итоге, все эти правила "ближаший туда ближайший сюда" по-меому оказываются лишними
```

Ответ Codex в том же обсуждении (не слова автора, кратко): при таком разграничении правило «ближайшей» лишнее. У code
локальное место определяется его правилами, выполненные записи последовательно меняют значение — три записи в одну
переменную не требуют выбирать между тремя переменными. При обращении к data нужное поле находится однозначно; несколько
одноимённых вхождений без индекса — ошибка неоднозначности, и то же правило действует, когда code передан самому себе как
data. Остаются двусторонняя видимость, подготовка локальных мест через `var` и обычный порядок исполнения: будущее
объявление позволяет заранее определить место, но его инициализатор выполняется на написанной позиции. Codex отозвал своё
предыдущее письмо Opus, закрепившее выбор по близости.
