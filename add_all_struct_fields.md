# Sol: плоский заголовок Lmx, ресиверы чтения и descriptor

ТЗ от 2026-11-13 на изменение документации и дополнение плана кодинга.
Имя файла `add_all_struct_fields.md` сохранено по поручению автора. Значения заголовка читают обычные
ресиверы `parent`, `native`, `length`, `storage`; `descriptor` возвращает обычные указатели на его поля для явной записи.

Исследован `main` до `7a9f6460` (срез 360, подготовка M8). Текущее продолжение проверять по
[steps/current.md](steps/current.md): Sol уже ведёт M8, исходный пакет P0 принят срезом 359.
Этот документ задаёт следующую работу Sol, но не утверждает, что изменения уже реализованы.
Дословные решения и последнее уточнение о расходе машинных ресурсов — в
[журнале автора](LMX_blog/2026-11-13-get-descriptor.md).

## 1. Окончательное решение

1. Перенести `size` и `data` непосредственно в `Lmx`, переименовав их в `length` и `storage`;
   убрать промежуточное поле `array: VoidArray`. Итоговый порядок — `parent/native/length/storage`.
2. Сохранить принятую архитектуру языковых массивов на общей физической основе `Lmx`.
   Предварительное предложение отделить Array от Lmx автор снял после исследования.
   Утверждения о структурном `parent` массива не отменяются.
3. Обеспечить полную взаимозаменяемость обычной Lmx Structure и массива нетипизированных указателей
   `@` (`void *`). Одинаковой C-раскладки недостаточно: операции языка также должны работать одинаково.
4. Для чтения значений дать ресиверы `parent(S)`, `native(S)`, `length(S)`, `storage(S)` и их варианты без аргумента.
   Адреса полей для записи даёт `descriptor: lmx`. Не добавлять в обычный поиск полей
   исключения для `S\parent`, `S\native`, `S\length`, `S\storage`.
5. Результат связан с исходной Lmx адресами её настоящих полей. Получение результата не копирует заголовок.
6. После обсуждения указателей выбран короткий вариант: результат содержит обычные указатели на поля,
   запись в исходную Lmx выполняется явным разыменованием. Не вводить автоматическое перенаправление
   присваивания полю результата, прокси, наблюдателей или синхронизацию копий.
7. Указатели имеют произвольную конечную глубину: `@`, `@@`, `@@@` и далее. Один и два уровня
   в примере descriptor — частные случаи общего механизма, не предел реализации.
8. Массивы имеют произвольную конечную мерность. Глубина указателя и мерность массива независимы;
   в обоих случаях не вводить фиксированный потолок или отдельные реализации для первых N случаев.
9. Без аргумента все четыре ресивера работают с `data` текущего запуска: `parent() = parent(data)`,
   `native() = native(data)`, `length() = length(data)`, `storage() = storage(data)`.
   Для `code` требуется явный аргумент.
10. `data` и `code` остаются доступными при исполнении как поля/аргументы-Structure запуска `call`.
    Они не обозначают физическое хранилище элементов Lmx. `node` сохраняет действующий контракт
    контекста активации; ресивер `node(S)` и дополнительное поле Lmx не вводятся.

Автор поставил расход машинных ресурсов выше удобства конкретной формы записи. Вариант с обычными
указателями выбран исполнителем по этому указанию и ответу «1?». Это обоснование конструкции,
а не заявление об уже измеренном выигрыше. При реализации проверить прямоту сгенерированного доступа;
отдельную инфраструктуру измерений ради этого не строить.

## 2. Физическое представление и глубина указателей

Окончательное имя ресивера адресов — `descriptor(S)` / `descriptor: S`, вместо `getDescriptor`.
Имя обозначает результат и согласуется с parent/native/length/storage. Это переименование не меняет
контракт результата, глубину указателей или явное разыменование. Двух действующих имён не вводить.
По [последнему решению автора](LMX_blog/2026-11-13-get-descriptor.md#descriptor-current-data)
descriptor также имеет два варианта: с одной S и без аргумента. `descriptor()` и `descriptor:`
равнозначны `descriptor(data)` от текущих данных запуска, в том числе во вложенных телах управления.
Для code требуется явный аргумент. Оба варианта возвращают адреса полей выбранной Structure.

Проверка имён в документации: `getType` уже заменён на `typeof`; его не переименовывать повторно.
`getPixel`, `getValue`, `getTypedValue` — прикладные функции в примерах, а не встроенные ресиверы.
Правило именования встроенных ресиверов не запрещает такие пользовательские имена и не меняет парсер.

Аналоги, использованные исполнителем при выборе имени: [Rust C-GETTER](https://rust-lang.github.io/api-guidelines/naming.html#c-getter)
рекомендует имена свойств без get_; [Julia](https://docs.julialang.org/en/v1/base/arrays/#Base.parent)
использует parent(A), length(A), а [Python](https://docs.python.org/3/library/functions.html)
— len, type, vars. Сходство касается именования, их контракты в LMX не переносятся.

Поля самого `Lmx`, в порядке `parent`, `native`, `length`, `storage`. Схема записана в порядке L2
«имя — требование», а не в прежнем порядке L1:

```text
(
    @: parent Lmx
    LmxEntry: native
    size_t: length
    @: storage void
)
```

Её машинный смысл:

```c
struct Lmx {
    Lmx *parent;
    LmxEntry native;
    size_t length;
    void *storage;
};
```

Это иллюстрация требуемой раскладки, не новый поддерживаемый C-исходник. Объявления по-прежнему генерируются
из поддерживаемого L2/L3 в штатной цепочке. В спецификации ядра согласовать с этой схемой также прежние
имена `count` и `size`: имя числа элементов теперь `length`, имя хранилища — `storage`.
Не сохранять рядом вторую конкурирующую запись заголовка.

`storage` хранит адрес элементов, `length` — их число. Для обычной Structure и массива нетипизированных
указателей элементы — `void *`. У числового массива по `storage` лежат сами числа соответствующего типа.
Тип массива определяется по адресу его заголовка в арене; машинное написание `void *storage` само по себе
не делает все массивы массивами указателей. Ссылка на массив указывает на заголовок Lmx, начинающийся
с `parent`, а не на `length` или первый элемент.

Убрать `VoidArray` именно из `Lmx`. Если эта техническая пара ещё нужна отдельному List или другому
существующему низкоуровневому потребителю, само это ТЗ не требует переписывать его устройство.

### 2.1. Что возвращает descriptor

`descriptor: S` принимает Lmx; без аргумента выбирает текущую data.
Оба варианта возвращают обычную Structure с четырьмя именованными полями.
В ней находятся адреса настоящих полей `S`, а не значения, прочитанные из этих полей:

```text
(
    @@: parent Lmx
    @: native LmxEntry
    @: length size_t
    @@: storage void
)
```

| Поле результата `d` | Значение поля | Машинный тип этого значения | Результат разыменования |
| --- | --- | --- | --- |
| `d\parent` | адрес `S.parent` | `Lmx **` | текущий `Lmx *parent` исходной S |
| `d\native` | адрес `S.native` | `LmxEntry *` | текущее слово нативного входа S |
| `d\length` | адрес `S.length` | `size_t *` | текущее число элементов S |
| `d\storage` | адрес `S.storage` | `void **` | текущий адрес хранилища S |

`LmxEntry` уже является типом указателя на функцию. `LmxEntry *` здесь — указатель на ячейку
этого указателя, а не ещё один вызываемый объект и не `void **` по принудительному приведению.
Для `parent` и `storage` дополнительный уровень косвенности обязателен: нужен адрес поля-указателя,
а не адрес объекта или буфера, на который оно сейчас ссылается.
В общем случае взятие адреса места типа с N уровнями указателя даёт N+1 уровней, разыменование
снимает один уровень. Это одна операция над описанием типа для любого конечного N; `@@` не является
специальным типом или отдельным механизмом для descriptor.

Пусть `d` — результат `descriptor(S)`. Тогда обычные операции имеют смысл:

```text
\(d\native) := 0
\(d\parent) := NewParent
\(d\length) := n
\(d\storage) := newStorage
```

Каждая запись меняет соответствующее поле исходной `S`. Чтение `\(d\length)` читает её текущее `length`.
Скобки явно отделяют разыменование от выбора поля; отдельной грамматики для этого не требуется.
Это требуемые примеры будущей поддержки, не результаты запуска нынешнего среза.

При этом `d\native := 0` изменяет обычное поле-указатель в самом результате `d`; оно не обнуляет
`S.native`. Прежняя обсуждавшаяся форма прямой записи заменена вариантом с явным разыменованием
ради обычной семантики указателей и короткого исполнения. Не реализовывать оба поведения одновременно.

### 2.2. Минимальный механизм

Получение настоящего адреса не задаёт момент публикации записи. По [M14](next_core_tasks_v3.md#native-structures)
запись через явный путь или разыменование меняет рабочее место кадра и dirty; готовое значение публикуется
на штатной границе. Это существующий механизм исполнения, не proxy или write-back результата descriptor.
После публикации нуля в S.native следующий dispatch использует обходчик; текущий машинный вход не переписывается.

Ресивер вычисляет четыре адреса и помещает их в обычное языковое значение с соответствующими типами
указателей. Дальше работают существующие чтение, разыменование и запись в типизированное место.
Дополнять их общую поддержку, если конкретный тип пока не поддержан, а не перехватывать выражения
с именем `descriptor`, переменной `d` или полем `native`.

Не принимать за готовое решение ни копию четырёх значений с последующим write-back, ни переименование
такой копии в «представление». Не добавлять реестр дескрипторов, объект с getter/setter на каждое поле,
кеш снимков, отдельный вид активации или вторую модель исполнения. Не вводить универсальную систему
отражения всех C-структур только ради этих четырёх адресов.

Не считать указатель на поле заголовка ещё одним самостоятельным заголовком Lmx. В частности,
адрес `S.parent` может численно совпадать с адресом `S`; разыменование идёт по типу обычного
указателя `Lmx **`, а не путём ошибочной повторной классификации этого адреса как нового объекта.
Использовать общий контракт типизированных указателей произвольной глубины.

Результат подчиняется обычным правилам ссылок, передачи и времени жизни исходного хранилища.
Получение `descriptor` не переносит владение, не копирует S и не создаёт скрытого продления её жизни.
Повторное получение адресов той же живой S должно достигать тех же физических полей.

### 2.3. parent, native, length, storage — обычные ресиверы

| С аргументом | Результат | Без аргумента |
| --- | --- | --- |
| `parent(S)` | Значение поля S.parent, структурный родитель; 0 у корня | `parent()` — то же, что `parent(data)` |
| `native(S)` | Значение S.native типа LmxEntry; 0 при отсутствии нативного входа | `native()` — то же, что `native(data)` |
| `length(S)` | Значение S.length, число непосредственных полей Structure или элементов Array | `length()` — то же, что `length(data)` |
| `storage(S)` | Значение S.storage, указатель на хранилище элементов | `storage()` — то же, что `storage(data)` |

Обычная форма с двоеточием, например `parent: S`, имеет тот же контракт. Отсутствие аргумента
выбирает данные текущего запуска, а не его `code` и не ближайшую вложенную Structure тела.
Вложенные тела управляющих ресиверов продолжают работать с данными своего запуска;
самостоятельный `call(D C)` задаёт собственные `data = D` и `code = C`.

Это не объявляющие ресиверы. В роли `code` применяется их обычный контракт; в роли `data`
одноимённая структурная запись остаётся данными. При одном вхождении `data\parent`,
`data\native`, `data\length`, `data\storage` выбирают записанные пользовательские Structure, как `data\for`;
повторные имена адресуются обычным индексом вхождения. Особого доступа к заголовку через путь нет.
Прямой проход по данным исполняет только корневые ресиверы объявления; возможность исполнения
кода, переданного такому ресиверу, сохраняется по общему контракту. Голый атом не вызывает ресивер:
без аргумента пишется `parent()`, `native()`, `length()` или `storage()`.

Чтение каждого значения должно сводиться к доступу к соответствующему полю без построения
`descriptor`, выделения вспомогательного объекта, поиска свойства или обхода графа ради заголовка.
Это значения полей, не адреса их ячеек: для записи по адресу остаётся §2.1. Использовать общие
разбор и выполнение ресиверов; не добавлять их распознавание в парсер или особые правила путей.
`native(S)` читает указатель на нативный вход и не вызывает его. Он не возвращает адрес ячейки
S.native: такой адрес с типом `LmxEntry *` находится в `descriptor(S)\native`.

Имена `data` и `code` при исполнении по-прежнему обозначают аргументы-Structure запуска.
`storage` освобождает имя `data` от второго смысла в физическом заголовке. `node` остаётся
зарезервированным контекстом текущей активации, одним для её вложенных тел. Это ТЗ не меняет
его вычисление, ABI или правила видимости и не требует вычислять `node` произвольной Structure.

## 3. Полная взаимозаменяемость массива @ и Lmx

Проверить и устранить различия, основанные только на способе создания объекта:
«обычная Structure» против «массив нетипизированных указателей». Для одного и того же содержимого
должны действовать общие операции индексации, длины, именованного доступа при наличии имён,
допуска, копирования, исполнения и получения дескриптора.

Не оставлять конструкцию «C-типы одинаковы, но L3 отказывает из-за категории ARRAY/STRUCT».
Пулы и классификация нужны для реальных типов и хранилища; они не должны сохранять отдельный
несовместимый языковой вид для этих двух взаимозаменяемых представлений. Согласовать также
наблюдаемый `typeof`; числовое значение кода типа этим ТЗ не назначается.

Из взаимозаменяемости не следует, что произвольные данные обязаны быть корректной программой:
при исполнении всё содержимое читается по общим правилам роли `code`. Для обычной Structure и
ссылочного массива одинаковой формы не вводить разные пути интерпретации.

Массивы `int`, `char` и других примитивов сохраняют своё типизированное хранилище и классификацию.
Не распространять требование `void *`-элементов на все Array. Сохраняются общая основа Lmx,
структурное родительство, отличие фиксированного Array от растущего List и существующая
семантика прямоугольного массива против массива ссылок на массивы.

Для любой конечной мерности N использовать общие описание размерностей, расчёт линейного адреса,
чтение и запись. Цепочки `a[i][j][k]...` и `a[i]\[j]\[k]...` сохраняют разный смысл:
первая индексирует один многомерный массив, вторая следует ссылкам между отдельными массивами.
Не сводить поддержку к ручным веткам для одномерного, двумерного и трёхмерного случая; прежний
фиксированный предел нельзя исправлять простым увеличением константы. Раскладка заголовка остаётся
`parent/native/length/storage`; сама по себе общая мерность не требует добавлять в него новые поля.

`S[i]` и `length(S)` относятся к содержимому `S.storage` и числу `S.length`; поля заголовка к этому
содержимому не дописываются. Решение с ресивером снимает конфликт между именем обычного поля
`parent`/`native`/`length`/`storage` и заголовком S: обычный путь продолжает выбирать обычное поле.

## 4. Голое имя и явный путь

Сохранить и ясно разделить три разных действия:

- Запись в голое имя Structure или функции не становится разрешённой перепривязкой этого имени.
- Запись в голое имя, полученное из внешнего контекста как вход активации, не становится неявной
  записью во внешний источник.
- Явные `struct\field := value` и запись через явно полученный указатель выбирают настоящее место.
  Запреты для голого имени на них не распространяются.

В частности, `struct\field := 0` нельзя запрещать только потому, что выбранное поле хранит
ссылку на Structure или функцию. Уточнить это и в тексте правил, и в примерах с внешним владельцем.
Тип места и уже действующие общие правила записи сохраняются; отдельные ограничения доступа
к дескриптору или новый слой «безопасности» из этого ТЗ не выводятся.

Общий путь записи должен обслуживать числа, указатели произвольной глубины и слово нативного
входа по их настоящим типам. Не выдавать поддержку присваивания `int` за поддержку всех этих случаев.
Обнуление настоящего `S.native` выбирает существующий маршрут обходчика при следующем вызове.
Остальное взаимодействие записи с рабочими значениями и инвалидизацией native согласовать
с действующим общим контрактом; систему наблюдения за descriptor не создавать.

## 8. Критерии завершения и соразмерные проверки

Достаточен один небольшой согласованный набор примеров на языке, постепенно включаемый в обычные
`test` и самосборку. Не строить отдельную систему тестирования или безопасности вокруг ресивера.

- На разных D и C в `call(D C)` сверить все четыре ресивера без аргумента с их вызовами от D;
  явный C должен выбирать C. Одноимённые записи в D должны читаться путями как обычные данные,
  без исполнения ресиверов и без подмены заголовком. Достаточен один компактный пример.
- Получить адреса четырёх полей, прочитать их и записать через них новые значения; проверить
  исходную S, а не только результат descriptor. Для `storage` использовать реальное совместимое
  хранилище, для `length` — осмысленное число элементов; после штатной публикации ресиверы должны видеть изменения.
- В том же запуске сверить адреса из `descriptor()` и `descriptor(data)`, включая вложенное тело
  управления. `descriptor(code)` должен выбирать явно переданный code, если он отличается от data.
- Проверить косвенность `parent/storage` и ячейку `native`: изменяется само поле S, а не родительская
  Structure, первый элемент хранилища или случайно отдельная копия.
- Получить результат дважды и увидеть одни и те же исходные поля; изменение S должно наблюдаться
  при последующем чтении через ранее полученные адреса.
- После записи нуля в настоящий `native` вызвать тот же код через штатный маршрут обходчика.
- Пройти одинаковую последовательность операций для Lmx и массива нетипизированных указателей;
  отдельно сохранить один числовой Array, чтобы не принять его хранилище за массив ссылок.
- Показать запись через `struct\field` во внешнее место и в поле со ссылкой на Structure/функцию,
  не снимая запрет перепривязки голого имени.
- Одним компактным примером проверить указатель глубже двух уровней и многомерный массив;
  если найден прежний фиксированный предел, взять значение выше него. Основание отсутствия потолка —
  общий алгоритм и представление, а не перебор всех глубин и размерностей тестами.

Широкие наборы запускать только по явной потребности интеграции. Новые примеры оформлять без лишнего
закрытия одного уровня отступа, с общими правилами языка и актуальным `call(data code)`.
Правила фаз `implements/test` из действующей передачи сохраняются; само получение дескриптора
не вводит новый механизм допуска или автоматический повтор тестов.

Готовность задания означает: документация и план согласованы с окончательными решениями,
плоский заголовок и заявленные операции реально работают, ресивер состоит из получения обычных
адресов без новой обслуживающей инфраструктуры. Эта передача сама по себе такую готовность не заявляет.
