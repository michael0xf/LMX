# Глубина оператора: одна точка и обычное выражение в скобках

Редакция 2026-11-26. Глубина — общий вход операции, включая пользовательский
операнд. Она выбирает логическую глубину по сохранённым измерениям
плоского Array. Это не уровень отступа и не глубина указателя; новый
вид функции или Structure не вводится.

<a id="syntax"></a>
## 1. Формы записи

| Запись | Переданная глубина |
| --- | --- |
| `p1 + p2` | 0: базовая операция принимает внешние значения целиком |
| `p1 .+ p2` | 1: стандартный VALUE-профиль проходит одно логическое измерение |
| `p1 .(2)+ p2` | 2 |
| `p1 .(10)+ p2` | 10 |
| `p1 .(0)+ p2` | 0 явно; та же операция, что без точки |
| `p1 .(1)+ p2` | 1 явно; та же операция, что с одной точкой |
| `p1 .(layers + 1)myOperator p2` | Результат обычного выражения глубины |

**В модификаторе допускается только одна точка.** Произвольная глубина
задаётся в круглых скобках. Последовательность точек не является
другой записью глубины.

Содержимое `.(…)` разбирает **тот же общий парсер**, что другие выражения.
Внутри допустимы имя, вызов, выражение вроде `1 + 9`. Отдельный разбор
только десятичных цифр, вычисление исходной строки или второй парсер
выражений не вводятся. Готовое вхождение графа сохраняет свой контекст.

**Точка, за которой непосредственно следует `(`, всегда начинает модификатор
оператора или функции.** В обычном лексическом контексте `.(` распознаётся
раньше десятичной точки и зоны точечных уровней. Числовой сканер не поглощает
эту точку. Поэтому `1.(3)+2.(2)+3` имеет те же границы, что
`1 .(3)+ 2 .(2)+ 3`, и даёт 6 по прежнему скалярному договору.

Это правило не требует новой грамматики выражения глубины: после `.(` общий
P0 разбирает обычное выражение до соответствующей `)`. Группировщик получает
готовое вхождение графа, а не сканирует исходный текст. Строки, комментарии
и точные идентификаторы сохраняют защиту своего содержимого. Остальная
числовая лексика сохраняется: в `1 .+ 2` нужна обычная граница, а `.(` не
является десятичной точкой даже без пробела после числа.

<a id="abi"></a>
## 2. Шаблон операнда и вход в метод

Первые три входа имеют порядок **left, depth, right**:

```lmx
operand_template:
    @: left
    int: depth
    @[]: right
    const: int: PASS_ARGS_AS_IS
    const: int: PRIORITY
```

Все пять именованных полей принадлежат фактическому описанию DATA.
`depth` — обычный числовой вход, а не ещё одно константное свойство
наподобие PRIORITY. Операндная форма подаёт 0, 1 либо допустимый результат
выражения в скобках. Требуется допустимое неотрицательное целое;
ошибка структуры, отказ вычисления выражения и обычный допуск входа
сохраняют свои каналы. Недопустимая готовая глубина — диагностика транслятора, если она уже
определима, иначе диагностика интерпретатора при достижении операции.
Это не пользовательское исключение и не дополнительная запись в throws.

Транспортные позиции 0/1/2 теперь содержат left/depth/right. Число глубины
**не добавляется** в массив правых аргументов. Сохраняются две формы:
без левого атома либо с одним левым атомом. Отсутствующий left остаётся
отсутствующим. Эквивалентность префиксной записи по-прежнему устанавливает
сам метод, а не перенос первого right в left при передаче.

PASS_ARGS_AS_IS продолжает задавать потребление left/right. У RAW-операции
эти вхождения остаются RAW; к моменту фактического вызова метода depth —
готовый числовой вход. Обнаружение читает тип этого входа и прежние
готовые mode/priority, но не вычисляет выражение глубины.

Пользовательский метод получает именно запрошенное число до любого
необязательного обхода, который определяет сама операция. Этот метод
возвращает число и не превращается автоматически в поэлементный map:

```lmx
DepthProbe:
    @: left
    int: depth
    @[]: right
    const: int: PASS_ARGS_AS_IS 1
    const: int: PRIORITY sys\priority("+")
    return: int
    read:
        return: depth

@: myOperator DepthProbe\read
int: observed 10 .(1 + 1)myOperator 20
```

Ожидаемое значение observed — 2. Это пример спецификации; статус проверки
реальным парсером и runtime учитывается отдельно.

<a id="receiver"></a>
## 3. Структурная форма и точные имена

В структурной форме используется **базовое имя**, а глубина передаётся
именованным входом `depth`. Точки и выражение в круглых скобках
внутрь имени в обратных кавычках не добавляются. Например, для системного
VALUE-ресивера:

```lmx
@: result `*`(a; b; depth := 2)
```

Этот профиль ресивера потребляет обычные значения аргументов и объявленный
именованный вход depth. Это не позиционный вызов трёх входов операндного
ABI. У пользовательского метода, открывающего именно этот ABI, входы
left/depth/right в структурном вызове следует указывать явно.

Обратные кавычки сохраняют обычную семантику точного идентификатора.
Имя с точкой внутри кавычек остаётся таким буквальным именем, если его
объявил пользователь; кавычки не разбирают модификатор глубины.
Стандартная операция не публикует отдельный вызываемый алиас с точкой.
Ссылка на её throws использует базовое имя: например `` `*`\throws ``.

Depth не является глобально перехватываемым словом любого вызова функции.
Это вход выбранного метода/профиля операции. Исходная функция, которую
оборачивает `asOperand`, сохраняет все собственные логические аргументы,
включая пользовательский аргумент с именем depth. Управляющий depth
обёртки имеет другого владельца и не подмешивается к этим аргументам.

<a id="evaluation"></a>
## 4. Вычисление и общий обход

Выражение глубины получается **один раз при достижении данного вхождения
операции**, в исходном контексте и по обычным правилам порядка аргументов.
Группировка, чтение приоритета и обнаружение кандидата его не исполняют.
Пропущенная логическая или условная ветвь не исполняет и свою вычисляемую
глубину. Приоритет и ассоциативность базовой операции от числа не зависят.

Стандартный VALUE-профиль использует один общий обход:

```text
applyDepth(base, acceptedDepth, actuals, output):
    if acceptedDepth == 0 or every original consumed actual is scalar:
        return base(actuals) through the admitted result contract
    level = prepareNextLogicalDimension(actuals)
    diagnoseMissingRequiredDimensions(level, originalScalarInputs)
    validateMatchingSelectedShapes(level)
    for each position on this dimension:
        values = sameStorageSlicesOrOriginalScalars(level, position)
        applyDepth(base, acceptedDepth - 1, values, output.at(position))
    publish the result with its full shape and result requirement
```

Измерения берутся из [внешнего служебного описания Array рядом с capacity](ARRAY_STORAGE.ru.md#side-metadata).
Один шаг по плоскому прямоугольному массиву выбирает логический срез
того же хранилища, не создавая Structure для строки. Порядок осей —
порядок их описания, от внешней к внутренним. После запрошенного числа
шагов базовая операция получает оставшиеся значения целиком. Форма
результата определяется её настоящим договором: произведение строк
может дать скаляр, сумма строк — строку. Если результат прямоугольный,
используется одно плоское хранилище результата. Отдельный граф строк
и временные объекты для каждой строки не требуются. Конкретный LMX-
исполнитель может линеаризовать выбранные измерения в один цикл по
проверенному плану формы/адресации; это тот же обход, не второй алгоритм.

Для определения типа не вызывается пробный элемент. Void остаётся void.
Массивные входы должны предоставлять требуемые измерения и согласованные
выбранные формы. Изначально скалярный вход может распространяться через
эти измерения; исчерпанный Array не становится скалярным broadcast, пока
требуются дополнительные измерения. Все исходные скалярные входы дают
неподвижную точку. Singleton Array остаётся массивом. Неверные depth/shape
диагностируются транслятором/интерпретатором. Пустой вход сохраняет полное
описание формы и типа без пробного первого элемента.

Для двух **плоских двумерных массивов** p1 и p2 с сохранённой формой `(2,2)`
и построчным хранилищем `[1 2 3 4]` и `[10 20 30 40]`:

| Операция | Что получает базовая операция | Результат |
| --- | --- | --- |
| `p1 * p2` | Две матрицы целиком | Форма `(2,2)`, хранилище `[70 100 150 220]` |
| `p1 .* p2` | Каждую пару логических строк | Форма `(2)`, значения `[50 250]` |
| `p1 .(2)* p2` | Каждую пару скалярных координат | Форма `(2,2)`, хранилище `[10 40 90 160]` |

Таким образом, покоординатное скалярное умножение массива ранга N использует
глубину N. Одна точка всегда равна глубине 1; её число не меняется неявно
из-за ранга. Прежнее утверждение «любой плоский Array имеет только один
уровень для depth» заменено этим правилом по сохранённой форме. Механизм
общий для операций, без специального исключения для умножения.

Обычная Structure остаётся `@[]`. Поле может ссылаться на другую обычную
Structure; отдельной сущности «массив массивов» из-за этого не возникает.
Путь `struct[i]\[j]` — индексная запись `struct\struct2\field`, если i и j
выбирают соответствующие поля; `struct[i]\[j]\[k]` соответствует
`struct\struct2\field[k]`. Это общий механизм доступа. Мерность плоского
Array читается из служебного описания, а не угадывается по ссылкам графа.

Глубина 0 означает прежний договор базовой операции над целым значением.
Она не обещает допустимость любого внешнего контейнера для этого договора.

Пользовательские, RAW-, DATA-, TYPE- и PLACE-потребители сохраняют свои
роли и смысл. Они получают depth тем же транспортом, но не переписываются
в VALUE-map вслепую. Профиль без определённого смысла ненулевой глубины
выдаёт диагностику транслятора/интерпретатора вместо игнорирования числа. VALUE-адаптер
использует общий обход и сохраняет фактическое зависимое требование
результата: нельзя обещать scalar R для Array или подменять все результаты
универсальной коробкой.

<a id="assignment"></a>
## 5. Семейство присваивания

Принятые записи присваивания сохраняются:

| Форма | Каноническая операция | Глубина |
| --- | --- | --- |
| `target := source` | `:=` | 0 |
| `target .: source` | `:=` | 1 |
| `target .(n): source` | `:=` | допустимое n |
| `target .(0): source` | `:=` | 0, присваивание целому месту |

Это таблица поверхностных форм существующего семейства присваивания.
Голое двоеточие не превращается в новый ресивер присваивания.
Группировщик, правило одного left и подготовка передачи не получают
отдельного раскрывающего прохода для присваивания. Структурный вызов
использует базовое `:=` и именованный depth; ссылка на стандартные
ошибки — `` `:=`\throws ``.

При положительной глубине обход назначения сохраняет настоящие PLACE.
Обычное присваивание получает все требуемые значения RHS и проверяет
допуск целей **до первой записи во всей операции**, а не отдельно перед
каждой дочерней ветвью. Поэтому перекрывающиеся перестановки сохраняют
правильный результат. Глубина 0 следует обычному допуску и правилам
идентичности целого места для :=. Явное fused-присваивание сохраняет
свой отдельный потоковый договор; увеличение depth не превращает
обычную запись в потоковую незаметно.

PLACE логической строки/плоскости в плоском хранилище — существующая
область памяти, а не независимая ячейка ссылки. На выбранной базовой
глубине присваивание записывает допустимый блок той же оставшейся формы;
перепривязки несуществующей ссылки на строку нет. Настоящее место переменной
или ссылки на глубине 0 сохраняет обычную перепривязку. Для заполнения
скалярных ячеек массива ранга N используется глубина N. Допуск всех
областей/ячеек и сохранение всей RHS предшествуют первой записи во всей
обычной операции присваивания.

Недопустимая глубина, несовместимость требуемых глубин/форм операндов
и непригодный `fuse(expression)` — ошибки подготовки языковой операции:
транслятор сообщает то, что может определить, интерпретатор — достигнутое
динамическое нарушение. Новые типы пользовательских исключений и обёртки
отказа не вводятся. Реальные отказы вычисляемых пользовательских вызовов
и выбранных скалярных операций сохраняют прежние договоры.
