# Асинхронность, исполнители и Message

[Руководство RU](LMX_Design_Patterns.ru.md) · [Guide EN](LMX_Design_Patterns.en.md)

Исходные 8 паттернов дополнены structured concurrency, supervision и MapReduce (88–90). Во всех LMX-примерах параллельная ветка означает отдельно созданный Message; один владелец никогда не исполняет два turn одновременно. Общий lifecycle/HTTP/provider профиль указан явно и не учитывается как бесплатный код.

## Повторный просмотр с общими ресиверами — 22 ноября 2026

Каждый пример ниже проверен на применение нового прямого API `fun`. Сохранены действующие клиенты: у предложенных замен либо меняется указанный протокол, либо полный клиент с необходимыми объявлениями исходов и адаптерами на одном текущем ядре не становится короче. Это решение относится к данным небольшим сценариям, а не запрет использовать библиотеку в более крупных программах.

| № | Рассмотрены | Причина сохранения |
| --- | --- | --- |
| 058 | `map, repeat` | Round-robin выбирает получателя и отправляет job в его Message; ответ worker отправляет collector. Локальный map/repeat не сохраняет распределение по владельцам, очередь и два независимых turn. |
| 059 | `repeat, map` | Четыре формы ask выражают три сообщения с разными значениями и отдельный finish в одном post. repeat одной функции не создаёт те же сообщения автоматически; callback с post добавляет другой turn/конверт, а готовый список/mapper длиннее четырёх записанных вызовов. |
| 060 | `scanl, foldl` | Actor хранит total между отдельными сообщениями и предоставляет read. foldl/scanl потребуют заранее собранную последовательность, не заменяют Message-владение и не дают чтение между независимыми приходами. |
| 061 | `apply, pipe` | Active Object содержит post/ask/answer и отдельный адрес sink.accept. apply был бы локальным синхронным вызовом; pipe не заменяет доставку результата. При сохранении post новые вызовы только добавляются к короткому протоколу. |
| 062 | `guard, predicate` | Reactor отдельно обрабатывает n>0 и n<0, а n=0 не делает ничего. guard с ошибкой или boolean predicate не передают три разных исхода readReady и необходимость unregister; обе ветви остаются. |
| 063 | `partial, apply` | submitRead регистрирует completionTarget и token7, completed позже проверяет token перед sink.write. partial не заменяет существующий completion-порт и жизненный цикл I/O, apply не убирает ни регистрацию, ни проверку токена. |
| 064 | `once, lazy` | Future сохраняет waiter IDs и рассылает один опубликованный результат; resolve после первого результата ничего не меняет. once может кешировать локальный вызов, но не создаёт очередь ожидающих и replies.send; его состояние не заменяет ready/value, используемые get. |
| 071 | `pipe, apply` | Ingress пересылает frame в worker, worker отдельно отправляет результат writer. Синхронная pipe сместила бы обработку в одного владельца вместо half-sync/half-async, а оборачивание уже написанных post не сокращает протокол. |
| 088 | `map, foldl, traverse` | Scope ждёт остановки обоих детей, подавляет повторное уведомление каждого childId, запрашивает остановку остальных после ошибки и завершает только при remaining=0. Последовательный foldl/traverse не является барьером жизненного цикла и не заменяет эти состояния. |
| 089 | `retryCall` | Supervisor запускает новый child после отдельного уведомления stopped, ограничивает число рестартов и сохраняет новый адрес. retryCall повторяет синхронную операцию в текущей активации и не управляет завершением/перезапуском Message-ребёнка. |
| 090 | `map, foldl` | MapReduce в этом примере — маршрутизация сообщений в even/odd reducers и подтверждение barrier.accepted. map/foldl общего fun являются последовательными локальными операциями над Structure; без сохранения post/answer/barrier получился бы другой сценарий. |

## Запуск R0 и вызов сценария

Программа всегда начинает выполнение с **R0**, обычного L3 Thread под родительской заглушкой, без DATA и пользовательских actuals. Отсутствие DATA пропускает только обработку входов; локальные переменные, обычные вызовы, диспетчеризация и выходы сохраняются. Именованный сценарий вызывается из уже запущенного корня или обработчика обычным механизмом и не заменяет точку старта.

Для фрагмента указываются его принимающий контекст и обычный вызов сценария. Описание DATA получает эту роль только по существующему договору принимающей операции; оно не превращает CODE корня в DATA и не вводит отдельный профиль загрузки или выбор Main. Родительская заглушка может передать свои значения обычным сообщением корню; внутренние параметры запуска Thread не становятся пользовательскими actuals. См. [запуск корня](../../LMX_semantics.en.md#root-entry).

Добавлены [109 Request-Response / Ask](109_request_response_ask_comparision.md), [110 Become / Selective Stash](110_become_selective_stash_comparision.md), [111 Phased Message Lifecycle](111_phased_message_lifecycle_comparision.md), [112 External Blocking Adapter](112_external_blocking_adapter_comparision.md). В группе 15 сравнений, 45 основных листингов. [Покрытие и границы providers](MESSAGE_PROTOCOLS_2026-11-28.md).

Message сохраняет штатное исполнение и сам не создаёт deadlock. LMX synchronized не применяется; физические блокирующие операции и locks принадлежат L2/native adapter. Новые листинги содержат полные прикладные алгоритмы, а отсутствующие физические providers помечены REQUIRE_IMPLEMENTATION. LMX и контрольные языки в этой редакции не исполнялись.
