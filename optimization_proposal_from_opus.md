## 2. Факты кода (установлены чтением source-full100)

### 2.1 Порядок проходов одного unit

Драйвер: `lm_compiler_translate` (`src/l2src/l2_frontend_emit.lm2:834`) →
`snap_parse`, выбор `os`-ветви, `program_tables`, `parts_read`,
`unit_from_root` → `translate_unit` (:560) → `parse_unit` (:5740) →
`emit_unit` (:16053).

В `parse_unit` (`emit.lm2:5740–5900`), по порядку:

1. :5760 `collect_asgn_binds`. Это **полный** проход по всем методам:
   `core.lm2:4404`, два цикла — сначала корни, затем остальные. Для каждого
   метода `collect_asgn_method` (`core.lm2:4385`) делает `ml_free`,
   `ml_collect` и `collect_asgn_body`.
2. :5767–5779 — цикл до неподвижной точки, пока меняются `m_n`/`ns_n`. Для
   каждого локального namespace с отложенным исходным телом вызывается
   `local_ns_proc` (`emit.lm2:1468`, затем `ns_proc_add` :384), и снова весь
   `collect_asgn_binds` (:5775).
3. :5782 `ns_exec_scan_body` для всех методов; :5791 `ns_resolve_refs`;
   :5796 `bind_calls` (`core.lm2:2372`).
4. :5802 `vis_method` и `merge_scan` для всех методов; затем снова
   `collect_asgn_binds` (:5808) и снова `ns_resolve_refs` (:5813).
5. :5816 `dyn_local` (`core.lm2:4478`); :5821 `d105_reset`
   (`useplan.lm2:2637`).
6. :5823 для всех методов: `body_throws` (`emit.lm2:15305`) — **вывод**
   throws из тела через `body_path_effects` и операторы; затем
   `trailer_throws`, `m_provider`; :5839 — проверка, что machine-методы
   объявили throws.
7. :5844 `pap_prepare` (`emit.lm2:13711`); :5848 `m2_close`
   (`core.lm2:11456`, 168 строк, 12 циклов) — межпроцедурное замыкание
   кандидатов `call:` (план M2).
8. :5851 для всех методов: `ml_rebuild`, `check_body` (`emit.lm2:5145`),
   `check_ret_tr`, `mad_captures_dynamic` и `admit_site`.
9. :5868 `throws_close` (`emit.lm2:15319`) — неподвижная точка по полной
   матрице рёбер метод×метод: callee throws ⇒ caller throws.
10. :5870 `dyn_close` (`core.lm2:4930`). Внутри: `cfl_close`, `cfa_apply`,
    `dyn_step` до отсутствия изменений, `dyk_close`, `anchor_close`, снова
    `dyn_step` до неподвижной точки, `d105a_close`, `dyn_typed`.
11. :5873 `wait_run` (`emit.lm2:1789`) — повторный прогон отложенных
    проверок источников (присваивание `colon_check_assignment`,
    `check_value_convert_field`, `wait_kinds` и др.) после замыканий.
12. :5875 `split_close` (`core.lm2:12016`); :5877 `copy_calls_verify`
    (`core.lm2:10414`); :5879 `check_immutable_calls` (`core.lm2:9716`).
13. :5881 — снова `collect_asgn_binds`; затем разрешение entry, `intern_mi`

В `emit_unit` (`emit.lm2:16053–17294`, 1241 строка) идут **ещё семантические
шаги**: `layout_owns` (:16219), `graph_places_seed` (:16221 и :16261),

### 2.2 Обращение к predef (место всех четырёх выборок attempt03)

- `predef_has_type` (`types.lm2:241`) и `predef_has_function`
  (`types.lm2:446`) перебирают все predef unit по очереди.
- Для каждого `predef_file_has_type`/`_function` (`types.lm2:153`/`:390`)
  линейно проходит поля корня разобранного документа, сравнивает имя через
  `text_same`/`memcmp` и **рекурсивно** следует `predef:` и отображённым
  `include: "*.lm1.h"` → `*.h.lm1` (через `predef_import`,
  `values.lm2:135`, относительно каталога включающего файла).
- Документ разбирается один раз: `snap_document` (`types.lm2:1433`) держит
  разобранный документ. Но обход полей и рекурсия повторяются при каждом
  запросе. Результат запроса не хранится.
- Вызывающие — классификация при сборе: `fnptr_local` (`types.lm2:657`) из
  `ml_collect`, `is_known` (`types.lm2:1078`) из `is_asgn`
  (`lower.lm2:748`). Они идут внутри повторного `collect_asgn_binds`.
- `snap_bytes` (`types.lm2:1346`) кэширует только удачное чтение, через
  линейный `strcmp` по списку. Неудачное открытие не запоминается, и следующий
  запрос откроет файл снова (замечание Codex 1). В корректном дереве attempt03
  я **не устанавливал**, есть ли вообще неудачные открытия; kernel time 0,7 %
  говорит против их заметной доли.

## 3. Что удалить и чем заменить (без сохранения анализа под другим именем)

1. **throws** (правило 2 автора). Удалить вывод `body_throws`
   (`emit.lm2:15305`, кроме чтения явного `throws_declared`) и `throws_close`
   в обоих местах (`emit.lm2:5868`, `:16248`) вместе с `m_throws` как
   выводимым признаком.
   - Замена во втором обходе: для каждого записанного вызова каждое имя
     объявленного throws callee должно быть в `catch` вызывающего блока
     (по правилам видимости catch из книги) или в явном `throws` вызывающего.
     Иначе — ошибка трансляции в месте вызова.
   - Неявные отказы операторов (`merge`, `interpreter`) остаются
     необязательными для перехвата, как в книге.
   - Канал статуса native raise читает объявленное, а не выведенное.
2. **M2 и доказательства тела** (правило 3).
   - Удалить `m2_close` (`core.lm2:11456`), сертификаты фактического тела,
     удаление пустого `call:` по доказательству и `pap_prepare`, если он
     служит только этому (проверить его потребителей при дизайне).
   - Замена: `call:` всегда исполняет текущее выбранное тело. Годность
     `native` — флаг runtime, который общий путь записи runtime ставит в 0 при
     изменении исполняемого кода. `unit_empty_pointer_rebound_call` должен
     дать 7 в native и walker без особого пути.
3. **D-105 и сводки эффектов.** Удалить `d105_close` (`useplan.lm2:3797`),
   `d105a_close`, «implements как эффект» и замыкание физических источников
   мест.
   - Замена: явные контракты проверяются во втором обходе; динамический
     случай решает runtime-допуск `lmx_implements` (UNKNOWN ≠ NO), а
     известное несоответствие даёт специальную ошибку (§5.2).
4. **Динамические входы** (`dyn_local`, `dyn_close`, `cfl_close`,
   `cfa_apply`, `dyk_close`, `anchor_close`, `dyn_typed`). Требуемый исход
   задан книгой (§dynamic, RU :729, EN :779): источник — ближайшая локальная
   привязка вызывающего, затем его унаследованный динамический вход, затем
   лексический fallback callee; пересылающий метод не материализует
   собственный fallback; `x` нельзя молча потерять или заменить нулём.
   Механизм общего контекста и прямых мест — **дизайн Fable**:
   - я его не выбираю;
   - никакого глобального runtime-реестра или поиска имени при каждом чтении;
   - транзитивный анализ не должен вернуться под новым именем.

   Фраза книги «Statically known call requirements propagate to a fixed point,
   including through mutual recursion» (EN :779 и её RU-пара в :729)
   **конфликтует** с последним уточнением автора. Её надо пометить
   конфликтующей, а не держать основанием анализа (см. §6).
5. **wait-checks** (`wait_run`, `emit.lm2:1789`). Проверки, отложенные до
   результатов замыканий, удалить вместе с ожиданием. Остающаяся явная
   проверка записанного присваивания и преобразования выполняется один раз во
   втором обходе по явным контрактам. То, что требует runtime-решения,
   решает runtime.
6. **Повторный сбор** (`collect_asgn_binds` ×4+, цикл :5767). Регистрация
   процедуры локального namespace (`local_ns_entry`, `core.lm2:3863`, →
   `local_ns_proc`/`ns_proc_add`) записывается в момент её встречи внутри
   единственного обхода сбора. Обходить уже обработанные тела всех методов
   ради неё не нужно. Лексическая и исходная видимость вхождений не меняется:
   учёт узла не делает позднее имя видимым раньше.
7. **Обращения к predef.** Объявления predef-closure индексируются один раз,
   при сборе или при загрузке документа. Классификация `fnptr_local`/
   `is_known` становится обращением к таблице, а не рекурсивным обходом
   документов на каждый запрос. Это требование документа Codex «табличные
   обращения не ищут заново обходом». Отдельный кэш или
   негативный кэш не вводить, пока не установлен факт неудачных открытий
   (замечание Codex 1).
8. **Семантика внутри emission.** Шаги `emit_unit` из §2.1 перенести в
   первый или второй обход, либо удалить, если они обслуживают удаляемые
   анализы. Третий обход только печатает по готовым таблицам.
9. **`split_close`, `copy_calls_verify`, `check_immutable_calls`**

## 4. Общий код с интерпретатором и граница генерации

Это предложение, решение за дизайном Fable (ответ Codex на Q2).

- **Сбор (обход 1).** Одна реализация учёта узлов, объявлений, владельцев,
  контекстов, мест использования и predef-объявлений. Её вызывают walker при
  подготовке исполнения построенного графа и транслятор над деревом
  парсера. Тонкое представление нужно там, где транслятор видит
  `LmP0Node`, а walker — `Lmx` граф. Какое — дизайн. Две реализации одной
  семантики не допускаются.
- **Валидация (обход 2).** Общие правила вызова и присваивания:
  - допуск используемых интерфейсов (сегодня `lmx_implements` в runtime и
    дубли `lm_compiler_implements`/`prep_implements` во frontend — оставить
    одну);
  - обязательства throws/catch;
  - явные контракты формалов и результата;
  - физические карты мест (одни для чтения, записи, `@` и публикации).
- **Runtime-допуск** — та же общая операция, вызываемая в момент вызова или
  записи, когда решение требует исполнения.
- **Генерация (обход 3)** — единственная часть только транслятора: печать L1
  из таблиц обходов 1–2. Каждую оставшуюся специфичную для транслятора часть
  дизайн должен обосновать. Пример — чтение predef-заголовков по путям;
  у walker такого входа нет.
- **Различия native/walker, которые уже известны** (их надо закрыть, а не
  закрепить):
  - walker берёт ширину входов из сигнатуры, построенной frontend-замыканием
    (§2.3);
  - решение о годности `native` сегодня принимает frontend, а не runtime;
  - отказ `implements` в аргументе сегодня даёт отказ трансляции
    (`os_implements_refused`), а не runtime-ошибку несовпадения.

## 5. Runtime-пути ошибок и сброса native

1. **throws/catch.** Обязательства проверяет второй обход (§3.1). Исполнение
   идёт через `lmx_walk_throw`/`lmx_walk_catch_bind` в walker и через канал
   статуса в native. Проверить:
   - записанный throw доходит до catch вызывающего;
   - вызов без throws и catch не транслируется;
   - неявный `merge`/`interpreter` ловится по желанию.
2. **Специальная ошибка несовпадения типов/implements.** Если присваивание
   или аргумент требует решения при исполнении, общий runtime-допуск
   (`lmx_implements`, UNKNOWN ≠ NO) возвращает NO, и выдаётся специальная
   ошибка, а не заранее введённый запрет трансляции. Строку
   `os_implements_refused` при дизайне отнести к одному из двух случаев:
   - несовпадение записанного контракта, которое видит второй обход;
   - runtime-случай.
3. **Сброс native.** Общий путь записи runtime при изменении исполняемого кода
   ставит `native = 0` у соответствующей структуры. Следующий вызов идёт
   walker по актуальному телу. Транслятор ничего не предсказывает. Сейчас
   этого общего сброса нет (§2.3), его место в пути записи — предмет дизайна.
   Проверка: изменение кода → `native = 0` → настоящий walker с актуальным
   телом, наблюдаемый результат как у walker.

## 7. Шаги миграции (предложение порядка; каждый — фокусно, существующими средствами)

Общие условия: быстрый цикл — `build-frontend-part` для изменённых модулей
и отдельные строки списка через `lmxtool suite`; whole quick — для сквозной
проверки; FULL — только финал. Новых runner/cache/scheduler нет.

1. **Явные throws.** Удалить `body_throws`/`throws_close`/`m_throws`-вывод и
   ввести проверку второго обхода. Проверки:
   - `os/os_throws.lm2` (nf);
   - отрицательный случай вызова без throws и catch — ошибка трансляции;
   - catch неявного `merge`.
2. **Один обход сбора.** Регистрация локальных namespace внутри него; убрать
   повторы `collect_asgn_binds` и цикл :5767. Проверки:
   - побайтное сравнение L1 frontend-модулей до и после;
   - счёт посещений тел;
   - строки с локальными namespace;
   - `sha256_vectors` native и pointer101 (pointer-copy101), если затронут
     производитель рабочих мест.
3. **Индекс predef.** Снять одно измерение до и после на одних байтах:
   перевод одного модуля из корректного дерева (как attempt03) и
   C-компиляция его результата.
4. **Runtime-сброс native и удаление M2.** Сначала runtime-сброс в общем пути
   записи, затем удаление `m2_close` и сертификатов; `call:` всегда
   исполняет. Проверки:
   - `unit_empty_pointer_rebound_call` → 7 в native и walker;
   - изменение кода → native 0 → walker по актуальному телу.
5. **Runtime implements и специальная ошибка.** Удалить D-105-замыкание и
   сводки эффектов. Проверки:
   - `os/os_implements.lm2`;
   - решение по `os_implements_refused`;
   - runtime-несовпадение.
6. **Динамические входы по дизайну Fable** (§3.4). Проверки — существующие
   строки динамических входов в native и forced walker: исход по §dynamic, без
   потери `x` и без нуля.
7. **Emission без семантики** (§3.8) и одна реализация обходов 1–2 с walker.
8. **Измерение цели.** По каждому компоненту отдельно: L2→L1, L1→C и
   C-компиляция, на одних байтах, с бинарём, flags, CWD, wall, CPU и памятью.
   Затем whole quick, а FULL — только в финале.

Зависимости: шаг 4 нужен до шага 5, потому что в обоих решение runtime
заменяет frontend-доказательство. Шаг 6 зависит от дизайна общего контекста.
Шаги 1–3 независимы и уменьшают объём до остальных.
