# Передача SBCL_comparison в текущую spec

## Размещение

Отдельный архив добавляет **`patterns/examples/SBCL_comparison/` относительно корня `spec`**. Его верхняя директория называется `SBCL_comparison`; распакуйте её в `spec/patterns/examples/`. Полный общий архив также содержит восстановленные примеры других языков и согласованные дополнения общего ядра.

Десять общих дополнений перечислены в [локальном контракте](STANDARD_LISP_AND_EXPRESSION.md) с точными относительными целями. Они уже включены в общий архив; отдельно перенесённая директория ожидает соответствующую базовую `spec`. [MANIFEST.sha256](MANIFEST.sha256) перечисляет локальные файлы и контрольные суммы, а `BASE_REFERENCES.json` фиксирует использованное ядро.

## Порядок интеграции

1. Добавить директорию целиком.
2. Проверить её манифест и соответствие внешних базовых файлов по [BASE_REFERENCES.json](BASE_REFERENCES.json).
3. Запустить локальные стенды и прочитать контракты внутри директории.

Пользователь отдельно разрешил перенос общих полезных функций в ядро, их реализации и документацию. Поэтому полный архив содержит соответствующие public/catalog/source изменения. Новая грамматика или отдельный вид операнда для Lisp-записи не вводятся; используется существующий общий Expression.

## База и пути

В спецификации и реестре `BASE_REFERENCES.json` все пути назначения считаются **от корня `spec`**, например:

| Назначение | Путь относительно spec |
| --- | --- |
| Семантика языка | `LMX_semantics.en.md` |
| Грамматика | `LMX_grammar.en.md` |
| Общее руководство | `LMX_semantics_guide.en.md` |
| Последовательности и Pattern | `CORE_SEQUENCES_REGEX.en.md` |
| Каталог текущих операций | `patterns/LMX_Fn_Receivers/catalog.json` |
| Исходники существующего ядра | `patterns/LMX_Fn_Receivers/src/` |
| Профиль Message и HTTP | `patterns/MESSAGE_HTTP_PROFILE.md` |
| Эта поставка | `patterns/examples/SBCL_comparison/` |

SHA-256 фиксирует конкретную основу сравнений. Несовпадение с вашей более новой редакцией — повод сопоставить соответствующие определения перед обновлением извлечённых копий, а не заменить внешний файл нашей копией. Полные определения, а не номера строк, перечислены в [implementation_data.json](implementation_data.json).

## Задача, которую нужно проверить отдельно

[MESSAGE_FIXTURE.md](MESSAGE_FIXTURE.md) описывает проверяемое окружение S24 на существующих Message/post. Контракт находится здесь и не применяется к внешним документам автоматически. Сначала необходимо получить реальный parser/runtime fixture, затем можно пересмотреть статус S24 и его участие в статистике.

Никакие экспериментальные имена автоматически не экспортируются в общее ядро. Если при интеграции окажется необходим новый операнд или ресивер, его контракт, полный исходник и точные цели интеграции должны сначала появиться в локальном контракте этой директории.

Согласованные `asOperand`, alist/plist и sequence-функции уже имеют полные тела и metadata общего экспорта. Обе полные клиентские формы считают все Throws и полные ссылки copy. Статистического удаления аргументов нет; общий библиотечный алгоритм и зависимости сохраняются в единственном каноническом исходнике.

## Проверка файлов

```sh
python3 tools/validate.py
python3 tools/verify_manifest.py
python3 tools/verify_manifest.py --spec-root /path/to/spec
```
Последняя команда дополнительно сверяет внешние базовые ссылки и ничего там не изменяет. Она не запускает LMX и не выдаёт проверку SHA-256 за проверку семантики.
