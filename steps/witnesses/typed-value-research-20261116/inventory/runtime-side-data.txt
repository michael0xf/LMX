## 0. Общее, что меняет почти всех вызывающих

0.1 Выравнивание дескриптора и 8-байтовых значений.
Запись = 4 байта метки, затем вплотную значение. Значит, значение 8 байт (size_t, double, указатель) и дескриптор
Structure/Array (parent/length/storage) начинаются со смещения 4 — не кратного 8.

Сейчас код обращается к полям заголовка напрямую, как к структуре: `header\parent`, `va\data`, `va\size` [код]:
- в lmx_*.lm2: `\parent` — 175 вхождений в 16 файлах, `\array` — 325 в 17;
- в выпущенном p.c (private_hidden_binding native): `->parent` — 136.

Отсюда два варианта:
- Lmx* = запись+4: обращения к полям остаются, но они невыровненные. Для x86-64 это законно на уровне машины, а в C99
  это UB при обычном разыменовании.
- Чтение копированием байтов, как сказал автор: каждое обращение к полю заголовка и к 8-байтовому значению
  переписывается через memcpy-аксессор.

Цена в машинном коде одинакова: memcpy 8 байт при -O2 — один mov [оценка]. Цена в исходниках — все места выше.
int (4 байта на +4) выровнен — его это не касается.

0.2 «Указатель на запись или адрес значения».
Смещение фиксировано (+sizeof(int)), так что одно выводится из другого вычитанием. Решать нужно не арифметику, а
договор: какой из двух адресов передают API и хранят слоты. Проблемные — адреса, которые НЕ получены из начала
записи:
- (а) элемент плотного Array<T>: M13 п.1 «числовой Array<T> хранит сами T», у элемента своей метки нет;
- (б) поле внутри дескриптора: sys\descriptor возвращает Lmx**/size_t*/void** (M13 п.5);
- (в) слот внутри storage Structure/Array<@>: адрес слота, а не запись;
- (г) внешняя C-память и сырой L2-указатель;
- (д) служебная память операций: scratch, строки активации, LmxWalkValue.
Для них метки нет; сейчас на них отвечает интервал. Где это важно — помечено ниже как «решение (0.2)».

### Для чего читаются поля
[код]
- Загрузка ссылки (lmx_walk_value_load:1044-1097):
  - lmx_value_loaded_context(context, raw) берёт контекст, ТОЛЬКО если context\ref == прочитанному указателю — это

  - `references` — отдающее пространство имён, в котором разрешаются имена модели (lmx_implements.lm2:3143,

    pool\scalar_abi/type/profile; lmx_walk_value_scalar_storage:486- проверяет совпадение контекста с пулом;

  - указатель: model, references, referent — через обратную карту context_cell_in.

### У каких ячеек контекст всегда пуст
[код] Пустой — нулевой, или с ref и без model/references/referent:
- uninit:T: lmx_graph.lm2:lmx_graph_uninit_int:401-415 пишет lmx_arena_pointer_void_write напрямую, минуя cell_fill;
- ячейки, записанные lmx_pointer_store_in(…) с context 0 — там model/references/referent = 0;
- все GRAPH_*_REF и UNINIT_GRAPH_* чистого графа, пока в них не писали через cell_fill.
[оценка] У ячеек, в которые пишет только native-код сырыми callbacks, тоже, но поимённо это не проверено.

### Куда уходит
- model / references / referent — состояние ЗНАЧЕНИЯ-ссылки, а не места → СОДЕРЖИМОЕ записи ссылочного типа.
  Решение: запись «ссылка» с полями {ref, model, references, referent} = 4+32 → 40 Б, или отдельный вид метки
  «ссылка с моделью», когда model ≠ 0 [оценка]. Утверждённого удаления нет: M13 «Exact scalar ABI и owned Value»
  требует, чтобы copier/qualification/GC сохраняли Model/references/companion/referent.
- referent указывает на запись указуемого → обратная карта lmx_value_context_cell_in исчезает: владелец = сама
  запись [оценка].
- present / kind / ref контекста — копия значения ячейки ради проверки свежести → исчезают, если контекст лежит в той
  же записи и пишется вместе со значением [оценка].
- scalar_abi / type / physical_profile у FOREIGN → МЕТКА: код строки ABI (см. d); неизменяемость — знак метки.
  Повтор «пул ↔ контекст» исчезает.

### Смысл
[код] steps/qualifier-receivers-20261010.md:30-54. Профиль — узел-корень КВАЛИФИЦИРОВАННОЙ ветви
(`independent: immutable` и eternal):
- пролог делает узел профиля l2_eprofile<k> и строит ветвь в пулах этого профиля, затем
  lmx_qualify_tree_preflight_full и запечатывание;
- неизменяемость = «у пула ненулевой профиль и пул запечатан»;
- eternal = вдобавок корень профиля с parent = 0: merge его удерживает (lmx_copy_retained_profiles);
- квалификация во время исполнения (RR2a) — copy или merge в целевой профиль, затем seal.
Норма, которой введено: L2 §3 type-by-range — обычные и неизменяемые в разных участках; kernel spec §2.2 —
`lmx:immutable`, `lmx:result`.
Переход уже начат: неизменяемость как отрицательный физический тип (lmx_type_immutable:60-66). Комментарий в
write_overlaps_profile: «Physical immutable type protects live bytes even before a seal», а legacy-конструкторы
положительных семейств пока держат охрану по профилю.

### Сколько профилей в арене
[оценка по тексту]
- 0 — обычные;
- по одному на каждую статическую квалифицированную ветвь единицы (пролог);
- по одному на каждую квалификацию во время исполнения.
Каждый профиль умножает число пулов: на каждый (kind, type), встретившийся в ветви, — свой пул.

### Куда уходит
Утверждено: §9 «LmxPool.role/profile/sealed … → физические виды — участки заголовков (§2.2, L2 §3); роль
определения — слово головы» — снять. В записи:
- неизменяемость → МЕТКА: знак или бит, как lmx_type_immutable. Проверка записи — одно чтение метки по указателю
  записи, без интервалов;
- role FN (`lmx:result`) → МЕТКА: свой вид заголовка, §2.2;
- eternal → СОДЕРЖИМОЕ: parent = 0 у корня, как и сейчас;
- «принадлежит ли ячейка ветви корня R» (has_root_profile, точный профиль, immutable_roots в native-проверках) →
  УДАЛЕНИЕ вместе с профилями (§9). Ветвь при квалификации копируется в неизменяемые виды, и каждая её запись несёт
  свою метку [оценка];
- байтовый барьер write_overlaps_profile — запись через сырой указатель в середину неизменяемой ячейки. У байта внутри
  записи метки нет. → УДАЛЕНИЕ: «на L2 вообще никаких проверок нет» (автор 2026-11-16, LMX_blog/2026-11-16.md),
  M13 п.3 «без проверок length/знака/арены/бывшего поля».

## c) LmxRange: links, holder, slot_owner, side_cells/side_stride

[код] lmx_range.lm2:800-1178, «side storage of an interval» (срез 253, design 4.4).

Размер side-массивов и копия stride/kind пула на момент вставки: при снятии интервала запись пула уже может быть
освобождена.
- Снятие: lmx_range_side_free:1020, descriptors_retire:1088, side_drop:1136, side_release:1167.
- При attach side-данные переезжают вместе с записью индекса: lmx_arena.lm2:605-757.

### Куда уходит

- §9 «LmxCodeLink / reset-only lmx_code_*, reset_gen, code_uses и инвалидизация — удалить вместе с таблицами,

- §9 «LmxRange.links/slot_owner/holder/side_*» — снять.
Без links holder и slot_owner никому не нужны: их единственный читатель — slot_holder для rebind.

## d) pool\scalar_abi и FOREIGN-скаляры

### Строки ABI
[код] LmxScalarABI {size, init, copy} (lmx.h.lm1).
- Генерирует frontend: l2_frontend_emit.lm2:960-1015 — по строке примитивного профиля typedef, init, copy, const ABI
  и lmx_primitive_profile_scalar(row) → const LmxScalarABI*.
- Одинаковые C-написания дедуплицируются: общий ABI, но не общая семантика.
- lmx_primitive_profile_scalar_type(row) — ядровый код типа или FOREIGN.
- План M13: 32 строки с ячейкой из 35. None, void и FILE ячейки не задают.

### Как по ячейке узнаётся её ABI и размер
[код]
- Код типа ячейки = LMX_TYPE_FOREIGN (40; −40 у неизменяемой) у ВСЕХ строк.
- ABI и размер — из пула. Пул ключуется (FOREIGN, profile, stride = abi\size, abi): lmx_arena_scalar_cells_profiled
  :522-567.
- Проверка «пул ↔ ABI ↔ контекст»:
  - lmx_walk_value_load:1044-1097, ветка FOREIGN;
  - lmx_walk_value_scalar_storage:486-;
  - lmx_walk_value_foreign_capture:433-.
- Обратно ABI → ядровый тип: lmx_graph.lm2:lmx_graph_scalar_type:850-864 — линейный проход по строкам профиля.

### Хватит ли кода типа в метке
Сейчас НЕТ: код 40 одинаков для 32 строк. Нужна метка «FOREIGN + номер строки» или id ABI. Тогда таблица
«тип → {size, init, copy}» — это уже сгенерированная lmx_primitive_profile_scalar(row), новой таблицы не нужно.
Для ядровых типов размер определяется кодом.

### Куда уходит
МЕТКА (код строки) + существующая сгенерированная таблица строк. pool\scalar_abi, контекстные scalar_abi и
physical_profile, проверки совпадения — исчезают.
[оценка] Если все 32 строки — POD-скаляры, copy сводится к memcpy(size), а init — к записи нулевого значения. Это
согласуется с «читаются копированием байтов»; отдельные callbacks остаются только ради семантики, а не хранения.

- Каждый p.c объявляет 102 функции `l2_u…_pcN_write(void *cell, void *value)` — по одной на тип указателя
  единицы. В e1_const_index p.c они НЕ определены и НЕ используются (grep).
- Фактически физических ABI два — `void *` и `char *` — плюс вариант charptr.

### Зачем
Точный C-объект ячейки при -fstrict-aliasing: ячейку `char *` нельзя читать как `void *`. В gc_cells: «A machine T *
cell is not a void * object».

### Куда уходит
Исчезает как следствие раскладки, а не по пункту плана. Если «метка и значение читаются копированием байтов»,
указатель = memcpy 8 байт с записи+4, и тип C-объекта ячейки не нужен. Отпадают:
- pointer_read и pointer_write;
- выбор в lmx_value_cell_access;
- проверка canonical;
- 102 объявления в каждом p.c.
Вызывающих (load, store, GC, copy, list) нужно переписать на memcpy.

пока жив чанк.

### Куда уходит
ТАБЛИЦА — новая, но уже утверждённая M13 п.2:
- «таблица "адрес дескриптора → capacity" в элементах; не добавлять capacity в Lmx, скрытый префикс или отдельное
  семейство VoidDynamicArray»;
- «Structure, Array<@>, Array<T> и служебные массивы используют общие выделение и изменение length/capacity»;
- «storage может перемещаться»;
- S8.2 — «удалить отдельное DynamicArray-хранилище capacity».
Что исчезает: пул на Structure, FIELD_ADDRESSES, slot_owner, holder, отдельный рост List.

[оценка] В нетипизированной арене storage — один кусок:
- Structure и Array<@>: n×8 указателей на записи;
- Array<T>: n×sizeof(T) — сами T, без меток (M13 п.1).
Решение (0.2а, в): есть ли у самого storage метка («backing T[n]»), или storage — память без метки, тип которой
известен только из дескриптора.

4. Где рёбра внутри записи. Сейчас по виду пула.

- Пометка и освобождение на выбор [оценка]:

  - (б) битовая карта куска со смещением/8 — §2.4 kernel spec: «битовая карта живых ячеек» на участок.
- Проход «блок → все пулы → все чанки» исчезает вместе с пулами.

## i) mark / revert (откат построения)

[код]
- lmx_arena.lm2:lmx_arena_mark:305-313 = голова списка блоков (стек).
- lmx_arena_revert:315-338 = lmx_arena_drop каждого блока после метки:
  - снимает интервал;
  - отцепляет чанк от пула;
  - пул целиком, если его запись в этом блоке;
  - плюс lmx_arena_impl_prune.
- Ячейки, взятые после метки из чанка, существовавшего ДО неё (used увеличен), revert НЕ возвращает: used не
  восстанавливается.
- На практике это почти не возникает:
  - рост идёт новым чанком на ячейку (chunk_capacity 1);
  - List ради отката делает свой пул (lmx_list_owned.lm2:~186 «A fresh backing descriptor lets local failure revert
    only new blocks»).

### Что потребуется для bump-кусков
Метка = (голова списка кусков, текущий кусок, смещение в нём). Откат:
- освободить куски после метки и снять их интервалы в индексе кусков;
- вернуть смещение текущего куска.
Это прямо требует §2.3 kernel spec: «освобождая присоединённые с метки участки и возвращая used прежних». Временные
таблицы операции — как сейчас (impl_prune).

### Куда уходит
Ни одна из четырёх категорий: это состояние куска арены, а не записи. Таблица — индекс кусков.

## Опись №1 → чтение метки. По одной строке на место
Обозначения:
- «БЕЗ ИЗМЕНЕНИЙ» — заменяется чтением метки по указателю из слота, вызывающий код не меняется;
- «РЕШЕНИЕ» — нужно решить, что держит вызывающий (запись или запись+4), либо вызывающий читает не тип.

- lmx_range_type_of — БЕЗ ИЗМЕНЕНИЙ для адресов из слотов (начала записей); РЕШЕНИЕ для адресов значения,
